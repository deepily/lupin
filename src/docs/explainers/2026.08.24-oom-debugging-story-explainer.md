# Six lines that ate 229 gigabytes — how we found the wrong culprit three times

**What this is**: the story of a four-day hunt for a memory bug, told in the order we actually
believed things rather than the order that would make us look good. **It has an ending, and the
ending is good**: a named cause six lines long, a fix we can enforce mechanically, and — the part
that outlives this bug — a way to cap the blast radius of the *next* one without knowing what it is.
The last third is the part worth keeping: §8 is what each wrong turn cost, §9 is what we walked away
holding, and §11 is the recipe for doing it again in an evening instead of four days.

**Audience**: anyone who wants to tell this story, and anyone about to debug something intermittent
under time pressure. No prior context needed.

**Source**: rows `32c58572`, `cd332d2b`, `5641d306`, `1ebc9be3`; commits `3fa9ed23`, `e0dd538c`;
`src/rnd/v0.2.0/2026.08.24-oom-allocator-named-happy-dom-assertion-diff.md`;
`src/rnd/v0.2.0/2026.08.24-oom-analysis-response-to-ts-runner-survey.md`;
`src/rnd/v0.2.0/2026.08.23-typescript-test-runner-oom-hazard.md`;
`src/rnd/v0.2.0/2026.08.23-plausible-and-wrong-seven-vacuity-shapes.md`.

## 1. The one-paragraph version

Over three days, machines died. We called all of it "the OOM," banned the test tier we thought was
responsible, condemned a worktree, and wrote a standing rule that turned out to contain a false
sentence. The real cause is that `node:assert`, when an assertion **fails**, builds a human-readable
diff by deep-inspecting the value you gave it — and if that value is a happy-dom element, the walk
goes `element → ownerDocument → defaultView → the entire browser Window`, and never finishes. Memory
climbs at about 2.5 GB per second until the kernel intervenes. The tier was never the problem. **A
failing assertion holding a DOM node was the problem** — which is precisely the state you are in
while fixing a broken test.

---

## 2. What we thought we had: one monster

Three violent events inside three days, all filed under one heading:

| | 2026-08-21 | 2026-08-22 | 2026-08-23 (×2) |
|---|---|---|---|
| Seats lost | 3 | ~2 dozen | 1 each |
| Killer | *(assumed OOM)* | kernel `oom-kill`, global | `systemd-oomd`, slice PSI 74.8% |
| Locus | *(assumed the tier)* | **one process**, 229 GB `anon-rss` | **a slice**, 30–52 processes |

Filing them together felt like diligence. It was the first mistake, and it made every subsequent
piece of evidence harder to interpret, because evidence that fit one column was read as evidence
about all three.

---

## 3. Three wrong culprits, in order

### Culprit 1: `dismiss_sessions` — the reaper that wasn't

On 08-21, three worker seats vanished inside one minute. A peer manager had run `dismiss_sessions`
in that same minute, and its result named exactly its own three sessions. Suspicion landed there and
sat for three days: *maybe the reap kills more than it reports.*

**What actually happened**, found by reading the kernel log rather than reasoning about the tool:
`/var/log/kern.log.1` contains **zero** OOM-kill lines on the 21st and **48** on the 22nd. So the
08-21 event was never an OOM at all. A worker had run `pkill -f "pytest src/tests/unit"`; the CLI's
own shim refused that pattern by name; the worker then hand-rolled
`ps -eo pid,args | grep … | while read p; do kill $p; done`, which walks straight past the shim. **A
seat's argv contains its entire spawn brief**, so a grep for a test path matches *live sessions*. It
killed two peers and then itself.

The tell nobody could explain — one seat survived — has a flat answer: **his process arguments did
not match the pattern.**

### Culprit 2: the TypeScript tier

The 08-23 pair genuinely involved a Node test runner, so the tier was banned at all four of its
doors — `npm test`, the runner script, the all-tests script's slot, and the API's `["all"]`
expansion, which silently includes the tier without anyone typing its name. Two seats had died; the
ban was the right call **on the evidence available**.

It also stayed too wide for too long, because the ban named a *command surface* rather than a
*mechanism*, and a rule shaped like a blocklist cannot tell you when it no longer applies.

### Culprit 3: the condemned worktree

One worktree was condemned as possibly-poisoned. Reasonable — until the bug reproduced in a clean
`/tmp` lab with fresh `node_modules`. **Quarantining that tree would have fixed nothing.**

## 4. The experiment that settled it — and why its *shape* was the whole argument

Two days before the answer, a reviewer proposed copying the fatal files somewhere clean and running
them. **It was refused**, on a specific ground: `systemd-oomd` kills the *worst* cgroup, not the
*guilty* one, so the experiment could take an uninvolved colleague's seat.

The version that ran was not a reversal of that refusal — it was the refusal's objection answered:

```bash
systemd-run --user --scope \
    -p MemoryMax=6G -p MemorySwapMax=0 -p RuntimeMaxSec=120 \
    --slice=oomlab.slice -- node --test …
```

The run gets **its own ceiling**, so it dies against its own limit instead of becoming fleet
pressure. And that containment was not assumed — a second worker watched the box independently and
measured it: **three kills in 68 seconds, each at ~6.25 GB, nothing outside the slice touched.**

> **The lesson is not "we should have run it sooner."** The first proposal deserved its refusal. The
> second deserved its approval. **What changed was the blast radius, not the courage.**

## 5. How the cause was actually named: controls, not hypotheses

The finding is not "we ran it and watched it die." It is a control matrix — four conditions, three
runs each:

| Condition | Outcome |
|---|---|
| happy-dom element + **failing** assert | **killed 3/3** |
| happy-dom element + **passing** assert | survives |
| plain object + failing assert | survives |
| no happy-dom at all | survives |

**Only the conjunction dies.** That single table is what converts a plausible story into a named
cause, and it is why the answer is trustworthy enough to change a standing rule.

Supporting measurements, all taken rather than inferred:

- RSS sampled every 250 ms: `1797 → 2418 → 3038 → 3681 → 4370 → 5000 → 5644 MB`. **Linear**, flat
  slope to the kill. Linear means *a hang plus a small per-tick allocation* — not one big grab. The
  allocator is tiny; **time** is what is unbounded.
- No V8 heap abort and no heap snapshot, even with `--heapsnapshot-near-heap-limit=1`. So the memory
  is **external**, and `--max-old-space-size` is irrelevant.

## 6. The twist: the file in the vault was already a mutant

The "fatal file" everyone had been reasoning about was **not the repository's code**. The banked copy
carried a left-over mutation from an interrupted mutation-testing run (blob `295259ce` against the
repo's `e391891e`). Reverting that one line turns a 6 GB kill into **19 of 19 tests passing in 1.44
seconds**.

Someone froze a tree mid-experiment and banked the mutant, and a faithful copy of a mutant is a
faithful copy of the wrong thing. `cmp` proves a copy is *identical*; it says nothing about whether
the original was *correct*.

The mechanical fix is three lines in the freeze script:

```bash
git -C "$tree" rev-parse HEAD      > FROZEN_HEAD
git -C "$tree" status --porcelain  > FROZEN_STATUS
git -C "$tree" diff HEAD           > FROZEN_DIFF     # this one would have caught it
```

## 7. What was actually wrong with our standing rule

The rule said: *"concurrency caps and timeouts do not mitigate this."*

Half of that was true — `--test-concurrency=1` was genuinely tried and genuinely did not help.

The other half had never been tested. **`timeout(1)` signals its direct child only**, not the process
group, and a Node process blocked in a synchronous C++ or GC frame never services `SIGTERM`. The
receipt was sitting in our own incident data the whole time: the fatal run was launched under
`timeout 300` and burned **6m28s of CPU** — 388 seconds against a 300-second ceiling. **The cap never
fired.** We had recorded the disproof and read it as a symptom.

Forms that actually enforce:

```bash
timeout --kill-after=10s 300 setsid --wait node …          # signals the whole group
systemd-run --user --scope -p RuntimeMaxSec=300 -p MemoryMax=8G -- node …   # time AND memory
```

## 8. Meta-analysis — the ten lessons, ranked by what they cost

### 1. A rule that names a *command* cannot tell you when it stops applying
The ban named four doors. The hazard was *a failing assertion holding a DOM node.* Everything the
ban blocked was a proxy for the real condition, so it was simultaneously **too wide** (119 files
dark, 98 of them unrelated) and **too narrow** (it says nothing about the same assert pattern
anywhere else). **Name the mechanism; derive the blocklist from it.**

### 2. Determinism is the discriminator — and it cuts both ways
Real contact reproduces the same way every time; noise does not. The half everyone skips: **one
green is also one sample.** On a check whose failure mode is nondeterministic, a single pass is
exactly as weak as a single fail. This is why the answer came from *four conditions × three runs*
and not from one dramatic crash.

### 3. A green mutation usually means a broken mutation
Twice in one evening a mutation "survived" and both times the mutation was the broken thing — once
because two code branches returned identical values (dead conditional), once because the tests called
a handler directly and never executed the `Depends(...)` default being mutated. **Assert that your
edit landed, in the same command that runs the test.** Then, when something truly survives, it means
something.

### 4. "I verified this myself" is not evidence — the line number is
A correction was written into a bug row claiming a class was *not* a subclass, with the words *"I
verified both line ranges myself."* It was wrong, and the quoted guard string did not exist in the
file at all. It sat for three days looking like settled forensics, and it *explained* things — which
is what made it durable. **A wrong claim that explains something is stickier than a wrong claim that
doesn't.**

### 5. Split incidents before you pool evidence
Merging 08-21, 08-22 and 08-23 into "the OOM" meant every fact had to be true of all three or be
discarded. Three different killers, three different loci. **A shared symptom is not a shared cause.**

### 6. Refuse experiments by blast radius, not by subject
The dangerous experiment and the decisive experiment tested the *same thing*. One could take a
colleague's seat; the other had its own ceiling. **"Is this safe?" is not a question about what you
are testing.**

### 7. Retract with a measurement, not an argument
Two corrections tonight were themselves corrected — including one where the person who had corrected
someone else went and sampled `memory.stat` inside his own repro's cgroup (`5,524 MB inactive_anon`
against `0 MB active_anon`, ~100%, against 08-22's 95%) and **withdrew his own distinction on the
number**. That is why 08-22 is now believed to be the same bug. A retraction backed by a measurement
advances the investigation; one backed by an argument just changes whose story is on top.

### 8. Provenance is not correctness
A banked artifact was faithfully copied and quietly wrong. Freeze the *state*, not just the *bytes*
— `FROZEN_DIFF` is three lines and would have caught it.

### 9. A guard must cover the first move, not just the workaround
The kill guard built from the 08-21 forensics denied the `ps | grep | xargs kill` form — the
*workaround* — while still allowing `pkill -f "…pytest…"`, the move that started it, and
`pkill -9 -f claude`, which matches every live seat on the box by name. **Guards get written from
the last step of the incident report, because that is the step still in your head.**

### 10. Never hand a colleague a guess in the shape of a finding
An unexplained exit code was labelled *"probably my own noise"* by someone who had a plausible
mechanism and no proof. The right form, which he then used: *"mechanism yes, finding no — I can
prove I ran the command, I cannot prove it hit your process."* **An honest unknown is more useful
than a confident answer, because the unknown keeps someone looking.**

## 9. The happy ending, stated plainly

§8 is a list of what things cost, and read alone it gives the wrong impression — that this was four
days of walking into walls. It was, and it also **ended**. Here is what we walked away holding.

### We have a name, not a shrug
The bug is not "something in the JS tier eats memory." It is: **`node:assert` deep-inspects the
actual value to build a failure diff, and on a happy-dom element that walk reaches the whole Window
graph and never terminates.** Six lines reproduce it. It dies in about five seconds, on demand, every
time. An intermittent, unattributable, fleet-killing event became a deterministic five-second test —
that is the single biggest thing that changed.

### We have a fix, and it is enforceable rather than remembered
**Never pass a DOM node as the ACTUAL value of an assertion.** Assert a primitive projection —
`tagName`, `id`, `textContent`, a count. The node can be built and inspected freely; it just must not
be the thing the assertion is holding when it fails. That is a **lint**, not a habit — a rule a
machine checks, which is the only kind this fleet has managed to keep.

### 🔴 We can cap the blast radius WITHOUT knowing the cause — and this is the real prize
The capped lane means any `node --test` run executes inside its own systemd scope with `MemoryMax`,
`MemorySwapMax=0`, and a wall clock. **A runaway now dies against its own ceiling long before it
becomes fleet pressure.** That protection does not depend on this diagnosis, or on any diagnosis: the
*next* unnamed allocator — in any language, from any dependency — is already contained.

**The happy-dom finding closes one bug. The lane closes the category.**

### The containment is measured, not believed
While the diagnostic run was hammering the box, a second worker watched it independently and counted:
**three kills in 68 seconds, each at ~6.25 GB, the cap held, nothing outside the slice touched.** We
are not asserting that the containment works — we watched it work while something was actively trying
to eat the machine.

### The tax comes off
The ban went dark over 119 JS files, 98 of them multiplexer tests with nothing to do with any of
this. Those come back.

### Every incident produced a detector, not just a rule
| Incident | What was built |
|---|---|
| A peer's stash applied into the wrong tree | `stash_guard` — 51 tests, five falsifiers, denies the mutating verbs at the hook |
| Three seats killed by a grep-and-kill sweep | `kill_guard` — 121 tests, ten falsifiers, reads `/proc/<pid>/comm` and refuses only when a live session would actually die: **5 denials in 6,513 real fleet commands, 0.08%** |
| Tests writing into the live fleet directory | a seam canary that fails loudly if a checked-in test writes to the real path |
| A future door bypassing the cap | a test pinning the funnelling, so a new uncapped door goes red |

None of those is a paragraph in a document. Each one fires.

### Nothing false survived contact
Three of the wrong claims in this story were mine. **Every one was refuted within hours by someone
who went and measured**, and the refutations were themselves refuted where they deserved it. A
reviewer took apart my central piece of evidence with a null control; an author checked a line number
and killed a "correction" I had signed *"I verified this myself"*; a worker retracted his own finding
four minutes after making it when the attribution turned out wrong. **The rate of wrong claims is not
the interesting number. Time-to-refutation is — and it was hours, in public, with receipts.**

### And nothing was lost
No work was destroyed. The condemned worktree was **cleared**, not deleted. Both endangered stash
entries survive as annotated tags. The 08-22 mystery — one process holding 229 GB — moved from
*unexplained* to *very likely the same bug at a different cap*, on a measured `inactive_anon`
signature rather than a hunch.

## 10. What changed as a result

| | Before | After |
|---|---|---|
| Diagnosis | "the TypeScript tier eats memory" | `node:assert`'s failure-diff walks a happy-dom element into the Window graph, unbounded |
| Ban | four doors, whole tier, indefinite | **capped `jstest.slice` lane, then the tier ban lifts behind it** (ruled 2026-08-24) |
| Worktree | condemned | **cleared** — reproduces in a clean lab |
| 08-22 (229 GB) | separate, unexplained | same `inactive_anon` signature; likely the same bug at a different cap |
| 08-21 (3 seats) | suspected reap tool | a worker's own unscoped kill sweep; **detector built** |
| Timeouts | "do not mitigate" | never tested; `timeout(1)` signals the direct child only |

The containment is now the control, and it does not depend on knowing what the next allocator is: a
runaway dies against its own ceiling long before it becomes anyone else's problem. **That is the part
that generalises. The happy-dom finding closes one bug; the capped lane closes the category.**

## 11. The recipe — how to do this again in an evening instead of four days

The method that finally worked is cheap, general, and has nothing to do with memory bugs. Total cost
of the run that named this one: **6 GB, about two minutes of compute, one evening.**

1. **Split the incidents before you pool the evidence.** Three events with different killers and
   different loci are three investigations. Merging them meant every fact had to be true of all three
   or be discarded.
2. **Cap first, diagnose second.** Reproduce inside a scope you can afford to lose —
   `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p RuntimeMaxSec=…`. This is what
   turns "too dangerous to investigate" into "run it and watch." It is also why the *second* proposal
   of the same experiment was approved when the first was refused.
3. **Build a control matrix, not a hypothesis.** Vary one thing at a time, three runs each. Four
   conditions is what converted a plausible story into a named cause — and the row that *survives*
   (the passing assert) is what tells you which half matters.
4. **Sample the shape over time, not just the peak.** Linear growth means a hang plus a small
   per-tick allocation; a step means one big grab. That single graph killed every remaining
   hypothesis at once.
5. **Check your artifact against `HEAD` before you reason about it.** The banked file carried a
   left-over mutation. `git diff HEAD` at freeze time — three lines — would have caught it.
6. **Falsify the instrument before you trust its clean result.** The audit hook that reported "zero
   writes" was first shown to *catch* a write when the seam was removed. A clean reading from an
   untested instrument is not a reading.
7. **Run it more than once, in both directions.** Determinism is the discriminator, and one green is
   as weak as one red on anything whose failure mode is nondeterministic.

⇒ Steps 2 and 7 are the ones people skip, and they are the two that made this tractable. **Everything
else in this document is a consequence of finally doing them.**
