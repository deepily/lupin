# Decision record: API-key authentication for the notification endpoints

**Source:** `src/rnd/v0.1.0/2025.11.10-phase-2.5-notification-authentication.md` (1,676 lines, read whole). Its status line names only the first stage, "Requirements & Acceptance Criteria". The file also holds a "Config Migration" block dated November 2025. It also holds a "Design & Technical Planning" section. It names no author and no approver.

**Status:** in force in part. The key format, the bcrypt storage and the `X-API-Key` header are built as designed. The designed 401 answers live in `require_api_key`, which no route mounts. A client receives the answers in rule 7. Four things were reversed or amended later. They are the config file path, the hardcoded default, the database engine and the dependency that guards the routes. Each is stated below.

**Checked against:** tree `d3d98a68a`. Files opened: `src/cosa/rest/middleware/api_key_auth.py`, `src/cosa/utils/config_loader.py`, `src/scripts/lupin_config.py`, `src/scripts/create_service_account.py`, `src/scripts/create_service_account_postgres.py`, `src/scripts/create_api_keys_table.py`, `src/scripts/init_test_database.py`, `src/cosa/rest/postgres_models.py` (`ApiKey`), `src/cosa/rest/routers/notifications.py` (route heads), `src/lupin_cli/notifications/notification_models.py` (recipient lookup), and the four citing test files.

## What is in force today

1. **A key is `ck_live_` followed by `secrets.token_urlsafe( 48 )`.** `generate_api_key` in both service-account scripts builds it. The accepted shape is the regex `^ck_live_[A-Za-z0-9_-]{64,}$`. The source's arithmetic is off. It counts the prefix as 6 characters and the key as 70. The prefix is 8 characters and a generated key is 72. The source also says 288 bits of entropy, and 48 bytes is 384 bits. `test_api_key_generation.py` asserts a length of at least 70. It imports only the SQLite script, so that covers that script's `generate_api_key` alone.
2. **The database holds a bcrypt hash at cost 12, and no plaintext key.** `store_api_key` in both scripts calls `bcrypt.gensalt( rounds=12 )` and stores the hash. The `ApiKey` model's docstring says the same and names the script that writes it.
3. **The plaintext key goes to a key file with mode 600, and is printed once.** `write_key_to_file` writes `src/conf/keys/notification-api-claude-code-{env}` for `dev`, `staging` and `prod`. `.gitignore` excludes `src/conf/keys/**`. The source put the staging and production files under `~/.notifications/keys/`. The scripts do not. The PostgreSQL script also survives a read-only mount: it warns and still prints the key.
4. **The client sends the key in the `X-API-Key` header.** `require_api_key` is the source's dependency, and no route mounts it. It returns the service account's user id. It answers 401 with `WWW-Authenticate: API-Key` in three cases. They are a missing header, a key that fails the regex, and a key that matches no active row. The regex check runs before any database lookup. The three detail strings start with the source's wording and add a hint. Rule 7 gives the answers a client receives today.
5. **Validation compares the key against every active row with `bcrypt.checkpw`.** `_validate_api_key_sync` reads `ApiKeyRepository.get_active_keys()` and checks each hash. On a match it sets `last_used_at` and returns the user id. The source returned an integer id from a SQLite cursor. Today the id is a UUID string and the read goes through the SQLAlchemy session from `get_db`. `validate_api_key` runs that work in a worker thread. A row whose stored hash is malformed is skipped and logged by key id.
6. **Revocation is the `is_active` flag.** Only active rows are read, so an inactive key answers 401. `ApiKeyRepository.deactivate` sets the flag. The source's `src/scripts/revoke_api_key.py` is not in the tree.
7. **The notification routes accept an API key or a JWT.** The source planned `Depends( require_api_key )` on `POST /api/notify`. That was amended. All 25 routes in `routers/notifications.py` depend on `require_api_key_or_jwt`. That function does not fall back. When an `X-API-Key` header is sent, the key decides alone. A bad format answers 401 "Invalid API key format". An unknown or inactive key answers 401 "Invalid or inactive API key". The Bearer token is read only when no key header is sent. A request with neither answers 401 with a detail that starts "Missing auth". Each 401 this function raises itself carries `WWW-Authenticate: API-Key, Bearer`. Twelve of the 25 routes also carry `require_path_identity_owner`. It answers 403 unless the path names the caller's own user. No route in the tree depends on `require_api_key` alone. I searched both spacings of that `Depends` call.
8. **There is no `/api/notify/sync` route.** The source names one, as `POST` in its requirements and as `GET` in its endpoint plan. Today `POST /api/notify` serves both modes, and its `response_requested` query parameter selects the blocking one.
9. **A service account is a user whose `roles` list holds `service_account`.** Both scripts default the email to `claude.code@deepily.ai`. They refuse to mint a key for an existing user that lacks the role. Three details differ from the source. The user id is a UUID, not an integer. The field is a `roles` list, not a `role` text column. The password hash is a bcrypt hash of a random throwaway value, not null.
10. **The "notification endpoints only" permission is planned in the source and not enforced.** The source limits the service account to the notify endpoints. The middleware checks no role. `require_api_key_or_jwt` also guards routes in `tasks.py`, `dm.py`, `arbiter.py`, `commons.py`, `voice_persona.py` and others. A valid key passes that dependency on each of them. Some routes add a further guard, as rule 7 says for the notification router. I did not count the guards in the other routers.
11. **Config precedence is environment variables, then `~/.lupin/config`. The hardcoded default is gone.** `get_api_config` uses the environment when it has a key source and a URL source. The key source is `LUPIN_API_KEY_FILE` or `LUPIN_API_KEY`. The URL source is `LUPIN_API_URL` or `LUPIN_API_KEY`, which implies `http://localhost:7999`. Otherwise it reads the file. A missing file raises `FileNotFoundError` that names `lupin-config init` and `lupin-config migrate`. The source's third level, a fallback to `localhost:7999` and the dev key, was removed. The source names `LUPIN_API_KEY` once, in its Cloud Run section, as a secret environment variable. Its precedence list and its loader design do not name it.
12. **Inside `get_api_config` the environment is the `env` argument, then `LUPIN_ENV`, then `[environments] default`, then `local`.** This matches the source. In practice the `default` key is not reached by the notify clients. Outside `lupin_config.py` and the loader's own smoke test, ten non-test call sites call `get_api_config`. Each passes the value of `LUPIN_ENV` with a fallback of `local` as `env`. So `lupin-config use` changes nothing for them. When the environment-variable branch of rule 11 fires, the `env` argument is ignored. An environment name that is not a section raises `ValueError`.
13. **The config file is `~/.lupin/config`. The source's migration to `~/.notifications/config` was reversed.** The source calls `~/.lupin/config` deprecated and `~/.notifications/config` current. `config_loader.py` reads only `~/.lupin/config`. `lupin-config migrate` merges `~/.notifications/config` and `~/.lupin/credentials.ini` into it. It skips a section the unified file already has. When at least one section was migrated, it renames the old files to `.bak`. When none was, it returns before the rename. `history/2026-03-03-to-12-history.md` records the swap in session 337c of `2026-03-10` and the removal of the fallback in session 339 of `2026-03-11`.
14. **The recipient key is `global_notification_recipient`, and the old names are gone.** `get_api_config` returns it when the section has it. The config key `target_user` is no longer read. `LUPIN_TARGET_USER` and `LUPIN_NOTIFICATION_RECIPIENT` appear in no tracked `.py` or `.sh` file. The recipient lookup in `notification_models.py` is explicit value, then `LUPIN_DEV_EMAIL`, then the config key. The API parameter and the CLI flag are still named `target_user`, as the source intended.
15. **Each environment section needs `api_url` and `api_key_file`.** `get_api_config` raises `ValueError` when either is missing or when `[environments]` is absent. `validate_api_config` checks that the URL starts with `http://` or `https://`, that the key file exists and that its content matches the key regex. The source also requires an absolute key-file path. The code does not check that.
16. **`lupin-config` has the six planned commands and a seventh, `migrate`.** `init` writes `~/.lupin/config` with mode 600, a `[local]` section and a `[lupin]` credentials placeholder. The placeholder email is `claude.code@lupin.deepily.ai`. `add` takes `--url`, `--key-file` and `--description`, or prompts. `test` is built in part. It checks the config and the key file. Its network and authentication steps print "not implemented" and are skipped.
17. **The `api_keys` table exists in two forms.** `create_api_keys_table.py` creates the source's SQLite table and its four indexes in `lupin-auth.db`. Its `user_id` is `TEXT`, where the source has `INTEGER`. The server reads the PostgreSQL `ApiKey` model. That model has UUID ids and `ON DELETE CASCADE`. Its table metadata holds six indexes on three columns. Three are named in `__table_args__` and three more come from `index=True` on the same columns. It has no composite `user_id, is_active` index. `create_service_account_postgres.py` says it replaces the SQLite script. Both scripts remain in the tree.
18. **`init_test_database.py` builds the SQLite auth schema for a test database.** It refuses to run unless `app testing` is true. It calls `init_auth_database` and then runs `create_api_keys_table.py` as a subprocess. The citing integration test does not use that path. It creates its user and key through the PostgreSQL repositories.

## Still open or not decided

- **Whether `last_login_at` is updated on key authentication.** The source's field list says so. The middleware sets `last_used_at` on the key and does not name `last_login_at`.
- **The performance criterion.** The source asks for under 50 ms of authentication overhead. The same source estimates 100 to 200 ms for one bcrypt check. The middleware checks every active key. I measured nothing.
- **The Cloud Run section.** Secret creation, secret mounting, the Dockerfile mount point and the five rotation steps were not checked against the tree.
- **The documentation and deployment criteria.** The source ticks every acceptance criterion. I checked only the ones the rules above name.
- **The middleware's own smoke test.** `quick_smoke_test` in `api_key_auth.py` calls `get_auth_db_connection`. The module does not import that name. I read this and did not run it.
- **The SQLite scripts' standing.** Nothing I found says whether `create_service_account.py` and `create_api_keys_table.py` are still wanted or left over.
- **Where `lupin-config` is installed.** The source names a path in a home directory. That is outside the tree and I did not look.
