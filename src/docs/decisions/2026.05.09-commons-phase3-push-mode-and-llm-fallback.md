## What is in force today

1. **Push mode for `commons_ask_async` is planned in the source and reversed.** The source's first work item describes it. So do its questions 2 to 4 and 8, its threats 1 and 3 to 8, and its criteria 1 to 5. The later document is `src/rnd/v0.1.8/2026.06.13-cosa-voice-token-reduction/03-phase4-legacy-commons-dm-retirement-proposal.md`. Its status line records Rick choosing a full retirement on `2026-06-15`. Its section 9 records a second ruling by Rick the same day, which changed the full delete to a comment-out. Commit `5ce5dba54` of `2026-06-15` is that comment-out. Commit `756336306` of `2026-06-17` deletes the watcher, its two unit test files and the smoke test. Neither commit is an ancestor of this tree. This tree's history has the squash `53fef4192` of `2026-06-19`, which deletes the smoke test and one watcher test file. No commit in this tree's history touches `src/cosa/rest/commons_question_watcher.py`. The lines of the proposal that I read name no ruling for the deletion of `2026-06-17`.
2. **`commons_ask_async` is polling only.** `ask_async` in `commons_ask.py` posts the question and returns `question_id` and `posted_ts`. It makes no HTTP call and reads no INI key. It has no `ttl_seconds` parameter, which the source's question 4 planned. The caller reads the topic and filters on `metadata.in_reply_to`. `ask_sync` is unchanged, as the source's criterion 5 required.
3. **The pieces of the push-mode item that are absent from the tree.** `src/cosa/rest/commons_question_watcher.py` is not tracked. `routers/commons.py` has no `register-question` route. The lifespan in `main.py` starts no question watcher. The listener's `_handle_action` has no `commons_answer_received` branch. No tracked `.py`, `.js` or `.ini` file under `src` contains the string `COMMONS PEER REPLY`. The unit tests for criteria 16 to 20 and the smoke test for criterion 13 are not tracked.
4. **`CommonsTopicWatcher` is the shared base for commons topic watchers.** This is the source's question 1 and the first half of criterion 8. The base owns the daemon thread through `start`, `stop` and `_run_loop`. It owns a `threading.Lock` and the `_in_flight` dict. `start` is idempotent and seeds the cursor once. `_run_loop` calls `tick()` every poll interval and survives an exception from `tick()`.
5. **The base's registry primitives are protected and lock-guarded.** `_register( record_id, record )` prunes expired entries, then inserts, and raises `ValueError` on a duplicate id. `_unregister( record_id )` pops and is silent on an unknown id. `_prune_expired_locked( now_monotonic )` requires the caller to hold the lock. Each record must expose `expires_at_monotonic`. The source's criterion 8 gives the signature as `_register(record_id, user_id, ttl_seconds)`. The code takes a ready-made record instead.
6. **A subclass supplies four things.** It supplies a record class, a public API with domain names that wraps `_register` and `_unregister`, `_initialize_last_seen_ts()` and `tick()`. The base raises `NotImplementedError` from the last two. The base's docstring still names `register_question` as an example of a public API. No method of that name exists in the tree.
7. **Mutation happens under the lock and dispatch happens outside it.** This is the source's threat 6. The base docstring states it as a contract. `CommonsAckWatcher.tick` follows it: it looks up and counts under the lock, then pushes after releasing it.
8. **Two subclasses exist, and neither is the one the source planned.** `CommonsAckWatcher` keeps `register_broadcast`, `unregister_broadcast` and `is_in_flight`. It re-raises a collision as `ValueError` with a broadcast-specific message. `CommonsActivityWatcher` came from a later design. It uses the base for the thread only and leaves `_in_flight` empty. The `Question` subclass of question 1 does not exist.
9. **The persona matcher falls back to an LLM on a mechanical miss.** This is the source's second work item. `match_persona` tries the normalized exact match first and then calls `disambiguate_via_llm`. That function delegates to a singleton set by `configure_llm_disambiguator`. With no singleton, or an empty candidate list, it returns `None` and makes no LLM call.
10. **The lifespan installs the disambiguator when commons is enabled.** `main.py` builds `CommonsLlmDisambiguator( config_mgr )` inside the `commons enabled` block and installs it. A failure there prints a warning, and the matcher stays without a fallback.
11. **The primary model is a local Phi-4 and the Haiku fallback is a stub.** This is question 5 and criterion 7. The client comes from `LlmClientFactory.get_client`, called with the value of `llm spec key for commons persona disambiguator`. That value is `Deepily/kaitchup/Phi-4-AutoRound-GPTQ-4bit`, which is not itself an INI key. So `get_client` falls to `_get_vendor_specific_client` and returns a `CompletionClient` for the `vllm` vendor. The model name sent is the whole value. Other spec entries in the INI name the served model as `kaitchup/Phi-4-AutoRound-GPTQ-4bit`, without the first segment. Whether the server accepts the longer name was not measured. The client is built on first use and kept. `_fallback_via_haiku` raises `NotImplementedError`. The caller catches that and returns `None`.
12. **The fallback is routed to on four exception types.** They are the builtin `TimeoutError`, `XMLParsingError`, `ValidationError` and `ValueError`. The source's criterion 7 names timeout and parse error. The sample code in the source's section 8 returns `None` directly and does not call the stub. The code follows criterion 7.
13. **The request is sanitized at the model boundary.** This is threat 2 and the request half of criterion 6. `PersonaDisambiguationRequest` runs `_t2_sanitize` on `ambiguous_reference` and `context` before validation. A character with a code point below 32, other than newline or tab, raises `ValueError`. Carriage return is rejected by that test. DEL (0x7f) and 0x85 are accepted. The characters `&`, `<` and `>` are escaped, ampersand first. `ambiguous_reference` is 1 to 256 characters and `context` is optional and at most 2048. Both lengths are measured after escaping, because the sanitizer runs before the field checks. An ampersand counts as five characters: 51 of them pass as a reference and 52 fail. A request that fails validation makes `disambiguate` return `None`.
14. **The request serializes to a nested persona envelope.** `to_xml` wraps one `<persona>` block per entry, each with `<name>` and `<icon>`, inside `<active_personas>`. It then writes `<ambiguous_reference>`. It writes `<context>` only when context is not `None`. The root tag defaults to `commons_persona_disambiguation`. The method overrides the base class's `to_xml`, which the source did not plan. Persona names and icons are escaped there but not checked for control characters.
15. **`PersonaInfo` is a plain Pydantic model with length bounds.** `name` is 1 to 64 characters and `icon` is 1 to 8. The source's section 8 sketches it as a `BaseXMLModel` and types `active_personas` as a `ClassVar`. The code uses `BaseModel` and an ordinary `List[ PersonaInfo ]` field.
16. **The response model bounds confidence and treats an empty match as no match.** `confidence` must be 0.0 to 1.0, or validation fails. An empty or whitespace `matched_persona` becomes `None`. The code adds a 64-character cap on `matched_persona` that the source does not list.
17. **The answer must be an active persona and must reach the confidence floor.** A `matched_persona` that is not among the `active_personas` names returns `None`. A confidence below the floor returns `None`, and a confidence equal to the floor is accepted. The floor comes from `commons llm disambiguator confidence floor`, with a code default of 0.7.
18. **The configured timeout is handed to the client call.** The value comes from `commons llm disambiguator timeout seconds`, with a code default of 5.0. The code calls `client.run( prompt, timeout=... )`. The source's sample calls `client.invoke`. On the shipped path the timeout is honoured. `CompletionClient.run` passes it to `LlmCompletion.run`. That method sets one deadline for the whole call and turns a `requests` timeout into the builtin `TimeoutError`. `ChatClient.run` has no `timeout` parameter and does not use one. The source says the function raises nothing publicly. That does not hold. `LlmCompletion.run` catches only the `requests` timeout, so a `requests` connection error escapes `disambiguate`. So does any answer that is not HTTP 200, which `LlmCompletion.run` raises as a bare `Exception`. The class docstring admits the transport error and cites a task-store row (`id=abe4188d`).
19. **The prompt is one string.** `_SYSTEM_PROMPT` has the same words as the source's outline, without its backticks. The code joins it to the request XML with a blank line and sends the result as one prompt. The source describes a system prompt with the XML as user content.
20. **The decision log is a `print` gated by an INI key.** This is threat 7. The switch is `bool( config_mgr.get( ... ) )` on `commons llm disambiguator log decisions`, with no `return_type`. `ConfigurationManager.get` returns a string by default. So any non-empty value turns the log on, the text `False` included. The log is off only when the key is absent or empty. The INI file sets `True`. The unit tests use a stub that returns Python booleans, so they cannot see this. It prints the outcome, the match, the confidence, the persona count and the reference. The outcomes are `accepted`, `below-floor` and `whitelist-miss`. It carries no timestamp, which criterion 6 listed. The splainer entry says "Default True" and lists a timestamp, and the code has neither. The failure paths print only under `debug`.
21. **There is no result cache.** This is question 6. `commons_llm_disambiguator.py` holds no cache of answers.
22. **The live call passes no context and a placeholder icon.** `disambiguate_via_llm` builds each `PersonaInfo` from a display name and one fixed icon. It calls `disambiguate( personas, input_str )` with no `context`. It is the only non-test caller of `disambiguate`.
23. **Ten of the source's keys remain in `lupin-app.ini`, and Python reads four.** They are the spec key, timeout, confidence floor and log switch. Each arrives as a string. All ten keys sit in the `[Lupin: Baseline]` section. Each key name appears once in the file, so no other section overrides one. `commons llm disambiguator fallback model name` is named by the constant `_KEY_FALLBACK_MODEL`, which nothing reads. No Python file names the other five. Three belong to the question tracker. They are `commons question tracker ttl seconds`, `commons question tracker per user max` and `commons question tracker global max`. Two belong to the register call. They are `commons ask async push mode enabled` and `commons api base url`.
24. **`commons_answer_received` is still an accepted notification type.** It is in `valid_types` in `routers/notifications.py`, as criterion 10 planned. `notifications.js` still checks for the title `action:commons_answer_received`. No tracked code under `src` sends it.
25. **The integration file for criterion 15 is tracked and skipped whole.** `test_commons_ask_async_push_integration.py` carries a module-level `pytest.mark.skip`. Its comment says the file is kept so it can be restored if the routes return. `test_commons_ac14_registration.py` now asserts that the two `register-question` routes are not registered.
