## What is in force today

1. **A pause is an in-memory override of the INI key `fcm wake push enabled`.** It goes through `set_config` on the process-wide ConfigurationManager. That changes memory only, and the INI file is never written. The source quotes Rick's voice message of `2026-09-29` asking for this. He asked for "a transient value on that key" that is never "serialize[d] ... to the local file system".
2. **The wake service re-reads the live key on every call.** `FcmWakeService.maybe_send_wake` returns `"disabled"` when the service cannot send at all. It then reads `fcm wake push enabled` and returns `"paused"` when that is false. The check sits before the live-mobile-WebSocket check, the debounce and the token lookup, so a paused server does none of that work. A delayed trailing wake re-enters `maybe_send_wake`, so a pause also stops a wake already scheduled. A send returns `"submitted"`; the source's test table writes `"sent"`.
3. **The door is two admin-only routes.** `POST /api/fcm/push-pause` takes `{ paused, minutes? }`. `paused: true` pauses and `paused: false` resumes now. `minutes` must be 1 to 1440, and a value outside that is a 400 with nothing changed. `GET /api/fcm/push-pause` returns `{ paused, resumes_at, set_by, set_at, push_enabled }`. `push_enabled` is the live key, a field the source's read-back table did not list. Both routes need the admin role. Revision 1 replaces the original design's route name (`/api/fcm/wake-enabled`, with an `until` clock time).
4. **At most one resume timer exists, and a resume restores the boot-time value.** A second pause cancels the first timer before arming its own. An explicit resume cancels the timer. A timed or explicit resume puts the key back to the value it had when the controller was built at startup. It never writes a hard-coded `True`, so a server configured off in the INI stays off.
5. **A restart ends a pause, and that is deliberate.** Nothing is persisted. The source records Rick's ruling of `2026-09-29` about 17:52 EDT ("Transient, as you said"). The source says Mr. Radio's sanity check proposed persisting `resumes_at` and María recommended it too. At shutdown the lifespan calls the controller's `shutdown()`. That cancels the timer and prints a line when a pause is still active.
6. **The controller must be built at startup.** `main.py` calls `init_controller( config_mgr )` before the queues are made. The boot value it captures is therefore the INI value. `get_controller()` builds one lazily when startup did not. That value equals the boot value only if nothing has set the key yet.
7. **The one Firebase send is `messaging.send` in `fcm_wake_service.py`.** In this tree no other non-test Python file calls it. The source's claim that every push goes through one function holds as of this tree. It is a fact about the code at one time, not a rule the code enforces.
8. **A per-person pause is not built.** The source says "Rick: not now". The check would move from the global key to a per-user lookup by `user_id` in `maybe_send_wake`. The controller keeps one global state and takes `user` only as the actor's label.
9. **A phone client exists.** `lupin-mobile` has a `PushPauseRepository` that reads `GET /api/fcm/push-pause` into the five fields above. Its focus-mode screen has a section that uses it. The source left the phone toggle and a voice phrase as "a client of the endpoint, built after it". I read the first 60 lines of the repository file and one grep of the screen.

## What the citing file relies on

`src/cosa/rest/fcm_push_pause.py` is the only code file with a `Design:` line for this source. Its docstring relies on rules 1, 2, 4 and 5. It states that the ConfigurationManager is a process-wide singleton and that `set_config()` changes memory only. It states that a pause sets the key false and may arm a timer. It states that nothing is written and nothing survives a restart. It states that the other half lives in `maybe_send_wake`. Each statement is held above.
