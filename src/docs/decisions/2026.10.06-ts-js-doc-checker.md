## What is in force today

1. **The checker is two parts.** A Node script extracts comments with the TypeScript compiler. The existing Python text rules run over what it extracts. The source's verdict gives the reason: one copy of the rules, and no TypeScript lexer in Python. The parts are `ts_doc_extract.mjs` and `tsdoc_lint.py`.
2. **The extractor walks the parse tree.** `extractFile` calls `ts.createSourceFile`. `collectRanges` reads the leading and trailing comment ranges at each node. The source rejects a bare scanner because it cannot tell division from a regular expression literal. Tests named "golden" cover a regular expression, a division, a template literal, strings and an HTML-style comment.
3. **The extractor's JSON Lines output is the contract between the parts.** Each file gets one file record with `kind`, `file`, `ts_version` and `parse_errors`. Each comment gets a record. Its fields are `kind`, `file`, `text`, `start_line`, `end_line`, `symbol_key`, `directive`, `commented_code`, `tags` and `ts_version`. The `kind` value is `jsdoc`, `block`, `line-run` or `trailing`. Text line i sits on file line `start_line` plus i. The source's section 6 list omits `commented_code`, and its section 5 table names it.
4. **A symbol key is `<file-header>`, or kind, dotted owner and ordinal, or null.** `buildRecords` joins three parts with a bar character. They are the compiler's kind name, the owner chain and a running count. A directive comment gets no key and takes no ordinal. A tag record holds `tag`, `type`, `name` and `raw`. The source's section 6 lists three tag fields, and its section 4 status paragraph adds `raw`.
5. **A JSDoc block gets every rule.** `_jsdoc_findings` calls `lint_text` with the structure rules and the model-order rule on. It adds the `Design:` path check when a root is given. It adds a `docstring-length` finding above `DOCSTRING_MAX_LINES`.
6. **A line run, block or trailing comment gets a reduced set.** `_plain_findings` runs the emphasis, tic and history rules. The history rule runs without its model-order check. The sentence, reference and length rules are not applied. The source recommends in question 1 the split that `comment_lint.py` applies to Python comments. The two sides differ in one place. `comment_lint.lint_source` calls `history_findings` with its default, so the Python side runs the model-order check. `_plain_findings` passes `agent_rule=False`, so the TypeScript side drops it.
7. **The file header run also gets the summary rule.** The test is `kind` equal to `line-run` and `symbol_key` equal to `<file-header>`. The source's question 10 asks this for test file headers. The code applies it to the header run of any file in scope.
8. **The model-order rule fires on JSDoc and not on other comments.** That is the first option of the source's question 2. The source says no client code registers text that a model reads. `tsdoc_lint.py` has no counterpart of `is_tool_registered`.
9. **The thresholds are the Python ones.** `tsdoc_lint.py` imports `DOCSTRING_MAX_LINES` from `rule_lists.py`. The other limits reach it through the shared `text_rules.py` functions. `rule_lists.py` holds 90, 25, 6 and 40, the four figures in the source's question 6.
10. **A directive comment gives no findings.** The extractor's `isDirective` sets the flag, and `lint_comment` returns an empty list for it. The pattern is anchored at the start of the comment body. The same words in the middle of prose are prose, as the source's section 5 asks. The code's pattern covers more forms than the source lists, among them `v8 ignore`, `@ts-check`, bundler purity marks and `@preserve`.
11. **A line run that is commented-out code gives no findings.** The extractor's `looksLikeCode` parses the whole run as a script. It is code when the parse has no diagnostics and holds a call, an assignment or a declaration. This is the revised predicate in the source's section 5. `lint_comment` applies the skip to a `line-run` record and to no other kind.
12. **`tsdoc_lint.py` masks shapes that Python docstring text cannot have.** `mask_jsdoc` and `_mask_tag_at` blank four things. They are the tag word, a balanced type in braces, the name after a named tag, and a `{@link ...}` span. The link pattern also matches `linkcode` and `linkplain`. The result keeps its length and its line breaks. An opening brace that does not close ends the masking after the tag word.
13. **A shape both languages can hold is not masked on the TypeScript side.** The source quotes Cheech's rule of `2026-10-06`. One sentence gets one verdict in both languages. The docstring of `mask_jsdoc` lists the unmasked shapes. Four are a backtick span, a dotted name, a URL and a fenced block. The other three are a bracketed placeholder, a configuration key line and a file name. A parity test feeds nine shapes through both paths and requires equal findings. Its name is `test_a_shape_that_both_languages_can_hold_gets_the_same_verdict_in_both`.
14. **Banner lines are layout, but the history rule still reads them.** The helper `_blank_banners` empties each banner line first. The emphasis, tic and summary rules then run on the result. `BANNER_LINE` has two branches. The first is four or more rule characters, with or without a space and a title after them. It needs no closing rule, so a rule of four dashes and a title is a banner. The second is a title between an opening rule of two or more and a closing rule of four or more. Box-drawing characters count. The history rule reads the unblanked text, so a date in a banner title is a finding. The source's question 4 recommended leaving banners alone. This applies to plain comments. A JSDoc block keeps every line.
15. **Scope is a predicate in `in_scope`.** It accepts a `.ts`, `.js` or `.mjs` path. It rejects a path under a `node_modules`, `.venv` or `dist` segment, and a `.min.js` file under a `vendor` segment. The source says the exclusion is the two vendored minified files. In this tree the two tracked `.min.js` files are those two. The four `.d.ts` files are in scope, as the source's question 5 recommends.
16. **The population comes from git, and it is wider than the source's survey.** `tracked_files` lists it with `git ls-files`. I measured 579 files in scope at `d3d98a68a` on `2026-10-12`. Of those, 352 are under `src/tests/unit` and 219 under `src/lupin_app/static`, the source's two groups. The source counted 549 there. Eight files sit outside both groups. Four are probe scripts under `src/rnd`. The others are `src/conf/constants.js`, `src/cosa/repo/symindex/ts_extract.js`, `src/scripts/ts_doc_extract.mjs` and `src/tests/websocket_smoke/multiplexer_frame_to_store.smoke.ts`.
17. **Files go to Node in batches.** `run_extractor` sends `CHUNK_SIZE` files, 200, to each process. The source asked for one process per package and not per file. An empty list starts no process. A failed run, a line that is not JSON, or a missing Node raises `RuntimeError`.
18. **A file that does not parse gives one `parse-error` finding.** `lint_comments` puts it on the first error line and still lints that file's comments.
19. **The command line is the module's own `main`.** It takes its parser from `cli.build_parser` and uses `--repo-root`, `--strict`, `--changed`, `--staged` and `--json`. The source planned the same `run_linter` entry point as the other linters. `tsdoc_lint.py` does not call `run_linter`.
20. **Enforcement is a per-file count table in the commit gate.** The source's question 7 recommended warn mode until a sweep is ruled. Commit `a73a7a866` added `ts_counts.py` and a second scope in `gate.py`, `TS_SCOPE`. The commit subject names the store item `id=4226b1b1`. In `scope_check`, a staged file is refused when its unwaived finding count exceeds its allowance. The table is `src/conf/doc-lint-ts-counts.json`. `counts.allowance` gives a file its own entry. A file with no entry takes the entry of the path it was renamed from, or zero. A table whose stamp is not the current rules stamp refuses any commit that stages an in-scope file. The gate counts the staged text in one `counts_for` call, and `run_extractor` starts one Node process per 200 files. The refusal depends on the extractor running. `run_extractor` raises `RuntimeError` when Node cannot start. `gate.main` catches every exception from `collect`, prints "GATE CRASHED, commit allowed" and returns 0. A file over its count is then not refused. On `2026-10-12` the table held 555 entries that sum to 26,240. Warn mode was the recommended answer to question 7, and the count table departs from it. I searched `TODO.md` for a ruling on a TypeScript count table and found none. Its one line on that store item is Rick's ruling to refuse lint findings in swept docstrings.
21. **No merge gate script runs the checker over the tree's files.** I searched `src/scripts/*.sh` and `src/tests/*.sh` for `ts_counts` and `tsdoc` and found no match. One script names the extractor for coverage: `src/tests/run-typescript-tests.sh` lists `src/scripts/ts_doc_extract.mjs` in its c8 include set. `BLOCKING_PACKAGES` in `gate.py` is empty. In `gate.py` the one `tsdoc_lint` name used is `in_scope`.
22. **The Python tests do not need Node, and one of them reads fixture files.** `test_doc_lint_tsdoc_lint.py` holds 50 test functions. One, `test_every_fixture_file_lints_without_error`, reads the fixture folder. The others build extractor records inline or replace the subprocess call. `src/tests/fixtures/ts_doc_lint/` holds a hand-written fixture and one captured from the real extractor. The capture's note says it was taken unedited on `2026-10-06` from `arg-interview.js`. The extractor is tested in the TypeScript tier. `run-typescript-tests.sh` adds `src/scripts/ts_doc_extract.mjs` to the c8 include set. The source expected that include in `package.json`.
