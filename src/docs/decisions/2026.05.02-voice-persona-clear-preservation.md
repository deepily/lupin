# Decision record: a voice persona survives `/clear` and `/compact`

**Source:** `src/rnd/v0.1.7/2026.05.02-voice-persona-clear-preservation/01-design.md` (327 lines, read whole). The file carries a later update that overturns its own first diagnosis. This record states the update. Where later code or documents differ, it says so.

**Status:** in force as built. The `reason` guard in the SessionEnd hook, the carry-forward in the SessionStart hook, the release-on-overwrite helper and the "Voice re-assigned" announcement exist in the tree.

**Checked against:** `src/lupin_cli/claude_code/hooks/session_end.py`, `src/lupin_cli/claude_code/hooks/register_session.py`, `src/cosa/rest/routers/voice_persona.py`, `src/lupin_cli/claude_code/hooks/lib/session_bridge.py`, `src/lupin_app/static/js/notifications.js`, `src/tests/unit/test_session_end.py` and `src/tests/unit/test_register_session_preservation.py`.

## What is in force today

1. **A persona is released only when the session really ends.** The SessionEnd hook calls the release helper when `session_id` is non-empty. It does so only if `reason` is neither `"clear"` nor `"compact"`. It releases on `"logout"`, `"prompt_input_exit"`, `"other"` and on a missing reason. A failure of the release call is swallowed and logged.
2. **The reason for rule 1 is a defect that the source first misplaced.** SessionEnd fires on `/clear` and `/compact` too. A release there writes `voice_persona: null` to the bridge before the next SessionStart reads it, so the carry-forward declines and a random persona is drawn. The source's first plan blamed a gate in `register_session.py`. The source's own update disproves that in its section 0.3, and the first plan's repair work is marked obsolete there.
3. **The carry-forward does not depend on the transient id changing.** Today the SessionStart hook copies the prior bridge's `voice_persona` whenever that value is a dict. The source's section 1.3 keyed the copy on `is_context_clear`. A later document found that a compaction can keep the same transient id and so lose the persona. The code was changed. Its comment says the gate is "NOT keyed on `is_context_clear`".
4. **A persona that was not carried forward is released over HTTP.** This happens before the bridge is rewritten. It applies when the old bridge had a persona dict and the new session data has none. The hook posts the release. It also keeps the outgoing `display_name` as `previous_persona_name`. This is the source's Fix 2, which it keeps as "defense-in-depth". It fails soft.
5. **A changed voice is announced aloud.** The allocate endpoint accepts `previous_persona_name`. It pushes a `task` notification `Voice re-assigned: <old> → <new>` when a persona is newly allocated and the old name differs. The endpoint also announces on a swap that it detects itself from the bridge, which the source did not specify.
6. **The release endpoint is idempotent and tells the browser.** It answers 404 when no bridge exists. It answers 200 with `released: false` when the slot is already empty. Otherwise it clears the field, answers 500 if the bridge write fails, and pushes a `voice_persona_released` notification. The browser handler deletes the sender's entry from `senderPersonaMap`.
7. **The idle backoff index is still carried forward only on a context clear.** The idle-detection block is rebuilt. Its `backoff_index` is copied from the old bridge when `is_context_clear` is true. The source's disposition table marked this "RE-EVALUATE" and "Probably NO-OP". The code kept the older gate here.
8. **The diagnostic prints are gone.** `register_session.py` has no `gate-result`, `preserve-check` or `gate-2-fail` print. A test-file comment says they were removed after the guard fix "landed ... and [was] live-verified".
