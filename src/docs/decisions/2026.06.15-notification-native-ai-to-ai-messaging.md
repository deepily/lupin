## What is in force today

1. **A peer DM is a notification with the body inline.** The source's goal is "ordinary notifications with the body inline". `POST /api/dm/send` pushes a notification with `direction="ai_to_ai"`. No commons board, no claim check and no `commons_read` re-fetch are involved. The source states about 204 tokens per received DM, against about 3,712. I did not re-measure that figure.
2. **The columns are first class, and the wire keys equal the column names.** `notifications` carries `direction`, `sender_persona`, `sender_icon`, `reply_to` and `thread_id`. `direction` is not null, defaults to `ai_to_human`, and is indexed. `thread_id` is indexed. The other three are nullable. The migration adds each column only when it is absent.
3. **`direction` has three values and is a separate axis from `type`.** The values are `human_to_ai`, `ai_to_ai` and `ai_to_human`. `POST /api/notify` rejects any other value with a 400. A notification with no `direction` is treated as the legacy voice path.
4. **The HTTP door is `/api/dm/send`, not `/api/notify-peer`.** The source names `POST /api/notify-peer`. The tree has an `/api/dm` router with four verbs, `send`, `respond`, `get` and `list`, each mirroring a `dm_*` MCP tool. The router also has three audit routes: `/project-audit`, `/length-audit` and `/quality-audit`. No Python file outside `src/rnd` and the tests contains the old route name.
5. **The idle or busy decision comes from a pane probe, not from heartbeat events.** The source reads `last_emitted_outcome` from the heartbeat store. `_recipient_is_injectable` replaced that with `_pane_is_idle_at_prompt`, which captures the tmux pane twice. A busy, dialog-blocked or unclassifiable pane is buffered. Only an observed idle prompt is woken by tmux. No code file reads `last_emitted_outcome` for this decision.
6. **The header reads `PEER DM from <persona> <icon> on <stamp>`.** The ids ride only the reply line. The source puts `[DM from <persona> <icon>]`, `message_id` and `thread_id` in the envelope. `build_peer_dm_reminder` puts the ids only in the `dm_send` reply line. A DM style line rides that reply line too. It comes from the `2026-07-31` verbosity-reduction work.
7. **A peer DM never receives the human voice rider.** `_handle_event` routes `ai_to_ai` to `_deliver_peer_dm` before the voice path. The idle branch injects with `wrap=False`. `format_voice_context` builds the same block for buffered DMs. Peers reply with `dm_send`, never by speech. This is the source's section 6a mandate.
8. **A buffered DM is delivered at every idle or stop boundary.** The source's Notification hook fix is carried out: at `idle_prompt` the hook calls `deliver_pending_peer_dms`. The Stop hook's speakerphone branch calls it too when the buffer holds pending messages, then allows the stop. The source said the stop hook should "drain + block + inject". It drains and tmux-delivers, then emits an empty answer.
9. **The commons DM live path is retired.** The source's section 8 lists the claim check, the forced `commons_read`, and the reply watcher. I searched the code for `_dispatch_commons_question_received`, `CommonsQuestionWatcher`, `_handle_commons_question_received` and `execute_notify_peer` and found none outside `src/rnd` and tests. `commons_ask_async` still exists as the open-question tool to a topic.
10. **`commons_send_to` is gone, and two comments still call it deprecated.** The tool function no longer exists in `cosa_voice_mcp.py`. The `dm_send` description and a comment above `_dm_send_impl` still name it. Both sentences also call `commons_ask_async` deprecated, and that tool is live.
