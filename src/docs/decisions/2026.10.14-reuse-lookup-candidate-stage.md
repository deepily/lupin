## What was decided

The reuse lookup stops asking Jev about every index entry. A first stage ranks the index by rank fusion.
The lists it fuses are word search, prose vectors, code vectors and the wiki page list. Jev judges only the top of the ranking.
The plan sets the shortlist at 128, widened to 512, in packs of 50 entries.
A lookup then makes 3 to 11 judge calls and not about 164.

The expert response and the prose-and-code addendum behind the plan are untracked, so this record cites them and does not link them.

## Decisions taken by Cheech, which Rick may overrule

- **X1:** Cheech decided to extend the existing embeddings endpoints.
  `generate` and `batch` take an optional `role` field, `query` or `document`, which defaults to today's behaviour.
  `info` gains an `engines` block that reports model, revision, dtype and device.
  Reason: both models need different prefixes for queries and documents, and the manifest must pin what the endpoint used.
  This extends the existing endpoints and builds none, as R9 requires.
- **X2:** Cheech decided that the search runs as a child process of cosa-voice (plan section 4.4). Rick may overrule it.
  - **The alternative:** a search endpoint on the Lupin FastAPI server, which cosa-voice would call over HTTP.
  - **Why it lost:** the server runs in a container, and the container would need the vector-set data directory mounted.
    The child process follows the existing pattern of the index builder, which runs `node` the same way.
  - **Start-up cost per lookup:** one process start plus importing `numpy` and the search code. The search itself is not yet measured.
    With `numpy` 2.4.4 on the seat's own interpreter, `import numpy` took 0.06 to 0.10 s over five runs.
    That figure is an import time and is not the whole cost.
    The first search phase measures the whole process start and the search time for the 30 needs.
  - **Amendment, after Rick asked whether the matrices are re-read on every lookup:** the child process holds for the first search phase and the offline comparison.
    The first search phase's exit gate measures the full per-lookup cost.
    The wiring phase switches to a resident search endpoint on the Lupin server if that cost exceeds 250 ms.
    The data-folder bind mount and the container recreate then belong in the wiring phase's scope.
- **X3:** Cheech decided, since nothing runs in production, that the page route is removed in the wiring phase with no switch.
  The wiki page list enters the fusion as one ranked list. The old page-first code and its tests go in the same change.
  Rick may overrule it, in which case the code stays behind a flag for one release.

- **X4:** Cheech decided that the purpose-line job may read body text, which `sendable()` does not screen. Rick may overrule it.
  Reason: the job is a bounded Claude Code session reading the same tree every seat already sends to Anthropic.
  The job's output is screened with `c1_hits` before storing.

- **X5:** Cheech decided that `role` and the `engines` block go on the FastAPI embeddings router only. Rick may overrule it.
  The seat that builds the vectors found that the shipped INI sends the provider's HTTP path to `lupin_model_server` first.
  That service has no role field and applies no prefixes. The INI line is `model server url = http://lupin-model-server:7998`.
  The provider therefore gains a `pin_fastapi` argument, which the build and query calls always pass.
  It also refuses a `role` sent to the model server, with `ROLE_UNSUPPORTED_ON_MODEL_SERVER`.
  Each engine reads its model revision from the loaded model's config, and it is `null` until the first load.
  The model server is unchanged. See plan section 11, X5.

## What is still open

- **Nothing is built.** Every name in the plan is a design. The capability page `candidate-stage` is marked planned.
- **Not measured:** embedding latency through the endpoints, the first stage's query and process-start time, and recall of any ranking.
  Also purpose-line quality per language, and peak GPU memory.
- **The replay window is short by ruling.** A receipt replays only until the next rebuild, possibly daily.
- **A bound on misses does not exist yet.** A bound near 1% needs about 300 audits.
  At 1% of lookups that is about 30,000 lookups.
