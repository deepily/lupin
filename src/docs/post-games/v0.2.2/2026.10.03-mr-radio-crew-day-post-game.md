## 6. Lessons for the failure-mode catalog

- **A green run recorded red.** Trigger: a reporting step runs after the test command, under `set -e`, and uses a `grep` whose no-match is a normal answer. Symptom: all tests pass, the banner is missing, the job's exit code is 1, and every reader counts failures and never reads the code. Guard: a test that calls the reporting function under `set -e` with a real all-green summary line; and read the exit code of a run you cite, not only its counts.
- **A fix that passes its one incident.** Trigger: a defect found as a single pair, and a predicate written to refuse that pair. Symptom: tests green, coverage 100%, and the nearest sibling input still passes through. Guard: before sending the sha, list the inputs that differ from the incident in one token each (target unit, sign, decimal point, order) and make each a test; then a reviewer who has not read the author's notes.
- **A probe on the wrong engine.** Trigger: a question about transaction or savepoint behaviour, answered on SQLite because it is at hand. Symptom: a confident sentence that is backwards on Postgres. Guard: run it on a throwaway Postgres, name the engine beside every such result, or leave the sentence out.
- **A clock written from memory after a clear.** Trigger: a fresh context that has just read a memento full of times. Symptom: times a few minutes ahead of the real clock, in durable rows. Guard: no rule has held for me on this in two days; the row store stamps its own time, so the amendment text does not need mine.
