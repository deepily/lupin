# CSS animation removal causes unexpected layout collapse

**Removing a CSS class that animates only box-shadow and outline can collapse elements to zero dimensions due to compositor layer demotion triggering cascading style recalculation and layout passes—a behavior rooted in browser implementation quirks, not CSS specification.** While box-shadow and outline are explicitly defined as non-layout-affecting properties, browser bugs (notably Firefox #1194480 and Chromium #396825) have historically caused these properties to incorrectly trigger reflow operations. The collapse-and-re-expand flash you're seeing is likely a race condition between layer demotion, style resolution, and layout recalculation.

## The hidden compositor layer problem

When CSS animations run, browsers automatically promote animated elements to their own GPU compositor layer—even when animating non-accelerated properties like box-shadow. This promotion happens because the CSS Animations specification states that "while an animation is applied, the user agent must act as if the `will-change` property additionally includes all animated properties." Your `.tts-playing` animation implicitly creates this layer.

The critical issue occurs during **layer demotion**: when you remove the animation class, the browser must reabsorb the element back into its parent layer. This triggers the full rendering waterfall—Recalculate Styles → Layout → Paint → Composite—affecting both the demoted element and potentially neighboring elements. Chrome's Layer Borders tool confirms this: the orange compositor-layer border disappears, and Paint Flashing shows the entire area repaint.

**Box-shadow and outline are not GPU-accelerated**—they render on the CPU even during animation, creating a hybrid situation where the compositor layer exists but the animated properties require main-thread repaint on every frame. When the animation class is removed, this awkward layer arrangement collapses, and the browser's style recalculation may momentarily compute incorrect dimensions before restoring them.

## Browser bugs directly relevant to this behavior

Firefox Bug #1194480 documents exactly this problem: the `CalcShadowDifference()` function was returning `NS_STYLE_HINT_REFLOW` for any box-shadow change, triggering full layout recalculation instead of just repaint. Though marked "RESOLVED FIXED," similar behavior patterns persist in edge cases involving animation removal.

Chromium Bug #396825 documents that box-shadow changes trigger unnecessary layout because shadows affect overflow area calculations, and Chrome was performing full layout instead of paint-only operations. This explains why removing a box-shadow animation could affect element dimensions despite the property theoretically being layout-neutral.

Firefox Bug #1046055 reveals that animation layers can persist incorrectly after completion, and the cleanup process during layer demotion can cause visual glitches. This directly applies to your scenario where the animation class removal forces immediate layer cleanup.

## Why the collapse happens mechanically

The zero-dimension collapse likely follows this sequence:

1. **Animation class removal** fires `animationcancel` event and strips animation contribution from cascade
2. **Implicit `will-change` removed**, triggering compositor layer demotion decision
3. **Layer demotion begins**, element must be repainted into parent layer
4. **Style recalculation triggered** on element and potentially neighbors
5. **Layout pass runs** during brief window where styles are partially resolved
6. **Bug: box-shadow removal triggers reflow** instead of paint-only
7. **Race condition**: layout computes before styles fully resolve → zero dimensions
8. **Next frame**: styles fully resolve → correct dimensions restored → visible flash

The `!important` flag on your animation property adds complexity. Per specification, `!important` is ignored inside `@keyframes` blocks, which could cause parsing inconsistencies or unexpected cascade behavior during removal. The `border-radius: 8px` in the animation class creates a stacking context interaction—when removed alongside the animation, it may affect how the browser calculates the element's containing block.

## Solutions that address the root cause

### Move animation to a pseudo-element (recommended)

The most reliable fix isolates the animation from the element's box model entirely:

```css
.action-required-notification div {
  position: relative;
}

.action-required-notification div::before {
  content: '';
  position: absolute;
  inset: 0;
  border-radius: 8px;
  pointer-events: none;
  box-shadow: none;
  outline: none;
}

.tts-playing::before {
  animation: ttsPulseGlow 1s ease-in-out infinite;
}

@keyframes ttsPulseGlow {
  0%, 100% {
    box-shadow: 0 0 5px 2px rgba(255, 193, 7, 0.4);
    outline: 2px solid rgba(255, 193, 7, 0.6);
  }
  50% {
    box-shadow: 0 0 15px 5px rgba(255, 193, 7, 0.9);
    outline: 2px solid #ffc107;
  }
}
```

The pseudo-element is absolutely positioned and doesn't participate in the parent's box model calculations, making animation removal layout-neutral.

### Use animation-play-state instead of class removal

Keep the animation definition always present but toggle its running state:

```css
.action-required-notification div {
  animation: ttsPulseGlow 1s ease-in-out infinite;
  animation-play-state: paused;
  border-radius: 8px;
}

.tts-playing {
  animation-play-state: running;
}
```

This maintains the compositor layer and prevents the demotion cascade that causes the collapse.

### Apply CSS containment for layout isolation

```css
.action-required-notification div {
  contain: layout paint;
  will-change: transform; /* maintains compositor layer */
}
```

The `contain: layout` property isolates the element's layout calculations from the rest of the document. Combined with `will-change: transform`, this keeps the element on its own compositor layer even after animation ends, preventing the demotion-triggered reflow cascade.

## Debugging steps to confirm the diagnosis

Open Chrome DevTools and enable three rendering overlays: **Layers panel** (More Tools → Layers), **Paint Flashing** (Rendering → Paint flashing), and **Layout Shift Regions** (Rendering → Layout shift regions). When you remove the `.tts-playing` class, observe whether the element's orange compositor-layer border disappears and whether the area flashes green (indicating repaint) or blue (indicating layout shift).

Use the Performance panel to record a trace during class removal. Look for forced reflow operations in the "Recalculate Style" and "Layout" entries. If the element shows a **Layout** entry during class removal, this confirms the bug—box-shadow animation removal is incorrectly triggering reflow.

## Conclusion

The layout collapse stems from a confluence of browser implementation details: implicit compositor layer creation during animation, the non-GPU-accelerated nature of box-shadow rendering, and long-standing browser bugs where shadow property changes incorrectly trigger layout instead of paint operations. The pseudo-element approach completely sidesteps this by removing the animated properties from the element's own box model, while `animation-play-state` avoids the layer demotion cascade entirely. Either solution should eliminate the collapse-and-re-expand flash.
