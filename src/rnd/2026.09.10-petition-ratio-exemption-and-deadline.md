## Finding 4: a petition is judged at P1 by the ratio gate

### Mechanism (code read at `699a0310`)

1. `routers/tasks.py` `create_task`: when the firewall refuses a manager's P0 and `authority="user_direct"`, it sets `effective_priority = priority_firewall.PETITION_HOLDING_PRIORITY` (P1) and prints `P0 PETITION opened … minted at P1`.
2. The ratio gate then runs on **`effective_priority`**, not `payload.priority` (`rules.ratio_gate_advisory( …, priority = effective_priority, … )`). The comment above it, beginning *"`effective_priority`, SO A PETITION BUYS NO RATIO EXEMPTION"*, says this is deliberate. Reading the requested priority would let any caller skip the throughput gate by typing `authority="user_direct"`.
3. `task_store_rules.py` `ratio_gate_advisory` exempts only `RATIO_GATE_EXEMPT_PRIORITIES = ( "P0", )`. **All three of its refusal messages end "(A P0 is exempt if this genuinely cannot wait.)"**, whatever priority the caller asked for. To a petitioner that sentence is false: they did ask for P0, and it did not exempt them.
4. The design says the same: `src/rnd/2026.09.09-p0-petition-relay-design.md` §4.1, "A petition buys no ratio-gate exemption … Flagged to Rick as a follow-up rather than settled unilaterally."

### Live evidence (`:7999` log, 2026-09-10)

| time (Z) | line | reading |
|---|---|---|
| 21:28:57 | arm 1 `ratio gate allow: created=64 closed=38 ratio=1.68 threshold=1.70` | allowed at P1; this create made it 65 / 38 = **1.71** |
| ~21:31 | arm 2 `P0 PETITION opened … minted at P1` → `POST /api/tasks 422` | refused on throughput, judged at P1. Mr. Radio's amendment quotes the 422 detail (inherited, not re-read): *"…created 65 and closed 38 (ratio 1.71 — the gate opens below 1.70)… (A P0 is exempt if this genuinely cannot wait.)"* |
| ~21:33 | `flow-ratio settings set by ricardo…: window=24h → 72h → 96h, allow_below=1.7` | **Rick widened the window by hand** ("Currently I'm holding room for 8 more") |

This settles the question left open in Mr. Radio's 21:31Z amendment: the log shows arm 1 was the create that pushed the ratio from 1.68 to 1.71.

### A second, smaller defect (4b)

The `P0 PETITION opened` line prints **before** the ratio gate runs, so a create the gate refuses still logs a petition that never existed. The 21:31 attempt created no row and no ticket (Mr. Radio's amendment), yet the log says one was opened.

### Guards

`test_the_petition_at_the_real_create_door.py`: `test_a_petition_does_NOT_inherit_the_P0_ratio_exemption` and `test_the_ratio_gate_POSITIVE_control_a_real_P0_is_still_exempt` both **passed** on the main tree at `699a0310` (3 passed, 0.64 s, with the deadline test below). They assert the **status** (422 vs 201) and that no ticket was minted. **No test reads the refusal text**, which is why the false sentence survives.

### Not measured

- Whether the "flag to Rick" follow-up exists anywhere. `git grep` over `TODO.md` for lines containing both "petition" and "ratio" returns nothing. The task store was **not** searched.

### Options (for Mr. Radio; B changes a security property, so it needs Rick)

| option | pros | cons |
|---|---|---|
| **A — Keep the rule; make the refusal honest for a petition (recommended)** | Keeps the anti-grant property the design argues for. Small: pass "was this a petition" into the message builder. Pin the text with a test that reads the 422 detail | A P0 that Rick ordered can still be stopped by fleet throughput and need his hand, as happened tonight |

The row still lands only at P1 in holding, but every such create puts an ask on Rick's screen. That shifts the throttle from the board onto Rick |

Either way: move the `P0 PETITION opened` print to after the ratio gate (4b).

## Finding 6: `resolves_by` is the stall deadline, not the answer window

### Mechanism (code read at `699a0310`)

- `task_promotion_resolver.py` `resolves_by_for` returns `requested_at + ask timeout + notification grace + APPLY_MARGIN_SECONDS`. Shipped values: `task approval promotion ask timeout seconds = 120`, `notification grace period seconds = 300`, `APPLY_MARGIN_SECONDS = 60`, **= 480 s**. Its docstring calls this the moment the ticket "must have resolved by", the point after which the sweeper declares an orphan. It deliberately runs past the ask so a late answer the notification API still accepts is not raced.
- The ask Rick sees is fired from `promotion_ask_kwargs` with `timeout_seconds = get_ask_timeout_seconds()` (120). When that ask times out, the resolver refuses the ticket.
- `routers/tasks.py` `create_task` returns the petition as `{ ticket_id, minted_at, requesting, resolves_by, check_with }`. **`resolves_by` is the only time given; there is no field for the answer window.**
- The `task_promotion_status` MCP tool describes `pending` as *"Rick has not answered and the deadline has not passed"*, which invites reading `resolves_by` as the answer deadline. That text lives in the cosa-voice server, not in this repo.

### Live evidence (`task_promotion_status`, read 18:07:37–18:08:04 EDT; `d9d9206e` at 18:11:31)

Two different things are measured, in two different columns:
- **actually resolved after** = `resolved_at − requested_at`, what happened
- **field says** = `resolves_by − requested_at`, what the ticket told the filer

| ticket | arm | requested (Z) | resolved (Z) | actually resolved after | field says | state |
|---|---|---|---|---|---|---|
| `7ad11385` | this morning | 14:44:27.15 | 14:46:27.64 | **120.5 s** | 480 s | refused, timed out |
| `1a3eaf94` | 1, approve | 21:28:57.14 | 21:29:11.76 | 14.6 s | 480 s | approved, keypress |
| `db12b61d` | 2, decline | 21:34:44.56 | 21:35:04.61 | 20.1 s | 480 s | refused, Rick's no |
| `9de7f6e9` | 3, timeout | 21:35:18.98 | 21:37:19.44 | **120.5 s** | 480 s | refused, timed out |
| `d9d9206e` | slider-bug P0, Mr. Radio's re-measure | 22:08:58.239 | 22:10:58.676 | **120.4 s** | 480 s | refused, timed out |

All three timeouts resolved about 120.4–120.5 s after the request. Every `resolves_by` is exactly 480 s after the request.

**The clock starts at the ask, not at the request** (`:7999` log, `docker logs -t`, ticket `d9d9206e`):

| event | time (Z) | since request |
|---|---|---|
| ticket `requested_at` | 22:08:58.239 | 0 |
| ask `36510bb4` sent (`POST /api/notify … timeout_seconds=120`) | 22:08:58.664 | 0.43 s |
| `notification_expired` broadcast for `36510bb4` | 22:10:58.674 | 120.43 s, **exactly 120.01 s after the ask** |
| ticket `resolved_at` (refused, timed out) | 22:10:58.676 | 120.44 s |

The ~0.4 s over 120 is the gap between minting the ticket and sending the ask, which `resolves_by_for`'s docstring already names. The ask's own timeout is exact.

### The harm is already measured, twice

**1.** This morning a seat notified Rick: *"The ticket-card row's P0 approval is still waiting on you until about 10:52."* That is `resolves_by` (14:52:27Z) in EDT. The ask had already closed at 10:46:27 EDT, so Rick was told he had six more minutes than he did (`:7999` log, `POST /api/notify` shortly after 14:44Z).

**2.** This evening, for ticket `d9d9206e`, Mr. Radio notified Rick at **22:10:00Z (18:10:00 EDT)**: *"A P0 approval ask is on your screen until about six sixteen."* Six sixteen is `resolves_by` (22:16:58Z). The ask expired at **18:10:58 EDT**, 58 seconds after that notify, so Rick was told he had about six minutes when he had under one (`:7999` log, `docker logs -t`, the `[NOTIFY] … alert/urgent` line). Mr. Radio recalled the notify as 18:08; the log line above is the timestamp cited.

### Guards

`test_the_asynchronous_promotion_resolves_or_shouts.py::test_the_deadline_is_the_ask_timeout_plus_grace_plus_margin_read_at_MINT_time` **passed**. It pins the 480 s sum, which confirms the value is intended. No test covers what the filer is told.

### Options

| option | pros | cons |
|---|---|---|
| **A — Add `answer_by` (requested_at + ask timeout) beside `resolves_by` in the petition body and in `task_promotion_status`; document `resolves_by` as "declared stalled after this" (recommended)** | Additive, so no caller breaks. The filer, and anyone relaying to Rick, gets the real window. Stamped at mint time like `resolves_by` | Storing it needs a column and a migration. Deriving it later from today's config would repeat the drift `resolves_by_for` was written to avoid |
| B — Rename `resolves_by` to `stalled_after` in response bodies | The name finally matches the meaning | Breaks the MCP tool, tests and any reader; still gives no answer window |

Either way, the cosa-voice `task_promotion_status` description should stop calling `resolves_by` the deadline Rick answers by.
