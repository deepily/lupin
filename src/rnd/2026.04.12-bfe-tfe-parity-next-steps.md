### B. BFE live E2E script — design ready for implementation

BFE still has no dedicated live E2E script (confirmed: only `run-tfe-live-e2e.sh` exists in `src/tests/e2e/`). Design follows the TFE script plus the dual-container pattern:

**File to create**: `src/tests/e2e/run-bfe-live-e2e.sh`

**Structure** (~180 lines mirroring TFE):

1. **Header + usage** — document `--dry-run` (default) vs `--live` modes; env vars `LUPIN_TEST_PORT`, `LUPIN_TEST_BASE_URL`, `LUPIN_TEST_INTERACTIVE_MOCK_JOBS_EMAIL/PASSWORD`
2. **Dual-container pattern** — `PORT="${LUPIN_TEST_PORT:-8000}"`; verify test server healthy at `/health`; verify `/api/server-info` reports `[Lupin: Testing]`
3. **Fixture** — `src/tests/fixtures/bfe/snapshot_known_bad.json` (new file, NOT in this plan's scope — just reference the path). This should be a realistic failed-job snapshot that BFE can diagnose. Candidates based on TODO.md:85: presentation-gen job with intentional source-path bug, OR a TestSuiteJob with a single known-failing test seeded into it.
4. **Preflight** — `--dry-run` needs: server healthy, testing config, test credentials. `--live` also needs: `bug fix expediter enabled = true` AND `auto fix enabled = true` in INI.
5. **Authenticate** — POST `/auth/login` with test credentials, capture token
6. **Submit the known-bad job** — POST `/api/push` with the fixture payload; job enters queue with known failure
7. **Wait for dispatch** — poll queue state until the original job moves to `dead` (failed), then poll until `DeadQueueWatchdog` dispatches a BFE job (`status=todo` with `triggered_by_bfe=true` in metadata)
8. **Poll BFE progress** — similar 600s window / 5s interval loop, tracking the BFE job ID through `todo → running → done/dead`
9. **Success criteria**:
   - BFE job reaches `done` with `status=completed`
   - BFE produced a commit + PR (check `artifacts.pr_url`)
   - Original job was auto-resubmitted (check `metadata.resubmitted_job_id`)
   - Resubmitted job reaches `done` (validation that the fix actually worked)
10. **Failure diagnostic** — on any failure, print: BFE job ID, phase reached, artifacts (plan_path, report_path), stack trace from `metadata.stack_trace`

**Dry-run vs live**:
- `--dry-run`: BFE runs but skips real SDK calls + real git ops; validates queue flow, watchdog dispatch, job lifecycle, artifact storage. $0.
- `--live`: Full real-agent execution. $2-5 per run (BFE budget is $2 USD default). Requires `bug fix expediter enabled = true`.

**Effort**: large once plan mode exits — ~1-2 hours to write, plus ~30 min first dry-run, plus ~30 min first live run. **Designing it now** (this document) shaves most of the write-time from the future session.

## Item 2 — TFE live E2E run

### The script

**Location**: `src/tests/e2e/run-tfe-live-e2e.sh` — 180 lines, written in Session 1cfcdf73 as step 18 of the approved TFE plan.

**What it does**:
1. Preflight: server health check, test credentials present, fixture snapshot present
2. Stage fixture → `io/test-suite/tfe-e2e-{TIMESTAMP}-remediation.json`
3. Authenticate via `/auth/login` using `LUPIN_TEST_INTERACTIVE_MOCK_JOBS_EMAIL` + `PASSWORD`
4. Submit TFE job via `/api/push` with `dry_run=true` (default) or `dry_run=false` (`--live` flag)
5. Poll `/api/get-queue/done` and `/api/get-queue/dead` for 600s, 5s interval
6. Pass = final state is `done` with `status=completed`; Fail = `dead` or 600s timeout

**Key prerequisites**:
- FastAPI server on port 7999
- `LUPIN_TEST_INTERACTIVE_MOCK_JOBS_EMAIL` / `_PASSWORD` env vars set
- Fixture snapshot at `src/tests/fixtures/tfe/snapshot_kcluster.json`
- For `--live`: either `test fix expediter auto fix enabled = true` in INI, or manual submission (works in both modes)
- Clean DB state for test user

**Real operations**:
- **SDK calls**: yes — Opus (lead) + Sonnet (worker) through TFEOrchestrator phases 0-2 and 3
- **Git ops**: yes in Phase 5, trust-mode gated
- **Failing tests**: real prior-failure snapshot, not live test-suite execution (fixture pre-baked)

### Cost & duration

- **Dry-run**: $0, ~5 min (LLM calls stubbed, polling still runs the 600s window in worst case)
- **Live**: $2–8 per run per TODO.md:86; the `cost cap usd` INI key defaults to $15 as a safety ceiling, not an expected cost
- **Wall-clock cap**: 2400s (40 min) via `test fix expediter wall clock timeout secs`

### What actually gets validated (currently unproven against real code)

Per `src/rnd/v0.1.6/2026.04.10-test-fix-expediter/08-phase6-rerun-validation-plan.md:4-95`:

| Phase | What the live run proves |
|-------|--------------------------|
| Phase 0 | Clustering heuristic + LLM refinement produces 1–8 clusters from a real failure set |
| Phase 1 | Diagnosis prompts return parseable root_cause + confidence per cluster |
| Phase 2 | Voice gate aggregation works end-to-end (user selects fix set via `ask_multiple_choice`) |
| Phase 3 | Multi-cluster FixExecutor runs Coder→Tester per cluster, records success/failure |
| Phase 5 | `GitStrategist.commit_and_pr_multi()` creates one branch, N commits, one PR (or atomic rollback) |
| Phase 6 | Recursion guard (`metadata["triggered_by_tfe"]`) prevents re-trigger; validation rerun dispatches with `affected` scope |
| Lifecycle | The just-landed forensics fixes (error capture, TARGET_USER, plan_path artifact) stick under real failure conditions |

### Effort

**Medium.** Prerequisites are in place and the script is already written. Operator time is polling + watching Opus/Sonnet do their work for 10–40 min. The actual difficulty is **interpreting a failure if one occurs** — a Phase 3 Coder-Tester loop failure will require reading the partial plan + remediation snapshot to diagnose.

### Open question to decide before running

Should the first live run be:
- **(a) Dry-run only** — prove the pipeline end-to-end at $0 (fastest confidence, but leaves SDK paths unvalidated)
- **(b) Live with a single-cluster fixture** — cheapest real run (~$2), validates full pipeline but only exercises one cluster
- **(c) Live with the default multi-cluster fixture** — full validation (~$5–8), exercises `commit_and_pr_multi` + continue-on-failure logic

Recommended sequence: (a) → (b) → (c) across separate sessions to isolate any failure to the specific tier that introduced it.
