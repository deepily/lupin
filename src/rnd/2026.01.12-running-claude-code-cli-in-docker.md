# Docker deployment guide for Claude Code CLI in production

**Anthropic provides official containerization support for Claude Code**, including a reference Dockerfile, devcontainer features, and Docker Desktop sandbox integration. Deploying Claude Code CLI in production containers requires Node.js 18+, secure runtime credential injection (never build-time), and careful MCP server configuration for path mapping. The most critical security principle: **API keys must never be baked into Docker images**—instead use Docker secrets, cloud secret managers, or volume-mounted credential files at runtime.

## Official Anthropic Docker support and installation patterns

Anthropic actively supports containerized Claude Code deployment through multiple official channels. The reference implementation lives in the [anthropics/claude-code GitHub repository](https://github.com/anthropics/claude-code/tree/main/.devcontainer), featuring a production-ready Dockerfile based on `node:20-bookworm-slim`. For quick integration, Anthropic publishes an official devcontainer feature at `ghcr.io/anthropics/devcontainer-features/claude-code:1`.

The recommended base configuration follows this pattern:

```dockerfile
FROM node:20-bookworm-slim

RUN apt-get update && apt-get install -y \
    git curl ca-certificates ripgrep

# Install Claude Code globally
RUN npm install -g @anthropic-ai/claude-code

# Non-root user setup
USER node
WORKDIR /home/node/app

ENTRYPOINT ["claude"]
```

**Node.js version 18+ is mandatory** for the npm installation path (`npm install -g @anthropic-ai/claude-code`). For environments where Node.js cannot be installed, Anthropic offers a native installer via `curl -fsSL https://claude.ai/install.sh | bash` that bundles all dependencies. Docker Desktop users can leverage the official sandbox with `docker sandbox run claude`, which includes pre-configured networking security and the `--dangerously-skip-permissions` flag enabled by default.

A critical consideration for Alpine Linux deployments: ripgrep must be installed separately (`apk add libgcc libstdc++ ripgrep`) and the environment variable `USE_BUILTIN_RIPGREP=0` must be set, as the bundled version expects glibc.

## Secure API key management eliminates build-time credential exposure

The most dangerous anti-pattern in containerized AI deployments is embedding API keys during image builds. Any credential passed via Docker `ARG` instructions persists in image layer history and can be extracted via `docker history --no-trunc`. **This exposure is permanent and irrevocable**—even if the key is deleted in subsequent layers.

Production deployments should follow this hierarchy of secret management approaches:

**Docker Secrets (Swarm mode)** mount credentials as in-memory tmpfs files at `/run/secrets/<name>`, encrypted in transit and at rest. Applications read credentials from the filesystem rather than environment variables:

```yaml
services:
  claude-service:
    image: claude-code:latest
    secrets:
      - anthropic_api_key
    environment:
      ANTHROPIC_API_KEY_FILE: /run/secrets/anthropic_api_key
secrets:
  anthropic_api_key:
    external: true
```

**Cloud secret managers** provide the most robust production solution. AWS ECS natively integrates with Secrets Manager through task definitions, GCP Cloud Run mounts Secret Manager values as volumes that refresh on each read (ideal for rotation), and Azure Container Apps reference Key Vault secrets via managed identity. The file-based approach is preferred over environment variable injection because environment variables are visible via `docker inspect` and can leak into logs.

For Kubernetes deployments, **HashiCorp Vault's sidecar injector** automatically populates secrets into pods via annotations, rendering credentials to `/vault/secrets/` on a shared tmpfs volume with automatic renewal capabilities.

## MCP server configuration requires transport-aware container setup

Model Context Protocol servers extend Claude Code's capabilities by exposing external tools and data sources. MCP uses three transport mechanisms, each with distinct containerization requirements.

**STDIO transport** (most common for Docker) spawns MCP servers as subprocesses, communicating via stdin/stdout. This requires the `-i` flag for interactive stdin and produces no network exposure:

```json
{
  "mcpServers": {
    "github": {
      "command": "docker",
      "args": [
        "run", "-i", "--rm",
        "-e", "GITHUB_PERSONAL_ACCESS_TOKEN",
        "ghcr.io/github/github-mcp-server"
      ],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

**HTTP transport** (introduced March 2025) enables remote MCP servers with optional Server-Sent Events for streaming. This requires explicit port mapping and should bind only to localhost when running locally.

Path mapping presents the primary containerization challenge for MCP servers requiring filesystem access. Host paths must be volume-mounted into containers, and MCP server configurations must reference container-internal paths. For database connections from MCP servers to services on the host, use `host.docker.internal` as the hostname.

Configuration scopes in Claude Code follow a clear precedence: local (`~/.claude.json`) overrides project (`.mcp.json`) which overrides user scope. The `.mcp.json` file supports environment variable expansion (`${VAR}` or `${VAR:-default}`), enabling secure credential injection at runtime.

## Production deployment patterns prioritize multi-stage builds

Multi-stage Docker builds separate build-time dependencies from the minimal runtime image, reducing attack surface and image size from **~1GB to 50-150MB**. The optimal pattern for Node.js CLI tools:

```dockerfile
# syntax=docker/dockerfile:1

FROM node:22-slim AS base
ENV NODE_ENV=production
WORKDIR /app

FROM base AS deps
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force

FROM base AS build
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM base AS runtime
RUN addgroup --gid 1001 --system appgroup && \
    adduser --uid 1001 --system --gid 1001 appuser
COPY --from=deps --chown=appuser:appgroup /app/node_modules ./node_modules
COPY --from=build --chown=appuser:appgroup /app/dist ./dist
USER appuser

# Headless mode defaults for CI/CD
ENV CI=true NO_COLOR=1

ENTRYPOINT ["node", "dist/cli.js"]
```

**Base image selection** favors `node:22-slim` (Debian-based) over Alpine for production AI workloads. Alpine's musl libc causes **15-35% performance degradation** in some Node.js workloads and compatibility issues with native modules. Reserve Alpine for pure JavaScript applications where image size is the primary constraint.

For CI/CD pipelines, BuildKit secrets enable secure build-time authentication without layer exposure:

```yaml
- name: Build Production Image
  uses: docker/build-push-action@v6
  with:
    secrets: |
      "npm_token=${{ secrets.NPM_TOKEN }}"
```

Docker Compose orchestration should disable interactive mode (`stdin_open: false`, `tty: false`) and set `CI=true` for headless operation. Claude Code's `--print` flag enables non-interactive output suitable for automation: `claude -p "Analyze codebase" --output-format json`.

## Security hardening follows OWASP container guidelines

Production Claude Code containers require defense-in-depth security controls. The **OWASP Docker Security Cheat Sheet** and **CIS Docker Benchmarks** establish baseline requirements.

**Non-root execution** prevents privilege escalation attacks. The official Node.js images include a built-in `node` user, or create dedicated users with `adduser --system`. Combine with capability dropping:

```bash
docker run --cap-drop all --security-opt=no-new-privileges \
  --read-only --tmpfs /tmp \
  -e ANTHROPIC_API_KEY_FILE=/run/secrets/key \
  claude-code:latest
```

**Network isolation** for AI API calls uses Kubernetes NetworkPolicies to implement default-deny egress, allowing only connections to `api.anthropic.com` on port 443. For FQDN-based policies, Cilium CNI provides `CiliumNetworkPolicy` resources that filter by domain name rather than IP addresses.

**Runtime monitoring** with CNCF Falco (graduated project) detects anomalous container behavior at the kernel level via eBPF. Custom rules can alert on unexpected outbound connections or secret file access patterns from AI containers.

**API key rotation** should occur every 60-90 days using a dual-key overlap pattern: generate new key while old remains active, deploy via rolling update, verify functionality, then revoke the old key. Anthropic partners with GitHub Secret Scanning to automatically detect leaked keys in repositories.

## Headless operation and CI/CD integration patterns

Claude Code's `-p` (print) flag enables non-interactive operation essential for containers:

```bash
claude -p "Review code for security issues" \
  --allowedTools "Read,Grep,Glob" \
  --output-format json \
  --max-turns 10
```

The `--dangerously-skip-permissions` flag bypasses interactive permission prompts but should only be used in **isolated environments** where the container has no access to sensitive host resources. Anthropic's official devcontainer includes network firewall rules that whitelist only GitHub, npm registry, and Anthropic API endpoints.

For authentication in headless environments, set `ANTHROPIC_API_KEY` as an environment variable—OAuth browser flows are incompatible with non-interactive containers. When using API keys, charges apply at pay-as-you-go rates regardless of any Claude subscription. Pre-configure `~/.claude/settings.json` to skip onboarding prompts:

```json
{
  "hasCompletedOnboarding": true,
  "env": {
    "ANTHROPIC_API_KEY_FILE": "/run/secrets/anthropic_key"
  }
}
```

## Conclusion

Successful Claude Code containerization balances developer velocity with security rigor. **Anthropic's official devcontainer reference** provides a production-ready starting point, while the devcontainer feature enables rapid integration. The non-negotiable security requirements are runtime credential injection (never build-time), non-root execution, and capability dropping. MCP servers demand careful attention to transport selection—STDIO for local Docker execution, HTTP for remote services—with explicit volume mounts for filesystem access. Organizations should implement automated secret rotation through cloud KMS integration, network egress filtering to restrict API endpoints, and runtime monitoring via Falco to detect anomalous behavior in AI workloads.
