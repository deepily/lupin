## What We Know

### The Full Call Chain (Verified)
```
job.py:207    cosa_interface.TARGET_USER = self.user_email  ← SET HERE
job.py:215    await voice_io.notify("Starting...")
                → core voice_io.notify()
                  → is_voice_available()  [first call: sends "Initializing..." ping]
                    → _cosa_interface.notify_progress("Initializing...", priority="low")
                      → _dispatcher.target_user = TARGET_USER  ← READ HERE
                        → AsyncNotificationRequest(target_user=self.target_user)
                          → notify_user_async(request)
                            → if request.target_user is None: resolve_target_user()  ← FAILS
```

### The Docker Factor
- Server runs in Docker (`172.19.0.1` = Docker bridge IP)
- Container path: `/var/lupin/src` (volume mount of host project dir)
- `LUPIN_DEV_EMAIL` set on host BUT: **not automatically visible inside container** unless passed via `-e` or `.env`
- `~/.notifications/config` set on host BUT: **different `~` inside container**

### What Still Fails (4 errors)
```
Running AgenticJob [podcast]...
HTTP 200 OK
Failed to send progress notification: Cannot resolve target_user...  (×4)
```

### Open Questions
1. **Did our code actually get loaded?** Volume mount + restart should work, but unconfirmed
2. **Is there a SECOND notification path?** The explore agent found 13 different files creating notification requests. Some bypass the dispatcher entirely (e.g., `fifo_queue.py:480`, `expeditor.py:624`)
3. **Docker env isolation**: Even with our code fix working perfectly, if `resolve_target_user()` is called as a fallback anywhere, it fails inside Docker because neither `LUPIN_DEV_EMAIL` nor `~/.notifications/config` exist in the container
