# SWE Team Trust Proxy: End-to-End Conceptual Overview

## Context

You want to understand how the entire decision proxy system works — from cold start
with no data, through bootstrapping with seed scenarios, to running in shadow mode,
and finally to the proxy generating autonomous predictions/actions. This document
traces the data flow across every component and shows where **your human judgment**
enters the loop to train the system.

---

## The Core Problem

When you launch a SWE Team agentic job at 8 PM and go to bed, the job blocks at its
first decision: "Should I deploy the hotfix?", "Run the test suite?", "Delete the
stale branch?". Each decision generates a voice notification and waits. Ten decisions
= ten interruptions = you're babysitting an agent.

**The proxy replaces real-time babysitting with asynchronous batch review.**

---

## The 5 Stages (Your Journey)

```
Stage 1: Bootstrap (Seed Data)       → Cold start: no decisions exist yet
Stage 2: Shadow Mode (L1)            → Proxy observes but never acts
Stage 3: Provisional Mode (L2)       → Proxy suggests; you ratify each one
Stage 4: Trusted Mode (L3+)          → Proxy acts on high confidence; queues the rest
Stage 5: Autonomous/Full Trust (L4-5) → Proxy handles most/all decisions
```

Each stage builds on the training signal from the previous one.

---

## Stage 1: Bootstrap — Generating Seed Data

### Why You Need It

The CBR (Case-Based Reasoning) engine predicts decisions by finding similar past
decisions and doing a majority vote. With zero data, it has nothing to compare against.
Seed data gives it a starting vocabulary of 50 realistic scenarios.

### What the Seed Script Does

**Script**: `src/scripts/seed_proxy_decisions.py`

```bash
# Step 1: Preview — see all 50 scenarios (no side effects)
python src/scripts/seed_proxy_decisions.py --dry-run

# Step 2: Insert — populate PG + LanceDB with 50 decisions
python src/scripts/seed_proxy_decisions.py

# Step 3: Ratify — apply your judgment to all 50 decisions
python src/scripts/seed_proxy_decisions.py --ratify --user-email you@example.com

# Step 4: Verify — confirm CBR can make predictions
python src/scripts/seed_proxy_decisions.py --verify
```

### Data Flow During Seeding

```
SCENARIO_CATALOG (50 Python dicts)
  │
  │  Each scenario has:
  │    question:               "Should I deploy the auth hotfix to production?"
  │    category:               "deployment"
  │    expected_decision:      "requires_review"
  │    suggested_ratification: "approve" or "reject"
  │    semantic_group:         "prod-deploy" (clusters similar questions)
  │    rationale:              "Hotfix for critical auth bug — correct to flag"
  │
  ├──→ PostgreSQL (proxy_decisions table)
  │      Row with: domain="swe", category="deployment", action="shadow",
  │                data_origin="synthetic_seed", ratification_state="pending"
  │
  └──→ LanceDB (proxy_decisions vector store)
         Row with: 768-dim embedding of question text, category, decision_value
         Embedding generated via: POST /api/embeddings/generate (GPU model on server)
```

### The 50 Scenarios Across 6 Categories

| Category     | Count | Cap Level | Approve/Reject Mix | Example                                           |
|-------------|-------|-----------|--------------------|----------------------------------------------------|
| Deployment   | 9     | L3        | 3 approve / 6 reject | "Deploy hotfix to prod?" vs "Skip review for deadline?" |
| Testing      | 9     | L5        | 7 approve / 2 reject | "Run pytest suite?" vs "Skip tests for speed?"     |
| Dependencies | 8     | L5        | 6 approve / 2 reject | "Update minor versions?" vs "Major framework upgrade?" |
| Architecture | 8     | L3        | 5 approve / 3 reject | "Extract helper class?" vs "Rewrite core module?"  |
| Destructive  | 8     | L3        | 3 approve / 5 reject | "Delete stale branch?" vs "Force push to main?"    |
| General      | 8     | L5        | 6 approve / 2 reject | "Add docstrings?" vs "Disable logging in prod?"    |

**Semantic groups** ensure multiple phrasings of the same intent exist (e.g.,
"deploy hotfix to prod" and "push auth fix to production environment"), so the
embedding similarity search can generalize across paraphrases.

### The Ratification Step

When you run `--ratify`, the script applies each scenario's `suggested_ratification`
(approve/reject) to the PostgreSQL record, simulating what you'd do manually on the
Ratification UI. This creates **training signal**: the CBR now has 50 decisions with
known-good verdicts.

**After ratification**, the `data_origin` column distinguishes this seed data from
organic (real) decisions:
- `synthetic_seed` — from the seed script
- `organic` — from real job executions
- `synthetic_generated` — from future augmentation

### Verification

`--verify` runs a spot-check: for a sample question in each category, it calls
`CBRDecisionStore.predict()` and confirms the returned verdict is not None. This
proves the embedding similarity search + majority vote pipeline is functional.

## Stage 2: Shadow Mode (L1) — Observing Without Acting

### How You Enter Shadow Mode

```bash
# Set the trust mode globally
PUT /api/proxy/mode  { "mode": "shadow" }

# Or start the proxy agent in shadow mode
python -m cosa.agents.decision_proxy --profile swe_team --trust-mode shadow
```

### What Happens at Runtime

You launch a SWE Team agentic job (via CJ Flow). As the job runs, it encounters
decisions:

```
SWE Team Job (running in CJ Flow)
  │
  │ Job needs approval: "Should I run the regression suite?"
  │
  ├──→ POST /api/notify (response_requested=true, response_type="yes_no")
  │      Server creates Notification in PostgreSQL (state=pending)
  │      Server opens SSE stream (blocks until response or timeout)
  │      Server emits notification_queue_update via WebSocket
  │
  ├──→ WebSocket event reaches Decision Proxy listener
  │      │
  │      ├── 1. Extract: notification_id, message, sender_id, response_type
  │      ├── 2. Check sender_id against accepted_senders list
  │      ├── 3. Classify: SWE Strategy evaluates → category="testing"
  │      ├── 4. Check trust: TrustTracker.get_level("testing") → L1
  │      ├── 5. L1 = Shadow → LOG ONLY, do NOT respond
  │      └── 6. Persist to proxy_decisions: action="shadow", data_origin="organic"
  │             Also write embedding to LanceDB
  │
  └──→ WebSocket event also reaches YOUR browser
         You see the notification in the UI
         You respond manually: "yes"
         POST /api/notify/response → SSE stream yields → Job unblocks
```

### Key Insight: Shadow Mode Is Data Collection

In shadow mode, the proxy is **passively learning** from your real decisions:

1. The proxy logs what it *would* have decided (shadow record)
2. You actually respond (organic decision)
3. Later, when you ratify shadow records, you're telling the proxy "yes, you
   would have been right" or "no, you would have been wrong"

**Your manual responses during this phase are the ground truth** that trains the
system. Every "yes" you click, every "no" you choose — these become CBR training
examples with `data_origin=organic`.

## Stage 3: How Your Judgment Enters the System

### The Morning Coffee Workflow

After the overnight job completes (or the next morning):

```
1. Open Trust Dashboard        → /app/admin/proxy-dashboard
   │
   │  See 6 trust cards (one per category):
   │    Testing:      L1 Shadow | 12 decisions | 0% success rate
   │    Deployment:   L1 Shadow | 4 decisions  | 0% success rate
   │    Destructive:  L1 Shadow | 2 decisions  | 0% success rate
   │    ...
   │
2. Open Pending Ratification   → /app/admin/proxy-ratify
   │
   │  See all shadow decisions the proxy logged:
   │    "Should I run regression suite?"     → category: testing     → [Approve] [Reject]
   │    "Deploy hotfix to staging?"          → category: deployment  → [Approve] [Reject]
   │    "Delete unused migration files?"     → category: destructive → [Approve] [Reject]
   │
3. You ratify each decision
   │
   │  POST /api/proxy/ratify/{decision_id}
   │    approved=true/false, user_email=you@..., feedback="looks good"
   │
   └──→ PostgreSQL updates:
          proxy_decisions: ratification_state → approved/rejected
          trust_states: total_decisions++, successful_decisions++ (or rejected++)
          LanceDB: ratification_state updated for embedding record
```

### The Trust State Update Cycle

```
                    ┌─────────────────────────────────┐
                    │     Your Ratification Action     │
                    │   (Approve or Reject decision)   │
                    └───────────────┬─────────────────┘
                                    │
                    ┌───────────────▼─────────────────┐
                    │     ProxyDecisionRepository      │
                    │   .ratify( id, approved=True )   │
                    └───────────────┬─────────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
    ┌─────────▼──────────┐ ┌───────▼────────┐  ┌─────────▼──────────┐
    │  proxy_decisions   │ │  trust_states  │  │  LanceDB vectors   │
    │  table updated:    │ │  table updated:│  │  record updated:   │
    │  ratification_state│ │  total++       │  │  ratification_state│
    │  ratified_by       │ │  successful++  │  │  (for CBR training)│
    │  ratified_at       │ │  or rejected++ │  │                    │
    └────────────────────┘ └───────┬────────┘  └────────────────────┘
                                   │
                    ┌──────────────▼──────────────────┐
                    │    TrustTracker recalculates    │
                    │    CategoryTrust for category    │
                    │                                  │
                    │  success_rate = successful/total │
                    │  + time-weighted decay           │
                    │  + trust model (count/beta/BLR)  │
                    │  → New trust level computed      │
                    └──────────────┬──────────────────┘
                                   │
                    ┌──────────────▼──────────────────┐
                    │   Trust level may graduate:     │
                    │   L1 → L2 at 50 decisions       │
                    │   L2 → L3 at 200 decisions      │
                    │   L3 → L4 at 500 decisions      │
                    │   L4 → L5 at 1000 decisions     │
                    │   (requires high success rate)   │
                    └─────────────────────────────────┘
```

### Three Trust Models (How Level Is Calculated)

1. **Count-based** (`trust_model="count"`): Simple threshold — "have we seen enough
   decisions in this category?" Time-weighted decay means older decisions count less.

2. **Beta-Bernoulli** (`trust_model="beta"`): Statistical model using the Beta
   distribution. Requires both minimum sample count AND 95% credible interval lower
   bound above the rate threshold. More conservative — won't promote on thin data.

3. **Bayesian Logistic Regression** (`trust_model="blr"`): 4-feature model using
   category_index, question_length, hour_of_day, and recent_error_rate. Online
   Bayesian updates via Sherman-Morrison inverse. Most sophisticated but needs more
   data.

## Stage 4: From Shadow to Predictions — The CBR Engine

### How Predictions Work

When the proxy encounters a new decision, the CBR engine activates:

```
New question arrives: "Can I add smoke tests for the auth endpoints?"
  │
  ├── 1. Generate 768-dim embedding via GPU model
  │      POST /api/embeddings/generate → [0.12, -0.34, 0.56, ...]
  │
  ├── 2. Vector similarity search in LanceDB
  │      find_similar( embedding, category="testing", top_k=5, threshold=0.75 )
  │      │
  │      Returns top-5 most similar past decisions:
  │        0.92 — "Add unit tests for registration endpoint" → approved
  │        0.89 — "Add smoke tests for WebSocket endpoints"  → approved
  │        0.87 — "Add integration tests for the new module" → approved
  │        0.82 — "Run full pytest regression suite"          → approved
  │        0.78 — "Update test fixtures for new API format"   → approved
  │
  ├── 3. Majority vote
  │      5/5 cases say "approved" → verdict = "approved"
  │
  ├── 4. Confidence scoring
  │      max_similarity    = 0.92
  │      verdict_consistency = 5/5 = 1.0
  │      confidence         = 0.92 * 1.0 = 0.92
  │
  └── 5. CBRPrediction returned
         verdict    = "approved"
         confidence = 0.92
         case_count = 5
```

### Where CBR Fits in the Decision Pipeline

```
Notification arrives
  │
  ├── SWE Strategy classifies → category = "testing"
  │
  ├── TrustTracker checks level → L2 (50+ decisions, high success rate)
  │
  ├── Trust mode = "suggest" (or "active")
  │
  ├── CBR prediction requested:
  │     CBRDecisionStore.predict( question, category, embedding )
  │     → CBRPrediction( verdict="yes", confidence=0.92 )
  │
  ├── Decision gating:
  │     If L2 (Provisional):
  │       → Queue for ratification (suggested="yes", pending your review)
  │     If L3 (Trusted) + confidence > 0.80:
  │       → ACT autonomously (submit "yes" to the job)
  │     If L3 + confidence < 0.80:
  │       → Queue for ratification
  │     If L4-L5:
  │       → ACT on almost everything
  │
  └── Decision persisted to PostgreSQL + LanceDB
        (regardless of action taken)
```

```bash

PUT /api/proxy/mode  { "mode": "active" }

# 2. Launch SWE Team job via CJ Flow
```

### The Flywheel Effect

Every ratification you do:
1. Updates trust_states counters
2. Updates LanceDB embedding records
3. Feeds the CBR with more training examples
4. Trust levels gradually climb
5. More decisions get handled autonomously
6. Fewer decisions need your review next time

**Net effect**: First week = 30 decisions to review per job. After a month = 3-5.

## Safety Mechanisms

### Circuit Breaker

If the proxy starts making bad decisions (>15% rejection rate), the circuit breaker
trips:

```
TrustTracker detects: error_rate > 0.15 for "deployment"
  │
  ├── Circuit breaker TRIPS
  ├── Trust level demoted by 2 levels (L4 → L2)
  ├── 1-hour cooldown period
  └── All "deployment" decisions now queue for ratification
```

### Category Caps

Some categories are permanently capped to prevent full autonomy on high-risk
decisions:

| Category     | Max Level | Meaning                              |
|-------------|-----------|--------------------------------------|
| Deployment   | L3        | Always queues low-confidence deploys |
| Architecture | L3        | Never fully autonomous on arch       |
| Destructive  | L3        | Force push/delete always reviewed    |
| Testing      | L5        | Can reach full autonomy              |
| Dependencies | L5        | Can reach full autonomy              |
| General      | L5        | Can reach full autonomy              |

### Time-Weighted Decay

Trust decays over time (14-day half-life). If you stop using the system for a month,
trust levels gradually drop, requiring re-validation. This prevents stale trust from
persisting when the codebase or team practices change.

## Quick-Start Checklist

1. **Ensure prerequisites**: FastAPI server running on :7999, PostgreSQL up, LanceDB
   directory accessible

2. **Run seed script** (one-time bootstrap):
   ```bash
   python src/scripts/seed_proxy_decisions.py --dry-run     # Preview
   python src/scripts/seed_proxy_decisions.py                # Insert 50 scenarios
   python src/scripts/seed_proxy_decisions.py --ratify --user-email you@example.com
   python src/scripts/seed_proxy_decisions.py --verify       # Confirm CBR works
   ```

3. **Start in shadow mode** (observe first):
   ```bash
   python -m cosa.agents.decision_proxy --profile swe_team --trust-mode shadow
   ```

4. **Launch a SWE Team job** and work normally — decisions flow to you as usual,
   proxy silently logs what it would have done

5. **Review shadow decisions** on the Ratification page — approve/reject to create
   training signal

6. **Graduate to suggest mode** when ready:
   ```bash
   PUT /api/proxy/mode  { "mode": "suggest" }
   ```

7. **Graduate to active mode** when trust levels reach L3+ in categories you're
   comfortable automating

8. **Monitor daily** via Trust Dashboard — the flywheel takes care of the rest
