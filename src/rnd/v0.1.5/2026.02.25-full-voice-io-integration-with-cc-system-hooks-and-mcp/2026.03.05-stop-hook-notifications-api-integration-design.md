# Claude Code Stop Hook × CoSA Voice Integration

## Design Document — Pseudocode & Architecture

---

## Problem Statement

When Claude Code finishes a task, we want to:

1. Drain any buffered voice commands that arrived while Claude was working
2. Ask the user (via voice) if they have additional work
3. Only allow Claude to stop when the user explicitly dismisses

Claude Code's **Stop hook** fires every time Claude finishes responding. It can
block the stop and redirect Claude with a new instruction. CoSA/Lupin's
**`notify_user_sync`** primitive sends a blocking yes/no question to the user
via voice (TTS prompt → STT response) and returns the answer synchronously.

---

## Key Concepts

### Stop Hook I/O Contract

**Input** (JSON via stdin):

```
{
  "session_id":       "abc123",
  "transcript_path":  "~/.claude/projects/.../UUID.jsonl",
  "cwd":              "/home/rick/my-project",
  "permission_mode":  "default",
  "hook_event_name":  "Stop",
  "stop_hook_active": false | true
}
```

**Output** (JSON to stdout, exit 0):

```
To BLOCK the stop and redirect Claude:
  { "decision": "block", "reason": "instruction string for Claude" }

To ALLOW the stop:
  exit 0 with no output (or empty JSON)
```

The `reason` string becomes Claude's literal next instruction — it is freeform
natural language that Claude treats as a direct prompt.

### The `stop_hook_active` Flag

- `false` on Claude's first attempt to stop
- `true` on subsequent stop attempts that result from a previous block

This flag exists to prevent infinite loops. See "Why Infinite Loops Happen"
below for why we don't need it in our design.

### CoSA `notify_user_sync`

A blocking RPC call to the Lupin app server. Speaks a prompt via TTS, listens
for a yes/no answer via STT, returns the boolean result. Defaults to `NO` on
timeout.

```
notify_user_sync(session_id, message, default=NO, timeout=30s) → bool
```

## Final Design — Pseudocode

```
ON_STOP_HOOK(session_id, stop_hook_active):

    # ── Phase 1: Drain the voice command buffer ─────────────────
    #
    # Check if any voice commands arrived while Claude was working.
    # These are buffered in Lupin, keyed by session_id.

    buffered_command = CHECK_LUPIN_QUEUE(session_id)

    IF buffered_command EXISTS:
        BLOCK("Voice command received: {buffered_command}")
        RETURN
        # Claude executes the command → eventually tries to stop again
        # → this hook fires again → loops back to Phase 1


    # ── Phase 2: Ask the user via voice ─────────────────────────
    #
    # No buffered commands. Ask user directly through CoSA voice.
    # This call BLOCKS until the user responds or timeout.

    user_wants_more = NOTIFY_USER_SYNC(
        session_id,
        "I've finished the current task. Is there anything else?",
        default = NO,
        timeout = 30 seconds
    )

    IF user_wants_more:
        BLOCK("The user wants to continue. Ask them what they'd like done next.")
        RETURN
        # Claude asks the user → user provides new task → work happens
        # → Claude finishes → this hook fires again → loops back to Phase 1

    ELSE:
        ALLOW_STOP
        # User said no (or timeout) → Claude exits cleanly
```

## Why Infinite Loops Cannot Happen

In the naive approach (without `notify_user_sync`), the Stop hook speculatively
blocks with "ask the user if they want more," Claude asks, the user says no,
Claude says goodbye, and the Stop hook fires again — with no way to know the
user already declined. This creates an inescapable loop.

Our design eliminates this because **the hook itself resolves the user's intent
before returning**. The `notify_user_sync` call blocks within the hook process,
gets a definitive yes/no, and only then decides to block or allow. There is no
speculative blocking — every BLOCK is backed by either a concrete buffered
command or a confirmed "yes" from the user.

```
Naive approach (dangerous):
  Hook blocks speculatively → Claude asks → user says no →
  Claude responds → Stop fires → Hook blocks speculatively → ∞

Our approach (safe):
  Hook asks user directly → user says no →
  Hook returns ALLOW_STOP → Claude exits. Done.
```

The `stop_hook_active` flag becomes unnecessary for loop prevention but remains
available as a useful signal (e.g., for telemetry or adjusting timeout behavior
on repeated stops).

---

## Decision Matrix

```
                     │  buffer has command  │  buffer empty
─────────────────────┼──────────────────────┼──────────────────────
                     │                      │
any stop attempt     │  BLOCK               │  ask user via voice
                     │  (drain the buffer)  │    ├─ yes → BLOCK
                     │                      │    └─ no  → ALLOW STOP
                     │                      │
```

Note: unlike the `stop_hook_active`-based approach which limits you to a single
bounce, this design supports unlimited continuation rounds. The user can say
"yes" repeatedly, provide new tasks each time, and the loop continues naturally
until they say "no."

## Integration Points

### Hook Configuration (settings.json)

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ~/.claude/hooks/cosa_stop_hook.py"
          }
        ]
      }
    ]
  }
}
```

### Session ID Routing

The Stop hook receives `session_id` via stdin JSON. This same ID is used to:

- Query the correct Lupin voice command buffer (`/api/pending-commands/{session_id}`)
- Route `notify_user_sync` to the correct voice channel
- Ensure multi-instance isolation (multiple Claude Code sessions in same repo)

Session ID is obtained via the **SessionStart hook → session file bridge**
pattern (see `session_bridge.py` and `register_session.py`).

### Dependencies

- **Lupin app server** running at configurable URL (default `http://localhost:7999`)
- **`/api/pending-commands/{session_id}`** — GET endpoint returning `{"command": "..." | null}`
- **`notify_user_sync(session_id, message, default, timeout)`** — blocking voice RPC
- **jq or Python** for JSON parsing in the hook script

---

## Edge Cases

| Scenario | Behavior |
|---|---|
| Lupin server unreachable | Treat as "no buffered commands" + skip voice prompt → ALLOW_STOP |
| Voice timeout (user doesn't respond) | `notify_user_sync` defaults to NO → ALLOW_STOP |
| User speaks while Claude is working | Command buffered in Lupin → drained on next Stop |
| Multiple commands buffered | Drain one per Stop cycle; subsequent commands caught on next Stop |
| Claude interrupted mid-task (Ctrl+C) | Stop hook does NOT fire on user interrupts — only on Claude's voluntary stop |

## Open Questions

1. **Should the voice prompt vary based on `stop_hook_active`?** E.g., first
   stop says "I've finished. Anything else?" while subsequent stops say
   "Done with that. Anything more?"

2. **Should we consume ALL buffered commands at once** and concatenate them into
   a single BLOCK reason, or drain one at a time? Single drain is simpler but
   adds round-trips.

3. **Timeout tuning**: 30 seconds is generous for voice. Consider shorter
   timeouts (10-15s) for subsequent rounds where the user is already engaged.
