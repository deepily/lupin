## Revision 3: Stateful Notification Listener (Major Architecture Change)

**Original**: Ephemeral hooks query PostgreSQL via HTTP at each invocation (DB accumulation + hook drain)
**Revised**: A stateful WebSocket notification listener runs for the duration of each CC session

### Architecture

**Key insight**: Hooks are ephemeral subprocesses that can't hold WebSocket connections. But we already have a battle-tested stateful WebSocket client in the notification proxy infrastructure.

**Reuse from existing codebase**:
- `src/cosa/agents/utils/proxy_agents/base_listener.py` — Abstract WebSocket client with auth, keep-alive, reconnection backoff
- `src/cosa/agents/utils/proxy_agents/base_config.py` — Connection defaults, credential resolution
- `src/cosa/agents/utils/proxy_agents/base_cli.py` — Shared CLI args
- `src/tests/smoke/utilities/embedded_proxy.py` — Subprocess spawn/shutdown patterns

### New component: CC Notification Listener

Subclasses `base_listener.py`. Instead of auto-responding to notifications (like the proxy), it **buffers** `user_initiated_message` events to a local JSONL file.

**Lifecycle**:
1. SessionStart hook spawns listener as background subprocess
2. Listener authenticates as `claude.code@lupin.deepily.ai` (dedicated account)
3. Listener connects via WebSocket, subscribes to `notification_queue_update`
4. Listener filters by `job_id` matching its CC session hash
5. Matching messages appended to `~/.claude/sessions/cc-buffer-{session_id[:8]}.jsonl`
6. Any hook calls `drain_voice_buffer()` — atomic rename-read-delete
7. SessionEnd hook sends SIGTERM, listener shuts down gracefully

### Credentials

- **Config file**: `~/.lupin/credentials.ini` (user-scoped, NOT in project keys dir)
- **Format**: INI with per-project sections
  ```ini
  [lupin]
  email = claude.code@lupin.deepily.ai
  password = ...

  [cosa]
  email = claude.code@cosa.deepily.ai
  password = ...
  ```
- **Resolution**: Hook reads `cwd` from payload -> derives project name -> reads matching INI section
- **Each project gets its own account** in the auth database
- **One account, multiple listeners**: Each CC instance spawns its own listener, all authenticate with same project credentials
- **Session scoping**: `job_id` field in notifications discriminates which CC session a message targets
- **No env vars needed**: Replaces original `CLAUDE_CODE_AT_LUPIN_EMAIL/PASSWORD` approach

### Runtime Observability (Debug, Verbose, Logging)

| Flag | Behavior |
|------|----------|
| `--debug` | Print connection events, auth status, message filtering decisions |
| `--verbose` | Print full message payloads (implies debug) |
| `--log-file PATH` | Tee all output to a log file (default: stdout only) |

**SessionStart hook passes flags**:
- `--log-file` is **always passed** (enables `tail-cc-listeners.sh` aggregator)
- `LUPIN_CC_HOOK_LISTENER_DEBUG=true` -> adds `--debug`
- `LUPIN_CC_HOOK_LISTENER_VERBOSE=true` -> adds `--verbose`

### Buffer Mechanism

**Writing** (Listener side): Appends JSONL lines to buffer file
**Reading** (Hook side): Atomic rename to random `/tmp/cc-drain-{session[:8]}-{random}.jsonl`, read, delete

**Why random drain path**: Prevents collision if two hooks fire simultaneously. Only one `os.rename()` succeeds; the other gets `FileNotFoundError` and returns empty.

### Multi-Instance Routing

All listeners receive all notifications via WebSocket broadcast (same user_id). Each filters locally:
- `if notification.get("job_id") == self.session_id_hash: buffer it`
- WebSocket session name: `cc-listener-{session_hash}` (unique per instance)

## Automated Testing Strategy

**No manual interaction required.** Uses existing `embedded_proxy.py` subprocess patterns.

| Test | What It Validates |
|------|-------------------|
| **Lifecycle** | Spawn listener, verify running, SIGTERM, verify clean exit |
| **Accumulation + Drain** | Send 3 messages via API, drain buffer, verify all 3 arrive in order |
| **Atomicity** | Drain mid-accumulation, verify no messages lost across 2 drains |
| **Reconnection** | Integration-tier: verify listener reconnects after WebSocket drop |

**Test credentials**: Read from `~/.lupin/credentials.ini` `[lupin]` section
**Test location**: `src/tests/smoke/test_cc_notification_listener.py`

## Monitoring

### Always-On Log Files

Log files are **always written** for every listener — no env var required. The `LUPIN_CC_HOOK_LISTENER_LOG`
env var is no longer checked; `--log-file` is passed unconditionally by `_spawn_listener()`.

**Location**: `~/.claude/sessions/cc-listener-{session_hash}.log`

Debug and verbose output remain opt-in via `LUPIN_CC_HOOK_LISTENER_DEBUG` and `LUPIN_CC_HOOK_LISTENER_VERBOSE`.

### Live Aggregator: `tail-cc-listeners.sh`

Aggregates live output from all active CC Notification Listeners into a single color-coded stream.

```bash
src/scripts/tail-cc-listeners.sh              # active listeners only
src/scripts/tail-cc-listeners.sh --all        # include stale logs too
src/scripts/tail-cc-listeners.sh --no-color   # for piping to files
src/scripts/tail-cc-listeners.sh --filter ID  # show only matching session(s)
```

Each session's output is prefixed with a color-coded `[hash]` tag (colors assigned round-robin
from red, green, yellow, blue, magenta, cyan). Uses `tail -F` for live following with log rotation support.

### Point-in-Time Status: `check-cc-listener-status.sh`

Shows process status, bridge files, and server-side WebSocket sessions:

```bash
src/scripts/check-cc-listener-status.sh          # full check (process + server)
src/scripts/check-cc-listener-status.sh --local   # process check only
```
