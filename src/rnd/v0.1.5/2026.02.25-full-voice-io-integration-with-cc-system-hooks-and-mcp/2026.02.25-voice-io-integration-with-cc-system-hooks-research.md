# Claude Code hooks: the complete I/O contract reference

**Claude Code exposes 18 hook events as of v2.1.50 (February 2026), five of which were added since January 2026.** Every hook receives structured JSON on stdin and communicates back via exit codes plus optional JSON on stdout — but the exact fields available for injection, blocking, and modification vary dramatically by event type. The Stop hook cannot inject `additionalContext`; it uses `decision: "block"` with a `reason` string to force continuation. MCP sampling remains unsupported. The Claude Agent SDK (renamed from Claude Code SDK) provides token-level streaming and additional hook events unavailable in the CLI hook system.

---

## All 18 hook events and when they fire

Claude Code's hook system has grown from 10 core events to **18 distinct lifecycle events**. Five hooks were added in February 2026 alone to support multi-agent teams, enterprise config auditing, and custom version control. Every hook receives a common base payload on stdin containing `session_id`, `transcript_path`, `cwd`, `permission_mode`, and `hook_event_name`. Event-specific fields extend this base.

The complete taxonomy breaks into four categories. **Session lifecycle** hooks include SessionStart (fires on startup, resume, clear, compact), SessionEnd (fires on exit/logout), and the new Setup hook (fires on init and maintenance). **Conversation loop** hooks cover the main agent interaction: UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Notification, and Stop. **Agent orchestration** hooks handle multi-agent scenarios: SubagentStart, SubagentStop, and the new TeammateIdle and TaskCompleted events (added in **v2.1.33, February 6, 2026**). **Infrastructure** hooks manage system-level concerns: PreCompact, ConfigChange (**v2.1.49, February 19**), WorktreeCreate, and WorktreeRemove (both **v2.1.50, February 20**).

Three handler types exist for hooks: `command` (shell scripts receiving JSON stdin), `prompt` (single-turn LLM evaluation via Haiku), and `agent` (spawns a subagent with tool access for up to 50 turns). Not all events support all three types — WorktreeCreate/Remove, SessionStart/End, ConfigChange, TeammateIdle, Notification, SubagentStart, and PreCompact support **only** `command` hooks.

## Exit code semantics and the blocking model

The exit code system is deceptively simple: **exit 0** means success (stdout parsed for JSON), **exit 2** means blocking error (only stderr used), and **any other code** is a non-blocking error. But the consequences of exit code 2 vary significantly by event:

| Hook Event | Exit 0 (JSON parsed) | Exit 2 (blocking) | Can block? |
|---|---|---|---|
| **PreToolUse** | Allow/deny/ask + modify input | Blocks tool call, stderr → Claude | ✅ |
| **PermissionRequest** | Allow/deny + modify input | Denies permission, stderr → Claude | ✅ |
| **PostToolUse** | Inject additionalContext | Stderr → Claude (feedback only) | Feedback |
| **PostToolUseFailure** | Inject additionalContext | Stderr → Claude | Feedback |
| **UserPromptSubmit** | Inject context or block | Blocks prompt, erases it, stderr → user | ✅ |
| **Stop** | Block stopping via decision | Forces continuation, stderr → Claude | ✅ |
| **SubagentStop** | Block stopping via decision | Forces continuation, stderr → subagent | ✅ |
| **TaskCompleted** | Exit codes only | Blocks task completion | ✅ |
| **TeammateIdle** | Exit codes only | Forces teammate to keep working | ✅ |
| **ConfigChange** | Block config changes | Blocks config change | ✅ |
| **Notification** | No decision control | Stderr → user only | ❌ |
| **PreCompact** | Inject customInstructions | Stderr → user only | ❌ |
| **SessionStart** | Inject additionalContext | Stderr → user only | ❌ |
| **SessionEnd** | Cleanup only | Stderr → user only | ❌ |

When exit code is 0, all hooks can return common JSON fields: `continue` (boolean; false halts Claude entirely), `stopReason` (shown to user when continue is false), `suppressOutput` (hide from transcript), and `systemMessage` (warning to user). The field **`continue: false` takes absolute precedence** over any `decision: "block"` output — it terminates the agent.

## Stop hook: the re-injection mechanism explained

The Stop hook is the most misunderstood event. **It does not support `additionalContext` or `continue: true` for forcing continuation.** The TypeScript SDK type definition confirms the Stop hook's output has no `hookSpecificOutput` variant — only the common fields plus `decision` and `reason`.

The correct re-injection pattern uses `decision: "block"` with a mandatory `reason` string. When a Stop hook returns `{"decision": "block", "reason": "Tests are failing. Fix the errors in auth.ts before stopping."}`, Claude receives the reason as its next instruction and continues working. The input payload includes a critical boolean field: **`stop_hook_active`**, which is `true` when Claude is already continuing due to a previous Stop hook. Failing to check this flag creates infinite loops — the single most common community bug report.

The community has developed several robust patterns. **Taskmaster** (github.com/blader/taskmaster) scans the transcript for incomplete tasks before allowing stops. The **"What's Next?" pattern** (documented on egghead.io) blocks every stop with a reason instructing Claude to use the `AskUserQuestion` tool, creating a persistent guided development loop. **Test validation hooks** run `npm test` and block if failures exist, feeding stderr back as Claude's next instruction. **Prompt-based Stop hooks** (`type: "prompt"`) send context to Haiku for evaluation, returning approve/block without any script. **Agent-based Stop hooks** (`type: "agent"`) spawn a verification subagent that can read files, run grep, and execute commands to assess completeness.

Known limitations: Stop hooks defined in SKILL.md files may not fire (GitHub issue #19225). Plugin-installed Stop hooks using exit code 2 may fail to actually continue (issue #10412). SubagentStop hooks correctly evaluate but have a reported bug where they don't actually prevent subagent termination (issue #20221).

## PreToolUse and PostToolUse: the full modification surface

**PreToolUse** is the most powerful hook, offering three distinct capabilities via `hookSpecificOutput`:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow" | "deny" | "ask",
    "permissionDecisionReason": "string",
    "updatedInput": { "command": "npm run lint --fix" },
    "additionalContext": "Remember to follow ESLint rules"
  }
}
```

The `updatedInput` field performs **transparent input modification** — Claude never sees the change. This enables automatic dry-run flag injection, secret redaction, path normalization, and commit message formatting. The `permissionDecision` field offers three behaviors: `"allow"` bypasses the permission system entirely (reason shown to user, not Claude), `"deny"` blocks execution (reason shown to Claude), and `"ask"` prompts the user for confirmation. The deprecated `decision`/`reason` top-level fields still work (`"approve"` maps to `"allow"`, `"block"` maps to `"deny"`), but `hookSpecificOutput` is preferred.

**PostToolUse** cannot undo tool execution but can inject follow-up context. Its `additionalContext` field (added in **v2.1.9**) provides information Claude processes on its next reasoning step. Combined with `decision: "block"` and a `reason`, PostToolUse effectively gives Claude feedback about the tool result — useful for enforcing code quality standards after file writes. A community pattern runs linters in PostToolUse hooks and feeds violations back as context.

**PostToolUseFailure** mirrors PostToolUse's output schema but adds `error` (string) and `is_interrupt` (boolean) to its input, letting hooks distinguish between genuine failures and user interrupts.

## UserPromptSubmit, Notification, and PermissionRequest contracts

**UserPromptSubmit** supports two injection methods. Plain text stdout (exit code 0) is added as visible "hook output" in the transcript. JSON with `hookSpecificOutput.additionalContext` injects context more discretely. Crucially, **injected text appears as system context, not as user-typed text** — Claude sees it as supplementary information attached to the prompt, not as part of the user's message. The `decision: "block"` option prevents prompt processing entirely and erases the submitted prompt from context, with `reason` shown only to the user.

**Notification** hooks fire on four `notification_type` values: **`permission_prompt`** (Claude needs tool approval), **`idle_prompt`** (Claude waiting for user input after 60+ seconds), **`auth_success`** (authentication completed), and **`elicitation_dialog`** (MCP tool needs user input). The hook **cannot block or modify** notifications — it's observation-only, designed for external alerting systems. The input includes `message` (notification text) and an optional `title` field. Community implementations use Notification hooks to trigger desktop notifications, play audio alerts, and send push notifications to phones.

**PermissionRequest** fires when a permission dialog is about to appear. Its output uses a nested decision object:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": {
      "behavior": "allow" | "deny",
      "updatedInput": { "command": "safer-command" },
      "message": "Denied: destructive operation",
      "interrupt": true
    }
  }
}
```

The `"allow"` behavior can include `updatedInput` to modify tool parameters. The `"deny"` behavior accepts `message` (shown to Claude) and `interrupt` (boolean that stops Claude entirely). **This hook can serve as a voice-driven approval mechanism**: a script listens for spoken "yes"/"no" via local speech recognition, then returns the appropriate JSON decision. The community project **claude-remote-approver** demonstrates a similar pattern using phone push notifications via ntfy.sh. No production voice-approval implementation exists yet, but the architecture — PermissionRequest hook → local STT → JSON decision — is straightforward. Note: PermissionRequest hooks **do not fire in non-interactive mode** (`-p` flag); use PreToolUse for headless automation.

## Five new hooks added since January 2026

**TeammateIdle and TaskCompleted** (v2.1.33, February 6) support the experimental multi-agent teams feature (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). TeammateIdle fires when an agent team member is about to go idle; exit code 2 forces it to keep working. TaskCompleted fires when a task is marked complete via the TaskUpdate tool; exit code 2 prevents completion and feeds stderr back as feedback. TaskCompleted receives `task_id`, `task_subject`, and optionally `task_description`, `teammate_name`, and `team_name`.

**ConfigChange** (v2.1.49, February 19) fires when configuration files (CLAUDE.md, settings.json) change during a session. Designed for enterprise security auditing, it can **block** configuration changes using exit code 2 or `decision: "block"` — with the exception that `policy_settings` changes cannot be blocked. Only supports `command` hooks.

**WorktreeCreate and WorktreeRemove** (v2.1.50, February 20) enable custom version control integration beyond git. WorktreeCreate must print the absolute path to the created worktree on stdout. WorktreeRemove receives `worktree_path` for cleanup. These hooks enable non-git VCS workflows and custom worktree directory layouts (already being used for Laravel Valet/Herd setups).

**What still doesn't exist**: There is **no AssistantOutput hook** for Claude's intermediate text between tool calls (requested in GitHub issue #14859, still open). No AskUser or elicitation-specific hook exists. No hook fires for Claude's streaming text output. The community observability dashboard request for agent hierarchy fields (`agent_id`, `parent_agent_id` in all events) remains unimplemented.

## Claude Agent SDK: streaming and hooks beyond CLI

The SDK was **renamed from Claude Code SDK to Claude Agent SDK** — `@anthropic-ai/claude-agent-sdk` (TypeScript) and `claude-agent-sdk` (Python). It exposes capabilities fundamentally unavailable in CLI hooks.

**Token-level streaming** via `SDKPartialAssistantMessage` (TypeScript) or `StreamEvent` (Python) provides real-time `content_block_delta` events with incremental text and tool input chunks. This is the closest thing to an "AssistantOutput" hook — the SDK yields every token as it's generated, including text between tool calls. Enable with `includePartialMessages: true`. Caveat: when `maxThinkingTokens` is set, streaming events are suppressed and only complete messages are yielded.

**CLI stream-json format** (`--output-format stream-json`) provides JSONL output with each line being a separate JSON message. It begins with an init system message (session metadata), followed by user/assistant messages as they occur, ending with a result message containing `total_cost_usd`, `duration_ms`, and `num_turns`. The `--input-format stream-json` flag accepts JSONL user messages on stdin for programmatic multi-turn conversations.

**Hook event coverage differs significantly**. The TypeScript SDK supports all hook events. Python SDK supports only 6: PreToolUse, PostToolUse, UserPromptSubmit, Stop, SubagentStop, and PreCompact. Notably, **PostToolUseFailure, SubagentStart, PermissionRequest, SessionStart, SessionEnd, and Notification are TypeScript-only**. SDK hooks are in-process callback functions (not subprocess shell commands), with access to `AbortSignal` for cancellation in TypeScript.

The Python SDK has an important split: the simple `query()` function does **not** support hooks, custom tools, or interrupts. The `ClaudeSDKClient` class is required for full hook support, session continuity, and the `interrupt()` method.

## Interrupts, abort mechanisms, and MCP sampling

**CLI interrupts** use Escape or Ctrl+C in interactive mode. In headless mode (`-p`), SIGINT terminates the process. Known reliability issues exist where Escape/Ctrl+C don't consistently stop active tool calls.

**SDK interrupts** offer more control. The TypeScript `Query` object exposes `interrupt()` (streaming input mode only) and accepts an `AbortController` via options. Python's `ClaudeSDKClient` has `interrupt()` for streaming mode. A hook can trigger an abort by returning `{"continue": false, "stopReason": "Aborted by external process"}` — this immediately halts the agent. PermissionRequest hooks can return `deny` with `interrupt: true` to stop Claude on a specific tool call.

**No external signal mechanism** exists for injecting messages into a running Claude session from outside. The closest pattern is **async hooks**: setting `"async": true` on a hook runs it in the background, and when it completes, its `systemMessage` or `additionalContext` is delivered to Claude on the next conversation turn. Timeout can be extended to 10 minutes. However, async hooks fire only from existing hook events — there's no way to push arbitrary messages from an external process.

**MCP sampling (`sampling/createMessage`) is not supported by Claude Code.** This is confirmed by GitHub issue #1785, which has **76+ thumbs-up reactions** making it one of the most requested features. If implemented, MCP servers could request LLM completions through the user's Claude instance, potentially serving as an async notification channel. Security researchers have flagged sampling as an attack surface for resource theft and conversation hijacking, which may explain Anthropic's caution.

## Community voice integration patterns and hook configuration

**Voice input** exists primarily through MCP, not hooks directly. **VoiceMode MCP** (github.com/mbailey/voicemode) is the most mature project, supporting OpenAI-compatible STT/TTS with optional fully local processing via whisper.cpp. **mcp-voice-hooks** (github.com/johnmatthewtennant/mcp-voice-hooks, 60 stars) combines hooks and MCP, using the browser's Web Speech API for zero-dependency STT — users can speak to interrupt or redirect Claude mid-work. For output-only voice, **claude-code-voice-handler** hooks into all lifecycle events and uses GPT-4o-mini to compress verbose outputs for natural speech across 6 voice options.

Hooks are configured in `~/.claude/settings.json` (user), `.claude/settings.json` (project), `.claude/settings.local.json` (local), or plugin `hooks/hooks.json`. Matchers use **case-sensitive regex** — `"bash"` will silently fail to match the `Bash` tool. All matching hooks execute **in parallel** (no sequential option exists; issue #21533 requests it). Identical commands are auto-deduplicated. Configuration is **snapshotted at session startup**; mid-session changes require review via the `/hooks` menu. Environment variables include `CLAUDE_PROJECT_DIR`, `CLAUDE_CODE_REMOTE`, `CLAUDE_PLUGIN_ROOT`, and `CLAUDE_ENV_FILE` (SessionStart only, for persisting environment variables to subsequent bash commands).

## Conclusion

The hook system's power lies in its asymmetry: PreToolUse can modify inputs transparently, but Stop cannot inject context — it can only block with a reason string that becomes Claude's next instruction. The five February 2026 additions (TeammateIdle, TaskCompleted, ConfigChange, WorktreeCreate, WorktreeRemove) reflect Anthropic's priorities in multi-agent orchestration and enterprise governance, not the community's most-requested features (AssistantOutput streaming hook, MCP sampling, sequential hook execution). For real-time text streaming between tool calls, the Agent SDK's `SDKPartialAssistantMessage` with `includePartialMessages: true` is the only viable path — CLI hooks fire only at discrete lifecycle boundaries. Voice-driven approval via PermissionRequest hooks is architecturally sound but lacks a production implementation; the combination of a local STT service with the hook's `allow`/`deny` JSON decision is the clear integration point.
