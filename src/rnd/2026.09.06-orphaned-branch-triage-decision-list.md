## 1. THE HEADLINE — the raw count is inflated by two things, and both are mechanical

`rev-list --count` asks *"is this commit reachable from the line?"*. It is the right question for
the mechanism and the **wrong** question for a triage, because two whole classes answer *no* while
representing no lost work at all.

| | branches | what they are |
|---|---|---|
| raw: ahead of the line | **74** | the population his predicate returns |
| − **historical release lines** | **13** | `wip-v0.1.x`, `wip-v0.2.0`, `v0.6.0-…` — the project's own past. Not orphans; the line diverged from *them* |
| − **fully patch-equivalent** | **14** | every commit already landed by another route. `git cherry` marks them `-` |
| − held by a registered worktree | **27** | has a tree, has a home, somebody can still be asked |
| ⇒ **actually orphaned and carrying new content** | **🔴 15** | no worktree, no live seat, real patches |

⇒ **`git cherry` is the discriminator `rev-list` cannot be.** A branch that was rebased,
cherry-picked or squash-merged is unreachable *and* fully absorbed. Counting it as unmerged work
sends a manager to review something that is already in the tree.

⚠️ **This does NOT weaken his mechanism proposal.** `rev-list` is correct at reap time — it is
cheap, it fails safe, and a false positive there costs one store row. `cherry` is what you want at
**triage** time, when a human is about to spend an hour. Different question, different tool.

## 4. WHAT I DID NOT DO — so nobody reads this as more than a list

- **I deleted nothing, merged nothing, pushed nothing.** Every command above is read-only.
- **I did not read the content of any branch** beyond its commit subjects and file counts. The
  "what it says it is" column is **the author's own subject line**, not my assessment. A subject is
  a claim; nobody has checked one.
- **I did not test any branch for conflicts against the line.** *Reviewable* and *mergeable* are
  different questions and tier 3/4 may be worse than they look.
- **`git cherry` is patch-equivalence, not semantic equivalence.** It compares patch-ids. A commit
  whose change was re-implemented differently upstream reads as `+` and is still redundant — so
  §2's 14 is a **floor** on the deletable set, never a ceiling.
- **The 13 release lines are excluded by NAME MATCH** (`wip-v*`, `v0.6.0-*`). That is a hand-written
  enumeration standing in for a predicate, which this repo files as its own defect class. It is
  right today and will be wrong the first time a release line is named differently.
- **The live-seat check is `tmux ls` at one moment**, 13:36 EDT. A persona can be re-spun a minute
  later and then the branch has an owner again.
