## 0. Read this first — three things that will mislead you if you skip them

**① THIS PANE CANNOT BE BUILT READ-ONLY AGAINST TODAY'S API.** Not because the data is missing —
it is all there — but because no endpoint will hand you *"which rows became terminal in the last 24
hours, with their titles"*. §3 is the whole of that finding and §4 is the one small server-side
change that fixes it. Everything after §5 assumes that change lands. **If you read only one section,
read §3.**

**② THE PANE'S CONTENT IS TINY — 47 rows a day — AND THAT IS WHY IT CAN WORK.** Measured over the
last 24 hours: 584 events total, of which **47 are terminal** (42 done · 5 dropped · 0 won't-fix).
At-a-glance is achievable here in a way it would not be at 500 rows.

**③ `wont_fix` IS AT ZERO IN THE LIVE WINDOW, WHICH LANDS DIRECTLY ON THE ACCEPTANCE TEST.** Two
won't-fix events exist in the last *thirty* days. The companion acceptance arm — *prove dropped and
won't-fix rows exist, are deliberately hidden, and appear when clicked* — **cannot be satisfied
against live data and must seed its own fixture**. §11 says so in the arm itself. A guard that waits
for a real won't-fix row would pass by showing nothing for weeks, which is the exact failure the
acceptance clause exists to prevent.

## 2. Settled before design started — do not re-derive

### 2.1 `wont_fix` is a real, first-class status

Re-derived by me at `1c9a7ea6` (not inherited):


🔴 **Line 39 is exactly Rick's three, SERVER-SIDE, already defined and already terminal.** He did not

and the control can be built exactly as he drew it. No sub-category modelling, no reason-predicate.

The client mirror is `taskListModel.ts:82` (`TERMINAL_STATUSES` as a `ReadonlySet`), but **cite line

### 2.2 A refusal carries its justification

⇒ **Won't-fix and dropped rows are guaranteed to carry a human-written reason.** §6 shows that done

## 3. 🔴 THE BLOCKING FINDING — the data exists and no door serves it

The pane's question is: **which rows became terminal in the last 24 hours, and what are they called?**
Four candidate sources, all measured at `1c9a7ea6`.

### 3.1 `/api/tasks` cannot answer it — four independent reasons

Read from the signature at `src/cosa/rest/routers/tasks.py:1611-1630`:

```
owner_persona · status · gate_class · urgency · accountable_manager · project · item_class
correlation_key · id_prefix · count_only · terse · include_terminal · unscoped_audit
owed_only · hide_parked · limit · offset · char_budget
```

| # | reason | receipt |
|---|---|---|
| 1 | **No time-window parameter.** No `since`, no `until`, no `updated_after`. | the parameter list above — 18 params, none temporal |
| 2 | **It orders by `created_ts` descending**, not by when a row finished. A row created last month and finished ten minutes ago sorts *below* 500 rows created today. | `tasks.py:1650` — *"ordered created_ts descending, stable tiebreak on id"* |
| 3 | **There is no terminal-timestamp column at all.** `grep -n "closed_ts\|terminal_ts\|completed_ts\|finished_ts\|done_ts" src/cosa/rest/postgres_models.py` → **zero hits.** Only `updated_ts`, which moves on *every* write — so amending a three-day-old done row makes it look freshly finished. | `postgres_models.py:1488-1500`, and the zero-hit grep above |
| 4 | **`status` is singular, and `include_terminal=true` is a known 500-cap defect in this codebase.** | see §3.2 |

⚠️ **Reason 2 is fatal on its own**, independent of the others. Even given a working time filter, the
sort order answers a different question than the pane asks.

### 3.2 The 500-cap defect is measured history here, not a hypothetical

`src/lupin_app/static/js/shared/task-list-query.js` says it in its own comment:

> *"NO `include_terminal` — the panel shows work that is still OWED. Pulling done/dropped history was
> the under-reporting bug (2026-07-22, Rick): `include_terminal=true` inflated the result to 1,171
> rows against a server-side `limit` hard-capped at 500, so **671 rows were dropped with no
> indicator** — and because ordering is newest-first, the rows evicted were OPEN ones the renderer
> then could not display."*

And again at `notifications.js:12694`:

> *"Called live against :7999 today, `status=done` returned **EXACTLY 500 of 1,912** matching rows,
> silently."*

⇒ **Any design here that reaches for `include_terminal=true` re-opens a defect this repo has already
eaten twice.** This document does not.

### 3.3 The event stream is the right source, and it nearly works

`GET /api/tasks/events` — `src/cosa/rest/routers/tasks.py:2036-2082`:

| it has | why it is right |
|---|---|
| `since` / `until` **on event ts** | the 24-hour window, server-side |
| ordered **`ts` DESC, id DESC** | newest-*finished*-first — exactly the pane's sort |
| `project`, `actor` filters | scope (§10, Q6) |
| `TaskEvent` carries `ts`, `actor`, `transition`, `receipt_refs`, `reason` | every column §6 wants, except one |

`TaskEvent` is append-only, one row per state change, written in the same transaction as the item
update (`postgres_models.py:1561-1640`). It is the honest record of *when a row became done* and
*who did it*, which is precisely what no column on `TaskItem` stores.

### 3.4 …but three gaps stand between it and the pane

| # | gap | receipt |
|---|---|---|
| **A** | 🔴 **`_serialize_event` returns NO TITLE.** Only `item_id`. The single most important at-a-glance column is not on the wire. | `tasks.py:637-656` — the returned dict is `id · item_id · ts · actor · transition · receipt_refs · authority · reason`. `grep -c title` over that function → **0** |
| **B** | **`transition` is EXACT match** on a `"from->to"` string, so *"anything → done"* is not askable in one call. | `task_repository.py:1383` — `query = query.filter( TaskEvent.transition == transition )` |
| **C** | **The unfiltered fallback truncates silently.** Ask for `since=now-24h` with no transition filter and you need 584 rows against `limit` capped at `le=500`. | measured, §3.5; cap at `tasks.py:1628` `limit: int = Query( default=100, ge=0, le=500 )` |

**On gap B — how bad is the multi-call workaround?** I counted the distinct terminal transitions
actually observed over 30 days:

```
in_progress->done 384 · queued->done 282 · blocked->done 111 · queued->dropped 28
blocked->dropped 25 · review->done 20 · parked->done 19 · parked->dropped 14
in_progress->dropped 11 · not_approved->dropped 4 · not_approved->done 2
review->dropped 1 · not_approved->wont_fix 1 · parked->wont_fix 1
```

**14 distinct transitions observed; the full space is 7 non-terminal sources × 3 terminal targets =
21 calls.** Not viable for a 60-second poll, and it would break the moment a new status is added.

### 3.5 Volume — measured live, 2026-09-06 ~13:10 EDT, `lupin_db_dev`

| population | count |
|---|---|
| all events, last 24h | **584** ← already over the 500 cap |
| **terminal events, last 24h** | **47** |

| ├ `->dropped` | 5 |

## 4. D1 — the one server-side prerequisite (RECOMMENDED SHAPE)

**This is a decision for Rick or María, not mine.** I name a recommendation because a design that
stops at *"the API cannot do this"* leaves the next person to invent the fix under time pressure.

### 4.1 Recommended: two small additions to the existing event endpoint

| change | where | why it is the minimum |
|---|---|---|
| **① add `title` to the event wire shape** | `_serialize_event`, `tasks.py:637` | closes gap A. `TaskEvent.item` is an existing relationship (`postgres_models.py:1632`), so it is `event.item.title` — **but it MUST be eager-loaded** (`joinedload`) or the endpoint becomes N+1 across up to 500 rows |
| **② add a `to_status` filter** matching the part after `->` | `query_events` / `query_event_stream` | closes gaps B and C together. `to_status=done` becomes one call returning 42 rows instead of 21 calls or a 584-row truncation |

**Why `to_status` and not a `transition_suffix` or a comma list:** the store already thinks in
terminal *statuses* (`TERMINAL_STATUSES`, §2.1), the UI filters by status, and Rick asked for status
filters. A parameter named for the thing the caller means survives a schema change to the transition
string; one named for the string does not.

⚠️ **Whether `to_status` accepts one value or several is a real fork.** One value ⇒ the pane makes up
to three calls (one per lit filter — at most 3, cheap, and each returns its own count for the badge).
Several ⇒ one call, but then the 500 cap applies to the union and the counts must be derived
client-side. **I recommend single-valued**, because three small calls give three independent counts
for free (§8) and each stays far under the cap.

### 4.2 Rejected alternatives

| alternative | why rejected |
|---|---|
| **Add `since`/`until` to `/api/tasks`** | it would have to filter on `updated_ts`, which moves on *every* write — an amended done row reads as freshly finished. It also does not fix the `created_ts` sort (§3.1 reason 2). **Wrong column, and it would look right.** |
| **A purpose-built `GET /api/tasks/completed`** | a whole new route, its own auth, its own tests and its own drift surface, to serve what two parameters on an existing route already almost serve. Reach for it only if `to_status` turns out to need a third and fourth friend. |
| **Client-side: pull 500 events and filter in the browser** | 584 > 500 **today**, so it is already broken, silently, in exactly the way §3.2 documents. It also gets worse as the fleet gets busier — the failure arrives without an alarm. |
| **N+1 title fetches from the event list** | up to 47 extra requests per 60-second poll for a read-only pane. Rejected on cost, and it degrades precisely when the fleet is most productive. |
| **Denormalise a `title` column onto `task_events`** | a second copy of a name that can be retitled. The repo's own comment on the `project` filter rejects this reasoning explicitly: *"events carry no project column of their own (one name, no denormalized copy)"* (`task_repository.py:1369-1370`). |

### 4.3 An index is NOT required, and I would not add one yet

`task_events` carries only `idx_task_events_item_id` (`postgres_models.py:1637`), so a `since`-bounded
sweep is a sequential scan. At **12,245 total rows** that is nothing. **Say so rather than adding an
index nobody measured a need for** — revisit if the table passes a few hundred thousand rows.

## 6. The column set — and this is the whole design

Rick's ask is at-a-glance, so **fewer, better columns beat completeness.** Every column below is
justified by what the glance loses without it; §6.5 lists what I cut and why.

### 6.1 Kept — four columns

| column | source | why it survives the glance test |
|---|---|---|
| **WHEN** | `event.ts`, rendered **relative** (`14m`, `1h12m`, `19h`) | the pane's entire premise is recency. Relative beats absolute because *"how fresh is this"* is one subtraction the reader should not have to do. Absolute time on hover / in disclosure |
| **WHAT** | `item.title` (**needs D1 ①**) | the irreducible column. Without it the pane is a list of UUIDs |
| **WHO** | `event.actor`, **persona only** | *who closed it* is the second question after *what closed*. See §6.3 — the raw field is not directly displayable |
| **WHY** | `event.reason`, **clamped to one line** | see §6.2 — this was the surprise of the investigation |

### 6.2 🔴 WHY earns its place on measurement, and the same measurement forces it to be clamped

I did not expect `->done` events to carry a reason. They do. Over 30 days:

| to_status | events | with non-blank reason | % | **avg reason length** |
|---|---|---|---|---|
| `done` | 818 | 802 | **98.0%** | **1,073 chars** |
| `dropped` | 83 | 83 | **100%** | 934 chars |
| `wont_fix` | 2 | 2 | 100% | 47 chars |

⇒ **A one-line human summary of what happened is available on essentially every row, for free.** It is
the difference between *"something called X finished"* and *"X finished, and here is what that meant"*.

⚠️ **AND THE SAME NUMBER IS THE ARGUMENT FOR CLAMPING IT.** 1,073 characters is a *paragraph*. Rendered
in full at 42 rows a day, the pane is several screens of prose and **fails the at-a-glance requirement
completely** — it would be the single worst thing in the design. So: **one clamped line in the column,
full text behind the row's disclosure toggle.**

⚠️ `wont_fix`'s 47-char average is **n=2**. Do not read a formatting convention out of it.

### 6.3 WHO needs stripping — the raw field is not displayable

`actor` is stored as `"<persona> <session8>"`. Sampled live from the last 24 hours:

```
Rachel 6578abf3   | in_progress->done     | All four acceptance criteria met
mr radio e97796db | not_approved->done    | Independent review DISCHARGED by
maria b9c93948    | in_progress->dropped  | DUPLICATE, and the duplication i
```

**Render the persona and drop the session hash.** The hash is a coordinate that answers a question
nobody asks at a glance; it belongs in the disclosure. 19 distinct actors appeared in the window, so
the column is genuinely informative and not a wall of one name.

⚠️ **WHO here is the ACTOR — the session that actually closed the row — which is a third thing,
distinct from both `owner_persona` and `created_by`.** `tasks.py:479` warns that filer and owner
differ on 3 of 13 live rows and that merging them *"reports the wrong person on a quarter of the
board"*. **Actor is the right one for this pane** precisely because the pane is about the closing
event, not about ownership. Say "closed by" in the tooltip so nobody reads it as owner.

### 6.4 The status glyph rides in WHEN, and the layout never reshuffles

In DONE-only view every glyph would be an identical ✅ — pure noise by the north star, and the
tempting move is to hide it until a second filter is lit.

**Rejected.** A layout that changes shape when you click a filter is worse for glancing than one
redundant character: the reader re-finds every column each time. **The glyph is a prefix inside the
WHEN cell, not a column**, so it costs no horizontal space and the grid is constant across all seven
filter combinations. A left-edge colour rail on the row carries the same signal for anyone who reads
colour faster than emoji.

### 6.5 CUT — and why each one loses nothing at a glance

| cut | why |
|---|---|
| **Task ID / row prefix** | 8 hex characters of pure coordinate. It is how the *fleet* names rows, not how Rick reads them. → disclosure |
| **Status as its own column** | the filter pills already say which statuses are showing, and the glyph says which one a row is. A third statement of the same fact |
| **Priority** | a property of work that was still owed. Once a row is done its P-level is history, and sorting by it would fight the recency premise |
| **Project** | the pane is scoped to one project (§10, Q6). A column with one distinct value is chrome |
| **Owner / filer** | §6.3 — actor is the right "who" for a completion pane, and showing three people-columns is how the glance dies |
| **`receipt_refs`** | 100% populated on `->done` (818/818, forced by the T3 receipt gate) and therefore **perfectly uninformative as a column** — every row would show the same "yes". Its *content* is valuable, so → disclosure |
| **`blocked_by` / `next_chase_ts`** | meaningless on a terminal row |
| **Absolute timestamp** | WHEN is relative by design. → hover + disclosure |
| **`authority`** | audit-grade, not glance-grade. → disclosure |
| **Grouping (by owner, by hour, by status)** | every existing pane groups, so this is the tempting default. **At 47 rows a flat newest-first list is shorter than a grouped one**, and grouping adds an expand/collapse decision per group — clicks, in a pane whose whole point is not clicking. **Flat, newest-first, no groups.** |

⚠️ **The grouping cut is the one I would expect to be argued with**, because it breaks symmetry with
the other four accordions. I am cutting it on the north star: grouping optimises for *finding a known
item*, and this pane is for *seeing what happened*. If Rick wants grouping later it is additive.

## 7. The control shape — three toggle pills, multi-select, DONE pre-lit

### 7.1 The recommendation

```
[ ✅ Done 42 ]   ( 🗑️ Dropped 5 )   ( 🚫 Won't-fix 0 )
```

- **Multi-select**, not exclusive. Rick: *"so I can see all of them if I want."*
- **DONE lit on first load and after any reset.** Non-negotiable (§1.2).
- **Each pill carries its own count**, which collapses the count badge and the control into one
  element — the counts *are* the filters.
- **A zero-count pill renders dimmed but present and still clickable.** *Zero is a claim, not a
  default* — `🚫 Won't-fix 0` is a fact Rick wants; a pill that vanishes at zero silently converts
  *"nothing was refused today"* into *"this feature does not exist"*.
- **Clicking every pill off** shows the DONE set with a quiet note rather than an empty pane, and
  re-lights DONE. There is no useful state in which this pane shows nothing on purpose.

### 7.2 Rejected alternatives

| alternative | why rejected |
|---|---|
| **A `<select>` / combo list** (Rick named it as an option) | it **hides its own state**. You cannot see what is filtered without opening it, and you cannot see the other statuses' counts at all. That is the direct opposite of at-a-glance. It also costs a click to *discover* and a second to *change* |
| **Tabs** | single-select by convention, so *"see all of them"* becomes impossible without inventing an "All" tab — at which point you have four controls expressing three facts |
| **Checkboxes** | functionally right, visually weakest: more chrome per unit of signal, no natural place for the count, and the surrounding page already speaks in buttons (`.task-accordion-btn`, `.refresh-btn`, `.toggle-button`) |
| **A single "show everything" switch** | loses the ability to see dropped without won't-fix. Rick asked for *"different clickable filters"*, plural |
| **Filter chips that disappear at zero** | see §7.1 — it is the *zero is a claim* violation, and it makes the control bar change width as the day goes on |

### 7.3 What the pills do NOT do

They do not re-query on every click if the data is already in hand. **All three sets fit in one poll
cycle** (42 + 5 + 0 = 47 rows), so lighting a filter is a client-side re-render of data already
fetched. The pane stays instant, which at-a-glance requires.

## 8. The count badge — the highest-value element here

María flagged this as *"worth proposing"*. **I am proposing it as the primary deliverable of the
feature**, above the table.

```
▶  ✅ Completed · last 24h    42 done · 5 dropped · 0 won't-fix
```

**Rick's literal ask is *"look at it at a glance and know what the status is."* This line satisfies
that with the accordion still closed.** Everything below it is for when he wants the detail.

Prior art is exact and already on the page: `#task-list-count` (`notifications.html:765`) and
`#holding-area-count` + `#task-list-flow-ratio` (`:807-810`) both put live counts in a section header.
This follows that pattern rather than inventing one.

⚠️ **THE BADGE MUST DISTINGUISH "ZERO" FROM "DON'T KNOW".** Before the first successful poll, and on
any error, it reads **`—`**, never `0`. *Nothing finished today* and *we could not find out* are
different facts, and a badge that prints `0` for both is a confident wrong answer — the exact defect
class §3.2 documents.

⚠️ The three existing surfaces use three different count conventions — task-list `"Live: 0"`,
fleet-status `"0"`, holding-area `"—"`. **This pane uses the holding-area convention for the unknown
state and a labelled triple for the known one.** Named here so build #2 copies it deliberately.

## 9. Persistence polarity — DECLARED, per the trap

### 9.1 The trap

| key | declared | shape |
|---|---|---|
| `lupin.taskList.collapsedOwners` | `notifications.js:444` | JSON **ARRAY** of **COLLAPSED** owner keys |
| `lupin.epicBoard.groupState` | `notifications.js:459` | JSON **MAP** of key → **isEXPANDED** |

Same feature, **inverted sense, different container type**. Porting one from the other inverts a
user's saved state and **fails invisibly**. Verified verbatim at `1c9a7ea6`; identical at `897f183d`.

### 9.2 🔴 There is a THIRD convention, and it is the one that governs section accordions

Neither of the two above applies to this pane. `notifications.html:1300-1338`:

```js
const LUPIN_ACCORDION_PERSIST_KEYS = {
    'broadcast-submit-section'    : 'notifications_broadcast_card_open',
    'commons-recent-activity-body': 'notifications_recent_activity_open'
};
// …
localStorage.setItem( persistKey, JSON.stringify( isOpen ) );
```

**A boolean, `isOPEN` polarity, one key per section, and "missing key = use the section's HTML
default."** The two conflicting keys above are the *group-within-a-section* axis; **this pane's
open/closed state is the section axis, and it has its own settled convention.**

⇒ **The polarity question resolves by not being either of the two that conflict.**

### 9.3 The two keys this pane declares

| axis | key | polarity | value |
|---|---|---|---|
| **section open/closed** | `notifications_completed_work_open` | **isOPEN (positive)** | `true` / `false` via `JSON.stringify( isOpen )` |
| **filter selection** | `notifications_completed_work_filters` | **ENABLED (positive)** | JSON array of lit statuses, e.g. `["done"]` |

**Both positive. The key names say so — `_open`, and `filters` holding what IS shown.** A key that
names its own polarity is the one thing the two trapped keys above do not do, and it is why this
convention is the safe one to extend.

### 9.4 Why the filter set is POSITIVE, and it is not a style preference

A negative array (*statuses hidden*) would express the required default `DONE ONLY` as
`["dropped","wont_fix"]` — **a list of things not shown.**

🔴 **That inverts the day a fourth terminal status is added.** `VALID_STATUSES` has grown before; the
next terminal status would not be in the hidden list, so it would **silently appear in a pane whose
whole specification is that it defaults to DONE only.** With a positive set, `["done"]` keeps meaning
exactly *done*, forever, and a new status is invisible until somebody chooses to show it.

⇒ **Positive polarity is forward-compatible under status growth; negative polarity leaks new statuses
into the default view.** That is the argument, and it survives the fourth status arriving.

### 9.5 Two behaviours the persistence must have

1. **A missing key means the HTML/spec default**, never an empty selection — matching
   `applyPersistedAccordions`'s *"Missing key = use the section's HTML-default state."* A corrupt or
   unparseable value is discarded and falls back the same way (both existing readers `try/catch` and
   `continue`).
2. **Write failures are swallowed.** Both existing keys do this deliberately — *"a private-mode /
   quota failure must never break rendering."*

⚠️ **The section collapse mechanism differs between the two clients and this is a build-#1 note.**
Legacy toggles a **`.collapsed` class on `.section-content`** (`notifications.css:195`;
`notifications.html:1323-1330`). `data-collapsed` is a **multiplexer-side idiom only** —
`git grep data-collapsed -- 'src/**'` returns hits exclusively under `css/multiplexer/`. Build #1
uses the class; build #2 uses whatever the multiplexer's shared contract uses. **Observationally
equivalent, mechanically different — which is the rule, not a violation of it.**

## 10. Answers to the open questions — recommendation + whose call it is

### Q2 · Window semantics — rolling or since-midnight?

**RECOMMEND: rolling 24 hours, recomputed at every poll.** ⚑ **Rick's call.**

Two reasons, and the second is measured:

1. *"Last 24 hours"* reads as rolling in plain English.
2. 🔴 **Since-midnight makes the pane nearly empty exactly when Rick opens it.** This box's own boot
   record (CLAUDE.md § off-peak scheduling, 91 morning boots, `journalctl --list-boots`) puts the
   **median morning boot at 09:34**, with 80 of 91 after 09:00. A since-midnight window at first
   login shows only what happened after he sat down — which on most days is *nothing*. **A rolling
   window is the only one of the two that is populated at the moment of first glance.**

⚠️ Rolling has one real cost: **rows leave the pane while he watches**, so a row seen at 09:00 may be
gone at 09:15. Show the window bound in the header (`last 24h`) so the disappearance reads as the
window moving rather than data loss.

### Q3 · Column set — §6. Four kept, nine cut, each justified.

### Q4 · Empty state — a quiet day must read as "nothing finished"

**RECOMMEND: distinct messages per state, following the legacy enumerated contract.** Mine to decide;
this follows an established pattern rather than inventing one.

| state | message | badge |
|---|---|---|
| nothing terminal in window | `✅ Nothing finished in the last 24 hours.` | live counts (`0 done · 0 dropped · 0 won't-fix`) |
| not yet loaded | `Completed work not loaded yet.` | **`—`** |
| store unreachable | `⚠️ Store unreachable.` | **`—`** |
| query module absent | `🧩 Completed-work query did not load` | **`—`** |
| response truncated | `✂️ Window truncated: {detail}.` | live counts + the notice |
| filters all off | `No filters selected — showing done.` | live counts |

🔴 **The first row and the next three are the whole point, and the existing panes get this wrong.**
The inventory (`2026.09.05-fleet-accordions-current-state-inventory.md` §5b) records that
`✅ No open tasks.` and `No tasks loaded yet.` **share the `task-list-empty` class and mean opposite
things** — success versus nothing-has-arrived — *"distinguished only by their text."* **This pane gives
each state its own class as well as its own text**, so a test can tell them apart without string
matching and the badge (`—` vs `0`) carries the same distinction independently.

⚠️ **A truncation notice is mandatory, not optional.** §3.2 is two recorded instances of this exact
endpoint family truncating silently. The pane must say when it is showing a partial answer, and the
existing `_renderTaskListTruncationBanner` is the pattern.

### Q5 · Count badge — **yes, and it is the primary deliverable.** §8.

### Q6 · Scope — fleet-wide or per-persona?

**RECOMMEND: fleet-wide, scoped to `project=lupin`.** ⚑ **Rick's call.**

*"All of these types of task list items"* reads fleet-wide, it matches the board immediately below it
(`unscoped_audit=true`, no owner filter), and the whole purpose is knowing what **the fleet** got
done. The event endpoint's `project` parameter serves this directly. 19 distinct actors appeared in
the last 24 hours, so a per-persona view would hide 18 of 19 columns of signal from a manager.

⚠️ **If he ever wants "just mine", it is `actor=` on the same endpoint** — additive, not a redesign.

## 11. Acceptance — both arms, non-negotiable

Per the row: mutation arms off a **green baseline**, guards reddening **by name**, controls green in
both states.

### Arm A — the default is DONE ONLY

**With no interaction**, after a successful load, the pane shows done rows and **only** done rows.

- ✅ every rendered row's status is `done`
- ✅ the DONE pill is lit; the other two are not
- ✅ persisted state absent ⇒ this is still the outcome (§9.5)

### Arm B — the companion, and Arm A is worthless without it

🔴 **A guard that passes by showing NOTHING AT ALL is not a guard.** Arm B must prove, in the same
fixture:

1. **dropped and won't-fix rows EXIST in the window** — asserted positively, with a count ≥ 1 each,
   *before* anything about hiding is claimed
2. they are **DELIBERATELY HIDDEN** in the default view — absent from the DOM, while their pills
   still show non-zero counts
3. they **APPEAR** when their filter is clicked — asserted by row identity, not by row count
4. and the done rows **remain** (multi-select, not exclusive)

### 11.1 🔴 The fixture must SEED won't-fix — it cannot use live data

**Measured: 0 `wont_fix` events in the last 24 hours, and 2 in the last 30 days.** So a test that
waits for a real won't-fix row would show nothing, assert nothing, and **pass** — for weeks. That is
precisely the failure the acceptance clause names.

⇒ **Both arms run against a seeded fixture containing, at minimum, 2 done + 1 dropped + 1 won't-fix
inside the window, and at least one terminal row OUTSIDE the window.** The out-of-window row is the
control that proves the window is doing work rather than the query returning everything.

### 11.2 The positive control on the corpus itself

The suite asserts **how many rows it seeded and how many it found**, and fails if the fixture is
empty. **A loop over nothing is green** — every per-row assertion in an empty list passes. The corpus
count is what makes the rest of the arm mean anything.

### 11.3 Mutation arms this design expects to be killed

| # | mutation | must redden |
|---|---|---|
| M1 | default the filter set to all three | Arm A |
| M2 | drop the `wont_fix` pill entirely | Arm B |
| M3 | make the pills exclusive instead of multi-select | Arm B step 4 |
| M4 | invert the persisted filter polarity (store hidden instead of shown) | a §9.4 guard, and **it must be its own named test** — a polarity bug is invisible on a fresh profile |
| M5 | widen the window to 48h | the out-of-window control (§11.1) |
| M6 | render `0` instead of `—` before first load | the §8 badge guard |
| M7 | drop the truncation notice | the Q4 truncated-state guard |

⚠️ **M4 is the one that would ship.** It only manifests for a user with saved state, so a fresh-profile
test passes it clean. **Its guard must load a persisted value, not just write one.**
