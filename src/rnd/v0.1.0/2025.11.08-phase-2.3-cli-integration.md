**Validation Examples**:
```python

    message="Approve deployment?",
    response_type=ResponseType.YES_NO,
    response_default="yes"
)

# Invalid - raises ValidationError
request = NotificationRequest(
    message="   ",  # Whitespace only - ERROR
    response_type=ResponseType.YES_NO,
    response_default="maybe"  # Must be yes/no - ERROR
)
```

**Key Features**:
- Type-safe SSE event handling (isinstance checks)
- Comprehensive error handling (connection, timeout, validation)
- Exit codes: 0=success, 1=error, 2=timeout
- Debug mode with detailed logging to stderr
- Response value output to stdout (bash-capturable)

**Usage**:
```python
from cosa.cli.notification_models import NotificationRequest, ResponseType

request = NotificationRequest(
    message="Approve deployment?",
    response_type=ResponseType.YES_NO,
    response_default="yes",
    timeout_seconds=60
)

response = notify_user_sync(request, debug=True)

if response.success:
    print(f"User responded: {response.response_value}")
elif response.is_timeout:
    print(f"Timeout - used default: {response.response_value}")
else:
    print(f"Error: {response.status}")
```

## Pydantic vs Manual Validation

### Why Pydantic Was Chosen

**Benefits Achieved**:
1. **Runtime Validation** - Catches invalid parameters before API call
2. **Clear Error Messages** - Pydantic provides structured, helpful errors
3. **Type Safety** - IDE autocomplete, isinstance checks for event types
4. **Self-Documenting** - Field descriptions generate documentation
5. **Easy Testing** - Model fixtures simplify test creation
6. **Scalability** - Easy to add new fields/validators without refactoring

**Comparison**:

| Aspect | Manual Validation | Pydantic (What We Built) |
|--------|------------------|--------------------------|
| Validation Lines | ~30 lines scattered | Centralized in models |
| Error Messages | Manual, inconsistent | Auto-generated, detailed |
| Type Safety | Type hints only | Runtime enforcement |
| IDE Support | Basic | Excellent (autocomplete) |
| Testing | Hard (many params) | Easy (model fixtures) |
| Code Lines | ~350 lines | ~750 lines (but more robust) |

**Example Error Message**:
```bash
$ notify-claude-sync "test" --response-type yes_no --response-default maybe

✗ Invalid parameters:
  response_default: For yes_no type, response_default must be 'yes' or 'no'
```

### File Organization

```
src/cosa/cli/
├── notification_types.py      # Enums, constants (70 lines)
├── notification_models.py     # Pydantic models (377 lines) ← NEW
├── notify_user.py             # Async fire-and-forget (300 lines)
└── notify_user_sync.py        # SSE blocking (375 lines) ← NEW

/home/rruiz/.local/bin/
└── notify-claude-sync         # CLI wrapper (66 lines) ← NEW
```

### Import Graph

```
notify-claude-sync (bash)
    ↓
notify_user_sync.py
    ├── imports notification_models.py
    │   └── imports notification_types.py
    └── imports notification_types.py (constants)
```

### Data Flow

```
User runs: notify-claude-sync "Message" --response-type yes_no --response-default yes
    ↓
Bash wrapper calls: python notify_user_sync.py ...
    ↓
argparse parses: args.message, args.response_type, ...
    ↓
Pydantic validates: NotificationRequest(**args) [automatic validation]
    ↓
SSE client sends: POST /api/notify?response_requested=true
    ↓
Server streams: SSE events (heartbeat, result)
    ↓
Client parses: Pydantic models (RespondedEvent, ExpiredEvent, etc.)
    ↓
Return response: NotificationResponse(response_value, exit_code)
    ↓
Output to stdout: print(response_value)
    ↓
Exit with code: sys.exit(exit_code)  # 0/1/2
```

## Exit Code Specification

| Code | Meaning | Scenarios |
|------|---------|-----------|
| 0 | Success | User responded, Offline with default |
| 1 | Error | Validation failed, Network error, User not found, Server error, Expired without default |
| 2 | Timeout | No response within timeout (with or without default) |

**Bash Examples**:
```bash
# Capture response
RESPONSE=$(notify-claude-sync "Approve?" --response-type yes_no --response-default yes)
EXIT_CODE=$?

if [ $EXIT_CODE -eq 0 ]; then
    echo "User said: $RESPONSE"
elif [ $EXIT_CODE -eq 2 ]; then
    echo "Timeout - used default: $RESPONSE"
else
    echo "Error occurred"
fi
```

## Key Design Decisions

### 1. Pydantic Over Manual Validation

**Rationale**: Runtime validation, type safety, self-documenting schemas, easy testing.

**Trade-off**: Additional dependency (already installed with FastAPI), slightly more upfront code.

### 2. Separate Models File

**Structure**: notification_types.py → notification_models.py → notify_user_sync.py

**Rationale**: Clean separation, reusable across CLI/API, independently testable, scales well.

### 3. Exit Code Design

**Specification**: 0=success, 1=error, 2=timeout

**Rationale**: Matches POSIX conventions, distinguishes timeout from general error, bash-scriptable.

### 4. stdout/stderr Separation

**Pattern**: Response value → stdout, Debug/errors → stderr

**Rationale**: Enables bash capture (`RESPONSE=$(notify-claude-sync ...)`), clean output.

### 5. Type-Safe Event Handling

**Pattern**: Pydantic models + isinstance checks

**Rationale**: Compile-time type checking, IDE autocomplete, prevents runtime type errors.

## Lessons Learned

### 1. Pydantic Validation Power

**Observation**: Pydantic caught validation errors that would have been runtime bugs.

**Example**: User accidentally passes `--response-default maybe` for yes_no type → Pydantic rejects immediately with clear error.

### 2. Type-Safe Event Handling

**Observation**: isinstance checks with Pydantic models provide excellent IDE support and prevent type errors.

**Example**: IDE autocompletes `event.response` after `isinstance(event, RespondedEvent)` check.

### 3. Test-Driven Benefits

**Observation**: Writing unit tests first helped clarify edge cases (expired without default, offline detection, etc.).

### 4. Separation of Concerns

**Observation**: Separate models file made testing much easier - could test validation independently from HTTP logic.
