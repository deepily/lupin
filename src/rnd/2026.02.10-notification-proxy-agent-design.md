# Notification Proxy Agent — Expediter Auto-Responder

**Date**: 2026-02-10
**Session**: 171
**Status**: Implementation complete (Checkpoint e485bb1)

---

## Context

**Problem**: Testing the Runtime Argument Expediter flow requires human interaction — someone must answer questions about missing args (query, budget, audience) and confirm the arg summary before jobs are created. When iterating through mock job submissions in one session, you need another "person" sitting in a second session clicking buttons. This is tedious and blocks automated testing.

**Solution**: Build a standalone CLI agent ("Notification Proxy") that logs in as `mock.tester@lupin.deepily.ai`, subscribes to notification events via WebSocket, and automatically answers expediter questions using a hybrid strategy: rules for known patterns, LLM fallback for unknowns.

**Design for the future**: The architecture should be extensible to Use Case 2 (meta-orchestrator proxy that fields ALL agent notifications when you're away), even though we only implement Use Case 1 now.

## Implementation Steps

### Step 1: WebSocket Listener (`listener.py`)

Create async WebSocket client using `websockets` library (already in project deps).

**Responsibilities:**
- Connect to `ws://localhost:7999/ws/queue/{session_id}`
- Send `auth_request` with `Bearer mock_token_email_mock.tester@lupin.deepily.ai`
- Subscribe to events: `notification_queue_update`, `job_state_transition`, `sys_ping`
- Respond to `sys_ping` with `sys_pong` (keep-alive)
- Exponential backoff reconnection (1s → 30s, max 10 attempts)
- Emit received events to a callback (the responder)

**Key pattern** (from existing test scripts):
```python
async with websockets.connect( uri ) as ws:
    auth_msg = {
        "type"              : "auth_request",
        "token"             : "Bearer mock_token_email_mock.tester@lupin.deepily.ai",
        "session_id"        : session_id,
        "subscribed_events" : [ "notification_queue_update", "job_state_transition", "sys_ping" ]
    }
    await ws.send( json.dumps( auth_msg ) )
```

**Critical files referenced:**
- `/src/scripts/debug/debug_websocket_auth_validation.py` — existing Python WS client pattern
- `/src/cosa/rest/websocket_manager.py` — server-side subscription logic
- `/src/fastapi_app/static/js/notifications.js` — client-side auth pattern

### Step 2: Notification Router (`responder.py`)

**Responsibilities:**
- Receive `notification_queue_update` events from listener
- Extract notification metadata: `id_hash`, `message`, `response_type`, `sender_id`, `abstract`, `response_requested`
- If `response_requested == True`: route to appropriate strategy
- If expediter notification (`sender_id == "arg.expeditor@lupin.deepily.ai"`): use `ExpediterRuleStrategy`
- If unknown sender or rule strategy returns `None`: fall through to `LLMFallbackStrategy`
- Submit response via `POST http://localhost:7999/api/notify/response`

**Response submission** (from exploration of notification API):
```python
payload = {
    "notification_id" : notification_id,
    "response_value"  : answer
}
response = requests.post(
    "http://localhost:7999/api/notify/response",
    json=payload,
    headers={ "Content-Type": "application/json" }
)
```

**Strategy interface:**
```python
class ResponseStrategy:
    async def can_handle( self, notification ) -> bool: ...
    async def respond( self, notification ) -> str | dict | None: ...
```

**Critical files referenced:**
- `/src/cosa/rest/routers/notifications.py` (lines 670-840) — POST `/api/notify/response` endpoint
- `/src/fastapi_app/static/js/notifications.js` — `submitResponse()` pattern
- `/src/cosa/cli/notification_models.py` — NotificationRequest/Response models

### Step 3: Expediter Rule Strategy (`strategies/expediter_rules.py`)

**Responsibilities:**
- Handle known expediter question patterns deterministically
- Use the expediter's agent registry as reference for what questions to expect

**Rule mappings** (derived from `/src/cosa/agents/runtime_argument_expeditor/agent_registry.py`):

| Notification Pattern | Response Type | Auto-Answer |
|---------------------|---------------|-------------|
| Title contains "query" or "topic" | OPEN_ENDED | Config value (e.g., "quantum computing") |
| Title contains "budget" | OPEN_ENDED | "no limit" (or config value) |
| Title contains "audience" | OPEN_ENDED | "academic" (or config value) |
| Title contains "research" | OPEN_ENDED | Path to latest research file |
| Title contains "language" | OPEN_ENDED | "en" (or config value) |
| Response type is YES_NO (confirmation) | YES_NO | "yes" |
| Batch questions | OPEN_ENDED_BATCH | Dict of answers from config |

**Config-driven test profiles:**
```python
TEST_PROFILES = {
    "deep_research" : {
        "query"    : "quantum computing breakthroughs 2026",
        "budget"   : "no limit",
        "audience" : "academic"
    },
    "podcast" : {
        "research" : "latest",
        "audience" : "general",
        "languages": "en"
    }
}
```

**Critical files referenced:**
- `/src/cosa/agents/runtime_argument_expeditor/agent_registry.py` — AGENTIC_AGENTS registry
- `/src/cosa/agents/runtime_argument_expeditor/expeditor.py` — Question generation logic

### Step 4: LLM Fallback Strategy (`strategies/llm_fallback.py`)

**Responsibilities:**
- Handle unknown or unexpected notification questions
- Use Anthropic SDK directly (like existing agents) for cost efficiency
- Construct prompt with notification context (message + abstract)

**Pattern** (from existing agents):
```python
from anthropic import AsyncAnthropic

client = AsyncAnthropic( api_key=api_key )
response = await client.messages.create(
    model     = "claude-sonnet-4-5-20250929",
    max_tokens = 500,
    messages  = [ {
        "role"    : "user",
        "content" : f"You are an automated test agent. Answer this notification question concisely.\n\nQuestion: {message}\nContext: {abstract}\n\nRespond with ONLY the answer, no explanation."
    } ]
)
```

**Firewalled API key** (following existing pattern):
- Env var: `ANTHROPIC_API_KEY_FIREWALLED`
- Fallback: `src/conf/keys/anthropic-api-key-firewalled`

**Critical files referenced:**
- `/src/cosa/agents/deep_research/api_client.py` — Direct Anthropic SDK usage
- `/src/cosa/agents/deep_research/config.py` — API key configuration

### Step 5: CLI Entry Point (`__main__.py`)

**Responsibilities:**
- Parse CLI arguments (server URL, email, session ID, test profile, verbosity)
- Initialize listener, strategies, and responder
- Start async event loop
- Graceful shutdown on Ctrl+C
- Log all received notifications and responses to console

**Usage:**
```bash
# Basic usage
python -m cosa.agents.notification_proxy

# With custom profile
python -m cosa.agents.notification_proxy --profile deep_research

# With custom email

# Verbose mode
python -m cosa.agents.notification_proxy --debug --verbose
```

**Default values:**
- Server: `ws://localhost:7999`
- Email: `mock.tester@lupin.deepily.ai`
- Session ID: `auto proxy` (adjective-noun format)
- Profile: `deep_research`

## Use Case 2 Extension Points

The architecture naturally extends to the meta-orchestrator by:

1. **New strategy**: `strategies/orchestrator.py`
   - Uses Claude Code interactive session (SDK mode) as the "brain"
   - Maintains conversation history across multiple notifications
   - Can ask clarifying questions back to the user (via voice_io)
   - Leverages existing dispatcher at `/src/cosa/orchestration/claude_code/`

2. **Strategy selection**: Config-based or auto-detected
   - Expediter notifications → expediter rules
   - Known agent patterns → agent-specific rules
   - Unknown/complex → orchestrator (Claude Code session)

3. **AgenticJob wrapper**: `job.py` (later)
   - Wraps the proxy as a background job in the queue
   - JOB_TYPE = "notification_proxy", JOB_PREFIX = "np"
   - Submitted via REST API, managed by RunningFifoQueue
