# Execution Path Analysis: TTS State After Action-Required Notification Completion

## Context

After applying the "stale `handleAudioComplete` clobbers next notification" fix, queued
yes/no notifications now play audio correctly back-to-back. However, a new symptom emerged:
after both queued notifications complete, the **next** notification (e.g., stop hook) fails
to play audio — user must hard-refresh the browser.

**File**: `src/fastapi_app/static/js/notifications.js`

---

## Key State Variables

| Variable | Purpose | Set by | Cleared by |
|----------|---------|--------|------------|
| `currentTTSMode` | Guards chunk routing (`instant`/`reliable`/`null`) | `playInstantTTS()` L3549 | `stopAudio()` L4262, `onended` handler (new) |
| `currentTTSText` | Text for audio caching | `playTTS()` L3467 | `handleAudioComplete()` (reliable only), `onended` handler (new) |
| `activeTTSItem` | Currently-playing queue item | `activateNextTTS()` L10070 | `onTTSPlaybackComplete()` L10472/10479 |
| `pcmStreamComplete` | All server chunks received | `handleAudioComplete()` L3737 | `onended` handler L3899, `stopAudio()` L4276 |
| `lastPCMSource` | Last scheduled AudioBufferSourceNode | `playPCMChunk()` L3888 | `onended` handler L3900, `stopAudio()` L4277 |
| `ttsFocusModeActive` | Queue paused for user response | `enterTTSFocusMode()` | `exitTTSFocusMode()` L10580 |
| `focusModeNotificationId` | Which notification triggered focus | `enterTTSFocusMode()` | `exitTTSFocusMode()` L10581 |

## The Three Execution Paths

### Path A: Audio finishes naturally, THEN user answers

This is the "happy path" — audio plays to completion before the user clicks yes/no.

```
playTTS() → playInstantTTS() → server streams chunks via WebSocket
    │
    ├── handleAudioChunk() → playPCMChunk() (for each chunk)
    │       └── source.onended fires after each chunk finishes
    │
    ├── handleAudioComplete() fires when server says "done streaming"
    │       └── Sets pcmStreamComplete = true
    │       └── Does NOT null currentTTSMode (deferred — new fix)
    │
    └── Last source.onended fires (pcmStreamComplete && source === lastPCMSource)
            ├── currentTTSMode = null          ← deferred cleanup
            ├── currentTTSText = null           ← deferred cleanup
            ├── firstChunkStartTime = null      ← deferred cleanup
            ├── firstChunkPlayed = false         ← deferred cleanup
            └── onTTSPlaybackComplete()
                    ├── wasActionRequired = true
                    ├── activeTTSItem = null
                    └── enterTTSFocusMode( notificationId )
                            └── Queue paused, waiting for user
```

Then user clicks yes/no:
```
submitResponse() → POST /api/notify/response
    │
    └── Server echoes notification_responded via WebSocket
            │
            └── handleNotificationResponded()
                    │
                    └── setTimeout( 1500ms ) →
                            ├── activeActionRequiredId = null
                            ├── activateNextNotification()
                            └── exitTTSFocusMode()
                                    ├── stopAudio()  ← audio already done, mostly no-ops
                                    │     └── currentTTSMode = null (already null)
                                    │     └── pcmStreamComplete = false (already false)
                                    │     └── lastPCMSource = null (already null)
                                    │     └── ⚠️ currentTTSText NOT cleared (already null from onended)
                                    ├── ttsFocusModeActive = false
                                    └── if queue.length > 0 → setTimeout( activateNextTTS, 100ms )
```

**State after Path A**: Clean. All TTS state nulled by `onended` handler before
`exitTTSFocusMode()` runs. Next notification can play.

---

### Path B: User answers WHILE audio is still playing

The user clicks yes/no before the last PCM chunk finishes (or before all chunks arrive).

```
playTTS() → playInstantTTS() → server streams chunks via WebSocket
    │
    ├── Chunks arriving and playing...
    │
    └── USER CLICKS YES/NO (audio still playing)
            │
            └── submitResponse() → POST /api/notify/response
                    │
                    └── Server echoes notification_responded
                            │
                            └── handleNotificationResponded()
                                    │
                                    └── setTimeout( 1500ms ) →
                                            └── checks: focusModeNotificationId === notificationId
```

**Critical fork**: Was `onTTSPlaybackComplete()` called before the user clicked?

#### Path B-1: `onended` already fired → Focus mode IS active

Same as Path A — `exitTTSFocusMode()` runs, `stopAudio()` cleans up.
State is clean.

#### Path B-2: Audio still playing → Focus mode NOT yet active

```
handleNotificationResponded():
    └── focusModeNotificationId === notificationId?
            └── focusModeNotificationId is NULL (focus mode never entered)
            └── Condition is FALSE
            └── exitTTSFocusMode() is NEVER CALLED
```

Meanwhile, audio continues playing in the background:

```
handleAudioComplete() fires (server done streaming)
    └── pcmStreamComplete = true
    └── currentTTSMode stays "instant" (deferred cleanup)

Last source.onended fires:
    └── currentTTSMode = null
    └── currentTTSText = null
    └── onTTSPlaybackComplete()
            ├── wasActionRequired = true
            ├── activeTTSItem = null
            └── enterTTSFocusMode( notificationId )
                    └── ⚠️ ENTERS FOCUS MODE for an already-responded notification
                    └── Queue is now PAUSED
                    └── No one will ever call exitTTSFocusMode()
                    └── ⚠️ QUEUE IS PERMANENTLY STUCK
```

**State after Path B-2**: `ttsFocusModeActive = true`, `focusModeNotificationId` set to
an already-responded notification. Queue is frozen. New notifications added to the queue
(like the stop hook) will never play because `activateNextTTS()` won't be called.

**This matches the observed symptom**: stop hook notification arrives, gets queued at L10023,
but at L10031 `ttsFocusModeActive` is true, so `activateNextTTS()` is NOT called.
Instead it falls through to L10033-10036 ("In focus mode: just render the minimized card,
don't auto-play"). The notification appears in the UI but audio never plays.

---

### Path C: User dismisses/cancels (X button)

```
cancelActionRequired()
    └── submitResponse( notificationId, defaultValue )
            └── Same flow as yes/no click
            └── Same Path B fork applies
```

**No difference from Path B** — dismiss goes through the same `submitResponse()` pipeline.

---

## The `handleNotificationResponded` 1.5-Second Delay

A key detail: `exitTTSFocusMode()` is called inside a `setTimeout( ..., 1500 )` at L12314.
This 1500ms delay exists "to let user see the 'responded' state" on the card.

This creates a **race window**: the `onended` handler from the last PCM chunk could fire
during that 1500ms gap, calling `enterTTSFocusMode()` for an already-responded notification.

```
Timeline:
    T+0ms     User clicks yes/no → submitResponse()
    T+50ms    Server echoes notification_responded
    T+200ms   Last PCM chunk's onended fires → enterTTSFocusMode() ← RACE
    T+1500ms  setTimeout callback → exitTTSFocusMode() ← Too late? Or just in time?
```

If `onended` fires BEFORE the setTimeout callback (T+200 < T+1500), then:
- `enterTTSFocusMode()` activates focus mode at T+200
- `exitTTSFocusMode()` runs at T+1500 and cleans up

If `onended` fires AFTER the setTimeout callback (rare, very long audio):
- `exitTTSFocusMode()` runs at T+1500 but focus mode isn't active → no-op (guard at L10566)
- `onended` fires later → `enterTTSFocusMode()` → **stuck** (no one will exit)

## State Comparison: What Each Path Leaves Behind

| State Variable | Path A (clean) | Path B-2 (stuck) |
|----------------|-----------------|-------------------|
| `currentTTSMode` | `null` | `null` |
| `currentTTSText` | `null` | `null` |
| `activeTTSItem` | `null` | `null` |
| `ttsFocusModeActive` | `false` | **`true`** ← stuck |
| `focusModeNotificationId` | `null` | **set** ← orphaned |
| `pcmStreamComplete` | `false` | `false` |

The only difference is `ttsFocusModeActive`. When stuck at `true`, new notifications
added to the TTS queue will never auto-play (L10031 condition fails).

---

## Queue Entry Point for New Notifications

When a new notification arrives (e.g., stop hook), it enters through `addToTTSQueue()`:

```javascript
// L10030-10036
if ( !this.activeTTSItem && !this.ttsFocusModeActive ) {
    this.activateNextTTS();                    // ← Only path to start playback
} else if ( this.ttsFocusModeActive ) {
    this.renderMinimizedTTSCard( item );       // ← Renders card but NO audio
    this.log( 'In focus mode, item queued but not auto-playing' );
}
```

When `ttsFocusModeActive` is orphaned at `true`, every new notification hits the
`else if` branch and gets rendered as a silent minimized card. Audio never plays.

## Summary of Execution Paths

```
                    ┌─────────────────────────┐
                    │  Audio starts playing    │
                    │  (playInstantTTS)        │
                    └────────────┬────────────┘
                                 │
                    ┌────────────┴────────────┐
                    │                         │
              Audio finishes           User answers early
              before user answers      (audio still playing)
                    │                         │
                    ▼                         ▼
           onended fires              submitResponse()
           enterTTSFocusMode()        server echoes back
                    │                         │
              User answers              1500ms setTimeout
                    │                    starts ticking
                    ▼                         │
           exitTTSFocusMode()          ┌──────┴──────┐
           Queue advances              │             │
           ✅ CLEAN                onended fires  setTimeout
                                   before 1500ms  fires first
                                       │             │
                                       ▼             ▼
                                  enterFocus()   exitFocus()
                                  at T+200ms     no-op (not
                                       │         active yet)
                                       ▼             │
                                  exitFocus()    onended fires
                                  at T+1500ms    enterFocus()
                                  ✅ CLEAN       ⚠️ STUCK
```
