## Context

Last night's scheduled `all` test-suite run (`ts-d2d890ed`) captured **38 failure entries** (24 failed + 14 errors across 3644 tests) in `io/test-suite/2026.04.15-at-00:56-EDT-all-remediation.json`. The completion watchdog auto-dispatched TFE, which reported:

## Part 1 — TFE Empty Clusters (PRIORITY)

### Root cause (confirmed by reading code)

**Not a clustering bug.** The `8 clusters` number is correct:

- `src/cosa/agents/test_fix_expediter/cluster.py::heuristic_seed()` successfully grouped the 38 failures into seeds.
- `llm_refine()` capped them at `config.max_clusters = 8`.

**Phase 2 (Propose) is a stub.** Per the orchestrator's own docstring (`src/cosa/agents/test_fix_expediter/orchestrator.py:4-10`):

```
0. Cluster   — ✅ REAL (step 7)
1. Diagnose  — ✅ REAL (step 8)
2. Propose   — STUB (step 9)      ← this is what "0 proposed" means
3. Fix       — STUB (step 10)
5. Git       — STUB (step 11)
6. Rerun     — STUB (step 12)
```

So `self.orchestrator.proposed_fixes` is never populated, which cascades into 0 selected and 0 fixed. The job looks "successful" because no phase raises — stubs return empty data structures.

This is consistent with prior planning docs:
- `src/rnd/v0.1.6/2026.04.10-test-fix-expediter/` (phase breakdown)
- `src/rnd/v0.1.6/2026.04.11-tfe-forensics-capture-plan.md`

### What we actually need to decide

Phase 2 implementation is a *real* piece of work (matches BFE's Phase 2 design, needs LLM-driven fix proposal + selection), not a bug fix. Before we write it, we need one observability fix so future TFE runs tell us clearly that they fell through a stub rather than emitting a misleading "completed" status.

### Plan

**Step 1 — Truth-in-status (fast, defensive)**

File: `src/cosa/agents/test_fix_expediter/orchestrator.py`

- When a phase is a stub and produces an empty result on non-empty input (e.g., Phase 2 returns `[]` despite `len(self.clusters) > 0` and `SDK_AVAILABLE`), set a new status `propose_stub_not_implemented` (or `phase2_stub`) on the orchestrator state and surface it in `job.py`'s completion summary.
- The final `response_text` should read something like: "TFE stubbed at Phase 2: 8 clusters diagnosed, propose step not yet implemented. Source: ts-…"
- This is a ~30 LoC change. No behavior change beyond the reported status.

**Step 2 — Assertions at phase boundaries**

File: `src/cosa/agents/test_fix_expediter/job.py` (~line 327-350 where the summary is built)

- After each phase call, assert shape invariants: `len(diagnoses) == len(clusters)` post-Phase 1; if Phase 2 is real, `len(proposed_fixes) >= 1 per cluster with actionable diagnosis`.
- When Phase 2 is still stubbed, the assertion is gated on a config flag `tfe_phase2_enabled` so we don't break scheduled runs.

**Step 3 — Phase 2 implementation spike (scoped SEPARATELY)**

Not part of this bug fix. Create a new planning doc: `src/rnd/v0.1.6/2026.04.15-tfe-phase2-propose-implementation.md` that mirrors `src/rnd/v0.1.6/2026.04.10-test-fix-expediter/04-phase1-diagnose-plan.md`. Out of scope for this plan — explicitly deferred.

## Part 2 — BFE Dead-Job Race

### Root cause (confirmed by reading code)

**Eviction window between watchdog dispatch and BFE execution.**

In `src/cosa/rest/dead_queue_watchdog.py:393-453`, `_submit_bfe()`:
- Has the live `failed_job` object in memory (line 410).
- Captures **only** `dead_job_id = job_id` string (line 427) and optional `dry_run` / model overrides.
- Pushes the BFE job to the todo queue (line 463) and returns.

Then, later (could be seconds to minutes depending on queue depth), BFE executes in `src/cosa/agents/bug_fix_expediter/job.py::_execute()` and calls `package_dead_job(self.dead_job_id)` (approx line 227). That calls `dead_job_packager.py::package_dead_job()` which calls `get_job_by_id_hash(dead_job_id)` — a fresh DB lookup. If the row has been evicted (done/dead bucket rotation, TTL, or the whole DB was wiped by an E2E run — cf. today's test-server auth lockout), the BFE reports `dead_job_not_found_dry_run` and exits cleanly.

Last night, the dead-queue row for `dr-b0060551` was almost certainly wiped by the E2E UI suite's `clean_test_db` between watchdog dispatch and BFE execution. Our earlier companion-reseed fix doesn't help — that only reseeds users.

### Plan

**Step 1 — Eager snapshot at watchdog time (minimal fix)**

File: `src/cosa/rest/dead_queue_watchdog.py`

- Before `self.todo_queue.push( bfe_job )` at line 463, call a new helper `snapshot_dead_job_context( failed_job )` that captures the subset of fields BFE needs: `id_hash`, `error`, `stack_trace`, `question_text`, `original_args`, `agent_class_name`, `user_id`, `user_email`, `session_id`, `created_at`, `failed_at`.
- Pass that dict into BFE via a new `bfe_args["dead_job_snapshot"]` entry.
- BFE accepts snapshot in its constructor, and `package_dead_job()` checks: (a) cached snapshot first, (b) DB lookup as fallback. If the snapshot is present and the DB row is gone, we proceed with packaging using the snapshot and log `dead_job_recovered_from_snapshot`.

**Step 2 — BFE's packager accepts both paths**

File: `src/cosa/agents/bug_fix_expediter/dead_job_packager.py`

- New signature: `package_dead_job( dead_job_id, snapshot=None )`.
- If `snapshot` provided: construct `DeadJobContext` directly from it.
- If not: existing DB lookup path unchanged.

**Step 3 — Test-database resilience (defensive)**

File: `src/tests/e2e_ui/conftest.py` — we just added `restore_companions_after_suite` for users. The dead queue + done queue + job_history rows are all also wiped when E2E drops tables, and nothing restores them. That's fine for tests. But if BFE is in flight **during** an E2E drop, it will observe the race.

- Gate the `DeadQueueWatchdog` on the same `[Lupin: Testing]` config block: during E2E runs, do not auto-dispatch BFE from the dead queue (it's just noise against an intentionally churned DB).
- Config key: `dead queue watchdog enabled = false` in the `[Lupin: Testing]` block of `src/conf/lupin-app.ini`, with a matching explainer in `lupin-app-splainer.ini` (per project convention).

### Critical files (BFE)

| Path | Role |

| `src/cosa/agents/bug_fix_expediter/job.py:~227` | BFE entry into `package_dead_job()` |
| `src/cosa/agents/bug_fix_expediter/dead_job_packager.py:38-42` | DB lookup, no cache/fallback |

### Verification (BFE)

1. **Unit**: `pytest src/tests/unit/ -k bfe_snapshot_fallback` — mock the DB lookup to return None; assert BFE completes with `dead_job_recovered_from_snapshot` status and produces a report.
