# Bug Fix: `set_session_topic()` Not Propagating to UI

**Date**: 2026-03-27 (Session 380)
**Status**: Complete

## Context

`set_session_topic()` returned `{"status": "ok"}` but the topic never appeared in the browser UI. This happened while integration tests were running in a parallel session, causing heavy server load. The other session (standard work session) propagated its topic successfully — 50% failure rate across 2 sessions.

**JS console evidence**: The `session_topic` notification never reached the browser (no `"Session topic updated for..."` log line), confirming the failure is server-side.

## Root Cause Analysis

The propagation chain: MCP tool -> bridge file write -> `_notify_impl()` POST to `/api/notify` -> WebSocket -> JS handler.

**Two bugs identified:**

### Bug 1: `set_session_topic()` masks UI push failure

`cosa_voice_mcp.py:1067-1070` always returned `{"status": "ok"}` even when the notification POST failed. Claude Code had zero visibility into UI push failures.

### Bug 2: `notify_user_async()` doesn't retry transient HTTP failures

`notify_user_async.py:225-233` immediately failed on any non-200 response. The existing retry logic only handled `user_not_available` (HTTP 200 with specific status). Under heavy server load, the 5-second HTTP timeout was insufficient with no retry.

## Changes Made

### File 1: `src/lupin_mcp/cosa_voice_mcp.py`

- `set_session_topic()` now returns `"ui_push": "ok"` or `"ui_push": "Failed: ..."` in the return dict
- Provides visibility into whether the UI notification was actually delivered

### File 2: `src/lupin_cli/notifications/notify_user_async.py`

- Added retry for transient HTTP errors: 429, 502, 503, 504
- Respects `Retry-After` header when present
- Added retry for `ConnectionError` (server unreachable under load)
- Added retry for `Timeout` (server too slow to respond)
- All use the existing retry loop with backoff delays
