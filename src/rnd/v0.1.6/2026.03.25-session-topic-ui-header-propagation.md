# Plan: Propagate `set_session_topic()` to Notification UI Header

## Context

When Claude calls `set_session_topic("Bug Fix Session — Awaiting bugs")` via the cosa-voice MCP server, the topic is written to the session bridge file (consumed by the stop hook's "Continue Session?" notification). However, it **never reaches** the notification UI's `sender-session-name` header span. The UI instead auto-generates mediocre session names from the first notification message. The MCP-crafted topic is higher quality and should be displayed.

The pipe is **half-built**: `AsyncNotificationRequest` already has a `session_name` field, the frontend already checks for `notification.session_name` and has a `refreshSessionNameDisplay()` DOM updater. But the server pipeline never plumbs `session_name` through `/api/notify` → `NotificationItem` → WebSocket, so the frontend handler never fires.

**Why a dedicated type**: Using `custom` + a title discriminator is fragile. A dedicated type gives clean routing at every layer and makes the intent explicit.

## Data Flow

```
set_session_topic("Bug Fix Session")
  ├─► Bridge file (for stop hook) ← existing
  └─► notify(type="session_topic", session_name="Bug Fix Session")
      └─► POST /api/notify?type=session_topic&session_name=Bug+Fix+Session
          └─► push_notification(session_name=...) → NotificationItem → to_dict()
              └─► WebSocket: notification_queue_update
                  └─► handleNotificationUpdate() INTERCEPTS
                      ├─► saveSessionName(id, name, {fromServer:true})
                      ├─► refreshSessionNameDisplay(id, name) ← updates DOM span
                      └─► return (no card, no sound, no TTS)
```

## Edge Cases

| Scenario | Behavior |
|----------|----------|
| Sender card doesn't exist yet | Name saved to localStorage; `createSenderCard()` picks it up later via `getSessionName()` |
| User renames session in UI | Still works — `pushSessionTopicNotification()` fires normally (no `fromServer` flag) |
| Multiple sessions | `sessionId` (8-char hex) is unique per session; names are independent |
| DB persistence | Session topic notifications persist harmlessly — they're low-priority fire-and-forget |
