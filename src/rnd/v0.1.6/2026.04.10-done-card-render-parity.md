# Plan: Done-Bucket Job Card Render Parity

## Context

The Notifications UI renders done-bucket job cards through **two divergent code paths** that produce visibly different results for the same logical state (`done`):

| Symptom | Dynamically inserted (WS transition) | Page-reload from server |
|---|---|---|
| Pause button (⏸) | **Visible (bug — irrelevant)** | Absent ✓ |
| Trash button (🗑) | **Absent (bug)** | Visible ✓ |
| Scheduled badge (🕐) | Visible | **Absent (bug)** |
| Monopolize badge (🔒) | Visible | **Absent (bug)** |

User wants both paths **fully equivalent**, sharing a single rendering method. The scheduled and monopolize badges should **always** appear on a done card when the underlying job has those properties — regardless of how the card got into the DOM.

## Root Causes

There are **four** discrete defects, in three files:

### 1. Backend omits fields in done-queue metadata
**File**: `src/cosa/rest/routers/queues.py`
**Lines**: 335–357 (the `if queue_name == "done":` branch)

The done branch builds `job_data` *without* `scheduled_at`, `monopolize`, or `paused`. The todo/run/dead branch (lines 384–399) **does** include them. So when the page reloads and `/api/get-queue/done` is called, the metadata stream is missing these fields entirely — `renderJobCard` has nothing to render.

### 2. Frontend `renderJobCard` gates scheduled badge to `todo` only
**File**: `src/fastapi_app/static/js/notifications.js`
**Lines**: 6664–6675

```javascript
if ( queueName === 'todo' && job.scheduled_at ) {
    const schedDate = new Date( job.scheduled_at );
    const now = new Date();
    if ( schedDate > now ) { ... }
}
```

Two compounding gates kill the badge for done cards: `queueName === 'todo'` and `schedDate > now`. By the time a job is in the done queue its scheduled time is necessarily in the past — so even if the gate was lifted, the future-only check would still suppress it.

(The monopolize badge at lines 6677–6681 has *no* gate — it works anywhere `job.monopolize` is truthy. The reason it's still missing on page-reload cards is purely defect #1: the field never reaches the frontend.)

### 3. WS transition handler surgically morphs instead of re-rendering
**File**: `src/fastapi_app/static/js/notifications.js`
**Lines**: 4805–4908 (`handleJobStateTransition`, the "card found in source" branch)

When a job transitions todo→run→done during a live session, the existing card is **DOM-reparented** between containers and surgically mutated (spinner removed, completion badge inserted, send-message UI removed, cancel button removed, etc.). The mutation list is incomplete:

- The **pause button** rendered when the card was in todo (line 6732–6734) is never removed → bug
- The **trash button** that should appear in done (line 6737–6740, gated by `queueName === 'run' || 'done' || 'dead'`) is never added → bug
- **Future** surgical-morph divergence is essentially guaranteed every time anyone touches `renderJobCard`

The cold-start branch (4744–4802) already calls `renderJobCard(job, toQueue)` correctly. The "card found in source" branch is the outlier.

### 4. (Related) `renderHistoryCard` data normalization gaps
**File**: `src/fastapi_app/static/js/notifications.js`
**Lines**: 5895–5952

The PostgreSQL job-history adapter omits `scheduled_at`, `monopolize`, `paused`, and `user_email` from its normalized object, and sets `_isHistory: true` which suppresses the delete button (line 6737). This path renders into the **`history-jobs-container`** (a separate persistent-history tab), not the live done bucket — so it is **not the bug the user reported**. But it shares the same `renderJobCard()` and the same root causes, so fixing it in the same pass keeps all consumers aligned.

## Fix

The strategy is **single source of truth via `renderJobCard()`**: feed it complete data from every path, then make `renderJobCard()` itself queue-agnostic for the scheduled/monopolize badges.

### Change 1 — Backend: include missing fields in done-queue metadata

**File**: `src/cosa/rest/routers/queues.py`
**Edit**: Inside the `for job in jobs:` loop at lines 335–357, append three keys to `job_data`:

```python
"scheduled_at" : getattr( job, 'scheduled_at', None ),
"monopolize"   : getattr( job, 'monopolize', False ),
"paused"       : job.state == JobState.PAUSED,
```

(These mirror lines 395–397 in the todo/run branch verbatim, including the `getattr` pattern already used there. Note: `getattr` is acceptable here because it matches the existing surrounding code; full attribute auditing across `AgenticJobBase` / `SolutionSnapshot` is out of scope for this bug.)

### Change 2 — Frontend: queue-agnostic scheduled badge

**File**: `src/fastapi_app/static/js/notifications.js`
**Edit**: Replace lines 6664–6675 (the scheduled badge block) with logic that renders whenever `job.scheduled_at` is set, regardless of queue or whether the time is in the past:

```javascript
let scheduledBadge = '';
if ( job.scheduled_at ) {
    const schedDate = new Date( job.scheduled_at );
    const tz = this.appTimezone || 'America/New_York';
    const schedTimeStr = schedDate.toLocaleTimeString( [], { hour: '2-digit', minute: '2-digit', timeZone: tz } );
    const schedDateStr = schedDate.toLocaleDateString( [], { month: 'short', day: 'numeric', timeZone: tz } );
    scheduledBadge = `<span class="scheduled-badge" title="Scheduled for ${schedDate.toISOString()}">🕐 ${schedDateStr} ${schedTimeStr}</span>`;
}
```

The monopolize badge at lines 6677–6681 already has no queue gate — leave it untouched. Once Change 1 lands, it will start rendering on done cards automatically.

### Change 3 — WS transition: re-render done cards instead of morphing

**File**: `src/fastapi_app/static/js/notifications.js`
**Edit**: In `handleJobStateTransition` at lines 4805–4908, when `toQueue === 'done'`, replace the surgical-morph block (4805–4908) with a **full re-render**:

1. Build the `job` object from `metadata` using the **same shape** as the cold-start branch at lines 4764–4786 (already proven to work).
2. Generate fresh HTML: `const newHtml = this.renderJobCard( job, toQueue );`
3. Reparent into the target container: remove the old card from `fromContainer`, insert the new HTML at the top of `toContainer` via `insertAdjacentHTML('afterbegin', newHtml)`.
4. Preserve the duplicate-target check (lines 4754–4759) and the count-badge update logic (4929–4934).
5. Keep the pause/resume in-place handler (4717–4720) untouched — it's a different event class.

This eliminates 100+ lines of surgical-mutation code (spinner removal, cancel-button removal, send-message removal, interaction-section conversion) — `renderJobCard` already produces the correct done-card markup. **Note**: the `live-interactions` → `Notification Conversation` conversion currently done at 4890–4906 is automatically handled by `renderJobCard`'s done-queue branch at lines 6800–6810 (different markup template per queue).

Apply the same pattern when `toQueue === 'dead'` (lines 4911–4921) — re-render rather than just stripping the cancel button.

For `toQueue === 'todo' || 'run'`, the existing reparent-and-mutate behavior is acceptable because those queues have live state (timers, send-message UI, activity log) that we don't want to recreate from scratch on every transition. The re-render strategy applies specifically to terminal states (`done`, `dead`).

### Change 4 — History tab parity (related cleanup)

**File**: `src/fastapi_app/static/js/notifications.js`
**Edit**: In `renderHistoryCard` at lines 5910–5929:

- Add `scheduled_at: metadata.scheduled_at || null`
- Add `monopolize: metadata.monopolize || false`
- Add `paused: metadata.paused || false`
- Add `user_email: job.user_email || metadata.user_email || null`
- Remove `_isHistory: true` so the delete button renders on history cards too. Verify no other code branch reads `_isHistory` (a quick grep for `_isHistory` confirms only line 6737 consumes it).

Note: The PostgreSQL `metadata_json` column already stores `scheduled_at` and `monopolize` (confirmed in `src/cosa/rest/job_persistence.py:131` — `_build_metadata_json` includes them). No backend change is needed for the history tab.
