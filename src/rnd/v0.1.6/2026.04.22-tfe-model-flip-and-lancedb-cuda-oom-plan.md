### Bug A — TFE harness + UI defaults still pin Opus

Session d8831785 (2026-04-20) ran a 5-arm Opus-vs-Sonnet × effort-level matrix on the TFE Phase 3 workload (harness `src/scripts/tfe_to_cc_phase3_live.py`, target `tfe-72adc928`). The matrix report (`src/rnd/v0.1.6/23-model-effort-matrix-results.md`) concluded:

> "Sonnet beats Opus by roughly 5× on this workload. More thinking does not help; at `xhigh` it mildly hurts."

**Winning arm**: Sonnet 4.6 + effort=`high`, 5/11 effective (3 fixed + 2 already-clean), 17.1 min, 0.29 fixes/min. All three Opus arms landed 0–1 effective. Two surface-level defaults were left pinned to Opus after the matrix: the harness `DEFAULT_MODEL` constant and the UI `renderResumeOverrideControls()` localStorage fallback. This session flips both.

### Bug B — LanceDB-GCS integration tests OOMing the GPU

Last integration run had 5 tests in `test_lancedb_gcs_integration.py::TestLanceDBGCSIntegration` fail with `torch.cuda.OutOfMemoryError` loading `nomic-ai/nomic-embed-text-v1.5` onto GPU 0. The user's GPU 0 has <1 GB VRAM free after the FastAPI server's model warm-up; a test process cannot coexist with the server on the same card.

**User's framing** (quoted, 2026-04-22):

> "Nobody should be touching the GPU at any point, so why is GPU Available ram even an issue? It is so tightly packed on the GPU that I barely have 1GB Available After all the models are loaded onto the first GPU card so I don't even wanna calculate how much RAM is available."

And later, correcting an overcomplicated first-draft plan:

> "You don't ever have to worry about memory or creating a new embedding generator. One is automatically and explicitly made available from the fast API server, which also has an API end point, which allows you to call for batch embedding generation. Why are you complicating this? Why are these tests so fucking opaque?"

The real bug is test-design, not GPU memory: the test process is constructing a fresh `ProseEmbeddingEngine` when it should be asking the already-loaded server for an embedding via HTTP.

## Bug B — Route tests through the server's embedding endpoint

### Canonical facts (from repo exploration 2026-04-22)

- **Batch endpoint**: `POST /api/embeddings/batch` at `src/cosa/rest/routers/embeddings.py:85-110`.
  - Request: `{"texts": [string], "content_type": "prose"|"code"}`
  - Response: `{"embeddings": [[float]], "dimensions": 768, "count": n}`
  - Auth: `require_api_key_or_jwt`.
  - Uses the server's singleton via `get_embedding_provider()` — no duplicate GPU load.
- **Server-side load at boot**: `src/fastapi_app/main.py:520-536` (lifespan hook). `ProseEmbeddingEngine` and `CodeRankEmbed` loaded and warmed once per process.
- **Singleton**: `src/cosa/memory/local_embedding_engine.py:244-355`. **NOT modified this session.**
- **Current test path**: `get_snapshots_by_question(question)` at `src/cosa/memory/lancedb_solution_manager.py:1228-1434` auto-embeds via `_question_embeddings_tbl.get_embedding(question)` at `:1360`. The underlying `_table.search(vec)` at `:1379-1382` accepts a pre-computed vector.
- **No precedent**: zero existing integration tests call `/api/embeddings/*`. This session sets the pattern.

### Design — test-only change, zero engine modification

The pytest process never touches the GPU. It HTTP-embeds via the server, then queries LanceDB-GCS by pre-computed vector.

### Files to edit

### Test rewrite sketch

```python
def test_query_by_question_from_gcs( gcs_manager, server_embedder ):
    question = "How do I sort a list?"
    gcs_manager.add_snapshot( SolutionSnapshot( question=question, ... ) )

    vec = server_embedder( question )  # HTTP call to :7999 — zero GPU in pytest process

    results = gcs_manager.get_snapshots_by_embedding( vec )
    assert len( results ) > 0
    assert results[0].question == question
```
