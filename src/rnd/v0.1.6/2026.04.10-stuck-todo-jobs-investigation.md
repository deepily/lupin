### Queue consumer and scheduled-job handling (code review)

From `src/cosa/rest/queue_consumer.py:64-72`:
```python
# Queue has items but none are eligible yet (all paused or future-scheduled)
earliest = todo_queue.earliest_scheduled_at()
if earliest is None:
    # All jobs are paused (no scheduled times) — wait for a resume/push notify
    if todo_queue.debug: print( "[CONSUMER] All jobs paused, waiting for resume..." )
```

The consumer **does** support "stuck" states:
- **Paused jobs**: sit in todo indefinitely until explicitly resumed (UI `▶` button). They're treated as "not ready" by the consumer, which waits on a push notify.
- **Future-scheduled jobs**: sit until `scheduled_at` fires. Consumer wakes up at the earliest scheduled time.

Both are legitimate states, not bugs. Jobs in these states would be visible in the UI as paused badges or scheduled badges on the job card.

### The e2e test suite's queue traffic

E2E tests that exercise queue APIs create **real** queue jobs during their runs:
- `test_qa_submission.py` (9 tests) — submits Q&A jobs via `/api/push`
- `test_job_dispatch.py` (31 tests) — submits various agent jobs
- `test_queue_display.py` (12 tests) — checks queue card rendering
- `test_job_history_ui.py` (30 tests) — tests job persistence
- Several others

These jobs land in the live in-memory queues (filtered to the test DB via hot-swap config) and flow through todo → run → done. At any moment during the ~17-minute e2e run, several jobs can be waiting in todo for the consumer to pick them up — this is expected traffic, not stuck state.

## Most Likely Explanation

The user was watching the UI during the scheduled 10:32 EDT e2e run. The jobs they saw:
1. Were submitted by test fixtures as real queue pushes (testing the queue API surface)
2. Landed in todo waiting for the consumer thread to dispatch them
3. Were transient — consumed within seconds as the test progressed
4. Were visible to them because the e2e test's hot-swap didn't isolate from UI observers (the same WebSocket/queue state is broadcast to any authenticated observer)

The "dead or paused" framing was likely a misread of "pending" state (jobs waiting in todo but not yet running). Dead is a specific terminal queue that only failed jobs enter; paused is a specific attribute set by the user via the pause button.

**Alternate explanation** (less likely but possible): the user's UI browser session was authenticated with **admin** privileges and they were viewing all users' jobs via the admin queue filter. In that case, the jobs would have been other users' historical/active jobs visible via the admin view. But:
- I queried as `claude.code@lupin.deepily.ai` (the email from `~/.lupin/config`) and that account is `user` role, not admin
- If the user uses a different UI account with admin role, that would explain the discrepancy
- The persistence DB has no stuck jobs regardless of user, so even admin view should show zero today

## Recommendations

### For future observability

Add a **"stuck job reaper"** that runs periodically (e.g., every hour) and logs or cleans up jobs in todo that:
- Have `paused=true` for >24 hours (warning — user may have forgotten)
- Have `scheduled_at` in the past by >1 hour and haven't transitioned (regression — scheduler missed them)
- Have `created_at` >7 days ago and still in todo state (stuck)

This is future work, not urgent — the current investigation shows no actual leaks.

### For when it recurs

A diagnostic script is provided at `src/scripts/diagnose-stuck-jobs.sh` (to be written by user or next session). It should:
1. Login as the user's configured account
2. Query all four queues with no filter
3. If user is admin, also query `?user_filter=*` to see all users' jobs
4. Query the postgres `job_history` table directly to see persisted state
5. For any job found in todo with `paused=true` or `scheduled_at` in the past, print a warning

### For the user's immediate question

**Was this session's e2e run responsible for what the user saw?** Almost certainly yes — the user watched during the run, saw in-flight test traffic in the todo queue, and interpreted it as stuck jobs. The test harness's queue submissions are real and visible.

**Is there a bug?** No active bug. The "stuck jobs" phenomenon is expected behavior during e2e runs. If the user wants to hide test traffic from normal UI observation during tests, the test harness could emit a "test mode active" banner or route test jobs to a non-broadcasting queue — both are feature work, not bug fixes.
