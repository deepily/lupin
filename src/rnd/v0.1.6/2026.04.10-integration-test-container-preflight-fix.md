# Fix scheduled integration test pre-flight for containerized execution

## Context

Last night's scheduled integration test run (`io/test-suite/2026.04.10-at-03:20-integration-results.md`) reported 0 tests passed, 0 failed, 0 skipped. The runner aborted during pre-flight with:

```
[POSTGRES] Ensuring PostgreSQL is ready...
✗ docker-compose.yml not found in LUPIN_ROOT: /var/lupin
[ERROR] Failed to start/verify PostgreSQL
```

This is a silent regression for scheduled runs only. Manual `./src/tests/run-integration-tests.sh --bg -v` from the user's shell still works because it runs on the host, where `docker-compose.yml` and the `docker` CLI are both present.

### Why it fails only when scheduled

1. The FastAPI server runs inside a Docker container (`lupin-rest`, image `lupin:0.9.0`). Inside that container, `LUPIN_ROOT=/var/lupin` is the correct bind-mount path — this is NOT an environment bug.
2. Only `src/` and `io/` are bind-mounted into the container. `docker-compose.yml` lives at the repo root on the host and is NOT mounted.
3. The container has no `docker` CLI, no `docker-compose`, and no `/var/run/docker.sock`. It cannot manage sibling containers at all.
4. The scheduled test-suite job runs its subprocess from inside this container via `subprocess.Popen` in `src/cosa/agents/test_suite/job.py:619`. The subprocess inherits the container environment and correctly sets `LUPIN_ROOT=/var/lupin`.
5. The subprocess invokes `src/tests/run-integration-tests.sh`, which immediately calls `src/scripts/run-postgresql-dev.sh` (line 143). That script hard-requires `$LUPIN_ROOT/docker-compose.yml` (line 76) and further calls `docker ps`, `docker compose up`, and `docker exec` throughout — every one of those would fail inside the container even if the compose file were present.
6. Meanwhile, `lupin-postgres-dev` has been up and healthy for two days. The test DB `lupin_db_test` already exists with schema applied. The pre-flight script is trying to "ensure" something that is already true, via a mechanism that cannot work from the container.

### Desired outcome

Scheduled integration tests run to completion from inside the `lupin-rest` container, using the same runner script as the manual host path. Manual host runs continue to work unchanged.

## Root cause

The runner's pre-flight was designed for a host-based execution model (one process, on the host, with docker access). When the same runner is reused from inside a container, every docker-CLI operation in `run-postgresql-dev.sh` is unreachable by construction. The pre-flight needs a context-agnostic readiness check — one that verifies Postgres is reachable and the test DB has schema, using only a Python client library that's already installed.

## Fix

Replace the shell-based pre-flight with a Python-based readiness check that works identically on the host and inside the container.

### 1. Create `src/tests/preflight_test_db.py` (new file, ~70 lines)

Requirements:
- Set `LUPIN_ENV=testing` in-process before importing the DB module so `get_database_url()` returns the test DSN.
- Import `get_database_url` from `cosa.rest.db.database` to build the DSN via the same path the app uses. This automatically picks up `DB_HOST=lupin-postgres-dev` inside the container and defaults to `localhost` on the host.
- Connect with `psycopg2` (already installed in the container; pinned in the project's deps).
- Verify:
  1. TCP reachability and auth (trivial `SELECT 1`).
  2. `lupin_db_test` is the active database.
  3. The `users` table exists in the `public` schema (proxy for "schema applied", same check the bash script uses at line 183 of `run-postgresql-dev.sh`).
- On success: print banner-style status lines matching the existing runner output style (`[POSTGRES] Ensuring PostgreSQL is ready...` then green `✓ PostgreSQL ready`).
- On failure: print a red error with the DSN (password masked) and the underlying exception, then `sys.exit(1)`.
- Use spaces inside parens/brackets, aligned equals signs, and Design-by-Contract docstring per project style.
- No defensive `getattr` chains; fail loudly if dependencies are missing.

Bootstrap pattern: this is a standalone script and must use the `LUPIN_ROOT` bootstrap per the project's path management rules (insert `LUPIN_ROOT/src` into `sys.path`, then `import cosa.utils.util as cu`).

### 2. Modify `src/tests/run-integration-tests.sh` lines 140–148

Replace the single call to `run-postgresql-dev.sh` with a direct invocation of the Python pre-flight. The Python script is context-agnostic, so no branching is needed:

```bash
# Ensure PostgreSQL test database is ready (works from host or inside container)
echo -e "${YELLOW}[POSTGRES] Ensuring PostgreSQL test database is ready...${NC}"

if ! python3 "$PROJECT_ROOT/src/tests/preflight_test_db.py"; then
    echo ""
    echo -e "${RED}[ERROR] PostgreSQL test database pre-flight failed${NC}"
    echo -e "${RED}        Is lupin-postgres-dev running? Try: $PROJECT_ROOT/src/scripts/run-postgresql-dev.sh${NC}"
    echo ""
    exit 1
fi
```

The existing `run-postgresql-dev.sh` remains untouched — it is still the correct tool for manually bringing Postgres up from the host when the container is actually stopped. We just stop using it as a mandatory pre-flight gate.

### 3. What we are NOT changing

- `src/cosa/agents/test_suite/job.py` — the subprocess launch (line 619–626) is already correct. It passes `env={ **os.environ, "LUPIN_ROOT": project_root }` explicitly and resolves `project_root` via `cu.get_project_root()`, both of which return the right values inside the container.
- `src/scripts/run-fastapi-lupin.sh` — despite the hard-coded `cd /var/lupin/src`, this script is ONLY intended to be invoked as the container's entrypoint where that path is correct. It is not the cause of this bug.
- `src/cosa/utils/util.py:649` — the `/var/lupin` fallback in `get_project_root()` is not being hit in this bug. The container genuinely has `LUPIN_ROOT=/var/lupin` set. Leave it alone.
- `src/scripts/run-postgresql-dev.sh` — still useful from the host for actually starting Postgres from nothing. Leave it alone.

## Verification

All verification commands are read-only / idempotent. No GPU workloads involved.

### Smoke the pre-flight directly

**Inside the container** (exercises the scheduled test path):
```bash
docker exec lupin-rest bash -c 'python3 /var/lupin/src/tests/preflight_test_db.py'
```
Expected output: green `✓ PostgreSQL test database ready` and exit 0.

**On the host** (exercises the manual path):
```bash
python3 src/tests/preflight_test_db.py
```
Expected: same success output, using `DB_HOST=localhost` (or whatever the user's shell has).
