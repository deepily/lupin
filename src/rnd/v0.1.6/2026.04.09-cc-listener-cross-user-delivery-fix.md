# Plan: Fix CC Listener Sessions Not Appearing in Notification Diagnostics

## Context

Claude Code hook notification listeners (`CCNotificationListener`) are running and connected via WebSocket, but the notification diagnostic output shows 0 listener sessions:

```
[NOTIFY]   Browser sessions  : 2 ['foolish goat', 'slow zebra']
[NOTIFY]   Listener sessions : 0 []
```

**Root cause**: User identity mismatch between browser and listener sessions.

- **Browser sessions** authenticate as the human user (e.g., `rruiz@deepily.ai`) → user_id UUID-A
- **CC Listener sessions** authenticate as `claude.code@lupin.deepily.ai` (service account from `~/.lupin/config`) → user_id UUID-B

The diagnostic at `notifications.py:427-432` only queries `ws_manager.user_sessions[target_system_id]` (the human user's UUID). Listeners under the service account UUID never appear. Additionally, `emit_to_user_sync()` broadcasts only to the human user's sessions, so listeners never receive notifications either.

**Confirmed evidence**:
- 3 listener processes are alive (`ps aux | grep cc_notification_listener`)
- All successfully authenticate and connect (`cc-listeners.log` shows "=== LISTENER STARTED ===" and "Authenticated")
- Listeners authenticate as user_id `931e9dae-6c61-41b7-b17e-9fc7d9faca25` (`claude.code@lupin.deepily.ai`)
- Browser sessions are under a different user_id

## Approach: Targeted Cross-User Delivery

Preserve the service account separation (don't change listener credentials). Instead, use the existing `emit_to_session()` capability to directly target listener sessions by their deterministic session ID (`cc-listener-{job_id_hash}`).

## Changes

### Fix 1: Add `emit_to_session_sync` to WebSocketManager (prerequisite)

**File**: `src/cosa/rest/websocket_manager.py`
**Insert after**: `emit_to_user_sync` method (~line 484)

Add a sync wrapper for `emit_to_session()`, following the exact pattern of `emit_to_user_sync()`. This is needed because the notification queue and router code call from synchronous contexts.

```python
def emit_to_session_sync( self, session_id: str, event: str, data: dict ):
    """Thread-safe synchronous wrapper for emit_to_session."""
    if session_id not in self.active_connections:
        return
    # ... same pattern as emit_to_user_sync: check main_loop, run_coroutine_threadsafe
```

### Fix 2: Fire-and-forget delivery — also emit to listener session

**File**: `src/cosa/rest/notification_fifo_queue.py`
**Three locations** where `emit_to_user_sync` is called:
- Line 253 (inside `push()` method — normal priority path)
- Line 346 (inside `push_notification()` — urgent/high priority path)
- Note: normal priority in `push_notification()` delegates to `push()` at line 356, so line 253 covers that case

After each `emit_to_user_sync` call, add a targeted emit to the cc-listener session if `notification.job_id` is present:

```python
# Cross-user delivery: CC listeners authenticate as service account
if notification.job_id:
    listener_sid = f"cc-listener-{notification.job_id}"
    self.websocket_mgr.emit_to_session_sync( listener_sid, 'notification_queue_update', event_data )
```

**Note**: The notifications.py router now has an idempotency layer (lines 452-467) and direct PostgreSQL persistence (lines 469-494) BEFORE the FIFO push at line 515. These are upstream of our fix point and don't affect it — the FIFO queue's `push_notification()` call at line 515 still triggers `emit_to_user_sync` internally, which is where we add the listener delivery.

### Fix 3: `user_initiated_message` delivery — also emit to listener session

**File**: `src/cosa/rest/routers/queues.py`

```python
# Cross-user delivery to CC listener
if job_id:
```

### Fix 4: Diagnostic output — show all listener sessions across users

**File**: `src/cosa/rest/routers/notifications.py`
**After**: line 432

Add a cross-user scan for all cc-listener sessions in `active_connections`:

```python
all_listener_sessions = [
    s for s in ws_manager.active_connections
    if s.startswith( "cc-listener-" )

print( f"[NOTIFY]   All CC listeners  : {len( all_listener_sessions )} {all_listener_sessions}" )
```

## Risk Assessment

- **Duplicate delivery**: If credentials ever change to match the human user, listeners would receive notifications twice (once via `emit_to_user_sync`, once via `emit_to_session_sync`). Benign — listener filters by `job_id`.
- **Performance**: `emit_to_session_sync` does an O(1) dict lookup first; no-op when listener isn't connected.
- **No breaking changes**: All changes are additive. Existing flows are untouched.
