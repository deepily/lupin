## Problem Statement

CJ Flow tracks job state across three overlapping dimensions that are increasingly fragmented:

| Dimension | Values | Location |
|-----------|--------|----------|
| `status` field | `pending`, `running`, `completed`, `cancelled`, `failed` | Job object + PostgreSQL `status` column |
| Queue position | `todo`, `run`, `done`, `dead` | Which FifoQueue instance holds the job |
| `paused` flag | `True`/`False` | Job object (runtime only, not persisted) |

**Redundancy**: "running" status + "run" queue is redundant. A job could have `status=running` but be logically paused.

**Fragility**: Adding more boolean flags (future: `suspended`, `waiting_for_dependency`, etc.) will compound the fragmentation. Each new flag doubles the state space without formal transition rules.

**Origin**: Identified in the [Timed Execution plan](2026.03.27-cj-flow-timed-execution-monopolize-pause.md) (Architectural Note, Section 6) and deferred as a standalone prerequisite for the Hybrid Fast Lane.

### 2. Complete State Graph Design

**Why**: The sketch from the timed execution plan is incomplete. It doesn't account for all current states or distinguish queue-position states from lifecycle states.

**States to enumerate**:
- `expediting` — speculative job card phase (pre-queue, voice path only)
- `queued` — in todo queue, eligible for immediate execution
- `scheduled` — in todo queue, waiting for `scheduled_at` time
- `paused` — in todo queue, skipped by consumer until resumed
- `running` — in running queue, `_execute()` in progress
- `completed` — in done queue, successful
- `failed` — in dead queue, error during execution
- `cancelled` — in dead queue, user-initiated cancellation
- `interrupted` — server crashed during execution (persistence recovery)

**Design decisions needed**:
- Is `dead` a state or a queue? (Currently it's a queue that holds both `failed` and `cancelled`)
- Does `expediting` belong in the state machine? (It's a speculative pre-queue phase)
- Can a `running` job transition to `paused`? (Currently no — pause is todo-queue only)
- What about `waiting_for_dependency`? (Future: job chaining, e.g., Research → Podcast)

### 3. Persistence Model Decision

**Current model**:
- `status` is a PostgreSQL column (`job_history.status`)
- `paused` is runtime-only (in-memory todo queue)
- `scheduled_at` and `monopolize` are in JSONB `metadata_json`

**Questions to answer**:
- Does `job_state` replace the `status` column? Or coexist?
- Should `paused` be persisted? (Today: no historical value. With state machine: yes, it's a real state)
- Migration: what happens to existing rows with old `status` values?
- Does the state machine column use an enum type or free-text?

## Sequencing Options

### Option A: State Machine First, Then HFL
```
State Machine Refactor → HFL Freshness Review → HFL Implementation
```
**Pro**: Clean foundation for HFL. Monopolize enforcement is a state transition, not a boolean check.
**Con**: Larger upfront investment before the concurrency payoff.

### Option B: HFL First (Minimal), Then State Machine
```
HFL Freshness Review → HFL Implementation (minimal) → State Machine Refactor → HFL Phase 2
```
**Pro**: Faster path to concurrent execution. State machine can be informed by HFL's actual needs.
**Con**: May need to retrofit HFL code after state machine refactor.

### Option C: Independent Tracks
```
HFL Freshness Review → Determine if truly independent → Parallel if so
```
**Pro**: No blocking dependencies.
**Con**: Only viable if HFL doesn't need formal state transitions.

**Recommendation**: Start with HFL freshness review (Step 1 above) to determine which option is viable.
