# Fix: extend `DELETE /api/queue/{queue_name}/{job_id}` to accept `todo`, then have the CJ Flow E2E test clean up after itself

## Context

Five `[Mock]` jobs are stranded in PAUSED state in the in-memory todo queue, all created by `e2e_test@example.com`. They were left behind by `src/tests/e2e_ui/test_cj_flow_pause_schedule.py`, which submits 14 mock jobs across its 14 test methods (per a `_submit_mock_job` grep) and never deletes any of them. The five you're seeing today happen to be the ones that ended their test in `PAUSED` state, so the queue consumer's eligibility predicate (`state != PAUSED AND scheduled_at <= now`) skips them forever.

The investigation revealed three contributing causes (full write-up in the previous version of this plan file, now superseded):

1. The test file has zero teardown primitives — no fixture, no `addfinalizer`, no `afterEach`.
2. The hot-swap test mode shares the in-memory todo queue across `[Lupin: Testing]` and `[Lupin: Development]` config blocks, so test residuals leak into your dev queue.
3. The existing `DELETE /api/queue/{queue_name}/{job_id}` endpoint at `src/cosa/rest/routers/queues.py:896` hardcodes `queue_map` to `{run, done, dead}` and explicitly returns 400 for `todo`. The capability exists in `src/cosa/rest/todo_fifo_queue.py:1198` (`delete_by_id_hash` already wakes the consumer via `condition.notify()`), but no router exposes it. The UI's ✕ button in `notifications.js:8095` is also a stub that just shows an "(not implemented yet)" alert.

Your decision: **extend the existing endpoint** to accept `todo` (rather than create a new endpoint), and have the test call it from a teardown fixture so future runs clean up after themselves.

This plan fixes (1) and (3). It does **not** address (2) — the hot-swap shared-queue contamination is a separate, larger architectural question — but with proper teardown the contamination becomes a non-issue in practice.

## What this fix does and does not do

**Does**:
- Extend `delete_queue_job` in `src/cosa/rest/routers/queues.py` to accept `todo` as a valid `queue_name`.
- Add a `pytest.fixture` to `src/tests/e2e_ui/test_cj_flow_pause_schedule.py` that tracks every mock job submitted during a test and deletes each one in teardown.
- Refactor `_submit_mock_job` calls in all 14 test methods to go through the tracker fixture.
- Wire the existing `deleteQueueJob(jobId, queueName)` UI flow into todo cards by repurposing the ✕ button: on todo cards it now calls `deleteQueueJob('${jobId}', 'todo')` instead of the currently-broken `cancelJob('${jobId}')`. Run cards keep `cancelJob`.

**Does not**:
- Add a new endpoint.
- Add a separate 🗑 button to todo cards (we use the existing ✕ slot to keep the UI uncluttered — see "UI change rationale" below).
- Touch the unrelated `deleteJob` stub at `notifications.js:8095` (a different code path tied to a different render — can be cleaned up in a follow-up).
- Address the hot-swap shared-queue isolation issue.
- Auto-expire old mock jobs.
- Clean up the five jobs currently stranded — those need a one-shot recovery (described at the bottom).

## Test change — `src/tests/e2e_ui/test_cj_flow_pause_schedule.py`

### Approach: tracker fixture + helper redirection

Add a per-test pytest fixture that owns a list of created job IDs. Each test method receives the fixture as a parameter; it returns a callable that wraps `_submit_mock_job` and appends the resulting `job_id` to the list. After the test yields, the fixture iterates the list and DELETEs each one against `/api/queue/todo/{id}`.

This is the standard pytest setup-yield-teardown pattern. It's autouse-friendly (we don't strictly need autouse here because every test takes the fixture as a named param), it covers all 14 test methods uniformly, and a single test failure during a delete doesn't block subsequent deletes.

### New fixture

Add to `src/tests/e2e_ui/test_cj_flow_pause_schedule.py` after the existing helper functions (after line 88, before the test classes start):

```python
import pytest


@pytest.fixture
def mock_job_tracker( notifications_page ):
    """
    Per-test mock job submission tracker with automatic teardown.

    Returns a callable with the same signature as _submit_mock_job (minus the
    page argument). Each call records the resulting job_id; at teardown, every
    recorded id is removed from the todo queue via DELETE /api/queue/todo/{id}.

    Requires:
        - notifications_page fixture is active and authenticated as e2e_test@example.com

    Ensures:
        - All jobs created via the returned callable are deleted on teardown,
          regardless of test pass/fail
        - 404s during teardown (e.g. job already drained to running) are tolerated
        - One delete failure does not block subsequent deletes
    """
    page         = notifications_page
    created_ids  = []

    def submit( scheduled_at=None, monopolize=False, description=None ):
        result = _submit_mock_job(
            page,
            scheduled_at = scheduled_at,
            monopolize   = monopolize,
            description  = description,
        )
        created_ids.append( result[ "job_id" ] )
        return result

    yield submit

    # Teardown: best-effort delete every tracked job
    token = _get_auth_token( page )
    for job_id in created_ids:
        try:
            response = page.request.delete(
                f"{BASE_URL}/api/queue/todo/{job_id}",
                headers = { "Authorization": f"Bearer {token}" },
            )
            if not response.ok and response.status != 404:
                print( f"[TEARDOWN] DELETE /api/queue/todo/{job_id} returned {response.status}: {response.text()}" )
        except Exception as e:
            print( f"[TEARDOWN] Failed to delete mock job {job_id}: {e}" )
```

## UI change — `src/fastapi_app/static/js/notifications.js`

### What's actually broken today on todo cards

The ✕ button you see next to your stranded paused cards is **not** the unimplemented `deleteJob` stub at line 8095 — that stub belongs to a different render path (the `delete-job` span class added only to done-list cards in `renderDoneJobsList`, lines 7904 / 7956–7984). The ✕ on a todo card comes from a different rendering branch at lines 6807–6810:

```javascript
const hasCancelBtn = ( queueName === 'run' || queueName === 'todo' );
const cancelBtnHtml = hasCancelBtn
    ? `<button type="button" class="job-cancel-button" id="job-cancel-${jobId}" onclick="event.stopPropagation(); window.notificationsUI.cancelJob('${jobId}')" title="Cancel this job">✕</button>`
    : '';
```

It calls `cancelJob(jobId)` which in turn hits `POST /api/jobs/{job_id}/cancel`. The server-side handler at `src/cosa/rest/routers/queues.py:826–893` looks the job up via `running_queue.get_by_id_hash(job_id)` and returns 404 if it isn't in the running queue (line 871–874), and additionally requires the job to be an `AgenticJobBase` instance (line 881–882). For a paused mock job sitting in the todo queue, the lookup fails immediately. So clicking ✕ on your stranded cards has been quietly throwing 404s — the broken UX you've been living with.

Meanwhile the **🗑 delete button** at lines 6818–6822 already wires through to a fully-implemented `deleteQueueJob(jobId, queueName)` method at line 6103: confirm dialog → DELETE call → DOM removal → count-badge update → error handling. It currently only renders for `run/done/dead`.

### UI change rationale: repurpose the ✕ button on todo cards instead of adding a third button

The natural mental model for ✕ on a queued job is "make this job go away." For a running job, the only correct way to make it go away is graceful cancel via `cancelJob`. For a todo queue job (queued, scheduled, or paused), the correct way is forceful delete via `deleteQueueJob`. Same intent, different mechanism. Splitting the rendering branch by `queueName` keeps one button per card and fixes the broken ✕ in passing. Adding a separate 🗑 alongside the broken ✕ would clutter the card and leave the broken-button bug unfixed.

### The change

Rewrite lines 6807–6811 from:

```javascript
const hasCancelBtn = ( queueName === 'run' || queueName === 'todo' );
const cancelBtnHtml = hasCancelBtn
    ? `<button type="button" class="job-cancel-button" id="job-cancel-${jobId}" onclick="event.stopPropagation(); window.notificationsUI.cancelJob('${jobId}')" title="Cancel this job">✕</button>`
    : '';
const headerCancelClass = hasCancelBtn ? ' has-cancel' : '';
```

to:

```javascript
// ✕ button means "make this job go away" — but the mechanism differs by queue:
//   - run queue: graceful cancel via cancelJob (POST /api/jobs/{id}/cancel)
//   - todo queue: forceful delete via deleteQueueJob (DELETE /api/queue/todo/{id})
let cancelBtnHtml      = '';
let headerCancelClass  = '';
if ( queueName === 'run' ) {
    cancelBtnHtml     = `<button type="button" class="job-cancel-button" id="job-cancel-${jobId}" onclick="event.stopPropagation(); window.notificationsUI.cancelJob('${jobId}')" title="Cancel this job">✕</button>`;
    headerCancelClass = ' has-cancel';
} else if ( queueName === 'todo' ) {
    cancelBtnHtml     = `<button type="button" class="job-cancel-button" id="job-cancel-${jobId}" onclick="event.stopPropagation(); window.notificationsUI.deleteQueueJob('${jobId}', 'todo')" title="Remove this job">✕</button>`;
    headerCancelClass = ' has-cancel';
}
```

That's the entire UI diff. The button keeps its `job-cancel-button` class so existing CSS, hover styles, and the `has-cancel` header class continue to apply unchanged. Only the click handler and the title differ for todo cards.

**Also**: the existing `deleteQueueJob` docstring at `notifications.js:6107–6109` still says `queueName is 'run', 'done', or 'dead'`. Update it to mention `todo` for consistency. Single-line edit, no logic change.

## Cleaning up the five currently stranded jobs

This is **out of scope of the code change** but we should agree on a recovery path before declaring the fix complete. Options:

1. **Use the new endpoint manually after deploying the fix.** Once the queues.py change is live, fire five `curl -X DELETE` calls (or call them from the browser console) against `/api/queue/todo/<id>` with your admin token. Clean and surgical.
2. **Click ▶ Resume on each card.** Each job's `scheduled_at` is now in the past, so resume → consumer picks it up → 25-second sleep → done queue → existing UI delete works. Five clicks, ~2 minutes of consumer time.
3. **Restart `lupin-rest`.** The in-memory todo queue is wiped on process restart. Caveat: anything else in the in-memory todo queue right now also vanishes.

I'd recommend (1) — it exercises the new endpoint, validates ownership, and leaves nothing else dirty.
