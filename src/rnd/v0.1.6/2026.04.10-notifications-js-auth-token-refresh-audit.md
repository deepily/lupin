## Context

During the 2026-04-10 e2e bug-fix session, the user clicked the **Activity Log** button on a long-running e2e job card and got:

```
notifications.js?v=20260310b:10394 [Notifications ERROR]
Error loading interactions for job ts-e49002f6::50c73ba7-...:
Error: HTTP 401
```

**Immediate cause**: `notifications.js:7185` `loadJobInteractions()` calls `fetch( '/api/get-job-interactions/...' )` with `Authorization: this.getAuthHeader()` but does **not** call `await this.ensureValidToken()` first. JWT access tokens expire after 30 minutes (`jwt access token expire minutes = 30`), and the user had been idle waiting for the e2e suite. So the fetch sent a stale token, and the server returned 401.

**Why this matters**: The same gap exists across many other UI buttons. Anyone idle 30+ minutes will hit 401s on those buttons until they hard-refresh the page. This is exactly the scenario users experience while waiting for long-running test/agentic jobs to finish.

## Approach Options

### Option A — Sprinkle `await this.ensureValidToken();` at each non-compliant site

**Pros**:
- Most surgical, minimum diff per site (one new line each)
- Pattern already exists 9 times in the codebase — consistent with prior style
- Zero new abstractions

**Cons**:
- 16 separate edits, each must remember to handle the case where `ensureValidToken` throws (the existing 9 compliant sites are inconsistent in error handling — some catch, some let it bubble)
- Adds 16 more places where a future contributor can forget the ritual — same bug class can re-appear
- No improvement in reviewability for the next 25 sites someone adds

### Option B — Introduce an `authedFetch( url, options )` helper, migrate all 25 sites to it

**Pros**:
- One central helper enforces the contract: `ensureValidToken` → inject `Authorization` header → `fetch` → return response
- Future fetch sites use the helper by default; the bug class is structurally prevented
- Diff at each call site is small (`fetch(...)` → `this.authedFetch(...)`) and trivially reviewable
- Catches mistakes in the 9 currently-compliant sites too if they drift later
- Single point to add future enhancements (retry-on-401, telemetry, header injection)

**Cons**:
- Touches 25 sites, not 16 (though the diff per site is smaller than Option A)
- One new method on `NotificationsUI` to maintain
- Requires reading every call site to preserve any custom headers/body each one passes

### Option C — Add a global `fetch` interceptor / wrapper at the window level + retry-on-401

**Pros**:
- Best UX: even if a token expires mid-request, the wrapper refreshes once and retries silently
- Catches any future code that uses raw `fetch` without going through `NotificationsUI`

**Cons**:
- Most invasive — patches `window.fetch`, affecting non-Lupin code that may share the page (third-party scripts, browser DevTools network, etc.)
- Subtle bugs: refresh-storms when many fetches fire concurrently and all see 401, race conditions in token rotation
- Out of scope for "fix the bug the user just hit"
- Hard to roll back without touching the same global

### Recommendation: **Option B**

Option B is the best balance of surgical and durable. Option A leaves the same footgun in the codebase; Option C is too big a swing for one bug. Option B makes the next 25 fetch sites someone adds automatically correct, with a one-line idiom (`this.authedFetch(url)`) that's at least as ergonomic as raw `fetch`.

### Phase 2 — Add the helper

Add to `NotificationsUI`, immediately after `ensureValidToken()` (around L908):

```javascript
async authedFetch( url, options = {} ) {
    /**
     * Fetch wrapper that proactively refreshes the JWT token before the call
     * and injects the Authorization header. Use this for any authenticated
     * API call from notifications.js — it ensures the token is valid and
     * eliminates 401s caused by stale tokens after the user is idle.
     *
     * Requires:
     *     - this.ensureValidToken() is callable
     *     - this.getAuthHeader() returns a valid Bearer string
     *
     * Ensures:
     *     - Token is refreshed if expired before the fetch fires
     *     - Authorization header is injected (does not overwrite if caller passed one)
     *     - All other fetch options pass through unchanged
     *     - Returns the Response object as-is — caller handles status checking
     *
     * Raises:
     *     - Whatever ensureValidToken() raises (auth failure)
     *     - Whatever fetch() raises (network failure)
     */
    await this.ensureValidToken();
    const headers = {
        'Authorization': this.getAuthHeader(),
        ...( options.headers || {} )
    };
    return fetch( url, { ...options, headers } );
}
```

**Constraint**: Must respect the project's spacing-inside-brackets convention. Above snippet is illustrative; exact final form follows existing notifications.js style.

### Phase 6b — Pattern A harmonization: auth.js + admin-snapshots.js ✅ DONE 2026-04-10

After user pushback on the too-narrow "notifications.js only" scoping, a cross-file audit revealed that Lupin had **two coexisting auth-refresh patterns**:
- **Pattern A (proactive)**: `notifications.js` — check token expiry before fetch, refresh if near-expiry. `authedFetch` helper wraps this.
- **Pattern B (reactive retry-on-401)**: `auth.js` `apiCall()` (L76) and `admin-snapshots.js` class method `apiCall()` (L184) — fire the fetch, catch 401, refresh, retry. Pre-existing, production quality.

Both patterns solve the same bug class. But mixed patterns in one codebase is a maintenance smell. User chose to harmonize on Pattern A.

**Changes**:
- **`src/fastapi_app/static/html/auth/js/auth.js`** — added two new standalone functions (`isTokenExpired`, `ensureValidToken`) between L61 and L63. Modified `apiCall()` to call `await ensureValidToken()` at the top of the `includeAuth=true` branch, guarded by `retryCount === 0` so reactive-path retries don't re-run the proactive check. Reactive retry-on-401 preserved as safety net (belt + suspenders — strictly better than removing).
- **`src/fastapi_app/static/html/admin/js/admin-snapshots.js`** — added `await ensureValidToken()` call in the class's `apiCall()` method before `getAccessToken()`. Uses auth.js's global (script load order already puts auth.js first on admin pages per `snapshots.html:241`).

**Key design choices**:
- `ensureValidToken()` returns `boolean` instead of throwing (auth.js's existing reactive path already handles the failure redirect; no new error paths needed)
- `isTokenExpired()` uses a 30-second buffer so tokens about to expire refresh before they actually do
- Both functions are standalone (not class methods) — admin-snapshots.js can call them globally the same way it already calls `getAccessToken`/`refreshAccessToken`
- Reactive retry-on-401 is KEPT as a safety net for edge cases (clock skew, mid-call server-side invalidation, race conditions)
- Recursion-safe: `refreshAccessToken()` calls `apiCall(..., includeAuth=false)` which bypasses the new `ensureValidToken` call entirely

**Verification**:
- `node --check` on both files → SYNTAX OK
- Cross-file audit confirmed: auth.js has 1 `ensureValidToken` definition + 1 call site; admin-snapshots.js has 1 call site (uses auth.js global); reactive retry present in both as expected safety net
- Manual smoke pending (user): login, admin snapshots search, 30+ min idle retry test

- `chunk-sequencer.js`, `websocket-diagnostic.js` — hardcoded mock tokens, security-adjacent

## Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| **Refresh storm**: many concurrent fetches all see expired token, all call refresh in parallel, server gets N refresh requests | `ensureValidToken()` already exists and presumably handles this — Phase 1 verifies the existing implementation isn't racy. If it is, fix that first as Phase 1.5. |
| **Helper diverges from manual sites in subtle ways** | Phase 4 (migrate the compliant sites too) eliminates this — uniform usage everywhere. |
| **Some fetch sites pass custom Authorization headers** (e.g. service-to-service auth) | Helper merges `options.headers` last so caller can override. Phase 1 manually checks for this. |
| **Token refresh itself fails** (refresh token also expired) | `ensureValidToken()` already calls `handleAuthFailure()` on refresh failure — that flow is unchanged. The user gets bounced to login as before, just earlier in the flow than they would with the old broken pattern. |
| **Migration breaks the 9 already-working sites** | Phase 4 is *separate* from Phase 3 in the diff. If anything breaks, Phase 4 can be reverted independently. |

## Why This Wasn't Caught Earlier

The 30-minute JWT TTL means the bug is invisible in normal interactive use — most users don't sit idle on a page for 30 minutes between clicks. It only surfaces during workflows where the user **is** idle that long: long-running e2e suite runs, agentic job execution, scheduled test waits. Those workflows became common only recently with the test-suite scheduling work in this branch, which is why the user is hitting it now.
