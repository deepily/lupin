## Two orthogonal root causes

### RC-1 — Interactions don't reach the job card

**Expected chain (happy path)**:
1. Agent: `voice_io.notify(msg, job_id=self.id_hash, ...)` (BFE, `bug_fix_expediter/job.py:207-228`) or `cosa_interface.notify_progress(..., job_id=self.job_id)` (TFE, `test_fix_expediter/orchestrator.py:146-174`).
2. Dispatcher → AsyncNotificationRequest → `lupin_cli/_notify_user_async()` → `POST /api/notify?job_id=...&sender_id=...&message=...`.
3. Endpoint persists via `NotificationRepository.create_notification(..., job_id=job_id, ...)` — confirmed forwarded at `src/cosa/rest/routers/notifications.py:482-493`.
4. Frontend renders card; `loadJobInteractions(jobId)` fetches `GET /api/get-job-interactions/{jobId}` (`notifications.js:~7454`).
5. Backend filters `Notification.job_id == jobId` (`queues.py:643-645`), returns rows.

**Where it can break** (in order of likelihood):
- (a) Agent-side: a subset of notify calls omit `job_id`, so those rows are persisted with NULL and never retrieved.
- (b) Dispatcher/lupin_cli-side: the `job_id` kwarg is accepted by the agent-facing helper but not included in the `/api/notify` query string.
- (c) `has_interactions` gate in queues.py (~line 344): if `bool(job.session_id)` is False for BFE/TFE jobs, the UI may not even call the interactions endpoint.
- (d) ID mismatch: job_id stored in DB is `dr-6f48863c` (id_hash), but frontend queries with compound `dr-6f48863c::uuid`. `loadJobInteractions` probably reads `job.id_hash` from the card data (queues.py surfaces `id_hash` at lines 336, 395, 444), so this is unlikely — but worth confirming.

**Investigation first** (do this before writing any code):
```sql
-- On test server Postgres (lupin_db_test):
SELECT id, job_id, sender_id, LEFT(message, 60) AS msg_preview, created_at
FROM notifications
WHERE job_id LIKE 'dr-6f48863c%' OR job_id LIKE 'ts-0df7387f%'
   OR sender_id ILIKE '%bug_fix%' OR sender_id ILIKE '%test_fix%'
ORDER BY created_at DESC
LIMIT 50;
```

Interpret:
- **Rows with matching job_id exist** → RC-1 is purely frontend (fetch uses wrong id). Fix: audit `loadJobInteractions` lookup key.
- **Rows exist with NULL job_id + matching sender_id** → RC-1 is agent/dispatcher side. Fix: find which notify sites don't pass job_id; fix each.
- **No rows at all** → notifications aren't landing on `/api/notify`. Check target_user resolution / auth / whether `_notify_user_async` actually ran.

Record the SQL result in-session; don't write code until RC-1's actual break point is known.

## Report content specifications

### BFE final report

Sections (markdown, H2 per section):
- **Summary** — final status (resubmitted / dry-run-only / failed), resubmitted_job_id if any, total wall time.
- **Dead job context** — dead_job_id, original question, failure excerpt.
- **Diagnosis** — the diagnosis text the model produced.
- **Proposed fixes** — table: index, description, rationale, one-line diff preview.
- **Selected fix** — which proposal won + reason + full diff.
- **Fix result** — pass/fail, stdout/stderr excerpt (last 40 lines).
- **Resubmission** — resubmitted_job_id + its current state if known.
- **Appendix: plan path** — link to the intermediate plan doc.

For **dry-run dead-job-not-found** path (the user's actual case), the report should still be written and contain: dead_job_id attempted, confirmation that the job wasn't found in any queue, troubleshooting pointers (stale reference? deleted job? wrong id format?).

### TFE final report

Sections:
- **Summary** — source_test_suite_job_id, cluster/proposed/selected/fixed counts, validation_run_job_id if rerun triggered.
- **Source test suite** — which suite(s), overall pass/fail counts, link to source junit report.
- **Cluster breakdown** — one subsection per cluster: cluster id, failure count, sample failure messages (first 3), proposed fix (if any) with diff excerpt, selected? applied? validation result.
- **Unfixable clusters** — ones where no proposal was produced + model's reason.
- **Validation rerun** — if triggered: rerun_job_id, diff of pass/fail counts pre/post.
- **Appendix** — plan_path, remediation_snapshot_path links.
