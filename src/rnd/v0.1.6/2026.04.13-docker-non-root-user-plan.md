# Docker Non-Root User — Permanent Fix for LanceDB Bind-Mount Permissions

**Date**: 2026-04-13
**Session**: 1cfcdf73 (follow-on, docker factoring)
**Prefix**: [LUPIN]
**Status**: Plan doc — to be integrated with ongoing docker-compose factoring work

---

## Context

Backup ran cleanly for months, then started exiting rsync code 23 ("Permission denied") against ~63k files in `src/conf/long-term-memory/lupin.lancedb/`. Root cause: the `lupin-rest-dev` and `lupin-rest-test` containers run as root (default — no `USER` directive in the Dockerfile). The `./src:/var/lupin/src` bind mount exposes LanceDB to the host, so every file the container writes lands on the host owned by `root:root` mode `-rw-------`. `rruiz` (the backup user on the host) can't read them.

Session 378's LanceDB test-isolation work (`src/rnd/v0.1.6/2026.03.26-upe-lancedb-test-isolation-and-warm-fix.md`) hit the same root cause from a different angle: *"test process can't drop root-owned LanceDB files, so we added a server-side `/api/prediction-engine/reset` endpoint because the container has root permission from Docker"*. Same file-ownership problem, different symptom.

## Immediate unblock (Option B, already done)

```bash
sudo chown -R rruiz:rruiz src/conf/long-term-memory/lupin.lancedb/
```

Fixes today's backup but regrows — the next container write will create new root-owned files.

## Permanent fix (Option C, this doc)

Run the `lupin-rest-dev` and `lupin-rest-test` containers as UID 1001 (`rruiz`) instead of root. Every file they write to bind-mounted volumes will be owned by `rruiz` on the host. Backup stays clean indefinitely.

---

## Why it's more than `user: "1001:1001"`

The Dockerfile (`docker/lupin/Dockerfile`) and compose file both assume `HOME=/root`. Five hard dependencies:

| Location | Reference | Switching to UID 1001 requires |
|---|---|---|
| Dockerfile line 128, 131 | `d2` CLI installed to `/root/.local/bin`, on PATH | Install d2 to a world-readable path, OR create `rruiz` home in image and install there |
| Dockerfile line 228 | `RUN mkdir -p /root/.claude` | Create `/home/rruiz/.claude` instead |
| Dockerfile line 231 | `COPY … /root/.claude/settings.json` | Copy to `/home/rruiz/.claude/settings.json` |
| Dockerfile line 232 | `COPY … /root/.claude/.mcp.json` | Copy to `/home/rruiz/.claude/.mcp.json` |
| compose mounts (x3) | `~/.lora_env:/root/.lora_env:ro`, `~/.lupin:/root/.lupin:ro`, `~/.claude/.credentials.json:/root/.claude/.credentials.json:ro` | Mount targets change to `/home/rruiz/...` |

**Fundamental constraint**: `/root` on Linux is mode `700` (owner-only access). UID 1001 cannot read *anything* under `/root` regardless of individual file perms. So the fix isn't "loosen perms in /root" — it's "relocate everything out of /root."

---

## Recommended approach

### 1. Dockerfile changes (`docker/lupin/Dockerfile`)

Add a non-root user early in the build so subsequent `RUN` / `COPY` lines can target its home:

```dockerfile
# Near the top, after base image setup:
ARG LUPIN_UID=1001
ARG LUPIN_GID=1001
RUN groupadd -g ${LUPIN_GID} rruiz && \
    useradd -m -u ${LUPIN_UID} -g ${LUPIN_GID} -s /bin/bash rruiz

ENV HOME=/home/rruiz

# Change existing lines:
# OLD: ENV PATH="/root/.local/bin:${PATH}"
# NEW:
ENV PATH="/home/rruiz/.local/bin:${PATH}"

# OLD: RUN mkdir -p /root/.claude
# OLD: COPY docker/lupin/claude-config/settings.json /root/.claude/settings.json
# OLD: COPY docker/lupin/claude-config/mcp.json /root/.claude/.mcp.json
# NEW:
RUN mkdir -p /home/rruiz/.claude && chown -R rruiz:rruiz /home/rruiz
COPY --chown=rruiz:rruiz docker/lupin/claude-config/settings.json /home/rruiz/.claude/settings.json
COPY --chown=rruiz:rruiz docker/lupin/claude-config/mcp.json /home/rruiz/.claude/.mcp.json

# d2 install: run as rruiz (or root then chown)
# Current install probably uses: curl ... | sh  → installs to $HOME/.local/bin
# If installer respects $HOME, switch to: USER rruiz before the curl, then USER root after if needed

# Near end, before CMD:
USER rruiz
```

### 2. docker-compose.yml changes

Add `user:` directive to both services + relocate the three credential bind mounts:

```yaml
lupin-rest-dev:
  # ... existing ...
  user: "1001:1001"
  volumes:
    - ./src:/var/lupin/src
    - ./io:/var/lupin/io
    - ./pytest.ini:/var/lupin/pytest.ini:ro
    - ~/.lora_env:/home/rruiz/.lora_env:ro              # was /root/.lora_env
    - ~/.lupin:/home/rruiz/.lupin:ro                    # was /root/.lupin
    - ~/.claude/.credentials.json:/home/rruiz/.claude/.credentials.json:ro   # was /root/.claude/...

lupin-rest-test:
  # ... existing ...
  user: "1001:1001"
  volumes:
    - ./src:/var/lupin/src
    - ./io:/var/lupin/io
    - ./pytest.ini:/var/lupin/pytest.ini:ro
    - ~/.lora_env:/home/rruiz/.lora_env:ro              # was /root/.lora_env
```

Leave the `postgres` service alone — it already uses its own `postgres` user inside and writes to an excluded bind-mount (`postgresql-dev-data` is in `rsync-exclude.txt`).

### 3. Verification that `HOME` resolves correctly

The Python code uses `os.path.expanduser("~")` or `Path.home()` in places (need to grep to confirm) — these respect `$HOME` at runtime. As long as the container ENV sets `HOME=/home/rruiz`, all consumer code should resolve to the right place without edits. **Action**: grep `src/cosa`, `src/fastapi_app`, `src/lupin_mcp`, `src/lupin_cli` for `os.environ["HOME"]`, `expanduser`, `Path.home` to confirm no hardcoded `/root/` exists.

## Side effects to watch during the docker bounce cycle

1. **Permissions on existing host files.** After rebuilding the image with UID 1001, the container expects to write to `./src/conf/long-term-memory/lupin.lancedb/` as UID 1001. Option B already chowned these to rruiz — good. But if any other bind-mounted subdir has leftover root ownership, the container will silently fail to write. Run a post-bounce check: `find src/ io/ -user root` — expect empty.

2. **`io/` dir.** Deep-research reports, podcast output, test results all land here. Same bind-mount, same root-write problem today. Will also self-heal after Option C.

3. **Test companions seeder.** `src/scripts/seed_test_companions.py` runs on container startup. If it assumes root to write seed artifacts to a bind-mount, may fail as UID 1001. Verify paths it writes to.

4. **Claude Code / MCP credentials mount.** `~/.claude/.credentials.json` is host-side at `/home/rruiz/.claude/.credentials.json`. Mounting it to `/home/rruiz/.claude/.credentials.json` inside the container looks clean but *the mount target directory doesn't exist in the image until the Dockerfile creates it* — which the updated Dockerfile above does (`mkdir -p /home/rruiz/.claude`). Just verify this survives rebuild.

5. **GPU device access.** `deploy.resources.reservations.devices.capabilities: [gpu]` — Nvidia runtime usually doesn't care about user, but if you see CUDA permission errors, check `/dev/nvidia*` ownership on host and whether the docker group grants access.

6. **`claude mcp` / `gh` CLI inside container.** If the BFE/TFE git strategy runs `gh pr create` from inside the container, it needs `gh auth` credentials accessible to UID 1001. Those typically live in `~/.config/gh/` — same pattern, same solution (mount to `/home/rruiz/.config/gh/`).

## Execution sequence (when you're ready to integrate)

1. Edit `docker/lupin/Dockerfile` per section 1 above
2. Edit `docker-compose.yml` per section 2 above
3. Build the new image: `docker compose build lupin-rest-dev lupin-rest-test`
4. Bounce: `docker compose down && docker compose up -d`
5. **Verify inside the container**: `docker exec lupin-rest-dev id` → expect `uid=1001(rruiz) gid=1001(rruiz)`
6. **Verify it can write**: hit an endpoint that writes LanceDB (e.g., submit a cached query) → check `ls -la src/conf/long-term-memory/lupin.lancedb/.../data/*.lance` → expect new files owned by `rruiz:rruiz`
7. **Run backup**: `/plan-backup --write` → expect exit code 0, no "Permission denied"

## What this does NOT solve

- **Historic root-owned files already chowned by Option B.** Those are fine; Option C only affects *new* writes.
- **Postgres data dir** (`postgresql-dev-data`). Already excluded from backup; postgres container uses its own internal user and writes stay inside that bind-mount. Not affected by this plan.
- **Live-churn during backup.** If you do a `/plan-backup --write` during heavy LanceDB writes, rsync may still see files vanish (normal for live systems) — but that's a rare benign warning, not the 63k-file permission flood we had.
