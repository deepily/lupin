## Context

CJ Flow Timed Execution (Phases 0-5) is backend-complete: `scheduled_at`, `monopolize`, and `paused` work end-to-end through the queue consumer, REST API, persistence, WebSocket events, and notification badges. But **users have no way to schedule a job** — scheduling is only possible via raw API calls. Two gaps remain:

1. **UI forms** — No date/time picker or monopolize toggle on any of the 6 job submission cards
2. **Voice path** — The Runtime Argument Expeditor collects agent-specific args but has no concept of runtime/infrastructure args like `scheduled_at` or `monopolize`

Additionally, the `ClaudeCodeQueueRequest` model is missing `scheduled_at` and `monopolize` fields entirely.

This plan closes those gaps plus the 3 remaining checklist items (3.10, 4.3, 6.3) from the parent plan (`src/rnd/2026.03.27-cj-flow-timed-execution-monopolize-pause.md`).

## Architecture: Option C — Runtime Args in Confirmation Step

Runtime args (`scheduled_at`, `monopolize`) are **not agent-specific** — they apply universally to all job types. Rather than expanding the expeditor's gap analysis or adding a separate interaction layer, we embed runtime args into the existing confirmation summary with sensible defaults:

```
**Deep Research Job Summary**

- **query**: What is quantum computing?
- **budget**: 50
- **audience**: technical

---
⏱️ **Scheduling**
- **Run at**: immediately
- **Exclusive mode**: no
```

The user can modify these via the existing `[comment: ...]` pattern: *"yes, but schedule it for 2am"* or *"yes, but run it in exclusive mode"*.

### Why This Works

- No new interaction flow — rides on the existing confirmation YES_NO
- Defaults ("immediately", "no") mean zero friction for users who don't care about scheduling
- The LLM modification parser already handles free-form changes — "schedule for 2am" maps naturally to `scheduled_at`
- Runtime args are extracted from `args_dict` in `_handle_agentic_command()` before passing to the factory

### Two-Tier Argument Model

| Category | Examples | Who Consumes | Scope |
|----------|----------|-------------|-------|
| **Agent args** | `query`, `budget`, `source`, `audience` | Job's `_execute()` | Per-agent, varies |
| **Runtime args** | `scheduled_at`, `monopolize`, `dry_run` | Queue consumer / infrastructure | Universal, all agents |

The expeditor handles agent args via LLM gap analysis. Runtime args bypass gap analysis — they get sensible defaults and appear only in the confirmation summary where the user can override them.

```javascript
_getSchedulingParams( formPrefix ) {
    const params = {};
    const scheduleCheckbox = document.getElementById( `${formPrefix}-schedule` );
    const scheduleTime = document.getElementById( `${formPrefix}-scheduled-time` );
    const monopolizeCheckbox = document.getElementById( `${formPrefix}-monopolize` );

    if ( scheduleCheckbox?.checked && scheduleTime?.value ) {
        params.scheduled_at = new Date( scheduleTime.value ).toISOString();
    }
    if ( monopolizeCheckbox?.checked ) {
        params.monopolize = true;
    }
    return params;
}
```

### Phase 2: Voice Path — Runtime Args in Expeditor Confirmation

**Goal**: Add runtime scheduling options to the expeditor's confirmation summary so voice users can schedule jobs.

#### 2.1 Add runtime args section to confirmation summary
**File**: `src/cosa/agents/runtime_argument_expeditor/expeditor.py`

In `_confirm_and_iterate()` (~line 326-335), after building agent arg summary lines, append:

```python
# Runtime scheduling section (universal, not agent-specific)
summary_lines.append( "" )
summary_lines.append( "---" )
summary_lines.append( "⏱️ **Scheduling**" )
summary_lines.append( f"- **run_at**: { args_dict.get( 'scheduled_at', 'immediately' ) }" )
summary_lines.append( f"- **exclusive_mode**: { 'yes' if args_dict.get( 'monopolize' ) else 'no' }" )
```

These use human-friendly display names (`run_at`, `exclusive_mode`) that the LLM modification parser can map back to `scheduled_at` and `monopolize`.

#### 2.2 Add runtime arg names to modification parser's valid set
**File**: `src/cosa/agents/runtime_argument_expeditor/expeditor.py`

In `_parse_modification()` (~line 378-446), the LLM receives a list of valid arg names. Add `scheduled_at` and `monopolize` to that list so the parser can recognize modifications like "schedule for 2am" → `{ arg_name: "scheduled_at", new_value: "2026-03-31T02:00:00" }`.

#### 2.3 Extract runtime args in `_handle_agentic_command()`
**File**: `src/cosa/rest/todo_fifo_queue.py`

After `expeditor.expedite()` returns `args_dict` and before `create_agentic_job()`, pop runtime args:

```python
# Extract runtime args (not agent-specific, consumed by queue infrastructure)
scheduled_at = args_dict.pop( "scheduled_at", None )
monopolize   = args_dict.pop( "monopolize", False )
```

After factory creates the job, set them on the job object:

```python
job.scheduled_at = scheduled_at
job.monopolize   = _parse_boolean( monopolize ) if isinstance( monopolize, str ) else bool( monopolize )
```

This happens in the same block (~lines 1106-1122) where `job.id_hash` is already mutated post-factory.

#### 2.4 Handle "immediately" → None normalization

When the user doesn't modify the default, `scheduled_at` will be the string `"immediately"` in args_dict. Normalize:

```python
if scheduled_at and scheduled_at.lower() in ( "immediately", "now", "none" ):
    scheduled_at = None
```

Similarly for monopolize: `"no"` → `False`, `"yes"` → `True`.
