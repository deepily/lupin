# Refactor: introduce a canonical "user + admin" WebSocket emit method, eliminate the dual-call discipline

## Context

Yesterday's CJ Flow E2E test cleanup fix is working correctly — the `mock_job_tracker` fixture deletes every parked mock job after each test, and the docker logs from last night's 8:50 PM EDT scheduled run prove it (14 successful `DELETE /api/queue/todo/...` 200 responses, one per test method). But the user came in this morning to find 14 stranded `[Mock]` cards in the admin queue UI. Hitting refresh made them disappear. The user's correct hypothesis: the deletes ARE landing server-side, but the WebSocket notification telling the admin browser to remove the cards is failing or not reaching them. Confirmed via grep.

Root cause: **broadcast scope asymmetry between the create path and the delete path**.

In `src/cosa/rest/queue_util.py:76–84`, `emit_job_state_transition()` does the right thing — emits to BOTH the owning user AND all admin sessions:

```python
if user_id:
    websocket_mgr.emit_to_user_sync( user_id, 'job_state_transition', data )
    websocket_mgr.emit_to_admins_sync( 'job_state_transition', data, exclude_user_id=user_id )
else:
    websocket_mgr.emit( 'job_state_transition', data )
```

This is why the admin UI saw the mock job CARDS appear — the test users have no browser sessions of their own, but `emit_to_admins_sync` reached the admin's `foolish goat` / `clumsy kangaroo` / etc. sessions and painted the cards.

But three handlers in `src/cosa/rest/routers/queues.py` only do half of this:

| File:line | Event | Handler | Bug |
|---|---|---|---|
| `routers/queues.py:988` | `job_removed` | `delete_queue_job` | Only `emit_to_user_sync` — admins never see deletions |
| `routers/queues.py:1267` | `job_state_transition` (PAUSED) | pause endpoint | Only `emit_to_user_sync` — admins never see pauses |
| `routers/queues.py:1338` | `job_state_transition` (QUEUED, from PAUSED) | resume endpoint | Only `emit_to_user_sync` — admins never see resumes |

So admins watch jobs appear, see them update through normal `job_state_transition` events, but never see them paused, resumed, or removed. Stale cards accumulate until refresh.

The user's directive: **"if we are continuously obligated to make these two calls consecutively, then that tells me we need to refactor and call only one method that essentially calls both under the covers so that we get consistency. All implementers call one function which handles both groups of target listeners."** Fix it once and forget about it.

## API design

### New canonical method

Add to `WebSocketManager` in `src/cosa/rest/websocket_manager.py`, immediately after `emit_to_admins_sync` (around line 568):

```python
def emit_to_user_and_admins_sync( self, user_id: str, event: str, data: dict ):
    """
    Canonical dual-emit for queue and job state events: deliver to the owning
    user AND every admin session watching the global queue, deduplicating so
    the owner is never sent the event twice.

    This is the right method to call for ANY event that signals a queue or
    job mutation that admins watching the system-wide view should see:
    job created, job removed, job paused, job resumed, job state transitions,
    etc. Use this instead of calling emit_to_user_sync followed by
    emit_to_admins_sync separately — that pattern was the source of the
    Session 248e740e bug where pause/resume/delete events stranded cards in
    admin browsers because callers forgot the second call.

    Use emit_to_user_sync directly only for events that admins should NOT
    see (private notifications, response payloads). Use emit() only for
    truly system-wide events (notification sounds, time updates).

    Requires:
        - user_id is the owning user UUID (non-empty string)
        - event is a non-empty string event name
        - data is a JSON-serializable dict
        - self.main_loop is set and running

    Ensures:
        - Owner receives the event via emit_to_user_sync
        - All admin sessions where session_is_admin is True receive the event,
          deduplicated, with the owner's user_id excluded to prevent double
          delivery when the owner is also an admin
        - Both underlying calls are thread-safe
        - Errors in either call are logged but never raised
        - No-op if main_loop is missing or stopped (matches existing primitives)
    """
    self.emit_to_user_sync( user_id, event, data )
    self.emit_to_admins_sync( event, data, exclude_user_id=user_id )
```

### Why one method instead of an event registry

I considered an event-type registry where each event name maps to its broadcast scope (`'job_removed' → 'user_and_admins'`, `'notification_queue_update' → 'user_only'`, etc.) and a single dispatcher method consults the registry. That would force every event type to be declared once. Pros: maximally robust against future drift. Cons: a separate registry can rot, adds an indirection layer for marginal benefit, and would touch every emit site in the codebase. The simpler "one canonical method per scope class" approach achieves the goal — anyone touching queue/job events has exactly one method to call — without introducing a new architectural layer. If we add new scope categories later (e.g. "deliver to job stakeholders only"), we add a new method named for the scope.

### Documentation update on `emit_to_user_sync`

Append to the existing docstring at `websocket_manager.py:442`:

> **WARNING**: This method delivers ONLY to the named user's sessions and is appropriate ONLY for events that should remain private to that user (e.g. notification queue updates, response payloads). For queue or job state events that admins watching the system-wide view should also see — job created, job removed, job paused, job resumed, etc. — use `emit_to_user_and_admins_sync` instead. The Session 248e740e bug was caused by forgetting the admin emit; the canonical method removes the discipline burden.

This is a nudge, not enforcement, but combined with the new canonical method's clear name and docstring, future readers will reach for the right primitive.
