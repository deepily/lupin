# Bug 9a — Test container lacked `.git`, breaking worktree creation in Phase 3

**Discovered**: 2026-04-17 mid-morning, Session 44581b8c
**Severity**: High — blocks **every** auto-dispatched or resumed TFE that reaches Phase 3 in the test container, since `cosa worktree enabled = true` became the default on commit `aed7c6d`.
**Status**: Fixed in this session. CoSA submodule untouched. `docker-compose.yml` edit committed by user.

## Symptom

With Bug 14 remediation live and the user's voice-gate response delivered (11 proposals selected — 500-char cap removal validated live), TFE `tfe-445f9e4b` got through Phases 0-2 cleanly and then crashed at Phase 3 entry:

```
RuntimeError: `git worktree add /var/lupin/.claude/worktrees/tfe-445f9e4b HEAD` failed:
fatal: not a git repository (or any of the parent directories): .git
```

Traceback originates at `src/cosa/agents/shared/worktree_context.py:151` inside `WorktreeContext.__aenter__`, invoked from `orchestrator.py:1509` (`worktree_scope()`), invoked from `job.py:317` (`_execute()`).

Job marked failed, dispatcher sent an urgent error notification, `AgenticJob [tfe-445f9e4b] complete!` — but the complete just meant "clean failure," not "work done."

## Root cause

The test container's bind-mount set did **not** include `.git`. Verified live:

- `docker-compose.yml:90-95` (pre-fix) for `lupin-rest-test` mounted only `./src`, `./io`, `pytest.ini`, and the creds files.
- `docker exec lupin-rest-test sh -c 'ls /var/lupin/.git'` → `No such file or directory`.
- `docker exec lupin-rest-test sh -c 'cd /var/lupin && git rev-parse --is-inside-work-tree'` → `fatal: not a git repository`.

`WorktreeContext.__aenter__` (line 149) runs:

```python
result = await self._run_git_in( project_root, "worktree", "add", target_path, effective_ref )
```

with `project_root = cu.get_project_root() = /var/lupin` inside the container. Git scans upward looking for `.git`, finds nothing, fatal-errors → the `raise RuntimeError` on line 151.

### The scope gap in Bug 9's design

The original Bug 9 design doc (`src/rnd/v0.1.6/2026.04.16-bug-9-worktree-isolation.md`, 9,334 bytes, 120 lines) contains no mention of `docker`, `container`, `volume`, `bind-mount`, or `.git` at the infrastructure level. The "Config + new helper + orchestrator hook" breakdown assumed execution in an environment where `git` operations just work — which is true on the host but not in the bind-mount-only test container.

When commit `aed7c6d` flipped `cosa worktree enabled = true` (default-on), it activated the code path without completing the deployment side. First Phase-3-reaching TFE exposed the gap.

## Fix

**File**: `docker-compose.yml`

**Diff** — added one volume entry to both `lupin-rest-dev` (lines 40-47) and `lupin-rest-test` (lines 91-96):

```diff
     volumes:
       - ./src:/var/lupin/src
       - ./io:/var/lupin/io
       - ./pytest.ini:/var/lupin/pytest.ini:ro
+      - ./.git:/var/lupin/.git
       - ~/.lora_env:/home/rruiz/.lora_env:ro
       - ~/.claude/.credentials.json:/home/rruiz/.claude/.credentials.json:ro
```

Dev container gets the mount for parity (any TFE dispatched against `:7999` needs the same infra) and to future-proof if the dev container ever serves TFE work directly.

### Rollout

`docker restart` does **not** pick up new volume mounts — only container recreation does. Sequence used:

```bash
docker rm -f lupin-rest-test
docker compose up -d lupin-rest-test
# poll /health until HTTP 200
```

(`docker compose up -d --force-recreate` hit a name conflict on the running container in this env, so the explicit `rm -f` + `up -d` path was used.)

### Verification

Inside the freshly-recreated test container:

```bash
$ docker exec lupin-rest-test sh -c 'cd /var/lupin && git rev-parse --is-inside-work-tree'
true

$ docker exec lupin-rest-test sh -c 'cd /var/lupin && git rev-parse --show-toplevel'
/var/lupin

$ docker exec lupin-rest-test sh -c 'cd /var/lupin && git worktree list'
/var/lupin  9610ed2 [wip-v0.1.6-2026.03.12-cjflow-upe-and-playwrite]
```

All three are now the happy path. The exact SHA `9610ed2` matches the host HEAD.

## Why this is the right fix (not just a workaround)

1. **Matches user intent** — commit `aed7c6d` explicitly turned worktree isolation on-by-default. The container should be able to honor that.
2. **Bug 9's isolation guarantee is preserved** — `.claude/worktrees/` is **not** bind-mounted, so FixExecutor edits still live in the container's writable layer (ephemeral, disappears on container destroy). Only the git metadata (`.git/`) is shared between host and container. The host's `src/` working tree is never touched by Phase 3.
3. **Concurrency risk is low** — `git worktree add` is additive: writes a new entry to `.git/worktrees/<job>/` and creates a new tree; host-side `git status` / `git commit` / `git diff` operate on the main worktree unaffected. `git gc` / `git fsck` could briefly contend, but those are rare and manual.
4. **No CoSA code change** — the orchestrator/worktree code was correct all along. Only the deployment was incomplete.

## Concerns noted (follow-up TODOs — not blocking)

- **Phase 5 `gh pr create`** runs inside the container's worktree. It needs `gh` CLI + valid GitHub credentials mounted in the container. Confirm once a run reaches Phase 5. (Related: `~/.claude/.credentials.json` is mounted, but `gh`'s auth dir is not; may need `~/.config/gh` bind-mount.)
- **Missing-`.git` fallback in `WorktreeContext`** — a defensive `enabled = False` degradation when `.git` is missing would prevent this class of error in future deployment drift (ephemeral CI, stripped-down runners, etc.). Explicitly declined today so the deployment gap stays loud. Worth landing as a CoSA follow-up with a clear WARNING log.
- **Unit test for container deployment** — hard to write cleanly (requires a docker-in-docker or isolated container fixture). An integration smoke test that starts the test container and runs `git worktree add .claude/worktrees/smoke HEAD` inside would have caught Bug 9a in baseline.
