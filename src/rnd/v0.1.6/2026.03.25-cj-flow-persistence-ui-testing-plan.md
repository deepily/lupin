# CJ Flow Persistence — Job History UI Automated Testing Plan

## Context

CJ Flow Persistence Phases 0-6 are **feature-complete** but the E2E UI tests are purely structural — 6 tests that only verify DOM elements exist. No tests verify actual job data display, filtering, delete/retry actions, or pagination with real data. The integration tests also lack seeded test data, validating only response structure on empty results.

**Goal**: Add data-driven automated tests so we can validate the Job History UI end-to-end before merging to main. Everything must be fully automated — no manual verification.

**Database**: All tests run against `lupin_db_test` (test database). Both test runners hot-swap the live server to `[Lupin: Testing]` config. The `clean_test_db` fixture enforces `"lupin_db_test" in db_url` as a safety guard. Development database is never touched.

    Returns list of seeded record dicts.

def seed_pagination_jobs( user_id, user_email, count=25 ):
    """

    Returns list of seeded record dicts.
    """

**Implementation details**:
- Uses `from cosa.rest.db.database import get_db` + `from cosa.rest.postgres_models import JobHistory`
- Generates `id_hash` as `f"test-job-{suffix}::{user_id}"` (matches CJ Flow format)

**Critical**: `user_id` must match what the JWT `uid` claim returns — this is the `user_data["id"]` UUID string from the registration API.

## Risk Areas

1. **User ID format**: `job_history.user_id` must exactly match JWT `uid` claim — this is the `user_data["id"]` UUID string from registration. Verified in `queues.py:872`.
2. **`confirm()` dialogs**: Delete/retry use browser `confirm()` — Playwright must auto-accept via `page.on("dialog", ...)`.
3. **Time-window flakiness**: Use generous margins (3d/10d/40d, not near boundaries).
4. **Async fetch timing**: After expand click, `loadJobHistory()` is async. Must `wait_for_response("**/api/job-history**")` before asserting card count.
5. **Retry side effects**: Retry creates a real job in the todo queue. Only assert the 200 response, don't wait for job completion.
6. **Deduplication**: With clean test DB and no live queue, `exclude_ids` is empty — dedup not testable in E2E without live queue pipeline. Noted as future gap; integration test covers exclude_ids via direct API parameter.
