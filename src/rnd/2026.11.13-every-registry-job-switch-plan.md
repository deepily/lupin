# Plan: every registry job gets a switch it honours (row c38a49bd)

## Goal and provenance
Every job in `src/conf/job-registry.json` has a `cron job <job> enabled` key, read from disk on each tick, and the accordion shows `honoured` truthfully. Rick's ruling (13 Nov, about 22:35 EST) adds a confirmation step before turning off fleet-arbiter, health-watcher, notify-outbox or socket-housekeeping.

Maria's ruling on scope: two jobs are carved out, so the goal reads **22 honoured now, 2 pending**: `yearly-reminders` (Rick's crontab) and `context-tick` (row 94033d80, Cheech). They stay `honoured=false`, so the accordion stays truthful.

Provenance. The per-job facts come from a read-only survey of main at 4004d2924 by a subagent. I have not re-read each file. Each "survey says" is re-checked in the commit that touches that file, and the line I re-read goes in that commit's message.

## What exists today
- 12 of 24 jobs are `cron_managed` and read their key through `lupin_mcp.job_run.switched_on`, a one-shot process using ConfigurationManager and `get_required`. It returns True for an entry with no `enabled_key`.
- `cosa.rest.cron_job_switches.read_switch` reads the key from disk with a strict true/false parse and returns None when unknown. `is_honoured` is true only for `cron_managed is True`.
- Registry entries already carry `enabled_key` on the 12 managed jobs. The 12 others have none.
- The 12 without a key: `yearly-reminders`, `fleet-arbiter`, `context-pressure-writer`, `health-watcher`, `worktree-janitor`, `notification-expiry`, `commons-archival`, `notify-outbox`, `socket-housekeeping`, `side-services`, `pokes`, `context-tick`.
- No loop re-reads the INI per tick. Each reads a boot-time ConfigurationManager, so a change needs a bounce.
- Checked by Maria on main: `fleet_cap_ini_io` imports only os, re, tempfile and `lupin_mcp.config_write_lock`, so it is light enough for the arbiter venv. `read_value_from_disk` never raises and returns None for absent, duplicate or unreadable.

## Design

### D1. One parse rule, in `lupin_mcp` (Maria R1)
Three readers must not exist. The plan extends the parse that `read_switch` uses and moves it to `lupin_mcp`, beside `fleet_cap_ini_io`.
- The shared function reads a job's key from disk and returns True, False or None, with the strict "true"/"false" rule. A value like `yes` or `1` is None everywhere.
- `cron_job_switches.read_switch` and `job_run.switched_on` both call it. Neither keeps its own parse.
- A loop's tick calls it and treats None as "skip this tick and log an error". There is no default in code. A raise or None never turns work on.
- One test feeds the same strings (`true`, `false`, `True`, `yes`, `1`, blank, missing, duplicated) to the shared function, `read_switch` and `switched_on`, and asserts the three agree.
- Reuse: this is an EXTEND of `read_switch`'s parse. `fetch_similar` receipts and a ruling go in the reuse review.
- First commit proves the module imports in the arbiter's light venv (`src/scripts/check-arbiter-venv.py`).

### D2. The registry and the census (Maria R2 and R3)
- `enabled_key` is not new. The change is to derive it from `switch_key( job )` and stop typing it per entry. The census asserts that every job's key equals the derivation, and that the INI and splainer each hold one line for it.
- A registry field `switch_read` names the tick: `module:function` for each in-process job. It is a claim, so the census checks it. It opens the named function with `ast` and asserts the function calls the shared reader with that job's id.
- `is_honoured` becomes: the job is cron-managed, or `switch_read` is set. A job gets `switch_read` only in the commit that makes its tick read the key, so every new job stays `honoured=false` until its own commit.
- The census also asserts the converse: every job that has `switch_read` has a key.
- Mutation check for each job: remove the reader call from the tick, and the named census test reddens, not only the per-loop test.
- The pending set is a named list in the census: job, owner, row. It can only shrink. A job in it must not carry `switch_read`.

### D3. The tick rule, one skip point per loop
At the top of one tick's work: read the key; if false or unknown, skip the work and return to the normal sleep. The sleep and the stop check stay outside the skip, so a skip never busy-spins.
- Log one line on a state change, then at most one per hour while the state holds. The last-logged state lives in memory per loop, so a restart logs once. A fake-clock test covers it.
- The read comes before the skip, the loop survives a bad value, and the error log is rate limited the same way. For fleet-arbiter a bad INI edit stops the arbiter's work, which Maria accepts as fail-safe.

### D4. Existing boot keys (Maria: B, with two additions)
The loop is built whenever it can run, and the new per-tick key is the only runtime switch.
- Each new key copies the job's effective state, measured at implementation time, in both directions: nothing ships off that is on today, and nothing ships on that is off today.
- In the same commit, delete the old boot-key reader, its INI line and its splainer twin. A census test fails on an orphaned boot key.
- This touches the readers and tests of: `arbiter health watch enabled`, `arbiter context watch enabled`, `arbiter worktree janitor enabled`, `arbiter auto poke enabled` (and its audience keys), `notification expiry sweep enabled`, `websocket heartbeat enabled`, `websocket cleanup enabled`, `notify outbox enabled`, `commons enabled`. Audience keys for pokes and commons may carry meanings beyond one job; each commit re-reads the key's users before deleting it, and says so.

### D5. Confirmation before turning off four jobs
- A registry field `confirm_off` (text) on exactly `fleet-arbiter`, `health-watcher`, `notify-outbox`, `socket-housekeeping`. A census test pins the set to those four.
- Server side is the control. `PUT .../enabled` with `on:false` for such a job answers 409 unless the body carries `confirm: true`. That 409 has its own detail text and its own code, so a client can tell it from the "does not read its switch" 409. It applies only to a change to off: off to off, and any turn-on, need no `confirm`.
- GET rows carry `confirm_text`. The legacy client (`cron-jobs.js`, in `flip`) asks, then sends `confirm: true`.
- The confirm text for fleet-arbiter says it also silences pokes and the janitor, whose switches become moot while it is off.
