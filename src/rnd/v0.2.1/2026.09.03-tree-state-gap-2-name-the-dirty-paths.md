## 🔴 The one real design fork, and why it needed no ruling

Mr. Radio's brief says two things that pull apart on the container case:

- *"name the edited paths"*
- *"five paths and `+120 more` is the right output there, not 125 lines"* — for the
  container where **125 files read ` D`** for an unrelated bind-mount reason (pocholo,
  2026-09-02) and only one file is genuinely edited.

Naming only edits gives one path there. Naming the whole tracked set spends all five slots
on phantom deletions and buries the edit.

🔴 **CORRECTED AFTER REVIEW — ORDERING ALONE DID NOT DISSOLVE IT, AND MY FIRST WRITE-UP
OF THIS SECTION WAS WRONG.** I shipped "sort edits before deletions, then cap" and wrote
that it dissolved the fork. **Rachel 🕊️ measured the container case and it does not.** With
one edit and 125 deletions the code printed
`epic-stories.json,.claude/f0.md,f1,f2,f3,+121-more` — the edit **is** first, and four of
five slots still go to phantom deletions. *"Buries the only path a reader needs"* was still
80% true.

⚠️ **And the example in my own commit message said `+125-more`, which is what an
edits-only build would print — not what the code did.** My test asserted the first element
and the tail and passed; the prose was the only thing that was wrong, so nothing caught it.
**A worked example is the durable artifact and the thing people copy** — this repo has that
rule already, written after a scheduling example propagated a dead window.

**THE FIX IS RACHEL'S AND IT IS BETTER THAN EITHER OF MY OPTIONS: the cap belongs to the
EDITS whenever there are any, and deletions report as a tail that names its own kind.**

```
tracked-dirty=126 deleted=125 dirty-paths=src/conf/epic-stories.json,+125-deleted
```

⇒ `+121-more` **cannot distinguish 121 phantom deletions from 121 more edits**, and that is
the one distinction the container case exists to make. `+125-deleted` can. With no edits at
all the deletions take the slots themselves, because then they are the whole report.

⇒ **So the fork was real and it was resolved by a THIRD option, not by ordering.** I claimed
it dissolved; it had softened. The distinction matters because "dissolved" told a reviewer
there was nothing left to rule on.

## Reading the field — the `_run_span` lesson, applied before it bites

`_run_span`'s docstring records that `grep -o 'run-span=[a-z-]*'` truncated a real value at
a digit and **read as absent**, because three of its four values are lowercase words and the
fourth carries digits. A pattern tuned on the quiet case goes blind exactly when the field
has something to report.

This field has the same asymmetry — `none` is lowercase, a real path carries `/`, `.`,
digits and `_` — so the value space is documented **where it is defined**, with the same
remedy: match to end-of-field (`[^ ]*`) or read the whole line.

⚠️ **And one honest caveat rather than a silent mangle.** The field is comma-separated and
space-free *for ordinary paths*. Two porcelain shapes break that, and neither is corrupted
to preserve a tidy invariant:

- a path containing a space arrives **git-quoted** (`"a b.py"`), so the field then contains
  a space;
- a rename arrives as `R  old -> new`, and only the destination is named.

Both are documented. **A reader who takes the whole line is correct in every case**, which
is the advice the field carries.

## Test plan

- clean tree ⇒ `dirty-paths=none` (the always-print rule)
- failed status read ⇒ `dirty-paths=UNKNOWN`, and **never** `none` (the anti-laundering rule)
- two edits ⇒ both named, comma-separated
- six edits ⇒ exactly five named, `+1-more`
- the container shape — 1 edit, 125 deletions ⇒ `src/conf/epic-stories.json,+125-deleted`
- 6 edits + 3 deletions ⇒ both tails, `+1-more,+3-deleted`, counting different kinds
- deletions only ⇒ they take the slots themselves
- no `-deleted` tail when there is no edit for it to be relative to
- a rename names the destination
- the git call count is still **9**
- the paths come from the existing `status` result, not a second call

**Mutation arms**, each expected red: drop the field entirely · render `none` on a failed
read · omit the field when clean · cap at the wrong boundary · sort deletions before edits ·
add a second `status` call.

touched"* describes a **different instrument** about the remote, not the working tree. This
closes the working-tree half only, and the distinction is stated here so the next reader
does not read gap 2 as fully discharged.
