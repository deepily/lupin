# The browser session-ID fallback: keep it, un-persist it, or remove it

**Row**: `a501a714` (bug, `in_progress` on purpose — the ruling is the last thing owed)
**For**: Rick. **Written by**: Rio ⚡, 2026-09-02. **Status**: 🔴 DECISION DOCUMENT — nothing here is built.

This exists because the row's evidence is spread across five amendments written over two days,
and a ruling should not require reading all of them in order. Everything below is on the row;
this is the readable form, with the measured and the inferred kept apart.

---

## 1. The question

`notifications.js` asks the server for a session id. If that throws, a `catch` block mints one
locally from a 10×10 name table and **persists it to `localStorage`**. Should that fallback exist?

Rick asked this himself, and deliberately kept it OFF the 403 fix (`ad2cbbbe`) so the fix could
not close it.

## 2. Why it is not a logging question

`ad2cbbbe` fixed the separator, so the degraded path now **works**. Before it, a failed fetch
produced a loud 403 loop. After it, it produces a working socket on an id the server never
issued.

⇒ **The fix made the symptom quieter without making the degradation rarer.** The next
occurrence has no symptom at all. That is the whole reason the row was kept separate.

## 3. What is measured

| # | claim | class | evidence |
|---|---|---|---|
| 1 | The `catch` has **five** origins, not the three the row's brief named | measured | `ensureValidToken()` and `response.json()` both throw inside the same `try`. Two of the five never touch the session endpoint |
| 2 | One origin needs **no network at all** | measured | `ensureValidToken()` runs inside the `try` and **before** the fetch. A token that cannot refresh degrades a laptop exactly as it degrades the GCP VM |
| 3 | The endpoint cannot 401/403 on auth grounds | measured, with a positive control | `/api/get-session-id` takes only `Depends(get_id_generator)`. Live on `:7999` it returns 200 with no header and with `Bearer garbage`; `/api/auth-test` returns 401 for both, so the probe could see an auth rejection had there been one |
| 4 | The degradation is **sticky** | measured | The fallback id is written to `localStorage`, and `getOrCreateSessionId()` returns a stored id without re-asking. **One transient fault pins that browser forever** |
| 5 | Server-issued ids **cannot** collide | measured | `TwoWordIdGenerator` holds a uniqueness set and opens a new namespace cycle when one fills |
| 6 | The fallback ids **can** collide | measured | 10 adjectives × 10 animals = 100 names, **no uniqueness check**; 50 of the 100 sit inside the server's own cycle-1 space |
| 7 | A collision **cross-routes between users** | measured directly | Probe against a real `WebSocketManager`, `single_session_per_user=False`: bob connecting on alice's id overwrites `active_connections[id]`, flips `session_to_user[id]`, drops alice's socket from `active_connections.values()`, and leaves both users' `user_sessions` listing the same id |

## 4. What is NOT measured, stated so nobody promotes it

**Whether any collision has actually occurred.** Rows 6 and 7 establish that collisions are
*possible* and that their consequence *is* cross-routing. They do not establish a frequency.

⚠️ I welded those two into a single causal claim in commit `584e7169`'s message and in an
earlier amendment, and the join was not measured. The retraction is on the row. The honest
headline is:

> A one-sided rename puts every browser onto self-minted ids, and self-minted ids are the only
> source of the collision whose consequence was measured to be cross-user routing. The rename
> does not cause a cross-route; it removes the property that makes cross-routes impossible.

**Which origin fired on Rick's VM.** That browser's console is the only witness and I do not
have it. What was delivered instead is that the *next* occurrence names itself: every throw is
tagged, the catch announces via `this.error()`, and the reason is persisted to
`notifications_session_fallback_reason`.

## 5. The options

### A — REMOVE the fallback, surface the failure ✅ *recommended*

| | |
|---|---|
| **for** | Deletes the only source of session-id collisions (rows 5–7). Turns a permanent degradation back into a visible transient one. The condition it exists to survive — no session id — is exactly where a loud failure costs less than a quiet wrong answer |
| **against** | A user who hits a transient fetch failure gets an error instead of a working page. That is a real regression in perceived reliability, and it is the reason the fallback was written |

### B — KEEP it, but stop PERSISTING it

| | |
|---|---|
| **for** | Strictly better than today at near-zero risk: the next page load retries the server, so one transient fault stops pinning a browser forever (row 4). Collision risk stays but shrinks to the length of one page view |
| **against** | Still ships clients on ids the server never issued. Row 7's consequence remains reachable |

### C — KEEP it as-is (it now announces)

| | |
|---|---|
| **for** | Zero further change; the reversible half is already landed and the next occurrence is diagnosable |
| **against** | Keeps a permanent degradation triggered by a transient fault, and keeps the collision surface. The announcement makes it *findable*, not *rare* |

**Recommendation: A, and B is the floor.** If the fallback is kept for the reliability reason,
it should at minimum not persist — that is the cheapest change on this page and it removes the
"transient fault, permanent symptom" property entirely.
