## 1 · The question, in one sentence

When a manager admits a row out of `not_approved`, the server asks Rick to approve it and
**holds the HTTP request open while he thinks** — up to 120 seconds. Should that ask become
asynchronous: return `202 awaiting approval` immediately and resolve out of band?

## 2 · The mechanism

Two independently-configured numbers, **12× apart**:

| side | value | where |
|---|---|---|
| CLIENT read timeout, every `/api/tasks/*` call | **10.0s** | `lupin_mcp/task_store_tools.py:39` |
| SERVER human-ask timeout on an admission | **120s** | `lupin-app.ini:1106`, `task_promotion_gate.py:72` |

The server may legitimately hold the request 120 seconds. The client quits at 10.

The ask fires **only** when all four conditions hold:

1. enforcement is active,
2. the transition is the **admission** edge (out of `not_approved`),
3. the caller **is** a manager figure,
4. the caller is **not Rick** — `ASK_EXEMPT_PERSONAS = ( "rick", )`.

Every other transition skips all three gates, which is why **only admission is slow**.

> ⚠️ **This is a source reading, not a receipt.** Nobody has reproduced it, because driving
> it fires a real question at Rick. Plain load remains unexcluded for an admission by a
> non-manager, by Rick, or with enforcement off — nobody has reported one, and if one
> appears this memo does not cover it.

## 3 · What it has already cost

A caller that gives up at 10s cannot distinguish **"did not land"** from **"landed after I
stopped looking"**. Three managers read a timeout as a failed approval when the write had
committed; one DM'd a worker that a live row was still blocked and had to retract it
(María 🌸, row `96cf5cec`).

## 4 · The options

### (a) Raise the client timeout above the ask timeout — **REJECTED** (Mr. Radio)

It pins two independently-configured numbers to each other **by convention only**. They
agree today and diverge silently the day someone sets the INI to 300. That is this repo's
own § *TWO SIDES THAT DERIVE ONE VALUE BY DIFFERENT ROUTES* — a coincidence with a
maintenance schedule is not a fix.

### (b) Go asynchronous — **THIS ROW, RECOMMENDED**

Return `202 awaiting approval` at once; no caller ever waits on a human.

| | |
|---|---|
| **Pro** | Removes the **class**, not the instance. No caller waits on a human, so the 10-vs-120 mismatch stops mattering instead of being managed forever. Frees a threadpool worker the gate's own docstring flags as held. |
| **Con** | Rick loses the *"someone is blocked on me right now"* pressure, and the manager learns the outcome later rather than in the call. |

### (c) Fix the vocabulary — **RULED YES, AND ALREADY SHIPPED**

> 🔴 **The row body says "Krishna is building it". That is stale — it is done.**

The client no longer reports `server_unreachable` for a read timeout. It returns
`server_read_timeout` with `outcome_indeterminate: True`, and its detail names the
human-approval case explicitly and warns that the write may have committed.

- Commits **`0b263518`** and **`708f398d`** (2026-09-05).
- Guarded by `src/tests/unit/lupin_mcp/test_task_store_read_timeout_is_not_unreachable.py`.
- The clause ORDER is load-bearing and documented at the catch site: `ConnectTimeout`
  subclasses **both** `ConnectionError` and `Timeout`, so catching `Timeout` would sweep up
  the one case that genuinely never reached the server. `ReadTimeout` is caught
  **specifically**.

**Whichever way (b) is ruled, the caller is already told the truth about why it is waiting.**

### (d) Not now — park it with a chase date

| | |
|---|---|
| **Pro** | It is P2 and nobody is hard-blocked. |
| **Con** | It currently blocks row `96cf5cec`, so parking it parks that one too. |

## 5 · What it costs to say no

**Nothing breaks.** With (c) shipped the caller is told the truth. What remains is that a
manager's request stays hostage to a human's thinking time, and the did-it-land ambiguity
survives.

## 6 · Deliberately NOT folded in

The `422 no-op transition queued->queued` reading as a *rejection*, when it really means the
row is already where you asked, is a **different defect** (row `3bf6ad1b`, closed). It
survives whichever way this is ruled and misreports on any duplicate transition, human gate
or not.
