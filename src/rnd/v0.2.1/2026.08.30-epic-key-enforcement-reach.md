# Epic-key enforcement: what a creation-time check would actually cover

**Row**: `5246bb67` (decision, owner `rick`, manager `mr radio`, `epic:board-visibility`)
**Author**: Maya 🌻, 2026-08-30
**Status**: analysis for Rick's ruling. **Nothing installed.** No write-path change was made.

## Verdict

The enforcement is buildable. **But both enforcement options on the row — a server-side
default (option 2) and a reject-on-creation (option 3) — key on the wrong thing.** They ask
*"is `correlation_key` blank?"*. Measured on the live board, `correlation_key` has **three
different occupants**, and only one of them is an epic key. A blank-check passes all three,
so it would report full compliance on rows the epic board still cannot group.

That is precisely the failure the row was raised to prevent, one level in: not an
enforcement that covers three doors of four, but an enforcement that covers **one occupant
of the field out of three** while reading as if it covered the field.

## The measurement

Live store, `:7999`, 2026-08-30, whole board paged with
`include_terminal=true&unscoped_audit=true&hide_parked=false`.

| population | rows | `epic:*` | blank | `cc-task:*` | other |
|---|---|---|---|---|---|
| **live (non-terminal)** | 14 | **14** | 0 | 0 | 0 |
| all-time | 2,217 | 191 | 1,685 | 52 | 289 |

**The live board is at zero drift right now** — all 14 live rows carry an `epic:` key,
including the two rows this session owns. María's 2026-08-29 pass held.

The all-time column is where the three occupants show:

| occupant | shape | count | written by |
|---|---|---|---|
| epic layer | `epic:<slug>` | 191 | agents, by hand, via `task_create` |
| harness mirror | `cc-task:<stable_sid>:g<gen>:<harness_id>` | 52 | `task_store_mirror.build_correlation_key`, an **idempotency upsert key** probed on read via `GET /api/tasks?correlation_key=…` |
| cascade tag | `cascade-quick-ask` (no prefix) | 289 | agents, by hand, as a free-text run tag |

The MCP verb's own docstring documents the field as *"Upsert key for hook-mirrored items"* —
`cosa_voice_mcp.py`, `task_create` Args block. The epic layer is a **later, undeclared second
tenant** of a field whose documented purpose is something else.

## Reach — the honest table

`repo.create_item` has **exactly one non-test caller in the repo**: the `POST /api/tasks`
handler (`src/cosa/rest/routers/tasks.py:738`). So the router handler is a genuine chokepoint
for every HTTP client, and there is already a precedent sitting on that exact line —
`rules.soft_guard_title`, whose comment says it lives *"at the SERVER write path so EVERY
caller (MCP wrapper, hook, raw POST) is covered."*

A check installed beside it would cover:

| # | creation path | covered? | note |
|---|---|---|---|
| 1 | MCP `task_create` (`lupin_mcp/task_store_tools.py:169`) | ✅ | the agent-facing door; where all 191 epic keys came from |
| 2 | hook-lane `client.create_task` (`task_store_client.py:144`) — mirror + drain | ✅ **but see below** | always sends a `cc-task:` key, so a blank-check is **always satisfied and never an epic key** |
| 3 | raw `POST /api/tasks` (curl, script, any API-key holder) | ✅ | |
| 4 | direct `TaskRepository.create_item` in-process | ⚠️ **not covered** | no such caller exists today, but the arbiter already does a direct-repo **read** that bypasses this chokepoint (`arbiter_job.py:271` names it), so the bypass is a live pattern, not a hypothetical |
| 5 | direct SQL / Alembic | ❌ not covered | no `INSERT INTO task_items` in the tree today; the one migration that touches the table only `UPDATE`s |

**Path 2 is the one that matters, and it is worse than "not covered" — it is
covered-and-wrong.** Every harness-mirrored row satisfies a blank-check with a key that can
never group it on the board. Under option 3 the mirror lane never trips the reject; under
option 2 it never gets the `epic:unassigned` default either. Both options are silently
inert for 52 of the board's historical rows and for every future one born that way.

**And path 1 does not need a code change to defeat either option.** `cascade-quick-ask` was
typed by an agent through the ordinary MCP door — 289 rows of it. A presence check accepts it.
Only a **value-shape** check (`startswith("epic:")`, and ideally membership in the 14 keys
`GET /api/epic-stories` already serves) would catch it, and that check collides head-on with
the mirror's legitimate `cc-task:` key on the same field.

## What follows for the ruling

The two cheap options on the row are not the two poles they look like, because the field is
shared. Stated plainly so Rick can rule on the real choice:

1. **Give the epic its own column.** The only option under which a creation-time check can be
   both strict and correct: `correlation_key` goes back to being the mirror's upsert key, and
   `epic_key` becomes a field with one meaning. Costs a migration + a backfill of 191 rows +
   the board reader. It is the answer that stops this recurring.
2. **Shape-check, scoped to the door that can honour it.** Reject a `task_create` whose
   `correlation_key` is neither `epic:*` nor `cc-task:*`, naming the 14 live keys plus
   `epic:unassigned` in the error. Cheap, but the exemption list is exactly the reach caveat —
   and it must be written down where a reader of the board sees it, not only in the handler.
3. **Detector instead of enforcement.** A read-only audit over the rows rather than a guard on
   the doors. It covers **every** creation path including ones nobody enumerated, because it
   reads the result rather than the entrance — the same argument CLAUDE.md already makes about
   misplaced heartbeat holds (*"treat the doc as a courtesy and the detector as the control"*).
   It does not prevent drift; it makes drift impossible to miss. `scan-prose-task-refs.py` is
   the working template, down to its own lesson: *"A detector with no caller is still silence."*

**Recommendation: 3 now, 1 when someone is paying for a migration.** A detector needs no
ruling on shared write-path infrastructure, breaks no caller, and is the only one of the three
whose stated reach is its actual reach. A creation-time guard on a field with three tenants
buys the *appearance* of a covered field — which, on a board people read instead of reading
18 bodies, is worse than the honest gap.

**Not built here.** The row says a write-path change to shared infrastructure is Rick's call,
and it is: three seats are mid-build against this store. This document is the input to that
call, not a fait accompli.

## BUILT — the detector, 2026-08-30 (Mr Radio approved option 3)

> *"A check that only tests whether `correlation_key` is BLANK is not enforcement, it is a
> non-empty-string assertion wearing enforcement's clothes."* — Mr Radio 🦉, approving the
> detector with the reach stated plainly in the code and the commit.

| file | what it is |
|---|---|
| `src/cosa/rest/task_store_epic_keys.py` | the pure detector — `classify_key`, `audit_rows`, `reach_disclosure` |
| `src/scripts/scan-epic-key-drift.py` | the caller — pages the board, fetches the known keys, prints, exits |
| `src/tests/unit/test_task_store_epic_keys.py` | 22 cases |
| `src/tests/unit/test_scan_epic_key_drift.py` | 27 cases |

Both source files at **100% lines and branches**. 49 tests.

**Reach is a REQUIRED output, not a docstring.** `reach_disclosure()` prints on every run,
clean or dirty — the same mandate `task_store_prose_refs.scope_disclosure` carries. A clean
epic verdict that does not name the mirror bucket reads as *"the board is fully grouped"*
while a whole tenant of the field sits underneath it unexamined.

### Measured both directions

```

  (every row carries a known epic key)
  epic: keys : 14 (0 carrying a slug with no story entry)

$ ... --include-terminal            # the negative control, over history
  epic: keys : 191 (65 carrying a slug with no story entry)
  blank      : 1578
  foreign    : 287
⚠️  BOARD TRUNCATED at 2000 rows — this result is PARTIAL.

```

The truncation warning is the instrument reporting its own limit rather than a clean-looking
partial: the `cc-task:*` rows are June-era and fell outside the 2,000-row window, which is
exactly why `mirror keys : 0` on that run does **not** mean the board has none.

### What it does NOT do — repeated here because it is the point

- **It does not prevent drift.** Between two runs the board can be wrong and nobody is told.
- **It cannot judge a `cc-task:*` row.** That key is load-bearing for the mirror's idempotency
  probe, so re-stamping it would break the probe. Those rows are counted and never flagged.
  Fixing them needs the epic in its **own column**, which is still Rick's call (option 1 above).
- **It only sees the rows handed to it.** A truncated fetch yields a verdict about a subset,
  and says so with exit 3.

What it *does* do, and a creation-time guard cannot: **cover every creation path, including
ones nobody enumerated**, because it reads the rows rather than the doors.
