## 1. The gap that was named, and what filled it

Mr Radio's entry said plainly *"I did not find this"* about the component that composes
and delivers the wake text, and warned that `self_respin_observer` and
`respin_wake_check` are **both innocent and both look like the culprit**.

**The injector is not a file, and that is why nobody found it.** It is a detached
`bash -c` chain that `self_respin_core` builds and launches before dying:

| | |
|---|---|
| composes the words | `src/lupin_mcp/self_respin_core.py` · `build_wake_text` |
| composes the delivery | `src/lupin_mcp/self_respin_core.py` · `build_guarded_clear_argv` |

The chain sleeps, `rm`s a one-shot fire token, sends `/clear`, polls the seat's bridge
until its `session_id` changes, then types the wake. **At fire time it has no owning
process**: the seat that scheduled it has been cleared and the Python that built it has
exited. What fires is an argv list. The module docstring credits
`hook_common.inject_qualifier_via_tmux` as the general injector — a red herring for this
row; the wake is delivered by the chain, not by that function.

### 3a. The race, which is narrowed and not closed

The wake was **queued at `21:13:15.663`, 0.165 s BEFORE the clear's own local-command
record at `21:13:15.828`.** The gate opens the instant the bridge reports a new

outcome was correct **and it was a race, not a guarantee.** A correct result from a race
is precisely the thing that stops being correct under load.

## 5. The fix: an oracle the seat cannot author

The memory question is **removed, not reworded.**

> *An instrument that needs its reader to remember its own limit is not an instrument.*

It could never work: **it detects a MISSING memory and cannot detect a RESTORED one.** A
seat that cleared and re-read its own record has no absence to find. Measured twice on
the same seat one day apart — the second time that seat had read the limit, quoted it in
its own dispute, and still ruled the wrong way. **Knowing a rule is not applying it.**

What replaces it: the wake quotes the session id the pane held **immediately before the
clear** and tells the seat to compare against its own `claude_code.session_id` from
`get_session_info()`. Both sides come from the bridge, written by the SessionStart hook.
**The seat cannot move either side.** And the answer holds whether the seat is asked in
one second or one hour — the property the old instrument lacked.

The id is unknowable at compose time, so the composer emits a sentinel and the chain
substitutes the fire-time value by **bash parameter expansion, never a subshell** — the
wake is arbitrary prose and must not be re-parsed by a shell.

## 6. Three defects in my own work, all caught by running it

### 6a. The bash never ran, and every string-match stayed green

An escaped quote inside `${s0%\"}` reads as an **opening quote** to bash. The script died
with `unexpected EOF while looking for matching '"'`, exit 2, **no wake typed** — and
every string-match assertion in the sibling suite passed.

⇒ **This is the whole case for executing the real chain** against a fake `tmux` and
reading what the pane was handed, rather than matching strings at the script.

### 6b. A tautology, for the second time in one evening

The unavailable-id test asserted `_PRE_CLEAR_SID_UNAVAILABLE in typed_wake`. **The wake
template already contains that literal** in its closing sentence. Deleting the fallback
from the chain left the test **GREEN**.

| where expected and actual met | |
|---|---|
| the corpus test, earlier the same evening | both sides derived from the exclusion set |
| this one | the expected value lives inside the subject's own template |

⇒ **Assert the substitution SITE, not the string.** The test now looks for the contiguous
phrase `was session (unavailable)`, which occurs only where the substitution lands.

### 6c. The new guard fired on its author

The first wake text quoted the banned memory question **inside the sentence explaining
why it is banned**, and `test_the_wake_never_asks_the_seat_what_it_remembers` went red.
Source-text assertions cannot tell an implementation from an explanation of one — this
repo says so about code, and it is equally true of prose. **The text was reworded; the
guard was not weakened.**

## 7. 🔴 VERIFY THE BREAK APPLIED BEFORE YOU READ THE COUNT

**Three times in one evening a falsification break was a no-op, and a no-op break and a
working guard are indistinguishable from the number alone.**

| break | why it did nothing |
|---|---|
| corpus exclusion (E, G) | the `sed` rewrote the pin's expected literal along with the declaration, so the pin moved with the break |
| wake substitution (J) | the `sed` targeted the **rendered bash**; the source is an f-string, so `__PRE_CLEAR_SESSION_ID__` is not in the file — the constant name is |
| unavailable fallback (K) | same: the source reads `{_PRE_CLEAR_SID_UNAVAILABLE}`, not `(unavailable)` |

All three returned **0 reds for reasons that had nothing to do with the guard.** Two of
them I nearly wrote up as blindness.

⇒ **Print the break's own receipt** — a grep count proving the edit landed — beside the
red count. This is the same discipline as printing the corpus size beside a green: *a
guard that reports only pass/fail cannot be caught being wrong.*
