## 1 · RETRACTION — `memento_io write` does not exit 0 on a refused write; it exits 3

**The claim, believed by two seats:** *"`memento_io.py write --slot root` was REFUSED and the
exit code said success — two independent callers, two different verbs, one exit code saying
success on a write that did not happen."* It was attributed to me. **I had no such finding**,
and it appears nowhere in my memento or on any row I wrote.

**Measured**, same verb and slot, against an already-existing root record so the refusal
reproduces and writes nothing:

```
printf '...' | memento_io.py write --slot root --persona rachel --session-id 1c8db7e3
EXIT=3
REFUSED: record already exists — /…/lupin/.claude-memento-rachel-1c8db7e3.md
         A record is IMMUTABLE. Nothing overwrites it, including you.
```

**Confirmed in the source, not only in the run:** that branch ends `sys.exit( 3 )` at
`memento_io.py:1361`, directly under the `REFUSED` block beginning at `:1345`. The refusal is
loud and non-zero **by construction**. Independently re-verified by Mr. Radio.

⇒ **The mechanism as stated is false**, and acting on it sends a reader into working code —
the expensive kind of wrong. A wrong count gets re-derived by the next reader; a wrong
mechanism spends their evening.

**What is still live, and is a real hazard — just not this one.** If a caller genuinely
observed `0`, the exit code was destroyed *between* the verb and the reader. This repo
already documents that shape: `cmd; echo "EXIT=$?"` makes the **wrapper's** status the
result, so the diagnostic line added to surface the exit code is the line that replaces it.
Capture immediately and re-raise: `cmd; rc=$?; …; exit $rc`.

**Not measured:** what the reporting seat's shell actually returned. This retracts the claim
about the verb and says nothing about which wrapper ate the code. **Ask for the literal
command line, not the number.**

## 3 · STILL OPEN — tonight's live `DEAD_NO_WAKE` is unexplained

Row `7ad5eba6` was minted on the premise that *a seeded spawn can arm a wake watch carrying
no identity*. **Measured, that premise does not hold on the live path** (row `7ad5eba6`,
event 10889): the arm hands the watch `tmux_session` — non-empty by construction — plus
`base_dir`, and no persona and no session id. The `"unknown persona / unknown session"`
wording that was read as evidence is a **constant** printed on every no-receipt alarm.

The renderer defect that produced that constant is **fixed** (commit `9ddc40ad`). What is
**not** fixed, and belongs to nobody yet:

> **Why did the live watch alarm?** Its cause was never established — it was inferred from a
> string that never varies. `base_dir` resolved correctly in the one measurement taken, so
> *"the root fix is not implicated"* keeps its plausibility and **loses its evidence**.

**A candidate nobody has ruled out**, offered as a lead and not a finding: the watch searches
by `tmux_session`, and a receipt is matched on the `tmux_session` field the **writer** put in
it. If the writer records a different value, or none, the finder sees nothing on the correct
root with a correct identity supplied — a **third** cause of `DEAD_NO_WAKE`, distinct from
both the wrong-root and the null-identity causes. **This has not been measured.**

### 3a · The third cause was CHASED and the data does NOT support it — mostly a negative result

**Measured 2026-09-03 against every boot receipt on this box: 201 receipts across three data
roots** (`lupin` 183, `planning-is-prompting` 14, `lupin-mobile` 4). Zero unparseable. Every
one carries a `tmux_session` key.

| what the writer recorded | n | |
|---|---|---|
| a spawn-shaped name (`cc-<role>-<manager>-<n>`) | **159** | agrees with what a watch would arm on |
| a `cc-tmux-session-<hex>` name | 26 | **a REAL live tmux session name — see the retraction below** |
| null or empty | 16 | 15 are one clustered burst, 2026-08-26, ~7 minutes, **all `persona=None`** — harness-shaped, not live spawns. The 16th is a real persona on `lupin-mobile` |

🔴 **A RETRACTION INSIDE THIS DOC, MADE WITHIN THE HOUR OF THE CLAIM.** I first bucketed the
26 as *"SYNTHESIZED fallback"* and reported **42 of 201 (20%) unmatchable**. That was wrong.
`tmux list-sessions` shows **three live sessions of exactly that shape right now**, so the
writer was recording a true name and my label invented a defect. The `20%` figure should not
be quoted; it was mine and it was bad.

⇒ **What actually holds: on every spawn-shaped receipt the two derivations AGREE.** So the
census gives no evidence of a writer/reader mismatch on the watched path, and **tonight's
alarm stays unexplained.** A negative result, reported as one.

**What the census DID establish, structurally rather than statistically** — and it is the
reason the lead was worth chasing:

| | derives the seat's tmux name from |
|---|---|
| **writer** (`register_session._find_tmux_session`) | the **live tmux process table**, matched by `cc_pid` at boot |
| **reader** (`arm_watches_for_spawn`) | the **string the spawner chose**, `record["session_name"]` |

**Two independent derivations of one value, and nothing checks that they agree.** They
coincide whenever the seat lands in the session the spawner named — which is every
spawn-shaped receipt on disk today. That is agreement by circumstance, not by construction:
the writer returns `None` whenever tmux cannot answer, and a `None` there is unmatchable by a
watch that keys on the name.

⚠️ **Not measured**: whether any seat has ever been spawned into a session whose live tmux
name differs from the spawner's. The historical receipts cannot answer it — they do not record
what the spawner asked for, only what the seat found. **Answering it needs a real spawn.**
