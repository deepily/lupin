# The server DOES write snapshots on repeat questions — and the guard behind it is enforced in one layer of two

**Row**: `7aa31303` (lupin, P2) — **closed as disproven**. The finding that survived is `54589356` (P1, blocked on Rick).
**Measured**: 2026-08-29, against live `:7999` and `lupin_db_dev`.

## The report, and why all three limbs are designed behaviour

> "The server does not write solution snapshots for repeat questions."

**Controlled probe** — one novel question, asked twice, the first allowed to complete:

| | path | route_reason | status | wrote_snapshot | snapshot_id | similarity |
|---|---|---|---|---|---|---|
| pass 1 | `agent` | `args_none` | `waiting` | False | None | 70.3 |
| pass 2 | `agent` | `args_none` | `waiting` | False | None | **100.0** |

1. **`wrote_snapshot=false` / `snapshot_id=null` is CORRECT.** `v2 executor = queued`, so the response returns
   `status=waiting` *before* any work runs. Pass 1's row appeared at `22:14:08` (table 11 → 12). The response model
   says so itself: `snapshot_id` is *"null on a warm pass by construction"*. The original reporter compared a field
   from the immediate response against a row that showed up afterwards.
2. **The original sighting had no repeat in it.** Arnold's words were *"asked twice, two different questions"* — so
   `path=agent` was right both times and there was nothing to replay.
3. **Pass 2 not replaying at similarity 100.0 is `_may_serve`** enforcing Rick's ruling that unconfirmed answers
   never replay. The probe ran `interactive=False`; nothing was confirmed.

## What the investigation actually found

**The replay happened anyway, one layer down.** Pass 2's HTTP response said `cache_hit=false`,
`replayed_snapshot_id=null` — and the row records `first_replayed = 22:14:20`. Server log:

```
[CACHE] Checking cache for question: ...
[CACHE] EXACT HIT: score 100.0% from 2026-08-29 @ 22:14:08.550616 EDT
[CACHE] Re-executing cached code for fresh result...
[CACHE] ✓ Code re-executed successfully
CACHE HIT - result retrieved in 138 ms   /   Time saved by cache hit: 9968ms
```

`AskFlow._may_serve` refuses the hit and falls through to the queue; the queue's consumer then runs its **own**
cache check, which never consults `answer_is_correct`. Every reference to that field in `running_fifo_queue.py` is
a write (`:1785`) or a payload entry (`:1630`, `:1706`, `:1911`) — **there is no read guard in the file.**

**Reachable by ordinary traffic, including the voice path.** Not via `push_job` — that is dead, no production
caller, sweep-enforced. Both live doors call the same function:
`speech.py:399` (`/api/upload-and-transcribe-mp3`) and `v2_ask.py:394` (`/api/v2/ask`) → `flow.ask(...)`, whose jobs
were observed reaching `[CONSUMER] Processing job:` → `[CACHE] Checking cache`.

**No stale answer was served here — the cached CODE is re-executed and the answer recomputed.** The one path that
serves a stored answer verbatim is the failure fallback at `running_fifo_queue.py:1846-1848`
(`else: # Code failed - use cached answer as fallback`), reached on any non-zero `run_code` return — including the
`ValueError` the preceding `try` converts to `return_code=1`, which covers "Cannot execute empty code list".
**Reachability is shown; frequency is NOT — one probe, and it took the success path.**

## Two couplings whoever rules on `54589356` needs

- **Nothing has ever been confirmed.** 12 of 12 rows are `answer_is_correct = null`, because the correctness prompt
  times out with nobody there (`[CORRECTNESS] No response ... (status=offline), leaving as None`). Guarding both
  layers *today* means unattended traffic can never build a servable cache: confirmation needs a human, and
  unattended traffic has none. The guard and the offline-default are one decision.
- **The cost of guarding is latency, not correctness** — 138 ms replay against 9968 ms saved, so ≈10 s per guarded
  replay. Worst case of guarding too much is a slow correct answer; too little is a fast wrong one.

⚠️ **`answer_is_correct` is a TEXT column** — Postgres rejects `IS TRUE` on it. `_may_serve` already defends (reads
the hydrated object, `is True` rather than truthiness). If a second guard lands on the same column, typing it moves
from *"worth doing"* to prerequisite.
