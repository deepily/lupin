# 2026.09.29 — Can Claude Code thinking be captured? What the community says, and what we measured

Rick's ruling (2026-09-29 ~15:27 EDT, row `2742f945`): show summaries inline, run the `showThinkingSummaries` A/B, and report what the community says "if they truly are not captureable". This is that report.

## Verdict

**Full reasoning is not capturable by anyone, by design. A short summary is, and our settings do not ask for it.** Setting `showThinkingSummaries: true` made Claude Code write a 106–140 character summary into the transcript on **3 of 3** interactive Opus 5.5 runs, against **0 of 3** with it `false`. Headless (`claude -p`) runs wrote **0 of 16** blocks with text under either setting. Our `~/.claude/settings.json` sets neither key (row body, 2026-09-29), so the 6% of thinking blocks that arrive with text are a floor the setting can raise. Whether it raises the share fleet-wide is unmeasured.

## 1. What Anthropic documents (read in full for the two quoted passages)

Source: [Thinking — Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/thinking), fetched 2026-09-29.

- On Opus 5.5, Opus 5, Sonnet 5.5 and others, `display` **defaults to `"omitted"`**: blocks come back with an empty `thinking` field, and the `signature` "still carries the encrypted full thinking for multi-turn continuity".
- `"summarized"` returns "a summary of Claude's full thinking process rather than the raw chain of thought". "No `display` setting returns the raw chain of thought." Full output is offered only through "contact Anthropic sales".
- You are billed for the full thinking tokens either way, not the summary.
- **Progress updates.** On Opus 5.5 and a few other models, "the model can write a progress update between tool calls", which comes back as its own `thinking` block. Under `"omitted"` its text is empty; under `"updates"` (beta header `thinking-display-updates-2026-08-18`) or `"summarized"` it carries text.

⚠️ **Unverified, and a lead worth a probe:** the 926 text-bearing Opus 5.5 blocks in our census were "always the first block of their message" and read as outcome summaries (row 2742f945). That resembles progress updates or summaries, but nothing here ties them to either. Note also that the visible summaries we produced in §3 said "no need to invoke any tools" in a run that then called a tool, so a summary is not a reliable record of what the model did.

Reading across them:

1. **The empty-text pattern is widely reported and dated to specific releases**, across Opus 4.6, 4.8, Sonnet 5 and desktop, CLI and VS Code. Our census (94% empty) is one more instance, not an outlier.
2. **The community splits on cause.** One camp blames an Anthropic policy or server change (#49807, #52376). The docs describe `omitted` as an intended default. Neither camp shows evidence of intent; treat both as unverified.
3. **No thread reports a way to get the raw chain.** The workarounds people trade are all about the summary: `showThinkingSummaries`, `verbose`, the VS Code extension, the terminal CLI over the desktop app.
4. **#52376's central claim is contradicted by our measurement** (§3): on Claude Code 2.1.285 with a subscription login, `showThinkingSummaries: true` did put text in the transcript. It may have been true in April; it is not true now for interactive Opus 5.5.
5. **None of the seven threads I read shows a maintainer reply**, and four are closed (two as not planned, one as a duplicate, one plain closed). That does not prove none exists; it is what the summaries showed.

## 3. The A/B we ran

Claude Code 2.1.285, Max OAuth login, run from this seat's worktree. Every run used `--settings '{"disableAllHooks":true,"alwaysThinkingEnabled":true,"showThinkingSummaries":<X>}'` and `--strict-mcp-config` with an empty MCP file, so no run fired a hook, registered a persona or joined the fleet. Same account, same minute-scale window, `X` alternated arm by arm. Raw runs are in this seat's scratchpad and are not checked in.

| Arm | Mode | Model | Prompt | Runs | Thinking blocks | Blocks with text |
|---|---|---|---|---|---|---|
| `showThinkingSummaries=true` | interactive (tmux) | claude-opus-5-5 | tool use (count `.py` files) | 3 | 3 | **3** (106, 125, 140 chars) |
| `showThinkingSummaries=false` | interactive (tmux) | claude-opus-5-5 | same | 3 | 3 | **0** |
| both | interactive (tmux) | claude-opus-5 | same | 1 + 1 | **0** | 0 |
| true / false | `claude -p` stream-json | claude-opus-5-5 | arithmetic, no tools | 4 + 4 | 4 + 4 | 0 / 0 |
| true / false | `claude -p` stream-json | claude-opus-5 | arithmetic, no tools | 2 + 2 | 3 + 2 | 0 / 0 |
| true / false | `claude -p` stream-json | claude-opus-5-5 | tool use | 4 + 4 | 1 + 2 | 0 / 0 |

The three visible summaries, in full: *"The user just wants a simple one-sentence answer, so there's no need to invoke any tools here — I'll just respond directly."* · *"The user explicitly asked for a one-sentence answer, which takes precedence over any longer startup routine, so I'll just answer directly."* · *"The directory change carried over, which is worth noting, but I can go ahead and answer in one sentence."*

What the table supports and what it does not:

- **Supported:** in interactive Opus 5.5, the setting is the difference between an empty block and a one-sentence summary (3 vs 0, one prompt). The transcript stores it. Headless mode stores nothing with text under either setting (0 of 16 blocks over 20 runs), which matches #32810's claim about non-interactive mode; the stream and the on-disk transcript agreed block-for-block.
- **Not supported:** anything about frequency. N=3 per arm on one prompt cannot say what share of a long working session's blocks would carry text. The ~6% census figure and the 15% Opus 5.5 figure came from real sessions and are not comparable to a 10-second task.
- **Not tested:** Opus 5 interactive beyond one run per arm, which produced no thinking blocks at all, so it neither confirms nor contradicts the census's "0 visible of ~8,400". Sonnet, `verbose`, the `redact-thinking` header itself, and the `updates` display are all untested.
- **Confound:** the interactive runs started inside a repo whose `CLAUDE.md` is large, and two of the three summaries mention startup or directory context. That may be why those turns produced text at all; the prompt was not varied.
