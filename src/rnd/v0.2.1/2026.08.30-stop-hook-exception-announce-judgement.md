# Should the Stop hook announce every internal exception? — a judgement

**Row**: `e3dd1df2` (decision, owner `rick`, manager `mr radio`, `epic:unassigned`)
**Author**: Maya 🌻, 2026-08-30
**Status**: judgement for Rick's ruling. **Nothing implemented**, as asked.

## First, the premise is wrong — and that changes the question

The row asks whether the Stop hook *"announces **every** internal exception as a TTS card."*
It does not. `stop.py` has **29 `except Exception` handlers and exactly ONE of them announces**
— line 983. The other 28 swallow silently. (`send_tts` appears 7 times in the file: one import,
two docstrings, one conv-mode narration, two normal-path status lines, and this single handler.)

So there is no announce-everything policy to rule on. There is **one handler**, and if a
general policy question exists here it points the *other* way: 28 silent swallows in the
fleet's liveness path is the larger untested surface, not the one card.

## Verdict

**Keep the one announcement — and narrow its catch.** Not because announcing is harmless, but because
the premise under the "announce nothing" argument does not hold on the measured code: at this
site, an exception card **cannot** be an outage. Every environmental failure inside that try
block is already swallowed one level down. What reaches the announce line is a defect in our
own code — which is exactly the traffic a liveness path should be loud about.

**This contradicts the constraint Tiberius added to the row**, and the contradiction is the
main thing worth carrying to Rick.

## The site

`src/lupin_cli/claude_code/hooks/stop.py:981-983`, the outer handler of `_ask_anything_else`:

```python
    except Exception as e:
        # Server down, network error, import error → allow stop gracefully
        send_tts( f"Stop — notify error: {e}" )
        return {}
```

The comment names "server down, network error" first. **The comment is wrong**, and it is
almost certainly where the amendment's constraint came from.

## Why "server down" cannot reach line 983

`notify_user_sync` is **total**. `src/lupin_cli/notifications/notify_user_sync.py` catches
`ConnectionError` → returns `status="connection_error"`, `Timeout` → `"request_timeout"`,
`RequestException` → `"request_exception"`, and a bare `except Exception` → `"unexpected_exception"`
(lines 457-495). Its docstring says so outright: *"Raises: No exceptions raised (all handled
internally)"* (line 81).

So on a dead `:7999` the call **returns** a `NotificationResponse` with
`response_value=None`. `extract_qualifier_comment(None)` returns `(None, None)` — it
short-circuits on falsy input (`notification_utils.py:237`). The answer is not `"yes"`, the
function returns `{}`, the Stop is allowed. **No card. No exception. Nothing reaches 983.**

There is a second, independent reason the same conclusion holds: `send_tts` delivers through
`notify_user_async` to **the same server** `notify_user_sync` would have failed to reach
(`hook_common.py:434`). Even if a server-down exception did arrive there, the announcement of
it would silently fail. **An announce-on-outage path cannot announce an outage.** The 212
cards Rick actually received are themselves the proof: they were delivered, so the transport
was up, so they were never outages.

## What can actually reach it

Every callable in that ~90-line try body is already total. Checked one by one:

| line | callable | contract |
|---|---|---|
| 907 | `build_sender_id_for_cc` | *"Returns None on any failure (import error, resolution failure)"* |
| 909 | `_summarize_task` | *"Returns None on any failure"* — bare `except` around the Gister call |
| 916 | `_get_session_context` | *"Never raises exceptions"* — two bare `except`s (bridge read, `git rev-parse`) |
| 936 | `notify_user_sync` | *"No exceptions raised (all handled internally)"* |
| 938 | `extract_qualifier_comment` | falsy-safe; falls through to a whole-string answer |
| 943 | `log_to_stream` | *"Never raises exceptions (logging failure is non-fatal)"* |
| 953 | `inject_qualifier_via_tmux` | *"Never raises exceptions"* |

The residue that can still throw is small and is **entirely our own glue**:

- `NotificationRequest( ... )` at line 924 — a pydantic `ValidationError` if a field is
  malformed. A defect, and a loud one: it means the Stop hook cannot ask its question at all.
- an `AttributeError` on `response.response_value` / `response.exit_code` — only reachable if
  `notify_user_sync` returns `None`, i.e. a defect in a function that promises it never does.
- a module-level `ImportError` in the glue itself.

⇒ **At this site, "an exception arrived" and "we have a bug" are the same statement.** Not by
classifying at the raise site, and not by anything the handler does — by the fact that every
non-defect failure was absorbed before it got there.

## Where the 212 cards came from, and what that changes

The row records the burst as *"a unit test's deliberately-raised RuntimeError… four per
unit-tier run across ~53 runs"*. That is consistent with the analysis rather than a
counter-example: in production `notify_user_sync` cannot raise, so a test had to **mock it to
raise** in order to exercise the handler. `ebb2c061` fixed the leak at `src/conftest.py:225`.

So the 212 cards were not a sample of the announce policy misfiring. They were a sample of a
test reaching the live transport. **The channel has been carrying almost no genuine traffic
from this site, which is why nobody could act on the traffic it did carry.**

## What I would change, and what I would not

**Do not** build the middle options as the row prices them — throttle, once-per-session,
route-elsewhere. Those all assume a volume problem. There isn't one; there was a leak, and it
is fixed.

**Do** two cheap things, neither of which needs a raise-site campaign:

1. **Narrow the try.** The catch spans `build_sender_id_for_cc` → `build_stop_block`. Wrapping
   only the glue that can genuinely throw would make the handler's meaning honest and cost
   nothing at runtime. Today its breadth is what makes it *look* unclassifiable.
2. **Fix the comment.** `# Server down, network error, import error → allow stop gracefully`
   is false for the first two. It is the load-bearing sentence a reader trusts, and it is what
   turned a narrow backstop into a debate about outage announcements.

**Add one thing to the card**: which session and which hook phase. The row's argument against
announcing is *"indistinguishable from a real notification, arrives with no context about
which session or why"* — that is true and it is a message-content defect, not an argument for
silence. `sender_id` is in scope on line 907.

## The honest caveat

This is an argument about **one site**. `stop.py` has 28 other `except Exception` handlers
and I did not audit them; `register_session.py` has 16 more. If Rick's ruling is meant to
cover "the Stop hook" as a whole, somebody has to walk the rest — and the finding here (every
inner callable already total, so the outer catch sees only defects) is a property of *this*
try body, not a law about the file. I would rule this site and leave the general policy open
rather than generalise from one handler, which is the mistake the off-peak window in CLAUDE.md
made twice.

## Where this disagrees with the row

The amendment states: *"THE HANDLER CANNOT TELL 'SERVER DOWN' FROM 'A BUG THREW'. Both arrive
at the same place as an exception, and line 983 has no way to distinguish them."*

The first sentence is true and the second is not: **server-down does not arrive there.** It is
absorbed by `notify_user_sync` and returns in-band. The amendment's conclusion — that keeping
any announcement means work at every raise site — therefore does not follow **at this site**.
It may well follow elsewhere in the hook; see the caveat above.

I am flagging this rather than editing the amendment out: Tiberius was reading a handler whose
own comment asserts the thing I am refuting, and the refutation is a five-file read that
nobody had a reason to do until the question was asked.

### ⚠️ Deviation from the approved wording, stated rather than absorbed

"Narrow the catch" was approved as **restricting the `except`**. It landed as *narrow its
meaning* instead, for a reason found while implementing: **the call site at `stop.py:2524`
has no guard of its own.** A raise escaping `_ask_anything_else` kills the hook process
before `emit_json()` runs, so the session's Stop goes unanswered — a worse failure than the
one being fixed, and squarely in the fleet's liveness path.

So the backstop stays broad and the *narrowing that was actually available* was applied: the
handler now names the phase and the session instead of emitting a bare exception string.
A reviewer who wants the literal narrowing should add a guard at the call site first; that
is a separate change and I did not make it.

### A finding the implementation produced

The phase tracker proved itself before any test asserted on it: a fixture with a malformed
`sender_id` made `NotificationRequest(...)` raise a pydantic `ValidationError`, and the card
correctly said `build_request`. That is the exact class the analysis predicted would be the
only kind of traffic this site sees — and under the old handler it would have arrived as an
unattributed wall of validation text.
