## The defect

A visual fixture seeds the state it cares about and captures an element whose subtree also contains
content the fixture never injects — a live commons feed, a live fleet roster, a live job history, a
live audio playback state. The snapshot then photographs whatever that live source happened to be
doing. Both the old image and the new one are correct renders; they are renders of *different
inputs*, and nothing in the test pins the difference.

## Operational definitions

These are the exact tests applied. They are deliberately narrow so the census can be audited.

| tier | definition |
|---|---|
| **measured exposed** | In a live render of *that exact capture*, I observed content inside the captured element that the test's own fixture does not inject. |
| **suspected** | The captured element's content derives from a source the fixture does not control (filesystem listing, fleet state, DM activity), but I have **not** observed non-fixture content in its frame. Listed so that absence is not read as a clearance. |
| **measured clean** | I enumerated the captured element's subtree in a live render and found **only** fixture-injected content. |
| **unexamined** | I have neither rendered nor enumerated it. No claim either way. |

## phase6a — the live input is visible, not latent

A two-arm test, one variable: the same capture taken with the real endpoint, then with
`page.route` fulfilling `/api/job-history` with an empty payload.

| arm | history bucket | pane |
|---|---|---|
| real endpoint | **21 cards** | 960x397 |
| stubbed empty | **1 card** (the fixture's own) | 960x397 |

The stub discriminates — the card count moves 21 → 1 — and the **height does not change**, because
the bucket is collapsed at 39px either way. But the two captures are **not** identical: **145 pixels
differ**, confined to `y364..375, x761..781`, inside the history bucket's header band (`y350..389`).

⇒ **This corrects an earlier reading in this document's own drafting.** The live job history was
first called *latent* on the grounds that a collapsed bucket contributes no height. Height is not
the only channel: the count reaches the frame. The exposure is **live**, and this arm can move
between runs on database contents alone, with no code change anywhere.

**The element is named.** Querying the bucket's subtree directly (an earlier `elementFromPoint`
probe returned nothing, because the pane sits outside the viewport at capture time):

| arm | element | box |
|---|---|---|
| real endpoint | `<span class="jobs-bucket-count">(111)</span>` | x760..787, y360..378 |
| stubbed empty | `<span class="jobs-bucket-count">(0)</span>` | x772..787, y360..378 |

Both overlap the differing region exactly, and in the stubbed arm the sibling `.jobs-bucket-label`
reflows (x15..764). The 145 pixels are the count text changing width plus that reflow.

### Correction — 111, not 21

An earlier reading of this arm reported **21**. Both numbers are real and they count different
things, so the correction is stated rather than silently replaced:

- **21** — the number of card *elements* rendered in the DOM inside the history bucket: the 20 rows
  the request returned, plus the fixture's own `phase6a_visual_history`.
- **111** — the API's `total` field, which is what the bucket header actually *paints*, and
  therefore the only one of the two that reaches the image.

The figure that matters for a snapshot is the painted one. This arm's capture carries a literal
three-digit tally of the database, as visible text.

⚠️ **And it does not explain phase6a's red.** The −7px height delta and the 106 genuinely-different
contentful rows are a separate, still-uncaused finding in the same arm. Pinning this input changes
145 pixels and therefore needs a rebaseline; it would not make this arm green.

## Two decisions, separately shaped

These are not the same choice twice, and collapsing them would hide the asymmetry that matters.

| | does pinning reproduce the committed golden? | cost of the fix |
|---|---|---|
| **phase6b** — AudioStore playback state | **Yes, exactly.** Pinned `idle` gives 960x244, the golden's own dimensions, with a 0.32% residual that is all host-versus-container text rasterisation. | **Zero.** No rebaseline. The exact match is itself the evidence that the golden was never wrong. |
| **phase6a** — `/api/job-history` count | **No, and it cannot.** The golden's number was whatever the database held on its capture day, and that value is unrecoverable. | **A rebaseline is unavoidable**, and the value to pin is a free choice. |

For phase6a the options are to pin the count to a fixed string and rebaseline **once, deliberately,
at that pinned value** — after which the number stops being data the snapshot carries — or to leave
it and accept that this arm's golden holds a live database tally indefinitely. The test already has
a `_STABILIZE_DOM_JS` pinning `.job-timing` and `.job-card[data-id-hash]`, so a count entry has an
existing home beside them.

**No recommendation is offered on either.** Both are rulings, not engineering calls.

## The one fix built so far

`test_multiplexer_phase6b_visual.py` — the focus-mode arm now pins `AudioStore`'s playback state
before capture, via a test-only override of the accessor on the store instance reached through
`__multiplexerTestHook`. No product source is touched.

Control, run on `:7999` with the browser timezone pinned to UTC:

| pin | chrome class | pane |
|---|---|---|
| `playing` | `tts-chrome is-playing-current` | 960x262 |
| `idle` | `tts-chrome` | 960x244 |
| `playing` | `is-playing-current` again | 960x262 |

960x262 is what `ts-2aa41f55`, `ts-df998099` and `ts-93b7e480` all produced; **960x244 is the
committed golden, exactly**. Pinning `idle` reproduces the golden — 748 differing pixels of 234,240
(0.32%), all host-versus-container text rasterisation, with `y71` identical in both. The golden was
never wrong; the red was the unpinned dimension.

**What the golden's state is, precisely**: pinning all six `AudioPlaybackState` values shows
`rootClass()` emits a class only for `playing` and `paused`. The other four render **two** distinct
images — `idle` and `decoding` are byte-identical (sha `4e1fb528c89e`), as are `ended` and `error`
(sha `5f7dff5cfae9`). The golden matches the `idle`/`decoding` pair, so it is **idle-or-decoding**
and **no image can ever narrow it further**.

**What this arm no longer guards** (the cost of the override, stated rather than implied):
`stores.audio.state()` is stubbed from the pin onward, so this arm can no longer fail if `AudioStore`
computes the wrong `AudioPlaybackState`, or if `rootClass()` maps a state to the wrong class. Both
are now unwatched *by this arm*. A snapshot that pins an input cannot also police that input; that
regression needs a unit test over `AudioStore` and `rootClass`.

## Measurement caveats carried by this document

- **Pixel counts here use a stated metric**: a pixel differs when the sum over the three RGB channels
  of |golden − capture| exceeds 8. This is **not** pixelmatch and **not** the suite's
  `threshold=0.1` colour distance. These numbers are not comparable to anything the suite prints.
- **Baseline file mtimes are mostly checkout times, not capture times.** 31 of the 39 baseline PNGs
  share one identical mtime (`2026-08-03 11:32`); thirty-one files were not captured in the same
  minute. A *shared* mtime proves a checkout; a *singleton* proves nothing either way. Neither can
  carry an argument on its own.
- **Host renders carry a timezone confound unless pinned.** The host runs EDT −0400 and both
  containers run `TZ=UTC`; an unpinned browser renders different clock digits, which shows up as a
  phantom diff band on any row holding a timestamp. Playwright's `timezone_id="UTC"` removes it at
  source.
- **A path being free in your own worktree is not evidence it is free.** This document was first
  written at its companion's path. The path was checked and was genuinely absent — but the check ran
  in this seat's worktree, and a worktree cannot see a peer's *untracked* file in theirs. Neither
  file was ever staged, so nothing was lost; the collision would have surfaced only at merge. The
  check that catches this is asking the peer, or looking across the worktrees, not `ls`.
- **Two instrument defects in this document's own measurements, disclosed rather than quietly fixed.**
  The `phase6a` probe raised `AttributeError` at teardown — a variable shadowed between the browser
  handle and a box dict, so `browser.close()` ran against a dict. It is the **final** statement in the
  script, after every screenshot write and every print, and it entered only in the last patch, so no
  reported figure is downstream of it; both arm PNGs decode through PIL's `load()` (which raises on
  truncation) and end with the 12-byte `IEND` chunk. It did leak one headless Chromium, since killed.
  Separately, the integrity check written to confirm those PNGs was **itself wrong** — it sliced the
  last **8** bytes and compared them against a **12**-byte `IEND` literal, so it reported
  "IEND present: False" on two perfectly sound files. A check that can only ever fail is worse than
  no check, and it was nearly filed as a finding. ⚠️ **And `Image.open()` alone would not have caught
  a real truncation either — PIL is lazy, so opening an image does not decode it.** `load()` is what
  forces the decode and raises; a check that only opens is a check that cannot see the defect it was
  written for.
- **A row-offset scan needs a content guard.** Uniform background rows match at *every* offset, so an
  unguarded scan reports a displacement that is an artifact of which offset was tried first.
