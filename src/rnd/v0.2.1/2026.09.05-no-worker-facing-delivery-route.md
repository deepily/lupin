## 0. The one-paragraph version

A worker finished a change, tiered it green, and could not deliver it. Two refusals, both
**correct**. The obvious repair — give the delivery branch its own integration worktree that
nobody sits in — is **measured to fail**, because `receive.denyCurrentBranch` counts linked
worktrees. The route that works is narrower than that: **the delivery branch must be checked
out in no worktree at all.** Then `git push <repo> <sha>:refs/heads/<branch>` delivers the
exact tiered sha, mutates nobody's working tree, and needs no permission exception.

### 3.1 G / H / I is the finding

**`denyCurrentBranch` counts LINKED worktrees, not just the main one.** So *"give the delivery
branch its own integration worktree that nobody sits in"* — the fix any reader reaches for, and
the one this author was about to propose — **does not work.**

**Arm I is why that is a measurement rather than a guess**: the same repo as G, with only the
integration worktree removed, pushes fine. The linked worktree was the sole cause, not
something else about that repository.

⇒ **The deciding variable is neither bareness nor permissions. It is whether the target branch
is checked out anywhere at all.**

## 4. The option, and what it costs

**The option** — stated as an option, not a recommendation, and not to be applied while the
ruling is outstanding:

```bash
git push <shared-repo> <tiered-sha>:refs/heads/<delivery-branch>
```

**Precondition**: the delivery branch is checked out in **no** worktree — not the main
checkout, not a linked one.

**What it buys**, and each line is why this shape rather than another:

- **It mutates nobody's working tree.** That is what the classifier was protecting (R3), and
  what Step 3.6 forbids doing to another seat's tree.
- **It delivers the exact sha the tier measured** — not a fresh merge commit with identical
  content and a different identity.
- **It is checkable before it runs**: `git merge-base --is-ancestor <branch> <sha>` says
  whether anything rebases.
- **It needs no permission exception.** A route that requires widening a control is a route
  that erodes the control.

**What it costs**, stated plainly because the ruling turns on this half:

- **The main checkout stops being on the branch.** `git status` there no longer names it, and
  people read that tree — including seats that resolve `$LUPIN_ROOT` to it.
- **Some tooling may assume a branch, not a detached HEAD.** Unsurveyed here.
- **Somebody must own the branch's tip** where a checkout used to make it obvious.
- **It is a change to shared layout**, so it is exactly the class of thing a worker should
  not do on its own initiative — which is how the seventh sighting arose in the first place.

## 6. The measurement errors this investigation made, and how each one was caught

Added 2026-09-05 by Rachel 🕊️ (4th incarnation) at María's explicit instruction:
*"a reader who sees only the final clean counts learns nothing about the trap."*
Every count in the sections above is correct as published. None of them was correct
the first time it was taken, and the failures are more transferable than the results.

### 6.1 A count needs its sha — and I invalidated my own by writing the prose

Section 3 reports a symbol count for `skip_to_fallback`. That figure was **TRUE at
`c3afdb5` and FALSE at HEAD**, and the reason is not that somebody else edited the
tree: **I added the two prose mentions myself**, in the very document reporting the
count, between taking it and quoting it.

⇒ **The author is not a safe reader of their own count.** The usual framing of
*a coordinate is not a reference* imagines a peer editing between your reading and
their acting. Here there was no peer and no interval to speak of — the writing of the
finding was the thing that falsified it. A number about a tree is a number about a
**moment**, and the moment ends when you start typing.

**The discharge is four characters**: write `N @ <sha>`, never a bare `N`.

### 6.2 `git merge-tree` against a COMMIT is not `git merge-tree` against a BRANCH, and the wrong answer looked like a finding

The first pass compared the target tip against a single **commit** rather than a branch
tip. That produced a clean-looking result for a comparison nobody had asked for.

Corrected, the same command returned **rc=129 for all three branches — including my
own**. My branch was 0-behind, so it **cannot conflict with the thing it is already
equal to**. That impossibility is the only reason I looked instead of publishing a
three-way conflict on my own file.

**`129` is a git USAGE error, not a conflict**: `--name-only` is not a valid
`merge-tree` option in git 2.34.1. Real trial merges in throwaway worktrees then showed
**all three merge CLEAN**.

⇒ **An impossibility is the cheapest detector you own, and it costs nothing to install
because it is already there.** I had no test, no reviewer and no second instrument. What
I had was one result that could not be true, sitting beside two that could — and the
false one is only visible *because* it landed on the case whose answer I already knew.
⚠️ Note which of the three saved it: **the arm I would have been most tempted to skip**,
because measuring my own branch against itself looks like a waste of a run.

### 6.3 "Merges clean" is not "landed", and a trial merge is exactly the artifact that blurs them

Mr. Radio's correction, and it survived a re-spin because it kept being nearly re-made.
A trial merge in a throwaway worktree answers *would this apply?* It says **nothing**
about whether anything reached the target, and it produces a green, satisfying, entirely
truthful result while the target carries none of the change.

⇒ The receipt for a landing is **the target branch's own sha carrying the symbols**,
never a successful merge somewhere else.

### 6.4 SYMBOL for presence, PATCH-ID for provenance, ANCESTRY for neither

María's ruling, 2026-09-05, and the clean worked example this row happened to produce.

| question | key | why the others fail |
|---|---|---|
| *is the capability in the tree?* | **symbol grep** | a cherry-pick makes NEW shas, so an ancestry check on the ORIGINAL shas reports absence forever, however well it landed |
| *is this Tiffany's reviewed change, or a lookalike?* | **`git patch-id --stable`** | a symbol says the words are there; it cannot say the diff is the one that was reviewed |
| *did this exact commit object land?* | ancestry | true only where nothing rebases, squashes or cherry-picks — i.e. almost nowhere here |

Measured on this row: the three cherry-picks carry patch-ids **identical** to their
originals (`ded8eed3…`, `e5ba1ecc…`, `7cda44a9…`), while **none of the three originals is
an ancestor of anything I produced**. Both readings are correct. Only one of them answers
the question.

### 6.5 A positive control that "drifts" usually changed population, not value

Three figures for the same control, `dismiss_sessions`, inside one evening: **58**, **59**,
**66**. They read as an instrument going soft. They are one instrument on three
populations — **58** = tracked files under `src/` at `5b86517e`; **66** = the WHOLE tracked
tree at the same sha; **59** = `src/`-scoped at the post-pick tip, where the new test file
adds one.

⇒ **Nothing drifted and nobody was wrong.** Reconciling took one command, and the reason
it was worth running is that a control whose value you cannot explain is not a control —
it is a second thing to worry about, sitting exactly where you put the thing that was
supposed to stop you worrying.
