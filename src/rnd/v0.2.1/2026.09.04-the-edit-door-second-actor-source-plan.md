## 3. 🔴 And door 1 did not fix attribution — including on its own door

This is a gap in my own landed work, found by planning this row rather than by reviewing it.

`3862c0b9:tasks.py:1035-1038` still passes `actor = payload.actor` to `apply_transition`. So

⇒ *"presents the same real identity mechanism"* is therefore ambiguous in a second way: door 1

## 4. The fork — A is a bug fix, B is a policy change

**(A) ATTRIBUTION ONLY — recommended.** Both doors record the authenticated identity instead of
the per-session string. No new refusal, no policy decision, no new surface. The consequential
fields the edit door already exposes without a gate — `owner_persona`, `accountable_manager`,
`priority`, `urgency`, `gate_class` — at least become truthfully attributable, which is the
accountability property `task_approval_settings`'s docstring already claims the store has and
which is currently false for every browser edit.

**(B) ATTRIBUTION + A GATE ON THE EDIT DOOR.** Adds an identity-aware refusal, e.g. restricting
reassignment of `owner_persona` / `accountable_manager`. ⚠️ **This is new policy, not a bug fix,
and the row is filed as a bug.** Who may reassign somebody else's work is Rick's ruling, not a
consequence of door 1. It also means the edit door starts refusing callers it has never refused,
which is the direction that breaks working workflows.

⇒ **Recommendation: (A) under this row; file (B) as a decision for Rick.** Under (A), DONE MEANS
#2's "discriminate" requirement is still satisfiable and still meaningful — the guard proves the
*recorded actor is the authenticated identity and not the client's string*, which a hard-wired
predicate cannot fake.

## 5. What the guard will look like (DONE MEANS #3)

Adopt **Maya's extractor** rather than writing a second one — her existing extractor deliberately
narrows to `_transitionTask`; widening it to both call sites is the change. The actor is read out

# PROPOSAL FOR RICK — should the edit door refuse anybody?

**Put by Rio, 2026-09-04. Not implemented. Recommending NO for now.**

## What the door lets anyone do today

An authenticated caller — any seat, any logged-in account — may PATCH any row's
`title`, `body`, `priority`, `urgency`, `gate_class`, **`owner_persona`** and
**`accountable_manager`**. The last two are reassignment: moving somebody else's owed
work onto a third party, or onto themselves. There is no gate. The only refusals in
`patch_task` are a 404 and shape validation.

## Why I am not proposing a gate

1. **It has never refused anyone, and the failure direction is bad.** A new refusal
   breaks working automation silently-from-the-caller's-view; the fleet's hooks and MCP
   wrappers all edit rows. The holding-area gate could be added safely because it
   guarded a move nobody was making yet. This one guards moves everybody makes hourly.
2. **Attribution may be the whole remedy.** The reason reassignment is worrying is that
   nobody could tell who did it. As of this change, for browser callers, they can. Watch
   the ledger before adding a wall — the same order this repo already learned the hard
   way: *reader before writer*.
3. **The honest scope is unknown.** I have not measured how often `owner_persona` /
   `accountable_manager` are patched, by whom, or whether any of it is a seat moving its
   own work. Proposing a gate without that is proposing a policy against a population
   nobody has counted.

## What I would want measured first

- How many patches touch `owner_persona` / `accountable_manager`, over a real window.
- How many come from a login account versus an API key. **A gate that only bites
  browser users while every seat holds the same fleet credential is theatre**, and this
  is the same honest limit `task_approval_settings` already documents about itself.
- Whether any reassignment in the log was one somebody would have wanted refused.

## If Rick says yes anyway

The mechanism is already here and costs one call: `refusal_for_admission`'s shape, with
`account_email` fed by the dependency the edit door now already takes. ⚠️ The design
question that would need HIS answer, not mine, is **which fields** — a gate on
reassignment only is a very different rule from a gate on all edits, and the second
would put a wall in front of every typo fix in the fleet.
