## 2. 🔴 The edit door refuses nobody, so one line of DONE MEANS describes something that does not exist

Read the whole function body rather than grepping for a gate name: `patch_task` contains
**exactly one `HTTPException`, a 404 at `tasks.py:1267`.** No approval gate, no manager-figure
gate, no 403 of any kind.

⇒ DONE MEANS #2 asks the guard to *"prove it still refuses an unauthorized actor."* **There is no
refusal on this door to preserve.** That is not an error in the row — it is a scope fork nobody
has ruled on, and it changes the size of the job by an order of magnitude.

## 3. 🔴 And door 1 did not fix attribution — including on its own door

This is a gap in my own landed work, found by planning this row rather than by reviewing it.

`3862c0b9:tasks.py:1035-1038` still passes `actor = payload.actor` to `apply_transition`. So
**after door 1, Rick approves successfully and the audit event still records "operator foolish
goat."** The gate reads the validated token; the ledger does not.

⇒ *"presents the same real identity mechanism"* is therefore ambiguous in a second way: door 1
established a mechanism for **admission**, and none for **attribution**. Adopting door 1 exactly,
as written, would give the edit door a gate it has no policy for and leave the goat in the ledger
on both doors.

## 4. The fork — A is a bug fix, B is a policy change

**(A) ATTRIBUTION ONLY — recommended.** Both doors record the authenticated identity instead of
the per-session string. No new refusal, no policy decision, no new surface. The consequential
fields the edit door already exposes without a gate — `owner_persona`, `accountable_manager`,
`priority`, `urgency`, `gate_class` — at least become truthfully attributable, which is the
accountability property `task_approval_settings`'s docstring already claims the store has and
which is currently false for every browser edit.

**(B) ATTRIBUTION + A GATE ON THE EDIT DOOR.** Adds an identity-aware refusal, e.g. restricting
reassignment of `owner_persona` / `accountable_manager`. ⚠️ **This is new policy, not a bug fix,
and the row is filed as a bug.** Who may reassign somebody else's work is Rick's ruling, not a
consequence of door 1. It also means the edit door starts refusing callers it has never refused,
which is the direction that breaks working workflows.

⇒ **Recommendation: (A) under this row; file (B) as a decision for Rick.** Under (A), DONE MEANS
#2's "discriminate" requirement is still satisfiable and still meaningful — the guard proves the
*recorded actor is the authenticated identity and not the client's string*, which a hard-wired
predicate cannot fake.

## 5. What the guard will look like (DONE MEANS #3)

Adopt **Maya's extractor** rather than writing a second one — her existing extractor deliberately
narrows to `_transitionTask`; widening it to both call sites is the change. The actor is read out
of the shipped client at test time, so the guard follows whatever the client does instead of
pinning a string that drifts.

⚠️ **The positive control is not optional here.** An extractor that finds zero call sites passes
every per-site assertion in its loop — the empty-corpus failure this repo has hit four times.
The guard must assert it found **both** doors, by count, before asserting anything about them.

⚠️ **And it must be reverted and watched go red on BOTH doors independently.** Two arms, not one:
a guard that reddens when door 1 regresses but not when door 2 does is exactly the blindness that
let this second call site exist unnoticed until a mutation harness refused to apply — *"ANCHOR
MATCHED 2x — NOT APPLIED"*, which is how Maya found it.
