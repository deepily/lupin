## The table

One row per server-side write path that can set `owner_persona`, `accountable_manager`,
`priority` or `status`. Handlers are named by symbol, never by line number — a line number
is a coordinate, and coordinates go stale between the writing and the reading.

| endpoint | file:symbol | fields it can set | role check | what identity it actually reads |
|---|---|---|---|---|
| `POST /api/tasks` | `rest/routers/tasks.py:create_task` | owner_persona, accountable_manager, priority, created_by, status (`queued`\|`blocked`), urgency, gate_class, authority | **NO** | `require_api_key_or_jwt` → a user UUID. Owner, manager, created_by and priority are taken from the payload verbatim |
| `POST /api/tasks/{id}/transition` | `rest/routers/tasks.py:transition_task` | status | **PARTIAL** | `refusal_for_admission` + `refusal_for_pull` — see below |

## The one check, quoted

`transition_task` calls:

```python
approval.refusal_for_admission( ..., actor=payload.actor, account_email=account_email )   # ADMIT / WONT_FIX / DEMOTE
approval.refusal_for_pull(       ..., actor=payload.actor, account_email=account_email )   # -> in_progress
```

Inside `refusal_for_admission`, in order:

```python
if not get_enforcement_active(): return None
if is_approver( actor ):         return None
# ...then the browser's door, which reads the validated account_email
```

### Measured, not reasoned

`is_approver` reads `payload.actor`, and it alone decides. Run with **no account email at
all** — which is every API-key caller:

```
ADMIT  not_approved -> queued,  account_email=None
   actor='mr radio'          -> ALLOWED
   actor='maria'             -> ALLOWED
   actor='cheech'            -> ALLOWED
   actor='chloe'             -> refused
   actor='chloe 315744e0'    -> refused
   actor='literally anyone'  -> refused

DEMOTE queued -> not_approved, account_email=None
   actor='mr radio'          -> ALLOWED
   actor='chloe'             -> refused
```

**The gate does not ask who you are. It asks what you typed.**

### And it is the only check for every MCP caller

`rest/middleware/api_key_auth.py:authenticated_account_email` returns `None` for an
API-key caller **by design** — its own docstring says so, and that is correct behaviour
for a route that must also serve CLI callers. But every `task_*` verb reaches the server
through `lupin_mcp/task_store_tools.py:task_store_request` with an API key, so on the
fleet path `account_email` is **always** `None` and the validated-account door is
unreachable.

⇒ **The browser's door works. The fleet's door is the string.**

## Three findings nobody asked for

1. **The repository layer has zero role checks.**
   `rest/db/repositories/task_repository.py` — `create_item`, `apply_transition`,
   `apply_patch`, `apply_amendment`, `apply_correlation`, `apply_chase`. Each body
   searched for `is_approver` / `refusal_for` / `approver` / `role` / `permission`:
   **0 hits in all six.** All authorization is router-side, so anything reaching the
   repository by another path is unguarded.

2. **The MCP verbs are not a second door** — this NARROWS the surface rather than
   widening it. `task_create` → `POST /api/tasks`; `task_transition` →
   `POST .../transition`; `task_reassign` **and** `task_edit` → `PATCH /api/tasks/{id}`;
   `task_amend` → `POST .../amend`; `task_correlate` → `POST .../correlate`. Same doors,
   same gaps, nothing extra to guard.

3. **P0 is exempt from the ratio gate** (`rules.RATIO_GATE_EXEMPT_PRIORITIES`), so the
   gate that stopped Krishna cannot stop a P0 create at all.

### Which gate actually stops a caller

The **flow-ratio gate**, inside `create_task`. It gates on **counts and priority, never on
role** — the right answer for the wrong reason, and it has a P0-shaped hole.

## A correction I made to my own draft

I nearly filed *"`require_admin` could not be read"* as a limit. **It can.** My search
looked for a `def` and it is an assignment — `rest/auth_middleware.py`,
`require_admin = require_roles( ["admin"] )`. It builds a dependency that resolves the
user via `get_current_user` and raises 403 unless their roles include `admin`.

So the three **YES** rows above are read from the enforcement itself, not merely inferred
from the `Depends()` binding. **An unverified "could not reach" is a false limit, and a
false limit is worse than no limit** — it tells the next reader a door is unexamined when
it has simply been examined badly.

## A process finding

This row could not be moved to `in_progress`. The pull toggle refused:

```
409  Pulling work into 'in_progress' is switched OFF right now.
     'chloe 315744e0' tried to move a 'queued' row into 'in_progress'.
```

It was OFF roughly forty minutes earlier (`get_manager_pull_disabled()` returned `False`)
and ON by the time the work started — switched on after Rick's broadcast, which is the
right response to what he asked for.

**The side effect is that a worker cannot start work his manager assigned him.** The
toggle gates the *transition* and asks nothing about whether the row is already the
actor's, so it cannot distinguish *"worker loads himself up with new work"* — Rick's
stated concern — from *"worker starts the row his manager just handed him"*. It stops
both.

The row therefore sat in `queued` from assignment through delivery. Recorded, not worked
around.

## Why this document exists at all

María's brief said *"the table IS the receipt"* and to close the row citing `doc_path`.
The store refuses that:

> *a `->done` receipt must cite at least one ref that can CARRY a close (`commit`,
> `test_run`, `operator_attestation`) — a `doc_path` or `log_line` proves a file exists,
> which is true whether or not the work landed.*

**An audit produces no commit and no test run.** So a pure measurement task cannot be
closed by its own worker under that rule — unless the measurement is itself committed,
which is what this file is. Committing the audit turns `doc_path` into a `commit`, and
both are cited on the close.

That is a finding about the store's receipt discipline rather than about this row, and it
is left here for whoever rules on it.
