> *"A guard whose failure path has never executed is a guard nobody has seen work, and its passing
> tells you nothing."* — the assignment, and it turned out to be right about all four.

## Part 1 — what drives what

| | |
|---|---|
| the **helpers** `cf.unreachable_subdirs` / `unseen_python_files` / `unreachable_declarations` | **well driven** — 9 / 10 / 4 unit-test call sites |
| the **gate script's own four branches** | **driven by nothing** |

`test_coverage_gate_tier_status.py` *does* subprocess `run-coverage-gate.sh`, but on a fixture copy
pinning **tier status** — it never reaches the frame block. This is § *IMPLEMENTED BUT NOT INSTALLED*
on a shell script: the class is tested, the assembled thing's branch is not.

## Part 2 — a positive control on MY OWN harness, before any result from it is trusted

The first attempt at this extracted the gate's frame block with an `awk` range pattern. **It matched
nothing, produced a 0-line file, and I ran an empty script twice** — once with the probe present and
once without. **Both exited 0**, which reads exactly like *"the branch does not fire"*: the conclusion
I was hunting, handed to me by a harness that had not run.

⇒ **An empty extraction and a broken query print identically** — this document's own predecessor said
so about a census, and it applies to the harness measuring it. So the extractor is now controlled
before it is used:

```
EXTRACTOR CONTROL: 44 lines; markers -> orphans=1 unexpected=1 undeclared=1 dead=1
⇒ the extractor CAN produce a non-empty block, so an empty one would be a real zero
```

It aborts if the block is empty or lacks the branch it is about to exercise. **What caught the empty
run was not vigilance** — it was the manager's *assert the control exists before asserting what it
does*: controls proved the probe was on disk, inside the frame, unseeable and undeclared, so the block
**had** to exit 1. The contradiction between that and `EXIT=0` is what exposed it.

## Part 3 — the negative control, which did not come back clean the first time

Run in a bare fixture, the block exits **1 even with nothing planted** — via `dead`, because a fixture
cwd cannot reach the real `KNOWN_UNSEEABLE` path. **The exit code therefore did not discriminate; both
cases were 1.**

**Fixed by making the fixture faithful rather than by disabling the check**: the declared path is
created inside the fixture and its directory listed in `source`, so the declaration is reachable and
`dead` has no reason to fire. It is now a clean **EXIT 0**.

⚠️ **Not fixed by monkeypatching `KNOWN_UNSEEABLE` empty** — that would have removed the branch rather
than satisfied it, and a control that passes because a check was deleted is not a control.

## Part 4 — all four branches, fired, with the output they printed

Fixture: `source = [ "top", "src/cosa/rnd" ]`; `top/plain.py` reported; the declared dot-file present.

| arm | planted | branch | EXIT | printed |
|---|---|---|---|---|
| **A** | *nothing* | — | **0** | `frame OK — 1 files reported, 1 declared unseeable, 0 unaccounted` |
| **B** | `top/2026.09.05-probe.py` | **undeclared** | **1** | *FILES COVERAGE CANNOT SEE AND NOBODY HAS DECLARED … `top/2026.09.05-probe.py`* |
| **C** | `top/dotless_probe.py` | **unexpected** | **1** | *FILES THE FRAME CLAIMS BUT THE REPORT DOES NOT CARRY: `top/dotless_probe.py`* |
| **D** | `top/sub/buried.py` | **orphans** | **1** | *FRAME IS NOT WHAT IT CLAIMS … `top/sub`* |
| — | *(fixture without the declared file)* | **dead** | **1** | *DECLARED UNSEEABLE BUT NEVER REACHED … `src/cosa/rnd/2026.05.21-…py`* |

**All four fire. None is decorative.** Arm A is what makes the other four mean anything.

### 🔴 B and C are a controlled pair differing by ONE CHARACTER, and that is the strongest thing here

Same directory, same content, same absence from the report. The only variable is a **dot in the stem**:

- **dotted** ⇒ coverage cannot see it ⇒ `unseeable` ⇒ **`undeclared`** fires
- **dotless** ⇒ coverage can see it ⇒ walked but unreported ⇒ **`unexpected`** fires

⇒ The gate does not merely *fail* on a bad file — it **routes** it to the branch whose remedy is
correct, and the routing turns on `coverage/files.py:579`. That is a discrimination test, not a
smoke test, and it reproduces the filename rule from the census doc as an unplanned second sighting.

## Part 5 — a manager hypothesis, cleanly dead

María proposed the empty extraction might itself have been caused by the fixture's dot-stemmed name —
*"your harness may be failing for the reason you are trying to detect."* A good hypothesis. **It is
false, and ruled out twice over:**

1. **By construction** — the empty extraction happened while parsing `run-coverage-gate.sh`. The
   fixture file did not exist yet.
2. **By measurement** — the second attempt used the **same** fixture name and extracted 44 lines.

⇒ Same fixture name, non-empty extraction. The cause was an `awk` range pattern that did not match,
and nothing else. ⚠️ **Her suggested remedy still paid**, just not as predicted: renaming the probe
dotless did not change the emptiness — it produced **arm C**, and with it the `unexpected` branch.

## What this does NOT establish

- The four branches were driven by the gate's **own frame block, extracted verbatim by line number**
  (`run-coverage-gate.sh:169-214`) and run in a fixture cwd. **The full script was not run end-to-end**
  — its tier invocation, coverage-json step and floor check are outside this measurement.
- It says **nothing** about whether the branches are *correct*, only that each **executes and prints
  its own message**. Whether `orphans` should fire on a given tree is a different question.
- **No test was added.** These arms are a measurement, not a regression guard. The branches remain
  undriven by the suite; making them driven is a separate piece of work nobody has ruled on.
- One tree, one sha, one moment. A census carries a timestamp whether it writes one or not.
