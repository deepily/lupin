## The discriminator, and why it settles it without re-firing

Two keys separate pre-merge from post-merge code, and they are **unconditional top-level
fields** — emitted on every return, dry run or not, provisioning success or failure:

```
session_spawner.py:951-952   "alarming_seat" : ...
                             "seat_worktrees": [ ... ]
```

Absent **repo-wide** before the merge, verified both directions:

```
git grep -c 'seat_worktrees' 4c8cf7b8 -- src/lupin_mcp/session_spawner.py   -> no match
git show e2a4261d:src/lupin_mcp/session_spawner.py | grep -c seat_worktrees -> 0
```

⇒ **Absent from a return ⇒ the process is serving pre-merge code. Present ⇒ the code is live**,
and a firing `placement_alarm` would then be a real defect.

Mr. Radio read his own 20:19:08 return: **no `seat_worktrees`, no `alarming_seat`.** He
verified the discriminator against the source rather than accepting it from me, which is the
only reason either of us should trust it.

⚠️ **`placement_alarm` cannot do this job**, and reaching for it is the obvious mistake. It
pre-exists the merge (3 hits at `4c8cf7b8`) and fires in merged code too — measured, on a
dry run, where provisioning is deliberately skipped. It is satisfied by more than one state,
so it cannot tell you which one you are in: CLAUDE.md § *UNGUARDED IS A THIRD STATE*.

## 🔴 The mechanism, which is worth more than the answer

`session_spawner` is imported **inside the tool function**, not at server startup:

```
src/lupin_mcp/cosa_voice_mcp.py:3222        from lupin_mcp import session_spawner
```

`sys.modules` is sticky. So a process binds the spawner module on its **first
`spawn_sessions` call** and serves that revision for the rest of its life, however long it
runs and whatever lands on disk afterwards.

| process | started | first spawn | serves |
|---|---|---|---|
| Mr. Radio's | earlier | **20:02:56** — Tiberius's respawn, 15 min pre-merge | **pre-merge** |
| Tiberius's | **20:02:57** | 20:23:42, post-merge | **merged** |

⇒ **His process is newer by a second and serves older code.**

🔴 **PROCESS START TIME DOES NOT PREDICT WHICH CODE A SEAT SERVES. FIRST-IMPORT TIME DOES.**

I had the start-time table on screen and was one message from reporting it as the answer. It
is a plausible, checkable-looking number that is simply about the wrong event — CLAUDE.md
§ *A COORDINATE IS NOT A REFERENCE*, where the coordinate is a timestamp and the reference is
the import.

⚠️ **And a lazy import inverts the usual intuition.** "A saved file is not a served file" is
already doctrine; the correction is that *restart time does not tell you when the serving
started*. With a module imported at startup the two coincide. With a lazy import they can be
fifteen minutes apart, in either direction.
