## The finding that changes the shape of the item

🔴 **The seven mount elements and the seven toolbar entries are ONE commit, not two.**

`src/tests/unit/multiplexer/the_hand_lists_are_checked_against_what_boot_reaches.test.ts` asserts
both directions between the panes the product declares and `SECTION_TOGGLES`:

| assertion | fires when |
|---|---|
| `🔴 EVERY PANE THE PRODUCT DECLARES HAS A VISIBILITY TOGGLE` | a pane exists with no toggle |
| `🔴 AND EVERY TOGGLE NAMES A PANE THAT ACTUALLY EXISTS` | a toggle names no pane |

Its page sweep is a regex over the markup:

```js
html.match( /<(?:section|div)\s+id="([a-zA-Z-]+-(?:pane|section))"/g )
```

⇒ The moment seven `<section id="…-pane">` elements land in `multiplexer.html`, the sweep sees
seven new panes and the **first** assertion reddens unless `SECTION_TOGGLES` gains the same seven
in the same commit. Pre-allocating the mounts alone is a red unit tier.

This is not a conflict with §2(b) — it is §2(b) becoming a *precondition* of §2(a) rather than a
sibling of it.

## 3. Insertion points

### boot.ts — already solved, use the marked slot

`boot.ts` carries an explicit block (search the fixed string `MOUNT-SLOT CONVENTION`) giving the
8-line handshake verbatim and the invariant:

> renderers mount FIRST, transports start LAST — a new slot goes ABOVE
> `attachLifecycleListeners()` / `transports.*.start`.

It also requires two lockstep edits per renderer: a `handlers` entry in `bootCompletePayload` and a
console line in the AC9 block. **No new convention is needed here** — the seven append into the
existing NEW-LANE MOUNT SLOT, which is what keeps seven worktrees from conflicting.

### multiplexer.html — no marked slot exists

Panes sit in a hand-ordered sequence of numbered comments, `(1) ACTION REQUIRED` … `(6) JOB QUEUES`.
There is **no** NEW-LANE marker in the markup. Pre-allocating therefore has to *create* one, and that
marker is precisely what the seven lanes would otherwise conflict over.

`SECTION_TOGGLES`'s own header comment asks that a new entry be placed to follow the page's vertical
order, so the toolbar list and the markup order must be decided together.

### 🔴 Open, and the build plan flags it too

**Does the lead's page order put Q&A above `action-required-section`?**

Legacy's order says yes: `section-qa` is its **first** section (`notifications.html:103`) and
`section-job-submit` its second (`:162`), both above `section-notifications` (`:478`). The
multiplexer begins at `(1) ACTION REQUIRED`.

**I measured legacy's order. I did not rule the multiplexer's** — that is the ruler's call, and it
decides both the markup positions and the `SECTION_TOGGLES` ordering.
