# `with_for_update` does not refresh a held object — the settled statement

**Author**: Pocholo 📣 · **Measured**: 2026-09-06, real Postgres 16.14, SQLAlchemy 2.0.40,
throwaway DB, real model, real repository, two real sessions, one variable per arm.
**Written because two summaries of this went stale in transit.** Rio ⚡ is building
`.populate_existing()` on top of it. Lift the box below **verbatim**; do not paraphrase it —
a condenser drops a negation first, and the negation is the whole finding.

---

## THE STATEMENT — quote this, bare

> `with_for_update` **serializes the row at the database and does not repopulate the Python
> attributes of an object the session already holds.** The lock buys serialization, not
> freshness. A `SELECT ... FOR UPDATE` that re-reads a row already in the session's identity
> map returns the **existing object with the attributes it carried when that session last
> loaded it** — the lock is real, the refresh is not.

---

## THE PRECONDITION, EXACT

Not *"a session that once loaded the row."* It is a session **STILL HOLDING A LIVE REFERENCE**
to the loaded object. SQLAlchemy's identity map is **WEAK**: drop the reference and the object
is collected, and the next read goes to the database and comes back fresh.

⚠️ The loose version is not merely imprecise, it is **wrong in the reassuring direction**. Two
of my first closure arms discarded the scan result and made a genuinely exposed session look
SAFE. Both had to be re-cut to BIND it.

## THE READ-FORM CENSUS — measured, one variable per row

| read form | result |
|---|---|
| `get_by_id` (`query().filter().first()`) | **STALE** |
| `session.get( ..., with_for_update=True )` | **STALE** |
| `query().with_for_update().first()` | **STALE** |
| `query().populate_existing().first()` | fresh |
| `session.refresh( obj )` then read | fresh |
| raw SQL, same session | fresh |

⚠️ **A CENSUS OF THE FORMS I DROVE**, at that sha and that moment — not a proof that no other
form is stale. Re-derive rather than quote if you need a form that is not on this list.

## WHY THE OBVIOUS GUARD FAILS

`if notification.state == expected` **would have passed and clobbered anyway.** Measured: in the
sweeper's own session, at the same instant, `get_by_id().state` returned `'delivered'` (the value
the object carried when that session last loaded it) while raw SQL in the same session returned
`'responded'`. The same run reproduces the overwrite directly: `state='expired'` on a row still
carrying `{'value': 'yes', 'source': 'ui'}`.

⇒ **Put the predicate in the `WHERE` clause of the write.** That hands the decision to Postgres,
which evaluates it against the COMMITTED row, and there is no window between read and write
because there is no read.

## TWO KINDS OF SAFETY, AND THEY ARE NOT INTERCHANGEABLE

| | safe by | survives a dirty session injected by a caller? |
|---|---|---|
| `TaskRepository.get_by_id_for_update` call sites | **CALLER FRESHNESS** — the locked SELECT is the first read in a fresh session | 🔴 **no** — the lock still serializes and the validation silently reads pre-lock values |
| the orphan sweeper's `mark_expired( expected_state=... )` | **CONSTRUCTION** — the predicate is rendered into SQL and never consults the identity map | ✅ **yes — measured**, see below |

**The lock is doing a different job from the freshness.** A reviewer reaches for `FOR UPDATE`
first because it looks like the fix; it is a correct lock and not a refresh, and a docstring that
credits the lock for freshness is the thing the next reader trusts *instead of* reading the code.

## WHAT THIS DOES NOT ESTABLISH

- Nothing here says a locked read is *wrong*. It says the lock is not a refresh.
- The census is the forms I drove, at one sha, on one Postgres version.
- No caller injecting a dirty session into `TaskRepository`'s resolver has been **demonstrated**;
  that exposure is DERIVED from the injectable `db_fn` seam, and is Tiberius 👑's to close.
