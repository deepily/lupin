# The defect whose only symptom is a SUCCESS

**Rio ⚡, 2026-09-04.** Banked at María's instruction: *"That is a whole class of invisible
defect and it deserves recording somewhere permanent, not just in a DM to me."*

Measured on branch `wt-rio-9d3a975e-door1-and-77f4e1d3-attribution` (`3862c0b9` … `fbe2b7e6`).

---

## The receipt

Door 1 of row `9d3a975e` made the holding-area approve gate read the login account off a
signature-validated token. It left the **ledger** reading `payload.actor`.

⇒ After the fix, Rick approves a row **successfully**, and the audit event records
`operator foolish goat` — **the exact string the gate had just declined to trust.**

I applied the one-line correction and, before writing any test, ran everything that could
plausibly have opinions about it:

| suite | result |
|---|---|
| `test_task_approval_gate.py` | pass |
| `test_the_transition_door_calls_the_approval_gate.py` | pass |
| `test_the_browser_actor_satisfies_both_endpoints.py` (the P0's own guard) | pass |
| `test_the_edit_door_records_a_real_identity.py` | pass |
| `test_tasks_router.py` | pass |
| **total** | **285 passed** |

🔴 **285 tests, and not one of them changed value in either direction.** The suite was
equally green with the ledger correct and with the ledger lying. Adding the fix proved
nothing; reverting it would have proved nothing either.

## Why nobody would ever have found it

**Because an approval that SUCCEEDS produces no error for anyone to chase.**

That is the whole class, and it is worth separating from the defects this repo already
knows how to catch:

| | what the user sees | who investigates |
|---|---|---|
| a **RED** (`cloud-run.env`) | failures naming the missing variable | everyone |
| a **REFUSAL** (`.env` / `JWT_SECRET_KEY`) | the import raises | everyone |
| a **FALSE FACT** (`static/dist/` census) | a live file reported dead | whoever doubts it |
| a **WEAKENED CHECK** (websocket baseline) | passes, having compared nothing | nobody |
| 🔴 **A CORRECT-LOOKING SUCCESS** (this) | **the thing you asked for, done** | **nobody, ever** |

The four above are already in `CLAUDE.md` § *THE WORKTREE ARTIFACTS THE TIER CANNOT SEE*,
ranked by how likely someone is to look. This one belongs at the bottom of that ranking and
is arguably below the weakened check: a weakened check at least logs a WARN. **Here the
operation does exactly what was asked, returns 200, and writes a durable falsehood.**

## The property that makes it invisible, stated so it transfers

**The defect rides the SUCCESS path.**

Everything we instrument is on the failure path. A gate that wrongly refuses generates a
403 somebody screenshots within the hour — that is precisely how `9d3a975e` was found, by
Rick, the same night. A gate that correctly admits and then **mis-records who was admitted**
generates nothing at all. The row is on the board, the click worked, the person moves on.

⚠️ **And it is worse than a silent no-op, because it is not empty — it is CONFIDENT.**

María put the reason better than my first cut did, and hers is the version to carry: **a
no-op leaves nothing behind to be trusted later.** My phrasing was that a no-op "leaves a gap
a later reader might notice", which makes the difference sound like a matter of how alert the
reader is. It is not. A no-op leaves **no artifact at all** — there is nothing for anyone to
build on, so nothing can be built wrong. This leaves a filled field that reads as an answer
and will be quoted as one, and every downstream conclusion inherits it. The failure is not
that a reader misses something; it is that a reader **correctly uses** what they were given.

⇒ *"An open gate deceives nobody; a ledger that confidently names the wrong actor lies to
every later reader."* — María, and it is the durable half of this document.

## What was underneath it

`task_approval_settings.py:23` claims, of the caller-declared actor:

> *"The authenticated user id IS recorded alongside, so a false claim is attributable after
> the fact — accountability rather than prevention."*

Measured:

```
authenticated_user_id in src/cosa/rest/routers/tasks.py :  bound 12x, read 0x
```

Bound in twelve signatures, present in no function body. **Positive control**, because an
empty grep is two different failures wearing one face: the same search shape finds three
real uses in `routers/commons.py`, so the zero is the code's and not the instrument's.

⇒ The store's entire accountability story rested on that sentence. **A sentence is not a
control** — this fleet's own doctrine, arriving at the fleet.

⚠️ Note the *shape* of what went wrong: the claim was not a lie, it was a **plan** that
never got wired, written in the present tense. Same family as § *A ROW BODY IS A PLAN, AND A
STALE MEASUREMENT IS MORE PERSUASIVE THAN A STALE OPINION* — and prose in the present tense
is exactly what a later reader takes as a statement of fact about today.

## Two things this cost me afterwards, both worth carrying

**AN INSTRUMENT CHECK DOES NOT CHECK THE TAXONOMY THE INSTRUMENT IS FEEDING.** María's
line, on my own error. My positive control — three real uses in `routers/commons.py` —
proved the *search* was sound, so I trusted the number it produced. The residual error
was one level up, in the **classification**: I counted bindings without splitting READ
from WRITE, and reported "12 sites broken" when 7 of them were correct by construction.
An unused binding on a read door is the dependency doing its whole job — refusing an
unauthenticated caller — by existing.

⇒ **A verified instrument gives you a trustworthy number and no protection at all
against the wrong question.** The count was right; the population it described was not.
⚠️ It nearly hardened into a fleet fact: the 12×/0× version had already been reported
upward before the narrower version replaced it.

**AND A DERIVED PARAMETRIZE POPULATION MAKES A KILL LOOK LIKE A SUBJECT-DESTROYING
BREAK.** Measured on the census guard here. When the parametrize list is *derived from
the thing under test*, a mutation of that population changes the test **count**, which
is exactly the signature CLAUDE.md tells you to treat as a syntax error:

| arm | ran | baseline | why |
|---|---|---|---|
| C4 empties the population | 14 | 19 | 5 parametrized cases stop being COLLECTED |
| C6 removes one door | 18 | 19 | 1 case stops being collected |

Both were real kills, and the discriminating fact is available without argument: **the
tests that reddened are NOT parametrized**, so they ran in every arm and their reds are
independent of the collection change. The arithmetic closes too — 19−5=14, 19−1=18,
exactly the population delta.

⇒ **Keep the ceiling check** — it caught a genuine ambiguity rather than crying wolf.
But when a guard derives its own population, add a non-parametrized assertion about
that population, or a mutation of it is indistinguishable from a broken file.

## How to find one, since no signal will bring you

There is no detector for this. What there is, is a question, and it costs one sentence per
change:

🔴 **"If this were wrong, what would anybody SEE?"**

If the honest answer is *nothing — it would still return 200 and still look right*, then the
test is not optional and the code review will not catch it, because a reviewer reads the
diff and the diff is correct-looking too.

Three sharper forms of the same question, in the order they are cheap:

1. **Does anything downstream READ the field I am writing?** If yes, is that reader tested?
   Here the reader is a human, weeks later, and humans are not in the suite.
2. **Would a mutation of this line redden a NAMED test that was passing?** If no, the line
   is unguarded regardless of the coverage number. `authenticated_user_id` had 100% line
   coverage on twelve signatures the whole time it was read zero times — **coverage counts
   the binding, not the use.**
3. **Is the operation's success the only observable?** Then the success is not evidence, and
   you need a second, independent reading of what it wrote.

## What was actually done about it

`fbe2b7e6` — one line, the same helper the edit door uses (**not** a second identity
scheme), plus **two** guard arms, both required:

| arm | catches |
|---|---|
| **T1** revert to `payload.actor` | the defect itself |
| **T2** rewrite EVERY actor, seat included | the over-correction |

**T2 is the one worth copying.** Every seat in the fleet authenticates by API key and holds
no login account, so a change that rewrote all of them would be a migration of the whole
audit history wearing a bug fix's clothes — **and T1 alone cannot see it**, because a
hard-wired rewrite satisfies *"the browser edit names a person"* perfectly. A one-armed
mutation pass would have called this fix proven.

⇒ **Both arms off one green 11/11 baseline taken FIRST**, run count 11 in both so neither was
a subject-destroying break, anchor matched exactly once, sha printed before and after,
per-arm purge-and-reconvert, restore control read.

## Scope — what this does NOT establish

- **One instance, measured once.** The 285-green result is a fact about these five files at
  this sha; it is not a claim about the tier's general blindness to attribution.
- **No survey was done.** I have not counted how many other fields in this codebase are
  written on a success path and read only by humans. That census would be the useful next
  step and nobody has run it.
- **The class is not new** — "test the success path, not only the failure path" is ordinary
  advice. What is new here is the *receipt*: a specific defect, in shipped code, that 285
  tests were structurally unable to see in either direction.
