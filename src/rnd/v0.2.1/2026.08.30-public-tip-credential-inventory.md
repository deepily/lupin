## Why the red was not what it looked like

The failing test was `test_a_detector_change_forces_a_full_rescan`, and the first read was that
cache invalidation had broken — that a new pattern would not re-examine already-scanned files.

**There is no cache.** The test re-runs the full scan every time; an earlier version *did* skip when
the recorded detector hash matched and that was removed on purpose (*"that was the hole: paste the
new hash and the skip fires"*).

**The detector change is behaviourally inert, measured.** The current detector over the previously
recorded tree (`1fa05b16`) reproduces the previously recorded fingerprint **byte-for-byte** —
`2e71f6d21da608914424…`, 239 locations / 116 distinct in both. Its file sha moved; what it finds did
not. Nothing went unscanned.

**The cause was the tree moving**, `1fa05b16 → 8bf71a64`, which the test's own docstring predicts:
*"It goes red whenever origin/main moves, by design."*

⚠️ **The diagnostic pointed at the wrong cause, and that is now fixed.** The failure message built
its label with an `if/elif` chain and printed only the *first* true cause. Both were true here; it
said `THE DETECTOR CHANGED` and never mentioned the tip had moved. It now joins every true cause
with `AND`. A red that names one of two causes points at the wrong one half the time it matters,
and this particular red is read by somebody deciding whether a credential is loose.
