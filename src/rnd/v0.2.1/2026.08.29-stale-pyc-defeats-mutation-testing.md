# A same-second, same-size source edit defeats CPython's pyc validation

**Row**: `d18ce9ef` (lupin, P2) · **Found**: 2026-08-29, while mutation-proving AC-G4 (`ed427d65`)
**Status**: measured; the repo-wide remedy is an OPEN DECISION for an owner. Nothing repo-wide was changed.

## The defect

CPython's default `.pyc` validation compares two things about the source: its **whole-second** mtime
and its **size**. An edit that changes neither is invisible, and the interpreter serves stale
bytecode as valid.

Measured on `src/cosa/rest/job_state.py`:

```
source mtime 21:33:22.780   "todo"   <- what grep read
pyc    built  21:33:22.568   "dead"   <- what import ran
```

For several minutes `grep` and `import` disagreed about the same file, at the same instant.

**Why it lands on mutation testing specifically.** The technique is: edit a source file, run the
suite, confirm red, restore, confirm green. Both the mutation and the restore are same-size edits
(`"todo"` -> `"dead"` is 4 characters either way), and a scripted loop does them inside one second.
**The failure points the wrong way**: you restore the file, read it back to confirm, and the
interpreter keeps running the mutant. Mutation testing is the technique this plan's receipts rest
on, so a hazard aimed at it is aimed at the evidence.

**It is CROSS-PROCESS.** This is not `importlib.reload` staleness — a *fresh* pytest process reads
the stale pyc off disk. So the exposure is not limited to tests that reload modules; it covers any
workflow that edits a source file and then runs pytest.

### Reproduction (deterministic)

```bash
printf 'LANE = "dead"\n' > pkg/m.py
python -c "import pkg.m"                      # bake the pyc
printf 'LANE = "todo"\n' > pkg/m.py           # same size
touch -r pkg/__pycache__/m.*.pyc pkg/m.py     # force the same whole second
python -c "import pkg.m; print(pkg.m.LANE)"   # prints: dead
```

## Candidate remedies, measured

Each was run against the reproduction above. A correct run prints `todo`.

| # | Remedy | Result | Verdict |
|---|---|---|---|
| R1 | `PYTHONDONTWRITEBYTECODE=1` | **`dead`** | ❌ **does NOT fix it** |
| R1b | `PYTHONDONTWRITEBYTECODE=1`, from a tree with no pycs | `todo` | ⚠️ only from clean |
| R2 | `PYTHONPYCACHEPREFIX=/tmp/...` | **`dead`** | ❌ relocates the cache, same race |
| R3 | delete `__pycache__` before the run | `todo` | ✅ works, must be remembered every time |
| R4 | bump the source mtime after restoring | `todo` | ✅ works, must be remembered every time |
| R5 | `compileall --invalidation-mode checked-hash` | `todo` | ✅ works, and is self-sustaining |

🔴 **R1 is the obvious candidate and it is measurably insufficient.** `PYTHONDONTWRITEBYTECODE`
only stops pycs from being *written*; a stale pyc already on disk is still read and still wins.
This repo has pycs throughout, so adopting R1 alone buys the appearance of safety, not safety.
It protects only a tree that was cleaned first (R1b) — which means the thing actually protecting
you is the clean, not the flag.

### Why R5 is different: it survives the recompile it triggers

The concern with a compile-time mode is decay — that the runtime rewrites the pyc as timestamp-based
at the first recompile and the fix quietly evaporates. **Measured, it does not:**

- after the hash check caught the change and the runtime recompiled, the new pyc holds the new value
  (`todo`) and its flags are still `3` — hash-based **and** checked;
- a **second** same-second, same-size edit against that runtime-written pyc was caught correctly.

So the invalidation mode persists across runtime recompiles. R3 and R4 are per-invocation habits
and fail the moment someone forgets; R5 is a property of the tree.

### Cost of R5

Import of a large graph, 3237 modules, mean of 7 runs each, warm cache:

| | mean |
|---|---|
| timestamp pycs | 2.7585 s |
| checked-hash pycs | 2.8500 s |

**+0.0915 s, about +3.3%** — roughly 28 µs per module, a source hash instead of a stat. A micro
benchmark on two modules could not separate them at all; this number is from the large graph, and
it is the honest one.

## What is NOT decided here

Whether to adopt R5 repo-wide, and where it would be enforced (a test-runner step, a venv build
step, a `conftest` assertion that pycs are hash-based) is **an owner's call, not this seat's**.
Scale for that decision: **1131** `.py` files under `src/cosa`, `src/lupin_app`, `src/lupin_cli`.

A narrower alternative worth pricing: leave the tree alone and give mutation-running tests a shared
helper that clears the target module's pyc and re-imports (R3 mechanised). That fixes the tests we
write and nothing about the ad-hoc edit-then-pytest loop an agent runs by hand — which is the case
that actually bit.

## The interim seatbelt already in the tree

`src/tests/unit/test_mobile_job_state_fixture_parity.py` reads `STATE_TO_UI_CONTAINER` twice — once
by import, once out of the source text — and fails loudly if they disagree, naming the pycache clear
as the remedy. **That is one file's seatbelt, not the fix**, and it is written up as such in the
file's own docstring so nobody reads it as coverage.
