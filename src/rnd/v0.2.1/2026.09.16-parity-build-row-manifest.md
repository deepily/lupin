**Report THREE states, not two.** The two-state table is the defect: it forces "built on a branch" to be spelled as either LANDED (wrong — it is not in the product) or OWED (wrong — it is written). Neither is true, and each misleads a different reader.

| state | test |
|---|---|
| **MERGED** | the anchor resolves at HEAD — today's LANDED, unchanged, and still the only state that means a user can see it |
| **BUILT-UNMERGED** | the anchor resolves on some ref that is NOT merged, **and** that ref is the NEWEST ref carrying this row key |
| **OWED** | the anchor resolves nowhere, **and** the legacy positive control is positive |

**The supersession rule, and why it is not optional.** An older branch carrying a row key that a newer branch also carries is **SUPERSEDED** — report it in its own list and never count it as built. Measured here 2026-09-19: `chloe/parity-a2-5-fleet-cap` (20 h, unmerged) sits beside `chloe/parity-a2-5-fleet-cap-v2`, whose commit `ee30e72c` **is** merged. The first branch is not pending work; it is work that was redone. A refs-wide search without this rule would have scored it BUILT and been wrong in the opposite direction from today's defect.

⚠️ **Three limits, stated rather than discovered later.** (1) "Newest ref carrying this row key" is a heuristic, not a proof — it reads commit dates, and a rebase rewrites those. (2) A branch from a reaped seat may be abandoned rather than pending, and nothing in git distinguishes the two; BUILT-UNMERGED therefore means *someone wrote this*, never *this is coming*. (3) The state is a **timestamped reading**, like every other figure in this document — a branch merges between your measurement and your reader's.

⇒ **The operational point for a manager**: never staff a row without checking BUILT-UNMERGED first.
