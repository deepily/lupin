# Which gates read a recorded artifact from the working tree — and which can be fooled

**Asked by**: Mr Radio 🦉, 2026-08-30, after `606af6b2` landed the tell in `src/tests/README.md`
**By**: Maya 🌻 · **Scope**: every gate in the PR-merge pyramid plus the unit tier

## Verdict

**There are two failure modes, not one — and the tell I just landed only catches the first.**

| | Mode 1 — TRACKED record | Mode 2 — UNTRACKED / GITIGNORED artifact |
|---|---|---|
| what happens | edit the record, red → **green** | artifact present ⇒ tests run; absent ⇒ tests **skip** |
| how it reads | a false pass | two machines "both pass" with different test counts |
| `git status --porcelain <path>` | `" M"` — **the tell works** | **nothing at all** — gitignored paths are suppressed entirely |

⇒ **The README block is correct and incomplete.** `git status` cannot see a gitignored artifact, so
"clean" is indistinguishable from "an un-versioned file is quietly deciding what runs here". Mode 2
needs a different check, and it is a property of the *gate* rather than of a run: **does this gate
read a path that git ignores?** That is answerable once, by the list below, not per-run by a seat.

## Mode 1 — tracked recorded verdicts (the tell works)

| gate | artifact | status |
|---|---|---|
| `test_secret_scan.py:255` — public-tip fingerprint | `src/tests/unit/fixtures/secret_scan_last_full_scan.json` | TRACKED |
| `test_secret_scan.py:317` — branch accepted-set | same file | TRACKED |
| parity-oracle golden capture (full-page + sender-card) | `src/tests/e2e_ui/fixtures/golden/*.golden.json` | TRACKED |
| `test_manager_figure.py:278` | `src/tests/fixtures/captured-legacy-bridge-c1404a70.json` | TRACKED |
| **the coverage gate's floor** | `pyproject.toml` → `[tool.coverage.report] fail_under` | TRACKED |

All five are fooled by the same move — edit the record, watch the red go away — and all five leave
a `" M"` behind.

✅ **The coverage gate already carries a partial tell, and it predates mine.**
`run-coverage-gate.sh:118` prints `sha=… tracked-dirty=… coverage-file=…` on every run. That is the
right instinct. Its gap is in the name: `git status --porcelain --untracked-files=no` counts tracked
modifications only, so it sees a hand-edited `fail_under` and is blind to everything in Mode 2.

## Mode 2 — gitignored artifacts a gate actually reads (the tell is blind)

**This is the answer to the question that was asked.** Two found, both real, both currently present
on this host and absent from a fresh clone:

| gate | artifact | ignored by | effect |
|---|---|---|---|
| `test_freeze.py:47` (DM compression) | `src/tmp/arm4/dm_traffic_snapshot_2026.08.07.jsonl` | `.gitignore:5` (`tmp`) | **7 test functions** `pytest.skip` when absent |
| `test_terraform_invariants.py:216` | `src/terraform/envs/test/.terraform/providers` | `.gitignore:93` | already documented in CLAUDE.md as one of the 11 worktree-only failures |

**Measured on this host**: `test_freeze.py` collects **494 tests** and reports **494 passed**,
because the corpus is sitting in `src/tmp/`. On a machine without it, seven of those functions skip
and the summary still reads as success. Nobody is lying; the two runs are measuring different
things and the output does not say so.

⚠️ **`.coverage` data files** are untracked by design and per-run isolated, so they are not a
fool-risk in the same sense — but they are the same shape, and the gate is right to print which one
it read.

## What I would change, and what I would not

**Would**: extend the README block to name Mode 2, because a tell that quietly covers half its class
is the exact defect this whole thread has been about. One sentence: *"`git status` cannot see a
gitignored artifact — if a gate reads a path under `src/tmp/` or `.terraform/`, its result is a
property of your machine and no marker will tell you."*

**Would not**: try to make `git status` cover it. The check for Mode 2 is a one-off audit of gates
against `.gitignore` — this document — not something to ask a seat to run before every report.

**Open, and not mine to rule**: whether `test_freeze.py`'s corpus should be tracked, or its seven
tests should fail rather than skip when it is missing. A skip is honest; seven silent skips inside a
494-test green is honest and useless.

## Method

`git ls-files --error-unmatch` and `git check-ignore -v` on every artifact path found by grepping
the test tree for recorded-artifact reads, plus `--fixtures-per-test` to count what actually depends
on the ignored corpus. Nothing was deleted, renamed, or moved; the corpus and the provider cache
belong to this host and were only read.
