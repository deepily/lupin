# A guard that declines to run, and reports success

**2026-09-02 · Rio ⚡ · sweep at `9efefb5c` · commit held on `rio-fold-status-matrices`**

## The question

After the row-control redesign merged, six Python tests went red. Those were loud and got
fixed. **The question nobody had asked was about their siblings**: a guard that reads the
client as TEXT and whose assertion quietly stops meaning anything keeps passing, and looks
exactly like one that works.

⇒ **The discriminator is not reading the guard. It is breaking the thing the guard names
and watching whether it reddens.** A guard that does not redden is not passing; it is
silent.

## 🔴 The find: an assertion behind an existence check

`test_tfe_error_capture_smoke` asserts a section is present in the shipped client. That
assertion sits inside `if os.path.exists( path )`, where `path` is built from `LUPIN_ROOT`
with a `/var/lupin` default and **no else branch**.

Measured on ONE mutant sha `16584c297148`, the environment the only variable:

| `LUPIN_ROOT` | result |
|---|---|
| the tree under test | **1 failed** — the guard works |
| a tree with no client file | **1 passed** — the guard never ran |

⇒ **The same defect, the same sha, and the guard reports success because it could not find
the file it was written to read.** Nothing in the output says so. This is the shape the
whole sweep existed to find, and it is not a bug in the assertion — the assertion is
correct. It is a bug in the guard's silence about its own precondition.

## The repair: every text-reading guard states its denominator

Not invented here — **the tree already contains the pattern**, in
`test_session_id_payload_contract.py`:

```python
keys = set( re.findall( r'"(\w+)"\s*:', src[ ret : close ] ) )
assert keys, f"parsed ZERO keys out of the {ENDPOINT} return — every assertion below would pass vacuously"
```

That is the whole idea: **say how many things you found, and fail when the answer is
none.** A loop over an empty corpus is green; a denominator turns that silence into a
failure. Pick N from what the tree holds today and say where it came from.

## Two instrument errors of mine, both thrown away

Recorded because anyone repeating this work will hit them, and neither is obvious.

**1. An early `return` is not a defect a text guard can see.** My first arm inserted
`return \`<div class="task-actions"></div>\`;` at the top of the cell and left the original
body below it, unreachable. Every string was still in the file, so every text-reading guard
saw no change and I nearly filed "nothing reddens" as a vacuity finding. ⇒ **For a
text-reading guard the defect must be a text DELETION.** The second arm removed the 40-line
body outright.

**2. A hit is not a use — committed by the sweep written to find it.** My first classifier
reported 21 of 21 TypeScript files as asserting on source text. Every one of those hits was
the shared harness slicing at `indexOf( "// Initialize when DOM is ready" )` before eval.
Corrected count: **0 of 21**.

**3. And the baseline moved under me.** The first pass ran against a file that was 6-red
awaiting repair, so "6 → 8 failed" counted six pre-existing reds plus two movers. On the
repaired green baseline the same mutation reddens **five**, and only two of the originally
named pair survive the correction. ⇒ **An arm against a red baseline is unreadable**, and
the reds it inherits will masquerade as its result.

## What this does NOT claim

The eleven "guarding" verdicts are each about ONE defect — the one that guard names. They
say nothing about other properties those files may claim and not watch. The sweep found the
class of hazard and one live instance of it; it is not a proof that the other ten are
complete.
