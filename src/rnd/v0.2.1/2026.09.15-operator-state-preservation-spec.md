# Operator-State Preservation — the multiplexer contract

**Status**: specification, pre-build. No ticket may open against operator-state preservation until **Mr. Radio 🦉** (build owner) has ratified or overruled the six open questions at the foot of this document. **Author**: María 🌸 — she wrote this spec and the build plan, so she is not an eligible reviewer of either (see the build plan §5 clause 3).
**Date**: 2026.09.15
**Ported from**: `src/lupin_app/static/js/notifications.js` — `_captureOperatorState` (:13231), `_restoreOperatorState` (:13323), `_operatorInputKey` (:13402), `_operatorInputByKey` (:13423), and the press-hold guard in `_wireTaskListAccordion` (:14274-14283) with its release half `_releaseTaskListPress` (:13216-13229).
**Ported to**: `src/lupin_app/static/js/multiplexer/` — the Task List, Holding Area and Epic Board panes.

## Why this document exists

The parity build plan describes this work as an OUTCOME ("capture and restore operator state") and points at `captureCardFocus` / `restoreCardFocus` (`multiplexer/render/NotificationsListRenderer.ts:1296-1344`) as though that pair were the specification. It is not. That pair is focus-only, captures no VALUES, and keys on `.sender-card[data-sender-id]` plus a tag-and-first-class selector — a different pane, a different key space, and five of the six categories missing. Five build tickets written against an outcome would produce five partial repairs of one mechanism.

## The contract, in one paragraph

A repaint of a task-bearing pane must not destroy operator work that has not yet been submitted. Before the pane's markup is replaced, six categories of state are read off the markup that is about to be discarded; after the replacement, they are put back into the fresh markup in a fixed order that is load-bearing, best-effort per row — a row the fresh data no longer contains is left gone. Where no capture can help because the node the browser is mid-gesture on is the thing being replaced, the repaint is DEFERRED for the length of the gesture instead. Where the state must outlive the document itself, it is persisted. The property being kept is narrow and stateable: **a poll tick landing between an operator's keystroke and their click must not change what that click does.**

## §1 — The category list

Legacy's capture object names six slots (`notifications.js:13266`):

```js
const state = { inputs: [], selects: [], priorities: [], stripes: [], disclosed: [], focusKey: null, selStart: 0, selEnd: 0 };
```

The docstring names the defect the whole mechanism exists for (`:13234-13242`):

> 🔴 THIS IS RICK'S DEAD BUTTON. Every pane here repaints by replacing `container.innerHTML` on a 60-second poll, and the operator's half-finished work lives in that markup. Type a won't-fix reason, let one poll land, then click: the box the handler reads is EMPTY, the blank-reason guard fires, and no request ever leaves the browser. The stripe explaining the refusal is wiped by the NEXT poll, so within a minute there is nothing on screen either. Type, pause, click, nothing — and no evidence afterwards.

And why it went unfound (`:13243-13248`):

> ⚠️ IT NEEDED NO PANE AND NO ROW IDENTITY, which is why it survived while a two-pane lookup collision, a pane with no listener, an item_class branch and the disclosure ellipsis were each examined and ruled out. And it went unseen because a tester types and clicks in one motion, inside a single interval, while every test called the handler by name so no poll could run between them.

### The repaint-idiom difference, and what it means for the contract

The Notifications pane repaints through `keyedListMerge` with node preservation — a matched card **keeps its node** when its signature is unchanged and only its volatile header is repainted (`render/NotificationsListRenderer.ts:514-543`). That is why its focus helper can start with `before.element.isConnected` and often just refocus the very same node (`:1332`).

The three panes this spec targets do not work that way. They call `replaceChildren` wholesale: `render/TaskListRenderer.ts:376`, `:397`, `:400`, `:432`, `:477`, `:485`, and `render/EpicBoardRenderer.ts:212`, `:219`, `:229`, `:242`, and `render/HoldingAreaRenderer.ts:320`, `:322`, `:542`.

**Consequences for the contract, all three of which a builder would otherwise have to discover:**

1. **Every node is new. There is no `isConnected` fast path.** Restoration is always a lookup by key in fresh markup, never a refocus of a surviving element. Do not port `captureCardFocus`'s structure; it is shaped around a merge that does not happen here.
2. **Capture must happen before each `replaceChildren` call, not once at the top of the render function.** `TaskListRenderer.renderFromStore` has three exits that do not reach the table paint: the sign-in branch repaints with a message and returns (`:375-379`), the unreachable branch delegates and returns (`:381-384`), and the pinned branch delegates and returns (`:392`). A single capture at the top would pay for the message branches, and a capture/restore pair straddling a delegating return would be dead code that looks live.
3. **There is exactly one moment to restore, and it is synchronous with the repaint.** `hydrateRequests()` runs immediately after `replaceChildren` (`:401`, `:434`, `:481`) and paints the pending chips — including a `.task-action-input.task-request-triage` box. Restore must run **after** hydration or a restored triage date is overwritten by the hydrator's own paint. Legacy's order is the opposite (`:12101` restore, then `:12102` hydrate) because legacy's hydrator does not repaint that box; **this is a real divergence and a builder must verify it against `render/requestChips.ts` rather than copying legacy's line order.**

## §2 — The key shape

`_operatorInputKey` (`notifications.js:13402-13421`):

```js
if ( !el || !el.dataset || !el.className ) return null;
const owner = el.dataset.taskId || el.dataset.filer || "";
if ( !owner ) return null;
const attr  = el.dataset.taskId ? "data-task-id" : "data-filer";
const which = String( el.className ).split( /\s+/ )
    .find( c => c !== "task-action-input" && ( c.startsWith( "task-" ) || c.startsWith( "holding-" ) ) );
return which ? `${attr}\0${owner}\0${which}` : null;
```

So the key is exactly **`"<attr>\0<owner>\0<whichClass>"`**, three NUL-separated fields:

- **`attr`** — the literal string `"data-task-id"` or `"data-filer"`, whichever the element carries; task id wins when both are present.
- **`owner`** — the value of that attribute. Null key (element skipped entirely) when neither attribute is present or both are empty.
- **`whichClass`** — the first class in the element's class list that is NOT `task-action-input` and DOES start with `task-` or `holding-`. So `class="task-action-input task-reason-input"` yields `task-reason-input`; `class="task-action-input holding-wont-fix-all-reason"` yields `holding-wont-fix-all-reason`.

Lookup is the mirror (`_operatorInputByKey`, `:13423-13435`): split on NUL, require exactly three parts, then `container.querySelector( ".${which}[${attr}=\"${CSS.escape( owner )}\"]" )`.

### Why there are two schemes

Capture (`:13271-13273`):

> ⚠️ TWO KEYING SCHEMES, because the markup has two. Row controls carry `data-task-id`; the holding area's BATCH reason carries `data-filer` and no task id at all, so a per-row sweep misses it — and losing that one costs a whole group's worth of typing rather than one row's.

Key builder (`:13405-13409`):

> A row carries several (a reason and a date on park and demote), so the owner id alone would restore a chase date into a reason field. And the owner is not always a row: the holding area's batch reason is keyed by FILER, so the attribute has to travel with the key or the lookup afterwards searches the wrong one.

The attribute name travels IN the key precisely because the two namespaces can collide: a filer named the same as a task id must not be looked up under the wrong attribute.

The multiplexer's markup has the same two schemes — `render/templates/holdingAreaTable.ts:81-84` says so in its own words: "the batch reason is keyed by FILER, not by task id, which is why the row-level `data-task-id` lookup the other panes use does not reach these."

### 🔴 One thing must NOT be ported: the `CSS.escape` interpolation

Legacy interpolates the escaped owner into a selector (`:13433-13434`, and likewise at `:13346`, `:13363`, `:13380`, `:13384`). The multiplexer tree has measured that this breaks under test, twice, in writing:

- `render/templates/rowDisclosure.ts:199-209`: "Measured: CSS.escape produces a VALID escape that happy-dom's selector parser then rejects outright — so a real-browser-correct port still breaks under test, and the failure is in the parser, not the id. Comparing the attribute directly has no escaping question at all and is correct whatever the id contains."
- `render/TaskListRenderer.ts:947-950`: "⚠️ NO SELECTOR INTERPOLATION — a task id is server data, and CSS.escape produces valid escapes that happy-dom's selector parser then rejects."

**Contract**: the mux lookup selects on the class alone — a code-controlled literal, safe to interpolate — and then compares the attribute value:

```
Array.from( container.querySelectorAll( `.${which}` ) )
  .find( el => el.getAttribute( attr ) === owner ) ?? null
```

The same rule governs the verb, priority, stripe and disclosure lookups in §3: **no task id, filer or owner may ever enter a selector string.**

Two further port notes: the NUL separator gets a named constant (`const KEY_SEP = "\0"`), and the `which` scan is a function shared by key-build and key-parse so the two cannot drift.

> 📏 **This document writes the separator as the two-character escape `\0`, never as a raw NUL byte.** Revision 1 embedded five literal NULs here and in §2. A raw NUL past the first 8 KB is invisible to git's binary heuristic — so the file diffed and reviewed as ordinary text — while `grep` classified the whole file as binary and returned **zero hits for every term in it**. A reviewer grepping this spec would have measured "not present" for content that is present. The escape reads the same and keeps the file greppable.

## §3 — The restore order

The order is not a style. Legacy states this at the top of the priority block and again at the verb block; each position prevents a specific silent failure.

1. **Verbs first.** For each `[ taskId, verb ]`: find the `.task-verb-select`, assign `sel.value = verb`, then **call the verb change handler** (`:13344-13351`).
   **Prevents**: the date box not existing when the text restore runs. Legacy, verbatim (`:13339-13343`):
   > ⚠️ THE VERB GOES BACK FIRST, AND THE ORDER IS LOAD-BEARING. Park and Demote's date box exists only because their verb is chosen — the change handler builds it — so restoring text before the verb would look for a field that has not been created yet and silently drop the date.

   True of the multiplexer too: `handleVerbSelectChange` (`render/TaskListRenderer.ts:588`) creates the `.task-chase-input` element on demand (`:604-623`) and removes it when the verb does not want one (`:624-626`). A restore that skipped the handler would put the verb back above a row with no date field.

   ⚠️ **Mux-specific hazard, and it is new**: `handleVerbSelectChange` also **clears the reason box** when the chosen verb takes no reason (`:601` — `if ( box.disabled ) box.value = "";`), and **disarms Submit** (`:628`). Clearing is correct on a real change and correct here too (the captured reason for a no-reason verb is not submittable), but the builder must confirm the order still yields the right answer: verb restored → box cleared → text restored on top. Since step 3 skips empty values but does not skip a disabled box, **step 3 must not write into a box whose `disabled` is true.** Legacy has no such branch because legacy's `_handleVerbSelectChange` is a different function; this is a genuine addition to the contract, not a port.

2. **Pending priorities second.** For each `[ taskId, priority ]`: find the `.task-priority-select`; **skip when no matching `<option>` exists**; assign; then call the priority change handler (`:13361-13368`). See §4 for the full reasoning.

3. **Typed inputs third.** For each `[ key, value ]`: **skip empty values**, resolve the element by key, assign `el.value = value` (`:13369-13373`).
   **Prevents**: two things. Dropping an empty capture stops a stale empty from overwriting a box the fresh render legitimately painted with content. Running after step 1 means the date box exists. Running after step 2 means nothing (the two are independent) — but the position is fixed anyway, because a reader reasoning about "what exists yet" needs one order, not two.
   Mux addition: also skip when `el.disabled` (see step 1).

4. **Stripes fourth.** For each `[ taskId, message ]`: skip empty, then re-render the refusal through the pane's own error renderer, scoped to this container (`:13374-13377`).
   **Prevents**: the refusal vanishing. It is, per `:13251-13252`, "the ONLY thing telling the operator why a control did nothing." Position: after the rows exist. Mux target is `TaskListRenderer.renderRowError( id, message )` (`:936-960`) — already pane-scoped and already interpolation-free, so it is reusable as-is. **The Holding Area and Epic Board have no equivalent renderer**; whether they need one is a build question, not a spec question, but a stripe captured in a pane that cannot re-render it would be captured and silently dropped, so the builder must either add the renderer or state in the ticket that those two panes capture no stripes.

5. **Disclosed rows fifth.** For each captured id: find the `.task-controls-row`, set `hidden = false`, and set the toggle's `aria-expanded="true"` and its title (`:13378-13389`).
   **Prevents**: "re-collapsing takes the form off screen mid-sentence" (`:13253-13254`). Position: after the inputs, because those inputs live INSIDE the controls row in the mux (`render/TaskListRenderer.ts:651-656`) — assigning a value into a hidden element is fine, but focus (step 6) into a hidden element is not, so the unhide must precede it.
   ⚠️ The mux flip lives in `toggleDisclosure` (`render/templates/rowDisclosure.ts:191-215`), which reads the CURRENT `aria-expanded` and inverts it. **Restore must not call `toggleDisclosure`** — it must set the state absolutely (hidden = false, aria-expanded = "true"), exactly as legacy does. Calling the toggle would close a row that the fresh render happened to paint open.

6. **Focus and caret last.** If `focusKey` is set: resolve the element, `el.focus()`, then `el.setSelectionRange( selStart, selEnd )` **inside a try/catch** (`:13390-13399`). Legacy's catch comment: `/* input types that refuse a selection range, e.g. date */`.
   **Prevents**: "restoring the text into a box the operator is no longer typing in is half a repair: the next keystroke would land nowhere" (`:13255-13257`). Position: dead last, because every earlier step can move, replace or unhide the node that focus targets.
   The try/catch is **required** in the mux, not optional: `.task-chase-input` is `type="date"` (`render/TaskListRenderer.ts:607`), which is exactly the case the legacy comment names.
   Recommendation (mine, not in the source): use `focus({ preventScroll: true })`, as `restoreCardFocus` does (`render/NotificationsListRenderer.ts:1343`) — a poll landing must never scroll the pane out from under the operator. Legacy uses a bare `focus()`; the mux already has the better idiom in-tree.

## §4 — The pending-only rule

**What "pending" means.** A priority select is captured only when `( el.value || "" ).trim()` is non-empty AND differs from `el.dataset.original` (`notifications.js:13306-13310`). `data-original` is stamped on the select when the row is painted (`:10640-10641`) and therefore re-stamped on every repaint.

Legacy's reasoning, verbatim (`:13298-13305`):

> 🔴 RICK'S SECOND DEAD BUTTON, AND THE SAME ASSIGNMENT KILLED IT. He reported the priority Update as "permanently disabled — no change in value re-enables it". The control works when you call it; what it could not survive was a POLL LANDING BETWEEN the choice and the click. Choose P2, wait one tick, and the repaint puts the row's stored priority back and the button back to `disabled`. From his side that is a button that never works, with nothing left on screen to show why.
>
> ⚠️ ONLY A PENDING EDIT IS CARRIED — a select still showing the row's own value is deliberately NOT captured. Restoring an untouched select would re-assert a stale value over a row somebody else has since re-prioritized, which would light Update over an edit this operator never made. `data-original` is what makes "pending" decidable, and it is re-rendered with the row, so it is always the fresh truth.

**Why the restore recomputes rather than forces.** Restore assigns the value and then hands the select to `_handlePrioritySelectChange` — the same handler the operator's own keystroke reaches (`:13361-13368`). It never touches `button.disabled` directly. Verbatim (`:13352-13360`):

> ⚠️ THE VALUE GOES BACK FIRST AND THE BUTTON IS RECOMPUTED SECOND, NEVER FORCED. Restoring the value alone is half a repair — the fresh markup renders Update `disabled`, so the operator would get their choice back above a button they still cannot press. And forcing it ENABLED would be wrong the other way: if the board caught up to the chosen value while the poll was in flight, there is nothing left to submit. Handing the saved value to the same change handler the operator's own keystroke uses is what makes both cases come out right without a second rule.
>
> A saved value with no matching option is left alone: assigning it would set the select to "" and light a button over a value the click handler then refuses.

The handler itself is small and is the whole rule (`:10648-10672`): `moved = value !== dataset.original`, then `disabled`, `aria-disabled` and the title all track `moved`. Its own docstring names why the truth lives on the element: "AGAINST `data-original`, NOT AGAINST A REMEMBERED VALUE. The row repaints on every poll tick, so any state held outside the DOM is gone within seconds; the original has to travel ON the element that survives the repaint."

### 🔴 The multiplexer divergence — this slot is vacant today

The mux priority select **has no Update button, no `data-original`, and commits on change**. The tree says so at the point of definition (`render/templates/taskRowControls.ts:147-158`):

> 🔴 `.task-priority-select` NAMES TWO DIFFERENT CONTROLS IN THIS PRODUCT, AND THEY HAVE OPPOSITE SEMANTICS. This one — the multiplexer's — has NO Update button and COMMITS ON CHANGE: `TaskListRenderer.handleControlChange` patches the row the moment the value moves. The classic notifications page (`notifications.js`, symbol `_priorityCell`) paints the same class name beside a `.task-priority-update` button that stays disabled until the value differs from `data-original`, and patches only on the click.
>
> ⚠️ SO A GUARD WRITTEN AGAINST ONE SAYS NOTHING ABOUT THE OTHER, and it will not look wrong: the selector matches in both, the test goes green, and the renderer you meant was never exercised. Name the renderer in the test, not just the class.

Confirmed at `render/TaskListRenderer.ts:555-562`: a `change` on `.task-priority-select` goes straight to `patchTask`. There is therefore **no pending priority edit in the multiplexer to lose** — the edit is already on the wire before the next poll can land.

**Contract decision** (María 🌸's recommendation, for **Mr. Radio 🦉** — the build owner — to ratify or overrule):

- The category **stays in the spec and stays in the capture module**, guarded by a feature-detect on `data-original` — absent attribute means nothing is pending, so the sweep captures nothing and costs one query. The day the mux grows an Update button (or any commit-on-click control), the rule is already written and already tested.
- The capture and restore code is written exactly as legacy's, including the "no matching option → skip" guard, because that guard is about the OPTION LIST drifting (P0–P3 widened to P0–P5 at `b4cdf47e`, per `render/templates/taskRowControls.ts:163-165`), not about the button.
- Any test touching this **names the renderer, not the class** — the tree already carries a guard test for exactly this confusion (`src/tests/unit/notifications_js/two_renderers_one_class_name.test.ts`, cited at `taskRowControls.ts:160`).

**Explicitly out of scope**: the in-flight optimistic patch. `commitMutation` (`render/TaskListRenderer.ts:910-922`) holds a de-dupe key and a `restoreState()` rollback across the await; a poll landing mid-flight is that mechanism's problem, not this one's. A builder who folds the two together will produce a rollback that fights a restore.

## §5 — The absent-node rule

**A row the fresh data no longer contains is left gone. Deliberately.** Verbatim (`notifications.js:13327-13332`):

> ⚠️ A ROW THAT IS GONE IS LEFT GONE, DELIBERATELY. If the poll returns a board without that row — somebody else closed it — its saved text has nowhere to go and re-creating the row to hold it would be worse than losing it. Restoration is best-effort by construction; the property being kept is that a repaint does not destroy work on rows that are STILL THERE.

Mechanically this is not a branch anywhere. Every restore step already ends in "no element → `continue`": verbs `:13347`, priorities `:13364`, inputs `:13371`, stripes (the renderer's own no-match no-op), disclosure `:13381`, focus `:13392`. The `Ensures` block states it as a guarantee (`:13336`): "a control that no longer exists is skipped, never a throw."

**What this means for the multiplexer, and it is more than it means for legacy.** The mux has more ways for a row to be absent than "somebody closed it":

- `renderPinned` (`render/TaskListRenderer.ts:427-437`) repaints the whole pane as ONE row. Every other row's captured state has nowhere to go and is correctly dropped.
- `renderUnreachable` (`:470-489`) repaints from `lastGoodTasks`, a snapshot that may predate the row.
- The Epic Board and Task List apply the same open-row filter (`render/EpicBoardRenderer.ts:236`, `render/TaskListRenderer.ts:386`) — a row that transitions to a terminal status disappears from both.

None of these change the rule. **The rule is not "restore everything"; it is "destroy nothing that is still on screen."** A builder tempted to re-create a missing row to hold its text is building a board that disagrees with the server, which is the failure mode `EpicBoardRenderer.ts:225-228` already refuses for the count ("Zeroing it would ASSERT there are no epics").

## §6 — The expiry rule for persisted state

### What the source actually does

**At SAVE, expired entries are filtered out** (`notifications.js:21327-21336`):

```js
const now = Date.now();
for ( const [ id, state ] of this.actionRequiredNotifications.entries() ) {
    if ( state.isExpired || state.isResponded ) continue;
    if ( state.isActive && state.expiresAt && state.expiresAt <= now ) continue;
    // pending notifications (expiresAt is null) are always saved
```

**At RESTORE, nothing is checked.** `restoreActionRequiredState` (`:21378-21440`) reads `now = Date.now()` at `:21386` and then **never uses it**. Every restored entry is written into the Map with `isExpired: false` hardcoded (`:21410`), whatever its `expiresAt` says. A prompt saved 3 seconds before its deadline and restored an hour later comes back looking live.

That is the gap. Nothing in the source settles it.

### 🔴 María 🌸's recommendation — **Mr. Radio 🦉** to ratify or overrule

**Filter at BOTH ends, and make the restore-time filter the authoritative one.**

Rule, stated so a builder can implement it without a second decision:

1. An entry with `expiresAt === null` (**pending** — queued but never activated) is **never** dropped on expiry grounds. It has not started its clock. This matches save-time behaviour exactly (`:21336`) and is not a judgment call.
2. An entry with a numeric `expiresAt` is **dropped at restore** when `expiresAt <= now - SKEW_GRACE_MS`.
3. `SKEW_GRACE_MS = 5000`. The grace is on the DROP side: an entry is discarded only once it is expired by more than the grace, so skew and timer coarseness can only ever make the client keep a prompt slightly too long, never discard a live one.
4. `serverExpiryEstimate` (saved at `:21351`, restored at `:21415`) is **never** used for the drop decision — display only. See the skew reasoning below.
5. Save-time filtering stays. It is not redundant: it keeps the payload from growing without bound across a long session, and it is the only filter that runs when the page is closed cleanly and never reopened.

**Why restore-time is the authoritative end.** The save-time filter is only as fresh as the last save. The whole point of the key is to survive a reload, and the interval between the last save and the next load is unbounded — a closed laptop, a browser restart, a tab restored from a session three days old. A filter that runs only at save is a filter that answers a question nobody asked. Restoring a dead prompt is not a cosmetic defect either: it re-renders an Action Required card whose server-side deadline has passed, so the operator answers a question the server has already given up on, and the answer is refused — which is Rick's dead-button shape again, in a different pane.

**Clock skew, specifically.**

- `expiresAt` is written by the same browser clock that will read it (`Date.now()` at save, `Date.now()` at restore). On the normal path — same device, same session, a reload — there is **no cross-clock comparison at all** and the skew question does not arise.
- It arises in three real cases: (a) the system clock is corrected or steps for DST/NTP between save and restore; (b) the device suspends and resumes, where monotonic and wall clocks disagree; (c) the value was ever derived from a server timestamp. Cases (a) and (b) are exactly what the 5 s grace covers, and both are small-and-bounded in the direction that matters (a clock that jumps FORWARD makes a live prompt look expired — the grace absorbs a small jump; a large one is indistinguishable from real expiry and dropping is then correct).
- Case (c) is why `serverExpiryEstimate` is excluded. It is the one field in the payload that came from a different machine, so comparing it to a local `Date.now()` compares two clocks that have never been reconciled. Legacy stores it and restores it but does not decide anything with it, and this rule keeps it that way.

**Where it lands in the multiplexer.** `stores/ActionRequiredStore.ts` — it already owns the per-entry countdown (`:433`, a 1 s `tick` per entry) and already injects `setIntervalFn` (`:179`, `:210`, `:226`), so the drop is unit-drivable with a fake clock and a fake timer. Do **not** put it in a renderer: a renderer-side filter would leave a dead entry in the store's own model, where the tick would keep counting it.

## §7 — Mechanism per lost-state surface, and the test tier that can drive it

Three mechanisms, not one. A builder handed "preserve operator state" will reach for capture/restore for all of it, and two of these cannot be fixed that way.

| # | Surface | Mechanism | Why that one | Test tier that can drive it |
|---|---|---|---|---|
| 1 | Typed inputs (reason, chase date, triage date, batch reason) | **capture/restore** | The value lives only in the markup being replaced. | **Unit, poll-driven.** Inject `setIntervalFn` into `TaskListStore` / `HoldingAreaStore`; type, fire the tick, assert the value survived. |
| 2 | Chosen verb | **capture/restore** | Same, plus it gates the date field's existence (§3 step 1). | Unit, poll-driven. Assert the date box exists after restore, not just the select's value. |
| 3 | Pending priority edit | **capture/restore** (slot vacant today — §4) | Same. | Unit, poll-driven — **naming the renderer**, per `taskRowControls.ts:160`. |
| 4 | Shown refusal stripe | **capture/restore** | The stripe is painted, not modelled; nothing outside the DOM remembers it. | Unit, poll-driven: drive a real refusal through the renderer, tick, assert the text is still there. |
| 5 | Disclosed row | **capture/restore** | Transient per-session UI state. **Not** persist-to-storage — see the note below. | Unit, poll-driven. |
| 6 | Focus + caret | **capture/restore** | Same assignment destroys it. | Unit, poll-driven, **with a caveat** — see below. |
| 7 | Batch in-flight guard / batch report | **neither — already state outside the DOM** | `HoldingAreaRenderer.ts:172-179` keeps `batchesInFlight` as a `Set<string>` and `batchReports` as a `Map<string,string>` precisely so a repaint cannot erase them: "`disabled` is a property on an element this pane repaints… A set keyed by filer cannot be repainted away." | Unit, poll-driven — assert the tick does NOT re-enable the buttons. **Named here so a builder sweeping "lost state" does not re-implement it as a capture category.** |
| 8 | A click whose node is replaced mid-press | **defer the repaint** | Capture cannot help: the node itself is gone before mouseup, so the click reaches no handler. | Unit: dispatch `mousedown`, fire the poll tick, assert no repaint; dispatch `mouseup`, assert exactly one repaint, with the LATEST composite. |
| 9 | Action Required prompts across a reload | **persist to storage** | The document itself is gone; there is no markup to capture from. | Module-boundary unit (see below) — **a reload is not unit-reachable.** |

### Surface 8 in detail — the multiplexer has no equivalent at all

Legacy installs it in `_wireTaskListAccordion` (`:14274-14283`):

> A repaint landing BETWEEN a press and its release replaces the pressed node, and the click then reaches no handler at all — no request, no refusal, nothing. The window is only as long as a press (~100ms against a 60s poll, roughly one click in six hundred), which is too rare to explain any one report and not too rare to happen. Preserving state cannot help here: the node itself is gone. So hold the paint for the length of the press instead, and take it the moment it ends.

Three parts: `mousedown` sets `_taskListPressInFlight` (`:14280`); `mouseup`/`mouseleave`/`blur` all call `_releaseTaskListPress` (`:14281-14283`); the render entry point checks the flag and stashes the composite instead of painting (`:12085-12090`), and the release replays it exactly once (`:13216-13229` — "a held composite is rendered exactly once, then forgotten; a release with nothing held is a no-op").

**The multiplexer has none of this.** A grep for `mousedown` across `multiplexer/**/*.ts` returns only `render/ReadingPaneRenderer.ts:185,217` — the splitter drag. No press-in-flight flag, no held composite.

⚠️ **Scope question for Mr. Radio 🦉** (open question 4 at the foot of this document): legacy installs the guard on `#task-list-container` only. The Holding Area's batch buttons (`render/templates/holdingAreaTable.ts:66-75`) and the Epic Board's row controls have the same exposure and no guard in either card. Widening it is a decision, not a port.

### Surface 5 — why disclosure is NOT persisted

Two persisted accordion keys already exist (`lupin.taskList.collapsedOwners`, `lupin.epicBoard.groupState`) and they are a different axis: they persist a viewer's standing preference about GROUPS. Row disclosure is a momentary act on one row inside a working session. Persisting it would mean a page opened tomorrow shows twelve rows with their control forms hanging open, which is not a preference anyone expressed. Capture/restore across a repaint, discarded at reload. **This is my recommendation, and the source settles it only by silence — neither card persists it.**

### On the test tiers

**A reload is not unit-reachable, and no amount of harness makes it one.** What IS reachable is the module boundary: read and write functions driven against an injected backend, then a "write, construct a fresh reader, read" sequence — the closest a unit gets. The tree already has the shape to copy: `FinishedTasksRenderer` takes `storage?: Pick<Storage,"getItem"|"setItem"> | null` as a construction option, and its comment makes the point that matters here (`render/FinishedTasksRenderer.ts:83-91`):

> ⚠️ `null` IS AN ACCEPTED VALUE AND MEANS "NO PERSISTENCE", not "use the default". A host with no localStorage at all is a real state — the production default resolves to null there — so it is a value a caller can pass and a test can drive, rather than a branch only the browser reaches.

**A poll IS unit-reachable, in every relevant store.** All of them inject the timer: `stores/TaskListStore.ts:170,207,246`; `stores/HoldingAreaStore.ts:189,216,261`; `stores/TaskRequestStore.ts:80,104,142`; `stores/ActionRequiredStore.ts:179,226,433`; `stores/FinishedTasksStore.ts:66,89,159`; `stores/FleetStatusStore.ts:49,71,103`.

🔴 **And the poll tier is the whole point of this spec's test story.** Legacy's own post-mortem says why nothing caught the dead button (`:13246-13248`): "every test called the handler by name so no poll could run between them." The existing mux guard test `src/tests/unit/multiplexer/render/task_controls_survive_the_disclosure.test.ts` is the right idiom for everything else — it "DRIVES THE ASSEMBLED RENDERER, NOT A TEMPLATE" and asserts both that the control is present AND that activating it reaches the store — but it does not tick a clock. **Every test written against this contract must put a real poll tick between the operator's action and the assertion.** A test that types, calls restore by name, and asserts is testing the function; it is not testing the property.

**Focus and caret (surface 6) carry a tier caveat.** `document.activeElement` and `setSelectionRange` are DOM surfaces happy-dom implements only partly. The builder must **verify, not assume**, that a happy-dom unit test can observe a focus move and a selection range before writing the assertion; if it cannot, the browser tier is `multiplexer/testkit/accordionHarness.ts:176-202`, which mounts all three real renderers over fake stores in one page and is the natural home for a focus check. Do not write a unit assertion that passes because the environment returns a default.

## §8 — The persistence backend

### The four idioms in the tree

| Idiom | Key | Shape | Polarity |
|---|---|---|---|
| `shared/StorageService.ts` | `lupin:` **+ key** (`:16`, `:69`, `:104`) | JSON envelope `{ schemaVersion, payload, ts }`, version-checked on read (`:87-93`), corrupt payload emitted on the bus (`:82-93`), backend injected (`:33-39`) | n/a |
| `render/taskListCollapse.ts` | `lupin.taskList.collapsedOwners` (`:18`) | raw `globalThis.localStorage`, JSON **array**, `catch {}` on both ends (`:55-81`) | array of **COLLAPSED** keys |
| `render/epicBoardCollapse.ts` | `lupin.epicBoard.groupState` (`:27`) | raw `globalThis.localStorage`, JSON **map**, absent key = no choice made (`:74-103`) | map of key → **isEXPANDED** |
| `render/FinishedTasksRenderer.ts` + `render/finishedTasksModel.ts` | `lupin.finishedTasks.shownStatuses` (`finishedTasksModel.ts:86`) | injected `Pick<Storage,…> \| null` (`FinishedTasksRenderer.ts:83-91`), JSON array | array of **SHOWN** statuses (positive) |

The tree warns about the collision between idioms 2 and 3 in two places. `epicBoardCollapse.ts:12-18`:

> 🔴 THIS FILE HAS THE OPPOSITE POLARITY TO taskListCollapse.ts, DELIBERATELY. The task list persists an ARRAY of COLLAPSED owner keys; the epic board persists a MAP of group key -> isEXPANDED. Porting one from the other INVERTS a viewer's saved state and fails INVISIBLY — the surface still renders correctly, so a CSSOM-level parity tier cannot see it.

And `finishedTasksModel.ts:78-85`:

> ⚠️ AND THIS FILE SITS BESIDE TWO KEYS THAT DISAGREE WITH EACH OTHER — `lupin.taskList.collapsedOwners` is an ARRAY of COLLAPSED keys and `lupin.epicBoard.groupState` is a MAP of key -> isEXPANDED. Same feature, inverted sense, different container. Copying either one inverts a user's saved state and FAILS INVISIBLY, which is why the polarity is written here rather than left to be inferred from a neighbour.

### 🔴 María 🌸's recommendation — **Mr. Radio 🦉** to ratify or overrule

**Use `StorageService` for the new key, with `FinishedTasksRenderer`'s injected-`| null` option shape for the call site.** Five reasons:

1. **The tree's own rule already says so.** `StorageService.ts:2-5`: "DC2 resolution: StorageService owns ALL storage; no raw localStorage elsewhere in the multiplexer tree." The two collapse modules bypass it for a stated reason that does not apply here — they are a **verbatim parity contract** with the JS card (`taskListCollapse.ts:5-13`: "These three constants are the PARITY CONTRACT shared VERBATIM with the JS card"). A key the JS card does not have has no parity contract to honour, so it has no licence to bypass.
2. **Schema versioning is worth more here than for a collapse set.** A stale operator-state payload restored into a changed markup shape is a silently wrong restore — the worst failure class this whole document is about. `getJSON` rejects a version mismatch and emits a corrupt event (`:87-93`), turning a silent wrong restore into a clean drop plus a bus event.
3. **The envelope already carries a save timestamp.** `setJSON` writes `ts: Date.now()` (`:102`). §6's expiry rule needs a save-time stamp and would otherwise invent one.
4. **A corrupt payload becomes visible instead of being swallowed.** The three hand-rolled modules all `catch {}` and degrade to a default (`taskListCollapse.ts:62-65`, `epicBoardCollapse.ts:84-87`). Right for a collapse set. Wrong for operator state, where a swallowed parse failure looks exactly like "nothing was saved."
5. **Testability.** `StorageService` takes a `StorageBackend` (`:33-39`); wrap the call site in the `storage?: … | null` option shape so "no persistence" is a value a test can pass rather than a browser-only branch (`FinishedTasksRenderer.ts:83-91`).

### The key-prefix collision, precisely

`StorageService` prepends **`lupin:`** — a **colon** (`:16`, `:69`, `:104`) — and strips that same prefix in `keys()` (`:117-119`). The three hand-rolled keys use **`lupin.`** — a **dot**.

Two consequences, and neither is hypothetical:

- **Naming**: a new key must be passed to `StorageService` WITHOUT its own `lupin` segment, or it lands as `lupin:lupin.operatorState`. Recommended name: `operatorState` → stored as `lupin:operatorState`.
- **`keys()` is blind to the dot keys, permanently.** `StorageService.keys()` skips anything not starting with `lupin:` (`:117`). So any "clear all Lupin state" or "audit what we persist" sweep written against `keys()` silently misses `lupin.taskList.collapsedOwners`, `lupin.epicBoard.groupState` and `lupin.finishedTasks.shownStatuses` — three real keys holding three real user preferences. That is worth a comment at the new key's definition point, because the next person to write such a sweep will not check.

**And declare the polarity at the definition point**, in the manner of `finishedTasksModel.ts:70-85`, for whatever this ends up storing. The rule the tree has already paid for: polarity written where the constant is defined, never inferred from a neighbour.
