### 🔴 AND THE CONFTEST ALREADY TRIES TO DO THIS — IT IS TOO LATE, AND THAT IS THE REAL MECHANISM

`src/tests/integration/conftest.py:19-21` sets the same variable at module scope, under a comment
reading **"CRITICAL: Set config environment variable BEFORE any other imports"**. Measured under a
real pytest collection in a bare shell, with a plugin printing at `pytest_collection_finish`:

```
[PROBE] engine=postgresql+psycopg2://lupin_dev:***@localhost:5432/lupin_db_dev
[PROBE] database_module_was_already_imported=True
```

⇒ **The conftest's own fix does not take.** By the time that line runs, `cosa.rest.db.database` has
already been imported and its engine already built — pytest loads the **root** `src/conftest.py`
before any per-directory conftest, and the root conftest imports `cosa`. The env assignment is
before *this file's* other imports and after the ones that matter.

⇒ **So the variable has to be set before the interpreter starts**, which is exactly what the runner
does and what a hand-typed pytest does not. This is the same shape as the `sitecustomize` finding
recorded in CLAUDE.md the same evening: **an import that has already happened cannot be steered by
a later path or env change**, because the module object already exists.

⚠️ Stated to the limit of what was measured: the probe proves the module was imported and the engine
bound to dev by collection time. It does not identify *which* import pulled it in first, and this
document does not claim to.

## Verdict, first — ⚠️ SCOPED BY THE CORRECTION ABOVE

`src/tests/integration/test_task_reassign_parity_e2e.py` runs its transactional fixture against
**`lupin_db_dev` — the fleet's live task store** — *when the tier is started by hand rather than
through `run-integration-tests.sh`*. The suite's session-scoped guard, `verify_test_environment`,
confirms the **server** points at the test database and never looks at the **pytest process's own
engine**, which is what that test actually uses — so nothing catches the hand-run case.

**Nothing has leaked.** Verified against the live database with positive controls. The realistic
harm is a **false RED** under fleet concurrency, not a false green and not corruption.

⚠️ **This is a guard whose scope reads wider than it is** — the same shape this repo has now
recorded several times, arriving in the test-environment layer.

## The mechanism, measured in both directions

`txn_session` opens a connection, begins an **outer** transaction, and joins a `Session` to it with
`join_transaction_mode="create_savepoint"`. It monkeypatches the router's `get_db` so every handler
shares that one session; each handler-level `commit()` releases a SAVEPOINT rather than committing.
At teardown the outer transaction is rolled back.

Measured on `lupin_db_test` (empty), inside a rollback, with `:8000` verified IDLE first
(`venue_idle` exit 0) and the table confirmed back to `0` afterwards:

```
A_inside_same_txn    1 row     the test's own write, visible to itself
B_other_connection   0 rows    the SAME instant, from a second connection
after rollback       0 rows
```

That single probe pins **both** failure directions:

| condition | what happens | how it fails |
|---|---|---|
| **1 — misses rows it should see** | uncommitted writes are invisible to every other connection (**B=0 while A=1**) | anything bypassing the monkeypatched `get_db` — its own engine connection, a worker thread, the live server in another process — sees nothing the test seeded |
| **2 — sees rows it should not** | the transaction joins `db_module.engine`, which binds **dev** | an unscoped query returns rows the test never created |

> *Checks `/api/server-info` to confirm the hot-swap to Testing config has taken effect (database

Both statements are true simultaneously. The server is on the test database; the test is not. **The
guard is not wrong about what it checks — it checks a different process from the one under test.**

## The one test does NOT pass for the wrong reason

It is built against the hazard on purpose. It reads baselines first, comments *"may be >0 — both are
real personas"*, and every assertion is a **delta**:

```python
maria_pre    = _owed_count( client, OWNER_ACCENTED_DISPLAY )
mr_radio_pre = _owed_count( client, OWNER_PUNCTUATED_DISPLAY )
...
assert _owed_count( client, OWNER_ACCENTED_DISPLAY )   == maria_pre + 1
assert _owed_count( client, OWNER_PUNCTUATED_DISPLAY ) == mr_radio_pre + 1
```

That is correct handling, not an accident, and it is why this is hygiene rather than an incident.

### But the deltas are computed against a store the fleet writes to continuously

State of the two owners it uses, at the time of writing:

| owner | owed | total rows | rows moved in the previous hour |
|---|---|---|---|
| `maria` | 1 | 268 | — |
| `mr radio` | 8 | 544 | **2** |

Any seat creating, closing or reassigning a `maria` or `mr radio` row **between the baseline read
and the final assertion** breaks the arithmetic. Both are active personas; one of them is the
manager who commissioned this write-up, and he moved two rows during the hour it was measured.

🔴 **THE FAILURE DIRECTION IS A FALSE RED, NOT A FALSE GREEN — and that inverts the intuition.**
The natural worry about a test inheriting ambient rows is that it *passes* quietly and makes the
suite order-dependent. Here the delta arithmetic converts inherited rows into a **loud, flaky
failure that blames the reassign code for a peer's unrelated write.** Better than a silent pass,
and still wrong: it burns whoever next reads that red.

## It writes — and nothing has ever persisted

The test genuinely creates and patches a real row through the router. Checked against the live
database rather than trusting the fixture's docstring:

| leak probe (`lupin_db_dev`) | result |
|---|---|
| rows titled `%reassign parity probe%` | **0** |
| rows `created_by = 'clayton f04dfb67'` | **0** |
| `task_events` with that actor | **0** |

🔴 **Three zeros are worthless without controls**, so the same query shapes over the same columns:

| positive control | result |
|---|---|
| titles `LIKE '%LUPIN%'` | 590 |
| `created_by LIKE 'clayton%'` | 3 |
| events actor `LIKE '%clayton%'` | 6 |

The third pair is the sharp one: **clayton rows do exist** under other session hashes, and the
test's exact actor string appears nowhere. If a run had ever leaked, that string is what would be
sitting there.

**No non-transactional escape path either**: `src/cosa/rest/routers/tasks.py` contains **zero**
websocket, broadcast, notify, emit or outbound-HTTP calls; its only file access is a read. A
rollback protects only what goes through the database, so this mattered and was checked.

⚠️ **What this does NOT establish**: that it *cannot* leak — only that it never has. A rollback that
fails, or a future handler that adds a broadcast, would escape, and the guard that would catch it is
the same one already missing.

## Remedy — the fix is not in the test

The test is the well-behaved party here. Two candidates, both cheap; **neither is ruled, and this
document rules nothing**:

1. **Bind the fixture to the test database**, like the rest of the tier. Removes condition 2 at the
   source and makes the delta arithmetic unnecessary rather than merely sufficient.
2. **Widen the session guard to the in-process engine.** `verify_test_environment` already refuses
   to start a suite whose *server* is misconfigured; having it also assert
   `"lupin_db_test" in str( db_module.engine.url )` closes the gap for every future test, not just
   this one — and it is the mechanical control rather than a paragraph asking people to remember.

⇒ Preference, offered as a preference: **(2)**, because it fails loudly for the whole tier at
session start rather than fixing one call site. `clean_test_db` already carries exactly this
assertion for its own engine (`assert "lupin_db_test" in db_url`), so the pattern is established
in the codebase and would only be extended.
