## 1. Rick's instinct is measurably right, on the population that exists

The question embedding fails because it encodes **topic**. Two questions about multiplying two
numbers look alike whichever numbers they name. **The generated code does not have that problem: it
contains the operands.**

Measured, read-only, over the 21 snapshot pairs where **both** rows carry real code:

| | code similarity | question similarity |
|---|---|---|
| `"what is 17 times 23"` vs `"What is 17 × 23?"` — **the same question** | **100.00** | 79.54 |
| every other pair — all genuinely different questions | **≤ 68.90** | up to 67.11 |

**A 31-point empty gap on code, against 12.4 on question text.** And the synonymous pair is a
*perfect* 100.00 — identical questions generate identical code, so the comparison is exact rather
than approximate.

⚠️ **n = 1 on the SAME side.** One pair is a promising sign, not a validated signal. Everything below
is written so the first step is the one that would kill it cheaply.

## 2. 🔴 The blocker, stated before the design: the code does not exist yet

Two separate problems, and they are not the same problem.

### 2a. The corpus is 59% empty

`code` is `{}` on **10 of 17** rows, and those are exactly the 10 whose `code_embedding` is an
**all-zero vector** — perfectly correlated, measured both ways. A zero vector makes cosine distance
undefined, which is why a pairwise sweep returns `NaN`.

⇒ **The signal is absent for 59% of today's corpus, including Rick's own 2+2 case.** Whatever is
supposed to populate `code` is not populating it. **Why is unknown — observed, not investigated —
and it probably deserves its own row before any of this is built.**

### 2b. 🔴 The chicken-and-egg, which is the real design problem

**At lookup time you have a question and no code.** Code is a *product* of running the agent. So code
similarity cannot be a first-pass retrieval signal the way question similarity is — there is nothing
to compare the candidate against.

**Any design that ignores this does not work.** The options below differ mainly in how they answer it.

## 3. Three candidate designs, cheapest first

### Option 1 — compare the ROUTED COMMAND AND ARGS. No embedding at all.

The router already turns a question into a command plus arguments *before* an agent runs. Two
synonymous questions should produce the same command with the same args:

```
"what's 2 plus 2"          -> command=calculate  args={op: add, a: 2, b: 2}
"what is the sum of 2+2"   -> command=calculate  args={op: add, a: 2, b: 2}   IDENTICAL -> replay
"what is 2 plus 3"         -> command=calculate  args={op: add, a: 2, b: 3}   DIFFERENT -> route
```

| | |
|---|---|
| **Pro** | Exact, not approximate. No threshold at all, so no overlap to sit inside. Free — the router runs anyway. Directly separates the pairs that defeat the embedding, because the operands are *in the args*. |
| **Con** | Only works where the router produces structured args. Says nothing about free-form agent questions. |
| **Kill it cheaply by** | dumping routed command+args for the 40 labelled pairs and checking they agree on SAME and differ on DIFFERENT. **No code written.** |

⇒ **This is the cheapest thing to test and it may be the whole answer for the calculator-shaped
traffic in this corpus. It should be tested before anything is built.**

### Option 2 — two-stage: question embedding for recall, code embedding to confirm

Answers the chicken-and-egg by *generating* the code before deciding.

```
stage 1   question embedding, LOW threshold (~70) -> top-k candidates   [high recall, low precision]
stage 2   generate code for the new question
stage 3   compare that code's embedding to each candidate's stored code_embedding
stage 4   replay only on a high code match; otherwise run the agent
```

| | |
|---|---|
| **Pro** | Uses the embeddings Rick already has. The 31-point gap is exactly the margin a confirm stage wants. Turns a topical guess into a behavioural check. |
| **Con** | **You must generate code before you can decide to skip work** — which spends part of what caching saves. Needs stage 2 to be much cheaper than a full agent run, and that is unmeasured. Depends on §2a being fixed. |
| **Kill it cheaply by** | measuring what code generation alone costs against a full agent run. If it is not a large fraction cheaper, the option is dead and no code need be written. |

### Option 3 — normalize the numerals out, match the shape, compare the numbers separately

Not an embedding approach. Extract the literals, match on the templated remainder, then require the
literals to be equal.

```
"what is 17 times 23"  ->  shape "what is N times N"   literals [17, 23]
"what is 17 times 24"  ->  shape "what is N times N"   literals [17, 24]   -> literals differ -> route
```

| | |
|---|---|
| **Pro** | Attacks the failure directly — every wrong replay measured differs only in a numeral or a direction. Cheap, deterministic, explainable. |
| **Con** | Hand-written extraction is an enumeration standing in for a predicate; it will be right today and wrong the first time a unit or format is named differently. Does not address direction ("F to C" vs "C to F") without extra work. |

## 3a. 🔴 MEASURED AFTER THE FACT — the full signal sweep, and it corrects Option 1 above

Added 2026-09-08 ~22:40 EDT, same sha, same read-only DB. **§3's Option 1 was written as a
prediction. I went and measured it, and the stored half of it does not work.** Everything below is
`solution_snapshots` in `lupin_db_dev`, 17 rows, zero excluded.

| candidate signal | populated | does it discriminate? | verdict |
|---|---|---|---|
| `question_embedding` | 17/17 | **no** — the original finding | the incumbent; cannot separate |
| `question_normalized_embedding` | 17/17 | tracks the question score within ~1 pt (84.94 vs 84.85, 78.74 vs 79.54) | **no added power** |
| `question_gist` (string) | 17/17 | **no** — `"what is 2 plus 2"` vs `"what is the sum of 2 plus 2"` stay different | does not collapse paraphrases |
| `question_gist_embedding` | **0/17 — all-zero** | unmeasurable | **never populated** |
| `solution_gist_embedding` | **0/17 — all-zero** | unmeasurable | **never populated** |
| `solution_embedding` | 17/17 | 🔴 **actively dangerous — see below** | **do not use** |
| `routing_command` | 17/17 | **no** — 3 distinct values across 17 rows | **far too coarse alone** |
| **`code_embedding`** | **7/17** | ✅ **31-point gap** | the only one with measured discriminating power — **NOT usable as-is, see §3b** |

### 🔴 Option 1 is half-refuted: the command is useless, the args are not stored

`routing_command` takes **three values across all 17 rows** — `agent router go to calculator` (10),
`… to math` (6), `… to datetime` (1). **`"What's 2 plus 2?"` and `"How many miles is 10 kilometers?"`
share the same value.** So the *command* half of Option 1 has no discriminating power whatever.

⇒ **All of Option 1's power would have to come from the ARGS, and args are not stored on the
snapshot at all.** The option is not dead — it is **untested and now harder to test**, because the
comparison needs a live routing call rather than a column read. §3 called its separation "predicted,
not measured"; this is what measuring it did to the prediction.

### 🔴 `solution_embedding` scores 100.00 between questions with different answers

| pair | solution score | actual answers |
|---|---|---|
| `"what is 3 + 3?"` vs `"What's 2 plus 2?"` | **100.00** | **6 and 4** |
| `"what is 3 + 3?"` vs `"What's the sum of 2 plus 2?"` | **100.00** | **6 and 4** |

**Mechanism, measured rather than inferred**: `solution_summary` is the literal string **`"N/A"`** on
all three rows, so the column embeds a placeholder and any two such rows match perfectly. The real
answer lives in `answer` as `{'status': 'ok', 'result': 6, …}` — **the discriminating content is
present in the row and is not embedded by anything.**

⇒ **A signal that returns 100.00 for 3+3 against 2+2 would serve a wrong answer with maximum
confidence.** This is the most attractive-looking and worst-behaved column of the eight.

### 🔴 §3b — DISCRIMINATING POWER IS NOT USABILITY, AND THE 31-POINT GAP IS NOT A RECOMMENDATION

Mr. Radio 🦉's correction, 2026-09-08, and it is right. The sweep's verdict column originally read
*"the only one that works"* for `code_embedding`. **That welds two separate claims** and I had already
written down the fact that separates them, in §2b, without applying it to my own table.

| the claim | status |
|---|---|
| the code signal **separates** synonymous from different questions | ✅ **measured** — 31-point gap, n=1 |
| the code signal **can be used to decide a replay** | 🔴 **false as stated** — see §2b |

**The sequencing makes it impossible as a drop-in.** At lookup time there is a question and no code.
Code is a *product* of running the agent, so the score cannot be computed for the incoming question
without first doing a substantial part of the work the replay was meant to skip.

⇒ **Nothing in this document recommends `code_embedding` as the replay signal.** What the 31-point
gap establishes is narrower and still valuable: **the information that separates these questions is
present in the code and absent from the question text.** That is a finding about *where the signal
lives*, not a proposal for *when to read it*. Any design still has to answer §2b, and Options 1–3
differ mainly in how they try.

⚠️ **Do not quote the 31-point gap without the sequencing caveat attached.** On its own it reads as
"use code embeddings", which is the one conclusion this section exists to forbid.

### What this sweep does to the plan

**It strengthens Rick's steer rather than weakening it.** Of eight candidate signals, `code_embedding`
is the **only** one with measured discriminating power — and it is also the one with the worst
coverage. The ordering in §4 is unchanged in shape but its first item now has a different owner:
Option 1 needs a live routing call, so **fixing the empty columns is now the cheaper of the two
first steps.**

⚠️ **Two of six embedding columns are 100% unpopulated and a third is 59% unpopulated.** That is a
data-health finding in its own right and it is not this row's subject. It probably wants its own row
before anyone builds on any of these columns.

## 4. What I would do first, and why it is not building anything

1. **Test Option 1 on the existing 40 labelled pairs.** Read-only, no code, one afternoon. If routed
   command+args separates them, the expensive options may be unnecessary.
2. **Open a row for the empty `code` column** (§2a). Nothing that depends on code embeddings can be
   evaluated honestly while 59% of rows have none — and a green result measured on the 41% that do
   would be a population error of exactly the kind this investigation already tripped over once.
3. **Only then** price Option 2's stage-2 generation.

⇒ **Steps 1 and 2 are both cheap and both can kill work. That ordering is the plan's only real
claim.**

## 5. What this document does NOT establish

- **The code-embedding result is n = 1** on the synonymous side. It is a promising sign and nothing
  more.
- **No option here has been implemented or tested.** Option 1's separation is *predicted*, not
  measured — I did not dump a single routed command.
- **Why `code` is empty on 10 rows is unknown.** It might be a defect, a schema migration, or
  intended for those agent types. Not investigated.
- **No cost measurement exists** for stage-2 code generation versus a full agent run.
- Everything rests on a **17-row dev corpus**. `lupin_db_test` was never read, and no traffic sample
  was taken.
- The `code_embedding` column is populated by **`CodeRankEmbed`**, a different model from the prose
  encoder. I did not check whether stored code vectors and freshly-generated ones share a space —
  **and that exact assumption already failed once in this investigation**, with `embedding_cache`
  turning out to be a different space from `solution_snapshots`. **Verify it before trusting any
  cross-comparison.**

## 6. The one thing to carry away

The question embedding cannot separate these classes, and no threshold on it will. **The code, the
routed args, or the extracted literals all contain the operands that decide the answer — and that is
the property the current signal lacks.** Which of the three to use is an open question this document
does not close.
