# Does `51950988` REPAIR the erased stamps, or only prevent new ones?

**Row**: `8a4647b8` (split off the class-decision row `e9b78e51`) · **Author**: Clayton 😎
**Date**: 2026-08-30 · **Branch**: `wt-clayton-e9b78e51` off `1d7f4846`

## The verdict

**Both prior answers are right, about different questions — and only one of them tells five seats what to do.**

| Question | Answer |
|---|---|
| Does an erased seat repair itself while it sits there? | **No.** Nothing reaches an idle bridge. |
| Does it repair on its **next SessionStart**? | **Yes** — measured, and caused by the fix. |
| Is a `/clear` a SessionStart? | **Yes** — so is a restart. |
| Is a fleet remediation step owed? | **Only for a seat that can afford neither.** |

The commit message for `51950988` says *"it does NOT heal — the eight erased seats stay
erased until each restarts"*, and the runbook on `e9b78e51` says it **"REPAIRS NOTHING
already broken."** Neither is wrong. Both are narrower than they read: the fix sets the key
on `session_data` at Phase 4.6, which runs on **every** SessionStart, so any seat that
clears or restarts re-stamps itself with no command at all.

**"Repairs nothing" and "repairs itself at the next SessionStart" are both true. The second
is the one that is actionable.**

## Measured, not read

Four tests in `src/tests/unit/test_register_session_stamp_repair.py`, driving the **real**
`main()` in a redirected seam with the **real** `_spawn_listener` path live. Only the
subprocess is faked — patching `_spawn_listener` away is exactly what hid this defect from
the original stamp test, so a seam that skips it cannot answer anything on this row.

Running `main()` a second time against the same session id **is** the `/clear` and re-spin
path. That is why two runs is the right instrument and not a contrivance.

| Direction | Test | Result |
|---|---|---|
| PREVENT | a fresh SessionStart lands the stamp **and** `listener_pid` together | ✅ |
| REPAIR | a second SessionStart restamps an already-erased bridge | ✅ |
| NO PASSIVE REPAIR | an idle erased bridge is never repaired on its own | ✅ |
| CLASS DEFECT (`xfail(strict=True)`) | an on-disk-only key **survives** the next SessionStart | ⌛ xfail |
| CLASS CONTRAST | the stamp is the only key with a rescue | ✅ |

**Negative control**: reverting the one line `session_data[ MANAGER_FIGURE_BRIDGE_FIELD ] = _mf_implicit`
turns **all 4 red**; restoring it turns all 4 green, `grep -c MUTANT` = 0. So the repair is
attributable to the fix rather than to something else in the path.

⚠️ **One of the four passed vacuously on the first control run and I fixed it rather than
keeping the pass.** `test_an_idle_erased_bridge_is_never_repaired_on_its_own` asserted only
an *absence* — and an absence is what the un-fixed code produces too, so it stayed green
while its three siblings correctly went red. Adding `assert field in healthy` before the
erasure makes it discriminate. A test that cannot fail for the reason it names is not
evidence.

## Addendum — the class test is an `xfail(strict=True)`, not a green test asserting the bug

My first cut asserted the *defect* and passed. **Mr. Radio 🦉 called it a trap**: a green test
asserting a defect reads as **approved behaviour** to anyone who did not write it, and the
comment saying otherwise is not what a reader checks.

It now asserts the behaviour we **want** — that an on-disk-only key survives — under
`@pytest.mark.xfail( strict=True )` carrying row `e9b78e51` in the reason. Same signal, no trap.

**Measured that the mechanism actually fires**, rather than trusting the flag: applying option
(d) — the one-line rebind at `register_session.py:2061` — turns it into

```

every on-disk key main() does not carry...
```

Reverting returns it to **4 passed, 1 xfailed**, `grep -c SIMULATED` = 0.
