## 4. Verification — proving "looks exactly" and "behaves exactly"

**Eyeballing is not a receipt** (Rick). It does not have to be — most of this already exists.

### 4.1 What exists: the Layout-Parity Oracle

`src/rnd/v0.1.9/2026.06.19-multiplexer-layout-parity-methodology/` — three documents,
Rick-directed, June. Its README's framing is strikingly close to this morning's ask: *"test the
layout **without Rick's eyes**"*, *"removing your eyes is the design center, not an add-on."*

| Tier | Proves | Venue |
|---|---|---|
| 0 | CSS source identity | static, ms, `:7999`/unit |
| 1 | DOM contract conformance | browser, per-renderer |
| **2** | **Computed-style isomorphism** | **cross-renderer — the core proof** |
| 3 | Geometry isomorphism | cross-renderer |
| 4 | Pixel diff — **backstop, explicitly not the gate** | browser |

Live code, not a proposal: `static/html/parity-harness.html`,
`js/multiplexer/testkit/parityHarness.ts`, `testkit/parityFixture.ts`. A failure prints
`node + property + legacy-value + mux-value` — regression report and to-do list in one line.

⇒ **We do not invent a verification story. We aim the existing oracle at three more surfaces.**

### 4.2 🔴 The gap: the oracle covers "looks", not "behaves"

Measured across all three methodology documents:

| term | hits |
|---|---|
| `behavior` / `behaviour` | **0** |
| `click` | **0** |
| `keyboard` | **0** |
| `persist` / `localStorage` | **0** |
| `interact` · `event` · `state` | 3 · 1 · 3 (incidental) |

Its own scope statement: *"parity is equality of the CSSOM, measured."* All five tiers are static
or visual.

⇒ **Rick asked for both axes; the oracle answers one.** The methodology needs a **behaviour
tier** — interaction, persisted state, and the observable results of clicking things. That is new
work this plan calls for, and §7.2 is the worked example of what falls through the gap today.

### 4.3 The behaviour tier's contract — what it WILL and WILL NOT catch

María's requirement, and she is right that it matters: **an oracle's blind spots are part of its
contract**, and this one will be cited for months. Stating them up front is what stops a future
reader treating a green tier as proof of something it never measured.

**MUST ASSERT** — the tier is not done until these hold:

| # | Assertion | Why it is on the list |
|---|---|---|
| B1 | **Persisted state round-trips with the same SENSE** — write, reload, read back, compare semantics not bytes | §7.2. The polarity trap is invisible to every other tier |
| B2 | **Row identity across all three panes, cell-for-cell** | §7.3. Rick asked for it personally; it re-splits silently |
| B3 | Toggling a section collapses/expands and the choice survives a reload | the accordions' whole point |
| B4 | Disclosure widgets reveal the `ROW_SCHEMA` line-2/line-3 fields, in that split | §7.3, and it is a declared table, so it is checkable |
| B5 | Controls fire the same request with the same parameters from both clients | a button that looks right and calls the wrong door is "behaves exactly" failing |

**WILL NOT CATCH — say so plainly:**

- **Anything the fixture does not exercise.** A behaviour tier drives a scenario; behaviours outside it are unmeasured, not proven absent.
- **Timing, animation and transition feel.** "Feels the same" is not reduced to an assertion here and this plan does not claim it is.
- **Server-side divergence.** Both clients hitting the same endpoint agree by construction; a wrong endpoint is B5's job, a wrong *response* is nobody's.
- **Emergent visual composition.** That is Tier 4's pixel backstop, deliberately not a gate.
- **Whether the reproduced behaviour is CORRECT.** The tier proves the two clients **agree**. If the legacy behaviour is itself wrong, a perfect score reproduces the bug faithfully.

🔴 **HARD GATE, at María's instruction and worth the whole section: if the behaviour tier cannot
reproduce a PASS on the already-ported Fleet Status pair, THE TIER IS WRONG, NOT THE PORT.** A
known-good pair is the only way to check an instrument before trusting its verdict on the other
three; without it you cannot tell a real divergence from a broken oracle. Same trap as a clean run
that turns out to mean the patch never applied.

## 7. Risks

### 7.1 🔴 Divergence is a permanent property, not a transition cost

With no shared client code, **no compiler keeps the two implementations in step**. Every
behaviour, colour and table rule is maintained twice, forever, and nothing fails when they drift.
A direct consequence of D1; it does not end when the port lands. The behaviour tier (§4.2) is the
only control proposed.

### 7.2 🔴 The persistence polarity trap — the worked example of the §4.2 gap

Found by María, independently confirmed by Maya. Same feature, **opposite sense**:

```
lupin.taskList.collapsedOwners   JSON ARRAY of COLLAPSED owner keys
lupin.epicBoard.groupState       JSON MAP   of key -> isEXPANDED
```

Port one from the other and **you invert a user's saved state**. It fails **invisibly**: the
surface renders correctly and only the remembered state is backwards. **Tier 2 cannot see it** —
computed style is identical either way. This one example is the argument for §4.2.

### 7.3 Row-level identity is a behavioural requirement Rick asked for — and it survives D1

`notifications.js:13418` — `_renderEpicRow` is a thin wrapper returning
`this._renderRow( task, null, { rowClass: "epic-row" } )`. So **"no shared code" is true at the
section level and false at the row level today.**

⚠️ **THREE panes share it, not two** — Task List and **Holding Area** both via `_renderTaskRow`
(same wrapper, same `task-row` class), Epic Board via `_renderEpicRow`.

⚠️ **It is deliberate, with Rick's reason in the docstring** (Maya): *"moving between the epic board
and the task list meant re-parsing the layout."* Cell-for-cell identity is therefore a
**behavioural requirement**, and **it survives the reuse question being descoped** — D1 removes the
shared *mechanism*, not the *requirement*.

⇒ The TS side must reproduce that identity **without** the helper that provides it in JS: its own
single row renderer used by all three panes, or they drift cell by cell, gradually and unflagged.
**This is an assertion the behaviour tier must make** (§4.3), not a note for an implementer to
remember.

🔴 **THE FIELD SPLIT IS ALREADY DECLARED — María's item 4, ANSWERED.** `ROW_SCHEMA` at
`notifications.js:43` is the authoritative progressive-disclosure split (Maya):

```
line1 : [ "id", "title", "class", "status", "priority" ]
line2 : [ "blocked", "chase", "accountable", "filer", "project" ]
line3 : [ "detail", "actions" ]
```

with `ROW_FIELD_LABELS` immediately below supplying display names. The TS side reproduces **this
table**, not a paraphrase of it.

⚠️ **How I nearly got this section wrong, recorded because it is this repo's own documented trap.**
I grepped `_renderRow(`, found **two** callers, and would have written "two panes" — the holding
area reaches it through the `_renderTaskRow` wrapper, which my search could not see. Maya had read
the bodies. **A population chosen by grep is wrong by default**; the correction is hers.

⚠️ **These line numbers have already moved once** — `_renderEpicRow` was cited at `:13418` an hour
ago and sits at `:13440` at this sha, because the file is being edited live. **Anchor on the
symbol, never the number.**

## 8. Phasing

Ordering rationale: **establish the yardstick before building anything against it**, and prove the
pattern on the cheap surface before the expensive ones.

| Phase | Work | Why here |
|---|---|---|
| **0** | Resolve **D2** and **D3**; confirm **D4**. | All three change the shape of what follows. None is an engineering task. |
| **1** | **Extend the parity oracle with a behaviour tier** (§4.2). Validate it on Fleet Status. | The yardstick must exist and be demonstrated *before* judging new work. Fleet Status is the only surface with a known-good pair to validate against. |
| **2** | **Task List gap-closure.** Run the full oracle legacy↔mux; close what it reports. | Cheapest — both sides exist. Proves the tooling on a real gap before any build. |
| **3** | **Epic Board build.** Shares a data path and endpoint with the task list (Maya: `/api/tasks?limit=500&unscoped_audit=true&hide_parked=false&char_budget=0`, `shared/task-list-query.js:50`) and shares the row renderer per §7.3. | Cheaper of the two builds, and it follows the task list while that context is warm. |
| **4** | **Holding Area build**, carrying Room-for-N per D3. | Most expensive: independent data path, its own controls, and the only surface with an in-flight P0 against it. |

⚠️ **Phase 1 is not overhead and must not be cut.** Without it, phases 2–4 are judged by eye —
the thing Rick explicitly ruled out.
