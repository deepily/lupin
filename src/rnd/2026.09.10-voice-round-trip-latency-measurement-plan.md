## 1. Why this exists

Rick's question is whether the wait between finishing a spoken question and seeing the answer is worth a
design change. The first number we have (section 2) says the **server's transcription step is under half a
second** even for 30 s of speech. That does not settle the question, because it was taken on localhost with
clean audio. This plan measures the **whole round trip, leg by leg, on the real clients**, so the decision
rests on where the time actually goes.

## 4. The clock rule

**Subtract two timestamps only when the same clock produced both.**

- **Phone legs**: Dart `Stopwatch` (monotonic), one per question.
- **Browser legs**: `performance.now()` (monotonic), one page load.
- **Server legs**: `time.perf_counter_ns()` inside one process. The model server is a **different process** —
  the API side times the HTTP call to it as one span and does not subtract the model server's numbers from its own.
- **Never** subtract a phone or browser wall-clock time from a server wall-clock time. The clocks are not
  synchronised, and a skew of a few hundred ms is the same size as the thing being measured.
- **Crossing a machine boundary**: the server reports its own processing time in the HTTP response (a
  `Server-Timing` header), and the client derives
  `network_and_queueing = client_observed_request_ms − server_total_ms`. Both terms are single-clock durations,
  so their difference is legitimate even though the clocks differ.
- The one cross-clock quantity left is the **WebSocket answer arrival**. Time it on the client clock only, from
  the client's own `ask POST sent` mark to the client's own `answer event received` mark.

## 5. Timeline — the marks

A question's life, with the clock that stamps each mark:

| mark | where | clock | meaning |
|---|---|---|---|
| C0 | client | client | user ends the recording (tap 2 / mic off) |
| C1 | client | client | audio bytes ready to send (file closed / blob built; browser: base64 done) |
| C2 | client | client | upload request handed to the HTTP stack |
| S1 | API | server | handler entered, body read (`await file.read()` / `request.body()` returned) |
| S2 | API | server | temp file written |
| S3 | API | server | `provider.transcribe` returned (includes the model-server hop) |
| S4 | API | server | `insert_io_row` returned |
| S5 | API | server | response built — `Server-Timing` reports S1→S5 and its sub-spans |
| C3 | client | client | response received, transcript in hand |
| C4 | client | client | transcript painted on screen (next frame after setting state) |
| C5 | client | client | user presses send — **human review time C4→C5 is recorded but excluded from machine latency** |
| C6 | client | client | ask POST handed to the HTTP stack |
| C7 | client | client | ask HTTP response received (`status`, `job_id`, `timings_ms`) |
| C8 | client | client | answer event received on the WebSocket |
| C9 | client | client | first answer audio plays (if TTS is on) |

**Derived legs** (each one a single-clock difference, or a difference of two such differences):

| leg | formula | what it tells Rick |
|---|---|---|
| L1 encode | C1 − C0 | client-side cost of packaging the audio |
| L2 upload + transcribe, as seen | C3 − C2 | the wait he feels before the draft appears |
| L2a server processing | S5 − S1 (from `Server-Timing`) | of which: server work |
| L2b transcribe | S3 − S2 (from `Server-Timing`) | of which: speech-to-text, incl. model-server hop |
| L2c network + queueing | (C3 − C2) − (S5 − S1) | of which: the phone's or browser's link |
| L3 paint | C4 − C3 | draft on screen |
| **DRAFT WAIT** | **C4 − C0** | **what option C would shorten, and what option B hides** |
| L4 ask round trip | C7 − C6 | small JSON leg — the only leg B removes |
| L5 answer | C8 − C6 | ask to answer (dominated by the job itself, not voice) |
| L6 first audio | C9 − C8 | TTS start |
| **MACHINE TOTAL** | (C4 − C0) + (C9 − C6) | end to end, excluding his review time |

**Option B's saving, computed rather than argued:** B keeps L1, L2 and L5, and removes L3, L4 and the human
review gap. Report `L3 + L4` as B's machine saving. The review gap is a UX cost B imposes, not a latency B saves.

## 6. Pseudo-code

### 6.1 Server — `Server-Timing` on both transcribe doors (`speech.py`)

```python
# one helper, used by upload_and_transcribe_wav_file and upload_and_transcribe_mp3_file
class SpanTimer:
    def __init__( self ):
        self.t0    = time.perf_counter_ns()
        self.marks = {}
    def mark( self, name ):
        self.marks[ name ] = time.perf_counter_ns()
    def header( self ):
        # durations in ms between consecutive marks, plus the total — all one clock
        spans, prev = [], self.t0
        for name, t in self.marks.items():
            spans.append( f"{name};dur={( t - prev ) / 1e6:.1f}" )
            prev = t
        spans.append( f"total;dur={( prev - self.t0 ) / 1e6:.1f}" )
        return ", ".join( spans )

async def upload_and_transcribe_wav_file( file, ... ):
    st = SpanTimer()                                   # S1
    content   = await file.read();          st.mark( "read" )
    temp_file = save_upload_to_temp( ... ); st.mark( "save" )       # S2
    text      = provider.transcribe( ... ); st.mark( "stt" )        # S3
    io_tbl.insert_io_row( ... );            st.mark( "io" )         # S4
    response  = PlainTextResponse( text )                           # today returns the str
    response.headers[ "Server-Timing" ] = st.header()               # S5
    response.headers[ "X-Upload-Bytes" ] = str( len( content ) )
    return response
```

Notes:
- **CORS.** A browser can only read `Server-Timing` cross-origin if it is listed in `expose_headers`. The pages
  are same-origin on :7999 today, but check before trusting an empty value.
- **Return type.** The wav door returns a bare `str` that FastAPI JSON-encodes. Changing it to a Response
  must keep the phone's parsing identical, which needs a unit test pinning the body.
- **Gate.** Put the header behind an INI flag (`voice latency timing enabled`) so the measurement can be
  switched off without a deploy.

## 8. Decision rule

- **If DRAFT WAIT p90 < ~1.5 s** on phone-over-LTE at 30 s: A wins. There is nothing to build, and the row closes.
- **If DRAFT WAIT is large but L2c dominates it** (network, not transcription): no server change helps.
  - Consider recording at 16 kHz on the phone, which cuts the upload ~2.76×. It is a one-line client change
    that needs its own accuracy check.
  - Consider option C (return the draft early while the job starts), because B would still pay the same upload.
- **If L2b dominates** (transcription): look at model-server contention or GPU first, before any client design change.
- **L3 + L4** is the whole machine saving option B can offer. If it is small, B's cost (losing the review step Rick
  asked for on 09-04) is not bought back by latency.
