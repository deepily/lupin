## 1. Why this exists

Rick, answering the measured card ~22:55 EDT (recorded on row `9df9f1c2`):

> "What I'm more interested in is understanding the latency or time introduced by returning to the client …
> I know the transcription is fast. So you're going to need to figure out a way to coordinate and measure the
> round trip and then separate the amount of time it takes to finish the POST of the audio file."

So the question is not transcription (section 2 already says it is under half a second for 30 s). It is:
**of the time between the user finishing and the text being back in the client, how much is (a) pushing the
audio up, (b) the server's work, and (c) the trip back down to the client?**

(c) is what a design that never returns to the client would save. This plan splits those three, on the phone
and on the browser, without ever subtracting one machine's clock from another's (section 4). The core trick
is in section 5: **each side times its own half, and the return trip falls out as a difference of two
single-clock durations.**

## 4. The clock rule

**Subtract two timestamps only when the same clock produced both.**

- **Phone legs**: Dart `Stopwatch` (monotonic), one per question.
- **Browser legs**: `performance.now()` (monotonic), one page load.
- **Server legs**: `time.perf_counter_ns()` inside one process. The model server is a **different process** —
  the API side times the HTTP call to it as one span and does not subtract the model server's numbers from its own.
- **Never** subtract a phone or browser wall-clock time from a server wall-clock time. The clocks are not
  synchronised, and a skew of a few hundred ms is the same size as the thing being measured.
- **Crossing a machine boundary**: the server reports its own durations in the HTTP response (a
  `Server-Timing` header): how long the audio took to arrive **as the server saw it**, and how long it worked.
  The client subtracts those from the durations **it** saw. Every term is a single-clock duration, so the
  difference is legitimate even though the clocks differ.
- The one cross-clock quantity left is the **WebSocket answer arrival**. Time it on the client clock only, from
  the client's own `ask POST sent` mark to the client's own `answer event received` mark.

## 5. Timeline — the marks

A question's life, with the clock that stamps each mark:

| mark | where | clock | meaning |
|---|---|---|---|
| C0 | client | client | user ends the recording (tap 2 / mic off) |
| C1 | client | client | audio bytes ready to send (file closed / blob built; browser: base64 done) |
| C2 | client | client | upload request handed to the HTTP stack |
| C2u | client | client | client finished writing the audio body (browser: `xhr.upload.onload`; phone: Dio `onSendProgress` with sent == total) — ⚠️ early by whatever the OS socket buffer still holds, so it is a cross-check, not the upload figure |
| S0 | API (ASGI middleware) | server | first `http.request` message received — the first body bytes arrived |
| S1 | API (ASGI middleware) | server | the `http.request` message with `more_body=False` — **the POST of the audio has finished arriving** |
| S2 | API | server | temp file written |
| S3 | API | server | `provider.transcribe` returned (includes the model-server hop) |
| S4 | API | server | `insert_io_row` returned |
| S5 | API (ASGI middleware) | server | `http.response.start` about to be sent — the middleware writes `Server-Timing` here |
| C3a | client | client | response headers received — first byte back (browser: Resource Timing `responseStart` or XHR `readyState == 2`; phone: Dio `ResponseType.stream` arrival) |
| C3 | client | client | response body complete, transcript in hand |
| C4 | client | client | transcript painted on screen (next frame after setting state) |
| C5 | client | client | user presses send — **human review time C4→C5 is recorded but excluded from machine latency** |
| C6 | client | client | ask POST handed to the HTTP stack |
| C7 | client | client | ask HTTP response received (`status`, `job_id`, `timings_ms`) |
| C8 | client | client | answer event received on the WebSocket |
| C9 | client | client | first answer audio plays (if TTS is on) |

**Derived legs** (each one a single-clock difference, or a difference of two such differences):

| leg | formula | what it tells Rick |
|---|---|---|
| L1 encode | C1 − C0 | client-side cost of packaging the audio |
| L2 audio request, as the client saw it | C3 − C2 | the wait he feels before the draft appears |
| **L2u UPLOAD — the POST finishing** | **S1 − S0** (server clock, `Server-Timing: upload`) | **the audio arriving, measured where it lands**; cross-check with C2u − C2 on the client |
| L2s server work | S5 − S1 (`Server-Timing: srv`) | save + transcribe + I/O row |
| L2t transcribe | S3 − S2 (`Server-Timing: stt`) | of which: speech-to-text, incl. model-server hop |
| **L2n network the server never sees** | **(C3a − C2) − (S5 − S0)** | the first byte's trip up **plus** the response's trip down (plus TCP/TLS setup on a cold connection) — about one RTT |
| RTT | C_ping1 − C_ping0 for a `GET /health` sent on the same connection just before (server work ≈ 0) | splits L2n: up ≈ down ≈ RTT ÷ 2, stated as an assumption of symmetry |
| **L2r RETURN TRIP to the client** | **RTT ÷ 2 + (C3 − C3a)** | **what returning the text costs on the wire** — first byte down, plus the (tiny) body |
| L3 paint | C4 − C3 | draft on screen |
| **DRAFT WAIT** | **C4 − C0** | **what option C would shorten, and what option B hides** |
| L4 ask round trip | C7 − C6 | small JSON leg — the only leg B removes |
| L5 answer | C8 − C6 | ask to answer (dominated by the job itself, not voice) |
| L6 first audio | C9 − C8 | TTS start |
| **MACHINE TOTAL** | (C4 − C0) + (C9 − C6) | end to end, excluding his review time |

**The answer to Rick's question, computed rather than argued.** Returning to the client costs, in machine time:

    RETURN_COST = L2r (text back down) + L3 (paint) + L4 (the second POST's full round trip, C7 − C6)

A design that pushes the transcript straight into the ask flow keeps L1, L2u, L2s and the first byte's trip
up, and removes RETURN_COST. It also removes the human review gap C4 → C5, but that is a UX change rather than
a latency saving, and it is reported separately so it cannot inflate the number.

**Why the upload is timed on the server, not the client.** A client marks "upload done" when its last bytes
enter the OS socket buffer, which can be well before they leave the device on a slow uplink. The server's
S0 → S1 is when the bytes actually arrived. C2u is still recorded because a large gap between `C2u − C2` and
`S1 − S0` is itself a finding: a buffered uplink.

## 6. Pseudo-code

### 6.1 Server — `Server-Timing` on both transcribe doors

**Why a middleware and not just the handler.** The wav door takes `file: UploadFile = File(...)`, so FastAPI has
already read and parsed the whole multipart body **before the handler runs**. A timer started inside the handler
can never see the upload. Only the ASGI `receive` channel sees the body arrive, and only the `send` channel sees
the response leave. The mp3 door reads `await request.body()` inside the handler, but the middleware treats both
doors the same way.

```python
# src/lupin_app/voice_timing_middleware.py — pure ASGI, mounted only for the two transcribe paths
TIMED_PATHS = { "/api/upload-and-transcribe-wav", "/api/upload-and-transcribe-mp3" }

class VoiceTimingMiddleware:
    def __init__( self, app ): self.app = app

    async def __call__( self, scope, receive, send ):
        if scope[ "type" ] != "http" or scope[ "path" ] not in TIMED_PATHS or not timing_enabled():
            return await self.app( scope, receive, send )
        t = { "S0": None, "S1": None, "bytes": 0 }
        scope.setdefault( "state", {} )[ "voice_spans" ] = spans = {}   # the handler adds stt / save / io here

        async def timed_receive():
            msg = await receive()
            if msg[ "type" ] == "http.request":
                now = time.perf_counter_ns()
                if t[ "S0" ] is None: t[ "S0" ] = now                    # first body bytes arrived
                t[ "bytes" ] += len( msg.get( "body", b"" ) )
                if not msg.get( "more_body", False ): t[ "S1" ] = now    # the POST has finished arriving
            return msg

        async def timed_send( msg ):
            if msg[ "type" ] == "http.response.start":
                s5  = time.perf_counter_ns()                           # S5, same clock as S0 / S1
                hdr = [ f"upload;dur={ ( t['S1'] - t['S0'] ) / 1e6 :.1f}",
                        f"srv;dur={ ( s5 - t['S1'] ) / 1e6 :.1f}" ]
                hdr += [ f"{k};dur={v:.1f}" for k, v in spans.items() ]  # stt / save / io, from the handler
                msg[ "headers" ] = list( msg.get( "headers", [] ) ) + [
                    ( b"server-timing", ", ".join( hdr ).encode() ),
                    ( b"x-upload-bytes", str( t[ "bytes" ] ).encode() ) ]
            await send( msg )

        return await self.app( scope, timed_receive, timed_send )
```

⚠️ **Two things to check when building it.**
- Does Starlette's multipart parser consume `receive` **before** the handler, so that S1 lands before the handler
  runs? It should, but a test must prove it: a slow chunked upload must show `upload` growing while `stt`
  stays flat.
- The mp3 body is base64, about 1.33× the audio bytes. Report `x-upload-bytes`, not the audio size.

Inside the handlers, sub-spans only:

```python
def span( request, name, t_start ):
    # a duration on the server clock, written where the middleware will read it at http.response.start
    spans = request.scope.get( "state", {} ).get( "voice_spans" )
    if spans is not None: spans[ name ] = ( time.perf_counter_ns() - t_start ) / 1e6

async def upload_and_transcribe_wav_file( request: Request, file, ... ):   # add `request` to read scope state
    t = time.perf_counter_ns(); content   = await file.read();          span( request, "read", t )
    t = time.perf_counter_ns(); temp_file = save_upload_to_temp( ... ); span( request, "save", t )   # S2
    t = time.perf_counter_ns(); text      = provider.transcribe( ... ); span( request, "stt",  t )   # S3
    t = time.perf_counter_ns(); io_tbl.insert_io_row( ... );            span( request, "io",   t )   # S4
    return text                                                          # body and type unchanged
```

Notes:
- **Body unchanged.** The header rides on the middleware, so neither door's return value changes and the
  phone's and browser's parsing stay as they are. A unit test should pin both bodies byte for byte, with the flag on.
- **CORS.** A browser can only read `Server-Timing` cross-origin if it is listed in `expose_headers`. The pages
  are same-origin on :7999 today, but check before trusting an empty value.
- **Gate.** Put the header behind an INI flag (`voice latency timing enabled`) so the measurement can be
  switched off without a deploy.

| factor | levels |

**Report per cell**: n, median, p90, min, max for every leg in section 5. Also report upload bytes per

**Run window**: 10 AM – 1 PM EDT per the off-peak rule (the host is most likely up). Each spoken question
writes an `InputAndOutputTable` row and the ask enqueues a real job, so use short harmless questions ("what
time is it") to keep the job leg small and constant. Otherwise L5 measures the question rather than the voice path.

## 8. Decision rule

Rick's question is answered by one number per cell: **RETURN_COST p90** (L2r + L3 + L4).

- **If RETURN_COST p90 is small** next to the upload — say under ~300 ms on phone-over-LTE at 30 s —
  returning to the client is cheap. Keeping the review step costs almost nothing, and A stands.
- **If L2u (upload) dominates the wait**, no design about the return trip helps, because every option still
  sends the audio. Levers:
  - record at 16 kHz on the phone, which cuts the upload ~2.76× (a one-line client change that needs its own
    accuracy check);
  - on the browser, send binary instead of base64, which cuts ~25%.
- **If L2t (transcription) dominates**, look at model-server contention or GPU first.
- **If UPLINK_BUFFER is large**, the client's own "upload done" is fiction on that network, and any
  client-only timing the team has used before overstated how fast the upload is.
- The human review gap C4 → C5 is reported beside RETURN_COST, never inside it.
