## Issue #1 — TOCTOU Race on Lockfile Creation (Phase 1)
**Severity**: Medium-High  
**File**: `src/lupin_cli/claude_code/hooks/register_session.py`

### Problem

The current pattern has a check-then-act race:

```python
if os.path.exists(stable_lockfile):   # ← check
    ...
else:
    with open(stable_lockfile, "w") as f:  # ← act (non-atomic)
```

Between the `exists()` check and the `open('w')`, a second concurrent `SessionStart`
hook — the documented double-fire on `--continue` — can win the race and write first.
Both processes then overwrite each other. Since the stable ID is whichever UUID fires
first, two concurrent writes can produce different lockfile content.

### Fix

Use exclusive creation (`open('x')`), which is atomic on Linux (O_CREAT|O_EXCL):

```python
try:
    with open(stable_lockfile, 'x') as f:
        f.write(stable_session_id)
except FileExistsError:
    # Lost the race — read the winner's value
    with open(stable_lockfile) as f:
        stable_session_id = f.read().strip()
```

**Note**: This fix is a prerequisite for Phase 3 to be reliable. Without atomicity,
two concurrent hooks can produce a non-deterministic stable ID, making the
`accepted_ids` set non-deterministic as well.

## Issue #2 — OSError Fallback Logic is Semantically Wrong (Phase 1)
**Severity**: Medium  
**File**: `src/lupin_cli/claude_code/hooks/register_session.py`

### Problem

```python
except OSError:
    stable_session_id = session_id  # Fallback: treat as first start
```

This branch is only reached when the lockfile **exists** but cannot be read (corrupted
file, permission denied). That is not "first start" — it is a failed read on a subsequent
lifecycle event. Silently falling back to the new transient `session_id` (a brand-new
UUID) breaks the stability guarantee for the remainder of that session with no observable
signal to the operator.

### Fix

Log to stderr (hooks emit to stderr without polluting Claude's context), then attempt
to overwrite the corrupted lockfile with `session_id` and continue:

```python
except OSError as e:
    print(f"[register_session] WARNING: failed to read lockfile {stable_lockfile}: {e}",
          file=sys.stderr)
    stable_session_id = session_id
    try:
        with open(stable_lockfile, 'w') as f:
            f.write(stable_session_id)
    except OSError:
        pass  # Best-effort recovery
```

This establishes a new stable anchor rather than silently diverging.

## Issue #3 — PID Reuse Edge Case in Stale Cleanup (Phase 4)
**Severity**: Low-Medium  
**File**: `src/lupin_cli/claude_code/hooks/register_session.py`

### Problem

Linux PIDs cycle (max 4,194,304 by default, often 32,768 in practice). If Claude Code
dies hard (SIGKILL, OOM) and a new unrelated process is later assigned the same PID,
the stale cleanup logic as written cannot distinguish "this PID is a live CC instance"
from "this PID was recycled." It would skip purging a stale lockfile that belongs to
an unrelated process.

### Fix

Before purging any `cc-stable-<pid>.id` file, check whether the PID is still a live
Claude Code process:

```python
import re

def _is_live_cc_process(pid_str: str) -> bool:
    try:
        pid = int(pid_str)
        os.kill(pid, 0)   # signal 0 = existence check, no signal sent
        return True
    except (ProcessLookupError, ValueError):
        return False
    except PermissionError:
        return True  # Process exists but we can't signal it — don't purge

# In the cleanup loop:
match = re.match(r"cc-stable-(\d+)\.id", entry)
if match and not _is_live_cc_process(match.group(1)):
    os.remove(fpath)
```

## Issue #4 — `_cleanup_old_listener` Argument Naming Ambiguity (Phase 2)
**Severity**: Low (clarity)  
**File**: `src/lupin_cli/claude_code/hooks/register_session.py`

### Problem

```python
_cleanup_old_listener(old_data, session_id)
```

At this call site, `session_id` is the **new** transient UUID from the current
`SessionStart` event — not the old one. This is functionally correct if the intent is
"here is the new session so don't accidentally kill its listener," but the parameter
name creates confusion because the function is named `_cleanup_old_listener`, making a
reader expect the arguments to be old-context data.

### Fix

Rename the argument at the call site for clarity:

```python
_cleanup_old_listener(old_data, new_session_id=session_id)
```

Or if the function signature uses positional args, add an inline comment:

```python
_cleanup_old_listener(old_data, session_id)  # session_id = new transient UUID, keep its listener alive
```

## Issue #5 — Duplicate Hash in `accepted_ids` on First Start (Phase 3)
**Severity**: Minor (cosmetic)  
**File**: `src/lupin_cli/claude_code/hooks/register_session.py`

### Problem

On a fresh `source: "startup"`, `stable_session_id` and `session_id` are the same UUID
(set in the `else` branch of Phase 1). The `--accepted-ids` argument therefore passes:

```python
f"{stable_session_id[:8]},{session_id[:8]}"  # → "abc12345,abc12345"
```

The listener's `set()` absorbs the duplicate harmlessly, but the intent is non-obvious
to a future reader.

### Fix

No code change required. Add a comment:

```python
# On first start, stable_session_id == session_id, so this deduplicates to one entry.
# On subsequent lifecycle events (compact, clear), they diverge and both are needed.
cmd.extend(["--accepted-ids", f"{stable_session_id[:8]},{session_id[:8]}"])
```

## Advisory Note — Lockfile Accumulation Between CC Restarts

**Not a bug — informational.**

When a user exits Claude Code entirely and relaunches it, a new PID means a new
lockfile — correct behavior, new stable ID for the new CC instance. The old lockfile
(`cc-stable-<dead-pid>.id`) is only cleaned up on the *next* `SessionStart` hook that
triggers the purge loop.

In patterns where users launch CC, quit, and relaunch in rapid succession, `~/.claude/sessions/`
will accumulate one stale `.id` file per prior session until the next purge cycle. This
is benign but can surprise operators inspecting the directory. Consider documenting this
in the doc's Verification section so it is not mistaken for a cleanup bug during manual
E2E testing.
