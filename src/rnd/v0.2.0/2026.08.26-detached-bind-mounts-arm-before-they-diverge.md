# A bind mount detaches before it diverges, and the preflight only sees the second half

**Date**: 2026-08-26 · **Author**: Tiberius 👑 (author, under Mr. Radio 🦉) · **Row**: `554e5d3e`
**Status**: 🟡 **PROPOSAL — authorized, NOT IMPLEMENTED.** Design only; no code written.
**Subject**: `src/tests/smoke/test_container_preflight.py::test_single_file_binds_serve_the_CURRENT_host_file`

---

## 1. The verdict

`test_container_preflight.py` compares **content only**. It md5s the host file and the
container's copy of it and fails when they differ. That catches a mount after it has
already served something wrong, and never before.

But a single-file bind mount does not fail by changing content. It fails by **losing its
inode**, and the content divergence is a *later consequence* that only appears once
somebody edits the file. Between those two events the mount is broken and the test says
it is healthy.

**The fix is one extra comparison inside the loop that already runs.** The loop already
shells into the container per bind; asking for `stat -c %i` alongside `md5sum` costs one
more exec per file and turns a lagging indicator into a leading one.

---

## 2. Why detachment precedes divergence

A single-file bind is resolved to an **inode** at container *create* time. The kernel
holds that inode, not the path.

Git does not edit files in place. A checkout, a commit, a rebase, a `git stash pop` —
each writes a **new** file and renames it over the old name. New name, same path, **new
inode**. The container is still holding the old one.

From that moment:

- the container keeps serving the *old* content, happily, forever
- `docker inspect` still lists the mount — it is present, and it resolves
- the md5 check still **passes**, because nobody has changed what the file *says* yet
- the first person to edit that file gets a silent no-op inside the container

⚠️ **`docker restart` does not fix this and neither does a commit.** Only a container
*recreate* re-resolves a bind. This was measured tonight and is the correction worth
carrying forward — see §5.

Directory binds (`./src`, `./io`) are **immune**: the kernel resolves *through* the
directory on every open. That is precisely why a `conftest.py` edit lands and a
`pytest.ini` edit does not, in the same commit, in the same container.

## 4. The proposal

**FAIL on present damage. WARN on pending damage. Name the file either way.**

| state | condition | verdict | why |
|---|---|---|---|
| **DIVERGED** | content differs | **FAIL** | the container is serving something wrong *right now* |
| **ARMED** | inode differs, content matches | **WARN** | correct today; will silently stop being correct on the next edit |
| ok | inode and content both match | pass | |

Both lines name the file. The ARMED line should also name the commit that severed it —
§3a proves that is cheap to compute from the checksum the test already takes.

### 4b. What the text must say — the file, and the action

Both lines name the file **and** the action, in the message itself. A verdict that makes
the reader go looking for either one is a verdict that gets ignored at 8pm.

The remedy line must carry the correction from §5 verbatim, because the wrong instinct on
reading "stale" is to assume somebody's pending edit explains it and wait for the commit:

```
FAIL  2 of 15 file binds are DIVERGED in 'lupin-rest-test' — the container is serving
      different content than the repo has, and every mount-presence probe still passes:
        ./docker-compose.yml -> /var/lupin/docker-compose.yml   host=3cb96fed ctr=d75b005b
        ./pyproject.toml     -> /var/lupin/pyproject.toml       host=97d1d794 ctr=8368ed0c

      Do this, IN THIS ORDER:
        1. PYTHONPATH=src python3 -m cosa.rest.venue_idle --port 8000   # exit 0 = IDLE
        2. docker compose up -d --force-recreate lupin-rest-test

      Step 1 is not a formality. :8000 is monopolize-mode and a recreate KILLS whatever
      is running on it — paste step 2 alone at a live box and you have destroyed
      somebody's in-flight job to fix a mount that could have waited ten minutes.
      Exit 1 is BUSY and exit 2 is UNKNOWN; UNKNOWN IS NOT IDLE.

      NOT a restart, and NOT a commit. `docker restart` reuses the old inode, and
      A COMMIT NEVER REATTACHES A SEVERED MOUNT — it writes a new file the container
      cannot see. There is nothing to wait for.

WARN  1 of 15 file binds is ARMED in 'lupin-rest-test' — inode severed, content still
      matching, so it is correct right now and will go wrong SILENTLY on the next edit:
        ./docker-compose.cloud-gpu.yml   host inode 24414159  ctr inode 26893847

      Same one action clears it, along with every other armed bind — and the same
      idle check first, because an ARMED bind is by definition not urgent and is
      never worth killing a live job for:
        PYTHONPATH=src python3 -m cosa.rest.venue_idle --port 8000   # exit 0 = IDLE
        docker compose up -d --force-recreate lupin-rest-test
```

Three properties that matter more than the wording:

1. **The file is named on its own line**, not summarised as a count. "2 of 15 are stale"
   sends the reader hunting; the path does not.
2. **The action is a command to paste**, not a description of a class of action.
3. **The two wrong remedies are named and refused** — restart and commit — because both
   are what a reasonable person tries first, and both leave the mount exactly as broken
   while looking like they did something.
4. **The idle check ships INSIDE the remedy, as step 1 of it** — not as separate advice
   elsewhere. A remedy is pasted; anything not in the paste does not happen. `:8000` is
   monopolize-mode, so a bare recreate at a live box kills a running job to fix a mount
   that was not urgent. An ARMED warn especially: it is correct today, so it is never
   worth interrupting somebody's work for.

Keep `MISSING` (bind declared in compose, absent from the container) exactly as it is: it
is a third, distinct mode with a different cause, and the existing docstring is right that
conflating them sends a reader hunting an inode problem that is not there.

### 4a. The one-action clear is what makes the split affordable

A warn state that accumulates becomes noise, and noise is how this row started. This one
does not accumulate:

**One `docker compose up -d --force-recreate <svc>` re-resolves every bind at once.** The
warn list resets to zero in a single action regardless of how many files are on it. There
is no per-file remediation, no triage queue, no suppression list to maintain.

**Expected frequency, measured over the last 30 days:**

- **14 of 30 days** had a commit touching at least one of the 15 bind files → something
  arms roughly every other day
- concentration is lopsided, so the warnings come from a handful of busy files:
  `docker-compose.yml` 14 commits · `pyproject.toml` 7 · `pytest.ini` 6 ·
  `docker-compose.cloud-gpu.yml` 4 · `package.json` 2 · four files 1 each · **6 of 15
  never touched**
- steady state: a recreate every week or two, with a few names showing in between

⚠️ **The 12 currently-healthy binds are healthy only because nothing has committed them
since the container was created.** Each detaches on its next commit. That is the standing
hazard — it is a property of the mechanism, not of those files.

This is also why ARMED must **warn and not fail**: on a normal working day something is
almost always armed, and a hard failure would put this control back in the state row
`554e5d3e` was opened to fix — red so often that nobody reads it.

## 5. The worked example, and a correction

Executed 2026-08-26 on Mr. Radio's authorization, after verifying `:8000` idle
(`venue_idle --port 8000` → exit 0, every lane empty):

```
docker compose up -d --force-recreate lupin-rest-test
```

| | before | after |
|---|---|---|
| `docker-compose.yml` | DIVERGED | ok |
| `docker-compose.cloud-gpu.yml` | **ARMED** | ok |
| `pyproject.toml` | DIVERGED | ok |
| preflight | 1 failed / 6 passed / 1 skipped | **7 passed / 1 skipped** |
| container `fail_under` | **96** (line 248) | **98** (line 269) |

After: **all 15 mounts attached and matching — 0 DIVERGED, 0 ARMED.** Container and repo
both report `fail_under = 98`, with identical md5 `97d1d7945a22841391dffa936fe1b8e2`, so
the container is serving the *same* file rather than a coincidentally-equal one.

**One command took three findings to zero.** That is the clearing behaviour §4a leans on,
now demonstrated rather than argued.

### 🔴 The correction: waiting for a commit is never the remedy

I predicted that `docker-compose.yml` would clear on its own once Rio's edit was committed,
on the reasoning that its divergence was "explained by an uncommitted edit." **It did not
clear.** Both files were still DIVERGED after `f8354a85` landed.

The reason is this defect stated in one sentence: **a commit never reattaches a severed
mount — it writes a new file the container cannot see.** The uncommitted edit explained why
the *content* differed; it never explained why the container could not *follow*. Both were
standing defects and only the recreate cleared either.

Anyone triaging a stale bind should not wait for anything. There is nothing to wait for.

## 6. Scope, and what is NOT proposed

- **In scope**: one `stat -c %i` per bind inside the existing loop; a third result bucket;
  the ARMED warn line; naming the severing commit where it is cheap.
- **NOT proposed**: changing what `MISSING` does · changing the venue of this file (it is
  `:7999`-eligible — read-only, 2.66s, no monopoly) · any automatic recreate. The remedy
  stays a human action; this control's job is to say when it is needed.

### 6a. WARN delivery — settled, and one option is dead

**RECOMMENDED: a separate non-blocking probe**, not a warning attached to the passing
content check. The two verdicts have different lifetimes — a DIVERGED fail is acted on
today, an ARMED warn may stand for days — and a probe of its own can say so in its own
name, in its own result line, without the reader having to notice a warning riding on
something that passed.

🔴 **`print` inside a passing test is not an option — MEASURED, not assumed.** pytest
captures stdout and DISCARDS it on a pass, so under the `-q` the smoke runner uses, a
printed block from a green test reaches the operator zero times. A probe run against a
deliberately-passing test:

```
print( "PRINTED-FROM-A-PASSING-TEST" )      -> 0 occurrences in the -q output
warnings.warn( "WARNED-FROM-A-PASSING-TEST" ) -> 2 occurrences in the -q output
```

So an ARMED verdict delivered by `print` is invisible in exactly the run that matters,
which is the same class of failure this whole proposal is about: a control that reports
nothing and reads as healthy. `warnings.warn` does survive `-q` (it lands in the warnings
summary), so it is the viable in-test carrier if a separate probe is rejected — but the
separate probe is the recommendation.
