# A test's session id can take a live browser session's routing entry, and the browser is never told

**Status**: MEASURED — mechanism demonstrated, arithmetic computed, cross-user reach read from source.
**Date**: 2026-08-26 · **Row**: `554e5d3e` · **Author**: Tiberius 👑
**Origin**: María's open question after the DM-inbox defect — *"worth asking what else in this tier
synthesises a session id the same way."* This is the answer that came back from a different keyspace.

---

## 1. The verdict

`src/tests/websocket_smoke/infrastructure/test_utilities.py:120` generates WebSocket session ids by
drawing `"adjective noun"` from **10 adjectives × 10 nouns**. Real browser sessions are named the same
way, from **32 × 32** (`src/cosa/agents/two_word_id_generator.py`). The two word lists overlap, so a
test can draw a name a live browser session is already using — and on a collision the test's socket
**takes over that session's routing entry**.

Three things are true at once, and only the third is still guesswork:

| Claim | Status |
|---|---|
| A second connect on the same id replaces the first's routing entry, silently | **DEMONSTRATED** (§3) |
| The probability of that happening in a run | **COMPUTED** (§2) |
| That it has ever actually happened in the wild | **INFERRED** — not searched for, not forced |

## 2. The arithmetic

Real namespace 32 × 32 = **1,024**. Test namespace 10 × 10 = **100**. Shared: **7 of 10** adjectives
(`bold brave bright calm clever quick wise`) and **10 of 10** nouns — so **70 of the test's 100 ids
exist in the live namespace**.

- P(a given browser session's id is even *drawable* by the test) = 70/1024 = **6.84%**
- P(one draw hits one specific live session) = (70/1024)·(1/100) = **0.0684%**

P(≥1 collision) per run, over *up to* 52 draws (52 is the call-site count across 5 files — an upper
bound; not every site runs every time):

| Live browser sessions | P(≥1 collision) |
|---|---|
| 1 | 3.49% |
| 2 | 6.86% |
| 5 | 16.29% |
| 10 | 29.92% |

🔴 **The number that matters is the conditional one.** If a live session's name happens to be one of
the 70 overlapping combos — itself a 6.84% event — then a **single run has a 40.7% chance of colliding
with it**. The rarity lives entirely in the naming, not in the drawing. Once a session is named inside
the overlap, a collision is closer to a coin flip than to a fluke.

```python
R, T, overlap = 32*32, 10*10, 7*10
p1 = (overlap/R) * (1/T)                       # one draw vs one live session
per_run = lambda L: 1 - (1 - p1)**(52*L)       # L live browser sessions
conditional = 1 - (1 - 1/T)**52                # given the name IS in the overlap -> 0.407
```

## 3. The demonstration, and how to re-run it

Run on **two sockets the prober owns**, on an id verified unused first, so no live session was touched.

```
BASELINE          "wise owl" present = False
AFTER socket A    present=True   connected_at=01:14:52.092897
AFTER socket B    present=True   connected_at=01:14:52.703568   <- ENTRY REPLACED
                  socket A: still OPEN — never closed, never notified, no error
AFTER B CLOSES    present=False  <- entry DELETED
                  socket A: still OPEN — orphaned
```

**Method** (`:7999`, read-mostly, no persistent state, no notifications fired):

1. Log in at `POST /auth/login`, take `tokens.access_token`.
2. Read `GET /api/websocket-sessions` (JWT, read-only) and assert the chosen id is **absent** — pick a
   different one if not. This is the step that keeps the probe off a real session.
3. Open socket A to `ws://…/ws/queue/{id}`, send `{"type":"auth_request","token":…,"session_id":…,
   "subscribed_events":[…]}`, expect `auth_success`.
4. Re-read the sessions endpoint; note `connected_at`.
5. Open socket B to the **same** id, authenticate identically.
6. Re-read: the id is still present but `connected_at` has **moved** — B replaced A. A is still open.
7. Close B; re-read: the entry is **gone** while A is still open.

⇒ **An orphaned socket does not error — it goes quiet.** That is why this would never be reported as a
bug by whoever it happened to. The browser shows a connected socket and simply stops receiving.

## 4. Cross-user reach — the part that sets the blast radius

**The account is irrelevant to the collision.** `websocket_manager.py:170` writes
`self.active_connections[session_id] = websocket` into a **flat dict keyed by session id alone** —
there is no per-user namespace. The queue route (`routers/websocket.py`) validates only the id's
**format**, via `is_valid_session_id`; there is **no ownership check anywhere on the connect path**.

So the blast radius is not "the test account's own sessions" — it is **every browser session on the
box whose name is drawable**. An earlier write-up of mine framed this as a same-account hazard; that
was wrong and made the finding look smaller than it is.

⚠️ **Stated limit**: the displacement was demonstrated within one account. The cross-user reach is read
from source (flat dict + format-only validation), **not demonstrated** — that would mean displacing
somebody else's live socket, which is the thing this document exists to prevent.

`websocket enforce single session per user = False` (`src/conf/lupin-app.ini:1535`), so the *deliberate*
displacement branch in `connect()` never fires. This is not that feature working — it is the plain
dict assignment underneath it.

## 5. What was true at the time of measurement

At 01:14 the live two-word sessions were **`slow zebra`** and **`foolish goat`**. Neither adjective nor
noun is in the test's lists, so **neither was drawable and the risk at that moment was zero**.

That is a fact about that moment, **not a mitigation**. The next browser session redraws from all
1,024, and 6.84% of those draws land inside the test's reach.

## 6. Not proposed here

No fix is prescribed. The obvious candidates — disjoint word lists, a reserved test prefix, or an
ownership check on connect — differ in blast radius and in who owns them, and picking between them is
a decision, not a repair. This document is the measurement and the reproduction method.
