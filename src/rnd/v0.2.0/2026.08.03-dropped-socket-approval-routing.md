# Row 2c0aaa34 — Where does Rick's approval prompt go if his browser drops?

**Investigator**: Clayton 😎 · **Date**: 2026-08-03 · **Scope**: characterize only, NO behavior change (per brief).

## Verdict

**A dropped browser on Thursday produces a VISIBLE FAILURE, not a silent hang.** Rick's approval prompt is **never** rerouted to another operator (the operator fallback is service-account-only, and Rick is a real human). When his socket is down the ask fails offline → the job dead-letters with "Podcast generation failed" — recorded and visible, not an infinite stall.

**Caveat (the real stage risk):** the failure's *own* notification is also addressed to Rick's down socket, so he gets no live audible/TTS error on stage — he sees it only when he reconnects (job card → DEAD + `answer_conversational`). So: honest failure, but the *live* signal depends on reconnect.

## The code path (with receipts)

1. **Ask origin** — podcast Phase 4 review loop: `orchestrator.generate()` → `voice_io.present_choices(...)` (`cosa_interface.py:155`) → `AgentNotificationDispatcher.present_choices` (`agent_notification_dispatcher.py`).
2. **Who it's addressed to** — `_resolve_target_user()`: ContextVar `agent_dispatcher_target_user` > `self.target_user`, set by `job.py` to the **job's own `user_email`** (for Rick's live drive, that's Rick).
3. **Operator fallback** — `_resolve_routing()` (`agent_notification_dispatcher.py:208`): swaps the target to the operator **only if** `target_user.lower() in service_set`, where `service_set` = INI `voice gate service accounts` (Bug 10, 2026-04-15: service accounts have no WebSocket sessions). **Rick's email is not in that list → NO reroute.** Returns `(rick, False, rick)`.
4. **Delivery** — `_notify_user_sync(request)` → `POST /api/notify` (`notifications.py:688`). With **no `response_default`** (the podcast approval passes none): offline detection is **immediate** (`notifications.py:730`), it attempts a cross-user CC-listener fallback (`:999`), and absent that returns **503** for an offline user (`:751`, `:1083`).
5. **Dispatcher on 503 / no-answer** — every no-answer path **raises `VoiceGateTimeoutError`** (empty answers, `exit_code==2`, no response value, `ConnectionError`). It never returns a silent empty selection.
6. **Orchestrator handling** — the raise propagates OUT of the `while not script_approved` loop → `generate()`'s outer `except` → `state = FAILED`, `voice_io.notify("Podcast generation failed: …", urgent)`, `raise` → `job.py` sets `JobState.FAILED` + `answer_conversational="Podcast generation failed: …"` and re-raises into the agentic-pool Future → `_transition_to_dead`.

## Who the operator resolves to

INI `voice gate operator email` (a single human). It is used **only** for `service_set` targets — i.e. test/service accounts like `interactive.job.tester@…`. That is exactly the 12:49 incident: a *service account's* ask was rerouted to the operator (Rick). **The Thursday inversion is different**: Rick's own ask is not a service account, so this fallback does not apply to him.

## Visible failure vs silent hang — the answer

- **Visible.** A cleanly-dropped socket → immediate offline 503 → `VoiceGateTimeoutError` → job dead-letters with a reason. Not the 240s (`podcast script review timeout seconds`) timeout — that only applies if the socket is UP but Rick doesn't answer.
- **NOT a silent hang.** The review loop cannot spin forever on an offline socket: the dispatcher raises rather than returning an empty answer (an explicit anti-silent-fall-through guard, Bug 7 / 2026-04-15).

## Two residual risks worth a decision (NOT fixed here)

1. **The failure notice needs Rick's socket too.** The dead-letter is real, but the live "generation failed" TTS/notification targets the same offline user, so on stage Rick sees nothing until he reconnects. If the demo wants a *visible-on-stage* signal, that is a separate change (e.g. an operator-visible failure surface) — deliberately not made before the demo.
2. **Cross-user CC-listener fallback (`notifications.py:999`).** Before 503, an offline user's notify attempts delivery to a CC-listener session. If one is active, Rick's approval could surface *there* rather than 503. Worth naming; not a silent hang, but a "somewhere else" path. Recommend characterizing who that resolves to under demo conditions if we want certainty.

## Recommendation

No behavior change before Thursday — the characterized behavior does not silently stall the demo. If we want to harden the *stage experience* (so a dropped socket shows Rick something live), do it as a measured, post-characterization change, not on the eve of the presentation.
