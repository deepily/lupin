2. **There is a family of HANGING Node tests here.** Seat #2 measured `queue_transport.test.ts`

   **98 of the 119 test files are multiplexer tests**, the family the hangs were found in.
3. **77 of 119 `*.test.ts` files import happy-dom** — measured, not estimated. Quarantining
   `arg_interview.test.ts` therefore **does NOT disarm `npm test`**; 76 other happy-dom tests remain
   in the glob.
4. **The allocator is unidentified.** I looked in the test, the module, the runner flags, the
   dependency size, and the worktree. It is in none of them. **State this as unknown; do not let the
   next reader infer that "happy-dom is the cause" has been established. It has not.**

## Why the per-session ceiling does not save you

`a52d160c` (`MemoryMax=24G MemoryHigh=18G MemorySwapMax=0`) bounds **one runaway's RSS**. It does
**not** bound fleet-wide pressure:

- `systemd-oomd` fires on **PSI pressure against the whole `user@1001.service`**, so a scope sitting
  well under its own 24 GiB ceiling still dies.
- oomd kills **the worst cgroup at that moment — not necessarily the one that caused the pressure.**
  An innocent seat can be the one that goes.
- Our own `MemoryHigh=18G` produces exactly the *reclaim activity* oomd's criterion requires.

**What the ceiling did buy** is real and should not be dismissed: on 08-22 the whole
`tmux-server.service` unit was torn down and ~2 dozen sessions died together. On 08-23, **one scope
died and every other seat survived, twice.** It converts a fleet-wide collapse into a single-seat
one. That is worth having. It is not protection from being the seat.

## 🔴 A freeze taken during a mutation run banks the MUTANT — and `cmp` will not tell you

**This is the most transferable finding of the day, and it very nearly shipped a defect.**

Mr. Radio's Phase 0 freeze copied `arg-interview.js` out of the worktree faithfully. **What was in
the worktree was not the source — it was mutant P1 of the red pass.** The mutation script restores
the original after each mutant; it was SIGKILLed mid-run, so P1 stayed on disk and got banked as if
it were the work.

The mutation, recovered by diffing the banked copy against the original (found at transcript line
1219 and landed at `e5b0077a`):

```diff
 export function isAnswerable( result ) {
     if ( !result ) return false;
-    return result.path === "needs_input";
+    return result.path === "needs_input" && Boolean( result.pending_id ) && Boolean( result.answer );
 }
```

The banked version **drops both guards** — it calls an expired park answerable, which is precisely
what the test file's `expired()` and `submitRefusal()` fixtures exist to catch.

### The reasoning error, stated plainly because it was mine

I verified the four banked copies with `cmp` against the worktree, reported them byte-identical, and
used that to argue the files were safe to land by inspection. **The `cmp` was true. The inference was
not.** `cmp` proves a copy is FAITHFUL. It says nothing about whether the thing copied is CORRECT.

⇒ **A freeze proves provenance, never correctness.** Had this landed, we would have shipped a
function that answers unanswerable parks — and the only test that catches it is the one quarantined
for killing sessions.

### The rule that follows

**Before trusting any frozen artifact, establish what the process was DOING when it was frozen.** A
seat killed mid-run leaves its intermediate state on disk, and intermediate state is
indistinguishable from finished work by any file-comparison tool. The transcript is the tiebreaker —
it says what the file was *supposed* to be. Mr. Radio found the original there, not on disk.

**This generalizes past this incident**: every seat killed by oomd today was killed *mid-something*.
Any freeze taken from a killed seat's tree inherits that same doubt.

### 🔎 NEW CANDIDATE for the allocator — `vm.runInThisContext` on a 20,900-line string

Found while reading the runner, **not yet tested against the deaths**:

- **17 test files** call `vm.runInThisContext`, and **all 17 also load happy-dom** (measured).
- They test `notifications.js` by **slicing its ~20,900-line source into a string and executing it**
  in a VM context (see `reading_pane_scroll_anchor.test.ts:40`). c8 cannot instrument that — a
  `runInThisContext`'d string is not in the require/import graph — which is why the file reports 0/0.
- Compiling ~21k lines into a VM context **per test file**, on top of a registered DOM, is a
  plausible way to reach tens of gigabytes across a suite run.

⚠️ **This does NOT explain the two deaths.** The fatal file, `arg_interview`, uses **zero**
`runInThisContext` — measured, not assumed. So this is a candidate for *suite-level* pressure, and
the single-file kills remain unexplained. **Recorded as a lead, not a cause.**
