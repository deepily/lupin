# `<persona>.md` means two different things, and that is the whole defect

**Date**: 2026-08-24 · **Author**: Tiberius 👑 (`af3c8d44`) · **Manager**: Mr. Radio 🦉
**Origin**: three false stale-memento accusations inside one hour — Clayton, Tiberius, Pocholo
**Scope**: `io/mementos/` naming, and what a monitor can and cannot conclude from it

---

## Root cause

**The plain name `io/mementos/<persona>.md` is a POINTER for some seats and the RECORD itself for
others.** Nothing in the filename says which, so a reader — human or monitor — cannot tell what kind
of file it just opened without reading line 1.

Measured tonight across 471 files in `io/mementos/`:

| shape | count |
|---|---|
| `<name>-<hash8>.md` (session snapshots) | 185 |
| descriptive / dated names | 174 |
| `<name>-legacy-<timestamp>.md` (archives) | 80 |
| plain `<name>.md` | 32 |

Of the plain per-persona files, **10 are pointers and 6 are records**:

- **pointer**: `arnold` `cheech` `chloe` `krishna` `mr-radio` `rachel` `rescued-mr-radio`
  `rescued-tiberius` `rio` `tiffany`
- **record**: `clayton` `john` `maya` `pocholo` `sam` `tiberius`

**The convention already exists and is already machine-readable.** A pointer opens like this:

```
<!-- MEMENTO POINTER — NOT THE RECORD. Safe to overwrite; it destroys nothing. -->
<!-- current: io/mementos/rio-89430bcc.md -->
<!-- mirror:  /home/rruiz/.claude/mementos/lupin/io/mementos/rio-89430bcc.md -->
<!-- regenerate: python3 $PLANNING_IS_PROMPTING_ROOT/workflow/scripts/memento_io.py regenerate-pointer --persona <p> --slot <io|root|tmp> -->
<!-- memento-record: persona=rio session_id=89430bcc written_at=2026-08-24T21:21:15-04:00 slot=io -->
```

That `memento-record:` line is exactly what a monitor needs: **persona, session, write time, slot.**
Six seats do not have it. The generator that writes it — `memento_io.py regenerate-pointer` — exists
and works.

**What I measured on top of that, and it makes the failure deterministic rather than occasional.**

⚠️ **This section was first written from READING the resolver, and it was wrong in both mechanism and

that the resolver *skips* headerless files — is false: `_memento_candidates` says outright that a

files are **demoted, not excluded**: a header's `written_at` puts a candidate in tier 1, and mtime-only
files sit in tier 0 beneath every tier-1 file **regardless of date**. Step 2 then returns the first
persona match in that order, so the outcome matches "skipped" while the mechanism does not.

### Row `a18bfec9`'s premise holds — so the record was never meant to sit at the plain path

Read at Mr. Radio's instruction before proposing anything further. The row (minted 2026-07-21 from
Tiffany's finding, now `done`) establishes the canonical shape: `memento_io.py write --slot io`
produces **record + out-of-repo mirror + pointer in one call**, and she verified peer slots already
matched it — `cheech.md` → `cheech-666a0ad7.md`, `clayton.md` → `clayton-b419346e.md`,
`rio.md` → `rio-ca9035af.md`, `rachel.md` → `rachel-df2cc55d.md`. She fixed her own case by
**promoting** `tiffany.md` to `tiffany-7341227d.md` with mirror and pointer.

**So the premise holds, and it means my earlier proposal was wrong in kind, not just in name.** Adding
a header to the record sitting at `io/mementos/<persona>.md` would entrench exactly the shape the row
calls a defect. The record belongs at `<persona>-<sid>.md`; the plain path is the pointer's.

**But "the fix belongs in the pointer file" needs one correction, and it is measurable.** A three-tree
control, same resolver, same legacy sibling present in each:

| tree | plain path holds | promoted record present | resolver returns |
|---|---|---|---|
| **X** — today's live shape | headerless record | no | `tiberius-legacy-2026.08.21-214351.md` |
| **Y** — the fix as phrased | a proper pointer | **no** | `tiberius-legacy-2026.08.21-214351.md` — **unchanged** |
| **Z** — promotion | a proper pointer | `tiberius-cb30ffac.md`, header on line 1 | **`tiberius-cb30ffac.md`** |

**Y is the negative control, and it fails.** Writing a correct pointer and nothing else leaves
resolution exactly where it was, because the resolver never reads a pointer's `current:` line and a
pointer's line 1 does not match the header marker. **What fixes resolution is the PROMOTION — the
headered record at `<persona>-<sid>.md`. The pointer is a by-product of the same call, not the
mechanism.**

That distinction matters operationally: a remedy described as "regenerate the pointer" can be carried
out in full, verify as done, and change nothing a booting seat sees. Row `a18bfec9`'s own item 3 asks
for exactly this shape of check — *"whether the assertion can still pass with the guarded thing
removed."* Y is that check, and it is why the remedy has to be named as promotion.

⚠️ **Carried from `a18bfec9`, unverified by me**: the row records that `stamp_header` writes
`Written: NOW` rather than authorship time. If so, a promoted record's header timestamp is the
promotion's clock, not the memento's — which would matter to any freshness check built on it, this
one included. I did not test it.

### The ranking is STRUCTURAL, and the pointer plays no part in it

Two code facts, both confirmed after Cheech pointed at the first:

1. `_memento_candidates` ends `sorted( out, key=lambda row: row[2], reverse=True )` over
   `( tier, stamp )` tuples. **Python compares tuples element-wise, so the tier decides absolutely and
   `written_at` is never compared across tiers.** The demotion is not a heuristic that a fresh enough
   timestamp could overcome — a tier-0 file cannot outrank a tier-1 file at any age. "By construction"
   is literal here, not a figure of speech.

2. `_header_of` reads **only the first line**, matching the marker `<!-- memento-record:`. Anything
   below line 1 is invisible to it.

**Fact 2 corrects something I wrote above.** I said Cheech resolves cleanly *because his plain file is
a pointer*. It is not the pointer that saves him. A pointer file's line 1 is
`<!-- MEMENTO POINTER — NOT THE RECORD… -->`, which does **not** match the marker — so `cheech.md` and
`rio.md` are **tier 0, exactly like a headerless record**:

| file | line 1 | tier |
|---|---|---|
| `rio.md` (pointer) | `<!-- MEMENTO POINTER — NOT THE RECORD… -->` | **0** |
| `rio-89430bcc.md` (record) | `<!-- memento-record: persona=rio … -->` | **1** |
| `cheech.md` (pointer) | `<!-- MEMENTO POINTER … -->` | **0** |
| `cheech-d7335dac.md` (record) | `<!-- memento-record: persona=cheech … -->` | **1** |
| `maya.md` (record at the plain name) | `<!-- memento-record: persona=maya … -->` | **1** |

**The resolver never follows a pointer's `current:` line.** Cheech and Rio resolve correctly because a
separate, current, line-1-headered RECORD file exists for them — written the same minute in Cheech's
case. The pointer is decorative as far as this code path is concerned.

⇒ **"Backfill the pointer" is the wrong name for the fix.** What a seat needs is a *record file whose
first line carries the header* — which is what `memento_io.py write` produces, pointer and mirror
included. A pointer alone would change nothing.

### The one-line fix, proven by mutation — and why I could not apply it

Same scratch tree, same resolver, one line added to the copy of `tiberius.md` and **nothing else
changed**:

| tree | resolver returns |
|---|---|
| **BEFORE** — current file headerless, one older headered sibling present | `tiberius-legacy-2026.08.21-214351.md` |
| **AFTER** — same tree, same files, `<!-- memento-record: … -->` prepended to the current file | **`tiberius.md`** |

One comment line moves the answer from a three-day-old archive to tonight's record. No resolver
change, no renaming, no deletion.

**I did not apply it to the live tree, and the reason is itself a finding.** Attempting to prepend
that header to `io/mementos/tiberius.md` is refused by an existing pre-write guard,
`memento_record_guard.py`, which reports that the path holds *"an UNMIRRORED RECORD … hand-written
straight to the slot"* and that a write there *"would be the last thing that ever happened to it."*
It names store row `a18bfec9` (2026-07-21), where the same shape went unnoticed for eight days, and
it names the sanctioned remedy — `memento_io.py migrate --apply`, which twins the content under an
immutable name and mirrors it, moving and deleting nothing.

**So the fleet already detects this exact state — at WRITE time.** A guard knows my memento is a
bare-slot record the moment anyone tries to touch it. Nothing checks the same condition at BOOT time,
which is where the false accusations are produced. The detector exists and is pointed at the wrong
moment.

Applying the remedy is left to whoever owns the memento tooling: `migrate` takes `--repo`, so the
obvious invocation reaches every seat's files, and five of the six affected mementos are not mine.

### Does "demote, not skip" lower the severity? Measured: no, and one file decides it

A controlled pair, run against a scratch tree holding a copy of `tiberius.md`:

| tree | resolver returns |
|---|---|
| **A** — the headerless current file, alone | **`tiberius.md`** — the current file |
| **B** — same tree, plus ONE older headered sibling | **`tiberius-legacy-2026.08.21-214351.md`** |

So demotion is real: with nothing to outrank it, a headerless file is returned normally. **And it is
also enough on its own — a single headered sibling of any age flips the answer.** Severity is
therefore unchanged for every seat that has one, which is five of the six. The wrong outcome is not
structural, it is *population-dependent*, and that cuts the other way too: **the staleness disappears
the moment a seat's current file carries the header**, with no resolver change at all.

⚠️ **Limit on this probe**: `_memento_dirs` also searches the two `~/.claude/mementos/` slots, and my
scratch tree could not exclude them. Result A therefore also depends on no tier-1 `tiberius` candidate
existing in the mirror — true today, and not something the probe controls for.

**Corrections this replaces**, listed rather than overwritten: my earlier table predicted
`clayton-4c07338d.md`, `john-d4eed929.md` and `sam-1fe241ea.md` from header inspection. All three are
wrong — those seats resolve into the mirror, not `io/mementos/`, and the staleness figures I gave

prediction; only the one built by running is a measurement.**

**Corrections to what I wrote above**: I called my case *"a real file wrongly chosen from 57
same-prefix variants"*, implying the resolver had no rule. It has a rule, the rule is sound, and the
current file fails it for a reason — the missing header. And the two "halves" I separated share one
cause after all: Pocholo's uppercase path was a symptom, not the mechanism.

## What the monitor is actually doing wrong

Independent of naming: **it reports a conclusion about a seat instead of what it observed.**

- *"You read `<stale file>`"* is a claim about a seat's behaviour, and the monitor never established
  it — it inspected a slot, not a read.
- *"Slot resolves to `pocholo-ef84b45b.md`, mtime 08-21 23:48, declared session `ef84b45b`"* is a
  fact. Any reader sees instantly that it says nothing about what the seat opened.

The cost is not the alarm. It is that each false alarm makes the accused seat reconstruct and prove
what it opened, and the manager verify that proof. **Three times in one hour tonight**, and my proof
was content-based — I quoted details that did not exist on 08-21 — because no timestamp was offered.

---

## Fixes, cheapest first

**1. Make the monitor report the observation, not the verdict.** No naming change needed, fixes the
false-accusation cost immediately, and is correct even if nothing else is done. It also turns the
`unparseable_present` alarm into something actionable: *"opened a record, expected a pointer."*

**2. Backfill the pointer for the six record-shaped seats** using the existing
`memento_io.py regenerate-pointer`. This makes `<persona>.md` mean ONE thing fleet-wide and gives
every seat the `memento-record:` line a monitor can read. ⚠️ It changes what a plain-name path
returns for those six seats — anything reading `tiberius.md` expecting the record would then get a
pointer, so the readers have to be checked first.

**3. Lowercase-normalise session hashes wherever paths are generated.** Narrow — closes the Pocholo
half only, and that half already fails safe.

**Do not** solve this by asking readers to remember which name is current. That is the rule that just
failed three times in an hour.
