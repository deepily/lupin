## 1. What we are doing, and why

Every vector in these tables gets **thrown away and rebuilt from the row's own logged text**, using the current model, at unit length.

Not a normalize. You caught why a normalize was wrong: about a quarter of the rows are OpenAI-era vectors. Scaling one of those to length 1 leaves it in **OpenAI's vector space** — still not comparable to a nomic vector. Cosine between two different spaces is noise whatever the lengths are. Measured cosine between the two producers **for the same text was 0.0079** — essentially at right angles. Regeneration puts everything in **one space at one scale**, which is a real fix rather than a cosmetic one.

**Nothing is on fire.** Cosine scoring already divides by both lengths, so every live comparison is correct today. This is consistency work, which is why it is P2.

## 3. The run, command by command

Four subcommands. **Three of them cannot write anything** — only `swap --apply` is destructive.

### Step 1 — `plan` (read-only)

```bash
python -m cosa.rest.db.embedding_regeneration plan
```

Prints, per table: row counts, how many already have a vector, and the norm histogram. This is where we confirm the era split still looks like what we measured (roughly 27% at norm 1.000, 73% at norm 17–24, nothing in between).

**What we are looking for**: a third population. We measured only two on a 4,000-row sample, but a sample cannot see a rare handful. If a third bucket appears here, we stop and look before filling anything.

### Step 2 — `fill` (writes to *shadow* columns only)

```bash
python -m cosa.rest.db.embedding_regeneration fill --limit=500        # dry-ish first pass
python -m cosa.rest.db.embedding_regeneration fill --apply
```

Regenerates each row's text into a **new shadow column** (`input_embedding_regen`, etc.). **The live columns are untouched at this step.** If the run dies halfway, the table is exactly as it was.

Every vector is validated as it lands — right dimension, finite numbers, norm ≈ 1.000. A vector that fails validation is rejected rather than written.

**It refuses to start** unless conditions are right. `should_proceed()` checks:
- **Queue busy?** It asks the live server, and refuses if work is running. **This is the real gate** — a clock cannot tell you the box is free; only the box can.
- **Off-peak?** Midnight–**11am** EDT. Widened from 9am on your instruction (2026-08-13) so a post-breakfast start is not refused by a courtesy check. `OFF_PEAK_END_HOUR` in the module; `is_off_peak()` takes it as an argument so a caller can tighten it without editing anything.
- `--force` overrides the clock. **It never overrides the busy check** — that is deliberate and tested.

**Checkpointing**: completed row ids are saved as it goes, so an interrupted run resumes rather than restarting.

### Step 3 — `verify` (read-only)

```bash
python -m cosa.rest.db.embedding_regeneration verify
```

Before anything swaps: row counts match, every shadow vector reads norm ≈ 1.000, and the count of bad norms is **zero**. Exit code 1 if not. **We do not swap on a verify that did not pass.**

### Step 4 — `swap` (the only destructive step)

```bash
python -m cosa.rest.db.embedding_regeneration swap            # prints what it would do
python -m cosa.rest.db.embedding_regeneration swap --apply    # does it
```

Points the live column at the regenerated data. **Everything before this point is additive.**

## 4. The defect we already hit, and what it taught

The first design batched 256 rows at a time. Measured on the live shared GPU:

| Batch | Result |
|---|---|
| 256 typical texts (17,850 chars total) | OK, 0.42s |
| 1 text @ 14,418 chars | OK, 0.31s |
| **8** of the longest texts (~100k chars) | **HTTP 500** |
| 256 of the longest texts | **HTTP 500** |

`torch.OutOfMemoryError` — GPU 0 has 23.65 GiB with **31 MiB free**, because two other processes hold 7.23 and 16.36 GiB. So it is **not** a per-text length cap and **not** a poison row: cost tracks *total text in the batch*, and a count-only bound lets the long tail through.

A fixed 256 works on the short head and dies on the tail — **mid-run, with a checkpoint full of successes**, which is the failure shape that looks like progress.

**Fixed in commit `0310aa05`**:
- Batches are bounded by a **character budget** (default 40,000 — above the measured-good 17,850, well under the ~100k failure point), not a row count.
- A single item larger than the budget is **isolated and attempted alone**, never dropped — alone is exactly where the 14,418-char row succeeded.
- A refused batch is **split in half and retried**, recursively, down to one row. A batch that 500s is not evidence any row is bad. **One row failing alone is a real reject** and is the recursion's floor, so it cannot retry forever.

**Red-proofed**: removing the budget bound reds exactly 6 of the tests — including one built directly from the batch that OOM'd live — while the rest stay green. That is what tells me those 6 gate the new behaviour and are not incidental.

### Correction — that measurement describes a machine that will not exist on the night

**My section above was written as if the crowded card were the run's condition. It is not, and you called that out.** You can unload the dev and test models before we start. Measured 2026-08-02: GPU 0 is a 24,564 MiB card holding the model server (7,416 MiB) and one vLLM (16,754 MiB). Unloading the vLLM takes free memory from **23 MiB to roughly 17 GiB** — so batches far larger than 256 are entirely reasonable.

**The code already handles this; only my write-up was stale.** `AdaptiveBudget` exists precisely for it, and its docstring names your point directly: the default *"was calibrated against a GPU with 23 MiB free… that number describes a machine that will not exist when the run happens."*

Rather than scale a budget from one crowded-card data point — which would be inventing the missing measurement — it **grows empirically**: start conservative, widen by 1.5× on every batch that lands, halve on any batch refused, bounded by a 5,000-char floor and a 2,000,000-char ceiling.

⇒ **On an emptied card the run climbs to a large batch on its own within the first minute or two, and no constant needs re-tuning by hand.** The 40,000 default is only ever the *starting* point. The ceiling is deliberate too: a freshly-emptied card should not tempt the run into one enormous batch whose failure would cost a long split-retry to unwind.

**What we should do on the night**: unload the models first, then watch the "final char budget" figure the fill prints per table. That number is the empirical ceiling of the actual hardware, and it is the measurement I currently do not have.

## 5. What I do NOT know, said plainly

**The database write side is unmeasured.** The ~16-minute figure I have quoted is **embedding time only**. The run also does ~289,000 UPDATE statements plus the reads, and that side is very likely the dominant term. I am not going to hand you a run-time estimate I cannot support.

Measuring it needs either a clone rehearsal or a bounded live fill into the shadow columns — and both sit behind this walkthrough, which is why they have not happened.

**Two smaller unknowns**:
- **Rows arriving mid-run.** The table grew 286,803 → 287,207 *during* a measurement, so it is actively written. New rows are already current-era, so they need no regeneration — but the run must tolerate them rather than assume a frozen snapshot.
- **Zero vectors.** The 4,000-row sample found none, which is not proof there are none. The guard stays, and it **counts** what it catches instead of skipping silently — if it fires more than trivially, that is its own finding.

**One environment gotcha**: the provider routes to `http://lupin-model-server:7998`, a Docker-internal name that does not resolve from the host. A host-side run needs `LUPIN_MODEL_SERVER_URL=http://localhost:7998` or it fails with a misleading "service may be down."

## 6. Rollback posture — RULED (Rick, 2026-08-13)

**Keep the shadow columns. No `pg_dump`.** In his words: *"Either we successfully write all of the shadow columns with the new embeddings or we don't. If we do, we throw out the original embeddings, pop the new ones into place and we get on with things. If it fails we drop the shadow column. I don't think it's that big of a deal."*

That is the correct read and it is simpler than the three-option menu I put in front of him. The job is **all-or-nothing on a column that does not yet matter**:

| Outcome | Action |
|---|---|
| Shadow columns fill and verify clean | Swap them in, drop the originals, move on |
| Anything fails | `DROP COLUMN` the shadow, table is untouched, try again |

The failure mode is a wasted GPU hour, not lost data — **the live columns are never written until the swap**, and every row keeps its source text so the work is repeatable.

I had flagged one counter-argument — *re-derivable is not restorable*, i.e. a dump also protects against the source text itself being wrong. It is a fair point in general and it does not apply here: we are not editing source text, and a bad regeneration is visible in `verify` before anything swaps. **Ruled, closed, no dump.**

## 7. What the run looks like on the night

**Timing**: after breakfast, ~10–11am. The window now closes at 11:00 EDT.

0. **You unload the dev and test models** to clear GPU 0. This is what lets the adaptive budget climb, and it is the single biggest lever on run time.
1. I confirm nothing is queued or running, and that we are inside the window.
2. `plan` — we read the histogram together and confirm two populations.
3. `fill --limit=500 --apply` — a bounded first pass into shadow columns. **This is where I finally measure the DB write side**, so we get a real run-time estimate before committing to the whole table.
4. We look at that number and decide whether to continue tonight or schedule it.
5. `fill --apply` — the full run, checkpointed and resumable.
6. `verify` — must pass clean, zero bad norms.
7. `swap --apply` — the one destructive command, with you present.

**Steps 1–5 are all reversible.** Step 6 is a gate. Step 7 is the only one that cannot be undone by re-running.
