The main working copy is the shared checkout every non-worktree session on this box operates in, so that single command moved the entire fleet onto a new branch at once. Nobody else had to agree, and nobody was asked.

Work then continued on **both** branches for the next five hours. As of this writing the new branch is **63 commits ahead** of the day-start branch, and the day-start branch is **30 commits ahead** of it.

**The good news, verified rather than assumed: the two reconcile cleanly.** Only 5 files were touched on both sides, and a `git merge-tree` dry run produces **zero conflict markers**. Nothing is lost and nothing needs hand-resolution.

## Why nobody caught it

The fork is invisible from inside a session. `git status` shows a branch name, and a branch name that looks like every other `wip-<row-id>-<slug>` in this repo's history reads as normal. No seat that arrived after 18:17 had any reason to suspect the branch was new, because arriving on a branch and being *put* on a branch look identical.

There is also no gate: nothing in the workflow requires authorization to cut a branch in the shared checkout, and the manager-autonomy envelope names push, prod, and destructive operations as gated — **branch creation is not on the list.** It fell through a genuine hole rather than past a rule someone broke.

## How it synchronizes

A single merge in either direction, no hand-resolution required. Recommended:

1. Merge the day-start branch **into** the new branch (or vice versa — the conflict count is zero either way), producing one history containing all 93 commits.
2. Run the merge gates in order on the result: unit → cosa tier → serial bridge guard → WebSocket smoke → E2E on `:8000` → integration on `:8000` as the final gate.
3. Decide **which branch name survives** — that is Rick's call, not a mechanical one. The day-start branch is the one the release line is named for (`v0.2.0`); the new branch is named after a single row that has long since been overtaken by five hours of unrelated work. My recommendation is that the day-start branch survives and the new one is merged into it and deleted, because a branch named for row `462b985c` no longer describes 3% of what it contains.
4. `origin` already has both. Whichever loses will need deleting there too — and push is Rick's.

**I have not executed any of this.** A merge of two branches carrying eleven seats' work, at midnight, on a shared tree, is exactly the class of action that should not happen while the person who owns the decision is asleep. The dry run is free and reversible; the merge is neither.

## What should change so it cannot recur

1. **Cutting a branch in the shared checkout should be a gated action**, in the same tier as push — because it is not a local act. One `checkout -b` in the main working copy relocates every session on the box, silently, with no announcement and no ack window. A worktree is the correct home for per-row work and already has one.
2. **A seat should verify its branch before its first commit of a session**, the same way it verifies staging scope. I did the second and skipped the first tonight.
3. **The bounce broadcast has an ack window; a branch change has nothing.** If a fleet-wide state change is worth warning about for a server restart, it is worth warning about for the branch every seat is committing to.
