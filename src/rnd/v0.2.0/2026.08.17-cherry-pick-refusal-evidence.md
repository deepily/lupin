## The two findings that matter

**1. The refusal is DETERMINISTIC, not a coin flip.** This is the row's central claim and the evidence contradicts it. The same target was refused in **three syntactically different forms inside 51 seconds** — a multi-line block with a leading `cd`, a `;`-compound, and a bare one-liner. Simplifying the command changed nothing. A non-deterministic classifier would not produce 3-for-3.

Note the direction, because it kills the obvious explanation: the **permitted** command was the *more* complex one (a pipe plus two `&&` clauses); the **refused** ones included the simplest possible form. So "a compound command tripped it" is refuted, not merely unsupported.

**2. The one thing that actually differs is the COMMIT BEING PICKED.**

| | permitted `45f16c8b` | refused `1f0f0bf0` |
|---|---|---|
| files | `src/cosa/training/xml_prompt_generator.py`, one unit test | `src/cosa/rest/routers/_scope_registry.py`, `src/cosa/rest/routers/docs_files.py`, two test files |
| what it is | ordinary source + test | **the doc viewer's credential-blocking and file-serving path** |

The permitted commit touches a prompt generator. The refused one modifies the code that decides whether a file containing credentials gets served to a browser.

## Ruled out

- **The ruleset did not change between the two.** There is **no `Bash(git cherry-pick:*)` rule at all** in any settings file — the project allowlist carries `git worktree/rev-list/merge-base/merge-tree/branch/tag/merge/reflog/for-each-ref/add/push/log/commit/rm/check-ignore/show/mv` and not `cherry-pick`. `.claude/settings.local.json` was last modified **2026-08-16 11:48**, over a day before either invocation; `~/.claude/settings.json` 2026-08-16 22:28. Nothing was edited tonight.
- **The static allowlist is not the mechanism.** The refusals name the *auto mode classifier*, which is a separate layer from the allowlist.
- **Command shape.** Refuted above — the simplest form was refused and the most complex was permitted.

## What I could NOT establish, and the one experiment that would

Two explanations remain consistent with everything above, and this evidence cannot separate them:

- **(a) target content** — the classifier reads what the commit touches, and rates a change to credential-blocking / file-serving code as needing a human.
- **(b) something changed between 19:45 and 19:56** — the three refusals are 51 seconds apart, so they cannot distinguish "this target is refused" from "everything is refused now".

I cannot see the classifier's inputs, so I am not guessing which. **The experiment is one command and settles it**: have Rachel attempt a cherry-pick of an *innocuous* commit now, then re-attempt `1f0f0bf0`.

| innocuous | `1f0f0bf0` | conclusion |
|---|---|---|
| permitted | refused | **(a)** — target content is the variable; the layer is deterministic and the row's "coin flip" framing should be withdrawn |
| refused | refused | **(b)** — something changed after 19:45; find what |
| permitted | permitted | the refusal was transient after all — the row's original claim, but on evidence nobody has yet produced |

I did not run it myself: cherry-picking into the shared working branch is not my lane, and the row assigned me the evidence half.

| hypothesis | killed by |

| the **time** drifted | 1 and 8 are permits either side of four refusals |
| the **commit content** is blocked | 6 and 8 — same commit, permitted |

**No single tested variable, and no pair, explains all eight.** The only combination not
yet cut is *flag + commit within one seat*, which run 6 already contradicts unless
`git -C <worktree>` is itself classified differently.

### The one cut nobody had made

Runs 1–8 never varied **only the commit while holding seat, session and flag fixed**.
That is `git cherry-pick -x 45f16c8b` from Rachel's seat, ordered 20:40.

- **permitted** → the conjunction rule holds: flag + that particular commit.
- **refused** → her session has drifted since 19:45 and the flag is doing the work.

⚠️ **Reading the result**: `45f16c8b` is already on the branch as `4df1db19`, so a permit
will be followed by git saying *"patch is empty"*. **The classifier answers before git
does** — an "empty" or "conflicted" outcome is still a PERMIT, and the two halves must be
reported separately or the permit will be misread as a failure.
