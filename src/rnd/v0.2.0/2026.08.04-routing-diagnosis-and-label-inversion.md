## The real story: the labels are inverted

The two podcast agents do the **opposite** of what their user-facing names say. Read from each job's constructor:

| Routing command | Actually does | Input | OLD label (wrong) |
|---|---|---|---|
| `podcast generator` | **Reads an existing document**, makes a podcast from it | `research_path` = "Path to the Deep Research markdown document" | "PodMaker (create a podcast **from a topic**)" |
| `research to podcast` | **Researches a topic from scratch**, then makes a podcast | `query` = "topic to investigate" | "Doc-to-Pod (**convert existing research** to podcast)" |

The name that sounds like "reads my document" (**Doc-to-Pod**) was attached to the agent that **researches from scratch**. The name that sounds like "from a topic" (**PodMaker**) was attached to the agent that **reads a file**. Both backwards.

This is not a cosmetic bug. Within one hour it misled the crew's own coordination — the manager relayed "steer to Doc-to-Pod" to two engineers before the measurement corrected it. A label that fools the people who read this code daily will fool a presenter reading it once. **A third engineer (Clayton) independently confirmed the file-reader is `podcast generator`, via its `fuzzy_file_match` handler.**

**Scope check**: the parallel *presentation* pair (`presentation generator` = `source_path`/document, `research to presentation` = `query`/topic) is **correctly** labeled. The inversion is isolated to the podcast pair.

## Step 1 classification (a / b / c)

- **(a) mis-classification — the operative cause.** The router sent a document request to the query/scratch agent.
- **(b) below-floor + confirm — NOT a factor.** The snapshot-cache confirm never fired (39.7%, below its 90% floor and ignored). A *separate* agentic-routing confirm did fire, but it isn't a confidence gate — every agentic command gets it.
- **(c) confirm-step wording — a real, compounding factor.** Because the labels are inverted, even a careful user who picks "Doc-to-Pod (convert existing research)" lands on the scratch agent. The confirm step, which exists to catch a routing miss, actively steers into it.

So the fix is two independent pieces: **correct the labels** (done — row fc8990c6) and **correct the classifier / training** (row fc4ccfe6, held for review).

### The rule (contradiction-tested — a CONJUNCTION of two conditions)

Two looser rules were each **refuted by a targeted probe**:
- "topic good, document bad" — refuted: "podcast **about** my KISS explainer" says "my explainer" yet routes to the file-reader 3/3.
- "the preposition is the whole lever (about wins)" — refuted: "podcast **about my document**" → `research to podcast` 3/3 (about, but no named topic).

The surviving rule needs **both** conditions:

| Utterance | "about/on" frame | Named topic (KISS) | Route |
|---|---|---|---|
| about **the KISS protocol** | ✓ | ✓ | `podcast generator` |
| **from** the KISS protocol | ✗ | ✓ | `research to podcast` |
| about **my document** | ✓ | ✗ | `research to podcast` |
| about **my KISS explainer** | ✓ | ✓ | `podcast generator` |

**`podcast generator` requires BOTH: an "about / on" frame AND a named topic (KISS) as the object.** Miss either — wrong preposition (`from` / `based on the contents of` / `turn … into`) OR no topic (bare "my document") — and it falls to the scratch agent. This also explains Rick's original sentence ("based on the contents of… document that discusses the KISS protocol"): it names KISS but fails the preposition, so it routes to scratch.

**Rehearsal rule for Rick:** *"Say 'a podcast ABOUT KISS' or 'ON KISS' — you must NAME KISS right after about/on. Don't say 'from', and don't say 'my document' without naming KISS."*

The "90% ask floor" (`similarity threshold confirmation`, line 503) belongs to the SNAPSHOT-CACHE gate — matching a request to a prior cached solution — a different mechanism entirely.
