## Verdict

Every claim in the predecessor doc holds when checked against the artifacts rather than
the report. One new receipt makes the case harder than "the names mislead": **the only VM
in the project has no GPU attached at all**, so the GPU-bearing compose file cannot run
on the one host we have — it is not merely unused, it is unrunnable here.

And the collision is not a matter of taste any more. Rick **ruled on 2026-07-01** that the
VM drops its L4 and the model server moves to Cloud Run. That ruling is applied. The file
named `cloud-test` is the configuration for a topology that was deliberately retired, kept
alive by parity tests, and the file named `cloud-gpu` is what we actually run.

### The receipt the predecessor did not have

```
$ gcloud compute instances describe lupin-host-test --zone us-central1-a \
      --format="yaml(name,machineType,guestAccelerators,status)"
machineType: .../machineTypes/e2-standard-8
name: lupin-host-test
status: RUNNING
```

**No `guestAccelerators` field — zero GPUs.** `e2-standard-8` is a CPU-only machine type.
So `docker-compose.cloud-test.yml`, which reserves `driver: nvidia`, would fail at `up` on
the only host in the project. The predecessor said it "runs on no host at all"; the
stronger and more useful statement is that **it cannot run on the host that exists**.

That is not an accident. Rick's Decision #4, 2026-07-01, in
`src/rnd/v0.1.9/2026.06.30-gpu-model-server-cloud-run-split/02-vm-downgrade-handoff.md`:

> **RULED (2026-07-01, Rick — Decision #4): `e2-standard-8`.** Keep the current 8 vCPU /
> 32 GB envelope, drop the L4. … Open question #1 "machine type" is CLOSED.

The measurement above shows the ruling was applied. **`cloud-test.yml` is the pre-migration
shape, not a fallback.**

**Distinct tracked code files touched by any of the seven: 35.**

**What "Docs" excludes and why.** `Docs` = `history/`, `todo-history/`, `src/rnd/`. Those
are dated records of what was true when written; renaming inside them would falsify the
record, so all **257** occurrences are deliberately out of scope for any rename. A doc
should be *annotated* at its head if it misleads, never silently rewritten.

`Code` includes the four `docker-compose.yml` bind-mount lines (l.184–185, 370–371) that
mount both cloud compose files read-only into the local dev/test containers so in-container
tests can read them, plus `src/conf/lupin-app.ini`, `src/conf/env-contract.tsv` (10 rows),
and `src/conf/vm-unversioned-manifest.tsv`.

### The transition hazard that constrains any new name

`cloud-gpu` and `cloud-test` are **substrings** of most candidate replacements. A rename to
`cloud-gpu-vm` leaves every `grep cloud-gpu` matching the new name, so a stale reference and
a migrated one are indistinguishable during the cutover. **Any accepted name must share no
substring with either old token**, checked mechanically, not by eye. That rules out the
otherwise-obvious `cloud-gpu-host` / `cloud-cpu-host` pair.

It also rules out the worst option: **reusing `cloud-gpu` for the GPU-bearing file.** Same
token, inverted meaning — every stale runbook, shell history and doc would silently mean
the other thing.

## 3. Three ways out

### Option A — retire `cloud-test.yml`, then one small rename (**recommended**)

The collision exists because two files describe two axes. Delete one file and the collision
goes with it: with no sibling, `cloud-gpu.yml` no longer implies a contrast, and it can be
renamed once — cleanly, or not at all.

- **Cost**: ~40 code sites, all in one direction. Remove the service from parity tests
  (`test_compose_service_parity.py`, `test_compose_nodeps_socket_guard.py`,
  `test_cloud_test_compose.py`, `test_axis_a_bind_mount_precondition.py`), drop 4 bind-mount
  lines from `docker-compose.yml`, retire `cloud-test.env.example`.
- **Why it is defensible**: it finishes a migration Rick already ruled on. The file is not a
  fallback — it is the shape we deliberately left, and the hardware to run it is gone.
- **What we give up**: the GPU-VM configuration, if we ever return to a G2 host. Mitigated
  by git history — the file is recoverable at any sha, and the R&D doc set describes it.
- ⚠️ **Not free**: the two files are maintained in lockstep (the last three commits touched
  both), so the parity tests are doing real work today. Retiring one means deciding those
  tests' second operand is gone, not merely deleting a file.

### Option B — keep both, rename both onto the same axis

Both names then answer one question ("does the VM itself have a GPU"), and `test` leaves the
topology names entirely — it belongs to the instance name, where it is already correct.

Subject to the substring rule in §2, e.g. `docker-compose.cloud-cpu.yml` (live) and
`docker-compose.cloud-l4.yml` (GPU VM), with containers and env files following. `cloud-cpu`
and `cloud-l4` share no substring with `cloud-gpu` or `cloud-test`.

- **Cost**: 169 code sites across 35 files, one coordinated commit, full unit + deploy test
  pass, plus head-notes on the affected runbooks.
- ⚠️ `cloud-cpu` vs `cloud-gpu` differ by one character. Grep-safe, easy to misread. If B is
  chosen, that pair should be reconsidered for legibility.

### Option C — rename nothing; state the inversion loudly where readers land

Head-block in both compose files and in `deploy-cloud-test.sh` naming what the file actually
holds. Cheapest; fixes the reader hazard; leaves the names wrong.

- Partly already done: `deploy-cloud-test.sh` has a venue guard (row `5f1532d1`) that aborts
  with an explanation, and `dctl_venue_present` documents the whole-line-exact match.

**Recommendation: A**, and it needs one answer from Rick — *are we ever bringing a GPU VM
back?* If no, A. If maybe, B. C only if neither is worth the change budget this cycle.

## 5. Adjacent findings — filed here, not fixed

1. **`cloud-test.env.example` is the only env example in the repo**, and it is for the venue
   nobody runs. It defines 6 keys and covers **2 of the 6** variables `cloud-gpu.yml`
   hard-requires via `${VAR:?}` (`CLOUD_SQL_CONNECTION_NAME`, `DB_PASSWORD`); it omits
   `LUPIN_BRIDGE_GID`, `LUPIN_HOST_SESSIONS_DIR`, `JWT_SECRET_KEY` and
   `LUPIN_MODEL_SERVER_URL`, and it carries `LUPIN_MODEL_SERVER_TAG`, which the live venue
   does not use. Mitigated by `src/conf/env-contract.tsv`, which **is** the authority and
   covers `cloud-gpu.env` properly — so this is a misleading second source, not a gap.
2. **`deploy-cloud-test.sh`'s two-axis routing has no other home.** The predecessor
   recommends not deleting it because `lupin-vm.sh deploy` implements only the code axis and
   nothing else writes down that a dependency change forces an image rebuild. Still true;
   Option A does not touch the script.
3. **The two compose files are maintained in lockstep** — the last three commits
   (`458d1730`, `e5a6a917`, `4c760cc0`) touched both, and they differ by **284 lines** after
   normalizing the venue token. That maintenance is being paid for an unrunnable config.
