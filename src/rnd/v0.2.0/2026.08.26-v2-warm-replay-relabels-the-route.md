## The verdict, in ten lines

1. **It is a DELIBERATE FALLBACK, not a phantom.** When the replay fails, `AskFlow._receptionist` really does build and run `ReceptionistAgent`; 115 of the 117 rows came back `status="done"` carrying a real receptionist answer, and they took a **median 2,466 ms** against **20 ms** for a successful replay. Something ran.
2. **The recording defect sits on top of it.** `_finish` is called with `command=self.RECEPTIONIST_COMMAND`, which **overwrites the command the router chose**. Correct behaviour, destructively recorded.
3. **It is a SHARED-EXIT-PATH defect, not a replay defect.** Every degrade door — unknown command, extract error, agent error, replay error — exits through the same `_receptionist` → `_finish` pair. In this artifact **212 of 300 warm rows** emit `agent router go to receptionist`: 117 replay_error + 94 unknown_command + 1 agent_error.
4. **WHY the replay fails is measured and single-cause for 108 of 117**: v2's write-back was not persisting the agent's generated code, so `SolutionSnapshot.run_code()` raised *"Cannot execute empty code list"* on replay. The discriminator is perfect — see §3.
5. **The row's "2 blame malformed XML" reading does not survive.** Those two error strings are the **receptionist's own** XML parse failure, not the replay's. At the artifact's era the replay path passed no `primary_error`, so the emitted `error` could only ever be the fallback's.
6. **The cause is already fixed at HEAD** — commit `94e03bc9`, 2026-08-21 18:50, ~5.5 h **after** this artifact was produced.
7. **The label defect is NOT fixed at HEAD.** The overwrite at `flow.py:1240` still stands, and it is reachable from four doors that have nothing to do with replay.
8. **Under the queued executor the RELABEL survives and only this artifact's TRIGGER for it disappears.** The overwrite is era-independent — `unknown_command` and `agent_error` keep producing it, and those account for 95 of the 212 relabels here. What goes away is the replay-shaped trigger: `QueuedExecutor.submit` never runs the replay, it returns `waiting`, and the flow treats that as success — so a dead snapshot is reported as `route_reason="exact_hit", cache_hit=True` and fails later off the HTTP response, where the eval cannot see it. That is worse, not better. (INFERRED from code; no queued warm run observed.)
9. **Nothing here is a routing regression.** The router's cold-pass decisions were fine; the warm pass overwrote them.
10. **No fix is proposed, no run scheduled.** The row is parked on Rick's precondition, and the confirming run is costed in §7 rather than launched. 🔴 **The blocker there is not machine time**: `terminal_waiting_ask` — the wrapper that would make a queued pass observe terminal outcomes — is written, documented and unit-tested, and **has no production call site**; `main()` passes `client.ask` raw to both passes. Run without it, a queued warm pass would report a *higher* cache-hit rate than the inline one, for exactly the rows that are broken.

## 2. The central question: fallback or recording defect? — **BOTH, and the fallback is real** (MEASURED + code-read)

`src/cosa/rest/v2/flow.py:1226-1240`:

```python
def _receptionist( self, trace, question, ctx, route_reason, primary_error=None ):
    if primary_error: trace.set( "primary_agent_error", primary_error )
    work    = Work( "receptionist", self._build_agent( self.receptionist_factory, question, ctx ), ... )
    outcome = self.executor.submit( work, trace )
    return self._finish( trace, "receptionist", route_reason, outcome, question, ctx,
                         command=self.RECEPTIONIST_COMMAND, primary_error=primary_error )
```

The fallback has a behavioural counterpart: a `ReceptionistAgent` is constructed and submitted, and its answer is what the user gets. Three independent confirmations from the artifact:

- **Latency.** Failed replays: median **2,466 ms** (p10 2,068 / p90 3,123). Successful replays: median **20 ms**, max 59 ms. Two orders of magnitude — that is an LLM call, not an error return.
- **Answers.** All 115 `done` rows carry a non-empty answer in the receptionist's own voice, e.g. *"I don't think so, I can't remember any specific reminder about a 'History quiz study' in Study or Homework."* That is `receptionist.txt`'s prescribed refusal wording (`src/conf/prompts/agents/receptionist.txt:24`).
- **Failure mode.** The 2 `failed` rows died of `Invalid XML format: no element found: line 9, column 13` on a payload beginning `<response>\n\t<thoughts>` — the exact shape `receptionist.txt:43-45` mandates. The agent ran and its output was truncated.

**The defect is the last argument.** `command=self.RECEPTIONIST_COMMAND` replaces the router's decision on the way out. The flow's own code comments already know this (`flow.py:1126-1128`, `1150`): *"`_receptionist` overwrites the caller's command with its own on the way out, so the emitted command cannot tell them apart either."* That comment was written about the deliberate-pick-vs-degrade conflation and fixed by adding `route_reason="user_picked_receptionist"`; the underlying overwrite was left in place.

So: **correct behaviour, destructively recorded.** The record loses the only evidence of what the router decided. Fixing the recording does not change any user-visible behaviour, and fixing the behaviour is not called for — the fallback is the right thing to do.

## 3. WHY the replay fails (MEASURED for 108 of 117; UNKNOWN for 9)

Cross-tabulating the **cold pass's** chosen command (i.e. which agent wrote the row) against the **warm pass's** outcome gives a clean split with no overlap:

| cold-pass writer command | warm `exact_hit` | warm `replay_error` |
|---|---:|---:|
| `agent router go to calculator` | **83** | 0 |
| `agent router go to todo` | 0 | **69** |
| `agent router go to math` | 0 | **34** |
| `agent router go to calendar` | 0 | **5** |
| `agent router go to receptionist` | 0 | **9** |

Every success was written by `CalculatorAgent`. Every failure was written by something else.

`src/cosa/memory/solution_snapshot.py:32`:

```python
CODELESS_AGENT_CLASSES = ( "CalculatorAgent", )
```

and `run_code()` at `:912-924`:

```python
if self.agent_class_name in CODELESS_AGENT_CLASSES:
    if self.answer: ... return self.code_response_dict     # served from the cached answer
...
if not self.code or all( line.strip() == "" for line in self.code ):
    raise ValueError( "Cannot execute empty code list — snapshot has no executable code" )
```

**`CalculatorAgent` is the only class that can be replayed from an answer alone.** Everything else needs the generated Python, and v2's write-back was not saving it. `src/cosa/rest/v2/executor.py:65-70` (added by the fix) states the mechanism verbatim:

> *v1's `SolutionSnapshot.create_from_agent` reads exactly these three keys off `prompt_response_dict`, and the v2 write-back read none of them — which is why every v2-written row had empty code and only `CalculatorAgent` snapshots could ever be replayed.*

That is **Rick's lead confirmed**: the failure is a runtime execution error inside the snapshot manager's `run_code()`, and the receptionist label is what the flow does about it.

**This is a genuine single cause for 108 of the 117 — not an over-attribution.** The claim rests on a discriminator that is perfect in both directions (83/83 and 108/108), on the class list being a one-element tuple, and on the raise site being the only place that string exists.

**The other 9 are UNKNOWN.** Their cold-pass rows carry `wrote_snapshot=False` and `route_reason="replay_error"` — the cold pass *also* degraded on them, meaning they matched **pre-existing rows already in the store**, not rows this run wrote. The artifact does not record `agent_class_name`, so the writer of those 9 rows cannot be identified from the file. Same symptom; cause not established. They may well be the same empty-code shape from an earlier v2 run, but that is a guess and is recorded as one.

### 3.1 Correcting the row: the two XML errors say nothing about the replay

Row `7e2125a7` reads *"2 blame malformed XML."* They do not.

At the artifact's era (`fbace5d2`), the replay branch read:

## 4. Under the queued executor: the label survives, the replay trigger does not (INFERRED, not measured)

**Two things are being asked at once and they have different answers.** The *relabel* is era-independent — it lives on the shared degrade exit, so every non-replay door keeps producing it (95 of the 212 here). The *replay-shaped trigger* is inline-only.

The artifact is INLINE-era: `22c85b5b` (2026-08-21 17:03) landed ~3.5 h after the run finished.

`src/cosa/rest/v2/executor.py:192-206` — `QueuedExecutor.submit`:

```python

    """Scope the job, push it, and answer waiting — every kind, no exceptions."""
    ...
    self.todo_queue.push( job )
```

**Every kind, no exceptions — including `replay`.** It never calls `run_code()`. And `flow.py:47`:

```python
SUCCESS_STATUSES = ( "done", "waiting" )
```

with the gate at `flow.py:237-248` taking the success branch on `waiting` and returning `_finish(..., "exact_hit", cache_hit=True)`.

Consequences, all inferred from these three code sites:

- The **specific symptom disappears**: an empty-code snapshot can no longer produce `replay_error` at flow time, so the 117 receptionist relabels would not appear in a queued warm pass.
- The **failure does not disappear**. It relocates to the queue consumer, after the HTTP response has already gone out saying `route_reason="exact_hit", cache_hit=True, status="waiting"`.
- **The instrument gets worse, not better.** Under inline, a dead snapshot produced a wrong-but-loud record. Under queued it produces a *confidently correct-looking* one — a reported cache hit for a replay that has not run and may be about to die. Row `7e2125a7` notes the 08-25 queued run never observed terminal outcomes at all; a queued warm pass measured only at the HTTP boundary would report **a higher cache-hit rate than the inline run** for exactly the rows that are broken.
- `QueuedExecutor` can still return `failed` — but only if the *push* throws, which is a queue defect, not a replay defect.

**This has not been run.** Confirming it needs a queued warm pass that observes terminal outcomes, on `:8000`, scheduled. Until then §4 is a code-reading, and the honest statement is: *the symptom is predicted absent and the underlying failure predicted invisible.*

### 7.6 The 9 UNKNOWNs are unresolvable — the replay records no identity for the row it replays

⚠️ **This corrects a line in an earlier draft of this doc**, which said the 9 could be settled with "a store query against the matched `snapshot_id`s." There are no matched snapshot ids to query.

**MEASURED at `d6163145`, across both artifacts:**

- `payload.snapshot_id` is **null on all 200 warm replay rows** — all 83 successes and all 117 failures. It is the *write-back* id, and a warm pass writes nothing back, so it is null by construction. It never names the row that was read.
- The day's trace file, `io/v2-flow/trace-2026-08-21.jsonl`, **joins cleanly** — 117 of 117 failures and 299 of 300 warm rows match by `trace_id` — and it does not carry the identity either. Its nearest field, `cache_candidate`, is a plain boolean (`flow.py:964`: `cache_candidate=lookup.best_candidate is not None`), and it reads `false` on all 117 failures **and on all 83 successes**.

So the replay path records the *similarity* of the match (100.0 on all 117) but never *which row* matched. A failed replay cannot be traced back to the snapshot that caused it from any recorded evidence.

The only remaining route is querying the live store by question text — which cannot establish what the store held on 2026-08-21, since eleven further eval runs have written to it since. **The 9 are therefore closed as unresolvable rather than left as owed work.**

This belongs to the same family as the defect the doc is about: the instrument records a confident number (`similarity: 100.0`) about an object it does not name.

**What was needed and was not captured** — one field would have settled all nine: **the `id_hash` of the snapshot the replay actually read**, recorded at the replay decision. The flow is holding it at that moment — `lookup.snapshot` at `flow.py:232-233` — and `InlineExecutor._replay` computes it too, then loses it:

```python
def _replay( self, work, trace ):
    try:
        snap   = work.job.for_current_user( work.user_id, work.session_id )   # :115 — CAN RAISE
        job_id = snap.id_hash                                                 # :116 — bound only if :115 survived
        snap.run_code()                                                       # :118 — the empty-code raise
        ...
        return Outcome( status="done", ..., job_id=job_id )                   # :121 — carried on SUCCESS
    except Exception as e:
        return Outcome( status="failed", error=str( e ) )                     # :123 — no job_id
```

⚠️ **This corrects a claim made earlier in this session's own work** (Mr. Radio's catch, 2026-08-26 20:47): I described adding `job_id=job_id` to that except branch as "the whole of it." **It is not, and as stated it is a bug.** Two reasons, both verified in the tree:

1. **`job_id` is bound INSIDE the try, one line below a call that can itself raise.** If `for_current_user()` is the raiser, the name is unbound and `job_id=job_id` in the handler raises `NameError` — converting a caught, degraded failure into an uncaught one. The binding has to move above the `try`, or the id has to come from the flow, which already holds it.
2. **Even bound and returned, it would not reach the record.** `flow.py:253` takes exactly one field off the failed replay outcome — `primary_error=outcome.error` — and hands control to `_receptionist`, which builds a *new* `Outcome` from the receptionist run. `_finish` then emits `job_id=outcome.job_id` (`flow.py:1319`) from **that** outcome, not the replay's. The replay's id is discarded at the degrade boundary the same way its command is.

So the missing evidence needs a change at **both** layers: bind the id where it cannot be skipped, and thread it through `_receptionist` → `_finish` the way `primary_error` already is. Worth noting for whoever designs it: the flow is *already* holding `lookup.snapshot` at the call site, so capturing the id there may avoid touching the executor at all — an observation, not a design ruling.

### 8.4 How these tests are written, and why

Per María's D7 catch: **assert on the record, not on the outcome.** A test asserting on the intermediate `Outcome` would have passed for D7 while the field never reached the emitted record. So the D5 claim is asserted **twice, at two different distances**. `test_terminal_wait_is_on_by_default_and_lands_in_the_record` reads what the wrapper returned; `test_terminal_state_reaches_the_WRITTEN_record_on_disk` drives the whole of `main` and then **opens `records.jsonl`**, because the wrapper's return value and the file the run produces are two different claims — between them sit `run_pass`, the record list and `write_outputs`, three chances to drop it. Asserting only the first would be the D7 mistake one level out. M7 is the mutation that separates them: un-wiring the wrapper leaves the return-value test green and reddens the on-disk one. A negative control reads the same file with the wait off and requires `waiting` to still be there, so the positive result is attributable to D5 rather than to the harness. Same for D6: the `"all"` test asserts on what `_expand_all` actually returns, not on the list literal.

One consequence worth naming: the fake listener's `ws_recv_events` is a **raiser**, not a stub returning a canned frame. No client in the existing file answers `waiting`, so it is never called — and if a future stub does, it fails loudly by name instead of quietly fabricating a terminal frame, which would be the wrapper reporting a completion that never happened.

### 8.5 M7 — why the on-disk test is not redundant, and must not be deleted

The two D5 tests look like one claim stated twice. **M7 measures the difference.** Un-wire the wrapper — pass `client.ask` raw to both passes in `main`, which restores *the original defect this row was filed about* — and:

| Test | Under M7 |
|---|---|
| `test_terminal_wait_is_on_by_default_and_lands_in_the_record` | ✅ **PASSED** — blind to it |
| `test_terminal_state_reaches_the_WRITTEN_record_on_disk` | 🔴 **FAILED** — catches it |

Run 2026-08-26, both directions, restored after.

**That is a demonstration, not an argument.** The first test asserts on what the *wrapper returns*; the second on what the *run writes*. Between them sit `run_pass`, the record list and `write_outputs` — three chances to drop the terminal state — and the defect that started all of this lives in exactly that gap: **`main` never called the wrapper at all, while the wrapper itself was correct and unit-tested the whole time.**

A future reader trimming a "redundant" test would delete the on-disk one in perfectly good faith, and the suite would stay green while the blind spot came back. **M7 is the reason it stays.** The same table is duplicated in the test's own docstring, because that is where somebody about to delete it is standing.

**The general form, worth carrying past this row** (Mr. Radio, 2026-08-26): **a well-tested function wired to nothing passes every check and does nothing.** `terminal_waiting_ask` was never broken — it had a definition, a docstring, and fifteen unit assertions, all of them correct and all of them green. The defect was that nobody called it. That is the same family as everything else on this row: an instrument that reports confidently about work it never observed. Coverage does not catch it, because the lines *are* covered; a unit test does not catch it, because the unit *is* correct. Only an assertion on what the run actually produces does.
