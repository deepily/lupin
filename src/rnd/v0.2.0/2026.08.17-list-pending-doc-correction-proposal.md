## The short version

`list-pending` is not a command. It is a **mode of the `schedule-tests` skill**, and it wraps
`GET /api/get-queue/todo`. The capability has been there all along, so this is a doc correction
— which is what `TODO.md` item 2 already concluded before I got here.

**But the rename alone would ship a still-broken instruction**, because the procedure returns a
confident wrong answer to anyone using the credential the config store hands them. That is the
second half of this proposal and it is the half that matters.

## Half 1 — the naming, and where it is wrong today

| file | line | current text |
|---|---|---|
| `CLAUDE.md` | 328 | "`list-pending` FIRST to decide placement" |
| `CLAUDE.local.md` | 31 | "list-pending FIRST: empty queue → bounce + schedule + run now" |

`list-pending` appears in 15 R&D docs and these two instruction files. It appears in **no** `.py`,
`.sh`, `.js` or `.ts` in the tree. The real call is:

```
GET /api/get-queue/todo      Authorization: Bearer <jwt>
```

returning `todo_jobs_metadata` — each entry carrying `job_id`, `agent_type`, `scheduled_at`,
`monopolize`, `status`. Two traps `TODO.md` already records and that survived my own run: the
login route is `/auth/login`, **not** `/api/auth/login`, and the token is nested at
`tokens.access_token`, not top-level.

### Proposed replacement wording

> **Check the pending queue FIRST** to decide placement — `GET /api/get-queue/todo` with a JWT
> (the `schedule-tests` skill's *list-pending* mode has a copy-paste snippet). **Authenticate as
> the account that submits test-suite jobs** — the view is filtered to the calling user and will
> report an empty queue, with no warning, if you call it as anyone else.

The last sentence is the one that must survive editing. Without it the corrected instruction is
still an instruction to trust a filtered view.

## Half 2 — why the rename is not enough

I ran the documented procedure tonight, correctly, and it told me two real queued jobs did not
exist. I reported that to two people before John's direct DB reading corrected me.

**The mechanism**: `/api/get-queue/{name}` filters to the calling user. Measured on `:8000`:

| call | result |
|---|---|
| `GET /api/get-queue/todo` | 200, 0 rows, `filtered_by=931e9dae…` |
| `GET /api/get-queue/todo?user_filter=*` | **403** — "Only admin users can query all jobs" |
| `GET /api/job-history` | 200, 14 rows, `filtered_by=931e9dae…` |
| `GET /api/job-history?user_filter=*` | **200, same 14 rows** — the parameter does not exist on this route, so it is dropped silently |

- `931e9dae` = `claude.code@lupin.deepily.ai`, the account `~/.lupin/config [lupin]` hands you.
- `50c73ba7` = `interactive.job.tester@lupin.deepily.ai`, the account the jobs in question carry.

The `schedule-tests` skill states the assumption plainly: *"Test-suite jobs all run as the shared
`interactive.job.tester@lupin.deepily.ai` account, so this view IS the full pending-test-suite
picture."* **True only if you authenticate as that account.** The credential store's `[lupin]`
section gives you a different one, and nothing in either file, the skill, or the API response
says the two disagree.

`get-queue` at least refuses loudly on `user_filter=*`. `job-history` does not — it accepts a
parameter it does not have and answers as though it complied. Neither offers a non-admin any
fleet-wide view, so there is no correct way to perform the mandated pre-check from a seat holding
the `[lupin]` credential.

### What actually needs to change

1. **Name the credential in the instruction**, or make `~/.lupin/config [lupin]` the submitting
   account. A procedure whose correctness depends on an unstated credential choice will keep
   producing confident empty answers.
2. **Make the filtered view say it is filtered.** `filtered_by` is already in the response body
   and no caller reads it. An empty queue and an invisible queue are the same output today.
3. **Reject unknown query parameters on `job-history`**, or give it the `user_filter` it is
   documented elsewhere to have. Silently dropping a filter someone passed deliberately is the
   failure mode that made me confident.

Items 2 and 3 are code, not doc, and belong on `e205a3b1` or a sibling row. Item 1 is the doc
edit this proposal is for.

## Why I am confident about the shape and not about my own first answer

This is `2026.08.17-instruments-that-cannot-see.md` instance 8 wearing a different hat — an
instrument scoped to a proxy for the thing (my account standing in for "the fleet's jobs") whose

in the same message where I concluded the jobs did not exist, and then leaned on a single

The checklist question that would have caught it is already written down in that doc: *"What ref
/ port / window / depth does this actually read, and is that the thing the claim is about?"*
Here the answer was "one account, and no." I did not ask it of myself until John's DB reading
forced the issue.
