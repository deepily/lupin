## (c) Cost — linear, not quadratic, and the budget is not what bounds it

Worst hostile file I could build: a document that is nothing but JSON-shaped strings, so every
node is a re-parse candidate. Best of three runs each.

| decoy strings | file | budget ON (64) | budget OFF |
|---|---|---|---|
| 5,000 | 111 KiB | 1.4 ms | 10.9 ms |
| 10,000 | 224 KiB | 2.8 ms | 21.6 ms |
| 20,000 | 458 KiB | 5.7 ms | 43.3 ms |
| 40,000 | 927 KiB | 12.1 ms | 87.0 ms |
| 80,000 | 1,864 KiB | 14.6 ms | 14.7 ms — past the 1 MiB window, parse fails, short-circuit |

Doubling the input doubles the time on both settings (×1.95 … ×2.13). **Linear.** No input hangs
and none is quadratic.

**What the budget actually buys is ~75 ms.** Total re-parse work is already bounded by the 1 MiB
read window: every re-parsed string is a substring of bytes already read, and escaping makes each
nested level strictly smaller than its parent. The cap is defensible, but it is not what makes
the walk safe — and it costs a real false negative (a credential behind 64 JSON-shaped strings is
served, which the author states and pins).

⚠️ **A note for whoever mutates this next.** The budget test sizes its own fixture from the
constant — `_a_file_with_json_shaped_decoys( CREDENTIAL_MAX_NESTED_PARSES * 2 )`. Editing the
constant to neuter the budget therefore tells the test to build a fixture proportional to the new
value; setting it to 10⁹ asks pytest for two billion decoys, which is a 66 GB process and not a
finding. **Neuter the CHECK, not the constant.** (I reported that runaway as a defect before
isolating it; it was mine. Retracted the same hour.)

## Findings

### 1 — a lead-in character inside the carried string still SERVES a credential

`_opens_a_json_container` strips lead-in noise before deciding a string is worth parsing.
`_json_carried_in_a_string` then calls `json.loads` on the **raw** text. So for
`{"k": "﻿{...service account...}"}` the opener says yes, the parse chokes on the mark and
returns `None`, and the walk reads `None` as "nothing here to see". **Measured SERVE.**

The two halves already disagree inside the suite: `test_a_string_that_is_not_json_is_not_re_parsed`
pins `_opens_a_json_container( "  ﻿[1, 2]" )` as True. This is the same invisible-lead-in
class that cost this detector 8 of 24 shapes at `ff6c9e46`, one layer further in.

Fix is one line — `json.loads( _strip_leadin_noise( text ) )`. **Not applied**; it is Rachel's file.

### 2 — `RecursionError` escapes the fail-closed contract

`json.loads` raises `RecursionError` on deeply nested input (≈20,000 levels, a 39 KiB file,
0.5 ms). Neither parse site catches it — both catch only `(ValueError, TypeError)` — so it
propagates out of `_prefix_looks_like_credential`, past the `except Exception` in
`is_credential_file` (which wraps only the file read), and becomes a 500 at the `docs_files.py`
call site.

That contradicts the function's own headline promise: *"True when the file cannot be read or
decoded, for ANY reason."* Here it neither blocks nor serves — it raises.

**Mostly pre-existing**: the top-level parse raises the same way at `ce943c5d`. This commit adds
a second raise site with the same narrow `except`. It fails to a 500 rather than a serve, so it
is not an exposure.

## Is Rachel's table the flat-payload shape the checklist warns about?

**No.** The earlier 15-attack table varied the lead-in and held the payload flat, which is why it
could not reach a depth bug. This table varies what the payload is **made of** — string-carried,
list-valued, list-of-list, nested-string — against a fixed container shape, which is the axis the
depth table held fixed. It is the correct next axis, and she says so in the test file's own
header comment.

The axis still open after this one, and the reason Finding 1 exists: the payload's **encoding**.
A carried credential can be lead-in-prefixed, and nothing in this table varies that.
