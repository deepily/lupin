**Author**: Tiberius 👑 (`e328974d`, tester seat) · **Date**: 2026-08-22

## The count

One morning, one feature, eight checks that were supposed to prove it. **Four could not fail
at all**, and a fifth suppressed its own result. Each was found by a different person, and
none was found by running it — a check that cannot fail is, by construction, green.

| # | the check | why it could not fail | found by |
|---|---|---|---|
| 1 | `test_qa_submission.py:176-180` — mode selector changes | the assertion sat inside `if is_visible()` **and** `if count >= 2`; an unrendered select **skips** and reports green | me |
| 2 | `test_notifications_sections.py:118` — `count() > 0` | counts the `<select>` **element**, not its options; a select with zero options passes | me |
| 3 | plan gate 2 — grep for `agent router go to` in the front end | option values are **mode keys** (`math`, `deep_research`), so the grep matched **nothing** and passed with the entire hand-written list intact | me |
| 4 | plan gate 3 — "for each `speakable` command…" | tested `speakable` while the dropdown is governed by `user_initiable`: **a gate testing a set it does not govern** | Mr Radio |
| 5 | gate 3, *after* the fix — set-equality on `user_initiable` | `user_initiable − speakable` is **empty**, so the discriminator does not exist in the data; revert the fix and nothing reds | Clayton |

| 8 | the coverage read itself | `--no-cov-on-fail` suppressed the report on any red tier — and a worktree tier is **always** red | me |

Rows 4 and 5 are the same gate, twice: written wrong, fixed, and **still** asserting nothing.
That is worth sitting with. The fix was correct and the gate was still empty.

## The five shapes

They are not one mistake repeated. They are five distinct ways for a check to be green
without being true, and only the first is the one people watch for.

**1 · The count.** `count() >= 2`, `count() > 0`. Named and disqualified by the plan's own §6
— *"a count over a list derived from the registry cannot fail unless a set-equality would have
failed first"* — and written anyway, twice. Worth noting against my own report: `count() >= 2`
**does** red on a total failure (`0 >= 2` is false). Clayton corrected me on that, and the
correction matters: the count's defect is that it survives a **partial** render, not that it
survives everything.

**2 · The guard that swallows the failure.** Row 1 is worse than a count. `if is_visible():`
turns "the thing under test did not render" into a **skip**, and a skip is reported as a pass.
A precondition must be **asserted**, never used as a conditional.

**3 · The wrong set.** Rows 3 and 4. The check is well-formed, falsifiable, and pointed at
something other than what governs the behaviour. This is the hardest to see by reading, because
nothing about it looks weak — it looks like a proper set-equality. It just isn't about the
dropdown.

**4 · The absent discriminator.** Rows 5 and 6, and the most interesting. A set-equality against
a table is a real check *only if the table contains a case that distinguishes right from wrong*.
When `user_initiable − speakable` is empty, a gate on the correct field and a gate on the wrong
field are green on identical inputs. The gate is well-written, points at the right set, and
**still asserts nothing** — because the data has no counterexample in it.

The remedy is not a better assertion. It is to **manufacture the discriminating case**
synthetically, and to add a paired test that watches for the day the real data grows one.

**5 · The derived oracle.** Row 7. When the thing under test is *computed from* the thing you
compare it against, mutating either end moves both. Clayton's catch, and the sharp edge is what
happens next: someone notices the control never reds, "fixes" it until it does — and has now
**un-derived the field**, breaking precisely the property the gate existed to protect. A control
that is hard to red is sometimes telling you the code is correct.

## What actually caught them

Not the test runs. Every one of these was green.

- **Reading the assertion and asking what input would red it.** Rows 1, 2, 6, 7.
- **Measuring the data the assertion depends on.** Rows 3 and 5 — nobody could have reasoned
  their way to "option values are mode keys" or "`user_initiable − speakable` is empty". Both
  needed somebody to go and look.
- **An adversarial reader who does not own the code.** Rows 5, 6 and 7 are all Clayton, and row
  6 is *my* test. I had spent the morning hunting this exact defect and shipped one myself.

That last point is the practical one. Self-review found none of my own three.

## What I changed, and what I did not

Fixed: rows 1, 2, 3, 5, 6, 8 — each **seen red before being kept**, with the red pasted into the
commit. Rows 4 and 7 were fixed in the plan and in Sam's implementation respectively.

**Not fixed, deliberately**: the underlying pattern has no test. There is no check that says
*"this assertion can fail"* — the closest thing this repo has is the **committed must-fail
control**, already used by `_card_drift` in `test_v2_registry_drift_guard.py` and now by
`option_value_drift` and `display_name_drift`. That pattern is the one defence here that
generalises: a predicate driven by both the live guard and a control that proves each arm fires,
so weakening the predicate reds the control instead of buying a green.

It is not free — it costs a second test file per predicate.

---

## ⚠️ The must-fail control does NOT catch shape 4. Read this before you rely on it.

**If you adopt the must-fail control and stop there, you are not covered.** The control proves
the *predicate* fires. It says nothing about whether the *data you feed the predicate* contains a
case that separates a correct implementation from a wrong one.

Watch it fail on today's actual example. Gate 3 compares the dropdown against
`{spec.command : spec.user_initiable}`:

- The predicate is fine. Its control drives `MISSING` and `PHANTOM` red on synthetic input. ✅
- The gate points at the right set. `user_initiable` is genuinely what governs the dropdown. ✅
- **And the gate still asserts nothing**, because `user_initiable − speakable` is empty — so a
  dropdown built on the *wrong* field renders exactly the same options. Revert the fix and
  **nothing reds**: not the gate, and not its must-fail control, which is off testing the
  predicate and never looks at the registry. ❌

Both instruments are green and correct, and the property is unguarded. **A must-fail control and
an absent discriminator are compatible.** That is the whole difficulty of shape 4 and the reason
it needs its own name.

**What does catch it — the only two things that do:**

1. **Measure the data for a counterexample, by hand.** Ask: *does a case exist in this table that
   would distinguish right from wrong?* Nobody reasons their way to `user_initiable − speakable
   == ∅`. Clayton went and counted.
2. **When the answer is no, manufacture the case synthetically** — and add a **paired test that
   watches the live data for the day a real one appears**, whose failure message says *retire the
   synthetic case in favour of the real command*. That paired test is the only thing standing
   between you and a synthetic case that quietly outlives its reason to exist.

Both are in `test_agent_select_contract_control.py::TestTheDiscriminatorIsManufactured`. Note
that step 2's paired test is *itself* shape 4's favourite victim: my first version of it compared
two hand-written dicts and never read the registry at all, so it could not fail. Clayton caught
that too.

---

## The one-line version

**A check is not a gate until you have seen it fail.** Four of eight had never been seen to fail,
and every one of the four looked fine.

And the corollary, which is shape 4 in one sentence: **seeing the predicate fail is not the same
as seeing the gate fail.** The must-fail control buys you the first. Only measuring the data buys
you the second.
