## The verdict first

**none of them occurs anywhere in the fleet's real command history.**

and 1 after.

## One cause

`_GIT_STASH_RE` requires `git` at start-of-string or immediately after `;` `&` `|` `(` or a
newline. Any prefix token — an absolute path, an env assignment, `sudo`/`env`, or a shell
keyword (`do` / `then` / `else` / `{`) — puts it outside that "command position" and the
match never fires.

The 31 not-in-command-position cases are heredocs, `echo` strings and `grep` patterns that
**mention** the verb without invoking it — the guard's deliberate design, not a hole. All 20
prefix-adjacent matches are one of: this session's probe, a peer's probe file listing these
same shapes, or a form that is in fact caught.

**Two findings that matter more than the count:**

1. **Seats write multi-line commands, and a newline IS a command position.** The only genuine
   keyword-prefixed use in the entire history is
   `if [ "$BR" = "$ST" ]; then` ⏎ `  git stash drop stash@{1}` — and it is **caught**, because
   `git` follows a newline. Every one of the eight above is single-line, which is exactly why
   they slip and exactly why nobody has hit them.
2. **The env-assignment form is the sanctioned escape hatch.**
   `LUPIN_ALLOW_GIT_STASH=1 git stash push` appears in real traffic and is how the hatch is
   meant to be used. Denying env prefixes outright would break it. Any fix has to let the
   hatch through while catching `GIT_DIR=…`.

## If someone fixes it

Widen the command-position test to skip a leading run of prefix tokens — a path ending in
`git`, an env assignment, `sudo`/`env`, and the shell keywords `do` / `then` / `else` / `{` —
while keeping the hatch check ahead of the deny. The existing suite plus the ten strings above
is the acceptance set: eight must flip to DENIED, the two controls must stay DENIED, and
`git stash list` / `git stash show` / `git status` must stay allowed.
