## What was wrong — two stops, one walk

The depth walk crosses objects and arrays. It stopped twice:

1. **At a string.** A whole credential carried as JSON *text* inside another JSON file
   was never opened. That is the ordinary shape of terraform tfvars, a kubernetes
   secret and a docker-compose env file — the key is a string to the outer document
   and a real key to anything that reads it.
2. **At a list under a credential key.** `_value_is_secret_material` wants a string, so
   a list answered no; the walk descends into the list's items, but they are strings
   rather than objects, so nothing ever tested them. A key written as an array of
   PEM-less lines fell between the two, and with no `type` field to catch the object on
   its declaration, the file was served.

## What changed

Three things, all in `src/cosa/rest/routers/_scope_registry.py`:

1. **`_parsed_value_carries_a_credential` re-parses strings.** A string whose first
   visible character opens a JSON container is parsed and pushed back onto the same
   stack, so a credential inside text is walked like a credential inside an object.
2. **`CREDENTIAL_MAX_NESTED_PARSES = 64`** bounds it. Without a budget, a document full
   of JSON-shaped strings turns one serve/refuse decision into thousands of parses.
   The measured shapes carry one or two levels.
3. **`_credential_field_carries_secret_material`** is the new field test:
   `_value_is_secret_material` if the value is a scalar, and *any item* if it is a list,
   at any list depth. Placeholder discrimination is applied item by item, so a template
   written as an array of lines is still a template.

Two small helpers carry the string arm: `_opens_a_json_container` (the cheap test that
decides whether a parse is worth attempting) and `_json_carried_in_a_string` (parse, or
None). Both walks use an explicit stack rather than recursion, so a file cannot put the
interpreter's stack in its own hands.

## The one-line claim, checked

Row `0cbf69c0` says the list gap closes in one line: *"treat a credential key whose value
is a LIST containing secret-material strings as secret material."* That is the right
behaviour, and the shortest way to get it is wrong.

The shortest patch teaches `_value_is_secret_material` to say yes to a list. That flips
an assertion Tiffany pinned when the depth fix landed —
`assert not _value_is_secret_material( [ "client_secret" ] )` — and the flip is not a
stale test: that function answers about ONE value, and a list is not a string.

So the list arm lives one layer up, in the field test, and the pinned assertion stays
true. Behaviour is what the row asked for; the seam moved by one function. A test now
records why, so the next reader does not "simplify" it back.

## The false-positive costs, decided rather than discovered

Both are asserted by tests, so they stay decisions on the record.

- **A document that embeds a WHOLE REAL KEY inside a string is now refused.** The
  detector cannot tell a key quoted for teaching from a key stored for use, and a real
  key pasted into a document is a real key being served. A template keeps working,
  which is the shape documentation should use anyway.
- **A credential field holding a list of real-looking strings is refused**, even if the
  author meant them as sample lines. A list of placeholders still serves.

Nothing else moved: prose about credentials, a tokenizer named `token.json`, an OpenAPI
spec naming `client_secret` at depth, a placeholder template, an ordinary report json, a
markdown doc quoting a whole ADC in a fenced block, a schema whose `private_key` is an
object, and a config file carrying a harmless JSON blob in a string — all still served,
measured.

## The accepted limit

A file that spends the whole 64-parse budget on JSON-shaped strings before the walk
reaches the credential is **SERVED**. Pinned by
`test_a_credential_past_the_RE_PARSE_BUDGET_is_SERVED_and_that_is_the_stated_limit`,
alongside the 1 MiB read bound the depth fix stated the same way.
