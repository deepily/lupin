# Response to the TypeScript test runner survey — what it explains, what it does not, and the two experiments that close the row

**Date**: 2026-08-24
**Responds to**: `2026.08.23-typescript-test-runner-oom-hazard.md` (María 🌸)
**Prior**: `2026.08.22-oom-incident-what-we-know.md` (María 🌸)
**Status**: analysis. One conclusion in the source document is contradicted below; two bounded experiments proposed.

---

## Summary

Three things in the survey are load-bearing, and one of them contradicts a conclusion the document draws.

1. The 08-22 and 08-23 events are **different failure modes** and should not share a table.
2. The CPU figures **falsify** the claim that timeouts do not mitigate. That timeout was never enforced.
3. The **52 processes** are the unexamined evidence, and the cheapest path to naming the allocator.

Plus a reframe: stop looking for a big allocation, look for a loop that never exits.

---

## 1. Stop treating 08-22 and 08-23 as one incident

The survey's table merges them. I think that is a mistake.

| | 08-22 | 08-23 (×2) |
|---|---|---|
| Killer | kernel `oom-kill`, `CONSTRAINT_NONE`, `global_oom` | `systemd-oomd`, PSI 74.8% > 50% for >20s |
| Locus | **one process**, `anon-rss:229468532kB` | **a slice**, 30–52 processes |
| Signature | `inactive_anon` 217 GB — allocated once, never re-touched | aggregate pressure; no single process need be large |

At 74.8% of 251 GiB you need roughly 188 GB *across the slice and its neighbours* — reachable by thirty processes at ~6 GB apiece with nothing pathological in any one of them.

The TypeScript runner is a credible and probably correct explanation for kills #2 and #3. It does **not** explain a single node process holding 229 GB of untouched anonymous memory. Different shape, different killer, different locus.

⇒ **Keep the 08-22 row open. The new intelligence does not close it.**

---

## 2. The CPU numbers falsify "timeouts do not mitigate"

Kill #3 ran under `timeout 300` — a 300-second wall cap — and consumed **6m28s of CPU**. That is 388 seconds of CPU against a 300-second ceiling. Two non-exclusive readings, both actionable:

1. More than one runnable thread/process (consistent with the 30–52 process count), and/or
2. **the process outlived its timeout.**

`timeout(1)` signals its **direct child only**, not the process group. A node blocked in a synchronous C++ or GC frame does not service SIGTERM, and any grandchildren are untouched regardless.

```bash
# what was run — signals node only, no kill escalation, no process group
timeout 300 node --test-concurrency=1 --import tsx --test <file>

# what actually enforces
timeout --kill-after=10s 300 setsid --wait \
    node --test-concurrency=1 --import tsx --test <file>

# better — caps wall time and memory in one primitive
systemd-run --user --scope \
    -p RuntimeMaxSec=300 -p MemoryMax=8G -p MemorySwapMax=0 \
    --slice=jstest.slice \
    -- node --test-concurrency=1 --import tsx --test <file>
```

Standing rule #1 and the sentence *"concurrency caps and timeouts do not mitigate this"* both rest on that invocation having been a fair test of a timeout. It was not.

`--test-concurrency=1` **was** genuinely tried and genuinely did not help — that half stands. The timeout half does not.

## 3. The 52 processes are the unexamined evidence

"One file. One worker." produced 52 processes in the slice.

`--test-concurrency=1` bounds concurrent test *files*. It bounds neither process count, nor tsx's transform workers, nor anything the import graph spawns. Nobody has looked at what those 52 were, and that census is the cheapest thing that could name the allocator.

```bash
systemd-cgls --user ccworker-<id>.slice          # who is actually in the cgroup
ps -o pid,ppid,rss,etimes,args --forest -g $(ps -o pgid= -p $node_pid)
```

Capture this **at the 16 GB watcher threshold**, not post-mortem. After the kill the evidence is gone — which is exactly why both prior seats came up empty.

## 4. Reframe: the allocator may be small; the run time is what is unbounded

María's instinct that a 218-line pure-function test *"should not turn that into tens of gigabytes"* is right, and I think it points at the wrong question.

Item 2 in her **KNOWN but NOT explained** list answers item 4: **`queue_transport.test.ts` returning RC=124.**

A hang under a registered happy-dom `Window` — which carries an async task manager and a live timer registry that `GlobalRegistrator.register()` installs and no `unregister()` ever tears down — means the per-tick allocation can be tiny. What is unbounded is *time*, not size.

Unbounded time × any per-tick allocation = OOM.

This is testable in five lines and costs nothing:

```bash
node --test-concurrency=1 --import tsx --test <file> & pid=$!
while sleep 5; do ps -o rss=,etimes= -p $pid || break; done
```

- **Linear growth** ⇒ hang plus per-tick allocation.
- **Step function** ⇒ one-shot allocation.

That single graph discriminates between every remaining hypothesis on the board.

## 5. The experiment that bisects the whole space — and honours the ruling

Rick's ruling condemns `lupin-wt-qa-card-8407333d`. The experiment does not need it. Copy the 218-line test and the 140-line module into a throwaway directory with a fresh `@happy-dom/global-registrator`, and run it inside a hard-capped scope where it *cannot* take the box.

```bash
mkdir -p /tmp/oomlab && cd /tmp/oomlab
npm init -y && npm i -D tsx @happy-dom/global-registrator
cp <banked>/arg-interview.js <banked>/arg_interview.test.ts .

systemd-run --user --scope \
    -p MemoryMax=6G -p MemorySwapMax=0 -p RuntimeMaxSec=120 \
    --slice=oomlab.slice -- \
    env NODE_OPTIONS="--max-old-space-size=2048 --heapsnapshot-near-heap-limit=1" \
    node --test-isolation=none --test-concurrency=1 --import tsx \
         --test arg_interview.test.ts
```

Two outcomes, both diagnostic. There is no third.

| Outcome | Meaning | Next step |
|---|---|---|
| Aborts with `JavaScript heap out of memory`, writes `Heap.<pid>.heapsnapshot` | It is **V8 heap** | Open the snapshot, sort by retained size — the retainer names the allocator in ~90 seconds. Prior: a happy-dom `Window`/`Document` graph rooted at `globalThis`. |
| RSS sails past 2 GB with no V8 abort; scope SIGKILLs at 6 GB | It is **external memory** — same class as 08-22 | `--max-old-space-size` is irrelevant. Sample `process.memoryUsage().external` / `.arrayBuffers` to localise. |

Cost: six gigabytes, two minutes, an isolated slice, **outside the condemned tree**.

If it fails to reproduce there, *that is the finding* — the worktree or its symlinked `node_modules` is implicated, and the 77-file blast radius collapses to one tree.

### On the cost of not running it

The current ruling permanently blocks the entire JS test tier — 119 files, 98 of them multiplexer tests — on an unnamed hazard. That is a large standing tax to avoid a bounded six-gigabyte experiment.

There is a defensible "not today, we are mid-recovery." I do not think "never" is the right end state, and the survey's own §*"the one job left"* quietly agrees by filing a row for the allocator.

## 6. On the oomd analysis

The observation that `MemoryHigh=18G` manufactures the very *reclaim activity* oomd's criterion requires is sharp, and I think correct. Two things follow.

**Tactical:**

```ini
# seats that must never be chosen as the victim
-p ManagedOOMPreference=avoid

# and: drop MemoryHigh on worker scopes, or raise it so it is not
# routinely generating reclaim under normal load
```

**Structural — a dedicated test lane:**

Any `node --test` runs in its own slice at `MemoryMax=8G`, no `MemoryHigh`, `MemorySwapMax=0`, `RuntimeMaxSec` set. It then dies against its own ceiling long before `user@1001` PSI approaches 50%, and never becomes fleet pressure.

This **dissolves standing rule #4** — test runs stop being blast-radius actions and become routine — without needing to know what the allocator is.

The survey's assessment of what the per-session ceiling *did* buy is correct and should not be dismissed: on 08-22 the whole `tmux-server.service` unit went down with ~2 dozen sessions; on 08-23 one scope died and every other seat survived, twice.

## 7. The freeze/mutant finding

This is the most valuable thing in the survey, and the reasoning is right: **`cmp` proves a copy is faithful and is silent on whether the thing copied is correct. Provenance ≠ correctness.**

There is a mechanical version of the rule, worth having because *"establish what the process was doing when it was frozen"* otherwise requires a human with a transcript.

```bash
# in the freeze script, per tree — these ARE correctness signals
git -C "$tree" rev-parse HEAD      > FROZEN_HEAD
git -C "$tree" status --porcelain  > FROZEN_STATUS
git -C "$tree" diff HEAD           > FROZEN_DIFF
```

`FROZEN_DIFF` would have shown mutant P1 as an unexplained modification against HEAD at freeze time — no transcript archaeology required.

Additionally, the mutation runner should write a sentinel naming the current mutant, under an `EXIT`/`TERM` trap:

```bash
trap 'rm -f .mutation-in-progress' EXIT TERM INT
echo "P${n}" > .mutation-in-progress
```

The freeze script then refuses to bank any tree carrying one. SIGKILL defeats the trap — but the sentinel survives *because* it was never cleaned up, which is precisely the signal you want.

## 8. Amendments to the handoff

The four-file landing plan, the quarantine, and "run nothing" are correct for that seat. Two amendments:

1. **Strike** *"concurrency caps and timeouts do not mitigate this"*. Replace with: *"concurrency 1 was tried and did not mitigate; the timeout was never enforced (`timeout` signals the direct child only) and remains untested."* The next reader will otherwise inherit a false negative on a control that works.

2. **The row for the unfound allocator should carry the two experiments above** (§4 RSS sampling, §5 heap-snapshot bisect), so it is a *bounded* row rather than an open-ended one. An unnamed hazard with no defined path to naming it tends to become permanent.
