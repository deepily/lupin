## 3. The four steps, in order

```
plan   →   fill (shadow column)   →   verify   →   swap
read-only  writes ONLY the new       read-only    the ONLY
           *_regen columns                        destructive step
```

1. **`plan`** — counts what would be regenerated. Read-only. Run today; table above.
2. **`fill`** — regenerates from each row's own logged text into a **shadow column** (`input_embedding_regen`, `output_final_embedding_regen`, `question_embedding_regen`). The live columns are untouched. Batched, resumable from a checkpoint, `--limit` bounded, `--apply` gated.
3. **`verify`** — read-only: row counts match, every regenerated vector reads norm ~1.000, no dimension mismatches. Produces the swap/no-swap verdict.
4. **`swap`** — promotes the shadow column, then the old column is dropped. **This is the only step that cannot be walked back by re-running.**

A half-finished or bad `fill` never leaves the table worse off. That is the whole point of shadow-then-swap.

## 4. What refuses to start, and why

`should_proceed()` gates every write pass:

| Condition | Result |
|---|---|
| Server busy (jobs in flight) | **REFUSE** — no embedding load on top of someone's run |
| Busy state **unknown** (probe unreachable) | **REFUSE** — the point of the check is not to guess |
| Outside 00:00–11:00 EDT | Refuse, unless `--force` |
| `--force` | Bypasses the **clock only**, never the busy check |

The window closes at **11:00** because Rick moved it on 2026-08-13: *"maybe make it 10 or 11 in the morning so that we can do that first thing after breakfast."*

**The GPU defect is fixed, not merely recorded** (commit `0310aa05`): a fixed 256-row batch CUDA-OOM'd the shared GPU on the long tail. Batching is now by **character budget** with an adaptive floor/ceiling, a refused batch is **split in half and retried down to a single row**, and a row that fails *alone* is a real reject. 122 unit tests green today; the module was red-proofed by removing the budget bound (6 tests go red, 98 stay green).
