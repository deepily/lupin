## 3. The four steps, in order

```
plan   →   fill (shadow column)   →   verify   →   swap
read-only  writes ONLY the new       read-only    the ONLY
           *_regen columns                        destructive step
```

1. **`plan`** — counts what would be regenerated. Read-only. Run today; table above.
2. **`fill`** — regenerates from each row's own logged text into a **shadow column** (`input_embedding_regen`, `output_final_embedding_regen`, `question_embedding_regen`). The live columns are untouched. Batched, resumable from a checkpoint, `--limit` bounded, `--apply` gated.
3. **`verify`** — read-only: row counts match, every regenerated vector carries a norm inside the **current local model's measured band (~17–24)**, no dimension mismatches. Produces the swap/no-swap verdict.

   > **Corrected 2026-08-17.** This line previously said verify checks for "norm ~1.000". That is backwards and would have made a good run look broken. A norm near 1.0 is the **retired OpenAI** model's fingerprint — an L2-normalized vector. The local nomic models emit **un-normalized** vectors in the 17–24 band, which is exactly what `classify_norm()` accepts and what freshly-generated vectors measure at. Caught when the first real embeddings came back with components like `-3.81`, impossible in a unit vector.

4. **`swap`** — runs `UPDATE <live_column> = <shadow_column>`. The live vectors are **overwritten in place**. **This is the only step that cannot be walked back by re-running.**

   > **Corrected 2026-08-17.** This line previously said swap "promotes the shadow column, then the old column is dropped." The code drops nothing — the shadow column **survives the swap by default**. That inverts the rollback question: *keeping* the shadows is the do-nothing outcome, and discarding them is the step that takes an explicit `DROP COLUMN`. Rick ruled on 2026-08-17 for **no retained shadows and no dump** — so the drop is a deliberate follow-up action, not something the swap does for you.

**Missing step — the shadow columns do not exist.** `fill` references `input_embedding_regen`, `output_final_embedding_regen`, and `question_embedding_regen`, and **nothing in the script creates them**. The first `UPDATE` fails with `column ... does not exist`. Before any fill:

```sql
ALTER TABLE input_and_output     ADD COLUMN input_embedding_regen        vector(768);
ALTER TABLE input_and_output     ADD COLUMN output_final_embedding_regen vector(768);
ALTER TABLE prediction_decisions ADD COLUMN question_embedding_regen     vector(768);
```

A nullable `ADD COLUMN` with no default is metadata-only in Postgres — instant, no table rewrite.

A half-finished or bad `fill` never leaves the table worse off. That is the whole point of shadow-then-swap.

## 4. What refuses to start, and why

`should_proceed()` gates every write pass:

| Condition | Result |
|---|---|
| Server busy (jobs in flight) | **REFUSE** — no embedding load on top of someone's run |
| Busy state **unknown** (probe unreachable) | **REFUSE** — the point of the check is not to guess |
| Any hour of the day | **Proceeds** — the clock no longer refuses anyone |
| `--force` | Bypasses the **clock only**, never the busy check |

**The clock is permissive as of 2026-08-17.** `OFF_PEAK_END_HOUR` went 9 → 11 → **24**, on Rick's word: *"You can update the clock to run for as long as we need it to. I am the human at the console. Nothing else will run or interfere. Let's not be too official on this — update the clock/gate so it's permissive and runs at my discretion."*

That costs nothing, because the clock was never the real gate. The busy check still refuses a busy box **and** still refuses when it cannot get an answer — a clock cannot tell you the box is free, only the box can. What the window actually protected was Rick's own interactive hours; when Rick is the one asking for the run, there is nobody left for it to protect. The boundary is still a parameter (`is_off_peak( hour, end_hour=N )`), so a tighter window can be reimposed without editing the module.

**The GPU defect is fixed, not merely recorded** (commit `0310aa05`): a fixed 256-row batch CUDA-OOM'd the shared GPU on the long tail. Batching is now by **character budget** with an adaptive floor/ceiling, a refused batch is **split in half and retried down to a single row**, and a row that fails *alone* is a real reject. 122 unit tests green today; the module was red-proofed by removing the budget bound (6 tests go red, 98 stay green).
