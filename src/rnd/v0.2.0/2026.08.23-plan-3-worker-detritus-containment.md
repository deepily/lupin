# Plan 3 — Stopping workers from leaving detritus on the disk

**Author**: María · **Date**: 2026-08-23 · **Status**: PLAN, not yet executed
**Companions**: Plan 1 (lane recovery), Plan 2 (worktree reclamation — the one-time cleanup
this plan exists to make unnecessary a second time)

## Purpose

Plan 2 reclaims ~8 GB of worktrees. This plan is about why there were 49 of them. Every
artifact below was created by a worker doing its job correctly; **none of them has an owner
responsible for removing it**, and that is the whole defect. Creation is instrumented;
disposal is not.

### The headline nobody has looked at

**`io/claude_code_hooks/logs` holds 748,040 files and 6.1 GB, accumulating since February.**
It is the largest single artifact on the list, it is bigger than every worktree combined, and
because it is gitignored it is **invisible to `git status`** — which is why it has never once
appeared in a session-end review. Six months of hook logs with no rotation and no retention.

That inode count matters as much as the bytes: three quarters of a million files in one tree
makes `find`, `du`, backup, and any repo-wide sweep slow — and a repo-wide sweep is exactly the
kind of unbounded-output command the OOM analysis fingered as hypothesis H1. **The detritus and
the crash are plausibly the same story.**

### The good news, stated plainly

The *tracked* working tree is clean: `git status --untracked-files=all` on the main repo shows
**one** untracked file. Workers are not scattering junk into version control. Everything above
is in gitignored or out-of-repo locations — which is why it went unnoticed, not because it is
harmless.

### A receipt from yesterday

Cheech's worker `7d9dc88c`, investigating four "flaky" unit tests, found they did not reproduce
and that the 11 real failures were "a gitignored config file absent from a fresh worktree."
**A worktree-hygiene problem was consuming a debugging lane.** The cost of this mess is not only
disk.

## Root causes, each with its fix

### RC1 — Nothing ever deletes a worktree

Workers create worktrees under standing authority. No step in reap, session-end, or memento
writing removes one, and `dismiss_sessions` does not take the worktree with it. A worker that
is re-spun creates a *second* worktree; nothing retires the first.

**Fix — make the reap own the disk.** Extend `dismiss_sessions` so that when a worker is
dismissed, its worktree is evaluated: fully merged and clean ⇒ removed automatically; carrying
work ⇒ bundled to `io/` and reported in the dismiss result. The reap already knows the seat;
it is the only moment that reliably knows the worktree is finished.

### RC2 — Worktrees have no expiry and no owner field

A worktree's name encodes a lane, not a deadline. Nothing distinguishes "live" from "abandoned
in June."

**Fix — a stamp file at creation.** Write `.worktree-meta.json` into every worktree holding
`{created_ts, owner_persona, row_id, manager}`. A janitor can then act on facts instead of
guessing from `mtime`. Without the row id there is no way to ask "is this lane still open?" —
which is precisely the question Plan 2 had to answer by hand for 49 directories.

### RC3 — Hook logs have no rotation

748,040 files, six months, no policy.

**Fix — rotate and cap.** A `logrotate` user config or a size/age cap in the hook logger
itself, with a hard retention (14 days is generous for something nobody has read since
February). This is the single highest-value item in the plan and the least risky.

### RC4 — Transcripts have no retention

2.7 GB in `~/.claude/projects`, and by the incident doc's own account transcript bloat is a
memory-pressure path.

**Fix — set `cleanupPeriodDays` in `settings.json`.** It exists, it is unset, and it is one line.

### RC5 — No inventory, so nothing is ever noticed

Nobody knew about the 748k files because nothing reports them.

**Fix — a weekly disk-hygiene tick.** A cron script emitting worktree count, worktree bytes,
hook-log bytes and inode count, transcript bytes — into a notify, not a log file nobody reads.
**Rule: it must state the numbers, not "cleanup complete."** A janitor that reports success
without counts is how you get to 748,040 files.

## Phases

### Phase 1 — Stop the bleeding (this week, no design needed)

1. `logrotate` on `io/claude_code_hooks/logs`, 14-day retention — reclaims ~6 GB immediately
2. `cleanupPeriodDays` in `~/.claude/settings.json`
3. The weekly inventory tick, reporting numbers

None of these three changes any worker's behavior. All three are reversible.

### Phase 2 — Make the reap own the disk

`dismiss_sessions` gains worktree disposition: merged+clean ⇒ remove, dirty ⇒ bundle and
report. **The bundle-before-delete rule from Plan 2 applies here permanently** — automatic
deletion is only acceptable because the work is recoverable from one file.

### Phase 3 — Stamp worktrees at creation

`.worktree-meta.json` with owner, row, manager, timestamp. Enables Phase 4.

### Phase 4 — The janitor

A scheduled sweep that removes worktrees which are fully merged, clean, older than N days,
**and** whose row is terminal. All four conditions, not any of them. It reports what it removed
with counts.

⚠️ **Do not build Phase 4 before Phase 3.** A janitor without the stamp file has to infer
ownership from directory names, and a deletion tool that guesses is worse than the mess.

### Phase 5 — Bound the output that started this

Adjacent but load-bearing: the `PreToolUse` Bash guard from the OOM analysis. A repo-wide
`find`/`grep` across 748,040 files is both the detritus symptom and a candidate crash trigger.
Shrinking the tree (Phase 1) and bounding the command (Phase 5) attack the same failure from
both ends.

## Sequencing note

Plan 2 without Plan 3 buys a few months. **Plan 3 Phase 1 is worth doing before Plan 2** — it is
three low-risk changes, it reclaims more disk than the entire worktree cleanup, and it does not
wait on Plan 1's recovery work to finish.

## Exit criteria

- Hook logs bounded by rotation; inode count under 10,000
- Transcript retention configured
- Reaping a worker disposes of its worktree, with a bundle when work is present
- Every worktree carries owner/row/timestamp metadata
- A weekly report that states numbers
- Total footprint under 3 GB and **flat over 30 days** — flat is the real test; a one-time
  cleanup that trends back up has proven nothing

## Where the doctrine half belongs

The mechanics above are lupin's. The *practice* — "the seat that creates an artifact owns
removing it, and the reap is where that debt comes due" — belongs in
planning-is-prompting `workflow/`, so it travels to every repo the fleet works in. Per standing
guidance, do not graduate it to doctrine on this one incident; note it, and codify once it
recurs.
