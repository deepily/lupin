## Purpose

Twelve sessions across two manager crews were killed mid-flight yesterday. This plan
establishes, for each one, **where the work actually stood**, **which worktree it lived in**,
and **what it would take to finish it** — then resurrects the lanes in an order that will not
reproduce the crash.

## What actually happened (verified, not inferred)

`journalctl --user -u tmux-server.service` for 2026-08-22:

| Time | Event |
|---|---|
| 09:53:18 | tmux server started — fleet spun up |
| **12:23:50** | `A process of this unit has been killed by the OOM killer` |
| 12:25:20 | `Failed with result 'oom-kill'` — unit torn down, **7 pytest/python children SIGKILLed** |
| 12:25:22 / 12:25:25 | restart counters 1 and 2 |
| ~12:37 | managers restore the fleet from mementos |
| **12:38:01** | second OOM kill — **~60 seconds after the restore** |
| 12:38:07 | `Failed with result 'oom-kill'` again; restart counter 3 |

### Two corrections to the incident doc's framing

1. **The fleet did not die because the kernel picked unlucky PIDs.** The whole
   `tmux-server.service` unit was marked `oom-kill` and systemd tore down *every* process in
   it — that is why ~2 dozen sessions dropped together, and why in-flight `pytest` runs died.
   The unit-level teardown is the mechanism; the per-session slice from `a52d160c` is
   precisely the right countermeasure.
2. **No transcript on the box supports the "poisoned transcript" hypothesis (H2).** The
   largest `.jsonl` written on crash day is **3.7 MB** — four orders of magnitude below the
   3.8 GB case in the issue H2 leans on. H2 should be **downgraded, not carried forward**.

### The finding that governs this whole plan

**The second crash arrived ~60 seconds after the restore.** Whatever the trigger was, the
resurrection reproduced it almost immediately. A naive "bring them all back at once" replay
is the single most likely way to cause a third event, so the sequencing in Phase 3 is not
ceremony — it is the deliverable.

## Phases

### Phase 0 — Freeze the evidence (do this before anything else)

Nothing here resurrects anything; it makes the rest reversible.

1. `git -C <wt> stash list` and a **bundle** of every non-merged branch:
   `git bundle create io/recovery-2026.08.23/<branch>.bundle <branch> --not <integration>`
2. Copy the 3 modified + 10 untracked files out to `io/recovery-2026.08.23/loose/` **before**
   any checkout, rebase or worktree operation touches them.
3. Record `git -C <wt> rev-parse HEAD` for all 8 worktrees into a manifest.

**Gate**: the manifest exists and the bundles restore in a scratch clone. Until that passes,
no lane is resurrected.

### Phase 1 — Land what is already finished

Three lanes need no session at all — their work is committed and merged:

- `ece4d86a` (flaky tests) — the finding was **negative**: the four named tests do not
  reproduce, and the 11 real failures are "a gitignored config file absent from a fresh
  worktree." **That is a Plan 3 input, not a bug in the tests.** Close the row with the
  negative result recorded; do not re-run the investigation.
- `004c94ec` (learn-back) — merged at `9c654a08`. Close, unless Cheech's dropped clarifying
  question changes the scope; the worker asked and never got an answer.
- `b0570b67` (wake check) — 1 commit, clean tree; needs only the regression sweep it was
  starting when it died.

### Phase 2 — Reconstruct the two dirty lanes

`lupin-wt-qa-card-8407333d` (2 modified, 4 untracked) and `.claude/worktrees/qa-card-tester`
(6 untracked) hold the only genuinely unrecoverable-if-lost work. Read the loose files copied
in Phase 0, diff them against the branch tip, and decide commit-or-discard **from the file
contents**, not from the transcript's description of them.

`8407333d`'s transcript ends at "Mandatory red pass:" — the red pass was never run. Per the
standing rule that an assertion is not a guard until you delete what it guards and watch it go
red, that lane is **not** done and must not be landed as if it were.

### Phase 3 — Resurrect, one lane at a time, under the new ceiling

The ordering exists because the last restore caused the next crash.

1. **One session at a time.** Bring up a single worker, confirm it is inside its own
   `ccworker-*.slice` (`systemd-cgls --user-unit ccworker.slice`), and let it work for a full
   turn before starting the next.
2. **Watch `memory.current` on the scope**, not the host. A lane that climbs past
   `MemoryHigh` (18 GiB) will throttle and reclaim — that is the early warning the old shared
   slice could not give.
3. **Do not `--resume` any crash-day transcript.** Seed from the memento or the store row.
   The 12:38 event happened a minute after a restore; until the trigger is identified, replay
   is the one action with a demonstrated correlation to a crash.
4. **Keep `pytest` off the critical path during resurrection.** Seven pytest children were
   killed in the teardown, and full-suite runs are the most memory-hungry thing these lanes do.
   Land the work first; run suites afterward, deliberately, one at a time.

### Phase 4 — Attribute the trigger (bounded)

The incident doc's forensic steps stay unexecuted. Now that the ceiling exists, the next event
is survivable, so wire capture rather than hunting the last one:

- On the 16 GB watcher crossing, snapshot `/proc/<pid>/fd`, `smaps_rollup`, and `status`.
- `fd` is the tiebreaker: a pipe to a Bash child ⇒ H1; a large `.jsonl` ⇒ H2 (now unlikely,
  given 3.7 MB is the crash-day maximum); a socket ⇒ H3/H4.
