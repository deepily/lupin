## 1. 🔴 v2_eval depends on v1_eval_arm for TWO things, not one

Step 2 relocates `make_ws_recv_events` + `WsJobEventListener` + `_TERMINAL_STATES`. There is a second
dependency, and it is on the live path of **every v2 run**, not just paired ones:

```
src/scripts/v2_eval.py:1421  def load_mappable_commands()
src/scripts/v2_eval.py:1433      from v1_eval_arm import load_v1_class_to_command   # lazy: v1 imports v2
src/scripts/v2_eval.py:2022      mappable = load_mappable_commands()
src/scripts/v2_eval.py:2023-24   compute_metrics( cold_records, mappable_commands=mappable )
```

`load_v1_class_to_command` lives at `v1_eval_arm.py:1240` and reads the live v1 registry **out of the
pinned worktree** — which Step 4 deletes.

**What happens after excision.** The lazy import raises, the `except` at :1437 catches it, and the
function returns `None`. The code's own comment says what `None` means:

> *"routing accuracy will be scored over the FULL corpus, which is NOT comparable to the v1 arm's
> eligible-only denominator."*

That is a **printed warning on stdout, not a failure**. v2 keeps running and keeps reporting a routing
accuracy — measured against a wider denominator than every v2 number recorded before the excision.
The number moves and nothing red appears. This is the same shape as the three coverage incidents
already on the record: the instrument reports under a condition where it cannot measure.

**Fix — pick one, before Step 3:**
- **(a) Freeze the list.** The eligible-command set comes from a pinned sha, so it is a constant now,
  not a lookup. Write it to a checked-in data file with the pin sha stamped on it, and repoint
  `load_mappable_commands` at that. Preserves comparability; ~an hour.
- **(b) Make the None path fatal.** If the list cannot be read, v2 refuses to score routing rather
  than scoring it wider. Cheaper, and it can never quietly widen — but it takes v2's routing metric
  offline until (a) is done.

**(a) is my recommendation.** (b) alone leaves the metric dark; (b) as a guard *on top of* (a) is
better than either.

Also add `test_v2_paired_bridge_reachability.py:434` to the Step-1 list — it patches
`v1_eval_arm.load_v1_class_to_command` directly.

## 2. 🟠 §3a's first action has no target in this repo

The plan says: *"Find the setter — `grep -rn 'COVERAGE_PROCESS_START|COVERAGE_PROCESS_CONFIG' src/`
and the runner scripts."*

**That grep returns zero hits repo-wide** (excluding `.venv`, `.git`, and the rnd writeups). Nothing
in this repository sets either variable.

The actual chain is outside the repo: **pytest-cov 7.1.0** is installed, and
`.venv/lib/python3.13/site-packages/a1_coverage.pth` fires on either variable and calls
`coverage.process_startup( slug="pth" )` — a non-standard call signature, injected into the venv, not
ours to edit and not stable across a venv rebuild.

**So there is no source to fix.** The `omit` for anything outside `src/` is not belt-and-braces — it
**is** the fix. And the guard test the plan proposes (*every file in the coverage report is under
`src/`*) becomes the whole control, which raises its priority rather than lowering it: it is the only
thing standing between this repo and a venv-layer change nobody in this repo will see.

Nothing else in §3a changes. The action is right; the first step should say "confirm the setter is
outside the tree" rather than "find and fix it."

## 3. 🟠 V1 excision cannot move the coverage denominator — the sign IS knowable

§0 and Step 5 say the sign is not knowable in advance, and §4 sequences the excision before the
test-writing grind *"because it changes the denominator."*

**It does not.** `[tool.coverage.run] source` (`pyproject.toml:200-208`) lists seven package
directories:

```
src/cosa · src/lupin_cli · src/lupin_mcp · src/lupin_arbiter_app · src/lupin_app · src/lib · src/lupin_model_server
```

**`src/scripts` is not among them**, and all 2,953 lines of v1 scripts live in `src/scripts/`.
Deleting them removes **zero** statements from the frame.

Deleting their ~3,646 lines of tests can only move the number **down**, where those tests incidentally
exercise measured packages — 6 of the 10 named unit files import `cosa` or `lupin_cli`.

⇒ **Excision is neutral-to-negative on coverage, never positive.** Still worth doing on Rick's
ruling, and still worth doing first for a clean tree. Just do not sequence it *for* a denominator
move, and do not be surprised by a small dip in Step 5's re-measure — expect one, and say so before
the run rather than after.

## 4. 🟡 The marker risk row's guard does not guard

The risk table pairs *"the `paired_eval_live` marker removed but still in addopts"* with the guard
*"`--strict-markers` turns a stale marker into a hard error — the suite tells us."*

`--strict-markers` validates markers **applied to tests** via `@pytest.mark`. An unknown name inside
the `-m` expression is silently evaluated as False.

**Measured, just now**, with `--strict-markers` live in `pytest.ini:82`:

```
$ .venv/bin/python -m pytest src/tests/unit/test_v2_paired_live_precondition.py \
      --collect-only -q -m "not bogus_marker_xyz_maria"
3 tests collected in 1.76s
```

Clean collect, no error, invented marker name. The real control is a grep of `pytest.ini:82`'s
addopts line at the end of Step 3(a) — not the suite. Low severity (a stale `not X` clause deselects
nothing and harms nothing), but a control that reads as automatic and is not belongs corrected in the
table rather than relied on.
