## 0. TL;DR (the four rulings this settles)

1. **Q3 dim = 768, SETTLED.** Every vector column in every live table is `fixed_size_list<float>[768]`. **ZERO 1536 columns anywhere.** `vector(768)` is correct across the board.
2. **Metric = dot (`vector_ip_ops` / `<#>`) is CORRECT — but the design's *rationale* is wrong.** All 4 ANN-searched columns use `.metric("dot")` live. The dot opclass is safe because it is the **identical metric**, NOT because vectors are L2-normalized. The keystone table's vectors are **NOT normalized** (norm ≈ 22). Do **NOT** substitute cosine `<=>`.
3. **F-SCOPE: the live vector surface is LARGER than the design's 6 tables.** Two additional live, actively-ANN-searched tables exist — `prediction_decisions` (1,776 rows) and `solution_snapshots` (35 rows, 7 vector cols) — raising the ANN-searched dot column count from the design's **1** to a live **4 across 3 tables**. **Manager scope decision required** (see §4).
4. **F6 resolved:** the live `query_log` column is `normalization_version` (underscore); the *space* (`"normalization version"`) exists only in the create-table source code, not on disk. Fresh-start Postgres column → `normalization_version`, no quoting needed.

## 2. F-NORM — the L2-normalization invariant does NOT universally hold (design-rationale correction)

Live vector-norm probe (3 rows/column):

| table.column | live norm | normalized? |
|---|---|---|
| `input_and_output_tbl.input_embedding` | **19.4–22.4** | **NO** |
| `input_and_output_tbl.output_final_embedding` | **19.4–22.2** | **NO** |
| `embedding_cache_tbl.embedding` | 1.000000 | yes |
| `canonical_synonyms.embedding_*` (all 3) | 1.000000 | yes |
| `query_log.embedding_*` (all 3) | 1.000000 | yes |
| `prediction_decisions.question_embedding` | 1.000000 | yes |
| `solution_snapshots.{question,code,solution}_embedding` | 1.000000 | yes |

- The **keystone ANN table** (`input_and_output_tbl`, the ONLY design-scope ANN column) stores **unnormalized** vectors (norm ≈ 22).
- Its **query path** (`input_and_output_table.py:292`, `get_knn_by_input`) draws the query vector from the **same** `question_embeddings_tbl.get_embedding()` source used on write → query and stored vectors are both unnormalized → the live `.metric("dot")` search is **internally self-consistent**.

**Consequence (load-bearing):**
- Ruling **stands**: pgvector **`vector_ip_ops` / `<#>`** (negative inner product; order-ascending `<#>` = order-descending dot) reproduces LanceDB `.metric("dot")` **exactly**, normalized or not.
- Design §4.2 rationale — *"safe to serve with cosine because embeddings are L2-normalized → dot≡cosine"* — is **empirically false for the keystone**. Correct framing: **dot is safe because it is the identical metric**, not because of normalization.
- **Do NOT use cosine `<=>`.** On the unnormalized keystone, cosine returns different neighbours than the live dot search → silent regression. The §7 equivalence harness must compare against **dot**.

## 3. F6 — `query_log` space-named column (resolved + code/live discrepancy)

- **Source code**: `query_log_table.py:190` declares `pa.field( "normalization version", ... )` and `:275` writes the dict key `"normalization version"` — **space**.
- **Live store**: the persisted column is **`normalization_version`** — **underscore** (confirmed by dump; no space-flag tripped). The space never made it to disk.
- **Resolution**: `query_log` is a cache → **fresh-start** (design §5). Name the Postgres column **`normalization_version`** (underscore, clean, no quoting). The create-table code's space is a latent bug — recommend Lane B/C fix it to underscore for consistency, but it does not affect the Postgres schema.
