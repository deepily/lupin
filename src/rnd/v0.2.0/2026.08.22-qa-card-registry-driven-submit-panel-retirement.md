Every field the front end needs is already declared. Nothing new has to be invented — only exposed.

| the UI needs | the registry already has |
|---|---|
| the option's value | `spec.command` — the full routing string |

## 5. The design

### 5.1 One new field, one new endpoint

Add two fields to `AgentSpec`:
- `description: Optional[str]` — move the 16 `MODE_METADATA` strings into the table.
- `user_initiable: bool` — **ruled 2026-08-22**. Means *"a person may start this by typing into the Q&A card."* Ratified data, checked by the same guard as `speakable`, and deliberately NOT derived from it. `False` for both expediters, whose only argument is a job id produced by a job that already failed.

Add **`GET /api/v2/agents`**, a pure projection of `REGISTRY`:

```json
{
  "agents": [
    { "command": "agent router go to weather", "label": "weather", "cls": "conversational",
      "description": "Weather queries", "speakable": true, "aliases": ["weather"],
      "required_args": ["location"], "arg_questions": {"location": "What location?"} },
    { "command": "agent router go to deep research", "label": "Deep Research", "cls": "agentic",
      "description": "Investigate a topic in depth", "speakable": true, "aliases": [],
      "required_args": ["query"], "arg_questions": {"query": "What should I research?"},
      "job_prefix": "dr" }
  ]
}
```

It takes `crud_enabled` into account exactly as `resolve()` does, so the label a user sees is the label of the agent that will actually run.

### 5.2 The Q&A card renders from it

```mermaid
flowchart TD
    A["Q&A card loads"] --> B["GET /api/v2/agents"]
    B --> C["build the select:<br/>Auto-Route + one optgroup per class"]
    C --> D{"what did the user pick?"}
    D -->|Auto-Route| E["POST /api/v2/ask<br/>{ question }"]
    D -->|a specific agent| F["POST /api/v2/submit<br/>{ command, args }"]
    E --> G{"response.path"}
    F --> G
    G -->|agent / replay| H["render the answer"]
    G -->|needs_input| I["render the arg question inline<br/>in the Q&A card"]
    G -->|receptionist| J["render the fallback"]
    I --> K["POST /api/v2/resume<br/>{ pending_id, answer }"]
    K --> G
```

**The `needs_input` loop is what replaces the Submit panel's forms.** A submit card is a form asking for `query` / `prompt` / `source` / `task` up front. The v2 flow already asks for exactly those, one at a time, from the same contract — it just does it in the response instead of in HTML. The Q&A card grows one inline answer box and inherits every agent's argument interview at once, including agents nobody has built a card for.

### 5.2a 🔴 A picked receptionist has no served path — Mr Radio's blocker 2

Ruling 3 kept the receptionist in the list. **The plan carried that exception only as far as the dropdown, and the hole is in the routing.**

**Measured at `9b49f04d`**: the spec is `AgentSpec( "agent router go to receptionist", cls=CommandClass.NONE, speakable=True )` — **`factory=None`**. `resolve()` returns `None` for it by design; `resolve_agentic()` does not serve it either. So when a user *deliberately picks* receptionist and the card posts `{ command: "agent router go to receptionist" }`, **nothing in this plan says what serves it.**

Two candidate behaviours exist today and they are not the same system:

| door | what happens | why it is wrong for a deliberate pick |
|---|---|---|
| `ask()` | falls through to the receptionist via `test_resolve_none_degrades_to_receptionist` | reaches the right place **down the failure path** — a deliberate choice arrives as an error outcome |
| `submit()` | a command neither reader resolves is **refused** (cf. `test_an_unknown_task_type_is_refused_and_queues_nothing`) | the user picked a real destination and gets a refusal |

**And the signal that gets destroyed is one the card actually renders.** `AskResponse.path` is `replay | agent | needs_input | receptionist`. A chosen receptionist and a routing failure would both arrive as `path="receptionist"` — so the field conflates *"you asked for this"* with *"we could not route you."* That is precisely the distinction the Q&A card shows differently, which is why this is a routing decision and not a cosmetic one.

**My recommendation**: give the receptionist an **explicit served path**, so the two are distinguishable in the response. The cheap shape is a `route_reason` that says which one it was (`receptionist_chosen` vs the existing `unknown_command` / `router_error`) while `path` stays `receptionist` — no new terminal path, no change to what the card already knows how to render, and the one bit of information that was being lost is carried.

⚠️ **Note what does NOT fix it**: simply hanging a `factory` on the spec. `resolve()` reads `ANSWER_COMMANDS`, which is the `CONVERSATIONAL` projection — a `CommandClass.NONE` spec is not in it, so a factory there is never reached. Either the flow branches on the command explicitly, or the spec's class changes — and changing its class has consequences for the router that want their own thought.

**This is one line of decision and it is owed BEFORE phase 3, not during it.** It is tracked as row `1568269d`, filed by Mr Radio; that row owns the ruling, not this document.

**THE HOLE MY REWRITE STILL HAD — empty versus empty.** I specified a set-equality and stopped. **Set-equality between two empty sets passes:**

> an emptied HTML file yields `expected == set()`, an errored endpoint yields `rendered == set()`, and the gate goes green on both being broken at once.

That is precisely the failure this section exists to prevent, and my version shipped it. The built predicate **refuses an empty oracle before it ever compares** — `ORACLE EMPTY` is an arm, not an assumption (`test_empty_oracle_is_refused_not_passed`, `test_empty_render_against_a_real_oracle_is_red`).

### The part that is cleverer than anything I wrote: the oracle moves, and the predicate makes it move
Before phase 3, the checked-in `<option>` values in `notifications.html` **are** the source of truth, so the live guard compares rendered DOM against the file on disk — browser versus tree, a real boundary. **Phase 3 empties that file, and `ORACLE EMPTY` fires the moment it does**: the guard goes red until whoever lands phase 3 repoints `expected` at `USER_INITIABLE_COMMANDS`. **The sequencing enforces itself instead of depending on somebody remembering.**

### And it found three vacuous tests already in the tree
Five tests touched `#agent-mode`; **three could not fail** — `assert options.count() >= 2`, another count, and two `if is_visible():` wrappers that turn *"the select did not render"* into a **skip reported as green**. Phase 3 makes that select JS-populated, so an endpoint 500 yields an empty select and all three pass. **The safety net had a hole shaped exactly like the change it was meant to catch.** Killed in `d643f1c4`.

### Still not a gate
"The dropdown has 16 options." A count over a list derived from the registry cannot fail unless a set-equality would have failed first. Ruled 2026-08-15 — and my own first draft of gate 3 broke that rule *inside the section that states it*, which is why this note stays.

### 🔴 PHASE 5 IS A FLEET PROTOCOL CHANGE, NOT A DOOR RETIREMENT — Mr Radio's blocker 4, ruled by Rick 2026-08-22

**RULED: keep it in scope, and update `CLAUDE.md` and `CLAUDE.local.md` in the SAME change.** Rick's reasoning: one coherent change, the panel actually empties, and nobody is left following a stale instruction because the instruction moves with the code.

**What makes it different from the ten retirements already done.** Each of those was a route with a handful of callers inside this repo. `/api/test-suite/submit` is named in both CLAUDE files as **the ONLY sanctioned way to schedule work on `:8000`** — the fleet's single test venue. The venue rules say it in as many words: integration steps and anything that spends inference go to `:8000` *scheduled via `POST /api/test-suite/submit`*. Every session in the fleet is following that instruction right now.

**⚠️ THE ORDERING GATE — this is the part that can go wrong, and it is not optional.**

`/api/v2/submit` carries `scheduled_at`, `monopolize` and `parent_id_hash` as top-level fields, and those exist precisely so it can do this job. But **that path has never carried a real scheduled `:8000` test run.** So:

> **The replacement must be PROVEN to schedule before the old door dies.** One real test-suite job submitted through `/api/v2/submit` with `scheduled_at` set, landing and running on `:8000`, with its `ts-` id as the receipt. Only then does `/api/test-suite/submit` become a 410, and only in the same commit that rewrites both CLAUDE files.

Retire it first and the fleet loses its only sanctioned test route at once — mid-sprint, with a training run in the same window. The proof run is cheap; the wrong order is not recoverable by a revert, because the instruction and the route would already have parted company in everyone's context.

**Where this came from, recorded because the miss is instructive**: I wrote phase 5 as *"one door retirement, the same shape as the ten already done."* I had read the door's callers and not its standing. Mr Radio caught it. Same habit as the CSS-class error in §2 — matching on the local evidence and reporting about the wider fact.

## 8. 🔴 Three questions for Rick — two of them change the shape

**Q1. Does the Broadcast card go too?** — ❌ **The question was invalid.** It is not in the Submit Agentic Jobs section; it never was. See the correction in §2.

**Q2. Sticky mode, or a per-request route?**
Today the dropdown sets a **sticky server-side mode** that persists until cleared. Rick's words were *"dial in a specific direct route to a specific agent"* — which reads per-request. The 2026-08-21 ruling kept user mode ("the queue resolves it first"), so both can coexist: the select could set sticky mode as it does now, or send `command` on one request and revert to auto. **My recommendation: per-request.** A submit card was always a one-shot — "run this one job" — and making the replacement sticky changes the behaviour people are used to. But mode stays for voice, exactly as ruled.

**Q3. Does `receptionist` stay in the dropdown?** — ✅ **RULED: yes, unchanged.** My recommendation here was to drop it, and it was wrong. See the rulings block at the top of this document for what replaced it and why.
