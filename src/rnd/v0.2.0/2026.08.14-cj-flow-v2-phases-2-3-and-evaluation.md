## 1. The decision this experiment exists to make — written before the data exists

Rick's framing: build v2 small, **"test it rigorously and evaluate it to see if it's worth further
investment to add on all the other bells and whistles."**

So the deliverable is not the code. **The deliverable is a decision**, and a decision needs its
criteria fixed *before* the numbers arrive. Written after, they get fitted to whatever came back.

> **The failure mode this section exists to prevent** is not hypothetical here: a prior run in this
> repo pre-registered a metric and then did not use it when the results came in. Pre-registering is
> not enough on its own — so each criterion below names **who checks it** and **what artifact proves
> it**, and the eval harness prints the table with a verdict column filled in. A criterion that only
> a human remembers to apply is a criterion that gets skipped.

### 1.1 The two metrics Rick named, with margins

| Metric | Measured how | Bar |
|---|---|---|
| **Latency to first useful response** | `t_first_useful − t_recv`, p50 and p95, v2 vs v1 over the **same corpus** in the **same session** | v2 p50 must beat v1 p50 by **≥ 20%**, and v2 p95 must not be worse than v1 p95 |
| **Cache-hit rate** | warm pass over the corpus; hit = replay branch taken **and** replay produced an answer | v2 ≥ v1 on the same corpus, and the **absolute number must be reported**, not just the delta |

⚠️ **A margin, not a direction.** "Faster" is not a result — an 8% p50 improvement across a corpus of a
few hundred utterances against LLM calls that vary by more than that is noise wearing a number's
clothes. 20% is the pre-registered line; if the crew wants a different one, it is changed **before**
the first run, in this document, with a reason.

⚠️ **p95 is in the bar on purpose.** A design that is faster on average and occasionally much slower
is worse to use than the average says, and the park-and-resume path is exactly where a long tail
would hide.

### 1.2 The floors — criteria that can only fail, never win

These do not make v2 worth investing in. They make it **eligible**. Any one of them failing ends the
evaluation regardless of how good the two headline numbers look.

| Floor | Bar | Why it's a floor |
|---|---|---|
| **Routing accuracy** | v2 ≥ v1 on the shared corpus, whose JSON keys are the expected commands | Faster wrong answers are not an improvement. This is the one that a cold model server silently breaks — everything falls to the receptionist while latency looks *better* |
| **Replay correctness** | a hand-checked sample of cache hits, ≥ 30 utterances, **zero** answers to a materially different question | Cache-hit rate is only a virtue if the replayed answer was right. Optimising a hit rate without this is optimising for being wrong faster |
| **No new silent failures** | every degradation path (`router_error`, `extract_error`, `replay_failed`, `agent_error`) appears in the trace with a distinct value | The four worst failures in the v1 survey all read as success. v2 does not get to add a fifth |
| **v1 untouched** | v1's existing suites green; `expedite()` output unchanged | Non-destructiveness is the premise of the whole exercise |

### 1.3 The criterion Rick actually complained about, and how to measure it

His words about the current implementation: *"full of bugs"* and *"ad hoc bolt-ons added across
time."* Neither headline metric captures that, and it is the real reason for the rebuild.

**Measure the control logic itself.** Count the statements on the request path — intake through agent
dispatch — for v1 and for v2:

| Quantity | v1 | v2 target |
|---|---|---|
| Statements on the request path | `push_job` alone is ~700 lines | **the flow ≤ 200** |
| Distinct command→agent mechanisms | **3**, and they disagree | **1** |
| Cache lookups per request | **2**, in two files | **1** |
| Places a request can block on a human | 2 (confirmation dialogue, interactive args) | **0** — the endpoint returns instead |

**This is a real number, not a vibe** — `ast` walks both paths and counts. And it is falsifiable in the
direction that matters: **if v2's flow lands over 200 lines, the "minimal control logic" claim failed**,
whatever the latency did. Say so in the report rather than quietly widening the target.

### 1.4 What a STOP looks like

Naming this now is the point of the section. **v2 does not earn further investment if**:

- it is not meaningfully faster (§1.1 margins unmet), **and**
- its control logic is not meaningfully smaller (§1.3 unmet).

Either one alone earns a conversation. **Neither one means stop**, and the phase-1 code stays as a
parallel curiosity rather than growing bells and whistles. That outcome is a successful experiment,
not a failure — it cost one day and it answered the question.

**And one result would be better than a win**: if v2 turns out *not* faster but *much* simpler, the
right move is probably to port v2's structure onto v1 rather than to keep two flows. Worth saying out
loud in advance, because it is the conclusion nobody reaches after they have built something.

### 1.4a The corpus — measured, and the sampling rule that follows

The phase-1 plan asserted that routing accuracy "comes out for free" from an existing corpus. **That
now has numbers behind it rather than a claim**, and the picture is better than assumed: every one of
the six phase-1 agents has a mapped corpus file, and the JSON key *is* the expected command.

| command | utterances | | command | utterances |
|---|---|---|---|---|
| calculator | 561 | | weather | 267 |
| todo | 527 | | calendar | 232 |
| math | 495 | | datetime | 127 |
| `none` | 524 | | receptionist | 175 |

**2,209 across the six agents, 2,908 including the two fallback paths.** Weather's 267 is ample for
the argument-chain demonstration.

⚠️ **A cost problem the plan did not have.** Two passes over 2,908 utterances is ~5,800 requests,
every one of them at least a router call and most an agent LLM call. That is not a run anybody
executes casually, and an eval nobody re-runs stops being an instrument.

**The sampling rule, pre-declared so it is not chosen after seeing results**: draw **n = 60 per
command, stratified, seeded** — every command contributes equally regardless of its file size, and the
seed is recorded in the report so a re-run is the same sample. That is ~480 utterances per pass, ~960
for the cold/warm pair. Full-corpus mode stays available behind a flag for a release run.

**Why stratified matters here specifically**: calculator has 4.4× datetime's utterances. Pooling
unweighted would let calculator's behavior dominate a "routing accuracy" number that reads as
system-wide, and the three smallest commands — the ones most likely to be weak — would be the least
visible.

⚠️ **Also verified, since a broken cross-check nearly put the opposite in this document**: the agentic
entries in the training JSON are objects carrying a `template_file` key, not bare path strings. A
naive comparison reads them as unreferenced and concludes ten corpora are orphaned. They are not.

### 1.4b 🔴 Three corrections to §1 from Rachel's review — all mine, all load-bearing

**(1) The harness cannot machine-decide the replay-correctness floor, and §1.5 pretended it could.**
§1.2 asks for a hand-checked sample; §1.5 said the harness fills in every verdict. Those contradict —
and a contradiction resolves itself the lazy way: the column gets filled with whatever is automatable
and the floor quietly becomes something weaker.

⇒ **Every row carries an `EXECUTOR`, and the two kinds are not interchangeable.** The automated
command-match oracle (R-C2) is a **one-way pre-filter**: if the matched snapshot's routing command
differs from the utterance's expected command, that replay **is** wrong — machine-decidable, and it can
only ever **FAIL** a row. If it agrees, the row is **not** thereby passed: the same command with a
different city is still the wrong answer, and only a human sees that. **The floor stays
`EXECUTOR: HUMAN` and the harness prints `PENDING HUMAN`, never a checkmark.** *A row marked PASS
because nobody could check it is worse than a blank.*

**(2) There was no STOP row, and the floors were not marked as vetoes.** §1.4 defines a STOP; the table
never computed one. As written, a report could show both headline metrics passing while a floor had
failed, and **nothing in the output would say the verdict is STOP** — the reader sees green.

⇒ **Floors are VETOES**: any floor at FAIL forces the overall verdict to STOP regardless of the
headline rows. And the table gains a final **`OVERALL`** line stating `INVEST` / `STOP` /
`SPLIT — port the shape`, computed from §1.4, **so the decision is printed rather than inferred.**

**(3) p95 from n=60, unpaired, can flip the verdict on one tail outlier.** At n=60 the 95th percentile
is about the third-largest value — a single slow LLM call moves it. Drawing independent samples per arm
then carries **both** arms' noise on a metric that is already unstable. I stated a margin as if the
measurement were steady. It is not.

⇒ **Three changes, costing nothing but discipline:**
- **Pair the design** — same utterances, same seed, both arms. Every comparison becomes a per-utterance
  delta, removing between-sample variance entirely. The largest cheap win available, and it should have
  been there from the start.
- **Gate on the paired median delta**, which is robust to exactly the tail that makes p95 unstable. The
  ≥20% bar is restated against it.
- **p95 is REPORTED, not GATING, at this n.** It stays in the table — the tail is where park-and-resume
  would hide — labelled `INFORMATIONAL (n too small to gate)`. Promoting it to a gate needs a larger n,
  declared before the run. *A gate nobody can trust gets argued with after the fact, which is the exact
  failure this section exists to prevent.*

### 1.5 What the harness must print

The report ends with this table. **Machine rows are filled by the harness; human rows print
`PENDING HUMAN` until a person signs them.**

```
CRITERION                        BAR                 EXECUTOR  MEASURED  VERDICT
latency p50, paired median Δ     ≥20% better         AI        …         PASS/FAIL
latency p95                      informational       AI        …         (n too small to gate)
cache-hit rate (warm)            ≥ v1                AI        …         PASS/FAIL
routing accuracy                 ≥ v1                AI        …         FLOOR·VETO PASS/FAIL
replay correctness (n≥30)        zero wrong          HUMAN     …         FLOOR·VETO PASS/PENDING HUMAN
  └ command-match pre-filter     zero mismatches     AI        …         may only FAIL the row above
degradation paths distinct       all 6 present       AI        …         FLOOR·VETO PASS/FAIL
v1 suites green                  green               AI        …         FLOOR·VETO PASS/FAIL
flow control-logic size          ≤200 stmts          AI        …         PASS/FAIL
command→agent mechanisms         1                   AI        …         PASS/FAIL
─────────────────────────────────────────────────────────────────────────────────
OVERALL                          §1.4 decision rule  AI        …         INVEST / STOP / SPLIT
      any FLOOR·VETO at FAIL ⇒ OVERALL = STOP, whatever the rows above say
      any FLOOR·VETO at PENDING HUMAN ⇒ OVERALL = PENDING, never INVEST
```

A verdict column the harness fills in is the difference between a criterion and a note — **and an
`EXECUTOR` column is the difference between a verdict and a guess.**

## 1a. Rulings made during the build, superseding the phase-1 text

The phase-1 document is frozen under cascade review, so decisions taken while building land here and
are merged into it when the cascade returns.

**`extract()` takes a REQUIRED argument spec, with no fallback to the registry table.** Cheech ruled
it, Mr Radio built it, it is green, and **I withdrew the opposite position** — I had proposed an
optional parameter falling back to a table lookup when absent.

**Why the ruling is right and mine was not.** Optional-with-fallback leaves the `AGENTIC_AGENTS`
lookup living *inside* `extract()` — which is precisely the coupling this work exists to delete, kept
alive in the function meant to replace it. Required pushes the lookup up into `expedite()`, where it
is legacy code that **dies when `expedite()` dies**. Mine was the more conservative change and the
structurally worse one.

**The condition that still holds**: `expedite()` builds the spec from the table itself, so v1 callers
behave identically — pinned by the existing `expedite()`-output test.

**`collect()` takes the spec required as well, for the identical reason.** Tiberius measured the split
during review: `extract()` reads **six** fields off the registry entry and `collect()` reads **two**
more. The phase-1 text noticed that `collect()` still touches the table and then under-specified what
to do about it — one rule covers both halves, not just the one that happened to get written down.

**Consequence for the weather case**: a fake `AGENTIC_AGENTS` entry for weather was proposed as a way
to make it reachable inside the first commit, and **rejected** — it would put a lightweight
conversational agent into the table built for the ten heavy jobs, deepening the mess phase 2 removes.
Weather is simply not reachable in the shared-file refactor commit, which is correct rather than a gap.

## 2. Phase 2 — the queued executor

**Decision: v2 gets its own four queue instances, subclassing `FifoQueue`. The UI split is closed at
the router, not by sharing queue objects.**

### Why not reuse v1's queues

The assumed benefit turns out to be mostly absent, and the costs are concrete.

**Job cards are free either way** — `JobStore.ts:355-391` creates a card on first sight of any unknown
job id and maps states through a table that knows nothing about v1 or v2. This is the biggest assumed
benefit of reuse and it is not a benefit at all. **Persistence is not inherited either**:
`emit_job_state_transition` persists only for agentic job types (`queue_util.py:91`), and none of v2's
six commands qualify.

What reuse would cost:

| Cost | Where |
|---|---|
| The known trap — a second cache lookup re-decides v2's verdict against a *different* threshold | `running_fifo_queue.py:273-297`, threshold at `:74` |
| **Monopolize deferral** — an unrelated test sweep can defer a v2 request by up to **300 s** | `queue_consumer.py:106-125`; `lupin-app.ini:976` |
| Untagged write-back — the `flow_version="v2"` tag never lands | `running_fifo_queue.py:1588` |
| A 60-second human yes/no fired on **every** serialized snapshot — 200 prompts per eval corpus | `:1765` |

Monopolize deferral is the one nobody had named, and it is disqualifying on its own: latency to first
useful response is a headline metric, and sharing the lane makes it a function of what else the server
happens to be doing.

### The honest cost of our own queues

~250 lines that structurally rhyme with v1's, one more dispatcher thread, one more shutdown ordering
constraint, and ~15 lines in `routers/queues.py` so the hydration endpoint's `queue_map` (`:461-466`)
can see v2 — **the one place the "own classes" decision costs real work.** Without it, v2 jobs vanish
on page reload while working fine over the live socket.

**A hard scope line, written down**: the v2 lane handles fast-lane work only. When agentic commands
arrive, v2 **hands them to v1's queue** rather than growing a monopolize gate — rebuilding that
machinery in v2 recreates exactly what this exists to escape.

### `QueuedExecutor.submit()`

Guard `user_email` first (at dispatch there is no response left to 400, and a dropped notification
reads as a successful job) → **mint a fresh job id** → register the scoped id *before* the push →
register the trace in a **side table keyed by scoped id** → mark `t_enqueue` → push → return
`status="parked"` with the job id. It never raises.

**Two decisions carry the design:**

**The job id must be fresh.** v1's replay path registers the *original snapshot's* hash
(`todo_fifo_queue.py:901`, after a `copy.copy` that preserves `id_hash` — `solution_snapshot.py:662`),
so the same user replaying the same cached snapshot produces an **identical scoped id every time**.
`FifoQueue.push` overwrites `queue_dict[id_hash]` while appending to `queue_list`
(`fifo_queue.py:162-165`), and the orphan is later discarded with a "stale job in queue_list" warning
(`:262-265`) — a bolt-on that *hides* the drop. **The eval's warm pass replays the same questions as
the same user, which is precisely the trigger.** v2 mints a per-request id and carries the snapshot's
hash separately as `snapshot_id`.

**The trace lives in a side registry, not on the job.** `SolutionSnapshot.create(running_job)`
(`running_fifo_queue.py:1568`) produces a **new object**, so a trace attached to the job is dropped —
and only on the snapshotable path, which is the cache path. That is the worst possible bias.

**Add `t_enqueue` and `t_dequeue`.** Under a queue, first-useful latency now contains queue wait;
without these two marks the executor flip reads as a latency regression nobody can attribute.

### The four queues, and what is deliberately dropped

**todo** carries a *decision* (a snapshot copy, a constructed agent, or the receptionist), not a
question — the structural inversion from v1, where `push_job` carries a raw question and makes every
decision inside itself. **running** starts at width **1**. **done** and **dead** are bounded rings —
v1's are never trimmed, so every job the server ever completed stays resident (`main.py:765-766`).

**Neither `STALLED` nor the ghost-job sweeper is carried over.** `STALLED` exists to preserve an
agentic checkpoint for resume (`running_fifo_queue.py:696`); none of v2's agents checkpoint, and
mapping "waiting on a human" onto it would be wrong twice — its legal transitions are
`{RUNNING, CANCELLED}` (`job_state.py:54`), and the card would render a Resume button wired to a
checkpoint that does not exist. **Use `PAUSED`.** The sweeper detects a state only the thread pool
creates; a synchronous dispatcher cannot produce it. v2 needs a plain **wall-clock watchdog** instead
— that catches a hung LLM call, which is its actual hang risk.

### `needs_input`, natively

The parked job lives **in the v2 todo queue in `PAUSED`**, not in a side dict — one place to look, one
place the UI reads, one eviction path. `PENDING → PAUSED → QUEUED` is already legal
(`job_state.py:46`, `:52`). The dispatcher skips paused jobs with the single clause that already
exists at `fifo_queue.py:234`. A small **collector pool** runs the human wait.

Note the irony plainly: v2 does end up with one pool — for *human waits*, not for work.

⚠️ **New hazard the inline version does not have**: a parked job now has a **card on the client**.
After a restart the card sits there with no server-side job behind it. Verify before flipping the key
that the client **replaces rather than merges** on hydrate; if it merges, the card is immortal.

### Flipping, and flipping back

**The acceptance test for the seam is that `AskFlow.run()` is untouched.** If flipping requires
editing the flow, the seam failed — revert, do not patch.

**Keep the dispatcher running unconditionally**; let the key choose only which executor the flow
receives. Gating the dispatcher on the key strands everything already queued with nothing to drain it.
One idle thread beats drain logic — that is the whole lesson of v1's conditional plumbing.

**Parked jobs are the real cost of a flip-back.** Resolve the executor **once, at park time**, and
store it with the job; resolving it at resume time silently switches delivery mechanism mid-conversation.

⚠️ **The most likely thing to be forgotten**: the eval harness reads `answer` from the response. Under
`queued` that is `None` and status is `"parked"`. It must poll or read the trace JSONL — **and it
fails as an all-zeros report rather than an error.**

## 3. Phase 2/3 — one argument interface across every agent

**Rick's north star.** Four findings moved the design away from the obvious answer.

### What the survey overturned

**(a) "The CLI is the source of truth" is already 40% false.** Three of ten `cli_module` values name
packages with **no `__main__.py`** — `claude_code`, `bug_fix_expediter`, `test_fix_expediter`. They
were run; all three exit 1. `get_cli_help` returns `stdout or stderr or ""` (`agent_registry.py:359`)
and **caches it**, so `"No module named …"` is cached as that agent's help text and injected into the
phi4 extraction prompt. A fourth has no CLI by design. **Only six agents have a runnable CLI.**

**(b) Where the CLI does answer, it is not derived from argparse anyway** — five modules carry a
hand-maintained `USER_VISIBLE_ARGS` list and `swe_team` hardcodes it at the print site. Nobody
introspects a parser today.

**(c) `MODE_TO_AGENT`'s values are already dead** — only `.keys()` is ever read. Seven agent classes
are imported at `todo_fifo_queue.py:11-19` to spell seven strings.

**(d) `create_agentic_job` has 15+ call sites**, not one. Any "single dispatch path" requiring all of
them to change will not land.

### The declaration

A leaf module `src/cosa/agents/arg_spec.py` importing nothing but stdlib, carrying `ArgDecl`
(name, required, system, type, help, question, default, aliases, handler, ctor_kwarg) and `ArgSpec`
with the eight accessors that replace every `agent_entry` read in the expeditor.

**A classmethod, not a class attribute or a decorator** — `hasattr(x, "declared_args")` is already the
migration flag phase 1 committed to, and a classmethod can consult config at call time where an
import-time attribute cannot. A decorator would need import-time registration, reintroducing the
implicit global registry this work exists to delete.

**`as_registry_entry()` is the load-bearing method** — it emits exactly the `AGENTIC_AGENTS` row
shape, which buys three things at once: the expeditor consumes a declaration with no code change
during migration, the equivalence test is one dict comparison, and **a revert is deleting a file**.

**Hand-written declarations, and invert the CLI dependency** — the CLI derives *from* the declaration,
not the reverse. Deriving from argparse gets the cheap 30% (name, required, help, default) and **none**
of `system_provided`, the LoRA aliases, the *spoken* fallback questions, the voice-shaped defaults, or
the special handlers — so you hand-write the rest in a second place, which is the disease, not the cure.

**The declaration lives in `<agent>/args.py`, not on the job class** — `hasattr(factory, …)` forces the
factory to resolve, and resolving `ClaudeCodeJob` imports the Claude SDK. Asking what arguments an
agent needs must not cost that.

### Migration — per agent, reversible, with a self-parametrizing net

**`AGENTIC_AGENTS` stays byte-identical for the entire migration.** A half-emptied dict makes
`expeditor.py:222` return `None` for a migrated-and-deleted command and silently kills it.

A migration unit is three files; **a revert is deleting one of them.** Plus an INI key so reversibility
does not mean a deploy. Which agents have migrated is **computed, never documented** —
`GET /api/v2/agents` returns each agent with a `source` field that is literally the resolution order.
**That endpoint is also the direct answer to Rick's requirement**: any agent can be queried for what it
requires and what is optional.

The equivalence test is **parametrized at collection time over the intersection** of declared and
tabled commands — zero cases before the first migration, each new declaration picked up automatically,
no checklist. **It will fail on first run for `research to presentation`** (its CLI publishes seven
names, its fallback questions have four) — **and that failure is a finding, not a bug in the test.**

Stronger still, a **behavioral** test: run each command's training utterances through `extract()`
twice, once via the table and once via the declaration, with the LLM mocked, and assert identical
`(final_args, missing)`. That catches alias ordering and default injection differences a field diff
misses.

### The single dispatch path

`build_job(command, args, user_id, user_email, session_id)` with **typed exceptions**, not `None` —
`create_agentic_job` returns `None` on unknown and each of its 15 call sites re-implements that check
differently. It lands **without touching those call sites**: `create_agentic_job` becomes a four-line
shim that catches and returns `None`.

**Keyword-only construction, always.** Phase 1 called the six conversational constructors "identical" —
true by keyword, **false by position**: `WeatherAgent` leads with `prepend_date_and_time`
(`weather_agent.py:18`) and `CalendaringAgent` orders its first five differently
(`calendaring_agent.py:15`). A positional call would pass the question as `prepend_date_and_time`.
Enforce with a signature-introspection test.

**Never pass `routing_command`** — each subclass defaults it correctly and `AgentBase` uses it as a
config lookup key. That is the honest handling of `todo`/`todo list` and `date and time`/`datetime`,
where two spellings share one agent.

**The agentic half stays honest rather than uniform.** The twelve factory branches do four things;
name translation and type coercion are expressible in the declaration, but **shape construction**
(RecipientSpec lists, a `shlex.split` that deliberately *raises* on unbalanced quotes) and **hardcoded
non-arg values** are not. So the base class gets a `from_args` classmethod whose default is generic,
and the four agents with irreducible construction **override it with the body lifted verbatim**. No
`if command ==` survives anywhere, each exception is a named method on the class that owns it, and
**the override count is a number you can watch go down.**

`MODE_TO_AGENT`, `AGENTIC_MODE_MAP` and `MODE_METADATA` collapse into two optional fields and become
derived names — which **structurally kills** the bug guarded by the nine-line comment at
`todo_fifo_queue.py:661-669`.

### Risks that would silently change behavior

1. **MathAgent's asymmetry is not cosmetic.** It alone gets `question=salutation_plus_question`
   (`:720`). Formatting is unaffected, but `question` is what a snapshot keys on and **v2's cache tier
   1 is SQL equality on `question`** — so uniform dispatch **invalidates every existing math
   snapshot's exact-match tier.** Count them before flipping.
2. **`system_provided` is decorative for 9 of 10 agents** — the factory takes identity as its own
   parameters and ignores the dict's copies. Modelling `system=True` as "inject into the constructor"
   would start passing values that have always been discarded. Model it as **"never ask, never show"**
   and nothing else.
3. **Three agents' phi4 input is currently an error message.** Migrating them replaces it with real
   help text — extraction quality will move, probably up, but this is **not a no-op** and cannot be
   validated by "the tests still pass."
4. **`user_visible` order is behavior** — it drives the batch question order, and one agent's CLI
   order already differs from its fallback-questions order, so it asks differently depending on
   whether a subprocess succeeded.
5. **Aliases collide across agents** — `topic` means `query` for one agent and `research` for another;
   `prompt` means `prompt` for one and `task` for another. Keep aliases scoped to their spec; a global
   alias table collapses them.

## 4. Phase 3 — creating a new agent

### The finding that reframes it

**Generating a solution on the fly and caching it is already built.** The system generates code from
an LLM (`agent_base.py:283`), runs it (`:319`), repairs it across multiple LLMs on failure
(`:355-405`), recasts it to a snapshot (`running_fifo_queue.py:1570`), and replays it later with **no
code generation at all**. That is not phase 3; it shipped.

What is missing: **every generation today happens inside a routing command's prompt template.** There
is no path where the system concludes "no template covers this" and proceeds anyway. That is a
**capability gap** — distinct from an intent gap (→ receptionist) and an argument gap (→ `needs_input`).

### The routing constraint, which is the whole problem

| Fact | Evidence |
|---|---|
| The router is a **merged and quantized** model, not a hot-swappable adapter | `lupin-app.ini:148`, `:295` |
| Retrain cost | **3-4 hours** (`peft_trainer.py:2493`), then merge, quantize, env rewrite, vLLM restart |
| **No confidence signal exists** | the router returns `(command, args)` only; the validator deliberately never rejects; zero logprob references anywhere in the tree |

**The load-bearing observation**: the runtime prompt list and the training vocabulary **have already
drifted** — the runtime file omits three commands the model was trained on, and the system works
anyway. That is direct evidence **the vocabulary lives in the weights, not the prompt list**, so
adding a line to the prompt file almost certainly does not make a new command routable.

**"Almost certainly" is not good enough to design on.** Phase 3 opens with a one-afternoon probe:
insert a plausible fake command into the runtime list, send ~50 matching utterances, count emissions.
**That single number decides whether a new command costs a text edit or four GPU hours**, so it runs
first.

**Two things are already free, and they change the shape of the answer**: the `none` command already
exists and already routes to the receptionist, so the branch can hang off it at zero cost; and **the
mode dropdown is already a complete non-LoRA routing path** — a new agent given a mode key is usable
**the day it merges**, by name. That is the cheapest answer to the routing problem and it is already
built.

### The recommendation — split in two

| | What | Why |
|---|---|---|
| **The runtime branch** | **One** `GenericQuestionAgent` — an ordinary `AgentBase` subclass with a schema-free prompt, snapshotable | Answers the user *this turn*, produces cache hits on repeats, and costs **one** router command rather than one per capability |
| **The offline pipeline** | When the generic agent keeps handling the same *kind* of question, a bounded Claude Code job drafts a real agent as a **branch and a pull request** | Durable capability, human-gated, off the request path |

**Agent synthesis is an offline promotion pipeline seeded by what the generic agent actually saw.**
That turns the router constraint from a blocker into a scheduling problem and guarantees the system
never builds an agent nobody asked for twice.

**Runtime registration is rejected explicitly.** Keeping the registry in source control **is** the
review gate; a runtime `register_agent()` deletes the gate to save writing a file.

The predicate: the router returned a command that **does not resolve**, *and* a small-model classifier
says the utterance is a request for work rather than conversation. Classifier failure **falls to the
receptionist, never to code generation** — fail closed.

### 🔴 The safety finding — and it is live today, not a phase-3 concern

**Generated code runs with no isolation at all.** `assemble_and_run_solution`
(`util_code_runner.py:247`) writes to a **single shared path** `/io/code.py` (`lupin-app.ini:490`) and
runs it as the same OS user as the server, with a 60-second timeout and nothing else.

**Two concurrent jobs overwrite each other's file.** That is a correctness bug **today**, and a
confused-deputy problem the moment the input becomes open-ended. Filed separately.

**Snapshot lookup is not user-scoped** — `user_id` is a column on the table but no repository method
filters on it, so code generated for one user is replayable for another.

**The only correctness gate is advisory** — the yes/no fires *after* the code already ran and leaves
the verdict null on timeout. A satisfaction survey, not a review gate.

**Two hardenings are prerequisites for phase 3**, because phase 3 is what makes the input open-ended:
a **per-job code file** instead of the shared one, and **generic snapshots replayable only by their
creator** until verified. A third is worth adding: a **static check of generated code before
execution** — deny `subprocess`, `os.system`, `shutil`, writes outside `/io`, network modules. Cheap,
deterministic, and the difference between "we trust the prompt" and "we don't have to."

### The minimum viable version, and what it must not claim

Classifier + `GenericQuestionAgent` + trace logging + a `generic` path. Reachable three ways on day
one, **none of them needing the model**: the classifier branch, a mode key, and a direct call with the
command supplied. Every `doable` verdict logged with the raw utterance — **that log is the corpus for
the promotion pipeline and the demand signal**.

⚠️ **Framing discipline**: this is *"the system answers things it has no agent for, and remembers the
answer."* It is **not** *"the system writes new agents."* Letting the demo blur those two is the main
way this looks like it works while not working.

**Stop condition, pre-registered**: if the demand-mining stage finds nothing that clusters, **stop —
that is the honest answer**, and no synthesis gets built.

### The risk that names itself

**Agents nobody can route to.** Mitigated structurally, not procedurally: an agent is not "done"
until it has a **mode key**, so it is usable without the model; the registry guard test **fails the
build** if an entry lacks either a router command or a mode key; and the pending-command queue is
surfaced in the stats endpoint so "3 agents waiting on a retrain" is a number someone sees.

**And a retrain can silently degrade the other 19 commands** — nothing measures per-command accuracy
today. The phase-1 eval harness already computes routing accuracy for free; **make a per-command table
the promotion gate for any new router build**, or phase 3.4 can quietly cost more than it adds.

### One closing note on Rick's own sentence — see §5 for what follows the verdict

His else has three conditions: intent unascertainable **and** no pre-built solution **and** not
creating a new one. Today the third is **always true by default**, so the receptionist absorbs
everything — which is exactly why the else currently looks like it works. **Phase 3 is the machinery
that makes that third condition decidable.**

## 5. Phase 4 — what happens after the verdict

**The gap this closes**: phases 1–3 build and measure. Nothing says what we *do* with the answer, and
an experiment with no exit plan tends to acquire one by drift — two flows running side by side
indefinitely, because nobody scheduled the day one of them stops.

**Two flows in production is the failure state, not the resting state.** Say that now, while neither
outcome is known and it costs nothing to agree to.

### The three outcomes, and what each triggers

| Verdict (§1.4) | What phase 4 is |
|---|---|
| **v2 wins** — faster *and* simpler | **Cutover.** v2 becomes the front door; v1 is retired on a schedule. |
| **v2 loses** — neither faster nor simpler | **Deletion, with the findings kept.** v2 is removed; the defects it surfaced stay filed and get fixed in v1 on their own merits. |
| **Split** — simpler but not faster (the likely one) | **Port the shape, not the code.** v1 keeps its machinery; v2's *structure* — one registry, one cache lookup, one dispatch path, no blocking on a human — is applied to it. |

**The split outcome deserves the most planning because it is the most likely and the least obvious.**
v2's advantage is structural: it deletes three mechanisms that disagree, one duplicate cache lookup and
two places a request blocks on a human. None of those wins is *latency*, and all of them survive being
transplanted. A design that is not faster is not a failed design if the thing it fixed was never speed.

### If v2 wins — cutover, in the order that keeps it reversible

1. **v2 takes a share of live traffic, not all of it.** A percentage on the existing endpoint,
   defaulting to zero, raised deliberately. Both flows already write to the same tagged snapshot store,
   so a rollback loses nothing.
2. **Agentic commands move last.** v2 hands them to v1's queue by design (§2). Until v2 has its own
   answer for long-running work, v1's queue stays in service *underneath* v2 — which means cutover is
   not "v1 off", it is "v1 no longer the front door."
3. **The three deletions in §3, in their stated order**, each behind its own precondition.
4. **v1's `push_job` is removed only when nothing calls it.** Not on a date.

⚠️ **The trap to name in advance**: a cutover that stops halfway is strictly worse than either end
state — two front doors, two registries, and the drift between them is silent. If the traffic share
stalls below 100% for more than one release, that is a decision to make explicitly, not a state to
live in.

### If v2 loses — delete it, keep what it taught

The four defects found while *planning* v2 are already worth more than a day of work: a question
leaking between users, generated code racing on a shared file path, four command lists that disagree,
and three agents whose extraction prompt is fed an error message. **Those get fixed regardless of the
verdict** — they are v1 bugs, not v2 features.

**Delete the code, keep the eval harness.** The harness measures v1 just as well, and it is the only
instrument in the repo that reports routing accuracy, cache-hit rate and latency together.

### What phase 4 needs that does not exist yet

- **A v1 baseline measured with the same instrument**, taken *before* v2 is finished. Without it, every
  comparison is v2-now against v1-remembered. Cheap, and it expires — take it early.
- **A named decision date.** The verdict is a judgment on numbers, and judgments without a date drift
  into "let's gather more data," which is how two flows become permanent.

### The honest risk in this section

**I am planning the disposal of something nobody has built.** The specifics above will be wrong in
detail. What is worth keeping regardless is the shape: *three outcomes, each with a named consequence,
written before the numbers exist.* The part that would actually cost something to get wrong is having
no plan at all, and discovering in three weeks that v2 is permanent because nobody decided otherwise.

## 4a. 🔴 MEASURED — the routing constraint in §4 is not real

§4 said phase 3's shape is decided by a one-afternoon probe, and treated a 3–4 hour retrain as the
price of a new command. **The probe has now run, and it overturns the premise.**

**Method**: two arms, ten recipe utterances, one invented command (`agent router go to recipe finder`).
The prompt template was modified **in memory against a copy** — the shared file the dev server reads
was never touched. Script kept at `scratchpad/router_vocab_probe.py`.

| arm | invented command emitted |
|---|---|
| **A** — listed in the prompt | **10 / 10** |
| **B** — control: absent from the prompt **and** from the 19-command training vocabulary | **6 / 10** |

Control-arm spread: 6 `recipe finder`, 1 `none`, 1 `presentation generator`, 1 `claude code`, 1 `todo`.

**The control arm is the result.** The router emitted a command that exists in no list anywhere. It is
a completion model following the pattern `agent router go to <thing>`, and it generates a plausible
command from the utterance. **The vocabulary is not closed** — not prompt-bound, and not weight-bound
in the way §4 assumed.

⇒ **Listing a command raises reliability (6 → 10). It does not create the capability.** A new command
is emittable *today*. **What a retrain buys is consistency, not reachability** — a far cheaper problem
than the one §4 planned around, and phase 3's staging should be re-cut against it.

⚠️ **It is also a live defect, filed as `d9ecd69e`.** `CommandResponse.validate_command` deliberately
never rejects an unknown command, so an invented one flows into the dispatch chain, misses every
branch, and lands in the v1 else that **silently web-searches the user's question**. Same wound as row
`30483697` from the other side: the model is not bounded even by the union of the four disagreeing
lists.

**What survives from §4**, and is now better supported: the phase-3 branch predicate — *open when the
returned command does not resolve in the registry* — is correct, and this measurement makes it
**load-bearing rather than an edge case**. It will fire more often than anyone expected.

**What must change**: the v2 registry guard cannot be set-equality against the prompt list, because
**the model's output is not drawn from that set.** And the mode-key path stops being the *only* way to
reach a new agent — it becomes the *reliable* way, which is a different and weaker claim than §4 makes.

### The instrument lied first, and that is worth keeping

**The probe's first run reported "the prompt list does not govern; a new command needs a retrain" with
complete confidence — while every single call was erroring** on an unexpanded environment variable in
the model path. Both arms returned zero emissions, and the verdict logic read identical zeros as a
finding rather than as a dead instrument.

The fix is now in the script and generalizes: **it refuses to render any verdict unless the control arm
produced at least one valid command.** A control arm that produces nothing cannot license a conclusion
in either direction.

*Had that first verdict been reported, it would have confirmed the assumption §4 was already built on —
which is exactly the circumstance in which nobody checks.*

## 6. Phase-2 review: the four findings beyond Rachel's three

Rachel's HIGHs are fixed in §1.4b. These four are Rio's and Tiberius's, and each changes a decision.

### 6.1 The equivalence net cannot judge the three agents worth migrating most (Rio, HIGH)

The self-parametrizing net proves a migration **changed nothing**. But the three agents whose CLI help
is currently a cached `"No module named …"` error string are precisely the ones whose extraction
**legitimately changes** — and sameness is the wrong question to ask about them. They either fail the
gate forever or get migrated unverified, and they have the most to gain.

⇒ **Those three get a different instrument, not a waiver.** Equivalence measures sameness; they need
**improvement measured against a labelled sample**: run their training utterances through `extract()`
before and after, and assert the post-migration args are a **superset** of the correctly-extracted args
— never a regression, improvement allowed. Where the label is ambiguous, the row is
`EXECUTOR: HUMAN`, reviewed as a before/after diff.

They still migrate **last** (§3's order already says so), and now the reason is sharper than "hand-written
is easiest to get wrong": *they are the only three the safety net cannot catch.*

### 6.2 A rule that is true 9 times out of 10 was applied 10 times out of 10 (Rio)

I wrote that `system_provided` is decorative — the factory takes identity as its own parameters and
ignores the dict's copies — and then applied that **universally**. One agent is not decorative, and
under a universal rule it **silently loses a value it consumes**.

⇒ **The rule is per-agent, and the exception is identified before the rule is applied**, not after
something breaks. The declaration's `system=True` still means "never ask, never show"; what it must not
do is authorize dropping a value some agent actually reads. **A 90%-true rule stated as universal is
how the 10% becomes a silent defect** — and it is the same shape as the `MathAgent` asymmetry, which is
the second time today the phrase "all six are identical" hid a real exception.

### 6.3 Phase 3's MVP ships the cross-user replay path ahead of its own prerequisite (Tiberius)

§4 names two hardenings — per-job code file, and generic snapshots replayable only by their creator —
as **prerequisites**. Then its own MVP ships a **snapshotable** generic agent, which *is* the
cross-user replay path. The section contradicts itself, in the direction that ships the risk.

⇒ **Hard gate, not a preference: stage 3.0 lands before 3.1 starts.** Until the creator-scoped replay
is in, the generic agent writes snapshots that are **not eligible for replay at all** — tagged and
stored for the demand-mining corpus, never served. Storing them is the point; serving them is the risk,
and the two are separable.

### 6.4 🔴 The v1 baseline contaminates itself (Tiberius) — the sharpest finding on the evaluation

**Unless write-back is off, the v1 arm writes into the very store the comparison reads from.** And it
is worse than it first looks, because of the two-pass design: the cold pass is only meaningfully cold
if the store does not already hold the answers. **v1's run populates the store that v2's cold pass then
reads**, so v2's "cold" pass is warm, its cache-hit rate is inflated, and its latency looks better —
**every headline number moves in v2's favour, which is the direction nobody would question.**

⇒ **Each arm runs against its own store state, restored to the same starting point.** The mechanism
already exists and I had already written it down for a different purpose: the manager takes its table
name from config, so `v2 snapshot table` gives each arm a clean, identical starting table. What was
listed in §6 as an "escape hatch, available but not default" is **mandatory for the evaluation**.

⚠️ **Note the reversal, so it does not read as a contradiction.** §6 argues *against* an isolated store
— for **production** write-back, where isolation would measure a different population than the one v1
has been filling. For the **evaluation**, isolation is exactly right, because a controlled comparison
needs both arms to start from the same state. *Same mechanism, opposite verdict, because the question
is different.*

**And one honest consequence**: with isolated tables, the eval's absolute cache-hit rate is no longer
the production cache-hit rate — it is the rate this corpus generates from a known starting state. That
is the right number for **comparing** v1 and v2, and the wrong number for reporting "how often the
cache helps Rick." Report both, labelled, and never let the comparison number be quoted as the
production one.

### What Tiberius did that is worth copying

He predicted the out-of-vocabulary emission rate would be **near zero**. The probe came back **6 of
10** — and **he flagged the refutation himself**, against his own finding. The mechanism he identified
survived; his magnitude did not, and he said so before anyone else could.
