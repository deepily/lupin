# Runtime Brake for a Runaway BFE — Design

**Row**: 5251ecf0-75f8-4f82-86f4-49a8a10cba19 (P1, bug)
**Author**: Sam 🎙️ (Mr Radio's crew)
**Date**: 2026-08-13
**Status**: DESIGN — no code written. Bring to Mr Radio before implementation.
**Trigger**: bfe-516bf863 ran 17+ min against a 600s limit, holding an agentic-pool slot, blocking a bounce.

---

## Verdict

The naive shape — "cancel the Future at N seconds" — **does not work** and would make things worse.
Python's `concurrent.futures.Future.cancel()` only succeeds while the task is still *queued*; once a
worker thread is executing, `cancel()` returns `False` and the thread runs to completion. There is no
safe way to kill a running Python thread. So a "preemptive Future cancel" against a hung, already-executing
BFE job is a no-op dressed as a brake.

The honest brake has **three legs**, and all three are required — any one alone is a stall with a nicer traceback:

- **(a) A real timeout at the hang point** — wrap the non-returning SDK call so the hang becomes a catchable exception.
- **(b) A defined handler** — the exception must land in code that transitions the job to `dead` and releases the slot.
- **(c) A status-guarded idempotent slot reclaim** — so a late-completing zombie thread cannot transition or commit onto an already-terminal row.

## Why the two existing flags are not brakes (measured, from the row)

1. `bug fix expediter enabled = false` gates ONLY the auto-detection watchdog
   (`bug_fix_expediter/orchestrator.py:1524`, `rest/watchdogs.py:76`). Nothing in the queue/spawn/exec
   path checks it — a submitted BFE runs regardless. It is not an off-switch for a live job.
2. `bug fix expediter wall clock timeout seconds = 600` IS read → `SafetyGuard(timeout_secs=…)`
   (`shared/fix_executor.py:231`). But `SafetyGuard.check_timeout()` (`swe_team/safety_limits.py:132-142`)
   is **cooperative**: it computes elapsed and raises ONLY when explicitly called *between* fix-loop
   iterations. A job hung inside a single phase — a non-returning SDK call — never reaches the check.

The pool (`rest/running_fifo_queue.py`) has no preemptive per-job kill. The ghost sweeper
(`_ghost_job_sweep_loop`, 30s cadence) dead-letters only futures whose `Future.done()` is already `True`
— it reaps *completed-but-untransitioned* jobs, the inverse of a runaway.

---

## The root cause is the uncatchable hang, so fix it there

The failure is not "the loop check runs too rarely" — it is "the thread never returns to the loop at all,"
because it is blocked inside one SDK call. Therefore the brake must live **at the SDK call**, not in the
outer loop.

### Leg (a): real timeout at the hang point

Wrap the BFE's blocking model call in a hard wall-clock timeout so a non-returning call raises instead of
hanging forever. Two viable mechanisms, decided at build time by whether the call site is async:

- **async path**: `await asyncio.wait_for( sdk_call(), timeout=budget )` → raises `asyncio.TimeoutError`.
- **sync path**: run the call under a bounded executor and `future.result( timeout=budget )`
  → raises `concurrent.futures.TimeoutError`. (Note: this leaks the inner thread if the call truly never
  returns — see Leg (c); the leak is bounded and accounted, the *logical* slot is freed.)

**Timeout value — provenance, so it cannot drift.** The wrapper reads the **SAME existing config key**
the cooperative guard already reads: `bug fix expediter wall clock timeout seconds` (the `600` that today
only *pretends* to be enforced, consumed at `shared/fix_executor.py:231`). Because the wrapper and
`SafetyGuard` read the one key, there is **no second number to disagree with, by construction** — no new
key, no new splainer, no literal `N` in the wrapper to drift from the 600. A hardcoded seconds value in the
wrapper is explicitly prohibited by this design.

**Fallback rule (only if ever needed).** IF a *distinct per-SDK-call* budget is later required — shorter than
the whole-loop budget — THEN it becomes its **own** config key and **ships with its splainer entry in the
same commit**. It is never a literal. This design does not introduce that key; it reuses the loop budget.

**Separate documentation-only reconcile**: the two wall-clock keys — this `600` inner-loop budget vs
`auto fix max wall clock seconds = 1800` (repair-chain budget, `repair_attempt_tracker.py`) — should be
documented so the two are not silently confused. Not a behavior change.

### Leg (b): the handler contract — what the exception DOES

A converted hang that lands in a handler nobody wrote is the same stall. So the handler is specified, not
implied. On catching the timeout exception from Leg (a), the BFE exec path MUST:

1. **Transition the job to `dead`** with a timeout reason, via the existing canonical
   `_transition_to_dead` primitive (`running_fifo_queue.py`) — reusing the primitive, not a bespoke path,
   so normalization/notification are identical to every other death.
2. **Release the pool slot** — remove the job from `_agentic_futures` under `_agentic_futures_lock`, and
   release the monopolize hold if held. This is the accounting that frees capacity for the podcast job.
3. **Leave the row terminal** — `dead` is terminal; the repair-chain tracker (`repair_attempt_tracker.py`)
   must NOT re-arm a new attempt for a timeout death. A brake that trips and immediately respawns the same
   runaway is not a brake.

The handler does NOT attempt to roll back partial work the killed job may have done (see risk analysis) —
it declares the job dead and reclaims the slot, and Leg (c) makes that declaration safe against the zombie.

### Leg (c): status-guarded idempotent reclaim — the mid-write answer

**The crux question**: *what happens to a job killed mid-write, and can the pool be left with a
half-transitioned row?*

Under a naive kill: **yes, corruption is possible.** If we mark a job `dead` and free its slot while its
thread is still alive (the sync-path leak, or any in-flight write), the zombie thread can later:
- complete and fire `_on_agentic_complete` → a second transition onto an already-`dead` row (double transition), or
- finish a file write / git commit the BFE was mid-way through → side effects landing for a job declared dead.

Guards that make reclaim safe:

1. **Idempotent, status-guarded transitions.** Both `_transition_to_dead` and the late
   `_on_agentic_complete` callback must no-op when the row is already terminal. Concretely: a
   `reclaimed`/`terminal` marker set on the job at brake time; the completion callback checks it first and
   returns without transitioning. This is the same shape as the ghost sweeper's done-but-running guard,
   applied to the inverse case (reclaimed-but-still-running). Reuse the existing `_agentic_futures_lock`
   (an `RLock`, already re-entrant for the callback-on-same-thread case) so the marker check and the dict
   mutation are atomic.
2. **Write-boundary safety for side effects.** The BFE's own mutation points (FixExecutor file writes +
   git ops) must be positioned so a timeout between them cannot leave a half-applied commit. The brake
   fires only at the SDK-call boundary (Leg a), never mid-`git commit`; a timeout before commit leaves an
   uncommitted working tree (recoverable, not corrupt), a timeout after commit is a completed unit. The
   smallest non-atomic window is a plain file write with no transaction — bounded and inspectable, not a
   partial DB row.
3. **No brake mid-DB-transition.** The store transition primitives are single calls; the brake never
   interrupts one because it fires at the SDK-call await, which is not inside a store write.

**Answer to the crux**: with (1)+(2)+(3), a killed job cannot leave a half-transitioned row — the row goes
`dead` exactly once, the zombie's late callback is a guarded no-op, and the only residue is a possibly-leaked
inner thread (bounded, logged) whose eventual completion changes no row state.

## Two enforcers, one budget — why it is not a race

Leg (a)'s wrapper and the existing cooperative `SafetyGuard.check_timeout()` read the **same** number. Two
enforcers on one budget is a race UNLESS one is provably unreachable once the other trips. It is — they act
at **mutually exclusive times on a single thread**:

- The **cooperative guard** runs ONLY *between* fix-loop iterations (the job returned to the loop and is
  making progress).
- The **wrapper** runs ONLY *during* a single in-flight SDK call (the job has not returned to the loop).

Case analysis — this is the derivation a future reader needs, not just the "provably unreachable" conclusion:

- **Hung job** (the failure this row exists for): control is inside the SDK call and never re-enters the
  loop. The wrapper trips; its exception **unwinds up the stack, past the loop body**, so the
  `check_timeout()` line at the top of the next iteration is **never executed**. That is the mechanism by
  which the cooperative guard is unreachable for that job — not an assertion, a consequence of exception
  propagation leaving the loop.
- **Progressing job**: each call returns quickly, no single call exceeds the budget, so the wrapper never
  arms. If cumulative elapsed exceeds the budget, the cooperative guard trips between iterations. The
  wrapper is unreachable because no single call ever held control long enough to trip it.
- **They cannot both fire**: one Python thread raises one exception and leaves the stack. There is no
  interleaving in which both enforcers observe a live job to kill.

And even the catch is unified: both raise a **timeout-class exception into the same Leg-(b) handler**, which
Leg-(c) already makes idempotent — so if the reasoning above were ever wrong, the failure mode is a
no-op second call, not a double kill.

## Alternatives considered and rejected

- **`Future.cancel()`** — no-op on a running task. Rejected (the myth this doc kills).
- **Thread kill (`ctypes`/`PyThreadState_SetAsyncExc`)** — can corrupt interpreter state, can fire while a
  lock is held, cannot target a blocked C call reliably. Rejected: exactly the "brake that corrupts state
  is worse than the cooperative one" it would replace.
- **Subprocess isolation + SIGKILL** — the only *true* preemption. Kills cleanly, frees the slot for real.
  But it changes the BFE execution model (larger blast radius), and SIGKILL mid-file-write still leaves a
  partial file — it does not escape the mid-write question, it relocates it. Deferred as a heavier future
  option; the timeout-at-the-hang-point brake is lower blast radius and sufficient for the observed failure
  (a non-returning SDK call is precisely what `wait_for` catches).

## Blast radius

- **Leg (a)** touches the BFE exec path (`shared/fix_executor.py` + the BFE's SDK call site) — a wrapper
  around one call. Does NOT touch the shared pool executor mechanics.
- **Leg (b)** reuses `_transition_to_dead` — no new death path.
- **Leg (c)** adds a terminal-status guard to `_on_agentic_complete` — this is the one change that touches
  shared pool code (`running_fifo_queue.py`), so it carries the most risk and needs the tightest review.
  It is additive (a guard that makes an existing callback idempotent), not a rewrite of the dispatch.
- The podcast job shares the pool (`cj flow max concurrent agentic jobs = 3` in `[Lupin: Development]`);
  the whole point is that a reclaimed BFE slot returns capacity the podcast depends on.
