# Integration suite is structurally unrunnable at its 2000s budget

**Date:** 2026-08-16
**Author:** Arnold 🪨 (Tester, Cheech's SWE crew)
**Status:** Finding for Rick — handed via Cheech (no store row per tonight's no-new-items rule)
**Severity:** The documented FINAL merge gate cannot complete a clean run.

## Verdict

The integration suite — named in CLAUDE.md as the **final PR merge gate** — takes longer to run than the test-suite harness allows it to run. It is killed by its own budget every time. Two measured numbers:

| Quantity | Value | Source |
|---|---|---|
| Suite wall-clock (measured) | **2046.9 s** | `io/test-suite/2026.08.16-at-20:54-EDT-integration-results.md`, job `ts-3e777149`, `duration_seconds` |
| Subprocess budget (configured) | **2000 s** | remediation JSON `failures[0].message`: "Subprocess killed after 2000s budget (actual 2000.1s)" |
| Margin | **−46.9 s** | the suite cannot finish, by design |

The run reached **99%** (killed at `test_v2_eval_live.py`) — it was not slow-starting or hung; it simply needs more than 2000s for the full suite (the run's own remediation record reports **58 collected modules**; `ls src/tests/integration/test_*.py` = 53 by glob — cite the run's 58 as the measured figure).

## Why this matters more than one lane

- The gate is the thing that certifies "safe to merge." A gate that always dies produces a **timeout error + partial results**, never a clean green.
- Partial results are **file-level only** — the SIGTERM lands before pytest prints its summary block, so a killed run yields **no per-test node-ids or tracebacks**. Every failure it reports is un-actionable without a second, narrower run.
- Therefore any recent "integration green" claim was, necessarily, **a subset run or a lucky-on-load finish** — not the full 53-file gate. The gate has not actually been passing.

## Evidence trail

- Killed run: `ts-3e777149`, 356 passed / 5 failed / 1 error / 43 skipped, `duration_seconds` 2046.9, `status` completed, exit 143 (SIGTERM).
- The "1 error" is the budget kill itself (`classname: TestSuiteJob.integration`, `name: timeout`), NOT a code fault.
- Report: `io/test-suite/2026.08.16-at-20:54-EDT-integration-results.md`
- Remediation: `io/test-suite/2026.08.16-at-20:54-EDT-integration-remediation.json`

## Options (Rick's call)

1. **Raise the budget** past the real duration with headroom (e.g. 3000s). `/api/test-suite/submit` exposes no per-run budget override today, so this is an INI/harness change, not a submit param.
2. **Split the gate** into 2–3 file-group sub-runs, each well under 2000s, union = full coverage. Proves green in halves; also the immediate workaround for getting clean node-ids.
3. **Shed/relocate the slow tail** — live-LLM E2E files (e.g. `test_lane2_podcast_e2e_live.py`, `test_v2_eval_live.py`) dominate wall-clock and spend real budget; moving them to a separate scheduled lane shrinks the gate.

Recommendation: (1) as the immediate unblock (one INI change restores the gate), with (2)/(3) as the durable shape.

## Mitigation (measured, not projected)

Splitting the run is not theoretical — it was measured tonight. A 27-test subset of the same suite completed **cleanly in 773s** (well inside the 2000s budget, full per-test summary + node-ids), against the full run's **2046s → SIGTERM at 99%, no node-ids**:

| Run | Scope | Duration | Outcome |
|---|---|---|---|
| Full gate | 58 collected modules | 2046s | **killed at 2000s**, file-level results only |
| Subset (`ts-dce769c8`) | 27 tests (3 files) | **773s** | **completed clean**, full node-ids |

So option (2) recovers exactly what the killed run destroys: a completed run with actionable per-test names. Until the budget is raised, splitting is the only way to get a clean integration result.
