## The rule, stated before it was applied

### The rule in force — `capability`

Label an utterance **CALCULATOR** if and only if it asks for one of the three operations
`CalculatorAgent` actually implements. Everything else — **bare arithmetic included** — is **MATH**.

`CalcIntent.VALID_OPERATIONS` (`src/cosa/agents/calculator/xml_models.py:54`) is exactly:

| Operation | What it does |
|---|---|
| `convert` | unit conversion within one category — length, mass, volume, temperature |
| `compare_prices` | which of two package sizes is cheaper per unit |
| `mortgage` | loan and interest payments |

There is no arithmetic operation, and there is no fourth entry.

**Measured result: 0 of 483 math-corpus lines move.** The math file holds 0 mortgage utterances,
0 price comparisons, and 0 same-category unit conversions. The nearest misses are five fuel-economy
word problems that mention kilometers and liters together — different categories, which `convert()`
cannot do, so they are rate problems and they stay.

### The three-bucket rule, for the record

The spec asked for a bucket rule and it was written before anything was applied. It is what the
**un-applied alternative** below uses, and it is what the audit CSVs are bucketed by:

| Bucket | Contents |
|---|---|
| 1 | Bare arithmetic — the four operations over stated numerals, no scenario |
| 2 | Symbolic algebra, geometry, calculus, trigonometry, statistics, probability, number theory |
| 3a | Word problems needing only `+ − × ÷` on the numbers the sentence already states |
| 3b | Word problems needing a formula, a rate, a unit conversion, or an unknown |

Bucket 3 is where the ambiguity lives, and it splits on one test: *does answering it require
anything beyond the four operations applied to numbers the sentence already states?* The apples and
bananas total does not. The car's distance does — that is a rate. The tank does — two rates against
a shared volume.

## Why the original evidence did not support moving anything

The spec's evidence was that on the cold pass the router sent 23 math-labelled utterances to the
calculator **and answered every one correctly** — 789−456=333, the apples and bananas total, the
circle's area. Both halves are true, and both were re-measured here from the records file. The
inference that the calculator is therefore the right home for them is not.

Here is what happens to "How much is 789 minus 456?" when the router sends it to the calculator, at
`src/cosa/agents/calculator/agent.py:175-190`:

```python
# Guard: convert with empty or unrecognized units → plain arithmetic, delegate to MathAgent
if self.calc_intent and self.calc_intent.operation == "convert":
    from_u = self.calc_intent.from_unit.strip().lower()
    to_u   = self.calc_intent.to_unit.strip().lower()
    if not from_u or not to_u:
        return self._delegate_to_math_agent()
```

**The 23 correct answers are MathAgent's.** The calculator extracted an intent, found no units, and
handed the whole question straight back. So the correctness that looked like a signal about labels
was a signal about a fallback — and relabelling arithmetic as calculator work would not move the
work to a different agent. It would insert one extra LLM extraction round-trip in front of the same
agent, and train the router toward a label its own agent cannot serve.

### Where the rule and the router agree

| Utterance | Capability rule | Router's own cold call |
|---|---|---|
| 3 apples at $1.20, 2 bananas at $0.75, total | MATH | calculator ✗ |
| Car at 60 mph for 2.5 hours, how far | MATH | math ✓ |
| Tank filled by one pipe in 5h, emptied by another in 7h | MATH | math ✓ |

The router's calculator call on the first one is the fallback path, not a capability match.

the calculator file, and 0 are repeated among themselves. `--apply` **refuses to run** if either

## The guard

`src/tests/unit/test_router_corpus_consistency.py` — 30 tests, green.

| Check | Today |
|---|---|
| No MATH-corpus line asks for convert / compare_prices / mortgage | **0 violations** |
| No CALCULATOR-corpus line is symbolic work the calculator has no operation for | **0 violations** |
| The gate reads this checkout's corpus, not another tree's | **enforced, fails loudly** |
| Duplicate groups per file have not increased | **0 files grown** |

Green here is the finding: **the corpus already agrees with the rule.** The gate exists so a future
edit that disagrees fails a test rather than reaching a training run.

**Both directions are proved able to go red.** Each gate has a test that plants one bad line —
"How many miles is 10 kilometers?" into a copy of the math corpus, "How do you solve the equation
3x + 7 = 22?" into a copy of the calculator corpus — asserts the gate catches exactly one offender,
and then asserts the real corpus file is byte-identical to what it was before the plant. The plant
happens in a `tmp_path` copy, so a crashed test cannot leave the real corpus modified.

The guard's shape detectors are deliberately separate from the routing classifier: the classifier
answers *where should this line be labelled*, the guard answers *does this line belong in the file
it is sitting in*. The guard uses positive markers only and never falls through to a default, so a
line it cannot recognize is reported as unrecognized rather than silently blamed.

**The gate reads its own checkout.** María also pointed out that resolving the corpus from
`LUPIN_ROOT` lets a run in worktree A guard worktree B's corpus — you edit one file, the gate reads
another, and it reports green about a file nobody touched. Both the tool and the two corpus files
are now resolved from the test file's own location, and a separate test fails loudly if
`LUPIN_ROOT` names a different tree. (The repo's own worktree false-green guard, row `a9f87d29`,
already refuses to collect in that situation — but this gate should not depend on another guard to
be wired correctly.)

## Found on the way, NOT fixed here

🔴 **An earlier draft of this section was wrong, and María caught it.** It claimed 55
calculator-corpus lines ask for conversions the agent's tables cannot do, and listed `fluid ounces`
first. **`fl_oz` is in `VOLUME`, and `resolve_alias( "fluid ounces" )` returns it** — the agent
handles those fine. The defect was in this guard's tokenizer: it scanned single words, read
"ounces" as the MASS unit, and concluded the conversion was cross-category. Fixed — multi-word unit
names now resolve before the single-token scan and are blanked out so their parts are not re-read,
and `cup` / `ton` were wrongly on the ambiguous-word stoplist when they are real units. Four
regression cases added.

**What is genuinely outside the agent's tables**, re-measured after the fix:

- `tablespoon` and `teaspoon` — not in `VOLUME`, which carries
  `liter, gallon, quart, pint, cup, fl_oz, ml` (`src/cosa/agents/calculator/conversion_tables.py`).
- Named referents rather than values — "What's a marathon distance in miles?", "Convert absolute
  zero to Fahrenheit", "What's room temperature in Celsius?", "Convert body temperature to Celsius",
  "What's boiling point in Fahrenheit?".

These take the same `_delegate_to_math_agent()` path the arithmetic ones do. Worth its own row; not
this change, and not filed tonight per the no-new-bug-rows instruction.

**The unrecognized count is a report and never a gate.** It stands at 45 after the fix, and most of
the remainder is this guard's own phrasing coverage for mortgages and price comparisons rather than
anything wrong with the corpus. A number that mixes "the agent cannot do this" with "my regex did
not match" is not a finding — which is exactly how the first version of it went wrong.
