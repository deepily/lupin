## The rule, stated before it was applied

Two rules were written, and the tool implements both. **The tool does not choose** — the caller
names one, and the audit CSV records which rule produced each destination.

### Rule A — `arithmetic` (Mr Radio's stated default, and the one applied)

| Bucket | Contents | Destination |
|---|---|---|
| 1 | Bare arithmetic — the four operations over stated numerals, no scenario | **CALCULATOR** |
| 2 | Symbolic algebra, geometry, calculus, trigonometry, statistics, probability, number theory | MATH |
| 3a | Word problems needing only `+ − × ÷` on the stated numbers | **CALCULATOR** |
| 3b | Word problems needing a formula, a rate, a unit conversion, or an unknown | MATH |

Bucket 3 is where the ambiguity lives, and it is split by one test: *does answering it require
anything beyond the four operations applied to numbers the sentence already states?* The apples
and bananas total does not (3×1.20 + 2×0.75), so it moves. The car's distance does (a rate), the
tank does (two rates against a shared volume), so they stay.

### Rule B — `capability` (proposed, not applied; recorded so it can be adopted without re-deriving it)

Label CALCULATOR **iff** the utterance maps to one of the three operations `CalculatorAgent`
actually implements. Everything else — bare arithmetic included — stays MATH.

Measured result of Rule B: **0 lines move.**

## What the router is actually doing, and why the premise needed checking

The spec's evidence was that the router sent 23 math-labelled utterances to the calculator on the
cold pass **and answered every one correctly**. Both halves are true. The inference that the
calculator is the right home for them is not.

`CalcIntent.VALID_OPERATIONS` is three operations — `convert`, `compare_prices`, `mortgage`
(`src/cosa/agents/calculator/xml_models.py`). There is no arithmetic operation. What happens to
"How much is 789 minus 456?" when the router sends it to the calculator is this, at
`src/cosa/agents/calculator/agent.py:179`:

```python
# Guard: convert with empty or unrecognized units → plain arithmetic, delegate to MathAgent
if self.calc_intent and self.calc_intent.operation == "convert":
    from_u = self.calc_intent.from_unit.strip().lower()
    to_u   = self.calc_intent.to_unit.strip().lower()
    if not from_u or not to_u:
        return self._delegate_to_math_agent()
```

**The 23 correct answers are MathAgent's.** The calculator extracted an intent, found no units, and
handed the whole question back. So relabelling arithmetic as calculator work does not move the work
to a different agent — it inserts one extra LLM extraction round-trip in front of the same agent.

That is the honest cost of Rule A, and it is stated here rather than in a commit message because a
commit message is not where a reviewer looks for a trade-off.

### The three bucket-3 examples the spec named, and where each landed

| Utterance | Rule A | Router's own cold call |
|---|---|---|
| 3 apples at $1.20, 2 bananas at $0.75, total | CALCULATOR | calculator ✅ agrees |
| Car at 60 mph for 2.5 hours, how far | MATH (rate) | math ✅ agrees |
| Tank filled by one pipe in 5h, emptied by another in 7h | MATH (rates) | math ✅ agrees |

The rule and the router agree on all three. That is a check on the rule, not evidence for it.

## Counts moved, per bucket

Rule A, applied:

| Bucket | Lines classified | Moved to calculator |
|---|---|---|
| 0 — routing phrases ("Open up the math agent for me") | 103 | 0 |
| 1 — bare arithmetic | 38 | **38** |
| 2 — symbolic | 304 | 0 |
| 3 — word problems | 38 | **14** (3a) — 24 stayed (3b) |
| **Total** | **483 content lines** | **52** |

Corpus after the move: math **483 → 431** content lines, calculator **508 → 560**.

**On the spec's "~489 lines / 240 ceiling":** the heuristic here counts 38 bare-arithmetic lines,
not 240. The spec was explicit that 240 was a ceiling from pattern matching and not a measurement,
and it is not being treated as one. The two numbers differ because this classifier sends anything
carrying a symbolic, geometric, or statistical marker to bucket 2 first, and the math file's
sections are mostly those. **The 38 and the 14 are also heuristic** — that is exactly why the audit
CSV exists.

## Duplicate check

**Result: 0 duplicates.** 0 of the 52 movers already existed in the calculator file, and 0 were
repeated among themselves. Comparison is on a normalized key (lowercased, whitespace collapsed,
curly quotes folded) so that the same sentence in two typographies still collides. `--apply`
**refuses to run** if either count is non-zero — the check is a precondition, not a report.

One duplicate already exists *inside* the math file and was left alone (a repeated mean-value-theorem
line); de-duplicating the corpus is not this change.

## Cold math-expected recount

Computed from `lupin/io/v2-flow/eval-2026-08-21-11-37-48/records.jsonl`, cold pass,
`expected_command = agent router go to math`, n = 60. **No interpretive rule is applied to the
router's output** — the comparison is `payload.command == expected label`, string equality.

| | Correct | Accuracy |
|---|---|---|
| Before (old labels) | 34 / 60 | 0.567 |
| After (Rule A labels) | 53 / 60 | 0.883 |
| After (Rule B labels) | 34 / 60 | 0.567 |

The router routed those 60 as: calculator 23, math 34, receptionist 3. **That distribution does not
change** — this is a relabelling, so the gain is bookkeeping, not behaviour.

🔴 **The 60 are not a sample.** They are content lines 1–60 of the math file, verified by matching
each utterance back to its line. That block is the arithmetic-dense head of the corpus, so it
over-represents exactly what Rule A moves. **0.883 is the accuracy on the head slice and is not a
corpus-wide estimate.** The 7 still wrong after the move are the 3 that fell to the receptionist
plus 4 arithmetic-shaped lines the router sent to the math agent anyway (for example "How do you
multiply 15 by 35?") — the router's line is not perfectly consistent either.
