## 5. Design of the extension

### 5.0 What is being extended, precisely

`AgentSpec` today (`registry.py:29-51`) carries five fields and one computed property:

```python
@dataclass( frozen=True )
class AgentSpec:
    command       : str
    factory       : Callable[ ..., Any ]
    aliases       : tuple[ str, ... ] = ()
    snapshotable  : bool              = True
    _required_args: Optional[ tuple[ str, ... ] ] = None

    @property
    def required_args( self ) -> tuple[ str, ... ]:
        if hasattr( self.factory, "declared_args" ):     # phase-2 destination
            return self.factory.declared_args().required
        entry = AGENTIC_AGENTS.get( self.command )       # today, agentic
        if entry: return tuple( entry[ "required_user_args" ] )
        return self._required_args or ()                 # today, conversational
```

**That property is already the consolidation, in miniature** — one accessor, three sources, an explicit migration order. The extension generalizes what it does for `required_args` to every other field the four lists disagree about.

Note what it implies: `AgentSpec.required_args` **already reads `AGENTIC_AGENTS` for commands that are not in `V2_AGENTS`**. The plumbing to serve agentic commands from the registry exists; what is missing is entries for them and the fields beyond `required_args`.

### 5.1 The registry owns the agentic set

Add `class` and the agentic fields, and register the eleven agentic commands as specs.

```python
class CommandClass( Enum ):
    CONVERSATIONAL = "conversational"   # fast-lane agent, no job, no CLI
    AGENTIC        = "agentic"          # builds a job; has an argument contract
    CONTROL        = "control"          # mode control; never routes to an agent
    NONE           = "none"             # receptionist / no-command outcome
```

```python
@dataclass( frozen=True )
class AgentSpec:
    # ── existing, unchanged ──
    command       : str
    factory       : Callable[ ..., Any ]          # conversational: the agent class
    aliases       : tuple[ str, ... ] = ()
    snapshotable  : bool              = True
    _required_args: Optional[ tuple[ str, ... ] ] = None

    # ── added by this design ──
    cls           : CommandClass      = CommandClass.CONVERSATIONAL
    job_factory   : Optional[ Callable[ ..., Any ] ] = None   # agentic: builds the Job
    cli_module    : Optional[ str ]   = None      # None ⇒ API-invoked (test_suite)
    cli_style     : Optional[ str ]   = None      # "package" | "module" — see §4
    arg_spec      : Optional[ ArgSpec ] = None    # the expeditor's carrier, §5.1.1
```

**`cls` is the field that makes the test honest.** It lets the guard say *"every AGENTIC command appears in all four sources; CONVERSATIONAL commands appear in exactly two"* instead of demanding uniform set equality and crying wolf nine times (§3).

**`cli_style` exists because of a live false positive.** `deep_research.cli` is module-style with a `__main__` guard; the other nine are package-style needing `__main__.py`. A checker that knows only one form reports a failure that is not real (§4).

#### 5.1.1 Reuse `ArgSpec` — do not restate its fields

`ArgSpec` (`expeditor.py:87`, Mr Radio, `a24d13d5`) already carries `arg_mapping` · `system_provided` · `required_user_args` · `fallback_questions` · `fallback_defaults` · `special_handlers` · `display_name` · `cli_module`, and its `from_entry()` already builds one from an `AGENTIC_AGENTS` row — **copying `fallback_defaults`** so one user's seeded default cannot leak to the next (bug `8aa89f42`).

⇒ **`AgentSpec.arg_spec` holds an `ArgSpec`; the fields are not re-declared.** Migration is `ArgSpec.from_entry( AGENTIC_AGENTS[ cmd ] )` per command, so the copy semantics come along for free. Re-typing those eight fields onto `AgentSpec` would create a ninth list to disagree with the others — the exact defect this document exists to remove.

#### 5.1.2 Keep the buckets; derive them

The four bucket constants are what the passing guard test compares against, so they must not simply vanish. Derive them from `cls` and leave the names in place:

```python
V2_AGENTS            = { c: s for c, s in REGISTRY.items() if s.cls is CommandClass.CONVERSATIONAL }
AGENTIC_COMMANDS     = { c: s for c, s in REGISTRY.items() if s.cls is CommandClass.AGENTIC }
CONTROL_COMMANDS     = frozenset( c for c, s in REGISTRY.items() if s.cls is CommandClass.CONTROL )
RECEPTIONIST_OR_NONE = frozenset( c for c, s in REGISTRY.items() if s.cls is CommandClass.NONE )
```

`DEFERRED_COMMANDS` **retires** — it named commands the registry knew but did not own, which is the state this design ends. Its members become `CommandClass.AGENTIC` entries.

⚠️ **`test_bucket_counts` hard-codes 6 / 7 / 1 / 2 and a 16-command total.** Those numbers change the moment the agentic set is owned. Update it deliberately, in the same commit, with the new numbers written out — never by loosening it to a range or a `>=`. A count assertion that stops counting is not a weaker guard, it is no guard.

#### 5.1.3 `resolve()` must not silently start returning specs

Today `resolve()` returns `None` for every deferred/control/none command, and the flow routes `None` to the receptionist with `route_reason="unknown_command"`. Once agentic commands are registered, a naive `REGISTRY.get()` would start returning specs for them — **changing v2's live routing behaviour as a side effect of a bookkeeping change.**

Keep `resolve()` scoped to `CommandClass.CONVERSATIONAL` and add a separate `resolve_agentic()`. Same table, two readers, no behaviour change in phase 1.

> This is the sharpest hazard in the design: a refactor that silently widens what a router-facing function returns. It is why phase 1's gate (§7) is *"existing suites green"* and not *"it compiles."*

### 5.2 Generate the prompt list

The template is 2,055 bytes of XML-ish `<command>` lines. Generating it from the registry is mechanical and is the **fast path to reachability** (see §5.4). Keep the generated file checked in — a reviewer should be able to read what the router is being told without running a build step.

🔴 **The agentic training JSON is not a command list.** Its values are synthetic-data generation configs:

  "template_file": "/src/ephemera/prompts/data/synthetic-data-agent-routing-deep-research.txt",

### 5.4 The retrain asymmetry — state it in the code, not just here

Four consumers, and one is not a file: the training corpus is consumed at **train** time and baked into the LoRA weights. Regenerating it does not make a new command live.

**Why that is survivable** — measured 2026-08-14, filed as `d9ecd69e`. A **two-arm probe** over ten utterances with one invented command (`agent router go to recipe finder`):

| arm | invented command emitted |
|---|---|
| **A** — command **listed in the prompt** | **10 / 10** |
| **B** — **control**: absent from the prompt **and** from the 19-command training vocabulary | **6 / 10** |

**The control arm is the result**: the router emitted a command that exists in no list anywhere. It is a completion model following the pattern `agent router go to <thing>` and generating a plausible command from the utterance. The vocabulary is **not closed** — not prompt-bound, and not weight-bound.

> **🔴 WORDING FIXED after cascade review (Tiberius, 2026-08-15).** The earlier draft cited *"6 of 10"* with no arm label. A reader reaching the source table sees both 10/10 and 6/10 and cannot tell which supports the claim — Tiberius reasonably read the 10/10. **The citation was correct; the sentence was ambiguous.** Both numbers are now stated with their arms.

⇒ **Retraining buys RELIABILITY, not REACHABILITY.** An agent is reachable the moment the prompt lists it; the retrain makes it dependable. The registry→prompt path is fast, and the retrain is allowed to lag.

⚠️ This is the design's most misreadable claim. *"Generated from the registry"* reads as *live*. Whoever builds this must put the asymmetry in a comment beside the training generator, or somebody will add a row and assume the router is dependable that afternoon.

### 5.5 Factory dispatch by lookup

Replace the eleven-branch `if/elif` at `agentic_job_factory.py:141-352` with a registry lookup:

```python
def create_agentic_job( command, args_dict, user_id, user_email, session_id, debug=False, verbose=False ):
    spec = resolve_agentic( command )
    if spec is None: return None                  # unchanged contract
    return spec.job_factory( args_dict, user_id, user_email, session_id, debug=debug, verbose=verbose )
```

This is where the two worst user-facing bugs die **by construction**: a command cannot be registered and missing from the factory, because they stop being separate lists.

⚠️ **The branches are not uniform — this is not a mechanical swap.** The eleven bodies span `:141-352`, roughly 19 lines each, and they do per-command argument coercion (`_SEMANTIC_NONE` handling, float parsing with defaults) before constructing. That per-command logic has to land *somewhere*: either inside each `job_factory` callable, or declared on the spec. **Read all eleven before choosing** — a design that assumes they are eleven identical constructor calls will discover otherwise in the middle of phase 5.

Recommended: each `job_factory` is a small named function holding its own coercion, moved out of the chain unchanged. Behaviour-preserving first; tidy the coercion afterwards, if at all.

## 6. The drift guard — and how to keep it falsifiable

> **🔴 RENAMED after the cascade re-check (arnold, via Rachel's consolidation §2.1, 2026-08-15). It was called "the completeness test" and that name overclaimed.**
>
> arnold was asked: *can a command be right everywhere this test looks and still be unreachable by voice?* **Yes — three ways:**
>
> 1. **No retrain.** The test reads training-JSON keys **on disk**; the deployed router emits from **LoRA weights**. A new key with no retrain is **green in the test and mute in production.** §5.4 states this asymmetry — but the *test* does not encode it, so using "present in the training keys" as a reachability proxy contradicts §5.4 itself.
> 2. **Runtime template ≠ checked-in template.** The test reads the checked-in file. If the running router loads a different or differently-rendered one, membership is not what the router was told. *(Marked UNVERIFIED by the reviewer — flagged as the load-bearing assumption, not a confirmed defect. Worth confirming during phase 4.)*
> 3. **Emitted string ≠ registry key.** Set-membership tests that the same *string* appears in four lists — never that the string the router **emits at runtime** matches a registry key or alias. `resolve()` handles V2 aliases (`registry.py:143`); whether `resolve_agentic()` will is a phase-1 open (§5.1.3).
>
> ⇒ **This section guards FOUR-LIST DRIFT CONSISTENCY. It does not, and cannot, prove voice reachability.** That is real and worth having — drift is what breaks agents today — but the three gaps above are **out of scope by design** and are stated here so nobody builds against a name that promises more than the test delivers.

**The deliverable is the failing run.** The test is expected to go red on first execution; that output is the drift inventory.

Assertions, class-aware:

1. every **agentic** command appears in: registry · prompt · training keys · factory
2. every **conversational** command appears in: registry · prompt · training keys — and in **no** factory branch
3. `control` and `none` commands appear in prompt + training only — **written as set-equality in BOTH directions**, not one-way membership. *(arnold: a one-way check catches a missing membership but never an extra one. Assertion 4 already does it correctly at `test_v2_registry.py:68` — copy that shape.)*
3b. ~~**`cls` and `AGENTIC_AGENTS` agree**~~ — **DROPPED, replaced by a by-construction note. Raised by Tiberius, endorsed and relayed by Rachel, 2026-08-15, caught during the phase-1 build; verified by me against merged `cca4a00b`.**

> **The assertion was sound against the design and is a tautology against the implementation.** Tiberius built the specs by **iterating `AGENTIC_AGENTS` itself** — one spec per entry — so `cls == AGENTIC` and the `AGENTIC_AGENTS` key set are equal **by construction**. Asserting they agree can never go red.
>
> **This is the SECOND tautology in this document**, after the derived-count fix (§7). Both times I closed a seam by asserting a property that the implementation had already made unbreakable, and both times a reviewer caught it before it was built. ⇒ **The question to ask of any new assertion here is not "is this true?" but "what change would make it false?"** If nothing can, it is a comment with a green tick.
>
> **What the code does instead is better than the assertion.** The build site carries the reasoning inline: the specs are built by iterating the table, *"so `AGENTIC_COMMANDS` equals the `AGENTIC_AGENTS` key set BY CONSTRUCTION — there is no second hand-written list… Adding one by hand is the ONLY way to reintroduce the `cls`↔`AGENTIC_AGENTS` drift."*
>
> **The residual risk is real but narrow**: a future hand-written agentic spec. That is a review concern, not a test concern, and naming it at the construction site puts it where the person about to do it will read it — which an assertion in a test file would not.
4. no command appears in two class buckets (this partition check already exists and passes)
5. ~~every `cli_module` is **runnable** — package-style needs `__main__.py`, module-style needs a `__main__` guard~~
6. ~~`get_cli_help` never caches a string matching `No module named`~~

> **🔴 ASSERTIONS 5 AND 6 REWRITTEN — cascade review, arnold, 2026-08-15. This is the finding this section existed to produce, and it landed on this section.**
>
> **Assertion 5 could not fail.** It checked the *filesystem* for `__main__.py` instead of *running* the module — so an unrunnable module that happens to have the file present passes. **That is the §4 defect class sitting green inside the check written to catch it.**
>
> **Assertion 6 could not fail either.** It matched the *wording* `"No module named"` rather than the failure. Change the interpreter's message, or hit a different import error, and the assertion goes quiet while the defect stands.
>
> **Both collapse into ONE check that cannot be fooled by either:**
>
> **5′. Every `cli_module` runs.** Invoke `python -m <cli_module> --help` in a subprocess and **assert the return code is 0**. A non-zero return catches the missing `__main__.py`, the module-style variant, an unimportable dependency, and any future failure mode nobody has thought of — because it tests the thing itself rather than a symptom of it.
>
> This also **retires `cli_style`** as a test concern: running the module doesn't care which form it is, so the field stays on the spec for documentation but the guard no longer branches on it. One check, no forms to enumerate.
>
> ⚠️ **The falsifiability demo for 5′ is not optional**: rename a real `__main__.py`, watch the assertion go red, restore it. Two assertions in this very section were green and useless; the demo is the only thing that would have caught them.

### 🔴 Falsifiability is a required deliverable, not a nicety

This is the guard for a defect class whose whole nature is *looking fine*. My standing weakness is writing checks that cannot go red — four unfalsifiable ones in a single session on 2026-07-22.

**Each assertion above ships with a demonstration that it fails when the thing it guards is broken** — delete a command from one source, watch that specific assertion go red, restore it. An assertion nobody has seen fail is not a guard; it is a comment with a green tick.

> **🔴 PHASE 4'S GATE REPLACED — cascade review, Tiffany, 2026-08-15.**
>
> The original gate was *"byte-compare the generated file against the hand-maintained one before switching."* **It cannot pass.** The 16 command lines are derivable from the registry set, but their **order in the template is neither alphabetical nor declaration order** — so a byte-compare fails on sequence alone, for a file that is semantically identical.
>
> A gate that cannot go green gets bypassed by whoever hits it, which would leave phase 4 effectively ungated. Two replacements, either acceptable:
>
> - **(a) 🔴 ADOPTED — make order REGISTRY-OWNED DATA.** Declare an explicit **ordered** command list in the registry and generate from it. Order stops being editorial and becomes a declared fact, so **byte-compare becomes an honest gate** rather than one that has to be abandoned. Applied once as a one-off reformat of the checked-in template.
> - **(b) Set equality + a declared sort rule.** The generator sorts alphabetically; the gate checks sets and applies the sort. Workable, but order remains a convention rather than data.
> - **(c) Set equality only.** Ignores order entirely — can never again detect an accidental reordering.
>
> **Correction to the first fold**: I originally adopted (b), which was Tiffany's **fallback**. Her **preferred** fix is (a), and Rachel's re-check flagged that I had *"taken the fallback, not the preferred"* — inheriting the weaker option by accident rather than by choice. (a) is now adopted deliberately: it is the only one of the three that keeps a byte-compare meaningful.
>
> **Not a defect in the generation plan** — only in how phase 4 proves itself.

> **⏱ WHEN the count assertion goes — ruled 2026-08-15, Rachel's question, then re-ruled after Tiffany's catch.**
>
> **Phase 1, deleted outright, in the same commit that would otherwise invalidate it.**
>
> Phase 1 is precisely the change that makes `6 / 7 / 1 / 2` and the `16` total wrong, because it moves the agentic set into the registry. Hand-updating those numbers in phase 1 is the **indistinguishable-diff move** — a one-line count change turning red to green, which §2.2 says cannot be told from a cover-up.
