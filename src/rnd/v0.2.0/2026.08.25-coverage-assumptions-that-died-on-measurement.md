## Why this file exists

María asked for the reasoning behind the test assumptions to be documented, **especially the
ones that failed on measurement**. Five did. Four were mine. Each was plausible enough to act
on and wrong in a way that only a measurement could show, and in three of the five the
*failure mode was a green* — something that looked covered, looked tested, or looked
reconciled, and was not.

The pattern worth keeping is not "check your work". It is narrower: **every one of these was a
claim about what the tests or the numbers were DOING, not about what the code does.** A wrong
belief about the code shows up as a failing test. A wrong belief about the harness shows up as
nothing at all.

## 1. "job.py is at 43% with 318 missing" — a figure from a run that never ran those tests

**Assumed**: the file carried ~318 statements of real test debt, worth a night's work.

**Measured**, pinned to María's own `START_SHA` `77b0dddc`:

| Scope | Cover | Missing |
|---|---|---|
| `src/tests/unit/test_test_suite_job.py` alone | 74% | 147 |
| ...plus `src/cosa/tests/unit/agents/test_suite/` | **93%** | **40** |

The figure was also not self-consistent with the file itself: at that sha `job.py` is **642
statements**, so 43% would be 366 missing, and 318 missing would be 50%. Neither reading closes.

**Cause** (confirmed by María): the number came from an **orphaned run that executed only the
unit tier**. The cosa-tier tests that cover most of this file never ran, so the file reported as
debt while being covered. Nothing had regressed.

**What it would have cost**: writing tests for ~100 statements another tier already exercised.

⇒ **A coverage figure is a statement about which tests RAN, not about the file.** Two scopes,
same sha, same file: 74% and 93%.

## 2. Six tests named after a function that never called it

`src/tests/unit/test_mcp_account_validation.py` had seven passing tests for
`_validate_repo_account`. It did not call it. It rebuilt a hand-written copy inside the test —
declared to *"mirror cosa_voice_mcp._validate_repo_account exactly"* — and exercised the copy.
Its `_import_validation_functions()` was a stub whose body was `pass`, and its
`TestSendValidationError` never called `_send_validation_error` either; it constructed an
`AsyncNotificationRequest` inline and asserted on that.

**The decisive receipt** — run that file under `--cov=lupin_mcp.cosa_voice_mcp`:

```
7 passed in 0.36s
```

…and **no row for the module at all**. Coverage does not print a file it never imported.

**And the copy had drifted.** The real function catches `( ConnectionError, Timeout )`; the copy
caught `ConnectionError` alone. `requests.exceptions.ReadTimeout` is **not** a subclass of
`ConnectionError` (verified: `issubclass(...)` is `False`), so the copy encodes the PRE-FIX
behavior — and its own `test_connection_error_sends_server_down_notification` passes anyway. A
fix landed in the real code and never reached its replica. It also had no final
`except Exception` arm, and never touched `_ACCOUNT_VALIDATED`, which IS the function's
observable output.

**Proof the real arm is load-bearing**, run at María's request — delete it from the real function:

```
except ( requests.ConnectionError, requests.Timeout ) as e:   ->   except requests.ConnectionError as e:

    2 failed, 26 passed
      ...test_every_transport_failure_is_caught_including_read_timeout[Timeout]
      ...test_every_transport_failure_is_caught_including_read_timeout[ReadTimeout]
```

`ConnectionError` and `ConnectTimeout` stay **green** under that mutation, correctly —
`ConnectTimeout` *is* a `ConnectionError`. Only the two non-subclasses expose the gap, which is
precisely what the replica could not see.

⇒ **A replica kept in step by hand is only as good as the last person who remembered.** Deleted
on María's ruling; all seven assertions now run against the real functions.

## 3. A test that asserted a crash was expected behavior

Writing tests for `ask_open_ended_batch` produced a red I had written to be green:

```python
logger.debug( f"...() called with {len( questions )} questions" )   # <- runs first

if not questions or not isinstance( questions, list ):             # <- the guard
    return { "error": "questions must be a non-empty list" }
```

The guard is correct and was **unreachable for exactly the input it rejects**: an argument with
no `len()` raises `TypeError` on the line above it. `"a string"`, `{}` and `[]` all have a
length and reached the guard, which is why it survived. `ask_multiple_choice` had the identical
shape.

The tempting move was to write the test around the crash. **María's ruling**: that is the
replica defect one layer over — *a green assertion pointed at something nobody wants to be
true*. Fix it, keep it minimal, carry a negative control, and give it its own commit.

Fixed by moving the validation above the log in both tools. Negative control: reverting to the
old ordering gives **4 failed / 22 passed**.

## 4. "The brevity guard raises" — it is switched off in this config

A test asserted `_enforce_spoken_brevity` rejects an over-long question and got
`DID NOT RAISE`. Measured:

```
enforce = False    cap = 500
```

The enforce kill-switch is **False** in this repo's config, so the guard is a no-op as
configured. A test written against the ambient value would have **passed while exercising
nothing** the moment someone flipped the switch back.

Fixed by pinning `_get_spoken_enforce` and `_get_spoken_char_cap` in the fixture — which tests
the real behavior *and* makes the assertions independent of an INI Rick can flip either way.

⇒ **Reading config at test time makes the test's meaning depend on a value nobody in the test
declared.**

## 5. A moving HEAD makes a counted figure unattributable

Two independent instances tonight, one mine, one María's.

**Mine** (row `0d175dac`, the venue-name blast radius): `git rev-parse HEAD` returned
`5cb04327`; two tool calls later the short sha was `7394cab1`. A peer had committed mid-count.
The first pass was **discarded** and re-run with `git grep <sha>` so every figure describes one
tree — 169 code occurrences across 35 files, with 257 doc occurrences published as excluded.

**María's**: a moving HEAD left a coverage figure that could not be attributed to a sha, which
is why commits to Lupin are on hold as this is written.

⇒ **María's wording, which is sharper than mine was**: resolve the sha, **MEASURE IN A TREE
THAT IS THAT SHA**, and say which. Stamping a sha on a figure taken in a dirty working tree
still describes something the sha does not contain. A number without a sha is not a
measurement; a number with a sha but taken elsewhere is worse, because it looks like one.

## 6. My own figures were taken in a dirty tree — and one of them was wrong

Item 5 was written and I then failed its own rule. All three coverage figures above were
measured in the **working tree** at `edf2c712`, which at that moment also held a peer's modified
`src/scripts/v2_eval.py`, `commit_scope_guard.py`, `test_v2_eval_unobserved_cache.py`, and two
untracked files. I asserted those were irrelevant to my three modules rather than checking.

Re-measured in a **detached worktree checked out at `edf2c712`**, `git status` empty:

| Target | Dirty working tree | Clean worktree at the sha |
|---|---|---|
| `answer_catchup.py` | 174 / 0 missing, 100% | **174 / 0, 100%** — holds |
| `test_suite/job.py` | 642 / 0 missing, 100% | **642 / 0, 100%** — holds |
| `cosa_voice_mcp.py` | 872 / **1** missing, **2** partial | 872 / **2** missing, **4** partial |

**The third figure was wrong.** Two lines — `505` and the arc `515->485` — read as covered in the
working tree and are NOT covered at that sha. Both sit inside `_session_watcher_thread`'s phase-2
poll loop, and **no test of mine reaches them**: the coverage was credited to the REAL watcher
daemon, which this module starts at import and which was polling live bridge files under the
repo's own `LUPIN_ROOT` while the suite ran. Point `LUPIN_ROOT` at a worktree with no bridges and
`_find_session_file()` returns `None`, so the daemon `continue`s before ever reaching line 505.

Not a flap: **two identical clean runs both report `505, 515->485, 1409->1415, 2764`**, and the
clean run executed MORE tests than the dirty one (1088 vs 949, because the file list was
re-derived from the worktree), so the extra coverage cannot be explained by test selection.

⇒ **Coverage can be credited to a background thread that merely ran during the suite.** That is
a false green with no test behind it at all, and it is invisible until the environment changes.
Corrected figure for `cosa_voice_mcp.py` at `edf2c712`: **99%, 2 statements and 4 branch arcs
uncovered** — `505`, `515->485`, `1409->1415`, `2764`.

## What the five have in common

| # | The green that lied | What exposed it |
|---|---|---|
| 1 | a coverage % that described a run, not a file | measuring the same file under two scopes |
| 2 | seven passing tests for a function never called | `--cov` printing no row for the module |
| 3 | a guard that could not run for its own input | writing the test and reading the red |
| 4 | a guard assertion against a disabled switch | `DID NOT RAISE` |
| 5 | a count with no sha under it | `rev-parse` twice, two answers |

Three of the five were **false greens** — the failure mode that costs the most, because nothing
asks to be looked at. The cheap defenses that actually caught them: run the mutation and watch
for the red, pin the sha, pin the config, and read the coverage row rather than the test count.

Two more assumptions died the same way while writing the tests, small enough to note in one
line each: `_dm_send_fn` is a plain function with no `.fn` while every sibling is a
`FunctionTool`, and the DM unresolved-recipient arm is **422**, not 404 — both found by calling
the interface instead of assuming it.
