## Verdict

The v1 fast-lane path (AgentBase / SolutionSnapshot — exactly what the corpus's simple
commands route to) **does not persist an execution-start or execution-complete timestamp on
the job object**, so the get-queue/done endpoint serializes `started_at=""`, `completed_at=""`
for those jobs. §3's contingency is real: the parity span is **not** measurable from the v1
job/done endpoint as-is. But there is a **zero-v1-touch** measurement path via WebSocket events.

## Three options (this is a manager-fork — it changes what the number means AND touches/【doesn't touch】 v1)

1. **WS-event capture — ZERO v1 touch (recommended).** The v1 arm subscribes to
   `job_state_transition` events, correlates by `job_id`, and computes the parity span =
   `ts(RUNNING→COMPLETED) − ts(QUEUED→RUNNING)`. This **excludes queue dwell** (the QUEUED
   interval before RUNNING) exactly as §3 demands, and the "v1 untouched" floor passes for
   free. Cost: the v1 client must open the queue WebSocket and match events to submitted jobs.
2. **Two behavior-neutral stamps in the pinned worktree.** `job.started_at` at QUEUED→RUNNING
   and `job.completed_at` before the done-push, for fast-lane jobs. Precise and simple to read,
   but a v1 touch — and §3 authorized *one* stamp; reality needs *two* (completed_at isn't
   persisted either). Must prove behavior-neutral (v1 suites green, `expedite()` unchanged).
3. **Mark latency rows `PENDING — parity unverified`** (§3 fallback) and ship the harness with
   the floors + non-latency AI rows now; defer the latency verdict. Honest, but leaves the
   headline (§1.1 faster) unmeasured, so OVERALL can't reach INVEST.

## Recommendation

Option 1 (WS-event capture). It is the only path that measures the §3 span precisely AND keeps
v1 literally untouched, so the "v1 untouched" veto is satisfied by construction rather than by a
green-suite argument.

Build-time check — DONE: the consumer emits `emit_job_state_transition(QUEUED→RUNNING)` at
`queue_consumer.py:198`, before `_process_job` (215); it stamps `timestamp` via
`queue_util.py:49`, so the dequeue anchor is on the event the listener sees.
