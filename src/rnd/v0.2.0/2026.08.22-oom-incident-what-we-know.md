## 1. ESTABLISHED — measured, quotable

### The kernel killed Claude Code. Twice.

From `journalctl -k`, verbatim:

```

                 total-vm:263893348kB, anon-rss:229468532kB, UID:1001
Aug 22 12:38:01  Out of memory: Killed process 746520 (node)
                 total-vm:159149280kB, anon-rss:124458944kB, UID:1001
```

Both carried:
```
oom-kill:constraint=CONSTRAINT_NONE, global_oom,
task_memcg=/user.slice/user-1001.slice/user@1001.service/app.slice/tmux-server.service,
task=node
```

| Fact | Value |
|---|---|
| Victim 1 resident | **229 GB** (`anon-rss:229468532kB`) |
| Victim 2 resident | **124 GB** |
| Machine RAM | 251 GiB |
| Swap | 4.0 GiB |
| Constraint | `CONSTRAINT_NONE`, `global_oom` — **no cgroup limit was hit; the machine ran out** |
| Slice | `tmux-server.service` — the slice every session shares |
| Kills in the preceding 14 days | **zero** |
| Kills since 12:38:01 (checked 13:25) | **zero** |
| Versions | claude-code **2.1.240**, node **v22.15.0**, Linux 5.15.0-33 |

### The allocation was abandoned, not working set

At the moment of the first kill the zone report read:

```
Node 0 Normal ... active_anon:41082900kB inactive_anon:217364960kB
```

**217 GB was `inactive_anon`** — allocated and then never touched again. A working set that grew gradually would be predominantly *active*. This is one or a few enormous allocations made and abandoned.

### It is not a JavaScript heap leak

- V8's old space defaults to roughly 4 GB and aborts with `JavaScript heap out of memory` — it cannot reach 229 GB.
- The installed 2.1.240 bundle contains **no** reference to `max-old-space-size` and **no** heap-OOM handler; the `OOM` strings present in it come from vendored dependency text, not from a Claude Code guard.
- The process died to the kernel with no chance to clean up, which is consistent with growth in **external memory** — `Buffer` / `ArrayBuffer` / native allocations — which `--max-old-space-size` does not bound.

⇒ **Raising `--max-old-space-size` is the wrong lead.** Recorded explicitly because it is the first thing anyone will reach for.

### Baseline for comparison — the fleet is not normally large

Measured 13:25 EDT, 3 live claude processes, no kills since 12:38:

```
claude-monitor  2.99 GB
uvicorn         1.50 GB
python          1.36 GB
```
Memory: 12 Gi used of 251 Gi. So a healthy session sits far below a gigabyte, and the 229 GB event is roughly **two orders of magnitude** outside anything observed since.

## 2. ESTABLISHED — the fix, and the correction inside it

Sam built containment and detection on `wip-oom-containment-df5c3696` (`2fcfe370`). **Not merged, not pushed, not in service.**

### 🔴 The obvious fix does not work

My original recommendation was `systemd-run --user --scope -p MemoryMax=24G claude`. **It does not cap anything.**

Measured: `MemoryMax=64M` against a 512 MB allocator — **the allocator ran to completion.** The cap was applied correctly (the scope's `memory.max` read `67108864`), but with `memory.swap.max` unset the cgroup reclaims by *swapping* rather than killing.

Adding `-p MemorySwapMax=0` produced the kill: child `rc 137`, and the scope's own `memory.events` read `oom_kill 1` / `max 22`.

⇒ **The swap bound is not a refinement of the cap. It is the half that makes it real.** Both are now always emitted together, and the negative control (`MemoryMax` alone → SURVIVED) is kept as a test so nobody quietly drops it.

This also inverts proposed remedy #2: **growing swap makes things worse.** More swap lets an uncapped runaway thrash longer before the kernel intervenes. With `MemorySwapMax=0` on session scopes, swap size stops mattering for this failure. Swap was left untouched.

### Containment
`src/scripts/start-cc-with-tmux.sh` wraps claude in a per-launch transient scope. Ceiling via `LUPIN_CC_MEMORY_MAX` (default 24G) and `LUPIN_CC_MEMORY_SWAP_MAX` (default 0); either accepts `off`/`none`/`infinity`. A pre-flight probe distinguishes "the scope would not start" from "claude exited non-zero"; on failure it launches **uncapped with a named reason on stderr** rather than refusing to launch. Composition and validation live in `src/cosa/utils/memory_cap.py` so the degrade paths get real branch coverage.

**Constraint honoured:** the cap is on a per-launch transient scope only. Nothing is written to `tmux-server.service` or the user slice — a slice-level cap would kill the entire fleet at once instead of one session. A test asserts the launcher never names them.

### Detection
`src/scripts/watch-cc-memory.sh` samples RSS of live claude processes and writes one line per threshold crossing:

```
2026-08-22T12:55:18-0400 [CC-MEM] pid=765583 rss_gb=21.4 threshold_gb=16.0
  session=645d5fed tmux=cc-reviewer-maria-1 scope=lupin-cc-… cmd="claude --model …"
```

Default threshold 16 GB — deliberately below the 24G cap, so the line lands **before** the kill and the transcript is still readable. Read-only: it never kills, notifies, or touches a session.

### 🟢 The attribution gap is closed, and it was narrower than it looked
I originally recorded that the owner pid was not stored in a form that greps back. That is true of the listener **log files** — but the listener **process** carries both ids in its own command line:

```
python3 -m …cc_notification_listener --session-id 0b7675fc --owner-pid 751918 …
```

So pid → session id was in the process table the whole time; it was only missing from the files anyone thought to grep. Attribution therefore works for sessions **already running** — no relaunch, no cap, no change to how anything was started. Verified live against three sessions. Two fallback resolvers sit behind it (`/proc/<pid>/cgroup` once the cap is in service, `/proc/<pid>/environ` → `TMUX_PANE`); a process answering to none prints `session=unresolved` rather than a blank, so a gap reads as a gap.

It keeps the negative control, so if someone drops the swap bound a test goes red instead of a cap going quiet.

## 3. NOT ESTABLISHED — stated so nobody inherits it as fact

### 🔴 We do not know what allocated 229 GB
Nothing in this work identifies the tool call, the session, the persona, or the repo involved in either kill. The suspects named at filing time — a Bash call with unbounded stdout (a repo-wide grep, a `find` over `/`, a `cat` of a large log) and an oversized MCP response — are **unconfirmed**, and no evidence has been gathered for or against any of them.

The two dead pids (674727, 746520) could not be linked to sessions after the fact. The attribution mechanism above works on **running** processes; both victims were already reaped. Do not attempt to infer which session died from the timing — roughly two dozen were live.

**The work done makes the next occurrence attributable. It cannot explain the last one.**

### The 24G ceiling is a judgement, not a measurement
There is no data on a healthy session's peak RSS. The observed fleet sits under 1 GB, so 24G is roughly 24-48x headroom — but a legitimately heavy session (a large file read, a big MCP response) could be capped for doing its job, and **that failure would look exactly like this bug rather than like a guard working**. If that matters, run the watcher with `--report` for a day and set the ceiling from the observed distribution before the cap goes into service.

### Why it started today is unexplained
Zero kills in the preceding 14 days, two within 15 minutes, none in the 47 minutes since. Nothing here explains the onset or the stop. A change in workload, a change in the CLI, and coincidence are all still open.

### Cost of chasing it further
The obvious next step — sweeping journals, transcripts and the filesystem for the culprit — is the same class of unbounded output that may be causing this. Any investigation should bound its own reads.
