### 🔴 The write guard cannot be the correctness prompt — it answers too late

The prompt Rick named is real, at `running_fifo_queue.py:1751` (`_fire_correctness_check_async`,
fired at `:1591`):

```python
msg = f"Was this answer correct? Question: '{truncated_question}' Answer: '{truncated_answer}'"
… ResponseType.YES_NO … → snapshot.answer_is_correct → save_snapshot()
```

But it runs on a **daemon thread, non-blocking**, and on timeout *"leaves `answer_is_correct` as
None (unverified)"* — **the row is already written at `:1565` before the user answers.**

| guard | mechanism that actually works there |
|---|---|
| **READ**, head of the process | refuse any row whose `answer_is_correct` is not a confirmed **True**. Three states, starting at unknown ⇒ **fails CLOSED** — exactly what my `routing_command` guard failed to do |
| **WRITE**, after the agent executes | **the router must have CHOSEN the agent.** A mode-forced answer is not evidence about the question — the user overrode the router — so it is not written. Plus the CRUD exclusion v2 is missing |

⇒ `answer_is_correct` is the **read** guard's field. The **write** guard keys on *who picked the
agent*, not on a verdict that has not arrived. **Both ends are Rick's ruling; only the write-side
mechanism differs from the one he named, and it differs because the prompt is asynchronous.**

### ✅ RULED — the read guard NEVER asks, and an unconfirmed row is never served even once

> **Rick**: *"We want to keep unconfirmed answers from replaying until they are confirmed."*

I put two readings to him rather than paraphrase, because they differ in a way that matters: under
one, an unconfirmed row is **never** served; under the other, its **first** replay still happens and
only a later one is stopped. **His sentence forbids the second.**

- **No new question is ever asked at the head end.** The only question put to the user stays the
  existing end-of-execution *"was this answer correct?"* The head merely **consumes** what the tail
  recorded.
- **Every hit on an unconfirmed row degrades to the spoken memory-problem path** and re-runs, until
  the completion-end confirmation flips it to `True`.

**How to write it** (finding 15, Krishna's serializer trace, on Tiberius's caution): the guard reads
the **hydrated snapshot object** — `snapshot.answer_is_correct is True` — **never the raw column
value**. Both writers serialize through the same shared record builder, so representations are
uniform; **typing the column is optional hardening** against a future writer that skips that
serializer, not a prerequisite. It **fails safe toward over-refusal.**

⚠️ Tiberius's underlying caution is why this note exists at all: **a guard hung on a loosely-typed
nullable column is exactly the mistake I already made once with `routing_command`.** Twice the same
shape. That is worth its own line, not a footnote.

## Rick's ruling on cache scoping — 2026-08-21. NOT user-scoped, and the reason is mechanical.

> *"I am inclined to not make cache lookup user-ID specific. We want person A to benefit from a
> cached answer for person B — that's for sure… questions about the weather or what time it is are
> utterly non-personal by their very nature, and questions about what's on my to-do list are actually
> scoped by the dataframe passed into them, such that the exact same question summons the exact same
> Python code that actually reads a different database. So while the answers are personal, the code
> that executes them is not. That cache exists not just to replay an answer but primarily to replay
> Python code that then recalculates the answer on a per-user basis. So in general we're okay, but we
> should probably document that particular lookup and note it may cause problems in the future."*

**The cache stays shared. Row `85b5c58c` closes on this.**

### I verified the mechanism rather than recording the argument — it holds

`InlineExecutor._replay` (`executor.py:96`):

```python
snap   = work.job.for_current_user( work.user_id, work.session_id )
snap.run_code()
answer = snap.run_formatter()
```

**A cache hit re-executes the stored code as the asking user, then re-formats.** It is not a text
lookup. The snapshot is a **cached computation**, and `for_current_user` rebinds it before it runs —
so the same question replays the same Python against a **different database**. Rick's account of his
own design is correct, and it is the reason the shared cache is safe rather than an argument that it
is.

### 🔴 THE ONE CASE WHERE IT DOES NOT HOLD — codeless snapshots serve stored TEXT

`solution_snapshot.py:848`, in the code's own words:

> *"CalculatorAgent and similar deterministic-dispatch agents have no Python to save… On replay,
> those snapshots' answers come from the cached `self.answer` field, **not from re-execution**."*

⇒ **For a codeless snapshot there is no per-user recalculation.** The stored words are served
verbatim. Rick's safety argument is load-bearing on `run_code()` doing something, and for these rows
it does not.

**Why this is a documented future risk rather than a live one:**

| | |
|---|---|
| today's codeless agent | `CalculatorAgent` — *"15% of 80"*. **Nothing personal to leak** |
| the 9 codeless receptionist rows | finding 14's evidence they exist; **they die on replay**, and the dump removes them |
| what would make it live | **any future agent that is deterministic-dispatch AND answers about a person's own data.** Codeless + personal is the combination to refuse |

⇒ **The rule to carry forward: a snapshot may be shared across users only if replaying it RE-RUNS.**
A codeless snapshot is a stored answer wearing a cached-computation's clothes. **If a future agent is
added with no code to save and a personal answer, it must not be snapshotted** — the same shape as
the existing CRUD exclusion, for the same reason.

## ✅ Rick's ruling on the cache — 2026-08-20

> *"We should simply suck it up and unify caching in the same change, and the [brain's] cache takes
> lead, the other caches get removed. There's no reason that we cannot add the confirmation dialogue
> back — it should be a literal one-line call, correct?"*

**Adopted: one cache. The brain's lookup leads; stages 1 and 2 are removed.**

### On the one-line question — the CALL is one line, the FEATURE is not

The classifier really is one line, near enough:

```python
run_previous_best_snapshot = ConfirmationDialogue( spec, debug=…, verbose=… ).confirmed( question )
```

But confirmation is **a two-turn protocol spread across two separate calls to `push_job`**, not a
synchronous prompt:

| turn | what happens |
|---|---|
| 1 | near-match found → a **blocking object** is stored, `is_accepting_jobs()` goes false, user is asked |
| 2 | the user's next utterance re-enters `push_job`; because the queue is not accepting, it is read as the **answer**; `pop_blocking_object()` retrieves the snapshot and replays it |

So the machinery is the accept-state gate plus the blocking-object push/pop. The one-line call is
only the classifier on turn 2.

### ⇒ And that is good news, because the brain already has that protocol

`AskFlow` already parks a request, asks a question, and resumes on the answer:
`_needs_input` → `PendingRequests` → `AskFlow.resume()` → `POST /api/v2/resume`. That is the same
two-turn shape, built and tested.

**So the confirmation should be expressed as a needs-input park, not re-plumbed onto the blocking
object.** One protocol for "the system asked you something and is waiting", instead of two —
which is the single-source-of-truth goal applied to the ask/resume path as well as to routing.

⚠️ This raises the stakes on the `parked` rename (finding 5): the confirmation dialogue would
literally *be* a needs-input park, sitting beside `Outcome.status="parked"` meaning "queued for
execution." Do the rename **first**, as step 1.

### B0(ii) — `main.py`'s construction order, READ rather than assumed

**The plan says of step 12: *"I have not read `main.py`'s construction order and will not assert that
it is fine."* It has now been read, at HEAD.**

| what | where |
|---|---|
| `lifespan()` | `src/lupin_app/main.py:569–1218` |
| `jobs_todo_queue = TodoFifoQueue( … )` | `:731` |
| `jobs_run_queue = RunningFifoQueue( … )` | `:734` |
| `restore_pending_jobs( … )` | `:1038` |

🔴 **The queues are up in time. The FLOW IS NOT — and that is the finding.** The AskFlow is **not
built during `lifespan` at all**. It has exactly ONE construction site: `build_ask_flow`
(`routers/v2_ask.py:83`), reached only through the `get_ask_flow` FastAPI dependency (`:124`) and
memoised in `_ASK_FLOW_CACHE` (`:134`). That dependency runs on an HTTP request. **The restore runs
before any request exists**, so at `:1038` there is no `flow` to call `submit()` on.

*(Found by Pocholo, checked here at HEAD. My first pass concluded "the restore can build the flow
itself" — true in the narrow sense that every ingredient is import-time constructible, and wrong as a
design, because it would leave TWO flow instances in one process with separate caches, pending stores
and executors.)*

**Two facts that decide the shape rather than merely permitting one:**

1. **`get_ask_flow()` raises `HTTPException( 503 )` when `v2 flow enabled` is false** (`:139`). That
   is an HTTP-layer refusal, and it would fire during boot. **The restore must not call it.**
2. **The flow is one-per-process today only because `ConfigurationManager` is a singleton.**
   `get_ask_flow` constructs a `ConfigurationManager` on every call and keys the cache on
   `id( config_mgr )` (`:133`). *Checked rather than assumed* — the class carries the `@singleton`
   decorator (`configuration_manager.py:72`), so the id is stable and "built once" holds. **It is an
   implicit dependency; if that decorator ever came off, every request would build its own flow and
   nothing would say so.**

⇒ **Proposed shape for step 12** (Pocholo's, adopted): build the flow, the registry and the
`QueueExecutor` **once inside `lifespan`, BEFORE the restore**, park the instance on `app.state`, and
have the route dependency return that singleton instead of building its own. One instance, explicit
ownership, no reliance on the config manager's singleton-ness, and no HTTP refusal reachable at boot.
The ingredients are all import-time constructible — the registry table is built at import
(`registry.py`), `make_executor` is a plain factory, `V2Cache()` takes no startup argument — so the
build can sit anywhere after `:734` and before `:1038`.

⚠️ **Code held until Lane A's step 2 (`QueueExecutor`) merges.** Today's `QueuedExecutor`
(`executor.py:120`) raises `NotImplementedError`, so there is nothing to park yet.

⚠️ **What would break it**, and what the pin catches: hoisting the restore above the queue
construction, calling `build_ask_flow` from inside `lifespan` without deciding its position relative
to the restore, or giving `build_ask_flow` a second parameter that only exists after `:1038`.

**Pin**: `src/tests/unit/test_main_boot_order_v2_submit.py`, five tests, source-order assertions by
AST over `main.py` (importing it runs a heavy module-level graph; the ordering fact lives in the
source). **Red on revert**: inserting a `restore_pending_jobs(...)` call above `:731` fails two of
the five.
