## Context

**The problem.** v1's routing grew into a hand-written `if/elif` ladder in `todo_fifo_queue.push_job`,
one branch per agent. v2 (`AskFlow`) was built as a single legible path — cache → router → resolve →
argument expeditor — and it works, but **nothing in the product calls it.** Its only caller is the
HTTP route `POST /api/v2/ask`; the surface people actually speak to never reaches it.

**Rick's framing, which corrects mine.** This is not about proving v2 is *better*. It is a
**replacement**: one comprehensible entry point in place of code that "had evolved into a pile of
spaghetti and was impossible to comprehend." The measurement only has to show it does not regress.
The asynchronous CJ Flow queue **stays** — `AskFlow`'s synchronous executor is an artifact of the
experiment's scope, and the head end was always going to be grafted onto CJ Flow.

**Already landed tonight** (committed, merge held behind attempt 12): the ladder is gone. Six
branches became one `registry.resolve_voice()` lookup, so a seventh conversational command is one
table row and zero edits to the queue. That closed **registration**. This plan closes **routing**.

## The shape: ONE integration, not three grafts

`push_job` calls `AskFlow.run()` with a **queue-backed executor** injected. Cache, router, resolve
and the expeditor all run **inside that one call** — they are not grafted separately, because taking
them one at a time would leave a v2 router beside a v1 expeditor and would re-implement `AskFlow`'s
degradation logic inside `push_job` step by step, rebuilding spaghetti somewhere new.

**The seam already exists.** `AskFlow` delegates execution to an injected `Executor` protocol
(`src/cosa/rest/v2/executor.py`); `InlineExecutor` is only the experiment's implementation. `Outcome`
already declares the other one:

```python
status is "done" when an answer was produced, "parked" when a QUEUED EXECUTOR
handed work off (phase 2), "failed" when replay or the agent threw.
    status : Literal[ "done", "parked", "failed" ]
    job_id : Optional[ str ] = None
```

The queued-executor slot, "phase 2" and `job_id` are already in the contract. Nobody built the
executor. **That is the new code: one class.** (The word "parked" there becomes `waiting` — see
finding 5.)

## 🔴 What exploration changed — five findings, and the first one is the plan's real subject

### 1. There are already TWO cache stages on the voice path. Adding v2's would make THREE.

This is the finding that matters and my earlier write-up missed it entirely.

| # | where | what it does |
|---|---|---|
| 1 | `todo_fifo_queue.push_job` | similarity search → `ConfirmationDialogue` → `_queue_best_snapshot` |
| 2 | `running_fifo_queue.py` (~line 292-325) | a **second** lookup at execution time, own `threshold_confirmation`, own CRUD exclusion |
| 3 | `AskFlow.run()` step 1 | `cache.lookup()` with `similarity_floor`, replay on exact hit |

Routing `push_job` through `AskFlow` puts all three in one request unless something is removed.
Three thresholds, three definitions of "hit", two of them already disagreeing about CRUD.

**This is the spaghetti, precisely located.** It is also the biggest decision in the work, and it is
Rick's — see Open Decisions.

### 2. `_build_agent` uses `spec.factory`, which bypasses tonight's CRUD ruling

`flow.py::_build_agent` constructs from `spec.factory` — the **v2 pin**, deliberately non-CRUD for
cache-hit reporting. Rick ruled tonight that voice keeps the CRUD fork and the registry carries the
flag (`resolve_voice`). **Routing voice through `AskFlow` as it stands would silently undo that
ruling within a day of making it.**

> 🔴 **SUPERSEDED 2026-08-20 by Rick's ruling on the reporting pin (below).** The fix is no
> longer "the flow resolves the voice binding" — it is **one CRUD-aware resolver**, so there is
> no wrong binding left to reach. Finding 2 is closed by deletion, not by plumbing.

### 3. `_build_agent` is not the queue's agent construction

It hardcodes `push_counter=-1`, `question_gist=agent_question`, `auto_debug=False`,
`inject_bugs=False`. `push_job` passes the real `question_gist` (used by the query log),
the real `push_counter`, and the real debug flags. Agents built by the flow are **not** the agents
the queue builds today.

### 4. Write-back fails SILENTLY, not loudly

`_maybe_write_back` opens with `if not ( snapshotable and outcome.status == "done" ): return None`.
A `parked` outcome writes nothing and says nothing. **The gap would not announce itself** — the
cache would simply stop learning, which is the failure mode nobody notices. And note finding 1:
`running_fifo_queue` may already be writing snapshots at completion, so the answer here may be
"reuse what exists" rather than "build a deferred path."

### 5. Two smaller things, mine to handle either way

- `_run_agent` treats anything but `"done"` as agent failure → receptionist. It must learn **parked
  is success-in-flight**. Small, but it sits in the core degradation path and needs its own control.
- **`parked` already means "waiting on a human answer"** in `flow.py` (`_needs_input`,
  `status="parked"`). `Outcome.status="parked"` means "queued for execution." Two states, one word,
  and the second is about to go live. **Rick's ruling, 2026-08-20**: the queued-for-execution state
  is called **`waiting`**, not parked — *"parked implies that it's temporarily paused, and that is
  not the state we are talking about."* A queued job is not paused; it is waiting its turn and will
  run. `parked` stays with `_needs_input`, where something genuinely IS suspended pending a human.
  Rename first, step 1.

## ✅ Rick's ruling on the cache — 2026-08-20

> *"We should simply suck it up and unify caching in the same change, and the [brain's] cache takes
> lead, the other caches get removed. There's no reason that we cannot add the confirmation dialogue
> back — it should be a literal one-line call, correct?"*

**Adopted: one cache. The brain's lookup leads; stages 1 and 2 are removed.**

### On the one-line question — the CALL is one line, the FEATURE is not

The classifier really is one line, near enough:

```python
run_previous_best_snapshot = ConfirmationDialogue( spec, debug=…, verbose=… ).confirmed( question )
```

But confirmation is **a two-turn protocol spread across two separate calls to `push_job`**, not a
synchronous prompt:

| turn | what happens |
|---|---|
| 1 | near-match found → a **blocking object** is stored, `is_accepting_jobs()` goes false, user is asked |
| 2 | the user's next utterance re-enters `push_job`; because the queue is not accepting, it is read as the **answer**; `pop_blocking_object()` retrieves the snapshot and replays it |

So the machinery is the accept-state gate plus the blocking-object push/pop. The one-line call is
only the classifier on turn 2.

### ⇒ And that is good news, because the brain already has that protocol

`AskFlow` already parks a request, asks a question, and resumes on the answer:
`_needs_input` → `PendingRequests` → `AskFlow.resume()` → `POST /api/v2/resume`. That is the same
two-turn shape, built and tested.

**So the confirmation should be expressed as a needs-input park, not re-plumbed onto the blocking
object.** One protocol for "the system asked you something and is waiting", instead of two —
which is the single-source-of-truth goal applied to the ask/resume path as well as to routing.

⚠️ This raises the stakes on the `parked` rename (finding 5): the confirmation dialogue would
literally *be* a needs-input park, sitting beside `Outcome.status="parked"` meaning "queued for
execution." Do the rename **first**, as step 1.

Self-contained, per-request, timeout with exponential backoff, safe default. **This is the design
Rick is asking for, already shipped.**

**And the two-turn path cannot fire.** Measured, not reasoned:

Nothing in the running system ever arms a blocking object ⇒ `is_accepting_jobs()` never goes false

⇒ **Step 5 is a DELETION, not a port.** Remove the `ConfirmationDialogue` branch, the

### Name the kludge, on the way out — Rick's instruction

> *"That is one reason why I wanted to build this better. There should be some kind of comment in the
> code that that is a terrible ugly piece of engineering, a true kludge! So I will not be sad to see
> that piece of ugly plumbing ripped out."*

The replacement carries a note recording **what it replaced and why that was bad**, so nobody
reinvents it:

- the old mechanism spread ONE user interaction across TWO calls to `push_job`, coupling it to a
  queue-wide `is_accepting_jobs()` flag — so a pending confirmation **blocked the whole queue for

- the state lived in a `pop_blocking_object()` side-channel, invisible to anything that did not

The synchronous ask already in the file has none of those: it blocks only the request that asked,
the answer is bound to that call rather than to the queue's state, and it carries its own timeout
and safe default instead of waiting forever on a flag.

## ✅ Rick's refinement — the receptionist IS the default, and the failure must be SPOKEN

> *"If we wrap the routing call correctly, perhaps we could give it a good default go-to string that
> explains that it just had a routing error and that for the moment we're going to leave you with
> the default, which is the receptionist — who is always going to be our default."*

**Both premises confirmed against the code.**

1. **The receptionist is already the universal default.** Six call sites in `flow.py`, one per
   failure mode: `replay_error` `:102`, `router_error` `:110`, `unknown_command` `:113` and `:185`,
   `extract_error` `:124`, `agent_error` `:247`. There is no failure path that lands anywhere else.
2. **Falling back to it is the right behaviour**, and it does not contradict *"fail loudly and
   bail."* Loud is about the **user hearing what happened**; bail is about **not routing around it**
   with a cached answer. The receptionist is where you land after saying so, not instead of saying
   so.

### 🔴 And the refinement exposes a gap that is live today

The flow already HAS the mechanism. `_receptionist` takes `primary_error` — *"the FAILURE THAT
CAUSED THE DEGRADE"* — and its own docstring states the principle exactly:

> *"a fallback that hides the fault it was reached by."*

**Two things break that promise:**

| # | gap | evidence |
|---|---|---|
| 1 | `router_error` **never passes `primary_error`** | `flow.py:110` — `self._receptionist( trace, question, ctx, "router_error" )`, no cause. Only `agent_error` at `:247` passes one. |
| 2 | even when passed, the cause is **never spoken** | `_finish` calls `_speak( trace, outcome.answer, … )` — the *receptionist's* answer. `primary_error` goes through `_compose_error` into the emitted `error` field of the response dict. **A JSON field Rick cannot hear.** |

So a routing failure today runs the receptionist, speaks its generic reply, and files the real cause
where only a log reader finds it. **Loud in the payload, silent in the room** — the same shape as
the bare-pytest warning noted earlier in this plan, where the guard did not reach the reader it
existed for.

### What lands

- **Wrap the routing call**; on failure pass a `primary_error` that names it.
- **The receptionist gets a go-to string that says so out loud** — a routing problem happened, and
  you are being handed to the receptionist meanwhile. Rick's words, and it is the part that makes
  "loudly" true rather than nominal.
- **No cache fallback beneath a broken router** — the earlier ruling, unchanged.
- Pinned by a test that a router failure produces a SPOKEN payload naming the routing failure, red
  on revert. A test asserting only the `error` field would pass while the room stayed quiet.

⚠️ Still not assumed: whether the *pre-existing* receptionist-degrades-on-`router_error` path should
be replaced by a hard failure. Rick's *"routing cannot fail"* can be read that way, but this
refinement points the other direction — degrade, and say so. **Reading it as "keep the receptionist,
make it speak"; correct me if that is wrong.**

## ✅ Rick's ruling on cache-vs-router order — 2026-08-20 (closes the ordering hole)

> *"Currently a router costs approximately 100 milliseconds. I'm happy to pay that cost if it makes
> everything read more easily and doesn't hide a potential bug. So I say route first and then check
> the cache."*

**`AskFlow.run()` reorders: router → resolve → cache.** The flow then knows the command before it
looks anything up, and applies the same skip `running_fifo_queue:291` applies today — **CRUD
commands do not read the cache at all**, because the data behind them is mutable.

### The hole this closes

`flow.py:93` made cache step 1 and the router step 2, so there was no `command` at lookup time and
the flow **structurally could not** do what the queue does. Dormant today (CRUD results are never
snapshotted, and tier 1 needs an exact string match) — **live the moment 6a lands**, because gist
matching is loose about wording by design. *"Put milk on my todo list"* would gist-match an earlier
*"what's on my todo list"*, the read replays, the write never runs, and nothing errors.

### Why Rick's option beat mine, on a point I missed

I recommended keeping cache-first and refusing to replay when the **matched snapshot's**
`routing_command` forks to CRUD. Cheech's reviewers then found what that leans on:

| evidence | reading |
