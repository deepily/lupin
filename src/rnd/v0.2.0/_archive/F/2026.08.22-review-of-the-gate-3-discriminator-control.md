**Verdict**: **The positive control is right and does exactly what it claims. The NEGATIVE control cannot fail — and it is the one carrying the retirement trigger.**

## The positive control — correct

`test_a_speakable_filter_SILENTLY_DROPS_a_typeable_not_sayable_command` builds two specs, one `user_initiable=True / speakable=False`, and asserts that a `speakable`-filtered dropdown produces a `MISSING` against a `user_initiable` oracle. That is the manufactured discriminator the data does not supply, driven through the real shared predicate. Reverting the gate to `speakable` turns it red. **This is the test that makes the rewrite mean something**, and it does.

The framing in his message is also right and worth keeping: the wrong filter *raises no complaint of its own* — it just quietly renders a smaller set. The predicate is what converts that silence into a red.

## 🔴 The negative control never reads the registry, so it can never fail

```python
def test_the_two_filters_are_indistinguishable_without_the_manufactured_case( self ):
    specs = [
        { "command": "agent router go to math",    "speakable": True, "user_initiable": True },
        { "command": "agent router go to weather", "speakable": True, "user_initiable": True },
    ]
    self.assertEqual( self._dropdown_from( specs, "speakable" ),
                      self._dropdown_from( specs, "user_initiable" ) )
```

Its stated job: *"If this ever fails, the real registry has grown the discriminating command and the synthetic case above can be retired in favour of it."*

**It reads two hand-written dicts. `REGISTRY` is never imported into it.** Both specs are declared with `speakable=True, user_initiable=True`, so the two filters return the same set **by construction** — the assertion is `{math, weather} == {math, weather}`, and no change to the registry, ever, can make it false.

So the retirement trigger he designed **does not exist**. The synthetic case will still be sitting there, still described as temporary, on the day a real typeable-but-not-sayable command makes it redundant — and nothing will say so.

**Fix — make it read the thing it is about:**

```python
from cosa.rest.v2.registry import REGISTRY
ui = { c for c, s in REGISTRY.items() if s.user_initiable }
sp = { c for c, s in REGISTRY.items() if s.speakable }
assert ui - sp == set(), (
    f"the registry has grown a typeable-but-not-sayable command: {ui - sp}. "
    "Retire the synthetic discriminator above in favour of this real one." )
```

Measured today: `ui − sp` is `set()`, so it is green now — and it goes red the day the discriminator appears, which is precisely when someone should be told. **Note it must be the one-sided difference, not `ui == sp`**: the full sets are genuinely unequal (`automatic` and `none` are speakable and not initiable), so an equality would be red today for the wrong reason.

## One naming hazard, not a defect

`TYPEABLE_NOT_SAYABLE = "agent router go to test fix expediter resume"` — a **real** command, carrying a **counterfactual** attribute. In the live registry that command is `speakable=True`; the test labels it `speakable: False`.

Using real command strings is the house convention (`_card_drift` insists on it), and the predicate genuinely does not care. But the constant *reads* as a statement about that command, and it is the opposite of what the registry says. One line naming the attribute as counterfactual — and why the string is real anyway — costs nothing and stops the next reader taking it as documentation.
