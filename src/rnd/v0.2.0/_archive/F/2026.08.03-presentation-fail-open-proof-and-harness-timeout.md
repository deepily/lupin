## 2. The proof that the fail-open fix works

Commit `0477becf` (Krishna) gave all four presentation gates a `response_default` of CONTINUE plus
a 600s timeout, mirroring the podcast gate. Rick ordered it after the earlier run died.

**Server log, verbatim:**

```
Gate 1: 'Narrative Arc' answered by a DECLARED DEFAULT, not a human (source=dispatch_failed, value='Approve').
Gate 2: 'Slide Outline'  answered by a DECLARED DEFAULT, not a human (source=dispatch_failed, value='Approve').
```

**Why this is strong rather than suggestive**: the auto-proxy answered *nothing* during this run —
its statistics read **5 received / 0 sent / 5 skipped**. So the gates did not pass because something
answered them. They passed because the declared default resolved on the `dispatch_failed` path —
precisely the 503 that raised `VoiceGateNotAnsweredError` and killed `pr-b1ea3708` at 110 seconds
earlier the same evening.

The log names both the *source* and the *value*, so an auto-continue remains distinguishable from a
human approval after the fact. That matters: fail-open means content can ship unreviewed, and the
record has to say so.

**Honest limit**: this proves the **dispatch-failed** path only. The **silence** path — a delivered
ask that nobody answers for the full 600 seconds — is not exercised here and remains unproven.

## 3. The defect this run exposed — the harness reports FAIL on a successful build

`test_presentation_live_smoke.py` polls for job completion with a **900-second** timeout. A real
presentation build takes **~15 minutes** — measured, not estimated, from this run's own log
(`"Presentation complete! Generated 15 slides, ~15 minutes"`).

So the test gave up while the job was still working, and the report reads:

```
Total: 0 passed, 1 failed
FAIL: Timeout after 900s waiting for job_id=pr-bf7ac6f5
```

**The job succeeded. The test failed.** Those are different facts, and the report only carries the
second one. A reader who trusts the report concludes the presentation pipeline is broken when it
just produced a 15-slide deck.

This misled the investigation twice tonight — once on `pr-b1ea3708` (where the job *had* genuinely
died, but at 110s, not at 900s) and again here (where it had not died at all).

**Fix direction, not yet assigned:**
1. Raise the poll timeout above a realistic build — 900s is below the measured p50.
2. Better: have the poller distinguish *still-running* from *dead* by reading job state, rather than
   inferring failure from its own patience running out. A timeout should report "gave up waiting,
   job state was X", never a bare FAIL.
