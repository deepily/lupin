## F2 — BLOCKING (pre-build, RAN). A harness process without `LUPIN_CONFIG_MGR_CLI_ARGS` produces a full arm of silence that looks like a clean run.

`_apply_dm_tutor` is **contractually incapable of raising** (`src/cosa/rest/routers/dm.py:1121`,
docstring *"returns … and NEVER raises"*). Its config comes from `get_dm_tutor_config()`
(`:719`), which is fail-closed: any config-read failure returns `_DM_TUTOR_DEFAULTS` with
`enabled: False` (`:711-716`) and prints a warning to stdout.

Executed, with the env var unset:

```
[dm-tutor] WARNING: config read failed, tutor OFF for this send: [LUPIN_CONFIG_MGR_CLI_ARGS] is NOT set
CONFIG WITH ENV UNSET: {'enabled': False, 'trigger_claims': 4, ...}
OUTCOME: disabled | fired: False | enabled: False
delivered == original: True
```

⇒ Both arms come back `tutor_outcome: "disabled"`, zero fabrications each, **perfectly paired and
entirely vacuous**. Nothing raises; the only signal is a stdout line in a long run.

**Ask**: the harness asserts `meta["tutor_enabled"] is True` and `meta["tutor_fired"] is True` per
row and ABORTS on the first row that is not, rather than recording it. This is the §1.2a
"a guard that cannot fire reads exactly like a guard that fired and found nothing" failure class,
relocated from the freeze guard into the harness.

## F3 — BLOCKING (pre-build). `model_failed` cannot be a passive metric on the Flash-Lite arm.

Same never-raises contract: a Vertex arm with missing ADC, a 404 region, or an expired credential
returns `tutor_outcome: "model_failed"` per row (`dm.py:1190-1195`) and the run completes. §2.3
lists `model_failed` as a *coverage* metric, which is right for a model that occasionally refuses —
but it is also the shape a **totally broken arm** takes, and the two are indistinguishable in the
recorded `meta`.

**Ask**: a pre-stated abort threshold on `model_failed` rate (and a check on the first N rows before
committing to the full replay), stated before arm 1 alongside the discordant floor.

## F4 — BLOCKING (pre-build). Nothing routes the tutor to `dm_tutor/flash_lite`; the obvious swap edits live production config.

Consumer set re-derived at HEAD by grep across `*.py`/`*.ini`/`*.md`/`*.sh` (venv excluded): the key
`dm_tutor/flash_lite` has **zero production consumers** — only `llm_client_factory.py:222` (a

`DmTutorAgent.ROUTING_COMMAND` → `AgentBase`.

⇒ The one-line way to run the Flash-Lite arm is to repoint `lupin-app.ini:303`. That swaps the model
for **every DM the fleet sends** while the arm runs, spends on a paid endpoint outside the
experiment, and writes those rows into the very corpus under study (~5 rows/min, §1.2).

**Ask**: use the seam that already exists — `_apply_dm_tutor( body, config=…, rewrite_fn=… )`
(`dm.py:1121`) takes a per-arm `rewrite_fn`. Swap the arm by injection in the harness process.
Do not edit `lupin-app.ini:303`.
