## F2 first, because it is already fixed — the pin, before and after

At `d764e00e` the test compared a recorded sha256 of the scanner. Measured on a clean export:

| step | result |
|---|---|
| baseline | 49 passed |
| append one comment line to `secret_scan.py` | **1 failed** — exactly the pin, as her receipt says |
| paste the new sha into `detector_sha256`, run **no scan** | **49 passed** |

So the cheapest way past the red was the one nobody should take. `3c94c787` removes the
hash comparison entirely and re-runs the scan, comparing a fingerprint over the whole
masked result set. Re-tested at `3c94c787`: the same paste-the-hash move now leaves the
recorded fingerprint in charge, and the recorded fingerprint cannot be written without
having scanned. **The hole is closed and the replacement is the right shape.**

⚠️ One property changed with it, worth stating rather than discovering: the byte-hash
trigger is gone, so a scanner change that alters no finding **at the scanned ref** is now
green — correctly, by her design, but it is a narrower trigger than `d764e00e` promised.
I confirmed the narrowness is real: widening the field vocabulary with
`connection_string|dsn` left the suite green, because no line anywhere in this repo
matches those keys. Green was right there; the point is that the trigger now depends on
the *content of the scanned ref*, which is F4.

## F1 — two definitions of "a secret", and they have already parted company

`secret_scan.py` copies `_PLACEHOLDER_VALUE` and `_PEM_PRIVATE_KEY` from
`_scope_registry.py` with a comment naming the commit they came from. Measured: both are
byte-identical to the detector's today. Nothing keeps them that way, and a comment naming
a sha is not a test.

The deeper drift is in what each side counts as a credential. Three shapes the doc-viewer
detector refuses as of `324a40d3` are invisible to the scanner:

| shape | doc-viewer detector | `secret_scan.py` | why it is missed |
|---|---|---|---|
| a whole service-account key carried as a JSON STRING (`google_credentials = "{\"type\": …}"`) | BLOCK | **missed** | `_looks_like_a_reference` returns `template` — the value contains `{` and `}` |
| the same line inside a JSON config file | BLOCK | **missed** | same |
| `"private_key": ["MIIEvQIBADAN…"]` — key material as a list of lines | BLOCK | **missed** | returns `structure` |
| `client_secret = "GOCSPX-…"` (control) | BLOCK | **found** | — |

These are her own precision heuristics firing on real secrets — the same trade the
detector made, and the same trade that hid these shapes from the detector until tonight.

**Suggested close**: (a) one home for the two shared patterns, or a three-line test
asserting the scanner's `.pattern` equals the detector's, so either side moving is loud;
(b) the three shapes above as scanner fixtures.

## F4 — the standing scan looks at a ref nobody commits to

`scan_fingerprint` is recorded against `origin/main`, and the test re-scans that ref.
Measured tonight:

| | |
|---|---|
| `origin/main` | `1fa05b16`, dated **2026-08-03** |
| the branch the fleet works on | **645 commits ahead** of it |
| findings at `origin/main` | 102 |
| findings at `HEAD` | **103** |

So the control's standing inventory describes a two-week-old snapshot. A credential
committed to the working branch today is seen by nothing: the gate only reads ADDED lines
and is not installed, and the full scan only reads a ref the fleet has not pushed to in
two weeks. That is not an argument against her design — scanning the ref rather than the
checkout is exactly right, and she documents why — it is an argument that `origin/main` is
the wrong ref for **this** repo's working reality.

**Suggested close**: record and re-scan the working branch tip as well as `origin/main`.
The published ref answers "what can a stranger read"; the branch tip answers "what did we
just write", and right now only the first question has an owner.

## F3 — everything under `src/tests/` is invisible to BOTH surfaces

`_is_text_path` returns False for any path containing `/tests/`, starting `tests/`, or
containing `/test_`, and the pre-commit gate imports that same function. Measured: a
credential added to `src/tests/unit/fixtures/thing.json` passes the gate, and the file is
never scanned.

The reason is sound — her own suite plants 13 fake secrets in test files, and scanning
them would make every run report itself. The remedy is narrower than the rule: exclude the
scanner's own fixtures, not the whole test tree. At minimum this belongs in the docstring's
**WHAT IT STILL CANNOT SEE** list, which is otherwise unusually honest and does not name it.

## F5 — a numeric value is never filtered, so a numeric constant reads as a candidate

`_looks_like_a_reference` filters paths, references, templates, prose and identifier
names, but nothing rejects a plain number. Receipt, and it is my own code doing it: the
two findings `HEAD` carries that the recorded snapshot does not are

```
src/cosa/rest/routers/_scope_registry.py   CREDENTIAL_SNIFF_BYTES       (value 8192)
src/cosa/rest/routers/_scope_registry.py   CREDENTIAL_MAX_SNIFF_BYTES   (value 1_048_576)
```

Both are read-window sizes. The key matches the field vocabulary, the value is a number,
and `_emit` only skips values shorter than four characters — so `8192` is reported.

**Suggested close**: one arm returning `numeric literal` for a bare integer, float or
underscore-grouped number. Name the trade the way she names the others: a purely numeric
secret — a PIN, a numeric API id — would then be missed.

## F6 — the new pin test needs git and a fetched `origin/main`

Measured: on a `git archive` export of `3c94c787` with no git metadata, the suite is
**1 failed, 48 passed** — the pin test, because `scan_ref` has no repository to read. It
takes **4.8s**, nearly all of the suite's runtime.

That puts it in the same class as `test_gate_reachability_census` and
`test_terraform_invariants`: tests whose result depends on the environment rather than the
code, which is what made my own branch comparison hard to read tonight. Worth either a
skip with a stated reason when the ref is unavailable, or moving it out of the unit tier.

## The two deliberate choices, tested rather than agreed with

**Added lines only** — verified through `added_lines_by_file` + `scan_text` on synthetic
staged diffs:

| case | result |
|---|---|
| the credential IS the added line | **BLOCKS** |
| the credential is already in the file, a comment is added above it | passes — the accepted trade, named in her docstring |
| the credential is added under `src/tests/` | passes — **not** named anywhere (F3) |

The trade is correctly described and correctly reasoned: a gate that fires on the repo's
existing credential-shaped lines gets switched off, and a gate that is off reads as
coverage while providing none.

**Not installed into `.git/hooks`** — verified: `.git/hooks/pre-commit` does not exist.
For a checkout worked by several sessions at once this is the right call. The consequence
to state plainly: **the gate is landed but not in force**, and the activation line lives in
a file only somebody already reading the gate would open. That is a decision for whoever
owns the checkout, not a defect in the commit.
