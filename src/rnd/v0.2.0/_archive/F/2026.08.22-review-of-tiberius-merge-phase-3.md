## Q1 — keeping both halves of `test_can_change_agent_mode`

His worry: *"have I just made one test do two jobs badly?"*

**No, and the framing is what resolves it: they are not two assertions, they are a synchronisation primitive and an assertion.**

- `wait_for( state="attached" )` on one option is a **wait**. It asserts nothing and cannot pass anything — it only unblocks. Without it the set-equality races the post-auth fetch and reds intermittently, which is Sam's point and it is load-bearing.
- `option_value_drift( rendered, expected_option_values() )` is the **assertion**, and it is the one that catches the partial render — Auto-Route plus `math` while fifteen agents are missing.

So his stated hole ("waiting on one option passes a partial render") is closed, because the wait is not what passes the test. They compose; neither is redundant.

**I checked the torn-read worry rather than assuming it away**: `renderAgentSelect` calls `replaceChildren()` and then appends in a loop, all inside one synchronous function. Browser JS is single-threaded, so Playwright cannot observe a half-built select between the two. No mid-render read is possible.

**One coupling, worth a comment and not a change**: the wait keys on the literal `agent router go to math`. If `math` ever leaves the `user_initiable` set — a legitimate future edit — this test fails as a 10-second timeout rather than as a drift report, and the next reader will debug the wait instead of reading the contract. A line saying "any user-initiable command will do; math is chosen because it is the least likely to move" costs nothing.

## Q2 — gate 2 as "notifications.html carries ZERO hardcoded options"

**It is a real check, and it is falsifiable in all three directions.** I mutated the tree and ran his file rather than reading it:

| mutation | result |
|---|---|
| baseline | **8 passed** |
| hand-write an `<option>` back into `#agent-mode` | **1 failed** |
| delete the `#agent-mode` select entirely | **3 failed** |
| drop the `agent-select.js` module `<script>` tag | **1 failed** |
| restored | **8 passed** |

**The middle row is the one that matters, and it is the trap I was going to raise.** A gate that asserts *absence* is satisfied by deleting the thing — an empty select and no select look identical to `"<option" not in markup`. He had already closed it with two counterweights: the select must still exist and still carry its `data-testid`, and the page must still load the module that fills it. So "emptied" and "deleted" are distinguishable, which is exactly what an absence-gate needs and usually lacks.

**`_agent_mode_select()` raises rather than skips.** It uses `html.index(...)`, so a renamed or removed element is a `ValueError` and a red test — not a quiet `return set()`. That is Mr Radio's rule from this morning ("a lookup miss must raise, never skip") already satisfied, independently.

**And it answers my own earlier objection.** I had said gate 2 would grep an empty room after phase 3 and pass vacuously. That was right about the *original* grep and wrong about this rewrite: this gate asserts the absence is **maintained**, so its red is "somebody pasted a list back in", which is a live failure mode for as long as the file exists. The vacuity I predicted lives in the counterweights, and the counterweights are present.

**Scope limit, stated because he asked me to try to break it**: the gate is scoped to `#agent-mode`, deliberately — other selects on the page are legitimately hand-written. So agent options hand-written into a *different* element would evade it. `test_the_page_names_no_routing_command` reads the whole file and closes that for command literals; a hand-written **mode key** (`value="math"`) in some other element would still slip through. That is a narrow gap, it is shrinking (phase 6 deletes the panel), and I would not widen the gate for it — recording it so nobody believes the coverage is broader than it is.
