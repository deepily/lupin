## 🔴 The finding — gate 3's discriminator does not exist in the data

Blocker 1 said gate 3 must test `user_initiable`, not `speakable`, because *"a command that is `user_initiable=True` but `speakable=False` — typeable, not sayable — can be missing from the dropdown entirely and gate 3 never notices."*

**Measured against the implemented table, that command does not exist:**

```
speakable       n = 18
user_initiable  n = 16

speakable but NOT user_initiable:   agent router go to automatic · none
user_initiable but NOT speakable:   (none)
```

`user_initiable` is a **strict subset** of `speakable`, and the two commands separating them are not agents at all — one is CONTROL, one is the internal no-command outcome. Neither would appear in the dropdown under any filter.

**So a gate 3 written on `user_initiable` and a gate 3 written on `speakable` are green on exactly the same inputs.** Revert the fix and nothing goes red. The assertion cannot distinguish the thing it was rewritten for — which is this plan's own stated failure mode, arriving through the door built to stop it.

**This does not make the field wrong.** Two questions genuinely deserve two fields, and the day a typeable-but-not-sayable command is added the field is already there. The problem is only that **real data provides no discriminating case, so the gate must manufacture one.**

**Fix**: gate 3's must-fail control drives the shared predicate with a **synthetic spec** — `user_initiable=True, speakable=False` — and asserts the dropdown must carry it. Then reverting the gate to `speakable` turns that control red, which is the only thing that makes the rewrite mean anything. Same shape as `_card_drift`'s control: drive the real predicate, withhold one side.

# Phase 2 — `GET /api/v2/agents`: clean, and it answers the open question

**Verdict: no findings. Every check I set out to make passes, and one of them settles Tiberius's question about gate 3.**

## The CRUD fork is applied once, not twice — verified by execution

The endpoint reads `effective = resolve( command, flow.crud_enabled ) or spec` rather than re-testing `if crud_enabled and spec.crud_factory`. One implementation of the fork, so the two cannot disagree. And `resolve()` was correctly extended to fork **both** user-facing strings (`registry.py:480-481`), so the new `crud_display_name` is live data rather than a field nobody reads:

| flag | command | `display_name` | `label` |
|---|---|---|---|
| off | todo | `Todo List` | `todo list` |
| off | calendar | `Calendar` | `calendaring` |
| **on** | todo | **`Todo List (CRUD)`** | `todo (CRUD)` |
| **on** | calendar | **`Calendar (CRUD)`** | `calendar (CRUD)` |
| either | math | `Math Agent` | `math` |

That matters because the plan's §5.1 requires the label a user sees to be the label of the agent that will actually run. It is.

**Taking `crud_enabled` off the flow rather than re-reading the INI key is the right call** and the docstring gives the right reason: a fourth read of `crud for dataframes agents enabled` is a fourth thing to drift, and the flow already holds the value it will itself route with.

## Pure projection, deliberately unfiltered

Nothing is filtered at the door — not the expediters, not `automatic`, not `none`. The client decides what to render by reading `user_initiable` or `speakable`. **This is what keeps gate 1 checkable**: the moment the door filters, "the endpoint equals the registry" stops being a statement anyone can test.

## Gate 1 is a real boundary, and so is gate 3

`test_command_set_equals_registry` asserts `served == set( REGISTRY )` — the left side parsed out of an HTTP response, the right side a Python dict. Genuinely falsifiable, as the review said.

**And the open question is answered**: `USER_INITIABLE_COMMANDS` is **derived**, not hand-maintained —

```python
USER_INITIABLE_COMMANDS = frozenset( c for c, s in REGISTRY.items() if s.user_initiable )   # registry.py:415
```

So `test_served_user_initiable_set_equals_the_registry_projection` compares the HTTP response against a projection of the table, across the same real boundary. **Gate 3 does not check the registry against itself.** That was Tiberius's second question to Sam and it comes back on the right side.

## One residual note, not a defect

Because the endpoint is a pure projection with no filtering, gate 1 can only go red if the **HTTP layer** loses something — a `response_model` pruning a field, a serialization drop, a duplicate key collapsing. That is a narrow failure class, but a real one and a known FastAPI foot-gun, and it is precisely the class no in-process assertion would catch. The gate is worth its keep.

## ⚠️ My first sweep could not have found it, and said so by returning zero

Worth recording because it is the day's theme arriving in my own work. My first pass derived the command from the mode key by string substitution (`presentation` → `agent router go to presentation`). That command does not exist, the lookup returned `None`, the comparison was skipped, and the sweep reported **TOTAL DRIFTED: 0** — a green that meant "I could not check these two rows", not "these two rows agree". The two keys it silently skipped were `podcast` and `presentation`: **the exact pair in question.**

The fix was to read the real mapping (`AGENTIC_MODE_MAP`) instead of inventing one, and to **print the unchecked keys** rather than let them vanish into a passing count. A sweep that cannot say what it skipped is a count over a list, which is the shape this plan disqualifies.

## Why this finding matters more than its size

**This is the drift the plan exists to kill, and it reached production with no gate noticing** — because until now nothing compared the two lists. It is the plan's premise arriving as a measured fact rather than an argument.

And it pairs instructively with the `user_initiable` finding above:

| | discriminator | status |

| gate 3 (`user_initiable` vs `speakable`) | **does not exist yet** — `user_initiable − speakable` is empty | latent; the gate must manufacture its case |

## One consequence to name before phase 3, so it is not read as a regression

The registry wins after phase 3 — the dropdown renders from it. So the option a user sees **changes from `"Presentation"` to `"Presentation Generator"`.** That is a user-visible text change riding along inside phase 3, correct and intended, and it will move any visual baseline that captures the select. It belongs on the rebaseline list beside the two already flapping, and it is not a regression.

**Unless someone rules the other way**: `MODE_METADATA`'s shorter `"Presentation"` may well be the better label. That is a human call, not a merge conflict — but it has to be made in the registry, because after phase 3 the registry is the only place that can carry it.
