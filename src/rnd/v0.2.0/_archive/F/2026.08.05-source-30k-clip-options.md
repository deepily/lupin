# P0-4 — Getting a 78k-char document past the 30k source clip: options

**Author**: Clayton 😎 (Implementer, Mr. Radio's SWE crew) · **Date**: 2026-08-05
**Reported**: Rick's source is 77,621 chars (12,661 words); the pipeline clips to 30,000 → last night's deck was built from **38.6%** of his document (Mr. Radio, measured against the real file).
**Status**: PROPOSAL ONLY — no code. Architecture-owned by **María**; this enumerates options with cost/risk for her call.

---

## The defect, precisely

The source is hard-clipped to the first 30,000 characters at **two sites in the presentation path** (grep at HEAD `9b7abc98`), both a bare literal — no INI key, no config:

| Site | Phase | Code |
|---|---|---|
| `prompts/narrative.py:178-179` | Phase 2 — narrative analysis | `if len( source_content ) > 30000: truncated = source_content[ :30000 ]` |
| `prompts/elaboration.py:171-172` | Phase 4 — slide content | same |

Phase 3 (outline) is not affected — it works from the narrative sections, not raw source. So the doc is read at 38.6% twice: once to decide the arc, once to write the slides. Everything after char 30,000 is invisible to the deck.

**A THIRD 30k clip exists — the podcast twin (whole-pipeline honesty).** `podcast_generator/prompts/script_generation.py:262`: `research_preview = research_content[:30000] if len(...) > 30000`. It is the **identical fidelity defect** on the podcast's research doc — same magic literal, same "back-N% silently dropped." It does NOT touch the presentation builders (separate module, podcast's own prompt path), so it does not widen Option A's blast radius. But "two sites" is a *presentation-scoped* count; whole-pipeline it is three. **This crew keeps landing a fix on one twin and leaving the sibling** (plan-mode bug, the podcast/presentation fences). Recommendation: give Option A's new ceiling a **shareable** name (a base config key both agents read), so podcast adopts it in a one-line follow-up instead of rediscovering this defect later. Naming it here is the cheap insurance. (The `30000` at `deep_research/rate_limiter.py:61` is unrelated — a tokens-per-minute rate limit, not a source clip.)

**Scale check:** 77,621 chars ≈ **~19.4K input tokens** (≈4 chars/token). claude-opus-5 context is **1M tokens**. The whole document fits with a ~50× margin — the 30k clip is a conservative default, not a model limit.

## Options (cost + risk each)

### Option A — Raise the clip (RECOMMENDED for Rick's deck tomorrow)
Replace the `30000` literal at both sites with a configurable ceiling (new INI key, e.g. `presentation generator max source chars`), defaulted high enough for real docs (e.g. 200,000).
- **Cost:** ~1 hour. Two-line change + one INI key + splainer entry. No pipeline restructure.
- **Risk:** LOW. 78k → ~19k input tokens, trivial against 1M context. The only real cost is that elaboration runs the source once per output batch (`batch_size=6`, ~10 batches for 60 slides) — so ~19k input tokens ×10. Fidelity: full document, nothing dropped.
- **The prompt-cache prefix is a COST optimization, NOT a precondition.** Option A *works* for Rick's deck without it — raise the two literals and the full document flows through. Caching only makes the repeated-per-batch input *cheaper*; it is a follow-up, not a gate. Do not let "cache first" turn a one-hour edit into a day. (And it's an unrun design assertion — see caveats.)
- **Ceiling of this option:** a genuinely huge doc (say 500k+ chars → 125k+ tokens) would bloat latency/cost and eventually approach context. For that, B or D. **Rick's 78k is nowhere near that** — A is the grounded fix for the deck that has to ship.

### Option B — Chunked / map-reduce narrative analysis (durable, for arbitrarily large docs)
Split source into N chunks → analyze each into partial narrative sections → merge/dedup into one arc. Mirrors the pattern elaboration already uses on output (`orchestrator.py:1097`, `batch_size=6`).
- **Cost:** DAYS. New chunk splitter, per-chunk analysis calls, a merge stage, cross-chunk arc reconciliation. Multiple API calls per deck.
- **Risk:** MEDIUM-HIGH. A narrative arc spanning a chunk boundary can fragment; merge logic is the hard part; more LLM spend. Justified only past the context window — overkill for 78k.

### Option C — Pre-summarization pass (REJECTED)
One LLM call condenses 78k → <30k, then the existing pipeline runs unchanged.
- **Cost:** LOW (one extra call, no pipeline change).
- **Risk:** HIGH — **lossy by construction.** It discards detail *before* the deck is built, and directly contradicts elaboration's own instruction (`elaboration.py:197`: *"Use this document as the authoritative source… Extract specific data, quotes, and examples."*). Wrong tool for a fidelity-sensitive deck.

### Option D — Section-aware digest (middle ground)
Phase 1 already pre-parses `raw_sections` (`orchestrator.py:485-488`). Feed narrative a section-structured digest sized to a budget (headings + proportional excerpts) instead of a blind first-30k slice — whole-doc *coverage* without sending every byte.
- **Cost:** MODERATE (~half a day). Change what's fed to narrative; reuse existing section parse.
- **Risk:** MEDIUM. Still lossy per-section, but no more "back 61% silently dropped." Better than A on cost for very large docs, worse on fidelity than A for a doc that simply fits.

## Blast radius of Option A (grep at HEAD `9b7abc98`)

Both clip literals live *inside* the two prompt builders, so "who calls them" IS the blast radius. `git grep` for each:

| Builder (holds the clip) | Production callers | Non-runtime callers |
|---|---|---|
| `get_narrative_analysis_prompt` (clip at `narrative.py:178`) | **`orchestrator.py:661,690` — presentation orchestrator ONLY** | its own `quick_smoke_test` (`narrative.py:327`); unit tests (`test_presentation_prompts.py`, `test_narrative_outline_elaboration.py`, `test_orchestrator_helpers.py`) |
| `get_elaboration_prompt` (clip at `elaboration.py:171`) | **`orchestrator.py:974` (all-at-once) + `orchestrator.py:1106` (chunked fallback) — presentation orchestrator ONLY** | own smoke test (`elaboration.py:344`); unit tests (`test_presentation_elaboration_prompts.py`, others) |

⇒ **Raising the ceiling changes the presentation path and nothing else.** Exemptions, each with firsthand proof:
- **Podcast generator** — does NOT import `presentation_generator.prompts.narrative` / `.elaboration`. Proof: `git grep` for those imports across `podcast_generator/` at HEAD returns **empty**. It has its own prompt path.
- **research-to-presentation** and **deep_research** — same: the import grep across their trees is **empty**. research-to-presentation hands off *after* research; it does not reuse these builders.
- **Tests + the two modules' own `quick_smoke_test`** are not runtime consumers — but they are a **live tripwire**: they assert the 30k behaviour (`test_presentation_elaboration_prompts.py:165` builds a `long_source`), so Option A **cannot land without touching them in the SAME edit** — anyone who raises the literal without moving the test gets a red that reads like a regression. Two requirements on that edit: (a) the assertions move in the same change; (b) the updated assertion pins the **new configured ceiling read from config**, NOT a fresh literal. Swapping one magic number for another is exactly how this defect was born — the fix must delete the magic number, not relocate it.

## Recommendation

- **For tomorrow's deck: Option A**, source-cached. 78k fits the context with room to spare; the clip is the only thing standing between Rick and his full document, and raising it is a ~1-hour, low-risk change. **This is grounded in his actual 78k file.**
- **Durable answer (María's call): B or D**, scoped to "docs that exceed the context window / a cost ceiling," not to Rick's case. A doesn't preclude either — it just unblocks now.

## Caveats I'm keeping honest

- The per-slide outline-token figure from P0-3 (~50–70 tok/entry) remains **an estimate, unrun** — it does not harden into a fact here. The 19.4K-token *input* figure above is a straight char/4 arithmetic on a known file size, not an LLM measurement, but it's an order-of-magnitude claim against a 1M window, so the margin holds even if it's off by 2×.
- The prompt-cache mitigation for Option A is a design assertion, not something I ran — flag it for verification before it's costed as a fact.
