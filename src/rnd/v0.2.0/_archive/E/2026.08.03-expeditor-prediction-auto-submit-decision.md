## The situation, in plain terms

When Rick asks by voice for "a podcast about that KISS explainer I wrote," the expeditor
finds five arguments missing and asks him five questions on one screen, with a five-minute
clock. The system has seen this request before and **already holds the right answers at 100%
confidence** — but today it only *shows* them in a "Predicted: … (100%)" box with a
thumbs-up/thumbs-down. It never fills the form and never submits it. (Measured; see row
bd0ce120 amendments.)

So the question is a product decision, not a bug fix: **when the system is confident it knows
the answers, should it answer for the user — and if so, how sure must it be?** Answering a
user's questions on their behalf is exactly the kind of autonomy the trust engine exists to
govern, so this is Rick's call, not ours to pick.

## The risk shape (read this first)

The two failure costs are **not symmetric**, and that asymmetry should drive the floor.

| If we auto-submit and it's **wrong** | If we keep the **five-field voice form** |
|---|---|
| A podcast generates on the wrong document / wrong audience. Visible on stage, costs real LLM spend, and — worst part — Rick looks like he lost control of his own tool in front of an audience. | Slow and clunky. Five answers by voice against a 300-second clock. Boring, a little awkward — but it works, and Rick stays in control the whole time. |

On a live stage, a **wrong auto-submit is a worse outcome than a slow form.** That argues for a
high bar and a human veto, not for eagerness.

## Options

### A — Keep it display-only (status quo)
- **Pros:** zero risk of acting on a wrong prediction; user always in control; no new code.
- **Cons:** the five-field voice form stays; the "we remember this" magic is shown but wasted.

### B — Auto-submit only at confidence exactly 1.0
- **Pros:** fires only on an exact prior match; conservative.
- **Cons:** 1.0 is brittle on the current embeddings (the non-unit-vector scorer behind bug
  78f21b1b) — it will rarely fire, so it mostly *looks* like the status quo. And a single
  mislearned 1.0 case still submits silently, with no veto.

### C — Auto-submit at confidence ≥ 0.9 **with a short "auto-submitting… tap/say wait to edit" grace window** *(recommended)*
- **Pros:** fires for repeat and near-repeat requests; the grace window is the governance
  surface — the human can veto before anything happens; mirrors the pattern already in the
  codebase (the similarity-confirm gate at `todo_fifo_queue.py:567` uses a 90% floor +
  confirm), so it's consistent, not novel.
- **Cons:** more work than A/B (a countdown UI + a cancel path); a wrong submit is still
  possible if the user doesn't react inside the window; the floor needs tuning over time.

### D — Auto-**prefill** every field + a single "submit all" (voice or one tap), no auto-submit
- **Pros:** collapses five actions to one; near-zero risk because the human still takes the
  final action; smallest, safest change — the demo-safe minimum.
- **Cons:** still one voice action on stage; doesn't fully deliver the "straight through" feel.

## Recommendation

**The feature:** Option **C**, floor **0.9**, with a mandatory 3–5 second grace window ("Making
your podcast now — say *wait* or tap to edit"). Below the floor, fall back to **D** (prefill +
one-tap submit-all). Reasoning: 0.9 matches the confirm gate the code already trusts, the grace
window keeps the human in the loop (which is the whole point of governed autonomy), and it
realizes the magic for exactly the repeat requests a demo shows off.

**For Thursday specifically:** if C can't land and be tested in three days, **ship D.** It removes
the five-field slog without the system ever acting unasked — the safe win that can't embarrass
Rick on stage. C is the real feature; D is the version that's certainly ready by Thursday.

**One number to name:** the grace-window length. Long enough to veto by voice (people are slow
to react to audio), short enough not to feel like a second form. 4–5 seconds is my starting
guess; Rick should set it by feel.

## What's NOT in scope here

- The user-facing "you cancelled" message is already fixed and merged (PR #20) — undeliverable,
  timed-out and declined now read differently; only a real "no" says cancelled.
- `target_user` routing is not a bug: the ask goes to whoever authenticated the push, so it
  reaches Rick's browser on the day as long as he's logged in as himself. (Row bd0ce120.)
