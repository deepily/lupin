# Two deploy scripts, one VM, and a set of names that mislead

**Date**: 2026-08-24 · **Author**: Mr. Radio 🦉 (session b98b9c38) · **Asked by**: Rick, live
**Companion**: `2026.08.24-gcp-vm-parity-plan.md` (the parity deploy this came out of)

---

## The short version

There is **one** VM in the project. It runs the compose file named **`cloud-gpu`**, which is the
variant with **no GPU container in it**. The other script, `deploy-cloud-test.sh`, drives a venue
that exists nowhere. Every name in this area describes something other than what it contains.

## 1. What actually exists

```
$ gcloud compute instances list
NAME             ZONE           STATUS
lupin-host-test  us-central1-a  RUNNING      <- the only VM in the project
```

On it:

| | |
|---|---|
| Running containers | `lupin-rest-cloud-gpu`, `lupin-cloudsql-proxy` |
| Compose file | `docker-compose.cloud-gpu.yml` |
| Env file | `cloud-gpu.env` |
| Driver | `lupin-vm.sh deploy` |

So the instance called **`-host-test`** runs the compose called **`cloud-gpu`**. The name of the
host and the name of its topology disagree, and neither is wrong exactly — they are describing
different axes (this is the *test* environment; its model server is the *cloud GPU* one) with
names that read as if they describe the same one.

## 2. The GPU that is not there

Rick's observation, confirmed. `docker-compose.cloud-gpu.yml` contains **no GPU** — no `nvidia`,
no `cuda`, no `device_requests`, no `deploy.resources`. Its own header says why (line 253):

> `# --- Lupin Model Server (GPU) — INTENTIONALLY OMITTED ---`
> On this cloud-GPU topology the model server runs on Cloud Run (L4, scale-to-zero).

And the file it was forked from, `docker-compose.cloud-test.yml`, **does** carry the local
`lupin-model-server` GPU container (line 169).

**So the file named `cloud-gpu` is the GPU-less one, and the file that is not named for a GPU is
the one that has it.** The name means "the GPU lives in the cloud, not here" — which is defensible
if you already know the split, and exactly backwards to anyone who does not. The two files differ
by 288 lines, and the presence or absence of that one service is the whole point of the fork.

## 3. `deploy-cloud-test.sh` — a script aimed at nothing

Hardcoded at the top:

```bash
REST_CONTAINER="lupin-rest-cloud-test"          # not running anywhere
COMPOSE_FILE="docker-compose.cloud-test.yml"    # no host uses it
ENV_FILE="cloud-test.env"                       # the VM has cloud-gpu.env
```

Every `docker restart` and `docker inspect` in it addresses a container that does not exist on the
only VM we have.

### Its AXIS-A abort is right about the wrong file

The header states the code path must abort because *"the `./src` mount was removed 2026-07-07 so it
cannot shadow the baked image"*. Measured:

| File | `./src:/var/lupin/src` |
|---|---|
| `docker-compose.cloud-test.yml` | **absent** — line 146 even says "if this service ever gains a `./src:/var/lupin/src` mount" |
| `docker-compose.cloud-gpu.yml` | **present**, line 101: `- ./src:/var/lupin/src  # mount model — code from the on-VM checkout` |

So the claim is true of the venue the script names and false of the venue we run. A reader who
picks this script by its name — and it reads like *the* deploy script — is told that fast code
deploys are impossible here. They are not; that is exactly how `lupin-vm.sh deploy` works.

### Is it dead code?

Not quite — it is **referenced** by `preflight-vm-lib.sh` and `provision-arbiter-on-vm.sh`, and its
design doc is the origin of the two-axis model that is still correct and still load-bearing. It is
the *driver* that is aimed at nothing, not the thinking behind it.

**Recommendation: do not delete it yet.** Its two-axis routing (code vs deps) is the only place
that logic is written down, and `lupin-vm.sh deploy` does not implement the deps axis at all — it
only does code. Deleting the script would delete the one artifact that knows a deps change needs an
image rebuild. Retire it *after* that routing has a home, not before.

## 4. Names worth reconciling (a ticket, not today's work)

| Name | Says | Is |
|---|---|---|
| `docker-compose.cloud-gpu.yml` | has a GPU | **has no GPU container** — the GPU is remote |
| `docker-compose.cloud-test.yml` | a test topology | the **GPU-bearing** one; runs on no host |
| `lupin-host-test` (instance) | test host | runs the `cloud-gpu` topology |
| `lupin-rest-cloud-gpu` (container) | GPU service | the plain REST app, no GPU |
| `deploy-cloud-test.sh` | *the* deploy script | drives a venue with no host |

A naming that describes topology-by-where-the-GPU-lives collides with a naming that describes
environment-by-purpose. Both are reasonable alone; together they produce `lupin-host-test` running
`cloud-gpu`, and a GPU file with no GPU.

**Filed as its own row** — deliberately not fixed here. Renaming compose files, container names and
env files touches the deploy path, preflight's container-name assertions, and several runbooks at
once; it is a coordinated change, not a drive-by.

## 5. A bootstrap trap found while deploying (separate defect)

`e5a6a917` (2026-08-18) correctly made `JWT_SECRET_KEY` fail-loud. Preflight then asserts it
**inside the running container**. But environment variables enter a container only at **CREATE**.
A VM whose container predates the variable therefore:

1. fails PRE because the running container lacks it, and
2. cannot acquire it without the recreate that PRE is blocking.

PRE is unpassable on such a VM until someone uses `LUPIN_SKIP_PREFLIGHT=1`. That happened on this
deploy. The assertion is not wrong — it is checking the right thing at a moment when it cannot yet
be true. It needs a bootstrap exemption: satisfied if the variable is present in the **host env
file** even when absent from the running container, since the imminent recreate is what closes the
gap. Filed separately.
