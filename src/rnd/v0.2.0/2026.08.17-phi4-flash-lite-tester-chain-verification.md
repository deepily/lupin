## 2. The pairing seam, proven rather than assumed

`DmTutorAgent` reads its arm **once at construction** — `agent_base.py:149` resolves
`llm spec key for dm tutor rewrite` (`= dm_tutor/phi_4` at `src/conf/lupin-app.ini:303`) — and only
resolves the client later, in `run_prompt` (`agent_base.py:305`). So a harness swaps arms by setting
`agent.model_name` **on the instance**:

```python
agent            = DmTutorAgent( dm_body=body )
agent.model_name = "dm_tutor/flash_lite"     # or dm_tutor/phi_4
out              = agent.rewrite()
```

No global config mutation — which matters, because a mutation that leaked between arms would run
both arms on one model and produce a complete, clean, wrong set of numbers.

`_apply_dm_tutor( body_text, config=None, rewrite_fn=None )` (`src/cosa/rest/routers/dm.py:1121`) is a
pure function: it returns `( delivered_text, meta )`, never raises, and writes nothing. The harness
can call it per body in-process, which is why the replay does not need the server at all.

**How the arm was proven** (this is the part "it answered" cannot do): `LlmClientFactory.get_client`
was wrapped in a spy, so the markers were read off **the client the tutor actually obtained**, not
off a second client built alongside it. Both arms rewrote the same body — the outputs alone would
not have distinguished them.

## 3. The two venue blockers

### V1 — the `:8000` container has no Google credentials, so the paid arm cannot run there

Measured inside `lupin-rest-test`:

```
project in container: hello-world-foo-423219      # resolves fine (src/scripts/cloud-run.env is bind-mounted)
constructed OK; vertexai=True api_key=None base=https://aiplatform.googleapis.com/
LIVE CALL FAILED: DefaultCredentialsError
```

Construction succeeds (credentials are lazy), so a harness that only *builds* the client will look
healthy there and fail at the first body. `docker-compose.yml` carries **zero** `gcloud`/`GOOGLE`/
`GCP` references, and neither container mounts `~/.config/gcloud`.

**This is a decision, not a fix to write.** Either (a) mount ADC into the test container and set the
env — a compose change, so `docker compose up -d --force-recreate`, never a plain restart — or
(b) run the paired replay host-side and accept that it sits outside the `:8000` submit protocol.
Recommend (a): it keeps the study inside the venue the handoff named.

### V2 — `:8000` was wedged, and that takes the whole integration tier with it

Every request from the host (`/health`, `/docs`, `/api/test-suite/list-pending`) timed out past 90s;
the docker healthcheck had a failing streak of 419 (~3.5h); inside the container the app still logged
`200 OK` and the consumer reported an empty queue. Nothing was running (only the server process; the
last suite finished 14:00 EDT) and Mr. Radio confirmed no seat had a job queued — so the bounce ate
nothing.

**Snapshot nuance worth recording**: `src/` and `.git` are bind-mounted into the test container, so
freshly-committed **test files** are picked up without a bounce; what goes stale is the **running
server's imported modules** (loaded 08:00:56 UTC). A replay that calls `_apply_dm_tutor` in a pytest
subprocess reads fresh code; anything routed through the server's HTTP surface does not.

## 5. What is NOT verified yet

- **The full-scale paired run.** Six rows proves the mechanism; it proves nothing about the models.
  Blocked on V1 (credentials in the mutating venue) and on the operational discordant floor, which
  is Rick's number and must be stated BEFORE arm 1, not after seeing row 16.
- **Hand-labelling a sample of each arm's delivered output** (§7 item 5). Without it the headline is
  detectability — "the guard blocked more" — not honesty. Nothing automated can stand in for this.
- **Latency.** phi_4 3.1s vs flash_lite 21.5s on one body, 2.8s on another, 22.1s vs 32.4s over six.
  Too few and too variable to be a number; a real latency claim needs the full run and a stated
  denominator ("rewrites fired" = attempts, per §2.4).
- **A portability trap worth fixing before anyone runs this somewhere clean**: the project id
  resolves from `src/scripts/cloud-run.env`, which is gitignored — so a **fresh worktree or a clean
  clone does not have it**, and the arm-surface tests fail there with no obvious cause. Clayton's
  worktree only works because the file was put there by hand today. Either set `LUPIN_GCP_PROJECT_ID`
  in the environment for such runs, or make the absence say so out loud.
- **The corpus scope question** (§4b) is untouched by any of this and remains Rick's: the pairing is
  internally valid regardless, but the corpus is fleet-to-fleet traffic, so the study can only speak
  about agent-to-agent chatter.
