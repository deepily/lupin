## 2. Two claims in the row that measurement did not support

The row is careful work and its *fix* was correct. Two of its *statements* were not, and both
change what the remedy should be. Both were measured, not reasoned. Recorded here so nobody
rebuilds on them.

### 2a. A `__pycache__` orphan cannot execute

The row's mechanism is "the VM was executing three-week-old bytecode" from
`cosa/memory/__pycache__/lancedb_solution_manager.cpython-313.pyc`. Python will not do that.

Measured on CPython 3.13 — compile a module, delete the `.py`, import it:

```
pkg/__pycache__/mod.cpython-313.pyc     ->  ModuleNotFoundError
pkg/mod.pyc  (sibling, no cache dir)    ->  imports and runs
```

PEP 3147 consults a `__pycache__` entry only *alongside* its source. Sourceless import requires the
pre-PEP-3147 sibling layout. Both orphans the row names are inside `__pycache__`.

This is now a standing test, not a note:
`test_preflight_vm_lib.py::test_the_class_split_matches_what_cpython_ACTUALLY_does`. If CPython
ever changes, the tiering in §3 fails loudly instead of quietly becoming wrong.

### 2b. The container never reads the bind-mounted cache anyway

All three compose files already set `PYTHONPYCACHEPREFIX` (added for bug b39c350d), which sends the
container's bytecode to a container-local directory **and makes it ignore in-tree entries**. So
clearing `src/**/__pycache__` on the VM could not have changed what the container imports.

Confirmed live by Mr. Radio on the VM: the running container reads `/tmp/pycache`, there are zero
sibling `.pyc` under `src`, and the container was created 2026-08-17 — after the env var landed.

**Therefore the restart is what fixed the incident, not the cache clear.** Agreed with Mr. Radio;
the row has been amended.

## 3. The detector, and why it is tiered rather than uniformly blocking

`preflight-vm.sh` check B5. Runs in **every** phase: `pre` finds what the last deploy left behind,
`post` finds what this one just created.

| Shape | Verdict | Why |
|---|---|---|
| `pkg/mod.pyc` — sibling, no cache dir | **BLOCK** | Python imports and runs it. Code in no commit and no grep. |
| `pkg/__pycache__/mod.cpython-313.pyc` | **WARN** | Inert (§2a), but still invisible to every grep, diff and review. |
| root unreadable / not a directory | **UNKNOWN-BLOCK** | A scan that could not look must not report what a clean scan reports. |

Blocking a deploy on bytecode that provably cannot execute would be an alarm firing where nothing
can hurt anyone. A reader who triages one of those learns to skip the tier, and then the one real
finding is invisible — the same failure this instrument already fixed once for `OPTIONAL` env vars.

### The false-positive generator it caught on first contact

The first cut stripped one trailing component to remove the cache tag. pytest's assertion rewriter
writes a **dotted** tag (`cpython-313-pytest-8.4.2`), so `mod.cpython-313-pytest-8.4.2.pyc` mapped
to `mod.cpython-313-pytest-8.4.py`, which never existed.

**It reported 1375 orphans on this repo. After the fix: 23, all real.** A module name cannot
contain a dot, so the first dot is the correct and only safe cut. The pytest form is now a
parametrised test case.

The 23 include both incident modules, still present on this host as inert `__pycache__` entries.

## 4. The prevention, and who actually writes the cache it purges

`do_push_bundle` gains a `purge_pyc` command, defined **once** and referenced by both `checkout`
and `reset`, so the two modes cannot drift. It runs after the tree moves and before the `chown`
(purging first would let the checkout re-orphan; purging after the chown leaves new dirs
root-owned), and echoes `PYCACHE_PURGED` so a silent no-op is distinguishable from never running.

Fetch-only mode does not purge — the working tree does not move, so no orphan is created.

**Who writes the in-tree cache, given §2b says the container does not?** Host-side Python, measured
directly: delete `src/cosa/utils/__pycache__`, run one plain host import, and two entries come
back. On the VM the host-side writers are the `:8001` arbiter (which runs on a **host venv, not a
container**), host `pytest` runs, the fleet hooks under `lupin_cli/`, and `preflight-vm.sh` itself
at line 360. The independent proof that this happens on the VM specifically is Mr. Radio's own
count: **35 `__pycache__` directories** under `/mnt/lupin-data/lupin/src`, none of which the
container wrote.

The purge's value does not rest only on who writes, though. **`git checkout` is what *orphans*
cache that already exists**, so the purge earns its place as long as any in-tree cache is present
at deploy time — which those 35 directories settle.

**Prevention and detection are both required.** Prevention stops orphans being made; detection
finds the ones made by a hand-run `git checkout` on the VM, a restored snapshot, or any deploy
predating this change. The precedent for not trusting an unverified fix is in this repo's own
history: *"lupin-vm.sh deploy runs `up -d` WITHOUT `--no-deps`"* sat in a runbook with the words
"Filing recommended", was never filed, and took `:7999` down the next day.

## 5. `PYTHONDONTWRITEBYTECODE` — measured, and the recommendation is **no**

Import graph: `cosa.utils.util` + `configuration_manager` + `queue_protocol` +
`running_fifo_queue`. Seven runs per arm, subprocess wall-clock, this host.

| Arm | Mean | Median |
|---|---|---|
| cache ON, warm (steady state) | 2737 ms | 2288 ms |
| cache ON, cold (first start in a fresh container) | 5455 ms | 5426 ms |
| `PYTHONDONTWRITEBYTECODE=1` (never caches) | 5216 ms | 5209 ms |

**Steady-state penalty: +2.5 s per process start, +91%.** Every start pays the cold price forever.

And it buys nothing here. The row's premise was "the src is a bind mount, so the cache buys
little" — but `PYTHONPYCACHEPREFIX` already moved the container's cache out of the bind mount
(§2b), so the container cannot create these orphans. The in-tree `__pycache__` on the VM is written
by **host** processes (§4), which a compose-level env var does not reach at all.

So the change would cost 2.5 s on every short-lived process start, to prevent something already
prevented, by a mechanism that does not touch the processes actually doing it.

## 6. The renamed-key guard — scoping handed to row 3e4a4a4a

Split out on Mr. Radio's call, P3, unassigned. Recommended approach: **`get_required()`**.

`ConfigurationManager.get( key )` with no `default` prints a banner, calls `splain_me`, and returns
`None`. That `None` then travels — in the incident it reached a string concat and raised
`can only concatenate str (not NoneType) to str` far from the cause.

**Blast radius, measured**: 497 config-manager `.get()` call sites; **81 pass no default** and would
newly raise. Those are read across five config blocks (Baseline / Development / Production /
Testing / Testing-GCS); a key present in one block and absent in another currently degrades to
`None` and would become a hard startup failure. That is a behaviour change to app startup, not a
local fix — which is why it is its own row.

**The migration-map angle is a dead end for this incident.** Nothing consults
`src/conf/config-key-migration-map.json` at read time — grep finds only the doc-viewer blocklist
tests referencing the file. And the map keys `old_snake_name → new spaced name`, while the failing
read asked for `"path to database wo root"` — the **new** name, simply deleted from the INI along
with the LanceDB sweep. A migration-map guard would not have fired on the incident it is proposed
for.

Options considered: (a) make `get()` raise when no default is given, and fix all 81 sites;
(b) add an explicit `get_required()` and migrate the 81 deliberately; (c) leave it. **(b)** keeps
every existing call site working while giving new code a way to say "this key is not optional".
