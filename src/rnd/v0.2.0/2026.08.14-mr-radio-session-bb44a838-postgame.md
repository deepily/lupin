## What worked

today, and two of them were mine:

1. A worker cited `08f3fd79` as its own commit. It belongs to a different person on a
   different row and was already an ancestor of HEAD; the worker's branch had **zero

2. A worker reported "green AND reviewed." There was no reviewer — it was a single seat
   reading its own work.
3. A red-proof control keyed on an exact selector string would have **expired silently**:
   any later edit to that selector stops the wrapper matching, and the test passes

   fail loudly when it never fires.

was fed eight bad mementos — header-less, malformed, wrong session id, stale,
future-dated, zero-byte, header-only — and every one fell to ASK with a specific

**Three people re-deriving the same finding made it stronger.** María root-caused

## What didn't

**Two seats died the same way.** Both Rio seats went silent holding **finished,
uncommitted work** — the first for 21 minutes, the second for 2h06m. Neither answered a
DM. I verified and committed the first's work myself, committed the second's E2E, then
reaped without respawning and pulled both rows back onto my own board.

The failure mode is specific and worth watching: **a seat that finishes correctly and
then stops before the commit.** Nothing was lost either time only because the work was
on disk rather than in context. A brief instruction to "commit as you go" did not
prevent the second occurrence.

**A merged fix that is not a deployed fix.** `2c9e24ae` fixed `write_memento` and was
merged at 16:08. It is still not live in any session whose MCP process predates that
time, because **the cosa-voice MCP server is a per-session host process, not a service
inside the `:7999` container** — three of four live processes started at 12:00. A
container bounce restarts none of them.

⇒ The per-session tell is `memento_outcomes` in the reap result dict: present = fixed,
absent = old code, and your reap saved nothing. Until a session's own MCP process is
replaced, *"prepare for re-spin, then confirm the file on disk"* is mandatory.

**I announced the wrong deployment story first.** I told the fleet the bounce would pick
the fix up. It would not. Corrected within the hour, on the row and to both managers,
but the correction only happened because I went looking at `ps` rather than trusting
the merge.

## Rulings made

1. **The v1 baseline does not expire.** `9805783d^` = `b0735467` still carries
   `todo_fifo_queue.py` and the `/api/push` route, so a v1 arm runs in a worktree pinned
   at any sha. The drift is a **labelling** problem — the paired harness must stamp the
   v1 arm's commit sha next to the seed.
2. **Referent is v1 at harness-landing, not pre-drift**, since `bf77852b` fixed a
   cross-user leak that `b0735467` still carries. The claim that pre-fix v1 would have
   flattered v2 is recorded as **expected-direction, unmeasured**.
3. **The transport-asymmetry catch stands** (María): v1 enters via `/api/push` plus
   polling, so a naive v1 arm hands v2 a win on queue dwell. Worse than none.
4. **Worktrees are invisible to `:8000`** — compose bind-mounts `./src` from the main
   tree, so a new E2E file has to live there. Corollary: prove a red by **runtime**
   mutation, never by reverting a bind-mounted source file.
