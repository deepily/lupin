## 2. The rule, and why it is "strict"

A capitalised token is exempt from the invented-name check **only when the vendored word list
holds it as a LOWERCASE entry.**

The obvious version — "exempt any dictionary word" — is the one that had to be rejected.
`/usr/share/dict/american-english` carries 20,494 **capitalised** entries, so `rachel`,
`clayton`, `krishna` and `tiffany` are all "dictionary words". Exempting any dictionary entry
would stop the guard flagging invented **person names**, which is the exact incident it was
built for ("there was no reviewer"). Proper nouns live in the list capitalised; only lowercase
entries exempt.

`test_plain_v3_would_have_blinded_the_guard_to_person_names` pins this: it asserts all four
names are absent from the lowercase set **and** still blocked. If anyone relaxes the rule to a
plain dictionary lookup, that test names exactly what broke.

## 3. The cost, accepted knowingly

The guard loses its **one demonstrated true positive**: a rewrite that turned "Force-recreated"
into "Deployed". `deployed` is a lowercase entry, so that rewrite now ships.

`test_force_recreated_rewritten_as_deployed_now_ships` asserts the loss on purpose. Rick was
shown this exact trade and took it; a suite that quietly special-cased "Deployed" back would
overturn a ruling somewhere he would never look. The escape hatch is real and also tested —
turning the flag off brings the catch back.

## 4. Three things found while building

### 4a. The curly apostrophe flipped the verdict on the same word

The rewriter is a language model and emits U+2019 constantly. The vendored list holds ASCII
apostrophes, so **"Update's" was exempt and "Update’s" was blocked** — same word, same meaning,
opposite outcomes, decided by a character invisible in a diff. Normalised before lookup, with a
negative control proving it does not release `Krishna’s`.

### 4b. Adding a config key broke 22 existing tests, and that was the right failure

The send path reads config by direct indexing (`config[ "enabled" ]`), per the house rule that a
missing key fails loudly rather than falling back. `test_dm_tutor_send_path.py` built its config
dicts from a hand-written literal, so the new key raised `KeyError` **inside** `_apply_dm_tutor`
— which catches it and delivers the original. 22 tests went red with assertions about delivered
text, naming nothing about config.

Fixed at the cause: `_cfg()` now seeds from `_DM_TUTOR_DEFAULTS`, so the next key costs nothing.
**Deliberately not fixed** by adding a `.get()` fallback in the send path — that would have made
a partial config dict silently disable the tutor, which is the failure mode the 22 reds were
warning about.

### 4c. The load is at import, and a test enforces it

Mr. Radio's constraint. 789 KB read per DM would put a file read on the send path.
`test_the_word_list_is_read_once_at_import_not_per_call` patches `open` to raise and then runs
18 comparisons; it fails the moment the read moves back inside the function.

An unreadable list degrades to an **empty exemption set** — the pre-V3 guard, i.e. *more*
blocking, never less — and never raises at import. Failing toward the permissive side would
silently disarm the guard exactly when something is already wrong with the deployment.
