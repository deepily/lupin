# Catastrophic Node RSS Blowup in Claude Code 2.1.240: Root-Cause Analysis and Prevention for a Fleet on Shared Linux

## TL;DR
- **No public bug report matches your exact signature.** There is no known, acknowledged Claude Code defect — in 2.1.240 or the 2.1.235–2.1.245 window — that produces a ~229 GB `node` RSS OOM. 2.1.240 shipped 2026-08-22 with only a generic "Bug fixes and reliability improvements" note, and the issues tracker has nothing tied to that version or a hundreds-of-GB event in August 2026. Treat the cause as *inferred*, not documented.
- **The evidence points to a single (or few) enormous, abandoned external-memory allocation(s) — Node `Buffer`/`ArrayBuffer`/string — not a V8-heap or gradual leak.** The `inactive_anon`-dominant zone report (~217 GB never re-touched) is the fingerprint of a one-shot blowup: unbounded in-memory accumulation of tool output (Bash stdout or an MCP response) truncated *after* buffering, or a poisoned transcript deserialized on resume. The 15-minute pair-then-silence pattern is most economically explained by an auto-resume replaying the same poisoned session transcript.
- **`MemoryMax=24G` + `MemorySwapMax=0` per-session scope is the correct primary control; harden it with `systemd-oomd` PSI kill, `oom_score_adj` tuning, and a `PreToolUse` hook that caps Bash output at the source.** Do not rely on any Node flag — there is *no* flag in Node 22 that bounds external/`Buffer` memory (`--max-old-space-size` explicitly does not). The cgroup swap bound is the only hard ceiling that works.

## Key Findings

1. **The `inactive_anon` signature is diagnostic of a one-shot allocation, not a working-set leak.** `inactive_anon` is anonymous memory that was allocated and then not referenced again recently. ~217 GB of ~229 GB sitting inactive means the process allocated a vast region in a burst and then stopped touching it (event loop blocked or waiting), rather than actively churning a growing structure. A gradual leak or a many-small-object retry storm would show high `active_anon`. This is consistent with `Buffer.concat`/`JSON.parse`/string amplification on a single gigantic payload.

2. **`--max-old-space-size` cannot cause and cannot prevent this.** V8's old-space default is 2 GB, raised to 4 GB only on 64-bit systems with ≥~15–16 GB physical memory (per V8 `heap.cc` `MaxOldGenerationSize`: "Increase the heap size from 2GB to 4GB for 64-bit systems with physical memory at least 16GB") — so your 251 GiB host runs the 4 GB default. V8 aborts with "JavaScript heap out of memory" at that limit — a graceful `SIGABRT`, not a kernel OOM. Your process was `SIGKILL`ed by the kernel with 229 GB resident, which is only reachable through *external* memory (`Buffer`/`ArrayBuffer`/native). Per the Node docs, `arrayBuffers` "refers to memory allocated for ArrayBuffers and SharedArrayBuffers, including all Node.js Buffers … also included in the external value," and per nodejs/node#24225 the V8 GC "does not know about and thus does not feel like it needs to trigger a GC" on this external memory — so a process can be OOM-killed while nominally under `--max-old-space-size`. Node has **no** `--max-external-memory` flag; a bound on total (heap + external) memory has been requested since 2018 in nodejs/node#24225 ("Ability to constrain the total heap used by v8 and Node.js (--max-heap-size)", opened by @giltayar), which remains open and unimplemented with no assignee. This is the crux: nothing inside the Node process bounds off-heap allocation.

3. **Claude Code's own output caps truncate *after* buffering, which is the likely amplifier.** The Bash tool default is `BASH_MAX_OUTPUT_LENGTH` = 30,000 characters with middle-truncation (head+tail retained); MCP responses default to `MAX_MCP_OUTPUT_TOKENS` = 25,000 tokens, enforced via an `MCPContentTooLargeError`. But issue #15001 documents a *silent crash from unbounded command output* — the process "captured all output into memory buffers" and died — showing the truncation is applied to an already-materialized buffer. A command emitting gigabytes to stdout (`find /`, `grep -r` over a huge tree, `cat` of a multi-GB file, `yes`) can therefore drive the node process's external memory arbitrarily high before any cap fires.

4. **The `CLAUDE_CODE_TOOL_MEMORY_LIMIT` cgroup (added in v2.1.233) does NOT protect against this.** It caps the memory of the *child* Bash/PowerShell process via a cgroup — it does not bound the node parent's buffering of that child's stdout. A command that stays under its own memory cap while emitting gigabytes to a pipe will still balloon the node process. This is a critical and non-obvious gap.

5. **The 15-minute pair, then nothing, is the fingerprint of resume-replay of a poisoned transcript.** Claude Code writes every turn — including full tool results — to `~/.claude/projects/<encoded>/<session-id>.jsonl`, and `--resume`/`--continue` deserializes the entire file back into memory. Issues #22365 (a 3.8 GB JSONL that consumed all available RAM, with a 207 MB debug file and the claude process at 12.8 GB RSS on a 30 GB box), #21022 (a 102 MB session file freezing the host at 90% RAM), and #31961 (a resume that blocks the event loop and accumulates 7–11 GB RSS synchronously, reaching the impossible state `heapUsed > heapTotal`) confirm transcript loading is unbounded and synchronous. A first blowup that writes a gigantic tool result to the transcript, followed by an orchestrator/tmux auto-resume that re-reads and re-parses it ~15 minutes later, then abandonment/clearing of the session, explains both the pair and the cessation better than any other single hypothesis.

6. **Recent releases were actively patching this class of bug — but the specific fixes bracket your incident.** 2.1.238 (Aug 20) "Fixed unbounded memory growth in long interactive sessions: subagent tool results are now released once they leave the recent display window." 2.1.239 (Aug 21) "Fixed WebFetch retaining expired page content in memory for the whole session instead of the intended 15 minutes." Earlier, 2.1.217 fixed "a memory leak where truncated MCP tool outputs kept the full untruncated result in memory," and 2.1.208 fixed MCP stdio stderr leaks up to 64 MB. This shows the failure mode is real and recurring in the codebase, even though none of these specific fixes matches your 229 GB magnitude.

## Details

### Ranked root-cause hypotheses

**H1 — Unbounded in-memory buffering of a single massive tool output (Bash stdout or MCP response), truncated only after materialization. Confidence: MODERATE-HIGH as the mechanism class.**
- *For:* Directly matches the `inactive_anon`-dominant, one-shot signature. Publicly documented in #15001 ("Claude Code captured all output into memory buffers… process terminates silently"). Consistent with your named suspects (repo-wide grep, `find /`, `cat` of a large log). `BASH_MAX_OUTPUT_LENGTH`/`MAX_MCP_OUTPUT_TOKENS` truncation is post-hoc. `CLAUDE_CODE_TOOL_MEMORY_LIMIT` does not cover the parent's buffer.
- *Against:* 229 GB is enormous even for this; requires either a near-infinite stream or `Buffer.concat` doubling amplification. No stdout cap is *known* to be fully absent in 2.1.240 — this is inference, not documented for this version.

**H2 — Resume-replay of a poisoned transcript containing a giant tool result. Confidence: MODERATE-HIGH for the temporal pattern specifically.**
- *For:* Uniquely explains the 15-min pair and the clean cessation. Transcript loading is unbounded and synchronous (#22365, #21022, #31961). `JSON.parse` of a multi-GB JSONL line plus UTF-16 string materialization amplifies. Fits a fleet with tmux auto-resume/orchestration.
- *Against:* Even the worst documented transcript (3.8 GB → ~13 GB RSS) is ~18× short of 229 GB; requires a transcript that itself embedded a giant H1-style tool result. So H2 is likely *downstream* of an H1 event, not independent.

**H3 — Oversized MCP response over stdio. Confidence: LOW-MODERATE.**
- *For:* 2.1.217/2.1.208 confirm MCP responses have caused retained-full-payload leaks; MCP stdio has no intrinsic size framing; a buggy/malicious server can stream GBs before the 25k-token check. You run MCP servers.
- *Against:* `MCPContentTooLargeError` normally rejects oversize responses; would need the leak-before-check path. No evidence gathered for/against in your incident.

**H4 — undici/fetch retry-storm or non-terminating SSE accumulation during the 529 overload window. Confidence: LOW-MODERATE, but temporally suggestive.**
- *For:* You were actively fighting 529s with backoff/circuit breakers. undici has documented memory-leak-on-abort behavior: nodejs/undici#2198 ("Memory leak when aborting fetch requests," opened Jul 2023) reports that when frequently aborting fetch requests, "in less than a minute, I see memory usage of the Node.js process climb to several gigabytes" (closed as not planned), and #4058 documents request-body retention in memory. A retry loop that re-buffers response bodies, or an SSE stream that never terminates, accumulates external memory; onset/cessation would track the overload window — matching your "unexplained onset and cessation."
- *Against:* Abort-leak growth is many small allocations (would trend `active_anon`); doesn't cleanly produce the `inactive_anon` one-shot signature unless a single huge malformed/gzip-bombed body was buffered. Speculative for your case.

**H5 — A known 2.1.240 defect. Confidence: VERY LOW / effectively REJECTED.**
- *Against:* Exhaustive search of the changelog and issues tracker found **no** memory/OOM/RSS report tied to 2.1.240 or the 2.1.235–2.1.245 window, and no hundreds-of-GB node RSS event dated around August 2026. The closest precedent is #22042 (a genuine, acknowledged memory regression — "Critical memory regression in 2.1.27 - OOM crash on simple input," RSS ~7.5 GB in ~20 s, fixed by rollback to 2.1.25 — but unrelated to your version line). **An honest "no public report matches" is the correct conclusion here.**

**H6 — V8 heap leak. REJECTED** by your own reasoning (would abort at ~4 GB with a heap-OOM message, not a 229 GB kernel kill), confirmed by the V8 default above.

### Why the fleet context matters
Your ~two dozen sessions share one `tmux-server.service` slice under `user@1001.service`. Under `CONSTRAINT_NONE`/`global_oom`, the kernel picked the largest-RSS task by `oom_score` — which is why the two dead PIDs were the runaways, but also why an *innocent* session could have been the victim if the runaway had a low score. Co-locating all sessions in one slice means one runaway is a whole-host problem. This is the single most important structural weakness to fix.

### The environment/config surface that actually bounds memory or output

Every memory- or output-size-relevant Claude Code variable and its default:

| Variable | Default | Bounds what | Caveat |
|---|---|---|---|
| `BASH_MAX_OUTPUT_LENGTH` | 30,000 chars | Bash tool output returned to model (middle-truncated) | Applied *after* buffering; does not bound peak node RSS |
| `MAX_MCP_OUTPUT_TOKENS` | 25,000 tokens | MCP tool response size | Enforced via `MCPContentTooLargeError`; historical leak retained full payload pre-truncation |
| `CLAUDE_CODE_MAX_OUTPUT_TOKENS` | 32,000 (max 64,000) | Model *response* tokens | Not a memory control |
| `MCP_TIMEOUT` / `MCP_TOOL_TIMEOUT` | 5,000 / 30,000 ms | MCP startup / call time | Bounds duration, not size |
| `BASH_DEFAULT_TIMEOUT_MS` / `BASH_MAX_TIMEOUT_MS` | 30,000 / 600,000 ms | Bash duration | Indirectly limits an infinite stream |
| `CLAUDE_CODE_TOOL_MEMORY_LIMIT` | off | cgroup cap on the **child** Bash/PowerShell process (v2.1.233+, Linux) | **Does NOT bound the node parent's stdout buffer** |
| `CLAUDE_CODE_WEBFETCH_CACHE_TTL_MS` | 900,000 ms | WebFetch URL cache TTL | Related to the 2.1.239 WebFetch retention fix |
| `cleanupPeriodDays` (settings.json) | — | Transcript retention | Limits transcript accumulation over time |

**Node flags: there is no external-memory bound.** `--max-old-space-size` and `--max-semi-space-size` bound only V8 heap generations, not `Buffer`/`ArrayBuffer`. `--max-http-header-size` bounds only header size. There is no `--max-external-memory`. The only real ceiling on off-heap growth is an OS/cgroup limit.

### Prevention — concrete and staged

**(1) Keep your per-session transient scope; it is the only hard control that works.** Your empirical finding is correct: `MemoryMax` alone lets the cgroup swap; `MemorySwapMax=0` makes the cap real.

```bash
# Launch each worker in its own transient scope, isolated in a per-session slice
systemd-run --user --scope \
  -p MemoryMax=24G \
  -p MemoryHigh=18G \
  -p MemorySwapMax=0 \
  -p MemoryAccounting=yes \
  --slice="ccworker-$(uuidgen | cut -c1-8).slice" \
  -- claude   # your args
```
Add `MemoryHigh=18G` (throttle + reclaim zone below the hard cap) so a slow climber shows as *slow* and trips your 16 GB watcher before the 24 GB `MemoryMax` SIGKILL. `MemoryHigh` throttles and reclaims; `MemoryMax` is the last-line kill. (Confirmed semantics: per `systemd.resource-control`, "It is recommended to use MemoryHigh= as the main control mechanism and use MemoryMax= as the last line of defense.")

**(2) Make the kernel target the runaway, never an innocent session.** Bias `oom_score_adj` so a worker is always preferred over the tmux server or the orchestrator:
```bash
# In each worker's wrapper, before exec claude:
echo 500 > /proc/self/oom_score_adj   # 0..1000; higher = killed first
```

**(3) Add `systemd-oomd` PSI-based pressure kill as a second, earlier line of defense.** Kernel OOM is reactive and fires too late; oomd acts on sustained pressure. Because oomd only kills *descendant* leaf cgroups (or those with `memory.oom.group=1`), per-session slices are a prerequisite — which you now have.
```ini
# /etc/systemd/system/user@1001.service.d/oomd.conf
[Service]
ManagedOOMMemoryPressure=kill
ManagedOOMMemoryPressureLimit=60%
```
Requires cgroup v2, memory accounting enabled, and swap present (you have 4 GiB — enough for oomd to get reaction time even with `MemorySwapMax=0` on the leaf scopes, since oomd reads system-level PSI). Validate with `oomctl` and `journalctl -u systemd-oomd -f`.

**(4) Bound tool output at the source with a `PreToolUse` hook.** Hooks receive the Bash command on stdin as JSON and can deny or rewrite it before execution (a `PreToolUse` hook can return `permissionDecision: "deny"`, `"ask"`, or silently rewrite arguments via `updatedInput`). This is the cleanest place to stop `find /`/`yes`/`cat huge` from ever reaching the buffer. Minimal working guard:
```python
#!/usr/bin/env python3
# ~/.claude/hooks/bound-bash.py  — PreToolUse matcher: "Bash"
import json, sys, re
d = json.load(sys.stdin)
cmd = d.get("tool_input", {}).get("command", "")
DANGER = [r"\byes\b", r"\bcat\s+/dev/(u?random|zero)", r"\bfind\s+/\s", r"\bgrep\s+-[a-zA-Z]*r"]
if any(re.search(p, cmd) for p in DANGER):
    print(json.dumps({"hookSpecificOutput":{"hookEventName":"PreToolUse",
        "permissionDecision":"deny",
        "permissionDecisionReason":"Unbounded-output command blocked; pipe through head -c 10M."}}))
    sys.exit(0)
sys.exit(0)
```
Register in `~/.claude/settings.json` under `hooks.PreToolUse` with matcher `"Bash"`. Note the documented limitation (#29709): a `PreToolUse:Edit` hook can be bypassed via the Bash tool, but a `Bash`-matcher hook *is* the right layer for shell commands. For defense in depth, also cap every command's output (`BASH_MAX_OUTPUT_LENGTH=20000`) and enable `CLAUDE_CODE_TOOL_MEMORY_LIMIT=4G` (bounds the child even though it does not bound the parent buffer).

**(5) Is 24 GB defensible?** Yes, with margin. Every documented "legitimate" heavy case sits far below it: healthy Claude Code baselines at 1.4–3.0 GB RSS; the worst *legitimate* long-session growth reports cluster in the 6–13 GB range (#29576 ~6.4 GB, #34161 10–13 GB, #31961 7–11 GB); the transcript-loading pathologies that reached tens of GB were themselves bugs, not legitimate work. A 24 GB ceiling is ~8× your observed healthy peak and above every non-bug heavy case, so it will not cap legitimate work while still catching a runaway two orders of magnitude smaller than your 229 GB event. If anything you could lower `MemoryMax` to 16 GB and lose little.

### Forensics — bounded steps to attribute a FUTURE occurrence

Trigger capture *before* the kill via a `systemd-oomd` dry-run alert (`systemd-oomd --dry-run` logs the intended kill) or your PSI/RSS watcher, and snapshot cheaply:
```bash
# On threshold crossing (your 16 GB watcher), for the offending pid:
p=<pid>
cat /proc/$p/smaps_rollup > /tmp/cc-$p-smaps.txt   # RSS/anon breakdown, cheap
cat /proc/$p/status      >> /tmp/cc-$p-smaps.txt    # VmRSS, VmSwap
ls -l /proc/$p/fd | head -50                        # open fds: is it a pipe? a socket? a .jsonl?
cat /proc/$p/cgroup                                  # confirm slice
readlink /proc/$p/fd/1 /proc/$p/fd/2                 # what stdout/stderr are wired to
```
`/proc/<pid>/fd` is the highest-value single artifact: if an fd is a pipe to a Bash child, H1; if it is a large `*.jsonl`, H2; if it is a socket to the API/an MCP server, H3/H4.

### Post-mortem — bounded steps still possible now

All size- and time-bounded (avoiding the very sweep class that may have caused this):
```bash
# 1. Transcripts written/modified around 12:23 and 12:38 EDT, by size — do NOT cat them
find ~/.claude/projects -name '*.jsonl' -newermt '2026-08-22 12:20' \
  ! -newermt '2026-08-22 12:45' -printf '%s\t%TY-%Tm-%Td %TH:%TM\t%p\n' | sort -rn | head

# 2. Largest transcripts overall (a poisoned one will be an outlier), bytes only
find ~/.claude/projects -name '*.jsonl' -printf '%s\t%p\n' | sort -rn | head

# 3. Peek the LAST record of a suspect file without loading it whole
tail -c 200000 <suspect>.jsonl | tail -1 | head -c 2000

# 4. tmux-server + oom around the window
journalctl --user -u tmux-server.service --since '2026-08-22 12:15' --until '2026-08-22 12:45'
journalctl -k --since '2026-08-22 12:20' --until '2026-08-22 12:45' | grep -i oom

# 5. Claude Code debug logs (debug files have themselves reached 207 MB — check size first)
ls -lS ~/.claude/debug/ 2>/dev/null | head

# 6. Telemetry that may survive a kill
ls -l ~/.claude/telemetry/ 2>/dev/null    # 1p_failed_events.*.json; may be absent if OOM killed before cleanup
```
Note (from #31961): a session OOM-killed before cleanup may leave *no* telemetry file, so absence is not exculpatory. Transcript file size + mtime is your most reliable surviving evidence.

## Recommendations

1. **Immediately:** deploy per-session transient scopes with `MemoryMax=24G MemorySwapMax=0 MemoryHigh=18G` in a *per-session slice* (not the shared tmux slice), plus `oom_score_adj=500` on workers. This alone converts a whole-host OOM into a single-session kill. **Threshold to change:** if legitimate work ever trips 18 GB `MemoryHigh` (visible as throttling/reclaim in `memory.events`), raise the pair; if nothing legitimate exceeds ~13 GB after a month, lower `MemoryMax` to 16 GB.
2. **This week:** enable `systemd-oomd` `ManagedOOMMemoryPressure=kill` on `user@1001.service`, and add the `PreToolUse` Bash guard + `BASH_MAX_OUTPUT_LENGTH=20000` + `CLAUDE_CODE_TOOL_MEMORY_LIMIT=4G` across the fleet.
3. **This week:** run the bounded post-mortem (transcript size/mtime scan first). If a transcript outlier exists near 12:23/12:38, H2 is confirmed — archive+delete it (`mv` out of the project scan path) and change your auto-resume logic to *refuse* to resume sessions whose JSONL exceeds a size threshold (e.g., 50 MB), the same threshold #22365 recommends Claude Code adopt.
4. **Ongoing:** wire your 16 GB RSS watcher to the `smaps_rollup`+`/proc/<pid>/fd` capture above so the *next* event is attributable in seconds. This is the single change that will end the "could not attribute post-mortem" problem.
5. **Version hygiene:** pin the fleet to a known-good version and set `DISABLE_AUTOUPDATER=1`. 2.1.238 fixed a real unbounded-growth path, so *staying current* on the patch line is net-positive — but pin+test rather than auto-update a fleet. Watch the tracker for any 2.1.24x memory regression report (none exists as of now).
6. **Decouple the retry storm:** since H4 cannot be excluded and you were mid-529-incident, ensure your backoff/circuit-breaker drops (does not buffer) response bodies on retry, and cap SSE stream lifetime; a non-terminating SSE during an overload window is a plausible external-memory sink.

## Caveats
- **The root cause is inferred, not proven.** No public Claude Code bug matches a 229 GB node RSS OOM in 2.1.240 or its neighbors. Everything above is mechanism-level reasoning from the `inactive_anon` signature plus adjacent documented bugs.
- **The magnitude is unexplained by any single documented case.** The largest documented legitimate/bug RSS events top out around tens of GB; 229 GB requires either a near-infinite stream (H1) or a poisoned transcript that itself embedded an H1-scale payload (H1→H2 chain). The two hypotheses most likely operate together.
- **H2's temporal fit is strong but its magnitude fit is weak alone** — treat the 15-min pair as evidence of *replay*, and the 229 GB as evidence of *what was replayed*.
- **`CLAUDE_CODE_TOOL_MEMORY_LIMIT` will feel like a fix but is not one for this failure mode** — verify in testing that it does not bound the node parent's buffering before relying on it.
- Third-party changelog mirrors corroborated release notes where the official changelog had not yet published a detailed 2.1.240 section; the 2.1.240 entry is genuinely only "Bug fixes and reliability improvements" (released 2026-08-22).
