# The tree-state line can name a repository it did not measure

**Date**: 2026-08-26 · **Author**: Rio ⚡ (`ea46bc1a`) · **Manager**: Mr. Radio 🦉
**For**: John — `src/conftest.py`, the `[tree-state]` diagnostic
**Status**: analysis only — no code changed, no test changed.
**Scope discipline**: every claim below is filed under **MEASURED** or **INFERRED**. Nothing is
promoted from one to the other by confidence.

---

## Verdict

The diagnostic cannot fail a suite and cannot currently print a wrong sha in this tree. It carries
two ways to be **confidently wrong rather than honestly unknown**, and one contract defect:

1. **It never says which repository it measured.** `git -C <dir>` walks *up* to the nearest
   ancestor repo, so a directory whose own gitdir pointer is gone reports its **ancestor's** sha in
   a fully confident line. Six worktrees already live inside this repo.
2. **`behind=` is computed against the last-*fetched* ref and printed with no fetch age**, so
   `behind=0` reads as "up to date" when it only means "up to date as of whenever I last fetched".
3. `tree_state_line`'s docstring says **"Raises: nothing"**; it can raise `UnicodeDecodeError`.

Both remedies are one line each and are Mr. Radio's, not mine: **print the resolved top level** and
**print the fetch age**.

---

## 1. MEASURED — `git -C` walks up, and the resulting line hides it

`git -C <dir>` resolves to the nearest ancestor repository, silently:

```
$ mkdir -p /tmp/x/outer/inner && git -C /tmp/x/outer init -q
$ git -C /tmp/x/outer/inner rev-parse --show-toplevel
/tmp/x/outer
```

The consequence, produced directly rather than reasoned about. A scratch directory nested inside
this repo, holding no gitdir pointer of its own (created, measured, and removed):

```
resolved toplevel: /mnt/DATA01/include/www.deepily.ai/projects/lupin
reported sha     : 729b2076        # the MAIN repo's sha, not this directory's

[tree-state] sha=729b2076 branch=wip-v0.2.0-2026.08.03-present-and-demo
             behind=0 ahead=74 vs origin/wip-v0.2.0-2026.08.03-present-and-demo tracked-dirty=3
```

**Nothing in that line is hedged.** No UNKNOWN, no `?`, no hint that the sha belongs to a different
directory than the one asked about. A reader quoting it tomorrow gets a wrong tree, not a missing one.

### Why this is reachable here and not theoretical

**MEASURED** — six worktrees live *inside* the repository, each with the main repo as an ancestor:

| Worktree | Ancestor repo | Its sha | Main's sha | Distance |
|---|---|---|---|---|
| `.claude/worktrees/tfe-08a75512` | the Lupin root | `1fa05b16` | `729b2076` | **1,581 commits** |
| `tfe-149ea7ca` · `tfe-99e41be5` · `tfe-d5b57795` · `tfe-e730b5ed` · `tfe-ef24f2da` | same | same | same | same |

**MEASURED** — all six currently hold their `.git` gitdir pointer, so **this is not live today**.
A run inside any of them reports its own sha correctly.

**INFERRED (not executed — I did not delete anyone's pointer)** — remove or stale-clean one of those
pointers and a run there walks up and stamps its green with main's sha, 1,581 commits from the tree
it actually ran on. The walk-up half of that chain is measured above; only the "someone removes a
pointer" half is inference.

**CORRECTION TO MY OWN FIRST REPORT**: I first named a container `.git`-mount-drift route. That one
is **not reachable** — I walked every ancestor above `src/` and Lupin's own `.git` is the only repo
in the chain, so with it absent git finds nothing and the line correctly prints UNKNOWN. Mr. Radio
caught this. The risk survives; the route I named for it did not.

### Remedy

Read `rev-parse --show-toplevel` and print it in the line. Then the diagnostic always states which
repository it measured, and a walk-up becomes visible instead of silent. Optionally compare it to
the directory passed in and print UNKNOWN on mismatch — but **printing it is the part that matters**,
because it converts a silent wrong answer into a readable one.

## 2. MEASURED — `behind=` is an unknown wearing a known value

`ref` is `@{upstream}`, which reads the **last-fetched** ref. That is deliberate and documented:
the docstring says the run performs no network access and cannot hang on a remote. Correct choice.

What is not disclosed is the **age**. `behind=0` is printed as a bare confident number, and reads as
"up to date"; it means "up to date with whatever I last fetched", which may be hours or days old.

**Remedy**: stamp the ref's age beside it — e.g. `git log -1 --format=%cr <ref>` — so the number
carries the as-of that makes it true.

## 3. MEASURED — the docstring's "Raises: nothing" is false

`_git_reader.read()` catches `OSError` and `subprocess.SubprocessError`.

```
UnicodeDecodeError is OSError?           False
UnicodeDecodeError is SubprocessError?   False
subprocess.TimeoutExpired is SubprocessError?  True
```

`text=True` decodes with the locale codec, and a ref name carrying invalid bytes raises
`UnicodeDecodeError` — a `ValueError`, caught by neither clause. Measured with an injected reader:
it escapes `read()`, and it escapes `tree_state_line`, whose contract states `Raises: nothing`.

**The suite is still safe** — `pytest_terminal_summary` wraps the call in `except Exception` and
degrades to the UNKNOWN line. Worth naming: that net carries `# pragma: no cover`, so the only line
standing between this and a diagnostic changing a suite's outcome is the one line no test exercises.

**Remedy**: catch `Exception` in `read()` (a diagnostic reader has no reason to be selective), or
add `ValueError`; and correct the docstring either way.

## 4. MEASURED — the timing budget is 7 calls, not 4

Counted with a spy reader on the no-upstream path:

```
WORST_CASE_GIT_CALLS: 7
    rev-parse --short HEAD
    rev-parse --abbrev-ref HEAD
    rev-parse --abbrev-ref @{upstream}
    worktree list --porcelain          # _primary_branch, only when there is no upstream
    status --porcelain
    rev-list --count HEAD..main
    rev-list --count main..HEAD
```

At `timeout=5` that is a **35-second** worst case against a suite's wall clock, not 20.

>
> He also caught a defect in his first cut of §2's remedy, worth reading: `--git-path FETCH_HEAD`
> returns a path relative to the *git process's* cwd, so a genuinely two-day-old FETCH_HEAD printed

**Can it fail a suite? No** — `TimeoutExpired ⊂ SubprocessError` is caught, and the caller wraps.

**INFERRED (not reproduced)** — one residual hang path: `subprocess.run` kills the child on timeout
and *then* drains the pipes, so a grandchild inheriting them can block past the 5 s. **MEASURED**
that it is not armed here: `core.fsmonitor` and `core.untrackedCache` are both unset. It is
config-dependent, and `git status` under fsmonitor is the classic case.

## 5. Minor — one unknown field inside a confident line

When the branch call fails, the line prints `branch=?` and then confident `behind=` / `ahead=`
anyway. Not wrong, but it mixes an unknown into a claim that otherwise reads as fully known.
