## 1. Goal

A second collapsible section in the notifications client, sitting **immediately below** the Task List,
that shows the same rows grouped **by epic** instead of by owner. Rick toggles between them to move
between the micro view (who owes what) and the macro view (what are we actually trying to finish).

It gets its own toolbar button, exactly like every other section.

## 2. Rick's repo question, answered — and the answer is bigger than "yes"

> *"Since this is being integrated into the notifications client I think the actual location of the
> source code should also be within the Lupin repo should it not?"*

**Yes. And the markdown board does not need to be involved at all.**

Today `docs/epic-board.md` lives in **planning-is-prompting**, generated every 10 minutes by
`workflow/scripts/generate_epic_board.py`, which reads the live task store and writes markdown for
the doc viewer. That pipeline is fine and should stay — a URL that survives across sessions in a
browser tab is worth having.

But the UI does not need it. **The notifications client already fetches every row the generator
reads**, from the same store:

```
/api/tasks?limit=500&unscoped_audit=true&hide_parked=false&char_budget=0
```

— `src/lupin_app/static/js/shared/task-list-query.js:50`

and that response already carries `correlation_key` (`src/cosa/rest/routers/tasks.py:349`), which is
where the epic lives (`epic:<slug>`).

⇒ **Grouping by epic is the same operation the task list already does by owner, keyed on a different
field.** No new endpoint, no markdown parsing, no cross-repo file read for the rows.

| Concern | Where it belongs |
|---|---|
| The accordion, the toolbar button, the renderer | **lupin** — it is client code, it lives with its siblings |
| The row data | **already served** by `GET /api/tasks` — zero backend delta |
| `docs/epic-board.md` + the cron + the doc-viewer URL | **planning-is-prompting**, unchanged. A different surface for a different reader |
| The epic *story* text (`epic-stories.json`) | **moves into lupin** and gets served from the tasks router — Rick's ruling, §5 |

## 3. Clone pattern — the task list is its own template

🔴 **CORRECTED 2026-08-24 by maya, who checked instead of trusting me.** This section originally
named the TypeScript multiplexer artifacts (`TaskListRenderer.ts`, `taskListModel.ts`,
`TaskListStore.ts`, `taskListCollapse.ts`). **Those belong to a different client and are not on
Rick's page.** Receipts: `notifications.html` references `multiplexer/boot.ts` **zero** times; its CSS
link at `:17` is `css/task-list.css`, *not* `css/multiplexer/task-list.css`; and the comment at `:692`
says *"**Ported from** the Cheech-approved TS multiplexer card onto the fleet-status section
structure"* — past tense, a port, not the live implementation. The task list Rick actually sees is
~40 methods on the `NotificationsUI` class in `static/js/notifications.js`, roughly lines 9009-10137.

**The lesson for the next person planning against this client**: `.ts` files under
`static/js/multiplexer/` serve `multiplexer.html`. `notifications.html` is served by
`static/js/notifications.js`. Sharing a name is not sharing a bundle — check the `<script>` and
`<link>` tags on the page you are actually changing.

| Artifact | Existing (task list) | New (epic board) |
|---|---|---|
| Card methods | `NotificationsUI` methods in `static/js/notifications.js` (~9009-10137) | epic-board methods on the same class |
| HTML mount | `notifications.html:695` `<div class="collapsible-section" id="section-task-list">` | new sibling immediately after its closing tag |
| CSS | `static/css/task-list.css` (linked at `notifications.html:17`) | `static/css/epic-board.css` |
| Toolbar button | `notifications.html:48` | new `.toolbar-btn` with `data-section="section-epic-board"` |
| Unit tests | `src/tests/unit/notifications_js/task_list_panel.test.ts` (`vm.runInThisContext` + happy-dom, under `npm test`) | `…/epic_board_panel.test.ts`, same harness |

**These line numbers ARE correct** and survived the correction: the toolbar at `:48`, the mount at
`:695`, the fetch at `task-list-query.js:50`, the binder at `notifications.js:10297`. Only the clone
*targets* pointed at the wrong bundle.

**Do not add a second poll.** The card already fetches every row both views need; the epic view reads
the same cached result. A second timer against the same endpoint is waste and gives the two panes
different clocks, which reads as a bug the first time they disagree.

## 4. Toolbar wiring — the mechanism is generic, so this is one line plus a button

`notifications.js:10297` binds every `.toolbar-btn` by `data-section` and routes to
`toggleSectionVisibility( sectionId )` at `:10315`. Nothing is per-section.

```html
<button class="toolbar-btn active"
        data-section="section-epic-board"
        data-testid="epic-board-toolbar-btn"
        title="Epic Board">🗂️</button>
```

⚠️ **Place it immediately after the task-list button (`:48`) and BEFORE the two
`.task-accordion-btn` controls at `:53-54`.** Those two are deliberately *not* `.toolbar-btn` and
carry no `data-section` — the comment at `:49-52` says so explicitly. Dropping the new button in the
middle of that pair is the obvious way to break collapse-all.

Emoji is a suggestion; 🗂️ reads as "grouped" against the task list's 🗒️.

## 5. Epic story text — RULED 2026-08-24 by Rick: move the file into this repo

**Rick's question was "isn't epic-stories.json generated by a Lupin endpoint?" The answer is no —
nothing generates it.** `grep -rn "epic-stories|epic_stories" lupin/src --include=*.py --include=*.js
--include=*.ts` returns zero hits; its own `_README` says *"Hand-maintained; the ONLY hand-maintained
input to docs/epic-board.md"*; it has one consumer, `generate_epic_board.py:62`, and two commits in
its entire history. Somebody types a line when they mint an epic.

**His conclusion survives the corrected premise, on a better argument.** The task store is this
repo's (`src/cosa/rest/routers/tasks.py`). `correlation_key` — where the epic lives — is a field on
this repo's rows. **Twelve of the fourteen epics are lupin work.** The file sits in
planning-is-prompting because that is where the board generator happened to be written, not because
anything about it belongs there.

### The build

1. **Move** `planning-is-prompting/workflow/epic-stories.json` → `src/conf/epic-stories.json`
2. **Serve** it from the router that already serves the rows — `GET /api/epic-stories`, same
   `require_api_key_or_jwt` guard as `/api/tasks`. Returns the JSON as-is
3. **The client reads it** alongside its existing `/api/tasks` fetch. An epic with no entry still
   renders de-slugged, exactly as the generator does today — a missing story is a nudge, never an error
4. **`generate_epic_board.py` reads it over HTTP** instead of off disk, with the on-disk copy dropped.
   ⚠️ **It must degrade to de-slugged names when the endpoint is unreachable** — the board is on a
   10-minute cron and must not start failing because :7999 bounced

**Why this beats the file-path coupling I first proposed.** My original recommendation avoided
option B because lupin reading a path in another repo breaks silently when either repo moves. Serving
it over an API that already exists has no such fragility, and it leaves **one** copy rather than two.

**Ordering note for the implementer**: steps 1–3 stand alone and ship the accordion. Step 4 touches
the *other* repo and can land separately — do not block the UI on it. Until step 4 lands the JSON
exists in both places; say so in the commit rather than leaving a reader to discover it.

## 6. What the epic view should show

Mirror the generator's own sections, because they were designed against this data and Rick already
reads them:

1. **⏳ Waiting on Rick** — highlight, not a move; rows also appear under their epic
2. **Per-epic groups**, each an accordion row: `<epic name> — N rows`, collapsed by default
3. **🔴 Drift** — rows carrying no `epic:` key, which is the nudge to stamp one

Columns: `id8` · `priority` · `status` · `title`. Owner is redundant here — that is what the pane
above is for.

**Default state: all epics collapsed.** The macro view's value is the list of epics and their counts;
opening one is a deliberate act.
