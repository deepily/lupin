## Per-assertion — the concrete mutation that should turn it red

**Assertion 1 — FALSIFIABLE (drift guard).**
Red mutation: remove `test suite` (or any agentic command) from the factory dict → the set-difference `agentic_commands − factory_commands` is non-empty → red. Restore → green.
Caveat (see follow-up below): it guards the four static lists, not runtime reachability.

**Assertion 2 — FALSIFIABLE.**
Red mutation: add a conversational command (e.g. `agent router go to math`) to a factory branch → the "in NO factory" clause fires red. Restore → green. Both directions are testable and clean.

**Assertion 3 — FALSIFIABLE, needs both-directions.**
Red mutation: register `agent router go to automatic` as a `CONVERSATIONAL` spec → it leaves the control-only set → red.
Weakness: "appears in prompt+training **only**" catches a *missing* membership but not an *extra* one unless the assertion also asserts absence from registry+factory. Write it as set-equality both ways, exactly the way assertion 4 already does (`test_v2_registry.py:68`).

**Assertion 4 — FALSIFIABLE and PROVEN.**
Red mutation: put one command in two buckets → `assertEqual( a & b, set() )` fires. This is not hypothetical — the check exists and passes in the current tree (`src/tests/unit/test_v2_registry.py:71`).

**Assertion 5 — FALSIFIABLE but UNSOUND.**
Red mutation (that works): delete the `if __name__ == "__main__"` guard at `deep_research/cli.py:1253`, or delete a package's `__main__.py` → a filesystem/substring check goes red.
The unsoundness (this is the finding): §4/§5.1 specify a **static** check — "package needs `__main__.py`, module needs a `__main__` guard". A static check sits **green** through real unrunnable states:
- a package that HAS `__main__.py` but raises `ImportError`/`ModuleNotFoundError` at import time;
- a module that HAS the guard but crashes on import before argparse.
Both pass a "does the file / guard exist" check and both die under `python -m`. The only sound predicate is to **run it**: `python -m cli_module --help`, assert `returncode == 0`.

**Assertion 6 — FALSIFIABLE but NARROW.**
Red mutation: any of the three suspect packages produces stderr `No module named …` → red (verified below).
The narrowness (this is the finding): `get_cli_help` at `agent_registry.py:359` is `help_text = result.stdout or result.stderr or ""` with **no returncode check**. So any non-zero exit whose stderr is a *different* text — a `KeyError`/`ValueError` traceback, an argparse usage error — is cached as "help text" and injected into the phi4 argument-extraction prompt (`runtime-argument-expeditor.txt:19`), while assertion 6 stays green because the magic substring `No module named` is absent. The assertion matches a **description** of the current failure, not the failure itself.

## A5 / A6 collapse to one check

Assertions 5 and 6 are two weak halves of one sound check. Both are asking "will `python -m cli_module --help` actually run?" — 5 guesses from the filesystem, 6 pattern-matches one error string. Replace both with a single runtime assertion:

```
result = subprocess.run( [ sys.executable, "-m", cli_module, "--help" ], capture_output=True, text=True, timeout=10 )
assert result.returncode == 0, f"{cli_module} not runnable: {result.stderr.strip()[:200]}"
```

This is falsifiable in the author's own §6 sense (delete a guard → red), subsumes 6 (a broken module returns non-zero regardless of the error spelling), and — because it executes — cannot be fooled by an import-time crash the way the static form can.

Verified exit codes on the current tree (`cosa/.venv` python, `PYTHONPATH=src`):

| cli_module | style | exit | stderr / stdout |
|---|---|---|---|
| `cosa.agents.claude_code` | package, **no `__main__.py`** | **1** | `No module named cosa.agents.claude_code.__main__` |
| `cosa.agents.bug_fix_expediter` | package, **no `__main__.py`** | **1** | `No module named …bug_fix_expediter.__main__` |
| `cosa.agents.test_fix_expediter` | package, **no `__main__.py`** | **1** | `No module named …test_fix_expediter.__main__` |
| `cosa.agents.deep_research.cli` | module, guard at `cli.py:1253` | **0** | real `usage: cli.py …` |

The exit code separates runnable from unrunnable cleanly; the static check does not.

## Follow-up 1 — do assertions 1–3 let through a command that is right everywhere the test looks and still unreachable by voice?

**Yes.** The test reads the checked-in template file and the training JSON keys as **static sets**. A command present in registry + prompt + training-keys + factory is still unreachable by voice when:

1. **The LoRA wasn't retrained.** §5.4 states plainly that training keys are baked into the model at train time. The test reads the JSON on disk; the deployed router emits from its weights. A new key in the file with no retrain is green in the test and mute in production. §5.4 acknowledges this asymmetry — but the *test* does not encode it, so assertion 1 treats "in the training keys" as a reachability proxy that §5.4 itself says it is not.
2. **Runtime template ≠ checked-in template.** The test reads `/src/conf/prompts/agent-router-template-completion.txt`. If the running router loads a different template (or a differently-rendered one), template membership does not equal what the router is told. *Unverified* that the two diverge today — flagged as the load-bearing assumption, not a confirmed defect.
3. **Emitted string ≠ registry key, no alias wired.** Set-membership tests that the *same string* appears in four lists; it never tests that the string the router actually emits at runtime matches a registry key or a registered alias. `resolve()` handles V2 aliases (`registry.py:143`); whether `resolve_agentic()` will is a phase-1 open.

So the honest scope is **four-list drift consistency**, which is real and worth having. Calling it the "completeness test" (§6 header) overclaims — it does not prove a user can reach the command by voice. Recommend renaming it a drift guard and stating the three reachability gaps as out-of-scope-by-design.

## Follow-up 2 — is phase 3's "green by the fixes, never by relaxing an assertion" gate enforceable by anything but good intentions?

**No — it is a review gate, not a mechanical one.** Nothing in the code stops a builder from reaching green by weakening the test rather than fixing the drift:

- loosen an assertion, or
- add a command to an "intentional exemption" set, or
- bump the hard-coded counts in `test_bucket_counts` — `6 / 7 / 1 / 2` and the `16` total (`test_v2_registry.py:75-80`) — to whatever passes.

§5.1.2 itself concedes those counts must be **hand-updated** in the same commit. But a count updated to the new *true* value is, in a diff, **indistinguishable** from a count updated to *silence* a failure — both are one-line number changes that turn red to green. The falsifiability "demos" §6 requires are themselves ordinary tests and can be edited too.

So the gate rests entirely on the cascade reviewer and code review catching a loosening in the diff. That is exactly how the fleet has lost guards before (a guard that cries wolf gets deleted the week it blocks someone). The doc is honest that phase 3's gate "is the one that matters" — but it supplies no mechanism, only intent. If a stronger gate is wanted, it has to be structural: e.g. derive the expected counts from the registry at test time so there is no magic number to edit, and require any exemption to carry a machine-checked reason field rather than a silent set-membership.
