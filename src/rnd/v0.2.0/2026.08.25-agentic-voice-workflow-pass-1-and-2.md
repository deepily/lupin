## The question this answers

Rick asked a plain question: **can a SWE team register a newly built agent so that it
runs by voice?**

The honest answer used to be "yes, if they find all four places." It is now **"yes —
one contract entry, two one-line opt-ins, and one construction branch that is on its
way out."** This document says what changed, what a crew actually does, and which
parts are measured rather than asserted.

## What a SWE team actually does, end to end

Seven steps. Steps 1–3 are registration; 4–5 are the things crews get wrong; 6–7 are
rollout and proof.

### 1. Write ONE contract entry

Add the command to `JOB_ARG_CONTRACTS` in
`src/cosa/agents/runtime_argument_expeditor/agent_registry.py`.

The v2 registry then builds the agent's `AgentSpec` **for you** — the agentic set is a
comprehension over that table:

```python
# src/cosa/rest/v2/registry.py
_AGENTIC = tuple( _agentic_spec( command, entry ) for command, entry in JOB_ARG_CONTRACTS.items() )
```

Display name, CLI module and CLI style are all read off the same entry, so there is no
second hand-written list to drift from the first. **This is what "one entry, not four
files" means.**

### 2. Declare the arguments and their questions TOGETHER

A command says what it needs and what to ask when it is missing, side by side, in the
same entry — so the two cannot drift apart:

```python
"agent router go to deep research" : {
    "required_user_args" : [ "query" ],
    "fallback_questions" : {
        "query"  : "What topic would you like me to research?",
        "budget" : "Would you like to set a budget limit in dollars? Say a dollar amount, or 'no limit'.",
    },
    "fallback_defaults"  : { "budget" : "no limit" },
}
```

`arg_mapping` translates what the router actually emits into your CLI's names — and
should map only what genuinely means the same thing. Aliasing `topic` → `research`
once delivered a spoken subject phrase where a **file path** was expected, and the job
died on a file nobody had named (row `9d89afe2`). Left unmapped, the argument stays
missing and the question fires, which is the correct outcome.

### 3. Set the two ratified opt-ins

Two one-line memberships, both **deliberately not derived** from anything:

- `_SPEAKABLE_AGENTIC` — "belongs in the voice router prompt."
- `_USER_INITIABLE_AGENTIC` — "a person may start this by typing into the Q&A card."

They answer different questions. Deriving one from the other works today by
coincidence and breaks on the first command that is typeable but not sayable. Two
commands are held out of the second on purpose: their only argument is a job id
produced by a job that already failed, and nobody types one of those — you press a
button on the failed job's card.

### 4. Understand the retrain asymmetry — it is measured

**Listing the command in the router prompt makes it reachable immediately. The retrain
only makes it dependable.** These are different things that land at different times,
and conflating them is how an agent ships mute.

Live A/B on the production adapter — same model, same training set, **only the prompt
differing** (`src/rnd/v0.2.0/2026.08.15-router-emission-probe.md`):

| arm | prompt-listed? | trained? | emitted correctly |
|---|---|---|---|
| `test fix expediter resume` | **no** | yes | **0/5** — routed to `swe team` every time |
| `test fix expediter resume` | **yes** | yes | **5/5** |
| `bug fix expediter` | no | no | **0/5** — routed to `claude code` every time |

Two honesty notes, because this table gets quoted:

- **Both A/B arms were trained.** So this shows prompt-listing is sufficient *given*
  training. It does **not** isolate prompt-listing *without* training — no command in
  the tree is prompt-listed and never trained, so that arm could not be run.
- **An earlier claim in the skill did not reproduce and has been retired.** It said an
  unlisted command "still fires 6/10" — i.e. that a missing entry causes *intermittent*
  failure. On this adapter the unlisted arms emitted the target **0/5**: the model did
  not invent, it confidently substituted the nearest listed command. **A missing prompt
  line is a clean, total, silent misroute, not a flaky one.** That is a worse failure
  than the old text described, and easier to miss.

Since 2026-08-25 the training artifact also carries a fingerprint of the corpus it was
built from, and a training run **refuses** if the two disagree (row `11390b57`) — so a
corpus edit can no longer be silently trained around.

### 5. Know which `elif` is forbidden — this is the subtle one

**Routing goes through the brain.** `AskFlow` (`src/cosa/rest/v2/flow.py`) sits behind
`POST /api/v2/ask` and `POST /api/v2/submit`. It resolves the command against the
registry, runs the expeditor to fill arguments, asks the user when one is missing, and
hands the built job to the queue. The v2 registry replaced **three** v1 routing
mechanisms that had drifted apart: the LLM-routing `if`/`elif` reached from
`push_job()` / `get_routing_command()`, the `MODE_TO_AGENT` map, and a command
`if`/`elif` in the factory. `src/tests/unit/test_v2_registry_drift_guard.py` exists to
stop them returning.

⚠️ **But "no `if`/`elif`" is about ROUTING, and that distinction is load-bearing.**
Job **construction** — turning an already-resolved command plus its arguments into a
Job object — *still* dispatches by branch in `create_agentic_job()`
(`src/cosa/rest/agentic_job_factory.py`). Verified in the tree on 2026-08-25:
**eleven branches, live.** The registry carries a `job_factory` field for exactly this,
but it is `None` in phase 1 and phase 5 ("wires factory dispatch by lookup", per the
registry's own docstring) has not landed.

So a new agent today **does** add a construction branch there, and should expect to
delete it when phase 5 arrives.

> This was nearly documented backwards. The first draft of pass 2 told crews to add no
> branch at all, which would have left a new agent unbuildable. It was caught by
> grepping the factory instead of trusting the design note — the same class of error
> the gate exists to prevent, in the opposite direction.

### 6. Do not mistake queue directives for agent arguments

`scheduled_at` and `monopolize` say **when** and **how** the queue should run the work,
never what the agent should do with it. `AskFlow._split_queue_directives()` pops them
out before the job is built.

**This is easy to get wrong because they arrive in the same dictionary as real
arguments.** The expeditor offers them for *every* agentic command, so "run the deep
research at ten tomorrow" comes back as ordinary keys alongside `query`.

The failure mode is quiet and specific: `create_agentic_job` reads its arguments **by
name** and does not name these, so a left-in `scheduled_at` is **dropped in silence and
the job runs immediately** — while the caller believes it is scheduled. They also
cannot be smuggled in through `args`, because `args` is validated against the command's
argument contract and no contract names them.

`"immediately"` / `"now"` / `"none"` normalise to no schedule — a user who says
"immediately" must keep meaning it.

### 7. Ship it in SHADOW first, then prove it

A new command is **not flipped live on its first day**. The INI carries it per agent
(`swe team trust mode = shadow`, `bug fix expediter trust mode = shadow`):

| mode | what happens |
|---|---|
| `disabled` | no proxy at all |
| **`shadow`** | **compute and log the decision, do not execute it** |
| `suggest` | surface it to the user, who still decides |
| `active` | act automatically at the trust level the agent has earned |

Default is `shadow` for a reason: you get a real trace, on real traffic, of what the
command *would* have done, before it can do it. Flipping without that trace is a guess.

**And the proof bar**: a green pipeline test does **not** mean voice-reachable. Those
are different claims, and the pipeline test cannot make the second one. Route the
command end to end, or say plainly that reachability is unverified.
