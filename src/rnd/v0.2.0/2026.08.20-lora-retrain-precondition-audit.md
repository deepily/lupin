### The silent-degradation hazard worth knowing about

`peft` and `trl` are imported inside `try/except ImportError` blocks (`peft_trainer.py:12-19` and
`:34-40`), which set `SFTTrainer = None` rather than failing. So a missing `trl` does **not** fail at
import — it fails at `SFTTrainer(...)` on **line 540**, *after* the base model has been loaded onto the
GPU. Left undiscovered, tomorrow's run burns the model-load time and dies mid-way instead of in the
first second. That is precisely the "discover blockers at run time" failure this audit exists to prevent.

## 4. How long a full run actually takes

**Headline: ~4.5–5.5 hours for one epoch + merge + quantize with light validation; ~6 h if all three
`*-stats` legs run at `--validation-sample-size 1000`.** A 12:00 EDT start finishes ~17:00–18:00 —
comfortably inside the box's up-window, with hours of slack before the ~22:53 power-off.

### The anchor — a real prior run, not a guess

`models/Mistral-7B-Instruct-v0.2.lora/training-2025-04-30-at-22-55/checkpoint-1317/trainer_state.json`:

| Measured | Value |
|---|---|
| Optimizer steps | 1,317 = exactly 1 epoch (`num_train_epochs: 1`, `max_steps: 1317`) |
| Per-device batch | 4 (`train_batch_size`), grad-accum 6 (`conf/mistral_7b.py:41`) ⇒ 24 rows/step |
| ⇒ train rows that epoch | 1,317 × 24 = **31,608** |
| In-training evals | 9, at 10% intervals (`eval_steps: 0.10`), **~413 s each** ⇒ **62 min of eval** |
| Eval set size | 413 s × 9.57 samples/s ≈ **3,952 rows** |
| Wall, training start → merge start | `22:55` → `merged-on-2025-05-01-at-02-10` = **195 min** |
| ⇒ pure training | 195 − 62 ≈ **133 min**, i.e. **~6.1 s / optimizer step** |

### Scaling that to tomorrow

Ministral-8B config (`conf/ministral_8b.py`): batch **2** × grad-accum **8** = 16 rows/step,
`max_seq_length` **683**, `eval_steps` 0.10.

- Steps for one epoch: 37,868 / 16 = **2,367 optimizer steps**
- Token-slots/epoch: 37,868 × 683 = 25.9 M vs prior 31,608 × 779 = 24.6 M ⇒ **1.05×**
- Model 8B vs 7B ⇒ **~1.14×**
- Combined **~1.20×** ⇒ training ≈ 133 × 1.20 ≈ **160 min (~2.7 h)**
- In-training eval: 4,734 rows × 9 evals, scaled 8B/7B ⇒ ~565 s each ≈ **85 min (~1.4 h)**
- **Train phase ≈ 4.0–4.2 h**

**Merge + quantize ≈ 25 min**, measured on *this exact model*: the Feb-20 Ministral artifacts run
`21:10:52` (merge shards written) → `21:36:09` (AutoRound output dir created), with the ~9.3 GB
quantized shards landing at 21:36.

### Assumptions named, because they move the number

1. **One epoch.** Both configs set `num_train_epochs: 1`; if tomorrow's run uses more, multiply the
   training+eval portion directly.
2. **Per-step time scales with model size × sequence length.** Crude. The new rows carry the full command
   menu inline, so if real token counts run longer than `max_seq_length` suggests, they get truncated at
   683 and the estimate holds — but if 7B-vs-8B costs more than 1.14× on these cards, it drifts high.
3. **The 195-min prior window is training + eval only.** If that run also did a pre-training validation
   leg, my 133-min training figure is over-stated and the estimate is **conservative** (too long).
4. **Validation legs are not in the 4.5–5.5 h core.** Each spins a fresh vLLM server (~2–4 min startup on
   an 8B) plus `--validation-sample-size` generations. At 100 that is minutes; at 1,000, budget ~1 h total
   across the three legs. I have no measured number for these — flagging rather than inventing one.
5. **Single 4090.** `device_map: auto` may shard across both; that changes the arithmetic and is
   untestable while vLLM holds them.
