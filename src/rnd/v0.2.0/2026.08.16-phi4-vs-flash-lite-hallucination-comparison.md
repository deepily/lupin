## 1. What we compare, and why it can be measured honestly

**The task**: the DM Tutor's rewrite — take a DM body over the trigger, return the same content in the house shape.

**Why this task and not a benchmark**: it already has a **hallucination detector in production**, and that detector has been firing. Measured over the live corpus today:

| tutor outcome | count |
|---|---|
| `under_trigger` (no rewrite needed) | 1,325 |
| `rewritten` (delivered) | 798 |
| **`fabrication_blocked`** | **158** |
| `model_failed` | 21 |
| `label_blocked` | 12 |
| `rescope_blocked` | 6 |

**158 rewrites refused for inventing content against 798 delivered — a 16.5% fabrication rate on attempts** for Phi-4 as configured today. Not a leaderboard number: our guard, our traffic, our prompt.

⇒ **The comparison is: swap the model behind the same prompt and the same guard, replay the same bodies, read the same counters.** No new judge, no new metric, no labelling project.

### 1.1 The dataset already exists

`/var/lupin/dm-corpus/dm_traffic.jsonl` — **5,562 rows, 9.2 MB, durable on disk** (it survives bounces; the in-memory audit does not). Every row carries the submitted `body`, the `delivered_body`, `tutor_claims_in`, `tutor_words_in`, `tutor_outcome`, and `tutor_fabricated` — *what* was invented, when it was refused.

**Replay set**: the rows where the tutor actually fired — **995 real bodies**, each with a known Phi-4 outcome. No synthetic data, no sampling design to argue about.

## 2. Design

### 2.1 Config only, no new client — Rick's constraint, satisfied structurally

The spec-key pattern already in the INI (`lupin-app.ini:227-228, 298`):

```ini
dm_tutor/phi_4        = vllm://192.168.1.21:3001@kaitchup/Phi-4-AutoRound-GPTQ-4bit
dm_tutor/phi_4_params = { "prompt_format": "instruction_completion", "model_name": "Phi-4-AutoRound-GPTQ-4bit",
                          "temperature": 0.0, "max_tokens": 4096, "stop": [ "</s>", "</stop>" ], "stream": False }
llm spec key for dm tutor rewrite = dm_tutor/phi_4
```

The new arm is the same three lines:

```ini
dm_tutor/flash_lite        = google-gla:<flash-lite-model-id>
dm_tutor/flash_lite_params = { "temperature": 0.0, "max_tokens": 4096, ... }
```

⚠️ **Colon, not slash.** `_parse_model_descriptor` (`llm_client_factory.py:402-435`) treats **colon as the only vendor delimiter**; a slash is explicitly never one and falls through to **vLLM** with a deprecation warning. `google-gla/gemini-…` would silently route to the local box and produce a comparison of Phi-4 against itself. This is the single most likely way to get a confidently wrong result on day one.

**Every parameter comes from the configuration manager** — the `_params` dict is where temperature, max tokens and stop sequences live, per Rick's instruction. Nothing is hardcoded in the harness.

### 2.2 The harness

`rewrite_dm( body )` is a **free function with a fail-closed contract**: the distilled lines, or `None`, and `None` always means deliver the original. The model behind it comes from the spec key. So the harness is:

1. Read the replay set from the corpus.
2. Per arm, point the spec key at that arm's model.
3. Call the **existing** `_apply_dm_tutor` path per body — same prompt, same guard, same claim counter.
4. Record the returned `meta` dict verbatim.

**Nothing in the tutor changes.** If the harness requires modifying the tutor, the design is wrong.

### 2.3 What gets reported, per arm

| metric | source | why it matters |
|---|---|---|
| fabrication rate | `fabrication_blocked / (blocked + rewritten)` | the headline |
| what was invented | `tutor_fabricated` | a rate without examples is unreviewable |
| rescope / label blocks | `rescope_blocked`, `label_blocked` | a model can trade one failure mode for another |
| `model_failed` | outcome | coverage — a model that refuses is not safer, it is absent |
| claims out, words out | `tutor_claims_out`, `tutor_words_out` | compression is the product; a faithful model that does not compress is useless here |
| pointer survival | `_restore_dropped_pointers` firing | paths are the one element the house rule names |
| latency, cost | wall clock, token counts | see §4.2 |

## 3. Paired, not aggregate

Run **both arms over the identical 995 bodies** and compare **per body**.

**Why this is not a detail**: aggregate rates over different message mixes are the defect that has bitten this fleet twice — a share moves because the population changed, not because the treatment worked. Paired, each body is its own control.

Report the disagreement cells explicitly:

|  | Flash Lite clean | Flash Lite fabricated |
|---|---|---|
| **Phi-4 clean** | both fine | Flash Lite worse *here* |
| **Phi-4 fabricated** | Flash Lite better *here* | both fail |

⇒ **The two off-diagonal cells are the finding.** A single overall percentage hides them.

## 4. What this CANNOT settle — stated up front

1. **The guard is not ground truth.** `fabrication_blocked` counts what our detector caught. A model that hallucinates in ways the guard does not recognise scores *better* while being *worse*. ⇒ **Hand-label a sample of each arm's delivered output.** Without it we are comparing detectability, not honesty.
2. **Cost is asymmetric, and the corpus already knows it.** Local vLLM is sunk GPU; Flash Lite is paid per call. A prior arm on this work published −30.4% and came out **+7.0% all-in** once paid inference was counted (`2026.08.04-dm-arm-all-in-cost-and-breakeven.md`). Report all-in or do not report cost.
3. **Prompt fairness.** The tutor prompt was written against Phi-4 and iterated on Phi-4. A fair comparison says so. An *unfair* one is still informative — it answers "would swapping help today", which is the operational question.
4. **Temperature 0.0 is not determinism** on a hosted API. Repeat a subsample to size run-to-run variance before attributing any difference to the model.

## 6. My weakest claim, named for the reviewers

**That `google-gla` is not merely *configured* but *exercised*.** I verified the vendor entry, the URL, the env var and the descriptor grammar by reading them. I did **not** find a live call site using `google-gla` anywhere in the tree — every current spec key is vLLM, groq or deepily. So the path may be **configured but cold**, and a cold path can carry a broken client construction, a wrong auth header shape, or an incompatible params dict that no test has ever exercised.

⇒ **The smoke step in §5 is not a formality; it is where this design is most likely to fail.** Go at that claim first.

**Secondary**: I assume Flash Lite accepts the same `_params` shape (`temperature`, `max_tokens`, `stop`, `stream`). If the client maps those differently for a Google vendor, §2.1's "config only" needs qualifying — though still no *connector*.
