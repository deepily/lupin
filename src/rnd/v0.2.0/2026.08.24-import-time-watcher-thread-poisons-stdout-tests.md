# An import-time daemon thread prints live fleet events into tests that read stdout

**Date**: 2026-08-24 · **Author**: Tiberius 👑 (`cb30ffac`) · **Manager**: Mr. Radio 🦉
**Found while**: establishing the unit baseline for row `47d45f1f`
**Status**: analysis only — no code changed, no test changed.

---

## Verdict

Importing `lupin_mcp.cosa_voice_mcp` starts a **daemon thread at module import** that polls the
live session-bridge file every 2 seconds and writes a log line to **stdout** whenever any seat in
the fleet changes session id. **25 unit test files import that module**, so the thread runs for the
remainder of the suite, and **67 unit test files capture stdout — 15 of them parse it as JSON.**

The consequence is not a flaky test. It is that **a unit-tier result is partly a function of how
busy the fleet was while it ran.** A quiet box passes; a box where three seats are working can red
a test that no commit touched.

Observed once, in the baseline run for `47d45f1f`: **1 failed / 17,463 passed**, and the one
failure was this.

---

## 1. The thread, and that it is unconditional

`src/lupin_mcp/cosa_voice_mcp.py` — the loop (`:481-522`) and the start (`:528-533`):

```python
poll_interval = 2.0  # seconds
…
while True:
    time.sleep( poll_interval )
    clear_cached_session_id()
    result = _find_session_file()
    …
    if new_suffix != last_session_id:
        …
        logger.info(
            f"Session ID changed: {old_sender} -> {SENDER_ID} "
            f"(context clear detected)"
        )

_watcher_thread = threading.Thread(
    target=_session_watcher_thread,
    name="session-id-watcher",
    daemon=True
)
_watcher_thread.start()
```

`.start()` is at module scope. There is no guard — no `if __name__ == "__main__"`, no env check, no
"am I running under pytest" test. **Importing the module is enough.**

### Measured, deterministically

```python
before = {t.name for t in threading.enumerate()}
import lupin_mcp.cosa_voice_mcp
after  = {t.name for t in threading.enumerate()}
print(sorted(after - before))
```

```
THREADS_STARTED_BY_IMPORT: ['session-id-watcher']
watcher present: True | daemon: True
```

This is the deterministic half of the finding: the thread starts every time, in every process that
imports the module. What is nondeterministic is only **when it prints**.

## 2. What it prints, and when

It prints when the bridge file's mtime moves *and* the session id inside it differs from the one
the thread last saw. That is a **live fleet event** — a seat clearing context, a session being
re-spun, a bridge rewritten.

Nothing about the test suite causes it. Nothing about the test suite can prevent it.

### Measured, from the baseline run

Five such lines landed in a single 12-minute run:

```
Session ID changed: claude.code@lupin.deepily.ai#d7335dac -> …
Session ID changed: claude.code@lupin.deepily.ai#50362a46 -> …
Session ID changed: claude.code@lupin.deepily.ai#cb30ffac -> …
Session ID changed: claude.code@lupin.deepily.ai#d7335dac -> …
Session ID changed: claude.code@lu… (truncated — this is the one that landed inside a test)
```

Three distinct sessions, one of them **this seat**. A session running the suite can poison its own
run by doing normal work — receiving a DM, pushing a topic — while the suite executes.

## 3. How it turns into a red

`src/tests/unit/test_user_prompt_submit_hook.py::TestHeartbeatPokeReset::test_reset_skipped_when_prompt_is_injected_peer_dm`
runs the hook, captures stdout, and parses it:

```python
return json.loads( output )
```

The hook's own contract is that it emits one JSON object on stdout. When the watcher thread writes
its line into the same stream, `output` starts with:

```
\x1b[2m2026-08-25T00:44:23.297036Z\x1b[0m [\x1b[32m\x1b[1minfo     \x1b[0m] …
```

and `json.loads` raises. **The test's own subject behaved correctly.** The assertion never ran.

### Determinism check — the discriminator, applied

Following the standing rule that real contact is deterministic and noise is not:

| run | result |
|---|---|
| the test alone, 3× | **3/3 pass** |
| the whole file (18 tests), 3× | **3/3 pass** |
| inside the full 17,463-test suite | **1 fail** |

Failing only in the full run, while passing in every scoped run, is what a timing race with an
asynchronous writer looks like. It is not evidence about the hook.

⚠️ **And the converse holds, so nobody over-reads the table above**: a green here is one sample of
the same race. The scoped runs did not *prove* the test correct — they only failed to lose the
race. The finding rests on the named mechanism, not on the pass counts.

## 4. The exposure is suite-wide, not one test

Counted across `src/tests/unit/`:

| | count |
|---|---|
| files importing `cosa_voice_mcp` (each starts the thread) | **25** |
| files capturing stdout (`capsys` / `capfd` / `StringIO` / `redirect_stdout`) | **67** |
| …of those, files that parse captured stdout as **JSON** | **15** |

The 15 JSON-parsing files are the sharpest edge, because a stray line breaks the parse outright
rather than merely adding noise to an assertion:

```
test_register_session_bridge_write_contract.py   test_register_session_manager_figure_stamp.py
test_arbiter_venv_import_gate.py                 test_dm_experiment_schedule_generator.py
test_session_bridge_atomic_write.py              test_lupin_arbiter_app_health_watcher.py
test_context_pressure_writer.py                  test_vertex_publisher_config_guard.py
test_lupin_arbiter_app_fleet_arbiter_loop.py     test_sessions_dir_seam.py
test_dm_experiment.py                            test_arbiter_outreach_logging.py
…
```

Note what is on that list: the **session bridge** tests, the **context-pressure writer**, the
**sessions-dir seam**, and both **arbiter loop** tests. These are the tests that assert on fleet
liveness plumbing — the same plumbing whose live activity triggers the thread. The tests most
likely to be poisoned are the ones covering the machinery doing the poisoning.

Ordering matters and is not controlled: the thread only affects tests that run **after** the first
import of `cosa_voice_mcp`. Collection order therefore decides which of the 15 are in the blast
radius on any given run.

## 5. A second, quieter effect of the same import

The import itself writes a substantial banner to stdout before any thread starts — the runtime
header, project/session/sender lines, and the `ConfigurationManager` initialisation dump
(sections, inheritance, splainer path).

This one is **deterministic**, so it is the lesser problem: a test that passes today will keep
passing. It is recorded here only because it means the module is already a heavy stdout writer
before the asynchronous line arrives, and any fix that considers only the thread will leave the
banner behind.

---

## 6. Fix shapes (none applied — this is Rick's call)

Roughly in order of how much they change:

1. **Do not start the thread on import.** Move `.start()` behind an explicit `start_watcher()` that
   the MCP server entry point calls. Tests import the module for its functions and never want the
   thread. This is the smallest change that removes the hazard entirely.
2. **Send the log to stderr.** The line is diagnostic, not output. Every one of the 15 JSON parsers
   reads stdout only. This does not stop the thread from running in test processes, but it stops it
   reaching the stream under test.
3. **Suppress under pytest** (`PYTEST_CURRENT_TEST` in the environment). Cheapest, and the least
   honest — it makes the suite green without making the design any safer for the next reader.

Option 1 and option 2 are complementary rather than alternatives.

`redirect_stdout`, and no `json.loads`. Its assertions are on `client.run.call_count` and a patched
`time.sleep`. A stray line on stdout cannot reach them.

His traceback is not available — the launch was piped through `tail -25` and the assertion was
truncated out — so the cause remains open, and a full-capture re-run of that tier is queued behind
integration. **Same shape is not same cause**, and the two should not be merged on the strength of
the resemblance.
