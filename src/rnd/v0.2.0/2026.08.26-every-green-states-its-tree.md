## 1. What it does

Every pytest run — pass or fail, every tier — now prints one line naming the tree it ran on:

```
[tree-state] sha=0982f9fe branch=wip-... behind=0 ahead=71 vs origin/wip-... tracked-dirty=1
```

## 2. Why

A pass is a statement about a **tree**, not about a repository. On a tree several people commit
to, "the suite is green" decays the moment somebody else lands a commit, and nothing in the
output said which tree earned it.

This is the same defect measured one layer over on this row: one coverage data file, read
seventy minutes apart, reported **99%** and then **38%** for the same file, because a report is
rendered against the source **on disk now** rather than the source that was **measured**
(`2026.08.26-a-coverage-number-expires-when-the-tree-moves.md`). A green has that identical
shape and carried no timestamp at all.

**Motivation, one sentence, as ruled**: this *reports* and decides nothing — whether a stale
worktree should be refreshed or reaped stays manager-gated and is deliberately not ruled here.

## 3. The review, run adversarially after the fact

Four risks a pre-code review should have raised. Each was checked, not assumed.

### 3a. Does the new line break anything that PARSES pytest output? — **No — and my first answer overstated the surface**

⚠️ **CORRECTED 2026-08-26, after Mr Radio ran the suite and checked the real output.** He found
the output matches **neither** of two parsers I had listed, and he was right about the
observation. The conclusion I drew from my version of this table was sound; the table itself
was not, because it treated three parsers as three risks when only one of them reads pytest at
all:

| pattern | source | what it parses | matches pytest output? |
|---|---|---|---|
| `(\d+)\s+passed` | `swe_team/test_runner.py:76` | **pytest** | **yes — this is the one that matters** |
| `^# pass (\d+)$` | `job.py:1930` `_parse_node_tap_summary` | Node/TAP (the TypeScript suite) | no, **by design** |
| `\bPassed:\s*(\d+)` | `job.py:2149`, inside `_parse_non_pytest_stdout` | non-pytest runners | no, **by design** |

Both non-matches are named for what they parse. They do not match pytest output **with or
without this change**, so listing them as risks this line might break was noise — it made the
check look broader than it was.

**The check that actually matters**, run against real captured output rather than a fixture:
with the tree-state line in the stream, `(\d+)\s+passed` still returns the run's true count.
Measured on a live run of the unit runner — 10 tests, line present, parser reads `10`.

That is now **pinned by three tests** rather than argued: the line may never contain a bare
number followed by a count word (`passed`/`failed`/`error`/`skipped`/`xfailed`/`xpassed`), must
be exactly one line so it cannot straddle a line-anchored regex, and must carry no braces so
nothing hunting a JSON payload in stdout can scoop it up. Mutations that grow a
`"<n> passed"`-shaped substring, split the line, or add braces all go red.

**THE DURABLE SENTENCE** (Mr Radio's wording, adopted verbatim — it carries a guarantee mine
did not):

> The line contains no `"N passed"`, `"N failed"` or `"N error"` substring **and is never the
> last line**, so no consumer of pytest's summary can misread it.

The second clause is the one my version missed: the substring rules protect a parser that
*searches*, and the ordering clause protects one that reads the **last line**.

⚠️ **That ordering is pytest's, not this code's.** This module cannot enforce where pytest
prints its own summary, so the clause is **verified on a live run** rather than asserted from a
fixture — a fixture written in the order I expect would only prove I can write a fixture. A test
spawns pytest against a small unit file (~0.5 s), inside the repo so the root conftest actually
loads, and requires: exactly **one** tree-state line, that it is **not** the last non-empty
line, that the last line **is** pytest's count, and that the live line carries no
`"N passed/failed/error"` substring. Mutations that unwire the hook, print the line twice, or
grow a count-shaped substring all go red.

Shape rules, for whoever writes the next parser: `[tree-state]` is a single line of `key=value`
pairs and contains digits only inside `key=value`.

### 3b. Cost — **~20 ms once per run; worst-case budget 9 calls, corrected**

Measured on this tree: `rev-parse` 1 ms, `@{upstream}` 1 ms, `status --porcelain` 12 ms,
`rev-list --count` 2 ms. `pytest-xdist` is not in use, so the hook runs **once**, not per
worker. Against a 13-minute unit tier this is not measurable.

⚠️ **The call-count claim was wrong and Rio corrected it.** I described the budget as four
calls. The worst case is the **no-upstream path** — which is also the **detached-worktree**
path, the one this diagnostic most exists for.

**Two counts, both right, for two different trees**: Rio measured **7** on the code as he
audited it; it is **9** as shipped, because the audit fixes below add two probes on that same
path. Neither figure corrects the other — only mine, at 4, was wrong. Each call carries
`timeout=5`, so the worst-case wall cost is **45 s**, not 20 s, and the number is now pinned by
a test so it cannot drift silently.

### 3c. Blast radius — the real reason this file needed a worktree

`src/conftest.py` is shared by both test trees. Three properties keep a diagnostic from
becoming an outage, and each is asserted rather than intended:

- the subprocess reader returns `None` on `OSError`/`SubprocessError`/non-zero exit — it never
  raises (tested against a non-repository directory);
- the hook call is wrapped, so a probe failure prints an UNKNOWN line instead of failing a run;
- **no network**: `@{upstream}` reads the last-fetched ref. A test fails if the probe ever
  issues `fetch`/`pull`/`ls-remote`/`clone` — a probe that fetched would add network time to
  every run and could hang a suite on an unreachable remote.

### 3d. The near-miss: placement, not logic

The line had to print **before** the unit-network guard's early return. That guard's summary
returns when its mode is off — which is the **default** — so the obvious placement would have
shipped a **silent no-op as a feature**: green everywhere, line never printed on an ordinary
run. Found mid-build rather than in review, and now pinned by a test that reads the source and
compares the two positions.

**This is the one item where design-before-code would have paid.** The trap is visible from the
existing hook's shape, and naming it in a design doc costs a sentence; finding it by accident
costs a build.

## 3e. Rio's audit — three ways it could be confidently wrong

Mr Radio had Rio ⚡ audit the diagnostic. Nothing was on fire — it cannot fail a suite and did
not print a wrong sha in this tree — but all three findings were real, reproduced here before
being fixed, and all three are now in the line or the contract. Rio's write-up:
`2026.08.26-tree-state-line-can-name-the-wrong-repo.md`.

**1. The line never said which repository it measured.** `git -C <dir>` walks **up** to the
nearest ancestor repo, so a directory that is not itself a repo yields a fully confident line
about a *different* repository — no hedge, no question mark. Rio made a scratch directory nested
inside this repo and got the **main repo's sha** back. Six worktrees already live inside the
repo at `.claude/worktrees/tfe-*`, ~1,581 commits from the branch; all still hold their gitdir
pointer, so this is **one deletion away rather than live**, and no one's worktree was deleted to
prove the last step. **Fixed**: the line carries `root=<resolved toplevel>`, so a walk-up is
visible instead of silent.

**2. `behind=` had no age.** It is computed against `@{upstream}`, the last-**fetched** ref.
Staying offline is right, but a bare `behind=0` reads as "up to date" when it means "up to date
*as of whenever I last fetched*". **Fixed**: `fetched=<age>-ago`, from the mtime of `FETCH_HEAD`
in the **common** git dir. The ref's own tip age cannot answer this — an untouched ref looks
fresh forever.

  ⚠️ *And the first version of that fix was wrong in the same family as the bug it fixed*:
  `--git-path` returns a path relative to the **git process's** cwd, not this process's, so a
  real two-day-old `FETCH_HEAD` reported as `UNKNOWN` — hiding exactly the staleness it exists
  to show. Now `--path-format=absolute --git-common-dir`.

**3. `Raises: nothing` was false.** `text=True` decodes stdout, and a ref name with invalid
bytes raises `UnicodeDecodeError`, which is neither an `OSError` nor a `SubprocessError` — so it
escaped both the reader and `tree_state_line`. The caller's `except Exception` did contain it,
**but that net carries `pragma: no cover`**, so the only thing holding it up was the one line
nobody tests. **Fixed**: the reader catches it explicitly, and `tree_state_line` is now total by
construction rather than by the caller's net. A test drives it with a git that raises.

Four mutations, each red: `root=` dropped · fetch age dropped · an unreadable fetch dir reported
as fresh · total-ness removed so a raising git propagates.

## 4. Decisions worth keeping

- **The UNKNOWN case prints too**, for the reason the network guard prints its zero: an
  instrument that goes quiet when it cannot answer is indistinguishable from one that was never
  armed, and silence reads as "not behind".
- **A detached worktree falls back** to the primary worktree's branch. It has no upstream, and
  it is exactly the tree most likely to be far behind — six of this repo's eleven worktrees are
  detached and 1,578 commits back, so a fallback-free version would leave the case this exists
  for as the one case it cannot answer.
- **Three things stay separate** because collapsing any of them lies: `behind` vs `ahead`;
  `tracked-dirty` vs untracked scratch (a clean tree 88 commits back and a dirty tree at the
  tip are different claims, and both invalidate a quoted figure differently); and `dirty=?` vs
  `tracked-dirty=0`.

## 5. Proof

10 tests, driven through an **injected** git so the hostile paths — no upstream, detached, a git
that answers nothing, a ref that cannot be walked — are exercised rather than hoped about.

Seven mutations, each red: a silent UNKNOWN · an unknown distance rendered as `behind=0` ·
untracked files counted as tracked dirt · unreadable dirt reported as clean · the comparison ref
dropped from the line · the detached fallback removed · the line moved after the early return.
Green control 10.

## 5b. The lesson that cost the most: a property, not a census

Four mutations survived their first pass tonight, all for one reason — **the test was shaped by
what happened to be in the tree rather than by the rule it was supposed to state.**

- the pin's single-line arm: no *scenario* could reach it, because a supplying line's text can
  never hash to a prose line's pin. Only a direct assertion on the arm could.
- `_line_pin` stripping whitespace: nothing said whitespace was part of the text.
- the file-scope of the moved-prose lookup, and the non-`.py` and unparseable arms: **invisible,
  because the live inventory has exactly one entry and it is a `.py` file that parses.** Three
  distinct weakenings that change nothing today and change something the moment a second pin
  lands.

Each was killed by asserting against an **injected** inventory instead of the live one.

> **A number counted off today's tree is a census. A rule is a property.** A test that can only
> be as strong as today's data is not a test of the rule — it passes for as long as the tree
> happens to agree with it, and stops the moment the tree moves.

That is this row's own coverage finding restated one level up: a figure valid only at the
instant it was rendered, reported as if it were valid generally. It showed up in a coverage
report, in a guard's inventory, and in my own tests, in one evening.

⚠️ **And a mutation that misses its target is not evidence of anything.** Twice I recorded a
"survivor" that was really a mis-aimed edit — a pass that said nothing about the test. Verify
the mutation landed before believing its result.

## 6. Residual risks, named

- The probe reports the tree **at the end of the run**. A commit landing mid-run is not
  detected, so a long tier can still be a hair stale. Reporting both start and end shas would
  close it; not done, and not obviously worth the second call.
- It says nothing about **which files** moved — a tree 88 commits behind may be 88 commits
  behind in a directory the run never touched. The line is a coarse instrument on purpose.
- Non-pytest greens (the shell runners' own output, TypeScript via `c8`) are **not** covered.
  The root conftest reaches every pytest tier and nothing else.
