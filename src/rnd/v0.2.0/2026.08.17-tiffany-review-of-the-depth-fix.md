## The gap he named in MY tests — real, and closed in `895bf0e6`

Extra 1 observed that gutting the lead-in strip at **one** call site leaves my suite green, and read
that as the tests proving nothing. Half right: it is a gap in the tests, and it is **not** evidence
the two sites are redundant. They differ — but only on the **false-positive** side, which is why no
blocking test could separate them:

| lead-in + payload | full | early strip gutted |
|---|---|---|
| plain mark + a template | SERVED | SERVED |
| **space + mark + a template** | SERVED | ***BLOCK*** |
| space + mark + a real credential | BLOCK | BLOCK |

With the early strip, `json.loads` succeeds and the decision goes down the **parsed** path, where his
placeholder rule recognises a template. Without it the parse fails on the invisible character and the
decision falls to the **truncated** branch — a raw substring scan with no placeholder rule — which
sees `"client_secret"` and refuses a document. Blocking a real credential still works either way,
through the weaker path. **The early strip is what keeps the strong path reachable, and losing it is
paid for by documents, not by credentials.**

Eight arms now cover it: four invisible lead-ins × two documents that must stay served. Gut the early
strip alone and 8 go red where the suite used to stay green.

The **second** strip provably cannot fire today — the first has already stripped the same prefix by
the time control reaches it. Stated in a test docstring rather than left for the next reader. I did
not delete it: a redundant strip on a security floor is cheap, and quietly removing one mid-review is
how the original mark hole was opened.

## What his rule change costs — a real trade, measured

He replaced my "the key is present" test with "the key holds a real, non-placeholder string." That is
the right call for a depth walk: a name-only rule at depth refuses every OpenAPI spec that documents
OAuth. It also opens four shapes that blocked at my base.

| shape | `6250f245` | `57d54836` | is it a credential? |
|---|---|---|---|
| `private_key` as an **array of PEM-less lines**, no `type` | BLOCK | SERVED | **plausibly yes** — some tools store key lines as a list |
| `refresh_token` nested under its own key, no `type` | BLOCK | SERVED | **plausibly yes** — a wrapper config |
| a real secret written `"<s3cret>"`, no `type` | BLOCK | SERVED | no — a real token is not angle-wrapped |
| `private_key` present but `null` or blank | BLOCK | SERVED | no — serving that is correct |

**Every one needs `type` to be ABSENT.** Both canonical downloads — the service-account key and the
user ADC file — carry `type` and both still block, which is why this is a residual rather than a
regression in practice.

The precise gap: `_value_is_secret_material` returns False for a **list**, and the walk descends into
the list's *items*, which are strings rather than objects, so nothing ever tests them. One line closes
it — treat a credential key whose value is a list of secret-material strings as secret material. Not
applied here: the review was scoped to soundness and the residual is filed separately.
