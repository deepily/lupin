## Verdict

Measuring the v1 baseline at pinned sha `b0735467` needs its **own server on its own database**, run **outside** the shared `:8000` test path. Recommended build: **a container from the pinned sha** (the boring, faithful option), not a bare host-side uvicorn. Three constraints must be designed in — its own DB, no `:8000` contention, and a sha stamp the report reads back from the *running process* — and this note names each.

## The root cause (one line, across three layers)

> Code that resolves a path at runtime does not know which tree it was meant to measure, and every wrong answer arrives as a plausible number rather than an error.

That is why it survived three layers of care. The fix differs at each level; the failure never does:

| Layer | Where it bit | Date |
|---|---|---|
| subprocess | Mr Radio's row `43fca908` — a subprocess resolved config through the wrong tree | 2026-08-14 |
| worktree tests | subprocess tests false-RED off the dirty main tree without `LUPIN_ROOT` (auto-memory `reference_worktree_testing_needs_lupin_root_override`) | (standing) |
| container mount | the `:8000` container mounts the MAIN tree, so a scheduled test-suite job measures TODAY's code and labels it `b0735467` | 2026-08-15 (this note) |

Record it as **one root cause**, not three incidents.

## Why NOT a `:8000` test-suite job (the deciding snag)

`docker-compose.yml`: the `:8000` (testing) service mounts the main working tree at `/var/lupin` and maps host `8000 → container 7999`. A job submitted via `POST /api/test-suite/submit` therefore runs **today's main-tree code**, not the pinned worktree. The eval would stamp the report with pin sha `b0735467` (a constant in the instrument) while the server it measured is a different tree entirely — a **false baseline that looks perfectly valid in the report**. This is the deciding factor: do not route the v1 baseline run through `:8000`.

## The two build options

### Option 1 — container from the pinned sha  ✅ RECOMMENDED ("the boring one")

Build a throwaway image from a checkout at `b0735467`, run it as its own service with its own DB and its own host port; point the eval's `--base-url` at it.

- **Faithful**: the app is Docker-native; the run script hardcodes `cd /var/lupin/src`, so a container is the environment the code expects — no host-path fights.
- **Tamper-evident sha**: bake `git rev-parse HEAD` into the image at build time (env var + a file the running process serves), so the stamp travels with the running code.
- **Cost**: one image build + a compose-override service. Bounded and disposable.

### Option 2 — bare host-side uvicorn from the worktree  (fallback only)

Run `python3 -m lupin_app.main` from the worktree host-side with `LUPIN_ROOT`→worktree, `DB_HOST=localhost`, an ephemeral port.

- **Viable**: verified host `fastapi`/`uvicorn` import, pg `5432` published, `lupin_db_test` reachable.
- **Fragile**: the run script's `cd /var/lupin/src` is container-pathed; host venv drift; every env var must be wired by hand — exactly the runtime-path-resolution surface the root cause lives on.

**Take Option 1.** Option 2 is documented only as the fallback if the image build proves impractical.

## Constraint A — its own database (never touch the `:8000` test DB)

The instrument's cold-start step `truncate_snapshots(connection)` is **destructive** (`TRUNCATE solution_snapshots`) and its guard `assert_test_db` today permits exactly one target: the marker `lupin_db_test`. Two facts collide:

1. If the v1 baseline server uses `lupin_db_test`, its cold-truncation can **wipe snapshots out from under a live `:8000` run** — the collision Cheech flagged as destructive.
2. If it uses its **own** DB (e.g. `lupin_db_v1baseline`), the current guard **refuses to truncate it** (marker mismatch → `EvalIntegrityError`), so the cold pass can't be made cold.

**Design decision required in the build step**: the v1 baseline server gets its **own** database, AND `assert_test_db` is generalized from a single hard-coded marker to an **allow-list of measurement DBs** (`lupin_db_test`, `lupin_db_v1baseline`) that **still refuses dev/prod/unparented targets**. Widening the guard must not weaken it — the refusal of `lupin_db_dev`, prod, and any unparented url stays. (This is a change to `v1_eval_arm.py`, my lane; scoped here, not made tonight.)

## Constraint B — no contention with a live `:8000` run

Two runs on the same box competing for the same Max-plan rolling window would throttle each other and Rick's interactive work.

- **Separate server, separate DB** removes the data collision; scheduling removes the compute collision.
- The run stays **off-peak (12 AM–9 AM EDT)** per the Max-plan batch rule, and is placed so it does **not overlap** an already-scheduled `:8000` job (check `list-pending` first; a v1-baseline run and a `:8000` suite must not share the window).
- A container-from-sha (Option 1) is isolated by construction; a bare host server (Option 2) shares the host venv and needs manual care not to disturb the containers.

## Constraint C — why this is NOT the banned side-door injection

The standing rule bans injecting `:8000` test work via any path other than `POST /api/test-suite/submit` (ad-hoc curl / direct `/api/push` / in-process instantiation), because a side-door **collides with in-flight scheduled `:8000` runs and poisons both**.

This design does **not** inject into `:8000` at all. It stands up a **separate server** (own port, own DB, own tree) and measures *that*. There is no shared queue to collide with and no scheduled `:8000` run to poison — the two servers never touch. The prohibition targets injection into the shared test path; a distinct server is a different thing. (Written down rather than assumed, per Cheech.)

## The stamp — read the sha back from the RUNNING process

The report must record which tree and sha it **actually measured**, never which one the launcher intended. Read it from the live server, not from launcher config/env:

- **Option 1 (container)**: the sha is baked into the image at build (`git rev-parse HEAD` → env + served file); the eval reads it back from the running container before the run and asserts it equals `b0735467`. A mismatch fails the run loudly.
- **Option 2 (bare host)**: resolve the process's *actual* code location — `/proc/<pid>/cwd` and the loaded `lupin_app` module file path — then `git -C <that path> rev-parse HEAD`; cross-check `/proc/<pid>/environ` `LUPIN_ROOT`. This asks the process what it booted from, not the launcher.

Either way: **the stamp is an assertion, not a label.** If the running server's sha ≠ `b0735467`, the run raises rather than printing a plausible-but-false baseline — the direct countermeasure to the root cause above.
