## Part 1 — Flash-Lite on the GCP VM

The VM's app runs under config block `Lupin:+Testing-GCS`
(`docker-compose.cloud-gpu.yml:185`, `docker-compose.cloud-test.yml:111`), and that block
`inherits = Lupin: Development` (`src/conf/lupin-app.ini:645`), where the arm is written. So **no
second entry was minted** — the VM and the local runs read the same two lines, as the row required.

Two things had to be fixed before it could actually run there:

| What was wrong | Evidence | Fix |
|---|---|---|
| The VM checkout was 20-odd commits behind and had **no `flash_lite` key at all** | VM at `af406cc9c`; `grep flash_lite src/conf/lupin-app.ini` on the VM returned nothing | `lupin-vm.sh push-bundle <branch> --checkout` |
| Nothing on the VM supplies `LUPIN_GCP_PROJECT_ID`, so **every** Vertex client raised at construction | `RuntimeError: LUPIN_GCP_PROJECT_ID is not set and could not be read from /var/lupin/src/scripts/cloud-run.env` — raised inside `lupin-rest-cloud-gpu` | shipped `src/scripts/cloud-run.env` and added the manifest row that says it must be there |

The second one is the interesting half. `src/conf/env-contract.tsv:62` declares
`LUPIN_GCP_PROJECT_ID` as a **HOST** variable — "required by lupin-vm.sh for every gcloud call" —
so nobody had ever asked the question the app asks: who gives it to the *container*? Nothing did.
`resolve_gcp_project_id()` falls back to `$LUPIN_ROOT/src/scripts/cloud-run.env`, which is
gitignored and so had never reached the VM. The manifest at
`src/conf/vm-unversioned-manifest.tsv` exists for exactly this category, and now carries the row,
which means `preflight-vm.sh` check B3 blocks on its absence instead of a future session
rediscovering it by failing.

**The proof, run inside the deployed container** (`sudo docker exec lupin-rest-cloud-gpu`, whose
own env is `config_block_id=Lupin:+Testing-GCS`):

```
CLIENT:     GeminiVertexClient gemini-3.1-flash-lite global hello-world-foo-423219
GEN_KWARGS: {'temperature': 0.0, 'max_output_tokens': 4096, 'seed': 20260817}
LIVE:       'OK'
```

That is a real Vertex round trip from the VM, not a config read.

### What that proof does and does not cover

**The seed is proven AVAILABLE on the VM, not proven IN EFFECT for served traffic.**

The call above ran as a **new** process (`docker exec … python`). The container bind-mounts
`/mnt/lupin-data/lupin/src` → `/var/lupin/src`, so a freshly started process there imports the new
code — the seed mapping is present at `/var/lupin/src/cosa/agents/gemini_vertex_client.py:64`
inside the container, read there directly.

The **running web service** is a different matter. Reload is off on the VM and nobody bounced that
container, so the long-running uvicorn process still holds pre-seed code in memory. **A request
handled by the serving process is not seeded until that container is bounced.**

Anyone quoting "proven running on the VM" without this section will believe served requests are
seeded. They are not.

## Part 2 — temperature and seed

### Temperature: 0.0, and it arrives

- Value: `src/conf/lupin-app.ini:224` — `{ "temperature": 0.0, "max_tokens": 4096, "seed": 20260817 }`
- Path to the call: `llm_client_factory.py:254-257` hands the dict to `GeminiVertexClient`, which
  maps INI names to SDK names (`_translate_generation_params`) and builds a
  `GenerateContentConfig` (`_build_gen_config`) that is passed into `generate_content` at
  `gemini_vertex_client.py:191` (sync) and `:205` (async).
- History: commit `643d16da` created the arm at `0.0` and it has never held another value.

### Seed: there was none, and the client would have rejected one

`GeminiVertexClient._GEN_KEY_MAP` listed `temperature`, `max_tokens`, `top_p`, `top_k` and nothing
else, and any other key raises. So the failure was not "somebody forgot to set the seed" — writing
one into the INI would have **broken the arm**:

```
ValueError: GeminiVertexClient: unknown generation param 'seed'
            (known knobs: ['max_tokens', 'temperature', 'top_k', 'top_p']; ...)
```

Why it matters: `temperature 0.0` is not the same thing as reproducible. With no seed the backend
picks one per request, so the same prompt can come back worded differently. `GenerateContentConfig`
carries a real `seed` field (google-genai 1.73.1), so the mapping is 1:1 —
`gemini_vertex_client.py:64`.

Value chosen: **20260817**, the same number the study already records for its corpus draw, so the
write-up carries one seed rather than two.

**Consequence for the study**: every Flash-Lite number produced before this commit came off an
unseeded arm. That does not invalidate the counts — the guard-refusal comparison does not rest on
byte-identical regeneration — but it does mean re-running an old row is not expected to reproduce
its old text, and nobody should treat a difference as a finding.

**Still unseeded**: the `phi_4` arm. Only Flash-Lite is pinned right now.
