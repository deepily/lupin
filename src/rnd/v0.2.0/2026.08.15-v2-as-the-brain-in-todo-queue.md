## 3. Why reuse the queues — and why my own objection collapsed

I initially flagged a tension: `executor.py` says `Work.job` is duck-typed on purpose because *"this module imports no agent or snapshot class, which is exactly the machinery v2 exists to shed."* I read that as *reuse drags that machinery back in.*

**It does not. Measured:**

`fifo_queue.py` imports `collections` · `datetime` · `typing` · `re` · `threading` · `queue_extensions.user_job_tracker` · `queue_protocol.is_queueable_job` · `job_state.JobState` · the notification models. **No agent class. No snapshot class.**

It touches a job through **four attributes**: `id_hash` · `state` · `artifacts` · `user_email`, behind an explicit `is_queueable_job` predicate. *(An earlier draft of this section said "six attributes" and listed `name` among them. Wrong twice: it is four, and `job.name` is never read — the only `.name` hits in the file are `self.name` in a stub and `retrieved_item.name` in a test.)*

⇒ **The PUSH side is already duck-typed on jobs — the same constraint v2 adopted for its own executor.** The machinery v2 exists to shed and the machinery the *push* requires were never the same thing.

### 🔴 3.1 But the RUN side is not duck-typed, and the distinction is the whole design — Clayton's crew, 2026-08-15

This is my §8 claim 2 (*"the queue is already duck-typed, so reuse is free"*) coming back with the 2,245 lines I admitted I had not read. **The claim survives for `fifo_queue.py` and fails for `running_fifo_queue.py`**, which reaches a job through **31 distinct members** — 16 on the plain `job` receiver, 29 on `running_job`, 31 in the union. Measured with a negative lookbehind so `running_job.` cannot match the plain receiver; the second receiver is the one my own first grep missed entirely.

> **The count took three tries between two people, which is worth recording.** My first pass said 16 (searched one receiver). Clayton's said 31 but by accident — his `job\.` matched *inside* `running_job.`, conflating the two. His re-measure with a boundary said 30. The residual one is **case**: `JOB_TYPE` (class constant, `:1327`) and `job_type` (instance attribute, `:1364`, `:1425`, `:1632`, `:1715`) are both live and distinct, and a case-folding pass merges them. `:837` uses both in a single expression — `getattr( job, "JOB_TYPE", job.job_type )`. **That fallback is the run contract leaking in miniature**: a job missing the constant silently falls back to the attribute, so neither is required and nothing declares either.

| what it demands | examples |
|---|---|
| **four METHODS** — a behavioural contract, not a data one | `run_code()` · `run_formatter()` · `update_runtime_stats()` · `set_solution_summary_gist()` |
| a wide **data** surface | `answer` · `answer_conversational` · `thoughts` · `solution_summary(_gist)` · `runtime_stats` · `code_ran_to_completion` · `formatter_ran_to_completion` · `is_cache_hit` · `routing_command` · … |
| a **private attribute written from outside the class** | `job._brake_terminal_claimed` — read at `:756`, written at `:758` and `:781` |

⇒ **Two contracts, and only one of them is cheap.** *Getting into* the queue costs four attributes. *Being run by* the queue costs four methods, ~26 fields, and tolerating an outside write to a private name.

**What this changes in the design**: nothing about §4 — the queue prepares the job, so the brain never has to satisfy the run-side contract. But it hard-bounds the fourth `Work.kind` of §4.1: when v2 says *"queue it,"* what it hands back must become a **real job object implementing the run-side contract**, and that is a job-class concern, not something the brain can synthesise. Anyone reading §3 as "the queue takes anything job-shaped" would design straight into that wall.

**And the private-attribute write is a latent defect regardless of this plan** — `_brake_terminal_claimed` is part of the run-side contract in practice while being spelled as private, so any new job class must set it and no interface says so. Worth its own row; not this plan's to fix.

**And the alternative costs ~4,739 lines** (`running_fifo_queue` 2,245 · `todo_fifo_queue` 1,495 · `fifo_queue` 999) that already carry websocket emission, focus mode, an accepting-jobs gate, scheduled-at ordering with predicates, per-user job lists, id-hash lookup and delete, change detection, and the notification wiring the CJ Flow cards render from. **Rebuilding it is the second registry problem** — a parallel system that starts identical and drifts — one day after the fleet spent a day undoing the first.

## 4. The design: v2 decides, the queue prepares

Pre-queuing does two separable things, and the seam between them is clean because one side is **judgement** and the other is **mechanism**.

| **DECIDING → moves to `AskFlow`** | **PREPARING → stays in `todo_fifo_queue`** |
|---|---|
| what did the user mean | mint the speculative job id (card on screen *during* the interview) |
| which agent handles it | register / remove with `user_job_tracker` |
| which arguments it needs | `emit_job_state_transition` (QUEUED→CANCELLED, →FAILED) |
| are they all present | pop `scheduled_at` / `monopolize`, with voice-path normalization |
| what to ask when one is missing | `create_agentic_job`, then push |
| the `else` that web-searches an unroutable question | the cache-replay execution |

### 4.1 The call

`todo_fifo_queue` hands `AskFlow` a question and a user, and receives **an outcome plus a filled argument dictionary**:

| outcome | what the queue does |
|---|---|
| `agent` | arguments complete → pop scheduling args, build the job, push. **Exactly as today.** |
| `needs_input` | v2 supplies **the question to ask** → queue asks, parks, keeps the card alive. **Exactly as today.** |
| `replay` | cache hit → answer without building a job |
| `receptionist` | intent unascertainable → route to receptionist, with a *reason* instead of a fall-through |

### 4.2 ~~Why it fits rather than being forced~~ — 🔴 **FALSE. v2's `needs_input` has no second half.**

> **What this section claimed**: *"Both halves already do the same thing when an argument is missing: ask one question and park… These are not two designs to reconcile — they are the same design, one of them tidier."*
>
> **This was my named weakest claim (§8 claim 1), and it is worse than I feared.** I guessed the two interviews might *differ* on re-asking, timeout or partial answers. Clayton's crew found there is nothing to differ **with**: v2 parks a request and hands back a handle **that nothing ever picks up.**

**Measured — the whole external surface of the pending store is one call:**

| `PendingStore` method | external callers |
|---|---|
| `put()` | **1** — `flow.py:210` |
| `get()` | **0** |
| `set_status()` | **0** |
| `__contains__` / `sweep()` | **0** |

And `pending_id` is written into the API response at `v2_ask.py:54` — *"Parked-request id when interactive + needs_input"* — then **read back by nobody**. There is no endpoint anywhere that accepts a `pending_id` to resume. `grep` over `src/cosa` and `src/lupin_app` returns only the write path.

⇒ **v2's interview is a one-way door**: it can ask the question and it cannot receive the answer. v1's head, by contrast, mints a speculative job id, puts a card on screen, and carries the conversation to a second turn over the websocket. **These are not the same design with different tidiness — one of them has half a mechanism.**

### 4.2a What that changes

**It strengthens option (b), which was already my lean.** If v2 cannot complete an interview, then a design where v2 *replaces* the head end (option (a)) must **build** the second turn before anything ships — a substantially larger piece of work than "wire the brain in." Under (b), the queue's head keeps owning the interview it already completes, and v2 supplies routing and argument resolution. **The missing half is a reason to keep the interview where it works, not a bug to fix in passing.**

⚠️ **And the parked entries are litter**: every `needs_input` outcome writes a `PendingEntry` that no code path will ever read, status, or resolve. `sweep()` exists and has no caller. Whoever wires v2 in should decide deliberately whether `put()` should be called at all until a resume path exists — writing state nobody reads is how a store becomes a graveyard nobody trusts.

**Worse: the store's own docstring claims a property the code cannot deliver** (Clayton, verified by me). `pending.py:1-20` states two properties *"enforced here rather than left to callers"*, and the first is:

> *"**Bounded growth.** An in-process dict that only ever grows leaks memory across a long eval run, so every entry carries a creation time and `sweep()` (and every `get()`) drops entries older than the TTL."*

**Both enforcement points are unreachable.** `get()` and `sweep()` have zero external callers; `put()` — the only reachable entry point — never evicts. So `ttl_seconds=3600.0` is configured, documented, and **cannot fire**: the dict only grows, for the lifetime of the process, exactly as the docstring warns.

The same docstring describes *"the resume thread [advancing] status pending → running → done/failed."* **There is no resume thread.** It describes a design that was never wired.

⇒ **Third instance today of the same disease** — the stale `:709` NOTE, the `test_bucket_counts` tautology, and now a module docstring asserting an invariant delegated to functions nobody calls. **Prose cannot fail.** A `len(store)` assertion after a TTL-expired `put()` would have gone red on day one.

**Bounding the claim honestly**: this leaks only while `/api/v2/ask` is taking traffic, since `flow.py:210` is its only writer. Today that endpoint is not on a user path, so nothing is leaking in production *right now* — **but wiring v2 in is precisely what starts it**, which puts this on the critical path of this plan rather than beside it.

### 🔴 4.2b Why none of this showed up as a failure: coverage measures EXECUTION, not REACHABILITY

**The callerless functions are fully unit-tested and green.** Measured in `test_v2_executor_seam.py` (36 tests):

| pending method | test calls | production callers |
|---|---|---|
| `put()` | 9 | **1** |
| `get()` | 10 | **0** |
| `set_status()` | 4 | **0** |
| `sweep()` | 1 | **0** |

⇒ **The tests are the only callers.** A function whose sole caller is its own test is **100% covered and 0% reachable** — and coverage reports the first number, which is the one everybody looks at. Green coverage on `pending.py` is exactly what *hid* the missing second half: the resume path was tested into existence without ever being connected.

**This is the finding to carry past this plan — but it covers ONE class of defect, not all of them.** My first draft of this section said *"every defect found today was invisible to a green suite."* **Too broad, and Clayton was right to narrow it.** Today's findings split cleanly into three kinds with three different remedies, and conflating them would send the fix to the wrong place:

| class | example | why the suite stayed green | the remedy |
|---|---|---|---|
| **1 · Reachability** | no second turn · TTL cannot fire | **No ordinary test catches this.** The unit works; a test of the unit passes. Nobody asks *"does anything call it?"* — coverage can't express the question | a **reachability assertion**: the lifecycle must have a caller outside its own tests |
| **2 · Ordinary defect, bad test** | `started_at` | **A competent test WOULD have caught it.** The fixture hard-assigned the value under test, so the failing input was unreachable through the fixture's own API | fixture discipline: make the failing input **expressible**, then **prove the test can go red** |
| **3 · Documentation** | the stale `:709` NOTE | Not a code defect at all — no behaviour test can catch a false comment | assert the property the prose claims, or delete the prose |

⇒ **Class 2 is not a limit of testing; it is a testing failure**, and saying otherwise excuses it. The distinction matters because only class 1 needs a new instrument — classes 2 and 3 need the discipline this fleet already has, applied.

⇒ **For class 1 specifically**: a reachability assertion is a different instrument from a coverage number, and this codebase has the second without the first. The §5.1 test — *for every emittable command, exactly one module can produce a job* — is that instrument for routing. `pending.py` needs the same shape: **assert that the parked-request lifecycle has a caller outside its own tests**, or delete the half that does not.

### 4.3 What this shape avoids

**v2 never learns card lifecycle** — no speculative ids, no state transitions, no tracker. That is genuinely the machinery v2 was built to shed.

**And no fourth `Work.kind` or fifth branch is needed yet.** v2 does not queue anything; it *tells the queue what to queue*. That question moves to a later phase, if and when v2 owns the head end outright.

## 5. Definitive — for deciding, not for handling

The brain becomes the single answer to *"what did the user want and can we proceed"*. It is **not** the single answer to *"how does an agentic job get built, queued, run and reported"* — that stays with the queue and the job classes. A brain that also built and ran jobs would be the monolith v2 exists to replace, wearing a new name.

### 🔴 5.1 "Definitive" is a property to ENFORCE, not to assume

There are two entry points today — `POST /api/v2/ask` and the voice/websocket path through `todo_fifo_queue`. Under this design **both call the same brain**, which is correct. But the four-list drift happened *because nothing checked that the lists agreed.*

**Required**: a test asserting there is exactly one routing path. Dead code that still compiles is a road back. A convention is what produced the four lists; this needs to be a check.

> 🔴 **The test as I first specified it was the weak version — Clayton, 2026-08-15.** I wrote *"assert the three named if/elif chains are deleted rather than merely unused."* That is a **source-shape assertion**: it greps for `elif`, or counts branches, and so matches a *description* of the defect rather than the defect. It passes the day someone reformats the chain into a dict, a match statement, or a helper — none of which removes the second routing path.
>
> **The falsifiable version asserts REACHABILITY, not shape**: *for every command in the router template's emittable set, **exactly one** module is capable of producing an agent or a job for it.* Two producers is the defect, zero is an unreachable command, one is the invariant.
>
> **What makes it go red**: reintroduce any second producer, in any syntax, and the count for that command becomes 2. **Shape-blind by construction** — which is the property the shape assertion lacked.
>
> ⇒ Third time today a check of mine matched the description of a problem rather than the problem. Worth stating as the rule this section is really about: **assert what must be TRUE of the system, never what the source must LOOK LIKE.**

## 6. Switchover — RULED: shadow mode, then per-command flip

> **RULED BY RICK, 2026-08-15, live.** Option (b) below. The recommended sequence at the end of this section is the plan of record. What follows is the reasoning that produced it, kept because the rejected option was cheap and defensible and a later reader should know it was considered rather than missed.

**Rick's initial proposal**: stop accepting agentic / long-running jobs until the build and switchover complete.

**It is defensible and it is cheap to implement** — `is_accepting_jobs()` already exists on `FifoQueue` (`:125`), alongside `is_in_focus_mode()`. No new machinery.

**My recommendation is against it, for one reason above the others**: a freeze costs the only cheap way to catch a routing regression. The way to know the brain decides identically is to watch it decide on real questions *before* it is in charge. **Under a freeze, switchover day is also the first day anyone finds out.**

Two further objections, weaker but real: *"until we finish"* is not a date, and un-freezing is a decision somebody must own under pressure — the fleet cleared a ten-day-stale hold yesterday. And it makes the change with the least evidence behind it go live to everything at once.

### The three options

| | approach | for | against |
|---|---|---|---|
| **(a)** | **Freeze** until switchover | simplest to describe; nobody hits a half-migrated path; no dual maintenance | loses the comparison; no natural end; biggest bang with the least evidence |
| **(b)** ⭐ | **Shadow mode** — call the brain on every request, **log what it would have decided, route on v1 anyway** | costs one extra call; after a day of real traffic you have an agreement table, and **every disagreement is either a v1 bug or a v2 bug** — both worth knowing before flipping | both paths exist for a few days; somebody must read the log |
| **(c)** | **Flag-flip with rollback** — `v2 flow enabled` already exists | simpler than (b) | you learn from failures in production rather than disagreements in a log |

### Recommended sequence

1. **Shadow mode through the build.** Brain decides, v1 routes, disagreements logged.
2. **Flip per-command, conversational first, agentic last.** The blast radius grows one command at a time.
3. **Freeze only during the factory swap** (the phase-5 dispatch replacement) — the single riskiest step. **Hours, bounded, with a stated un-freeze condition**, not open-ended.
4. **Delete the three if/elif chains**, and land the one-routing-path test in the same commit.

### What decided it

Not the cost — the freeze was cheaper. **What decided it is the shape of a routing failure here.**

None of today's routing defects crash. A question gets **web-searched** instead of routed; an agent runs a full argument interview and then **cannot build a job**; two agents are **unreachable by voice entirely**. All three look like the system working.

⇒ **A wrong answer delivered confidently is the failure mode of this change**, and that is precisely the kind you do not notice in production but do notice in a disagreement log. The freeze optimizes against breakage; the risk here is not breakage.

### 🟢 SUPERSEDED BY A BETTER REMEDY — Krishna, verified by me, 2026-08-15

**Compare the RESOLVED ROUTING DECISION — the resolved bucket and agent choice, plus the extracted args — not the terminal outcome, and never the emitted command.** Then the 100%-disagreement below dissolves: it was an artifact of comparing outcomes that differ *by design* (queued job vs. answer), not evidence that the two arms decide differently. **The agentic lane becomes measurable today — no fourth `Work.kind` first, no conversational-only relabel.**

> 🔴 **"Resolved routing decision," never "emitted command" — and the distinction is the whole remedy, not a caveat on it.** (Clayton, sharpening a bound I had written too weakly.) v1's `_get_routing_command` (`:993`) is a **thin shim** over the module-level `get_routing_command` (`:104`), and v2's `RouterClient` imports **that same function**. So comparing emitted commands compares one function against itself: guaranteed agreement, zero signal — **a check that reads its own source.** That is the third tautology caught in my documents in two days, and the same shape as the other two: a property the implementation had already made unbreakable.
>
> ⇒ **The comparison must sit DOWNSTREAM of the shared seam** — what each side *does* with the shared command: which bucket it resolves to, which agent it picks, which args it extracts. **That is precisely where the four-list drift lives**, so the remedy is aimed at the defect rather than around it.

**Verified in the tree by me, not taken on the relay:**
- `AGENTIC_AGENTS` holds **10** commands; `DEFERRED_COMMANDS` holds **7**. They are not the same set, and I had been treating them as one.
- **`AGENTIC_AGENTS ∩ (v2 non-deferred) = ∅`.** So the 100% figure below is *exact*, not approximate.
