## 1. Goal & done-state

Replace LanceDB as Lupin's vector store with **PostgreSQL + the `pgvector` extension**, hosted on the
**Postgres instance Lupin already runs** for relational data. "Done" =

- All 6 LanceDB-backed tables serve their reads/writes from Postgres via a repository layer that mirrors the
  existing `src/cosa/rest/db/repositories/*` pattern.
- Similarity search returns results equivalent (same metric, same top-k semantics) to the LanceDB path.
- The LanceDB dependency, its on-disk store, and its config keys are removed after a soak window.
- 100 % line/branch/function coverage on all new/changed code (CLAUDE.md §100 % COVERAGE MANDATE).
- A documented cutover + rollback procedure; no in-app "migration code" beyond a one-time offline backfill
  utility (per the no-backward-compat-migration-code doctrine — drop+recreate the caches).

## 2. Why this is cheaper than it looks — Postgres is already here

The 2026-06-26 ruling reads like "stand up a new database," but it is **not**. Lupin already depends on
Postgres for auth, tasks, jobs, FCM, prediction logs, refresh tokens, audit logs — a complete DAO layer:

- `src/cosa/rest/db/database.py` — engine/session factory.
- `src/cosa/rest/postgres_models.py` — SQLAlchemy models.
- `src/cosa/rest/db/repositories/` — `user_repository.py`, `task_repository.py`, `prediction_log_repository.py`,
  `refresh_token_repository.py`, `fcm_token_repository.py`, `auth_audit_log_repository.py`,
  `email_verification_token_repository.py`, `failed_login_attempt_repository.py`.
- `src/cosa/rest/db/auto_migrate.py` + alembic — schema bootstrap/migration.

**Implication**: the migration is *additive* — enable `CREATE EXTENSION vector` on the existing DB, add vector
tables + repositories alongside the relational ones, and reuse the existing engine/session/migration machinery.
No new server, no new connection-pool story, no new deploy target. This materially de-risks the arc.

## 4. Target architecture

### 4.1 Schema mapping (LanceDB → Postgres)

Each `pa.list_(pa.float32(), 768)` column → `vector(768)`. String columns → `text`. Example for the keystone:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE input_and_output (
    id                      bigserial PRIMARY KEY,
    date                    text,
    time                    text,
    input_type              text,
    input                   text,
    input_embedding         vector(768),
    output_raw              text,
    output_final            text,
    output_final_embedding  vector(768)
    -- (remaining columns per the live LanceDB schema — full inventory is a Phase-1 task)
);
```

### 4.2 Index strategy — per-column, gated on "is it ANN-searched?" (Pass-1 F2 correction)

**Pass-1 verified that only ONE of the 9 vector columns is ever ANN-searched** —
`input_and_output.input_embedding` (`input_and_output_table.py:302`: `search(embedding,
vector_column_name="input_embedding")`). The other 8 are KV / exact-match / telemetry:
`question_embeddings` and `canonical_synonyms` do scalar exact-match lookups (`.search().where(question=)` /
pandas exact-match — explicitly commented "NOT search().where() which requires vector",
`canonical_synonyms_table.py:322/371/420`); `embedding_cache` is get-by-text; `query_log` is write-only
telemetry. So **HNSW-on-everything is over-broad** — it self-inflicts the §11 build-memory risk AND fails to
give the cache lookups the scalar/btree indexes they actually need.

**Per-column rule:**
- `input_and_output.input_embedding` → **HNSW** (the only true ANN target).
- KV / exact-match scalar keys (`question`, `normalized_text`) → **btree** scalar index, NO vector index.
- write-only telemetry vectors (`query_log.*`, and `output_final_embedding` if confirmed unsearched) → **no
  index** until a real ANN consumer appears.

**Metric — `dot`, not cosine (Pass-1 F1 correction).** LanceDB's live search uses **`.metric("dot")`**
(`input_and_output_table.py:303`; `lancedb_solution_manager.py:1382/1503/1625`), NOT cosine. This is **safe to
serve with cosine because embeddings are L2-normalized** (`local_embedding_engine.py:402`: `F.normalize(p=2)`) →
on unit vectors dot ≡ cosine. So the pgvector operator is defensible, but the design MUST: (a) state the
**L2-normalization invariant** as load-bearing; (b) **verify the OpenAI embedding path also normalizes** (if not,
normalize at write); (c) prefer pgvector **inner-product `<#>` / `vector_ip_ops`** to mirror the live `dot`
exactly (or cosine `<=>` only with the normalization invariant asserted); (d) make the equivalence harness (§7)
compare against **dot**, not cosine.

### 4.3 Repository layer

Add per-table repositories under `src/cosa/rest/db/repositories/` (or a `memory/` sub-package) mirroring the
existing pattern — e.g. `solution_snapshot_repository.py`, `embedding_cache_repository.py`. Each exposes the
methods its current LanceDB table class exposes (`add_embedding`, `get_embedding`, `search`/`nearest`, …) so the
callers in `cosa/memory/*` and the two consumers swap their storage backend without changing call sites where
possible. **One descriptive name everywhere** (no shim/alias layer) — rename globally if a method name changes.

### 4.4 Config + splainer

- New keys in `lupin-app.ini [Lupin: Baseline]` + matching `-splainer.ini`: `vector store backend`
  (`lancedb` | `postgres`, see §6 cutover flag), `vector index type` (`hnsw`), `vector index m` / `ef_construction`
  (HNSW params), reuse of the existing Postgres connection keys.
- Remove the LanceDB path keys at end-of-soak (not before).

## 5. Data handling — backfill vs fresh-start (per-table)

Doctrine: *no backward-compat migration code; drop+recreate for local stores* (Rick, auto-memory
`feedback_no_migration_code`). Applied per-table by durability:

| Table | Nature | Recommendation |
|---|---|---|
| `embedding_cache`, `gist_cache`, `question_embeddings`, `canonical_synonyms`, `query_log` | **caches** — repopulate on demand | **fresh-start** (create empty; no backfill code) |
| `input_and_output` | solution-snapshot store, 176,877 rows of accumulated value | **one-time OFFLINE backfill utility** (export LanceDB → bulk `COPY`/insert into Postgres), run once at cutover — NOT in-app migration code. Or fresh-start if Rick rules the cache rebuilds acceptably. **(Open question Q1.)** |

A fresh-start for `input_and_output` would lose the cached solution snapshots (they rebuild as queries re-run);
given Rick abandoned the 88 GB store without ceremony, fresh-start may be acceptable — but it is **his call**.

## 6. Cutover + rollback

- **Migration-window flag** `vector store backend = lancedb|postgres` (default `lancedb` until cutover). The
  `cosa/memory/*` classes dispatch on it. This preserves the old path during the soak per
  `feedback_feature_flag_preserves_old_path` — but note Rick is **abandoning** LanceDB, so the flag + LanceDB
  path are **removed after a clean soak**, not kept forever (surface as Q4).
- **Rollback**: flip the flag back to `lancedb` (the on-disk store is untouched until end-of-soak deletion).
- **Cutover steps**: enable `vector` extension → create tables + HNSW indexes (alembic migration) → (optional)
  run the offline backfill → flip flag to `postgres` on a watched run → soak → remove LanceDB path + keys + dep
  + on-disk store.

- **Integration** (:8000 scheduled): end-to-end solution-snapshot flow (input → embed → store → nearest-neighbor

- **Smoke**: `quick_smoke_test()` in each new repo module.
- **Equivalence harness**: a one-off comparison proving Postgres nearest-k matches LanceDB nearest-k on a fixed

### 9.1 Lane C batch 3b — `lancedb_solution_manager.py` postgres cache-BYPASS (RIDER-2, soak implication)

The postgres branch of `LanceDBSolutionManager` (activated by `vector store backend = postgres`)
**DELIBERATELY BYPASSES** the in-memory `_question_lookup` / `_id_lookup` caches that the LanceDB path
builds at `initialize()` / `reload()` via a full-table scan. In postgres mode:

- `_pg_initialize()` sets the initialized flag and builds **no** caches; `_pg_reload()` is a no-op.
- Every `get_snapshot_by_id` / `get_snapshots_by_question` / similarity call queries pgvector (HNSW dot)
  **directly, per call** — there is no read-through cache.
- `save_snapshot` resolves the dedup / Session-108 base-hash by a **verbatim-question query** against the
  table (not the cache), preserving LanceDB's dedup + base-hash-override semantics cache-free.

**Trade-off (NOT a surprise at soak)**: this leans on HNSW query latency where the LanceDB path leaned on
in-memory exact-match hits on the hot cache-hit path. A latency regression on repeated identical questions
at soak is an **expected** consequence of this design, not a defect — the remedy, if soak shows it, is to
re-introduce a bounded read-through cache in postgres mode (a follow-up, deferred until measured). **Caller-visible
cache-hit SEMANTICS** (same question → same snapshot returned, ~100% via the Level-4 dot tier) are preserved and
proven by the RIDER-1 equivalence harness `src/cosa/tests/unit/rest/db/repositories/test_solution_manager_pg_equivalence.py`
(real pgvector: caches stay empty end-to-end while the same question round-trips the same snapshot).

## 11. Risks

- **Metric mismatch**: if LanceDB search uses L2 not cosine, swapping to cosine silently changes neighbors —
  the equivalence harness (§7) is the guard.
- **HNSW build memory** on `input_and_output` at full backfill — build the index *after* bulk load, tune
  `maintenance_work_mem`.
- **Dim drift**: a production table actually at 1536 would break `vector(768)` — P0 inventory must verify.
- **pgvector availability — ✅ CONFIRMED GAP (verified 2026-06-30)**: `docker-compose.yml:6` runs the **stock
  `postgres:16.3-alpine` image, which does NOT bundle pgvector** — `CREATE EXTENSION vector` fails today. **P1 hard
  prerequisite**: swap the base image to **`pgvector/pgvector:pg16`** (Debian-based; the existing data volume at
  `lupin-data/postgresql-dev-data` is compatible — same PG major 16). **Cloud-SQL for PostgreSQL supports pgvector
  natively** (just `CREATE EXTENSION`), so `docker-compose.cloud-test.yml` / prod need no image change — only the
  local/dev+test compose. NOTE: an image change requires `docker compose up -d --force-recreate` (not `restart`),
  same caveat the preflight-test-container check guards.
