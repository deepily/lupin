## 1. What happened — the pilot stopped, it did not run thin

`src/conf/dm-experiment-schedule.json` declared **28 slots covering Tuesday 2026-08-04 and
Wednesday 2026-08-05 only** (`generate_schedule.py` pinned `TUESDAY_DATE` / `WEDNESDAY_DATE`
as module constants). The last slot ended **2026-08-06T03:00Z** — Wednesday 22:00 EDT.

Outside a declared slot `ExperimentPolicy.assignment_at()` returns `None` **by design**, and
the DM is written to the corpus untagged. So from Wednesday 22:00 onward every DM was logged
as an untagged `signal_only` row, invisible to the analyzer's eligibility filter
(`experiment == "two-arm-v1"`).

**This was the fail-safe behaving exactly as specified — not a defect.** No code was broken,
no writer regressed. The pilot simply reached the end of its declared window and stopped
accruing, while traffic kept flowing.

**Detection**: Rick asked for pilot status. The first answer described 08-04/08-05 coverage as
"short" without checking whether *today* was contributing. Rick pushed back — *"are you telling
me the experiment was not running today?"* — and the per-day tag breakdown showed 71 rows on
08-06, **all untagged**. The check that would have caught it earlier is one line: group the
corpus by day *and by experiment tag*, not by day alone.

> **Mechanism note, consistent with the 08-05 retro**: a real check aimed at the wrong property.
> The slot-coverage report was correct about the days it covered, and silent about the day it
> did not. A coverage report that cannot say "zero" for today is not a liveness check.

## 4. ⚠️ The statistical caveat — stated, not buried

**This extension was authorized after the interim result was seen.** That makes the stopping
rule data-dependent, which is a genuine threat to the reported p-values. It is recorded here
rather than discovered later.

Mitigations actually in force:

- **The estimator is unchanged.** Both pre-declared co-primaries and the ±46-word exact null
  band stay exactly as specified. Nothing was re-specified after looking.
- **The end is fixed in advance.** Saturday 19:00 EDT, written into the schedule before the
  block ran. This is not "run until it turns significant."
- **The blocks are separable — by DATE, not by a field.** ⚠️ **Corrected 2026-08-06 19:16
  after reading a real row back.** The `block` field I added to the schedule JSON does **not**
  reach the corpus: `dm_experiment._parse_slots` builds the caller-facing slot dict from only
  `slot_id` / `arm` / `local_hour` / `start_utc`, so `block` is dropped at that boundary and
  every row carries `block: null`.
  **Separation is still exact**, because `slot_id` carries the date: `2026-08-04*` /
  `2026-08-05*` are the original block, `2026-08-06*` / `2026-08-07*` / `2026-08-08*` are the
  extension. Tue/Wed standalone vs pooled is fully recoverable.
  **Deliberately NOT fixed mid-run**: plumbing `block` through would need a `:7999` bounce
  inside a live slot, and it would split the extension into rows-with-field and
  rows-without — buying a convenience field at the cost of a discontinuity in the very data
  the field exists to separate. Use the date.
- **The original arms are frozen.** A unit test pins the 28 Tue/Wed `(slot_id, arm)` pairs as a
  literal, so a future regeneration cannot silently re-label already-collected rows.

**How to report it**: lead with the pooled result, show the Tue/Wed-only result beside it, and
state that the extension was added mid-flight. If the two disagree, the disagreement is the
finding.
