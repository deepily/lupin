## XML vs JSON — you asked, and the measurement says keep XML

Your instinct that JSON has the same class of vulnerability is **correct**. Both formats break when the model emits an unescaped reserved character inside the payload. But they are not equally exposed, and the gap is not close.

### The escaping burden, measured on 2,977 real DMs

| | messages affected | share |
|---|---|---|
| Needs **XML** escaping (`<` `>` `&`) | 258 | **9%** |
| Needs **JSON** escaping (`"` `\` newline) | 2,289 | **77%** |

| Characters requiring escape, corpus-wide | |
|---|---|
| XML | 556 |
| JSON | **19,195 — 34.5×** |

The JSON breakdown is what does it: **double quote in 55% of DMs, newline in 64%.** Our traffic is multi-line and full of quoted spans — the judge's own grade notes quote the message they grade. JSON's hostile characters are the two most common characters in this corpus after letters and spaces.

### The decisive difference: XML has an escape hatch, JSON has none

`<![CDATA[ ... ]]>` lets us tell the model *"everything between these two markers is literal — do not touch it."* That is one instruction about one opaque wrapper, the same shape as the placeholder rule it already has to follow. And `]]>` appears **zero times** in 2,977 bodies, so the one thing that would break it does not occur in this traffic.

**JSON has no equivalent.** There is no "literal from here to here" in JSON. The model must correctly escape *every* quote and *every* newline across an entire message body — which is precisely the per-character transcription accuracy the freeze protocol was built to stop depending on.

### Failure granularity

A malformed JSON object is unrecoverable **as a whole** — one stray quote in the middle and the entire response is lost. Malformed XML degrades **per tag**: a regex can still pull `<compressed>…</compressed>` out of a document whose `<thoughts>` block is broken. That is exactly what `_repair_llm_xml()` (`judge.py:315`) and the legacy `util_xml.py` extractors do today.

### The in-tree receipt

`src/cosa/agents/io_models/utils/json_object_recovery.py` exists *because* JSON recovery kept failing on this stack, and its own docstring records a silent zero-segment podcast: trailing prose after a `]` defeated brace-matching, `json.loads` failed, recovery returned `None`, and the failure was invisible. That is the JSON failure mode on real model output, already paid for once here.

### Where JSON would genuinely win

Two honest points for the other side. Its escaping rules are **closed and mechanical** — three characters, no ambiguity — where XML has `<`, `>`, `&`, entity references, and CDATA edge cases. And it would sidestep the `BaseXMLModel` ampersand-repair defect described below, which is a real bug in our own base class.

**Neither outweighs 34.5×, and the second one we are fixing anyway.**

⇒ **Recommendation: keep XML.** Not on consistency with the existing agents — on the measurement. Your original prohibition was right; the reason is stronger than "it's what COSA does."

## 🔴 The one hard problem, with its receipt

**A DM body cannot be put inside an XML tag as raw text.** Measured across 2,977 corpus bodies:

| | count | share |
|---|---|---|
| contain `<` | 146 | 5% |
| contain `>` | 157 | 5% |
| contain `&` | 86 | 3% |
| contain a tag-like span (`<response>`, `<memory-fragment>`) | 118 | 4% |
| contain `]]>` | **0** | **0%** |

Every existing COSA agent emits *short, controlled* values — a grade label, a line number, a category. This agent must round-trip **an arbitrary message body**, and roughly one DM in twenty carries a character that breaks XML.

I tested all three ways of crossing that boundary:

| Approach | Result |
|---|---|
| **Raw text in the tag** | 🔴 `XMLParsingError: not well-formed (invalid token)` — fails outright |
| **CDATA** | ⚠️ parses, but **corrupts**: `&` comes back as `&amp;` |
| **Escaped entities** | ✅ exact round trip |

**Why CDATA corrupts** is a real defect and worth naming: `BaseXMLModel.from_xml()` escapes bare ampersands *before* parsing (`util_xml_pydantic.py:193`). Inside a CDATA section nothing is unescaped, so the injected `&amp;` survives into the value. **The base class's own repair step is what breaks it.**

### Recommended approach: CDATA, with a CDATA-aware ampersand repair

- **CDATA over escaping** because the *model* is the one producing the output. Asking Phi-4 to emit `&lt;` and `&amp;` correctly across a whole message body is asking for exactly the transcription accuracy the freeze protocol exists to avoid relying on. `<![CDATA[ ... ]]>` is one opaque wrapper it must not touch — the same shape of instruction as "don't touch the placeholder", which it already has to follow.
- **`]]>` appears zero times in 2,977 bodies**, so the one thing that would break CDATA does not occur in this traffic — and the extractor will treat it as a literal anyway.
- The fix is narrow: override `from_xml()` on our model so the ampersand repair skips CDATA spans, and add a repair helper that **wraps the payload in CDATA if the model forgot** — precisely what `_repair_llm_xml()` already does for the judge (`judge.py:315`).

This keeps the canonical `BaseXMLModel` round trip intact rather than inventing a side channel.

## What gets built

### 1. The XML model — `src/cosa/agents/dm_compression/xml_models.py`

`DmCompressionResponse( BaseXMLModel )`, following `DmQualityJudgeResponse` exactly:

```xml
<response>
  <thoughts>...</thoughts>
  <compressed><![CDATA[...]]></compressed>
</response>
```

- Fields declared with `Field( ..., description=... )`; `field_validator` rejecting an empty `compressed`.
- **`to_xml()` override** — emits the `compressed` payload as CDATA.
- **`from_xml()` override** — CDATA-aware ampersand handling, so the round trip is byte-exact.
- **`get_example_for_template()`** — feeds `{{PYDANTIC_XML_EXAMPLE}}`.
- **`quick_smoke_test()`** with a round-trip block, per the convention in every model file.

### 2. The agent — `src/cosa/agents/dm_compression/compressor.py`

`DmCompressionAgent( AgentBase )`, shaped like `MathAgent` (`math_agent.py`) — the minimal canonical form:

- `routing_command = "dm compression rewrite"`
- `super().__init__(...)`, then `self.prompt = self.prompt_template.replace( "{dm_body}", frozen_text )`
  ⚠️ **`.replace()`, not `.format()`** — the frozen text contains `[[L00]]` and DM bodies contain literal braces; `str.format` treats every brace as a field. The judge hit exactly this and documents it at `judge.py:748`.
- `self.xml_response_tag_names = [ "thoughts", "compressed" ]`
- `restore_from_serialized_state()` — `NotImplementedError`, as `MathAgent` does.
- A bounded retry loop copied from the judge's shape (3 attempts, 0.5s/1.0s backoff), because unlike the base class the judge actually has one.

### 3. The Alpaca template — `src/conf/prompts/agents/dm-compression.txt`

Same skeleton as `dm-quality-judge.txt`: `### Instruction:` / `### Task:` / `### Input:` / `### Response:`, ending with `{{PYDANTIC_XML_EXAMPLE}}` and the `<response>`-first / `</response>`-last requirement.

Task section must carry, as explicit Requirements:
- Preserve every `[[L00]]` token **exactly** — same count, same spelling, do not translate or renumber.
- Do not invent tokens of that shape.
- Preserve negation, uncertainty, modality, actor/action, status, conditions and ownership — the expert review's semantic contract (issue 1).
- The **only** thing that may be deleted is a leading glyph run — the declared removable class from Phase 1.
- Emit the compressed body inside `<![CDATA[ ... ]]>`.

### 3b. The `</stop>` sentinel — required, automatic, and easy to lose silently

You remembered right: this model needs it. Verified in the tree:

- **It is never hand-written.** `grep` finds `</stop>` in **zero** template files. `PromptTemplateProcessor.process_template()` (`prompt_template_processor.py:126-128`) appends it to the injected XML example:
  ```python
  # Append </stop> sentinel for vLLM stop token termination
  xml_with_sentinel = xml_example.rstrip() + "</stop>"
  processed = template.replace( '{{PYDANTIC_XML_EXAMPLE}}', xml_with_sentinel )
  ```
- **It is a stop token on every completion-mode key**, Phi-4 included — `kaitchup/phi_4_14b_params` carries `"stop": [ "</s>", "</stop>" ]`.

So the template shows the model an example ending `</response></stop>`, the model imitates it, and vLLM halts on the sentinel — which is what guarantees a *complete* `</response>` rather than a truncated one.

⚠️ **The trap**: the processor injects the sentinel only if **both** conditions hold — the template contains `{{PYDANTIC_XML_EXAMPLE}}`, **and** the routing command resolves to a model in `MODEL_MAPPING`. Miss the registry entry and `get_example_for_agent()` returns `None`, the `else` branch keeps the template **unchanged**, and the prompt ships with a literal `{{PYDANTIC_XML_EXAMPLE}}` in it and no sentinel. **Nothing raises.** You get a bad prompt and a model that runs to `max_tokens`.

⇒ **Guard for it**: a construction test asserting the processed prompt contains `</stop>` and no longer contains `{{PYDANTIC_XML_EXAMPLE}}`. Cheap, and it catches the registration mistake at test time instead of in a corpus run.

### 4. Registration — both registries, and the INI

Adding to only one is the trap the exploration surfaced; they are different dicts with different keys.

| Where | Entry |
|---|---|
| `prompt_template_processor.py` `MODEL_MAPPING` | `'dm compression rewrite': DmCompressionResponse` |
| `xml_parser_factory.py` `agent_model_map` | same |
| `src/conf/lupin-app.ini` | `llm spec key for dm compression rewrite = dm_compression/phi_4` |
| | `prompt template for dm compression rewrite = /src/conf/prompts/agents/dm-compression.txt` |

**A dedicated spec key, not the shared `kaitchup/phi_4_14b`.** Same endpoint and same model, but that shared key runs `temperature 0.25` / `stream True` and a dozen agents depend on it — this is a fidelity task that wants **temperature 0.0**, and changing the shared key to get it would be a change to everyone else's behaviour. The judge already set this precedent with its own `dm_quality_judge/phi_4` line. New pair, mirroring it:

```ini
dm_compression/phi_4        = vllm://192.168.1.21:3001@kaitchup/Phi-4-AutoRound-GPTQ-4bit
dm_compression/phi_4_params = { "prompt_format": "instruction_completion",
                                "model_name": "Phi-4-AutoRound-GPTQ-4bit",
                                "temperature": 0.0, "max_tokens": 4096,
                                "stop": [ "</s>", "</stop>" ], "stream": False }
```

#### On `max_tokens` — you were right to push, I had guessed at 2048

Measured the frozen bodies the model would actually receive, across all 2,977 corpus records:

| | all bodies | bodies actually sent (not bypassed) |
|---|---|---|
| mean | 179 | 187 |
| p50 | 165 | 171 |
| p90 | 295 | 299 |
| p99 | 488 | 488 |
| **max** | **1,339** | **1,339** |

The output is `<thoughts>` + the compressed body + XML scaffolding. The compressed body is bounded above by the input, so the realistic ceiling is roughly **1,339 + ~100 thoughts + ~30 tags ≈ 1,470**.

So 2048 would have *worked* on today's corpus — but on only ~40% headroom, against three things that erode it:

1. **The tokenizer is a proxy.** The real Phi-4 tokenizer isn't in the local HF cache, so these counts are o200k. Close, not identical — assume ±15%.
2. **The corpus is live and growing.** Today's max body is 900 words; nothing caps it there.
3. **`<thoughts>` is unbounded** unless the prompt bounds it.

⇒ **Use 4096**, matching the shared `kaitchup/phi_4_14b` key. On a **local** model there is no per-token cost, so the cap is free headroom — its only real cost is latency on a runaway generation, and a runaway response fails validation anyway.

🔑 **The reassuring part**: hitting the cap is a **yield** problem, not a **safety** problem. Truncation means no `</response>` and no `</stop>`, so `from_xml()` fails, validation fails, and `compress_or_original()` delivers the original. **Too small degrades to "no compression on this message" — never to a corrupted one.** That is the same fail-closed posture Phase 1 already has, and it should get its own test rather than be assumed.

**Verification owed**: confirm these counts against the real Phi-4 tokenizer during the live corpus run, and record observed p99 output tokens alongside latency.

`instruction_completion` is what routes to `CompletionClient` and makes the Alpaca template the actual prompt — the chat path would wrap it in a chat template instead. There is a smoke test in-tree, `src/tests/smoke/test_llm_spec_key_served.py`, that guards a spec key against what the endpoint really serves; the new key should be covered by it. That guard exists because of the 07-31 Mistral-24B cutover, where ~29 keys pointed at a model the endpoint wasn't serving and everything 404'd.
