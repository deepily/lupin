## 3. The claim drop is a bloat meter, not a damage meter

The obvious headline — *75 of 76 rewrites lost a claim* — invites the reading that the tutor deletes rather than distils. The corpus does not support that reading.

**The output is fixed; only the input varies.**

| Claims in | Rows | Avg claims lost | Claims out |
|---|---|---|---|
| 5 | 42 | 1.8 | 3–5 |
| 6 | 29 | 2.8 | 3–4 |
| 7 | 5 | 3.4 | 3–5 |
| 8 | 1 | 5.0 | 3 |
| 9 | 1 | 6.0 | 3 |

Every rewrite lands at **3–5 claims regardless of what went in**. The tutor fires at `tutor_trigger_claims = 4`, so a DM that already sits at the house shape never reaches it — and **236 tutor-enabled DMs today never fired**, median 3 claims.

⇒ The 42% figure is a measure of how far past *one topic per DM* the senders wrote. Compressing a 17-topic message into three sentences necessarily drops claims; that is the requested behaviour, not a fault in the rewriter. **Retire claim-delta as a fidelity metric.** It belongs on the sender-discipline dashboard, not the tutor's.

The remedy for the claim drop is upstream and social: write one topic per DM. The tutor cannot restore a topic the sender should not have bundled.

## 4. DEFECT — the pointer restore only sees a pointer alone on its own line

`_restore_dropped_pointers` ( `src/cosa/rest/routers/dm.py:748` ) delegates to `pointer_lines` ( `src/cosa/agents/dm_tutor/sentences.py:179` ), which walks the body **line by line** and keeps a line only when `_ATTACHMENT.match( stripped )` matches the **whole stripped line**.

Nobody writes that way. Pointers appear mid-sentence — *"the lead is `_monopolize_active = job.id_hash` (running_fifo_queue.py:422)"*, *"recording to row e0bb5a94"*. Those are invisible to the restore, so the model paraphrases them away and nothing puts them back.

**Measured on the current sha `18132d08`** (26 rewrites): **4 dropped a file path, 9 dropped an 8-hex row id.**

Eaten on the record: `running_fifo_queue.py:422` · `job.py:1163` · `test_json_object_recovery.py` · rows `0c4e8cfa`, `e0bb5a94`, `89bfcc8f`, `587e399a`, `9eafa885`, `c9d3ddcb`, `0ae6e18f`.

**Worst pair** (sam → Cheech, 16:29:46 — 153 → 48 words, 9 → 3 claims):

> *Original*: "…The lead for Mr Radio: `_monopolize_active = job.id_hash` (running_fifo_queue.py:422), and the probe shows self.id_hash is the FULL job_id WITH the ::user suffix… This probe run costs ~$0…"
>
> *Delivered*: verdict + the token value + the next step. The file:line lead, the cost note, and the *on-the-record-not-inference* framing are gone.

**Concrete harm, already realised**: row `e0bb5a94` was eaten out of a live DM. That row was Krishna's only continuity after his memento failed to write — losing the id loses the one pointer to the one record.

**Verification caveat** (Cheech, in his own words, 2026-08-13): his confirmation of the pointer fix used **one message whose path sat on its own line** — precisely the case a line-anchored restore already handles. The easy half was certified; the common half was never exercised.

**The shape of the guard is right and should not change**: take the pointer out of the model's reach and put it back in code, rather than asking the prompt to preserve it. Only the *predicate* is too narrow. The fix is to match pointer **tokens** anywhere in the body — file paths with optional `:line`, and bare 8-hex row ids — and re-append any that the rewrite lost, with unit tests covering the mid-sentence case that today's tests miss.

Filed as a store row (see §7).

## 5. The fabrication guard works — and its count is a floor

`a28c24b6` ("Refuse a tutor rewrite that INVENTS a fact") blocked **8 of 84** firings; none was delivered. That is the guard doing exactly its job.

The caveat is about how the original case was found, not about the guard. The invented-person rewrite (`779b6084`) was caught because the message was **also incoherent enough that Cheech refused to act on it**. Severity and detectability ran in opposite directions: a *plausible* fabrication would have been acted on silently. So 8 is a floor on how often the model invents, not a census.

## 5b. Token accounting — the tutor cannot explain the MCP share drop

Rick observed (2026-08-13) that Claude Code reported only **28%** of the day's tokens going through the MCP server, against the mid-50s on other post-KISS days and ~82% before KISS. The corpus rules the tutor out as the cause.

| | |
|---|---|
| Whole day's DM text | 35,163 raw words ≈ **47k tokens** |
| Tutor's total saving | 4,498 delivered words ≈ **6k tokens** |
| Tutor's cost on the Anthropic ledger | **0** |

A 6k-token net saving cannot move a daily share by 25 points. Two candidates that can:

1. **The denominator grew.** MCP share is a ratio. Today was unusually heavy on local work — 52 commits, pytest runs, corpus analysis, file reads and writes — all non-MCP tokens. The share can fall with MCP consumption flat or rising.
2. **Volume, not length.** 375 DMs today against 782–962 on the pilot days. Fewer DMs is a far bigger lever than shorter DMs.

**Did the tutor make senders write shorter?** Not within the day. Mean raw words **before** the tutor started serving (14:14) were 90.5; **after**, 94.4 — slightly up. Per sender against the Aug 11–12 baseline, María fell 38% (136.3 → 83.9) while I fell 5% (141.1 → 133.4), though the tutor fired on both of us. One day cannot separate teaching from a quiet DM day; the corpus keeps running.

**Coverage check**: the corpus matches the DM API exactly wherever both cover today (16:00 → 78/78, 17:00 → 55/55, 23:00 → 4/4). Honest hole: no rows before 13:43, and a gap 17:55 → 23:56 — I cannot distinguish "no DMs sent" from "not captured" in those windows without a second source.
