## 2. The approved list — what renders on OUR two models

### ✅ ON THE LIST (evidence-backed)

| Marker | Form | Models | Renders? | Caveat |
|---|---|---|---|---|
| **SSML break** | `<break time="1.5s" />` (≤ 3.0s) | multilingual_v2, turbo/flash v2 family (all **non-v3**) | Yes, per docs | **Two preconditions on OUR endpoint** — see §3 |
| **Ellipsis** | `…` / `...` | ALL models | Yes — hesitant pause | Plain text, no SSML flag needed; "less consistent" than break |
| **Dash** | `-` / `--` | ALL models | Yes — short pause | Plain text; "less consistent" |
| **Capitalization** | `WORD` in caps | ALL models | Yes — emphasis | Plain text |

The punctuation/caps items are the **safest** — they always render, need no query param, and cannot be "stripped" because they are not bracket markers. The current strip regex only eats `*[...]*`, so these already survive to synthesis.

### ❌ NOT ON THE LIST (do NOT emit — inert on our models)

The expressive **audio tags** — `[excited]`, `[laughs]`, `[whispers]`, `[sighs]`, `[sarcastic]`, `[pause]`, `[short pause]`, `[long pause]`, etc. — are **Eleven v3 ONLY**. Our `turbo_v2_5` / `multilingual_v2` do not render them. WebSockets are not even available for v3, and multi-context streaming explicitly excludes v3. Our current `*[pause]*` / `*[excited]*` vocabulary lives entirely in this camp — that is why it is inert today.

Phoneme tags (`<phoneme>`) are Turbo/Flash-v2 + **English-only** and control pronunciation, not prosody — out of scope.

## 3. Two code-level preconditions before `<break>` is "known-to-work" on OUR endpoint

Documentary support ≠ heard output. Per Rick's rule ("a config field is not behaviour observed"), `<break>` is **not yet** proven on our path because:

1. **`enable_ssml_parsing=true` is missing from our URL.** The stream-input endpoint gates SSML behind this query param (default off). Our `WS_URL_TEMPLATE` (`tts_client.py:113-116`) does not set it, so a `<break>` tag today would be spoken/ignored, not honored. Implementation must add it.
2. **SSML must arrive as a fully-contained message.** ElevenLabs guidance for the streaming endpoint: send SSML tags in one complete message, else latency/parse issues; rendered text uses a period as a break placeholder. Our client already sends the whole segment text in a single `ws.send` (`tts_client.py:530-535`) — so we satisfy this, but it must stay that way.

**Open empirical gap**: even after adding the query param, "renders on our endpoint" is a *heard/measured* claim. The objective test is to synthesize one segment containing `<break time="1.5s"/>` and measure the silence gap in the returned PCM. That spends real TTS → **:8000 only** (currently wedged, owned by Clayton). Until that probe runs, `<break>` is **doc-supported, not yet measured**.

## 4. The decision this surfaces for Rick/Cheech

The list that works on our **current** models is essentially **`<break>` + punctuation/caps** — pacing only, no emotional expression. To get the rich expressive markers (the `*[excited]*`-style intent behind the original row), we would have to move script TTS to **`eleven_v3`**, which:
- is a different endpoint (v3 has **no** streaming WebSocket — our whole `stream-input` path would change), and
- is a product/cost decision, not a prompt tweak.

So Phase 2 splits cleanly:
- **Phase 2a (small, in-scope)**: add `enable_ssml_parsing=true`; instruct the script LLM to emit `<break time="x.xs"/>` (≤3s, sparingly) and punctuation pauses; stop the regex from eating `<break>`; keep stripping the dead `*[...]*` vocabulary; measure the gap on :8000.
- **Phase 2b (bigger, needs a ruling)**: expressive audio tags → requires eleven_v3 migration. Out of Phase 2a scope.

## 5. Sources

- [How can I add pauses? — ElevenLabs docs](https://elevenlabs.io/docs/help-center/product/speech-synthesis/text-to-speech/how-can-i-add-pauses) — break tag syntax `<break time="1.5s"/>`, ≤3s, supported on Multilingual v2 / Flash v2 / Flash v2.5; v3 uses `[pause]` tags instead; overuse warning.
- [TTS best practices — ElevenLabs docs](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/best-practices) — ellipsis/dash pauses (all models, less consistent), capitalization for emphasis, "Eleven v3 does not support SSML break tags."
- [Do pauses & SSML phoneme tags work with the API? — ElevenLabs help](https://help.elevenlabs.io/hc/en-us/articles/24352686926609-Do-pauses-and-SSML-phoneme-tags-work-with-the-API) — "All models except Eleven v3 support SSML break tags via the API"; phoneme tags Turbo/Flash v2, English-only.
- [Audio tags 101 (Eleven v3) — ElevenLabs blog](https://elevenlabs.io/blog/v3-audiotags) — audio tags `[excited]`/`[whispers]`/etc. are a v3 feature.
- [stream-input WebSocket API reference — ElevenLabs](https://elevenlabs.io/docs/api-reference/text-to-speech/v-1-text-to-speech-voice-id-stream-input) — `enable_ssml_parsing` query parameter exists on this endpoint.
- [SSML dropped in streaming — livekit/agents #3330](https://github.com/livekit/agents/issues/3330) — the "break tags vanish in streaming" reports are a LiveKit plugin regression, not ElevenLabs itself.

## 6. Verdict

On our current endpoint the honest approved list is **`<break time="x.xs"/>` (≤3s) + ellipsis/dash/caps** — and even `<break>` needs `enable_ssml_parsing=true` added and one measured :8000 probe before it is truly "known-to-work." The expressive `[excited]`/`[laughs]` markers Rick likely pictured are **v3-only** and cannot render on our streaming models without an endpoint migration. Bring this to Rick before writing Phase 2 code.
