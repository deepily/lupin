## 1. What it must produce (§1.5)

The decision table, every machine row's verdict filled by the harness, the one human row printed
`PENDING HUMAN`, ending in an **OVERALL** line stating INVEST / STOP / SPLIT.

```
CRITERION                        BAR                 EXECUTOR  VERDICT
latency p50, paired median Δ     ≥20% better         AI        PASS/FAIL
latency p95                      informational       AI        (n too small to gate)
cache-hit rate (warm)            ≥ v1                AI        PASS/FAIL
routing accuracy                 ≥ v1                AI        FLOOR·VETO PASS/FAIL
replay correctness (n≥30)        zero wrong          HUMAN     FLOOR·VETO PASS/PENDING HUMAN
  └ command-match pre-filter     zero mismatches     AI        may only FAIL the row above
degradation paths distinct       all 6 present       AI        FLOOR·VETO PASS/FAIL
v1 suites green                  green               AI        FLOOR·VETO PASS/FAIL
flow control-logic size          ≤200 stmts          AI        PASS/FAIL
command→agent mechanisms         1                   AI        PASS/FAIL
──────────────────────────────────────────────────────────────────
OVERALL                          §1.4 rule           AI        INVEST / STOP / SPLIT
```

**Verdict rules** (§1.4b): any FLOOR·VETO at FAIL ⇒ OVERALL = STOP, whatever the rows above say; any
FLOOR·VETO at PENDING HUMAN ⇒ OVERALL = PENDING, never INVEST. INVEST needs faster (§1.1) AND smaller
(§1.3); smaller-but-not-faster ⇒ SPLIT (port v2's shape onto v1); neither ⇒ STOP.

## 2. Two arms, two transports (the fact that drives everything)

| | v2 arm | v1 arm |
|---|---|---|
| Entry | `POST /api/v2/ask` (synchronous, §8 body) | `POST /api/push` (`queues.py:237`) → poll `get-queue/done` |
| Returns | §8 result inline | job id; result harvested from the done queue |
| Control logic | AskFlow (`flow.py`) | v1 queue pipeline (`push_job`, running_fifo_queue) |

**Different transports, not just different control logic.** That single fact creates §3.

### 2a. 🔴 The v1 arm runs in a WORKTREE PINNED at a sha (Mr. Radio, via Cheech 15:07)

The v1 baseline is **expiring code** — phase-2 deletes v1's queue path. Measure it against a **pinned
worktree at `b0735467`** (= `9805783d^`), the last sha that still carries `todo_fifo_queue.py` and
`routers/queues.py` where `POST /api/push` lives. Two hard requirements:

1. **Stamp `b0735467` next to the seed in the printed report** — the baseline is then non-expiring and
   the whole comparison is reproducible (a reader knows exactly which v1 produced the number).
2. **`export LUPIN_ROOT=<worktree>` before trusting ANY number.** Subprocess tests resolve config +
   `__main__` through `LUPIN_ROOT`; without the override they read the **dirty main tree** — a peer's
   uncommitted code — and **false-RED**, which reads as a v1 result and is not one. (auto-memory
   `reference_worktree_testing_needs_lupin_root_override`.)

## 3. 🔴 The load-bearing decision — `t_first_useful` parity

**The trap** (Cheech; same class as Tiberius's §6.4 baseline contamination): if v1's latency includes
**queue dwell** (wait in the todo queue before a consumer picks the job up), v2 wins merely for being
**synchronous** — measuring the *transport*, not the *redesign*, and flattering v2 in the direction
nobody audits.

**The rule**: measure the **same span** in both arms — **work-start → first-useful** — and **exclude
v1 queue dwell**. Print the exclusion so a later reader can check the number against it.

| Arm | work-start anchor | first-useful mark |
|---|---|---|
| v2 | `t_recv` (synchronous: request received ≈ work begins) | `timings_ms["t_first_useful"]` (flow.py:207/238) |
| v1 | **job dequeued / running-started** (NOT request received) | v1's first-useful equivalent |

⚠️ **Build-time seam to VERIFY by reading the consuming code, not assumed**: the v1 running queue must
expose a **dequeue/running-start timestamp** and a **first-useful timestamp**. Candidates:
`running_fifo_queue` transition stamps, the job/snapshot `runtime_stats`, or a stage trace. If v1 stamps
only received + done, the parity span isn't directly measurable and the v1 instrument must add ONE stamp
at the dequeue point — a v1 touch that must stay behavior-neutral (floor: "v1 untouched").

**If parity can't be achieved honestly, mark the latency rows `PENDING — parity unverified`** rather
than printing a flattering number.

## 4. Per-arm table isolation (§6.4 — mandatory for the eval)

Each arm runs against **its own snapshot table, restored to the same start**, or v1's run populates the
store v2's cold pass reads → v2's cold pass is warm → every headline moves in v2's favour.

**Mechanism** (§6.4): the cache manager takes its table name from config. Add a new INI key
**`v2 snapshot table`** (+ splainer entry) and a matching v1-table selector; point each arm at a clean,
identical table before its run. What §6 called an "escape hatch, optional" is **mandatory here**.

**Honest consequence to PRINT** (§6.4): with isolated tables the absolute cache-hit rate is the rate
*this corpus generates from a known start*, NOT the production rate. Report both, labelled; never let
the comparison number be quoted as the production one.

## 5. Corpus + sampling (§1.4a)

- Same corpus both arms, **same seed** (recorded in the report → a re-run reproduces the sample).
  The report header prints **both** the seed AND the v1 worktree sha `b0735467` (§2a) — the two facts
  a reader needs to reproduce the exact comparison.
- **n = 60 per command, stratified, seeded** (~480/pass, ~960 for the cold/warm pair PER ARM ⇒ ~1,920
  total — count BOTH arms in the cost, §1.8/finding-8). Full-corpus behind a flag for a release run.
- Stratified because calculator (561) is 4.4× datetime (127); unweighted pooling lets the biggest
  command dominate a "system-wide" number and hides the three smallest.
- **New vs shipped**: `v2_eval.load_corpus` takes `--limit` (first-N/command), NOT a seeded stratified
  sample. B adds seeded stratified sampling.

## 6. Paired metric computation (§1.4b fix)

- Both arms run the **identical utterance list in identical order** (pairing preserved).
- Per utterance u: `Δ(u) = v1_first_useful(u) − v2_first_useful(u)` over rows where BOTH arms returned a
  usable latency (drop a pair if either arm failed u; **record how many dropped**).
- **Gate = median of Δ**, restated as ≥20% of the v1 median — robust to the tail that makes p95 unstable
  at n=60.
- **p95 REPORTED, not GATING** — labelled `INFORMATIONAL (n too small to gate)`.
- cache-hit rate (warm): v2 ≥ v1. routing accuracy (floor): v2 ≥ v1, command vs corpus JSON key.

## 7. The floors (vetoes) and how each is decided

| Floor | How measured | Executor |
|---|---|---|
| routing accuracy v2 ≥ v1 | command vs corpus JSON key, both arms | AI |
| replay correctness, n≥30, zero wrong | command-match pre-filter can only FAIL a row; a human signs PASS | **HUMAN → `PENDING HUMAN`** |
| degradation paths distinct (6) | all of `router_error`/`extract_error`/`replay_error`/`agent_error` + the 2 from R-D3 appear with distinct values | AI |
| v1 untouched | v1 suites green; `expedite()` output unchanged | AI |

**Replay correctness prints `PENDING HUMAN`, never a checkmark** — the automated oracle can only ever
FAIL a row (§1.4b(1)). A PASS nobody checked is worse than a blank.

## 8. The two non-latency AI instruments (§1.3) — CONFIRMED unit F's (Cheech, 15:04)

Both are F's: they print in F's own table as AI-executor rows, F computes the OVERALL that consumes
them, and they're static AST work needing no server — handing them off buys nothing.

- **flow control-logic size ≤200 stmts**: `ast` walks v2's request path (intake→dispatch) and v1's,
  counts statements. Falsifiable; if v2 > 200 the "minimal control logic" claim failed — say so.
- **command→agent mechanisms = 1**: v2 has one registry; v1 has 3 that disagree (`MODE_TO_AGENT` short
  forms vs router-template / `AGENTIC_AGENTS` full strings — R-A1). Count distinct mechanisms per arm.

## 9. Build order (each a checkpoint; I get re-spun mid-build)

1. **v1-arm instrument** — `V1PushClient` over `POST /api/push` + poll `get-queue/done`, extracting
   routing command, first-useful (parity span §3), cache signal. Runs against the **pinned worktree at

3. **Seeded stratified sampling** — n=60/command, seed printed in the report (§5).
4. **Paired metrics + report table** — median-Δ gate, p95 informational, veto/OVERALL/PENDING-HUMAN (§6, §1.5).
5. **AST counters** (if owned, §8).
6. **Integration wrapper** for the paired run + scheduled `:8000` submission (same bridge pattern as
   `test_v2_eval_live.py`).

Every step: unit tests to 100% lines+branches; the run itself is `:8000` scheduled post-midnight.
