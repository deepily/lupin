# The receptionist routing hole — measured, and what I recommend

**Reviewer**: Clayton 😎 (`b36934bf`) · **Date**: 2026-08-22 · **Crew**: Mr. Radio 🦉's Q&A-card crew, adversarial-reviewer seat
**Answers**: blocker §2 of `src/rnd/v0.2.0/2026.08.22-qa-card-plan-review.md`
**Measured at**: `9cbabf03` (= `9b49f04d` + the plan-doc commit; no code between them)
**Wanted by**: before phase 3 ships

## Verdict

**Recommend option A: a new `route_reason` value, `user_picked_receptionist`, on both doors. `path` stays `receptionist`.** Four lines of branch, no contract change, and the distinction lands on the field whose whole job is naming which rule fired.

## What I measured, not read

Mr Radio's §2 predicted two *different* behaviours — `ask()` degrading and `submit()` refusing. **There is only one, and that is worse than the review said.** I ran all three shapes through a real `AskFlow` (real registry, real `QueuedExecutor`, stubs only for queue/cache/router/receptionist) and read the emitted body:

| what was asked | `path` | `route_reason` | `command` in the response |
|---|---|---|---|
| `submit` naming the receptionist **on purpose** | `receptionist` | `unknown_command` | `agent router go to receptionist` |
| `submit` naming a **garbage** command | `receptionist` | `unknown_command` | `agent router go to receptionist` |
| `ask` whose router **could not place** the question | `receptionist` | `unknown_command` | `agent router go to receptionist` |

**Identical on every field.** There is no refusal shape — `submit` degrades exactly as `ask` does, because both fall through the same two readers to the same `_receptionist( …, "unknown_command" )` call (`flow.py:415` and `flow.py:207`). And `command` does not save you either: `_receptionist()` hardcodes the receptionist's own command string (`flow.py:1175`), so the command the caller actually asked for is **gone from the response**.

So the Q&A card cannot tell "you chose this" from "we could not route you" by any means at all — not `path`, not `route_reason`, not `command`.

Probe was a throwaway; it is deleted. Reproduce by borrowing the fixture in `src/tests/unit/test_v2_submit_claude_code_through_path.py` and posting the three bodies above. ⚠️ Set `LUPIN_ROOT` to the worktree first or the false-green guard (row `a9f87d29`) refuses to collect.

## The three options

**A — new `route_reason`, `path` unchanged.** In `submit()`, before the fall-through at `flow.py:415`, recognise the receptionist command and pass `"user_picked_receptionist"` instead of `"unknown_command"`. Same for the `ask()` arm if a router ever returns it.

- `path` staying `receptionist` is *correct*, not a compromise — the receptionist genuinely is what served the request. What differs is why it was reached, and `route_reason` is the field the flow's own docstring (`flow.py:783`) describes as recording **which rule fired**.
- Costs one branch and one string constant. Touches no contract, no class semantics, no guard.
- The card renders on `route_reason`; so can the eval harness and the trace.

**B — give the receptionist a `factory` so `resolve()` returns it and it comes back as `path="agent"`.** Rejected. `resolve()`'s docstring promises *"Returns None for every non-conversational command — agentic, deferred, control, receptionist, none, or unknown"*, and the registry derives its four template buckets from `cls` (§5.1.2). Making the receptionist resolvable changes what `cls=NONE` means, puts it inside the write-back guard's reach, and makes it a snapshot candidate. That is a large blast radius bought for a UI distinction.

**C — do nothing; the front end knows what it sent.** Rejected, and this is the one worth arguing. The card *could* infer it locally — but every other reader is left blind, and one of them is already sore about exactly this. Bug `38815328` was a warm pass in which 117 of 300 requests came back as the receptionist and 115 could not say why; the fix was to make the degrade explain itself. Leaving a deliberate pick indistinguishable from a degrade re-opens that measurement hole in the other direction: a report counting receptionist outcomes as failures would count every deliberate pick as a failure. `src/scripts/v2_eval.py:83` already declares `PATH_RECEPTIONIST` — unused today, which means the next person to use it inherits the conflation.

## What this obliges the crew to

1. **Phase 3's card renders on `route_reason`, not on `path` alone** — the plan's §5.2 flowchart branches on `response.path` and needs the extra arm.
2. **A gate that can go red**: post the receptionist command deliberately, assert `route_reason == "user_picked_receptionist"`; post a garbage command, assert `route_reason == "unknown_command"`. *Falsify it*: collapse the two branches back into one and both assertions cannot hold at once. This is a distinction across a real boundary, not a count.
3. **Not my call to make alone** — ruling 3 was Rick's, and this is the mechanical half of it. Recommendation goes to Mr Radio; if he wants B instead, the registry contract change is a separate conversation with María.

## 🔴 ANSWERED, AND IT CHANGES THE PRIORITY — this is live today, on voice

I listed "does the voice ladder ever route to the receptionist as a POSITIVE detection?" as
the thing I had not checked. **It does, and it always has.** Two receipts:

1. `agent router go to receptionist` sits in `_SERVED_ORDER` in `router_prompt_generator.py:61`
   — it is offered to the router as a selectable command, not as the else-branch.
2. It has **174 training utterances** of its own
   (`src/conf/training/agent-router-compound-commands.json` →
   `src/ephemera/prompts/data/synthetic-data-agent-routing-receptionist.txt`), and every one of
   them is a deliberate ask: *"Switch to receptionist." · "Receptionist, please." ·
   "Go to receptionist." · "Activate receptionist."*

**So the model was trained to say "the user asked for the receptionist on purpose", and the flow
reports that as `route_reason="unknown_command"`** — the precise opposite of what happened. My
probe already measured it: the ASK-routed row used a router returning exactly this command and
came back indistinguishable from garbage.

**This is not a phase-3 nicety.** It is a live defect on the voice path today, needing no new UI
to reach, and it inverts what I wrote above: the **`ask()` arm is the one that matters most**, and
the Q&A dropdown is the second caller of a fix that is already owed. The `submit()` arm is still
needed — it is just no longer the reason.

## What I did not check

Whether the router in practice emits it (trained-for is not the same as observed-in-traffic). A
warm-pass trace scan for `route_reason="unknown_command"` where the router's chosen command was
the receptionist would size it. Not in my seat, and it does not change the fix — a positive
detection reported as "unknown_command" is wrong at any frequency.
