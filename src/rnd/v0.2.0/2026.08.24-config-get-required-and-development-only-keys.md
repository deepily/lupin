# get_required(), and two keys that only exist in Development

**Date** 2026-08-24
**Row** `3e4a4a4a` — "Config get() returns None into callers that concatenate it"
**Author** Clayton 😎 (session `d4af6641`), on Mr. Radio's assignment

---

## 1. What the row asked for, and what I built

On 2026-08-18 the GCP VM returned HTTP 500 on every voice transcription. Transcription
itself worked; the failure was `can only concatenate str (not NoneType) to str` in
post-processing. A caller asked the config manager for a key that no longer existed,
got `None` back, and concatenated it. The config manager did exactly what it was told
to do, and the caller had no way to notice.

The fix is **not** to make `get()` raise. Config resolves across five blocks
(Baseline, Development, Production, Testing, Testing-GCS) with inheritance, so a key
present in Development and absent in Testing-GCS would become a hard startup failure
on the VM — a bigger blast radius than the bug.

So: a new `get_required()` that raises, with `get()` untouched.

```python
raise MissingConfigKeyError( key, self.config_block_id, self.config_path )
# -> "Required configuration key [vox command prompt path wo root] not found
#     in block [Lupin: Production] of [/src/conf/lupin-app.ini]"
```

The message names **which key**, **which resolved block**, and **which file**. That is
the whole point: the 08-18 traceback named none of those three.

**It also raises on a BLANK value.** A required key set to nothing concatenates
without complaint and silently builds a wrong path — the quiet cousin of the `None`
crash. `get_required()` is new, so it has zero existing callers and strictness costs
nothing. Flagged here because it is a judgment call, not something the row asked for.

and no `default=` keyword rather than "the line looks like it": **110** no-default
`*config*.get()` sites across `src/`, of which **7** concatenate the result on the
same statement, and one of those 7 is a mock inside a test.

| file:line | key | why |

| `src/cosa/rest/multimodal_munger.py:1340` | `vox command prompt path wo root` | the exact shape of the 08-18 outage |

The remaining ~104 no-default sites are untouched, per the row's own instruction not to
migrate all of them in one sitting.

## 3. The finding — two keys live only in Development

Before believing the migration was safe I built the manager under **all five blocks**
and asked `exists()` for each migrated key, rather than reasoning about the inheritance
chain:

| key | Baseline | Development | Production | Testing | Testing-GCS |
|---|---|---|---|---|---|
| `deep research output path` | yes | yes | yes | yes | yes |
| `agent prompt for debugger minimalist` | **NO** | yes | **NO** | yes | yes |
| `vox command prompt path wo root` | **NO** | yes | **NO** | yes | yes |

The chain explains it: Testing and Testing-GCS inherit **Development**, while
Production inherits **Baseline**. Both keys are defined inside the Development block
(lines 74 and 540) and nowhere else.

**So under Production, those two call sites already crash today** — `get()` returns
`None` and the concatenation raises `TypeError`. My change does not create that
failure. It changes an unattributed `TypeError` into a message naming the key and the
block.

⚠️ **The real fix is a config change I did not make.** Moving the two keys into
Baseline would give Production the same paths Development uses, but that is a
Production config change and belongs to Rick, not to a migration commit. Mr. Radio is
putting it to him as a decision (2026-08-24 22:14).

## 5. What is still open

- **Rick's decision**: move `vox command prompt path wo root` and `agent prompt for
  debugger minimalist` into Baseline, or leave Production without them.
- **The other ~104 no-default call sites.** Not urgent — none of them concatenate on
  the same statement — but a value that reaches an f-string renders as the literal
  `"None"` and produces a wrong string with no crash at all. That is a quieter failure
  than the one this row fixed, and nobody has swept for it.
- **A startup assertion** that every key a module reads resolves under its deployed
  block remains the stronger control, and the more expensive one. Still unscoped.
