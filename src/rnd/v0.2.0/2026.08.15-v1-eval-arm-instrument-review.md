# Independent review — v1-arm eval instrument (as a measuring device)

**Date**: 2026-08-15
**Reviewer**: Extra 2 🪨 (crew under Cheech 🌿) — did NOT build the instrument
**Under review**: `src/scripts/v1_eval_arm.py` (commits afbfa3ee, b24f9872, 4f26c1dd) + `src/tests/unit/test_v1_eval_arm.py` (32 green)
**Lens**: this instrument produces the INVEST / STOP / SPLIT verdict for the whole v2 program. Reviewed for **bias toward one arm**, not for code quality.

**Verdict**: the module is faithful to its inputs and its purity/failure-handling are sound, BUT it carries **two head-to-head comparison biases that point in opposite directions** (F1 favours v1, F2 favours v2) and **one unguarded precondition** (F3). None is a coding bug; all three are measuring-device defects that can move the verdict. F1 is the most consequential because it contradicts an explicit claim the instrument makes about itself.

---

## F1 — the "compute span, comparable across arms" is NOT comparable (bias: v1 looks faster) — HIGH

**Claim under test**: docstring lines 8/17-23 and the report header (line 381) state the compute span `RUNNING→COMPLETED` "measures the SAME span in both arms" and excludes only "queue dwell."

**What the code actually measures**: `span_ms = completed_ts - running_ts` (v1_eval_arm.py:193), where `running_ts` is the RUNNING transition = the instant the consumer picks the job off the queue.

**Why the label is false**: in v1, `push_job` (todo_fifo_queue.py:422) runs — synchronously inside the `/api/push` handler, BEFORE the job is queued (`self.push(job)` at :960) — the **embedding generation** (:479-482), the **two-tier cache lookup / match** (:518-684), and the **routing** (`_get_routing_command`, :737). All of that finishes before the QUEUED transition, so it is before both `queued_ts` and `running_ts`. The v2 arm's `first_useful_ms` (v2_eval.py:409) measures from request receipt and INCLUDES routing + extract + cache-lookup + replay.

⇒ v1's compute span omits routing+embedding+cache-lookup; v2's span includes them. The span boundaries enclose **different work**, so the "comparable" compute-latency comparison — and the paired median-Δ gate built on `spans` — systematically flatters v1. Even the wall-clock span does not rescue it: `queued_ts` is emitted AFTER `push_job`, so wall-clock also omits the pre-queue work.

**Fix (agreed with Cheech 2026-08-15)**: measure **BOTH arms from a client-side send timestamp** — the instant just before the client POSTs (`/api/push` for v1, `/api/v2/ask` for v2) → the observed completion. Symmetric by construction: neither arm's server-side span boundary is trusted, so v1's pre-queue routing+embedding+lookup and v2's inline routing+extract+replay are both inside the measured span. This replaces the earlier v1-only framing — measuring only v1 from client-send would swing the bias the other way. Keep the server-side spans (RUNNING→COMPLETED, QUEUED→COMPLETED) as **informational sub-spans**, clearly labelled as NOT the cross-arm comparison, so the queue-dwell breakdown is still visible.

## F2 — routing_accuracy is scored by a lossy rule for v1 and an exact rule for v2 (bias: v1 looks worse) — MEDIUM (corpus-dependent)

**v2**: `matched_command(r)` reads the command v2 itself reports (it routes by command) — exact.
**v1**: `resolve_command(agent_type, class_to_command)` maps the agent CLASS name through `build_class_to_command`, which (correctly, honestly) **drops ambiguous classes** and **cannot see agentic-mode utterances** — they route via `AGENTIC_MODE_MAP`, absent from `MODE_TO_AGENT` (the module's own KNOWN GAP, lines 320-323). Every such utterance is a forced routing MISS.

Both arms then feed the same `route_matches` + `_rate(routed_right, n_ok)`. The denominator shape matches, but v1's **numerator is depressed** by unmappable/ambiguous/agentic classes that v2 scores correctly. The module labels this a lower bound (R-A1/R-C2) — the defect is not the label, it's that the **paired report diffs v1's lower-bound routing against v2's exact routing as if like-for-like**.

**Severity is corpus-dependent**: if the sampled corpus contains no agentic-mode or ambiguous-class utterances, the bias vanishes; if it does, v1 routing is understated and the verdict tilts toward v2 on routing.

**Fix (agreed with Cheech 2026-08-15)**: exclude un-mappable/agentic utterances from **BOTH arms' routing denominator**, so the two numbers are computed by one rule — AND **print the excluded count and its share of the corpus** in the report. The exclusion must be auditable, not silent: a reader has to see how much of the corpus was dropped from routing before trusting the accuracy number (a large excluded share is itself a finding about coverage). Excluding from only v1's denominator, or excluding silently, both re-introduce a bias.

## F3 — the COLD pass is not guaranteed cold (shared-store warmth is unguarded) — MEDIUM

`run_two_pass` (v1_eval_arm.py:341) runs cold then warm; v2's `main` does the same. **Neither empties or segregates the solution store before the cold pass**, and both arms **write back to the SAME shared snapshot store** (tagged `flow_version`). So a prior harness run, or simply running the other arm first, pre-warms the cache the "cold" pass reads.

⇒ cold `cache_hit_rate` can be >0 and cold latency understated, contaminating the headline cold→warm delta and the cache-hit numbers. The intra-run order (cold before warm) correctly prevents backward leak WITHIN one run — the leak vector is **cross-run and cross-arm shared-store warmth**, which nothing here guards. (v2's `guard_run_integrity` runs on the WARM pass only.)

**Fix**: a cold-start precondition before the cold pass — empty the store, or read cache scoped to a per-run tag, or at minimum stamp+assert "store was cold at pass start" in the report so a contaminated baseline is visible rather than silent.

---

## F4 — cold/warm correctness depends on `collect_fn` being fully blocking — LOW (note)

`run_two_pass` starts the warm pass immediately after `run_v1_pass` returns for cold. That is only leak-free if `collect_fn(job_id)` **blocks until COMPLETED** for every cold job; if it returns early (e.g. on a timeout that still yields partial transitions), a cold job could still be running when the warm pass begins, cross-contaminating the cache and the warm latencies. The contract is implied by the docstring but not asserted. Worth an explicit contract line + a test that a non-terminal `collect_fn` return is treated as a failure, not a completion.

---

## What is SOUND (stated, so the review is not all-negative)

- Purity: every IO seam is injected; the record-assembly + metric tree is unit-provable with fakes (32 green). Good.
- Failure honesty: a job with no RUNNING/COMPLETED pair is `ok=False` with a named `failure`, counted in the failure rate, never silently dropped (`assemble_v1_record`). A negative span → None, not a fabricated measurement (`span_ms_between`).
- Ambiguity is excluded, not guessed: `build_class_to_command` drops a class reachable from >1 mode rather than coin-flipping — an honest under-count, not a fabricated hit.
- Rates return None (not 0.0) on a zero denominator (`_rate`), so an empty arm cannot fabricate a perfect or zero score.

## Recommendation

**SPLIT is premature to trust on latency or routing until F1 and F2 are resolved** — those two biases move the two headline comparison axes in opposite directions, so the current instrument cannot be quoted for a go/no-go without correcting them. F3 must be closed before ANY cold-number is trusted. Cheapest path: F1 fix (a), F2 fix (shared denominator), F3 fix (per-run cache tag) — all three are in the harness, not the arms.
