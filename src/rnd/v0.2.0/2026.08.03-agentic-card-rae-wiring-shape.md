## What Rick asked for

Verbatim (row 7c46fdde): *"I want the agentic card to use the runtime argument facilitator! That card must be traversable from within the agentic job submission card for podcasts."* When a podcast submission from the agentic card is missing arguments, the expeditor's question flow must be reachable and answerable **without the user leaving that card**.

## What the card does today (measured — Lane 3, and code read)

The "Submit Agentic Jobs → Generate Podcast" card posts to **`POST /api/podcast-generator/submit`** (`notifications.js:3200`), NOT `/api/push`. That endpoint (`podcast_generator.py:460`) has two flows and **never calls the RAE**:

- **Flow A (direct path):** `is_research_path()` true → `validate_source_path()` → create job.
- **Flow B (description):** `match_research_docs()` (its OWN phi-4 fuzzy match) → if no match, **404**; if matches, `get_user_document_selection()` **BLOCKS on a multiple-choice notification** and waits for the pick → create job.

Two facts that decide the shape:
1. **The card already resolves a file** (Flow B, `match_research_docs`) — so this is NOT "add file resolution." It's "add the expeditor's *missing-argument* questioning," and reconcile the two resolvers.
2. **The endpoint already blocks on the notification-answer mechanism** (`get_user_document_selection`, `podcast_generator.py:623`) — the exact same surface the RAE uses. So invoking the RAE server-side from this endpoint is **reach, not rebuild**: the machinery to ask a question from inside this endpoint and route it to the card's spec job (`voice_io.set_job_id(spec_id)`) is already here and proven.

## The shape options

### Option A — Server-side: the endpoint invokes the RAE *(recommended reach)*
`submit_podcast_job` calls the expeditor to collect any missing args, reusing the notification-answer flow it already uses for document selection. The asks route to the card's existing spec job card (`voice_io.set_job_id(spec_id)` already does this).
- **Pros:** smallest change; reuses proven in-endpoint blocking-notification machinery; no new UI; keeps the card's request contract (scheduling/monopolize/dry_run/max_segments/force_failure_mode).
- **Cons/risk:** must reconcile the **two resolvers** — the endpoint's `match_research_docs` vs the RAE's `fuzzy_file_match` — so the user isn't asked to pick a document twice. Decision needed: RAE owns resolution (drop the endpoint's), or the endpoint resolves the file and the RAE only fills the *other* args.

### Option B — Reach via the voice/queue path: card submits through `/api/push` with `mode=podcast`
Point the card's client at the Lane 2 path, which already reaches the RAE **and** fuzzy-matches (measured, `c72002be`).
- **Pros:** inherits both halves wholesale; zero server change to the RAE path.
- **Cons/risk:** abandons the bespoke endpoint's Flow A/B and its request fields (target_languages, dry_run, scheduled_at, monopolize, max_segments, force_failure_mode) — those would have to be re-expressed through the push path; and the RAE's asks arrive as generic notification cards, which **may not read as "within the card"** to Rick.

### Option C — Client UI affordance: an in-card RAE question panel
Build the expeditor's Q&A directly into the agentic card UI.
- **Pros:** literally "within the card" if that's what Rick means.
- **Cons/risk:** largest build (new client surface + wiring); highest risk three days out.
