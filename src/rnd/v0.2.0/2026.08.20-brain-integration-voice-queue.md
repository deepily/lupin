## 3. Two rulings that are behavior, not plumbing

The registry already decided both — in the opposite direction from what the voice path does today.
Routing voice through it as-is would change what users experience.

### 3a. The CRUD fork — the flag is ON

**Measured, not assumed**: `crud for dataframes agents enabled = true` at `src/conf/lupin-app.ini:1909`,
and the live `ConfigurationManager` returns `True` inside **both** `lupin-rest-dev` and `lupin-rest-test`.

| | today (voice) | registry |
|---|---|---|
| `agent router go to todo` | `TodoCrudAgent` | `TodoListAgent` |
| `agent router go to calendar` | `CalendarCrudAgent` | `CalendaringAgent` |

The registry's stated reason for pinning, from its own comment: CRUD agents are never snapshotted,
so inheriting the fork *"would report 0% cache-hit forever and read as a v2 bug."*

⚠️ **That is a reporting concern, not a product judgement.** Changing what a spoken command does so
that an eval metric reads better is the wrong direction.

🔴 **And today's behavior is already pinned by tests.** `src/tests/unit/test_crud_mock_pipeline.py`
asserts at lines 101 and 121 that with the flag true, todo creates `TodoCrudAgent` and calendar
creates `CalendarCrudAgent`; `test_crud_queue_integration.py` carries 29 tests over the same path.
So adopting the registry pin is a **deliberate reversal of a ratified assertion**, not an oversight —
and it cannot happen silently, because the suite goes red.

**Recommendation**: keep today's voice behavior; give the registry a flag-aware binding for these
two commands. One conditional living in the table beats a table that pretends a live fork does not exist.

### 3b. Math's salutation quirk

Every agent receives the bare question except `MathAgent`, which receives `salutation_plus_question`.
The registry already ruled to drop it (logged as *risk 10*).

**Nobody has measured whether the salutation helps math parse anything.** "Drop it" is the tidy
answer; "measure it" is the honest one. Rick's call.

## 9. THE CORRECTED PROPOSAL — one integration, and it IS the brain

**Rick's question, 2026-08-20 ~19:30 EDT**: *"I originally understood that you were going to use them
together as what you called the 'brain'. Is that something you still plan on or has that plan changed?"*

**The plan has not changed. My §8b description of it was wrong.** The cache, router, expeditor and
resolve are not four things to graft one at a time — they are the four steps *inside* `AskFlow.run()`,
with a defined degradation at each. Taking them separately means re-implementing that degradation
inside `push_job` piece by piece. **It is one integration.**

### 9a. The seam already exists, and it was designed for exactly this

`AskFlow` does not execute agents itself. It delegates to an injected **`Executor`**:

```python
class Executor( Protocol ):
    def submit( self, work: Work, trace: StageTrace ) -> Outcome: ...
```

`InlineExecutor` — run it here, on this thread — is only ONE implementation, and it is the
experiment's. And `Outcome` already declares the other one:

```python
status is "done" when an answer was produced, "parked" when a QUEUED EXECUTOR
handed work off (phase 2), "failed" when replay or the agent threw.
    status : Literal[ "done", "parked", "failed" ]
    job_id : Optional[ str ] = None
```

**"parked", "a queued executor", "phase 2", and a `job_id` field are already in the contract.** The
design anticipated the graft onto CJ Flow. Nothing produces a `parked` outcome yet because the
queued executor was never built.

### 9b. What gets integrated with what

```
  push_job( question, websocket_id, user_id, user_email )
        │
        └──► AskFlow.run( ..., executor=QueueExecutor( self ) )
                  │
                  ├─ 1  cache.lookup      → exact hit? replay
                  ├─ 2  router.route      → command + raw args
                  ├─ 3  resolve           → AgentSpec        ← already grafted (ab802215)
                  ├─ 4  expeditor.extract → args, or PARK and ask
                  │
                  └─ _run_agent → executor.submit( Work )
                                        │
                                        ▼
                            QueueExecutor.submit  ← THE NEW PIECE
                                  · register_scoped_job
                                  · self.queue.push( agent )      ← the EXISTING CJ Flow FIFO
                                  · return Outcome( status="parked", job_id=... )
```

**One new class.** The router, the expeditor and the cache arrive *because they are inside `run()`* —
they are not grafted individually. The queue, the job card and the websocket answer path are
untouched: `QueueExecutor` hands the agent to the same `push()` that runs today.

### 9c. THREE THINGS THAT ARE NOT FREE — Rick should weigh these before I build

**① `_run_agent` treats anything but "done" as failure.**
```python
if outcome.status != "done":
    return self._receptionist( trace, question, ctx, "agent_error", ... )
```
A `parked` outcome would degrade to the receptionist today. It must learn that **parked is
success-in-flight**, not an error. Small change, but it is in the flow's core degradation path and
deserves its own control proven red.

**② Cache write-back happens after an answer, and a queued job has no answer yet.** `_finish` calls
`_maybe_write_back` immediately, then `_speak`, then emits. With deferred execution there is nothing
to snapshot at that moment. **Write-back has to move to job completion** — where the websocket answer
already arrives. This is the one genuinely new piece of design, not a wiring change, and it is where
I would want Rick's or Mr Radio's eye before building.

**③ Two "parked" words, one collision.** `AskFlow` already uses `status="parked"` for *needs-input*
— a question waiting on a human answer. `Outcome.status="parked"` means *queued for execution*.
Same word, different states, and the second is about to become live. **Name them apart before
building**, not after a confusing bug.

### 9d. What I am NOT proposing

- **Not** replacing the CJ Flow queue. It stays exactly as it is.
- **Not** making voice synchronous.
- **Not** grafting the pieces separately — §8b's framing, retracted above.
- **Not** touching the HTTP route, which keeps `InlineExecutor` and its current behaviour.

### 9e. Sequence, if approved

1. Name the two `parked` states apart (③) — pure rename, its own commit.
2. `QueueExecutor` + its unit tests, red-on-revert, nothing wired yet.
3. Teach `_run_agent` that parked is success-in-flight (①), with a control.
4. Move cache write-back to job completion (②) — **the piece that needs a design ruling first**.
5. `push_job` calls `AskFlow.run()` with the queue executor. Shadow-mode first if the migration
   window rule applies.
6. Full ladder: unit + cosa pre-merge; websocket smoke, E2E UI and integration post-merge,
   post-bounce, per Mr Radio's sequencing.
