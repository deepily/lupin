**Revisions accepted**

### 3.C — Corpus reconciliation (§2.4, §1.1, §6)

| Severity | Finding | Closure |

| inconsistency | §2.4 must not take a fresh registry read (Maya) | **revised** |
| — | §6's weakest claim: is one-step regeneration safe? | **ANSWERED** |

**§6 is resolved.** This was the author's self-named weakest claim, and she asked for it to be attacked first. The answer came in two independent passes that had to be kept apart:

- **Serving is safe** (Maya). Live routing reads the checked-in `.txt`, never the compiled string. That string's only consumers are the three training-corpus interpolation sites, and **nothing parses it back into a list**.
- **Training is safe under two conditions** (Clayton, grounded from source). `_compile_agent_router_commands()` (`xml_prompt_generator.py:244`) builds one menu string — 8-space-indented `<command>` lines, order compound→simple→agentic, `.strip()`ed — interpolated identically into every row (`xml_coordinator.py:387/634/805`). Order therefore lives in the corpus **as plain text the model reads**, not as structure any parser depends on. One-step is safe **provided** (a) corpus and serving `.txt` regenerate together from the same list, and (b) the retrain runs after, never before — which §4 step 3 already requires.

⇒ **§6 downgrades from "unverified hazard" to "safe with two named preconditions."** The author's fear was real about order-as-text, and harmless given (a) and (b).

> ⚠️ **A scoping error the cascade caught, recorded because it nearly propagated.** The Manager relayed Maya's **serving-scoped** verdict to Stage 3 as an unqualified *"decided upstream: safe in one step."* Krishna rejected the framing: §2.4 is the **training corpus**, a different surface from serving reachability, and per §1.1 a silently-shrunk list bakes into the next LoRA. He was right, and the over-broad relay was the Manager's, not Maya's. **The revision below exists because Stage 3 refused an upstream handoff that had flattened two surfaces into one.**

**Revisions accepted**

1. **Add a diff-and-confirm gate.** Diff the old and new command lists; assert the delta equals a **checked-in, hand-declared expected-drop constant**. Neither of Clayton's two preconditions detects a *membership* change — they cover regeneration order and retrain sequencing. Nothing else in the plan proves a drop was intended.

2. **Disambiguate "the list."** §2.4 must reuse §2.2's command-**name** list and let the corpus builder re-wrap in its own 8-space XML. It must **not** reuse §2.2's formatted `.txt` lines — different scaffolding. As written, the implementer would guess.

3. **No fresh registry read in §2.4.** Reading the registry again would make the corpus builder a *third* derivation of "what exists" — the exact shape parent row `30483697` exists to eliminate.

## 4. Cross-section ratification — the one decision Rick made

**Escalation Trigger 1 — foundational.** Raised by Krishna (§A Stage 3), sharpening Clayton's Stage 2 finding.

**The finding**: `speakable` has no correctness oracle. Nothing can prove the list is right, because which commands the router should offer is a human design judgement.

**Why it was foundational** — it exposed a gap in Rick's own 2026-08-15 ruling:

> *one registry is the source of truth; GENERATE what can be generated, TEST what cannot.*

`speakable` is **neither**:

- **Cannot be generated** — trap 3 forbids deriving it from the current template. That would make the generator reproduce today's file by construction and turn §2.3's pin test into a tautology — the *third* killed on this row.
- **Cannot be tested** — no oracle exists for "is this the right set of speakable commands?"

It fell between the two halves of the ruling.

**Rick's ruling, verbatim (2026-08-16)**:

> "Ratified list, pinned by a drift test (Recommended) — You name the speakable commands once, or rule that María derives them; the list is checked in; the test proves the prompt file has not DRIFTED from that ratified list."

**What this settles**

1. `speakable` gets a **third disposition** the original ruling had no slot for: not generated, not tested — **ratified and pinned**.
2. The test's claim becomes honest. It proves **no drift from a decision**, not that the decision is correct. A test claiming the latter would have been the fourth unfalsifiable assertion on this row.
3. **It absorbs Clayton's silent-drop finding.** The ratified list is where the dropped command gets named on purpose, and Krishna's expected-drop constant belongs in the *same* ratified decision — so no membership change can land unratified.

**A correction to the input plan's own headline, from the author.** §1 framed the 18-vs-19 as *"Two lists, no shared parent, and they already disagree."* On reviewing the ruling, María corrected herself: **it is not drift.** The single difference is a **documented START exemption**. The plan overstated the problem it exists to solve — worth fixing before the framing gets quoted onward as evidence of drift.
