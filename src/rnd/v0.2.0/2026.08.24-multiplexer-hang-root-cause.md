# The two hanging multiplexer tests — root cause, and it is one cause, not two

**Author**: Tiberius 👑 · **Date**: 2026-08-24 · **Status**: ANALYSIS ONLY — nothing from the
TypeScript tier was executed
**Row**: `f8055be3` · **Related**: [`2026.08.24-ts-oom-addendum-kernel-dump-evidence.md`](2026.08.24-ts-oom-addendum-kernel-dump-evidence.md), [`2026.08.23-typescript-test-runner-oom-hazard.md`](2026.08.23-typescript-test-runner-oom-hazard.md)

---

## The finding in one line

**33 transports are started across the two files and never stopped.** Each one leaves an
inherited handshake→backoff→reconnect loop running on **real** timers for an expected **~440
seconds**. `node --test` waits for the event loop to drain before printing its summary, so the
files pass every assertion and then sit there.

The row's hypothesis — *"an open handle keeping the event loop alive — an uncleared timer, an
un-closed socket or WebSocket mock"* — is **correct**, and this names which handle, in which
object, and why nobody notices.

---

## 🔴 Two sentences to carry away before anything else

**1. Counting timers in a FILE is not counting timers in a CLASS.**
`AudioTransport.ts` contains zero `setTimeout`. It is not timer-free — it `extends
BaseTransportImpl`, which owns every timer involved. That one fact is why this looked like two
independent problems needing two investigations, and it is one problem with one fix. Detail in §2.

**2. A completed `npm test` run is NOT evidence the hang is fixed.**
Expected hang is ~440 s against door 1's `timeout 900` cap, and `backoffDelayMs` is
`Math.random()`-driven with a range reaching 681 s. So the current outcome is a **coin toss**, not
a reliable hang. Anyone who runs it once, sees it finish, and concludes the leak is gone has
measured the dice. Detail in §3.

## 2. It is ONE cause, not two — `AudioTransport` inherits the timers

> ⚠️ **A correction to my own first read.** `AudioTransport.ts` is 82 lines and contains **zero**
> `setTimeout`, `setInterval` or `clearTimeout`, and I concluded from that the two hangs must have
> different causes. **Wrong, and the next line of the file says so:**
>
> ```ts
> export class AudioTransportImpl extends BaseTransportImpl implements AudioTransport {
> ```
>
> `BaseTransportImpl` lives in `QueueTransport.ts:90` and owns `backoffTimer` (`:105`),
> `handshakeTimer` (`:106`) and `stop()` (`:156`). `AudioTransportImpl.start()` calls
> `super.start(sessionId)` (`AudioTransport.ts:61`), so it arms **exactly the same watchdogs**. It
> does not override `stop()` either — it inherits the correct one and the tests simply never call
> it.
>
> Counting timers in a file is not counting timers in a class. Recorded because the row treats the
> two files as separate work (*"find the open handle in each file"*), and they are one fix.

## 3. The loop, and why it outlives a five-minute cap

`stop()` is **not** buggy. It cancels both timers, drops the lifecycle subscriptions, and stops
the channel and the state machine. The defect is entirely that it is not called.

Left running, one transport cycles:

```
start() → arm handshakeTimer (10s)
        → no auth_success ever arrives in a unit test
        → onHandshakeTimeout() force-closes the socket
        → socket_close → backoff → scheduleBackoff(): setTimeout(backoffDelayMs(attempt))
        → backoff_expire → reconnect → openSocket → arm handshakeTimer (10s) → …
```

until `csm.attempts >= maxAttempts` (`QueueTransport.ts:349`).

| constant | value | where |
|---|---|---|
| `HANDSHAKE_TIMEOUT_MS` | 10,000 ms | `QueueTransport.ts:51` |
| `DEFAULT_MAX_ATTEMPTS` | **20** | `QueueTransport.ts:34` |
| `BACKOFF_BASE_MS` | 1,000 ms | `ConnectionStateMachine.ts:51` |
| `BACKOFF_CAP_MS` | 30,000 ms | `ConnectionStateMachine.ts:52` |
| `backoffDelayMs(a)` | `random(0, min(1000·2^a, 30000))` | `ConnectionStateMachine.ts:64` |

Only **3** of the 29 tests pass `maxAttempts: 10`; the rest inherit the default of 20.

Expected life of one un-stopped transport:

```
handshake watchdogs   20 × 10s                 = 200 s
backoff (expected)    Σ min(1000·2^a,30000)/2  = 240 s
                                          TOTAL ≈ 440 s   (7.3 min)
range, because backoffDelayMs is random:  200 s … 681 s
```

### This predicts the measurement in the row

The row records `RC=124` under `timeout 300` **and** under the older uncapped `tsx --test` shape.
An expected ~440 s hang is **always** killed by a 300-second cap. ✅ Consistent.

⚠️ **And it predicts something about `package.json` nobody has stated.** Door 1 carries
`timeout 900`. An expected ~440 s hang usually finishes *under* 900 s — but the range reaches
**681 s** and `Math.random()` makes it **non-deterministic**. So once the leak is fixed the
question is moot, and until then `npm test` is not reliably-hanging or reliably-passing: it is a
coin toss weighted by randomness the suite does not control. **Do not read a single completed run
as proof the hang is gone.**

---

## 4. The fix, and the one that would hide the bug

**Fix**: stop the transport in teardown. `stop()` already does the right thing, so this is
per-test cleanup, not new production code — e.g. collect each started transport and stop them in
an `after`/`afterEach` hook, or `try/finally` around each body, matching the pattern the file
*already uses correctly* for `mock.timers` (`try { … } finally { mock.timers.reset(); }` at
`:478/:511` and `:592/:602`).

**Do NOT reach for `--test-force-exit`.** The row already says this and it is right: it would kill
the process at the end of the run regardless of what is still open, hiding an un-closed resource
in the transport code under test. The transports here are leaked *by the tests*, but the same flag
would mask a genuine leak in `BaseTransportImpl` later.

## 5. What this does and does not say about the OOM

🔴 **This is NOT the allocator.** Row `d84839ae` remains open on that question and the standing
ban on the tier is unchanged.

What it does add is a mechanism connecting the two: an un-stopped transport reconnecting on a
timer for 7+ minutes is **live, allocating work** — each cycle constructs a fresh mock socket and
pushes lifecycle events onto an `EventBus` that nothing drains. 33 of them run concurrently. That
is a plausible *contributor* to suite-level memory pressure.

⚠️ **Plausible is not proven, and it does not fit the fatal file.** The two 08-23 single-file
kills ran `arg_interview.test.ts`, which imports **no transport at all** (its whole graph is
`node:test`, `node:assert/strict`, `@happy-dom/global-registrator`, `arg-interview.js`). And the
kernel dump shows the allocator reaching **218.8 GiB in one process** — far more than 33 mock
sockets plausibly account for. **Recorded as a lead about suite pressure, explicitly NOT as the
cause of the deaths.**
