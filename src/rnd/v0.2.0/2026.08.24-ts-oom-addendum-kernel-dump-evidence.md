### 🔴 The consequence, stated plainly in BOTH directions

**Every kill for which kernel evidence exists came through the uncapped hand-run door
(`npx tsx --test`).** Therefore:

- ❌ **Do not read this as "`npm test` is safe."** No kernel-dumped kill is attributable to it.
  Absence of evidence here is absence of *evidence*, not of danger — and door 1 runs the same
  119 files through the same runner.
- ❌ **Do not read this as "`npm test` is proven dangerous" either.** Nothing in this dump
  touches it.

⇒ **What `npm test` does is UNKNOWN.** It stays banned on the parent survey's standing rules,
which are about the tier and not about any one door. A ban that quietly narrowed to "only the
hand-run form is risky" would be this addendum being *misread into* a safety claim it does not
make.

Two facts fall out, and each removes a hypothesis:

1. **Exactly one of the three node processes ballooned.** The runner parent and npm's wrapper sit
   at ~10 MiB. Under `--test-concurrency=4` there would be up to four workers; there is **one**.
   ⇒ The allocator is a **single node:test worker — one test file's process**. That is reachable
   by running one file, exactly matching the 08-23 single-file deaths.
2. ⇒ **One worker alone is sufficient to take the box** — 89% of a 251 GiB machine. Whatever
   concurrency is set to, the per-worker ceiling is the thing that matters, and there is none.

## 4. It is NOT the V8 JavaScript heap — which changes what a fix must be

V8's default old-space ceiling is roughly **4 GiB**, and V8 aborts with *"JavaScript heap out of
memory"* on reaching it. This process reached **218.8 GiB — about 55× that ceiling — without V8
throwing.**

⇒ The memory is **external to the JS heap**: `Buffer` / `ArrayBuffer` / typed arrays, or a native
allocation. V8's limit does not govern it and V8's error never fires.

**The consequence for whoever fixes this is concrete:**

- ❌ `--max-old-space-size` would **not** have bounded this. It caps the JS heap, which is not
  where the memory went.
- ✅ Only a **cgroup `MemoryMax`** bounds external allocation.

And measured today: **no door sets any heap cap at all** — `grep` for `max-old-space-size` and
`NODE_OPTIONS` across `package.json`, `run-typescript-tests.sh` and `test_suite/job.py` returns
nothing. So no Node-level bound existed either way; the point is that adding one would have been
the *wrong* fix, applied confidently.

## 5. The caps that WERE applied send SIGTERM only

Separate from the above, and established purely by reading the invocations:

| Door | Invocation | `--kill-after`? |
|---|---|---|
| 1 | `package.json:17` — `timeout 900 node --test-concurrency=4 …` | **no** |
| 2 | `run-typescript-tests.sh:154` — `exec timeout "$TS_TIMEOUT_SECS" npx c8 … node …` | **no** |

`grep -cE '--kill-after|timeout +-k'` returns **0** for both.

`timeout N` without `-k` sends **SIGTERM and nothing else**. Node services SIGTERM *in JavaScript,
on the event loop* — a process thrashing in GC never yields a turn, so the handler never runs.
SIGTERM is a request; only SIGKILL is unconditional.

Door 2 has a second, independent problem: `timeout → npx → c8 → node`. `timeout` signals its
**direct child** (`npx`), three levels above the process doing the work, and orphaned grandchildren
keep counting against the `user@1001.service` PSI pressure that `systemd-oomd` fires on.

**Recommended (NOT applied — this row is analysis-only):** add `-k 30` to both doors; better, move
the cap so it wraps `node` directly, or use process-group signalling. ⚠️ **Neither makes the tier
safe to run.** They make a runaway *stoppable*. The standing ban is unaffected.

### 5.1 🔴 A correction to my own first draft — the CPU arithmetic proves nothing

My first pass argued that kill #3 consuming **388s of CPU under a `timeout 300` wall cap** was
arithmetic proof the cap never fired. **That was wrong, and it nearly went to Rick that way.**

The journal attributes that figure to `run-r93f5bac…scope`:

```
Aug 23 16:06:34 systemd[1251]: run-r93f5bac…scope: Consumed 6min 28.168s CPU time.
```

That scope is created by `start-cc-with-tmux.sh:338` (`systemd-run --user --scope`) and wraps the
**entire Claude Code seat** — which is why oomd reports killing **30** and **52** processes in it.
The CPU figure is therefore the seat's total across Claude, the MCP servers and tmux, **not the
test's**.

⇒ **The 388-vs-300 arithmetic is not evidence about the cap.** It is also why the parent survey's
observation that two seats died "at nearly the same point" (403s vs 388s) should be read as an
**artifact of two similar Claude Code seats**, not a signature of the workload. §5 stands on the
invocation reading alone, which needs no help from that number.

## 6. Suspect demoted: register-without-unregister has zero discriminating power

The parent lists this first under *KNOWN but NOT explained*, calling it *"suspicious, not proven"*.
Measured across all 119 `*.test.ts` files under `src/` today:

| | count |
|---|---|
| import `@happy-dom/global-registrator` | **74** |
| call `GlobalRegistrator.register()` | **74** |
| call `unregister()` | **0** |

**All 74 of 74 fail to unregister.** A property every file shares cannot explain why one file kills
and another survives. As a discriminator it is dead. It may still add *suite-level* pressure; it
does not explain a single-file kill, and §2 shows the single-file shape is the one that matters.

### A trap for whoever fixes it

`GlobalRegistrator.unregister()` is **async** — `static unregister(): Promise<void>`, documented as
*"Closes the window"*. A repair with a braced body,

```js
after(() => { GlobalRegistrator.unregister(); });   // ← fires it, never awaits it
```

drops the promise: the window is not closed and the fix reads as applied while changing nothing.
The hook must **return** the promise — concise arrow form, or an explicit `return`. Worth a comment
at the first call site, because this is the kind of repair that gets pasted 74 times.

## 9. What is still open — the next reader starts here

The search is now bounded. What remains:

1. **Which test file's worker was pid 674727?** Its comm is the bare string `node`, so the dump
   does not say. ⚠️ But **comm CAN carry a command line** — pid 674692's is `npm exec tsx --`,
   which is how the invocation was identified at all (§2). So the technique is worth repeating on
   any other dump: read the *whole* trailing name field, not the first token. For this dump the
   remaining leads are the shell history of the seat that ran it and the parent `bash` at 674689.
   Needs **no execution**.
2. **What allocates externally?** §4 says `Buffer`/`ArrayBuffer`/typed-array/native, not JS heap.
   The 17 files calling `vm.runInThisContext` on a ~20,900-line source string are the obvious
   place to look **on that specific evidence** — compiling a large string is external work — but
   the parent survey already measured that `arg_interview` uses **zero** `runInThisContext`, so it
   cannot be the whole answer.
3. **Is there a growth curve?** A single sample at death cannot distinguish a fast leak from an
   unbounded single allocation. `MemoryHigh` reclaim events in the journal might.
