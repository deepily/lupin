# The v2 `/api/v2/ask` "slowdown" is the todo agent's normal cost, not a degrading model server

**Date**: 2026-08-17 · **By**: John (🏄🏽, session 3619a192), implementer on Mr. Radio's crew
**Row**: d8d019f6 (P1 — the v2 go/no-go paired median-Δ gate) · **Commit**: 740a0ea6 (the timeout fix this doc justifies)
**Evidence**: `io/v2-flow/trace-2026-08-17.jsonl` — 1,162 completed v2 calls, 983 of them in today's two long runs

## Verdict

There is no model-server degradation to fix. The ~64-second calls that looked like a machine
slowing down are `agent router go to todo`, which costs about 65 seconds per cache-miss
inference **deterministically**, at any point in a run. The n=60 closer `ts-1686ce29` died on a
read timeout because the old 120s wall sat too close to a routine 65-second call, not because
anything was getting worse.

The wall is now 300s (`ASK_READ_TIMEOUT_SECONDS`, commit 740a0ea6) — 4× headroom over the
slowest call that has ever completed.

## What the trace says

Splitting today's 983 completed calls at 30 seconds:

| | slow (>30s) | fast (≤30s) |
|---|---|---|
| count | 171 | 812 |
| `t_router` median | 0.02 s | 0.22 s |
| `t_agent` median | 0.85 s | 0.95 s |
| `t_first_useful` median | **64.51 s** | 1.09 s |
| path | `agent` ×171 (100%) | receptionist 420 · agent 302 · replay 84 · needs_input 6 |
| command | **todo ×165** · calendar ×6 | calculator 181 · automatic 177 · math 101 · todo 55 |

Routing and dispatch are fast in both buckets. The entire difference lives between `t_agent`
(0.85 s) and `t_first_useful` (64.5 s) — inside the agent's own generation. And every slow call
is one of the two agents whose response schema is a full code block (`CodeResponse`): todo and
calendar. Same model as the fast agents (`kaitchup/phi_4_14b`), same prompt size (~1,000 tokens),
different output length.

## It is generation, not a stall

A tight band around 64 s could be a fixed timeout. It is not. Fifty-seven todo utterances ran
three or more times each, and each one repeats its own cost within about two seconds:

```
n=3  median 68.22s  spread 66.23-68.97   "how many item are leave to purchase on my grocery sh…"
n=3  median 67.95s  spread 67.71-69.84   "how many decoration are leave to buy as per my event…"
n=4  median 67.73s  spread 66.94-69.57   "update save $200 monthly status in personal goal…"
```

A stall does not reproduce per-utterance. Real generation does. There is also no ~60 s timeout
constant anywhere in the v2 or agent path. And 55 of the 220 todo calls came back under 30 s —
those are the cache-hit replays, which is exactly what a real inference cost looks like when the
cache absorbs it.

## Why it *looked* like degradation

`stratified_sample` groups the sample by command, so todo utterances arrive in a block. Whole
stretches of the run are therefore slow and whole stretches are fast, and the pattern oscillates
rather than trending. The clearest refutation is the tail: the last twelve calls before the run
died were 8–13 seconds each — the arm was perfectly healthy at the moment it was killed.

```
14:15:05  11.19s  calculator      14:15:24  10.30s  calculator
14:15:13   8.44s  math            14:15:34  10.26s  calculator
                                  14:15:45  10.85s  math   <- last row; client gave up shortly after
```

## The one thing this does not explain

Nothing in 983 completed calls exceeded **73.85 s**. The request that blew the 120 s wall left no
trace row at all — rows are written at `t_complete`, so that call never finished server-side
within the client's patience. It is a genuine outlier, not a point on the trend, and I cannot say
from the trace whether the server eventually finished it. A 300 s wall gives it four times the
room the slowest completed call needed, which is the most the evidence supports doing about it.

## Run budget for the re-run

Corpus `simple` at `n_per_command=60` is 300 utterances across five commands. Projected v2-arm
wall from the measured medians, assuming every call is a cache miss (the pessimistic case):

| command | n | measured median | projected |
|---|---|---|---|
| `agent router go to todo` | 60 | 64.36 s | **64.4 min** |
| `agent router go to math` | 60 | 10.21 s | 10.2 min |
| `agent router go to calculator` | 60 | 4.55 s | 4.5 min |
| `agent router go to automatic` | 60 | ~1.0 s | 1.0 min |
| `none` | 60 | ~1.0 s | 1.0 min |
| | | | **≈ 1.35 h** |

Todo is 80% of the v2 arm's cost. Add the warm pass (mostly cache hits) and the v1 arm
(~6.7 s/push × 300 ≈ 33 min) and the ~3 h observed wall is accounted for. If the run ever has to
fit a shorter window, the lever is todo's share of the sample — but that changes what the sample
measures, so it is a decision for the row's owner, not a knob to turn quietly.

## What changed in code

`src/scripts/v2_eval.py`:

- `ASK_READ_TIMEOUT_SECONDS = 300.0` — a named constant carrying the measured reason above.
  `HttpAskClient`'s default reads it.
- `_default_client_factory` passes it explicitly and honors `LUPIN_V2_ASK_TIMEOUT_SECONDS`, so a
  run can move the wall without a code edit. The live run builds its client through the factory,
  so the factory is where the budget has to land.

Three controls, each proven RED on revert (see 740a0ea6):
`test_http_ask_client_read_timeout_survives_a_slow_inference` ·
`test_default_client_factory_read_timeout_default_and_env_override` ·
`test_clean_v2_snapshot_store_truncates_after_both_guards` (commit assertion).

## Side finding: a control that had never run

`src/tests/unit/test_v2_eval.py` was RED at HEAD. Commit 9b90ae5d added `connection.commit()` to
the v2 clean step and described a unit control asserting it, but never gave `_FakeConnection` a
`commit()` method — so the test died on `AttributeError` and the assertion it was written for has
never executed once. Fixed in 740a0ea6: the fake records commits (and stores SQL as a string,
because 291fb3fa wraps the statement in `text()` and a `TextClause` compared with `==` builds an
expression instead of answering True or False). The three refusal controls now assert
`committed == 0` alongside their existing `executed == []`.
