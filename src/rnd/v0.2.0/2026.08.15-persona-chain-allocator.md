# Persona-chain allocator — walk-in-order vs bail-at-first-miss

**Investigator**: Arnold 🪨 (`ca8fbfcc`, lupin seat)

**Store row**: `462b985c`
**Reporter**: Rachel 🕊️ — spawned reviewer seat 2 with `persona_preference` chain Krishna → Sasha; got neither; wildcard allocated Tiffany.

## Verdict

**The allocator walks the chain in order and falls through only on genuine unavailability. It does NOT bail at the first miss. There is no allocator bug.**

The "strong coincidence" of two named entries failing in one spawn dissolves once you look: only ONE of them was ever a valid request. **Sasha is not a pool persona at all** — so its failure was guaranteed, not coincidental. Krishna was genuinely occupied by a live session. The wildcard then did exactly its job.

---

## The code — it loops the whole chain

`cosa/rest/voice_persona_helpers.py:1101-1134`, `allocate_persona_chain_for_session`:

```python
for element in chain:
    if element == PERSONA_CHAIN_WILDCARD:            # "*" → random from free pool
        persona = allocate_persona_for_session( ... )
        ...return ok (wildcard_used=True)
    result = allocate_requested_persona_for_session( config_mgr, stable_session_id, element )
    if result is None:                               # ONLY pool_error short-circuits
        return { "status": "pool_error", ... }
    if result[ "status" ] == "ok":
        return { ...satisfied_by: element... }
    outcome = { "name": element, "status": result[ "status" ] }   # occupied | not_in_pool
    outcomes.append( outcome )                       # record the miss and CONTINUE
    ...
return { "status": "exhausted", ... }                # only if chain ends with no "*"
```

The loop advances to the next element on every `occupied` / `not_in_pool` outcome. The single short-circuit is `pool_error` (an empty/misconfigured pool — `result is None`), which is a server misconfiguration, not a per-name miss. So "bail at first miss" is structurally impossible here; the walk records each miss in `outcomes` and proceeds.

`allocate_requested_persona_for_session` (`:703-773`) scans live bridges for occupancy (excluding the requesting session's own current allocation, so a swap works) and returns `pick_requested_persona`'s status — `ok`, `occupied`, or `not_in_pool`.

## What is actually worth fixing (upstream, not the allocator)

The allocator is correct; the request was malformed and the failure was silent.

- **`Sasha` is not a configured persona.** The chain degraded past it with a `not_in_pool` outcome, but nothing surfaced "you asked for a persona that does not exist" back to the spawning manager. The `outcomes` list carries `{"name":"Sasha","status":"not_in_pool"}`, yet the spawn result Rachel saw showed only the final Tiffany allocation.
- **Recommendation**: have `spawn_sessions` (or the allocate endpoint's caller) log/return the `outcomes` list when the satisfied element is not the chain head — so a manager who typo'd a name or picked a non-pool persona sees *why* each preferred name was skipped, instead of inferring an allocator bug from a surprising result. This is a visibility fix, not a logic fix.
- **No code change to `allocate_persona_chain_for_session` is warranted.** Its walk, its outcome records, and its loud `exhausted` (chain with no `*`) are all correct.

**The degradation is not fully silent today — but it never reaches the spawner.** The allocate router already builds the per-entry story and pushes it:

`cosa/rest/routers/voice_persona.py:481-503` — on `wildcard_used and outcomes`, it fires a `voice_persona_conflict` notification: *"Persona chain 'Krishna,Sasha,*': Krishna is held by session cc-3237…, Sasha is not in the configured pool. Allocated Tiffany via the wildcard instead."*

Two limits on that existing surface:
1. **It targets `authenticated_user_id`** (`:497`) — the human user's notification UI. The **spawning manager** (Rachel's session) reads the `spawn_sessions` MCP *return value*, which carries none of this.
2. **It fires only on the wildcard path.** Landing on a later NAMED element is treated as expressed intent and stays silent (by design).

**Why the manager can't get it synchronously.** `spawn_sessions` transports the chain CSV into the child's env (`session_spawner.py:453-455`) and returns immediately; the child allocates its persona later, in its own SessionStart hook. Spawn is fire-and-forget — the outcome does not exist yet when the manager's call returns.

**Recommended fix, split by what is knowable when:**

| miss type | knowable at spawn time? | fix | where |
|---|---|---|---|
| **not_in_pool** (the Sasha case) | **Yes** — pool membership is static config | validate each named chain element against `load_persona_pool_from_config` **before** spawning; return the unknown names in the manager's own `spawn_sessions` result | `lupin_mcp/session_spawner.py` (may import the pool loader from `cosa/rest/voice_persona_helpers.py` — same repo) |
| **occupied** (the Krishna case) | No — a live race, only known after the child boots | already surfaced to the human UI (`voice_persona.py:481-503`); optionally also route that `voice_persona_conflict` payload to the spawning manager | router (already built) |

The high-value half is the first row: "Sasha" was a typo/unknown name and should have been caught **synchronously, in Rachel's own spawn result**, with zero dependence on the child booting. That closes the actual complaint — a manager inferring an allocator bug from a surprising persona — without touching the allocator, which is correct.

### Implemented (Rachel redirect, 18:09) — thread the EXISTING outcomes, do not re-derive

Rachel corrected the approach: do NOT add a validation pass in `session_spawner.py` that recomputes which names are unknown — that manufactures a second copy of a fact the allocator already computes, the exact drift this crew is removing elsewhere. Instead thread the outcomes the walk already produced through to the caller-visible result, matching the `memento_outcomes` pattern (`session_spawner.py:1064`, principle at `:1004`: an outcome you cannot see is the same as one that did not happen).

**Root cause, refined.** `allocate_persona_chain_for_session` already returns `outcomes` + `satisfied_by` and *does* distinguish a degraded landing from a clean hit. The drop is at the **router's 200 body**: it forwarded only `chain_conflict`, which is wildcard-only by design (`voice_persona.py:427`). So a chain that names a **nonexistent** persona and then lands on a later NAMED element (e.g. `Frobozz,Rio` → `Rio`) returned a body byte-identical to a clean `Rio` hit — the `not_in_pool` skip vanished. A typo is a caller error, not the "expressed intent" the silence rule was written for.

**Fix** (`cosa/rest/routers/voice_persona.py`, 3 edits, all threading the existing list — no re-derivation):
- declare `chain_outcomes = None` beside `chain_conflict`;
- on chain success, set `chain_outcomes = { satisfied_by, wildcard_used, outcomes }` from `chain_result` — always, not only on the wildcard path;
- add `"chain_outcomes"` to the success `JSONResponse`.

`chain_conflict` and its human notification are untouched; this is additive visibility on the result.

**Test** (`tests/unit/test_voice_persona_request.py::test_chain_nonexistent_name_then_named_hit_is_distinguishable`): posts `Frobozz,Rio` and `Rio`, both land on `Rio`, and asserts the two response bodies are **not** equal — the degraded one carries `outcomes == [("Frobozz","not_in_pool")]`, the clean one `outcomes == []`.

- full file, natural order: **59 passed with the fix vs 58 on clean HEAD** — exactly one test added, no regression.
