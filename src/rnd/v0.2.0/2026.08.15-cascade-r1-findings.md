## Item 1 — §5.4 "retraining buys RELIABILITY, not REACHABILITY"

**VERDICT: SOUND. The claim survives. The defect is clarity, not citation.**

### The measurement, as it actually reads

Source: `src/rnd/v0.2.0/2026.08.14-cj-flow-v2-phases-2-3-and-evaluation.md:626-649` (row `d9ecd69e`, measured 2026-08-14).

- **Design**: one probe, **two arms, n=10 utterances each**, one invented command (`agent router go to recipe finder`). Prompt template modified **in memory against a copy** — the shared dev-server file was never touched. Script at `scratchpad/router_vocab_probe.py`.
- **Arm A** — command **listed in the prompt**: emitted **10 / 10**.
- **Arm B** — control, command **absent from the prompt AND from the 19-command training vocab**: emitted **6 / 10**.
- Control-arm spread (`:640`): 6 `recipe finder`, 1 `none`, 1 `presentation generator`, 1 `claude code`, 1 `todo`.

### Both numbers are real — they are two arms of the same probe

My first DM called this a "wrong-arm citation." That was my error. **6/10 is the genuine control-arm result**; **10/10 is the listed-in-prompt arm.** Neither is a misprint. The doc's §5.4/§9 name only "6 of 10," which is what invited the misread — including mine.

What each number measures:
- **10/10 (Arm A)** = the effect of *listing a command in the prompt*. This is the path the design ships (registry → generated prompt). It is the direct support for **"reachable the moment the prompt lists it."**
- **6/10 (Arm B)** = the effect with the command listed **nowhere**. It proves the *stronger, more surprising* fact — **the router invents commands from the `agent router go to <thing>` pattern; its vocabulary is not closed.**

### Does "reliability not reachability" survive the correction?

**Yes — it survives, and the correction strengthens it.**

- **Reachability** is established by Arm A = 10/10: once the prompt lists a command, the router emits it. The generated-prompt path delivers reachability without any retrain.
- **Reliability** is what the retrain adds: Arm B shows that *even absent from every list* the command fires 6/10, so the vocabulary was never the gate — the retrain moves a command from "fires sometimes" toward "fires dependably." That is consistency, not capability.
- Therefore **letting the retrain lag is safe**: the shipped path is the 100% arm, not the 60% one. The §9 self-worry — *"6 of 10 is not a reliability figure anybody would ship against"* — argues against a number the design never ships against. Nobody ships on the control arm.

The evaluation doc reaches the identical conclusion independently at `:647-663` ("Listing a command raises reliability 6→10. It does not create the capability").

### The one real limitation (name this, not the 60%)

The genuine soft spot is **statistical power, not the 6/10**: the whole asymmetry rests on **n=10, one invented command, one topic**. 10/10 at n=10 has a wide confidence interval (~69% lower bound) and there is **no evidence it generalizes across all agentic commands**. If the fast-path reachability story is ever challenged, this — not the control-arm percentage — is the gap to shore up (more commands, more utterances).

### Required action

- **Clarity fix in §5.4/§9**: state both arms of the one probe (listed 10/10, control 6/10) and attribute reachability to the 10/10 arm, reliability to the delta. Do **not** rest the reachability claim on "6 of 10."
- Optional hardening: widen the probe (more commands / larger n) before treating the asymmetry as settled for the whole agentic set.
- **No design change required.** The phasing (§7) and the "retrain may lag" stance stand.

## Item 2 — §5.1 does the new `CommandClass` field carry its weight?

**VERDICT: SOUND, claim slightly overstated. `cls` is NOT a fifth hand-maintained list.**

Code read: `src/cosa/rest/v2/registry.py:82-116` (the four bucket constants) and `src/cosa/agents/runtime_argument_expeditor/agent_registry.py:22-48` (AGENTIC_AGENTS rows).

### What the existing data can and cannot distinguish

Every `AGENTIC_AGENTS` row carries `job_class_path` + `cli_module` (`agent_registry.py:24-26`). The nine conversational/control/none commands are **absent** from `AGENTIC_AGENTS` by design (§3, confirmed).

- **AGENTIC vs everything-else**: **fully derivable today** from `AGENTIC_AGENTS` membership (equivalently, presence of a `job_factory`). A new field is **not required** for this split.
- **CONVERSATIONAL vs CONTROL vs NONE**: **not derivable from any agentic signal** — all three lack a job, a CLI, and an `AGENTIC_AGENTS` entry. Today they are told apart **only** by which hand-maintained frozenset they sit in: `V2_AGENTS` (`registry.py:82`), `CONTROL_COMMANDS` (`:111`), `RECEPTIONIST_OR_NONE` (`:116`).

### Why the "carries its weight" claim is slightly overstated

§5.1 sells `cls` on the completeness-test assertion *"agentic appear in all four sources, conversational in two."* That specific assertion needs only the **agentic / not-agentic** split — which is **already derivable** from `AGENTIC_AGENTS` membership. So `cls` is not strictly required for the sentence the doc uses to justify it.

`cls`'s **real, defensible** job is the finer three-way split among the non-agentic commands (§6 assertion #3, "control and none appear in prompt + training only"), which no agentic signal can produce — and turning a fragile derived-**negative** ("absence from `AGENTIC_AGENTS`") into an explicit positive label.

### It is NOT a fifth list

§5.1.2 (lines 180-184) **derives all four bucket constants FROM `cls`**. So `cls` replaces four hand-maintained frozensets with one field per spec: **net 4 → 1, fewer hand-maintained lists, not more.** The "fifth list" worry does not apply.

### The one real drift seam `cls` opens (recommend a cross-check)

If `AGENTIC_AGENTS` **survives** the migration — and §5.1.1 keeps `ArgSpec.from_entry( AGENTIC_AGENTS[cmd] )` reading its rows — then **`cls == AGENTIC`** and **`AGENTIC_AGENTS`-membership** become **two sources for the same fact**. That is exactly the drift this whole design exists to eliminate. **Recommendation**: the completeness test (§6) must assert the two agree — every `cls == AGENTIC` command is in `AGENTIC_AGENTS` and vice versa. Cheap; closes the seam `cls` introduces.

### Required action

- Keep `cls` — it earns its place on the CONTROL/NONE/CONVERSATIONAL distinction and the 4→1 consolidation.
- Soften §5.1's justification: the agentic/conversational split alone does **not** need a new field; the finer non-agentic split does.
- **Add** to §6: an assertion that `cls == AGENTIC` and `AGENTIC_AGENTS` membership are the same set, so the two cannot drift.
