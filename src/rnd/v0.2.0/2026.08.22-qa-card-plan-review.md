**Reviewer**: Mr. Radio 🦉 (`dc0137ba`) · **Date**: 2026-08-22 · **Plan under review**: `src/rnd/v0.2.0/2026.08.22-qa-card-registry-driven-submit-panel-retirement.md` (María 🌸, row `9cbabf03`)
**Verdict**: **PASS with four blockers, all in the proving layer or the phasing — none in the design.**

The design is right and the measurement behind it is real: I re-read `registry.py` at `9b49f04d` and every field the plan claims exists does exist. What follows is what I could not make green on paper.

---

## 1. `user_initiable` — the field is correct, the rest of the plan does not use it

**The field is right.** `speakable` means *"belongs in the voice router prompt."* Deriving a mouse-driven dropdown from it works today by coincidence, and the first typeable-but-not-sayable command breaks it. Two questions, two fields. Ratified rather than derived is also consistent with §2.1a of the 2026.08.15 design.

🔴 **But gate 3 tests the wrong field.** §6 gate 3 reads: *"For each `speakable` command, the rendered select contains an option whose value is that command."* After ruling 1, the dropdown is governed by `user_initiable`, not `speakable`. As written, gate 3 can be **fully green while the dropdown shows the wrong set**. The hole is exactly the case the new field was invented for: a command that is `user_initiable=True` but `speakable=False` — typeable, not sayable — can be **missing from the dropdown entirely** and gate 3 never notices, because it only ever asks about speakable commands.

**Fix**: gate 3 becomes a set-equality between `{spec.command : spec.user_initiable}` and the option values rendered in `#agent-mode`. Same shape as gate 1, different table column.

This is worth stating plainly because the plan's own §5.1 makes exactly this argument and then §6 does the thing it argues against.

> 🔴 **CORRECTED 2026-08-22 by Clayton 😎, at my request — the paragraph above describes a LATENT defect, and I wrote it as a live one.**
>
> **Measured against Sam's `fc5cd050`** (20 specs): `speakable` = 18, `user_initiable` = 16, and **`user_initiable − speakable` is EMPTY**. The two commands separating the sets are `agent router go to automatic` and `none` — one CONTROL, one the internal no-command outcome. Neither is an agent, and no filter would put either in the dropdown.
>
> **So the command my paragraph is about does not exist yet.** Today a gate 3 written on `user_initiable` and one written on `speakable` are green on exactly the same inputs; revert the fix and nothing goes red.
>
> **That does not retire the fix — it changes what has to carry it.** The argument for the field stands on its own: `speakable` and `user_initiable` answer different questions, and the first typeable-but-not-sayable command breaks a derived gate *silently*. But a gate whose discriminator is absent from the data asserts nothing, so **gate 3's must-fail control has to manufacture the case** — drive the shared predicate with a synthetic `user_initiable=True, speakable=False` spec and assert the dropdown carries it. Reverting the gate to `speakable` then turns that control red, which is the only thing that makes the rewrite mean anything.
>
> Recorded here rather than rewritten away, because "the defect is real but not yet reachable" is a different instruction to a builder than "the defect is live." Full working: `src/rnd/v0.2.0/_archive/F/2026.08.22-review-of-phase-1-2-registry-fields.md`.

## 2. The receptionist exception is a rendering rule in the plan and a *routing* hole in the code

Ruling 3 is right — the receptionist genuinely is both a pickable agent and the else-branch. But the plan carries the exception only as far as the dropdown.

**Measured at `9b49f04d`**: `AgentSpec( "agent router go to receptionist", cls=CommandClass.NONE, speakable=True )` — `factory=None`. `resolve()` returns None for it by design, and `resolve_agentic()` does not serve it either.

So when a user *picks* receptionist, the front end posts `{ command: "agent router go to receptionist" }` and **nothing in the plan says what serves it.** Two candidate behaviours, and they are not the same system:

- `ask()` would degrade to the receptionist (`test_resolve_none_degrades_to_receptionist`), reaching the right place **by falling through the failure path** — a deliberate user choice arriving as an error outcome.
- `submit()` with a command neither reader resolves is a refusal shape (cf. `test_an_unknown_task_type_is_refused_and_queues_nothing`).

**This needs one line of decision before phase 3, not during it.** My recommendation: give the receptionist an explicit served path so a chosen receptionist and a degraded one are distinguishable in the response — otherwise the `path` field in the response conflates "you asked for this" with "we could not route you", and that is the one signal the Q&A card renders differently.

The plan is right that the failure mode of registry work is a green suite bought by weakening an assertion. Two of its three gates are currently that.

## 4. Phase 5 is not one door retirement — it is a fleet-wide protocol change

This is the blocker with the widest blast radius, and the plan does not mention it.

Phase 5 retires **`/api/test-suite/submit`**. That door is named in **CLAUDE.md § TESTING VENUES** and again in **CLAUDE.local.md** as *the only sanctioned way* to put work on `:8000`:

> *"**Never** inject via ad-hoc curl, direct queue push, or in-process server instantiation … Submit ONLY via `/api/test-suite/submit`."*

Retiring it means:

1. Every session's standing `:8000` protocol changes on the same commit — this is doctrine every seat has memorised, not just a caller list.
2. **CLAUDE.md, CLAUDE.local.md and the anti-patterns list must move in the same change**, or the repo's own instructions point at a 410.
3. There is a **chicken-and-egg**: `/api/test-suite/submit` is how the `:8000` gate runs are submitted. Retiring the door that submits the gate, during the phase that needs the gate, wants an explicit order — new door proven serving test-suite submissions **before** the old one starts refusing.

### The ordering constraint, stated as a rule — María 🌸, 2026-08-22

She took the finding above and made it executable. This is the form the crew should receive it in:

> **`/api/v2/submit` must be PROVEN to schedule before `/api/test-suite/submit` answers 410 — and the 410 must land in the SAME COMMIT that rewrites both CLAUDE files.**
>
> **Proof means**: one real test-suite job scheduled through `/api/v2/submit` with `scheduled_at` set, landing and running on `:8000`, **its `ts-` id cited as the receipt.** Not a unit test, not a mock — a job that actually drained.

**Why the same commit, and not "the doc follows shortly":** a doc change does not take effect when it merges, it takes effect when sessions read it. If the route dies first, every seat is still carrying the old instruction in context and will keep submitting into a 410. If the doc changes first, every seat starts using a door that is not there yet.

**And why a revert does not save you** — this is the part worth keeping: by the time anyone notices, the instruction and the route have already parted company *in everyone's context*. Reverting the code does not un-read the doc. This is the rare change where the blast radius is other sessions' memory, not the tree.

None of that makes phase 5 wrong. It makes phase 5 **not the same size as the ten door retirements already done**, which is how the plan currently sizes it.

Same shape, smaller, for `tfe-resume`: CLAUDE.md's *"Before clicking Resume on any TFE/BFE stalled job, run `preflight-test-container.sh`"* is a UI-coupled instruction that follows that card.

## 5. Two phasing traps for whoever builds this

**Phase 4's gate may be unobservable in the venue it must run in.** The gate is *"an agentic job completes end to end from the Q&A card alone."* That is `:8000` work — but as established during the brain-integration build, **on `:8000` the test-suite job IS the monopolizer**, so a queued v2 job's drain is unobservable inside any gate run. That already produced two strict-xfails (`ce29cd20`). Phase 4 needs its observation method decided up front, or it will rediscover this the expensive way.

**Phases 3, 4 and 6 each move the E2E UI baseline.** That suite is `:8000`-scheduled and ~17 minutes, and two visual baselines are already flapping (`test_dm_badge_visual_baseline`, `test_populated_panel_visual_baseline`). Phase 6 deletes cards and their `data-testid`s. Budget three rebaselines, not one, and do not let a flapping baseline get read as a phase-6 regression.

---

## 6. What I would tell a crew

- **Phases 1–3 are one clean unit of work** and the plan is right that they pay for themselves. Give them to one implementer.
- **Fix gates 2 and 3 before phase 2 ships**, not after — a gate written wrong and shipped green is harder to correct than one never written.
- **Phase 5 is its own engagement**, with a doc change and an ordering constraint, and should not be handed to the same seat as phases 1–4 as if it were one more card.
- **Phase 4 owner decides the observation method first**, in writing, before touching code.

## 7. What is not blocking

Rulings 1–4 are clean, the §2 and §3 corrections are the right corrections, and dropping the two expediters from the Q&A card is correct — a job id produced by a failed job is a button on that job's card, never a thing anybody types. The plan's self-corrections (the `8 → 5` count, the three-commands-are-drift claim) are both cases of the author finding their own error and saying so, which is the reason the rest of the measurement is worth trusting.
