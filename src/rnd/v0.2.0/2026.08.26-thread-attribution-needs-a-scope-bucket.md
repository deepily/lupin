## The verdict in one line

The tool reports **thread name** and nothing else, so 2,085 lines of module-scope declaration code
sit in its attribution column pretending to be findings — **88% of them under one thread whose name
invites an allow-list.** The fix is a third bucket, not an exclusion. Separately: **`tasks.py`'s 399

## 1. What the tool does TODAY (recorded, not proposed)

Two files, both in `src/scripts/`, both unchanged by this doc.

### `thread_attribution_plugin.py` (73 lines)

A pytest plugin. `threading.settrace` + `sys.settrace` install a line tracer; every first-party line
is recorded under the name of the thread that executed it.

```python
def _tracer( frame, event, arg ):
    if event != "line": return _tracer
    fn = frame.f_code.co_filename
    if PREFIX not in fn or "/tests/" in fn or "site-packages" in fn:
        return _tracer
    with _lock:
        _hits[ threading.current_thread().name ][ fn ].add( frame.f_lineno )
    return _tracer
```

Output shape: `{ "<thread name>": { "<file>": [line, ...] } }`

⚠️ **There is no scope information in the record at all.** A `class Foo:` statement and a line
inside a `while` loop are stored identically. Nothing downstream can tell them apart, because the
distinguishing fact was never captured.

### `detect_thread_credited_coverage.py` (168 lines)

Reduces the map to lines only a non-test thread reached. The whole filter is `exclusive_lines()`:

```python
TEST_THREAD = "MainThread"

def exclusive_lines( attribution, allow_threads ):
    test_lines = { fn: set( ls ) for fn, ls in attribution.get( TEST_THREAD, {} ).items() }
    findings = {}
    for thread, files in attribution.items():
        if thread == TEST_THREAD or thread in allow_threads: continue
        for fn, lines in files.items():
            gained = sorted( set( lines ) - test_lines.get( fn, set() ) )
            if gained: findings.setdefault( thread, {} )[ fn ] = gained
    return findings
```

**One dimension, one escape hatch.** The dimension is the thread name; the escape hatch is
`--allow-thread NAME`, an all-or-nothing exemption of a whole thread. **Module-scope lines flow
straight into `findings`** — there is no bucket for them, no flag that separates them, and no
column in the report that would let a reader notice them.

⇒ **This is the current state Mr. Radio asked to have on the record: module-scope lines are inside
the attribution column, indistinguishable from findings.**

## 2. Why that is wrong (Mr. Radio's correction, and it revises my own claim)

I had called the 1,840 module-scope lines under `AnyIO worker thread` "the same defect as
`session-id-watcher`, 24× bigger." **That was wrong and this doc corrects it.**

A module-scope line — `class Foo:`, `@dataclass`, `name : str`, `MODEL_PRICING = {` — executes
**once, on import**. It is covered by *any* import from *any* thread. There is no test that could
assert on a `def` statement, and no arrangement of tests that would leave it uncovered while the
module is imported at all.

**So the discriminator has nothing to say about it.** "Does a test start the thread and assert on
its work?" is not a question that applies to a declaration. Such a line is:

- **not a defect** — it is not propping up a coverage number with unasserted logic; and
- **not earned** — no test drove it.

It is a **third category**, and a two-bucket tool has nowhere to put it, so it lands in the wrong one.

### The measurement that settles it

Every credited line in the 8-chunk sweep, classified by whether it lies inside a function body
(call-time) or not (module-scope):

| Thread | total | module-scope | call-time |
|---|---:|---:|---:|
| `AnyIO worker thread` | 2,464 | **1,840** | 624 |
| `session-id-watcher` | 77 | **0** | 77 |
| `v1-ws-listener` | 34 | **0** | 34 |
| `tok-B` | 19 | **0** | 19 |
| `tok-A` | 17 | **0** | 17 |
| `dm-grade_0` | 8 | **0** | 8 |
| **whole sweep** | **7,580** | **2,085** | **5,495** |

**Two things this shows, and the second is the one that makes the change safe:**

1. **`AnyIO worker thread` holds 1,840 of the 2,085 module-scope lines — 88%.** It is not a general
   problem sprinkled across the report; it is one thread. The next largest contributor is a single
   portal at 228/245.
2. **Every adjudicated thread is 100% call-time.** `session-id-watcher`'s 77 lines are all inside
   the watcher loop body. **Bucketing module-scope separately changes no verdict that has been
   reached** — the defect stays at 77, exactly where it was. A filter that removes only noise is
   the shape you want; this one is measurably that.

### Why `AnyIO worker thread` is the one that collects them

Not a guess — confirmed in the tree. `agentic_job_factory.py` imports **inside** its builder
functions rather than at module top:

```python
def _build_podcast_generator( command, args_dict, ... ):
    from cosa.agents.deep_research.job     import DeepResearchJob      # line 228
    from cosa.agents.podcast_generator.job import PodcastGeneratorJob  # line 231
```

A test hits a **sync** endpoint → FastAPI runs it through `run_in_threadpool` on the AnyIO worker
thread → the lazy import cascade fires **there** → every module-level line of the podcast and
deep-research packages is credited to that thread. Whole files arrive at once, at 100% module-scope:

```
149/149  deep_research/narrowing_mocks.py    136/136  podcast_generator/state.py
113/113  podcast_generator/orchestrator.py   107/110  podcast_generator/config.py
 95/95   deep_research/state.py               88/88   deep_research/cost_tracker.py
```

⇒ **The thread name is not a proxy for how a line was reached.** `AnyIO worker thread` sounds like a
request and is 75% import cascade. That is precisely why allow-listing it on the TestClient story
would have been wrong — it would have blessed 1,840 declaration lines as tested.

## 3. The change — ✅ BUILT 2026-08-26

### 3a. Capture scope in the plugin

The plugin cannot classify at trace time without paying for it — but it does not need to. The frame
already knows: a module-scope line executes in a frame whose `co_name` is `"<module>"` (and a class
body's is the class name). Recording that one string alongside the line is O(1) and adds no parse.

```python
# PROPOSED — not applied
_hits[ threading.current_thread().name ][ fn ][ frame.f_code.co_name ].add( frame.f_lineno )
```

Output becomes `{ thread: { file: { scope_name: [lines] } } }`. **This changes the JSON shape**, so
`detect_thread_credited_coverage.py` and any saved sweep JSONs move together with it.

**Cheaper alternative, no format change**: leave the plugin alone and classify in the detector by
parsing each file's AST once, exactly as the throwaway script in this analysis did. Slower per run,
zero migration, and it works on the sweep JSONs already on disk. **Recommended for a first cut** —
the format change can follow if the per-run parse cost shows up.

### 3b. Three buckets in the detector

`exclusive_lines()` returns one map. It should return three, or one map with each line tagged:

| Bucket | Meaning | Belongs in the verdict? |
|---|---|---|
| `call_time` | inside a function body, non-test thread, absent from MainThread | **YES — this is the finding** |
| `module_scope` | declaration executed on import | **NO — reported separately, never in the count** |
| `allowed` | thread on `--allow-thread` | NO — already the current behaviour |

**Bucket, do not exclude.** Dropping module-scope lines destroys a real signal: *which modules were
imported only from a worker thread* is worth being able to see, and it is exactly what surfaced the
lazy-import cascade above. A bucket costs one dictionary key; an exclusion costs the finding that
made this doc possible.

### 3c. The exit code must key on `call_time` only

Today `main()` fails on any non-empty `findings`. With buckets, **the verdict is `call_time` alone** —
otherwise the tool still fails on declarations and the change is cosmetic.

### 3d. What NOT to do

- ❌ **Do not allow-list `AnyIO worker thread`.** 624 of its lines are genuine handler execution
  (§4). A thread-level exemption would hide them along with the noise, and thread-level is the only
  granularity the current flag has.
- ❌ **Do not exclude module-scope at trace time.** The plugin would then be unable to answer "was
  this module imported anywhere but the main thread", which is the question that found the cascade.
- ❌ **Do not treat `--allow-thread` as the remedy for a mixed thread.** It is all-or-nothing by
  construction; a thread carrying both classes needs the scope split, not an exemption.

### ⚠️ A method trap, recorded because it is the same trap as §2 one level down

My first pass at this over-counted, reporting call-time lines in files §2 had shown to be 100%
module-scope. Cause: it credited a function's **`def` line and decorators** to that function's body.
**A `def` statement executes at import** — it creates the function object — so it is module-scope by
the same argument that governs a `class` statement. Only the statements in `node.body` are
call-time. Re-running with the strict definition gave exactly **225**, reconciling with §2's figure.

⇒ **Any implementation of §3 must use `node.body`, not the `lineno..end_lineno` span.** The span is
the intuitive reading and it is wrong, quietly, in the direction of over-reporting findings.

thread a test starts deliberately, whose work that test then asserts on. The coverage is real; it
simply did not happen on the test's own thread.
