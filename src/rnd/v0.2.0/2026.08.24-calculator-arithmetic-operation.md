# CalculatorAgent gets a real arithmetic operation

**Row**: `11af54f8-f1fe-4b7e-87a8-353c5129dbe2` (P2) · **Author**: Krishna 🦚 · **Date**: 2026-08-24

## What changed

`CalculatorAgent` now has a first-class `arithmetic` operation. Before this, its declared
operations were `convert` / `compare_prices` / `mortgage` / `unsupported` — there was no
way for it to add two numbers. Arithmetic questions the router sent to the calculator were
answered by handing the whole question to `MathAgent`. The calculator was a waypoint.

Measured from `io/v2-flow/eval-2026-08-21-11-37-48/records.jsonl`: 166 utterances were routed
to the calculator, and the arithmetic ones among them ("How much is 789 minus 456?", "What is
the product of 64 and 23?", "the total of 34, 67, and 129") all took that detour. Every answer
was correct — this removes a detour, it does not fix a defect.

## The shape

| Piece | Where |
|---|---|
| `arithmetic( operands, operator )` | `src/cosa/agents/calculator/calc_operations.py` |
| `operator` + `operands` fields, `get_operands_list()`, `VALID_OPERATORS` | `src/cosa/agents/calculator/xml_models.py` |
| `arithmetic` route + `_format_arithmetic_for_voice()` | `src/cosa/agents/calculator/dispatcher.py` |
| `## Operation: arithmetic` section; arithmetic removed from the `unsupported` list | `src/conf/prompts/agents/calculator.txt` |

`operands` is a JSON array rather than the existing `value` / `value_2` pair because the corpus
contains genuinely n-ary questions — "the sum of 98, 134, and 201" is three numbers, not two.

`add` and `multiply` are n-ary. `subtract`, `divide`, `modulo` and `power` fold from the left,
so `[100, 20, 5]` with `subtract` is `(100 - 20) - 5 = 75`. Order matters for those four, and the
prompt says so explicitly: "Subtract 299 from 450" is `[450, 299]`, not `[299, 450]`.

Integral results come back as `int`, so the voice line says "333" and never "333.0".

## What deliberately did NOT change

The row warned that the three `_delegate_to_math_agent()` call sites in `agent.py` are not the
same thing, and that deleting all three would send unparseable questions nowhere. **All three
survive untouched.** `agent.py` has no edit in this change at all — `arithmetic` simply never
reaches a delegation site, because `dispatch()` handles it. The fallbacks that remain:

1. `_fallback_to_math` — the LLM returned something that is not parseable as a `CalcIntent`.
2. `operation == "unsupported"` — algebra, geometry, trigonometry, calculus, statistics.
3. `convert` with empty or unrecognized units — the LLM guessed `convert` for something else.

`TestDelegationSitesSurvive` in `src/tests/unit/test_calculator_mock_pipeline.py` pins all three.

## Falsification

The row asked for a test that is red by construction before the change and asserts the
CALCULATOR produced the answer. `TestArithmeticPipelineMocked` does that: it patches
`CalculatorAgent._delegate_to_math_agent` and asserts it is **not called**. Before the change all
six failed with `Unknown calc operation 'arithmetic'`.

Five mutations were applied to the shipped code, each proven to have landed before the run:

| # | Mutation | Result |
|---|---|---|
| M1 | `agent.py` sends `arithmetic` back to `MathAgent` (restores the detour) | killed — 6 failed |
| M2 | `subtract` silently becomes `add` | killed — 1 failed |
| M3 | `dispatcher.py` drops the `arithmetic` route | killed — 6 failed |
| M4 | `get_operands_list()` always returns `[]` | killed — 6 failed |
| M5 | divide-by-zero guard disabled | killed — 1 failed |

Harness: `scratchpad/mutate.sh` (backup → mutate → grep-prove → run → restore).
