## (b) Collapse state — 11/11, attacked with hostile storage

`probe.js`. The shape is exactly what was reported:

```
localStorage["lupin.epicBoard.groupState"] == {"epic:seal-the-test-tier":true}
```

a **map**, not an array, and it survives the reload path (`loadEpicGroupState` →
`_epicGroupIsExpanded`). What I fed it, and what happened:

| Hostile input | Behaviour |
|---|---|
| an ARRAY `["epic:a","epic:b"]` | rejected → `{}` (explicit `Array.isArray` guard) |
| garbled JSON `{not json` | `{}`, no throw |
| `null` payload | `{}` |
| non-boolean values (`"yes"`, `1`) | dropped; only the boolean survives |
| `{"__proto__":true}` | no prototype pollution |
| `localStorage.getItem` **throws** (private mode) | `{}`, no throw |
| `localStorage.setItem` **throws** (quota) | swallowed, render unaffected |
| **unknown key** | falls through to `_epicDefaultExpanded` → closed. Does not throw |

The choice-map decision is load-bearing and correct: a newly-minted epic is
absent from the map, so it takes the closed default rather than inheriting a
stale set's membership.

## (d) Auth — refused without a key, same guard object

`probe_auth.py` (TestClient, no curl) mounts the router and asks without
credentials:

| case | `/api/epic-stories` | `/api/tasks` |
|---|---|---|
| no key | **401** | 401 |
| wrong `X-API-Key` | **401** | 401 |
| junk `Authorization: Bearer` | **401** | 401 |

The refusal leaks no story content. The dependency is the **same callable
object** `require_api_key_or_jwt` on both endpoints, verified through the
`Annotated` metadata rather than by eyeballing the decorator.

🔎 **Worth knowing**: the author's own `test_epic_stories_endpoint.py` calls
`tasks_router.get_epic_stories( AUTHED )` **directly**, which bypasses the
dependency — so the DoD line "behind the same auth guard" was asserted
structurally and never exercised until now. The guard is right; the test for it
was not a test of it.

## DEFECT (minor) — the outage banner leaves a stale epic count beside an empty pane

`notifications.js:10682` — the `unreachable` branch of `renderEpicBoard` clears
the table but does **not** reset `#epic-board-count`.

**Reproduction** (`probe-degrade.js`; plain objects stand in for elements, so no
real DOM is involved):

```
good render      → body = <table>…                                    count = "2"
store goes down  → body = "⚠️ Store unreachable — showing nothing…"    count = "2"   ← stale
```

The other two error branches in the **same method** (`auth_required`,
`query_unavailable`) both reset it to `"0"` — controls in the probe, both PASS.
So this is an omission, not a policy. The method's own docstring says it
"mirrors the task-list card's four states so the two panes degrade identically",
and here it does not: the task list replays last-known rows and keeps a coherent
count, while the epic board shows nothing under a header claiming N epics.

**Fix**: one line — `if ( countEl ) countEl.textContent = "0";` in that branch.

**Untested at every tier**: the Playwright check at
`test_epic_board_card.py:577` asserts only that the container text contains
"unreachable"; it never looks at the count. Worth adding when that suite becomes
runnable.

## NIT — two distinct epic keys can collide into one element id

`_epicGroupIdSlug` maps every non-`[A-Za-z0-9_-]` character to `-`, so
`epic:a-b` and `epic:a:b` both become `epic-group-epic-a-b` — a duplicate `id`
and a duplicate `aria-controls`. **Not functional**: the accordion toggles off
`tbody.dataset.epic` (the raw key), and the persisted choice map is keyed on the
raw key too. HTML-validity and screen-reader correctness only, and it needs an
epic slug containing punctuation, which none of the fourteen has today.
