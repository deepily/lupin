## The defect

`pair_records` joins the two arms on **`row_index`** — the position in the *draw* — not on
**`frozen_index`**, the position in the frozen snapshot. It compares the two index *lists* and raises
when they differ (`:552-559`).

Two draws of the same size always produce identical `row_index` lists (`0..N-1`). So the guard
passes, and the function pairs rows that are **different bodies**.

## Proof — ran it, using the harness's own functions

```
arm A frozen indices: [25, 114, 281, 654, 759]      # --seed 42
arm B frozen indices: [39, 147, 292, 712, 780]      # --seed 43

pair_records RAISED? no — it returned 5 paired rows

  row_index 0: phi_4 body BODY-25   vs flash_lite body BODY-39
  row_index 1: phi_4 body BODY-114  vs flash_lite body BODY-147
  row_index 2: phi_4 body BODY-281  vs flash_lite body BODY-292
  row_index 3: phi_4 body BODY-654  vs flash_lite body BODY-712
  row_index 4: phi_4 body BODY-759  vs flash_lite body BODY-780

SAME BODY in every pair? False
```

Every McNemar cell built from that is a comparison of two different populations — precisely what
plan §3 exists to prevent, and what the freeze was built for.

## How it is reached, without anyone doing anything odd

`--arm` is a supported mode (`:634`): *"run one arm only; omit to run both."* So:

```
python -m …replay_harness --arm phi_4       --sample-size 400 --seed 42
python -m …replay_harness --arm flash_lite  --sample-size 400 --seed 43      # or a re-freeze between
```

`--seed` carries a **default** (`20260817`, `:627`), so the seeds need not even be passed explicitly
for the two runs to diverge — a re-freeze between the two invocations changes the population, and I
verified the same seed against a different population draws different rows.

Within ONE invocation the draw happens once before the arm loop (`:649-650`, `:664`) and both arms
walk the same list — that part is correct and I confirmed it. **The pairing guarantee simply does not
extend across two invocations, and nothing says so.**

## The fix is one line, and the field already exists

`frozen_index` was added in `69394217` for exactly this reason — the commit message says it:
*"row_index is the position in the DRAW, and the moment you sample, the two stop being the same
number."* It is then not used as the join key.

```python
a_key = [ r.get( "frozen_index", r[ "row_index" ] ) for r in arm_a_records ]
b_key = [ r.get( "frozen_index", r[ "row_index" ] ) for r in arm_b_records ]
```

(Written with `.get` only because records from an unsampled run may predate the field; if every
record carries it, use explicit access per the no-defensive-getattr rule.)

Also worth closing: the docstring's `Requires: both lists came from the SAME frozen snapshot` is a
precondition **nothing checks**. Each arm's records could carry the snapshot sha256 from the manifest,
and `pair_records` could refuse a mismatch — then the guarantee is enforced rather than requested.

## Test that must go with it

Two draws, same size, different seeds → `pair_records` **raises**. That test fails today and is the
only proof the fix works; the existing pairing test uses one draw, so it cannot see this.
