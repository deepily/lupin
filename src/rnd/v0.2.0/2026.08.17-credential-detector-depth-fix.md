## What was wrong

The parsed branch asked `key in parsed` — the top level of the object and nothing
else. Six shapes carried real credential material past it. Clayton measured them;
I reproduced all six independently before touching anything.

| # | shape | why it walked through | now |
|---|---|---|---|
| 1 | `client_secret_<...>.json` as the **GCP console downloads it** — every field under `"installed"` | top level only | BLOCK |
| 2 | the same download, `"web"` variant | same | BLOCK |
| 3 | a service-account key nested under a config wrapper, no PEM header | same | BLOCK |
| 4 | a credential inside a **JSON array** | arrays were rejected outright before any field was read | BLOCK |
| 5 | a real ADC whose signature sits **past the 8192 window** behind a big leading field | the truncated branch needs the signature inside the window | BLOCK |
| 6 | a truncated object whose key is spelled with **JSON `\u` escapes** | that branch scans raw text, so the escaped key is a different string | BLOCK |

Shape 1 is the one to lead with: it is not a contrived nesting, it is the file
Google hands you when you create an OAuth client, and nesting is its normal shape.

## What changed

Four things, in `src/cosa/rest/routers/_scope_registry.py`:

1. **`_parsed_value_carries_a_credential`** — walks the parsed value with an explicit
   stack over objects *and* arrays, applying the field test at every object. An
   explicit stack, not recursion, so there is no depth cap to tune and no crash on a
   deeply nested document. Closes 1–4.
2. **`_the_window_may_be_hiding_the_signature`** — the read widens once, to
   `CREDENTIAL_MAX_SNIFF_BYTES` (1 MiB), and only when the first window was *filled*
   by something opening a JSON container. Closes 5. Both stages stay bounded.
3. **`_decode_json_unicode_escapes`** — puts `\uXXXX` escapes back before the
   truncated branch scans raw text. Closes 6.
4. The truncated branch now recognises `[` as well as `{`, so a truncated array of
   credentials is a truncated credential file.

## The false-positive trade, decided rather than discovered

Clayton flagged this before I started: once the search goes to any depth, a bare key
NAME cannot be enough to refuse on, or every OpenAPI spec documenting an OAuth flow
becomes a credential.

**`_value_is_secret_material` is the answer**: a credential field counts only when its
value is a non-blank string that is not a syntactic placeholder. A spec carries an
object under `client_secret`; a template carries `<your secret>`, `${CLIENT_SECRET}`
or `{{ client_secret }}`; a credential carries the secret itself.

This is a **shape test, not a vocabulary list** — no word has to be guessed in
advance, and a real secret cannot be written in placeholder form and still be the
secret. Cost of the choice, stated plainly: `{"private_key": {...}}` with an object
value is now served where it was refused before. A key's `private_key` is always a
string, so that is a schema, not a key.

## The accepted limit

A JSON container larger than 1 MiB whose only credential material sits past that mark
is **SERVED**. Closing it means refusing every large JSON document on the grounds that
it might be hiding something, which costs more than it buys.

This is pinned by `test_a_credential_past_the_SECOND_window_is_SERVED_and_that_is_the_stated_limit`,
so it stays a decision on the record instead of drifting back into an assumption — the
same failure the old docstring had when it asserted the signature "sits well inside"
the window.

## What the widened read costs

`is_credential_file` is called once per file-fetch request in
`docs_files.py:379`, not once per directory listing. So the second read costs at most
1 MiB of extra reading on a request for a JSON document that is larger than 8 KB, and
nothing at all on every other request. Nobody pays it while browsing.
