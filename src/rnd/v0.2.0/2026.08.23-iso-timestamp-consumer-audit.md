# Who actually reads these timestamps? An audit before swapping `utcnow()` for `now( timezone.utc )`

**Date**: 2026-08-23 · **Author**: John 🏄🏽 · **Rows**: `3b4002fe` (the deprecation cleanup) · `63506bd0` (the live expiry defect found inside it)

## The verdict, first

`datetime.utcnow().isoformat()` emits `2026-08-24T01:45:00.123456` — **no offset**.
`datetime.now( timezone.utc ).isoformat()` emits `2026-08-24T01:45:00.123456+00:00`.

Every remaining site emits one of those into something that a browser later parses. So the
swap is **not cosmetic**: it changes what the reader believes the instant is.

⇒ **And it changes it in the RIGHT direction.** These are not sites where a swap risks
breaking a working display. They are sites where the display is **already wrong** and the
swap is what fixes it. Two exceptions, both named below, where it would break something.

## The rule, and this repo already wrote it down

`src/lupin_app/static/js/notifications.js:9432-9436`, in a docstring, about a different field:

> NAIVE TIMESTAMPS ARE UTC — a genuine cross-language trap. The Python twin does
> `chase_ts.replace( tzinfo=timezone.utc )` for a naive value, while
> `Date.parse( "2026-07-22T14:00:00" )` (no zone) resolves as LOCAL time. Left alone, the two
> twins would disagree by the operator's UTC offset — silently, and only for zone-less rows.

And `:9458-9460` compensates for it, by hand, for **one field only**:

```js
const hasZone  = /(?:Z|[+-]\d{2}:?\d{2})$/.test( trimmed );
const chaseMs  = Date.parse( hasZone ? trimmed : `${trimmed}Z` );
```

⇒ So the trap is known, was hit once, and was patched at exactly one call site. Every other
consumer below calls `new Date( value )` raw.

## The sharpest one: two adjacent lines disagree

`src/cosa/rest/user_service.py:137-138`

```python
"created_at"    : user.created_at.isoformat() if user.created_at else None,
"last_login_at" : datetime.utcnow().isoformat()  # Just updated
```

`created_at` is read off a `TIMESTAMPTZ` column, so it comes back **aware** and serialises
with `+00:00`. `last_login_at` on the very next line is **naive** and serialises without one.
Both land in the same dict, and the admin users table renders both through `new Date( … )`.

⇒ **On one row of one table, one column is right and the column next to it is wrong**, and
nothing about the code says so. That is the whole audit in two lines.

## What to do

1. **Swap the notification `timestamp` sites and `user_service.py:138`.** These fix a live
   display shift. Land them with a test that asserts the emitted string carries an offset —
   not one that asserts the string equals a literal, which would just re-freeze whichever
   spelling is current.
2. **Leave `csv_writer.py:137` alone, or swap it AND drop the `+ "Z"`.** It is the one place
   the naive spelling is load-bearing. A blind sweep over "class 1" corrupts it.
3. **`create_service_account.py` is free either way** — nothing parses it programmatically.
4. **Consider deleting the client-side compensation at `notifications.js:9460`** once the
   server stops emitting zone-less strings — but only after, and only with the regex kept as
   a tolerance for old rows already in the store.

⇒ **The reason this was worth an audit rather than a sed**: the same one-line change is a
bug fix at five sites, a no-op at three, and a new bug at one. Nothing in the call site tells
you which — only the consumer does.
