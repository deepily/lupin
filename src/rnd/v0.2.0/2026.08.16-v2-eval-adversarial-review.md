## Blocking findings

### B1 — auth KeyError crashes the scheduled run before any measurement *(Sam's catch; Mr. Radio confirmed the run died here)*

`_default_client_factory` (v2_eval.py:1052) reads `reply.json()[ "access_token" ]`. The real `/auth/login`
returns the token nested under `tokens` — `LoginResponse` (auth.py:328), and **every** real test reads
`data['tokens']['access_token']` (test_auth_endpoints.py:53). So the live `:8000` run raises `KeyError`
at auth, before a single utterance is sent.

**Why 55 green tests missed it**: `test_default_client_factory_logs_in` (test_v2_eval.py:530) fakes the
login reply as `{ "access_token": "jwt-123" }` — the *wrong shape* — and asserts `client.bearer == "jwt-123"`.
The test mocks past the seam, so it is green over the bug. **A green tier vouching for a false mock.**

**Fix (two edits, not one)**:
1. v2_eval.py:1052 → `reply.json()[ "tokens" ][ "access_token" ]`
2. test_v2_eval.py:530 fixture → `{ "tokens": { "access_token": "jwt-123" } }`

**Can the fixed factory be covered by a test that can FAIL?** Yes. With edit (2) alone, the test would
**fail on today's unfixed code** — that corrected fixture *is* the can-fail regression pin. Note the
`# pragma: no cover` on `__main__` (v2_eval.py:1056) claims "exercised by the scheduled :8000 run" — a run
that crashed here, so the pragma currently launders an unrun path.

### B2 — `paired_median_delta_gate` does not compute the spec's paired median Δ

Design §6 (line 122–124) specifies, per utterance over the **shared** set: `Δ(u) = v1(u) − v2(u)`, drop a
pair if either arm failed `u`, record how many dropped, and **gate = median of Δ**, restated as **≥20% of
the v1 median** (design §1 line 19: `PASS/FAIL`).

The code (v2_eval.py:577–594) computes `median(v2_spans) − median(v1_spans)` — **difference of independent
medians**, over two flat `spans` lists that carry no utterance identity and need not be aligned or equal in
length. That is a different statistic (median is not linear), the sign is inverted vs the spec
(`v2 − v1`), and there is **no ≥20% threshold and no PASS/FAIL** — it returns only `delta_ms` + `faster_arm`.
The inputs cannot support pairing even in principle.

The go/no-go latency verdict rests on this gate. The unit tests (test_v2_eval.py:643, `delta == -60.0`)
lock in the difference-of-medians behaviour, so the suite vouches for the wrong computation. **A function
named `paired_median_delta_gate` that a downstream reader will trust as "the median-Δ gate shipped."**

**Fix**: either rebuild to design §6 (pair by utterance, drop-count, median-of-Δ, ≥20% PASS/FAIL) in the
combined step — which requires the arms to carry per-utterance identity, not flat `spans` — or rename it to
what it is (an informational unpaired median comparison) so nothing reads it as the gate. Coordinate with
Rio ⚡ (row d8d019f6, gate wiring).

### B3 — the v2 arm is not seeded/stratified; the v2 report is non-reproducible

`main()` samples via `load_corpus(..., limit=args.limit)` — **first-N per command, order-dependent, no
randomness** (v2_eval.py:1005). There is no `--seed`, no `--n-per-command`, and `render_report` stamps no
seed. The v1 arm uses `stratified_sample(seed=1024, n_per_command=60)` and stamps the seed in its header
(v1_eval_arm.py:642, 556–571).

Design §5 requires "n = 60 per command, stratified, seeded … **PER ARM**" and "same seed recorded in the
report." Consequences:
- the scheduled v2 report is **not reproducible** (no seed);
- if the arms are diffed, they ran **different populations** — first-N lets the biggest command (calculator
  561 ≈ 4.4× datetime 127) dominate v2's p50/p95 and rates, the exact bias stratified sampling exists to
  remove (design §5 line 112–113), applied to v1 but not v2.

`v1_eval_arm.py`'s own docstring (line 84–85) asserts it uses "the same corpus + same seeded stratified
sampler as the v2 arm" — a parity claim that is **currently false**.

**Fix**: route the v2 arm through `stratified_sample` with `--seed`/`--n-per-command`, and stamp the seed in
`render_report`; or (if the combined step samples once and feeds both arms one shared list) build that step
and stop treating `main()`'s first-N path as the v2-arm number.

## Non-blocking (flag / question / nit)

- **N1 (comparability — flag, coordinate)**: the F1 client-send span for v1 is `send → observed-completion`,
  which **includes v1 queue dwell**; v2 (synchronous) structurally cannot incur it. Design §3 requires
  excluding v1 queue dwell or marking latency `PENDING — parity unverified`. The gate's `instrument`
  residual discloses network + serialization but **not** the dwell asymmetry. In the eval jobs run
  one-at-a-time so dwell ≈ consumer pickup (likely small) — but "likely small" is unmeasured, which is why
  §3 said print the exclusion. Fix lives partly in `v1_eval_arm`.
- **N2 (systemic — the sweep)**: every §8 field is read through `.get()` accessors (v2_eval.py:284–332) with
  **no schema assertion**, and no *executed* test drives the harness through the real payload shape — unit
  tests fabricate `_rec`/stub payloads; the only through-the-seam test (`test_v2_eval_live.py`) has never
  run (died at auth, B1). So a renamed/missing §8 key degrades silently to `None`/`0` instead of failing
  loud. B1 is the first instance of this class; the gate tests (B2) are the second.
- **N3 (nit)**: `matched_command` docstring calls `command` a replay-only field; `flow.py:_emit` populates
  `command` on every path (agent, receptionist, replay, needs_input) — routing_accuracy is correct across
  paths, but the docstring misleads.
- **N4 (question)**: trace-parity reads the day trace file after the warm pass; a non-synchronous
  `trace.write()` flush could yield a partial file → a false trace-parity violation. Verify flush semantics.
