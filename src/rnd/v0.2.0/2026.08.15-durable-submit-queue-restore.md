# Durable Submit Queue — Restart Restore for Immediate Jobs

**Row**: 2817b0f5-57eb-4b7b-8a2f-1a6194933adf (P1) · **Owner**: Rio ⚡ · **Manager**: Mr. Radio 🦉
**Date**: 2026-08-15 · **Status**: Phase 0 (design) — approved to GO by Mr. Radio

---

## 1. The bug, in one line

Bouncing the `:8000` test container loses every job that was waiting to run. On
2026-08-15 two immediate test-suite submits vanished when Cheech bounced a
wedged `:8000`.

## 2. What actually happens (confirmed, with receipts)

The four live queues (todo / run / done / dead) are pure in-memory Python —
`FifoQueue.queue_list` (list) + `queue_dict` (OrderedDict), guarded by an
`RLock`, with **no disk backing whatsoever**.

- `src/cosa/rest/fifo_queue.py:48-49` — the two in-memory structures.
- `src/lupin_app/main.py:764-767` — all four queues are re-instantiated **empty**
  on every startup.

A **durable side-ledger already exists** in Postgres — the `job_history` table,
written by `src/cosa/rest/job_persistence.py`. It is NOT the queue; it records
job *state transitions + metadata*. Crucially, it stores only these statuses:

| Persisted status | Written by | When |
|---|---|---|
| `pending` | `persist_job_created_from_metadata` (job_persistence.py:262) | on create (pending→todo) |
| `running` | `persist_job_started_from_metadata` (job_persistence.py:296) | on todo→run |
| `completed` / `failed` / `stalled` | terminal persisters | on finish |
| `interrupted` | `mark_interrupted_jobs` (job_persistence.py:496,529) | at startup |

**`queued`, `scheduled`, and `paused` are never persisted.** They are in-memory /
UI states only (`STATE_TO_UI_CONTAINER`, job_state.py:74). Every pre-execution
job — immediate, scheduled, or paused — sits in `job_history` as **`pending`**,
distinguished ONLY by whether `metadata_json` carries a `scheduled_at`.

> Note: `test_suite.py:181` writes `status="queued"` on the HTTP **response DTO**
> (`TestSuiteSubmitResponse`), not to `job_history`. The durable row is `pending`.

### The restart path today

`mark_interrupted_jobs()` (job_persistence.py:463) at startup:

- `running` rows → **INTERRUPTED** always (correct — mid-execution, unsafe to auto-rerun).
- `pending` + future `scheduled_at` → preserved.
- `pending` + `scheduled_at` inside the measured downtime window → preserved (catch-up).
- `pending` + **no `scheduled_at`** (or scheduled before downtime) → **force-INTERRUPTED**
  (job_persistence.py:526-532, comment: *"don't silently resurrect"*).

`get_restorable_jobs()` (job_persistence.py:583) then returns only `pending`
rows **that have a `scheduled_at`** (line 610), and main.py:1063-1098 rebuilds +
re-pushes those.

### Root cause

An **immediate** submit (no `scheduled_at`) is a `pending` row with no schedule,
so `mark_interrupted_jobs` force-interrupts it and `get_restorable_jobs` skips
it. It is **lost by deliberate design** — the "don't silently resurrect" branch
was written for anomalous *scheduled* misses but also swallows plain immediate
jobs that simply never got their turn before the bounce.

## 3. The RUNNING-at-bounce fork (raised to Mr. Radio)

**Resolved: keep existing behavior.** A `running` job is already marked
INTERRUPTED (never auto-rerun) — this is exactly option **B** (dead-letter,
human resubmits). Test-suite runs are monopolize-mode and mutate the test DB, so
auto-rerunning after an unclean kill risks colliding with whatever state the
bounce left. **This fix does not touch running-job semantics.**

## 4. The fix

Restore **immediate** pre-execution jobs on restart instead of interrupting
them. Two edits, plus a paused-state carry.

### 4a. `mark_interrupted_jobs()` — preserve immediate pending jobs

The `else` branch at job_persistence.py:526-532 currently force-interrupts
`pending` rows with no future/downtime schedule. Split it: a row with **no
`scheduled_at` at all** is an immediate job that never ran → **preserve it**
(leave `pending`) for re-enqueue. Keep force-interrupting only the genuinely
anomalous case (a `scheduled_at` that is *past* and *before* the downtime window
— a scheduler miss while the server was up, which we do not want to resurrect).

### 4b. `get_restorable_jobs()` — return immediate pending jobs

Drop the `if scheduled_at:` gate (line 610) so `pending` rows with **no**
`scheduled_at` are also returned. `scheduled_at` becomes `None` in the payload;
the restore site already tolerates that (an immediate job runs on next consume).

### 4c. No-resurrect guarantee — reuse the id_hash

The restore site (main.py:1075-1091) builds a **new** job via
`create_agentic_job` (fresh `id_hash`) and pushes it, leaving the ORIGINAL
`pending` row untouched — so without care the same row would be restored on
**every** boot, multiplying the job. Fix: on restore, set the rebuilt job's
`id_hash` back to the original row's `id_hash` before pushing, so the job's own
lifecycle transitions that one row `pending → running → terminal`. Once it is no
longer `pending`, no later boot re-picks it. One row, one identity, one restore.

### 4d. Paused-ness carry (the third orphan)

A user-paused job with no schedule is also `pending`+no-`scheduled_at`, so 4a/4b
would restore it as **active** (silently un-paused). But `job_history` does not
record paused-ness. Add a `paused` boolean into `metadata_json`
(`_build_metadata_json`, job_persistence.py:197-228, and a small persister on the
todo↔paused transition), and have the restore site re-push with the paused state
preserved. A restored paused job comes back paused, not running.

## 5. Test plan (100% lines/branches/functions on touched code)

Unit (`:7999`-eligible, no live server — direct against `job_persistence` +
a fake/rolled-back `job_history`):

1. **Immediate restore**: a `pending` row, no `scheduled_at`, survives
   `mark_interrupted_jobs` as `pending` and is returned by `get_restorable_jobs`.
2. **No-resurrect (Mr. Radio's ask)**: two consecutive restart cycles with the
   SAME immediate row leave **exactly ONE** queue entry; a THIRD adds none —
   proven by id_hash reuse transitioning the row out of `pending`.
3. **Scheduled unchanged**: future-scheduled and downtime-catch-up rows behave
   exactly as before (regression guard on the existing path).
4. **Anomalous scheduled miss still interrupted**: a past-scheduled-before-downtime
   row is still force-INTERRUPTED (we did not widen resurrection to it).
5. **Running still interrupted**: a `running` row → INTERRUPTED, never re-enqueued.
6. **Paused carry**: a paused immediate row restores as paused, not active.

Integration (`:8000`, final gate) — **EXECUTED 2026-08-15, PASSED.** Sequence:
bounce to deploy (only when `:8000` is verified idle AND empty — the deploy bounce
runs OLD code and would eat a live queue), submit an immediate `dry_run` `unit` job,
pause it (deterministically holds it in `todo`, and exercises the paused path),
bounce again, confirm it returns. Definitive round verdict: **visible in the user's
todo view · same id_hash · re-held paused · args preserved (`[Tests] unit`) · did
NOT run** — all true. Creds came from `~/.lupin/config` `[lupin]` via configparser
(the schedule-tests skill's fallback), not the env.

**The live run earned its keep — it caught THREE wiring defects the unit tests
(fake factory/queue) could not, each now fixed and regression-guarded:**

1. **Paused set AFTER push → consumer race.** `push()` notifies the consumer, so a
   `state = PAUSED` set after push let the consumer start the job first: a restored
   paused job RAN. Fix: set PAUSED BEFORE push. Guard:
   `test_paused_set_BEFORE_push_no_consumer_race`.
2. **Rebuilt from the wrong args.** Restore passed the whole `metadata_json` as
   `args_dict` instead of `metadata_json["original_args"]`, so a dry_run `unit` job
   came back as a REAL `integration, e2e` run (defaults). Fix: reconstruct from
   `original_args`. Guard: `test_rebuilds_from_original_args_not_envelope`.
3. **Invisible restored job.** `user_job_tracker` is not rebuilt at startup and
   restore did not register the job, so `/api/get-queue` (which filters by the
   tracker) showed the restored job as absent — present + running but unseeable and
   unresumable. Fix: register on restore via `register_scoped_job`. Guard:
   `test_registers_in_tracker_for_visibility`. (Pre-existing — the scheduled-restore
   path had it too; this fix closes both.)
