## 2. Claim A — phase 4's own gate, on `:7999`, in seconds

The feature phase 4 adds is **the inline answer box**: a `needs_input` response renders its question in the card, the answer posts to `/api/v2/resume`, and the loop repeats until the flow terminates. Nothing in that sentence requires an agentic job. It requires a command that *asks a question*.

**`agent router go to weather` is exactly that command and it runs inline.** It is conversational, it declares `required_args=("location",)`, and it is served by `resolve()` on the fast lane — no queue, no pool, no monopolizer. The full loop is observable end to end:

```
POST /api/v2/ask     { question: "what's the weather" }   → path=needs_input, pending_id, answer="What location?"
POST /api/v2/resume  { pending_id, answer: "Boston" }     → path=agent, status=done, the answer
```

That is the whole phase-4 mechanism, exercised over HTTP against a real flow, on the venue the AI may run at will. **Three tiers, same split as phase 3:**

| tier | what it crosses | where |
|---|---|---|
| **A1** | flow → HTTP: `/api/v2/ask` parks and returns a question; `/api/v2/resume` completes it | Python unit, `:7999` |
| **A2** | HTTP → DOM: a `needs_input` body renders an answer box; submitting it posts `pending_id` + answer to `/api/v2/resume` | happy-dom `.test.ts`, `:7999` |
| **A3** | the real page, real server | Playwright, `:8000` — rides the rebaseline phases 3 and 6 already pay for |

A1 and A2 are the gate. A3 is confirmation.

**What A does not prove**, said plainly rather than left to be discovered: that an *agentic* command's interview ends in a job that runs. That is B.

## 3. Claim B — and why `:8000` is no longer the dead end it was

`ce29cd20` is an xfail on **`/api/v2/ask`**. Phase 4's agentic path goes through **`/api/v2/submit`**. That distinction is load-bearing, and it is not mine — `test_monopolize_lineage_smoke_coverage.py` states it in as many words:

> *"`v2_ask.py` has three [doors] and only `/api/v2/submit` takes the field."*

The field is **`parent_id_hash`**. The consumer's Gate B admits a monopolizer's own lineage children *through* the intake hold (`queue_consumer.py:95-124`):

```python
def _is_admissible_child( j ):
    return ( getattr( j, "spawned_by_id_hash", None ) == parent
             and not getattr( j, "monopolize", False ) )
job = todo_queue.pop_next_eligible( predicate=_is_admissible_child )
if job is not None:
    break  # admitted a lineage child — dispatch it normally
```

And the sweep already hands its own id to its pytests — `test_suite/job.py:1292` exports **`LUPIN_TEST_MONOPOLIZE_PARENT_ID`**.

So the pieces exist: a lineage-aware door, a consumer that admits lineage children mid-hold, and an env var telling the child who its parent is. **"A consumer that is not the test itself" is precisely what Gate B provides** — the consumer thread dispatches the child while the hold is still active.

⚠️ **This does NOT retire `ce29cd20`.** `/api/v2/ask` has no `parent_id_hash` field, so the write-back round trip stays unobservable on `:8000` for the reason its docstring gives. Phase 4 is reachable because it uses the other door. Nobody should read this section as clearing that xfail.

### 3b. How B is written so a starve reports as the right defect

If Gate B does not admit, that is a finding about `7451bebe`, **not a phase-4 regression** — and the test must say so itself rather than relying on whoever reads the failure:

- The observable is the **conjunction María already specified**: one `/api/queue/pool-status` sample where `monopolize_inflight` is true **AND** `monopolize_id` names *my* sweep **AND** `inflight_agentic_jobs >= 1`. Her own near-miss is why the middle term exists — her first watcher read `mono=True` off *someone else's* hold and would have closed the gate on another session's job.
- A starve fails with a message naming **Gate B and row `7451bebe`**, not the Q&A card.
- **Not** "the job eventually completed." A child that runs after the hold releases looks identical from outside and is the exact failure the row is about.

### 3c. Which command B submits, and why not the obvious one

**Not `agent router go to test suite`** — a test-suite job submitted from inside a test-suite job is a nested monopolizer, and Gate B defers those on purpose (*"a nested monopolizer needs its own exclusive window"*). It would starve by design and read as a Gate B failure. That trap is worth writing down because it is the zero-required-args command and therefore the tempting one.

**`agent router go to claude code`**, trivial prompt. It is agentic, it is not a monopolizer, it takes one arg the interview can supply, and per CLAUDE.md § COST MODEL its inference is covered by the Max subscription rather than metered against the firewalled account — the cheapest honest agentic drain available.

### 3d. One constraint phase 4 inherits whether it likes it or not

`test_monopolize_lineage_smoke_coverage.py` derives its endpoint set from the routers: any door declaring `parent_id_hash` is lineage-aware, and **any test file POSTing to one must read `LUPIN_TEST_MONOPOLIZE_PARENT_ID` in code** (comments do not count — Tiberius hardened that at `00cd8a70` after his own control failed to fail). `/api/v2/submit` is in that set. **Any phase-4 smoke that submits through the Q&A path must thread the tag or an existing gate goes red.** Not a new rule; a standing one that now applies to this work.

## 4. The decision

1. **Phase 4's gate is claim A**, tiers A1 + A2 on `:7999`, with A3 riding the rebaseline. It is falsifiable, cheap, and needs no monopolize slot.
2. **Claim B is written but SEQUENCED BEHIND `7451bebe`.** It is authored against the conjunction in §3b, and it is not run — and certainly not read as green — until Gate B's live admission is either cited or observed. An unproven mechanism is not a foundation for a gate.
3. **The plan's phase-4 gate line should be re-worded** from *"an agentic job completes end to end from the Q&A card alone"* to name the two claims separately, so the next reader does not re-derive this.
4. **`7451bebe`'s status is escalated, not assumed** (§3a).

## 5. What I am least sure of

**That Gate B admits.** I read the code and the receipts and both say it should; I have not seen it happen and neither, as far as the row records, has anyone. If that turns out false, §3 is wrong and claim B goes back to being unobservable — which changes nothing about claim A, and that is the main reason for splitting them.

Secondarily: A2 asserts the answer box against a payload rather than a live flow. A1 covers the flow, A3 covers the page; the seam between A1 and A2 is a shape both agree on, which is the same structure phase 3 shipped and the same limitation.
