## 0. Verdict

**The plan's design is sound and its evidence is not.** Every structural conclusion
survived review — reuse the queues, put v2 inside the head as its brain, shadow-mode
before flipping. What did not survive is a large share of the *receipts*: line
citations, counts, and one claim taken from a code comment that is false about its own
file.

That distinction matters because this plan's stated purpose is to end a drift that
happened when **four lists were allowed to disagree with nothing checking them.**
A plan that ends list-drift cannot itself ship with a mis-stated inventory.

**Recommendation**: proceed, after the corrections below land. None of them changes the
architecture; all of them change what a builder would go looking for.

### 1.2 Enforceability — §5.1

**The test §5.1 asks for can be written, but not as specified, and the specified
version is the weak one.**

*"Assert the three chains are DELETED"* is a **source-shape** assertion. It matches a
*description* of the defect, so it goes green the moment someone rewrites a chain as a
dict, a `match` statement, or nested `if`s — **none of which removes the second
decider.** It is also blind to the fifth site by construction: you can only assert the
deletion of what you enumerated.

**The falsifiable version asserts reachability, not shape**: for every command in the
router template's emittable set, **exactly one module is capable of producing an agent
or job for it.** Two is the defect, zero is unreachable, one is the invariant. That
goes red regardless of syntax.

**What both versions sit green through** — and the plan should say so: the router
template itself. All five sites and the registry consume the same emittable set, so a
command in no list anywhere is invisible to every one of them. That is exactly the
state three commands are in today (§1.4 below).

*(Adopted — §5.1 has been rewritten to reachability.)*

### 1.3 Shadow mode — §6

Rick ruled shadow mode. The question reviewed was not the ruling but **whether it
produces the evidence it is claimed to produce.**

- **It does not, on the agentic lane.** v1 ends in a queued job with a card; v2 returns
  `route to receptionist` because those commands sit outside `V2_AGENTS`. That lane
  disagrees **100% of the time by construction**, so §6's core justification —
  *"every disagreement is either a v1 bug or a v2 bug, both worth knowing"* — **is false
  for exactly the lane §6 ordered flipped last.** *(Adopted into §6.)*
- **The conversational lane does not disagree cleanly either.** Three by-construction
  confounders: v2 replays only at 100.0 exact vs v1's confirmation-gated fuzzy replay;
  four v2-internal degrade paths all land on receptionist; and the CRUD fork sends
  `calendar`/`todo` to different agent classes on each side. ⇒ **Agreement must be
  defined on `routing_command`, not agent class**, and the log segmented by
  `route_reason`. The plan never says which.
- **The remedy the plan missed** — and the best thing produced in this review:
  **compare at the routing-decision layer, not the terminal outcome.** The
  100%-disagreement is an artifact of comparing outcomes that differ *by design*.
  *(Adopted.)*
- **…with a correction to that remedy.** v1's `_get_routing_command` (`:993`) is a thin
  shim over the module-level `get_routing_command` (`:104`), and `v2/router_client.py:13`
  imports **that same function**. So comparing the *emitted command* compares a function
  against itself — a tautology with guaranteed agreement and zero signal. **The
  comparison unit must be the RESOLVED routing decision** (bucket/agent + extracted
  args), never the emitted command.
- **The disagreement log has no owner.** By the plan's own line 166, without a named
  owner the ruling *"silently degrades into option (c)."* Stated but **not enforced** —
  the same disease as §5.1. This should be a hard gate before shadow mode starts, not a
  §8 "known gap."

### 1.6 The `started_at` defect — §8 claim 2

Verified, and worse than stated.

- All four citations exact. Nothing assigns `started_at` for `AgentBase` or
  `SolutionSnapshot`; only agentic jobs set it.
- **The guard is asymmetric**: `completed_at` is a local generated on the spot at
  `:1611` — always truthy. `started_at` is read off the job — always `""`. So the guard
  can only fail on one side, and it fails **silently to `None`**.
- **Nothing gates it.** `test_job_persistence.py:542` sets `duration_seconds = 60.0`
  then asserts it is `60.0` — it **manufactures the value it checks**.
- **Four conventions for one field**: `""`-never-assigned (`AgentBase`,
  `SolutionSnapshot`) · `None`-then-ISO-string (`AgenticJobBase` + subclasses) ·
  `Optional[datetime]` (the DB column) · truthiness-then-`.isoformat()`
  (`job_persistence:937`, `:1060`).
- **The `isinstance` guard is load-bearing, not cruft** — `claude_code/job.py:194`,
  `swe_team/job.py:203`, `bug_fix_expediter:137`, `deep_research:145` all assign an ISO
  **string**. Drop it and you break agentic duration to fix fast-lane duration.

**Agreed remedy (row `4a9ebc4b`)**: ISO-string-or-`None` in memory, `datetime`-or-`None`
in the DB, **one converter at the persistence seam**, replacing seven `isinstance`
checks and three `is-not-None` guards — landed in a single commit.

**Two conditions attached**: (a) the fix needs a test that **constructs a real
`AgentBase`/`SolutionSnapshot` and observes the field**, not one that supplies it — a
mock cannot prove an initializer, because the mock *is* the initializer under test;
(b) it stays **its own row**, not a phase of this plan.

### 1.9 §4 / §4.1 — the largest finding: `needs_input` has no second half

*Krishna's pass; the load-bearing claim re-verified independently. Full receipts:
`2026.08.15-cascade-section4-findings.md`.*

María's §8 flags §4.2 — *"these are the same design, one of them tidier"* — as her
weakest claim. **It understates it.** v2's `needs_input` is not a tidier interview;
**its second half is absent.**

**Measured:**

- `pending.put()` (`flow.py:210`) is the **only external call** into the parked-request
  store.
- `get()`, `set_status()`, `exists()` are called **only from inside `pending.py`**
  (`:126`, `:153`, `:182`) — self-calls. **No consumer anywhere in the tree.**
- The v2 router exposes **exactly one endpoint**: `POST /api/v2/ask`. **No route exists
  to answer a parked request.**

⇒ **Dead-ended twice: nothing reads the park, and there is no door to feed it.** The API
still returns `pending_id` to the caller (`v2_ask.py:54`) — a handle for a conversation
that can have no second turn. `PendingRequests` is an in-process dict in
`_ASK_FLOW_CACHE`, so even given a resume route it would not survive a bounce or a
second worker.

**And the TTL that is supposed to clean up after it is unreachable.** `pending.py:12`
states *"sweep() (and every get()) drops entries older than the TTL"* — naming both
eviction paths. **`sweep()` has no caller. `get()` has no caller.** Neither path can
fire. The store is also **unbounded** — no `max_entries`, no cap on the dict. So in a
long-lived server every `needs_input` outcome writes an entry that nothing reads,
nothing evicts and nothing caps: **slow unbounded in-process growth**, not merely a dead
feature.

⇒ The question is not whether `put()` should be called before a resume path exists — it
plainly should not. The question is **what `needs_input` should do instead**, because
returning a `pending_id` the caller cannot use is worse than returning nothing: **it
advertises a capability the system does not have.**

**And the callerless functions are fully unit-tested.** `test_v2_executor_seam.py`
exercises `get()` (`:323`, `:334`, `:340`, `:343`), TTL eviction (`:350`), and
`set_status()` (`:353-357`). Under the 100% coverage mandate they are **covered and
green**.

⇒ **Coverage measures whether a line ran, not whether anything reaches it.** A
fully-covered module that no production caller touches passes the gate while being
unreachable. These are good tests of the right behaviour — the point is that **green
coverage on `pending.py` is precisely why nobody noticed the second half was missing.
The gate reported the module healthy.**

Also: v1 **batch-asks all missing args in one prompt** (`_batch_collect_args`, 300s) or
single-asks (180s). v2 returns the first missing argument.

**§4.1 ↔ §4.3 is internally contradictory.** The `needs_input` row says *"Exactly as
today"* and *"keeps the card alive"*, while §4.3 says v2 **sheds** card lifecycle — but

#### 1.10a "Never 500s" is a convention, not a property — and §2 lists its own counterexample

*Found by María on re-check after the review closed; verified here.*

`flow.py` has **exactly one** `try`/`except`, at `:120-123`, wrapping **only**

| call | line | protection |
|---|---|---|

table.

the inline executor**. As written the claim is true of the configuration that happens to
be running.

## 2. The pattern under the findings

Six of the thirteen are the same defect wearing different clothes: **a check that
cannot fail, or a claim that was never checked.**

- a count assertion that manufactures the value it asserts (§1.6)
- a test file frozen for ten weeks inside a live merge gate (§1.7)
- a comment asserting a fact about keys nobody measured (§1.8)
- a proposed test that pattern-matches a description of the defect (§1.2)
- a comparison of one function against itself (§1.3)
- an inventory that omits a member and a step that deletes fewer than exist (§1.1)
- **a fully-covered module that no caller reaches** (§1.9) — the gate itself reporting
  healthy on unreachable code

**The plan is right that routing drifted because nothing checked the lists.** The
review's finding is that the *same habit* produced the plan's own evidence. That is not
an argument against the plan — it is an argument for the enforcement §5.1 already
demands, applied one level up.

### 2.1 But the findings split two ways, and the split is the useful part

It is tempting to say *"every defect here was invisible to a green suite."* **That is
too broad, and an overbroad lesson gets discounted the first time someone finds the
exception.**

**Group A — reachability defects no coverage tool can see.** The callerless `pending`
module, the uncounted fifth routing map, the missing resume endpoint. Each is a fact
about **what calls the code**, not what the code does. Coverage answers *"did this line
run?"*; these need an instrument that answers *"can anything reach it?"* **This codebase
has the second without the first.**

**Group B — ordinary defects a competent test would have caught, and didn't.** The
`started_at` duration bug is a fact about what the code *does*: the guard fails and
duration returns `None`. A unit test that constructs a real `AgentBase` and asserts a
duration catches it. It survived because **both test copies manufacture the input** —
that is a bad test, not a blind instrument. Same for the manufactured `60.0` assertion
and the stale twin.

⇒ **Group A needs a new instrument. Group B needs the tests we already believe in,
written honestly.** Collapsing them into one lesson lets Group B off the hook — and
Group B is the half anyone can fix today.
