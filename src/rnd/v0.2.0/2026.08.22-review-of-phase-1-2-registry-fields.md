## 🔴 The finding — gate 3's discriminator does not exist in the data

Blocker 1 said gate 3 must test `user_initiable`, not `speakable`, because *"a command that is `user_initiable=True` but `speakable=False` — typeable, not sayable — can be missing from the dropdown entirely and gate 3 never notices."*

**Measured against the implemented table, that command does not exist:**

```
speakable       n = 18
user_initiable  n = 16

speakable but NOT user_initiable:   agent router go to automatic · none
user_initiable but NOT speakable:   (none)
```

`user_initiable` is a **strict subset** of `speakable`, and the two commands separating them are not agents at all — one is CONTROL, one is the internal no-command outcome. Neither would appear in the dropdown under any filter.

**So a gate 3 written on `user_initiable` and a gate 3 written on `speakable` are green on exactly the same inputs.** Revert the fix and nothing goes red. The assertion cannot distinguish the thing it was rewritten for — which is this plan's own stated failure mode, arriving through the door built to stop it.

**This does not make the field wrong.** Two questions genuinely deserve two fields, and the day a typeable-but-not-sayable command is added the field is already there. The problem is only that **real data provides no discriminating case, so the gate must manufacture one.**

**Fix**: gate 3's must-fail control drives the shared predicate with a **synthetic spec** — `user_initiable=True, speakable=False` — and asserts the dropdown must carry it. Then reverting the gate to `speakable` turns that control red, which is the only thing that makes the rewrite mean anything. Same shape as `_card_drift`'s control: drive the real predicate, withhold one side.
