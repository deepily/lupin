## R1 — LIFT `_live_own_pressure` out of `pragma: no cover` (my ruling on Cheech's open question)

**The seam**: `self_respin_core.py:470` `_live_own_pressure(persona)` carries `# pragma: no cover - live :8001 pressure read`. It is the standard live-sensor-boundary shape — BUT it is also the exact function that held a wrong default ("over_budget") for a full day with no test noticing (now fixed to "unknown").

**Why the pragma label is wrong here (label vs measurement)**: the pragma claims "nothing to test — pure live boundary." The function is not pure boundary: it **fetches, parses, AND defaults** in one body. Two behaviours hide under the pragma — (a) parse a present persona's record into `(status, pct)`, (b) fall back to `("unknown", None)` on an absent persona / missing status / exception. Behaviour (b) is exactly what was wrong for a day; a pragma'd function is invisible to the coverage gate that would have caught it.

**The fix is already demonstrated NEXT DOOR in the same diff.** The observer isolates its IO correctly: `_fetch_live_pressure` (observer:354) is a THIN httpx call under pragma, and the parse/default logic lives in `observe_fleet_self_respin` behind an injectable `fetch_pressure` seam — fully covered. `_live_own_pressure` should match that pattern:
- extract a pure `parse_own_pressure(section, persona) -> (status, pct)` (present → its status/pct; absent/missing status → `("unknown", None)`), unit-test both arms;
- keep only the `_fetch_live_pressure()` call under pragma.

⇒ **Lift it.** The observer's own `_fetch_live_pressure` pragma is CORRECT and should stay (thin IO, parse covered elsewhere) — the asymmetry is the tell: apply the observer's discipline to the core's twin function that already burned once.

## R2 — gate 5: a decision-proxy "no" is indistinguishable from a human "no" (label vs measurement)

**Claim**: gate 5 says "proxy can't answer no." **What the code guarantees**: `gate_proceed` proceeds on the `[default used]` prefix (offline/timeout/None/503) and aborts a *clean* "no"/"neither" — it cannot tell a proxy-originated clean "no" from a human's. So "proxy can't answer no" is enforced only for the OFFLINE case; a decision-proxy that auto-answers this ask with a clean "no" WOULD abort the respin, which contradicts "an absent user must not cost a manager."

I could not confirm from `ask_yes_no` (cosa_voice_mcp.py:1489) whether this specific ask is proxy-answerable, so I raise it as **verify, not confirmed defect**:
- (a) confirm this ask is excluded from decision-proxy auto-answer (then the gate holds as-is, and a one-line comment saying so closes it), OR
- (b) make the intent explicit in code: only a clean HUMAN "no"/"neither" aborts; a proxy-provenance answer is treated like default-used (proceed). Requires the return to carry proxy provenance, which the current string does not.
