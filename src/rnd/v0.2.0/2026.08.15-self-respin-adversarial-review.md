## R1 — LIFT `_live_own_pressure` out of `pragma: no cover` (my ruling on Cheech's open question)

**The seam**: `self_respin_core.py:470` `_live_own_pressure(persona)` carries `# pragma: no cover - live :8001 pressure read`. It is the standard live-sensor-boundary shape — BUT it is also the exact function that held a wrong default ("over_budget") for a full day with no test noticing (now fixed to "unknown").

**Why the pragma label is wrong here (label vs measurement)**: the pragma claims "nothing to test — pure live boundary." The function is not pure boundary: it **fetches, parses, AND defaults** in one body. Two behaviours hide under the pragma — (a) parse a present persona's record into `(status, pct)`, (b) fall back to `("unknown", None)` on an absent persona / missing status / exception. Behaviour (b) is exactly what was wrong for a day; a pragma'd function is invisible to the coverage gate that would have caught it.

**The fix is already demonstrated NEXT DOOR in the same diff.** The observer isolates its IO correctly: `_fetch_live_pressure` (observer:354) is a THIN httpx call under pragma, and the parse/default logic lives in `observe_fleet_self_respin` behind an injectable `fetch_pressure` seam — fully covered. `_live_own_pressure` should match that pattern:
- extract a pure `parse_own_pressure(section, persona) -> (status, pct)` (present → its status/pct; absent/missing status → `("unknown", None)`), unit-test both arms;
- keep only the `_fetch_live_pressure()` call under pragma.

⇒ **Lift it.** The observer's own `_fetch_live_pressure` pragma is CORRECT and should stay (thin IO, parse covered elsewhere) — the asymmetry is the tell: apply the observer's discipline to the core's twin function that already burned once.

## R2 — gate 5: a running notification-proxy CAN answer this ask "no" (CONFIRMED — fact settled 2026-08-15)

**Claim**: gate 5 says "proxy can't answer no." **Settled fact: it can.** The `NotificationProxy` Responder processes ANY notification with `response_requested=True` (responder.py:204-315); nothing marks the self-respin ask exempt (grep for `proxy_exempt`/`no_proxy`/`skip_proxy`/`human_only`/`exempt` across `cosa_voice_mcp.py` + `notification_proxy/` returns nothing). Two reachable paths submit a clean "no":
- **dry_run** (responder.py:273-275): `cancel_value = "no" if response_type == "yes_no"` is submitted UNCONDITIONALLY, before any strategy runs — a dry-run proxy declines every yes_no, self-respin included.
- **live "auto"/"llm_script" mode**: the cloud-LLM fallback's `can_handle` is a CATCH-ALL — `return self._available and notification.get("response_requested", False)` (llm_fallback.py:89) — so the self-respin yes_no reaches the LLM, which builds a yes_no prompt (llm_fallback.py:184) and can return "no".

Either path submits a REAL answer (`response.default_used=False`), so `_default_ask` returns a clean "no" with NO `[default used]` prefix, and `gate_proceed` (self_respin_core.py:98-105) aborts it — indistinguishable from a human "no". A Responder is a supported, routinely-run component (`--auto-proxy` during :8000 proxy-integration tests, and any assisted-answer deployment), so this is not hypothetical: under the proxy a manager at its ceiling would be auto-declined its own re-spin, the exact "an absent user must not cost a manager" failure gate 5 names.

**Severity**: MEDIUM. In bare production with no Responder running, the offline path (default-used→proceed) is fine; the gap opens whenever a proxy runs — which includes the very test venue that exercises this mechanism.

**Fix (settled)**: mark the self-respin ask **proxy-exempt** and honor it in BOTH the strategy chain AND the dry_run blanket-decline. Concretely: `_default_ask` sets a notification field (e.g. `human_only=True`); the Responder returns without answering when it is set, checked BEFORE the dry_run branch (else dry_run still "no"s it) and as a universal gate ahead of the strategy chain. That leaves the decision to the human or the offline default (proceed) — exactly gate 5. Provenance-in-`gate_proceed` (the earlier option b) is inferior: it cannot fix the dry_run blanket "no" without the same flag anyway.
