# Gate 3 cannot pass as written, and fixing it forces a phase-3 decision nobody has made

**Reviewer**: Clayton 😎 (`b36934bf`) · **Date**: 2026-08-22 · **Crew**: Mr. Radio 🦉's Q&A-card crew, adversarial-reviewer seat
**Measured at**: `9cbabf03` · **Wanted by**: before Sam writes the phase-3 render

## Verdict

Gate 3 reads *"the rendered select contains an option whose value is that command."* **No option in that select has ever held a command.** They hold **mode keys**. So the gate is not merely testing the wrong column (Mr Radio's §1) — as written it cannot pass at all, and what it *should* say depends on a fork in phase 3 that has not been decided.

## The measurement

`#agent-mode` in `notifications.html` holds **16 options**, and every value is a short mode key:

```
system · math · calendar · weather · receptionist · todo · datetime · calculator
deep_research · podcast · research_to_podcast · claude_code · swe_team
presentation · research_to_presentation · test_suite
```

Not one is `agent router go to …`. And the 16 decompose exactly:

| source | count | contents |
|---|---|---|
| `MODE_TO_AGENT` (`todo_fifo_queue.py`) | 7 | math, calendar, weather, receptionist, todo, datetime, calculator |
| `AGENTIC_MODE_MAP` (same file) | 8 | deep_research … test_suite |
| hand-written | 1 | `system` — the Auto-Route option |
| **total** | **16** | = the dropdown, exactly |

**So those two maps ARE the key→command translation**, and they are two of the three lists the plan does not collapse until phase 7.

## The fork this forces

Phase 3 must decide what `value=` carries, and the two answers are not the same system:

**(a) render `value` = the COMMAND.** The mode-key vocabulary dies at the front end. Gate 3 becomes a genuine set-equality across a real boundary — registry table vs rendered DOM — with nothing in between to launder it. Phase 7's collapse gets easier, because the front end no longer needs the maps at all.

**(b) keep mode keys.** A hand-maintained key↔command mapping survives *somewhere*, and gate 3 then either checks the registry against itself or has to test the mapping too. **That is the exact defect this plan already shipped once** — a gate testing a set it does not govern.

**Recommendation: (a).** And Auto-Route takes the sentinel value regardless, so gate 2 has nothing to exempt (see the separate note on why an exemption is wrong there).

## The second defect: gate 3 has nowhere to read from after phase 3

Tiberius raised this and it is right. After phase 3 the static `notifications.html` has **no options left** — they are rendered from `GET /api/v2/agents`. A set-equality that reads the file from disk would compare against the empty set: vacuously green, or permanently red, and neither is a gate.

There is **no JSDOM tier in this repo** — I looked; the only thing that reads `#agent-mode` is Playwright (`src/tests/e2e_ui/test_job_dispatch.py:299`). So gate 3's venue is either a new unit tier over the render function, or the existing `:8000` e2e. That is the implementer's call, but it has to be made **before** the gate is written, not after.

## Rebaseline item, for the tester

`src/tests/e2e_ui/test_job_dispatch.py:299` asserts `option[value='research_to_presentation']` exists. **Under (a) that dies**, and it is an ordinary consequence of the change, not a regression. It belongs on the phase-3 rebaseline list alongside the two already-flapping visual baselines.
