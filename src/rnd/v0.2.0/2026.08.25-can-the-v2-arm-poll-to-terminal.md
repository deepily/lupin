# Can the v2 eval arm poll to terminal?

**Row**: `a2e360f8` · Krishna 🦚 · 2026-08-25 ~21:00 EDT · head `bebfc42b`
**Answer: yes, and the mechanism is already built and shipped — but the cause was not a missing
poll.** It was a one-line config flip, and it is dated.

Every claim below comes from an artifact on disk or from reading the producer. Nothing is inferred
from a fixture.

## Q1 — Why did earlier runs observe outcomes and tonight's did not?

replay and agents **synchronously on the calling thread**; `QueuedExecutor` hands them to the
existing FIFO queue and **answers `waiting`**." `QueuedExecutor.submit` at :193 pushes and returns
`Outcome( status="waiting", job_id=job.id_hash )` — "every kind, no exceptions."

## Q2 — Can the arm poll to terminal today?

**Yes, two ways, and the strong one is already written.**

**The identifier is already on disk.** Every record in tonight's artifact carries a real
`payload.job_id` of the form `<id_hash>::<user_id>` —
`b292b1c092231d13539569dbb812f38713edebebe418f642421610c11cffe308::50c73ba7-…`. Nothing needs to be
added to the response to make a wait addressable.

**(a) The v1 arm's own mechanism — the recommended one.** `v1_eval_arm.make_ws_recv_events` starts a
`WsJobEventListener` on the queue websocket and blocks for `QUEUED→RUNNING→COMPLETED`, with
`collect_timeout=120.0` already a parameter. It runs against the *same* FIFO queue the
`QueuedExecutor` pushes to. This is not a design — it is shipped code that took tonight's v1
baseline. The natural stopping condition is the COMPLETED event for the `job_id`; the timeout
already exists.

**(b) `GET /api/get-queue/done` polling** — weaker. It is user-filtered and in-memory, so it dies
with the container and cannot serve a post-hoc recovery.

🔴 **What it is NOT: `job_history`.** I checked and the check was wrong twice before it was right,
which is worth recording. `QueuedExecutor.submit` calls `todo_queue.push( job )` and **no
persistence hook** — `grep persist_job_created` over `todo_fifo_queue.py` returns nothing. Querying
tonight's 200 id_hashes found 0, but that number proves nothing on its own: my first query hit
`lupin_db_dev` while the eval ran against `lupin_db_test`, and the correct database holds only **4**
rows in total. A negative result against a near-empty table is not evidence. The producer is what
settles it — the queued path never writes there.

## Q3 — What would it cost?

**~15–30 minutes added per paired run, best estimate ~17 min.** Reasoning, not an adjective:

- The corpus is 100 utterances per pass, 2 passes = **200 waits**.
- The best available per-wait number is the **v1 arm's own measured span tonight: client p50
  4997.8 ms, p95 16471.7 ms** — and that span *is* push→terminal-WS-event against this same queue,
  which is exactly the operation being proposed for v2.
- 200 × ~5 s ≈ **17 min** at the median; the p95 tail and any serialization push it toward 30.
- Tonight's entire paired run took **27 minutes**, so this roughly doubles it. Well inside the
  30000 s integration budget; it is a wall-clock cost, not a timeout risk.

⚠️ **What this estimate is not.** It uses v1's work time as a proxy for v2's. v2's agent mix and
code path differ, so the true number could fall either side. Nobody has measured a v2 wait, because
no run since 08-21 has waited for one.

## Q4 — What breaks if we do it?

1. **A hung job holds the pass open.** Mitigated by construction — `collect_timeout` already exists
   on the listener — but the default of 120 s × 200 waits is a **6.7 h worst case** against a
   30000 s (8.3 h) budget. The timeout needs sizing against the corpus, not left at its default.
2. **🔴 The timeout produces a THIRD state, and this is the real hazard.** A wait that times out is
   neither "observed" nor "waiting" — it is "we looked and never found out". If it lands back in the
   `waiting` bucket it becomes invisible again, which is precisely the blindness row `e7aa19bf` just
   made visible. It needs its own status and its own count, or the fix quietly re-creates the defect
   one layer up.
3. **`fail_fast` interaction.** A poll loop changes when a failure is detected relative to when the
   guard fires; the guard's ordering assumptions were written against an enqueue-and-move-on arm and
   should be re-read, not assumed.
4. **The container ceiling changed tonight.** `lupin-rest-test` now runs at 12G with
   `memory.swap.max = 0` (Tiberius, `873b0687`, live 00:19:16Z). A poll holds more concurrent state
   than enqueue-and-forget, and with swap at zero an overshoot is a kill rather than a slowdown.
   Not a reason to avoid the poll — a reason to watch RSS on the first one.
5. **Nothing durable to recover from.** Because the queued path does not persist (Q2), a run that
   dies mid-pass loses its outcomes entirely. The early-artifact-dump pattern already used for the
   v1 arm would need extending, or a long poll becomes a long thing to lose.

## The cheapest next step, and why it is not "build the poll"

**Flip `v2 executor` back to `inline` for the eval and re-run.** One INI key, no new code, no new
failure mode, and it is the exact configuration that produced all four observed runs above. It
answers whether the go/no-go numbers become readable **before** anyone spends a day on a poll loop
and a third state.

The poll is the right answer if v2 must be measured *as it will ship* — and if `queued` is the
shipping configuration, then an inline measurement is measuring something users will not get. That
is a question for the go/no-go owner, not for this row: **which v2 is the referent** is the same
question row `647f3733` spent a week settling for v1.

**Not proposing an implementation in this message.** Q1's answer changed what the row is about.
