## Q2 — Can the arm poll to terminal today?

**Yes, two ways, and the strong one is already written.**

**The identifier is already on disk.** Every record in tonight's artifact carries a real
`payload.job_id` of the form `<id_hash>::<user_id>` —
`b292b1c092231d13539569dbb812f38713edebebe418f642421610c11cffe308::50c73ba7-…`. Nothing needs to be
added to the response to make a wait addressable.

**(a) The v1 arm's own mechanism — the recommended one.** `v1_eval_arm.make_ws_recv_events` starts a
`WsJobEventListener` on the queue websocket and blocks for `QUEUED→RUNNING→COMPLETED`, with
`collect_timeout=120.0` already a parameter. It runs against the *same* FIFO queue the
`QueuedExecutor` pushes to. This is not a design — it is shipped code that took tonight's v1
baseline. The natural stopping condition is the COMPLETED event for the `job_id`; the timeout
already exists.

**(b) `GET /api/get-queue/done` polling** — weaker. It is user-filtered and in-memory, so it dies
with the container and cannot serve a post-hoc recovery.

🔴 **What it is NOT: `job_history`.** I checked and the check was wrong twice before it was right,
which is worth recording.

⚠️ **AND THE REASON I GAVE IS WRONG — see the Addendum's "Refuted" section. Sam caught it.** I
wrote that `QueuedExecutor.submit` calls `todo_queue.push( job )` with **no persistence hook**,
because `grep persist_job_created` over `todo_fifo_queue.py` returns nothing. It returns nothing
because the call lives one layer up: `queue_util.py:91` calls
`persist_job_created/started/completed_from_metadata`, gated on `is_agentic_job_type( agent_type )`,
and `AGENTIC_JOB_TYPES` (`job_persistence.py:42`) holds only agentic types — `deep_research`,
`podcast`, `presentation`, `claude_code`, `swe_team`, `bug_fix_expediter`, `test_suite` and kin.
None of the conversational commands the eval corpus routes to are in it. **The persistence is
wired; these rows are declined BY TYPE.** Verified in both files rather than taken on the relay.

That distinction is not pedantry: "never wired" reads as a bug someone should fix, while "declined
by type" is a deliberate design and the remediation is completely different. My grep proved a
absence in one file and I read it as an absence in the system.

The conclusion is unchanged — `job_history` is not a poll target — and the rest of this paragraph
still stands: Querying
tonight's 200 id_hashes found 0, but that number proves nothing on its own: my first query hit
`lupin_db_dev` while the eval ran against `lupin_db_test`, and the correct database holds only **4**
rows in total. A negative result against a near-empty table is not evidence. The producer is what
settles it — the queued path never writes there.

## Q3 — What would it cost?

**~15–30 minutes added per paired run, best estimate ~17 min.** Reasoning, not an adjective:

- The corpus is 100 utterances per pass, 2 passes = **200 waits**.
- The best available per-wait number is the **v1 arm's own measured span tonight: client p50
  4997.8 ms, p95 16471.7 ms** — and that span *is* push→terminal-WS-event against this same queue,
  which is exactly the operation being proposed for v2.
- 200 × ~5 s ≈ **17 min** at the median; the p95 tail and any serialization push it toward 30.
- Tonight's entire paired run took **27 minutes**, so this roughly doubles it. Well inside the
  30000 s integration budget; it is a wall-clock cost, not a timeout risk.

⚠️ **What this estimate is not.** It uses v1's work time as a proxy for v2's. v2's agent mix and
code path differ, so the true number could fall either side. Nobody has measured a v2 wait, because
no run since 08-21 has waited for one.

## Q4 — What breaks if we do it?

1. **A hung job holds the pass open.** Mitigated by construction — `collect_timeout` already exists
   on the listener — but the default of 120 s × 200 waits is a **6.7 h worst case** against a
   30000 s (8.3 h) budget. The timeout needs sizing against the corpus, not left at its default.
2. **🔴 The timeout produces a THIRD state, and this is the real hazard.** A wait that times out is
   neither "observed" nor "waiting" — it is "we looked and never found out". If it lands back in the
   `waiting` bucket it becomes invisible again, which is precisely the blindness row `e7aa19bf` just
   made visible. It needs its own status and its own count, or the fix quietly re-creates the defect
   one layer up.
3. **`fail_fast` interaction.** A poll loop changes when a failure is detected relative to when the
   guard fires; the guard's ordering assumptions were written against an enqueue-and-move-on arm and
   should be re-read, not assumed.
4. **The container ceiling changed tonight.** `lupin-rest-test` now runs at 12G with
   `memory.swap.max = 0` (Tiberius, `873b0687`, live 00:19:16Z). A poll holds more concurrent state
   than enqueue-and-forget, and with swap at zero an overshoot is a kill rather than a slowdown.
   Not a reason to avoid the poll — a reason to watch RSS on the first one.
5. **Nothing durable to recover from.** Because the queued path does not persist (Q2), a run that
   dies mid-pass loses its outcomes entirely. The early-artifact-dump pattern already used for the
   v1 arm would need extending, or a long poll becomes a long thing to lose.

## The cheapest next step, and why it is not "build the poll"

**Flip `v2 executor` back to `inline` for the eval and re-run.** One INI key, no new code, no new
failure mode, and it is the exact configuration that produced all four observed runs above. It
answers whether the go/no-go numbers become readable **before** anyone spends a day on a poll loop
and a third state.

The poll is the right answer if v2 must be measured *as it will ship* — and if `queued` is the
shipping configuration, then an inline measurement is measuring something users will not get. That
is a question for the go/no-go owner, not for this row: **which v2 is the referent** is the same
question row `647f3733` spent a week settling for v1.

**Not proposing an implementation in this message.** Q1's answer changed what the row is about.

## 🔴 RULING SUPERSEDES §"The cheapest next step" — BUILD THE POLL

Mr. Radio ruled: **do NOT flip `v2 executor` back to `inline`.** If `queued` is how v2 ships, an
inline measurement measures a path users will not get. The section above that recommends the flip,
and Sam's own option A, are both **closed**. The open question it named — *which v2 is the
referent* — is answered: the shipping one.

## Refuted: `job_history` is not a poll target, and the reason is a TYPE GATE

Sam's doc recommended `GET /api/job-history/{job_id}`, keyed on the scoped `id_hash` every artifact
row already carries. **That is wrong for this corpus**, and this doc's conclusion stands — but its
stated reason ("`QueuedExecutor.submit` calls `todo_queue.push` and no persistence hook") is
incomplete in a way that would send the next reader to the wrong file.

The hook **exists**, one seam further down: `queue_util.emit_job_state_transition` calls
`persist_job_created/started/completed_from_metadata` on the PENDING→QUEUED, QUEUED→RUNNING and
→COMPLETED transitions (`queue_util.py:88-104`). It is gated:

```python
agent_type = metadata.get( "agent_type" ) if metadata else None
if is_agentic_job_type( agent_type ):        # queue_util.py:90
```

`AGENTIC_JOB_TYPES` (`job_persistence.py:42`) is a frozenset of ten job types — `deep_research`,
`podcast`, `presentation`, `claude_code`, `swe_team`, `research_to_*`, `bug_fix_expediter`,
`test_suite`, `test_fix_expediter`. **The v2 eval corpus is conversational agent commands; not one
of them is in that set.** So the rows are never written — not because the wiring is missing, but
because the wiring declines them by type.

⇒ Anyone "fixing" this by adding a persistence call at the push site would be patching a file that
was never the problem. The WS-listener mechanism this doc recommends (§Q2a) is the right one.

## Carried forward — three findings that survive the refutation

**1. `fail_fast` structurally cannot see this failure — that is why twelve runs went blind.**
It fires only when `index == 0` **and** `record["status_code"] != 200` (`v2_eval.py:1459`). A
`waiting` row **is** an HTTP 200. The guard was working exactly as written the whole time. Any poll
must ship beside a guard that asserts on the **outcome distribution**, not the status code — or the
next silent mode change costs another twelve runs. (This sharpens §Q4 item 3 from "re-read the
ordering assumptions" to a named, quoted defect.)

**2. `similarity` never reaches any durable surface, so no poll of any kind recovers it.**
It is returned live by `_finish` (`flow.py:1388`, from `trace.fields`), and it is present in the
inline artifacts (371 of 600 rows on 08-21 11:37). It is **absent from `_build_metadata_json`'s
16-field whitelist** (`job_persistence.py:239`) and `grep -n similarity src/cosa/rest/job_persistence.py`
returns **nothing**. Every queued run shows `similarity` present = **0**.
⇒ **A poll alone does not unblock row `2ebe4ccb`'s §6a threshold table.** Persisting `similarity`
is a required, separable second change. Whether the terminal WS event can carry it instead of the
DB is **open and unmeasured** — do not assume either way.

**3. An independent cost estimate that converges with §Q3.** From the artifacts' own
`client_span_ms` rather than from v1's span: inline 08-21 = **10.4 s/ask** over 600 asks (104.3 min
total); queued 08-25 = **1.5 s/ask** over 200 (5.1 min total). For a 200-ask corpus that is
**~12 min median-weighted, ~35 min mean-weighted**, p90-weighted worst case ~1.7 h.
§Q3's ~17 min sits inside that band, derived from a different measurement. ⚠️ **Same caveat, stated
so it can be refuted**: it assumes a **serial** drain. The fast-lane/agentic-pool split for this
corpus was **not measured**, and that is the one number to get before committing to a budget.

## A fourth defect, found while chasing this — it makes a number APPEAR and be WRONG

Mr. Radio, chasing the finding above, turned up something neither Sam nor Krishna had: **the paired
latency gate compares v2's ENQUEUE acknowledgement against v1's OBSERVED COMPLETION.** On tonight's
pair it would have reported **v2 8.57× faster than v1**. Every other defect here makes a number
refuse to appear; this one publishes a wrong one. It needs its own row.

# The span asymmetry, and the only number that may be quoted about it

Added by Krishna after Mr Radio's `v1_eval_arm.py:373` catch. This section post-dates §Q1–Q4 and
the Addendum; where it disagrees with them, this is later.

## The defect, which needs no number

- **v1** (`v1_eval_arm.py:373`): `client_span_ms` = send → **observed COMPLETION**, the WS terminal
  frame. Its own comment: *"F1 — the ONLY comparable span is client-side send→observed-completion."*
- **v2** (`v2_eval.py:1305-1312`): `client_span_ms` = send → **reply in hand**. Under `v2 executor
  = queued` the reply is the **enqueue ack**.

The paired gate therefore compares **v1-at-completion against v2-at-enqueue**. Read from the two
producers; no artifact arithmetic involved.

The v2 docstring still claims the span "encloses ALL of v2's server-side work … the SAME kind of
measurement the v1 arm takes." That was **true under `inline`**. `22c85b5b` flipped the executor in
an **INI file**, so nothing in that Python file changed and the equivalence claim was never re-read.

## 🔴 3415.3 ms — and the sentence that must never be separated from it

From tonight's single artifact (`ts-f06f5961`), all four inputs within-run:
rendered delta **3152.81 ms** · bar **999.561 ms** · margin **3.15×** · v1 warm p50 **4997.806 ms**
· v2 warm p50 **582.971 ms**.

For the gate to fall to its bar, v2's p50 would have to reach `4997.806 − 999.561` = 3998.2 ms. It
is 582.971 ms. So:

> **v2's deferred work would have to be ≥ 3415.3 ms to drag this run down to a bare pass.
> This says how much it would TAKE. THERE IS NO DEFENSIBLE ESTIMATE OF WHAT IT IS.**
> Anyone filling that blank from a two-era comparison is redoing arithmetic that was **withdrawn**:
> figures of ~2400 ms and ~1909 ms were published from `eval-2026-08-21-11-37-48` minus
> `eval-2026-08-25-19-31-31` and are **retracted** — those runs differ by eight days, n=60 vs n=20
> per command, server state and code, and no subtraction across them is defensible. Correcting the
> first to the second made a bad method look careful, which is worse. **The symmetric run is the
> only thing that fills this blank.**

That warning is inside the same block as the figure deliberately. A caveat one paragraph away does
not survive the first person who quotes the number.

## The rule this produced

**An invalid comparison that passes by a wide margin cannot be called immaterial ON ACCOUNT OF the
margin — because the margin is computed by the same broken instrument.**

Both edges travel together or neither does:

- Invalid **and** firing PASS at 3.15× ⇒ the defect is not academic. A decisive pass on a
  mismatched pair is *more* dangerous than a marginal one, because it is the kind that gets cited
  downstream without re-derivation.
- **3415.3 ms is a large amount of deferred work.** If v2's true terminal span is below it, the
  corrected gate still passes. **This is not a prediction.**

Neither edge is knowable from any artifact now on disk.
