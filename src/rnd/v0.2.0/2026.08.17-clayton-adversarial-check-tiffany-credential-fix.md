## What still SERVES — measured

| # | shape | why it walks through |
|---|---|---|
| **1** | `client_secret_<...>.json` exactly as the **GCP console downloads it** — fields under `"installed"` | parsed branch checks `key in parsed`, i.e. **top level only** |
| **2** | same file, `"web"` variant (web-app OAuth client) | same |
| **3** | a service-account key **nested** under a config wrapper, e.g. `{"gcp": {...}}`, private_key with no PEM header | same |
| **4** | a credential inside a **JSON array**: `[ {ADC} ]` | `if not isinstance( parsed, dict ): return False` — an array is served outright |
| **5** | a real ADC whose signature fields sit **past the 8192-char window** (big leading field) | truncated branch requires the signature IN the window; "starts with `{`" is not enough |
| **6** | truncated object using **JSON `\u` escapes in key names** (`"refresh_token"`) | the truncated branch is a raw substring scan, so it never sees the decoded key |

Findings 1–4 are one defect: **the check is depth-blind and container-blind.** Findings 5–6 are one
defect: **the truncated branch is a substring scan over a bounded window**, so anything that moves the
signature out of the window, or spells it differently in raw text, is served.

Finding 1 is the one to lead with. It is not a synthetic shape — it is the file Google hands you when
you create an OAuth client, and it is commonly committed by accident under exactly that name.

## False-negative controls — all 5 still serve

Two of these are new; her review carried one.

| control | result |
|---|---|
| prose mentioning `client_secret` / `refresh_token` (her control) | SERVED |
| a doc quoting a **whole ADC key inside a fenced block** | SERVED |
| a doc that **starts** with that fenced block | SERVED |
| a large OpenAPI spec naming `client_secret` as a parameter | SERVED |
| a small spec with `client_secret` nested under `securitySchemes` | SERVED |

⚠️ The last two serve for the *wrong reason* — they are the same depth-blindness as findings 1–3.
Fixing depth will pull these two into the blocked set. That is the real cost of the fix, and it should
be decided deliberately rather than discovered later: **a spec or fixture that merely names a
credential field at any depth will be refused.** Keying on a credential-shaped *object* (a type value
plus a matching field, at any depth) rather than on a bare key name is the way to keep them served.

## Suggested direction (not applied — the fix is Tiffany's)

- Walk the parsed value **recursively** (bounded depth, e.g. 6) over dicts *and* lists, applying the
  existing type/field test at each object. Closes 1–4.
- Decide the false-negative trade above before doing it: match on `type ∈ _CREDENTIAL_TYPE_VALUES`
  **or** a credential key whose value is a non-placeholder string, so `{"client_secret": "<yours>"}`
  in a spec survives.
- Findings 5–6 are the bounded-read residual and are the same whitelist-shape concern Tiffany already
  raised. Cheapest honest move: state the window as an accepted limit in the docstring, since the
  current text asserts the signature "sits well inside" it and finding 5 shows that is an assumption.
