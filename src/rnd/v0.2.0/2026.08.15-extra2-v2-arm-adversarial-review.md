## Check 1 — client-send span measures what its label claims

**Label** (`HttpAskClient.ask`, v2_eval.py:764-801): "monotonic clock from the instant just before the POST to the instant the reply is in hand … encloses ALL of v2's server-side work."

**Measured**: `send_ts = self.clock()` (790) → `reply = self._post(...)` → `recv_ts = self.clock()` (792) → `client_span_ms = (recv_ts - send_ts) * 1000`. Clock is injected (`time.monotonic` default), so both ends are the client's clock — no skew, no trusted server boundary. **PASS.**

**Sub-ms nit (immaterial)**: `payload = reply.json()` runs AFTER `recv_ts`, so v2's span EXCLUDES its own response deserialization. v1's client span (WS-event driven) includes the analogous parse. This biases v2 marginally faster, at a magnitude far below network+compute. Not worth a change.

## Check 2 — refuse-gate cannot be satisfied by an arm that did not run

**Mechanism** (`_arm_client_instrument_reason` + `paired_median_delta_gate`, v2_eval.py:530-594): an arm qualifies iff `client_p50_ms` is present AND `spans` is a non-empty list. `spans` is populated only from `ok` (HTTP-200) records carrying `client_span_ms`, so **qualification requires ≥1 successful round-trip**. A zero-200 arm (never ran, or all requests failed) has empty `spans`, is disqualified, and is NAMED in the refusal with no number emitted. **PASS.** Tests `test_paired_gate_declines_and_names_each_disqualified_arm` + `test_arm_client_instrument_reason_variants` prove it.

**Caveat (intended, not a defect)**: the guarantee is LOCAL to input shape. The gate validates the shape of whatever two dicts it is handed — nothing binds v1's and v2's metrics to the same corpus, sample, or paired session. The gate is also **not wired into any executable path** (no paired `main()`; `render_report` renders v2-only). The integration-test header (`test_v2_eval_live.py:15`) states the paired verdict is "a separate build."

**Plan-with-an-owner, or a deferral? (Cheech, 2026-08-15) — it is a DEFERRAL.** A gate nothing calls is indistinguishable from no gate, so this is stated plainly: I found NO named owner and NO open task-store row for wiring the paired harness. The design doc (`2026.08.14-cj-flow-v2-phases-2-3-and-evaluation.md:159,173`) gates the go/no-go verdict on the paired median-Δ, but assigns nobody to build the harness that produces it. ## The one finding — LOW severity (tighten when the gate is wired)

The gate's `instrument` string (v2_eval.py:587) and `render_paired_verdict` name only "network + serialization" as the client-send proxy residual. They OMIT the larger structural asymmetry:

- **v1 client span** = `POST /api/push` → `collect_fn` blocking until the COMPLETED WS event — includes full FIFO **queue-dwell**.
- **v2 client span** = one synchronous `POST /api/v2/ask` round-trip — no queue.

Including queue-dwell is LEGITIMATE for an end-to-end UX-latency verdict (it is real v1 user-facing latency). The risk is purely legibility: a reader could misread `delta_ms` as a compute-only difference. **Two fixes when the paired harness is built**: (1) add a provenance check that both arms ran the same sample/session before firing; (2) name queue-dwell (not just network+serialization) in the residual string. Not a blocker.

**Where the residual belongs (Cheech, 2026-08-15)**: write it into the gate's `instrument` string that prints in the verdict table — NOT as a prose caveat in this doc. A caveat in prose loses to a number in a table; the reader who acts on `delta_ms` is looking at the table, so the qualifier has to travel with the number.
