## The question that was asked

"Why are 32% of the v2 asks in the live run returning 500?" — read-only, run untouched.

## The answer

**Not a v2 defect and not load. The `:8000` server was running pre-sweep code against a
post-sweep config.**

## Root cause

```
TypeError: can only concatenate str (not "NoneType") to str
  File "/var/lupin/src/cosa/memory/input_and_output_table.py", line 68, in __init__
  File "/var/lupin/src/cosa/memory/question_embeddings_table.py", line 71, in __init__
... in the same log:  Key [path to database wo root] NOT found
```

Each link checked:

| link | evidence |
|---|---|
| container started **14:24 EDT** | `lupin-rest-test` StartedAt `2026-08-17T18:24:05.776628826Z` |
| the sweep landed **after** it | `e3659ccc` 15:55:37 — LanceDB out of six cache modules; `497168db` 16:16:45 — *"retire `path to database wo root` — Lane A took its last reader"* |
| files were **current**, imports were not | `src/` is mounted live; the container's own `lupin-app.ini` has **zero** occurrences of the key |
| the sweep was self-consistent | current on-disk code has **no reader** of that key |

⇒ stale in-memory reader asks for a retired key → `None` → `str + None` → 500.

**Corroborating tell:** the traceback's line numbers land on **docstrings** in the current
files. Loaded code ≠ on-disk code, stated by the traceback itself.

**Why only some commands:** only the `automatic` and `none` paths construct the
embeddings / input-and-output tables. `todo`, `math` and `calculator` never reach that
constructor — which is why it read as "partly broken" rather than down.

## The container id, and why it matters

```
BEFORE-RECREATE  id=8ded0671e47677b2fe35f444ca16612ba8058728961acd296b7b8dc9104cd1db
                 started=2026-08-17T18:24:05.776628826Z   (14:24 EDT)
                 captured=2026-08-17T19:17:16-0400
```

Captured **before** the recreate, because it cannot be captured afterwards. `docker restart`
**reuses** the container — mounts and env stay resolved as they were at CREATE time — so only
`docker compose up -d --force-recreate` makes a new one. **The id changing is the proof.** A
moved start-time with the same id means a restart happened and the problem may be untouched.

That is what makes "we recreated it" falsifiable instead of a claim.

## Verifying the fix — four checks, ordered by how easily each is faked

1. **Container id changed** from `8ded0671…`. Restart ≠ recreate.
2. **New StartedAt postdates `497168db`** (16:16:45 EDT). Anything older holds pre-sweep imports.
3. **Negative signal**: no further `Key [path to database wo root] NOT found` in the log after
   the first ask. While that line appears, imports are still stale whatever the id says.
4. **Positive signal — the only one that proves it**: drive one `agent router go to automatic`
   utterance ("Auto mode", "Normal routing") and require a **200**.

> ⚠️ **Do not accept a clean start as evidence.** The failing container served **174 successful
> asks** while an entire command family was dead. A health check and three of the five families
> looked fine the whole time.
