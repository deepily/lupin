# Arbiter fleet loop dies silently on a disabled feature's import

| | |
|---|---|
| **Date** | 2026-08-10 |
| **Session** | `df4207f2` (Mr. Radio 🦉) |
| **Status** | 🟡 Approved by Rick, in flight — all four phases |
| **Symptom** | The Fleet Status panel on the tunneled test-server app reads "No active sessions." while two workers are demonstrably live |
| **Root cause** | `fleet-arbiter-loop` thread dies on its first tick with `ModuleNotFoundError: No module named 'sqlalchemy'`; the service stays `active (running)` and `/health` keeps returning 200 |

---

## 1. What the operator saw

Rick, viewing the VM's app through an IAP tunnel on `:7999`, reported the fleet panel showing
**"No active sessions."** Two Claude Code sessions (`maria`, `sam`) were running on that VM at
the time.

## 2. The chain, hop by hop

```
Fleet Status panel
  → GET /api/arbiter/fleet-state            (VM :7999, lupin-rest-cloud-gpu)
    → reverse-proxy PULL http://host.docker.internal:8001/state
      → lupin-arbiter-app (host systemd --user service)
        → fleet_arbiter section of the composite snapshot
```

Every hop **works**. Measured from inside the container:
`host.docker.internal:8001/state` → HTTP 200, 1,894 bytes. `extra_hosts: host.docker.internal:host-gateway`
is present at `docker-compose.cloud-gpu.yml:98`. The config key resolves correctly.

**The payload is the defect:**

| Host | `fleet_arbiter` section |
|---|---|
| VM | `{ "status": "awaiting", "session_count": 0, "sessions": [] }` |
| Dev box | `{ "session_count": 1, "sessions": [ mr radio … verdict LIVE ] }` |

The **same VM response** carries a `context_pressure` section listing María (ACTIVE, last turn
60 s) and Sam, with real token counts. Two sections of one snapshot, written by two different
loops, disagreeing about whether any sessions exist.

## 3. Root cause

```
Exception in thread fleet-arbiter-loop:
  fleet_arbiter_loop.py:899   in run       →  job = self._job_factory()
  fleet_arbiter_loop.py:764   in factory   →  return ArbiterConsumerJob(
  arbiter_job.py:1191         in __init__  →  follow_through_watcher_factory( self )
  fleet_arbiter_loop.py:608   in factory   →  from cosa.rest.follow_through_escalation_watcher import …
  follow_through_escalation_watcher.py:58  →  from cosa.rest.db.database import get_db
  database.py:19                           →  from sqlalchemy import create_engine, text
ModuleNotFoundError: No module named 'sqlalchemy'
```

The thread dies on tick one and **does not retry**, so `fleet_arbiter` never leaves its
`status: "awaiting"` placeholder.

### 3a. The aggravating factor: the feature is switched OFF

`lupin-app.ini:816` — `follow through escalation enabled = false`.

`make_follow_through_watcher_factory` imports the watcher **at job construction, unconditionally**,
before any flag is read. Its own docstring (`fleet_arbiter_loop.py:598`) promises:

> construction is pure in-memory (no DB / clock / hold-file IO until the flag is flipped AND
> sweep_once runs)

True for IO. **False for the import.** A disabled feature is killing the loop.

## 4. Why nothing looked wrong for two days

45-minute journal tally on the VM:

| Loop | Events | State |
|---|---|---|
| `health_watcher` | 180 | ✅ running |
| `context_pressure_writer` | 45 | ✅ running |
| **`fleet_arbiter`** | **0** | ❌ **dead since boot** |

`systemctl status` = `active (running)`. `/health` = 200. Two of three loops reporting normally.
**One dead thread inside a healthy process is invisible everywhere except the panel it feeds.**

The identical traceback appears at the **2026-08-08 16:22** boot, so this survived at least two
restarts.

## 5. The dependency closure is three packages, not one

Measured in a disposable venv built from `requirements-arbiter.txt`, walking the import until clean:

| Round | Missing | Note |
|---|---|---|
| 1 | `sqlalchemy` | the one in the traceback |
| 2 | `pgvector` | pulled by the vector-store models |
| 3 | `psycopg2` | **failed to build** — no `pg_config` / libpq on the box |
| 4 | `psycopg2-binary` | ✅ import OK |

Dev-box versions: `SQLAlchemy 2.0.40`, `pgvector 0.4.2`, `psycopg2-binary 2.9.11`, `greenlet 3.5.0`.

⚠️ **Probe caveat**: the probe ran Python 3.13; the VM runs 3.10. Module names hold; exact
versions get confirmed against the VM interpreter before they are written into the pins file.

**Consequence**: pinning these into the *light* arbiter venv means the out-of-band watcher carries
a Postgres client stack to support a feature that is off — contradicting the stated purpose of
`requirements-arbiter.txt`, whose header says the arbiter's import chain pulls "ZERO heavy modules."
**That is why the import gate (Phase 1), not the pin, is the primary fix.**

## 6. This is the third instance of the same class

`requirements-arbiter.txt` is labelled **"CLOSED + FROZEN"**. Its own header records `pyyaml` being
added on 2026-07-22 after a live `ModuleNotFoundError('yaml')` **on this same VM**. The frozen list
drifts behind the import graph; the failure is silent every time.

A written freeze is not a control. The control is a check that fails the deploy.

---

## 7. Plan (Rick approved all four phases, 2026-08-10)

### Phase 0 — unblock the VM

1. Confirm the closure against the VM's Python 3.10 interpreter.
2. Pin the measured set in `requirements-arbiter.txt`, annotated as required only when
   `follow through escalation enabled = true`.
3. Re-run `provision-arbiter-on-vm.sh` (idempotent); restart the service.
4. **Verify**: `fleet_arbiter.session_count ≥ 1`, `fleet_arbiter_render` ticks in the journal,
   panel populates through the tunnel.

### Phase 1 — stop a disabled feature importing the DB

Move the import inside the enable-gate so `enabled = false` performs no DB import at all, making
the light venv's "no heavy deps" claim true again. Phase 0's pins remain as the flag-on path.

### Phase 2 — build/deploy checks

- **Deploy-time gate** — `provision-arbiter-on-vm.sh` verifies only `/health` today, which returns
  200 with a dead loop; that is how this hid. Add a construction smoke after pip install: build the
  job factory in-process, fail the deploy loudly on a raise.
- **Committed test** — walk the arbiter's import graph and fail when it grows a dependency the
  requirements file does not carry. **The durable control**; the header comment is already a written
  rule and has been walked past twice.
- **Health tells the truth** — per-loop last-tick + alive status in `/health` and `/state`.
- **`preflight-vm.sh`** — add the arbiter-venv import check.
- **Docs** — provisioning doc, requirements header, CLAUDE.md touchpoints table.

### Phase 3 — verification

100% lines/branches/functions on new code, full check run, live confirmation on the VM.
