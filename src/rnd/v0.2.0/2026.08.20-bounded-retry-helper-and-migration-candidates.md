# Bounded retry: one helper, and the seven loops that could use it

**Row**: 3598c1d3 · **Author**: Chloé 🗼 (76309ba8) · **Date**: 2026-08-20 · **Branch**: `wip-v0.2.0-2026.08.03-present-and-demo`

---

## What was asked, and what this document is for

Rick, verbatim: *"how about you think about a reusable component that you can use to facilitate
the bounded retry and back off? Is this something that we can generalize and use elsewhere also?"*

The answer is yes. `src/cosa/utils/bounded_retry.py` is that component. It is used by exactly one
caller today — the Kagi FastGPT search that row 3598c1d3 is about — **and the other seven loops
were deliberately left alone.** This document is the hand-back: what each existing loop does, what
it would take to move it, and what could go wrong. Nobody should migrate from this list without a
row of their own.

---

## The helper

`src/cosa/utils/bounded_retry.py` — `RetryPolicy` · `retry_call` · `retry_call_async` · `next_backoff`

It is the **union** of what the seven loops already do, not a new opinion about retrying:

| Capability | Which existing loop needed it |
|---|---|
| bound by attempt count | podcast TTS, embeddings, speech-to-text, both judges, the verifier |
| bound by wall-clock deadline | `auto_migrate.wait_for_database` |
| both bounds at once (first to hit wins) | none yet — falls out of supporting both |
| exponential backoff with a ceiling | podcast TTS, embeddings; `auto_migrate` contributed the cap |
| flat / linear backoff | both judges, the verifier (`0.5 * attempt`) — expressible with `backoff_multiplier=1.0` |
| retry filtered by exception TYPE | all of them, implicitly |
| retry filtered by a PREDICATE on the error | the new Kagi caller — "a 503 but never a 401" |
| retry on a RETURNED value | embeddings and speech-to-text, which see a 5xx `Response`, not a raise |
| a per-retry hook | `auto_migrate` (`on_retry`), podcast TTS (an **async** callback) |
| injectable `sleep` and clock | `auto_migrate` — the reason it is the only one testable without waiting |

**The property that is not configurable, on purpose**: an exhausted retry **re-raises the last
exception unchanged**. Never wrapped, never summarised. A caller that wants a friendly message
writes one at its own boundary, where it still has the original.

`quick_smoke_test()`: `python -m cosa.utils.bounded_retry`.

## The one caller wired tonight

`KagiSearch.search_fastgpt()` was a bare single call between two stopwatch lines. `kagiapi` ends
`fastgpt()` with `raise_for_status()`, so one momentary upstream fault became a user-visible
weather failure with certainty. Now: 3 attempts, 1s doubling to a 4s ceiling, retrying transport
errors and `408/425/429/500/502/503/504`, and **not** retrying a 401/403/404 — a standing answer
does not improve by being asked three times, and making the user wait for it is a second defect.

`get_summary()` in the same file is the same bare-call shape and was **not** changed. It is the
first migration candidate below.

## Migration candidates — in the order I would take them

**Assume nothing here is scheduled.** Each row is a proposal with its own risk, and three of them
carry a behaviour change that a user or a test could notice.

### 1. `KagiSearch.get_summary` — `src/cosa/tools/search_kagi.py`
Same file, same defect, ~6 lines. The retry policy and the predicate already exist beside it.
**Risk: none identified.** Left out only because the row fenced this to one caller.

### 2. `SpeechToTextProvider._call_with_retry` — `src/cosa/memory/speech_to_text_provider.py`
A static helper that retries transport failures and 5xx **responses** (`retry_if_result`), with a
fixed `(2, 4, 8)` backoff sequence.
**Behaviour change**: `(2,4,8)` is not exponential-from-1.0; expressed as
`initial_backoff=2.0, multiplier=2.0` it reproduces exactly. **Risk: low.**
⚠️ Its sibling — the CUDA-OOM single retry around local Whisper — is **not** a candidate. It
retries after *clearing a cache*, i.e. it changes the world between attempts. That is a
recovery step, not a backoff.

### 3. `EmbeddingProvider._post_with_retry` — `src/cosa/memory/embedding_provider.py`
Retries transport failures plus a configured retryable-status set, reading `retries` and
`backoff` from the config manager. Maps cleanly onto `retry_if_result`.
**Behaviour change to watch**: on exhaustion it raises a `RuntimeError` naming the url and the
attempt count. The helper returns the last **response** for a value-triggered retry, so that
`RuntimeError` must be raised by the call site afterwards, not deleted.
⚠️ It is also load-bearing for bug `13b35b37` — the distinction between "nothing is listening"
and "the batch was too big" drives whether the caller retries by shrinking. Preserve the
exception TYPES exactly; the retry mechanics are the only thing being replaced. **Risk: medium.**

### 4. `AnswerVerifier` — `src/cosa/agents/notification_proxy/verification.py`
3 attempts, `0.5 * attempt`, and on exhaustion it **degrades gracefully** — returns a result
carrying `"LLM error after N attempts"` rather than raising.
**Shape note**: the helper re-raises, so the call site keeps its own `try/except` and writes the
degraded result there. That is a small readability win at best. **Risk: low, value: low.**

### 5–6. `DmQualityJudge.judge` — `src/cosa/agents/dm_quality_judge/judge.py` and `judge_v2.py`
Same 3-attempt/`0.5 * attempt` shape as #4, plus one thing none of the others have: on retry it
**prepends a reply-anchor to the prompt** to break a deterministic degenerate mode at temp=0.
⚠️ **The attempt is not identical to its predecessor.** The helper retries the same callable, so
the call site must close over the attempt number to vary the prompt — doable via `on_retry`
mutating state, but it is a genuine semantic wrinkle and the comment above that code explains
why a plain retry does not work. **Risk: medium. Read the comment before touching it.**

### 7. `PodcastTTSClient._generate_segment_audio` — `src/cosa/agents/podcast_generator/tts_client.py`
The most demanding caller and the reason `retry_call_async` exists: async, exponential, with an
**async per-attempt notification callback** so the user hears that a segment is being retried.
On exhaustion it returns a failed-segment record rather than raising.
⚠️ It also fires the callback only when another attempt will follow — the helper's `on_retry`
already has that timing. **Risk: medium** — it is a user-visible progress surface, so a change
here shows up in the product, not just the logs.

### 8. `auto_migrate.wait_for_database` — `src/cosa/rest/db/auto_migrate.py`
The best of the existing loops and the model this helper was built from. Deadline-bounded,
injectable clock, `on_retry`, re-raises unchanged.
**Recommendation: leave it.** It is 20 lines, fully tested, sits on the boot path, and the only
thing a migration buys is one fewer implementation. Migrate it last or never.

## What would make me distrust this list

I read these seven loops; I did not run any of them. The risk ratings are from reading code and
its comments, not from exercising each path. Anyone taking one of these rows should re-derive
the risk from the tests, not from this table.

## Deliberately not in the helper

**Jitter.** Every loop here is deterministic today, and adding randomness would make each of them
untestable in the way `auto_migrate` is testable now. If a thundering-herd case ever appears, add
it as an explicit opt-in field with its own row — not as a default that quietly changes seven
call sites' timing.
