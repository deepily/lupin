# A coverage number expires when the tree moves

**Date**: 2026-08-26 · **Author**: john 🏄🏽 · **Row**: `e2099400` (§3c/§3d)
**Status**: MEASURED, and re-runnable — the demonstration below is a live reproduction, not a recollection.

---

## The finding in one sentence

A coverage percentage is rendered against the source **on disk at render time**, not the source that
was **executed at measurement time** — so on a tree several people are committing to, a stored figure
silently decays, and the decay is indistinguishable from a regression.

## What was observed

One coverage data file. Three reports. **Zero re-execution between them.**

The data file is `.cov-john-frame`, written **2026-08-26 20:28:51 EDT** during my §3c/§3d framing run.
The file it measured is `src/lupin_mcp/cosa_voice_mcp.py`.

| Rendered against | Stmts | Miss | Cover |
|---|---:|---:|---:|
| `6f75b227` — the source that was actually executed | 878 | 3 | **99%** |
| `4f9e718f` — HEAD, two peer commits later | 889 | 502 | **38%** |
| the working tree during this re-derivation (21:01–21:06 EDT; HEAD + a peer's uncommitted edit) | 894 | 515 | **36%** |

**A 63-point swing on an untouched measurement.**

The two commits in between are both a peer's, both on row `87ae7234`:

| sha | committed | change to that file |
|---|---|---|
| `3cfee443` | 20:53:18 | +131 / −47 |
| `4f9e718f` | 20:55:31 | +24 / −4 |

## Why it happens

`coverage.py` stores **line numbers**, not line content, and it computes the denominator by parsing
the file **when you ask for the report**. Two things then go wrong at once, and the second is the
one that does the damage:

1. **New statements are added.** Real, and small here: 878 → 889 is **+11**.
2. **Every statement below an edit moves.** The recorded "these lines ran" set now points at
   different code, so lines that did run are reported as missing.

The arithmetic separates them cleanly: the file gained **11** statements and gained **499**
missing ones. Only 11 of the 499 can possibly be new untested code. **The other 488 are
misattribution** — coverage confidently naming lines that were, in fact, executed.

This is worse than a stale number. A stale number is merely old. This one is *wrong in a specific
direction that mimics the failure everyone is watching for*: a file that was at 99% now reads 38%,
which reads exactly like somebody broke the tests.

## What it implies for the numbers on row `e2099400`

Stating this plainly, because the row carries figures and they should not be quietly assumed safe:

**The row's own numbers survive this — for a checked reason, not by luck.** The 165 closed statements
were reported as a **union of six data files against one file listing**, over five source files:
`lupin_app/main.py`, `session_bridge.py`, `notify_user_sync.py`, `register_session.py`, `stop.py`.
**None of the five was edited by anyone during the window** — verified, not assumed:

```
$ git log --format='%h %an %cI' 6b7533eb..HEAD -- <the five paths>
(empty)
$ git status --porcelain -- <the five paths>
(empty)
```

The reason is structural rather than lucky: closing coverage means **writing tests**, and all six of
my commits are test-only additions (`+525`, `+268`, `+226`, `+404`, `+292` lines, every one of them
a new file under `src/tests/unit/`). A run that adds tests and touches no source cannot suffer this
defect at all. The before/after pairs are therefore rendered against the exact source that produced
them, and the 165 stands.

**What does NOT survive is the 71% tier total**, and it already carried a caveat for a different
reason (a refused cosa tier). Add this one: a tier-wide percentage measured on a shared tree is
valid **only at the instant it was rendered**, because it aggregates files any peer may be editing.
`cosa_voice_mcp.py` alone moved that total materially between two renders of the same run.

**The general rule this fleet should adopt**: before quoting a stored per-file coverage number,

```bash
git diff <run-sha>..HEAD -- <path>     # must be EMPTY
```

and require it to be empty. If it is not empty, the number is not stale — it is **unreadable**, and
the honest move is to re-render against the run's sha (below) or re-run.

## Reproducing it

No worktree and no checkout of the shared tree is needed — extract the historical source to a
private path and repoint the data file's row at it. The data file is SQLite:

```bash
SP=<your scratchpad>
git show 6f75b227:src/lupin_mcp/cosa_voice_mcp.py > $SP/asmeasured/src/lupin_mcp/cosa_voice_mcp.py
cp .cov-john-frame $SP/.cov-repro
sqlite3 $SP/.cov-repro \
  "update file set path='$SP/asmeasured/src/lupin_mcp/cosa_voice_mcp.py' where path like '%cosa_voice_mcp.py'"
cd $SP/asmeasured && COVERAGE_FILE=$SP/.cov-repro python -m coverage report \
  --include="$SP/asmeasured/src/lupin_mcp/cosa_voice_mcp.py"
```

That same three-line remap is also the **repair**: a stored data file can be re-rendered correctly
after the fact, as long as you know the sha it ran at. Which is the practical recommendation —
**record the sha next to every coverage figure**, because without it the figure cannot be recovered,
only re-earned.

## What this is not

It is not a coverage.py defect; storing line numbers is the only thing it can do. It is not an
argument against shared trees. It is a statement about **what a percentage means**: on this fleet,
a coverage figure is a measurement of a *moment*, and it needs a timestamp and a sha attached the
same way any other measurement does.
