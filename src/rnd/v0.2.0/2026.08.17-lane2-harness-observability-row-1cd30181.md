## 2. Why the job takes ~733s — the mechanism

The podcast chain raises three unconditional asks. The harness answers the first two and **never sees
the third**:

- The script-review gate is raised at `src/cosa/agents/podcast_generator/orchestrator.py:497-511`,
  dispatched by `_present_script_review` at `orchestrator.py:1668-1722`.
- Its timeout is `podcast script review timeout seconds = 600` (`src/conf/lupin-app.ini:1581`;
  dataclass default `config.py:298`), and it **fails open to "Approve script"** — `response_default`
  at `orchestrator.py:1717`.
- Operator routing redirects it: `_resolve_routing` at
  `src/cosa/agents/utils/agent_notification_dispatcher.py:208-254`. The harness logs in as
  `interactive.job.tester@lupin.deepily.ai`, which is listed in `voice gate service accounts`
  (`lupin-app.ini:2048`), so the gate is re-addressed to `voice gate operator email` — Rick
  (`lupin-app.ini:2047`).
- Gates 1 and 2 reach the harness because neither goes through the dispatcher
  (`todo_fifo_queue.py:1088`, `expeditor.py:1049/1119/1256/1372` set `target_user` directly).

**The duration is bimodal, and this matters more than the 733 figure.** If Rick's account has no live
websocket, `/api/notify` returns the default immediately rather than waiting
(`src/cosa/rest/routers/notifications.py:1203-1228`), and the run lands near 320s — a prompt-answered
run is recorded at 5m21s in `2026.08.06-thursday-morning-preflight.md:158`. The 733s figure is the
*connected-and-silent* case. So the harness cannot predict its own runtime within ~400s, which is
precisely why a fixed cutoff is the wrong instrument and why an expiry must be inconclusive rather
than fatal.

**No escape hatch exists on the production path.** No `--fast-approve`, no env var; `--dry-run`
short-circuits before the gate entirely (`job.py:209-210, 428ff`) so it does not exercise it. The only
shortening seam in-repo is test-side monkeypatching (`src/tests/e2e/test_podcast_fail_open_gate_live.py:89`).

## 3. What changed since Rachel filed — the escalation

Commit `7fe3ba2b` (2026-08-15) added `src/tests/integration/test_lane2_podcast_e2e_live.py`, a wrapper
that runs the harness and asserts `rc == 0`. It sets `@pytest.mark.timeout(1500)` — 25 minutes, ample —

defeated from inside. `src/tests/run-integration-tests.sh:219` runs `pytest src/tests/integration/`,
collecting the whole directory. Integration is the **final merge gate**.

Rachel's mitigation was "read completion from the server log, not the stage table." Nobody reads a log
for a scheduled suite. The mitigation stopped working the day the wrapper landed.

## 4. The fix

**Not** "raise the timeout." Mr. Radio's constraint was explicit: a fix that makes FAILs disappear by
widening a window is how a false FAIL becomes a false PASS.

The stage table is now three-valued, and **every stage starts INCONCLUSIVE**. Under the old table a
stage the harness never observed was indistinguishable from a stage observed to be broken — both
printed FAIL. A stage must now be earned in both directions.

| Change | Why |
|---|---|
| Stages start `INCONCLUSIVE`, not `False` | the harness must earn its reds as well as its greens |
| Exit codes 0 / 1 / 2 — pass / observed-negative / could-not-tell | 2 is non-zero, so an inconclusive run still fails its suite; it just no longer accuses the product |
| `TIMEOUT_S` 720 → 1200, `LANE2_TIMEOUT_S`-overridable | covers the fail-open case with margin — necessary, not sufficient |
| Poll clock is `time.monotonic()`, not `elapsed += POLL_EVERY` | the old counter added 3 per iteration while each iteration made up to three HTTP calls at 20s timeout apiece, so "720" was not seconds and the harness could not state its own cutoff |
| Stage-3 log window derived from run start | the fixed `--since 10m`, evaluated after the loop, mechanically excluded the push-time line it was looking for |
| `find_job` returns `UNOBSERVED` on non-200 / connection error | a dead queue API is not evidence the job never finished |
| `WsAutoAnswer.is_alive()` / `.authed` / `.error`, checked each poll | if the auto-answer socket dies, every later ask goes unanswered and the job stalls — a stall that is the harness's fault, not the product's |
| A red produced while the observer was degraded is downgraded to INCONCLUSIVE | a verdict from a broken instrument is not a verdict |
| `verify_content` returns INCONCLUSIVE on an empty haystack | finding nothing in no text is not a wrong-document finding |

## 6. What is NOT proved — do not read these as done

- **No end-to-end run was executed.** Everything above tests the *instrument* with scripted queue
  answers and a fake clock. That no live podcast was generated is the honest limit of this work: the
  fix is verified to reason correctly about completion, not verified against a real completion.
  A real run needs `:8000` scheduled, ~12–20 min, real inference spend.
- **`TIMEOUT_S = 1200` is a judgement, not a measurement.** It covers 733s with margin. If a slower
  run exists that nobody has recorded, the harness will now say INCONCLUSIVE rather than FAIL — which
  is the correct behaviour, and is the reason the exact number no longer has to be right.
- **The bimodal-duration finding rests on reading the offline path** (`notifications.py:1203-1228`)
  plus two recorded runs at 733s and 5m21s. Two runs is not a distribution.

## 7. The scheduled `:8000` run — read its green narrowly

Submitted as `ts-5a5d4e4e`, `test_types=integration`, `pytest_args="-v -k lane2"` (1 of 433 collected),
`auto_fix_on_failure=False` so the Test Fix Expediter cannot "repair" the instrument if it reports
INCONCLUSIVE.

**That run will not exercise the case this row is about, and a pass must not be read as though it did.**
The test container logs in as `claude.code@lupin.deepily.ai`. The service-account list is
`claude.code@`**`deepily.ai`** (`lupin-app.ini:2048`) — a different domain, so it does not match. The
script-review gate is therefore delivered to the harness's own user, whose websocket the harness holds
open and auto-answers, and the run lands near 320s instead of near 733s. **The 600s fail-open path is
never entered.** What the run does prove: the chain still works end to end, and the three-state table
does not break a good run. What it cannot prove: that the fix handles the timeout case it was built for.

Whether that domain mismatch is itself a defect — a service account that was meant to be on the list and
silently is not — is a separate question worth someone's time.
