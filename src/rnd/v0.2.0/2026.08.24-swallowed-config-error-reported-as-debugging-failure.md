## The swallow

`src/cosa/agents/agent_base.py:372`, inside `run_code`'s auto-debug path:

```python
for minimalist in [ True, False ]:
    try:
        debugging_agent = IterativeDebuggingAgent(
            code_response_dict[ "output" ], "/io/code.py",
            minimalist=minimalist, ...
        )
        debugging_agent.run_prompts()
        ...
    except Exception as debugging_exception:
        # ANY exception during debugging should be logged but not crash the system
        du.print_banner( f"Minimalist [{minimalist}] debugging crashed with exception: ..." )
```

`minimalist=True` is tried **first**, so under Production the very first construction raises
`MissingConfigKeyError`, is caught by `except Exception`, and is reported as the debugger
crashing. The second pass (`minimalist=False`) does not read that key and can proceed, so the
symptom is not total — it is that the minimalist debugger is silently unavailable.

**The handler is not wrong to exist.** Its comment is explicit that a debugging failure should
not crash the system, which is correct. What it cannot do is distinguish *"the debugger ran and
lost"* from *"the debugger could not be built"* — and those need different fixes from whoever
reads the banner.

## Does the user get a wrong answer that looks right? No — traced

`self.error` decides, and it is set **before** the loop and cleared **only** on success:

| Line | What happens |
|---|---|
| `:366` | `self.error = self.code_response_dict[ "output" ]` — set before any debugging attempt |
| `:384` | `self.error = None` — **only** on `was_successfully_debugged()` |
| `:403` | `if self.error is not None:` → `raise CodeGenerationFailedException` |

Both constructions raise, so `:384` never runs, so `self.error` still holds the original error,
so the run ends in `CodeGenerationFailedException`. The broken code is **not** returned as
though it were fixed.

Note `:403` tests `is not None`, not truthiness — so even an empty-string error still raises.
Had it been written `if self.error:`, an empty output would have fallen through to
`return self.code_response_dict` and handed back unfixed code silently. **It is not written that
way**, and that is the difference between this being a reporting defect and a correctness one.

⇒ **User-visible symptom, complete**: two misleading banners, and a `CodeGenerationFailedException`
whose message names the *original* code error rather than the configuration error that actually
stopped the repair. Someone debugging this is sent to the generated code. The generated code is
not the problem.

## What is NOT recommended here
