## The fact that makes this cheap

**`git worktree remove` does not delete the branch.** The commits stay reachable through the
branch ref; the directory is only a checkout. So for any worktree whose branch is fully merged —
or whose branch we keep — removal risks **nothing**, and the 53-directory sprawl is a different
problem from the 90-branch sprawl. Treating them as one problem is why nobody has swept.

Method, per worktree: `git rev-list --count INT..branch` (ahead), `git cherry INT branch` (counts
patches genuinely absent upstream — survives rebase and squash, which a raw ahead-count does not),
plus `git status --porcelain` in the worktree for uncommitted and untracked files. Detached heads
were tested with `git merge-base --is-ancestor HEAD INT`.

`INT` = `wip-v0.2.0-2026.08.03-present-and-demo`.

## Why they accumulate — the part worth fixing

Every row above was created by a healthy reflex: a worker gets an isolated tree so parallel lanes do
not collide. Nothing ever ran the reverse step. **A worktree's life is bounded by the lane, but
nothing reads the lane's end** — the branch merges, the row closes, the seat is reaped, and the
directory stays. 32 of 52 are in that state right now: the work is done, landed, and the tree
outlived it by weeks.

**This has been done before, and it regrew.** Krishna ran the same two-signal audit (ancestry +
patch-id) on 2026-07-01 — Rick-approved and executed the same evening, 38 branches deleted, 61 → 23,
recorded in `src/rnd/2026.07.01-git-branch-worktree-cleanup-proposal.md`. **Seven weeks later the
count is 90 branches and 53 worktrees.** A hand-run sweep is not a fix; it is a receipt that the
sweep was needed. Any proposal that ends at "delete these 36" ends where the last one did.

⇒ The durable fix is not a bigger sweep, it is making the merge that closes a lane also remove the
lane's tree — or a periodic pass with the tier test above, which is mechanical enough to automate.
A sweep run once by hand is a sweep that will be needed again in a month.
