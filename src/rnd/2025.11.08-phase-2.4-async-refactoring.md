## Motivation

### Problem Statement

Prior to Phase 2.4, the notification system had naming inconsistency:
- `notify-claude` - Fire-and-forget (async), but name didn't reflect this
- `notify-claude-sync` - Response-required (sync), clearly named

**Issues**:
1. Ambiguous command names led to confusion about behavior
2. Async notifications lacked Pydantic validation (while sync had it)
3. No clear migration path for distinguishing notification types

### Goals

1. **Clear Naming**: Commands explicitly denote async vs sync behavior
2. **Consistent Validation**: Apply Pydantic models to async (matching sync pattern)
3. **Backward Compatibility**: Ensure existing scripts continue working
4. **Project-Wide Updates**: Migrate all Lupin slash commands to new naming

## Design

### Command Naming Strategy

**Before Phase 2.4**:
```bash
notify-claude "message" --type=task --priority=medium          # Async (fire-and-forget)
notify-claude-sync "message" --response-type=yes_no            # Sync (response-required)
```

**After Phase 2.4**:
```bash
notify-claude-async "message" --type=task --priority=medium    # Async (explicit)
notify-claude-sync "message" --response-type=yes_no            # Sync (unchanged)
notify-claude "message"                                        # Deprecated alias → async
```

**Rationale**:
- Symmetric naming: `-async` and `-sync` suffixes
- Self-documenting: Command name describes behavior
- Backward compatible: Old `notify-claude` still works (with warning)

### Pydantic Model Design

**Async Request Model** (`AsyncNotificationRequest`):
```python
class AsyncNotificationRequest(BaseModel):
    message: str = Field(..., min_length=1, max_length=5000)
    notification_type: NotificationType = Field(default=NotificationType.CUSTOM)
    priority: NotificationPriority = Field(default=NotificationPriority.MEDIUM)
    target_user: str = Field(default="ricardo.felipe.ruiz@gmail.com")
    timeout: int = Field(default=5, ge=1, le=30)  # HTTP timeout, not user timeout
```

**Key Differences from Sync**:
- No `response_type` field (async doesn't wait for responses)
- No `timeout_seconds` (no blocking wait time)
- No `response_default` (no fallback needed)
- Shorter `timeout` (1-30s for HTTP, vs 1-600s for user response)

**Async Response Model** (`AsyncNotificationResponse`):
```python
class AsyncNotificationResponse(BaseModel):
    success: bool
    status: str  # queued, user_not_available, error, connection_error, timeout
    message: Optional[str] = None
    target_user: str
    target_system_id: Optional[str] = None
    connection_count: int = Field(default=0, ge=0)
```

**Key Differences from Sync**:
- No `exit_code` (async doesn't have standard exit codes like 0/1/2)
- `connection_count` field (useful for delivery status)
- `is_queued` property (indicates successful queueing)
- More informative than simple `bool` return

### Implementation Details

#### Pydantic Models (notification_models.py)

**AsyncNotificationRequest**:
```python
class AsyncNotificationRequest(BaseModel):
    """Fire-and-forget notification request."""

    message: str = Field(..., min_length=1, max_length=5000)
    notification_type: NotificationType = Field(default=NotificationType.CUSTOM)
    priority: NotificationPriority = Field(default=NotificationPriority.MEDIUM)
    target_user: str = Field(default="ricardo.felipe.ruiz@gmail.com")
    timeout: int = Field(default=5, ge=1, le=30)

    @field_validator('message')
    @classmethod
    def message_not_whitespace(cls, v: str) -> str:
        stripped = v.strip()
        if not stripped:
            raise ValueError('Message cannot be empty or whitespace-only')
        return stripped

    def to_api_params(self, api_key: str) -> dict:
        """Convert to API query parameters - excludes response_requested."""
        return {
            "message": self.message,
            "type": self.notification_type.value,
            "priority": self.priority.value,
            "target_user": self.target_user,
            "api_key": api_key
        }
```

**AsyncNotificationResponse**:
```python
class AsyncNotificationResponse(BaseModel):
    """Structured response from async notification."""

    success: bool
    status: str  # queued, user_not_available, error, connection_error, timeout
    message: Optional[str] = None
    target_user: str
    target_system_id: Optional[str] = None
    connection_count: int = Field(default=0, ge=0)

    @property
    def is_queued(self) -> bool:
        return self.status == "queued"

    @property
    def is_error(self) -> bool:
        return self.status in ("error", "connection_error", "timeout")
```

#### Async Client (notify_user_async.py)

**Core Function**:
```python
def notify_user_async(
    request: AsyncNotificationRequest,
    server_url: Optional[str] = None,
    debug: bool = False
) -> AsyncNotificationResponse:
    """
    Send fire-and-forget notification with Pydantic validation.

    Requires:
        - request is a validated AsyncNotificationRequest model
        - server_url is None or a valid HTTP/HTTPS URL
        - debug is a boolean

    Ensures:
        - Returns AsyncNotificationResponse with status and details
        - Prints status messages to stdout (success) or stderr (errors)
        - Uses Pydantic validation for all data

    Raises:
        - No exceptions raised (all handled internally)
    """
    base_url = server_url or os.getenv(ENV_SERVER_URL, DEFAULT_SERVER_URL)
    base_url = base_url.rstrip('/')

    try:
        url = f"{base_url}/api/notify"
        params = request.to_api_params(api_key=DEFAULT_API_KEY)

        response = requests.post(url, params=params, timeout=request.timeout)

        if response.status_code == 200:
            data = response.json()
            return AsyncNotificationResponse(
                success=True,
                status=data.get("status", "queued"),
                message=data.get("message"),
                target_user=request.target_user,
                target_system_id=data.get("target_system_id"),
                connection_count=data.get("connection_count", 0)
            )
        else:
            return AsyncNotificationResponse(
                success=False,
                status="error",
                message=f"HTTP {response.status_code}: {response.text}",
                target_user=request.target_user
            )

    except requests.exceptions.ConnectionError:
        return AsyncNotificationResponse(
            success=False,
            status="connection_error",
            message=f"Cannot reach server at {base_url}",
            target_user=request.target_user
        )

    # ... (timeout, request exception handling)
```

## Migration Guide

### For End Users

**Before (deprecated, still works)**:
```bash
notify-claude "Build completed" --type=task --priority=medium
```

**After (recommended)**:
```bash
notify-claude-async "Build completed" --type=task --priority=medium
```

**For response-required notifications**:
```bash
notify-claude-sync "Approve deployment?" --response-type=yes_no --response-default=no
```

### For Developers

**Old Pattern** (pre-Phase 2.4):
```python
from cosa.cli.notify_user import notify_user

# Returns bool
success = notify_user(
    message="Notification text",
    target_user="user@example.com",
    notification_type="task",
    priority="medium"
)

if success:
    print("Notification sent")
```

**New Pattern** (Phase 2.4):
```python
from cosa.cli.notify_user_async import notify_user_async
from cosa.cli.notification_models import AsyncNotificationRequest, NotificationType, NotificationPriority

# Create validated request
request = AsyncNotificationRequest(
    message="Notification text",
    target_user="user@example.com",
    notification_type=NotificationType.TASK,
    priority=NotificationPriority.MEDIUM
)

# Returns structured response
response = notify_user_async(request, debug=False)

if response.success:
    print(f"Notification {response.status}")
    print(f"Connections: {response.connection_count}")
else:
    print(f"Error: {response.message}")
```

**Benefits of New Pattern**:
1. **Type Safety**: Pydantic catches errors at runtime
2. **IDE Support**: Autocomplete for fields
3. **Structured Errors**: Clear validation messages
4. **Richer Responses**: Connection count, system ID, detailed status

## Lessons Learned

### What Went Well

1. **Pydantic Consistency**: Applying Pydantic to async notifications (matching sync) ensured uniform error handling
2. **Backward Compatibility**: Deprecated alias approach prevented breaking existing workflows
3. **Comprehensive Updates**: Updating all slash commands ensured consistency across the project
4. **Clear Documentation**: Phase 2.3 doc already outlined the planned rename, making implementation straightforward

### What Could Be Improved

1. **Global Config Updates**: Excluded from Phase 2.4 scope (being handled by another agent)
2. **Planning-is-Prompting Updates**: Excluded from Phase 2.4 scope (separate repository)
3. **Historical Docs**: Some old design docs still reference `notify-claude` (low priority)

### Future Enhancements

1. **Notification Queuing**: Offline notification storage and delayed delivery
2. **Delivery Confirmation**: Track when notifications are actually delivered to client
3. **Notification History**: User-facing UI for viewing past notifications
4. **Multi-User Support**: Expand beyond single target user
