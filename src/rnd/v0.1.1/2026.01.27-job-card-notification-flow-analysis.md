# Job Card Notification Flow Analysis

**Date**: 2026-01-27
**Status**: Bug Investigation (Round 4)
**Problem**: Job cards get stuck in the run queue after job completion

---

## Executive Summary (For Product Managers)

When you submit a research job, a "job card" appears in the Running Queue to show you progress. Notifications stream in as the job runs. When the job finishes, the card should move to the Done Queue.

**The Bug**: The card stays stuck in the Running Queue forever, even though the job is complete.

**Why This Happens**: The system is too protective. We built a safeguard to prevent cards from disappearing while jobs are running, but that same safeguard prevents cards from being removed when jobs finish.

---

## The Two Worlds Problem

The notification system lives in two different "worlds" that don't always agree:

### World 1: Real-Time WebSocket Events
- Notifications arrive instantly via WebSocket
- First notification: "🧪 Dry run: Starting..."
- The UI creates a card immediately (before the server's job queue is updated)
- This card is called a **"provisional card"** - it exists before the API knows about the job

### World 2: REST API Queue Data
- The server maintains job queues (todo, run, done, dead)
- The UI periodically fetches queue data via `/api/get-queue/run`
- This data is the "source of truth" for what's really in each queue

### The Conflict
When a notification arrives for job `dr-7d92bfda`:
1. WebSocket says: "Here's a notification for this job!"
2. UI says: "I don't know this job yet - let me create a provisional card"
3. 250ms later, UI asks API: "What's in the run queue?"
4. API says: "Nothing yet" (job hasn't been registered in queue yet)
5. **Protective Logic kicks in**: "I see a provisional card, so I'll keep it safe"

This works great for job startup. But the same logic breaks job completion:
1. Job finishes
2. API says: "Run queue is empty"
3. Protective Logic: "I see a provisional card, so I'll keep it safe" ← **WRONG!**
4. Card stays in run queue forever

## The Sequential Flow (Normal Scenario)

Here's exactly what happens when you submit a dry run job:

### Phase 1: Job Submission
```
User clicks "Submit" → POST /api/run-job
                       ↓
                 Server creates job
                       ↓
             Server adds job to run queue
                       ↓
             Server starts job execution
```

### Phase 2: First Notification Arrives
```
WebSocket delivers: {type: "job_notification", job_id: "dr-7d92bfda", message: "🧪 Starting..."}
                       ↓
handleJobNotification() asks: "Is dr-7d92bfda registered?"
                       ↓
                   Answer: "No"
                       ↓
createProvisionalJobRegistration("dr-7d92bfda", notification, "run")
   ├─ Stores in registeredJobs Map: {job_id, queueName: "run", provisional: true}
   └─ ensureJobCardExists() → Creates HTML card with data-provisional="true"
                       ↓
             Card appears in Run Queue UI
                       ↓
appendNotificationToJobCard() → "🧪 Starting..." shows in card's activity log
                       ↓
scheduleQueueRefreshForJob() → Sets 250ms timer to fetch real API data
```

### Phase 3: More Notifications Stream In
```
WebSocket delivers: "🧪 skipping query clarification..."
                       ↓
handleJobNotification() asks: "Is dr-7d92bfda registered?"
                       ↓
                   Answer: "Yes" (from Phase 2)
                       ↓
appendNotificationToJobCard() → Notification added to activity log
                       ↓
         (This repeats for each notification)
```

### Phase 4: Deferred Queue Refresh (250ms after Phase 2)
```
Timer fires: loadQueueJobCards("run")
                       ↓
             Fetch /api/get-queue/run
                       ↓
    API returns: jobsMetadata = [] (empty - server hasn't caught up yet)
                       ↓
updateJobRegistration("run", []) → Called with empty array, does nothing
                       ↓
Check: jobsHtml.length === 0? → YES
                       ↓
Check: Any provisional cards exist? → YES (our card has data-provisional="true")
                       ↓
     ⚠️ PROTECTIVE EARLY RETURN ⚠️
     Log: "[Phase 6] Preserving 1 provisional card(s) in run"
     return; // Exit without destroying the card
```

### Phase 5: Job Completes
```
Last notification arrives: "🧪 Dry run complete!"
                       ↓
Server moves job: run_queue → done_queue
                       ↓
Server emits: queue_running_update {value: 0}
Server emits: queue_done_update {value: 1}
```

### Phase 6: Run Queue Update (THE BUG)
```
WebSocket delivers: queue_running_update
                       ↓
updateQueueLists("run")
                       ↓
             Fetch /api/get-queue/run
                       ↓
         API returns: jobsMetadata = [] (empty - job moved to done)
                       ↓
updateJobRegistration("run", []) → Called with empty array, does nothing for existing cards!
                       ↓
Check: Any provisional cards exist? → YES (card still has data-provisional="true")
                       ↓
     ⚠️ PROTECTIVE EARLY RETURN (AGAIN!) ⚠️
     Log: "[Phase 6] Preserving 1 provisional card(s) in run"
     Card stays in run queue forever
```

### What SHOULD Happen in Phase 6
```
updateQueueLists("run") with empty array
                       ↓
     Detect: "I have registered jobs in 'run' queue that aren't in API response"
                       ↓
     For each missing job:
         cleanupRunQueueCard(jobId)  ← Stop timer, remove card
         registeredJobs.delete(jobId)
                       ↓
     Card removed from run queue
     Done queue refresh shows card there instead
```

## Why Previous Fixes Failed

### Round 1 Fix Attempt
"When `updateJobRegistration("run", [])` gets empty array, clean up all run-registered jobs"

**Why it broke**: The fix ran during Phase 4 (the 250ms deferred refresh) when the API genuinely hasn't caught up yet. It deleted the provisional card before notifications could accumulate.

**The Symptom**: No card appeared at all during job execution.

### Round 2 Fix Attempt
"Call `cleanupRunQueueCard()` when job appears in done/dead queue"

**Why it partially worked**: If the done queue is refreshed with the job data, and the job was registered as "run", cleanup is triggered.

**Why it's incomplete**: The done queue refresh isn't always called, or the timing means the run queue's protective logic kicks in first.

### Round 3 Fix Attempt (What I Just Rolled Back)
Same as Round 1 - triggered cleanup too early during job execution.

## The Core Design Flaw

The protective logic at line 4556-4562 asks the wrong question:

```javascript
if ( jobsHtml.length === 0 ) {
    const provisionalCards = container.querySelectorAll( '.job-card[data-provisional="true"]' );
    if ( provisionalCards.length > 0 ) {
        // Don't destroy - provisional cards exist
        return;  // ← THIS IS TOO AGGRESSIVE
    }
}
```

**What it asks**: "Are there any provisional cards?"

**What it should ask**: "Are there any provisional cards for jobs that are STILL RUNNING?"

The system cannot distinguish between:
- **Legitimate provisional**: API is slow, job is still running, keep the card
- **Stale provisional**: Job finished, moved to done queue, remove the card

---

## The Missing Signal

The system needs a way to know when a job has truly completed. Options:

### Option A: Track Job Completion State
When a "job complete" notification arrives (e.g., "🧪 Dry run complete!"), mark the job as complete. Then during queue refresh, treat completed jobs differently from running ones.

### Option B: Cross-Queue Verification
When run queue returns empty, check done/dead queues. If the job is there, it's truly done - clean it up.

### Option C: Time-Based Expiration
If a provisional card hasn't received notifications for N seconds AND the API says it's not in the run queue, expire it.

### Option D: Server-Sent Job State
Have the server include job state (running/completed) in notifications. The UI can then know when to stop protecting the card.

## Console Log Translation

When you see:
```
[Phase 6] Preserving 1 provisional card(s) in run
```

It means:
- The API returned 0 jobs for the run queue
- BUT there's still a provisional card in the UI
- SO the system is "protecting" it from being removed
- **If the job is done**: This is the bug - the card should be removed
- **If the job is still running**: This is correct behavior

---

## Next Steps for Round 4 Fix

The fix must:
1. Allow provisional cards to accumulate notifications during job execution (Phase 3-4)
2. Detect when a job has COMPLETED (not just when API returns empty)
3. Only then remove the provisional card from run queue

The fix must NOT:
1. Remove cards during the 250ms deferred refresh when API is just slow
2. Break notification accumulation while job is running
3. Require changes to the backend
