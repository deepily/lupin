## The Critical Event: `notification_queue_update`

This is the event that creates job cards. The flow:

```
Server emits: notification_queue_update
       │
       ▼
handleQueueMessage() [L1799]
       │
       ▼
case "notification_queue_update": [L1874]
       │
       ▼
handleNotificationUpdate( envelope ) [L3994]
       │
       ▼
Extract notification from envelope.notification or envelope.data.notification
       │
       ▼
Check: Does notification have job_id (explicit or extracted from sender_id)?
       │
       ├─── YES ──► Check: Is job registered in registeredJobs Map?
       │                    │
       │                    ├─── NO ──► createProvisionalJobRegistration()
       │                    │           ensureJobCardExists()
       │                    │           appendNotificationToJobCard()
       │                    │           scheduleQueueRefreshForJob() [250ms]
       │                    │
       │                    └─── YES ─► appendNotificationToJobCard()
       │
       └─── NO ───► Route to sender card or general notifications
```


### Phase 4: Deferred Refresh (250ms later)

```javascript

    │
    ▼
fetch( `/api/get-queue/run` )
    │
    ▼
Response: { jobs: [] }  // Empty - server hasn't updated yet
    │
    ▼

```

### Phase 5: More Notifications Stream In

```
Each notification_queue_update with same job_id:
    │
    ▼
isJobRegistered( jobId ) → true
    │
    ▼
appendNotificationToJobCard( jobId, notification )
    │
    ▼
Card's activity log grows
```

### Phase 6: Job Completes

```
Server moves job: run_queue → done_queue
Server emits:
    queue_running_update: { value: 0 }
    queue_done_update: { value: 1 }
```

## The Fundamental Problem

The protective logic at lines 4556-4565 uses a **single boolean condition** to handle **two semantically different states**:

| State | API Response | Provisional Cards | Correct Action |
|-------|--------------|-------------------|----------------|
| API latency during job startup | `[]` | Yes | **Preserve** cards |
| Job completed, moved to done | `[]` | Yes | **Remove** cards |

The code cannot distinguish between these states because both produce:
- `jobsHtml.length === 0` → `true`
- `provisionalCards.length > 0` → `true`

The conditional `if (provisionalCards.length > 0) return;` fires in both cases, causing the card to remain in the run queue indefinitely after job completion.

## Summary of Key Events

| Event | When Emitted | UI Action |
|-------|--------------|-----------|
| `notification_queue_update` | Each status message during job execution | Creates/updates job card |
| `queue_running_update` | Run queue count changes | Calls `loadQueueJobCards("run")` |
| `queue_done_update` | Done queue count changes | Calls `loadQueueJobCards("done")` |
| `queue_dead_update` | Dead queue count changes | Calls `loadQueueJobCards("dead")` |

The bug occurs because `queue_running_update` with `value: 0` triggers a refresh that cannot distinguish "API slow" from "job complete."
