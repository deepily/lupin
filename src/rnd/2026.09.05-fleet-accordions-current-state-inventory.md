## 0. Read this first — two claims that will mislead you if you skip them

**① "Four" is the file's number, not a selection.** `notifications.html` contains **fifteen**
`.collapsible-section` divs. Exactly four carry a toolbar toggle button, and exactly four have a
render container the JS writes into — and **both fours name the same four**. Two independent
signals, same answer.

**② The four are SIBLINGS, not nested.** An early hypothesis held that four accordions live *inside*
the fleet-status pane. **Refuted on both sides:**

| side | evidence |
|---|---|
| legacy | `#section-fleet-status` (`notifications.html:687-763`) holds a header, a ▼ toggle, the fleet-size-cap controls, one container. No nesting. |
| multiplexer | `FleetStatusRenderer.ts:125` says it itself — *"The container IS the collapsible body"*. Its `toggle` is `renderFleetOfflineToggle`, a Show/Hide-offline **view** button (*"read-only — changes what the table shows, never fleet state"*, `fleetStatusTable.ts:44`). Its `group` is `groupFleetByManager`, a **table row grouping**. |

⚠️ **john measured SIX sections in the multiplexer and was right.** His six are the *destination*;
these four are the *source*. Only **Fleet Status** and **Task List** exist on both sides — which is
exactly why the two counts look like they should reconcile and do not.

## 2. Structure — shared vs duplicated, and it is LAYERED

The question "one component or four near-duplicates?" has no single answer. It resolves differently
at three layers, and a spec written at the wrong layer will be wrong.

### 2.1 SECTION layer — four separate implementations

Normalising each render body (every surface token → `X`), dropping punctuation-only and sub-12-char
lines, shared substantive lines against the **smaller** body:

| pair | shared | |
|---|---|---|
| epic-board vs task-list | 19/36 | **52%** |
| epic-board vs fleet-status | 8/36 | 22% |
| fleet-status vs task-list | 7/44 | 15% |
| holding-area vs any | 3/41 | **7-8%** |

⇒ **One lineage plus two independents**: epic-board was forked from task-list; holding-area and
fleet-status share almost nothing with anything.

⚠️ **What this measurement can and cannot see.** It is line-level identity after normalisation, so
it sees **copied structure**. It **cannot** see two independent implementations of one behaviour —
a low score is not evidence of differing behaviour.

### 2.2 ROW layer — ALL THREE row panes SHARE ONE RENDERER

🔴 **This is the single most important fact in this document for a "carbon copy".**

`_renderEpicRow` (`notifications.js:13418`) is a thin wrapper:

```js
return this._renderRow( task, null, { rowClass: "epic-row" } );
```

Its own docstring:

> *"IT USED TO BE A SECOND IMPLEMENTATION, with its own column order (ID / P / Status / Title /
> Actions), no Class field, and its own colspans. That is exactly the shape Rick asked us to kill:
> moving between the epic board and the task list meant re-parsing the layout. The markup now lives
> in `_renderRow` alone"* ... *"identical cell-for-cell to the task list's row, by construction."*

🔴 **CORRECTED 2026-09-05, after first publication — it is THREE panes, not two.** The first cut of
this section named task-list and epic-board. `_renderRow`'s own docstring (`notifications.js:10092`)
says otherwise: *"THE row renderer — one implementation, all three panes … The task list, the
holding area and the epic board render the same shape because they run the same code, not because
three copies happen to agree today."* Verified by call site, not by docstring: there are exactly
**two** `this._renderRow(` calls, and both are wrappers —

| wrapper | line | called from |
|---|---|---|
| `_renderTaskRow` — *"the task list's **and holding area's** entry point"* | :10159 | :11340 (task list) · :12655 (**holding area**) |
| `_renderEpicRow` | :13418 | :13479 (epic board) |

**I reported two and told both María and john two.** The error came from reading the epic wrapper's
docstring, which truthfully names only its own pair, and never opening the other wrapper.

⇒ **Spec line: the TS side must render task-list, holding-area and epic-board rows identical
cell-for-cell.** This is an observable behaviour Rick personally asked for. A spec that documents
the three panes separately, in good faith, is how it silently gets re-split.

⚠️ **This does NOT contradict §2.1.** Holding-area's *section* body really does share 7–8% with the
others — the sharing is at the ROW layer, which is exactly why the layering in this section matters
more than any single percentage.

⚠️ `_renderEpicRow` passes `null` for the timezone **deliberately** — *"this pane never had one, so
next-chase formats exactly as it did before."* Not an omission; do not "fix" it in the port.

### 2.3 DATA layer — epic-board and task-list read the same endpoint

`renderEpicBoard` calls **`fetchTaskList`**. Same function, same endpoint:

```
/api/tasks?limit=500&unscoped_audit=true&hide_parked=false&char_budget=0   (shared/task-list-query.js:50)
/api/tasks?limit=500&unscoped_audit=true&status=not_approved&char_budget=0 (shared/task-list-query.js:79)
```

Epic board is **the same rows as the task list, grouped on `correlation_key` instead of owner.**
Fleet-status uses `fetchFleetState`; holding-area uses `fetchHoldingArea`.

## 5a. Progressive-disclosure editor widgets — RESOLVED

> §6 of the first cut left this **unresolved**. It is Rick's own phrase and a named requirement, so
> a gap here is a hole in the spec. Resolved below, from source.

### 5a.1 `ROW_SCHEMA` is the authoritative field split (`notifications.js:43`)

```js
const ROW_SCHEMA = {
    line1 : [ "id", "title", "class", "status", "priority" ],
    line2 : [ "blocked", "chase", "accountable", "filer", "project" ],
    line3 : [ "detail", "actions" ]
};
```

**Line 1 is always visible. Lines 2 and 3 are behind the disclosure.** Labels come from
`ROW_FIELD_LABELS` at `:49` — ID · Title · Class · Status · Priority · Blocked by · Next chase ·
Accountable · Filed by · Project · Detail · Actions.

⚠️ **The TS side must read a schema, not hard-code five columns.** That is the whole point of the
constant; see §5a.4.

### 5a.2 The toggle — `_disclosureToggle( task )` :10175

Emits exactly:

```html
<button type="button" class="task-disclose-button" data-task-id="{id}"
        aria-expanded="false" title="Show row controls">⋯</button>
```

🔴 **The state lives in `aria-expanded`, NOT in a CSS class.** Its docstring: *"A disclosure that
only exists in CSS is invisible to a keyboard user, who then has no way to reach any of these verbs
at all."* The `hidden` attribute on the controls row carries the visual half. **Both are required.**

⭐ **Rick's spec, quoted in the source**: *"an ellipsis right-justified ON THE TITLE LINE indicating
hidden functionality; clicking it discloses the controls as ONE narrow row spanning the full width
of the item; that second row is NOT displayed by default."*

⚠️ **A vertical stack of controls is explicitly WRONG** — *"Nine controls inline turned a dense,
scannable board into a wall: the thing the board is FOR, seeing many rows at once, was paid away to
make five verbs reachable without a click."*

### 5a.3 Row markup emitted by `_renderRow` :10092

```html
<tr class="task-row {statusClass}">
  <td class="task-col-{field}">…</td>   <!-- one per ROW_SCHEMA.line1, in order -->
  <td class="task-col-disclose">{toggle}</td>
</tr>
<tr class="task-controls-row {statusClass}" data-controls-for="{id}" hidden>
  <td colspan="{_rowWidth()}">…</td>
</tr>
<tr class="task-row-error-stripe" data-error-for="{id}" hidden>
  <td colspan="{_rowWidth()}"></td>
</tr>
```

Disclosed fields render as
`<div class="task-disclosed-field task-col-{f}"><span class="task-disclosed-label">…</span><span class="task-disclosed-value">…</span></div>`,
grouped into `<div class="task-disclosed-line task-disclosed-line--{modifier}">`.

The title cell alone also carries a `title=` attribute (`_taskTitleLabel`, :…) — non-empty title, else
literal `"(untitled)"`.

### 5a.4 🔴 `_rowWidth()` — every colspan derives from one place

```js
return this.ROW_SCHEMA.line1.length + 1;   // fields + the toggle's own cell
```

Its docstring names the defect this kills: *"They used to be hand-written literals — 12, 12, 11, 5,
5, 5, 5 across seven sites — and a stale colspan does not look broken: the table still renders
perfectly while the controls row and the error stripe quietly stop spanning it."*

⇒ **A TS port that hard-codes a colspan re-opens a class of defect that is currently gone by
construction.**

### 5a.5 The click handler is PANE-SCOPED, and that is load-bearing

`_handleDisclosureToggle( button )` — *"A row rendered in both panes has TWO controls rows carrying
the same `data-controls-for`, and an unscoped query would open the task list's copy when the
operator pressed the epic board's ellipsis."*

⇒ **Scope the lookup to the pane that was clicked.** An unscoped `document.querySelector` on
`data-controls-for` is the bug, not a simplification.

### 5a.6 Title truncation — the JS cap is GONE

`TASK_TITLE_TRUNCATE_LEN` / `_truncateTaskTitle` no longer exist as a live pair (one textual
occurrence remains). A 2026-09-04 measurement found the title cut to **60 characters in JavaScript
before reaching the DOM**, which made every "widen the title column" change cosmetic by
construction. **Do not reintroduce a JS-side cap in the port** — the CSS ellipsis plus the `title=`
attribute are the intended mechanism.

## 5b. States — sign-in, offline, empty, error, truncated

> §6 of the first cut listed these as unenumerated. Enumerated here **verbatim**, because a spec
> whose acceptance test is *"a third party can verify they did"* cannot say *"an empty state."*

Every message is a single element; the **class pair** and the **exact text, emoji included**, are
both part of the contract. The count element is set on the same branch — that pairing is the part a
port drops.

### Fleet Status — `renderFleetStatus` :9074

| state | element | count |
|---|---|---|
| sign-in | `<p class="fleet-status-message fleet-status-signin">🔒 Sign-in required.</p>` :9099 | `"0"` |
| arbiter offline | `<p class="fleet-status-message fleet-status-offline">🛰️ Arbiter offline — last known: none.</p>` :9105 | `"0"` |
| empty | `<p class="fleet-status-message fleet-status-empty">No active sessions.</p>` :9128 | — |
| all offline & hidden | `<p class="fleet-status-message fleet-status-empty">No live sessions.</p>` :9132 | — |
| populated | grouped table + count + last-updated stamp | live count |

⚠️ **Two distinct empty states share one class.** *"No active sessions"* (nothing exists) and *"No

collapses them loses the distinction that tells an operator whether to go looking.

⚠️ The composite is **cached** so the offline toggle re-renders in place **without a re-fetch**.

### Task List — `renderTaskList` :11347

| state | element | count |

| empty | `task-list-message task-list-empty` — `✅ No open tasks.` :11416 | — |

⚠️ **`✅ No open tasks.` and `No tasks loaded yet.` share the `task-list-empty` class and mean

⚠️ The count reads **`"Live: 0"`**, not `"0"`. Fleet-status uses `"0"`. Holding-area uses **`"—"`**.
Three surfaces, three conventions, all deliberate-looking and none shared.

### Holding Area — `renderHoldingArea` :12560

Driven by a **sentinel map on `composite.status`** (:12586), which the other three do not have:

```js
const sentinels = {
    auth_required     : "Sign-in required to read the holding area.",
    query_unavailable : "The shared query module did not load — this is a deploy defect, not an outage.",
    unreachable       : "Task store unreachable — last known state not shown."

```

Rendered as `<div class="holding-area-empty">{escaped sentinel}</div>`, count set to `"—"`.
**Empty**: `<div class="holding-area-empty">Nothing waiting on triage.</div>`.

🔴 **The empty state is load-bearing and the source says why**: *"AN EMPTY HOLDING AREA IS A REAL
STATE AND SAYS SO. Rendering nothing would be indistinguishable from the pane failing to load, and
this pane is expected to be empty most of the time — which is exactly when a silent blank is most
likely to be read as 'broken' and least likely to be checked."*

⇒ **A TS port must not render an empty holding area as nothing.** This is the one state in the
document with a written rationale, and it is the state a port is most likely to treat as trivial.

⚠️ Note the `query_unavailable` wording — *"a deploy defect, not an outage"*. It tells the operator
which of two very different problems they have. Do not generalise it to "unavailable".

### Epic Board — `renderEpicBoard` :13548

🔴 **It renders `task-list-message task-list-*` classes, not `epic-board-*`** — sign-in :13576,
query-unavailable :13583, unreachable :13591. Count `"0"`.

Its unreachable text is **longer than the task list's**:

```
⚠️ Store unreachable — showing nothing rather than something stale.
```

versus the task list's `⚠️ Store unreachable.` (:11563).

🔴 **CORRECTED 2026-09-05 — the first cut of this line dropped the final word, `stale.`** Caught by

⚠️ **This is the failure this document exists to prevent, committed by this document.** §5b opens by

write *"an empty state."* A one-word truncation in a verbatim block is worse than a paraphrase,

⇒ **A fourth piece of cross-surface coupling**, alongside `_renderRow`, `fetchTaskList` and

## 5c. Holding Area internals, and the sorting rules

> §6 of the first cut called this the thinnest section — named from CSS selectors rather than read
> handler-by-handler. Read properly here.

### 5c.1 Grouping is BY FILER, and filer ≠ owner

`_groupHeldRowsByFiler( tasks )`. Its docstring is the rule and the reason together:

> ⭐ *"FILER, NOT OWNER — and the two genuinely differ. `created_by` names who PUT the row in the
> holding area; `owner_persona` names who would do it if approved. On the live board they disagree
> on 3 of 13 rows, which is why they are two columns and never one merged 'who'. Triage asks 'what
> did this person file', so it groups on the filer."*

⇒ **A port that groups the holding area by owner produces a plausible, wrong pane.** Nothing would
look broken.

**Contract**: returns `[ { filer, tasks } ]`; a falsy/absent argument yields `[]`; pure, never throws.

### 5c.2 Sort order — two levels, and the second one is deliberate

| level | rule |
|---|---|
| groups | filer name, `localeCompare` ascending |
| rows within a group | `_taskPriorityRank` ascending, **then** title `localeCompare` |

⚠️ **Status is deliberately NOT a sort key here** — *"status is uniform here — every row is
`not_approved` — so ranking by it would discriminate nothing."* A port that adds status to the
comparator is not wrong so much as inert, and it hides that the pane is single-status by definition.

### 5c.3 Group markup — `_renderHoldingAreaGroup( filer, tasks )`

```html
<div class="holding-area-group" data-filer="{key}">
  <div class="holding-area-group-header">
    <span class="holding-area-filer">{label}</span>
    <span class="holding-area-group-count">{tasks.length}</span>
    <button type="button" class="task-action-btn holding-approve-all"   data-filer="{key}" title="…">Approve all</button>
    <button type="button" class="task-action-btn holding-wont-fix-all"  data-filer="{key}" title="…">Won't fix all</button>
    <input  type="text"   class="task-action-input holding-wont-fix-all-reason" data-filer="{key}"
            placeholder="one reason, applied to every row below…" aria-label="Batch won't-fix reason">
    <span class="holding-area-group-status" data-filer="{key}"></span>
  </div>
  <table class="task-list-table holding-area-table">
    {_taskTableHeaderRow()}
    <tbody>{rows}</tbody>
  </table>
</div>
```

🔴 **`data-filer` on every control is how the handler finds its rows.** Not decoration.

⚠️ **The tooltips carry the SEMANTICS and must be ported verbatim** — they are the only place the
reversibility difference is stated to the operator:

| control | tooltip |
|---|---|
| Approve all | *"Approve every row {filer} filed — **reversible**, a row approved by mistake can be demoted straight back"* |
| Won't fix all | *"Close every row {filer} filed as won't-fix. **TERMINAL**, and every row gets the SAME reason — use the per-row control when the reasons differ"* |

⚠️ Rows are rendered by **`_renderTaskRow`** — the task list's own wrapper (§2.2), with the resolved
IANA zone passed through. The holding area **does** get a timezone; the epic board does not.

### 5c.4 A fifth coupling — the table class

| pane | table class |
|---|---|
| task list | `task-list-table` |
| **holding area** | **`task-list-table holding-area-table`** |
| epic board | `epic-board-table` |

The holding area carries the task list's class **plus** its own. So it inherits task-list table rules
by design, and `holding-area-table` is an override layer rather than a standalone style.

### 5c.5 The shared `<thead>`

`_taskTableHeaderRow()` is now a thin wrapper over `_rowTableHeaderRow()`, *"which all three panes
use"*. Its docstring records a lesson worth carrying into the port:

> *"THIS DOCSTRING USED TO WARN ABOUT ONE COLSPAN AND MISS ANOTHER … A warning that lists sites is a
> warning that will be incomplete the next time."*

⇒ Every colspan in the three panes now reads `_rowWidth()` (§5a.4). **There is nothing left to keep
in step** — and a TS port that reintroduces literals reintroduces the drift.

## 5d. Grouping and sort order — all three row panes

> §6 previously said I had captured only the holding area's comparator and warned against assuming
> the others matched. Read now. **They very nearly do match, and the one difference is principled.**

| pane | grouper | group order | within a group |
|---|---|---|---|
| Task List | `groupTasksByOwner` :9806 | owner alpha, **`Unassigned` LAST** | status-rank → priority → title |
| Epic Board | `groupTasksByEpic` :13227 | generator's `sort_key`, **`epic:unassigned` LAST**, ties broken by key for stability | status-rank → priority → title — *"the same urgency order the task list uses"* |
| Holding Area | `_groupHeldRowsByFiler` :9540 | filer alpha | **priority → title** |

**Status-rank puts blocked first; priority puts P0 first.**

⇒ **Task list and epic board share one comparator by intent**, and the epic board's docstring says so
outright. The holding area's omission of status is **principled, not an oversight** — every row there
is `not_approved`, so *"ranking by it would discriminate nothing."*

⚠️ **Both "unassigned" buckets sort LAST, by different mechanisms** — the task list by an explicit
`isUnassigned` flag on the group, the epic board by the generator's `sort_key` convention. A port
that implements one and not the other produces a pane that looks right until an unowned row appears.

⚠️ **Epic group ties are broken by key "so the order is stable across renders."** A port using an
unstable sort will show rows shuffling between refreshes — intermittent, hard to reproduce, and it
will not look like a sort bug.

### 5d.1 🔴 A STALE DOCSTRING THAT WILL MISLEAD A PORTER

`renderTaskListTable` (:11291) still describes the pre-disclosure table:

> *"**Eleven columns**: ID · Title · Class · Status · Blocked by · Next chase · Accountable · Filed by
> · Priority · Project · Detail"*

**`ROW_SCHEMA` (§5a.1) contradicts it**: the visible line is five fields plus the disclosure cell —
**six**. The other six fields moved behind the disclosure. `_rowWidth()` returns
`ROW_SCHEMA.line1.length + 1`, so the *code* is right and the *comment* is stale.

⇒ **Port from `ROW_SCHEMA`, never from this docstring.** Flagged rather than fixed: this row is
read-only, and the fix is a one-line comment change somebody should make deliberately.

⚠️ It also names a different field ORDER than `ROW_SCHEMA.line1` (`id, title, class, status,
priority`) — Priority sat ninth there and is fifth now. **Two stale facts in one sentence.**

### 5d.2 Group header markup — task list

Each owner is its **own `<tbody class="task-group" data-owner="…">`**, opening with a clickable
group-header accordion bar: **chevron + `"owner · N"` label**, then that owner's rows.

⇒ **The grouping unit is a `<tbody>`, not a wrapper `<div>`.** One table, many bodies. A port that
emits a div-per-group breaks the column alignment the single table gives for free.

## 5e. Colours, value by element — and why the coupling in §4 exists

> §4 gave a palette and where it lives. §6 said a spec needs value-by-element. Here it is, plus the
> mechanism that explains four of the five couplings this document has found.

### 5e.1 The status palette — exact values

Declared **twice, identically**, and the duplication is deliberate:

| custom property | value | meaning |
|---|---|---|
| `--task-blocked` | `#c62828` | red — blocked, owed + waiting |
| `--task-active` | `#2e7d32` | green — `in_progress` / `claimed` |
| `--task-review` | `#1565c0` | blue — awaiting review |
| `--task-queued` | `#f57f17` | amber — queued, not yet started |
| `--task-done` | `#9e9e9e` | grey — terminal: done |
| `--task-dropped` | `#bdbdbd` | light grey — terminal: dropped |
| `--task-unknown` | `#bdbdbd` | light grey — unrecognised status |

Sites: `task-list.css:63-69` (on `.task-list-table`) and `epic-board.css:26-32` (on
`.epic-board-table`).

⚠️ `--task-dropped` and `--task-unknown` are **the same value**. Deliberate or not, a port that
"tidies" them into one property loses the ability to change one without the other.

### 5e.2 🔴 THE MECHANISM — the props are scoped to a CLASS, not to `:root`

This is the single fact that explains the CSS coupling in §4 and §5c.4:

```
.task-list-table  { --task-blocked: …; … }    /* task-list.css:62 */
```

**Not `:root`. Not `html`. The table class itself.** So a custom property is only visible to
elements inside a table carrying that class. Consequences, all measured:

| pane | table class | gets the props |
|---|---|---|
| Task List | `task-list-table` | ✅ declares them |
| **Holding Area** | `task-list-table holding-area-table` | ✅ **inherits — re-declares NOTHING** (verified: zero `--task-*` declarations under `.holding-area-table`) |
| Epic Board | `epic-board-table` | ❌ carries neither → **must re-declare, and does** |

`epic-board.css:9` states exactly this: *"The status custom props are RE-DECLARED on
`.epic-board-table` because … `.task-status-*` dot rules would resolve every dot to the fallback
grey."*

⇒ **The holding area's odd double class in §5c.4 is not sloppiness — it is how that pane gets its
colours.** Strip `task-list-table` from it in a port and **every status dot silently turns grey**.
Nothing errors; the page renders; the meaning is gone.

⇒ **And the epic board's duplication is not drift** — it is the correct response to a class-scoped
property. A port that hoists these to `:root` removes the need for both, which is a **design change**
and must be a decision, not a side effect of tidying.

### 5e.3 Colour is never the only signal

`task-list.css:57-60`: *"Color is ALWAYS redundant with the status WORD in the Status cell
(WCAG 1.4.1)."*

The props drive **two** elements: the `.task-status-dot` background
(`.task-status-{blocked,dropped,unknown} .task-status-dot { background: var( --task-… ) }`,
:439-448) and a **3px row left-accent**.

⇒ **A TS port must keep the status word in the cell.** Dropping it because the dot "already says it"
is an accessibility regression that no visual-parity tier will catch — both look identical to a
computed-style comparison.

### 5e.4 Surface palette (from §4, restated as values)

`#28a745` success · `#6c757d` and `#868e96` muted · `#e9ecef` / `#f8f9fa` / `#fafafa` surfaces ·
`#007bff` accent · `#495057` body · `#333` text · `#adb5bd` disabled.

Persona colours arrive as `rgba( var( --persona-color-rgb, <fallback triple> ) )` — **the fallback
triple is part of the contract**; omit it and unknown personas change colour rather than degrading
to the intended neutral.

## 5f. Truncation, widths and responsive behaviour

> §6 said this needed a live browser. **Most of it did not** — the rules are in CSS, and
> `task-list.css` carries its own measured width table. What genuinely still needs a browser is
> narrower than I thought, and is named at the end.

### 5f.1 The six-column schema is percentage-based, and the reason is a spec line

`task-list.css:1097` onward. **Identical in all three panes** — *"because the requirement is that a
reader never re-parses the left-to-right layout when switching views."*

| column | % | px at 916 |
|---|---|---|
| id | 8.52 | 78.0 |
| title | **59.06** | **541.0** |
| class | 6.77 | 62.0 |
| status | 11.35 | 104.0 |
| priority | 8.73 | 80.0 |
| disclose | 5.57 | 51.0 |
| | **100.00** | **916.0** |

🔴 **WIDTHS ARE PERCENTAGES ON PURPOSE, AND THE COMMENT SAYS WHY**: *"The pane is 916px, but 916 is
NOT declared anywhere in this repo's CSS — it is a computed width … Hard-coding 916 here would pin
the layout to a number no rule owns, and would overflow the moment any ancestor moved."*

⇒ **A TS port must use percentages of the table's own width, not pixel columns.** Pixel columns
would appear to work at one pane size and break silently at every other.

⚠️ **`.section-content` is 956 border-box and 916 after its 20px padding** — *"which is how two
correct measurements of 'the pane' can differ by 40."* Both numbers are right; say which you mean.

⚠️ The status column previously **disagreed between panes** (87.4 task list / 100.4 holding area).
The schema unified it at 104. A port that re-derives widths per pane re-opens that divergence.

### 5f.2 A measured near-miss worth porting the reasoning of

`disclose` was first set to **3.71% (34px)** and the `⋯` rendered **7px outside the pane**, adding a
horizontal scrollbar — `paneScrollWidth 923` against `clientWidth 916`. The cell needs
**10 + 31 + 10 = 51px**: padding either side of a 31px button.

⇒ **The control cell's width is derived from the button plus its padding, not chosen.** A port that
picks a round number reproduces the overflow.

### 5f.3 Title truncation — clamp, not character cap

```css
.task-row .task-col-title .task-title,
.epic-row .task-col-title .task-title {
    display: -webkit-box; -webkit-line-clamp: 2; line-clamp: 2;
    -webkit-box-orient: vertical; overflow: hidden;
    overflow-wrap: anywhere; line-height: 19.5px;
}
```

**Two lines, then clipped.** ⚠️ *"THE `title=` TOOLTIP STAYS ON THE `<td>`, so a clamped title is
still readable in full on hover. A clamp that hides text with no way to recover it would be the
character cap again wearing a different mechanism."*

⇒ **The clamp and the `title=` attribute are one mechanism, not two features.** Port the clamp
without the tooltip and you have re-created the JS character cap this codebase deliberately removed
(§5a.6).

### 5f.4 Responsive — there is exactly ONE media query

Across `task-list.css`, `epic-board.css` and `shared/notifications-surface.css`, one rule:

```css
@media ( max-width: 900px ) { .task-controls-row .task-actions { flex-wrap: wrap; } }
```

⇒ **Responsive behaviour is carried almost entirely by the percentage widths**, not by breakpoints.
The single query wraps the *disclosed* controls row below 900px and touches nothing else.

⚠️ **Do not read this as "the panes are not responsive."** They are — by percentage. A port that adds
breakpoints is adding a mechanism this design deliberately does without.
