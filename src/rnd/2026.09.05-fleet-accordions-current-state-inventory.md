## 0. Read this first — two claims that will mislead you if you skip them

**① "Four" is the file's number, not a selection.** `notifications.html` contains **fifteen**
`.collapsible-section` divs. Exactly four carry a toolbar toggle button, and exactly four have a
render container the JS writes into — and **both fours name the same four**. Two independent
signals, same answer.

**② The four are SIBLINGS, not nested.** An early hypothesis held that four accordions live *inside*
the fleet-status pane. **Refuted on both sides:**

| side | evidence |
|---|---|
| legacy | `#section-fleet-status` (`notifications.html:687-763`) holds a header, a ▼ toggle, the fleet-size-cap controls, one container. No nesting. |
| multiplexer | `FleetStatusRenderer.ts:125` says it itself — *"The container IS the collapsible body"*. Its `toggle` is `renderFleetOfflineToggle`, a Show/Hide-offline **view** button (*"read-only — changes what the table shows, never fleet state"*, `fleetStatusTable.ts:44`). Its `group` is `groupFleetByManager`, a **table row grouping**. |

⚠️ **john measured SIX sections in the multiplexer and was right.** His six are the *destination*;
these four are the *source*. Only **Fleet Status** and **Task List** exist on both sides — which is
exactly why the two counts look like they should reconcile and do not.

## 2. Structure — shared vs duplicated, and it is LAYERED

The question "one component or four near-duplicates?" has no single answer. It resolves differently
at three layers, and a spec written at the wrong layer will be wrong.

### 2.1 SECTION layer — four separate implementations

Normalising each render body (every surface token → `X`), dropping punctuation-only and sub-12-char
lines, shared substantive lines against the **smaller** body:

| pair | shared | |
|---|---|---|
| epic-board vs task-list | 19/36 | **52%** |
| epic-board vs fleet-status | 8/36 | 22% |
| fleet-status vs task-list | 7/44 | 15% |
| holding-area vs any | 3/41 | **7-8%** |

⇒ **One lineage plus two independents**: epic-board was forked from task-list; holding-area and
fleet-status share almost nothing with anything.

⚠️ **What this measurement can and cannot see.** It is line-level identity after normalisation, so
it sees **copied structure**. It **cannot** see two independent implementations of one behaviour —
a low score is not evidence of differing behaviour.

### 2.2 ROW layer — task-list and epic-board ALREADY SHARE ONE RENDERER

🔴 **This is the single most important fact in this document for a "carbon copy".**

`_renderEpicRow` (`notifications.js:13418`) is a thin wrapper:

```js
return this._renderRow( task, null, { rowClass: "epic-row" } );
```

Its own docstring:

> *"IT USED TO BE A SECOND IMPLEMENTATION, with its own column order (ID / P / Status / Title /
> Actions), no Class field, and its own colspans. That is exactly the shape Rick asked us to kill:
> moving between the epic board and the task list meant re-parsing the layout. The markup now lives
> in `_renderRow` alone"* ... *"identical cell-for-cell to the task list's row, by construction."*

⇒ **Spec line: the TS side must render task-list rows and epic-board rows identical cell-for-cell.**
This is an observable behaviour Rick personally asked for. A spec that documents the two panes
separately, in good faith, is how it silently gets re-split.

⚠️ `_renderEpicRow` passes `null` for the timezone **deliberately** — *"this pane never had one, so
next-chase formats exactly as it did before."* Not an omission; do not "fix" it in the port.

### 2.3 DATA layer — epic-board and task-list read the same endpoint

`renderEpicBoard` calls **`fetchTaskList`**. Same function, same endpoint:

```
/api/tasks?limit=500&unscoped_audit=true&hide_parked=false&char_budget=0   (shared/task-list-query.js:50)
/api/tasks?limit=500&unscoped_audit=true&status=not_approved&char_budget=0 (shared/task-list-query.js:79)
```

Epic board is **the same rows as the task list, grouped on `correlation_key` instead of owner.**
Fleet-status uses `fetchFleetState`; holding-area uses `fetchHoldingArea`.

## 3. The two collapse axes

| axis | what collapses | mechanism |
|---|---|---|
| **1 - section** | the whole accordion | toolbar button + header `onclick="toggleSection(...)"` + a `▼` `.toggle-button`; body is `.section-content`, hidden by `[data-collapsed="true"] > .section-content` |
| **2 - group** | groups *within* a section | task-list: owner groups · epic-board: epic groups · holding-area: `.holding-area-group` |

### 3.1 🔴 Axis-2 persistence has OPPOSITE POLARITY between the two panes

| key | declared | shape |
|---|---|---|
| `lupin.taskList.collapsedOwners` | `notifications.js:444` | JSON **ARRAY** of **COLLAPSED** owner keys |
| `lupin.epicBoard.groupState` | `notifications.js:459` | JSON **MAP** of key -> **isEXPANDED** |

Same feature, **inverted sense, different container type**. Both swallow write errors on purpose —
*"a private-mode / quota failure must never break rendering."*

`toggleEpicCollapsed( epicKey )` :13399 reads `loadEpicGroupState()`, flips, calls
`saveEpicGroupState( state )`, returns the **new collapsed boolean**.

> **Correction recorded rather than hidden**: I first reported epic collapse as *not persisted*. It
> is. I had grepped for `COLLAPSE` and the key is named `groupState` - a name-shaped search missing
> the use, in the middle of a job about exactly that hazard.

## 4. Look - where the colours actually live

`notifications.html` loads, in order:

```
lupin-base.css · shared/notifications-surface.css · notifications.css?v=20260904b
lupin-nav.css · broadcast-panel.css?v=20260619a · task-list.css?v=20260904c · epic-board.css?v=20260904a
```

| file | lines | owns |
|---|---|---|
| `shared/notifications-surface.css` | 1237 | `.collapsible-section`, `.date-accordion*`, the surface chrome |
| `task-list.css` | 1368 | ⚠️ **also** `.holding-area-*`, `.epic-board-table`, `.epic-row`, `.flow-ratio-*`, `.task-accordion-btn` |
| `epic-board.css` | 236 | `.epic-accordion-btn`, `.epic-group-*`, `.epic-story-row`, `.epic-board-table` |

🔴 **`.epic-board-table` is styled from BOTH `task-list.css` and `epic-board.css`.** `epic-board.css:9`
states this is deliberate - *"The status custom props are RE-DECLARED on `.epic-board-table`"* - so
**load order is load-bearing** and a port that consolidates these files can silently change the
cascade.

⚠️ **`task-list.css` is not a task-list file.** It is the de-facto shared stylesheet for three of the
four surfaces. Its name is the trap.

Palette is literal hex, not tokens - `#28a745` success, `#6c757d`/`#868e96` muted, `#e9ecef`/`#f8f9fa`/
`#fafafa` surfaces, `#007bff` accent, `#495057` body - plus persona-driven
`rgba( var( --persona-color-rgb, ... ) )` with **built-in fallbacks**; the fallback triple must be
carried over or unknown personas change colour.
