## 1. The problem in one line

The VM can't reach private GitHub, so today **you (the dev box) are the only distributor** — every VM update
requires you to ship a bundle. The question: keep that, or make the VM a first-class git peer that anyone can
`pull`/`push` from directly?

## 2. Options, compared

| Option | Creds on VM | Repos reachable | Unattended (cron/systemd)? | Who it acts as | Setup weight | Blast radius if VM compromised |
|---|---|---|---|---|---|---|
| **A. Bundle** (today) | none | n/a (file-fed) | ✅ (file is local) | — | ✅ done | none — no creds to steal |
| **B. Deploy key** | 1 SSH key | **1 repo** | ✅ | the key | light | that one repo (revoke key) |
| **C. Machine user (bot)** | 1 SSH key | **many** (org/team) | ✅ | bot account | medium | every repo the bot can see |
| **D. GitHub App** | short-lived install token | fine-grained per-repo | ✅ | the app install | heavy | scoped + short-lived (smallest) |
| **E. SSH agent forwarding** | **none** | **all yours** | ❌ interactive only | **you** | trivial (`-A`) | your agent, only while connected |

## 3. What each is actually good for

- **A — Bundle** (`push-bundle`): simplest, most locked-down (no creds at rest). Cost: you're forever the
  distributor; the VM can only get what you ship. Great for a low-touch test box; poor for a self-updating deploy.
- **B — Deploy key**: the classic "server needs one repo." Clean and revocable, but **one key per repo** — the
  ceiling you flagged. Fine if the VM only ever tracks `lupin`; annoying once it needs `planning-is-prompting` + more.
- **C — Machine user**: one identity, many repos, unattended. The standard answer for a build/deploy server that
  touches several repos. Cost: a shared bot identity (commits/pushes attributed to it), and a write-enabled bot on a
  shared VM = anyone with VM access can push as it.
- **D — GitHub App**: automation-grade. Short-lived, fine-grained tokens minted per operation → smallest blast
  radius and no long-lived secret on the box. Cost: the most setup (app registration, installation, token minting).
  The right end-state if the VM becomes a real deployment platform.
- **E — Agent forwarding**: best match for "treat the VM like my dev box." Nothing stored; your local key is
  forwarded over the IAP session, so `git pull`/`push` on the VM run **as you** against **all** your repos. Each
  teammate uses their own key. Cost: **interactive only** — no unattended jobs; and the VM root can use your agent
  while you're connected (don't forward onto an untrusted host).

## 4. Recommendation

Two axes decide it: **interactive vs unattended**, and **one repo vs many**.

- **Now (done):** keep **A (bundle)** for shipping controlled snapshots — `push-bundle` makes it one command.
- **For hands-on "it's my dev box" work:** add **E (agent forwarding)** — one-line change to `lupin-vm.sh shell`
  (`--ssh-flag="-A"`). Zero creds at rest, your identity, every repo. This directly answers "not limiting."
- **When the VM needs to self-update unattended (a deploy pipeline):** go **D (GitHub App)** — or **C (machine
  user)** as the lighter interim. Not **B** (single-repo ceiling).

**Suggested path:** A now → add E for interactive use → graduate to D when unattended deploys arrive. Skip B —
its one-repo limit is exactly the constraint you want to avoid.

## 5. What exists today (implemented this session)

- `lupin-vm.sh push-bundle [branch] [--checkout]` — rebuilds the VM bundle from this dev checkout + `git fetch`
  on the VM. **Fetch-only by default** (refs update, working tree unchanged); `--checkout` points the tree at the
  branch. **Code-sync only — does NOT restart the servers.** Verified live: VM fetched `wip-v0.1.9` → `FETCH_HEAD`,
  `origin/wip-v0.1.9` created.
- `lupin-vm.sh push-repo <local-path> [dest-name]` — archive+SCP a local repo as a sibling under `/mnt/lupin-data/`
  (no `.git`; for fresh sibling repos, not for updating lupin).
- **`lupin-vm.sh deploy [branch]` — the full one-shot cycle (added 2026-07-23).** Closes the last mile:
  `push-bundle --checkout` (move the tree) → **restart `:7999` `lupin-rest`** (docker compose force-recreate) →
  **restart `:8001` arbiter** (host `systemd --user` unit) → **verify** (print checked-out `HEAD`, probe `/health`
  on both ports). Both restarts are mandatory because **neither server hot-reloads on the VM**: `:7999` runs with
  `LUPIN_ENV=testing` (uvicorn `--reload` OFF), and the arbiter is `reload=False` by design. `push-bundle` and
  `deploy` share one internal `do_push_bundle` primitive, so the bundle/checkout plumbing never drifts between them.

**Does the branch get checked out on the VM after a bundle push?** **No** — `push-bundle` fetches; the working
tree stays on its current branch until `push-bundle --checkout` (or a manual `git checkout <branch>` on the VM).
This is deliberate: a working-tree move re-points the bind-mounted `./src` the app runs from, so it's opt-in.
**`deploy` always checks out** (that is its whole point) and then restarts, so the running servers actually pick
up the new code.

### 5a. WHERE these commands run — dev box vs the laptops (Rick, 2026-07-23)

`deploy` is a **dev-box operation**: it builds a local `git bundle`, which requires the git checkout *and* the
GitHub-backed history that live on the dev box (and, by extension, any laptop that holds a full lupin checkout).
It is **not** run *from the VM* — the VM is the deploy *target*, not the actor.

The rest of `lupin-vm.sh` is the opposite: the **majority of day-to-day use** is the **two laptops remoting into
the VM** to operate the running Lupin app — `shell`, `tunnel`, `svc status|logs|restart`, `vm-start/stop`. Those
need only `gcloud` + IAP access, no checkout. So the mental model is:

| Command | Run from | Needs a lupin checkout? | Role |
|---|---|---|---|
| `deploy`, `push-bundle`, `push-repo` | **dev box** (distributor) | **yes** (builds the bundle) | ship code to the VM |
| `shell`, `run`, `tunnel`, `svc *`, `vm-*`, `firewall *` | **laptops / any machine** | no | operate / observe the VM |

**No cron (Rick, 2026-07-23):** `deploy` is an **on-demand** operation, invoked by hand when you want the VM on a
new commit — deliberately **not** wired to a timer/cron. If unattended self-update is ever wanted, that is the
separate GitHub-App path (Decision #2), not a cron wrapper around `deploy`.

### 5b. COMMITTED work only — the bundle never ships an in-motion tree (Rick, 2026-07-23)

`git bundle create <file> <branch>` packs the objects reachable from the **branch's committed tip**. That means
what reaches the VM is **committed history only** — three categories are *excluded by construction*:

- **working-tree edits** (modified-but-not-staged),
- **staged-but-not-committed** changes (the index),
- **untracked files.**

Nothing "in motion" can be pushed: the bundle captures a commit object, not the state of your editor. The VM's
`git checkout -B <branch> FETCH_HEAD` then lands *exactly* that committed snapshot — byte-for-byte the tip commit,
never a half-saved file. This is inherent to `git bundle` (it is a transport for commits/refs), not a flag we set.

⚠️ **Consequence — commit before you deploy.** `deploy [branch]` (and `push-bundle`) ship the branch's **last
commit**, not your live working tree. If you have local edits you want on the VM, **commit them first**; an
uncommitted change is silently left behind (correct, safe — but surprising if you expected "deploy = whatever I
see in my editor"). Rule of thumb: `git status` clean on the target branch ⇒ what you see is what deploys.

## 7. Full new-instance bring-up runbook (dev-box CLI + Vertex Opus 4.8) — 2026-07-23

The end-to-end sequence to make a fresh VM's **host CLI** identical to the dev box (Claude Code + Agent SDK +
cosa-voice MCP + 8 hooks + shell env + direct Opus 4.8 via Vertex). Every state-changing `gcloud` step runs from
the **dev box** (`!` prefix / your terminal); the Bash classifier blocks the agent from those. Order matters.

| # | Step | Command / action | Runs on | Verify |
|---|------|------------------|---------|--------|
| 1 | Sync code | `lupin-vm.sh deploy` | dev box | both servers 200 |
| 2 | Install CLI (uv → Python 3.13 → Agent SDK → `claude`) | `lupin-vm.sh install-cli` | dev box | prints python 3.13.x, Claude Code ver, `claude-agent-sdk` ver |
| 3 | Push shell env (aliases + `LUPIN_ROOT` + `PLANNING_IS_PROMPTING_ROOT` + `~/.lupin/config`) | `lupin-vm.sh push-env` | dev box | on VM: `env \| grep ROOT`, `cat ~/.lupin/config` |
| 4 | Install cosa-voice MCP **+ the 8 hooks** | `cd $LUPIN_ROOT && src/scripts/install-cosa-voice.sh` | **VM** (from inside the repo) | `claude mcp get cosa-voice` (Scope: User); "Hooks: 8/8" |
| 5 | Grant the **VM service account** Vertex access | `gcloud projects add-iam-policy-binding hello-world-foo-423219 --member="serviceAccount:lupin-host-test-sa@hello-world-foo-423219.iam.gserviceaccount.com" --role="roles/aiplatform.user"` | dev box | wait ~1 min for propagation |
| 6 | Vertex env for Opus 4.8 (global-only) | export `CLAUDE_CODE_USE_VERTEX=1`, `ANTHROPIC_VERTEX_PROJECT_ID=hello-world-foo-423219`, `CLOUD_ML_REGION=global` in VM `~/.bashrc` | VM | a real predict returns 200 at `global` |
| 7 | Claude Code OAuth (interactive, one-time) | run `claude` once, complete login | VM | session starts |

**Gotchas learned this session (each cost a round-trip — encoded so the next spin-up doesn't repeat them):**
- **`install-cli` is idempotent** — `uv venv --clear` wipes a half-built venv from a failed first run (commit `d90415a6`).
- **`LUPIN_ROOT`/`PLANNING_IS_PROMPTING_ROOT` are NOT in the aliases file** — the aliases *reference* them; `push-env`
  now *exports* them with **VM-correct** paths (`/mnt/lupin-data/{lupin,planning-is-prompting}`), never the dev
  `/mnt/DATA01` paths. The env-var NAMES are canonical and unchanged; only the values adapt (commit `5eb54324`).
- **MCP ≠ hooks.** `install-cosa-voice.sh` registers the MCP server AND now installs the 8 hooks from the canonical
  in-repo template `src/conf/claude-code-hooks.json`. Both are `$LUPIN_ROOT`/`$PLANNING_IS_PROMPTING_ROOT`-relative,
  so the SAME template ports verbatim (no path rewriting).
- **Two Vertex principals.** The **dev box** authenticates as your user `admin@rickruiz.altostrat.com`; the **VM**
  authenticates as its attached **service account** `lupin-host-test-sa@…`. Each needs its OWN `roles/aiplatform.user`
  grant — granting the user does nothing for the VM (step 5).
- **Opus 4.8 on Vertex is `global`-only.** A regional `CLOUD_ML_REGION` (e.g. `us-central1`) → model-not-found;
  `us-east5` currently → quota 429. The Claude Code wizard tests a non-global region and mis-reports the failure as
  "permission denied" — SKIP its verification (Save anyway); the env vars in step 6 are the real config.
- **The 8 hook event-types:** SessionStart, SessionEnd, UserPromptSubmit, PreToolUse (×2 matchers), PostToolUse,
  Stop, Notification, PermissionRequest.

## 7a. Addendum — 2026-07-24 fixes (Mr. Radio) : dedicated CC venv, notify auth, env + tooling

A live VM bring-up surfaced several gaps the 2026-07-23 runbook did not cover. All committed on
`wip-v0.1.9-2026.06.21-bug-fix-implementation` (`abd217c7`→`289d793a`). The step table above is amended by the
notes below.

### The single biggest trap — `$LUPIN_ROOT/.venv` is the ARBITER's venv on the VM
On the VM, `$LUPIN_ROOT/.venv` is a **symlink → `.venv-arbiter`** (uid-1001, Python 3.10 — the arbiter service's
venv). The installer + hooks defaulted to `$LUPIN_ROOT/.venv/bin/python`, so the entire host CC integration (MCP
server + 8 hooks) was pointed at another service's venv: **missing deps AND unwritable by the operator**. The dev
box masks this (there `.venv` is the operator-owned venv). Fix (commits `a3afbe7c` + `de9291d4`):
- `install-cosa-voice.sh` now resolves a dedicated **`LUPIN_CC_VENV`** (default `$LUPIN_ROOT/.venv`; per-machine
  override), **provisions** it (`uv venv --python 3.13` + installs the host closure), and **refuses** (loud) to
  register when the resolved venv is a symlink into a foreign-uid service venv.
- The host closure is **`fastmcp==2.14.2 requests pydantic regex pytz`** (`regex`/`pytz` come in transitively via
  `cosa.utils.util`; confirmed complete when MCP connected with 30 tools).
- Hooks resolve their interpreter from `${LUPIN_CC_VENV:-$LUPIN_ROOT/.venv}`.
- **On the VM, set `LUPIN_CC_VENV=$HOME/.venv-lupin-mcp`** (operator-owned). `push-env` now exports it; but a
  `gcloud ssh --command` shell is non-login (does NOT source `~/.bashrc`), so run the installer from an
  **interactive** VM shell, or pass it inline: `LUPIN_CC_VENV=$HOME/.venv-lupin-mcp bash …/install-cosa-voice.sh`.

### `push-env` now exports more (step 3 amended)
`push-env` writes VM `~/.bashrc` (idempotent) with, additionally: `DEEPILY_PROJECTS_DIR=/mnt/lupin-data` (alias
library depends on it), `LUPIN_CC_VENV=$HOME/.venv-lupin-mcp`, and `LUPIN_DEV_EMAIL=ricardo.felipe.ruiz@gmail.com`
(notify() target-user). It does **NOT** ship `LUPIN_API_KEY` — see next. The `~/.lupin/config` seed is
**create-only** (`if [ ! -f ]`), so hand-edited `[lupin]`/`[plan]` sections are never clobbered on re-run.

### Notify auth is a TWO-part credential chain (new — the 401s)
`notify()` needs BOTH:
1. **`LUPIN_DEV_EMAIL`** (target-user) — shipped by `push-env`. Without it: 401 "no target user". `~/.lupin/config`
   `global_notification_recipient` is NOT read in the hook/MCP runtime — the env var is.
2. **`LUPIN_API_KEY`** (the `X-API-Key`, `ck_live_` format) — **per-DATABASE**, validated against a bcrypt hash in
   the server's `api_keys` table. The dev-box key is NOT valid on the VM's separate test DB — it must be **MINTED
   against the VM DB**. Do NOT ship the dev key (a reverted footgun: it can't validate cross-server AND would
   clobber the manual VM key via `~/.bashrc` last-wins — commit `90b56fd4`).

**Mint the VM notify key** — run INSIDE the app container (host venvs lack `sqlalchemy`/`bcrypt`; the container holds
the exact test DB + connection):
```
docker exec -w /var/lupin lupin-rest-cloud-gpu \
  python src/scripts/create_service_account_postgres.py \
  --email=claude.code@lupin.deepily.ai \
  --description="Claude Code cosa-voice notifications on lupin-host-test VM (created YYYY-MM-DD)"
```
- The DB is chosen by the **container's `LUPIN_ENV`** (prints `PostgreSQL Environment: testing`), NOT `--env`
  (which only labels the key file). Do not override it.
- Step 1 is idempotent ("Using existing service account"), so re-runs are safe.
- **Gotcha (fixed `289d793a`):** `/var/lupin` is a **read-only** mount, so the Step-4 write-to-file failed and
  originally aborted the run before Step 5 printed the plaintext — the key was lost (DB keeps only the hash). The
  script now catches that OSError and continues to Step 5, which prints the key "shown only once". **Capture it
  from stdout** and `export LUPIN_API_KEY=<value>` on the host, then restart `claude`.

### WS notification-listener needs per-project creds + the right launch dir (new)
A VM `claude` launched from `/mnt/lupin-data/planning-is-prompting` auto-detects project **`plan`**; the CC
Notification Listener then fails because the VM `~/.lupin/config` has no `[plan]` (or `[lupin]`) section. For a clean
lupin test, launch `claude` from the **lupin** dir and ensure a `[lupin]` section (email/password) exists on the VM
(hand-edited; `push-env` won't overwrite it). This is separate from the `X-API-Key` above.

### `.mcp.json` must never be committed (new — scope-conflict warnings)
A committed `.mcp.json` with absolute dev-box paths pollutes every checkout (on the VM: EACCES + a stale
cosa-voice scope-conflict warning). Removed from **lupin** (`98a1ac7f`) and **planning-is-prompting** (María, PIP
`58bd6b1`), both now `.gitignore`d. cosa-voice is a **per-machine USER-scope** MCP — never a committed project scope.

### Tooling quality-of-life (new)
- `lupin-vm.sh tunnel` takes **`TUNNEL_VERBOSITY`** (default `critical`) to silence benign macOS
  `[Errno 9] Bad file descriptor` IAP noise; `TUNNEL_VERBOSITY=info` restores full logs (`abd217c7`).
- `shell`/`run`/`svc` now send an **SSH keepalive** (`ServerAliveInterval=60`, `CountMax=3`) so idle sessions no
  longer drop with `Broken pipe` / exit 255 (`5369519d`).
