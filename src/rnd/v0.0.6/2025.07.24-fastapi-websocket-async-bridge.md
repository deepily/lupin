# FastAPI WebSocket Audio Streaming – Async Bridge and Session Solutions

## Problem Overview and Architecture

Your FastAPI application uses **native WebSockets** (no Socket.IO) with a custom `WebSocketManager` to manage connections. Each user establishes **two WebSocket connections**: one for real-time queue updates (`/ws/queue/{session_id}`) and another for streaming text-to-speech audio (`/ws/{session_id}`). The intended flow is: the user asks a question → the server processes it and emits a `speech_update` event via the queue WebSocket → the browser receives this and triggers audio playback (with HybridTTS audio data streaming over the audio WebSocket).

Right now, **audio is not playing** as expected. The root causes are twofold:

- **Session ID mismatches:** The client and server are using different `session_id` values (e.g. browser shows "wise penguin" while server references "graceful cheetah"), leading to 404 errors and messages not reaching the correct WebSocket. This likely arises from multiple tabs or reconnects generating new session IDs without cleaning up the old ones.

- **Async vs. Sync context conflict:** Your background **COSA queue** (running in sync threads) calls `emit_to_user_sync()` in `WebSocketManager` to send WebSocket messages. This crosses the boundary from *synchronous thread code* to *async WebSocket sending*, causing warnings like *“coroutine was never awaited”*. In particular, you see `RuntimeWarning: coroutine 'WebSocketManager.emit_to_user' was never awaited`, indicating that an async function was called from a sync context without being properly awaited or scheduled. WebSocket send operations are **asynchronous** and must run in the event loop, not directly in a background thread【4†L90-L97】.

## Issue 1: Session ID Mismatch and WebSocket Session Management

Each WebSocket connection currently uses a **random session identifier** (e.g. “wise penguin”, “graceful cheetah”). When multiple browser tabs/windows are open or when a client reconnects, new session IDs are generated but the server may still have the old session in its connection mapping. This leads to confusion about where to send events:

- In your case, the server tried to stream audio to *graceful cheetah* (old session), but the browser was listening on *wise penguin* (new session), hence no audio and 404s. This suggests the `WebSocketManager` was not updated or was still targeting the stale session.

**Why it happens:** Likely the client-side generates a new session ID on each new tab or reconnect (instead of reusing a stable ID), and the server’s `WebSocketManager` either doesn’t remove the old connection or doesn’t know which one to use. The result is **multiple active session IDs for one user**. Indeed, if a user refreshes a page or opens a second tab, you might briefly have two WebSocket connections for that user. Without cleanup, the server might attempt to send data to the wrong one.

**Best Practices for Session Management:** 

1. **Map WebSockets by User (and support multiple connections if needed):** Upon WebSocket connect, associate the WebSocket with the *user’s ID* (you mentioned adding this for the audio WS, which is good). Use a data structure that allows multiple connections per user if you intend to support multi-tab or multi-device sessions. For example, keep a dictionary mapping `user_id -> list of WebSocket connections` instead of just one【20†L52-L60】. This way you can target all of a user’s sessions or a specific one. If you only want **one active session per user**, you can still map by user but decide to replace the old connection (see next point).

2. **Cleanup and De-duplication:** Ensure that when a WebSocket disconnects, it’s removed from your manager. FastAPI’s WebSocket endpoint can catch a `WebSocketDisconnect` exception – use that to call a `manager.disconnect(session_id or user_id)` that pops it from the internal dict. This prevents the server from keeping “ghost” entries. If a user opens a new tab (new session), you have a design decision: you can **replace the old session** with the new one, or support both. Many systems will drop the old connection when a duplicate session is detected. As a recent guide notes, *“if a user refreshes their browser, you may see two connections briefly overlap. If a session is duplicated, decide whether to replace the old one or support both. Implementing a cleanup policy on disconnection is important”*【20†L93-L100】. In your scenario, since audio should play in the latest active window, you might choose to close the previous audio WS when a new one connects for the same user.

3. **Consistent Session ID usage:** Ideally, the **same session ID** should be used for both the queue WS and audio WS in a given client session. Verify that your frontend is indeed using one ID for both endpoints (it sounds like it is, but the mismatch implies otherwise). If the frontend is generating these IDs, consider storing the session ID in a cookie or `localStorage` so that a refresh or new tab reuses the existing session ID instead of creating a new random one. A stable session identifier (tied perhaps to the user’s session or conversation context) will avoid the mismatch entirely. Alternatively, you could use an authentication token or user ID in the WebSocket URL or headers (FastAPI can accept query params or headers on WS connect). For example, passing a JWT or token on connect and looking up the user – then you rely on user ID alone for routing【20†L45-L53】. In any case, **server-side mapping** should ultimately use the user (or conversation) identity to route messages, rather than an ephemeral name string that can desynchronize.

4. **Targeting the Correct WebSocket:** When emitting events, ensure you target the right connection. If your `WebSocketManager.emit_to_user(user_id, event, data)` currently sends to *all* of a user’s connections, you might want a method to emit to a specific session. For instance, you could include the `session_id` in the `speech_update` event payload or in the task context, so that when it’s time to stream audio, you know which session’s audio WS to use. If you maintain a mapping of `session_id -> WebSocket` (perhaps alongside user mapping), you can call `emit_to_session(session_id, data)` to send only to that client. This way, multiple sessions for a user won’t mix up their audio streams. The key is to **track that session ID through the workflow** of the question-processing task, so the right one gets the audio.

By cleaning up stale connections and using a consistent mapping strategy, the server will “know” about the correct session (the one the browser is actually using) and send the audio data there. You’ll eliminate the scenario where the server “only knows about graceful cheetah” while the client is on “wise penguin.” In practice, after these fixes, you should no longer get 404s on the audio endpoint because the session IDs will align.

## Issue 2: Bridging Synchronous Queues with Async WebSocket Sends

The COSA queue system runs in background threads (no asyncio event loop). Yet it needs to trigger WebSocket sends, which are async operations tied to the main event loop. Python asyncio does **not** allow simply calling an async function from a normal thread – if you do so without the proper handling, you get a coroutine object that was never awaited (hence the RuntimeWarning). Moreover, FastAPI’s WebSocket objects are not thread-safe; you cannot call `websocket.send_*` from a different thread directly without risking race conditions【4†L90-L97】.

**Why your attempts failed:**

- `asyncio.create_task()` in a thread: This throws `RuntimeError: no running event loop` because `create_task` must be called from within an active event loop (usually on the main thread in FastAPI). In a plain thread, there is no loop by default.

- `loop.run_until_complete()` from the background thread: This fails because the FastAPI/Uvicorn event loop is already running on the main thread. You can’t start/run the loop again from another thread – doing so either raises an error or would block if somehow called on the main loop.

- `asyncio.run()` inside a thread: This attempts to create a brand new event loop to run the coroutine. It conflicts with the existing loop and can lead to errors (e.g. if it tries to use resources like the WebSocket that belong to the main loop). Also, it’s generally not recommended to nest `asyncio.run` when an event loop is already running.

**Correct Approaches to Sync→Async Bridge:**

To safely have synchronous code notify async WebSockets, you need to **schedule the coroutine on the existing event loop** (the one running your FastAPI app). In other words, the background thread should hand off the work to the main thread’s loop. Python provides thread-safe mechanisms to do this:

1. **`loop.call_soon_threadsafe()`**: This is a method on the event loop that schedules a callback to be called in the loop’s thread **as soon as possible**. Crucially, it’s **safe to call from another thread**【32†L300-L307】. You can obtain the event loop in the main thread (e.g. store `loop = asyncio.get_running_loop()` in a startup event or global variable). Then, in your sync thread code do:

   ```python
   loop.call_soon_threadsafe(asyncio.create_task, manager.emit_to_user(...))
   ```

   This line will effectively tell the loop, “when you get a chance, start this coroutine (emit_to_user) as a task.” The actual sending will then occur on the event loop thread, avoiding any thread-safety issues. The official docs note that when scheduling callbacks from another thread, **“this function must be used, since call_soon() is not thread-safe.”**【32†L300-L307】

   Alternatively, you could use `loop.call_soon_threadsafe(partial(manager.emit_to_user, ...))` or even schedule the lower-level WebSocket send. The key is that the **actual I/O is performed on the main thread’s loop**. This avoids the “coroutine never awaited” warning because now the coroutine *is* being awaited by the event loop (as part of the created task).

2. **`asyncio.run_coroutine_threadsafe()`**: This is another utility that takes a coroutine and a loop, and submits the coroutine to run on that loop. It returns a concurrent.futures.Future which you can ignore or inspect. Usage would be:

   ```python
   asyncio.run_coroutine_threadsafe(manager.emit_to_user(...), loop)
   ```

   This achieves a similar result – scheduling the coroutine on the given loop from another thread – in one call. Under the hood it’s doing a thread-safe call akin to the above.

3. **Use an Async Queue or Event System:** Instead of calling the manager directly from the thread, you can adopt a **producer-consumer pattern** with a queue:

   - In the COSA thread, put the message or event into a thread-safe queue (e.g. Python’s `queue.Queue` or `asyncio.Queue` with proper thread access). For example, `message_queue.put((user_id, audio_chunk))` from the thread.
   - Have an **async task running on the event loop** that pulls from this queue and sends to the WebSocket. You could start such a task at app startup or on first WebSocket connect. This task simply loops with `msg = await async_queue.get()` and then does `await websocket.send_bytes(msg)` or uses `WebSocketManager.emit_to_user`. This way, the background thread never touches the WebSocket; it only enqueues data. The FastAPI event loop task handles all actual sending. 

   This pattern is demonstrated in a similar context (streaming partial results): a background thread produces messages, and the FastAPI handler awaits on a queue to send them over the WebSocket【34†L158-L166】. By yielding control with `await` on each send, you also keep the event loop responsive. The code sketch:

   ```python
   # In FastAPI context (event loop)
   async def websocket_endpoint(ws: WebSocket):
       ...  # accept, etc.
       # Start background thread that does work and enqueues messages
       thread = threading.Thread(target=worker_function, args=(message_queue, ...))
       thread.start()
       try:
           # Loop to send messages as they become available
           while True:
               message = await async_queue.get()   # wait for data from thread
               await ws.send_text(message)         # or send_bytes for audio chunks
       except WebSocketDisconnect:
           pass
       finally:
           thread.join()
   ```

   In your architecture, the queue consumer could even be outside the WS endpoint (since you want to push events independently of a client request). For example, you might spawn an async task at startup that monitors a global queue of “events to push to users”. Your COSA threads would `.put()` events into it, and the async task uses `emit_to_user` internally. This decoupling is robust – it effectively serializes sync->async calls through a queue. (It’s similar to how one might use an actor or message broker model for thread communication.)

4. **Refactor the background work to be async:** If it’s possible to make the COSA queue processing **asynchronous**, this would simplify things greatly. For instance, if the tasks can be awaited (or if they are I/O-bound, they could be converted to `async` functions that use `await` for I/O), then you could run them in the FastAPI event loop (perhaps via `BackgroundTasks` or startup events). Then calling `await manager.emit_to_user(...)` would be straightforward. However, often such queue systems are not trivial to convert to async (especially if they involve CPU-bound work or blocking libraries). If they are CPU-bound, using threads or processes is still necessary to avoid blocking the event loop. In that case, sticking to the thread-and-queue pattern is fine.

5. **Avoid creating asyncio loops in threads unless truly needed:** You attempted `asyncio.run()` in a thread, which is not ideal here. If you ever consider running a separate event loop in a dedicated thread for offloading, a cleaner way is to use `asyncio.new_event_loop()` and `loop.run_forever()` in a thread, then use `asyncio.run_coroutine_threadsafe` to that loop. But this is usually overkill for just sending WebSocket messages (plus you’d then have to funnel WS sends back to the main loop anyway, since the sockets belong there). So, it’s simpler to schedule back onto the *existing* loop as described above.

In summary, **the best practice is to never directly await or send on a WebSocket from a different thread**. Instead, signal the event loop to do it. Using `loop.call_soon_threadsafe` or an async queue achieves this. As the Python docs emphasize, `loop.call_soon_threadsafe()` is the safe way to schedule callbacks from another thread【32†L300-L307】. And as one Medium article warns, creating asyncio Tasks from multiple threads needs caution since tasks (and asyncio in general) aren’t inherently thread-safe if done incorrectly【28†L154-L158】. By confining all actual async operations to the main thread’s loop, you avoid those pitfalls.

## Recommendations Summary

- **Manage WebSocket sessions by user and session ID:** Use a mapping like `connections[user_id] = {session_id: websocket, ...}`; clean up old sessions on disconnect; decide on multi-session vs. single-session policy.【20†L52-L60】【20†L93-L100】
- **Align session ID usage:** Generate a stable session token (cookie/localStorage or use auth token) so that the WS URLs stay consistent across reloads and tabs.【20†L45-L53】
- **Bridge threads to async correctly:** In `emit_to_user_sync()`, schedule the coroutine on the main loop with `loop.call_soon_threadsafe(asyncio.create_task, ...)` or `asyncio.run_coroutine_threadsafe(...)` instead of calling async from sync.【32†L300-L307】【4†L90-L97】
- **Consider an asyncio.Queue producer-consumer pattern** for audio chunk streaming, where background threads enqueue data and an async task dispatches it over WebSockets.【34†L158-L166】
- **Verify user association fix:** Ensure `/ws/{session}` connect registers the session under the user in `WebSocketManager` so that `emit_to_user` can find it.

With these changes, the event loop will handle all WebSocket I/O safely, session IDs will be consistent, and audio chunks will reliably flow to the correct browser session—finally enabling the automatic playback you’re after.
