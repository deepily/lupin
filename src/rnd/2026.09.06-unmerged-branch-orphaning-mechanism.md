## 1. The defect, in one sentence

**Reviewed-and-merged is nobody's standing job.** Work finishes on a worktree branch,
the author is reaped, and the branch becomes the only thing that remembers it. A reap
writes a memento; **it does not merge a branch, and nothing else does either.**

That is the whole cause of Rick's 2026-09-06 morning — he asked twice why two P0s "got
zero attention" yesterday. They got attention. They were **built and never merged**, both
sitting on one unmerged branch while their author was reaped. Mr. Radio landed them at
`c0c95966`.

⚠️ **This is not a story about one careless evening.** Nothing in the reap path looks at
git at all, so the outcome is structural: it recurs for every seat, every time, and the
only thing that has ever prevented it is somebody happening to remember.

## 3. What already exists — and why it points the safe way only

Three relevant pieces are already built. None of them closes this.

| component | what it does | why it does not close this |
|---|---|---|
| `src/lupin_mcp/reap_memento.py` — the **memento gate** | proves each reaped seat's memento is fresh + complete on disk; **withholds the kill** when it is not; raises `memento_alarm` at top level | a memento is prose. It can *mention* a branch and routinely gets that line wrong — see below |
| `src/lupin_mcp/memento_merge_claim.py` — the **merge-claim check** | refutes a memento line claiming work is unmerged **when git proves it already landed** | 🔴 **it only points the safe way.** It catches a FALSE "there is unmerged work". Nothing catches a TRUE unmerged branch the memento never mentions |
| arbiter §4b **worktree janitor** | retires abandoned sandbox worktrees; "preserves WIP + keeps branches; never pushes" | ✅ good news — it is **not destroying anything**. It removes the tree and leaves the branch, which is why all 18 are still recoverable |

### 3.1 The merge-claim check's own docstring names this gap

> "IT DOES NOT CATCH A CLAIM WITH NO SHA … that gap is real and is NOT closed here; it is
> closed by john's template rule — carry the BRANCH NAME plus `git log HEAD..<branch>`
> rather than a claim — which is a fleet-template change and Rick's call."

⇒ **A template rule is a rule that depends on remembering, and this repo's own doctrine
says that is not installed.** The proposal below is the mechanical form of the same idea:
git answers the question at reap time, so no author has to remember to write the line and
no successor has to trust it.

### 3.2 The asymmetry that decides the design

The memento gate **withholds the kill**. It is right to, and a branch gate must **not**
copy that, for a reason worth stating precisely:

| | what is at risk | correct response |
|---|---|---|
| **memento** | **data that only this seat can produce.** Kill it and the work is gone | 🔴 **withhold** — refuse until it is on disk |
| **branch** | **attention.** The commits are already in git, durable, and the janitor keeps them | ✅ **transfer** — move the obligation to a live board |

Withholding a reap over a branch would manufacture the immortal-seat class the memento
gate's own `force_kill` escape hatch exists to prevent, and it would do so for a condition
that loses nothing. **Nothing is lost at the reap. What is lost is that anyone is looking.**

## 4. Proposed mechanism — two halves, because one cannot cover the other

### Half A — the reap transfers the obligation (closes the future)

A new seam on `dismiss_sessions`, mirroring the memento seam's shape exactly (injected
callable, fail-safe, top-level alarm — never a nested dict a reader walks past):

1. For each seat being reaped, resolve its worktree branch and run
   `git rev-list --count <working-line>..<branch>`.
2. `> 0` ⇒ **mint a store row** — `review_request` or `task`, owned by the **reaping
   manager**, titled with the branch and the commit count, body carrying the branch name
   and the exact `git log` line a successor can run.
3. Surface `branch_alarm` at top level, one sentence naming every reaped seat that left
   commits behind — the same treatment `memento_alarm` gets, and for the same reason
   (row `3b0c5f90`: a per-seat verdict in a nested dict got missed while the reap reported
   success around it).
4. **Fail-safe, like every other seam on that path**: a raising probe never breaks the
   reap; it records itself and the reap proceeds. A reap that cannot run must never be a
   consequence of a git hiccup.

⚠️ **The kill is NOT withheld.** See §3.2.

### Half B — a sweep reports the standing backlog (closes the past)

No future reap will ever cover the 72 branches that already exist — their seats are gone.
A sweep is the only thing that can see them:

- enumerate branches ahead of the working line, classify by **whether a registered
  worktree still holds them** (the discriminator that produced the 18), and deliver.
- **DELIVER, not print.** `context-pressure-tick.sh` carries the argument in its own
  header: its output path used to be `print`, it correctly printed the alarm every ten
  minutes into a log nobody tails, and nothing happened until Rick noticed by hand. **A
  monitor that only prints is the defect wearing a monitor's clothes.**

### 4.1 What the mechanism must NOT do

- **Never push.** Rick's ruling, unchanged.
- **Never merge automatically.** Merging needs green + reviewed; the mechanism's job is to
  make the branch *visible and owned*, not to land it.
- **Never delete a branch.** The janitor's branch-preserving behaviour is why the 18 are
  recoverable; nothing here should weaken it.

## 5. The open question I cannot answer alone

🔴 **Half A mints store rows, and the store's flow-ratio gate refuses new rows when the
fleet's create:close ratio is above 1.20.** It refused *this very ticket* at 12:56 today
(fleet 183 created / 146 closed, ratio 1.25).

So a mechanism whose whole job is to convert forgotten branches into owed rows can be
switched off by the same pressure that makes forgetting likely — **the gate is tightest
exactly when the backlog is worst.** CLAUDE.md records that the gate exempts P0 and the
harness mirror lane unconditionally; whether a reap-born branch row should ride an
exemption is **Rick's call, not mine**, and I have not assumed an answer.

**Fallback if it may not:** Half A degrades to alarm-only (`branch_alarm` plus a line in
the reap result), which is strictly better than today and cannot be gated off.

## 6. What this design does NOT establish

- **Nothing here is built or tested.** This is a measurement and a proposal.
- **I did not verify that every one of the 18 contains work worth landing.** Some may be
  superseded, experimental, or already re-done elsewhere. The claim is that **nobody has
  decided**, not that all 18 deserve a merge.
- **I did not re-derive Mr. Radio's 14** to the point of explaining it (§2.2).
- **The janitor's "keeps branches" behaviour is read from its call-site comment**, not
  reproduced by running it. Worth one arm before Half B relies on it.
