# Fresh-Start Minimalist Queue UI Implementation

**Date**: 2025.08.04  
**Status**: 🔄 IN PROGRESS  
**Priority**: HIGH  

## Executive Summary

This document tracks the implementation of a fresh-start minimalist queue UI to replace the complex existing system that suffers from the Q&A audio silence mystery. The new system will be built incrementally across 4 phases, starting with the hardest functionality first (Q&A with TTS) and progressing to easier features.

## Problem Statement

The current queue UI system consists of 6,562+ lines of JavaScript across multiple files, creating debugging complexity that has resisted solution. The Q&A audio silence mystery remains unsolved despite extensive debugging tools (PathTracer, granular logging, direct test UI). A fresh start eliminates architectural debt and provides a clean foundation.

## Implementation Strategy: Hardest First

**Phase 1**: Q&A Core (Most Complex) → **Phase 2**: Notifications → **Phase 3**: Queue Status → **Phase 4**: Polish

This approach ensures the most problematic functionality is addressed first, with each phase building on a solid foundation.

#### TTS Mode Implementation

**Instant Mode Flow**:
1. Submit text via `/api/get-speech-elevenlabs`
2. Receive `audio_streaming_status` ("loading")
3. Stream `audio_streaming_chunk` events (binary data)
4. Play chunks progressively via Web Audio API
5. Receive `audio_streaming_complete`

**Reliable Mode Flow**:
1. Submit text via `/api/get-speech`
2. Receive `audio_streaming_status` ("loading") 
3. Collect `audio_streaming_chunk` events
4. On `audio_streaming_complete`, play via HTML audio element

## Architecture Benefits

### Single Module Approach ✅

**Advantages**:
- **Debugging**: All logic in one file, clear execution paths
- **Maintenance**: Single point of modification 
- **Testing**: Easier to isolate and verify functionality
- **Performance**: Reduced HTTP requests and dependency complexity

**Trade-offs**:
- **File Size**: Larger single file vs. multiple smaller files
- **Modularity**: Less separation of concerns (acceptable for this scope)

### WebSocket Strategy ✅

**Two Connection Pattern**:
- **Queue WebSocket**: General application events
- **Audio WebSocket**: High-throughput audio streaming
- **Separate Sessions**: Independent connection management

**Benefits**:
- **Specialization**: Each connection optimized for its purpose
- **Reliability**: Audio streaming doesn't affect queue operations
- **Scalability**: Different reconnection strategies per connection type

## Issue Tracking

### Known Issues

*None currently - will be updated as implementation proceeds*

### Resolved Issues

#### 2025.08.04 - Session ID JSON Parsing Bug ✅ RESOLVED

**Problem**: WebSocket connections failing with error code 1006 due to malformed session IDs.

**Root Cause**: The `/api/get-session-id` endpoint returns JSON:
```json
{"session_id":"relaxed turtle","timestamp":"2025-06-24T01:29:36.304976"}
```

But our code was using `await response.text()` instead of `await response.json()`, treating the entire JSON string as the session ID.

**Result**: Invalid WebSocket URLs like:
```
ws://localhost:7999/ws/queue/{"session_id":"sad zebra","timestamp":"..."}
```

**Fix**: Updated `getOrCreateSessionId()` method in `queue-fresh.js`:
- Changed `await response.text()` to `await response.json()`
- Extract `data.session_id` field from JSON response
- Added validation to ensure session ID exists

**Status**: ✅ COMPLETE - WebSocket connections now establish successfully

#### 2025.08.04 - localStorage Cache Invalidation ✅ RESOLVED

**Problem**: Even after fixing the JSON parsing bug, browser was still using cached malformed session IDs from localStorage.

**Evidence**: 
- Browser logs: `[SESSION] Reusing queue session: {"session_id":"sad zebra","timestamp":"..."}`
- Server rejected connections with 403 Forbidden due to malformed session IDs in URLs

**Root Cause**: localStorage persisted the old malformed JSON session IDs from before the bug fix.

**Fix**: Added automatic cache invalidation system:
- Version tracking: `CURRENT_VERSION = '1.0.1'`
- `validateCache()` method detects malformed session IDs (starts with `{` or contains `timestamp`)
- Automatically clears bad session IDs on startup
- Version-based cache invalidation for future updates

**Status**: ✅ COMPLETE - Fresh sessions will now be generated automatically

## Decision Log

### 2025.08.04 - Architecture Decisions

**Single Module vs. Multiple Files**:
- **Decision**: Single unified module
- **Rationale**: Eliminates complex interdependencies that caused debugging issues
- **Trade-off**: Less modular but more debuggable

**WebSocket Event Subscriptions**:
- **Decision**: Use exact events from `websocket-events.md` documentation
- **Correction**: Previous plan had incorrect event names (`["queue_update", "speech", "time", "notification"]`)
- **Accurate Events**: Documented subscription arrays for queue and audio connections

**TTS Mode Implementation**:
- **Decision**: Embed both modes in single module
- **Rationale**: Avoids hybrid-tts.js complexity that contributed to silence mystery
- **Approach**: Separate code paths for instant vs. reliable, shared Web Audio API setup

**Testing Strategy**:
- **Decision**: Hardest functionality first (Q&A + TTS)
- **Rationale**: Address core problem immediately, build confidence early
- **Progression**: Each phase must be fully functional before proceeding
