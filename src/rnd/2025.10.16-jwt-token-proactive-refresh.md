## Executive Summary

### Problem
JWT access tokens expire after 30 minutes. Current reactive-only refresh strategy causes poor UX during idle periods - first action after inactivity fails with 401 Unauthorized, then retries after refresh.

### Solution
Implement hybrid proactive token refresh using:
1. **Periodic background monitor** (every 10 minutes via `setInterval`)
2. **Heartbeat-triggered checks** (every 30 seconds via WebSocket `sys_ping`)
3. **Server-driven configuration** (lupin-app.ini → `/api/config/client` endpoint)
4. **Explicit unit naming convention** (`_ms`, `_secs`, `_mins` suffixes prevent conversion bugs)

### Impact
- ✅ Seamless UX during idle periods (>1 hour)
- ✅ High-priority notifications playback after inactivity without 401 errors
- ✅ Zero user-visible authentication failures for returning users
- ✅ Configuration-driven (no hardcoded timing values in JavaScript)
- ✅ Dual redundancy (periodic + heartbeat mechanisms)

### Key Metrics
- **401 Errors After Idle**: Reduce from ~10-20/day to 0
- **User-Visible Errors**: Reduce from 100% to 0% of post-idle interactions
- **Token Refresh Frequency**: Every ~25 minutes during idle (before 30-min expiry)

## Problem Statement

### Current Token Lifecycle

**Configuration** (`src/conf/lupin-app.ini`):
```ini
jwt_access_token_expire_minutes = 30
jwt_refresh_token_expire_days = 7
```

**Current Refresh Strategy** (REACTIVE ONLY):
```javascript
// queue-fresh.js - Only refreshes BEFORE API calls
async ensureValidToken() {
    if (!this.authToken || this.isTokenExpired(this.authToken)) {
        await this.refreshAccessToken();
    }
}

// Called before every API request
await this.ensureValidToken();
await fetch('/api/push', { ... });
```

**Works well for**: Active users making frequent API calls (every few minutes)

**Fails for**: Idle users who don't trigger API calls for >30 minutes

### Gap Analysis: Idle Period Failure Scenario

```
Timeline: User idle for 90 minutes (browser open, tab active or backgrounded)

T+0m:   User authenticates, access token valid until T+30m
T+5m:   User makes API call → ensureValidToken() → token fresh (25 mins left)
T+10m:  User goes IDLE (no more clicks, no more API calls)

T+30m:  ⚠️ Access token EXPIRES
        ✅ WebSocket still CONNECTED (sys_ping/pong heartbeats continue every 30s)
        ❌ Token NOT refreshed (no API calls = no ensureValidToken() trigger)

T+60m:  Still idle...
T+90m:  User returns, sees notification

        📢 HIGH PRIORITY NOTIFICATION arrives via WebSocket
        ├─> Notification event delivered successfully (WebSocket alive)
        ├─> User clicks to play audio
        ├─> playInstantTTS() calls /api/get-speech-elevenlabs
        ├─> API call includes EXPIRED token (60 minutes old)
        ├─> Server returns 401 Unauthorized ❌
        ├─> ensureValidToken() recovers by refreshing token
        ├─> Second API attempt succeeds ✅
        └─> Audio plays (but user saw error, experienced delay)

Result: Poor UX - double request, visible delay, potential error flash in UI
```

### Root Cause

**Reactive-only refresh assumes regular API activity**:
- ✅ Works: Active user (API calls every few minutes)
- ❌ Breaks: Idle user (no API calls for >30 minutes)
- ⚠️ Partial: WebSocket keeps connection alive but doesn't refresh token

**WebSocket heartbeat doesn't help**:
- `sys_ping`/`sys_pong` maintains connection health
- Does NOT trigger token refresh logic
- Connection stays alive, but token expires

### Requirements

**Functional Requirements**:
1. Token must remain fresh during WebSocket-connected idle periods (up to multiple hours)
2. Notifications must play immediately after >1 hour inactivity (no 401 errors)
3. No user-visible authentication errors after returning from idle
4. Background refresh must not impact foreground performance
5. Must work when browser tab is backgrounded (but not closed)

**Non-Functional Requirements**:
1. **Configuration-driven**: All timing values from server config (no hardcoded magic numbers)
2. **Explicit units**: Variable names indicate units (`_ms`, `_secs`, `_mins`) to prevent conversion bugs
3. **Server-controlled**: Single source of truth in `lupin-app.ini`
4. **Graceful degradation**: Fall back to hardcoded defaults if config fetch fails
5. **Security**: Config endpoint requires JWT authentication (no public access)
6. **Testable**: Unit, smoke, and integration tests for all behaviors

### Dual Refresh Mechanism

Our solution employs TWO complementary refresh triggers for maximum reliability:

#### Mechanism 1: Periodic Background Monitor ⏰

**Implementation**:
```javascript
// Runs every 10 minutes via setInterval
setInterval( () => {
    checkAndRefreshToken( "periodic" );
}, TOKEN_REFRESH_CHECK_INTERVAL_MS );  // 600000ms = 10 mins
```

**Characteristics**:
- ✅ **Predictable timing**: Fires exactly every N minutes (configurable)
- ✅ **Works when tab is active**: Primary mechanism for foreground tabs
- ⚠️ **Throttled when backgrounded**: Browser optimizations may slow/pause setInterval
- 🎯 **Role**: Primary refresh mechanism for active use

**When it works best**:
- User actively using the application
- Tab is in foreground
- Regular, predictable refresh schedule needed

**When it may fail**:
- Tab backgrounded for extended periods (browser throttling)
- Browser aggressively conserving resources
- Mobile devices in low-power mode

#### Mechanism 2: Heartbeat-Triggered Check 💓

**Implementation**:
```javascript
// Runs every 30 seconds on WebSocket sys_ping
async handlePing( connectionType ) {
    // ... send sys_pong response ...

    // Piggyback token check on heartbeat (queue WS only to avoid duplicates)
    if ( connectionType === "queue" ) {
        await checkAndRefreshToken( "heartbeat" );
    }
}
```

**Characteristics**:
- ✅ **Works even when backgrounded**: WebSocket heartbeats continue regardless of tab state
- ✅ **Leverages existing infrastructure**: No additional network overhead
- ✅ **More frequent checks**: Every 30 seconds vs 10 minutes
- 🎯 **Role**: Backup mechanism when periodic monitor throttled

**When it works best**:
- Tab backgrounded for long periods
- Browser aggressively throttling timers
- Need maximum reliability during idle

**Why it's reliable**:
- WebSocket heartbeats bypass browser timer throttling
- Server sends `sys_ping`, client responds with `sys_pong`
- Built-in connection health monitoring already proven reliable

### Why Both Mechanisms?

**Redundancy = Reliability**:
```
Scenario 1: Active tab
├─> Periodic monitor: ✅ Works (primary)
└─> Heartbeat trigger: ✅ Works (backup)

Scenario 2: Backgrounded tab
├─> Periodic monitor: ⚠️ May be throttled by browser
└─> Heartbeat trigger: ✅ Works (takes over as primary)

Scenario 3: Mobile/low-power
├─> Periodic monitor: ⚠️ May pause completely
└─> Heartbeat trigger: ✅ Works (WebSocket keeps alive)

Result: Token stays fresh in ALL scenarios
```

### Deduplication Logic

**Problem**: Both mechanisms might trigger simultaneously

**Example Collision**:
```
T+25m00s: Periodic monitor fires → "Token expires in 5 mins, refresh!"
T+25m10s: Heartbeat trigger fires → "Token expires in 4m50s, refresh!"

Without deduplication: TWO refreshes 10 seconds apart (wasteful!)
```

**Solution**: Track last refresh timestamp, skip if recent

**Implementation**:
```javascript
async checkAndRefreshToken( source ) {
    // Check if refreshed in last 60 seconds
    if ( this.lastTokenRefresh_ms ) {
        const timeSinceRefresh_ms = Date.now() - this.lastTokenRefresh_ms;

        if ( timeSinceRefresh_ms < this.TOKEN_REFRESH_DEDUP_WINDOW_MS ) {
            // Skip duplicate refresh
            this.log( `Token refresh skipped (${source}): refreshed ${timeSinceRefresh_secs}s ago` );
            return;
        }
    }

    // Proceed with refresh check...

    // Update timestamp after successful refresh
    this.lastTokenRefresh_ms = Date.now();
}
```

**Benefits**:
- ✅ Prevents rapid-fire refreshes (max 1 per minute)
- ✅ Both mechanisms coordinate via shared state
- ✅ Reduces server load
- ✅ Maintains token freshness without waste

## Configuration Management

### Design Principles

**1. Server as Single Source of Truth**:
- All timing values stored in `lupin-app.ini`
- Client fetches config from `/api/config/client` on startup
- Easy to adjust without redeploying JavaScript

**2. Explicit Unit Naming Convention**:
- `_ms`: Milliseconds (JavaScript `Date.now()`, `setInterval`)
- `_secs`: Seconds (JWT `exp` claim, Unix timestamps)
- `_mins`: Minutes (Human-readable config, display values)
- **Prevents bugs**: Can't accidentally compare milliseconds to seconds

**3. Environment-Specific Overrides**:
- Development: More aggressive refresh for testing
- Production: Balanced for performance/security
- Testing: Extreme values for edge case validation

### Configuration Endpoint

**File**: `src/cosa/rest/routers/system.py`

**Endpoint**: `GET /api/config/client`

**Authentication**: ✅ REQUIRED (JWT via `get_current_user_id` dependency)

**Security Rationale**:
- Prevents information leakage to unauthenticated users
- Token refresh timing could aid attack reconnaissance
- Consistent with other `/api/*` endpoints

**Implementation**:

```python
from fastapi import APIRouter, Depends
from cosa.config.configuration_manager import ConfigurationManager
from cosa.rest.auth import get_current_user_id

router = APIRouter()

@router.get( "/api/config/client" )
async def get_client_config( user_id: str = Depends( get_current_user_id ) ):
    """
    Return client-side configuration parameters for authenticated users.

    **Authentication**: REQUIRED - JWT token validated via dependency injection

    Requires:
        - Valid JWT token in Authorization header
        - ConfigurationManager initialized
        - lupin-app.ini contains timing settings (or uses defaults)

    Ensures:
        - Returns JSON with all client timing parameters
        - Only accessible to authenticated users (401 if unauthenticated)
        - Units converted appropriately for client use
        - Fallback defaults provided for missing config values

    Args:
        user_id: Authenticated user ID (injected by dependency, ensures JWT valid)

    Returns:
        JSON response with timing parameters:
        {
            "token_refresh_check_interval_ms": 600000,    # 10 mins in milliseconds
            "token_expiry_threshold_secs": 300,           # 5 mins in seconds
            "token_refresh_dedup_window_ms": 60000,       # 60 secs in milliseconds
            "websocket_heartbeat_interval_secs": 30       # Reference value (secs)
        }

    Example:
        GET /api/config/client
        Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

        Response 200:
        {
            "token_refresh_check_interval_ms": 600000,
            "token_expiry_threshold_secs": 300,
            "token_refresh_dedup_window_ms": 60000,
            "websocket_heartbeat_interval_secs": 30
        }
    """
    # Note: user_id parameter required by Depends() - validates JWT token
    # We don't use the actual user_id value, but it ensures authentication

    config_mgr = ConfigurationManager( env_var_name="LUPIN_CONFIG_MGR_CLI_ARGS" )

    # Fetch from config with fallback defaults
    refresh_check_interval_mins = config_mgr.get(
        "jwt_token_refresh_check_interval_mins",
        default=10
    )
    expiry_threshold_mins = config_mgr.get(
        "jwt_token_refresh_expiry_threshold_mins",
        default=5
    )
    dedup_window_secs = config_mgr.get(
        "jwt_token_refresh_dedup_window_secs",
        default=60
    )
    heartbeat_interval_secs = config_mgr.get(
        "websocket_heartbeat_interval_seconds",
        default=30
    )

    return {
        # Convert minutes → milliseconds (for setInterval)
        "token_refresh_check_interval_ms": int( refresh_check_interval_mins * 60 * 1000 ),

        # Convert minutes → seconds (for JWT exp comparison)
        "token_expiry_threshold_secs": int( expiry_threshold_mins * 60 ),

        # Convert seconds → milliseconds (for Date.now() comparison)
        "token_refresh_dedup_window_ms": int( dedup_window_secs * 1000 ),

        # Already in seconds (reference value for logging/debugging)
        "websocket_heartbeat_interval_secs": int( heartbeat_interval_secs )
    }
```

### Unit Naming Convention

**Standard Suffixes** (enforced throughout codebase):

| Suffix | Meaning | Used For | Example |
|--------|---------|----------|---------|
| `_ms` | Milliseconds | JavaScript `Date.now()`, `setInterval`, `setTimeout` | `TOKEN_REFRESH_CHECK_INTERVAL_MS = 600000` |
| `_secs` | Seconds | JWT `exp` claim, Unix timestamps | `TOKEN_EXPIRY_THRESHOLD_SECS = 300` |
| `_mins` | Minutes | Human-readable config, display values | `refresh_check_interval_mins = 10` |

**Code Examples**:

```javascript
// Time point variables (absolute timestamps)
this.lastTokenRefresh_ms = Date.now();           // Milliseconds since epoch
const tokenExpiry_secs = payload.exp;            // Seconds since epoch (JWT standard)

// Duration/interval variables (relative time spans)
this.TOKEN_REFRESH_CHECK_INTERVAL_MS = 600000;   // 10 minutes in milliseconds
this.TOKEN_EXPIRY_THRESHOLD_SECS = 300;          // 5 minutes in seconds

// Conversions (always explicit with units clear in variable names)
const threshold_mins = this.TOKEN_EXPIRY_THRESHOLD_SECS / 60;        // 300 secs → 5 mins
const interval_secs = this.TOKEN_REFRESH_CHECK_INTERVAL_MS / 1000;   // 600000 ms → 600 secs
const now_secs = Math.floor( Date.now() / 1000 );                    // ms → secs

// Comparisons (units match - no conversion needed)
if ( timeUntilExpiry_secs < this.TOKEN_EXPIRY_THRESHOLD_SECS ) {
    // Both in seconds - safe comparison ✅
}
```

**Benefits**:
- ✅ **Self-documenting**: Units clear from variable name alone
- ✅ **Prevents bugs**: Can't accidentally compare milliseconds to seconds
- ✅ **Easy validation**: Code reviewers spot mismatches instantly
- ✅ **IDE-friendly**: Autocomplete suggests correct conversions

**Anti-Patterns** (DO NOT DO THIS):

```javascript
// ❌ BAD: Units unclear, easy to mix up
const threshold = 300;  // Is this ms, secs, or mins?
const interval = 600000; // Is this ms, secs, or mins?

if ( timeUntilExpiry < threshold ) {  // Bug waiting to happen!
    // Are we comparing apples to apples?
}

// ❌ BAD: Implicit conversion, error-prone
const interval = config.tokenRefreshInterval * 60000;  // What unit is input?
```

```javascript
async fetchClientConfig() {
    /**
     * Fetch client configuration from authenticated server endpoint.
     * Populates timing constants for token refresh monitoring.
     *
     * Requires:
     *     - this.authToken is valid (called AFTER setupAuthentication)
     *     - Server /api/config/client endpoint available
     *
     * Ensures:
     *     - All TOKEN_* constants populated with server values
     *     - Falls back to hardcoded defaults if fetch fails
     *     - Logs configuration values for debugging
     *     - Sends JWT authentication header (endpoint protected)
     *
     * Raises:
     *     - None (handles errors gracefully with fallback defaults)
     */
    try {
        // Authenticated API call (requires valid JWT token)
        const response = await fetch( '/api/config/client', {
            method: 'GET',
            headers: {
                'Content-Type': 'application/json',
                'Authorization': this.getAuthHeader()  // JWT authentication required
            }
        });

        if ( response.ok ) {
            const config = await response.json();

            // Populate constants from server configuration
            this.TOKEN_REFRESH_CHECK_INTERVAL_MS = config.token_refresh_check_interval_ms;
            this.TOKEN_EXPIRY_THRESHOLD_SECS = config.token_expiry_threshold_secs;
            this.TOKEN_REFRESH_DEDUP_WINDOW_MS = config.token_refresh_dedup_window_ms;
            this.WEBSOCKET_HEARTBEAT_INTERVAL_SECS = config.websocket_heartbeat_interval_secs;

            // Log configuration for debugging
            this.log( "✓ Client config loaded from server:", {
                refresh_check_interval: `${config.token_refresh_check_interval_ms / 60000} mins`,
                expiry_threshold: `${config.token_expiry_threshold_secs / 60} mins`,
                dedup_window: `${config.token_refresh_dedup_window_ms / 1000} secs`,
                heartbeat_interval: `${config.websocket_heartbeat_interval_secs} secs`
            });

        } else if ( response.status === 401 ) {
            // Authentication failed (shouldn't happen after setupAuthentication)
            this.error( "Config fetch failed: 401 Unauthorized (token invalid?)" );
            throw new Error( "Unauthorized" );

        } else {
            throw new Error( `Config endpoint returned ${response.status}` );
        }

    } catch ( error ) {
        // Fallback to hardcoded defaults if config fetch fails
        this.error( "Failed to fetch client config, using defaults:", error );

        // Conservative defaults (same as baseline config)
        this.TOKEN_REFRESH_CHECK_INTERVAL_MS = 10 * 60 * 1000;  // 10 minutes
        this.TOKEN_EXPIRY_THRESHOLD_SECS = 5 * 60;              // 5 minutes
        this.TOKEN_REFRESH_DEDUP_WINDOW_MS = 60 * 1000;         // 60 seconds
        this.WEBSOCKET_HEARTBEAT_INTERVAL_SECS = 30;            // 30 seconds

        this.log( "⚠️ Using default client config (server fetch failed)" );
    }
}
```

#### Step 3: Token Refresh Check Logic

**Location**: New method after `fetchClientConfig()` (around line 410)

```javascript
async checkAndRefreshToken( source = "manual" ) {
    /**
     * Check token expiration and refresh proactively if needed.
     * Uses explicit unit suffixes to prevent conversion errors.
     * Implements deduplication to prevent rapid-fire refreshes.
     *
     * Requires:
     *     - this.authToken exists and is valid
     *     - TOKEN_* constants initialized via fetchClientConfig()
     *
     * Ensures:
     *     - Refreshes token if < threshold seconds to expiry
     *     - Skips refresh if refreshed within dedup window
     *     - Updates lastTokenRefresh_ms on successful refresh
     *     - Logs all refresh decisions for debugging
     *
     * Args:
     *     source: String describing trigger source for logging:
     *         - "periodic": Triggered by setInterval periodic monitor
     *         - "heartbeat": Triggered by WebSocket sys_ping handler
     *         - "manual": Manually triggered (testing/debugging)
     */

    // Skip if no auth token
    if ( !this.authToken ) {
        return;
    }

    // Deduplication: Skip if recently refreshed
    if ( this.lastTokenRefresh_ms ) {
        const timeSinceRefresh_ms = Date.now() - this.lastTokenRefresh_ms;

        if ( timeSinceRefresh_ms < this.TOKEN_REFRESH_DEDUP_WINDOW_MS ) {
            const timeSinceRefresh_secs = Math.round( timeSinceRefresh_ms / 1000 );
            this.log( `Token refresh skipped (${source}): refreshed ${timeSinceRefresh_secs}s ago` );
            return;
        }
    }

    // Parse token to get expiration claim
    const payload = this.parseJWTPayload( this.authToken );
    if ( !payload.exp ) {
        this.error( "Token has no expiration claim - cannot check freshness" );
        return;
    }

    // Calculate time until expiry (both in seconds for comparison)
    const now_secs = Math.floor( Date.now() / 1000 );
    const timeUntilExpiry_secs = payload.exp - now_secs;

    // Refresh if below threshold (comparing seconds to seconds - units match ✅)
    if ( timeUntilExpiry_secs < this.TOKEN_EXPIRY_THRESHOLD_SECS ) {
        const timeUntilExpiry_mins = Math.round( timeUntilExpiry_secs / 60 );
        this.log( `⏰ Proactive token refresh (${source}): ${timeUntilExpiry_mins} minutes until expiry` );

        const refreshed = await this.refreshAccessToken();

        if ( refreshed ) {
            // Update timestamp and token reference
            this.lastTokenRefresh_ms = Date.now();
            this.authToken = this.getStoredTokens().accessToken;
            this.log( `✓ Token proactively refreshed (${source})` );
        } else {
            this.error( `✗ Token refresh failed (${source})` );
        }
    } else {
        const timeUntilExpiry_mins = Math.round( timeUntilExpiry_secs / 60 );
        this.log( `Token fresh (${source}): ${timeUntilExpiry_mins} minutes remaining` );
    }
}
```

- More aggressive during business hours (8am-6pm)
- Less aggressive during off-hours (reduce server load)

#### 2. Token Expiry Warnings
- Visual indicator when token < 10 mins remaining
- "Extend session?" prompt before expiry
- User-initiated refresh button

#### 3. Offline Token Management
- Cache token refresh requests when offline
- Retry when connection restored
- Handle airplane mode gracefully

#### 4. Multi-Tab Coordination
- Use BroadcastChannel API to coordinate tabs
- Only one tab refreshes, broadcasts new token to others
- Reduces server load for multi-tab users

#### 5. Refresh Token Rotation
- Implement refresh token rotation (security best practice)
- Invalidate old refresh tokens on use
- Detect stolen refresh tokens

### D. Troubleshooting Guide

**Issue**: Token still expires during idle
- **Check**: Browser console for "Token refresh skipped" messages
- **Verify**: Config loaded from server (check console logs)
- **Debug**: Add `console.log()` to `checkAndRefreshToken()` to see if it's firing

**Issue**: Too many token refreshes
- **Check**: Deduplication window configured correctly
- **Verify**: Both mechanisms not firing simultaneously without deduplication
- **Debug**: Check `lastTokenRefresh_ms` timestamp updates

**Issue**: Config endpoint returns 401
- **Check**: Token is valid and not expired
- **Verify**: Authorization header includes "Bearer " prefix
- **Debug**: Check server logs for authentication failures

**Issue**: Periodic monitor stops working
- **Check**: Browser tab backgrounded? (Expected - heartbeat takes over)
- **Verify**: setInterval handle not cleared accidentally
- **Debug**: Check `tokenRefreshIntervalHandle` is not null
