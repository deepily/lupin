### Problem Summary

Runtime statistics were being calculated correctly in memory but not persisting to LanceDB after `merge_insert()` operations. The `run_count` would stay stuck at 1 even after 7-8 executions of the same question.

### Root Causes Identified

1. **Missing Scalar Index** - LanceDB's `merge_insert()` requires a scalar index on the join column (`id_hash`) for reliable matching. Without it, merge operations can fail silently or create duplicates instead of updating.

2. **Stale Cache** - Cache was populated with in-memory record after merge, not fresh DB data. If merge failed silently, cache would mask the persistence failure.

3. **No Cache Invalidation** - Cache held stale data during merge operation, no fresh DB read to verify persistence.

### Fixes Implemented ✅

All fixes have been successfully implemented in the following files:

#### 1. lancedb_solution_manager.py

**Scalar Index Creation** (Lines 480-492):
- New tables: Index created automatically during table creation
- Existing tables: Index verified/created when opening tables
- Uses `create_scalar_index("id_hash", replace=True)` for idempotent operation

**Cache Invalidation Before Merge** (Lines 784-792):
- Cache entries (`_id_lookup`, `_question_lookup`) cleared BEFORE `merge_insert()` executes
- Forces fresh DB read after merge completes

**Fresh DB Read for Cache Repopulation** (Lines 820-836):
- After merge, cache repopulated from fresh DB query
- No longer uses stale in-memory record
- Fallback to in-memory record only if DB read fails

**Cache Consistency Verification** (Lines 851-909):
- New `_verify_cache_consistency()` method compares cache vs DB stats
- Called automatically in debug mode after each merge (line 839-840)
- Validates cache matches DB state, catches any future issues
