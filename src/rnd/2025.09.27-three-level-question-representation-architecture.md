# Three-Level Question Representation Architecture

**Date**: 2025.09.27
**Status**: Design Complete, Implementation Pending
**Priority**: Critical (Fixing search failures)
**Complexity**: High (Affects core data model)

## Executive Summary

This document proposes a fundamental redesign of how Lupin stores and searches user questions, moving from a single normalized representation to a three-level architecture: Verbatim, Normalized, and Gist. This change addresses critical search failures while establishing a foundation for sophisticated question understanding.

**Key Problem**: The query "What time is it?" returns zero snapshots despite having a perfect match in the database due to punctuation normalization inconsistencies.

**Proposed Solution**: Three separate representations with hierarchical exact-match search, eliminating similarity computation overhead for most queries.

## Background: The Discovery

### The Symptom
Console output showing zero results for a question that should match:
```
push_job(): Using snapshot similarity threshold of [95.0] and gist similarity threshold of [90.0]
Performing similarity search for: What time is it?
Found 0 similar snapshots
```

### Root Cause Investigation
- **Database contains**: `"what time is it"` (no punctuation)
- **Current normalization produces**: `"what time is it?"` (preserves sentence-ending punctuation)
- **LanceDB exact match fails**: `"what time is it?" != "what time is it"`

### Deeper Analysis
The current normalizer preserves punctuation (`lines 235-238 in normalizer.py`):
```python
elif token.is_punct and token.text in '.!?':
    # Preserve sentence-ending punctuation
    if sent_tokens:
        sent_tokens[-1] += token.text
```

But older snapshots were stored without this preservation, creating systematic search failures.

## The Fundamental Question: What IS a Question?

Through our investigation, we realized we're conflating multiple concepts:

1. **User Intent** - What the user actually said/typed (emotional context, style, errors)
2. **Semantic Core** - The normalized, searchable form (technical matching)
3. **Essential Meaning** - The gist extracted by LLM (conceptual understanding)

Each serves different purposes and requires different processing strategies.

## Design Philosophy: Three Levels of Representation

### Level 1: Verbatim Representation
**Purpose**: Preserve user intent and original context
**Content**: Exactly what the user typed or spoke
**Constraints**: Must be unique (one verbatim question = one solution)
**Use Cases**:
- Exact match lookup (fastest possible search)
- User experience (show what they actually asked)
- Quality assurance (detect voice transcription errors)

**Example**: `"What time is it?"`

### Level 2: Normalized Representation
**Purpose**: Standardized form for reliable matching
**Content**: Lowercase, lemmatized, punctuation-free, no filler words
**Processing**: Deterministic normalization for consistent results
**Use Cases**:
- Primary matching when verbatim fails
- Cross-linguistic matching
- Handling variations in phrasing

**Example**: `"what time be it"`

### Level 3: Gist Representation
**Purpose**: Capture semantic essence and intent
**Content**: LLM-extracted core meaning
**Processing**: Semantic distillation via language model
**Use Cases**:
- Conceptual matching when normalized fails
- Understanding complex, verbose queries
- Cross-domain question matching

**Example**: `"current time inquiry"`

## Architecture Overview

### Three-Table Design

#### 1. QueryLog Table
**Purpose**: Append-only log of every query attempt
**Characteristics**:
- Write-optimized (every query logged)
- No uniqueness constraints
- Captures context, errors, and user behavior
- Source of truth for analytics

```python
class QueryLog:
    id: str
    timestamp: datetime
    user_id: str
    session_id: str

    # Three-level representation
    query_verbatim: str           # Exactly what user asked
    query_normalized: str         # Normalized version
    query_gist: str              # LLM-extracted gist

    # Embeddings (generated async)
    embedding_verbatim: list[float]
    embedding_normalized: list[float]
    embedding_gist: list[float]

    # Match results
    matched_snapshot_id: str      # What solution was returned
    match_type: str              # 'exact_verbatim', 'exact_normalized', 'similarity', 'none'
    match_confidence: float       # How confident was the match

    # Context
    input_type: str              # 'voice', 'text', 'api'
    processing_time_ms: int      # How long to find answer
    user_satisfaction: str       # 'satisfied', 'unsatisfied', 'unknown'
```

#### 2. CanonicalSynonyms Table
**Purpose**: Validated question→solution mappings for fast lookup
**Characteristics**:
- Read-optimized (heavily indexed)
- Uniqueness constraints enforced
- Curated, high-quality mappings only
- Primary source for exact matching

```python
class CanonicalSynonym:
    id: str
    snapshot_id: str             # Foreign key to solution

    # Three-level representation (all indexed)
    question_verbatim: str       # UNIQUE constraint
    question_normalized: str     # Indexed for fast lookup
    question_gist: str          # Indexed for fast lookup

    # Embeddings (cached for performance)
    embedding_verbatim: list[float]
    embedding_normalized: list[float]
    embedding_gist: list[float]

    # Quality metrics
    confidence_score: float      # How confident is this mapping
    validation_method: str       # 'user_confirmed', 'admin_added', 'auto_validated'
    usage_count: int            # How often this synonym gets matched
    last_matched: datetime      # When was this last used

    # Lifecycle
    created_date: datetime
    created_by: str             # 'system', 'user', 'admin'
    is_active: bool            # Can be disabled without deletion
```

#### 3. SolutionSnapshot Table (Enhanced)
**Purpose**: Immutable solutions with three-level primary questions
**Characteristics**:
- Append-only (immutable once created)
- Self-contained solutions
- Enhanced with three-level representation

## The Search Algorithm: Hierarchical Early Exit

### Design Principle: Exact Matches Win Immediately

```python
def search_for_solution(query: str) -> Optional[SolutionSnapshot]:
    """
    Hierarchical search with immediate return on exact matches.
    NO scoring, NO weighted combinations - first exact match wins!
    """

    # LEVEL 1: Exact verbatim matches (fastest possible)

    # Check primary questions
    if snapshot := solution_snapshots.get_by_verbatim(query):
        log_match('exact_verbatim_primary', query, snapshot.id)
        return snapshot

    # Check canonical synonyms verbatim
    if synonym := canonical_synonyms.get_by_verbatim(query):
        snapshot = solution_snapshots.get(synonym.snapshot_id)
        log_match('exact_verbatim_synonym', query, snapshot.id)
        return snapshot

    # LEVEL 2: Exact normalized matches

    query_normalized = normalizer.normalize(query)

    # Check primary normalized questions
    if snapshot := solution_snapshots.get_by_normalized(query_normalized):
        log_match('exact_normalized_primary', query, snapshot.id)
        return snapshot

    # Check canonical synonyms normalized
    if synonym := canonical_synonyms.get_by_normalized(query_normalized):
        snapshot = solution_snapshots.get(synonym.snapshot_id)
        log_match('exact_normalized_synonym', query, snapshot.id)
        return snapshot

    # LEVEL 3: Exact gist matches (optional - may be too loose)

    query_gist = gister.get_gist(query)

    if snapshot := solution_snapshots.get_by_gist(query_gist):
        log_match('exact_gist_primary', query, snapshot.id)
        return snapshot

    # LEVEL 4: Similarity search (only when all exact matches fail)

    similar_snapshots = vector_similarity_search(
        query_normalized=query_normalized,
        query_gist=query_gist,
        threshold=85.0
    )

    if similar_snapshots:
        snapshot = similar_snapshots[0]  # Best match
        log_match('similarity', query, snapshot.id, similar_snapshots[0][0])
        return snapshot

    # LEVEL 5: No match found
    log_match('none', query, None)
    return None
```

### Why This Approach Works

1. **Performance**: 80%+ queries should hit Level 1 or 2 (sub-millisecond response)
2. **Accuracy**: Exact matches eliminate false positives from similarity scoring
3. **Simplicity**: No complex scoring algorithms or weight tuning
4. **Maintainability**: Clear, debuggable logic flow

## Data Flow and Processing Pipeline

### Input Processing Pipeline

```python
def process_user_query(query: str, user_id: str) -> str:
    """Complete query processing with three-level generation."""

    # Step 1: Log the raw query immediately
    query_log_id = query_log.create({
        'query_verbatim': query,
        'user_id': user_id,
        'timestamp': now(),
        'processing_status': 'started'
    })

    # Step 2: Generate normalized and gist versions
    query_normalized = normalizer.normalize(query)
    query_gist = gister.get_gist(query)  # May be slow - consider async

    # Step 3: Search for solution using hierarchical algorithm
    solution = search_for_solution(query)

    # Step 4: Update query log with results
    query_log.update(query_log_id, {
        'query_normalized': query_normalized,
        'query_gist': query_gist,
        'matched_snapshot_id': solution.id if solution else None,
        'match_type': last_match_type,
        'processing_status': 'completed'
    })

    # Step 5: Queue async embedding generation
    if solution:
        async_embedding_queue.put({
            'query_log_id': query_log_id,
            'texts': [query, query_normalized, query_gist],
            'types': ['verbatim', 'normalized', 'gist']
        })

    return solution
```

### Solution Creation Pipeline

```python
def create_new_solution(question_verbatim: str, solution_data: dict) -> str:
    """Create new solution with three-level representation."""

    # Step 1: Validate uniqueness
    if solution_snapshots.get_by_verbatim(question_verbatim):
        raise ValueError(f"Solution already exists for: {question_verbatim}")

    # Step 2: Generate representations
    question_normalized = normalizer.normalize(question_verbatim)
    question_gist = gister.get_gist(question_verbatim)

    # Step 3: Create solution snapshot
    snapshot = SolutionSnapshot(
        question_verbatim=question_verbatim,
        question_normalized=question_normalized,
        question_gist=question_gist,
        **solution_data
    )

    snapshot_id = solution_snapshots.save(snapshot)

    # Step 4: Add to canonical synonyms (self-reference)
    canonical_synonyms.add(CanonicalSynonym(
        snapshot_id=snapshot_id,
        question_verbatim=question_verbatim,
        question_normalized=question_normalized,
        question_gist=question_gist,
        confidence_score=100.0,
        validation_method='primary_question'
    ))

    # Step 5: Queue async embedding generation
    async_embedding_queue.put({
        'snapshot_id': snapshot_id,
        'texts': [question_verbatim, question_normalized, question_gist],
        'types': ['verbatim', 'normalized', 'gist']
    })

    return snapshot_id
```

## Risk Analysis and Mitigation

### High-Impact Risks

#### 1. Data Migration Complexity
**Risk**: Existing synonymous_questions data contains inconsistencies
**Mitigation**:
- Comprehensive validation scripts
- Manual review of conflicts
- Phased migration with rollback capability
- Extensive testing on copy of production data

#### 2. Performance Degradation
**Risk**: Three-level processing adds computational overhead
**Mitigation**:
- Async processing for expensive operations (gist, embeddings)
- Aggressive caching at all levels
- Early exit search algorithm minimizes work
- Performance monitoring and alerting

#### 3. Storage Growth
**Risk**: 3x embeddings and representations increase storage needs
**Mitigation**:
- Embedding compression using quantization
- Lazy loading of embeddings
- Tiered storage (hot/cold data)
- Regular cleanup of old query logs

#### 4. Search Quality Degradation
**Risk**: Hierarchical search might miss good matches
**Mitigation**:
- Comprehensive A/B testing before rollout
- Fallback to similarity search when exact matches fail
- Quality metrics tracking and alerting
- Easy rollback to previous search algorithm

### Medium-Impact Risks

#### 5. Uniqueness Constraint Violations
**Risk**: Multiple solutions for same verbatim question during migration
**Mitigation**:
- Pre-migration duplicate detection
- Conflict resolution procedures
- Admin interface for manual resolution
- Graceful handling of constraint violations

#### 6. Gist Generation Inconsistency
**Risk**: LLM gist generation varies over time
**Mitigation**:
- Version tracking of gist models
- Deterministic prompt engineering
- Periodic gist regeneration for critical questions
- Fallback to normalized matching if gist fails
