# Best small embedding models for code and prose on an RTX 4090

**CodeRankEmbed (137M) for code and nomic-embed-text-v1.5 (137M) for prose is the optimal pairing** — together they consume under 1.5 GB VRAM in float16, deliver state-of-the-art results for their size class, both support 8192-token context, and load cleanly via HuggingFace transformers. This leaves over 22 GB of headroom on your RTX 4090's 24 GB, far under the 4 GB-per-model budget. The text model supports Matryoshka dimensions from 64 to 768, enabling flexible vector storage. No single small model handles both code and prose well enough to justify a unified approach.

---

## The code model: CodeRankEmbed dominates its weight class

**nomic-ai/CodeRankEmbed** is a 137M-parameter encoder released in December 2024 (ICLR 2025) that outperforms models 10× its size on code retrieval benchmarks. Built on Snowflake's Arctic-Embed-M-Long backbone and contrastively fine-tuned on CoRNStack (21M dual-consistency-filtered code examples), it achieves **78.4 Python MRR on CodeSearchNet** and **60.1 nDCG@10 on CoIR** — beating CodeSage-Large (1.3B), Jina-Code-v2, and OpenAI Ada-002.

| Model | Params | Python CSN MRR | CoIR nDCG@10 | Max Tokens | Embed Dim | VRAM (fp16) |
|---|---|---|---|---|---|---|
| **CodeRankEmbed** | **137M** | **78.4** | **60.1** | **8192** | **768** | **~275 MB** |
| Jina-Code-v2 | 161M | ~62* | 58.4 | 8192 | 768 | ~320 MB |
| CodeSage-base-v2 | 356M | ~68.7 | 57.5 | 2048 | 1024 | ~710 MB |
| CodeSage-large-v2 | 1.3B | 74.2 | 59.4 | 2048 | 1024 | ~2.6 GB |
| UniXcoder | 126M | 72.0 | — | 512 | 768 | ~250 MB |
| CodeBERT | 125M | ~67 | — | 512 | 768 | ~250 MB |

CodeRankEmbed's **8192-token context window** is critical for code — many Python functions exceed 512 tokens, which renders CodeBERT and UniXcoder impractical for real-world use. The model handles natural language → code retrieval natively: you prefix queries with `"Represent this query for searching relevant code: "` and embed code snippets without any prefix. It uses cosine similarity and is MIT-licensed.

The only models that beat it are the **7B-parameter nomic-embed-code** (81.7 Python MRR, but ~14 GB VRAM) and closed-source Voyage Code 3 — neither fits your constraints. CodeSage-small-v2 (130M) offers Matryoshka dimension support, but its benchmark scores trail CodeRankEmbed by 15+ points on CSN. **CodeRankEmbed is the unambiguous choice.**

## The prose model: nomic-embed-text-v1.5 balances quality, MRL, and efficiency

For voice-to-text transcription similarity search, **nomic-ai/nomic-embed-text-v1.5** (137M parameters) delivers the best combination of retrieval quality, Matryoshka support, long context, and small footprint. It scores **~53.0 nDCG@10 on MTEB retrieval** and supports embedding dimensions from **64 to 768 via Matryoshka Representation Learning** — the widest MRL range among models in this size class.

| Model | Params | MTEB Retrieval | MRL Dims | Max Tokens | Embed Dim | VRAM (fp16) |
|---|---|---|---|---|---|---|
| **nomic-embed-text-v1.5** | **137M** | **~53.0** | **64–768** | **8192** | **768** | **~262 MB** |
| Arctic-Embed-M v2.0 | 113M | ~55.4 | 256 only | 8192 | 768 | ~220 MB |
| BGE-base-en-v1.5 | 110M | ~53.3 | None | 512 | 768 | ~220 MB |
| GTE-base-en-v1.5 | 137M | ~54.0 | None | 8192 | 768 | ~274 MB |
| mxbai-embed-large-v1 | 335M | ~54.4 | Truncatable | 512 | 1024 | ~670 MB |
| stella_en_400M_v5 | ~400M | ~56+ | 512–8192 | 512 | Variable | ~800 MB |
| GTE-large-en-v1.5 | 434M | ~57.9 | None | 8192 | 1024 | ~870 MB |

**Snowflake Arctic-Embed-M v2.0** edges ahead on raw retrieval score (55.4 vs 53.0) and deserves serious consideration as an alternative. However, its MRL only truncates to a single dimension (256), whereas nomic-embed-text-v1.5 lets you experiment across 64, 128, 256, 512, and 768. For voice transcription search — where inputs are typically short, informal, and English-only — nomic-embed-text-v1.5's **Matryoshka flexibility** is more valuable than a 2-point retrieval edge, since you can tune the dimension/quality tradeoff to your latency and storage constraints.

If maximum retrieval accuracy matters more than MRL, consider **stella_en_400M_v5** (~56+ retrieval, MRL from 512–8192 dims, ~800 MB fp16) or **GTE-large-en-v1.5** (57.9 retrieval, no MRL, ~870 MB fp16). Both still fit comfortably within the 4 GB budget.

## Combined VRAM budget is well under target

Both recommended models together consume a fraction of the 8 GB budget:

| Component | VRAM (fp16) |
|---|---|
| CUDA context overhead | ~400 MB |
| CodeRankEmbed (137M) | ~275 MB |
| nomic-embed-text-v1.5 (137M) | ~262 MB |
| Inference activations (batch=32) | ~200 MB |
| **Total** | **~1.1–1.4 GB** |

Even with float32 loading, the pair would use only ~1.5–2 GB. This leaves **22+ GB free** for other workloads. At batch size 32 with 128-token sequences on an RTX 4090, expect throughput of **1,500–3,000 sentences/second** per model in fp16. Using `torch.float16` gives roughly **1.5× speedup** over float32 with negligible accuracy loss.

## Why a single dual-purpose model doesn't work here

Research into dual-purpose code+text models reveals a clear gap: **models that excel at text retrieval consistently underperform on code retrieval**, and vice versa. The CoIR benchmark paper explicitly states that "models excelling in text retrieval may not necessarily perform well in code retrieval." The only models competitive on both are 3B+ parameters:

- **Jina Embeddings v4** (3.8B) scores 71.59 on CoIR with a dedicated code LoRA adapter, but requires ~8–10 GB VRAM and carries a CC-BY-NC-4.0 non-commercial license
- **CodeXEmbed-400M** (Salesforce) handles both modalities but lacks MRL and trails CodeRankEmbed on code benchmarks by a wide margin
- **nomic-embed-text-v1.5** was not trained on code data — it handles StackExchange-style Q&A but fails on code similarity tasks

Two dedicated 137M models at ~1.1 GB total outperform any single sub-1B dual-purpose model. The VRAM savings from a single model are negligible given how small these models are.

## Working code: load, embed, compare, and monitor VRAM

Below is a complete, minimal implementation that loads both models onto a specific CUDA device in float16, generates embeddings, computes cosine similarity, and reports VRAM usage.

### Code embedding with CodeRankEmbed

```python
import torch
import torch.nn.functional as F
from sentence_transformers import SentenceTransformer

# ── Load model ──────────────────────────────────────────────────
device = "cuda:0"
code_model = SentenceTransformer(
    "nomic-ai/CodeRankEmbed",
    trust_remote_code=True,
    device=device,
    model_kwargs={"torch_dtype": torch.float16},
)

print(f"VRAM after loading CodeRankEmbed: "
      f"{torch.cuda.memory_allocated(0) / 1024**3:.3f} GB")

# ── Embed queries and code ──────────────────────────────────────
queries = [
    "Represent this query for searching relevant code: calculate fibonacci numbers",
    "Represent this query for searching relevant code: read a CSV file into a dataframe",
]

code_snippets = [
    "def fib(n):\n    a, b = 0, 1\n    for _ in range(n):\n        a, b = b, a + b\n    return a",
    "import pandas as pd\ndf = pd.read_csv('data.csv')",
    "def quicksort(arr):\n    if len(arr) <= 1:\n        return arr\n    pivot = arr[0]\n    return quicksort([x for x in arr[1:] if x < pivot]) + [pivot] + quicksort([x for x in arr[1:] if x >= pivot])",
]

# Queries get the prefix; code snippets do NOT
query_embs = code_model.encode(queries, convert_to_tensor=True)
code_embs = code_model.encode(code_snippets, convert_to_tensor=True)

# ── Cosine similarity ───────────────────────────────────────────
# Embeddings are already L2-normalized by SentenceTransformer
scores = query_embs @ code_embs.T  # [2, 3] similarity matrix

for i, query in enumerate(queries):
    ranked = sorted(zip(code_snippets, scores[i].tolist()), key=lambda x: -x[1])
    print(f"\nQuery: {query.split(': ', 1)[1]}")
    for code, score in ranked:
        print(f"  {score:.4f}  {code[:60]}...")
```

### Prose embedding with nomic-embed-text-v1.5 (with Matryoshka)

```python
import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModel

# ── Helpers ─────────────────────────────────────────────────────
def mean_pooling(model_output, attention_mask):
    token_embs = model_output[0]
    mask = attention_mask.unsqueeze(-1).expand(token_embs.size()).float()
    return torch.sum(token_embs * mask, dim=1) / torch.clamp(mask.sum(dim=1), min=1e-9)

# ── Load model ──────────────────────────────────────────────────
device = torch.device("cuda:0")
model_name = "nomic-ai/nomic-embed-text-v1.5"

tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
text_model = AutoModel.from_pretrained(
    model_name,
    trust_remote_code=True,
    torch_dtype=torch.float16,
).to(device)
text_model.eval()

print(f"VRAM after loading nomic-embed-text-v1.5: "
      f"{torch.cuda.memory_allocated(0) / 1024**3:.3f} GB")

# ── Embed documents and a query ─────────────────────────────────
# Prefixes are REQUIRED: "search_query: " or "search_document: "
documents = [
    "search_document: The quick brown fox jumped over the lazy dog near the riverbank.",
    "search_document: Machine learning models require large amounts of training data.",
    "search_document: The fox ran swiftly across the field and leaped over a sleeping hound.",
]
query = ["search_query: a fox jumping over a dog"]

matryoshka_dim = 256  # Try 64, 128, 256, 512, or 768

def encode(texts, dim=768):
    tokens = tokenizer(texts, padding=True, truncation=True, return_tensors="pt")
    tokens = {k: v.to(device) for k, v in tokens.items()}
    with torch.no_grad():
        out = text_model(**tokens)
    emb = mean_pooling(out, tokens["attention_mask"]).float()
    # Matryoshka: layer_norm → truncate → L2 normalize
    emb = F.layer_norm(emb, normalized_shape=(emb.shape[1],))
    emb = emb[:, :dim]
    emb = F.normalize(emb, p=2, dim=1)
    return emb

doc_embs = encode(documents, dim=matryoshka_dim)
query_emb = encode(query, dim=matryoshka_dim)

# ── Cosine similarity ───────────────────────────────────────────
scores = (query_emb @ doc_embs.T).squeeze()

print(f"\nQuery: '{query[0].split(': ', 1)[1]}'  (dim={matryoshka_dim})")
for doc, score in sorted(zip(documents, scores.tolist()), key=lambda x: -x[1]):
    print(f"  {score:.4f}  {doc.split(': ', 1)[1][:70]}")
```

### VRAM monitoring utility

```python
def vram_report(device_id=0):
    alloc = torch.cuda.memory_allocated(device_id) / 1024**3
    reserved = torch.cuda.memory_reserved(device_id) / 1024**3
    peak = torch.cuda.max_memory_allocated(device_id) / 1024**3
    print(f"VRAM — Allocated: {alloc:.3f} GB | Reserved: {reserved:.3f} GB | Peak: {peak:.3f} GB")

# Call after loading both models:
vram_report()
# Expected output: Allocated: ~0.6 GB | Reserved: ~0.8 GB | Peak: ~0.7 GB

# Reset peak tracking between experiments:
torch.cuda.reset_peak_memory_stats()
torch.cuda.empty_cache()
```

## Conclusion

The **CodeRankEmbed + nomic-embed-text-v1.5** pairing is the clear recommendation. Both models are 137M parameters, MIT/Apache-2.0 licensed, support 8192-token context, and together use barely 5% of an RTX 4090's VRAM in float16. CodeRankEmbed's 78.4 Python MRR is remarkable for a model this small — it punches above models nearly 10× larger. The nomic text model's Matryoshka support across five dimension steps (64 through 768) gives practical flexibility to tune the storage-vs-quality tradeoff without retraining.

If retrieval accuracy on the text side is paramount and MRL is secondary, swap in **Snowflake Arctic-Embed-M v2.0** (55.4 vs 53.0 on MTEB retrieval, MRL at 256 only, CLS pooling with `"query: "` prefix) or **stella_en_400M_v5** (~56+ retrieval, MRL from 512–8192, ~800 MB fp16) for a ~3-point improvement at the cost of narrower Matryoshka options. All three alternatives still fit trivially within budget.
