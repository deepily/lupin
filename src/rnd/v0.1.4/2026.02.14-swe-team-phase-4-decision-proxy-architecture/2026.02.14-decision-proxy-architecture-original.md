# SWE Team Phase 4: Trust-Aware Decision Proxy — 4-Layer Hybrid Architecture

## Context

Phases 1-3 of the SWE Team built a working Lead → Coder → Tester delegation loop (946 unit tests, v0.3.0). Phase 4 adds **graduated-trust autonomous decision-making** so the SWE team can operate during off-hours without requiring human approval for every decision.

**Problem**: The SWE team's `cosa_interface.py` routes all decisions (task decomposition approval, dangerous command gating, architecture choices) to the user via voice notifications. When the user is offline, the team blocks.

**Solution**: A **decision proxy** framework that intercepts these decisions, classifies them by category and risk, and either acts autonomously (at earned trust levels) or queues them for morning ratification.

**Architecture decision**: After evaluating 3 approaches (extend existing, standalone, hybrid), we chose **Approach A: Separate packages** — the cleanest separation of concerns with 4 layers:

1. **Shared proxy infrastructure** extracted from the notification proxy
2. **Notification proxy** refactored to use shared infra (backward-compatible)
3. **Decision proxy** as a generic trust framework (domain-agnostic)
4. **SWE engineering proxy** as a domain-specific extension inside the SWE team package

---

## 4-Layer Architecture

```
Layer 1: Shared Infrastructure (src/cosa/agents/utils/proxy_agents/)
    ├── Base WebSocket listener, REST submission, strategy protocol, config, CLI
    │
    ├─→ Layer 2: Notification Proxy (src/cosa/agents/notification_proxy/) [REFACTORED]
    │   └── Expediter Q&A strategies (script matcher, rules, LLM fallback)
    │
    └─→ Layer 3: Decision Proxy (src/cosa/agents/decision_proxy/) [NEW - GENERIC]
        ├── Trust tracker, circuit breaker, decision store
        ├── Base decision strategy (abstract), smart router, category classifier interface
        │
        └─→ Layer 4: SWE Engineering Proxy (src/cosa/agents/swe_team/proxy/) [NEW - DOMAIN]
            └── 6 engineering categories, SWE sender patterns, concrete strategy
```

**Why 4 layers instead of 3**: The trust framework (tracker, circuit breaker, decision store) is inherently domain-agnostic. SWE engineering decisions (deployment, testing, deps, architecture, destructive, general) are one set of categories — future agents (DevOps, data pipeline, etc.) would define their own category sets and sender patterns on top of the same trust framework.

---

## Strict Dependency Flow

```
Layer 1: proxy_agents/
    ↑              ↑
Layer 2:         Layer 3:
notification_    decision_proxy/
proxy/               ↑
                 Layer 4:
                 swe_team/proxy/
                     ↓
              cosa.rest.db + postgres_models
```

**Rules**:
- `proxy_agents/` NEVER imports from notification_proxy, decision_proxy, or swe_team
- `notification_proxy/` NEVER imports from decision_proxy or swe_team
- `decision_proxy/` NEVER imports from notification_proxy or swe_team
- `swe_team/proxy/` imports from decision_proxy (for base classes) and proxy_agents (for shared infra)

### Phase 4c: Trust Tracker + Circuit Breaker (~2 sessions)

These live in `decision_proxy/` because they are **domain-agnostic** — they track trust scores and detect anomalies regardless of what categories are defined.

| File | Purpose |
|------|---------|
| `decision_proxy/trust_tracker.py` | `CategoryTrust` (rolling window, time-weighted decay) + `TrustTracker` (L1→L5 graduation, per-category isolation). Categories are **registered at runtime**, not hardcoded. |
| `decision_proxy/circuit_breaker.py` | Error rate spike detection, confidence collapse, OOD detection, auto-demotion + urgent notification |

**Trust levels** (configurable thresholds):
- **L1** (0 decisions): Shadow — predict only, log, don't act
- **L2** (50+): Suggest — queue as provisional, human ratifies
- **L3** (200+): Act + Notify — commit decision, async audit
- **L4** (500+): Autonomous + Sample Audit — 10% random audit
- **L5** (1000+): Full Autonomy — circuit breaker only safety net

**Category caps**: Configurable per domain (SWE caps destructive/deployment at L3).

**Config keys**:
```
trust proxy l2 threshold                                        = 50
trust proxy l3 threshold                                        = 200
trust proxy l4 threshold                                        = 500
trust proxy l5 threshold                                        = 1000
trust proxy decay half life days                                = 14
trust proxy rolling window days                                 = 30
trust proxy circuit breaker error rate threshold                = 0.15
trust proxy circuit breaker confidence collapse threshold       = 0.3
trust proxy circuit breaker auto demotion levels                = 2
trust proxy circuit breaker recovery cooldown seconds           = 3600
```

**Tests**: `src/tests/unit/test_trust_tracker.py` (~25-30 tests)

### Phase 4d: Decision Store + Ratification API (~2 sessions)

**Database** (PostgreSQL, following existing SQLAlchemy 2.0 + BaseRepository patterns):

| File | Purpose |
|------|---------|
| `src/cosa/rest/postgres_models.py` (modify) | Add `ProxyDecision` + `TrustState` ORM models |
| `src/cosa/rest/db/repositories/proxy_decision_repository.py` (new) | Extends `BaseRepository[ProxyDecision]` — `log_shadow()`, `log_decision()`, `get_pending()`, `ratify()`, `find_similar()` |
| `src/cosa/rest/routers/decision_proxy.py` (new) | `GET /api/proxy/pending/{email}`, `POST /api/proxy/ratify/{id}` |
| `src/scripts/sql/2026.02.XX-decision-proxy-schema.sql` (new) | Migration SQL |

**Tables**:
- `proxy_decisions` — every decision logged (notification_id, domain, category, question, decision_value, confidence, trust_level, ratification_state). Note: `domain` field distinguishes SWE from future domains.
- `trust_states` — per-user per-domain per-category trust snapshot (trust_level, total/successful/rejected counts, circuit breaker state)

**Key patterns to follow**:
- `src/cosa/rest/db/repositories/base.py` — `BaseRepository` with `get_by_id()`, CRUD ops
- `src/cosa/rest/postgres_models.py` — SQLAlchemy 2.0 declarative, UUID PKs, JSONB, timestamps

**Ratification flow**:
1. Decisions at L1-L2 stored with `ratification_state = "pending"`
2. User opens `GET /api/proxy/pending/{email}` to see queue
3. User approves/rejects via `POST /api/proxy/ratify/{id}`
4. Trust tracker learns from ratification outcome

**Tests**: `src/tests/unit/test_decision_store.py` (~15 tests, mocked DB sessions)

### Phase 4e: SWE Engineering Proxy — Domain Layer (~2 sessions)

| File | Purpose |
|------|---------|
| `__init__.py` | Package exports |
| `config.py` | SWE-specific: accepted senders (`swe.*@lupin.deepily.ai`), 6 engineering categories with keyword sets and cap levels |
| `engineering_categories.py` | Category definitions: `deployment` (cap L3), `testing` (cap L5), `deps` (cap L5), `architecture` (cap L3), `destructive` (cap L3), `general` (cap L5) — each with keyword patterns |
| `engineering_classifier.py` | Concrete `CategoryClassifier` subclass — classifies SWE team questions into the 6 categories using sender ID prefix + keyword analysis |
| `engineering_strategy.py` | Concrete `BaseDecisionStrategy` subclass — uses engineering_classifier + trust tracker + decision store to gate/act/shadow |

**How it connects**: The decision proxy's `responder.py` loads domain-specific strategy implementations via the `--profile` flag:
```
python -m cosa.agents.decision_proxy --profile swe_team
→ Loads swe_team/proxy/engineering_strategy.py as Tier 0
→ Uses swe_team/proxy/engineering_categories.py for category definitions
→ Registers categories with decision_proxy's TrustTracker
```

## Risk Mitigations

| Risk | Mitigation |
|------|------------|
| Import path changes break notification proxy tests | Re-export all moved constants through notification_proxy/config.py |
| Trust proxy makes bad autonomous decision | L1-L2 always require ratification; destructive/deployment/architecture capped at L3 |
| Both proxies on same WebSocket | Different session IDs ("auto proxy" vs "decision proxy") |
| Database migration on live system | Additive only (CREATE TABLE) — no ALTER on existing tables |
| Over-abstraction in decision_proxy | Start with one concrete domain (SWE); the abstract interfaces are minimal (classify, gate, decide) |
| 4-layer complexity | Each layer has clear ownership; strict import rules prevent tangling |

## Future Extensibility

To add a new domain (e.g., DevOps proxy):
1. Create `src/cosa/agents/devops_agent/proxy/`
2. Define domain-specific categories in `devops_categories.py`
3. Implement `DevOpsClassifier(CategoryClassifier)` and `DevOpsStrategy(BaseDecisionStrategy)`
4. Add `--profile devops` to decision proxy CLI
5. Register devops sender IDs in config
6. The trust framework, circuit breaker, decision store, and ratification API are all reused unchanged
