# Unified Notification Proxy + Interactive Smoke Test Framework

**Created**: 2026-02-13
**Status**: IN PROGRESS
**Pattern**: Refactoring (Extract Superclass + Mixin)

## Problem

Three independent live pipeline smoke tests (calculator, CRUD, expeditor) each duplicate ~150 lines of identical infrastructure code (login, session resolution, submit-and-poll, answer validation, results table). Adding a new voice-interactive agent requires copy-pasting boilerplate, manually launching the notification proxy in a separate terminal, and knowing which profile/Q&A script to use.

## Solution

1. **`LivePipelineTestBase`** — Extract all shared test infrastructure into a single base class
2. **`EmbeddedProxyMixin`** — Auto-launch notification proxy as subprocess (no separate terminal needed)
3. **`InteractiveSmokeTest`** — Merge base + mixin for tests that need voice proxy support

## Architecture

```
LivePipelineTestBase                 EmbeddedProxyMixin
├── _get_credentials()               ├── _start_proxy( profile, strategy )
├── _login()                         ├── _stop_proxy()
├── _get_websocket_session_id()      └── proxy_running property
├── _set_mode() / _clear_mode()
├── _submit_and_wait()                    InteractiveSmokeTest
├── _check_answer()                       (LivePipelineTestBase + EmbeddedProxyMixin)
├── _print_results_table()                ├── auto-starts proxy before interactive scenarios
├── run_scenarios()                       ├── auto-stops proxy after last scenario
└── build_argparser()                     └── reports proxy stats alongside test results
```

## What Changes vs What Doesn't

**Changes**: 4 new files in utilities/, 3 existing tests refactored, ~450 lines of duplication eliminated
**Does NOT Change**: notification proxy code, Q&A scripts, server endpoints, CJ Flow, unit tests

## Key Design Decisions

1. **Subprocess auto-launch (Option A)** over in-process polling — zero changes to existing proxy code, zero new server endpoints
2. **Base class + mixin** over single inheritance — calculator doesn't need proxy, clean separation of concerns
3. **Scenario-driven** — each subclass defines SCENARIOS list, base class handles the loop
4. **Backward compatible** — all CLI interfaces preserved, standalone proxy still works
