## 1. What is a Bounded CJ Flow Job?

A **bounded job** is a fire-and-forget asynchronous task that flows through the CJ Flow
queue pipeline:

```
todo  -->  running  -->  done / dead
```

The queue consumer picks up jobs from the `todo` queue, moves them to `running`, executes
`do_all()`, and deposits the result into `done` (success) or `dead` (failure). The user does
not interact with the job once it has been submitted. Progress and results are delivered
through notifications.

### Bounded vs. Interactive

| Property | BOUNDED | INTERACTIVE |
|----------|---------|-------------|
| Direction | Fire-and-forget (unidirectional) | Bidirectional dialogue |
| User input after submit | None | Real-time via notifications |
| Typical duration | Minutes to hours | Minutes (with pauses) |
| Examples | Deep Research, Podcast Generation, Claude Code tasks | Future: pair-programming, guided wizards |
| Notification pattern | Progress breadcrumbs + final completion | Questions + confirmations + progress |

### When to Use Bounded

Use a bounded job when:

- The task is **long-running** (research, audio generation, code analysis, batch processing)
- The task does **not need real-time user dialogue** once started
- The user can be away from the terminal and receive a notification when the work is done
- The task has a clear **start, execute, finish** lifecycle
- You want the task to survive page reloads and reconnections (queue persistence)

Do NOT use bounded when:

- The task requires multiple rounds of user input mid-execution
- The task is fast enough to return synchronously (under a few seconds)
- The result needs to be streamed token-by-token to the client in real time

## 2. The Seven Required Pieces

Every bounded job requires seven components. Missing any one of them will result in queue
failures, missing notifications, or untestable code.

### 2.1 Job Class

**Location**: `src/cosa/agents/<name>/job.py`

The job class is a subclass of `AgenticJobBase` and implements the core execution logic.

**Requirements**:

- Set class constants `JOB_TYPE` and `JOB_PREFIX`
- Call `super().__init__()` in the constructor
- Implement `last_question_asked` as a `@property`
- Implement `do_all()` as the synchronous entry point
- Implement `_execute()` as the async internal execution
- Implement `_execute_dry_run()` for testing without external dependencies
- Set `self.answer_conversational` before returning from `do_all()`

**Key class constants**:

| Constant | Purpose | Format | Example |
|----------|---------|--------|---------|
| `JOB_TYPE` | Type identifier used in queue UI and routing | lowercase snake_case | `"claude_code"` |
| `JOB_PREFIX` | ID prefix for generated job IDs | 2 lowercase letters | `"cc"` |

The `JOB_PREFIX` must be unique across all job types. The generated ID format is
`{prefix}-{uuid8}`, e.g., `cc-a1b2c3d4` (11 characters total).

### 2.2 Protocol Compliance

**Location**: `src/cosa/rest/queue_protocol.py`

The `QueueableJob` protocol defines **22 attributes and 4 methods** (including properties)
that every job flowing through the queue system must satisfy:

**Identity attributes** (2):
- `id_hash` -- unique job identifier
- `push_counter` -- queue position tracking

**Ownership attributes** (3):
- `user_id` -- job owner (uid from auth)
- `session_id` -- WebSocket session for notifications
- `routing_command` -- command used to route this job

**User context** (1):
- `user_email` -- for TTS notification routing

**Timestamps** (4):
- `run_date` -- when the job was executed
- `created_date` -- when the job was created
- `started_at` -- when execution started (None until running)
- `completed_at` -- when execution finished (None until done)

**Question/Answer** (4):
- `question` -- raw question text
- `last_question_asked` -- display string for queue UI
- `answer` -- raw answer text
- `answer_conversational` -- formatted answer for display/TTS

**Type identification** (1):
- `job_type` -- unified type identifier

**Status tracking** (3):
- `is_cache_hit` -- always False for agentic jobs
- `status` -- pending / running / completed / failed
- `error` -- error message (None if successful)

**Required methods** (4):
- `do_all()` -- execute and return conversational answer
- `code_ran_to_completion()` -- True if status is "completed"
- `formatter_ran_to_completion()` -- True if answer_conversational is set
- `is_cacheable` -- property, always returns False for agentic jobs

All 22 attributes and 4 methods are **inherited from `AgenticJobBase`**. You do not need to
implement them manually, but you must understand what they do because the queue system reads
them directly (no `getattr()` fallback chains).

### 2.3 Factory Registration

**Location**: `src/cosa/rest/agentic_job_factory.py`

The `create_agentic_job()` factory function is the single entry point for creating agentic
jobs from both the voice routing path (via the Runtime Argument Expeditor) and the REST
endpoint path. Both paths converge here.

**What to do**: Add an `elif` branch for your routing command string.

**Routing command conventions**:

- Followed by the human-readable job name in lowercase
- Must match the string used in the LORA intent classifier training data
- Must match the string used in `agent_registry.py` if the job uses the Runtime Argument Expeditor

### 2.4 Config Keys

**Locations**:
- `src/conf/lupin-app.ini` -- actual configuration values
- `src/conf/lupin-app-splainer.ini` -- human-readable explanations for each key

**Every** config key added to `lupin-app.ini` **must** have a corresponding explanation in

**Typical config keys for a bounded job**:

```ini

```

### 2.5 REST Router

**Location**: `src/cosa/rest/routers/<name>.py`

The REST router provides the FastAPI endpoint for submitting jobs to the queue. It follows
a consistent pattern across all job types.

**Required components**:

1. **Pydantic request model** -- defines the API contract (field validation, defaults, descriptions)
2. **Pydantic response model** -- defines the response shape (status, job_id, queue_position, message)
3. **Dependencies** -- `get_current_user` for auth, `get_todo_queue`, `get_user_job_tracker`
4. **Endpoint function** -- creates the job, associates with user, pushes to queue

**Critical ordering in the endpoint**:

```python
# 1. Create the job
job = MyNewJob( ... )

# 2. Associate BEFORE push (prevents race condition)
user_job_tracker.associate_job_with_user( job.id_hash, user_id )
user_job_tracker.associate_job_with_session( job.id_hash, session_id )

# 3. Push to queue
todo_queue.push( job )
```

The `associate_job_with_user()` call **must** happen before `push()`. The consumer thread may
grab the job immediately after `push()`, and if the user mapping does not exist yet, the job's
notifications will not route to the correct user. This is a documented race condition from
Session 108.

**Router registration**: Add the router to `src/fastapi_app/main.py`:

```python
from cosa.rest.routers.my_new_job import router as my_new_job_router
app.include_router( my_new_job_router )
```

### 2.6 Notifications

Bounded jobs communicate with the user exclusively through notifications. There is no
synchronous response channel.

**Two notification mechanisms**:

| Method | Purpose | When to Use |
|--------|---------|-------------|
| `cosa_interface.notify_progress()` | Progress breadcrumbs during execution | Every significant step |
| `cosa_interface.notify_completion()` | Final result with abstract | Job completion |

Both methods accept a `job_id` parameter that routes the notification to the correct job card
in the queue UI.

**Sender identity setup** (required before sending any notifications):

```python
# In _execute() or _execute_dry_run(), before any notify calls:
# MUST use self.base_id — NOT self.id_hash (see Pitfall 6.4)
cosa_interface.SENDER_ID   = cosa_interface._get_sender_id( suffix=self.base_id )
cosa_interface.TARGET_USER = self.user_email
```

**Notification pattern for a typical bounded job**:

```python
# At start
await cosa_interface.notify_progress(
    f"Starting: {self.query[ :60 ]}...",
    priority="low",
    job_id=self.id_hash
)

# During execution (one per significant step)
await cosa_interface.notify_progress(
    f"Step 2 of 5: Analyzing results...",
    priority="low",
    job_id=self.id_hash
)

# At completion
await cosa_interface.notify_progress(
    f"Task complete. Cost: {cost_str}",
    priority="medium",
    abstract=completion_abstract,
    job_id=self.id_hash
)
```

**Dry-run mode**: The `_execute_dry_run()` method should send breadcrumb notifications at
each simulated step with `await asyncio.sleep( 1.0 )` between them. This validates the
notification pipeline without invoking real external services. See `ClaudeCodeJob._execute_dry_run()`
for the canonical pattern (5 breadcrumbs with 1-second delays).

### 2.7 Smoke Test

**Location**: Inline `quick_smoke_test()` at the bottom of `job.py`, plus optional standalone
test in `src/tests/smoke/`.

The inline smoke test validates:

- Module imports successfully
- Job instantiation works with all required parameters
- ID format is correct (`{prefix}-{uuid8}`, 11 characters)
- `last_question_asked` returns expected format
- `is_cacheable` returns False
- Class constants (`JOB_TYPE`, `JOB_PREFIX`) are set correctly
- All queue-required attributes exist and have correct initial values

**Invocation**: `python -m cosa.agents.<name>.job`

The smoke test does NOT call `do_all()` because that would require external dependencies.
Use the `dry_run=true` flag through the REST endpoint for integration-level testing.

## 3. Reference Implementation: ClaudeCodeJob

The `ClaudeCodeJob` at `src/cosa/agents/claude_code/job.py` is the canonical reference
for bounded job implementation. This section walks through each component.

### 3.1 Class Constants

```python
class ClaudeCodeJob( AgenticJobBase ):
    JOB_TYPE   = "claude_code"
    JOB_PREFIX = "cc"
```

- `JOB_TYPE` is used in the queue UI, in `job_type` property, and as the `routing_command`
- `JOB_PREFIX` generates IDs like `cc-a1b2c3d4`

### 3.2 Constructor Pattern

```python
def __init__(
    self,
    prompt: str,
    project: str,
    user_id: str,
    user_email: str,
    session_id: str,
    task_type: str = "BOUNDED",
    max_turns: int = 50,
    timeout_seconds: int = 3600,
    dry_run: bool = False,
    debug: bool = False,
    verbose: bool = False
) -> None:
    super().__init__(
        user_id    = user_id,
        user_email = user_email,
        session_id = session_id,
        debug      = debug,
        verbose    = verbose
    )
    # Task-specific attributes
    self.prompt          = prompt
    self.project         = project
    self.task_type       = task_type.upper()
    self.max_turns       = max_turns
    self.timeout_seconds = timeout_seconds
    self.dry_run         = dry_run
    # Results (populated after execution)
    self.task_result  = None
    self.cost_usd     = None
    self.output_text  = None
    self.cost_summary = None
```

**Key points**:

- `super().__init__()` must be called first -- it sets all 22 protocol attributes
- Task-specific attributes come after the super call
- Result attributes are initialized to None and populated during execution
- The `cost_summary` attribute is required by `queues.py` for the unified job interface

### 3.3 last_question_asked Property

```python
@property
def last_question_asked( self ) -> str:
    prefix    = "Bounded" if self.task_type == "BOUNDED" else "Interactive"
    truncated = self.prompt[ :50 ] + "..." if len( self.prompt ) > 50 else self.prompt
    return f"[Claude Code - {prefix}] {truncated}"
```

This property is displayed in the queue UI. It should be human-readable and include enough
context to identify the job at a glance. Truncate long inputs to keep the display manageable.

### 3.4 do_all() -- Sync Entry Point

```python
def do_all( self ) -> str:
    self.status     = "running"
    self.started_at = datetime.now().isoformat()
    try:
        result = asyncio.run( self._execute() )
        self.status       = "completed"
        self.completed_at = datetime.now().isoformat()
        self.result       = result
        self.answer_conversational = result
        return result
    except Exception as e:
        self.status       = "failed"
        self.completed_at = datetime.now().isoformat()
        self.error        = str( e )
        self.answer_conversational = f"Claude Code task failed: {str( e )}"
        return self.answer_conversational
```

**Key points**:

- `do_all()` is called by `RunningFifoQueue` on the consumer thread (synchronous context)
- It bridges to `_execute()` via `asyncio.run()`
- It MUST set `self.answer_conversational` in both success and failure paths
- It MUST set `self.status` to either `"completed"` or `"failed"`
- It MUST set `self.completed_at` in both paths
- The `except` block catches all exceptions, stores the error, and returns gracefully

### 3.5 _execute() -- Async Execution

The `_execute()` method contains the real work. For `ClaudeCodeJob`, it:

1. Checks for dry-run mode and delegates to `_execute_dry_run()` if true
2. Imports the `ClaudeCodeDispatcher` and `cosa_interface` for notifications
3. Sends a start notification with `priority="low"`
4. Creates and dispatches the task
5. On success: stores artifacts, formats completion message, sends completion notification
6. On failure: stores error artifacts, sends urgent notification, raises `RuntimeError`

The `raise RuntimeError(...)` on failure is caught by the `except` block in `do_all()`.

### 3.6 _execute_dry_run() -- Test Mode

```python
async def _execute_dry_run( self ) -> str:
    from cosa.agents.claude_code import cosa_interface
    import asyncio

    # 5 breadcrumb notifications with 1-second delays
    await cosa_interface.notify_progress( "Dry run: Initializing...", priority="low", job_id=self.id_hash )
    await asyncio.sleep( 1.0 )
    # ... 3 more breadcrumbs ...
    await cosa_interface.notify_progress( "Dry run: Generating completion report", priority="low", job_id=self.id_hash )
    await asyncio.sleep( 1.0 )

    # Set mock results
    self.output_text  = f"Mock execution completed for: {self.prompt[ :100 ]}..."
    self.cost_usd     = 0.0
    self.cost_summary = { "total_cost_usd" : 0.0 }
    self.artifacts    = { "cost_usd" : 0.0, "dry_run" : True, ... }
    self.status       = "completed"

    # Final completion notification with abstract
    await cosa_interface.notify_progress( f"Dry run complete: {self.id_hash}", priority="medium", abstract=completion_abstract, job_id=self.id_hash )
    return self.output_text
```

Dry-run mode validates the full notification pipeline and queue lifecycle without invoking
external services. It is essential for integration testing.

In `src/cosa/rest/routers/claude_code_queue.py`:

### 4.1 Job Class (`src/cosa/agents/my_new_job/job.py`)

            query: The task description

            session_id: WebSocket session ID
            dry_run: If True, simulate execution
            debug: Enable debug output
            verbose: Enable verbose output

            user_id    = user_id,
            user_email = user_email,
            session_id = session_id,
            debug      = debug,
            verbose    = verbose

        Returns:
            str: Human-readable job description

            str: Conversational answer summarizing results

            result = asyncio.run( self._execute() )

            self.completed_at = datetime.now().isoformat()
            self.result       = result
            self.answer_conversational = result

            if self.debug:

                print( f"[MyNewJob] Completed in {duration:.1f}s" )

            return result

        except Exception as e:

            self.completed_at = datetime.now().isoformat()

                import traceback
                traceback.print_exc()

            return self.answer_conversational

### 4.3 REST Router (`src/cosa/rest/routers/my_new_job.py`)

```python
from fastapi import APIRouter, HTTPException, Depends
from pydantic import BaseModel, Field
from typing import Optional

from cosa.rest.auth import get_current_user

router = APIRouter( tags=[ "my-new-job" ] )


class MyNewJobRequest( BaseModel ):
    query: str = Field( ..., min_length=1, description="The task description" )
    websocket_id: Optional[ str ] = Field( None, description="WebSocket session ID" )
    dry_run: bool = Field( False, description="Simulate execution" )


class MyNewJobResponse( BaseModel ):
    status: str = Field( ..., description="Job status (queued)" )
    job_id: str = Field( ..., description="Unique job identifier (mn-{uuid8})" )
    queue_position: int = Field( ..., description="Position in the todo queue" )
    message: str = Field( ..., description="Human-readable confirmation" )


def get_todo_queue():
    import fastapi_app.main as main_module
    return main_module.jobs_todo_queue


def get_user_job_tracker():
    from cosa.rest.queue_extensions import user_job_tracker
    return user_job_tracker


@router.post( "/api/my-new-job/queue/submit", response_model=MyNewJobResponse )
async def submit_my_new_job(
    request_body: MyNewJobRequest,
    current_user: dict = Depends( get_current_user ),
    todo_queue = Depends( get_todo_queue ),
    user_job_tracker = Depends( get_user_job_tracker )
):
    from cosa.agents.my_new_job.job import MyNewJob

    user_id    = current_user.get( "uid" )
    user_email = current_user.get( "email" )

    if not user_id:
        raise HTTPException( status_code=400, detail="User ID not found in token" )
    if not user_email:
        raise HTTPException( status_code=400, detail="User email not found in token" )

    session_id = request_body.websocket_id or f"api-{user_id[ :8 ]}"

    try:
        job = MyNewJob(
            query      = request_body.query,
            user_id    = user_id,
            user_email = user_email,
            session_id = session_id,
            dry_run    = request_body.dry_run
        )

        # Associate BEFORE push (race condition prevention)
        user_job_tracker.associate_job_with_user( job.id_hash, user_id )
        user_job_tracker.associate_job_with_session( job.id_hash, session_id )

        todo_queue.push( job )

        return MyNewJobResponse(
            status         = "queued",
            job_id         = job.id_hash,
            queue_position = todo_queue.size(),
            message        = f"Job queued: {job.last_question_asked}"
        )

    except Exception as e:
        raise HTTPException( status_code=500, detail=f"Failed to submit job: {str( e )}" )
```

## 6. Common Pitfalls

### 6.1 Forgetting to call super().__init__()

**Symptom**: `AttributeError: 'MyNewJob' object has no attribute 'id_hash'` (or any of the
22 protocol attributes) when the queue system tries to read the job.

**Fix**: Always call `super().__init__()` as the first line of your constructor:

```python
def __init__( self, query, user_id, user_email, session_id, **kwargs ):
    super().__init__(
        user_id    = user_id,
        user_email = user_email,
        session_id = session_id,
        debug      = kwargs.get( "debug", False ),
        verbose    = kwargs.get( "verbose", False )
    )
    self.query = query
```

### 6.2 Not setting self.answer_conversational

**Symptom**: `formatter_ran_to_completion()` returns False, causing the queue system to treat
the job as failed even though it ran successfully.

**Fix**: Set `self.answer_conversational` in BOTH the success and failure paths of `do_all()`:

```python
# Success
self.answer_conversational = result

# Failure
self.answer_conversational = f"Job failed: {str( e )}"
```

### 6.3 Missing user_job_tracker association BEFORE push()

**Symptom**: Job notifications route to the wrong user or do not appear in the queue UI.
The job runs successfully but the user never sees it.

**Fix**: Always associate before push:

```python
# CORRECT
user_job_tracker.associate_job_with_user( job.id_hash, user_id )
user_job_tracker.associate_job_with_session( job.id_hash, session_id )
todo_queue.push( job )

# WRONG - race condition
todo_queue.push( job )
user_job_tracker.associate_job_with_user( job.id_hash, user_id )
```

### 6.4 Using `id_hash` instead of `base_id` for sender_id

**Symptom**: `AsyncNotificationRequest` Pydantic validation error — `String should match
pattern` with a full UUID appearing in the sender_id suffix:

```
Failed to send progress notification: 1 validation error for AsyncNotificationRequest
sender_id
  String should match pattern '^[a-z]+(\.[a-z]+)+@[a-z]+\.deepily\.ai(#...)?$'
  input_value='deep.research@lupin.deep...-4cd4-addf-79810fd32b15'
```

**Root cause**: The router calls `register_scoped_job()` which mutates `job.id_hash` from
`rp-5c35fd5c` to `rp-5c35fd5c::0cf47e2d-d5a1-4cd4-addf-79810fd32b15` (appending user UUID).
If you use `self.id_hash` as the sender_id suffix, the `::UUID` fragment creates an invalid
sender_id that fails Pydantic validation. Notifications silently fail — the job runs but the
user sees no progress updates.

**Fix**: Always use `self.base_id` (which strips the `::user_id` scope suffix) when
constructing sender_id:

```python
# CORRECT — base_id strips ::user_id → "rp-5c35fd5c"
cosa_interface.SENDER_ID = cosa_interface._get_sender_id( suffix=self.base_id )

# WRONG — id_hash includes ::user_id → "rp-5c35fd5c::0cf47e2d-..."
cosa_interface.SENDER_ID = cosa_interface._get_sender_id( suffix=self.id_hash )
```

**Note**: `job_id=self.id_hash` is still correct for notification *routing* (the `job_id`
parameter in `notify_progress()` calls). The scoped ID is needed there for user-filtered
queue display. Only the *sender identity* must use the unscoped `base_id`.

### 6.4 Using asyncio.run() inside an already-running event loop

**Symptom**: `RuntimeError: This event loop is already running` when `do_all()` is called
from within an async context (e.g., during testing with pytest-asyncio, or if the queue
consumer is ever made async).

**Fix**: Check for an existing event loop and use `asyncio.create_task()` instead:

```python
try:
    loop = asyncio.get_running_loop()
    # Already in async context
    task = asyncio.create_task( self._execute() )
    result = await task
except RuntimeError:
    # No running loop - safe to use asyncio.run()
    result = asyncio.run( self._execute() )
```

Currently, `RunningFifoQueue` calls `do_all()` from a synchronous thread, so `asyncio.run()`
is safe. But be aware of this if the architecture evolves.

### 6.5 Hardcoding defaults instead of reading from ConfigurationManager

**Symptom**: Changing a default value requires a code change, rebuild, and redeploy instead
of a config file edit.

**Fix**: Store job-specific defaults in `lupin-app.ini` and read them at construction time:

```python
# WRONG
self.max_turns = 50

# CORRECT
config_mgr = ConfigurationManager( env_var_name="LUPIN_CONFIG_MGR_CLI_ARGS" )
self.max_turns = config_mgr.get_int( "my new job max turns" )
```

Remember to add the corresponding entry in `lupin-app-splainer.ini`.

### 6.6 Not implementing _execute_dry_run()

**Symptom**: The only way to test the job end-to-end is to invoke real external services
(which may cost money, require API keys, or be rate-limited).

**Fix**: Always implement `_execute_dry_run()` that:

1. Sends breadcrumb notifications at each simulated step
2. Uses `await asyncio.sleep( 1.0 )` between steps to simulate real timing
3. Sets mock values for `self.artifacts`, `self.cost_summary`, `self.status`
4. Returns a mock completion message
5. Is triggered by `if self.dry_run:` at the top of `_execute()`

This enables full integration testing through the REST endpoint without any external
dependencies.

## Summary

Adding a new bounded job to CJ Flow requires seven coordinated pieces:

| # | Piece | File | Key Action |
|---|-------|------|------------|
| 1 | Job class | `src/cosa/agents/<name>/job.py` | Subclass `AgenticJobBase`, implement `do_all()` and `_execute()` |
| 2 | Protocol compliance | (inherited) | Call `super().__init__()`, set `answer_conversational` |
| 3 | Factory registration | `src/cosa/rest/agentic_job_factory.py` | Add `elif` branch for routing command |
| 4 | Config keys | `lupin-app.ini` + `splainer.ini` | Add job-specific defaults with explanations |
| 5 | REST router | `src/cosa/rest/routers/<name>.py` | Endpoint + Pydantic models + auth + associate-before-push |
| 6 | Notifications | Inside `_execute()` | Progress breadcrumbs + completion with abstract |
| 7 | Smoke test | Bottom of `job.py` | `quick_smoke_test()` + `if __name__ == "__main__"` |

Follow the `ClaudeCodeJob` reference implementation at `src/cosa/agents/claude_code/job.py`
for the canonical patterns. Use the quick-start template in Section 4 to scaffold a new job
in under 30 minutes.
