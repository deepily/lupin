# PEFT Trainer: Resume-Path OOM — Root Cause Analysis

**Date**: 2026-02-16
**Status**: WILL NOT FIX — Intractable (PyTorch CUDA allocator internals)
**Affected Code**: `src/cosa/training/peft_trainer.py` → `run_pipeline()` with `--resume-from-merged`
**Symptom**: `ValueError: No available memory for the cache blocks` from vLLM after 8-bit quantization

---

## Executive Summary

When resuming from a merged model (`--resume-from-merged`), the 8-bit quantization step is the **first GPU operation** in the process. PyTorch's CUDA caching allocator creates a monolithic memory segment for the ~16 GB model. After quantization cleanup, a small residual allocation (~62 MB) pins the entire ~14 GB segment, preventing `empty_cache()` from releasing it. The subsequent vLLM subprocess sees only ~10 GB free on GPU 0 and OOMs during KV cache allocation.

The happy path (full pipeline) avoids this because prior training/merge/validation cycles create a "mature" allocator with granular block structure, allowing `empty_cache()` to release memory cleanly.

**This is not fixable at the application level** — the root cause is inside PyTorch's CUDA caching allocator and its interaction with the CUDA driver's memory management. Potential workarounds (allocator warmup, subprocess isolation) are either unreliable or require significant architectural changes disproportionate to the benefit.

## The Two Execution Flows

### Happy Path (Full Pipeline)

```
GPU Timeline:
1. __init__           → GPU clean (model=None, tokenizer=None)
2. HF login           → No GPU impact
3. Pre-validation     → vLLM subprocess (own CUDA context, killed after)
4. Fine-tuning        → Model on BOTH GPUs (device_map="auto"), release_gpus()
5. Adapter merge      → Model on GPU, release_gpus()
6. Post-validation    → vLLM subprocess (own CUDA context, killed after)
7. 4-bit quantization → Model on GPU 0, cleanup, wait_for_gpu_memory_release()
8. 4-bit vLLM         → Subprocess, killed after
9. 8-bit quantization → Model on GPU 0, cleanup ← ALLOCATOR IS WARM
10. 8-bit vLLM        → SUCCEEDS (GPU memory is clean)
```

By step 9, the CUDA caching allocator has been through **3-4 full allocation/deallocation cycles** on GPU 0. The allocator has a mature, granular block structure. When the 8-bit quantization cleanup runs, `empty_cache()` can release the model's memory blocks independently of any residual allocations.

### Resume Path (`--resume-from-merged`)

```
GPU Timeline:
1. __init__           → GPU clean (model=None, tokenizer=None)
2. HF login           → No GPU impact
3. Resume branch      → Sets merged_adapter_dir, NO GPU usage
4. 8-bit quantization → FIRST GPU OPERATION EVER ← ALLOCATOR IS COLD
5. 8-bit vLLM         → CRASHES (OOM)
```

At step 4, quantization is the **first-ever GPU operation**. The allocator creates a fresh CUDA context with a single monolithic ~16 GB segment. After cleanup, 62 MB of residual allocation pins the entire segment.

## The Numbers

After quantization cleanup on the resume path:

```
GPU 0:
  Allocated: 0.062 GB  ← 62 MB of live PyTorch tensors remain
  Reserved:  13.939 GB ← Allocator holds ~14 GB (model's segment, pinned by 62 MB)
  Peak:      15.938 GB ← Model WAS ~16 GB at peak

GPU 1:
  Clean (not used by quantizer, which uses device_map="cuda:0")
```

When vLLM starts (`tensor_parallel_size=2`, `gpu_memory_utilization=0.80`):

```
GPU 0: 23.65 GB total - 13.9 GB reserved = ~9.7 GB visible to vLLM
GPU 1: 23.65 GB total - 0 GB reserved    = ~23.3 GB visible to vLLM

vLLM needs: 4.29 GB model shard + KV cache (~14.6 GB at 0.80 util) = ~18.9 GB per GPU
GPU 0 has only 9.7 GB → KV cache allocation fails
```

## Root Cause: Two Intersecting Factors

### Factor 1: Cold Allocator Effect

PyTorch's CUDA caching allocator manages memory in **segments** (large blocks requested from CUDA) containing **blocks** (sub-allocations). `empty_cache()` can only release segments where **ALL blocks are free**.

| Allocator State | Segment Layout | empty_cache() Behavior |
|----------------|---------------|----------------------|
| **Cold** (first operation) | One monolithic ~16 GB segment | 62 MB residual pins entire segment |
| **Warm** (after cycles) | Many smaller segments (2-4 GB each) | 62 MB pins only its segment (~2 GB) |

The 62 MB residual is likely from GPTQ packing's in-place tensor modifications, cuBLAS workspace allocation, or AutoRound internal buffers that survive `release_gpu_memory()`.

### Factor 2: Subprocess Visibility

vLLM runs as a **subprocess** with its own CUDA context. From vLLM's perspective:

```
Available GPU memory = Total - Memory used by ALL processes on this GPU
```

The parent process's 13.9 GB of **reserved** memory (even though only 62 MB is allocated) is consumed from CUDA's perspective. External processes cannot access PyTorch's internal free blocks.

## Why This Is Intractable

### Warmup Approach (Attempted)

Pre-fragmenting the allocator with allocation/deallocation cycles before quantization. **Unreliable** because:
- `empty_cache()` after warmup returns all free blocks to CUDA, resetting allocator state
- Skipping `empty_cache()` leaves ~16 GB in the allocator pool, reducing CUDA-visible memory
- The stray 62 MB tensor's segment placement is non-deterministic — depends on allocator internals
- PyTorch's `expandable_segments` (default in recent versions) can consolidate segments unpredictably

### Subprocess Isolation (Considered)

Running quantization in a child process via `torch.multiprocessing` with spawn context. **Feasible but disproportionate** because:
- Requires re-architecting quantize_merged_adapter() for IPC (result queue, error handling)
- `spawn` context re-imports all modules (slow, potential import side effects)
- Adds complexity to an already complex pipeline for an edge case (resume mode)
- The resume path is an operational convenience, not a production workflow

### Other Approaches Considered

| Approach | Why Not |
|----------|---------|
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False` | Runtime env change may not take effect after CUDA init |
| Force-delete stray tensors via `gc.get_objects()` | Slow, fragile, may delete tensors still needed by cleanup |
| `nvidia-smi --gpu-reset` (nuclear option) | Kills ALL GPU processes, inappropriate between pipeline stages |
| Reduce `gpu_memory_utilization` for vLLM | Only shifts the threshold; 14 GB reserved is too much regardless |

## Workaround for Users

When using `--resume-from-merged`, skip `--post-quantization-stats` (vLLM validation after quantization). Run vLLM validation separately in a new process:

```bash
# Step 1: Quantize only (no post-quant validation)
python src/cosa/training/peft_trainer.py \
  --model-name Ministral-8B-Instruct-2410 \
  --resume-from-merged /path/to/merged-adapter \
  --quantize-bits 8

# Step 2: Validate manually in a new process
cd $DEEPILY_PROJECTS_DIR/vllm-pip && source .venv/bin/activate
vllm serve /path/to/quantized-model \
  --quantization gptq_marlin \
  --tensor-parallel-size 2 \
  --gpu-memory-utilization 0.80 \
  --max-model-len 2048
```

This works because step 2 starts with a clean CUDA context (no parent process holding reserved memory).

## Confirmed: Happy Path Exercises Same Code

The happy path runs with `--post-quantization-stats` and `--quantize-bits both` (4-bit then 8-bit). The exact same quantization cleanup + vLLM startup code executes successfully. The **only** difference is the CUDA allocator's block history at the time of 8-bit quantization.
