# Verification Plan: Unified Smoke Test Framework

## Context

The unified smoke test framework (commit `013e1d2`) extracted ~450 lines of duplicated infrastructure from 3 live pipeline smoke tests into reusable base classes. All code changes are committed. **This plan covers Phase 3 verification** — confirming the refactored tests produce identical behavior to the originals.

**What was built** (already committed):
- `LivePipelineTestBase` — shared auth, session, polling, validation, reporting
- `EmbeddedProxyMixin` — auto-launch notification proxy as subprocess
- `InteractiveSmokeTest` — merged base + mixin with `--auto-proxy` flag
- 3 tests refactored: calculator, CRUD, expeditor

**What needs verification**: The refactored tests must behave identically to the originals against the live server.

---

## Prerequisites

**Server stack** (must be running):
- FastAPI server on `localhost:7999`
- Phi-4 LLM server (for intent extraction)

**Environment variables** (must be set):
- `LUPIN_TEST_EMAIL` / `LUPIN_TEST_PASSWORD`
- `LUPIN_ROOT` (for proxy subprocess PYTHONPATH)
- `LUPIN_INTERACTIVE_TESTS=true` (expeditor only)

## Verification Tiers

```bash

pytest src/tests/unit/ -v
```

**Pass criteria**: All imports succeed, --help shows expected flags, unit tests unchanged.

### Tier 1: Calculator — Simplest (No Proxy Needed)

**Why first**: No proxy dependency, fastest feedback loop.

```bash
# Step 24: Explicit calculator mode, 2 queries (fast)
python src/tests/smoke/test_calculator_live_pipeline.py --queries 0,1

# If that passes, run all 6 queries
python src/tests/smoke/test_calculator_live_pipeline.py

# Step 25: LORA auto-routing (optional — requires trained adapter)
python src/tests/smoke/test_calculator_live_pipeline.py --auto-route -q 0,1
```

**Expected output**: Results table showing PASS for each query with answer previews containing expected keywords (6.21 for km→miles, 22.22 for F→C, etc.).

**What to watch for**:
- Login succeeds (token acquired)
- WebSocket session ID resolved
- Mode set to "calculator" (or None for auto-route)
- Job submitted via `/api/push`, `job_id` returned
- Done queue polled, answer found with expected keywords
- Mode cleared after each scenario

### Tier 2: CRUD Direct — Without Proxy

**Why**: Tests scenarios 0-3, 5 (all non-interactive). Scenario 4 (DELETE) will timeout/cancel — that's expected and tests the timeout path.

```bash
# Direct mode, no proxy — DELETE will timeout, that's OK
python src/tests/smoke/test_crud_live_pipeline.py --mode direct
```

**Expected output**:
- Scenarios 0-3 (ADD, ADD_2, QUERY, DUPLICATE): PASS
- Scenario 4 (DELETE_TODO): FAIL or CANCEL (expected — no proxy to confirm)
- Scenario 5 (ADD_CALENDAR): PASS

**What to watch for**:
- Mode switches per scenario (todo → todo → todo → todo → todo → calendar)
- Duplicate detection works (scenario 3 returns "already exists")
- Calendar schema recognized (scenario 5)

---

### Tier 3: CRUD Direct — With Auto-Proxy (Single Terminal!)

**Why**: This is the key new capability. Tests `--auto-proxy` flag launches the proxy subprocess correctly.

```bash
# Single terminal! Auto-proxy handles delete confirmation
python src/tests/smoke/test_crud_live_pipeline.py --mode direct --auto-proxy
```

**Expected output**:
- All 6 scenarios PASS (including DELETE_TODO)
- Proxy startup message: "Starting notification proxy (profile=crud, strategy=llm_script)..."
- Proxy PID printed
- Delete confirmation auto-answered by proxy
- Proxy stopped gracefully at end

**What to watch for**:
- Proxy launches (5s wait, then PID shown)
- Proxy stays alive throughout all scenarios
- Scenario 4 (DELETE) passes (proxy auto-confirms)
- Proxy SIGINT shutdown prints stats
- No orphan proxy processes after test exits

**Fallback verification** (backward compat — manual proxy still works):
```bash
# Terminal 1: Start proxy manually
python -m cosa.agents.notification_proxy --profile crud --debug

# Terminal 2: Run test WITHOUT --auto-proxy
python src/tests/smoke/test_crud_live_pipeline.py --mode direct
```

### Tier 5: Expeditor Interactive — With Auto-Proxy

**Why**: Full end-to-end validation of the most complex refactoring. Tests custom `_submit_and_wait()`, custom credentials, and proxy auto-launch.

```bash
# Run 2 scenarios with auto-proxy
LUPIN_INTERACTIVE_TESTS=true python src/tests/smoke/test_expeditor_mock_job_smoke.py --scenarios 0,1 --auto-proxy

# If that works, try more scenarios
LUPIN_INTERACTIVE_TESTS=true python src/tests/smoke/test_expeditor_mock_job_smoke.py --scenarios 0,1,2,3 --auto-proxy
```

**Expected output**:
- Pre-checks pass (health + baseline)
- Proxy auto-launches with `expeditor_smoke` profile
- Scenarios 0-1 (DR_HAPPY, DR_MISSING) complete via mock job endpoint
- Proxy auto-answers expeditor prompts
- Results table with PASS/FAIL status
- Proxy gracefully stopped

**What to watch for**:
- Custom `_submit_and_wait()` uses `/api/mock-job/submit` (not `/api/push`)
- 600s REQUEST_TIMEOUT (blocking endpoint, no polling)
- Proxy profile is `expeditor_smoke` (not `crud`)
- Job completion verified via done queue check

## Execution Strategy

| Tier | Test | Time | Risk | Server | Proxy |
|------|------|------|------|--------|-------|
| 0 | Offline smoke | 30s | None | No | No |
| 1 | Calculator | 2-3min | Low | Yes | No |
| 2 | CRUD no proxy | 3-4min | Low | Yes | No |
| 3 | CRUD auto-proxy | 4-5min | Medium | Yes | Auto |
| 4 | Expeditor pre-check | 30s | Low | Yes | No |
| 5 | Expeditor interactive | 5-10min | Medium | Yes | Auto |

**Recommended order**: 0 → 1 → 2 → 4 → 3 → 5 (increasing complexity, early failures = fast feedback)

**Stop-on-failure rule**: If Tier 1 (calculator) fails, debug before proceeding. If Tier 2 (CRUD no proxy) fails on non-DELETE scenarios, the base class has a bug. If only DELETE fails, that's expected.
