## 0. Problem statement (grounded)

The GCP cloud-test VM `lupin-host-test` runs the app from a **bind-mount** (`./src:/var/lupin/src`, `docker-compose.cloud-test.yml:85`) with `reload=False`. Getting new code onto it today is fully manual: `git bundle` on the dev box → SCP → on-VM `sudo git pull` into the UID-1001-owned checkout → `sudo chown -R 1001:1001` → `docker restart`. Problems: no automation/staleness risk; "origin" is a one-way **local bundle file**, not a real remote; no CI/CD; UID-ownership friction every deploy.

**Firsthand confirmation (today):** deploying the FCM ADC change, I discovered the on-VM `src/` was STALE (missing commit `3155ca22`) and had to hand-sync files (SCP → `sudo cp` → `chown 1001:1001`) — exactly the friction this task kills. I also had to *grep on-VM code* to discover the staleness because nothing records what ref the VM runs.

## 1. The TWO code-delivery axes (the key insight today surfaced)

The original framing ("code reaches the VM") undersells a fork the mechanism MUST handle, because the two axes have **different delivery paths**:

| Axis | What changed | Delivery path | Restart vs rebuild |
|---|---|---|---|
| **A. Pure `src/` code** | `.py`/`.ini`/`.js` under `src/` | rides the `./src` bind-mount | file sync + `docker restart` (reload=False picks it up) — **NO image rebuild** |
| **B. Dependencies** | `pyproject.toml` / `uv.lock` (e.g. firebase-admin today) | baked into the venv **inside the image** | **image rebuild → push → pull → `up --force-recreate`** — restart is a silent no-op |

Any "code-sync" tool that only does the bind-mount path will **silently fail** on a deps change (the firebase-admin case: a `docker restart` would never load the new dep). The mechanism must DETECT the axis (diff `pyproject.toml`+`uv.lock` between deployed and target ref) and route accordingly.

## 2. Options compared

| | A. Real GitHub remote + VM pull | B. Baked-image CI/CD | C. Scripted rsync/export wrapper | D. Push-to-deploy trigger |
|---|---|---|---|---|
| **Mechanism** | Replace bundle-origin with a real GitHub remote; VM `git pull` (one-liner or sidecar) + restart | Cloud Build/Actions on push → build → AR → VM pull+recreate | One-command `deploy-cloud-test.sh`: export committed ref → SCP → chown → restart (or rebuild on deps) | git hook/webhook fires the sync on push |
| **Handles axis A** | ✅ (pull + restart) | ✅ (in image) | ✅ | ✅ |
| **Handles axis B (deps)** | ❌ still needs separate image rebuild | ✅ uniform | ✅ (explicit `--deps` route) | depends on backend |
| **Needs real GitHub remote** | ✅ (blocker — origin is a bundle today) | ✅ for trigger | ❌ (works off local checkout) | ✅ |
| **Iteration speed** | fast (pull+restart) | **slow** (full ~minutes image build per change) | **fast** | fast |
| **Build effort** | medium (remote + creds + pull script) | high (CI pipeline) | **low** (scripts today's manual flow) | medium-high (listener infra) |
| **Prod convergence (M3 = baked image + Secret Mgr)** | partial | ✅ this IS the prod model | cloud-test-only | partial |
| **Provenance** | git SHA on VM ✅ | image tag ✅ | needs an explicit `.deployed-ref` stamp | git SHA ✅ |

## 3. Recommendation — phased hybrid (C now, B for prod, A as enabling infra)

- **NOW (cloud-test fast path) → Option C**: build `src/scripts/deploy-cloud-test.sh` that automates exactly what I did by hand today, correctly:
  1. **Export a committed ref, never the dirty working tree** — `git archive <ref>` (default `HEAD`) to a tarball so the VM always matches a known SHA (today I hand-synced working-tree files — provenance-ambiguous; the VM ran "synced-but-unpushed" code with no record).
  2. **Two-axis auto-routing** — diff `pyproject.toml`+`uv.lock` between the VM's recorded `.deployed-ref` and the target ref. Unchanged → bind-mount path (SCP `src/` → `chown 1001:1001` → `docker restart`). Changed → fail-loud and require/trigger the **image path** (build→push→pull→`--force-recreate`) — never silently restart on a deps change.
  3. **UID-1001 handling** — stage in `/tmp` → `sudo cp` + `chown 1001:1001` (the friction I hit); or rsync as UID 1001.
  4. **Provenance stamp** — write `/mnt/lupin-data/lupin/.deployed-ref` (SHA + timestamp + axis) so "what's running?" is one `cat`, not a code-grep.
  5. **Reversible** — keep prior `src/` as `.bak-<stamp>` for instant rollback (mirrors today's `.old-fcm` discipline).
- **CONVERGE (prod, M3) → Option B**: prod drops the bind-mount; Cloud Build on push → AR → deploy is the prod model. cloud-test can adopt B for parity later but keeps C's fast restart loop for iteration (feature-flag-preserves-both, not A/B-then-retire).
- **ENABLING INFRA → Option A foundation**: a real GitHub remote (replacing the bundle-file origin) is the prerequisite for B's CI trigger AND D. **This is a Rick/infra decision** (where the repo lives, private GitHub org, deploy-key vs PAT) — flagged in §6, not assumed.

**Why C first, not B:** cloud-test's whole point is fast iteration; the bind-mount was deliberately chosen for it. B's per-change full image build (~minutes, as the 1.2.0 build took today) would wreck that loop. C automates the fast path and *correctly* delegates the deps case to the image path — covering both axes without forcing every code change through a slow rebuild.

## 4. Mechanism design — `deploy-cloud-test.sh`

```
deploy-cloud-test.sh [--ref <git-ref>=HEAD] [--deps] [--dry-run]
  1. resolve SHA = git rev-parse <ref>;  refuse if working tree dirty for that path (commit first) unless --allow-dirty
  2. read VM /mnt/lupin-data/lupin/.deployed-ref (prev SHA)
  3. AXIS DETECT: git diff --quiet prev SHA..SHA -- pyproject.toml uv.lock
        clean  → AXIS A (code): git archive SHA src/ | ssh 'extract to /tmp → sudo cp → chown 1001:1001 → docker restart lupin-rest-cloud-test'
        differ → AXIS B (deps): require --deps; run cloud-run-build.sh <newtag> → push → ssh pull+force-recreate (today's proven path)
  4. write .deployed-ref (SHA, ts, axis); keep prior src/ as .bak-<ts>
  5. health-gate: poll lupin-rest health → healthy or roll back (.bak swap)
```
Bind-mount + UID + config-block facts confirmed from `docker-compose.cloud-test.yml` (mount `:85`, `LUPIN_CONFIG_MGR_CLI_ARGS … config_block_id=Lupin:+Testing-GCS`, keys `:ro`).

## 5. Smoke / E2E proof (I own this — automated, not manual)

- **Axis-A E2E**: commit a marker (`src/conf/.deploy-probe`) → `deploy-cloud-test.sh` → assert (a) marker present in-container (`docker exec cat`), (b) container restarted (uptime reset), (c) `.deployed-ref` SHA matches. 
- **Axis-B E2E**: bump a harmless dep → `--deps` → assert image tag advanced + new dep importable in-container + `.deployed-ref` axis=deps.
- **Rollback test**: deploy a deliberately-broken ref → health-gate fails → assert auto `.bak` swap restores the prior healthy `src/`.
- Venue: the cloud-test VM (real infra); dry-run first on `:7999`-equivalent logic where possible.
