## Detailed Failure Analysis

### 🟢 Failure #1: test_failed_login_rate_limiting (SIMPLE FIX)

#### Error Output
```python
AssertionError: assert ('Invalid credentials' in 'Invalid email or password' or 'Incorrect' in 'Invalid email or password')
```

#### Root Cause
**Test assertion mismatch** - Test expects error message containing `"Invalid credentials"` OR `"Incorrect"`, but actual implementation returns `"Invalid email or password"`.

#### Evidence
**Source**: `src/cosa/rest/user_service.py:133, 141`
```python
# Line 133: User not found
if not row:
    return False, "Invalid email or password", None

# Line 141: Password verification failed
if not verify_password( password, row["password_hash"] ):
    return False, "Invalid email or password", None
```

**Test**: `src/tests/integration/test_auth_integration.py:192`
```python
assert "Invalid credentials" in data["detail"] or "Incorrect" in data["detail"]
```

#### Analysis
This is a **test spec issue**, not a code bug. The implementation correctly uses security-conscious error message `"Invalid email or password"` to prevent user enumeration attacks (same message for both "user not found" and "wrong password").

#### Fix Options
| Option | Change | Pros | Cons |
|--------|--------|------|------|
| **A** (Recommended) | Update test assertion | Matches actual implementation, preserves security | None |
| **B** | Change error message in code | Satisfies original test | Weakens security message consistency |

#### Recommended Fix
**Option A**: Update test to match actual implementation

**File**: `src/tests/integration/test_auth_integration.py`
**Line**: 192

**Change**:
```python
# OLD
assert "Invalid credentials" in data["detail"] or "Incorrect" in data["detail"]

# NEW
assert "Invalid email or password" in data["detail"]
```

**Impact**: Test now correctly validates security-conscious error message

### 🔴 Failure #2: test_password_change_flow (COMPLEX - UTF-8 Decoding)

#### Error Output
```python
AssertionError: Password change failed: 'utf-8' codec can't decode byte 0x9a in position 0: invalid start byte
assert 200 == 401
```

#### Root Cause
**Binary/text encoding mismatch** - Byte `0x9a` at position 0 indicates **binary data being interpreted as UTF-8 text**.

#### Critical Evidence
**Error context**: Exception in `update_user_password()` at user_service.py:362-364
```python
except Exception as e:
    conn.rollback()
    return False, f"Password update failed: {e}"  # ← UTF-8 decode error caught here
```

**Byte Analysis**:
- `0x9a` = Non-ASCII byte (not valid UTF-8 start byte)
- Position 0 = First character of retrieved data
- This suggests **database returning bytes instead of string**

#### Hypothesis Chain

**Hypothesis 1**: Database schema uses BLOB instead of TEXT
- SQLite BLOB columns return `bytes` objects
- TEXT columns return `str` objects
- Passlib expects string hashes (base64-encoded ASCII)

**Hypothesis 2**: Password hash corruption
- Bcrypt hashes should be ASCII (base64 format like `$2b$12$...`)
- If stored as BLOB, SQLite might mangle encoding
- Retrieval as bytes causes passlib verification to fail

**Hypothesis 3**: Row cursor encoding issue
- SQLite `cursor.fetchone()` returns dict-like Row object
- Row encoding depends on column type
- TEXT → str, BLOB → bytes

#### Investigation Required
1. **Check schema**: `auth_database.py` - Is `password_hash` TEXT or BLOB?
2. **Verify hash format**: What does `row["password_hash"]` actually return? (str vs bytes)
3. **Test passlib**: Can `verify_password()` handle bytes input?
4. **Database inspection**: Check actual stored hash format

#### Debugging Steps
```python
# Add to update_user_password() before line 343
print( f"DEBUG: password_hash type: {type(row['password_hash'])}" )
print( f"DEBUG: password_hash repr: {repr(row['password_hash'][:20])}" )
```

#### Potential Fixes

**Fix A**: Ensure schema uses TEXT
```python
# auth_database.py - Verify password_hash column
CREATE TABLE users (
    ...
    password_hash TEXT NOT NULL,  -- ← Must be TEXT, not BLOB
    ...
)
```

**Fix B**: Add explicit decoding
```python
# user_service.py:343 - If database returns bytes
password_hash = row["password_hash"]
if isinstance( password_hash, bytes ):
    password_hash = password_hash.decode( 'utf-8' )

if not verify_password( old_password, password_hash ):
    return False, "Current password is incorrect"
```

**Fix C**: CryptContext encoding configuration
```python
# password_service.py - Ensure passlib handles encoding
pwd_context = CryptContext(
    schemes=["bcrypt"],
    deprecated="auto",
    bcrypt__rounds=12,
    encoding="utf-8"  # ← Explicit encoding
)
```

#### Risk Assessment
- **Severity**: HIGH - Blocks password changes entirely
- **Scope**: Affects all password update operations
- **Data Integrity**: May indicate schema design flaw
- **Related Bug**: Likely connected to Failure #4 (WebSocket UTF-8 error)

### 🟢 Failure #3: test_email_verification_flow (SIMPLE FIX)

#### Error Output
```python
AssertionError: Verification request failed: {"detail":"Request verification failed: 'id'"}
assert 500 == 200
```

#### Root Cause
**KeyError**: Field name mismatch - Code expects `user["id"]` but dictionary has `user["user_id"]`

#### Evidence
**Error location**: `src/cosa/rest/routers/auth.py:690`
```python
# Line 690 - Inside request_verification()
success, message, token = generate_verification_token( user["id"] )  # ❌ KeyError: 'id'
```

**User dict structure**: `src/cosa/rest/auth.py:156-167`
The `verify_jwt_token()` function returns:
```python
return {
    "uid": user_data["id"],           # ✓ Exists
    "email": user_data["email"],
    "email_verified": user_data["email_verified"],
    "name": user_data["email"].split("@")[0],
    "roles": user_data["roles"],
    "picture": None,
    "iss": "lupin-jwt",
    "aud": "lupin-api",
    "auth_time": payload.get("iat"),
    "user_id": user_data["id"]        # ✓ Exists
    # ❌ NO "id" field!
}
```

#### Analysis
The `get_current_user_dependency()` middleware returns a user dict with `uid` and `user_id`, **but not `id`**.

This follows JWT standards:
- `"sub"` (subject) in JWT payload = user ID
- Mapped to `"user_id"` in user dict
- Also provided as `"uid"` for Firebase compatibility

#### Fix
**File**: `src/cosa/rest/routers/auth.py`
**Line**: 690

**Change**:
```python
# OLD (line 690)
success, message, token = generate_verification_token( user["id"] )

# NEW
success, message, token = generate_verification_token( user["user_id"] )
```

#### Additional Checks
Search for other occurrences of `user["id"]` that should be `user["user_id"]`:

**Affected endpoints**:
- `/auth/request-verification` (line 690)
- Any other code using `Depends(get_current_user_dependency)`

#### Impact
- **Severity**: MEDIUM - Breaks email verification flow
- **Scope**: All endpoints using `get_current_user_dependency` with `user["id"]`
- **Fix Time**: 5 minutes (simple find/replace)

### 🔴 Failure #4: test_websocket_jwt_authentication (COMPLEX - Known Issue)

#### Error Output
```python
websockets.exceptions.InvalidStatus: server rejected WebSocket connection: HTTP 403
```

#### Context
This is a **known deferred issue** documented in history.md (2025.10.01):

> **Known Issue (Deferred)**:
> Fresh Queue WebSocket authentication failing with UTF-8 decoding error:
> `'utf-8' codec can't decode byte 0x9a in position 0: invalid start byte`
> - **Scope**: Queue WebSocket only (Audio WebSocket works fine)
> - **Type**: Token validation UTF-8 decoding issue (different auth handler than HTTP)
> - **Impact**: Queue UI can't connect, but separate from HTTP auth system
> - **Next session**: Investigate WebSocket-specific token handling

#### Root Cause Hypothesis
WebSocket authentication uses **different validation logic** than HTTP endpoints.

**Evidence**:
- HTTP endpoints: Use `auth_middleware.py` → `verify_token()` (works fine)
- WebSocket endpoint: Uses WebSocket-specific auth handler (fails with 403)
- Different error from history (403 vs UTF-8 decode) suggests **connection rejection before token validation**

#### Analysis

**Hypothesis A**: WebSocket expects mock tokens, not JWT
- WebSocket handler might still use old mock auth
- JWT tokens rejected as "invalid format"
- Returns 403 Forbidden

**Hypothesis B**: WebSocket handshake missing Authorization header
- Test sends JWT token after connection
- WebSocket expects token in connection URL or headers
- Handshake fails before auth_request message

**Hypothesis C**: WebSocket auth middleware mismatch
- WebSocket uses different auth middleware than HTTP
- Middleware incompatible with JWT format
- Rejects connection before validating token

#### Investigation Required

1. **Find WebSocket connection handler**
   - Likely in `src/fastapi_app/main.py` or WebSocket router
   - Check auth decorator/middleware on `/ws/queue/{session_id}`

2. **Check WebSocket auth flow**
   - Does it validate token on connection?
   - Or does it wait for `auth_request` message?
   - What token format does it expect?

3. **Compare with HTTP auth**
   - HTTP: Uses `verify_jwt_token()` from `auth.py`
   - WebSocket: Uses ??? (to be determined)

4. **Review test expectations**
   ```python
   # test_auth_integration.py:555-570
   async with websockets.connect( ws_url ) as websocket:
       # Send auth_request
       await websocket.send( json.dumps({
           "event": "auth_request",
           "token": access_token
       }))
   ```
   Test expects to:
   1. Connect to WebSocket (failing here with 403)
   2. Send auth_request message
   3. Receive auth_success response

#### Potential Fixes

**Fix A**: Update WebSocket to accept JWT tokens
```python
# WebSocket handler - Use same auth as HTTP
from cosa.rest.auth import verify_jwt_token

@app.websocket("/ws/queue/{session_id}")
async def websocket_endpoint( websocket: WebSocket, session_id: str ):
    await websocket.accept()

    # Wait for auth_request
    message = await websocket.receive_json()
    if message.get("event") == "auth_request":
        token = message.get("token")
        user = await verify_jwt_token( token )  # ← Use JWT validation
        # Continue if valid...
```

**Fix B**: Add Authorization header support
```python
# Allow JWT in WebSocket upgrade headers
@app.websocket("/ws/queue/{session_id}")
async def websocket_endpoint(
    websocket: WebSocket,
    session_id: str,
    authorization: Optional[str] = Header( None )
):
    # Validate token before accepting connection
    if authorization:
        token = authorization.replace("Bearer ", "")
        user = await verify_jwt_token( token )

    await websocket.accept()
    # ...
```

**Fix C**: Dual auth mode (JWT + mock)
```python
# Support both token types during migration
try:
    user = await verify_jwt_token( token )
except:
    try:
        user = await verify_mock_token( token )
    except:
        raise HTTPException( 403, "Invalid token" )
```

#### Risk Assessment
- **Severity**: HIGH - Breaks WebSocket functionality entirely
- **Scope**: All WebSocket connections using JWT auth
- **Complexity**: HIGH - Requires understanding WebSocket auth flow
- **Related**: Possibly connected to UTF-8 error in Failure #2
