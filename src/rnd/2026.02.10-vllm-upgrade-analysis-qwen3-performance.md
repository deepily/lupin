# Research: Should We Upgrade vLLM 0.8.5 → 0.9.2 for Qwen3-4B Performance?

**Project**: [LUPIN] PEFT Validation Pipeline — vLLM Upgrade Analysis
**Date**: 2026-02-10
**Status**: ANALYSIS COMPLETE — Recommendation: Stay on 0.8.5
**Prior Work**: [Root Cause Analysis](2026.02.10-qwen3-vllm-inference-slowdown-root-cause.md) | [PEFT Part 2](2026.02.07-peft-trainer-optimization-plan-part-2.md)

## The Paradox

Qwen3-4B-Base (4B params, 4-bit GPTQ) runs at **353.4 ms/item** on vLLM 0.8.5.
Ministral-8B (8B params, 4-bit GPTQ) ran at **~210 ms/item** on the same vLLM 0.8.5.

A model with **half the parameters** is **1.7x slower**. That shouldn't happen.

---

## Timeline of What Actually Happened

| Date | vLLM | Qwen3-4B ms/item | What Changed |
|------|------|-------------------|-------------|
| 2026-02-09 | 0.8.2 | 7,392 (PRE), 5,008 (POST) | No native Qwen3 → Transformers fallback |
| 2026-02-10 AM | 0.8.5 | 549 (PRE), 481 (POST), 353 (4-bit) | Upgrade → native `qwen3.py` present |
| Ministral baseline | 0.8.5 | — / — / ~210 (4-bit) | Mature, heavily optimized Mistral kernel |

**The 0.8.2 → 0.8.5 upgrade gave ~15x** because 0.8.2 had ZERO native Qwen3 support (no `qwen3.py` file existed) and fell back to unoptimized HuggingFace Transformers. The 0.8.5 install has both `qwen3.py` and `qwen3_moe.py` — confirmed on disk.

## Why Qwen3-4B Is Still 1.7x Slower Than Ministral-8B at 4-bit

Three compounding factors explain the remaining gap:

### 1. Kernel Maturity Gap (Primary Factor)

Mistral/Ministral models have been in vLLM since **v0.2.x** (2023). They have had **2+ years** of kernel optimization:
- Custom CUDA graph profiles tuned for Mistral attention patterns
- Marlin GPTQ kernels specifically validated against Mistral architectures
- Flash attention paths battle-tested across thousands of production deployments

Qwen3 native support landed in **v0.8.4** (2025) — less than a year of optimization. The community data confirms this:

| Issue | Problem | Version |
|-------|---------|---------|
| [#17788](https://github.com/vllm-project/vllm/issues/17788) | Qwen3-32B FP8 only 1.35x speedup (expected 1.6x) | 0.8.5 |
| [#18195](https://github.com/vllm-project/vllm/issues/18195) | Qwen3-32B-AWQ **slower** than FP16 baseline | 0.8.5-0.9.x |
| [#29869](https://github.com/vllm-project/vllm/issues/29869) | Qwen3-VL 3x slower than SGLang | 0.10.x |

### 2. GPTQ Kernel Selection (Likely Contributing)

Community benchmarks on H200 (Qwen2.5-32B, JarvisLabs guide):

| GPTQ Mode | Throughput | vs FP16 Baseline |
|-----------|-----------|-----------------|
| Regular GPTQ | 276.6 tok/s | **0.6x (40% slower)** |
| **Marlin-GPTQ** | 712.45 tok/s | **1.55x faster** |

A 2.6x gap between regular GPTQ and Marlin-GPTQ kernels. If vLLM auto-selects the wrong kernel for Qwen3's GPTQ format (especially AutoRound GPTQ), it could account for much of the 1.7x gap vs Ministral (which likely gets the optimized Marlin path).

### 3. Small Model Overhead (Minor Factor)

vLLM is architecturally optimized for throughput on large models (70B+). For small models (4B), fixed per-request overhead (scheduling, memory management, CUDA graph capture) becomes a larger fraction of total time. This affects Qwen3-4B more than Ministral-8B simply because there's less computation to amortize the overhead against.

## Would Upgrading to vLLM 0.9.2 Help?

### Short Answer: **No. It would likely make things worse.**

### Evidence

#### Regression 1: V1 Engine Default Hurts Small Models

v0.9.x defaults to the V1 engine (V0 is frozen). Community benchmarks on Qwen2.5-1.5B-Instruct:

| Metric | V0 (0.8.x) | V1 (0.9.0) | Change |
|--------|-----------|-----------|--------|
| Throughput (req/s) | 9.61 | 6.88 | **-28%** |
| Token throughput | 1,178 tok/s | 843 tok/s | **-28%** |
| Mean TTFT | 10,198 ms | 13,147 ms | **+29% worse** |

Source: [GitHub #19499](https://github.com/vllm-project/vllm/issues/19499)

#### Regression 2: AllReduce Kernel Overhead

Single-request latency on H100 (v0.9.1):
- V0 engine AllReduce: 66.67 ms
- V1 engine AllReduce: **637.13 ms** (9.5x overhead)

Source: [GitHub #21852](https://github.com/vllm-project/vllm/issues/21852)

#### Regression 3: Qwen3-Specific TTFT Collapse

Qwen3-14B-AWQ on single A100 (v0.9.1):

| Concurrency | TTFT |
|------------|------|
| 1 | 3,345 ms |
| 5 | 5,091 ms |
| 25 | **34,952 ms** |

Source: [GitHub #20469](https://github.com/vllm-project/vllm/issues/20469) — issue remains open.

#### Regression 4: General Latency

Whisper large-v3-turbo on 2x A100: 92ms (v0.7.3) → 105ms (v0.9.0), +14% regression. Closed as "not planned."

### What 0.9.x Does Add (Not Relevant to Your Workload)

- Full CUDA graph support for FA3/FlashMLA — helps large models, multi-GPU
- AutoRound quantization format support — you already use AutoRound GPTQ, which works in 0.8.5
- Blackwell GPU support — not your hardware
- FP4/MXFP4/NVFP4 quantization — you use GPTQ 4-bit, not these formats
- MoE kernel tuning for DeepSeek/Qwen3-235B — irrelevant for a 4B dense model

---

## Empirical Basis for the Claim

**Is there documented evidence that 0.8.5 → 0.9.2 improves inference speed?**

**For Qwen3 on single GPU, single-request latency: No.**

Every community benchmark I found shows either:
1. **Neutral** (no measurable change) for established model architectures
2. **Regression** for small models due to V1 engine overhead
3. **Regression** for Qwen3 specifically under various conditions

The 0.9.x improvements target:
- Multi-GPU throughput (tensor/expert parallelism)
- Large batch concurrent serving (high-concurrency scenarios)
- New hardware (Blackwell, AMD ROCm)
- New quantization formats (FP4, NVFP4)

None of these match your workload: **single GPU, sequential validation, one request at a time, GPTQ 4-bit, small model.**

## What WOULD Actually Help Close the Qwen3 vs Ministral Gap

### Option A: Force Marlin GPTQ Kernel (Quick Win — Test First)

Check if vLLM is using the optimized Marlin kernel for your GPTQ model:
```bash
# In vLLM server logs, look for:
# "Loading model weights with Marlin" → GOOD
# "Loading model weights with GPTQ" → SUBOPTIMAL (2.6x slower)
```

If Marlin isn't being selected, the AutoRound GPTQ format might not be triggering it. The community benchmark shows Marlin-GPTQ at 1.55x vs FP16 baseline, while regular GPTQ is 0.6x — a **2.6x gap** from kernel selection alone.

### Option B: Optimization Flags for vLLM 0.8.5

```bash
# Disable chunked prefill (documented Qwen3 perf issue)
--no-enable-chunked-prefill

# Explicit CUDA graph sizes for small-batch inference
--cuda-graph-sizes 1,2,4,8

# Reduce CPU overhead (container deployments)
export OMP_NUM_THREADS=1
```

### Option C: Accept the Gap (Pragmatic)

353 ms/item vs 210 ms/item is a **143 ms difference per validation item**. Over 34 items that's ~4.9 seconds total. For a pipeline that takes 15+ minutes, this is noise. The real question is whether Qwen3-4B can match Ministral-8B's accuracy — this will be answered by the full training run (100% dataset) scheduled for this evening. The 20.6% exact match in the latest results was from a **1% smoke test** run to validate the end-to-end pipeline, not a representative accuracy measure.

### Option D: Wait for vLLM Qwen3 Kernel Maturation

SharedFusedMoE for Qwen3 arrived in v0.15.0. Dense Qwen3 optimizations continue to ship. The gap will narrow over time, but waiting for v0.12+ or v0.15+ is a different proposition than upgrading to 0.9.2.

---

## Recommendation

**Do NOT upgrade from 0.8.5 to 0.9.2.** The empirical evidence points to regressions for your specific workload (small model, single GPU, sequential inference, GPTQ quantization).

**Instead:**
1. Test whether Marlin kernel is being used — if not, this could close most of the gap
2. Try `--no-enable-chunked-prefill` and `OMP_NUM_THREADS=1`
3. Run full training set (100%) this evening and compare Qwen3-4B accuracy vs Ministral-8B (the 20.6% was a 1% smoke test, not representative)
4. Revisit the latency gap after accuracy results are in — if Qwen3-4B matches Ministral accuracy, the 143 ms/item gap is acceptable noise
