# Research: Qwen3-4B-Base Inference Slowdown — Root Cause Analysis

**Project**: [LUPIN] PEFT Validation Pipeline Performance
**Date**: 2026-02-10
**Status**: ROOT CAUSE IDENTIFIED — Fix: Upgrade vLLM

---

## Context

Qwen3-4B-Base (4B params) takes **~7,392 ms/item** during PEFT validation, while Ministral-8B (8B params, 2x larger) takes **~368.7 ms/item** — a **20x slowdown** that is architecturally impossible since Qwen3 is smaller in every compute dimension.

---

## ROOT CAUSE: vLLM 0.8.2 Has No Native Qwen3 Support

**Confirmed**: Our vLLM installation is **v0.8.2**.

```
/projects/vllm-pip/.venv/.../vllm/_version.py → __version__ = '0.8.2'
```

**Evidence**: `vllm/model_executor/models/` directory contains:
- `qwen2.py` (Qwen2 native support)
- **Zero Qwen3 files** — no `qwen3.py` exists

Meanwhile `MistralForCausalLM` (used by Ministral-8B) has full native support with CUDA graphs, flash attention, continuous batching, etc.

**What happens**: When vLLM encounters `Qwen3ForCausalLM` (from the model's `config.json`), it falls back to the **generic HuggingFace Transformers implementation**, which lacks all vLLM performance optimizations. This single factor explains the entire 15-20x gap.

**Community confirmation**: [vLLM Issue #17630](https://github.com/vllm-project/vllm/issues/17630) documents exactly this — "Qwen3ForCausalLM has no vLLM implementation, falling back to Transformers implementation."

Native `Qwen3ForCausalLM` support was added in **vLLM 0.8.4**.

## Architecture Comparison (Rules Out Model Design)

| Parameter | Qwen3-4B-Base | Ministral-8B |
|-----------|:---:|:---:|
| num_attention_heads | 32 | 32 |
| num_key_value_heads | 8 (GQA 4:1) | 8 (GQA 4:1) |
| num_hidden_layers | 36 | 36 |
| hidden_size | **2560** | **4096** |
| intermediate_size | **9728** | **12288** |

Qwen3-4B is **smaller** in every compute-heavy dimension. It should be **faster**, not slower. The gap is 100% software, not architecture.

---

## Thinking Mode — NOT the Issue

Qwen3 instruct models have a "thinking mode" (`<think>...</think>` blocks). However:
- We use **Qwen3-4B-Base** (not instruct) — no thinking template
- We hit the `/v1/completions` endpoint, not `/v1/chat/completions`
- No `enable_thinking` parameter is involved

---

## Fix: Upgrade vLLM to >= 0.8.5

### Step 1: Upgrade vLLM

```bash
cd /mnt/DATA01/include/www.deepily.ai/projects/vllm-pip
source .venv/bin/activate
pip install --upgrade vllm
```

**Risk**: The `transformers` library was previously downgraded from 5.1.0 to 4.57.6 for vLLM 0.8.2 compatibility. The new vLLM version may require a different `transformers` version — check the dependency resolution.

### Step 2: Verify native support post-upgrade

After upgrading, start the vLLM server for Qwen3-4B-Base and check the logs for:
- **GOOD**: No warnings about Transformers fallback
- **BAD**: "falling back to Transformers implementation" → upgrade didn't work

### Step 3: Re-run PEFT test pipeline

```bash
src/scripts/run-agentic-intent-training.sh --test --llm qwen3-4b --quantize-bits both
```

**Expected results with native support**:
- ms/item should drop from ~7,400 to ~200-400 (comparable to or faster than Ministral-8B)
- 4-bit quantization should show further speedup (1.5-2x)

### Step 4: Post-upgrade optimization flags (if still slow)

Community-reported vLLM flags that help Qwen3 specifically:

```bash
# Disable chunked prefill (known Qwen3 issue)
--no-enable-chunked-prefill

# Explicit CUDA graph sizes
--cuda-graph-sizes 1,2,4,8

# Environment variable for multiprocessing overhead
export VLLM_ENABLE_V1_MULTIPROCESSING=0
```

## Summary

The 20x slowdown is **entirely** caused by vLLM 0.8.2 lacking native Qwen3 support, forcing a fallback to the unoptimized HuggingFace Transformers engine. Upgrading vLLM to >= 0.8.5 should resolve the issue completely. No code changes are needed in our codebase — only the vLLM pip package upgrade.
