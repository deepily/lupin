## COSA Agent Architecture

### Core Design Principles

1. **Abstract Base Class Pattern**: `AgentBase` defines contract via ABC
2. **Three-Phase Pipeline**: prompt → code → format
3. **State Machine**: Tracks execution state via constants
4. **LLM Vendor Agnostic**: `LlmClientFactory` supports multiple vendors
5. **XML-Based Responses**: Structured output parsing
6. **Serialization**: JSON state persistence for replay

### Execution Pipeline

```
Input: question, routing_command
         │
         ▼
┌─────────────────────────────────────┐
│ Phase 1: run_prompt()               │
│                                     │
│ Load template → LLM call → XML parse│
│                                     │
│ Output: prompt_response_dict        │
│   - thoughts                        │
│   - code                            │
│   - example                         │
│   - explanation                     │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Phase 2: run_code()                 │
│                                     │
│ Execute Python → Handle errors →    │
│ Auto-debug if needed                │
│                                     │
│ Output: code_response_dict          │
│   - return_code                     │
│   - output                          │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Phase 3: run_formatter()            │
│                                     │
│ Raw output → LLM → Natural language │
│                                     │
│ Output: answer_conversational       │
└─────────────────────────────────────┘
```

### Routing System

```python
MODE_TO_AGENT = {
    "math"        : MathAgent,
    "calendar"    : CalendaringAgent,
    "weather"     : WeatherAgent,
    "receptionist": ReceptionistAgent,
    "todo"        : TodoListAgent,
    "datetime"    : DateAndTimeAgent,
}

# Two routing paths:
# 1. User Mode (direct): user_mode="math" → MathAgent
# 2. LLM Router (dynamic): LLM parses question → selects agent
```

### Key Characteristics

| Aspect | COSA Agents |
|--------|-------------|
| **Execution Model** | Synchronous, single-turn |
| **LLM Integration** | Multi-vendor via factory |
| **Code Execution** | Local Python runtime |
| **Debugging** | IterativeDebuggingAgent (self-healing) |
| **Tool System** | None (generates code instead) |
| **State Persistence** | JSON serialization |
| **User Interaction** | None during execution |

## Option A/B Dispatcher Architecture

### Core Design Principles

1. **Concrete Class**: No abstract base, single implementation
2. **Two Execution Modes**: Bounded (Option A) vs Interactive (Option B)
3. **Streaming Output**: Async callbacks for real-time updates
4. **Claude-Only**: Designed specifically for Claude Code CLI/SDK
5. **MCP Tool Integration**: Voice I/O via cosa-voice server
6. **Session Management**: Active session tracking for Option B

### Option A: Bounded Task Execution

```
Task → subprocess → Claude Code CLI → stream-json → Result
                          │
                    MCP tools for
                    clarification
```

**Characteristics**:
- Fire-and-forget subprocess
- Natural completion endpoint
- No user-initiated input (only via MCP tools)
- Best for: CI/CD, batch processing, scheduled jobs

### Option B: Interactive Session

```
Task → SDK Client → Persistent Session → Streaming Messages
           │               │
      inject() ────────────┤
           │               │
      interrupt() ─────────┤
           │               │
      end_session() ───────┘
```

**Characteristics**:
- Bidirectional control
- Message injection with context preservation
- Session interruption support
- Best for: Pair programming, exploratory work

### Key Characteristics

| Aspect | Option A/B Dispatcher |
|--------|----------------------|
| **Execution Model** | Async, multi-turn conversations |
| **LLM Integration** | Claude-only (CLI/SDK) |
| **Code Execution** | Delegated to Claude Code |
| **Debugging** | Claude handles its own debugging |
| **Tool System** | MCP tools (voice, files, bash) |
| **State Persistence** | MessageHistory (Option B only) |
| **User Interaction** | Via MCP tools during execution |

## Commonalities

### 1. Task/Work Unit Pattern

Both systems define a "unit of work" with similar attributes:

| COSA Agent | Option A/B | Commonality |
|------------|------------|-------------|
| `question` | `Task.prompt` | Input text describing the work |
| `routing_command` | `Task.type` | Classification/routing info |
| `push_counter` | `Task.id` | Unique identifier |
| `execution_state` | `session["running"]` | Lifecycle tracking |

### 2. State Tracking

Both track execution state:

```python
# COSA
STATE_INITIALIZING = "initializing"
STATE_WAITING_TO_RUN = "waiting to run"
STATE_RUNNING = "running"
STATE_STOPPED_DONE = "stopped done"
STATE_STOPPED_ERROR = "stopped error"

# Option A/B
active_sessions[task_id] = {
    "running": True,  # or False
    "client": ...,
    "pending_messages": ...,
    "history": ...
}
```

### 3. Result Capture

Both capture structured results:

```python
# COSA
prompt_response_dict = {...}      # LLM output
code_response_dict = {...}        # Code execution
answer_conversational = "..."     # Final answer

# Option A/B
TaskResult(
    success=True,
    result="...",
    cost_usd=0.15,
    duration_ms=8600
)
```

### 4. Serialization/Context Preservation

Both have mechanisms for state preservation:

```python
# COSA
agent.serialize_to_json()  # Save to file
agent.restore_from_serialized_state()  # Restore

# Option B
history.add_assistant_text(text)
history.add_user_message(message)
context = history.get_context_prompt()  # For injection
```

### 5. Message/Callback Patterns

Both support output streaming/callbacks:

```python
# COSA (via serialization to log files)
topic = config_mgr.get(f"serialization topic for {routing_command}")
# Logs to: {topic}-{question}-{timestamp}.json

# Option A/B
def on_message(task_id: str, data: Any):
    # Real-time streaming callback
    websocket.broadcast(data)
```

## Key Differences

### 1. Execution Model

| Aspect | COSA | Option A/B |
|--------|------|------------|
| **Paradigm** | Synchronous, single-turn | Async, multi-turn |
| **Control Flow** | Sequential pipeline | Event-driven streaming |
| **User Input** | Before execution only | During execution (MCP) |
| **Duration** | Seconds to minutes | Minutes to hours |

### 2. LLM Integration

| Aspect | COSA | Option A/B |
|--------|------|------------|
| **Vendor Lock-in** | No (multi-vendor factory) | Yes (Claude only) |
| **Model Selection** | Per-agent configuration | CLI/SDK determines |
| **Prompt Templates** | External files | Inline prompts |
| **Response Format** | Structured XML | Natural + tool calls |

### 3. Code Execution

| Aspect | COSA | Option A/B |
|--------|------|------------|
| **Location** | Local Python runtime | Claude Code sandbox |
| **Isolation** | RunnableCode class | Claude's permission model |
| **Debugging** | IterativeDebuggingAgent | Claude self-corrects |
| **Side Effects** | Controlled via code | Via Bash/Write tools |

### 4. Tool System

| Aspect | COSA | Option A/B |
|--------|------|------------|
| **Paradigm** | Code generation | Tool invocation |
| **Available Tools** | None (generates code) | MCP + Read/Write/Bash |
| **Extensibility** | Add new agents | Add MCP servers |
| **User Interaction** | Post-execution | Via MCP tools |

### 5. Abstraction Level

| Aspect | COSA | Option A/B |
|--------|------|------------|
| **Base Class** | Abstract (AgentBase) | Concrete only |
| **Inheritance** | Required for new agents | Not applicable |
| **Interface** | Defined by abstract methods | Implicit (dispatch/inject/etc.) |
| **Extension** | Subclass AgentBase | N/A (single dispatcher) |

## Decision Framework

### Question 1: Should they share a base class?

**Arguments FOR unification:**
- Common patterns (task, state, result) suggest shared interface
- Could reduce code duplication
- Unified testing and tooling

**Arguments AGAINST unification:**
- Fundamentally different execution models (sync vs async)
- Different LLM integration strategies
- Different code execution paradigms
- Would create artificial coupling

**Verdict**: **No shared base class** - execution models are too different

### Question 2: Should they share interfaces/protocols?

**Arguments FOR shared interfaces:**
- TaskInput protocol could unify task definition
- TaskResult protocol could standardize output
- StateTracking protocol could share lifecycle patterns

**Arguments AGAINST:**
- Python's duck typing makes protocols optional
- Adds complexity without clear benefit
- Each system has domain-specific needs

**Verdict**: **Consider lightweight protocols** for TaskResult-like structures

### Question 3: Should they share behavioral contracts?

**Yes - shared contracts make sense for:**
- Logging/observability patterns
- Error handling conventions
- Result reporting format
- TodoWrite integration

**Verdict**: **Document shared behavioral contracts** without code coupling

## Recommendations

### Option A: Parallel with Shared Contracts (Recommended)

Keep COSA agents and Option A/B dispatcher separate, but document shared behavioral contracts:

```
┌─────────────────────────────────────────────────────────────┐
│                   Shared Contracts (Documentation)          │
│                                                             │
│  - TaskInput: prompt, type/routing, id, timeout             │
│  - TaskResult: success, result, cost, duration, error       │
│  - StateLifecycle: init → running → complete/error          │
│  - Observability: structured logging, TodoWrite integration │
│  - Error Handling: exception → result with error message    │
└─────────────────────────────────────────────────────────────┘
                    │                       │
         ┌──────────┴──────────┐   ┌───────┴───────┐
         │                     │   │               │
    ┌────▼────┐           ┌────▼────┐         ┌────▼────┐
    │ COSA    │           │Option A │         │Option B │
    │ Agents  │           │Bounded  │         │Interact │
    │         │           │         │         │         │
    │ Local   │           │ Claude  │         │ Claude  │
    │ code    │           │ CLI     │         │ SDK     │
    │ exec    │           │ subproc │         │ session │
    └─────────┘           └─────────┘         └─────────┘
```

**Rationale:**
- Preserves each system's strengths
- Avoids artificial coupling
- Enables independent evolution
- Documents patterns for future systems

### Option B: Unified Base (Not Recommended)

Create `AgentInterface` or `WorkerProtocol`:

```python
# NOT RECOMMENDED - over-engineering
class WorkerProtocol(Protocol):
    def execute(self, task: TaskInput) -> TaskResult: ...
    def get_state(self) -> ExecutionState: ...
    def serialize(self) -> dict: ...
```

**Issues:**
- Forces sync/async abstraction complexity
- Requires significant refactoring
- Benefits don't justify costs
- Python's duck typing makes this unnecessary

### Option C: Hybrid (Consider for Future)

If future needs require unified dispatching:

```python
# FUTURE CONSIDERATION
class UnifiedDispatcher:
    def dispatch(self, task: Task) -> TaskResult:
        if task.type == TaskType.COSA_AGENT:
            return self._run_cosa_agent(task)

            return self._run_bounded(task)

            return self._run_interactive(task)

**When to consider:**
- Need unified API for all agent types
- Building higher-level orchestration
- Want single entry point for callers

## Integration Use Cases

This section documents specific integration patterns between COSA agents and the Claude Code dispatcher.

### Use Case 1: Code Generation Failure Escalation

#### Current Flow (Fails Hard)

```
Question → Local LLM (Phi-4/Ministral) → run_code()
                                              ↓
                                   [If fails] IterativeDebuggingAgent (tries multiple LLMs)
                                              ↓
                                   [If still fails] raise CodeGenerationFailedException
                                              ↓
                                         ❌ Job moves to dead_queue
```

**Problem**: When local LLMs exhaust all debugging attempts, the job fails permanently with no recovery path.

#### Proposed Flow (Escalates to Claude)

```
Question → Local LLM (Phi-4/Ministral) → run_code()
                                              ↓
                                   [If fails] IterativeDebuggingAgent
                                              ↓
                                   [If still fails] CATCH exception
                                              ↓
                                   ClaudeCodeDispatcher.dispatch(Task)
                                   - Option A: Simple code fix (bounded)
                                   - Option B: Complex debugging (interactive)
                                              ↓
                                   [If Claude succeeds] Return result to AgentBase flow
                                   [If Claude fails] THEN raise CodeGenerationFailedException
```

**Benefit**: Claude Code serves as a "rescue tier" before permanent failure.

#### Hook Point in agent_base.py

**Location**: Lines 420-428 (where CodeGenerationFailedException is raised)

```python
# CURRENT CODE (agent_base.py:420-428):
raise CodeGenerationFailedException(
    f"Code generation failed: Unable to fix code errors after exhausting "
    f"all debugging models. {error_details}"
)

# PROPOSED ENHANCEMENT:
if self.escalate_to_claude:
    result = await self._escalate_to_claude_code(
        original_question=self.last_question_asked,
        failed_code=code,
        error_details=error_details
    )
    if result.success:
        self.code_response_dict = result.code_response
        return self.code_response_dict
    # Fall through to raise exception if Claude also failed

raise CodeGenerationFailedException(...)
```

#### Option A vs B Selection Criteria

| Criteria | Option A (Bounded) | Option B (Interactive) |
|----------|-------------------|------------------------|
| **Error type** | Syntax error, simple logic bug | Complex algorithm failure |
| **Code length** | < 50 lines | > 50 lines |
| **User preference** | Quick fix, minimal interaction | Wants to supervise |
| **Retry count** | First escalation | Second+ escalation |
| **Timeout** | Short (< 5 min) | Extended (> 5 min) |

#### Context Passing Requirements

The escalation must preserve context for Claude:

```python
Task(
    prompt=f"""
    Original question: {self.last_question_asked}

    Failed code:
    ```python
    {failed_code}
    ```

    Error encountered:
    {error_details}

    Previous debugging attempts:
    {self._get_debugging_history()}

    Please fix the code to correctly answer the original question.
    """,
    type=TaskType.BOUNDED,  # or INTERACTIVE based on criteria
    max_turns=10,
    timeout_seconds=300
)
```

### Use Case 2: Queue Integration

Enable ClaudeCodeDispatcher tasks to participate in the same queue system as COSA agents.

#### Current Queue System

```
TodoFifoQueue → RunningFifoQueue → Done/Dead Queue
      ↓               ↓                  ↓
   push_job()    _process_job()    jobs_done/dead_queue

Jobs tracked: AgentBase subclasses only
```

#### Three Integration Options

##### Option A: Add as User Mode (Simplest)

```python
MODE_TO_AGENT = {
    ...existing agents...,
    "claude_code": ClaudeCodeDispatcher  # New mode
}
```

**Pros**:
- Minimal code changes
- Uses existing routing infrastructure
- User explicitly selects Claude Code

**Cons**:
- ClaudeCodeDispatcher isn't an AgentBase subclass
- Would need adapter to match AgentBase interface
- Doesn't support escalation from failed agents

##### Option B: Extend RunningFifoQueue (Recommended)

```python
def _process_job(self, job):
    if isinstance(job, ClaudeCodeQueueTask):
        return self._handle_claude_code_task(job)
    elif isinstance(job, AgentBase):
        return self._handle_base_agent(job)
```

**Pros**:
- Unified job tracking across all task types
- Same dead/done queue semantics
- User can see all tasks in one UI
- Escalated tasks appear in same flow
- Supports the escalation pattern from Use Case 1

**Cons**:
- Requires new task wrapper class
- RunningFifoQueue needs modification

##### Option C: Parallel Queue (Most Isolated)

```python
claude_code_queue = ClaudeCodeFifoQueue()
# Separate consumer thread
# Independent from voice pipeline
```

**Pros**:
- Doesn't interfere with existing flow
- Already partially exists via REST endpoint
- Complete isolation of concerns

**Cons**:
- Less unified visibility
- Separate dead/done tracking
- Can't easily show all tasks together

#### Recommended Approach: Option B

**Rationale**:
1. Unified job tracking across all task types
2. Same dead/done queue semantics
3. User can see all tasks in one UI
4. Escalated tasks appear in same flow
5. Supports escalation pattern naturally

#### ClaudeCodeQueueTask Wrapper

```python
@dataclass
class ClaudeCodeQueueTask:
    """Wrapper to make ClaudeCodeDispatcher Task queue-compatible."""

    # Required by FifoQueue
    id_hash: str
    push_counter: int
    run_date: str
    last_question_asked: str

    # The actual dispatcher task
    task: Task

    # Optional tracking
    user_id: Optional[str] = None
    escalated_from: Optional[str] = None  # Original agent id_hash if escalated

    def do_all(self) -> dict:
        """
        Execute via dispatcher.

        Note: Async wrapper needed since dispatch() is async.
        """
        result = asyncio.run(dispatcher.dispatch(self.task))
        return {
            "success": result.success,
            "result": result.result,
            "cost_usd": result.cost_usd,
            "duration_ms": result.duration_ms,
            "error": result.error
        }
```

#### Escalation Tracking

The `escalated_from` field enables:

```python
# When an AgentBase task fails and escalates:
escalated_task = ClaudeCodeQueueTask(
    id_hash=generate_unique_id(),
    push_counter=original_job.push_counter,  # Keep same order
    run_date=datetime.now().isoformat(),
    last_question_asked=original_job.last_question_asked,
    task=Task(prompt=..., type=TaskType.BOUNDED),
    user_id=original_job.user_id,
    escalated_from=original_job.id_hash  # Link to failed job
)

# UI can show:
# "Task 'calculate interest' escalated from MathAgent to Claude Code"
```

## The Conversation Identity Problem

### Current State: Project-Level Identity Only

The notification system currently groups all interactions by project:

```
sender_id = claude.code@{project}.deepily.ai

Example:
  claude.code@lupin.deepily.ai  ← ALL Lupin messages here
  claude.code@cosa.deepily.ai   ← ALL CoSA messages here
```

### The Problem: Parallel Sessions Are Indistinguishable

```
User runs TWO parallel Claude Code sessions in same repo:

  Terminal 1: Claude Code (lupin) → Working on WebSocket bug
  Terminal 2: Claude Code (lupin) → Writing documentation

Notification UI sees:
  sender_id = claude.code@lupin.deepily.ai (BOTH sessions)

  └── lupin
      └── 2026-01-12
          ├── "Fixed the connection handler" (from Session A)
          ├── "Updated README section 3" (from Session B)  ← INTERLEAVED!
          ├── "Now testing the fix" (from Session A)
          └── "Added API documentation" (from Session B)

Problems:
  ✗ Can't tell which message came from which session
  ✗ Voice responses route to... which session?
  ✗ Conversation history is merged/meaningless
  ✗ No way to focus on one work stream
```

### Three Levels of Conversation Identity

| Level | Description | Current State | Use Case |
|-------|-------------|---------------|----------|
| **Process** | Individual Claude Code session or AgentBase task | NOT tracked | "Show me messages from this specific session" |
| **Repo** | All work in a project | CURRENT model | "Show me all Lupin activity" |
| **Work Track** | Semantic grouping (user-defined) | NOT supported | "Show me the WebSocket investigation work" |

### Design Decision: Process-Centric Model

**Chosen approach**: Each process (session/task) gets unique conversation identity.

**Rationale**:
- Matches mental model of "I'm having a conversation with THIS terminal"
- Enables precise voice routing (most recent sender)
- Supports conversation history per session
- Can still aggregate to repo level for overview

## Proposed Conversation Model

### 1. Session Identity Format

```

### 4. Backward Compatibility

```python
# Parsing sender_id (notification_models.py)
def parse_sender_id(sender_id: str) -> dict:
    """Parse sender_id into components."""
    # Handle both old and new formats
    if "#" in sender_id:
        # New format: agent@project.deepily.ai#session
        base, session_id = sender_id.rsplit("#", 1)
    else:
        # Old format: agent@project.deepily.ai
        base = sender_id
        session_id = None

    # Parse agent type and project
    agent_part, domain = base.split("@", 1)
    project = domain.split(".")[0]

    return {
        "agent_type": agent_part,
        "project": project,
        "session_id": session_id,
        "full_sender_id": sender_id
    }

### Proposed: Full Conversation Context

```python
@dataclass
class ConversationTurn:
    """Single turn in a conversation."""
    role: str  # "user" or "assistant"
    content: str
    timestamp: datetime
    metadata: Optional[dict] = None  # code output, error details, etc.

@dataclass
class ConversationContext:
    """Full conversation history for multi-turn agents."""
    conversation_id: str
    turns: List[ConversationTurn]
    created_at: datetime
    last_activity: datetime

    def add_turn(self, role: str, content: str, metadata: dict = None):
        """Add a turn to the conversation."""
        self.turns.append(ConversationTurn(
            role=role,
            content=content,
            timestamp=datetime.now(),
            metadata=metadata
        ))
        self.last_activity = datetime.now()

    def get_history_prompt(self, max_turns: int = 10) -> str:
        """Format recent history for prompt injection."""
        recent = self.turns[-max_turns:]
        lines = []
        for turn in recent:
            prefix = "User" if turn.role == "user" else "Assistant"
            lines.append(f"{prefix}: {turn.content}")
        return "\n".join(lines)

    def get_token_estimate(self) -> int:
        """Estimate token count for history."""
        total_chars = sum(len(t.content) for t in self.turns)
        return total_chars // 4  # Rough estimate

# Enhanced AgentBase
class AgentBase:
    def __init__(
        self,
        question: str,
        conversation_context: Optional[ConversationContext] = None,  # NEW
        ...
    ):
        self.question = question
        self.conversation_context = conversation_context

        # Add current question to history if context provided
        if conversation_context:
            conversation_context.add_turn("user", question)

    def run_prompt(self):
        """Run LLM prompt with conversation history."""
        prompt = self._load_template()

        # Inject history if available
        if self.conversation_context:
            history = self.conversation_context.get_history_prompt()
            prompt = f"Previous conversation:\n{history}\n\n{prompt}"

        response = self.llm_client.generate(prompt)

        # Record response in history
        if self.conversation_context:
            self.conversation_context.add_turn(
                "assistant",
                response,
                metadata={"agent_type": self.routing_command}
            )

        return response
```
