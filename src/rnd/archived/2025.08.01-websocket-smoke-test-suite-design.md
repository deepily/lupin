## Current System Analysis

### Server-Side Components
- **WebSocketManager**: Connection management, event subscriptions, user-session mapping
- **WebSocket Endpoints**: `/ws/queue/{session_id}` and `/ws/audio/{session_id}`
- **19 Event Types**: Queue, Audio/TTS, Notification, System, Authentication, Control events
- **Key Features**: Event subscription filtering, session persistence, user-based routing, heartbeat/cleanup

### Client-Side Components
- **queue.js**: Main queue interface WebSocket client with unified audio queue
- **hybrid-tts.js**: Audio-specific WebSocket client for TTS streaming
- **Dual Session Architecture**: Separate queue and audio sessions to prevent conflicts

### Existing Tests (Gaps Identified)
- `test_websockets.py`: Basic connection, queue events, concurrent connections (limited coverage)
- Multiple HTML test files: Event subscription, session persistence, heartbeat testing (fragmented)
- **Major Gap**: No unified smoke test suite for comprehensive pre/post session validation

## Integration with Polish Workflow

### Pre-Polish Session Workflow
```bash
# 1. Run smoke tests to establish baseline
./src/scripts/websocket-smoke-pre-polish.sh

# 2. Save results as baseline for comparison
# Results stored in /tmp/websocket-smoke-baseline-$(date +%Y%m%d_%H%M%S).json

# 3. Proceed with polish tasks if all tests pass
# If tests fail, fix issues before beginning polish work
```

### Post-Polish Session Workflow
```bash
# 1. Run smoke tests after completing polish tasks
./src/scripts/websocket-smoke-post-polish.sh

# 2. Compare results with pre-polish baseline
# Automatic comparison and regression detection

# 3. Generate comparison report
# Shows any performance regressions or functionality breaks

# 4. If regressions detected, provide rollback guidance
# Clear steps to revert problematic changes
```

### Regression Handling Protocol
1. **Test Failure**: Identify specific failing test category
2. **Impact Assessment**: Determine if failure is critical or cosmetic
3. **Rollback Decision**: Revert changes if critical functionality affected
4. **Fix and Retry**: Address issue and re-run tests
5. **Documentation**: Record issue and resolution for future reference

## Dependencies and Risks

### Dependencies
- **Server Running**: FastAPI server must be operational on port 7999
- **Configuration**: All WebSocket configuration must be valid
- **Network**: Stable localhost networking for WebSocket connections
- **Browser**: Modern browser for visual tests (Chrome/Firefox recommended)

### Risks and Mitigations
- **Test Environment**: Tests could interfere with development
  - **Mitigation**: Use dedicated test database/cache, isolated sessions
- **Performance Variance**: Network/system load affects timing tests
  - **Mitigation**: Multiple test runs, statistical analysis, reasonable thresholds
- **Maintenance Overhead**: Tests require updates as system evolves
  - **Mitigation**: Modular design, comprehensive documentation, regular review
