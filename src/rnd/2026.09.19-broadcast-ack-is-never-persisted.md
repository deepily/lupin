# The broadcast-ack reconciliation path cannot work, because the acks are never persisted

**Date**: 2026.09.19
**Measured by**: Chloé 🗼 (session `42899779`), for row `384591dd` (lupin-mobile Phase 5)
**Status**: code path conclusive · live confirmation **not** obtained (see § What I could not reach)

---

## The claim

`GET /api/notifications/undelivered` **can never return a `commons_broadcast_ack`**, so the
reconciliation path that §6.2 of the fleet-panes plan prescribes — and that row `384591dd`'s
acceptance is written against — has nothing to operate on.

This is **not** the truncation defect the plan already names. That defect says the drain cannot
tell a complete read from a truncated one. The truth is one level deeper: **the drain recovers
no acks at all.**

## Why

Two independent blockers. Either alone is sufficient.

### 1. The ack is never written to the database

Persistence is **not** a property of the notification queue. It lives in the `notify_user`
**route**, which calls `_persist_notification_sync` behind a `persist` flag — and that is the
**only** call site of that helper in `notifications.py`.

The ack watcher does not go through that route. `main.py` binds its push function directly to
the queue method:

```python
commons_ack_watcher  = CommonsAckWatcher(
    push_notification_fn   = jobs_notification_queue.push_notification,
```

`NotificationFifoQueue.push_notification` appends to the in-memory queue and emits over the
WebSocket. It contains no `create_notification` call; searching `notification_fifo_queue.py`
for one returns nothing. The DB writers in the tree are the POST routes in `notifications.py`,
plus `dm.py` and `queues.py`.

⇒ No row is written. `GET /api/notifications/undelivered` reads the `notifications` table via
`NotificationRepository.get_undelivered_for_recipient`. It cannot return a row that does not
exist.

### 2. Even a persisted row could not be folded

Every field that *identifies* an ack — `broadcast_id`, `session_id`, `persona_name`,
`persona_icon`, `persona_color`, `status`, `body_summary` — is passed by the watcher inside
`payload=`.

- `payload` is **not a column** on the `notifications` table. The table's columns are id,
  sender_id, recipient_id, job_id, progress_group_id, title, message, abstract, type, priority,
  direction, sender_persona, sender_icon, reply_to, thread_id, created_at.
- `_project_undelivered_notification` returns exactly **ten** keys — id, sender_id, title,
  message, abstract, type, priority, state, job_id, created_at. No payload.
- `payload` exists only on the live frame, where the queue item serialises it as
  `"payload" : self.payload`.

⇒ A drained ack could not be attributed to a broadcast or to a seat even in principle. It would
be an opaque row of the right `type` and nothing more — and the count would span every
broadcast inside the 24-hour age cap, not the one on screen.

## What I could not reach

**The live confirmation was not obtained, and the code trace is not a substitute for it.**

The two-sided probe I wrote reads the same question from both sides — the in-memory queue
(`GET /api/notifications/{user_id}`, which the endpoint's own description says is served from
the FIFO queue) and the database (`GET /api/notifications/undelivered`). An ack visible in the
first and absent from the second would settle it in one run.

It could not be run from this seat. The available credentials are
`interactive.job.tester@lupin.deepily.ai`, a test account. Broadcasts originate from Rick's
account and the acks are addressed there, so **this account's empty drain says nothing about
acks** — an empty answer from the wrong population looks exactly like an empty answer from the
right one.

⇒ To settle it: run the same two-sided read from the originating account, immediately after a
broadcast with `require_ack` that at least one seat has acked.

### A defect in the probe itself, recorded because it nearly counted

The first run printed `population: 0 rows` for the in-memory arm. **That arm never ran.** It
answered **403** — the path had been built from `login["tokens"]["user_id"]`, which does not
exist in the login response; the id is at `login["user"]["id"]`. The script was counting an
error body as an empty population, and the zero was about to be reported as a measurement.

It was caught only by re-running with the raw response printed rather than the parsed count.
The positive control that *did* pass — `GET /api/notifications/senders/{email}` returning a
large live population for the same account (916 rows from `queue.running`, 119 from `ask.flow`,
more behind) — is what establishes that the DB read path works and that an absence found on the
right account would mean something.

⇒ **A clean-looking zero is not a measurement until you have watched the same instrument return
a positive.**

## What it means for row `384591dd`

- **Compose, mic and send are unaffected** and buildable as written.
- **The ack-reconciliation half cannot be built to the written acceptance** against today's
  server. It needs a lupin-side change first: either persist the ack, or carry its identity
  somewhere the drain can see. That is a separate row.
- The plan's §6.2 and the row's acceptance should be amended to say so, rather than prescribing
  a remedy that silently no-ops.
