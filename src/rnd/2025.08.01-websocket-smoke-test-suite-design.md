The goal is to ensure no regressions are introduced during the 62-task polish effort while maintaining high confidence in system functionality.

The test suite provides automated validation of all critical WebSocket functionality in 8-10 minutes, replacing hours of manual testing and providing immediate feedback on system health.

## Current System Analysis

### Server-Side Components
- **WebSocketManager**: Connection management, event subscriptions, user-session mapping
- **WebSocket Endpoints**: `/ws/queue/{session_id}` and `/ws/audio/{session_id}`
- **19 Event Types**: Queue, Audio/TTS, Notification, System, Authentication, Control events
- **Key Features**: Event subscription filtering, session persistence, user-based routing, heartbeat/cleanup

### Client-Side Components
- **queue.js**: Main queue interface WebSocket client with unified audio queue
- **hybrid-tts.js**: Audio-specific WebSocket client for TTS streaming
- **Dual Session Architecture**: Separate queue and audio sessions to prevent conflicts

### Existing Tests (Gaps Identified)
- `test_websockets.py`: Basic connection, queue events, concurrent connections (limited coverage)
- Multiple HTML test files: Event subscription, session persistence, heartbeat testing (fragmented)
- **Major Gap**: No unified smoke test suite for comprehensive pre/post session validation

## Test Suite Architecture

### 1. Core Tests (Automated - 2-3 minutes)
**Purpose**: Validate fundamental WebSocket functionality

#### Connection Tests:
- WebSocket endpoint availability (`/ws/queue/`, `/ws/audio/`)
- Connection establishment timing (<500ms)
- Connection cleanup on disconnect
- Network error recovery

#### Authentication Tests:
- Authentication flow (auth_request → auth_success)
- Token validation and error handling
- Session ID format validation
- User-session association

#### Session Management Tests:
- Session persistence across reconnections
- Dual session architecture (no conflicts between queue/audio)
- Single-session-per-user policy enforcement
- Session cleanup and expiration

#### Event System Tests:
- All 19 event types can be emitted and received
- Event subscription filtering works correctly
- User-based routing (events reach correct users only)
- Event payload validation and error handling

### 2. Integration Tests (Automated - 3-4 minutes)
**Purpose**: Validate end-to-end workflows

#### Job Processing Workflow:
- Job submission → Queue events → TTS completion → Audio streaming
- Queue state transitions (TODO → RUNNING → DONE)
- Error handling (DEAD queue population)

#### Audio Streaming Workflow:
- TTS request → Audio chunks → Progressive/collected playback
- Both instant and reliable modes functional
- Audio caching and replay capability

#### Notification Workflow:
- External notification → Queue storage → WebSocket delivery → Audio playback
- Priority-based audio selection (high/low/error sounds)
- User-specific notification routing

#### Client-Server Synchronization:
- JavaScript WebSocket clients connect and authenticate properly
- Event subscription changes propagate correctly
- UI updates reflect server state accurately

### 3. Visual Tests (Manual - 5 minutes)
**Purpose**: Human verification of UI and audio functionality

#### Interactive Test Dashboard:
- Real-time connection status for both queue and audio sessions
- Live event log with filtering and statistics
- Audio test panel with instant/reliable mode switching
- Load test controls for stress testing
- Error scenario simulation buttons

#### Validation Points:
- UI updates correctly reflect WebSocket events
- Audio plays without gaps or distortion
- Error messages are user-friendly
- Performance metrics display within acceptable ranges

### 4. Performance Tests (Automated - 2 minutes)
**Purpose**: Ensure performance standards are maintained

#### Latency Measurements:
- Connection establishment time (<500ms)
- Event delivery latency (<100ms for local events)
- Audio streaming first-chunk latency (<500ms)
- WebSocket message round-trip time

#### Load Testing:
- Multiple concurrent connections (5-10 clients)
- Event broadcasting performance
- Memory usage under load
- CPU usage during high throughput

#### Baseline Comparison:
- Compare current metrics with stored baselines
- Alert if performance degrades >20%
- Track performance trends over time

### 5. Configuration Tests (Automated - 1 minute)
**Purpose**: Validate configuration and environment setup

#### Configuration Validation:
- All 11 WebSocket configuration keys are valid
- Event subscription lists properly loaded from config
- Single-session policy configuration respected
- Heartbeat and cleanup intervals functional

#### Environment Validation:
- Required environment variables set
- Server health check passes
- Database connections (if applicable)
- File permissions for audio/cache directories

```bash
# 2. Save results as baseline for comparison
# Results stored in /tmp/websocket-smoke-baseline-$(date +%Y%m%d_%H%M%S).json

# 3. Proceed with polish tasks if all tests pass
# If tests fail, fix issues before beginning polish work
```

### Post-Polish Session Workflow
```bash
# 1. Run smoke tests after completing polish tasks
./src/scripts/websocket-smoke-post-polish.sh

# 2. Compare results with pre-polish baseline
# Automatic comparison and regression detection

# 3. Generate comparison report
# Shows any performance regressions or functionality breaks

# 4. If regressions detected, provide rollback guidance
# Clear steps to revert problematic changes
```

### Regression Handling Protocol
1. **Test Failure**: Identify specific failing test category
2. **Impact Assessment**: Determine if failure is critical or cosmetic
3. **Rollback Decision**: Revert changes if critical functionality affected
4. **Fix and Retry**: Address issue and re-run tests
5. **Documentation**: Record issue and resolution for future reference

## Dependencies and Risks

### Dependencies
- **Server Running**: FastAPI server must be operational on port 7999
- **Configuration**: All WebSocket configuration must be valid
- **Network**: Stable localhost networking for WebSocket connections
- **Browser**: Modern browser for visual tests (Chrome/Firefox recommended)

### Risks and Mitigations
- **Test Environment**: Tests could interfere with development
  - **Mitigation**: Use dedicated test database/cache, isolated sessions
- **Performance Variance**: Network/system load affects timing tests
  - **Mitigation**: Multiple test runs, statistical analysis, reasonable thresholds
- **Maintenance Overhead**: Tests require updates as system evolves
  - **Mitigation**: Modular design, comprehensive documentation, regular review
