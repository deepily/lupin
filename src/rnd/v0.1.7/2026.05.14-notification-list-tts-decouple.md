## Context — the bug

Yesterday's TTS preview-and-pause shipment introduced an unintended downstream UX bug. **Symptom**: when the TTS queue auto-pauses after a preview slice plays (`isTTSPaused=true`), subsequent high/urgent fire-and-forget notifications arriving over WebSocket failed to appear in the visible notification list. The user (Rick) had a 20+ item backlog of invisible notifications stuck behind a paused TTS queue — including a doc-link notify he was waiting for.

**Root cause** (verified by Explore investigation): the original notification-list architecture had high/urgent notifications take a DEFERRED render path. Path A (TTS queue add) fired immediately on WS arrival; Path B (visible list render via `addNotificationToSenderGroup`) was deferred to inside `activateNextTTS()` at `notifications.js:13281`. The guard `if ( this.isTTSPaused ) return;` at `notifications.js:13244-13246` made this fragile: any TTS pause stranded the deferred list render.

The 2026-05-13 preview-and-pause feature dialed this fragility from "rare" to "every long-message notification."

**Scope of bug**: high/urgent FIRE-AND-FORGET notifications only. Low/medium priority already rendered immediately on WS arrival (line 5634). Action-required notifications render through a separate path (`addActionRequiredNotification`) and are unaffected.

---

## The fix — Option A: decouple list render from TTS queue

**Approach**: render the notification to the visible list IMMEDIATELY on WS arrival. The TTS queue still queues, pauses, advances per its own logic — but the visible list never depends on TTS advancement. Mirrors the pre-existing low/medium pattern.

**Plus**: small CSS state `.is-tts-pending` for the visual cue that a notification is queued for TTS but not yet playing.

### Change 1 — `handleNotificationUpdate` (notifications.js, line ~5610)

Render to sender group + apply pending-TTS class BEFORE queueing for TTS. Removed the misleading deferred-render comment.

### Change 2 — `activateNextTTS` fire-and-forget branch (notifications.js, line ~13281)

Removed the duplicate `addNotificationToSenderGroup` call (was the trapped deferred render). Added pending-class clearing so the regular playing-state visual can take over.

### Change 3 — `.is-tts-pending` CSS (notifications.css, after `.is-paused-current` rules)

Subtle treatment: 0.78 opacity, amber-tinted left border stripe (matches `.is-paused-current` palette), small ⏳ glyph in the corner where the pause button normally lives. When TTS engages, the class is removed and `.is-playing-current` adds the pause button.

## Trade-off Rick accepted

The original architecture rendered fire-and-forget notifications in the visible list at the moment TTS engaged playback ("see when you hear"). The decouple changes this to "see immediately, hear when TTS gets to you" — closer to every modern messaging app. No regression in any feature; just a slightly different cadence between visual and audio.
