## TL;DR

**Symptom**: A single system broadcast against 5 active sessions renders **5 cards** in the Recent Activity panel instead of 1. A single "completed" status produces multiple ack cards instead of 1.

**Root cause**: `CommonsActivityWatcher._tick()` dispatches one `commons_activity` WS event per row read from the `broadcasts` / `broadcast-acks` topics. `perform_fanout()` writes N per-recipient rows by design (one per session, for `target_session_id`-scoped routing in the HTTP path). The HTTP read endpoint `/api/commons/broadcast-history` collapses these N rows back to 1 via `_dedupe_broadcasts_by_id` + `_dedupe_broadcast_acks_by_recipient`. **The WS push path bypassed both dedupes.**

**Fix**: Mirror the HTTP-path dedupe inside `CommonsActivityWatcher._tick()`. Single 100-LOC addition + 7 new unit tests. Zero changes to write-side (`perform_fanout` still writes per-recipient rows — that data is needed for the `target_session_id` branch of `_entry_passes_same_user_scoping`).

**Verification**: 22/22 watcher unit tests pass (15 pre-existing + 7 new). 438/438 full commons unit suite passes. No regressions.

## Diagnosis

### Layer 1 — Symptom

Rio observed on 2026-05-16 ~12:16 EDT during a multi-session voice-persona bug investigation:

1. Single `📢 System Broadcast` → notification panel rendered the same broadcast card **5×** in succession (matches the active-session count exactly)
2. Single "completed" status → **4 × Mr. Radio + 1 × Rio** "completed" entries (5 total cards = 5 sessions)

Rio's hypothesis: "WS emit is fanning out per-session-with-persona instead of per-user."

### Layer 2 — Architectural review

The data path for a broadcast card has three legs:

```
                                  ┌─────────────────────────┐
                                  │ POST /api/commons/      │
                                  │   broadcast-to-cc-      │
   User clicks "Send broadcast" → │   sessions              │
                                  │                         │
                                  │ → execute_broadcast()   │
                                  │ → perform_fanout()      │
                                  │   ↓                     │
                                  │   writes N rows to      │
                                  │   `broadcasts` topic    │
                                  │   (one per recipient,   │
                                  │    target_session_id    │
                                  │    in metadata)         │
                                  └────────────┬────────────┘
                                               │
                  ┌────────────────────────────┴──────────────────────────┐
                  │                                                       │
                  ▼                                                       ▼
   ┌──────────────────────────────────┐               ┌──────────────────────────────────┐
   │ HTTP read path                   │               │ WS push path                     │
   │ GET /api/commons/                │               │ CommonsActivityWatcher           │
   │   broadcast-history              │               │ _tick() polls every 1s           │
   │ → execute_broadcast_history()    │               │ → reads new entries since cursor │
   │ → _dedupe_broadcasts_by_id()  ✅ │               │ → _dispatch_activity_event()     │
   │ → _dedupe_broadcast_acks…()   ✅ │               │   for EACH entry                 │
   │ → returns 1 row per broadcast   │               │ → fires commons_activity WS push │
   └──────────────┬───────────────────┘               └──────────────┬───────────────────┘
                  │                                                  │
                  ▼                                                  ▼
   ┌──────────────────────────────────┐               ┌──────────────────────────────────┐
   │ Client polls on dropdown change  │               │ Client `_handleCommonsActivityWS`│
   │ → renders 1 row                  │               │ → PREPENDS 1 row per WS event   │
   │ ✅ correct                        │               │ ❌ 5 events from 5-row fanout    │
   └──────────────────────────────────┘               │    = 5 rows in panel             │
                                                       └──────────────────────────────────┘
```

The HTTP read path was patched on 2026-05-15 (María's `_dedupe_broadcasts_by_id`) and 2026-05-15 evening (Arnold's `_dedupe_broadcast_acks_by_recipient`). The WS push path was never patched — it dispatched one event per raw entry, untouched by dedupe.

### Layer 3 — Confirmation

Read at `src/cosa/rest/commons_activity_watcher.py` lines 108-166: `_tick()` reads new entries → sorts newest-first → loops over each entry calling `_dispatch_activity_event()`. No dedupe step exists between read and dispatch.

The fan-out write side at `src/cosa/rest/routers/commons.py` lines 368-426: `perform_fanout()` iterates over `sessions` and calls `store.post(topic="broadcasts", ...)` once per session. By design — this supports the `target_session_id` branch of `_entry_passes_same_user_scoping` for HTTP-path same-user filtering.

This is a classic **producer/consumer asymmetry bug**: the producer writes N rows (correct for per-recipient scoping); one consumer dedupes N→1 (correct for activity oversight); the other consumer doesn't dedupe (wrong).

## Fix

**Approach**: mirror the HTTP-path dedupe inside the watcher, between sort and dispatch.

### Changes

#### 1. `src/cosa/rest/commons_activity_watcher.py` — add pre-dispatch dedupe

- New method `_dedupe_for_dispatch(entries)` — adapts `_dedupe_broadcasts_by_id` and `_dedupe_broadcast_acks_by_recipient` from `routers/commons.py` to operate on the watcher's decorated-entry shape (each dict carries `_topic` from the collection step).
- Called from `tick()` immediately after the newest-first sort, before the dispatch loop.
- Cursor advancement fixed: captures `latest_ts_pre_dedupe` from the original (pre-dedupe) entry set so the cursor advances past dropped duplicates. Otherwise dropped duplicates would re-surface on the next tick.

**Dedupe rules** (identical to HTTP path):
- `broadcasts` topic: collapse on `metadata.broadcast_id`. Dispatched copy has `target_session_id` stripped from metadata.
- `broadcast-acks` topic: collapse on `(broadcast_id, sender_session_id, metadata.status)` triple.
- All other topics: passthrough unchanged.
- Defensive passthrough on missing / non-string keys.

#### 2. `src/tests/unit/commons/test_commons_activity_watcher.py` — 7 new tests

| Test | What it verifies |
|---|---|
| `test_tick_dedupes_broadcasts_by_broadcast_id` | The 5×-card regression: 5 per-recipient rows → 1 dispatch; `target_session_id` stripped from dispatched metadata |
| `test_tick_dedupes_broadcasts_keeps_distinct_broadcast_ids` | Distinct broadcasts in same tick stay distinct (no over-collapse) |
| `test_tick_dedupes_broadcast_acks_by_recipient_triple` | 3 identical-triple acks → 1 dispatch (Arnold's write-side multiplicity regression) |
| `test_tick_keeps_acks_with_distinct_sender_sessions` | Multi-recipient acks stay distinct (different `sender_session_id`) |
| `test_tick_dedupe_defensive_passthrough_on_malformed_entries` | Missing/non-string keys → pass through, no silent disappear |
| `test_tick_dedupe_unaffected_topics_pass_through` | Free-form topics not dedupe-touched |
| `test_tick_cursor_advances_past_dropped_duplicates` | Cursor reaches max ts of original entry set, not just dispatched subset |

## Not-fixed-yet — pending follow-ups

This fix closes the **consumer-side leg** of the duplicate-card problem. Two related issues remain (logged previously, still outstanding):

### A. Write-side broadcast-acks multiplicity (Arnold's investigation note)

The `_dedupe_broadcast_acks_by_recipient` docstring at `routers/commons.py:687-688` documents that "the underlying write-side multiplicity (something is causing N `notification_queue_update` deliveries → N `_handle_broadcast_received` → N `_post_ack` calls in `src/lupin_mcp/broadcast_handler.py`) is a SEPARATE investigation." That root-cause work has not been done. The fix in this doc + Arnold's earlier dedupe both **mask** the symptom on the read path; the producer-side N-call bug remains.

### B. Completion-cards persona stamping anomaly (4×Mr-Radio + 1×Rio)

Rio's filing observed that a single completion produced **4× Mr. Radio + 1× Rio** ack cards. The dedupe in this fix collapses identical-triple acks (same `broadcast_id`, `sender_session_id`, `status`), but if the 5 acks came from 5 different `sender_session_id`s — one per recipient — they all pass through as distinct rows (correctly, by the current rule). The persona stamping asymmetry (4 vs 1) suggests something deeper about how recipient-side persona resolution interacts with multi-session-same-user scenarios. Worth a follow-on investigation.

**Recommended next step for follow-ups**: open a fresh R&D doc for the write-side investigation in the same `src/rnd/v0.1.7/` namespace.
