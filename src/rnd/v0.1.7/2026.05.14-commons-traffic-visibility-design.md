## TL;DR

Rick has zero admin-side visibility into the inter-session commons today: he can send a broadcast and receive acks, but he can't see (a) the history of broadcasts he's sent, (b) any AI replies to those broadcasts, or (c) AI-to-AI coordination chatter (which tonight's session demonstrated is a real blind spot — Maria was waiting on `notifications-ui-coord` while Mr. Radio was answering on `coord-notifications-js`, invisible to Rick).

This design adds a "Recent Activity" sub-section inside the existing broadcast card on `/app/notifications` that surfaces a real-time flat reverse-chronological stream of conversational commons traffic, scoped to the calling user, with topic-chip prefixes that make routing visible.

**Eight Q-decisions ratified** via `ask_multiple_choice` over voice, all on 2026-05-14:

| # | Decision | Choice |
|---|---|---|
| Q1 | AI replies to user | **broadcast-card-only** (moved out of session cards) |
| Q2 | AI-to-AI traffic rendering | **topic chip prefix** (e.g. `[coord-notifications-js]`) |
| Q3 | Freshness model | **real-time WS push** via new `commons_activity` notification type |
| Q4 | Cutover model | **INI feature flag** with hot-reload via existing config re-init endpoint |
| Q5 | Reserved-topic filtering | **exclude `presence` + `system-events`** by default; keep `broadcasts` + `broadcast-acks` + free-form |
| Q6 | Initial render limit + pagination | **Today + history-window dropdown** (mirrors existing pattern in notifications.html top) |
| Q7 | Threading model | **flat reverse-chronological** (no threading; `metadata.in_reply_to` retained for v2) |
| Q8 | Expand/collapse default + persistence | **default-EXPANDED**, no localStorage persistence; **session-scoped toggle** in the section header (standard collapse pattern) |
| Q9 | Default-visibility on first land — both gating layers | **INI flag default `True`** (feature ships enabled) + **broadcast card parent default-expanded** (no `collapsed` class on the parent `section-content`). Zero clicks to see Recent Activity on page load. Reversible: flip INI to `False` via hot-reload to disable; user can manually collapse the broadcast card to hide. |

## Post-ship fix — 2026-05-15: dedupe per-recipient fanout rows

**Reported by**: Rick (voice, 2026-05-15) — his morning `@all` broadcast appeared **five times** in Recent Activity.

**Root cause**: Phase 2's `perform_fanout` (`src/cosa/rest/routers/commons.py:329-380`) writes one `broadcasts`-topic row **per recipient** by design (line 348 comment: `# AC4: per-recipient broadcasts entry`). This supports the `target_session_id` branch of `_entry_passes_same_user_scoping` for normal session-receipt scoping. It became visible-as-noise once Traffic Visibility surfaced the raw topic into the UI: an `@all` broadcast to N active sessions produced N rows in the admin overview.

**Fix**: `_dedupe_broadcasts_by_id` helper added to `commons.py` and wired into `execute_broadcast_history` between the merge-sort and limit-cap steps. Collapses fanout rows by `metadata.broadcast_id` (one row per logical broadcast), strips `target_session_id` from the kept row's metadata (admin-overview row represents the broadcast as a whole, not any single recipient slice). Non-`broadcasts` topics pass through unchanged — `broadcast-acks` per-recipient rows remain the intended chip-row UX.

**Safety**: UUIDv4 generation at `commons.py:429` (`broadcast_id = body.broadcast_id or str(uuid.uuid4())`) guarantees distinct broadcast calls never share an id. Dedupe collapses **within** a broadcast, never **across** broadcasts.

- 2 new smoke tests in `src/tests/smoke/test_commons_broadcast_history_endpoint.py` asserting the wire-level invariant on `:7999`.
- `src/cosa/rest/routers/commons.py` stays at **100% line/branch/function coverage** (238 stmts, 0 missing).

## Backend design

### NEW endpoint

```
GET /api/commons/broadcast-history?since=<iso8601>&hours=<int|null>&limit=<int>
Authorization: Bearer <JWT>
```

**Response shape**:
```json
{
  "entries": [
    {
      "ts": "2026-05-14T23:21:04.567240+00:00",
      "topic": "broadcasts",
      "topic_kind": "reserved" | "free-form",
      "sender_session_id": "broadcast-a021fde0",
      "persona_name": "System Broadcast",
      "persona_icon": "📢",
      "persona_color": "#FFC107",
      "body": "@all I want you both to coordinate your work...",
      "metadata": { "broadcast_id": "...", "sender_user_id": "0cf47e2d-..." }
    },
    ...
  ],
  "since_used": "2026-05-14T00:00:00-04:00",
  "next_cursor": null
}
```

**Filter semantics** (mirrors the same-user-scoping pattern fixed earlier today in `filter_and_project_sessions`):
- Reads from commons store across topics: `broadcasts`, `broadcast-acks`, and all free-form topics (everything except `presence` + `system-events`).
- Same-user scoping: each entry is included iff (a) `metadata.sender_user_id == authenticated_user_id`, OR (b) `metadata.target_session_id` belongs to one of the authenticated user's sessions, OR (c) the entry was authored from a bridge whose `owner_user_id == authenticated_user_id` (graceful: bridges with no `owner_user_id` pass through, same pattern as the broadcast-recipient filter).
- Time window: `since` is the cutoff timestamp; `hours` is a back-window from `now()` ("today" → since-local-midnight, computed client-side); both reuse the `getEffectiveHoursForQuery()` resolver semantics already in `notifications.js:11238`.
- Limit: default 200, max 1000. Pagination via `next_cursor` (defer for v1 if "Today" + dropdown suffices).
- Order: newest first.

### NEW WS notification type

`commons_activity` — fired by the server whenever a new commons entry is persisted to a topic the authenticated user has subscribed to (same-user-scoping applied at WS-fanout time).

**Payload shape** (subset of the GET response entry):
```json
{
  "type": "commons_activity",
  "entry": { ...same shape as GET response entry... }
}
```

**Subscription**: clients are auto-subscribed when authenticated (no explicit subscribe call needed) — the server applies same-user filtering on the fanout side.

|---|---|---|
| `commons traffic visibility enabled` | `True` | Master feature flag — when False, the new section + WS push are no-ops. **Q4 ratified: hot-reloadable via the existing config-re-init endpoint. Q9 ratified: default `True` so the feature ships enabled.** Flip to `False` via INI + hot-reload to disable as a kill-switch. |

### JS render in notifications.js

NEW methods on `NotificationsUI`:

- `_initCommonsRecentActivity()` — checks `/api/config/client` for `commons_traffic_visibility_enabled`; if False, hides the section entirely. If True, fetches initial data + wires WS handler + binds dropdown / refresh button.
- `_loadCommonsRecentActivity(hours)` — calls `GET /api/commons/broadcast-history?hours=<x>`, renders entries.
- `_renderCommonsEntry(entry)` — builds the row DOM: persona icon (color-coded), persona name, optional topic chip (only for free-form / non-broadcast-reserved topics), HH:MM timestamp, body (markdown-rendered via existing renderer).
- `_handleCommonsActivityWS(payload)` — WS handler for the new `commons_activity` event type; prepends the new entry to the body (newest-first ordering preserved).
- `_setCommonsActivityWindow(value)` — dropdown change handler; re-fetches with new window.

WS event routing: extend `handleNotificationUpdate` (already the dispatcher) with a new case `"commons_activity"`.

**INI feature flag check** — at constructor time, read `commons_traffic_visibility_enabled` from `/api/config/client`. If False, skip ALL of the above wiring; the HTML section can still exist (just stays empty + hidden via CSS `display: none` toggled by JS).

### CSS in notifications.css

NEW `.commons-recent-activity-*` rule block:
- Header: flex with title left, controls right
- Body: bordered container, max-height + overflow-y for scroll on long streams
- Entry row: grid layout (icon | name | chip | time | body); persona-color CSS variable for the icon background
- Topic chip: small pill, persona-color border, monospace
- Hover state on rows for affordance

### Migration / cutover behavior (Q4 — INI flag; Q9 — default True)

**On first land (default `True` per Q9)**:
- Broadcast card parent renders expanded (no `collapsed` class). Compose-row + Recent Activity both visible immediately on page load.
- Recent Activity section visible.
- WS push wiring active — new commons entries arrive in real-time.
- AI replies to broadcasts route to Recent Activity only — no longer rendered in session cards. (Q1 ratified — broadcast-card-only.)

**Kill-switch — if the new UX needs disabling at any point**, flip `commons traffic visibility enabled = False` in `lupin-app.ini` + trigger the config re-init endpoint:
- Recent Activity section hidden via `display: none`.
- WS push wiring becomes a no-op.
- AI replies return to session cards on next page load.
- Broadcast card parent's expanded-default stays (Q9 only flipped the INI flag, not the parent state) — to also re-collapse the parent, manually click its header.

Hot-revert is symmetric: flip `True` again and everything comes back without restart. Tonight's parked focus-bar bug is a fresh reminder that big UX moves benefit from a kill switch — even on a default-on rollout.

## Acceptance criteria

**AC1** — `GET /api/commons/broadcast-history` returns `entries[]` sorted newest-first; honors `hours` window; honors same-user scoping; excludes `presence` + `system-events` per INI default.

**AC2** — INI key `commons traffic visibility enabled` gates the entire feature. **Default `True`** (Q9): on first land, section is visible + WS push is live + AI replies route to Recent Activity only. Flip to `False` via INI + hot-reload at any time to disable (kill-switch): section hidden + WS push no-op + AI replies return to session cards on next page load.

**AC3** — `commons_activity` WS event delivers new commons entries in real-time to authenticated users. Same-user scoping applied at fanout. Includes `entry` with persona stamps + topic + body + metadata.

**AC4** — Recent Activity section's history-window dropdown matches the existing notifications history-window UX (Today | 24h | 2d | week | month | All). Backend reuses `hours` query-param semantics.

**AC5** — Topic chip renders for free-form topics only; `broadcasts` + `broadcast-acks` get no chip (the persona icon + body already disambiguates them). Excluded topics never render.

**AC6** — Flat reverse-chronological ordering: every entry is a sibling row; `metadata.in_reply_to` is captured but not used for visual grouping in v1.

**AC7** — Default-expanded on every page load. Section header click toggles within-session hide/show. No localStorage persistence of the toggle state (Q8 ratified).

**AC8** — Markdown rendering in entry bodies (same renderer as broadcast bodies); XSS-safe (sanitization at the renderer layer, mirrors Phase 2 §F1 markdown approach).

**AC9** — Unit tests on `execute_broadcast_history` pure-logic helper: same-user scoping, time-window filtering, reserved-topic exclusion, ordering, limit. Target ≥90% line + branch coverage on the new module.

**AC10** — Smoke test for the WS push round-trip: post a commons entry → observe `commons_activity` event delivered to subscribed clients with correct payload shape.

**AC11** — Live `:7999` integration test (AI-discretionary): hit the new endpoint with a JWT, verify the response shape + filtering against a controlled commons store fixture.

**AC12** — `:8000` integration test (user-scheduled): full pipeline test that submits a broadcast via `POST /api/commons/broadcast-to-cc-sessions`, waits for fanout, confirms the entry appears in `GET /api/commons/broadcast-history` AND was delivered via WS.

**AC13** — **Urgent-priority absolute bypass for all TTS-shaping rules**. When a commons entry, or any notification that relays a commons-traffic event, carries `priority == "urgent"`, the TTS pipeline MUST render the message in FULL — regardless of:
- TTS preview percentage settings (`tts_preview_*` INI keys established by `src/rnd/v0.1.7/2026.05.13-tts-preview-and-pause-design.md`)
- Muting state (per-session or global)
- Any other TTS shaping / truncation mechanism

This is a **system-wide TTS principle** ratified by Rick (voice, 2026-05-14): *"Urgent means all bets are off when it comes to muting and percentage of text to speech to render."* It applies beyond this design doc; it is a cross-cutting invariant of the notification subsystem.

**Audit obligation**: before Step 7 (JS render + WS handler) lands, audit `src/fastapi_app/static/js/notifications.js` paths that fire TTS for commons-relayed notifications (the existing `activateNextTTS` + `handleNotificationUpdate` paths Mr. Radio's commit `efbcae3` recently touched) to confirm `priority == "urgent"` short-circuits any preview/mute/truncate gating. If it doesn't, that's a separate (likely small) fix that should land before AC13 can be marked closed.
