# Bounded ClaudeCodeJob Billing — Empirical Confirmation + Migration Policy

## TL;DR

**Bounded ClaudeCodeJobs in Lupin are paid for by Rick's Claude Code Max 200 plan and incur ZERO per-token Anthropic API charges.** The `cost_usd` field in CC job records is SDK-reported telemetry, not actual billing.

This unlocks a cost-shifting migration pattern: agents that currently call the Anthropic SDK directly via `ANTHROPIC_API_KEY_FIREWALLED` (deep research, podcast script generation, presentation generation) are candidates for migration to bounded `ClaudeCodeJob` execution — converting per-token metered spend into the fixed monthly Max-plan cost.

This doc is the load-bearing empirical record other policy docs reference. If someone (Claude Code or human) ever questions the policy, this is the evidence.

---

## 1. Why we ran this experiment

Lupin already migrated two agents to the bounded ClaudeCodeJob pattern:

- **BFE (Bug Fix Expediter)** — `src/cosa/agents/bug_fix_expediter/`
- **TFE (Test Fix Expediter)** — `src/cosa/agents/test_fix_expediter/`

Both ride the CJ Flow agentic pool with `task_type=BOUNDED`, fire-and-forget. The cost assumption underlying both migrations was: "the Claude Code CLI uses Max-subscription auth, so bounded jobs are zero marginal cost". That assumption was documented (e.g., `src/cosa/agents/deep_research/__init__.py:27` — "NEVER use ANTHROPIC_API_KEY - that is reserved for Claude Code CLI") but had never been empirically confirmed end-to-end against the Anthropic console.

Before expanding the migration to more agents (podcast, presentation, deep research) — each of which is a non-trivial engineering investment — Rick wanted **definitive empirical confirmation** that the cost path actually works the way the architecture claims.

The retired test `src/tests/smoke/test_claude_code_max_subscription.py::test_claude_code_bounded_job_uses_max_subscription` (skipped/retired) made the same claim, but it submitted only a single trivial file-write job — a result so small (~$0.00 telemetry) it couldn't disambiguate "Max-covered" from "tiny-bill-rounded-to-zero". A multi-job probe with non-trivial per-job telemetry was needed to make the result unambiguous.

## 2. Architecture context — the two LLM-cost paths in Lupin

| Path | Auth mechanism | Code location | Billing |
|---|---|---|---|
| **Bounded ClaudeCodeJob** (CJ Flow, `task_type=BOUNDED`) | Claude Code CLI / Claude Agent SDK using Max-subscription OAuth token | `src/cosa/agents/claude_code/job.py`; routes through `_dir_listing.py` agentic pool dispatch | **Covered by Max plan — zero per-token cost** |
| **Direct Anthropic SDK** | `ANTHROPIC_API_KEY_FIREWALLED` env var → `AsyncAnthropic( api_key=... )` | `src/cosa/agents/utils/proxy_agents/base_config.py:88` `get_anthropic_api_key()`; consumed by `deep_research/`, `podcast_generator/`, `presentation_generator/`, `notification_proxy/strategies/llm_fallback.py`, `decision_proxy/` | **Billed per token against the firewalled key's Anthropic account** |

The "firewalled" naming is intentional defense-in-depth: the API key lives in env as `ANTHROPIC_API_KEY_FIREWALLED`, **not** as `ANTHROPIC_API_KEY`, so even a process that inherits the env doesn't accidentally pick it up via the Anthropic SDK's default auto-discovery (which looks for the bare `ANTHROPIC_API_KEY` name).

### Pre-experiment evidence (necessary but not sufficient)

A `grep` across `src/cosa/agents/claude_code/`, `src/scripts/`, and `src/conf/` for `ANTHROPIC_API_KEY` or `FIREWALLED` returned **zero** matches. This means the bounded CC code path does **not reference, propagate, or remap** the firewalled key. The SDK should therefore fall back to its OAuth Max auth — and Anthropic should bill against the Max subscription (zero marginal), not against the firewalled account.

This was strongly suggestive but not proof. The probe below is the proof.

## 3. Experiment design

### Question

Do bounded ClaudeCodeJob executions cause the firewalled Anthropic account's credit balance to drop, or are they entirely covered by the Max plan?

### Hypothesis

Console credit balance moves $0.00 despite the jobs reporting non-zero `cost_usd` telemetry. (Theory: telemetry is the SDK's local accounting; billing happens out of band against the OAuth Max-plan account.)

### Method

A probe script (`src/scripts/probe_cc_bounded_billing.py` — written as a throwaway, then **promoted to a committed reproducer**; see §8, which is authoritative over this sentence) submitted **10 bounded ClaudeCodeJobs** in **two clusters of 5**:

- **Cluster A — in-repo only (cheaper)**: Read/Grep/Write operations entirely within the repo file system. No web tools. Expected per-job cost telemetry: ~$0.10-$0.25.
- **Cluster B — web search + synthesis (expensive)**: WebSearch / WebFetch + multi-paragraph synthesis. Expected per-job cost telemetry: ~$0.20-$0.50.

Spacing: **uniform 60s wait** between every job (including between clusters) so Rick's Anthropic console UI had time to settle and any movement could be attributed to a specific job rather than to batched effects.

Auth path: same JWT-authenticated `/api/claude-code/submit` endpoint that production code uses. `task_type=BOUNDED`, `max_turns=8` for Cluster A, `max_turns=15` for Cluster B.

Observation method: Rick watched the live Anthropic console credit-balance UI throughout the run and for 10 minutes after completion.

### Anti-confounders considered

- **Same auth path as production?** Yes — JWT-auth + `/api/claude-code/submit` is the same path BFE/TFE use.
- **Same SDK invocation?** Yes — `ClaudeCodeJob.do_all()` is the agentic-pool execution code that all bounded jobs go through.
- **Bounded vs interactive?** Probe used `BOUNDED` (the migration-candidate mode). INTERACTIVE could plausibly be billed differently; that's a separate experiment if needed (not blocking).
- **Cache/aggregation delay in the console?** Mitigated by 10-minute post-run wait. Anthropic's billing pipeline typically reports within minutes.
- **Max plan quota saturation masking the cost?** Not relevant — we're measuring *whether the firewalled account is billed*, which is independent of the Max plan's own quota state.

## 5. Conclusion

**Theory confirmed.** Bounded ClaudeCodeJobs are paid for by the Claude Code Max 200 plan via OAuth subscription auth. The firewalled Anthropic API key is never touched by this path. The job-record `cost_usd` field is SDK-reported telemetry for local accounting and observability, NOT an actual API charge.

This is now the authoritative empirical basis for the migration policy below.

## 6. Migration policy

### Rule

When designing a new LLM-driven agent OR refactoring an existing one, **prefer the bounded `ClaudeCodeJob` pattern over direct Anthropic SDK calls** that use `ANTHROPIC_API_KEY_FIREWALLED`. Migration shifts cost from per-token metered spend → fixed Max-plan spend.

**Important framing**: this is a **cost-shift, not a zero-cost**. The Max 200 plan is a fixed monthly bill. The migration converts metered cost into already-paid fixed cost. Claude Code should not propose migrations as "free" — propose them as "covered by existing fixed cost."

### Already migrated (precedent)

- **BFE** (`src/cosa/agents/bug_fix_expediter/`) — autonomous bug-fix workflow via Claude Code CLI.
- **TFE** (`src/cosa/agents/test_fix_expediter/`) — autonomous test-fix workflow.

Both have been running on bounded CC for some weeks and have already absorbed substantial Lupin LLM workload without firewalled-key charges.

### Migration candidates (TODO)

| Agent | Current path | Proposed path | Why |
|---|---|---|---|
| **Deep Research** (`src/cosa/agents/deep_research/`) | Direct `AsyncAnthropic` via firewalled key — multi-turn web research + synthesis pipeline | Bounded CC job with WebSearch / WebFetch tools | Long-running, async, batch-friendly. Largest current line-item on the firewalled bill. |
| **Podcast script generation** (`src/cosa/agents/podcast_generator/`) | Direct SDK for script-generation phase | Bounded CC job for script phase only (audio generation stays on whatever path it uses today) | Script generation is text-only, multi-turn synthesis — perfect fit. |
| **Presentation generation** (`src/cosa/agents/presentation_generator/`) | Direct SDK for content-generation phase | Bounded CC job for content phase (pptx assembly stays as-is) | Same shape as podcast — text synthesis with structured output. |

### When NOT to migrate

The bounded CC pattern has guardrails. **Do NOT migrate** if any of these apply:

1. **High-frequency tiny calls** (e.g., notification_proxy's LLM classifier at many-QPS) — SDK subprocess spawn overhead (~1-3s per invocation) dominates and breaks latency.
2. **Hard latency budget below ~2s** — same reason.
3. **Non-Anthropic models required** — Max plan only covers Claude. If the agent needs OpenAI, Groq, Mistral, etc., direct SDK is the only path.
4. **Token-by-token streaming UX** — bounded CC returns a result on completion; no progressive streaming back to the caller.

The notification proxy LLM fallback and decision proxy fall under (1) and (2) — keep them on direct SDK.

### Off-peak scheduling rule (operational)

Even though bounded CC is "free" in marginal cost terms, **Max-plan usage is not infinite** — the plan has rolling-window usage limits that, if exhausted, throttle Rick's interactive Claude Code work.

**Rick's daily usage pattern**:
- **Peak (9 PM – 12 AM EDT)** — heavy interactive Claude Code work; do NOT compete with scheduled bounded jobs.
- **Off-peak (12 AM – 9 PM EDT)** — fine for ad-hoc bounded jobs.
- **Optimal window (12 AM – 9 AM EDT)** — Rick asleep, zero interactive use; ideal for batch/long-running scheduled jobs.

**Rule**: For any bounded CC job that does NOT need to complete synchronously (i.e., batch / async work like podcast generation, deep research, overnight test sweeps), **schedule for the post-midnight window** using the existing `scheduled_at` field on `/api/claude-code/submit` (supported in `ClaudeCodeQueueRequest` at `src/cosa/rest/routers/claude_code_queue.py:49`).

Example payload:
```json
{
  "prompt"       : "…",
  "project"      : "lupin",
  "task_type"    : "BOUNDED",
  "scheduled_at" : "2026-05-13T02:30:00-04:00",
  "max_turns"    : 15
}
```

User-interactive bounded jobs (e.g., user clicks "regenerate this section") are exempt from the off-peak rule — they run immediately.

## 9. Open dependencies / follow-on questions

Not blocking this policy, but worth noting:

1. **INTERACTIVE-mode billing**: This probe only tested `task_type=BOUNDED`. INTERACTIVE jobs (bidirectional, longer-lived) could in principle be billed differently. If a future migration considers an interactive variant, re-confirm.
2. **Cache-hit jobs**: Two cluster B jobs (B3, B5) had longer elapsed times (60-70s) suggesting longer reasoning chains. Cache-hit semantics (`is_cache_hit` in the job record) for these — not investigated. Doesn't affect billing conclusion but worth understanding for performance modeling.
3. **A4 streaming-chunk failure**: `src/cosa/agents/claude_code/job.py:339` streaming-parse fragility under large file inputs. Independent of this policy but should be filed as a bug for the next time someone touches that module.
