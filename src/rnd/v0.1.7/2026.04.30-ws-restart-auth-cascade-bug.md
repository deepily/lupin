## Findings (server-side, code-grounded)

### Bug A — Mislabeled error message
**Location**: `src/cosa/rest/routers/websocket.py:458-459`

```python
except Exception as e:
    print( f"[WS-QUEUE-AUTH] ❌ Token verification failed for session [{session_id}]: {type( e ).__name__}: {e}" )
```

The `try` block at `:422-449` covers both `verify_token(token)` (line 424) **and** the post-auth `await websocket.send_json({"type": "auth_success", ...})` (line 444). When the socket dies between verify-success and auth_success-send, the `WebSocketDisconnect` raised by `send_json` is caught here and printed as "Token verification failed" — even though the token verified fine.

This misled my initial reading of the trace and would mislead any operator scanning logs. Fix: separate the two concerns into nested try blocks, or distinguish in the print message which step failed.

### Bug B — Cascading send-on-closed-socket
**Location**: `src/cosa/rest/routers/websocket.py:462-466`

```python
await websocket.send_json({
    "type"    : "auth_error",
    "message" : str( e )
})
await websocket.close()
return
```

After Bug A's mislabel, the same except block tries to `send_json({"type": "auth_error", ...})` on the socket that's **already** dead — that's why `send_json` failed in the first place. This produces a second `WebSocketDisconnect`, which falls through to the outer `except Exception` at `:473-481` as `RuntimeError: Cannot call "send" once a close message has been sent`.

Fix: wrap the `send_json` + `close` calls inside a `try: ... except Exception: pass` (matching the pattern already used at `:359-360` and `:477-480`).

### Smell C — Zombie session in `websocket_manager`
**Evidence**: `[WS] emit_to_user: notification_queue_update to user 0cf47e2d-... — sent_count=0 (sessions=1)`

`sessions=1` means one connection is registered for the user; `sent_count=0` means the message was sent to zero of them. The registered connection's underlying socket is dead but the `websocket_manager` entry was never reaped. If the only registered session for a user is a zombie, the UI will stay silent even after a fresh socket reconnects — depending on how `websocket_manager.connect()` reconciles a duplicate session_id.

**TODO for next session**: read `websocket_manager.connect()` and `disconnect()` paths; check whether `connect()` replaces an existing entry under the same `session_id`, or whether it appends a second (and emit_to_user iterates over all of them — including the zombie).

## Client-side reconnect path (for context)

`src/fastapi_app/static/js/notifications.js`:

| Concern | Line(s) |
|---------|--------|
| Queue WS lifecycle (`onopen` → `authenticateQueueWebSocket`, `onclose` → `scheduleReconnect`) | 2143-2191 |
| `authenticateQueueWebSocket` — sends `auth_request` with bare token + subscribed_events | 2246-2274 |
| `auth_success` handler — clears retry counter, calls `loadInitialData()` | 2308-2320 |
| `auth_error` handler — single-shot token refresh then `connectWebSockets()`; redirect to login on second failure | 2322-2347 |
| `scheduleReconnect` — exponential backoff capped at 30s (60s after 10 retries) | 5606-5624 |

The client's reconnect loop **looks correct** for a transient 1012 — first attempt at 2s should fail (server still down), 4s, 8s should succeed. If the user is reporting **permanent** UI breakage (i.e. requires page reload), that points away from backoff timing and toward either:

- Token actually expired across the downtime → would surface as `auth_error: Token expired`. Single refresh attempt is wired (`:2328`).
- `websocket_manager` zombie reconciliation → fresh socket auths fine but server still emits to the dead entry instead of the new one.
- Race: `connect()` overwrites + `disconnect()` (from old socket's onclose handler firing late) wipes the new entry.

## Resolution (2026-05-01 Session f742b1bc)

**Actual root cause was different from this doc's hypothesis.** The cascade traceback at the top of this doc was real but cosmetic — the user-visible "30s to 2min unable to connect" symptom was a separate bug entirely.

### What the user actually sees

When the user answered the three deferred §Open Questions:
1. **Duration**: "30 seconds to a couple minutes — incredibly annoying" (not permanent until reload).
2. **Browser-console state**: "the page displays the default browser unable to connect" — i.e. the Chrome `ERR_CONNECTION_REFUSED` page itself, NOT a Lupin-side `auth_error` or a JS-level disconnect banner.
3. **Trigger**: "passage of time" — no manual restart, no `--reload` from a save, just sitting there.

That combination ruled out the original hypothesis (1012-after-restart cascade, zombie session in `websocket_manager`). If the browser is showing `ERR_CONNECTION_REFUSED` against `localhost:7999`, the server-port itself is unbound at that moment — which on a healthy container can only happen during a uvicorn reload window.

### Diagnosis

Per docker logs, the dev container has `RestartCount: 0`, healthy, no OOM, no signal — so it's not the container cycling. But uvicorn `--reload` (StatReload) was firing repeatedly on test files in `src/tests/` (`test_voice_persona_helpers.py`, `test_voice_persona_allocation.py`). One concrete burst on 2026-05-01 between 02:08 and 02:15 UTC: 8 reloads in 7 minutes. Each reload tears down the server and rebuilds it; the rebuild takes 12-18 seconds before `Application startup complete` re-fires. During that window port 7999 is unbound — exactly the user's symptom.

`uvicorn.run()` in `src/fastapi_app/main.py` was launching with `reload=not is_production_or_test` and **no scope-narrowing**, so the entire `/var/lupin/src` tree was watched, including `tests/` and the LanceDB long-term-memory store at `conf/long-term-memory/lupin.lancedb/...` (which writes constantly at runtime).

### Fix

`src/fastapi_app/main.py:846-862` — switched from a default-watch-everything `reload=True` to a `reload_dirs` whitelist:

```python
reload_kwargs = {}
if not is_production_or_test:
    reload_kwargs[ "reload" ] = True
    reload_kwargs[ "reload_dirs" ] = [ "fastapi_app", "cosa", "lib", "lupin_cli", "lupin_mcp" ]
uvicorn.run(
    "fastapi_app.main:app",
    host="0.0.0.0",
    port=port,
    workers=1,
    log_level="info",
    **reload_kwargs
)
```

### False starts (worth recording)

1. **First patch — `reload_excludes=["tests/*", "rnd/*", ...]`**: failed because uvicorn's StatReload uses `Path.match()` for pattern matching, where `*` matches a single path segment only (not `/`). `tests/*` does NOT match `tests/unit/foo.py`. Verified empirically by touching a test file post-bounce and seeing StatReload still fire.

2. **Second patch — `reload_excludes=["tests/**/*", ..., "**/*.lance/**"]`**: pegged CPU during reload-watcher init. The `**/*.lance/**` glob walks every subdirectory of every `.lance` directory, and LanceDB's `gist_cache.lance/`, `prediction_decisions.lance/`, etc. each contain hundreds of `_versions/`, `_transactions/`, and `data/` entries. The container hung past `[LUPIN] Starting FastAPI server` for several minutes with the python process pegged at 99% CPU — the watcher was enumerating the long-term-memory tree.

3. **Final patch — `reload_dirs` whitelist**: 5 explicit runtime code dirs. `Will watch for changes in these directories: ['/var/lupin/src/cosa', '/var/lupin/src/fastapi_app', '/var/lupin/src/lib', '/var/lupin/src/lupin_cli', '/var/lupin/src/lupin_mcp']` — verified banner. Touching test files post-bounce produces zero StatReload events. Verified.

### Bugs A + B still open (cosmetic)

The original §Findings — Bug A (mislabeled "Token verification failed" log) and Bug B (cascading send_json on closed socket) at `websocket.py:458-466` — are real but log-hygiene-only. Both <10 line fixes. Held for a follow-up commit since they don't affect the user-visible symptom.

### Open question (parked)

**What's bumping test file mtimes?** Even after the fix, the underlying question of why `tests/unit/test_voice_persona_helpers.py` and `tests/smoke/test_voice_persona_allocation.py` are getting their mtimes touched at irregular intervals (02:08, 02:14, 09:12 today) without anyone running tests is unexplained. Plausible suspects: backup script, IDE indexer, hook, periodic git operation. Not blocking now that reload ignores them, but worth tracing if it surfaces another way.

### Smell C verdict

The `websocket_manager` zombie-session smell (`sessions=1, sent_count=0`) was a **byproduct** of the reload cascade — a fresh socket that couldn't fully reconcile with the dying instance during the 12-18s reload window. Not investigated further; with reloads no longer firing on test/lancedb writes, the trigger condition for the zombie state is gone. If it ever surfaces again outside a real restart, audit `WebSocketManager.connect()` for stale-entry reconciliation as previously planned.
