## Phase 5 — Cluster A: notification 503 cascade diagnosis

**Started**: 2026-05-01T13:00 EDT
**Completed**: 2026-05-01T13:20 EDT
**Status**: ✅ ROOT CAUSE IDENTIFIED — fix deferred to follow-up bug entry (out of scope for this session)

### Root cause (concrete, file:line evidence)

The 503 cascade is **NOT transient and NOT yesterday-only**. Fresh container logs from 2026-05-01 show the exact same pattern firing right now in unrelated test runs:

```
POST /api/notify?...response_type=open_ended_batch&...&sender_id=arg.expeditor%40lupin.deepily.ai...
  HTTP/1.1" 503 Service Unavailable
✗ Failed to send notification: HTTP 503
[Expeditor] _batch_collect_args response: success=False, status=http_error_503, exit_code=1
```

**Server-side trigger**: `src/cosa/rest/routers/notifications.py:727-731` — the `/api/notify` endpoint raises **HTTP 503** when:
1. The `target_user` has NO active WebSocket connection (`user is offline`), AND
2. The request body has no `response_default` field set

**Client-side gap**: `src/cosa/agents/runtime_argument_expeditor/expeditor.py:821-833` — `_batch_collect_args` builds the `NotificationRequest` WITHOUT a top-level `response_default`. Per-question `default_value` fields are nested inside `response_options` and not consulted by the offline-user 503 check.

**Why calc/CRUD passed in the same test run**: those scenarios don't go through the expediter at all (mode-routed, no notifications needed). Only the expediter-flow scenarios (DR/PG/RTP/SWE) hit `_batch_collect_args` → /api/notify → 503.

**Why the auto-proxy didn't help**: log shows `[NOTIFY] User interactive.job.tester@lupin.deepily.ai (50c73ba7-...) is not connected - notification not delivered`. The auto-proxy server does NOT maintain a WS connection for the test user, so the user is "offline" from the server's perspective and the 503 fires before any proxy can intercept.

### Why this isn't fixed in this session

The clean fix has **multiple plausible owners** and is bigger than a single edit:

| Option | Owner | Risk |
|--------|-------|------|
| A. Server: for `response_type=open_ended_batch`, synthesize `response_default` from per-question `default_value` fields when offline | Server (notifications.py) | Medium — changes 503 contract |
| B. Client: expediter sets a JSON-encoded `response_default` (e.g. `{"answers": {...defaults...}}`) so offline path returns the synthesized default | Client (expeditor.py) | Low-medium — defensive, doesn't change server |
| C. Test harness: auto-proxy server opens & maintains a WS connection for `interactive.job.tester` so the user is "online" during scenarios | Auto-proxy / test harness | Higher complexity but most "correct" |
| D. Test-runner: smoke harness pre-flights `/api/notify` with a probe and aborts the suite early with a clear "notification dispatch unavailable" message rather than running 21 scenarios that will all 503 | Smoke harness | Low — informational only |

**Picking ONE without a longer design conversation is premature**. Option B is the most surgical (single function), but it changes implicit semantics. Option C is the "right" fix but spans the proxy server I haven't read. Option D is unconditionally helpful and should land regardless.

### What I am doing in this session

1. **Filing as a high-confidence follow-up bug** in `bug-fix-queue.md` Queued at session-end (with this evidence + the 4 options).
2. **Implementing Option D** (smoke-harness label improvement) — surface the cascade as 1 infra failure not 21 cancellations on next run. (Still pending — will land in Phase 7 wrap-up if time permits, or filed for next session.)

## Phase 7 — Cluster C: synchronous preflight at submit endpoint

**Started**: 2026-05-01T14:05 EDT
**Completed**: 2026-05-01T14:15 EDT
**Status**: ⚠️ DOCUMENTATION-ONLY — full implementation blocked on architectural constraint, filed as follow-up

### Architectural blocker found

The plan called for `POST /api/test-suite/submit` to synchronously run `src/scripts/preflight-test-container.sh` and return HTTP 412 if it fails. **This is not possible from the endpoint** because:

1. The FastAPI server runs INSIDE the test container (`lupin-rest-test`).
2. `preflight-test-container.sh` runs `docker exec` / `docker inspect` against the host's docker daemon.
3. The test container does NOT mount the docker socket (and doing so has security implications for the production deployment surface).
4. The preflight smoke test (Phase 1A subject) already correctly skips inside the container precisely because the docker daemon is unreachable.

So the "synchronous preflight at submit" pattern needs either:
- a) A server-side surrogate that checks fixture presence + bind-mount paths from within the container (duplicating the script logic without docker calls), OR
- b) A pre-submit hook in whatever client invokes /api/test-suite/submit (UI / slash command / scheduler), running preflight on the host before posting, OR
- c) Mounting the docker socket into the test container (not preferred).

Choosing among (a)/(b)/(c) is a design decision beyond this session's scope.

### What I did instead

1. **Documented the constraint in the endpoint's docstring** (`src/cosa/rest/routers/test_suite.py:104-125`) so future readers don't re-encounter the same dead-end. The docstring now explicitly references the post-mortem and the workaround (run preflight from host before submitting).

2. **Filing as follow-up** in bug-fix-queue.md (Wrap-up phase): "Server-side preflight surrogate for /api/test-suite/submit (2026-05-01 Phase 7 deferred)".

### Verification
