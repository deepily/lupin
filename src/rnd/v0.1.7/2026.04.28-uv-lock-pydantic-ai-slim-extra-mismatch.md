# `uv sync --locked` fails — `pydantic-ai==0.6.2` lockfile records non-existent `[slim]` extra

**Audience**: external Python-packaging / `uv` expert.
**Status**: build-blocking. Repro is deterministic.
**Project**: Lupin (FastAPI app on Python 3.13). `pyproject.toml` is uv-managed; `uv.lock` is committed.

---

## TL;DR

In our `Dockerfile`, `uv sync --locked --no-install-project` exits non-zero with:

```
warning: The package `pydantic-ai==0.6.2` does not have an extra named `slim`
The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
To update the lockfile, run `uv lock`.
```

The lockfile was generated previously (per the `pyproject.toml` header comment) with `ghcr.io/astral-sh/uv:0.8 uv lock`. That older lock pass produced an internally inconsistent lockfile: it recorded `extras = ["slim"]` for `pydantic-ai` even though the published wheel/sdist for `pydantic-ai==0.6.2` on PyPI exposes **no** `slim` extra. A more recent `uv 0.8.x` now enforces this consistency under `--locked`, breaking our build.

We need a recommendation on the right *durable* fix, not just a workaround.

## Evidence

### A. `pyproject.toml:53`

```toml
"pydantic-ai[slim]==0.6.2",
```

The dependency is declared with the `[slim]` extra and pinned to exactly `0.6.2`.

### B. `uv.lock:2087` — recorded ask

```toml
{ name = "pydantic-ai", extras = ["slim"], specifier = "==0.6.2" },
```

The lockfile faithfully records that the user asked for the `slim` extra.

### C. `uv.lock:3096-3106` — resolved package metadata

```toml
[[package]]
name = "pydantic-ai"
version = "0.6.2"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "pydantic-ai-slim", extra = ["ag-ui", "anthropic", "bedrock", "cli",
      "cohere", "evals", "google", "groq", "huggingface", "mcp", "mistral",
      "openai", "retries", "vertexai"] },
]
sdist = { url = "https://files.pythonhosted.org/packages/.../pydantic_ai-0.6.2.tar.gz", ... }
wheels = [
    { url = "https://files.pythonhosted.org/packages/.../pydantic_ai-0.6.2-py3-none-any.whl", ... }
]
```

Critical observation: the resolved `pydantic-ai==0.6.2` has **no `[package.optional-dependencies]` table**. The published metadata exposes zero extras at the meta-package level. The 14 extras listed are all on the *transitive* `pydantic-ai-slim` dep, not on `pydantic-ai` itself.

### D. `uv.lock:3108+` — `pydantic-ai-slim` is a separate package

```toml
[[package]]
name = "pydantic-ai-slim"
version = "0.6.2"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "eval-type-backport" },
    { name = "griffe" },
    { name = "httpx" },
    { name = "opentelemetry-api" },
    { name = "pydantic" },
    { name = "pydantic-graph" },
    { name = "typing-inspection" },
    ...
]
```

So `pydantic-ai` is a small meta-package that simply pulls `pydantic-ai-slim` (with all 14 sub-extras) transitively. Whatever `[slim]` was *meant* to add at the meta-level is already added by the transitive dep.

### E. PyPI direct verification

`pip show pydantic-ai==0.6.2` (out-of-band): the `Provides-Extra:` field is empty for the meta-package. Only `pydantic-ai-slim==0.6.2` exposes extras (the same 14 listed above).

## Hypothesis

The lockfile is internally inconsistent — it persists an extras spec that the resolved package metadata doesn't validate. We suspect one of:

1. **Earlier `uv` was lenient** about unknown extras during `uv lock` (treated unknown extras as no-ops without warning), then `uv 0.8.x` tightened the rule. The on-disk lock predates the tightening; running `uv lock` again with current uv would surface the warning at lock time and either drop the extra or error out.
2. **`pydantic-ai`'s published metadata once exposed `slim` as a meta-extra and was later removed** (in a re-upload or a different sub-version) without changing the version number. (We have not verified release-history evidence of this — open question for the expert.)
3. **uv resolver bug**: the lock writer accepted `extras = ["slim"]` as user-input without cross-checking the resolved package's metadata.

The build failure is correct behavior on uv's part — the lockfile *is* inconsistent. The question is whether the right fix is (a) drop the extra in `pyproject.toml`, (b) switch to depending on `pydantic-ai-slim` directly, (c) bump the `pydantic-ai` version, or (d) something else we haven't seen.

## Potential solutions

### Option 1 — Drop the `[slim]` extra (recommended)

```diff
- "pydantic-ai[slim]==0.6.2",
+ "pydantic-ai==0.6.2",
```

Then `uv lock` (host or in container) → commit `pyproject.toml` + `uv.lock` together → rebuild.

**Pros**:
- Smallest possible change.
- Functionally a no-op: the 14 sub-extras under `pydantic-ai-slim` are *already* transitively included by the meta-package's own dependency declaration. Dropping the meta-level `[slim]` loses nothing.
- Internal consistency restored.

**Cons**:
- Doesn't answer *why* the extra was specified originally. If a previous engineer believed `[slim]` was load-bearing, we're invalidating a (possibly) intentional choice without understanding it.
- Doesn't fix the root cause (whatever produced the inconsistent lock could re-occur for another package).

### Option 2 — Depend on `pydantic-ai-slim` directly with explicit extras

```diff
- "pydantic-ai[slim]==0.6.2",
+ "pydantic-ai-slim[anthropic,openai,google,mcp]==0.6.2",   # or whichever subset we actually need
```

**Pros**:
- More explicit; documents which providers we use.
- Drops the meta-package indirection.

**Cons**:
- Requires identifying *which* of the 14 transitive extras the codebase actually uses (non-trivial audit — the codebase touches Anthropic, OpenAI, Google, possibly MCP).
- Larger surface change; risk of dropping an extra that's used somewhere.
- Doesn't solve the "why was the lock inconsistent" question either.

### Option 3 — Bump `pydantic-ai` to a newer version that exposes a `slim` extra at the meta level

**Cons**:
- Out of scope for a build-fix. Mixes two changes (build fix + dep bump).
- We don't know which version (if any) exposes `slim` as a meta-extra. Searching pydantic-ai's GitHub releases would be necessary.
- Risks unrelated transitive churn (especially across the 295 resolved packages).

### Option 4 — Switch the Dockerfile to non-`--locked` resolve

```diff
- uv sync --locked --no-install-project
+ uv sync --no-install-project
```

**Cons**:
- Removes the reproducibility guarantee that motivated using `uv` in the first place.
- Hides the underlying inconsistency rather than fixing it.
- Strongly disrecommended.

## Open questions for the expert

1. **Provenance**: Has `pydantic-ai==0.6.2`'s published metadata changed since 2025-08-07? If so, where is that history visible, and how does uv handle a lockfile whose recorded extras have since been retracted upstream?
2. **`uv` behavior**: Is there a `uv` version diff that would explain why `uv sync --locked` previously succeeded with this lockfile and now fails? Specifically — at what `uv` version was extra-validation-on-`--locked` introduced or tightened?
3. **Tooling**: Is there a `uv lock --check` (or equivalent) we should add to CI to catch this kind of drift earlier, before it surfaces in a Docker build?
4. **`pydantic-ai` design intent**: Was `pydantic-ai[slim]` ever the intended meta-extra surface, or is `pydantic-ai-slim` the canonical direct dep for slim users? (i.e., should Option 1 or Option 2 be preferred from a `pydantic-ai` upstream perspective?)
5. **Should we file a `uv` bug** for "lock writer accepts user-spec extras that the resolved package's metadata does not expose, producing an internally inconsistent lockfile that later fails `--locked`"? Or is that already triaged?

Expected (the bug we're seeing): step 2 fails with the warning and non-zero exit. If step 1 silently writes a lockfile with `extras = ["slim"]` (matching our state), the lock writer is the culprit. If step 1 itself errors, behavior has tightened across uv patch versions.
