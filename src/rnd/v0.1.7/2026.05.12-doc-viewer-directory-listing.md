# Doc Viewer — Directory Listing Extension

## 1. Context

The Lupin document viewer lives at `/app/docs?path=<file>&scope=<docs|io>`. Today it renders a SINGLE file: the frontend (`document-viewer.html`) fetches `/api/docs/file?path=...` (or `/api/io/file`), receives `text/markdown` (or other text type), and pipes it through `marked.js` + `DOMPurify` into the DOM.

If `path` resolves to a directory, the backend currently returns `404 File not found` (rejected at `src/cosa/rest/routers/docs_files.py:119` by the `os.path.isfile` gate).

**The ask**: extend the viewer so that when `path` resolves to a **whitelisted directory**, the endpoint returns a clickable listing of that directory's children (subdirectories + viewer-renderable files), each entry linking back into the viewer at the deeper path. This turns the viewer into a lightweight, scope-bounded directory browser — useful for navigating `src/rnd/`, `src/docs/`, `src/workflow/` without leaving the browser and without an external file-tree UI.

**Why this is worth doing**:
- 20+ existing call sites in the codebase emit `/app/docs?path=<file>` URLs (notifications.js, deep_research/cli.py, podcast_generator, presentation_generator). All point at files. Once directory listings work, the same URL scheme can point at containers — e.g., a job done-notification can deep-link to a job's parent directory and let the user browse siblings.
- R&D plans live in dated directories under `src/rnd/v0.1.7/` (e.g., `2026.05.02-notifications-ui-js-refactor/` has 20+ files inside). The viewer can't currently surface those sub-trees.
- A scope-bounded browser is materially safer than a generic file-tree view — the existing whitelist (`src/docs/`, `src/rnd/`, `src/workflow/`, root-level whitelisted `*.md`) caps what's reachable.

**Out of scope for this design** (after Q1 resolution — scope=io is IN):
- Per-user auth gating — current `/api/docs/file` and `/api/io/file` are both public; staying consistent.
- Recursive tree view — one-level listings only; user drills in via clicks.
- Pagination — directory listings are small (max ~30 entries in practice for `src/rnd/`); no pagination needed.
- New viewer pages — mp3/wav use the existing `/app/audio` player, md/etc use the existing `/app/docs` viewer, pdf renders inline via direct `/api/io/file` link, pptx force-downloads. No new HTML pages.

## 3. Proposed design

### 3.1 Endpoint contract — polymorphic on BOTH `/api/docs/file` AND `/api/io/file`

Same polymorphism applied to **both** endpoints (per Q1 resolution). `GET /api/docs/file?path=<relative-path>` and `GET /api/io/file?path=<relative-path>` each become polymorphic by `Content-Type`:

| Resolution | Status | `Content-Type` | Body |
|---|---|---|---|
| `os.path.isfile(full_path)` | 200 | `text/markdown` / `text/plain` / etc. (per ext) | raw file text (UNCHANGED) |
| `os.path.isdir(full_path)` | 200 | `application/json` | directory listing JSON (see 3.2) |
| Whitelist miss | 400 | `application/json` | `{detail: "Path not in docs whitelist: ..."}` |
| Traversal artifact | 400 | `application/json` | `{detail: "Invalid path: must be within project root"}` |
| Whitelisted but missing | 404 | `application/json` | `{detail: "Path not found: ..."}` (UPDATED wording — previously "File not found") |
| Path is file with non-whitelisted ext | 400 | `application/json` | `{detail: "Unsupported file type: .xyz"}` (UNCHANGED) |

**Why polymorphic over a new sibling endpoint** (e.g., `/api/docs/list`):
- Single round-trip — frontend doesn't need to probe with HEAD first.
- Whitelist + traversal checks shared (DRY).
- No new URL surface to deprecate later.
- File responses unchanged → all 20+ existing callers keep working with zero edits.
- Frontend dispatch on `Content-Type` is a clean, well-trod pattern.

**Why allow a sibling endpoint instead**: arguably more REST-orthodox (one resource shape per endpoint). Rejected because the cost (extra fetch, divergent error handling) outweighs the purity benefit for this internal API.

### 3.2 Directory listing JSON shape (mtime dropped per Q3)

```json
{
  "kind": "directory",
  "scope": "docs",
  "path": "src/rnd/v0.1.7",
  "parent": "src/rnd",
  "entries": [
    {
      "name": "2026.05.02-notifications-ui-js-refactor",
      "kind": "directory",
      "size": null,
      "rel_path": "src/rnd/v0.1.7/2026.05.02-notifications-ui-js-refactor",
      "view_url": "/app/docs?path=src%2Frnd%2Fv0.1.7%2F2026.05.02-notifications-ui-js-refactor&scope=docs"
    },
    {
      "name": "2026.04.24-cosa-voice-nested-repo-detection-fix.md",
      "kind": "file",
      "size": 4170,
      "rel_path": "src/rnd/v0.1.7/2026.04.24-cosa-voice-nested-repo-detection-fix.md",
      "view_url": "/app/docs?path=src%2Frnd%2Fv0.1.7%2F2026.04.24-cosa-voice-nested-repo-detection-fix.md&scope=docs"
    }
  ]
}
```

For `scope=io` listings, an audio entry would look like:
```json
{
  "name": "episode-01.mp3",
  "kind": "file",
  "size": 8421076,
  "rel_path": "podcasts/my-show/episode-01.mp3",
  "view_url": "/app/audio?path=podcasts%2Fmy-show%2Fepisode-01.mp3"
}
```

**Field semantics**:
- `kind` — always `"directory"` at top level; per-entry `"file"` or `"directory"`
- `scope` — `"docs"` or `"io"`. Lets the frontend derive subsequent links + tells callers which whitelist applied. Echoed from the request (inferred from which endpoint served the response).
- `path` — the resolved relative path that was listed (normalized — trailing slashes stripped)
- `parent` — `os.path.dirname(path)` if that parent is itself whitelisted; otherwise `null`. Lets the frontend decide whether to render an "up to parent" link.
- `entries[].size` — bytes for files; `null` for directories
- `entries[].rel_path` — pre-computed full relative path
- `entries[].view_url` — **server-built link to the appropriate viewer/player/download URL** per the per-extension routing table below (§3.4a). Frontend uses this directly — no extension-sniffing in the JS.
- (NO `mtime` field — dropped per Q3 resolution.)

### 3.3 Whitelist tweak — bare prefix root browsing

Current `_is_whitelisted("src/rnd")` returns `False` (only `src/rnd/` with trailing slash passes the `startswith` check, since the prefix is `src/rnd/`). The user expects both forms to work.

**Fix**: `_is_whitelisted` accepts the path if any of:
1. `path in ALLOWED_FILES` (existing — exact match)
2. `any(path.startswith(prefix) for prefix in ALLOWED_PREFIXES)` (existing — children of prefix)
3. `path == prefix.rstrip("/") for prefix in ALLOWED_PREFIXES` (NEW — bare prefix root, e.g. `src/rnd`)

This is a minimal surface change: existing semantics preserved, plus one new accepting clause.

### 3.4 Entry filtering rules

| Entry type | Include? | Rationale |
|---|---|---|
| Subdirectory (not starting with `.`) | YES | User can drill in |
| Subdirectory starting with `.` (e.g., `.git`, `.coverage`) | NO (per Q5) | `ls` convention; no value in surfacing dotfiles |
| File with extension in endpoint's `MEDIA_TYPES` whitelist | YES | A viewer/player/handler exists for it |
| File with extension NOT in `MEDIA_TYPES` (e.g., `.py`, `.png`) | NO | No handler exists; entry would be a dead link |
| File starting with `.` (e.g., `.DS_Store`) | NO (per Q5) | Hidden files always excluded |
| Symlinks | List as-is (no special handling) | Same posture as the existing handler |

`scope=docs` MEDIA_TYPES: `.md, .txt, .json, .yaml, .yml` (text only — same set used today).
`scope=io` MEDIA_TYPES: `.md, .txt, .json, .yaml, .yml, .mp3, .wav, .pdf, .pptx` (same set the io handler accepts today).

### 3.4a Per-extension link routing (NEW — drives `view_url` builder, per Q1 resolution)

For each file entry, the backend builds `view_url` using this table:

| Extension(s) | scope | `view_url` shape | Why |
|---|---|---|---|
| `.md`, `.txt`, `.json`, `.yaml`, `.yml` | `docs` | `/app/docs?path=<rel>&scope=docs` | Existing doc viewer renders markdown/text/json/yaml |
| `.md`, `.txt`, `.json`, `.yaml`, `.yml` | `io` | `/app/docs?path=<rel>&scope=io` | Same viewer; just different scope |
| `.mp3`, `.wav` | `io` | `/app/audio?path=<rel>` | Existing audio player page (`audio-player.html`) — offers play + download button. Per Q1: NOT a download URL. |
| `.pdf` | `io` | `/api/io/file?path=<rel>` | Browser renders PDF inline natively from `Content-Type: application/pdf` |
| `.pptx` | `io` | `/api/io/file?path=<rel>&download=true` | No browser-native viewer; force download via existing `download` flag in `io_files.py:50,131-145` |
| (Subdirectory) | either | `/app/docs?path=<rel>&scope=<scope>` | Drills back into the doc viewer's directory listing |

The frontend uses `view_url` as-is — no JS-side extension sniffing. This keeps the routing rule canonical in one place (the backend) and prevents drift.

### 3.5 Sort order

1. **Group**: subdirectories first, then files (canonical browser convention)
2. **Within group**: case-insensitive alphabetical by `name`

No mtime-based sort — users browsing R&D mostly know what they're looking for by name, not by recency. (Alternative considered: newest-first by mtime, useful for "what changed recently?" — rejected as a default but could be added as `?sort=mtime` query param later if desired.)

### 3.5a Sort order (per Q4 resolution — confirmed default)

1. **Group**: subdirectories first, then files
2. **Within group**: case-insensitive alphabetical by `name`

No mtime-based sort. Reverse-alpha within the file group (which would surface newest YYYY.MM.DD-prefixed R&D docs first) was considered and rejected — alphabetical is more predictable.

### 3.6 Frontend rendering

Inside `document-viewer.html` inline JS:

```js
const response = await fetch( apiPath + '?path=' + encodeURIComponent( path ) );
if ( !response.ok ) { /* existing error path */ }

const contentType = response.headers.get( 'content-type' ) || '';

if ( contentType.includes( 'application/json' ) ) {
    const listing = await response.json();
    renderDirectoryListing( listing, scope );
} else {
    // existing markdown path — unchanged
    const markdown = await response.text();
    // ... existing frontmatter + marked + DOMPurify
}
```

**`renderDirectoryListing(listing)` responsibilities** (`scope` is read from `listing.scope`, not a separate param):
1. Set `document.title` to last segment of `listing.path` (or `"Lupin Docs"` / `"Lupin IO"` if path is a scope root)
2. Build breadcrumb HTML: split `listing.path` on `/`, each segment is a link to `/app/docs?path=<accumulated>&scope=<listing.scope>`
3. Render `<ul class="doc-dir-listing">` with one `<li class="doc-dir-entry">` per entry
4. Each entry: `<a href="<entry.view_url>"><span class="icon">📁|📄|🔊|📑|📊</span> <span class="name">...</span></a> <span class="doc-dir-meta">size</span>`
5. Icon picked client-side from `entry.kind` + filename extension (purely cosmetic — directory icon for dirs, audio icon for `.mp3`/`.wav`, pdf icon for `.pdf`, pptx icon for `.pptx`, generic doc icon otherwise)
6. `entry.view_url` is consumed AS-IS — no client-side URL construction (per §3.4a, the backend owns the routing rule)
7. Sanitize via `DOMPurify` before injection (same `ALLOWED_TAGS` + `ALLOWED_ATTR` as the markdown path — `class` is already permitted)
8. NO mtime rendered (per Q3 resolution)

**`_is_whitelisted`** (`:54-67`) — add bare-root clause:
```python
def _is_whitelisted( relative_path: str ) -> bool:
    if relative_path in ALLOWED_FILES:
        return True
    for prefix in ALLOWED_PREFIXES:
        if relative_path.startswith( prefix ):

        if relative_path == prefix.rstrip( "/" ):  # NEW: bare prefix root
            return True
    return False
```

**`_list_directory(abs_dir, rel_dir)`** (new helper, ~25 lines):
- `entries = []`
- For each `entry in os.scandir(abs_dir)`:
  - Skip if `entry.name.startswith(".")`
  - If `entry.is_dir(follow_symlinks=False)`:
    - Append `{name, kind:"directory", size:None, mtime:<YYYY-MM-DD>, rel_path:<rel_dir>/<name>}`
  - Elif `entry.is_file(follow_symlinks=False)`:
    - `ext = os.path.splitext(entry.name)[1].lower()`
    - If `ext not in MEDIA_TYPES`: skip
    - Stat for size + mtime
    - Append `{name, kind:"file", size, mtime, rel_path}`
- Sort: `entries.sort(key=lambda e: (e["kind"] != "directory", e["name"].lower()))`
- Compute `parent = os.path.dirname(rel_dir)` and clear to `None` if not `_is_whitelisted(parent)`
- Normalize `path` (strip trailing slash): `rel_dir.rstrip("/")`
- Return `{"kind": "directory", "path": rel_dir.rstrip("/"), "parent": parent, "entries": entries}`

## 6. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| Existing file callers break due to Content-Type dispatch | High → Low | File-response shape is UNCHANGED. Polymorphism only adds a branch for `isdir`. Verified by regression smoke. |

## 9. What this design explicitly does NOT do

- Does NOT add auth gating (consistent with current public `/api/docs/file` and `/api/io/file`)
- Does NOT change file-response shape or wire format (zero regression risk for 20+ existing callers — `text/markdown` etc. stay exactly as today)
- Does NOT add pagination (listings are small)
- Does NOT implement recursive tree view (one-level only; click-to-drill)
- Does NOT fix the latent `os.path.normpath` vs `os.path.realpath` symlink question (same posture as existing handler — out of scope for this change)
- Does NOT alter the whitelist contents — only adds a "bare prefix root" accepting clause to `_is_whitelisted` in `docs_files.py`
- Does NOT add new viewer/player pages — reuses existing `/app/docs`, `/app/audio`, and the browser's native pdf renderer
- Does NOT sniff file extensions in the frontend JS — all routing decisions live in the backend `_build_view_url` helper (single source of truth per §3.4a)
