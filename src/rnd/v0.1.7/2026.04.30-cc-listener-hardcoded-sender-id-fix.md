## Summary

`CCNotificationListener._send_gist_response()` builds the auto-receipt notification's `sender_id` with the project segment **literally hardcoded to `"lupin"`**, regardless of which repo the CC session is running in. When a CC session launched in a nested repo (e.g. `src/cosa/`) emits its first voice-receipt ACK, the notification routes under `claude.code@lupin.deepily.ai#<sid>` instead of `claude.code@cosa.deepily.ai#<sid>`. The notifications UI groups sender cards by `sender_id`, so the same `session_id` shows up under **two project labels** — the legitimate one from SessionStart-era notifications, plus a new ghost card under `[LUPIN]`.

---

## Bug Demonstration

User report (Session 406cadbf, 2026-04-30):

1. Started a fresh CC session inside `src/cosa/` with session ID `77dac746`.
2. Original notifications routed correctly under the CoSA sender card.
3. Spoke a voice message; the listener's `_send_gist_response()` fired with text `"Received: Why haven't you updated your..."`.
4. The receipt rendered as a **new sender card titled `[LUPIN]`** with the **same session_id `77dac746`**.

Result: dual-identity in the UI for what is logically one session.

---

## Root Cause

`src/lupin_cli/claude_code/hooks/lib/cc_notification_listener.py:453` (pre-fix):

```python
# Build sender_id matching the CC session format
sender_id = f"claude.code@lupin.deepily.ai#{self.session_id_hash}"
```

The project segment is a literal string. The 2026.04.24 nested-repo detection fix (`2026.04.24-cosa-voice-nested-repo-detection-fix.md`) repaired `detect_project()` inside the CoSA submodule's `sender_id.py`, which is why **most** notification paths (including the parallel `send_tts()` ACK at `permission_request.py:123`) now resolve project correctly via `build_sender_id_for_cc()` → `_resolve_project_from_bridge_cwd()`. That fix's audit didn't sweep the parent Lupin code for hardcoded `"lupin.deepily.ai"` strings, and this listener offender was missed.

### Why the bridge-anchored helper exists

`session_bridge.build_sender_id_for_cc()` was specifically designed for this scenario — see its docstring at `session_bridge.py:436-491`:

> Without this stabilization, the same CC session produces sender_ids alternating between e.g. `claude.code@lupin.deepily.ai#abc12345` and `claude.code@cosa.deepily.ai#abc12345` depending on where the bash subshell happens to be standing — which the notifications UI renders as duplicate sender cards for what is logically one session.

The listener pre-dates this helper (or its author wasn't aware of it) and rolled its own.

---

## Fix Strategy

Option 1 — **symmetric with `send_tts()`**: replace the hardcoded line with a call to `build_sender_id_for_cc()`, with an `or` fallback that retains the legacy hardcoded value if the helper returns `None`. Preserves failure-mode parity.

Other option considered (Option 2 — pass `project` at construction time): cleaner architecturally, larger blast radius. Deferred.
