# Lupin Dockerfile hygiene plan: April 2026 hardening

**Bottom line up front.** The Test Fix Expediter is right that you must move off 3.11.5, but the specific target of **3.11.9 is wrong** — it leaves you ~2 years behind on CVEs (CVE-2024-6923, CVE-2024-50602, CVE-2025-59375, CVE-2026-24515, CVE-2026-25210, plus quadratic-complexity fixes in `xml.dom.minidom`, `os.path.expandvars`, and use-after-free fixes in `ssl`/list internals — all landed in 3.11.10 → 3.11.15). The single highest-leverage change is **replacing `./configure --enable-optimizations` with `uv python install` backed by `python-build-standalone`**, which collapses a 10–15-minute PGO build into a ~20-second tarball extract while preserving identical `pgo+lto` performance. Combined with consolidating your 20+ `RUN pip install` lines into a single `uv sync --locked` under a BuildKit cache mount, your iteration-loop wall-clock drops by an order of magnitude in one PR. The April 2026 community canon (Astral, Hynek Schlawack, Itamar Turner-Trauring, vLLM, Hugging Face TGI) has converged on this exact pattern; everything else in this report is sequencing decisions around it.

## Tier 0 — Validate the Python target (do this before anything else)

**Push back on 3.11.9.** As of April 2026, latest 3.11.x is **3.11.15** (released 2026-03-03 in the joint 3.12.13 / 3.11.15 / 3.10.20 security release per `blog.python.org/2026/03/python-31213-31115-31020/`). 3.11 is in security-only mode per PEP 664, with EOL ~October 2027. There are **no pytest-, asyncio-, or ML-library-breaking regressions** in 3.11.10 → 3.11.15; the branch is strictly accumulative. The TFE's bug-fix concern (gh-97382) is satisfied by anything ≥3.11.6, so picking 3.11.9 specifically is gratuitous.

**Better still: jump to 3.12.13 or 3.13.13.** Your stated Python flexibility removes the only good reason to stay on 3.11. Compatibility as of April 2026:

## Tier 1 — Highest ROI, lowest risk (the "do this in one PR" set)

These six changes are mechanically safe, individually revertible, and collectively eliminate the build-time and reproducibility pain. They all stay inside your stated "consolidate RUN layers, pin deps, multi-stage" scope.

### 1. Replace the 15-minute CPython build with `uv python install`

`uv python install 3.12.13` downloads the `astral-sh/python-build-standalone` artifact for `x86_64-unknown-linux-gnu` — a `pgo+lto` build dynamically linked against glibc ≥2.17 (Ubuntu 22.04 ships 2.35, no skew), which loads C extensions normally and coexists cleanly with the CUDA runtime libraries already in `nvidia/cuda:12.2.2-base-ubuntu22.04`. **Performance is identical to your `--enable-optimizations` build** because `pgo+lto` is exactly what python-build-standalone publishes by default (`github.com/astral-sh/python-build-standalone/blob/main/docs/distributions.rst`). Project transferred from indygreg to Astral on 2024-12-17 and is now full-time-maintained (`astral.sh/blog/python-build-standalone`).

Critically, **do not** try `COPY --from=python:3.11-slim /usr/local /usr/local`: the `slim` tag now points at Debian trixie (glibc ≥2.41), and the resulting binary fails on Ubuntu 22.04 with `GLIBC_2.38 not found` errors — a well-documented failure mode in `actions/setup-python` issues #1053 and #1224. python-build-standalone exists precisely to solve this libc-skew problem.

```dockerfile
# syntax=docker/dockerfile:1.7
FROM nvidia/cuda:12.2.2-base-ubuntu22.04

COPY --from=ghcr.io/astral-sh/uv:0.8 /uv /uvx /usr/local/bin/

ENV UV_PYTHON_INSTALL_DIR=/opt/python \
    UV_PYTHON_PREFERENCE=only-managed \
    UV_LINK_MODE=copy \
    UV_COMPILE_BYTECODE=1 \
    PATH=/opt/python/bin:$PATH

RUN uv python install 3.12.13 && \
    ln -s "$(uv python find 3.12.13)" /usr/local/bin/python
```

Drop `build-essential`, `wget`, all the `lib*-dev` packages, and the `apt-get purge` cleanup dance — you no longer need any of them. That alone removes ~400 MB of intermediate layer churn even before multi-staging.

### 2. Collapse 20+ `RUN pip install` lines into one `uv sync`

Each `RUN pip install foo` is a separate layer, runs an independent resolver, and produces inconsistent transitive pins. A single `uv sync --locked` against a checked-in `uv.lock` resolves the whole graph once in parallel and installs in a single layer with bit-exact hashes. Astral's published claim of "10–100× faster than pip" (`github.com/astral-sh/uv`) is backed by the resolver running sub-second on a 30-package ML graph that takes pip 30+ seconds; downloads and wheel installs are also parallelized.

Adoption signal as of April 2026: **Hugging Face TGI** (`COPY --from=ghcr.io/astral-sh/uv:... /uv /uvx /bin/`), **vLLM** (`docker/Dockerfile` uses `--mount=type=cache,target=/root/.cache/uv`), HF Transformers install docs lead with `uv pip install "transformers[torch]"`, and FastAPI itself publishes wheels via uv. **Dependabot security updates for uv.lock went GA on 2025-12-16** (`github.blog/changelog/2025-12-16-dependabot-security-updates-now-support-uv/`). Renovate has supported `uv.lock` since 2024 with a dedicated integration page (`docs.astral.sh/uv/guides/integration/renovate/`).

A minimal `pyproject.toml` to seed from your Dockerfile-only state:


**Per-package pinning policy** (matches the April 2026 consensus from `docs.astral.sh/uv/concepts/projects/dependencies/` and Hugging Face's own PyTorch install guide at `huggingface.co/blog/daya-shankar/pytorch-install-guide`): pin **torch, flash-attn, autoawq exactly** (ABI-locked); **range-pin everything else with an upper bound on the next major** so Renovate can bump weekly without breaking you on a major release; let `uv.lock` carry the bit-exact transitive graph. Don't `==`-pin every direct dep — that's "paranoid" pinning that costs you weekly merge conflicts without buying reproducibility you already have via the lockfile.

### 3. Add BuildKit cache mounts and remove `--no-cache-dir`

The `--no-cache-dir` flag and a BuildKit cache mount are **mutually exclusive** — `--no-cache-dir` tells pip/uv to skip writing to the cache, making the mount inert. The "always pass `--no-cache-dir` to keep images small" advice predates BuildKit and is now an anti-pattern when you have a cache mount; the cache lives outside the image layer, so the image stays small *and* downloads stay cached across builds. Itamar Turner-Trauring's `pythonspeed.com/articles/docker-cache-pip-downloads/` is the canonical reference. Astral's Docker integration guide (`docs.astral.sh/uv/guides/integration/docker/`) requires `UV_LINK_MODE=copy` to suppress hardlink warnings across the mount filesystem boundary.

The apt cache requires removing the `docker-clean` hook and using `sharing=locked` because of apt's exclusive lock semantics — this is the canonical `reproducible-containers/buildkit-cache-dance` recipe.

```dockerfile
# Keep apt cache across builds (Docker's default base image deletes it post-install)
RUN rm -f /etc/apt/apt.conf.d/docker-clean && \
    echo 'Binary::apt::APT::Keep-Downloaded-Packages "true";' \
        > /etc/apt/apt.conf.d/keep-cache

RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends \
      ca-certificates curl

RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    uv sync --locked --no-install-project
```

Bind-mounting the lockfile rather than `COPY`ing it (per Astral's pattern) keeps it out of layer history while still feeding the resolver.

### 4. `MAX_JOBS` as `ARG`, not `ENV`

`ENV MAX_JOBS=12` persists into every container subprocess at runtime, where it's meaningless and occasionally surprises downstream tools. The Docker blog states this directly: *"The ARG instruction allows you to define variables that will be accessible during the build stage but not available after the image is built"* (`docker.com/blog/docker-best-practices-using-arg-and-env-in-your-dockerfiles/`). Convert in place:

```dockerfile
ARG MAX_JOBS=12          # build-time only
RUN MAX_JOBS=${MAX_JOBS} FLASH_ATTENTION_FORCE_BUILD=TRUE \
    uv pip install --no-build-isolation flash-attn==2.7.4
```

### 5. Replace the `sed -i` patch with a real `.patch` file

`sed -i` succeeds silently when context drifts (zero substitutions, exit 0 — your runtime then explodes). `patch --forward` exits non-zero on drift, is idempotent on cache replays, and is reviewable in `git diff`. The upstream package (`iloveitaly/pytest-playwright-visual-snapshot`) is actively maintained and hard-depends on the maintainer's own `structlog-config`, so file an upstream PR in parallel; meanwhile:

```dockerfile
COPY patches/pytest-playwright-visual-snapshot-optional-structlog.patch /tmp/

RUN set -eux; \
    PKG_DIR="$(python -c 'import pytest_playwright_visual_snapshot,os; \
print(os.path.dirname(pytest_playwright_visual_snapshot.__file__))')"; \
    cd "$PKG_DIR/.."; \
    patch -p1 --forward \
      < /tmp/pytest-playwright-visual-snapshot-optional-structlog.patch; \
    python -c "import pytest_playwright_visual_snapshot"   # smoke test
```

The trailing import smoke-test is the part `sed` can't give you: build fails immediately if the package is broken, instead of at e2e-test time.

### 6. Other quick wins in the same PR

- Delete the duplicate `RUN pip install pyaudio` (move to `pyproject.toml`).
- Delete both `RUN ln -sf /usr/local/bin/python3.11 /usr/bin/python3` blocks — once you stop installing system pip, nothing clobbers the symlink.
- Combine `apt-get update` + `apt-get install` into single `RUN`s (separate `update` layers cache independently and produce 404s on rotated package versions — explicitly called out in `docs.docker.com/build/building/best-practices/`).
- Remove `pip install --upgrade` patterns; lockfile resolution replaces them.

## Tier 2 — Medium effort, high impact (the "second PR" set)

### Multi-stage CUDA: devel builder, base runtime

Builder stage uses `nvidia/cuda:12.2.2-devel-ubuntu22.04` (has `nvcc` + CUDA headers needed for flash-attn / autoawq native builds); runtime stage stays on the locked `nvidia/cuda:12.2.2-base-ubuntu22.04` and receives only `/opt/venv` plus the app. This is the canonical April 2026 pattern from Astral's docs and Hynek Schlawack's `hynek.me/articles/docker-uv/`. The flash-attn build is captured **once** as a `.whl` via `uv pip wheel --no-build-isolation --no-deps`, then installed cheaply — mirrors the IBM TGI fork's idiom and lets you publish the wheel to an internal index later if you want to skip compilation entirely (community pre-built wheels at `github.com/mjun0812/flash-attention-prebuild-wheels` use the convention `flash_attn-2.X.Y+cu12torch2.7cxx11abiTRUE-cp312-…whl`).

What Python *actually* needs at runtime on Ubuntu 22.04: `python3.12` (or copy `/opt/python` from the builder), `libssl3`, `libffi8`, `ca-certificates`. **Not** `build-essential`, **not** any `lib*-dev`. The `nvidia/cuda:…-base` image already carries the CUDA driver-compat libs; `libcuda.so` is bind-mounted by the NVIDIA Container Toolkit at runtime and never baked.

A complete, minimalist multi-stage Dockerfile (~75 lines) for your scenario:

```dockerfile
# syntax=docker/dockerfile:1.7
ARG CUDA_VER=12.2.2
ARG MAX_JOBS=12

############################################################
# Stage 1: builder (devel image, has nvcc + CUDA headers)
############################################################
FROM nvidia/cuda:${CUDA_VER}-devel-ubuntu22.04 AS builder
ARG MAX_JOBS

ENV DEBIAN_FRONTEND=noninteractive \
    UV_LINK_MODE=copy \
    UV_COMPILE_BYTECODE=1 \
    UV_PYTHON_INSTALL_DIR=/opt/python \
    UV_PYTHON_PREFERENCE=only-managed \
    UV_PROJECT_ENVIRONMENT=/opt/venv \
    PATH=/opt/python/bin:/opt/venv/bin:$PATH

RUN rm -f /etc/apt/apt.conf.d/docker-clean && \
    echo 'Binary::apt::APT::Keep-Downloaded-Packages "true";' \
        > /etc/apt/apt.conf.d/keep-cache

RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends \
      build-essential git ninja-build ca-certificates curl

COPY --from=ghcr.io/astral-sh/uv:0.8 /uv /uvx /usr/local/bin/
RUN uv python install 3.12.13

WORKDIR /app

# Resolve + install everything except flash-attn (which needs torch present first)
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv venv /opt/venv && \
    uv sync --locked --no-install-project --no-group flash

# Build flash-attn wheel ONCE and capture it — survives layer cache replays
RUN --mount=type=cache,target=/root/.cache/uv \
    MAX_JOBS=${MAX_JOBS} FLASH_ATTENTION_FORCE_BUILD=TRUE \
    uv pip wheel --no-build-isolation --no-deps \
        --wheel-dir /wheels  flash-attn==2.7.4

RUN --mount=type=cache,target=/root/.cache/uv \
    uv pip install /wheels/flash_attn-*.whl

# App source LAST (most volatile)
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-editable

############################################################
# Stage 2: runtime (locked base image, no toolkit)
############################################################
FROM nvidia/cuda:${CUDA_VER}-base-ubuntu22.04 AS runtime

ENV PATH=/opt/python/bin:/opt/venv/bin:$PATH \
    PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 \
    HF_HOME=/home/rruiz/.cache/huggingface \
    HF_HUB_ENABLE_HF_TRANSFER=1

RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    rm -f /etc/apt/apt.conf.d/docker-clean && \
    apt-get update && apt-get install -y --no-install-recommends \
      libssl3 libffi8 ca-certificates tini

RUN useradd -m -u 1000 -s /bin/bash rruiz
COPY --from=builder --chown=rruiz:rruiz /opt/python /opt/python
COPY --from=builder --chown=rruiz:rruiz /opt/venv   /opt/venv

USER rruiz
WORKDIR /home/rruiz/app
COPY --chown=rruiz:rruiz src/ ./src/

ENTRYPOINT ["tini", "--"]
CMD ["python", "-m", "lupin"]
```

**Note the `--chown` flags on every `COPY` instead of a final `chown -R`.** A recursive chown over a multi-GB venv adds an entire-venv-sized layer because it changes inode metadata for every file; `--chown` sets ownership atomically as the layer is created. This pattern, from the Astral/Depot reference (`depot.dev/docs/container-builds/optimal-dockerfiles/python-uv-dockerfile`), eliminates the need for the `USER rruiz`-only-at-end dance entirely.

### Replace `COPY src/conf/keys` with runtime secret mounts

Baking `keys/` into a layer means anyone with `docker pull` access — or anyone who exfiltrates the registry image — gets every credential, even if you delete the file in a later layer (`docker history --no-trunc` reveals everything). **If you have already pushed a build with these keys, rotate every key now**; squashing or `--squash` does not help because previous tags still reference the old layers in the registry.

For Cloud Run, mount from Secret Manager directly to your existing `/var/lupin/src/conf/keys` path:

```bash
# Push each key into Secret Manager once
for f in src/conf/keys/*; do
  gcloud secrets create "lupin-$(basename "$f")" --data-file="$f" \
    --replication-policy=automatic
done

gcloud run deploy lupin \
  --image=REGION-docker.pkg.dev/PROJECT/repo/lupin@sha256:... \
  --update-secrets=/var/lupin/src/conf/keys/openai_api_key=lupin-openai_api_key:1,\
/var/lupin/src/conf/keys/anthropic_api_key=lupin-anthropic_api_key:1 \
  --cpu-boost --min-instances=1 --execution-environment=gen2
```

Pin a numeric secret version, **not `latest`** — env-var-injected secrets are resolved once at instance start. For local dev, bind-mount the same path: `docker run -v "$HOME/.config/lupin/keys:/var/lupin/src/conf/keys:ro" lupin:dev`. Add a CI gate via `trivy image --scanners vuln,secret,config` to prevent regression.

For *build*-time secrets (private PyPI tokens, HF auth) use BuildKit's `--mount=type=secret`, which is excluded from SLSA provenance and `docker history`:

```dockerfile
RUN --mount=type=secret,id=hf_token,env=HF_TOKEN \
    uv sync --locked
# docker buildx build --secret id=hf_token,env=HF_TOKEN .
```

### Replace `curl | bash` installers

**Claude Code** as of April 2026: Anthropic now publishes signed apt/dnf/apk repos with a verifiable GPG key at `downloads.claude.ai/keys/claude-code.asc` and a signed `manifest.json` per release containing per-platform SHA256s. The native installer (`curl https://claude.ai/install.sh | bash`) is still endorsed for interactive use, but for containers prefer the apt repo. *(One uncertainty flag: re-verify the exact `deb` line and suite name at `code.claude.com/docs/en/setup` before merging — the path was reconstructed from docs and may have shifted.)*

```dockerfile
RUN curl -fsSL https://downloads.claude.ai/keys/claude-code.asc \
      | gpg --dearmor -o /etc/apt/keyrings/claude-code.gpg && \
    echo "deb [signed-by=/etc/apt/keyrings/claude-code.gpg] \
https://downloads.claude.ai/claude-code-releases/apt stable main" \
      > /etc/apt/sources.list.d/claude-code.list && \
    apt-get update && apt-get install -y --no-install-recommends claude-code
```

**d2** as of April 2026: `d2lang.com/install.sh` is **not** signed and the upstream README explicitly recommends "using your OS's package manager directly instead for improved security" (`github.com/terrastruct/d2/blob/master/docs/INSTALL.md`). Releases ship without `.sha256` sidecars. Compute the hash yourself, commit it, and pin:

```dockerfile
ARG D2_VERSION=v0.7.1
ARG D2_SHA256=<sha256 you computed once>
RUN set -eux; \
    curl -fsSLO "https://github.com/terrastruct/d2/releases/download/${D2_VERSION}/d2-${D2_VERSION}-linux-amd64.tar.gz"; \
    echo "${D2_SHA256}  d2-${D2_VERSION}-linux-amd64.tar.gz" | sha256sum -c -; \
    tar -xzf "d2-${D2_VERSION}-linux-amd64.tar.gz"; \
    make -sC "d2-${D2_VERSION}" install PREFIX=/usr/local; \
    rm -rf "d2-${D2_VERSION}"*
```

**MARP CLI**: cleanest path is multi-stage copy from the official digest-pinned image — drops the entire Node toolchain from your final image:

```dockerfile
FROM ghcr.io/marp-team/marp-cli:v4.3.1@sha256:<digest> AS marp
# ... in your runtime stage:
COPY --from=marp /usr/local/bin/marp /usr/local/bin/marp
```

The general SHA256-verify idiom for any tarball is `set -eux; curl -fsSLO <url>; echo "${SHA256}  $(basename <url>)" | sha256sum -c -; tar -xzf …`. Two spaces between hash and filename; `set -eux` so checksum mismatch aborts loudly. **Never** use `https://github.com/.../archive/refs/tags/*.tar.gz` — those auto-generated archives are not byte-stable per `github.blog/changelog/2023-01-30-git-archive-checksums-may-change`. Always pull from Releases.

## Tier 3 — Defer to a later PR

These changes are valuable but carry more failure modes. Schedule them after Tier 1+2 stabilize.

### Base image digest pinning + Renovate

Tags are mutable: NVIDIA rebuilds `12.2.2-base-ubuntu22.04` on Ubuntu CVE patches without changing the version string. Pin the **manifest-list** digest (not a per-arch digest, which would break cross-arch builds) and let Renovate own the bumps:

```dockerfile
FROM nvidia/cuda:12.2.2-base-ubuntu22.04@sha256:<MANIFEST_LIST_DIGEST>
# obtain via: docker buildx imagetools inspect nvidia/cuda:12.2.2-base-ubuntu22.04
```

Renovate config (`docs.renovatebot.com/docker/`):

```jsonc
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended", "docker:pinDigests"],
  "packageRules": [
    { "matchFileNames": [".devcontainer/**"], "pinDigests": false },
    { "matchDatasources": ["docker"],
      "matchUpdateTypes": ["digest", "patch"],
      "automerge": true, "automergeType": "branch",
      "minimumReleaseAge": "3 days" }
  ]
}
```

`minimumReleaseAge: "3 days"` filters out 0-day broken releases (especially valuable for `huggingface_hub` 0.x.0 PRs that regularly break the world). Dependabot **does not yet add a digest** to a tag-only `FROM` line as of April 2026 (`dependabot/dependabot-core` issue #14065); it only updates already-pinned digests, so use Renovate for first-time pinning.

### HuggingFace models: stop baking, start mounting

The April 2026 community consensus, reflected in Google Cloud's own ML deployment guides (`cloud.google.com/blog/products/ai-machine-learning/how-to-deploy-llama-3-2-1b-instruct-model-with-google-cloud-run/` and `medium.com/google-cloud/scale-to-zero-llm-inference-with-vllm-cloud-run-and-cloud-storage-fuse-42c7e62f6ec6`) and reinforced by jpetazzo's anti-pattern post: **don't bake multi-GB model weights into images**. Your four pre-baked models (~3 GB combined for distil-large-v3 + nomic embeds + bert-base) are defensible to bake but strictly suboptimal across all four of your priority axes.

Production (Cloud Run) — Cloud Storage FUSE volume mount, no `gcsfuse` install required:

```yaml
spec:
  template:
    metadata:
      annotations:
        run.googleapis.com/startup-cpu-boost: "true"
        autoscaling.knative.dev/minScale: "1"
        run.googleapis.com/execution-environment: gen2
    spec:
      containers:
      - image: REGION-docker.pkg.dev/PROJECT/repo/lupin@sha256:...
        env:
        - { name: HF_HOME, value: /mnt/hf }
        - { name: HF_HUB_ENABLE_HF_TRANSFER, value: "1" }
        volumeMounts:
        - { name: hf-models, mountPath: /mnt/hf }
      volumes:
      - name: hf-models
        csi:
          driver: gcsfuse.run.googleapis.com
          volumeAttributes:
            bucketName: lupin-hf-models
            mountOptions: "implicit-dirs,file-cache:max-size-mb:-1,metadata-cache:ttl-secs:-1"
```

Same-region GCS gives 100s of MB/s; combined with `min-instances=1` and `--cpu-boost` (which doubles vCPU for 10s after start), warm-from-GCS instances start in seconds rather than minutes. Local dev shares weights via host bind-mount: `-v $HOME/.cache/huggingface:/root/.cache/huggingface`.

For reproducibility, **always pin model revisions by full 40-char SHA**, not tag (truncated SHAs raise `OSError: Can't load config` per huggingface/transformers#13264):

```python
AutoModel.from_pretrained(
```

### Beyond hygiene: paradigm shifts to consider later

These are not hygiene-pass changes; they're architectural ones the community is debating in 2025–2026, included for completeness so you can sequence them deliberately:

- **NGC images (`nvcr.io/nvidia/pytorch:25.xx-py3`)**: the Red Hat 2025 guide (`next.redhat.com/2025/08/26/a-developers-guide-to-pytorch-containers-and-nvidia-solving-the-puzzle/`) recommends NGC as the path of least resistance ("the most reliable solution. No conflicts.") because PyTorch ↔ CUDA ↔ cuDNN ↔ NCCL ↔ flash-attn versions are pre-validated. Cost: 8–20 GB images, hundreds of unused packages, NVIDIA's release cadence rather than yours. Your CUDA 12.2-locked constraint actually argues *against* NGC here — NGC tags are by release date and force a specific PyTorch version per tag.
- **Chainguard PyTorch images (`cgr.dev/chainguard/pytorch`)**: strong fit for FIPS/regulated workloads; effectively gated behind paid tier since Nov 2024. The "33 vs 268 packages" / "zero CVEs" claims are vendor marketing but the SBOMs are auditable.
- **pixi (prefix.dev)**: the SciPy 2025 paper "Reproducible Machine Learning Workflows for Scientists with Pixi" (Feickert et al.) and the Nov 2025 arXiv paper 2511.04827 argue pixi eliminates containerization overhead for many ML+robotics workloads. Wins over uv when non-Python conda packages are in play; for a pure-PyPI stack like yours, **uv is the lower-disruption choice**.
- **Nix for ML**: NVIDIA ↔ Flox ↔ NixOS Foundation deal in late 2025 made CUDA redistribution legal; Canva's ML platform moved to `dockerTools.buildImage` from nixpkgs. Niche but no longer fringe.
- **Devcontainers** (`containers.dev`): now the de facto local-dev story for ML in 2025–26 across VS Code, Cursor, and JetBrains Gateway. Your `lupin-rest-dev`/`lupin-rest-test` containers could migrate at low cost.
- **Model-as-an-Artifact** (separate OCI artifacts for weights via Docker Model Runner): Mihiraja Kuruppu's Jan 2026 piece is the most-cited articulation, though vendor-adjacent. The structural argument — "weights don't compress well; treating them as application code was always the wrong abstraction" — is independently held by HF TGI, vLLM, and NVIDIA Triton model-repository conventions.
