# GPU Doom Loop — uvicorn `--reload` + cu124/driver-535 forward-compat fragility

**Date**: 2026-05-15
**Author**: Claude (Lupin parent context, persona unallocated this session)
**Severity**: HIGH — `:7999` dev container becomes unrecoverable without `docker restart`; reproducible from any code edit that lands in a `reload_dirs`-watched path
**Branch context**: `wip-v0.1.7-2026.04.22-spit-and-polish-for-cjflow-tfe-and-bfe`
**Related plans**:
- `src/rnd/v0.1.7/2026.04.27-cuda-driver-vs-image-torch-cu124-mismatch.md` — original cu124/driver-535 expert handoff (recommends driver upgrade to 550.x)

---

## TL;DR

`lupin:1.0.0` ships `torch 2.6.0+cu124` on a host driver of `535.104.05` (CUDA 12.2 native). On RTX 4090s (consumer cards), CUDA Forward-Compatibility is officially unsupported — but the cu124 shim limps along on the *first* Python process per container lifetime, so the dev container's initial boot succeeds and GPU pre-warming in `lifespan` startup completes.

When Claude Code (or any editor) saves a file under `cosa/`, `fastapi_app/`, `lib/`, `lupin_cli/`, or `lupin_mcp/`, uvicorn's `--reload` watchfiles thread kills the worker process and spawns a fresh one **inside the same container**. The new Python process can no longer reinitialize NVML or `cuInit()` — both fail. The `lifespan` startup hits the GPU pre-warm at `main.py:621` and dies. uvicorn then keeps re-detecting changes (or stale state) and tries again → doom loop until the container itself is bounced.

The "GPU doom loop" is the interaction of three layers; remove any one and the symptom doesn't manifest.

## The three-layer root cause

### Layer 1 — cu124 wheel running on driver 535 (consumer GPU)

Per the 2026-04-27 handoff:

- Image: `torch 2.6.0+cu124`, `flash-attn 2.8.3` built against cu124, `cuda-toolkit-12-4` in the apt layer
- Host driver: `535.104.05`, native CUDA 12.2 — both GPUs are GeForce RTX 4090 (compute 8.9, Ada)
- NVIDIA's **CUDA Forward-Compatibility** package is explicitly **Tesla / data-center only**; on consumer GPUs the runtime aborts with `Error 804: cudaErrorCompatNotSupportedOnDevice` the moment forward-compat is attempted

The 2026-04-27 doc observed `cuda.is_available() == False` on a *single* probe. What it didn't see — and what this doc adds — is that the cu124 forward-compat shim **does** appear to load successfully for the **first** CUDA-touching process per container lifetime. The dev container's `lifespan` startup runs through GPU pre-warming without complaint on the first boot.

Why first-only? Best current theory: the shim mutates per-container kernel state (e.g., a mapping in `/dev/nvidia-uvm` or a `libcuda` thread-local) that survives the original process's exit in a corrupted form, and the next process can no longer engage the shim cleanly. NVML itself goes into a "won't init" state in the new process — which is observable as the `Can't initialize NVML` warning at `torch.cuda.__init__:734`.

This is consistent with the 2026-04-27 doc's recommendation that the *real* fix is a driver upgrade to 550.x (native cu124 support, no forward-compat shim involved).

### Layer 2 — uvicorn `--reload` spawns the new worker in the same container

`src/fastapi_app/main.py:977-980`:

```python
reload_kwargs = {}
if not is_production_or_test:
    reload_kwargs[ "reload" ] = True
    reload_kwargs[ "reload_dirs" ] = [ "fastapi_app", "cosa", "lib", "lupin_cli", "lupin_mcp" ]
```

This is correct behavior for dev ergonomics (Claude Code edits routers constantly during sessions; auto-reload is desirable). The problem is that uvicorn's reloader spawns the replacement worker as a child of the supervising process **inside the existing container**. The container's NVIDIA hooks (`nvidia-container-runtime`) only inject GPU device handles when the container is created — they don't re-run for child processes. So the new worker inherits the *container's* GPU access, which is fine on data-center GPUs but flaky on consumer GPUs with cu124-on-535 forward-compat.

In other words: `docker restart lupin-rest-dev` recovers because that re-runs the NVIDIA hooks; uvicorn's internal reload does not.

### Layer 3 — eager GPU pre-warming in `lifespan` startup

`src/fastapi_app/main.py:619-657`:

```python
print( "Loading CodeRankEmbed embedding engine... ", end="" )
code_engine = get_code_engine( debug=app_debug, verbose=app_verbose )
code_engine.encode_code( [ "def hello(): return 'world'" ] )           # <-- 621
code_engine.encode_query( [ "How do I sort a list in Python?" ] )
...

prose_engine = get_prose_engine( debug=app_debug, verbose=app_verbose )
prose_engine.encode_query( [ "What is the meaning of life?" ] )
...

whisper_pipeline = await load_stt_model()
warmup_path = du.get_project_root() + "/src/conf/warmup/whisper-warmup-85s.mp3"
if os.path.exists( warmup_path ):
    whisper_pipeline( warmup_path, chunk_length_s=30, stride_length_s=5, return_timestamps=False )
```

Pre-warming exists for legitimate reasons: it establishes a stable CUDA footprint up front instead of letting the first user request pay multi-second cold-load latency. But it makes `lifespan` startup **fatally dependent on CUDA** — when `_load_model()` calls `.to("cuda:0")` and `cuInit()` returns "No CUDA GPUs are available", the whole startup aborts and FastAPI logs `Application startup failed. Exiting.`

The result: a transient driver-shim hiccup that would otherwise be recoverable (engine could lazy-load on the next real request, possibly succeed on retry) becomes terminal at startup.

### Why all three matter

| Layer | Removed → still doom-looping? |
|---|---|
| cu124 / driver 535 fragility | No — native cu124 driver makes process re-init safe |
| uvicorn `--reload` in container | No — full container restart re-runs NVIDIA hooks, gets a clean shim |
| Eager GPU pre-warming | No — server boots, lazy-load defers CUDA until first request (which can be retried/queued) |

Any one layer fixed → the bug stops being a doom loop. Some layers are cheaper to address than others.

---

## Recovery (immediate, no code change)

```
docker restart lupin-rest-dev
```

Per the `server-lifecycle` skill — this is the standard `:7999` bounce. Recreates the NVIDIA device handles inside the container so the forward-compat shim has a fresh first-process slot to engage on.

`docker compose restart` and process-level kills are **not** equivalent. Only full container restart re-runs the NVIDIA injection hooks.

## Fix options, ranked

### 1. Make GPU pre-warming non-fatal (cheapest, ships today)

Wrap the three pre-warm blocks in `main.py:619-657` in try/except. On `RuntimeError: No CUDA GPUs are available`:

- Log loudly with a distinctive banner
- Leave the engine singletons in their unloaded state (the existing `_load_model()` lazy-load path will retry on first real request)
- Let `lifespan` startup complete so the HTTP socket binds and the rest of the server (notifications, WebSocket, queues, commons) comes up

Tradeoff:
- ✅ Defangs the doom loop with ~30 lines of code, zero driver/image changes
- ✅ Preserves the dev `--reload` ergonomics Rick relies on
- ✅ Server still serves non-GPU endpoints during a CUDA outage (queue management, notifications, doc viewer, auth)
- ❌ First user request after a hot reload pays the cold-load latency we currently amortize at startup
- ❌ If lazy-load also fails (same shim state), user-facing requests start returning 500s — but at least the failure is per-request, not catastrophic

**Recommended.** Lowest blast radius, highest value, fastest to land.

### 2. Drop `cosa/rest/routers/` from `reload_dirs`

Claude Code edits routers during sessions far more often than `cosa/agents/` or `cosa/memory/`. Narrowing the watch list reduces reload-trigger frequency.

Tradeoff:
- ✅ Cheap (a few lines in `main.py`)
- ❌ Doesn't fix the root cause — a `cosa/agents/` or `fastapi_app/` edit still trips it
- ❌ Routers DO benefit from hot-reload during active development
- ❌ Easy to forget and re-add later

**Skip.** Band-aid that papers over the real interaction.

### 3. Driver upgrade to 550.x (proper long-term fix)

Per the 2026-04-27 doc — driver 550.x natively supports CUDA 12.4, no forward-compat shim involved. Reloads should become safe because each new process initializes against a driver that genuinely supports its compiled-against CUDA version.

Tradeoff:
- ✅ Proper fix — eliminates the underlying fragility
- ❌ Requires host reboot (planning + interactive-use coordination)
- ❌ Doesn't help today — the doc has been sitting since 2026-04-27

**Schedule.** Land #1 first to stop the bleeding; do #3 when the host-reboot window opens.

### 4. Repin lupin image to a cu121 wheel

Match the driver natively without touching the host.

Tradeoff:
- ✅ No host change
- ❌ Requires image rebuild + re-test + flash-attn rebuild against the older toolkit
- ❌ Means staying on an older torch + downstream chain
- ❌ Reverses the Tier 0+1 hygiene wins the 2026-04-27 doc was protecting

**Last resort.** Only if #3 is permanently blocked.

---

## Recommendation

1. **Immediate**: `docker restart lupin-rest-dev` to recover the currently-stuck container.
2. **Today**: Implement option #1 (non-fatal pre-warm). Lands the doom-loop fix without driver/image work.
3. **Next reboot window**: Driver 550.x upgrade per the 2026-04-27 doc. Permanent fix.

Options #2 and #4 are not recommended.

## Repro pointer

Any edit to any file under `reload_dirs` (currently `fastapi_app`, `cosa`, `lib`, `lupin_cli`, `lupin_mcp`) inside the `lupin-rest-dev` container, after the container has been running long enough for the first lifespan startup to complete. Watch:

```
docker logs -f lupin-rest-dev
```

Once one full reload cycle fails with `No CUDA GPUs are available`, subsequent reloads inside the same container also fail. Only full container restart recovers.
