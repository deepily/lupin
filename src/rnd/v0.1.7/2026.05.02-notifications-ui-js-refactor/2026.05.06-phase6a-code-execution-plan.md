## Context

The multiplexer's Phase 5 shipped the notifications-list pane (read-only) with hidden mount points for Phase 6 (`#jobs-pane` + `#tts-pane`, both `data-phase6-pending="true"`). Phase 6a is the **first slice of Phase 6** per the slicing manifest (`07-phase6-slicing-manifest.md`): light up the jobs surface — render the 5-bucket layout (todo / running / done / dead / history), invoke `JobStore.hydrateHistory(api)` on mount (Q7 hook reserved through Phase 5), and lift `data-phase6-pending` from `#jobs-pane`. Phase 6b will deliver TTS chrome + action-required interactive widgets + delete-button handler; Phase 6c will deliver voice-persona modal + audio recorder + focus tray.

The design is frozen — no Q-decisions, no Pass 1, no Pass 2 findings are re-opened by this plan. This document is the **execution sequence** that lands the ratified design into code while keeping AC1–AC10b green inside one or more user-approved commits, with AC11a/AC11b executed separately on `:8000` via `POST /api/test-suite/submit`.

### Scope-of-work delta discovered during recon (2026-05-06)

The design doc assumed a FastAPI client-config endpoint already exists for `boot.ts` to fetch `multiplexer_max_meta_display_bytes` from. **Recon confirms it does not** — `boot.ts` has zero `fetch` calls today.
