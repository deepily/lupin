## Tier 1 — Latent bugs and regressions

### 1.1 Binary audio frames are silently dropped under the WSChannel-mediated path

In `ws-channel.js` (lines 261–276), every inbound frame is unconditionally parsed:

```javascript
socket.onmessage = function ( ev ) {
    if ( myGen !== generation ) return;
    let envelope = null;
    try { envelope = JSON.parse( ev.data ); } catch ( e ) { return; }   // ← Blob lands here
    ...
};
```

WebSocket's default `binaryType` is `"blob"`. `JSON.parse(<Blob>)` throws on the implicit `toString()` (`"[object Blob]"`), the catch swallows it, and the channel emits nothing. The `onMessage` callback never fires for binary frames. The consumer's `handleAudioMessage(event)` has a `if (event.data instanceof Blob)` branch (line 2649) that is now dead code under this transport — there is no other listener attached to the audio socket. The comment at line 2256 ("Audio binary chunks flow through a different pathway") describes a pathway that does not exist.

This is a Phase 2 regression. The fix that preserves the channel's invariants:

```javascript
// In createChannel opts
const onBinary = typeof opts.onBinary === "function" ? opts.onBinary : null;

socket.onmessage = function ( ev ) {
    if ( myGen !== generation ) return;
    if ( typeof ev.data !== "string" ) {        // Blob | ArrayBuffer
        if ( onBinary ) {
            try { onBinary( ev.data ); } catch ( e ) { /* swallow */ }
        }
        return;
    }
    let envelope = null;
    try { envelope = JSON.parse( ev.data ); } catch ( e ) { return; }
    // ... existing JSON path
};
```

Then in `connectWebSockets()`, wire `onBinary: (blob) => this.handleAudioChunk(blob)` on the audio channel only. (The `handleAudioMessage` Blob branch can then be deleted.)

### 1.2 Two `playAudioBlob` definitions — first is dead and broken

Lines 4189 and 4868 both define `async playAudioBlob(...)`. JavaScript class semantics: the second wins and silently shadows the first. The first version takes a parameter named `audioUrl`, but its single caller (`playTTS` at 4166) passes the Blob returned from `audioCache.checkCache()`. It then does `audio.src = audioUrl` — assigning a Blob to `HTMLMediaElement.src`, which coerces to the string `"[object Blob]"` and fails silently. If anyone ever moved that method below the duplicate, the cache-hit path would break instantly.

Action: delete the 4189 version. Same pattern at:

- `escapeHtml` (8174 vs 12582 — second uses a regex-replace map, first uses `div.textContent`; second wins)
- `moveSenderCardToTop` (10410 vs 16434 — second additionally promotes the strip icon; second wins)

These triplicate definitions tell me the file has accumulated additions without anyone reading the whole class. It is a strong signal for the structural refactor below.

### 1.3 XSS surface in `addNotificationToList` and elsewhere

`title="${message}"` on line 11630 interpolates server-controlled `message` directly into a quoted attribute. A double-quote in `message` escapes the attribute. Across the file there are 62 raw `innerHTML =` assignments and only 34 `escapeHtml(...)` calls. DOMPurify is loaded (HTML line 958) but only invoked from `renderMarkdown` / `renderMarkdownInline`. Every other `innerHTML` is a potential sink.

The state-of-the-art remedy here is structural, not point-fix: stop building HTML strings. Either use `<template>` cloning (cheap, vanilla, your stack), or a tiny tagged-template helper that calls `textContent` on interpolated values. Example helper:

```javascript
function html( strings, ...values ) {
    const tpl = document.createElement( "template" );
    tpl.innerHTML = strings[ 0 ];
    let cursor = tpl.content;
    values.forEach( ( v, i ) => {
        const tn = document.createTextNode( v == null ? "" : String( v ) );
        cursor.appendChild( tn );
        const next = document.createElement( "template" );
        next.innerHTML = strings[ i + 1 ];
        cursor.appendChild( next.content );
    } );
    return tpl.content;
}
```

Then `addNotificationToList` builds a `DocumentFragment` with safe text nodes for `message`, `type`, `priority` and only the static skeleton in HTML.

### 1.4 `refreshAccessToken()` has no in-flight mutex

Three independent code paths can each call `refreshAccessToken()` concurrently: `_showCircuitBanner` (4001 path), `handleQueueMessage` (`auth_error`), `handleAudioMessage` (`auth_error`). `authRefreshAttempted` is a non-atomic flag — both auth_errors can read `false` in the same microtask before either writes. Beyond that, `ensureValidToken()` at line 948 also calls `refreshAccessToken` directly without checking the flag at all.

If your refresh tokens rotate (typical OAuth2 RFC 6749 §10.4), only the first refresh wins; subsequent concurrent refreshes fail and force-logout the user. This is the most likely cause of any "spurious logout" reports in the field.

The correct 2026 primitive is `navigator.locks` — globally exclusive across all tabs of the app:

```javascript
async refreshAccessToken() {
    return navigator.locks.request( "lupin-token-refresh", async () => {
        // Re-read after acquiring the lock — another tab may have just refreshed
        const tokens = this.getStoredTokens();
        if ( tokens.accessToken && !this.isTokenExpired( tokens.accessToken ) ) {
            this.authToken = tokens.accessToken;
            return true;
        }
        // ... existing fetch('/auth/refresh') body
    } );
}
```

This eliminates `authRefreshAttempted` entirely and fixes the cross-tab problem (today, two tabs of `/notifications` will each fire `/auth/refresh` on the same expiring token; only one wins).

### 1.5 No fetch timeouts or aborts anywhere

48 fetch sites, zero `AbortController`, zero `AbortSignal.timeout`. A hung `/auth/refresh` blocks the entire UI indefinitely. A lifecycle-mid request (page hide, tab close) lingers. The 2026-canonical pattern is:

```javascript
async authedFetch( url, options = {} ) {
    await this.ensureValidToken();
    const ctrl = new AbortController();
    const timeout = options.timeoutMs ?? 15000;
    const signal = AbortSignal.any( [
        ctrl.signal,
        AbortSignal.timeout( timeout ),
        ...( options.signal ? [ options.signal ] : [] )
    ] );
    return fetch( url, { ...options, signal, headers: {
        "Authorization": this.getAuthHeader(),
        ...( options.headers || {} )
    } } );
}
```

`AbortSignal.timeout()` and `AbortSignal.any()` are both stable across all evergreen browsers as of 2026. Then thread `signal` through to consumers that should cancel on page hide / new submission / nav.

## Tier 2 — Architectural rot

### 2.1 The 16,797-line god class

`NotificationsUI` is doing the work of at least ten independent components. The duplicated method definitions in §1.2 are a direct symptom — no human can hold the surface area in their head. A reasonable decomposition along existing seams in your code:

```
notifications/
├── auth/AuthManager.js                  (JWT, refresh, lock, ensureValidToken)
├── transport/QueueTransport.js          (wraps WSChannel for queue)
├── transport/AudioTransport.js          (wraps WSChannel for audio + binary)
├── transport/ClaudeCodeTransport.js     (replaces raw WebSocket — also via WSChannel)
├── tts/TTSEngine.js                     (playTTS, instant/reliable, PCM context)
├── tts/TTSQueue.js                      (addToTTSQueue, activate, focus mode, persistence)
├── notifications/ActionRequiredQueue.js (countdown timers, pause/resume, grace period)
├── notifications/SenderGroups.js        (sender cards, date accordions, focus strip)
├── jobs/JobQueueRenderer.js             (todo/run/done/dead/history)
├── jobs/JobCardRenderer.js              (renderJobCard, expand, metadata)
├── ui/StatusPills.js                    (the duplicated status maps)
├── ui/CircuitBanner.js
├── shared/SHA256.js                     (currently re-implemented in 2 caches)
├── shared/storage.js                    (storage key constants + JSON helpers)
└── notifications.js                     (orchestrator: 200-300 lines, wires modules)
```

Use ES modules and `<script type="module">`; you're already doing dynamic `import()` for `ws-channel.js`, so the pivot is small. The orchestrator becomes a graph wiring: pass `authManager` into `QueueTransport`, pass an `eventBus` (a tiny `EventTarget` instance) for cross-module signals like `auth-refreshed`, `tts-completed`, `circuit-open`. Every cross-module call goes through the bus or an explicit dependency-injected handle, never through `window.notificationsUI` (your `DELETE_HANDLERS` constant currently bakes that in).

### 2.2 Triple page-lifecycle wiring

`ws-channel.js` (480–491) auto-attaches `online`/`offline`/`pageshow`/`pagehide`/`freeze`/`resume` window listeners *per channel at construction*. `notifications.js` `_attachPageLifecycle()` (2468–2515) attaches the same set again and forwards to both channels. Result: when the `online` event fires, `manualRetry()` runs four times in quick succession across two channels. The author acknowledges this in the comment ("idempotent — duplication is benign"), but idempotent-by-luck is fragile, and the watchdog (line 494, `setInterval(tickWatchdog, 30s)`) plus the channel's own `online` handler plus the orchestrator's `online` handler is three distinct opinions about when to reconnect.

The right separation: the channel is a transport, not a lifecycle manager. Move the page-lifecycle listeners *out* of `createChannel` entirely (delete lines 482–491 in ws-channel.js). The `_attachPageLifecycle()` in the orchestrator becomes the single owner. The watchdog stays, since it's a different concern (passive idle reconciliation, not event-driven).

This is an API-contract change; ship it behind a `lifecycle: false` constructor opt for one release if needed, then flip the default.

### 2.3 Three transports, two policies

You have three WebSocket connections:

- `queueChannel` (WSChannel — has backoff, circuit breaker, generation tokens)
- `audioChannel` (WSChannel — same)
- `claudeCodeWs` (raw `new WebSocket()` at line 3916 — no reconnect, no backoff, no token refresh, no circuit breaker)

Migrate `claudeCodeWs` to `createChannel`. The `authMessage` builder is a one-liner; `onMessage` becomes the existing `handleClaudeCodeMessage` body. You inherit the entire reliability story for free.

### 2.4 Inconsistent fetch wrapping

32 raw `fetch(...)` sites, 16 `authedFetch(...)` sites. Of the 32, only 4 have a nearby `ensureValidToken()` call. The others assume `this.authToken` is fresh, which is true *only* because the periodic monitor runs every 10 minutes — anything between the 5-minute expiry threshold and a stale-token drift will 401. After the AuthManager refactor in §2.1, route every authenticated call through one helper. The audit becomes mechanical: `grep "fetch(" notifications.js` should match zero.

### 2.5 JSON round-trip in the message dispatcher

```javascript
// In createChannel callback:
onMessage: ( envelope ) => {
    if ( envelope === null || envelope === undefined ) return;
    this.handleQueueMessage( { data : JSON.stringify( envelope ) } );  // ← stringify
},

// Then handleQueueMessage does:
const envelope = JSON.parse( event.data );  // ← parse
```

The channel parses, you stringify, the handler parses again. This is wasteful, but more importantly it's a footgun — any envelope value that doesn't survive `JSON.stringify` round-trip (Date, undefined fields, NaN) breaks. Have the channel pass the parsed envelope directly:

```javascript
handleQueueEnvelope( envelope ) { /* original body, no JSON.parse */ }
```

…and update both queue and audio dispatchers. This also cleans up the `handleAudioMessage` Blob branch from §1.1 — the binary path goes via `onBinary`, the JSON path via `onMessage`, both pre-parsed.

## Tier 3 — Sync/async hygiene (state-of-the-art for 2026)

### 3.1 Race conditions documented as comments are still race conditions

`playPCMChunk` captures `firstChunkPlayed` before `await blobData.arrayBuffer()` (lines 4546–4550) precisely because `handleAudioComplete` may run during the await. `handleAudioChunk` mutates `this.audioChunks` and `handleAudioComplete` reads it — both racing with `stopAudio`. The documented guards work but are brittle and proliferate (search the file for "Race condition" — you have at least four).

The structural fix: encapsulate per-stream state in an object created when TTS playback starts, dropped when it ends. The shared `this.audioChunks` / `this.currentTTSMode` / `this.firstChunkPlayed` go away. Each `playTTS` call owns a `TTSPlaybackSession` instance; `stopAudio()` cancels the active session by setting `session.cancelled = true` and dropping the reference. Late chunks check `session === activeSession` (the same generation-token pattern that `ws-channel.js` uses successfully — port it).

### 3.2 Fire-and-forget IndexedDB transactions in JobCompletionCache

`evictOldEntries` (line ~283) does:

```javascript
if ( this.db ) {
    const transaction = this.db.transaction(['jobMessages'], 'readwrite');
    transaction.objectStore('jobMessages').delete(oldest.jobId);   // not awaited
}
```

The in-memory map is updated synchronously, but the IDB delete is fire-and-forget. If the user triggers another `store()` before the delete commits, the cache state diverges. Promisify properly:

```javascript
async _idbDelete( jobId ) {
    return new Promise( ( resolve, reject ) => {
        const tx = this.db.transaction( ['jobMessages'], 'readwrite' );
        tx.objectStore( 'jobMessages' ).delete( jobId );
        tx.oncomplete = () => resolve();
        tx.onerror    = () => reject( tx.error );
    } );
}
```

Same issue in `delete()` (also async-by-name, also fire-and-forget) and in `TTSAudioCache.cleanup()` (cursor traversal not awaited; `this.stats.totalSize` mutated synchronously before the cursor finishes).

For the IDB write paths in both caches, consider migrating to the `idb` library API or the newer Storage Buckets API (Chrome 122+, Safari 17.4+) which gives you per-bucket eviction policies — relevant since both caches are racing for the same origin quota.

### 3.3 `setInterval` in `TTSAudioCache.scheduleCleanup` never cleared

Constructor schedules a 30-minute interval; nothing clears it. If the page transitions through BFCache or the cache instance is re-created, you accumulate timers. Add a `destroy()` (you have one in `JobCompletionCache` already — copy it) and call it from `NotificationsUI` teardown.

### 3.4 `cacheKey` semantics divergent across caches

`TTSAudioCache.generateCacheKey` normalizes (`text.trim().toLowerCase()`); `JobCompletionCache.generateCacheKey` does not. Same name, different contracts, both use SHA-256 in the same way. Extract to a shared helper:

```javascript
// shared/sha256.js
export async function sha256Hex( text ) {
    const buf = await crypto.subtle.digest( "SHA-256", new TextEncoder().encode( text ) );
    return Array.from( new Uint8Array( buf ), b => b.toString( 16 ).padStart( 2, "0" ) ).join( "" );
}
```

…and make normalization the caller's choice.

### 3.5 Cross-tab coordination

Beyond the token-refresh lock (§1.4), use `BroadcastChannel("lupin")` to share state across tabs — auth changes, TTS playback (so two tabs don't both speak the same notification), session names. Replaces the localStorage-storage-event hack you'll otherwise reach for.

### 3.6 Firefox detection is broken

`applyFirefoxCompatibilityHack` at line 445 checks `typeof InstallTrigger !== 'undefined'`. Mozilla removed `InstallTrigger` in Firefox 128 (mid-2024); by May 2026 this branch is dead. The UA string check still works. Modernize to UA Client Hints where available:

```javascript
const isFirefox = navigator.userAgentData
    ? navigator.userAgentData.brands.some( b => /firefox/i.test( b.brand ) )
    : /firefox/i.test( navigator.userAgent );
```

(Firefox doesn't ship UA-CH yet; the fallback handles them.)

### 3.7 `parseInt(...) || 48` swallows zero

Line 308: `this.historyWindowHours = parseInt( storedWindow ) || 48;` — `parseInt("0")` is `0`, falsy, becomes 48. Use `Number.isFinite`:

```javascript
const parsed = Number.parseInt( storedWindow, 10 );
this.historyWindowHours = Number.isFinite( parsed ) ? parsed : 48;
```

Trivial but symptomatic — there are several similar `||` defaults in the file that quietly mistreat zero.

## Tier 4 — Connectivity / fallback specifics

### 4.1 `refreshAccessToken` has no retry

One transient network blip → false return → forced logout via `handleAuthFailure`. Wrap the `/auth/refresh` fetch in 1–2 retries with full-jitter backoff (you already have the helper in `ws-channel.js`'s `fullJitterDelay` — export it from a shared module). Distinguish *network errors* (retry) from *4xx* (don't retry). 5xx → retry once.

### 4.2 `fetchClientConfig` fallback is silent

If `/api/config/client` fails, you fall back to hardcoded defaults (lines 720–727) and continue. This is the right behavior. But there's no surfacing to the user, no telemetry, and no retry. Add a deferred retry (60s later) and emit a status badge so a stale-config tab is observable.

### 4.3 `claudeCodeWs` has zero fallback

`onclose` just updates a status string; no reconnect, no backoff, no notification to the user. After the §2.3 migration this becomes free.

### 4.4 Reconnect storm vs server overload

Your `MAX_ATTEMPTS_PER_CHANNEL = 20` with a 30s cap and full jitter means the worst-case reconnect spend per channel is ~10 minutes. With two channels independently retrying that's twice the load on a recovering server. Consider a shared `BackoffBudget` keyed on the host — when one channel observes 5 rapid fails, both channels enter `BACKOFF`. This is straightforward via your existing `ws-circuit-open` window event: the orchestrator listens, calls `manualRetry()` on neither channel and instead waits for an explicit user action.

### 4.5 AudioRecorder upload semantics

`_uploadAndTranscribe` (line 258) sends a base64 *string* as the body with `Content-Type: 'audio/mpeg'`. That's a lie — it's text. Either send the raw blob (faster, no base64 inflation):

```javascript
const response = await fetch( this.uploadEndpoint, {
    method: this.uploadMethod,
    headers: { "Content-Type": audioBlob.type, ...authHeaders },
    body: audioBlob,
    signal: AbortSignal.timeout( 30000 )
} );
```

…or keep base64 and set `Content-Type: text/plain` plus `Content-Encoding: base64`. The current setup will fail any server with strict `Content-Type` validation.

Also: `error()` only logs when `this.debug` is true (line 455) — a production user with debug off gets silent failures. Errors should always log (or be surfaced via `onError` only); only `log()` should be debug-gated.

## Tier 5 — Smaller wins

**5.1 Deduplicate the status-pill maps.** `connectWebSockets` defines the same 6-state status map twice (queue and audio). Extract to a constant or a small `attachStateChangeRouter(channel, statusElementId)` helper.

**5.2 Storage key namespace.** Mix of `notifications_*` (most) and `lupin_*` (token keys, section visibility). Pick `lupin:` or `lupin/` and write a one-shot migration. Wrap all storage in a small typed helper that does JSON.parse with try/catch — you have at least three places that crash on malformed JSON.

**5.3 `processedEvents` truncation pattern is allocation-heavy.** Lines 3673–3676 reconstruct the entire Set on every overflow. Use a bounded deque or a circular buffer — or simpler, `Map` with insertion-order iteration and `.delete(map.keys().next().value)` to evict the oldest.

**5.4 `DELETE_HANDLERS` couples module load to `window.notificationsUI`.** After the module split, this becomes a method on `JobQueueRenderer` — no globals.

**5.5 The cache-bust query string `?v=20260502b`** in HTML and dynamic import is a manual ritual. Switch to content-hashed paths in your build (or use HTTP `ETag` + `Cache-Control: max-age=0, must-revalidate` with the file name unchanged). Manual cache-bust strings drift between the HTML script tag and the dynamic import in `connectWebSockets` (line 2175 — currently `?v=20260502a` while HTML uses `?v=20260502b`).

**5.6 `crypto.randomUUID()`** for `generateFallbackSessionId` (line 2134, not viewed but referenced) is a one-liner replacement for any custom session-ID generator.

## What's strong (worth preserving as you refactor)

`ws-channel.js` is the cleanest module in the bundle. The closure-private state, frozen public API, single transition point, generation tokens to drop late callbacks, full-jitter backoff with a non-zero floor, separation of `wasEverOpen` accounting from the attempts counter — all genuinely good. The full-jitter formula matches Brooker's 2015 AWS post and the lower bound of `base` (rather than the usual zero floor) is a thoughtful refinement that prevents the thundering-herd reconnect at `t=0`. Use this module's design as the template when you split the rest.

The Phase 5 `_showCircuitBanner` 4001-token-refresh path (line 2349) is also a nicely designed control flow — the user genuinely never sees a banner flash during a routine refresh, and the `authRefreshAttempted` mutex (despite §1.4) is the right shape, just needs to be promoted to a `navigator.locks` lock and the `.then()` migrated to `await`.

## Suggested order of operations

If you want to do this incrementally without freezing feature work:

1. **Week 1 — bug fixes (Tier 1):** binary-frame path in `ws-channel.js` (1.1), delete duplicate methods (1.2), wrap `refreshAccessToken` in `navigator.locks` (1.4), add `AbortSignal.timeout` to `authedFetch` and migrate the 4 most-called fetch sites (1.5). XSS audit (1.3) can be a multi-week project on its own; start with `addNotificationToList`'s `title="${message}"` as a hotfix.
2. **Week 2 — transport unification (2.2, 2.3, 2.5):** strip lifecycle handlers out of `ws-channel.js`, migrate `claudeCodeWs`, kill the JSON round-trip.
3. **Week 3+ — module split (2.1):** extract `AuthManager` first (it's the most-touched cross-cutting concern), then `TTSEngine` + `TTSQueue` (most race-prone), then renderers. Each extraction lands as its own PR so you can revert independently.

The two cache modules are small enough to clean up in an afternoon each (§3.2, §3.3, §3.4). AudioRecorder is also small (§4.5).
