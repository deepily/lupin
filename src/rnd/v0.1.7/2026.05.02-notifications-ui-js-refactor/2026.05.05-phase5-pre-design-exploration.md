### 1.5 Layout, flow & order observations

**Column position**: Right-hand pane in a multi-pane layout (alongside action-required, tts-queue, job-queues sections)

**Visible section trigger**: Header shows count (`#notifications-count`), filter badge, clear-all button, collapse toggle. Sticky chrome persists while section content scrolls.

**Sender card ordering**:
- **Runtime updates** (`insertAtTop=true`): Newest card moves to position 0 (or 1 if conversation-mode pinned card exists)
- **Initial load** (`insertAtTop=false`): API sort order preserved (newest-first from `/api/get-queue` endpoint)
- **Pinned card invariant** (line 10594): If a sender has `data-pinned-conv-mode="true"`, new cards insert after it (not before)

**Date ordering within sender card**:
- **Descending chronological** (line 10668): Dates compared lexicographically (YYYY-MM-DD), newest date at top
- **Insertion logic**: New date finds first existing date older than it, inserts before; if no older date found, appends (line 10692)

**Message ordering within date**:
- **Newest first** (line 10913): `container.insertBefore(messageDiv, container.firstChild)` — each new message goes to top

**Scroll behavior**:
- `.date-accordion-messages`: Vertical scroll when overflow, custom webkit scrollbar (6px wide, gray #c1c1c1, hover #a1a1a1)
- **No sticky headers**: Date accordion headers scroll with messages (not fixed)
- **No virtualization**: All messages in expanded date rendered to DOM (potential perf issue for large date groups)

**Pagination/lazy-load**: None for notifications-list. All cards/dates/messages live in memory. Soft delete hides (doesn't remove from DOM until page refresh or explicit deletion).

**Grouping**:
- **By sender** (project + session): Sender cards act as conversation namespaces
- **By date** (within sender): Date accordions bucket messages by calendar day
- **By progress group** (within date): Progress groups (optional) accordion history of status updates for a single task

**Sort stability**:
- Newest arrivals bump sender card to top (unless card already at position 0 for conversation mode)
- Within a date, newest message always visible (is head of progress group or standalone)
- History within progress group: newest update at top, older updates hidden until toggle expanded

### 1.6 Ambiguity flags

- Shared `.sender-message`, `.message-text`, `.message-time` styles apply to both sender-card messages AND job-card interactions (job-card context not Phase 5 scope, but CSS is shared)
- `.cc-voice-input` rendering only for Claude Code sessions; other agent types (deep.research@, research_to_podcast@) do not get voice input row (by design, Phase 6 feature for other agents)
- Filter badge (`#notifications-filter-badge`) and history dropdown (`#history-dropdown-container`) populated by JS at runtime; HTML markup minimal

### 2.6 Section summary

Phase 5 consumes two primary store APIs: **NotificationStore** (list, unread count) + **ActionRequiredStore** (per-prompt item list with countdown state). Both emit domain events on EventBus; renderer subscribes to `store_notifications_changed` and `store_action_required_changed` without reaching into stores' internal state or controlling transitions. Three pre-flagged hooks constrain design: (1) **RE-12** `response_type` field is now live on `ActionRequiredItem` for widget selection, (2) **F16** `claude_code_event` flows unhandled (intentional; Phase 5+ may add consumer), (3) **Q7** `JobStore` history is lazy-loaded by Phase 5+ renderer via explicit `hydrateHistory(api)` call (Phase 5 does NOT call it; Phase 6 does). Q12 single-tab policy and Q9 unbounded old-page coexistence are hard constraints.
