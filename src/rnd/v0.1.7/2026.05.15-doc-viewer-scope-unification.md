## TL;DR

The doc-viewer has two parallel scope mechanisms — `docs` and `io` are hardcoded built-ins with their own whitelists in `docs_files.py` / `io_files.py`; every other scope flows through `_scope_registry.py`. The dual-track architecture is the root cause of: (a) Rick's 404 on root-level `.md` files, (b) Mr. Radio's `/api/init` cache invalidation bug, and (c) every future "why doesn't repo X's README show up?" support request. This plan retires the built-in path, makes the registry the single source of truth, fixes invalidation, and introduces an optional repo-owned manifest (`.docview.yml`) so new repos register themselves with zero Lupin-side INI edits.

User experience today:

1. **Rick (2026-05-15)**: clicked `[Open: bug-fix-queue.md](/app/docs?path=bug-fix-queue.md&scope=docs)` — 404. Authenticated. Authorized. The link should have worked per CLAUDE.md guidance.

Root cause: there are TWO scope-resolution mechanisms with different invalidation semantics, different whitelist models, and different file-resolution roots.

## 2. Current State Audit (Evidence-Driven)

### 2.1 Two scope mechanisms

**Built-in scopes** (`docs`, `io`) — declared inline:

| Aspect | Where it lives |
|---|---|
| Whitelist (root files) | `src/cosa/rest/routers/docs_files.py:46-52` — `ALLOWED_FILES` hardcoded set |
| Whitelist (prefixes) | `src/cosa/rest/routers/docs_files.py:55-59` — `ALLOWED_PREFIXES` hardcoded list |
| Path resolution root | `cu.get_project_root()` → `/var/lupin` inside container |
| Invalidation | None — values are module-level constants |
| Branch in handler | `if scope == "docs": ...` at `docs_files.py:187-206` |

**External scopes** — config-driven via INI keys parsed into `_SCOPE_REGISTRY`:

| Aspect | Where it lives |
|---|---|
| Registry build | `_scope_registry.py::build_scope_registry(config_mgr)` |
| Whitelist | `ScopeConfig.allowed_prefixes` tuple (empty → wildcard per `_scope_registry.py:131`) |
| Path resolution root | INI key `external repo <name> path` |
| Invalidation | None — `_SCOPE_REGISTRY` is lazy-built once at first request, cached for process lifetime (`docs_files.py:92,103-107`) |
| Branch in handler | `else: registry.get(scope); ...` at `docs_files.py:208-238` |


## 3. Architecture Smell Catalog

| Smell | Where | Impact |
|---|---|---|
| Two scope mechanisms | `docs_files.py:187-206` vs `:208-238` | Doubles surface area for every scope-related bug |
| Hardcoded whitelists | `ALLOWED_FILES`, `ALLOWED_PREFIXES` | Adding a root file requires code edit, not config |
| Module-level cache, no reset | `_SCOPE_REGISTRY` | `/api/init` "lies success" (Mr. Radio's framing) |
| Path-root asymmetry | Built-in uses `get_project_root()`; registry uses `external repo X path` | Bind-mount mismatches surface as 404 instead of clean 400 |
| `lupin` scope misconfigured | INI | Lone oddball; root files invisible despite mount availability |
| No repo-owned whitelist | All whitelisting is consumer-side | Adding a repo means modifying Lupin, not just registering the repo |
| `.venv` / dev-artifact exposure risk | Future wildcard scopes | Secrets blocklist covers credentials, not bulk dev output |
| `docker-compose.yml` ad-hoc | Granular sub-mounts per file | Doesn't scale to new repo roots |

## 4. Design Principles

The target architecture must satisfy:

1. **Single resolution path** — one function, one branch tree, one set of edge cases
2. **Config-driven** — adding a scope is INI-only (or, with Phase 5, drop-a-file-only)
3. **Hot-reloadable** — `/api/init` is the contract; every derived cache MUST honor it
4. **Defense-in-depth preserved** — secrets blocklist applies universally, never bypassed
5. **Backward compatibility for URLs** — every existing `?scope=docs&path=...` link in CLAUDE.md, chat history, abstracts, and external systems MUST keep working forever
6. **Fail loud, not silent** — unknown scope → 400 with name; out-of-whitelist path → 400 with path; missing file → 404 with path. Never 200 with empty body, never silently degrade
7. **Auditable** — every successful resolution + every rejection logged with scope name + decoded path + reason

## 5. Target Architecture

### 5.1 Unified registry

The `_SCOPE_REGISTRY` becomes the only resolution mechanism. `docs` and `io` are demoted to registry entries with explicit `path` + `allowed_prefixes` derived from the legacy hardcoded values. The `if scope == "docs"` branch is deleted.

Structurally:

```text
                ┌───────────────────────────────┐
                │   GET /api/docs/file          │
                │   GET /api/io/file            │
                └────────────┬──────────────────┘
                             │
                             ▼
                ┌───────────────────────────────┐
                │   _get_scope_registry()       │
                │   (lazy-init + invalidate     │
                │    hook + observer pattern)   │
                └────────────┬──────────────────┘
                             │
                ┌────────────▼──────────────┐
                │   resolve_in_scope(       │
                │     scope_cfg,            │
                │     decoded_path,         │
                │   )                       │
                └────────────┬──────────────┘
                             │
                ┌────────────▼──────────────┐
                │   secrets_blocklist       │
                │   (universal, applied     │
                │    before AND after path  │
                │    resolution)            │
                └────────────┬──────────────┘
                             │
                             ▼
                          serve()
```

### 5.2 Generic invalidation contract

Introduce `cosa.config.cache_registry` with:

```python
# pseudocode for design discussion — exact shape decided at code-write time
def register_invalidator(name: str, fn: Callable[[], None]) -> None: ...
def invalidate_all() -> List[str]: ...  # returns list of invalidated cache names
```

`/api/init` calls `invalidate_all()` after `config_mgr.init()` and includes the result in the response payload:

```json
{
  "status": "success",
  "config_block_id": "Lupin: Development",
  "caches_invalidated": ["scope_registry", "snapshot_mgr", "prediction_engine"],
  "timestamp": "..."
}
```

This solves Mr. Radio's bug AND makes every future derived cache discover its invalidation site automatically by self-registering on import.

### 5.3 Repo-owned manifest (Phase 5, optional but elegant)

Each registered repo MAY ship a `.docview.yml` at its root:

```yaml
# .docview.yml at repo root
version: 1
allowed_prefixes:
  - src/
  - docs/
  - tools/
allowed_root_files:
  - README.md
  - CHANGELOG.md
  - LICENSE
extra_secrets_blocklist:
  - "deploy/keys/**"
  - "*.env"
```

When `build_scope_registry` sees an INI entry pointing at a path that contains `.docview.yml`, it MERGES the manifest's whitelist with the INI's (intersection-conservative: INI restrictions still apply; manifest can NARROW but never WIDEN).

This makes adding a new repo:
1. Drop `.docview.yml` at the repo root (one-time, in the repo itself)
2. Add `external repo <name> path = ...` to Lupin INI (2 lines)
3. `GET /api/init`
4. Done.

Repos own their whitelist. Lupin owns the namespace. Clean separation.

### 5.4 Backward compatibility

The string `scope=docs` and `scope=io` are KEPT FOREVER as the public URL contract. The migration is internal: `docs` becomes a registry entry whose path is `/var/external-projects/lupin` and whose `allowed_prefixes` mirror the current `ALLOWED_PREFIXES` list + a new `allowed_root_files` field initialized from the current `ALLOWED_FILES` set.

External-facing behavior: identical (same files served, same 404/400 patterns).
Internal-facing behavior: one code path, hot-reloadable, repo-owned.

### Q1: `allowed_root_files` whitelist — config-driven or hardcoded?

Currently `ALLOWED_FILES` is a hardcoded Python set. The migration must expose it somewhere. Options:

- **Q1-A (Recommended)**: New INI key `external repo <name> allowed root files` (comma-separated). Mirrors the existing `allowed prefixes` shape. Per-scope, hot-reloadable, no repo edit required.
  - Pros: Symmetric with existing `allowed prefixes` mechanism. Config-only. Lupin owns the namespace control.
  - Cons: Adds N INI keys.
- **Q1-B**: Auto-discover by reading repo root and serving all top-level `*.md`. No INI key.
  - Pros: Zero config. Every repo gets `README.md`, `CHANGELOG.md`, etc. for free.
  - Cons: Less explicit; harder to audit. Surprise files. Conflicts with secrets-blocklist verbosity.
- **Q1-C**: Repo-owned via `.docview.yml` `allowed_root_files` field. INI declares path only.
  - Pros: Repo controls its own public surface. Clean separation.
  - Cons: Adds a new file convention; existing repos need touch.

**Recommendation: Q1-A for Phases 1-4, Q1-C as Phase 5 enhancement (additive, not replacement).**

### Q2: Empty `allowed_root_files` semantics

- **Q2-A (Recommended)**: Empty = NO root files served (must opt in explicitly). Mirrors the secrets-first philosophy.
- **Q2-B**: Empty = wildcard (all top-level files served). Mirrors the existing `allowed_prefixes` empty=wildcard rule.

**Recommendation: Q2-A.** Root files often include sensitive items (`.env`, `.credentials`, `.npmrc`). Defaulting to explicit opt-in matches the principle of least surprise.

### Q3: `.docview.yml` precedence vs INI

- **Q3-A (Recommended)**: INI declares scope existence + path; `.docview.yml` (if present) declares the whitelist. INI keys `allowed prefixes` + `allowed root files` are IGNORED when manifest is present.
- **Q3-B**: INI and manifest INTERSECT (most restrictive wins).
- **Q3-C**: INI and manifest UNION (most permissive wins).

**Recommendation: Q3-A.** Single source of truth for whitelist per scope. Predictable.

### Q4: Scope-name namespace collision

If a repo's `.docview.yml` declares a scope name, does it override the INI?

- **Q4-A (Recommended)**: NO. Manifest only defines the whitelist; the scope NAME is owned by Lupin's INI (the consumer). Multiple consumers could register the same repo under different scope names with different whitelists.
- **Q4-B**: YES. Manifest declares a `canonical_scope_name` field; Lupin's INI must match or the entry is dropped.

**Recommendation: Q4-A.** Consumer owns the namespace; repo owns the content surface.

### Q5: Migration path for legacy `docs` and `io`

- **Q5-A (Recommended)**: Dual-route during transition. New code reads from registry first; if the registry returns `KeyError` for `docs` or `io`, fall back to the legacy hardcoded path with a `warnings.warn` and a deprecation log. Once registry entries land in INI + a release cycle passes, delete the fallback.
- **Q5-B**: Big-bang. Delete legacy path on the same commit that adds registry entries. Atomic; simpler diff.
- **Q5-C**: Permanent dual-route. Keep both forever for safety.

**Recommendation: Q5-B.** The migration is small (4 INI keys total, identical surface area). Big-bang is cleaner; a single commit either ships or doesn't. The deprecation-fallback pattern in Q5-A adds complexity without buying much because the public URL contract is preserved either way (the user sees `?scope=docs` work; they don't see whether it routes through built-in or registry).

### Q6: `.venv` / dev-artifact exposure — secrets blocklist extension?

Today the secrets blocklist (`_scope_registry.py::SECRETS_BLOCKLIST_PATTERNS`) covers credentials. With wildcard scopes pointing at repo roots, dev artifacts become reachable:
- `.venv/lib/python3.X/site-packages/anthropic/_client.py` (potentially huge LLM-keyed source files)
- `node_modules/<pkg>/package.json` (npm leak surface)
- `__pycache__/` (compiled, useless)
- `.idea/`, `.vscode/` (editor config, sometimes credentials)
- `.coverage`, `coverage/` (test artifacts)

Options:
- **Q6-A (Recommended)**: Extend `SECRETS_BLOCKLIST_PATTERNS` with `.venv/**`, `node_modules/**`, `__pycache__/**`, `.idea/**`, `.vscode/**`, `dist/**`, `build/**`, `target/**`, `*.pyc`, `coverage/**`, `.coverage`, `.pytest_cache/**`. Single config knob; defense-in-depth; matches industry-standard `.gitignore` patterns.
- **Q6-B**: Require explicit `extra_secrets_blocklist` in `.docview.yml` per repo. More precise; more burden.
- **Q6-C**: Both. Universal floor (Q6-A) + per-repo override (Q6-B).

**Recommendation: Q6-C.** Universal floor catches the obvious wins; per-repo manifest handles repo-specific quirks (e.g., a repo with custom secrets in a non-standard location).

### Q7: `/api/init` payload shape

Per §5.2 the response gains `caches_invalidated`. Strict additive (no breaking change) but the field needs a contract.

- **Q7-A (Recommended)**: `caches_invalidated: List[str]` — names of registered invalidators that ran. Empty list = no caches registered.
- **Q7-B**: `caches_invalidated: Dict[str, Dict]` — per-cache metadata (last reset time, current size, etc.).

**Recommendation: Q7-A.** Minimal contract; observability via separate `/api/cache/status` endpoint if needed later.

### Q8: Per-cache registration mechanism — global registry or DI?

- **Q8-A (Recommended)**: Module-level `cosa.config.cache_registry` with `register_invalidator(name, fn)` called at module import time. Mirrors the existing pattern for FastAPI routers.
- **Q8-B**: Explicit DI — invalidators are passed into `/api/init` at boot via a list in main.py.

**Recommendation: Q8-A.** Self-registration scales; explicit DI requires updating main.py for every new cache.

### Q9: Doc-link scope guidance in CLAUDE.md

Today CLAUDE.md says "prefer built-in `docs` for Lupin files." After migration, `docs` still works (backward compat) but is no longer special. Update guidance:

- **Q9-A (Recommended)**: Keep `docs` as the recommended scope name for Lupin files in CLAUDE.md (no consumer-facing churn). Internally it's a registry entry; externally it's still `?scope=docs`. Best of both worlds.
- **Q9-B**: Rename `docs` to `lupin-docs` to make the migration externally visible. Forces all existing links to break.

**Recommendation: Q9-A.** No reason to break public contracts that already work.

### Q10: Test posture during migration

- **Q10-A (Recommended)**: Add new tests for unified registry path PLUS keep existing tests for legacy paths PLUS add a parametrized regression test that exercises both the legacy URL (`?scope=docs&path=bug-fix-queue.md`) and the equivalent registry-routed URL produce IDENTICAL responses.
- **Q10-B**: Replace existing tests with new ones; trust the diff review.

**Recommendation: Q10-A.** The parametrized regression test is the single most valuable test in this migration — it proves backward compat is intact.

### Phase 1 — Generic invalidation contract + `/api/init` upgrade

- **NEW module** `src/cosa/config/cache_registry.py`:

  - `cosa/agents/prediction_engine/prediction_engine.py` calls `register_invalidator("prediction_engine", PredictionEngine.reset)`
- **`/api/init` handler edits** in `system.py`:

### Phase 2 — Universal secrets-blocklist floor extension (LOAD-BEARING; ships before any wildcard scope)

Per Q4-B + Q2-C, the floor blocklist is the sole guardrail when a repo lacks a manifest. It MUST be comprehensive and ship FIRST.

**Pattern syntax (F4)**: All patterns are `re.Pattern` objects stored in the existing `SECRETS_BLOCKLIST_PATTERNS` tuple. Glob-style notation like `.venv/**` is conceptual shorthand for "anywhere this directory name appears as a path segment." The actual regex is `re.compile(r"^\.venv$")` — the existing `_is_secrets_path()` matcher iterates path segments and applies each pattern via `pattern.search(part)`, which catches `.venv` at the directory boundary regardless of how deep the requested path goes.

### Phase 3 — `.docview.yml` manifest parser + ScopeConfig extension

Per Q2-C, the manifest is the whitelist authority. Per Q4-B add-only, the manifest can EXTEND the blocklist.

- New `cosa/config/docview_manifest.py` with Pydantic `BaseModel`:
  ```python
  from pydantic import BaseModel, ConfigDict, Field, field_validator
  import re

  class DocviewManifest( BaseModel ):
      model_config = ConfigDict( extra="forbid" )  # rejects unknown fields per F6 + AC3.4

      version           : int       = Field( default=1, ge=1, le=1 )
      allowed_prefixes  : List[ str ] = Field( default_factory=list )
      allowed_root_files: List[ str ] = Field( default_factory=list )
      extra_blocklist   : List[ str ] = Field( default_factory=list )
      # NO 'remove_from_blocklist' field — per Q4-B repos cannot weaken the floor

      @field_validator( "extra_blocklist" )
      @classmethod
      def compile_blocklist_patterns( cls, value: List[ str ] ) -> List[ str ]:
          """F6: regex pattern syntax for extra_blocklist; reject malformed regex at parse time."""
          for pattern in value:
              try:
                  re.compile( pattern )
              except re.error as e:
                  raise ValueError( f"Invalid regex in extra_blocklist: {pattern!r} ({e})" )
          return value
  ```
