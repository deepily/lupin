## TL;DR

The reported "body-display truncation" is **two distinct symptoms with one real bug**:

| Manifestation | Reality | Root cause |
|---|---|---|
| **#2 — ~750-char inbound DM system-reminder** | **Not a truncation bug.** The listener's `_handle_commons_question_received` injects a *fixed-length framing template* (~700 chars). The body is **never** included in the system-reminder by design (v1.0 punt per `cc_notification_listener.py:408-413`). Recipient must call `commons_read` to fetch the actual body. | Design-as-intended |
| **#1 — ~250-char outbound `commons_read` body** | **Real bug.** Entry bodies containing a markdown `---` thematic break are silently truncated at the first `---` because `commons_store.ENTRY_SEPARATOR = "\n---\n"` collides with markdown syntax. The disk file is intact; the *parser* drops content. | Separator-collision in `commons_store._parse_entry_block` / `read()` |

**Net effect on the user**: Manifestation #2's template tells the recipient "call `commons_read` to retrieve the body." If the body happens to contain `---` (extremely common in markdown — section breaks, YAML frontmatter, table starts), the read returns only the header portion. The wrapper's `push_mode_active=true, dm_dispatched=true` success-return is misleading — verification-observability gap.

**Recommended fix (minimum-blast-radius):** change `ENTRY_SEPARATOR` to a token that cannot legitimately appear in markdown bodies (e.g., `\n<<<__lupin_commons_entry_boundary__>>>\n`). Update both writer (`_format_entry` callsite) and reader (`read()` split). One-shot migration script needed for existing topic files.

## 2. Manifestation #2 — NOT a bug (listener framing template by design)

### 2.1 Listener code reads

`src/lupin_cli/claude_code/hooks/lib/cc_notification_listener.py:391-442`:

```python
def _handle_commons_question_received( self, notification ):
    # ...
    payload          = notification.get( "payload" ) or { }
    question_id      = payload.get( "question_id" )
    topic            = payload.get( "topic" )
    asker_session    = payload.get( "asker_session" ) or "unknown"
    # ...
    reminder_body = (
        f"COMMONS PEER MESSAGE (question_id {question_id}, topic {topic}, from session {asker_session[:8]}):\n\n"
        f"A peer CC session has addressed a directed DM to you on topic '{topic}' with question_id '{question_id}'.\n"
        f"Read the message body via commons_read(topic='{topic}', limit=10) and look for the entry whose "
        f"metadata.question_id == '{question_id}'. To reply, call commons_post(topic='{topic}', body='<your reply>', "
        f"metadata={{'in_reply_to': '{question_id}'}}) — the original asker's watcher will push your reply back "
        f"to their tmux session via Phase 3 commons_answer_received."
    )
    wrapped = f"<system-reminder>\n{reminder_body}\n</system-reminder>"
    # ...
    self._inject_via_tmux( wrapped, wrap=False )
```

The docstring at lines 408-413 is explicit:

> "For v1, the body is not in the dispatch payload (the entry sits in the commons topic) — the listener injects the framing with a pointer to the topic + question_id so the recipient AI can call commons_read() to retrieve the actual body and any subsequent context. **v1.1 enhancement: include body in dispatch payload to avoid the read round-trip.**"

### 2.2 Template length calculation

With a 36-char UUID, 11-char topic (e.g., `dm-mr_radio`), 8-char session prefix:

| Component | Length |
|---|---|
| Header line `COMMONS PEER MESSAGE (question_id …, topic …, from session …):` | ~95 |
| First explanatory line | ~145 |
| Read-instructions line | ~138 |
| Reply-instructions line | ~110 |
| Closing line | ~115 |
| `<system-reminder>\n…\n</system-reminder>` wrapper | ~37 |
| **Total** | **~640 chars + topic-specific padding ≈ 650–760** |

That matches Tiberius's observed "~750 chars" exactly. **What he saw was the framing template, not a truncated body.**

### 2.3 Implication

Manifestation #2 is consistent with v1's deliberate design: the system-reminder is a *pointer*, not a body carrier. The bug Tiberius observed is downstream — the recipient calls `commons_read`, which then truncates per Manifestation #1.

A v1.1 enhancement (include body in dispatch payload) is a worthwhile follow-up but unrelated to the truncation bug at hand.

## 3. Manifestation #1 — REAL bug (separator collision)

### 3.1 The root cause line

`src/lupin_mcp/commons_store.py:37`:

```python
ENTRY_SEPARATOR              = "\n---\n"
```

### 3.2 The write path

`_format_entry` (line 131-155) builds an entry's markdown block:

```python
return (
    f"## {ts} | {persona_name} {persona_icon} #{session_id}\n"
    f"**metadata**: `{metadata_json}`\n\n"
    f"{body.strip()}\n"
)
```

`CommonsStore.post` (line 196-253) then appends the entry's markdown + `ENTRY_SEPARATOR` to the topic file under `fcntl.flock`. **Body is written verbatim, no character escaping or sanitization.**

### 3.3 The read path

`CommonsStore.read` (line 255-286):

```python
content    = path.read_text( encoding="utf-8" )
_, body    = _split_frontmatter( content )
raw_blocks = body.split( ENTRY_SEPARATOR )    # ← splits on every "\n---\n" in the file
entries: List[ Dict[ str, Any ] ] = [ ]
for block in raw_blocks:
    entry = _parse_entry_block( block )       # ← returns None if block lacks "## TS | persona icon #session" header
    if entry is not None:
        entries.append( entry )
```

`_parse_entry_block` (line 87-128) requires the FIRST line of the block to match `_HEADER_RE` (the `## TS | persona_name persona_icon #session_id` regex). If not, it returns `None` and the block is silently dropped.

### 3.4 The collision

Markdown commonly uses `---` on its own line as a **thematic-break** separator (after H1 headings, between sections, etc.). When an entry body contains any `\n---\n`, the `read()` split splits the body at that point. The post-`---` content fails the header-line regex, gets `None`-returned, and silently dropped.

### 3.5 Direct evidence — disk vs `commons_read` comparison

Topic `cascaded-prototype-section-A` (32,224 bytes on disk, 8 real entries). I probed `commons_read(topic="cascaded-prototype-section-A", limit=50)` and compared to disk content:

| Entry | Body bytes via commons_read | Body bytes on disk (header → next valid ENTRY_SEPARATOR) | Truncation? |
|---|---|---|---|
| Mr Radio Round-2 revision (16:42:56) | ~440 | ~4,007 | **YES** — `---` thematic break after preamble |
| Tiberius "Suggested Author Revisions" (16:40:50) | ~1,500 | ~1,500 | No |
| Tiberius "Manager Classification — Stage 2" (16:34:24) | ~2,300 | ~2,300 | No |
| Arnold "Viability/Gap Review" (15:50:38) | ~440 | (multi-KB review) | **YES** — `---` in review structure |
| Tiberius "Manager Classification + Stage 1 Handoff" (15:47:59) | ~2,200 | ~2,200 | No |
| Mr Radio Round-1 revision (15:46:35) | ~280 | (multi-KB section) | **YES** — `---` thematic break |
| Rachel "Usability/Reuse Review" (15:03:53) | ~210 | (multi-KB review) | **YES** — `---` in review structure |
| Mr Radio original draft (14:59:38) | ~210 | (multi-KB section) | **YES** — `---` thematic break |

Pattern is unmistakable: entries with `---` in their body get truncated; entries without `---` come through fully.

`grep -n "^---$" io/commons/cascaded-prototype-section-A.md` returned 10+ matches at lines 1, 6, 8, 18, 57, 63, 73, 108, 119, 158, … — far more than the 8 actual entries. Each of those internal `---` lines is a markdown thematic break inside someone's body, and each one breaks parsing.

### 3.6 Why this contradicts Mr Radio's fastmcp conclusion

Mr Radio's 2026-05-17 investigation (commit `062c731`, doc `src/rnd/v0.1.7/2026.05.17-commons-dm-topic-case-and-truncation/90-execution-log.md` §Phase 3-4) concluded:

> "Combined evidence … The cap **lives in the fastmcp transport layer** (or above — in Claude Code's MCP body serialization). NOT in commons_store."

His chain of reasoning:
1. Direct-write probe via `probe_commons_post_direct.py` — all 9 lengths (100 → 128,000 chars) survived intact through `CommonsStore.post`. ✅ True — the WRITE side has no cap.
2. Tiberius's truncated entry on disk: 195 chars in body, well-formed `---` separator after, well-formed next entry. → "body was already short when it reached `_format_entry`" → "truncation upstream"

**But step 2's interpretation hinges on assumption that the disk content showed the entry's BODY ending mid-sentence — and Mr Radio reached that conclusion via `awk '/header/,/^---$/'` or equivalent**, which itself stops at the first `---`. The same separator collision affects any tool that scans for `---` as an entry boundary. The on-disk *file* likely had the full ~4000-char body, but Mr Radio's extraction stopped at María's internal `---`.

**This is a serious challenge to the Sub-bug B conclusion.** If confirmed, Sub-bug B and Manifestation #1 share the same root cause — and the fastmcp-cap finding (commit `062c731`) is the wrong story.

## 5. Recommended fix scope

### 5.1 Minimum-blast-radius fix

**Change `ENTRY_SEPARATOR`** to a token that cannot legitimately appear in markdown bodies. Candidates (final choice is Rick's call):

| Candidate | Pros | Cons |
|---|---|---|
| `\n<<<__lupin_commons_entry_boundary__>>>\n` | Cannot appear in any sane markdown / code / prose | Slightly verbose on disk |
| `\n===__entry_boundary_v2__===\n` (any unique stamp) | Short-ish; visually clear | Future markdown may invent `===` syntax |
| Use a binary-safe NUL byte sequence `\n\x00ENTRY\x00\n` | Cannot collide with text | Breaks `cat` / `less` UX on the topic files (currently the files are human-readable markdown — a feature) |

**Recommended**: `\n<<<__lupin_commons_entry_boundary__>>>\n` (preserve human-readability; collision-free in practice).

### 5.2 Migration story

Existing topic files use `\n---\n`. After landing the separator change, options:

| Option | Pros | Cons |
|---|---|---|
| **α — one-shot migration script** | Single canonical file format going forward; idempotent re-run safe | Has to handle the ambiguity: is `\n---\n` in an old file an entry boundary or a body thematic break? Heuristic: an entry boundary is *immediately followed* by a `## <ISO-ts> \| <persona> <icon> #<session>` line. |
| **β — read-path fallback** | Zero data mutation; reads both old and new separators | Two read codepaths forever; α heuristic still required to disambiguate within old files |
| **γ — leave existing files alone, switch only for new writes** | Trivial | Permanent fragmentation between old and new files; doesn't fix already-corrupted reads |

**Recommended**: α (one-shot migration), using the post-`---`-line lookahead for `## <ISO-ts>` as the disambiguator. Pairs with `src/scripts/migrate-commons-entry-separator.py` analogous to Mr Radio's `src/scripts/migrate-dm-topic-case.py`.

### 5.3 Defense-in-depth (orthogonal)

`_parse_entry_block` could emit a `_log` warning when it receives a block that doesn't start with `## ` — currently those are silently dropped. A non-failing warning at read time would have surfaced this bug months ago.

### 5.4 Test pyramid

Per the 100% coverage mandate + `:7999`/`:8000` venue rubric:

- **Unit (`:7999`)**: `src/tests/unit/test_commons_store_separator_collision.py` — parametrize: bodies containing `\n---\n` round-trip intact; bodies containing `---` not surrounded by newlines round-trip intact; multi-`---` bodies round-trip intact; legacy file-format read via fallback works
- **Smoke (`:7999`)**: extend `quick_smoke_test()` in `commons_store.py` to write+read a body containing a markdown thematic break
- **Migration unit (`:7999`)**: dry-run + with-backup + idempotent re-run tests for the migration script (mirror Mr Radio's `test_migrate_dm_topic_case.py` shape)
- **Integration (`:8000`, scheduled)**: end-to-end DM round-trip with a `---`-containing body, verify the recipient's downstream `commons_read` returns the full body

### 5.5 Escalation vs in-place

- **In-place fix** is correct here — the bug is localized to two files (`commons_store.py` + migration script) and the fix is mechanical.
- **NOT bug-fix-mode**: bug-fix-mode is for architectural changes; this is a 5-LOC writer change + 2-LOC reader change + one migration script.
- **Scope-creep risk**: if Sub-bug B is in fact this same bug (cf §3.6), the Sub-bug B fix-shape candidates (atomic write, fsync, checksum) may all become unnecessary. Rick's call.

## 7. Ownership-lens framing

This bug is a **textbook verification-observability failure** in the sense Pass 2 of `/plan-review` targets:

- The wrapper returns `push_mode_active=true, dm_dispatched=true` — the success-contract claims completion.
- The recipient's `commons_read` returns a truncated body — the work is silently incomplete.
- No `EXECUTOR: AI` step that runs `commons_send_to` can verify the message landed intact, because the success-return doesn't carry the on-disk content for comparison.

The §5.3 defense-in-depth fix (warn on orphan blocks at read time) is the structural ownership-fix: it converts a silent failure into an observable one. The §5.1 fix is the proximate cause closure.

A future Ownership-rubric audit could surface: **any wrapper that returns `success=true` based on the WRITE completing should also verify the READ round-trips**. That's a broader pattern worth catching in future plan reviews.
