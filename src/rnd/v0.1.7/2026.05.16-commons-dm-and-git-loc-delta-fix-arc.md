## Root causes (the deeper-dive findings)

### F1: `LUPIN_MCP_API_KEY` env-var read-without-set — a wiring gap from yesterday

The cosa-voice MCP server is a subprocess that needs to make authenticated HTTP calls to the Lupin REST API (specifically `/api/commons/register-question` for Phase 0 DM push). I added the read site for the env var in commit `9bbf298` (Inter-Session DM Phase 0, 2026-05-15) but never landed the matching set-side wiring — no docker-compose entry, no .env file, no keys/ file. The env var has been UNSET in both host and container ever since.

**Rick caught the deeper issue**: there's already an established canonical pattern. `cosa.memory.embedding_provider._http_api_key()` at line 177 uses `du.get_api_key("notification-api-claude-code-dev")` — the same long-lived `ck_live_*` API key used by the embedding HTTP endpoints and the notification authentication infrastructure (Phase 2.5). The key file is already in place (`src/conf/keys/notification-api-claude-code-dev`, mode 600, established March 4).

**Fix**: Add a `_mcp_outbound_api_key()` helper in `cosa_voice_mcp.py` mirroring the embedding_provider pattern. Swap the env-var lookup to the canonical helper. No new key to mint, no docker-compose changes, no wiring.

### F2: `commons_send_to` calling a `@mcp.tool` decorator instance

`commons_send_to` at `cosa_voice_mcp.py:1931` called `commons_ask_async(topic=..., body=..., ...)`. But `commons_ask_async` is also `@mcp.tool`-decorated, which means the bare name resolves to a `fastmcp.FunctionTool` instance — NOT a Python-callable function. Result: `TypeError: 'FunctionTool' object is not callable` on every invocation.

**Fix**: Extract a private `_commons_ask_async_dispatch()` helper that both `@mcp.tool`-decorated functions delegate to. Standard refactor — preserves both public tool APIs while eliminating the self-call.

### F3: Silent push-mode fallback with zero observability

When `push_mode_enabled=True` but `auth_header is None` (e.g., the env-var gap above), `_commons_ask_async_impl` skipped push-mode WITHOUT logging anything, WITHOUT setting any error key in the result dict. Caller saw `push_mode_active: false` and no other signal — couldn't distinguish "I forgot to enable push-mode" from "I tried but auth was missing." The 422 `RecipientResolutionError` was the only error path that surfaced anything.

**Fix**: Add a `register_skip_reason` key whenever push-mode is REQUESTED but skipped. Values: `"missing_api_base_url"`, `"missing_auth_header"`, `"register_network_error"`, `"register_failed_status_<N>"`, `"register_failed_422"` (last one paired with the existing `recipient_resolution_error` key).

### F4: Cross-repo path resolution — Tiberius's bug

`_default_csv_path` was using `cu.get_project_root()` (always LUPIN_ROOT) as the base directory. When users ran `python -m cosa.repo.run_git_loc_delta --repo-path /path/to/sibling-repo --branch --output csv`, the CSV landed in Lupin's `io/git-loc-delta/` tree instead of the target repo's tree. Cross-contamination + wrong location for any cross-repo workflow (which IS the primary use case — Tiberius wired this tool into the canonical session-end ritual for every repo).

**Two-stage fix**:
1. **First pass**: switch `cu.get_project_root()` → `os.path.abspath(repo_path)`. Worked for cross-repo but **broke in-tree case when invoked from a subdir** (cwd=`lupin/src/`, `--repo-path .` → CSV at `lupin/src/io/git-loc-delta/` instead of `lupin/io/git-loc-delta/`).
2. **Final fix**: use `git rev-parse --show-toplevel` from the supplied `--repo-path` to resolve the actual repo root. Matches Tiberius's workaround in his `workflow/session-end.md` §6.2 integration. Subprocess timeout 5s; non-zero return code → fall back to `os.path.abspath(repo_path)` (handles paths that aren't git repos).

### F5: Cross-target test coverage — the underlying testing-failure

My test pyramid for the initial Daily LoC Delta ship only invoked the tool with `--repo-path .` and `--repo-path src/cosa` — both INSIDE the Lupin tree. I never tested running it against a sibling repo at a different filesystem location, which is exactly the case Tiberius hit. The Testing Ownership Mandate ("user is never the tester") was violated.

**Fix**: Add 3 new unit tests:
- `test_default_csv_path_branch_mode_resolves_under_target_repo_not_lupin` — locks the cross-repo case
- `test_default_csv_path_today_mode_also_target_aware` — locks the today/explicit-range case
- `test_default_csv_path_same_tree_still_lands_under_lupin` — locks the no-regression-on-in-tree case

**Memory saved**: `feedback_tests_must_cover_cross_target_invocations` — whenever a CLI takes `--repo-path` / `--dir` / `--workspace`, the test pyramid MUST include an invocation pointing OUTSIDE the project tree.

## Deployment caveat — MCP subprocess staleness

The cosa-voice MCP server is a subprocess started at CC-session-start. **fastmcp does NOT auto-reload on file change** (unlike uvicorn's `--reload`). So:

- **Code on disk**: fix is correct (verified via py_compile + unit tests).
- **Running MCP process in this session**: still on pre-fix code. Verified by re-issuing `commons_ask_async` with `recipient_persona="Tiberius"` — got `push_mode_active: false` and NO `register_skip_reason` key (which the post-F3 code would have surfaced).
- **Next CC session**: spawns a fresh MCP subprocess that reads the latest disk state. Fix is live there automatically.

No special restart command needed. Rick can either let it pick up on the next session start, or explicitly kill the cosa-voice MCP subprocess and reattach.
