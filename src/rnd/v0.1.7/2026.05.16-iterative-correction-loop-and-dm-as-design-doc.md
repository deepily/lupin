## TL;DR

A two-session collaboration pattern emerged organically across 2026-05-16 between María 🌸 (Lupin) and Tiberius 🌑 (planning-is-prompting). Over ~4 hours and ~12 directed DMs across 3 nested correction loops, we shipped:

- A 5-fix bug-fix arc (commit `f4e0370`)
- A doc-architecture framework (5-surface MCP discovery model)
- A 21,316-char MCP `instructions` payload (commit `b550f10`)
- A refresh of `cross-session-communication.md` doctrine
- 2 new bug findings (case-fragmentation, system-reminder truncation)
- 8+ memories saved to durable storage

The output was **measurably sharper** than either of us would have produced alone. The mechanic that made this possible is the **iterative correction loop** — a low-ego peer-review pattern where both sides willingly retract earlier positions when the framing improves. The substrate that carried it is **DM-as-mini-design-doc** — the threaded DM exchange itself became the canonical artifact, lower-overhead than a meeting and higher-fidelity than chat. This doc captures both patterns + supporting infrastructure + open questions for replication.

## 2. Pattern: Iterative Correction Loop

**Definition**: a peer-review exchange in which BOTH parties willingly retract earlier positions when the framing improves, even after publicly committing to those positions. The output sharpens through 2-5 rounds of correction.

**Mechanism**:

```
1. Side A proposes framework F1
2. Side B counters with framework F2 ("F1 wrong because X")
3. Side A considers F2 — accepts, retracts F1
   OR Side A counter-counters with F3 ("F2 wrong because Y")
4. Side B considers F3 — accepts, retracts F2
   OR re-proposes F2' with refinement
5. Convergence — both sides agree on F-final
6. F-final is saved to durable storage (memory or design doc)
```

**Worked example** (from Loop 3 above — the truncation debate):

- **F1 (María)**: "The 00:18:31Z entry in `dm-maria.md` is truncated at the file level — I can see it ends at 'ranked by impact:' on disk via `cat`"
- **F2 (Tiberius)**: "No, file is intact on my side — `wc -c` reports 31,495 bytes; `grep -n '(Q1)'` finds the Q&A headers at line 231. Your `cat` must be hitting a stale FS / wrong path."
- **Evidence exchange**: both sides produce substrate-level proofs (file sizes, grep output, line numbers). The disagreement is REAL — both observations are honest — but EXACTLY ONE must be wrong about the underlying file state.
- **F3 (María, retracting F1)**: "Just re-ran from the absolute path — your grep is correct, file IS intact. My earlier `cat` was reading something stale."
- **F-synthesis (joint)**: "The file is intact. But the system-reminder push-injection layer DOES truncate — that's a SEPARATE real bug (#7) worth documenting. Misunderstanding produced a true finding via evidence-based debate."
- **F-final**: bug #7 documented in MCP instructions §"Failure Modes" + receipt-etiquette rule "always re-fetch via `commons_read` for the canonical body, don't trust the system-reminder text"

This is the canonical iterative-correction-loop shape — public position A asserted, public position B counter-asserted, evidence exchanged, A retracted in favor of new synthesis C. The Loop 2 framework convergence (see §2) is a DIFFERENT pattern (additive refinement, §4) where one side never publicly committed to the initial framing.

**Replicable conditions**:

| Condition | Why it matters |
|---|---|
| **Low-ego peer-review** | Neither side defends a position past the point of evidence — retraction is honorable, not a loss |
| **Written-medium-so-arguments-can-be-revisited** | DM thread persists; each side can re-read the other's framing before committing. Verbal exchanges lose this affordance. |
| **Explicit framework-vocabulary** | "5-layer" / "3-layer" / "reading-timing" — labels are short enough to argue about. Without vocabulary, corrections devolve into vague disagreement. |
| **Asymmetric domain knowledge** | If both sides knew everything, no correction would occur. The loop works because Side A knows X and Side B knows Y; both have to listen. |
| **Bounded scope** | The architectural framework was a small enough decision to converge in 4 rounds. A larger scope (e.g. "redesign the entire commons protocol") would deadlock or fragment. |

**Failure modes** (anti-patterns):

- One side defends a position past evidence: loop deadlocks, escalates to user
- No explicit framework vocabulary: corrections become "I think you're wrong" without traction
- Scope too large: too many subdecisions to converge in bounded rounds
- Both sides defer to the user: no peer correction happens; user becomes the bottleneck

## 3.5 Sibling Pattern: Additive Refinement (distinct from §3)

**Definition**: a peer-review exchange in which one side proposes a framework, the other side ENDORSES it on receipt (silently retiring any private working model that disagreed) and ADDS structure (enrichments, corollaries, missing cases) rather than counter-proposing. Convergence happens in 2-3 DMs with no public retraction.

**Why distinct from §3**: in iterative correction with retraction, BOTH sides publicly assert positions that then get retracted. In additive refinement, only ONE side asserts a public position; the other side's contribution is enrichment, not opposition.

**Worked example** (from Loop 2):

- **F-public (María)**: 5-layer model with MCP `instructions` as a discrete surface
- **F-private (Tiberius, never asserted publicly)**: 3-layer model that omitted MCP `instructions`
- **Tiberius's response on receipt**: "Your architectural framework is better than what I was proposing. I had a 3-layer mental model... You correctly identified a 5-layer model." [public retirement of private framing]
- **Tiberius's contribution**: 6 Q2 enrichments (nav map, cross-session-bug-filing pattern, receipt-side framing, DM-vs-broadcast, instructions-vs-rider distinction, deep-doctrine cross-pointer footer)
- **F-final**: 5-layer model + 6 enrichments — saved as `feedback_mcp_doc_layering_decision_point_vs_doctrine`

**Replicable conditions** (overlap with §3 + DM-as-Mini-Design-Doc):

| Condition | Why it matters for additive refinement specifically |
|---|---|
| **Honest acknowledgment of better framing** | Side B has to be willing to publicly say "your framing is better than mine" — even when their private model differed. Without this, the additive contribution gets contaminated by face-saving counter-arguments. |
| **Asymmetric domain knowledge** | Side A proposes the framework; Side B enriches it from their own domain. If both knew the same things, no enrichment would happen. |
| **Explicit enrichment structure** | "Q2 additions: a, b, c, d, e, f" — enumerated. Without structure, enrichments scatter and get lost. |

**When this pattern is the right choice** (vs §3):

- One side has a clearer initial framing; the other side has complementary knowledge
- Time pressure favors fast convergence
- No public assertion has been made yet that needs retraction

**When §3 is the right choice** (vs §3.5):

- Both sides have already asserted public positions
- Evidence is available to resolve the disagreement
- Time available for 3-5 rounds of correction

## 3.6 What This Pattern Is NOT

Adjacent patterns that look similar but are distinct:

| Not... | Because... |
|---|---|
| **Pair programming** | No shared editor; both sides edit independent surfaces. Coordination happens via DM, not via cursor co-location. |
| **A meeting transcript** | Asynchronous-friendly; durable + threaded + scannable. A meeting is bounded by clock-time; this is bounded by problem-convergence. |
| **Code review** | Architecture > implementation. Code review typically arrives AFTER the architectural decision; this pattern PRODUCES the architectural decision. |
| **Slack / chat** | Every message is threaded + correlated + durable. Scroll-loss isn't possible. The thread persists as a first-class artifact. |
| **Mob programming** | 2 sides, not N. The patterns here might NOT extend to 3+ participants — that's open question §8.1. |
| **Email threads** | Push-mode delivers in seconds, not minutes/hours. Latency profile is closer to chat than email, but durability profile is closer to email than chat. |
| **GitHub PR review** | No central artifact under review; the DM thread IS the artifact. PR reviews require something to review BEFORE the conversation; this pattern PRODUCES the thing-to-be-reviewed. |

The closest adjacent pattern is **architecture-design-via-Discourse-thread** (long-form async forum discussion). The differences: this pattern uses MCP-mediated commons + push-mode for low-latency exchange, and participants are AI personas not humans.

## 4. Pattern: DM-as-Mini-Design-Doc

**Definition**: a directed DM thread between two CC sessions serves as both the working medium AND the persistent artifact of an architectural conversation. The thread itself is the design doc — no separate document gets created until convergence.

**Mechanism**:

```
1. Initiator A DMs B with the problem statement + initial framing
2. B replies threaded with counter, refinement, or convergence-vote
3. A iterates with B's input incorporated
4. (Optionally: re-loop steps 2-3 until convergence)
5. At convergence: one side writes the durable artifact
   (R&D doc, memory, code change, etc.) referencing the DM thread by ID
```

**Worked example** (Loop 2):

- Initiator: Rick "tapped" both María + Tiberius via broadcast
- DM thread became the design discussion: 4 DMs over 10 minutes
- At convergence: María saved `feedback_mcp_doc_layering_decision_point_vs_doctrine` memory; both sides retained the thread for reference

**Replicable conditions**:

| Condition | Why it matters |
|---|---|
| **Blackboard-style commons backbone with threaded `in_reply_to` correlation** | Every message is durable, scrollable, search-indexable. The thread is reconstructable later by anyone with `commons_read` access. |
| **Push-mode for low-latency exchange** | Without push, the loop slows from minutes to hours. Push-mode is what makes the cadence feel like a conversation, not asynchronous mail. (Caveat: see §5 — push is upgrade, not requirement) |
| **≥2 sessions awake-and-engaged simultaneously** | Today both sessions were active. Async-first variants of this pattern are an open question (§9). |
| **Shared frame ("Rick tapped both of us")** | Both sides know they're in a designated collaboration, not a random ping. Without the shared frame, each side might triage as low-priority and never engage. |

**Advantages over alternatives**:

- vs. **scheduled meeting**: zero coordination overhead, conversation happens whenever both sides are available
- vs. **chat/Slack**: every message is durable + scannable; no scroll-loss; can be replayed for new participants
- vs. **comment-on-doc**: design doesn't have to exist yet; thread BECOMES the doc

## 4. Pattern: Paired-by-DM-Paired-by-Commit

**Definition**: two sessions working on adjacent surfaces (different repos, different files, different layers of a stack) coordinate via DM during design, then ship their respective surfaces in COORDINATED commits with cross-references. Each commit message points at the other side's surface as "already shipped — see X."

**Mechanism**:

```
1. Pair design via DM (per §3)
2. Each side identifies their work surface
3. Each side commits independently to their surface
4. Each commit message includes a cross-pointer to the other side's surface
5. (Optionally: project README adds an entry pointing at both surfaces)
```

**Worked example** (today's full arc):

| Surface | Side | Result |
|---|---|---|
| `planning-is-prompting/workflow/cross-session-communication.md` refresh + thin pointer in `~/.claude/CLAUDE.md` | Tiberius | Shipped 2026-05-16 PM |
| `lupin/src/lupin_mcp/cosa_voice_mcp.py` MCP `instructions` expansion + 6 commons_* docstring upgrades | María | Shipped 2026-05-16 PM commit `b550f10` |

María's commit message cross-points: "Tiberius took the boot-time-doctrine side (his refresh already shipped); I took the MCP-server-bound side."
Tiberius's §7 of his doctrine doc cross-points: "f4e0370 ✅ SHIPPED with the verification details from this session."

**Replicable conditions**:

| Condition | Why it matters |
|---|---|
| **Distinct work surfaces** | Avoids merge conflicts; each side ships independently |
| **Cross-reference discipline** | Without explicit pointers, future readers can't navigate between the two halves |
| **Parallel sessions agreeing to ship within the same wall-clock window** | The "paired" aspect is temporal — both ship today, not "eventually." Out-of-sync commits lose the cross-reference value because one side ships into a tree the other isn't ready for. |
| **Independent commit authority** | Each side has push access to their respective repo. Today's pattern works because Lupin parent and planning-is-prompting are both pushed independently. |

## 5. Five Additional Patterns (Tiberius-contributed)

### 5.1 Misunderstanding-as-Information

**Definition**: a debate launched from a WRONG premise can still yield a RIGHT conclusion if both sides bring evidence rather than positions.

**Today's example**: María observed "file-level truncation" in `dm-maria.md`. Tiberius observed "file is intact" via his own grep. The disagreement was real, but both sides brought EVIDENCE (file size byte counts, grep output, direct cat). Outcome: María's earlier observation was wrong (stale FS state), but the productive byproduct was identifying that the system-reminder push-injection layer DOES have a truncation cap (real bug #7, now documented in MCP instructions).

**Mechanic**: when positions disagree, both sides must produce substrate-level evidence (file sizes, grep output, byte counts, ps output) rather than re-asserting their position. The substrate is shared — both sides can verify against it.

**Replicable conditions**: shared substrate access (filesystem, server, etc.) + evidence-first norms.

### 5.2 Physical-Substrate-as-Fallback-Channel

**Definition**: when an abstraction layer (push, MCP, message bus) fails, drop one level lower to the durable substrate (filesystem, database, etc.).

**Today's example**: when push-mode wasn't working pre-`f4e0370`, both María and Tiberius could `cat` the same `dm-tiberius.md` file on disk because we share `LUPIN_ROOT`. The filesystem-as-substrate provided graceful degradation.

**Mechanic**: the commons system is layered:
- **Abstraction tier**: `commons_send_to`, push-mode, MCP injection
- **Substrate tier**: `io/commons/<topic>.md` files

When the abstraction breaks, drop to the substrate. The pattern works because the underlying medium is durable (write-once + append-only).

### 5.3 Look at the Substrate When Confused

**Definition**: when something seems off at the abstraction layer, look at the substrate directly.

**Today's example**: the case-fragmentation bug surfaced when Tiberius listed `io/commons/` directly via `ls` and saw TWO files (`dm-Tiberius.md` + `dm-tiberius.md`). Neither side would have noticed via `commons_read` alone (each call resolves to one topic file at a time).

**Mechanic**: abstraction layers can hide structure that the substrate exposes plainly. `ls` + `cat` + `grep` are the primitives that bypass abstraction.

### 5.4 Push-Mode is Ergonomic Upgrade, NOT Requirement

**Definition**: the cross-session bug-filing pattern (DM + queue-as-fallback) works under degraded push because of the queue backup. Don't design patterns that assume push will always succeed.

**Today's example**: when push failed (pre-fix), the message still landed on the topic file via the blackboard write. Recipients could poll. The pattern was robust to push failure because the substrate (file write) remained intact.

**Mechanic**: dual-channel design. Every interaction should land on the substrate FIRST; push is the optimization layer that surfaces the substrate event to the recipient's tmux faster.

### 5.5 Bug-Discovery-as-Collaboration-Byproduct

**Definition**: bugs are surfaced naturally when sessions dogfood the system to collaborate on something else. The collaboration is the test harness.

**Today's example**: María + Tiberius did not set out to find bugs in the commons / DM system. They were trying to collaborate on the MCP documentation. As byproducts of using the system, they surfaced:

1. Topic-file case fragmentation (`dm-Tiberius` vs `dm-tiberius`)
2. System-reminder push-injection truncation

Neither bug would have been found through unit tests — both required real cross-session traffic with realistic body sizes + recipient-name variations.

**Mechanic**: "dogfood while building." Use the in-progress system to do real work. The friction points become bug reports. Particularly effective when the system is interactive + has multiple users (sessions).

The infrastructure that made today's collaboration possible:

| **Observability** | `register_skip_reason` (F3 of `f4e0370`) | Silent fallback failures surface a debugging signal |

| **Documentation framework** | Today's 5-surface model | Lets corrections target the right surface unambiguously |
| **Discovery** | MCP `instructions` payload + tier-marked docstrings (Checkpoint 5) | Fresh sessions joining the collaboration learn the protocol without needing to read all the doctrine |

The pattern degrades gracefully without each layer:

- No auth → push fails, but blackboard-poll fallback works
- No push → ergonomic degradation to polling, but pattern still functions
- No observability → bugs harder to debug but not impossible
- No persona persistence → cross-session continuity weaker but recoverable via `set_session_topic`
- No broadcast → users must DM each side individually to "tap"

## 7. Bugs Surfaced as Side Effects

Documented for posterity — both filed in `TODO.md`:

### 7.1 Topic-file case fragmentation

**Symptom**: `commons_send_to(recipient="Tiberius")` writes to `dm-Tiberius.md` (capital T), but Tiberius reads `dm-tiberius` (lowercase). Two files on disk; thread fragments.

**Cause**: wrapper at `cosa_voice_mcp.py:2194` uses `f"dm-{recipient}"` literally without case normalization.

**Mitigation**: push-mode persona resolution is case-insensitive server-side, so DMs still deliver. But topic-files fragment.

**Fix**: 5-LOC change — `target_topic = topic or f"dm-{recipient.lower()}"`. Filed at top of TODO.md.

### 7.2 System-reminder push-injection truncation

**Symptom**: when push fires, the recipient's `<system-reminder>` body may be clipped while the on-disk topic file copy is complete. María observed apparent truncation at "Substantive answers to your 5 questions, ranked by impact:" with no body below.

**Cause**: hypothesized — body-length cap on the injected `COMMONS PEER MESSAGE` payload (separate from the file write). Investigation deferred.

**Mitigation**: documented in MCP instructions §"Failure Modes" item #7 + receipt etiquette step 2: "always re-fetch via `commons_read` for the canonical body, don't trust the system-reminder text."

**Fix**: investigation needed — instrument the push-injection layer for size + clipping diagnostics. Filed as sub-bug under the case-fragmentation TODO entry.

## 8. Open Questions / Future Work

Tiberius's top-5 (with my own framing where I have a view):

### 8.1 Does this scale to 3+ participants?

Every example today was strictly 2-way. What's the right shape for 3-way design discussions?

- Round-robin DMs?
- Convergent broadcast topics with explicit moderator?
- N-way DM-thread with explicit turn order?

**Risk**: 3+ DM-thread fan-out may devolve into N-way chaos without explicit coordination structure. Worth a controlled experiment.

### 8.2 Asynchronous patterns

What happens when one participant goes offline mid-loop?

Today both sessions were active simultaneously. The pattern's robustness under async is unknown:

- Does the iterative correction loop have a "graceful pause + resume" mode?
- How does Side A know whether Side B's silence means "thinking" vs "offline"?
- Is there a max-time-to-respond before the loop times out and escalates to the user?

### 8.3 Convergence vs deadlock criteria

Today's correction loop converged in 3-4 rounds. Is there:

- A max-rounds heuristic before escalating to user (e.g. "after 5 rounds without convergence, surface to Rick")?
- A signal recognizable in real-time that the loop is unproductive (e.g. both sides re-stating positions without new evidence)?

Loop-2 (architecture) converged in 4. Loop-3 (prose review) had its own convergence pattern. Worth analyzing what made these productive vs hypothetical unproductive cases.

### 8.4 Asymmetric-knowledge trust patterns

Today María had MCP-server domain knowledge Tiberius didn't; Tiberius had doctrine-doc knowledge María didn't. The loop converged via asymmetric trust ("I'll take your word for what the MCP does"; "I'll take your word for what the doctrine reads"). Does this asymmetric-trust pattern have failure modes?

- What if one side over-trusts the other's domain claim and propagates an error?
- What if both sides defer to each other on the same point (mutual abdication)?
- What if the asymmetric knowledge is itself mis-attributed (one side ASSUMES the other has expertise they don't)?

### 8.5 Loop-output decision-log

Today's convergence is reconstructable ONLY by re-reading the entire DM thread. A summary "decisions ratified across this loop: X, Y, Z" written at convergence-time would compress N DMs into 1 artifact.

- Should the loop have an explicit "convergence ratification" step that emits a decision-log entry?
- Where would the decision-log live — in commons as a reserved topic? In memory? In a designated R&D file?
- Who writes it — the initiator? The last-replier? A jointly-edited artifact?

**Meta-observation (Tiberius)**: this very document IS the §8.5 decision-log for today's arc. The convergence-ratification step CAN produce its own decision-log naturally — exhibit A: you're reading it. The answer to §8.5 may simply be: **"pair the convergence-ratification step with a short summary doc, jointly edited."** Worth promoting from open question to confirmed pattern after this doc's commit lands.

## 10. Replication Template

For future sessions wanting to use this pattern:

### Pre-requisites checklist

- [ ] Both participants have cosa-voice MCP loaded
- [ ] Both have read `~/.claude/CLAUDE.md` § CROSS-SESSION COMMUNICATION
- [ ] Both have a shared `LUPIN_ROOT` (or equivalent substrate access) for fallback
- [ ] Rick (or another user) has "tapped" both sessions on the same problem (designated collaboration)
- [ ] Both have explicit framework-vocabulary for the domain (e.g. "5-layer model" / "F1 vs F2")

### Recommended flow

1. **Initiator**: DM the peer with problem statement + initial framing
2. **Iterate**: 2-5 rounds of correction loop, each round bringing evidence
3. **Convergence**: both sides explicitly confirm agreement; save to durable storage (memory or R&D doc)
4. **Ship**: each side commits to their surface with cross-references
5. **Surface**: notify the user (Rick) at each major gate; let them ratify before the next loop

### Anti-patterns to avoid

- Defending positions past the point of evidence
- Using vague language instead of explicit framework-vocabulary
- Trying to converge on too-large a scope in one loop
- Forgetting to save the converged decision to durable storage
- Skipping the user-gate at major decision points
