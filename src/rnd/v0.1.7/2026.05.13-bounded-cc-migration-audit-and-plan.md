## Per-candidate analysis

### 1. Podcast Generator (`src/cosa/agents/podcast_generator/`)

| Q | Answer |
|---|---|
| Q1 Anthropic-only OK? | ✅ Yes |
| Q2 Self-contained prompt, bounded turns? | ✅ Yes — single-shot script generation |
| Q3 Fits CC tool surface? | ✅ Yes — no external tools needed beyond Read for source material |
| Q4 Tolerates 1-3s spawn overhead? | ✅ Yes — generation is minutes-long; spawn is noise |
| Q5 No token-streaming UX? | ✅ Yes — script is delivered post-completion |
| **Verdict** | **Clear-win** |

**Migration boundary**: only the script-generation phase (`api_client.py:184` and surrounding `_call_with_retry`). The audio TTS phase stays on whatever path it currently uses.

**Risks**:
- Output is multi-paragraph structured text with speaker tags. Bounded CC delivers raw text — the prompt must include parseable delimiters (e.g. `[HOST]: ...` / `[GUEST]: ...`) and the result parser must tolerate minor formatting variance.
- Audio TTS phase consumes the script. If the bounded-CC output format drifts from the SDK output, the TTS phase may break silently. Need a regression check on output schema.

**Why this should go first** (despite NOT being the biggest dollar-line-item):
- Simplest single-shot pattern of the three
- Lowest blast radius if rollback needed (script regeneration is a single user re-click away)
- Establishes a "text-synthesis" reference closer to Deep Research's shape than BFE/TFE provide (those are bug-fix-flavored)

### 2. Presentation Generator (`src/cosa/agents/presentation_generator/`)

| Q | Answer |
|---|---|
| Q1 Anthropic-only OK? | ✅ Yes |
| Q2 Self-contained prompt, bounded turns? | ✅ Yes — single-shot content generation |
| Q3 Fits CC tool surface? | ✅ Yes — no external tools needed |
| Q4 Tolerates 1-3s spawn overhead? | ✅ Yes — async batch friendly |
| Q5 No token-streaming UX? | ✅ Yes |
| **Verdict** | **Clear-win** |

**Migration boundary**: content/YAML-generation phase (`api_client.py:190`). The pptx-assembly phase stays as-is.

**Risks**:
- Structured output (YAML or JSON for slide content). Bounded CC doesn't enforce schema as tightly as the SDK's structured-output mode. Mitigation: prompt for explicit `<output>...</output>` tags + post-parse validator with schema check.
- Per-slide content. The structure is more nested than the podcast script — schema validation is non-trivial.

**Why this should go second**:
- Same shape as Podcast but with stricter output schema. Podcast pattern de-risks the basic refactor; Presentation tests the structured-output handling.

### 3. Deep Research (`src/cosa/agents/deep_research/`)

| Q | Answer |
|---|---|
| Q1 Anthropic-only OK? | ✅ Yes |
| Q2 Self-contained prompt, bounded turns? | ⚠️ Yes if bounded — Deep Research is multi-turn iterative research, currently unbounded. **Caller must set `max_turns`** (e.g. 15-20). |
| Q3 Fits CC tool surface? | ✅ Yes — WebSearch + WebFetch are native CC tools |
| Q4 Tolerates 1-3s spawn overhead? | ✅ Yes — research runs minutes to hours |
| Q5 No token-streaming UX? | ⚠️ Mostly — currently emits per-step progress via `notify_progress`. Bounded CC tool-use events can substitute (BFE/TFE precedent). |
| **Verdict** | **Clear-win with caveats** |

**Migration boundary**: the LLM-driven research loop (`api_client.py:165`). The result assembly + cache/store phases stay as-is.

**Risks**:
- **Per-step progress notifications**. Currently the UI shows "Searching… (3 sources found)" etc. Need to confirm BFE/TFE-style tool-use event surfacing works for the iterative research loop, or refactor to emit progress from a wrapper that polls job state.
- **ApiResourceManager integration**: currently uses `get_arm().acquire("anthropic_web_search")` for rate limiting. Bounded CC has Max-plan rolling-window limits instead. The ARM call becomes a no-op for the migrated path — drop it (or leave it harmless) for the Anthropic-specific resource pool.
- **`max_turns` cap**: bounded CC requires an explicit turn limit. Research could in theory run longer than the chosen cap and return incomplete. Need a safe default (15-20 turns) and a clear failure UX if the cap is hit before synthesis completes.
- **Tool-permission scope**: the `can_use_tool` callback must allow WebSearch + WebFetch + whatever else Deep Research needs (likely just those two + Read for context loading).

**Why this goes last**:
- Most complex of the three
- Two reference implementations (Podcast + Presentation) already in place by the time we tackle it
- Biggest cost-shift, but also biggest blast radius — best to migrate after the pattern is well-trodden

## Operational notes (apply to every migration)

- **`scheduled_at` defaulting**: all three agents have batch-friendly callers. Default `scheduled_at` to post-midnight per the off-peak rule (cost-model doc § "Off-peak scheduling"). Synchronous user-initiated runs omit `scheduled_at` and fire immediately.
- **Max-plan throughput awareness**: bounded ≠ infinite. Three concurrent migrated agents firing during peak (9 PM – 12 AM EDT) could throttle Rick's interactive Claude Code work. The `scheduled_at` rule mitigates this, but watch for it.
- **Failure mode mapping**: SDK `_call_with_retry()` retries on API errors. CJ Flow's bounded path has its own retry primitives (dead-letter, ghost-job sweeper). The migration must map existing retry behavior onto CJ Flow primitives, not duplicate it.
- **Verification gate per phase**: submit a representative payload, confirm functional parity with the SDK baseline, confirm Anthropic console balance shows zero movement post-run. This is the only ground-truth check for "did it bill?"
- **Test pyramid**: per CLAUDE.md TEST OWNERSHIP MANDATE — every migration includes Python `py_compile`, unit tests on the prompt/parse helpers, smoke test for an end-to-end bounded submission, and (where appropriate) an `:8000` integration test for the full pipeline. AI executes all tiers; Rick never asked to verify.
- **Plan-review discipline**: per `feedback_pip_plan_review_is_sequential`, each phase plan walks REUSE → Pass 1 Fitness → Pass 2 Adversarial sequentially with user gate between each. No parallel passes.

### D1. Phase ordering — Podcast-first vs Deep-Research-first

**Option A — Podcast → Presentation → Deep Research (simplest-first, MY RECOMMENDATION)**

✅ **Pros**:
- Lowest-risk first step. Podcast is single-shot text synthesis; if rollback is needed, one user re-click regenerates.
- Two clean reference implementations (Podcast + Presentation) in hand before tackling Deep Research's multi-turn complexity.
- Establishes a new text-synthesis migration pattern closer to Deep Research's shape than BFE/TFE (which are bug-fix-flavored).
- Predictable session sizing — each migration roughly equal effort.
- Pattern of "simplest first to validate, hardest last to capitalize" matches how BFE → TFE were sequenced historically.

❌ **Cons**:
- Defers the biggest cost-shift (Deep Research) by 1-2 weeks.
- Two intermediate "wins" might create false confidence that Deep Research will be as easy.
- If Deep Research is the dominant line-item, the per-day savings curve is concave-down: most savings come from the LAST migration.

**Flip-condition**: becomes incorrect if Deep Research's monthly firewalled-account burn is so dominant (>70% of total) that even a 1-2 week delay outweighs the technical risk of doing it first.

---

**Option B — Deep Research → Podcast → Presentation (biggest-cost-first)**

✅ **Pros**:
- Captures dominant savings on day one.
- Forces us to confront the hardest problems (max_turns, tool-use progress, ARM retirement) early when momentum is fresh.
- If Deep Research migration fails, we learn that sooner without sunk cost in Podcast/Presentation.

❌ **Cons**:
- Highest risk first. If Deep Research has unexpected blockers, the whole migration stalls.
- No bounded-CC text-synthesis reference exists yet — BFE/TFE are bug-fix shape, which is different.
- Larger blast radius: Deep Research has more callers and dependencies (UI progress events, ARM, caching) than Podcast.

**Flip-condition**: becomes correct if monthly burn data shows Deep Research dominates.

---

**Option C — Parallel Podcast + Presentation (both ~1 session), then Deep Research**

✅ **Pros**:
- Two reference implementations land in one calendar window instead of two.
- Parallelism IF a second session is available to take one of them.

❌ **Cons**:
- Risks pattern drift if implemented by two sessions independently — Podcast and Presentation might diverge in subtle ways.
- Coordination overhead between two sessions.
- Per memory `feedback_approved_sequences_execute_end_to_end`, multi-step sequences execute end-to-end — parallelism breaks that contract.

**Flip-condition**: becomes correct if there's a second available session AND the user explicitly authorizes parallel execution AND the Podcast pattern is so well-specified that drift risk is negligible.

---

**My recommendation: Option A (Podcast first)**. Lowest risk per step, builds pattern confidence, leaves the highest-value tackle for last when we have the most context. Rick should pick B only if monthly-burn data makes the cost-of-delay dominant.

### D6. Output-parser fallback strategy — strict vs lenient vs hybrid

The SDK delivers token-streamed output that's typically schema-clean. Bounded CC delivers a single completion string that might have minor formatting variance (whitespace, trailing newlines, occasional explanatory prose). The parser strategy matters per migration.

**Option A — Strict parser, fail-loud on any variance (MY RECOMMENDATION for Presentation; appropriate for Deep Research)**

✅ **Pros**:
- Catches output drift early — bugs surface before reaching downstream consumers (pptx assembly, TTS).
- Forces prompt-engineering to produce consistent output.
- Standard practice for structured-output pipelines.

❌ **Cons**:
- Brittle. A single trailing newline could fail an entire job.
- Bounded CC has no native structured-output enforcement — even good prompts produce occasional variance.

**Flip-condition**: becomes incorrect if observed bounded-CC output variance is >5% — at that rate, fail-loud becomes user-hostile.

---

**Option B — Lenient parser, best-effort with fallbacks (MY RECOMMENDATION for Podcast)**

✅ **Pros**:
- Resilient to minor formatting drift.
- Better UX — users get a result rather than an error.

❌ **Cons**:
- Bugs can hide in "almost-correct" outputs.
- Harder to debug when output format silently degrades.

**Flip-condition**: becomes incorrect if downstream consumers (TTS, pptx) have strict format requirements.

---

**Option C — Hybrid: strict parse with explicit fallback chain to retry on failure**

✅ **Pros**:
- Best of both worlds. Strict-parse the happy path; on failure, retry with explicit "produce STRICTLY the following format" prompt.
- Self-healing under transient variance.

❌ **Cons**:
- More implementation effort.
- Retry doubles latency on failure — bad for users awaiting results.
- Could mask repeated drift if both attempts succeed but downstream slowly degrades.

**Flip-condition**: becomes correct if variance is observed but rare (<10% of runs).

---

**My recommendation**: per-migration call. Podcast = Option B (lenient — TTS is tolerant). Presentation = Option A (strict — pptx assembly is fragile). Deep Research = Option A initially, escalate to Option C if observed variance > 5%.

### D7. Concurrency limit — how many migrated jobs can run in parallel via the agentic pool

The CJ Flow agentic pool has a configurable size (`cj flow max concurrent agentic jobs` INI key, prod default 1, dev/test default 3). Each migrated job consumes a pool slot. If multiple migrations land and all submit concurrently (e.g. 3 podcasts + 2 research runs queued at midnight), pool capacity becomes a bottleneck.

**Option A — Keep pool size at current values, accept queueing on the migrated path (MY RECOMMENDATION)**

✅ **Pros**:
- No new INI knob to tune. Conservative.
- Queueing is normal CJ Flow behavior — already well-tested.
- Predictable max-plan throughput consumption.

❌ **Cons**:
- Multiple concurrent migrated jobs serialize behind the pool slots. A bulk podcast run could block research.
- User who clicks "generate podcast" + "do deep research" simultaneously sees one execute, one queued.

**Flip-condition**: becomes incorrect if observed queueing latency at production scale exceeds user tolerance.

---

**Option B — Increase pool size to accommodate migrated jobs**

✅ **Pros**:
- More parallelism. Faster aggregate throughput.

❌ **Cons**:
- Risks Max-plan throttle hits (parallel = burstier API usage).
- Higher subprocess memory footprint.

**Flip-condition**: becomes correct if pool-status observability shows consistent saturation AND Max-plan headroom is well below cap.

---

**Option C — Separate pool/queue for migrated jobs**

✅ **Pros**:
- Migrated jobs don't compete with BFE/TFE/etc. for pool slots.

❌ **Cons**:
- Significant architectural change. Pool partitioning is non-trivial.
- Premature optimization.

**Flip-condition**: becomes correct after observing real competition between migrated and non-migrated agentic jobs — not before.

---

**My recommendation: Option A**. Don't tune the knob until observed need.

### D9. Migration-path naming convention — banner / comment / INI key

How do future developers know an agent is migrated vs direct-SDK without grepping?

**Option A — Update `__init__.py` banner with explicit migration date + link to this doc (MY RECOMMENDATION)**

✅ **Pros**:
- Follows existing pattern (per cost-model doc § "Migration playbook" step 7).
- Banners are read by humans opening the file.
- Links to authoritative migration record.

❌ **Cons**:
- Banners can rot. Future devs may not update them.

**Flip-condition**: becomes incorrect if banner pattern is removed from the codebase entirely.

---

**Option B — Marker INI key (e.g., `deep research llm path = bounded`)**

✅ **Pros**:
- Runtime queryable. Operators can `grep` config for migration state.
- Could enable A/B testing or rollback toggling (but see Option C reject).

❌ **Cons**:
- Looks like a feature flag, which per `feedback_feature_flag_preserves_old_path` commits to permanent maintenance.
- Configuration drift risk — what if the INI says "bounded" but the code is direct-SDK?

**Flip-condition**: becomes correct if we explicitly DO want feature-flagging (which we don't).

---

**Option C — Just the code, no marker — trust git history**

✅ **Pros**:
- Zero overhead.

❌ **Cons**:
- Future devs reading an agent file have no immediate signal which path it uses.
- `git blame` is slow at scale.

**Flip-condition**: becomes correct only if the team is very small and history-aware.

---

**My recommendation: Option A**. Banner pattern is established; cost is one paragraph per migrated agent.

## Rollback playbook per phase

If a migration regresses in production, what does revert look like?

| Phase | Rollback action | Time to revert | Data loss risk |
|---|---|---|---|
| **Podcast** | `git revert` the migration commit; restart server | <5 min | None (script regeneration is idempotent) |
| **Presentation** | `git revert` the migration commit; restart server | <5 min | None (slide regeneration is idempotent) |
| **Deep Research** | `git revert` the migration commit; restart server | <5 min | None (research results are stored, just the production path reverts) |

**Critical**: no feature-flagged dual paths. Per `feedback_feature_flag_preserves_old_path`, feature flags become permanent maintenance burden. Revert is via git history; both paths CANNOT coexist long-term.

**Pre-revert checklist**:
1. Confirm the regression is in the migrated path (not an unrelated bug surfacing concurrently)
2. Save evidence (job IDs, output samples, error messages) to the migration's R&D doc execution log
3. After revert lands, file a follow-up ticket: what went wrong + path forward
