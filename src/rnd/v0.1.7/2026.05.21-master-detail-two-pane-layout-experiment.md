## Context

Today every rich `notify(abstract=...)` payload + every `[Open: ...](/app/docs?path=...)` doc-link lives in transient surfaces — the abstract tooltip is a fixed-position overlay (`#abstract-tooltip` mounted on `document.body` at `notifications.js:8337-8384`) that dismisses on outside-click + Esc + close-button, and doc-links open in new tabs via the `target="_blank"` attribute baked in by the markdown renderer at `notifications.js:13215-13221`. Both surfaces are ergonomic on a single laptop screen but two specific failure modes recur:

1. **Scroll-context loss**. Every popup dismissal returns you to the activity stream at top, even if you were scrolled deep into an older session card. Cross-referencing a doc against an active conversation requires multi-tab juggling.
2. **No durable reading surface**. Long abstracts (broadcast summaries, design-doc deltas, multi-step proposal walkthroughs) compete with the activity stream for vertical real estate. A persistent reading pane would let the user keep the activity stream OPEN while a doc/abstract is rendered alongside.

Rick's proposal: switchable two-pane "horizontal" layout where the existing `.container` collapses to 2/3 of the viewport width and a new "content rendering section" occupies the right 1/3. Doc-links + abstracts route into the pane instead of opening popups/new-tabs. Clicking a doc-link inside the pane replaces the pane content in place (mini-browser model). The existing vertical layout stays available via a toggle.

Viewport math at Rick's typical screen (~2000px wide): 1/3 = ~667px reading width — comfortable for prose AND tables. At a typical laptop (~1440px): 1/3 = ~480px — fine for prose, tight for tables. We respect the user's toggle and add an auto-fallback only if friction emerges.

This is a self-contained UI experiment. No backend changes. No new endpoints. No schema impact. Reversible by toggling back to vertical.

## Layout Spec

### HTML Structure (Horizontal Mode)

Wrap `<body>` content in a new flex shell. The existing `.container` becomes the left pane; a new `<aside class="content-pane">` becomes the right pane.

```
<body data-layout-mode="vertical|horizontal">
  <div class="content-shell">                  ← NEW (flex row in horizontal mode)
    <div class="container">                    ← existing (2/3 width in horizontal mode)
      [section-toolbar — STICKY inside container in horizontal mode]
      [...all existing accordions unchanged...]
    </div>
    <aside class="content-pane" hidden>        ← NEW (1/3 width; hidden until populated)
      <div class="content-pane-header">
        <button class="content-pane-back">←</button>
        <span class="content-pane-title">[Title]</span>
        <button class="content-pane-close">×</button>
      </div>
      <div class="content-pane-body">          ← dynamic content (abstract or iframe)
        <!-- abstract: rendered markdown -->
        <!-- doc-link: <iframe src="/app/docs?path=..."> -->
      </div>
    </aside>
  </div>
</body>
```

In **vertical mode**, the `.content-shell` is a no-op pass-through (block layout); the `<aside>` stays `hidden`; everything looks like today. The wrapper exists in both modes — no DOM swap on toggle.

### CSS — Mode-Gated Layout

All new layout rules gate on `body[data-layout-mode="horizontal"]`. Existing vertical CSS stays untouched. Representative rules:

```css
/* Default — vertical mode (existing behavior) */
.content-pane[hidden] { display: none; }

/* Horizontal mode activates the split */
body[data-layout-mode="horizontal"] .content-shell {
    display: flex;
    align-items: stretch;
    gap: 16px;
    min-height: 100vh;
}
body[data-layout-mode="horizontal"] .container {
    flex: 2;             /* 2/3 of available width */
    max-width: none;     /* override the existing 1000px constraint */
    margin: 0;
}
body[data-layout-mode="horizontal"] .content-pane {
    flex: 1;             /* 1/3 of available width */
    min-width: 360px;
    border-left: 1px solid #dee2e6;
    background: #fafbfc;
    overflow-y: auto;
    position: sticky;
    top: 0;
    align-self: flex-start;
    max-height: 100vh;
}
body[data-layout-mode="horizontal"] .section-toolbar {
    position: sticky;    /* was fixed; now sticky within the left pane */
    top: 0;
    left: auto;          /* override the fixed-left-offset rule */
}
```

The section-toolbar repositioning is the only invasive change to existing behavior. In vertical mode the existing `position: fixed; left: calc(50% - 500px - 60px); top: 136px` (notifications.css:14-29) is unchanged; horizontal-mode-only rules override.

### Click Interception

Two click paths get rerouted in horizontal mode:

1. **`.abstract-indicator` click** (today: opens `#abstract-tooltip` fixed-position popup at `notifications.js:8337`)
   - Horizontal mode: render the abstract markdown into `.content-pane-body`, unhide the pane, push history entry.
   - Vertical mode: existing tooltip behavior unchanged.

2. **Doc-viewer link click** (today: `[Open: ...](/app/docs?path=...)` opens new tab via `target="_blank"` baked into the markdown renderer at `notifications.js:13218`)
   - Horizontal mode: `preventDefault()`, embed `<iframe src="/app/docs?path=...">` into `.content-pane-body`, unhide the pane, push history entry.
   - Vertical mode: existing new-tab behavior unchanged.

   The interception fires on any anchor with `href` matching `^/app/docs\?path=` inside the page — abstracts, notification bodies, recent-activity entries — all participate.

### Mode Toggle

- New button at the **top of `.section-toolbar`**, above the existing 11 emoji toggles. Icon: ⇆ (horizontal-resize glyph) or 🪟; label tooltip "Switch to horizontal layout" / "Switch to vertical layout".
- Click handler: toggles `body[data-layout-mode]` attribute, writes `notifications_layout_mode` to localStorage, updates the tooltip text.
- Restore mode on page load: read localStorage in constructor, set the attribute BEFORE first paint (avoids flicker).

### Content Pane Implementation Details

**For abstracts** (markdown text):
- Reuse `renderMarkdown()` (the existing helper at `notifications.js:13215`) — same DOMPurify pass, same `target="_blank"` baked into outbound links from inside the pane.
- BUT: anchors with `href ^= "/app/docs?path="` get a click handler attached that prevents default + swaps in an iframe.

**For doc-viewer links** (`/app/docs?path=...`):
- Embed `<iframe src="/app/docs?path=...">` filling the pane body.
- The doc viewer page (`document-viewer.html`) is already an SPA — it renders fine inside an iframe with no modification.
- iframe-based approach is the simpler path; we can graduate to inline-fetch-and-render later if we want richer interactions (the iframe sandbox prevents the embedded doc from posting messages back to the parent).

**Navigation**:
- Close (×): hides the pane, clears `.content-pane-body`, drops the history stack.
- Back (←): pops the previous entry off the history stack, re-renders. Disabled when history is at base.
- No Forward button initially (per Rick's "I just want to get back" framing in the pre-plan conversation).
- History stack: in-memory JS array of `{type: "abstract" | "doc", payload: string}`, depth-capped at 10. Not persisted across reloads (the in-flight reading session is ephemeral).

### Persistence

| State | localStorage key | Shape | Default |
|-------|------------------|-------|---------|
| Layout mode | `notifications_layout_mode` | `"vertical"` \| `"horizontal"` | `"vertical"` |

That's the only persistent piece. Content pane state (open/closed, current content, history) is per-session.

## Reuse Review (2026-05-21 Walkthrough — Pre-Implementation Pass)

Findings folded into "Files to Modify" + the design above. Consolidated DO/DON'T table for the implementer:

| Concern | DO this | DON'T |
|---------|---------|-------|
| Markdown render in pane | `this.renderMarkdown(text)` — class method at `notifications.js:13167` | Reimplement marked + DOMPurify standalone |
| localStorage key | `notifications_layout_mode` (matches the established `notifications_*` convention at lines 160-170) | Invent a different prefix or namespace |
| Body attribute | `data-layout-mode="vertical"|"horizontal"` (fresh, no collision) | Use bare `data-mode` — already taken by filter-mode badges |
| Sticky positioning | Mirror `.cc-session-strip` at `notifications.css:2073-2076` (`top: 0; z-index: 50`) | Invent a new z-index — coordinate with existing layer hierarchy |
| Mode toggle button styling | New `layout-mode-btn` class with `border-bottom` separator from the existing 11 section buttons below | Reuse `toolbar-btn` (different semantics — section visibility vs layout mode) |
| Mode toggle button attributes | NO `data-section` attribute (the section-toolbar's existing JS handler dispatches on `data-section`) | Add `data-section` — would trigger the wrong handler |
| Visual placement of mode-toggle button | First child of `#section-toolbar` (top of the vertical column), with a small `margin-bottom` + `border-bottom` to separate semantically | Mix it inline with the section toggles |
| Narrow-viewport breakpoint | Use 1200px for the toggle button tooltip hint (new breakpoint, but documented purpose) | Use existing 768px (that's the mobile breakpoint — too aggressive for a "cramped" hint) |
| Class name `content-pane` | New — no collision verified via grep | Use `pane` / `panel` / `sidebar` (too generic or risk of collision) |
| Show/hide pane | Use the `hidden` attribute (`aside.hidden`) — declarative, CSS-aware | Use inline `style.display = "none"` — ad-hoc |

**Functions to ADD** (genuinely new — no existing analogue):

- `_toggleLayoutMode()` — toggles `body[data-layout-mode]` + writes localStorage
- `_openContentPane(type, payload, title)` — populates pane, pushes history
- `_closeContentPane()` — hides + clears + drops history stack
- `_backContentPane()` — pops history, re-renders
- `_renderContentPaneAbstract(markdown, title)` — markdown branch
- `_renderContentPaneDoc(docPath, title)` — iframe branch
- `_interceptDocLinks()` — document-level click handler for `^/app/docs\?path=` anchors
- History stack: in-memory `this._contentPaneHistory = []`, capped at 10

**Functions to BRANCH** (existing, gated on mode):

- `.abstract-indicator` click handler (existing, `notifications.js:8337-8384`) — add a horizontal-mode branch that calls `_openContentPane("abstract", ...)` and skips the tooltip path.

This locks the implementation surface: every other touchpoint is either an augment of existing code or a small DOM utility with no existing analogue.

## Resolved Design Choices (Walkthrough 2026-05-21 PM)

All six confirmed by Rick via item-by-item `ask_yes_no` / `ask_multiple_choice`.

1. **Right pane**: CSS class `content-pane`, UI label **"Reading Pane"**. Confirmed via `ask_multiple_choice` (4 options).
2. **Doc-link rendering**: **iframe** (`<iframe src="/app/docs?path=...">`). Confirmed yes. Can graduate to inline later if double-chrome nesting annoys.
3. **Navigation buttons**: **Close (×) + Back (←) only**, no Forward. In-memory history stack capped at 10, dropped on Close.
4. **Mode toggle button location**: **top of `.section-toolbar`**, icon `⇆`, dynamic tooltip ("Switch to horizontal layout" / "Switch back to vertical layout").
5. **Narrow-viewport behavior**: **Respect the toggle — no auto-fallback.** Tooltip hint on the toggle button: "Best at viewports ≥ 1200px wide." Mobile (<768px) behavior deferred to follow-up.
6. **Notification arrival while pane is open**: **Never interrupt.** Activity stream in the left pane retains all existing badge/animation/TTS/urgency-color behaviors; the Reading Pane stays focused on what the user is reading.

## Limitations (Acknowledged, Not Blockers)

- **iframe sandbox**: the embedded doc viewer can't postMessage back to the parent without explicit setup. If we want cross-pane interactions later (e.g., highlighting an entry in the activity stream when its referenced doc opens), we'd need to add `postMessage` plumbing. Out of scope for this experiment.
- **Print/copy from pane**: iframe content prints fine in modern browsers but text selection across the iframe boundary doesn't work. Acceptable; users can open the doc in a new tab via the iframe's own controls.
- **Mobile**: this experiment is desktop-only. On viewports below 768px (existing breakpoint), the toggle could be hidden entirely OR force-vertical. Defer that decision.
- **Notification streams that arrive while pane is open**: see Open Question 6.

---

## Out of Scope (Explicit)

- Inline doc rendering (post-iframe) — follow-up if iframe friction surfaces
- Forward navigation button
- Cross-pane interactions (postMessage, scroll-sync, highlight-on-open)
- Resizable splitter between panes (drag handle)
- Multi-pane (three-up or n-up)
- Mobile horizontal mode
