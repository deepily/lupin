## TL;DR

The broadcast UI's "Sending to: …" chip-row reads from `GET /api/commons/active-sessions`. The endpoint enforces T7+Q9 same-user scoping via `bridge.get("user_id") != authenticated_user_id`. But `session_bridge.py` never writes a `user_id` field on bridge files, so every bridge fails the filter and the response is `{"sessions": []}`.

The Phase 2 test that should have caught this (`test_broadcast_two_session_e2e.py`) constructs a **mock** bridge dict with `user_id` populated, masking the production gap.

## Evidence (file:line)

**Filter that rejects everything** — `src/cosa/rest/routers/commons.py:194-207` (`filter_and_project_sessions`):

```python
for path, sid, persona in raw_sessions:
    bridge = bridge_loader( path )
    if bridge is None:
        continue
    if bridge.get( "user_id" ) != authenticated_user_id:   # ← always True (None != <uuid>)
        continue
    ...
```

**Bridge writer never sets `user_id`** — `src/lupin_cli/claude_code/hooks/lib/session_bridge.py`:

```bash
$ grep -n 'user_id' src/lupin_cli/claude_code/hooks/lib/session_bridge.py
# (no matches)
```

**Phase 2 test masks the bug** — `src/tests/smoke/test_broadcast_two_session_e2e.py:104-108`:

```python
def _make_bridge_dict( user_id: str, age_seconds: float = 5.0 ) -> Dict[ str, Any ]:
    return {
        ...
        "user_id" : user_id,   # ← mocked, not produced by real bridge writer
        ...
    }
```

The test passes because the mock bridge_loader returns dicts with `user_id`; the real `_load_bridge_fields` reads JSON from disk and gets `None`.

**Endpoint wiring is correct** — the bug isn't in routing, auth, or the watcher daemons; it's purely in the filter contract vs. the bridge schema.

---

## Hypothesis

Phase 2 design (Q9 + T7) specified same-user scoping as the cross-user isolation primitive. The design's "user_id check" was implemented in the router filter, but the corresponding **stamping** on the bridge writer was not landed. Possible reasons:

1. The Phase 2 work was implemented test-first with a mocked bridge that satisfied the filter; the real-bridge gap was never exercised because no E2E test hits the live `_load_bridge_fields` against real files.
2. The design assumed an existing `user_id` field on bridges that didn't actually exist (the bridge schema pre-dates Phase 2 and was never extended).
3. Stamping was deferred to a follow-on but never tracked in TODO.md.

Either way: the filter assumes a contract the bridge writer doesn't satisfy.

## Ranked solutions

### Option 1 — Graceful degradation (RECOMMENDED, smallest-blast-radius)

Patch the filter so it applies ONLY when the bridge has a `user_id` field. Bridges without `user_id` pass through (no filtering).

```python
# src/cosa/rest/routers/commons.py:198 (approx)
bridge_user_id = bridge.get( "user_id" )
if bridge_user_id is not None and bridge_user_id != authenticated_user_id:
    continue
```

| Property | Verdict |
|---|---|
| Effort | ~5 LOC single-file change + 2-3 unit tests for the new branch |
| Unblocks Rick today | ✅ |
| Future-proof | ✅ once Option 2 stamping lands, the filter auto-applies |
| Multi-user safety | ⚠ degraded until stamping lands; on Rick's single-user box, no practical impact |
| Coverage impact | Maintains 100% on `routers/commons.py` |

**Becomes correct if** you later land Option 2's stamping — then this branch matures from "graceful-degradation-for-missing-field" to "actually-enforcing-cross-user-isolation" with zero downstream change.

### Option 2 — Stamp `user_id` on bridges at session start

Have the listener/hook resolve the authenticated user_id (from email→DB lookup or a cached config) and write it to the bridge JSON.

| Property | Verdict |
|---|---|
| Effort | ~40-60 LOC across: `session_bridge.py` (writer + helper), listener startup (resolution), unit tests (3-5), and a migration concern for existing in-flight bridges |
| Unblocks Rick today | ❌ — blocked while implementation lands |
| Architectural correctness | ✅ matches Phase 2 design intent |
| Multi-user safety | ✅ proper enforcement |
| New dependencies | Listener needs API access to resolve email→user_id, OR the user must supply `LUPIN_USER_ID` env var, OR the user_id must be cached in `~/.lupin/config` |

**Open sub-questions if you pick this:**
- Where does the listener get the user_id from? (API lookup vs. env var vs. cached config)
- What's the migration story for bridges that already exist when the change lands? (They lack user_id; do we backfill, age them out, or apply Option 1's fallback indefinitely?)

### Option 3 — Drop the `user_id` filter entirely

Remove the cross-user check.

| Property | Verdict |
|---|---|
| Effort | 1 LOC delete + remove the related test |
| Unblocks Rick today | ✅ |
| Multi-user safety | ❌ permanently degraded |
| Reversal cost | Same as Option 2 — bridges still need to stamp user_id to ever re-enforce |

Strictly worse than Option 1 because there's no upgrade path.

### Option 4 — Diagnose more first

Sanity-check this finding (maybe the stamping happens via a path I didn't see; maybe the design intent was actually `bridge.get("user_email")` or some other field; maybe there's a config option that gates the filter).

| Property | Verdict |
|---|---|
| Effort | Half a turn of investigation |
| Cost | One more conversation cycle before any fix lands |
| Likely outcome | Confirms Option 1 (no stamping mechanism exists anywhere in the hooks dir) |

## My recommendation

**Option 1, with a follow-on TODO for Option 2's stamping.**

- Option 1 ships today, ~5 LOC, unblocks broadcast UI for your single-user dev work
