## Context

Two refinements following tonight's TTS preview-and-advance + slider shipment (commit `5836a6f`):

### 1. Move the TTS slider

Currently lives in `#cc-session-strip` (chrome strip nested inside the section-content area of the Claude Code notifications accordion). Rick wants it at the **top of the accordion** — in the `.section-header` row that's always visible whether or not CC sessions exist. The strip works but it's buried inside the content area; the header is more discoverable.

### 2. Per-session DND toggle (NOT silent mute)

Refines the speakerphone-toggle plan parked this afternoon. Originally framed as "audible vs silent" (mute). Rick reframed tonight: **muted ≠ silent.** Notifications still arrive for the historical record; they just get demoted from `priority='high', suppress_ding=True` to `priority='medium', suppress_ding=False`. Small ding on arrival, no full TTS playback, list-render preserved.

**Quote from Rick (2026-05-14 evening):** *"I want to make sure that when we put any given Claude Code session on mute that we are not telling them to shut up. I want their notifications to arrive. We want a historical record of conversations. All I want to do is basically de-escalate the priority of whatever they're sending both on their side via the prompt and on our side as a kind of belt-suspenders approach."*

### Combined UX

- **GLOBAL slider** in the accordion header (% of text rendered for high-priority items — already shipped tonight)
- **PER-SESSION quiet toggle** on each sender card (whether THIS session's items are high vs medium priority in the first place)

Together they're a verbosity filter + a per-source DND switch. The slider controls how much of each high-priority message plays as TTS; the per-session toggle controls whether THIS session's messages are even classified as high-priority.

### Belt-and-suspenders enforcement

- **Source side (hook rider)**: when session is in quiet-mode, the rider tells Claude to send `priority='medium', suppress_ding=False`
- **Receive side (client)**: if Claude doesn't comply, client rewrites the priority on arrival before the priority-branch dispatches

## Phase 5 — Client-side belt-and-suspenders priority rewrite

**File:** `src/fastapi_app/static/js/notifications.js` — `handleNotificationUpdate` near line 5610.

INSERT at the TOP of `handleNotificationUpdate` (before the priority branch fires):

```javascript
// Belt-and-suspenders: if the session is in quiet-mode and Claude didn't
// honor the rider (still sent priority=high), rewrite the priority on the
// client side. The notification then falls into the existing medium-priority
// branch: immediate list render via addNotificationToSenderGroup, small ding,
// no TTS engagement.
if ( notification.sender_id ) {
    const parsed    = this.parseSenderId( notification.sender_id );
    const sessionId = parsed && parsed.sessionId;
    if ( sessionId && this.speakerphoneState[ sessionId ] === false ) {
        if ( notification.priority === 'high' || notification.priority === 'urgent' ) {
            this.log( `[QUIET-MODE] Rewriting priority for muted session ${sessionId}: ${notification.priority} → medium` );
            notification.priority      = 'medium';
            notification.suppress_ding = false;
        }
    }
}
```

After this rewrite the existing low/medium branch at line 5631-5636 dispatches normally (immediate list render, no TTS engagement, small ding).
