## TL;DR

Focus-mode and the hide-inactive ("Active") toggle each already had localStorage save/restore wiring at constructor time, AND per-card / per-icon application at `createSenderCard` / `_addStripIcon` time. But on a real refresh, Rick still loses focus and sees every session. This fix adds a **belt-and-suspenders post-load reconciliation** that runs once after `loadConversationHistory()` finishes — re-reads localStorage directly (bypassing potentially-wiped in-memory state), walks the now-hydrated DOM, and applies focus + active-toggle state in full. Also honors the original 2026-04-30 design contract by **discarding stale `focused_sender_id`** when the focused sender has no notifications in the current data set.

## Diagnosis — pre-fix state

Both pieces of state ARE persisted and partially restored:

| State | localStorage key | Saved at | Restored at |
|---|---|---|---|
| Focus mode | `notifications_cc_focus_state` | `_saveCcFocusState` (notifications.js:9512) — called from `_enterFocusMode` + `_exitFocusMode` | Constructor line 182 + toggle-pill visual lines 192-198 + per-card `_applyFocusHiddenToCard` line 9491 + per-icon `data-focused` in `_addStripIcon` lines 9079-9082 |
| Hide-inactive ("Active") toggle | `notifications_cc_hide_inactive_strip` | `_setHideInactiveStrip` (notifications.js:9472-9476) | Constructor line 204 + toggle-pill visual lines 206-212 + per-icon filter in `_addStripIcon` lines 9113-9116 |

So the **happy path looks correct in code**. Yet Rick reports the symptom deterministically. Three plausible causes were identified (the fix covers all three without requiring me to pin down the exact one):

1. **An `_exitFocusMode()` fires during init.** Possible callers: `_removeStripIcon` (when focused session's icon is removed, line 9135), `_clearAllStripIcons` (bulk clear paths, line 9157). Hard to rule out without instrumentation — a WS event handler that churned a strip icon early in the lifecycle could trigger it.
2. **A render path other than `createSenderCard`** produces cards (cached/server-side render, hot-restore from IndexedDB, etc.), and that path doesn't call `_applyFocusHiddenToCard`.
3. **Constructor toggle-pill restore races the DOM.** Constructor runs in a `DOMContentLoaded` callback, so the strip-toggle button SHOULD exist, but if the HTML render path defers the toggle's insertion (lazy hydration), the `getElementById` returns null and the visual restore silently no-ops.

A fourth cause was identified in the design doc but not enforced in code:

4. **Stale `focused_sender_id` after notification cleanup.** The 2026-04-30 design says: *"If the persisted focused session does NOT exist on reload (e.g. user cleared notifications since), state is discarded and default mode is shown."* The constructor doesn't enforce this — if the saved focused sender has no cards in the current data set, every card gets `data-focus-hidden` (none match) and the user sees an empty notifications list. Rick's symptom is "all cards visible," not "empty list," so this isn't HIS bug — but it's a latent footgun the fix also addresses.

## Fix — `_restoreCcUiAfterLoad`

A single new method `_restoreCcUiAfterLoad()` placed right after `_saveCcFocusState` (notifications.js:9522), called once from `init()` immediately after `await this.loadConversationHistory()` (right before `restoreActionRequiredState()`).

```js
_restoreCcUiAfterLoad() {
    // ─── Focus mode ─────────────────────────────────────────────────
    let persistedFocus = null;
    try {
        persistedFocus = JSON.parse( localStorage.getItem( this.CC_FOCUS_STATE_KEY ) );
    } catch ( e ) { /* swallowed + logged */ }

    if ( persistedFocus && persistedFocus.enabled && persistedFocus.focused_sender_id ) {
        // Reconcile in-memory state with persisted (covers cause #1)
        if ( !this.ccFocusState.enabled
             || this.ccFocusState.focused_sender_id !== persistedFocus.focused_sender_id ) {
            this.ccFocusState = { ...persistedFocus };
        }

        const expectedId  = `sender-card-${this.ccFocusState.focused_sender_id.replace( /[@.#]/g, '-' )}`;
        const focusedCard = document.getElementById( expectedId );

        if ( !focusedCard ) {
            // Cause #4: stale focused sender — design contract says discard
            this._exitFocusMode();
        } else {
            // Walk all cards (covers cause #2 — even if createSenderCard skipped some)
            document.querySelectorAll( '#notifications-list .sender-card' ).forEach( card => {
                if ( card.id === expectedId ) {
                    card.removeAttribute( 'data-focus-hidden' );
                } else {
                    card.setAttribute( 'data-focus-hidden', 'true' );
                }
            } );
            // Mark focused strip icon
            document.querySelectorAll( '#cc-strip-icons .cc-strip-icon' ).forEach( icon => {
                if ( icon.getAttribute( 'data-sender-id' ) === this.ccFocusState.focused_sender_id ) {
                    icon.setAttribute( 'data-focused', 'true' );
                } else {
                    icon.removeAttribute( 'data-focused' );
                }
            } );
            // Toggle pill (covers cause #3 — idempotent if constructor already set it)
            const toggle = document.getElementById( 'cc-strip-toggle' );
            if ( toggle ) {
                toggle.setAttribute( 'data-focus-active', 'true' );
                toggle.textContent = '👁 Focus: ON';
            }
        }
    }

    // ─── Hide-inactive (Active) toggle ──────────────────────────────
    const persistedHideInactive = localStorage.getItem( this.CC_HIDE_INACTIVE_KEY ) === 'true';
    if ( persistedHideInactive !== this.ccHideInactiveStrip ) {
        this.ccHideInactiveStrip = persistedHideInactive;
    }
    if ( this.ccHideInactiveStrip ) {
        this._applyHideInactiveStripFilter();
        const toggle = document.getElementById( 'cc-hide-inactive-toggle' );
        if ( toggle ) {
            toggle.setAttribute( 'data-hide-inactive', 'true' );
            toggle.textContent = '👁 Active';
        }
    }
}
```

All log paths use `this.log(...)` with `[FOCUS-RESTORE]` / `[ACTIVE-TOGGLE-RESTORE]` prefixes so future failures are easy to diagnose in DevTools console.

---

## Why "belt and suspenders" rather than fixing the root cause

The three plausible causes (#1, #2, #3) require live-instrumented repro to pin down precisely, and a "race with X" fix would only handle one of them. Adding a post-load reconciliation handles all three (and the stale-id case) in one pass, without touching the existing entry/exit paths that Mr. Radio's coincident `notifications.js` work depends on. **Minimal conflict surface, maximal robustness.**

If Rick still hits a refresh-loses-focus symptom AFTER this fix, the `[FOCUS-RESTORE]` log lines will tell us exactly which code path ran, and we can target the root cause precisely.
