## 1. Motivation

The user-facing scenario: **María wants to ask Mr. Radio "do you have the latest commit hash for X?" WITHOUT Rick acting as middleman.**

Today, María must say to Rick: "please ask Radio for X" → Rick turns around to Radio's terminal → Radio answers → Rick relays back. That is the broken path.

The desired path: María's MCP tool fires a directed message → Radio's listener injects a `<system-reminder>` into his terminal context → Radio reads, prepares an answer, fires a return DM → María's listener injects the answer. Rick is a **witness** (the DM appears in his Recent Activity panel for transparency) but NOT a participant.

This is the **INTRA-AI principle** (Phase 0 §13 of the commons doc-set) applied to the bidirectional 1:1 channel. Phase 1 gave us file-based commons reads/writes; Phase 2 gave us user-broadcast push fanout; Phase 3 gave us reply-push-back-to-asker. **None of those three is "Phase X session-to-session push."** That is the gap.

### 2.2 What's missing — REVISED 2026-05-15 post-Rick feedback

**Rick's challenge** (verbatim, voice): *"I'm looking at your gap analysis and in section 2.2 where you're talking about what's missing you say there is no `commons_send_to` recipient method when in fact you list 2 methods that accomplish just this: `commons_ask_sync` and `commons_ask_async`. Why can't you reuse them?"*

**Rick was right.** `commons_ask_async` IS most of the DM mechanism — it already writes to a topic, registers a watcher, and pushes back to the asker on reply. The original §2.2 over-stated the gap by treating DM as a parallel system. Corrected analysis below.

#### 2.2.a What `commons_ask_async` already does (the bulk of DM)

1. ✅ Posts a question entry to a topic via `commons_store.post()` — persona-stamped, immutable, persists to `broadcasts` topic OR a free-form topic
2. ✅ Optionally fires `POST /api/commons/register-question` (push-mode) with `{topic, question_id, asker_session_id, ttl_seconds}` (see `src/lupin_mcp/commons_ask.py:33-76` `_register_push_mode`)
3. ✅ The `CommonsQuestionWatcher` polls the registered topic for replies with `metadata.in_reply_to == question_id`
4. ✅ On reply arrival, watcher dispatches `commons_answer_received` to the **asker's** listener via tmux injection (Phase 3 push)
5. ✅ Listener has `_handle_commons_answer_received` helper that frames the reply as `COMMONS PEER REPLY (question_id X, from @PersonaName):\n\n[body]` and injects via `<system-reminder>`

#### 2.2.b The actual gap — the *recipient*-side leg is missing

What `commons_ask_async` does NOT do today: push the **question** to the **recipient** when it lands. The recipient only sees the question if they:
- Manually call `commons_read(topic, since=...)` to poll, OR
- Are pre-registered as an asker on the same topic for a different question_id (and even then, they'd only get pushed for replies matching their own question_id)

**There's no "watch this topic for incoming messages addressed to me" daemon on the recipient side.** Phase 3's watcher is asymmetric — it polls on behalf of the asker, not the recipient.

#### 2.2.c Revised gap analysis (the small surgical extension)

| Gap | Evidence | Severity | Fix |
|---|---|---|---|
| **G1** — Endpoint doesn't dispatch to recipient at register time | `POST /api/commons/register-question` registers the watcher but only the watcher's tick dispatches, and only for replies, only to the asker. | 🟠 Endpoint MOD | Extend `RegisterQuestionRequest` with optional `recipient_session_id` (or `recipient_persona`); when present, dispatch `commons_question_received` to recipient's listener immediately on successful register |
| **G2** — Listener `commons_question_received` handler doesn't exist | `_handle_action` has `commons_answer_received` only. | 🟠 Listener MOD | Add `_handle_commons_question_received` mirroring `_handle_commons_answer_received` shape; frame as `COMMONS PEER MESSAGE (from @PersonaName, question_id X)` per Phase 3 framing convention |
| **G3** — `valid_types` whitelist missing entry | `notifications.py:362` allows `commons_broadcast_ack`, `commons_answer_received`, `commons_activity`. | 🟠 1-line MOD | Append `"commons_question_received"` |
| **G4** — `commons_ask_async` doesn't expose recipient param | Function signature in `commons_ask.py` accepts `topic`, `body`, `ttl`, push-mode kwargs — no recipient. | 🟠 MCP-tool MOD | Add optional `recipient` param; when present, pass through to the register-question payload |
| **G5** — Recent Activity DM visual differentiation | `_renderCommonsEntry` renders all entries uniformly. Question-with-recipient entries would be indistinguishable from user-broadcasts. | 🟡 Soft UX gap | Conditional badge for entries with `metadata.recipient_persona` or `metadata.kind=dm` |
| **G6** *(optional ergonomic)* — Fire-and-forget mode without watcher overhead | `commons_ask_async` always registers a watcher; for "FYI" DMs that don't expect a reply, the watcher is wasted | 🟢 Optional optimization | Add `expect_reply=False` param; when set, skip register-question call and use a one-shot endpoint variant OR have register-question accept `expect_reply=False` to dispatch-only-no-watch |

#### 2.2.d Direct answer to "is it implemented?"

**More-than-partially.** Phase 3's machinery does ~80% of the work:
- Topic write ✅
- Watcher infrastructure ✅
- Tmux injection ✅
- Asker-side push (for replies) ✅
- HTTP register endpoint ✅
- LLM persona disambiguator ✅

The missing 20% is the **recipient-side push at register time** — a ~30-line extension of the existing endpoint plus a parallel listener handler.

**Revised estimated effort**: ~80-100 new LOC + ~20 MOD LOC; **1-2 sessions, ~2-3h code-time** (down from the original over-estimate of 4-6 sessions / 6-10h based on the parallel-system assumption).

### 2.3 Direct answer to "is it implemented?"

**Partially.** The plumbing exists for:
- Posting to a topic (`commons_post`)
- Pushing user-broadcasts to all sessions (Phase 2 fanout)
- Pushing Phase-3 replies back to the original asker (`commons_answer_received` via `CommonsQuestionWatcher`)
- Per-recipient targeting via `target_session_id` (used internally by broadcast fanout)
- LLM-fuzzy persona resolution

What's NOT there: an MCP-tool entrypoint that lets a CC session push a directed message to another CC session's listener, with the message surfacing in Recent Activity. **Five distinct gaps, three of them hard blockers.**

**Estimated effort to close**: ~6-10 hours code-time across 4-6 sessions (Phase 0 design + REUSE + Pass 1 Fitness + Pass 2 Adversarial + Implementation + Test pyramid).

## 3. Architectural principle (proposed)

**INTRA-AI DM follows the same INTRA-AI principle** established in the commons Phase 0 §13:
1. Commons is INTRA-AI — user-bound comms via existing notification API. *(Inherited directly.)*
2. User-as-witness, not-as-middleman. *(The whole point of this initiative.)*
3. Naming consistency: `_sync` / `_async` suffix. *(Inherited.)*

Proposed addition:
4. **DM is "broadcast with N=1 recipient."** Reuse the broadcasts-topic + per-recipient-fanout machinery; the only semantic difference is `metadata.kind="dm"` for downstream rendering + observability.

## 5. Phase 0 — Q-decisions awaiting ratification (10 questions)

Per `feedback_pip_plan_review_is_sequential` + `feedback_always_include_pros_cons_recommendation`, each Q must be walked one-at-a-time with pros/cons/recommendation/flip in both spoken + abstract.

### Q1 — Endpoint name & path

- **Option A** *(recommended)* — `POST /api/commons/dm` (and `DELETE` if delete-DM ever needed). Pros: new path, no semantic confusion with user→all `/api/commons/broadcast`. Cons: one more route. **Flip**: becomes B if we want `broadcast` endpoint to grow a `target_session_id` mode.
- **Option B** — extend `/api/commons/broadcast` with required `target_session_id` body field + new `kind=dm` discriminator. Pros: single route, single code path. Cons: conflates user→all and session→one semantics; auth-mode coupling.

### Q2 — Auth on the new DM endpoint

- **Option A** *(recommended)* — `require_api_key_or_jwt` (mirrors existing commons endpoints). API-key for AI-session callers, JWT for human-debugging via curl/dev tools. Cons: API-key authority is broader than session-bridge-stamped session_id.
- **Option B** — session-bridge auth (read `session_id` from bridge file via cosa-voice MCP). Pros: enforces "only this MCP-registered session can DM as this persona." Cons: requires new auth middleware; doesn't mesh with curl-debugging.
- **Option C** — both, with bridge-auth required when sender-session attribution is part of the DM (default true).

### Q3 — Recipient addressing

- **Option A** *(recommended)* — both persona-name AND session_id accepted on the input. Server resolves persona-name via PHI-4 LLM disambiguator (Phase 3 reuse) when exact match fails; rejects ambiguous matches with HTTP 422. Cons: two-mode input adds branches.
- **Option B** — persona-name only. Pros: simplest UX. Cons: brittle if two personas share a name; impossible if recipient hasn't been assigned a persona yet.
- **Option C** — session_id only. Pros: unambiguous. Cons: AI doesn't naturally know session_ids of peers — has to call `commons_who()` first every time.

### Q4 — Recent Activity visibility

- **Option A** *(recommended)* — same `broadcasts` topic with `metadata.kind="dm"` + recipient persona name. UI renders a small "DM" badge + recipient name on entries where `kind=dm`. Reuses every Phase-2 + Traffic-Visibility primitive.
- **Option B** — separate `dms` reserved topic. Pros: clean isolation; Recent Activity can opt-in/out. Cons: need a new topic + render path; Rick's "all in one stream" intent works less well.
- **Option C** — both, with toggle.

### Q5 — Listener action name & system-reminder framing

- **Option A** *(recommended)* — action `commons_dm_received`; system-reminder body `COMMONS DM (from @PersonaName, dm_id <uuid>):\n\n[body]`. Mirrors Phase 3 `COMMONS PEER REPLY (question_id X, from @PersonaName)` framing exactly.
- **Option B** — reuse `broadcast_received` action with a `kind=dm` discriminator handled in `broadcast_handler.py`. Pros: one less handler. Cons: conflates user-broadcasts with AI-DMs in the listener too.

### Q6 — Acknowledgment

- **Option A** *(recommended)* — fire-and-forget for now. No ack topic. The DM exists in `broadcasts` topic so the sender can `commons_read` to verify post; tmux-injection success is the de-facto delivery confirmation. Pros: minimum surface. Cons: no proof-of-delivery to sender.
- **Option B** — reuse `broadcast-acks` topic — recipient's listener writes an ack on successful injection. Pros: feature-parity with Phase 2. Cons: extra writes per DM.
- **Option C** — strict ack with reply correlation via `in_reply_to` (mirror Phase 3 question/answer round-trip).

### Q7 — TTL / retention

- **Option A** *(recommended)* — same as Phase 1: 24h active + indefinite archive. Pros: consistency. Cons: privacy-by-aging is weaker than per-DM TTL.
- **Option B** — short TTL (e.g. 1h) for DMs by default. Pros: less noise in Recent Activity over time. Cons: divergence from Phase 1.

### Q8 — Rate limit

- **Option A** *(recommended)* — 1 DM / 5s / sender (INI-configurable). Pros: prevents accidental floods. Cons: slows iterative debugging dialogues.
- **Option B** — 1 / 30s (mirror Phase 2 broadcast rate-limit, Q11).
- **Option C** — no rate limit. Pros: free use. Cons: bug → flood.

### Q9 — MCP tool name & signature

- **Option A** *(recommended)* — `commons_send_to(recipient: str, body: str, metadata: dict | None = None, in_reply_to: str | None = None) -> dict`. Returns `{dm_id, recipient_session_id, recipient_persona, dispatched: bool}`. Pros: clear verb, mirrors `commons_post` + `commons_ask_async` shape. Cons: `send_to` is one more name to remember.
- **Option B** — `commons_dm(...)`. Pros: shortest. Cons: less self-documenting.
- **Option C** — overload `commons_post(...)` with an optional `target_persona` param. Pros: zero new tools. Cons: conflates "write to topic" with "directed push" semantics.

### Q10 — Reply ergonomics

- **Option A** *(recommended)* — recipient uses `commons_send_to(recipient=<sender_persona>, body=<reply>, in_reply_to=<dm_id>)` to reply. Phase 3 `in_reply_to` correlation already exists in the metadata field convention. Cons: requires recipient to remember dm_id.
- **Option B** — recipient uses `commons_ask_async(...)` to reply (with hard-coded `in_reply_to`). Pros: reuses Phase 3 register-watcher-dispatch. Cons: heavier mechanism than needed for one-shot replies.

## 13. Architectural correction post-Rick feedback (2026-05-15)

**Lesson**: Before scoping a new mechanism, ask whether an existing primitive's *symmetry* can be extended. Phase 3's `commons_ask_async` has a watcher that pushes ONE direction (replies → asker). Extending it to ALSO push the QUESTION → recipient at register time is a ~30-line surgical addition, not a parallel system.

**What I missed initially**: I cataloged `commons_ask_async` correctly in the "what works" table (§2.1) and then ignored its symmetry potential in the "what's missing" table (§2.2). I framed each missing piece as needing a NEW thing (`commons_send_to`, `commons_directed_message`, `commons_dm`, `/api/commons/dm`) when the right framing was EXTEND-an-existing-thing.

**The corrected shape** (§2.2.c table reflects this):
- No new MCP tool — extend `commons_ask_async` with optional `recipient` param
- No new endpoint — extend `POST /api/commons/register-question` to dispatch on register when recipient is set
- New listener action — `commons_question_received` mirroring `commons_answer_received` (a parallel handler, not a parallel mechanism)
- One-line `valid_types` MOD
- Recent Activity badge for entries with recipient metadata
- Optional `expect_reply=False` mode if we want to skip watcher registration for FYI-only DMs

- **Rationale**: clear DM verb at the MCP surface (discoverability for AI agents); `ask_async` stays as the flexible power-user primitive; consistent code path; no behavioral divergence risk.

### Q2-rev — Dispatch synchrony → **Option B: Fire-and-forget**

- **Implementation**: `POST /api/commons/register-question` returns 201 immediately after registering the watcher. Dispatch of `commons_question_received` to recipient's listener happens via the existing `notification_queue.dispatch` path (background, best-effort).
- **Rationale**: mirrors Phase 2 `execute_broadcast` fanout's `failed_recipients` best-effort isolation pattern (battle-tested); recipient-offline doesn't block sender; tight register-call latency. If sender needs delivery confirmation, use `expect_reply=True` and the reply itself is the confirmation.

### Q3-rev — Recipient addressing → **Option C: Both (persona name + session_id) with LLM fallback** + amendment (rich 422 error contract)

- **Implementation**: `RegisterQuestionRequest` accepts both `recipient_session_id` and `recipient_persona`. Precedence: session_id wins if both supplied. Persona resolution chain: exact → case-insensitive → punct/whitespace-tolerant → PHI-4 LLM disambiguator → 422 ambiguous.
- **Amendment (Rick voice 2026-05-15)**: when ALL disambiguation levels fail, the 422 response must give the AI caller actionable feedback so it can rectify and retry. Pydantic-validated `RecipientResolutionError` model:

  ```python
  class RecipientResolutionError( BaseModel ):
      error                       : Literal[ "recipient_persona_ambiguous",
                                             "recipient_not_found",
                                             "recipient_inactive",
                                             "recipient_required" ]
      supplied_persona            : Optional[ str ]
      supplied_session_id         : Optional[ str ]
      resolution_chain_attempted  : List[ str ]   # e.g. [ "exact", "case_insensitive", "punct_tolerant", "llm_phi4" ]
      candidate_alternatives      : List[ Dict[ str, str ] ]   # from commons_who() — active sessions
      suggested_next_action       : str
  ```

- **Rationale**: AI agents naturally think in personas; session_id is the escape hatch when persona resolution would fail; PHI-4 disambiguator already exists (Phase 3 reuse, zero new code); rich error feedback lets the AI caller self-correct without involving the human.

### Q4-rev — Recent Activity rendering → **Option A: Same `broadcasts` topic with DM badge**

- **Implementation**: DM entries write to existing `broadcasts` topic with `metadata.recipient_persona` stamped. `_renderCommonsEntry` in `notifications.js` conditionally appends a `→ @<recipient>` badge for entries with `metadata.recipient_persona` set. | # | Threat | Mitigation | Inherits from |

| **T3** | Cross-user DM — session A authenticated as user X tries to DM session B owned by user Y | `execute_register_question` same-user scoping check: reject 403 if recipient's bridge-stamped `owner_user_id` (or `user_id` fallback) differs from sender's authenticated user_id | Phase 2 T7 same-user scoping |

| **T5** | DM flood — sender hammers the endpoint with thousands of DMs to overwhelm a recipient | Existing Phase 3 register-question rate limit applies (per-user-id + global caps via INI keys).
