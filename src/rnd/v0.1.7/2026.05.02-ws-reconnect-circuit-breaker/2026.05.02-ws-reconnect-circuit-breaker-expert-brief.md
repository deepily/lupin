# WebSocket Reconnect Loop — Expert Review Brief

**Subject**: Browser-side WebSocket reconnect logic spirals into Chrome `Insufficient resources` after enough consecutive failures, never self-recovers.
**Author**: Claude Code (session 0022baba)
**Date**: 2026-05-02
**Audience**: Local socket / browser-network expert
**Status**: Diagnosis complete; fix design draft pending external review (no code changes applied)

---

## TL;DR

Browser-side reconnect loop in `notifications.js` has no max-attempt cap. When the network drops out for long enough (today: SSH tunnel exhausted FDs), cumulative `setTimeout`-scheduled reconnect attempts saturate Chrome's per-tab WebSocket slot pool (~255). The error reason on subsequent attempts flips from `failed:` (TCP RST/abort from tunnel) to `failed: Insufficient resources` (renderer-side cap hit). The loop cannot self-recover — only killing the tab process drains the renderer counters. We need a circuit breaker that caps consecutive failures, surfaces a user-actionable banner, and stops digging the hole. Design draft below — please weigh in before any code lands.

## Environment

| Item | Value |
|------|-------|
| Browser | Chromium-family (recent Chrome stable, exact version not captured) |
| OS / topology | Lupin server runs in Docker on Linux box; user's browser on a different host, accessed via `ssh -L 7999:localhost:7999 user@lupin-host` |
| Server | FastAPI + uvicorn behind Docker (port 7999 dev, healthy throughout the incident) |
| WebSocket library | Browser's native `WebSocket`; server uses FastAPI's `@router.websocket` decorator (Starlette/uvicorn under the hood) |
| Affected file | `src/fastapi_app/static/js/notifications.js` (~16k lines, monolithic class `NotificationsUI`) |
| WS endpoints | `/ws/queue/{session_id}` and `/ws/audio/{session_id}` — two separate WS per page |
| Reconnect strategy (current) | Single shared `connectionRetries` counter, exponential backoff `2s → 4s → 8s → 16s → 30s → ... cap 60s` after attempt 10, **no upper bound on attempts** |
| Health monitor | Polls every 90 s during work hours (8 AM – Midnight); independently calls `scheduleReconnect` |

## Symptom

User opened the notifications UI through an SSH tunnel; the tunnel had previously hit `accept: Too many open files` (EMFILE) and was failing forwards.

Browser console showed:
- HTTP requests to `/api/get-queue/done`, `/api/get-queue/dead`, `/api/job-history`, `/api/notify/response`, `/api/stats/time-saved/global`: `net::ERR_CONNECTION_RESET`
- WebSocket connect attempts to `/ws/queue/foolish%20goat` and `/ws/audio/slow%20zebra`: `code=1006 reason=` (abnormal closure, no close frame)
- Reconnect attempts climbed past `#461 for audio` and `#454 for queue`, all spaced 60 s apart, no recovery

After the user bumped `ulimit -n 8192` on the SSH client (giving the tunnel more FDs), the symptom string on subsequent WS attempts changed:
- **Before**: `WebSocket connection to 'ws://...' failed:` (bare colon, no reason — tunnel-layer abort)
- **After**: `WebSocket connection to 'ws://...' failed: Insufficient resources` (Chrome-internal renderer cap)

This transition is the load-bearing diagnostic. The tunnel was no longer the bottleneck — the renderer was. Killing the tab and opening a fresh one (with the now-bumped tunnel FD limit) recovered fully on the first attempt: queue + audio WS authenticated, `sys_ping` flowing both directions, `env=DEVELOPMENT`.

## File:line evidence

### Reconnect scheduler — `notifications.js:5616-5634`

```javascript
scheduleReconnect( target = 'both' ) {
    if ( this.isConnecting ) {
        return; // Already attempting to reconnect
    }

    this.connectionRetries++;
    // Exponential backoff: 2s, 4s, 8s, 16s, 30s... then cap at 60s after 10 failures
    const maxDelay = this.connectionRetries > 10 ? 60000 : 30000;
    const delay = Math.min( 1000 * Math.pow( 2, this.connectionRetries ), maxDelay );

    this.wsDiag( `Scheduling reconnect attempt #${this.connectionRetries} for ${target} in ${delay}ms` );

    setTimeout( () => {
        this.isConnecting = true;
        this.connectWebSockets( target ).finally( () => {
            this.isConnecting = false;
        });
    }, delay );
}
```

**Issues**:
- `this.connectionRetries` is shared across both channels (queue + audio). A healthy queue auth doesn't drain the audio counter.
- No upper-bound check before `setTimeout`.
- `isConnecting` only blocks REENTRANT calls during in-flight `connectWebSockets`. Once that resolves, the next failure can fire freely.

### Close handlers — `notifications.js:2174-2179` and `:2224-2229`

```javascript
this.queueWS.onclose = ( event ) => {
    this.wsDiag( `Queue WebSocket closed: code=${event.code} reason=${event.reason}` );
    this.queueWsConnected = false;
    this.updateStatus( "queue-ws-status", "Disconnected", "error" );
    this.scheduleReconnect( 'queue' );
};
```

(Audio handler is identical except channel name.) Every close — including those that immediately follow a failed open — calls `scheduleReconnect`. No debounce, no failure-burst detection.

### Health monitor — `notifications.js:880-911`

```javascript
if ( queueNeedsReconnect || audioNeedsReconnect ) {
    const target = ( queueNeedsReconnect && audioNeedsReconnect ) ? 'both'
                 : queueNeedsReconnect ? 'queue' : 'audio';
    this.wsDiag( `Health check: Disconnected WebSockets detected ...` );
    this.updateHealthStatus( "Reconnecting...", "status-warning" );

    // Reset retry counter to give reconnection a fresh start from health monitor
    this.connectionRetries = 0;

    // Trigger targeted reconnection
    this.scheduleReconnect( target );
}
```

**This is the smoking gun for the "461 attempts" log line.** The health monitor runs every 90 s and zeros `connectionRetries` to "give reconnection a fresh start". Combined with the close handler's independent call to `scheduleReconnect`, the cumulative attempt count never reflects reality — the on-screen `#461` was the close-handler chain, while the health monitor was silently re-zeroing the counter every 90 s. The two reconnect paths race each other AND hide each other's state.

### Counter reset gap

The counter resets ONLY inside `checkWebSocketHealth`. So a successful `WebSocket → auth_success → drop → reconnect` cycle accumulates the counter forever during a long-lived session. Latent today (masked by the health monitor's 90 s reset) but exposed if the health monitor is fixed. A correct reset point is `auth_success` for the corresponding channel — TCP `open` is too early because TCP can succeed and auth still fail.

## Hypothesis (multi-stage cascade)

| Stage | Cause | Evidence |
|-------|-------|----------|
| 1. TCP RST on the wire | SSH tunnel `accept()` returns EMFILE → kernel completes handshake locally but SSH can't claim FD to forward → RST | User reported `accept: Too many open files` from the tunnel process |
| 2. Browser sees `code=1006` close | TCP abort never produced a WS close frame | Console: `code=1006 reason=` |
| 3. Reconnect loop fires on every close | Close handler unconditionally calls `scheduleReconnect` | Code at `:2178` / `:2228` |
| 4. Health monitor compounds the storm | Independent reconnect path runs every 90 s, zeros counter | Code at `:904`–`:907` |
| 5. Renderer hits per-tab WS slot cap | Each failed WS still consumes a renderer-side slot until released; ~255 per tab in Chromium | Symptom flip from `failed:` to `failed: Insufficient resources` |
| 6. No recovery without process restart | Slots don't drain until tab process exits (or browser GCs old `WebSocket` objects, which it isn't doing aggressively here) | Killing tab + fresh tab = first-attempt success |

**The Lupin-side bug is stages 3 + 4** (no cap, redundant reconnect paths). Stage 1 is a host-config issue outside Lupin's scope (user already remediated via `ulimit -n 8192` and an `~/.ssh/config` `ServerAliveInterval` will harden it further).

**Confidence**: high. Server side `:7999` was healthy throughout (`curl /health` 200 in 1.3 ms; `active_connections` showed only the Claude-Code listener — no browser WS handshakes ever reached uvicorn). Diagnosis is forensic, not speculative.

## Proposed fix — ranked solutions

### Solution A — Per-channel circuit breaker (RECOMMENDED)

**State model**:
- Replace shared `connectionRetries` with `queueRetries` + `audioRetries`.
- Add per-channel `circuitOpen` boolean.
- (Optional) per-channel `lastAuthSuccessAt` timestamp for diagnostics.

**Reset rule**: `<channel>Retries` zeros on `auth_success` for that channel — NOT just on TCP `open`, because TCP can succeed and auth still fail.

**Trip rule**: when `<channel>Retries >= MAX_ATTEMPTS_PER_CHANNEL` (proposed **20**), set `circuitOpen = true` for that channel, STOP scheduling reconnects for it, surface a UI banner.

**Banner**: combined for both channels (when ≥1 breaker open) — "Connection lost — server unreachable after 20 attempts. Refresh to retry." With a "Retry now" button that zeros both counters, closes both breakers, and re-attempts.

**Health monitor change**: when `circuitOpen` is true for a channel, the health monitor MUST NOT re-call `scheduleReconnect` for it. Remove the `connectionRetries = 0` line entirely; rely on the new per-channel reset-on-`auth_success` rule.

**Configurability**: class-level constants at top of `NotificationsUI` (`MAX_RECONNECT_ATTEMPTS_PER_CHANNEL = 20`, `RECONNECT_BACKOFF_FLOOR_MS = 2000`, `RECONNECT_BACKOFF_CEIL_MS = 60000`). No INI plumbing for v1; we can promote to server-fed config later if needed.

**Why 20**: at the existing backoff curve (2, 4, 8, 16, 30, 60, 60…), 20 attempts ≈ 16 minutes of trying. Long enough that a flaky-but-recoverable network blip won't trip; short enough that we don't burn renderer slots indefinitely.

**Tradeoffs**:
- ✓ Surgical; touches only the reconnect/health-monitor paths.
- ✓ Bounded blast radius (UI string + a few state fields).
- ✗ Doesn't address the latent issue of `connectWebSockets` retrying both channels even when only one failed (separate concern, file separately).
- ✗ The 20-attempt budget could be too generous for renderer health on weaker clients — open question.

### Solution B — Solution A + rapid-failure fast-path

Same as A, plus:
- Track per-channel failure timestamps (rolling buffer of last N).
- If `>= 5` failures within `30 s` for a channel AND no `auth_success` in between, trip the breaker immediately rather than waiting for the 20-attempt budget.

**Rationale**: the `Insufficient resources` failure mode happens when failures arrive faster than the reconnect backoff can space them out (specifically: when the WS errors-out near-synchronously on `new WebSocket()` because the renderer has no slots to allocate). Catching this fast-path means we trip in seconds instead of 16 minutes when the renderer is already wedged.

**Tradeoffs**:
- ✓ Faster recovery for the worst-case (renderer-saturation) scenario.
- ✗ Adds a second decision rule — more surface area for false trips.
- Open question: is this worth v1, or defer to v2 if the simple cap turns out to be sufficient?

### Solution C — Replace rolling reconnect with single-shot connect-or-fail-loud

Each WS gets ONE connect attempt at page-load. Failure → immediate banner. Manual retry button is the only recovery path.

**Tradeoffs**:
- ✓ Conceptually simplest.
- ✗ Hostile to the actual common case (transient network blip during a 6-hour browser session — user doesn't want to manually click retry every WiFi-handoff). Rejected.

### Solution D — Server-side rate-limit on WS handshake endpoint

Add a per-source-IP cap on WS handshakes per minute. Anything past the cap returns 429.

**Tradeoffs**:
- ✓ Defense-in-depth; protects server from any misbehaving client.
- ✗ Doesn't fix today's bug (handshake never reached uvicorn — was aborted by the SSH tunnel). Browser still spirals into renderer saturation. Worth doing IN ADDITION to A/B, but not as a substitute.

## Open questions for the expert

1. **Renderer slot cap reality check.** Is the ~255 per-tab WS limit in Chromium accurate as of recent Chrome versions, or has it changed? Are slots reclaimed on `WebSocket.close()` or only on full GC of the `WebSocket` object? (If GC-only, the JS reconnect path needs to explicitly null out old `WebSocket` references to make them collectable. Does it currently? — we don't see explicit nulling in the close handler today.)

2. **`code=1006 reason=` vs distinguishable causes.** Is there a robust JS-level signal for "the connection was reset by the network layer" vs "the server actively refused the upgrade" vs "we have run out of renderer FDs"? The Solution-B rapid-failure heuristic is a proxy because we can't read the underlying cause directly — is there a better one?

3. **Backoff curve.** The current `2,4,8,16,30,60×N` curve has a sharp jump from 16 s to 30 s and another from 30 s to 60 s. Is there a standard "RFC-flavored" curve that handles renderer health better? (Linear-then-cap? Pure exponential to a higher ceiling? Decorrelated jitter à la AWS?)

4. **Two reconnect paths.** Today's code has the close handler AND the health monitor independently calling `scheduleReconnect`. The intuition behind a periodic health monitor (catch the case where the close handler somehow didn't fire — e.g. tab woken from sleep with a half-open socket) is reasonable, but the current implementation races itself. Is there a clean pattern for "close handler is primary, health monitor only fires if close handler hasn't reacted within X seconds"?

5. **Tab-suspend handling.** When Chrome suspends a backgrounded tab, the WS may close with `code=1006`. On tab resume, the close handler fires and the reconnect loop starts. Should the circuit breaker treat tab-resume as a special case (maybe via the Page Visibility API), or just trust that one `auth_success` will reset the counter?

6. **Test surface.** I can write a Playwright E2E test that injects a mock `WebSocket` constructor on the page and drives the state machine. Is there a more idiomatic way to unit-test browser WS behavior — Karma/Jest with a WS mock, Playwright's CDP route interception? The codebase doesn't currently have a JS unit harness.

## Reproducer

**Steps to reproduce on a fresh setup**:

1. Open the Lupin notifications UI in Chrome.
2. While the page is open with both WS connected, induce sustained network failure to `:7999`. Three viable methods, ranked by faithfulness to today's actual repro:
   - **Tunnel-FD method (today's actual repro)**: SSH-tunnel `:7999` from a host where `ulimit -n` for the SSH client process is lower than the number of FDs needed. Open the page → reload a few times → many short-lived connections will exhaust the tunnel.
   - **iptables method**: `sudo iptables -A INPUT -p tcp --dport 7999 -j DROP` — clean but requires root, faithful to the "TCP RST in flight" pattern.
   - **Server-stop method**: `docker stop lupin-rest-dev` — simulates outage; less faithful (no TCP RST, just connection refused).
3. Watch the console. After ~2 minutes, reconnect attempts will be in the 20s. After ~10 minutes, per-tab WS slot pressure becomes visible. After ~16 minutes, the error string flips from `failed:` to `failed: Insufficient resources`.
4. Restore network. The loop will NOT recover — the renderer is already saturated. Killing the tab and opening a fresh one is the only recovery.

**Steps to verify the fix**:

Same setup; with the circuit breaker in place, after the threshold (default 20) reconnects, the banner should appear and the loop should halt. Restoring the network and clicking "Retry now" should recover on the first attempt.

## Fallback

If the expert flags Solution A/B as inadequate or risky:

1. **Minimum viable**: hardcode a single max-attempt cap (no per-channel state, no rapid-failure detection) — just `if ( this.connectionRetries >= 20 ) { showBanner(); return; }` at the top of `scheduleReconnect`. Three lines, ships today, fixes the user-visible bug. Loses per-channel granularity and the rapid-failure fast-path, but the page stops digging the hole.
2. **Soak-mode rollout**: ship a feature flag (`circuit_breaker_enabled` in localStorage) that gates the new behavior, default off. Lets the fix soak in production traffic without risk of regressing the (rare but possible) cases where today's loop happens to recover after, say, 25 attempts.
