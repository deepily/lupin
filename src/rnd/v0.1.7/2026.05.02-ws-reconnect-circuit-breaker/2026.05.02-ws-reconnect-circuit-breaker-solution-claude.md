# Browser WebSocket Reconnect & Circuit Breaker: Forensic Brief Response

**TL;DR**

- **Your hypothesis is correct and the smoking gun is now grounded in primary source.** Chromium's `services/network/websocket_throttler.h` defines `kMaxPendingWebSocketConnections = 255` enforced **per renderer process** on connections **whose handshake has not completed**. `Insufficient resources` (`net::ERR_INSUFFICIENT_RESOURCES`) is what you get when that pool is exhausted. Your two channels × no-cap retry × periodic counter zero-out is exactly the pathology that fills the pending pool faster than handshakes can drain it. The proposed Solution A (per-channel circuit breaker, max attempts, reset on `auth_success`) is correct in shape; the parameter choices and supporting machinery need three targeted refinements (decorrelated jitter, single-trigger state machine with idempotency token, Page Lifecycle integration) detailed below.
- **The single most important code change is to delete the periodic counter-zeroing health monitor and replace it with an idempotent watchdog** that *only* schedules a reconnect when (a) `readyState === CLOSED` AND (b) no reconnect token is currently pending. Never reset the attempt counter except on `auth_success`. This is industry consensus across Phoenix Channels, signalr, ably-js, centrifuge-js, and Socket.IO — none of them reset the retry counter on a wall-clock timer.
- **MAX_ATTEMPTS=20 is at the upper end of reasonable but defensible** if and only if combined with: (i) decorrelated-jitter backoff capped at 30s (so 20 attempts ≈ 6–10 min of wall-clock, not 16), (ii) pause-while-hidden via Page Visibility, and (iii) hard guard against constructing a new `WebSocket` while a previous instance is still in `CONNECTING` state — that guard is what actually keeps you off the 255-pending cliff. Without (iii), even a perfect circuit breaker can re-trip the renderer cap if the upstream is slow-rejecting handshakes (FastAPI/uvicorn behind an exhausted SSH tunnel will do exactly that).

## Key Findings

### 1. The Chromium 255 limit is per-renderer, on *pending* handshakes, not on open sockets

The authoritative source is `services/network/websocket_throttler.h` in Chromium main:

```cpp
class WebSocketPerProcessThrottler final {
  // ...
  bool HasTooManyPendingConnections() const {
    return num_pending_connections_ >= kMaxPendingWebSocketConnections;
  }
  static constexpr int kMaxPendingWebSocketConnections = 255;
};

class WebSocketThrottler final {
  std::map<network::RendererProcessId,
           std::unique_ptr<WebSocketPerProcessThrottler>> per_process_throttlers_;
  // ...
};
```

Four facts that change how you reason about your bug:

1. **The 255 counter increments on `new WebSocket(...)` and decrements on `OnCompleteHandshake()`** — i.e., on the WebSocket *opening* handshake completing, *not* on `close()`. A `WebSocket` whose handshake is stalled (slow upstream, half-open TCP through a dying SSH tunnel, etc.) holds a slot indefinitely until the underlying request completes or is cancelled. This is the precise mechanism by which "tunnel exhausts FDs ⇒ uvicorn TCP accept stalls ⇒ each `new WebSocket()` sits in pending state ⇒ pool fills at 255 ⇒ `ERR_INSUFFICIENT_RESOURCES`."
2. **It is per-renderer process**, not per-tab and not per-origin. Multiple tabs in the same site-isolated process share the pool. With site isolation enabled (default since 2018), one origin in one tab generally maps to one renderer, but cross-origin iframes spawn their own renderer.
3. **Chromium also imposes a separate, lower limit of 32 for WebSockets going through an HTTP CONNECT proxy** (per the Electron issue #15895 thread linking `websocket_stream.cc:117`).
4. **There is also a soft throttling delay calculated from the prior period's success/failure ratios** — `WebSocketPerProcessThrottler::CalculateDelay()` — that adds a randomized delay on subsequent connects when failures are concentrated. So even before you hit 255 pending, a tight reconnect loop will start being slowed down by the network service itself, which is what makes the renderer-side error look like the symptom-state transition you observed: bare `WebSocket connection failed:` (handshake aborted by renderer-side throttle delay or tunnel) → `Insufficient resources` (pool truly full).

**Slot reclamation:** The slot is released when the URLRequest underlying the handshake terminates — successful upgrade, server reject, or the renderer cancelling the request when the JS `WebSocket` object becomes unreachable. In practice, calling `ws.close()` on a still-CONNECTING socket *does* cancel the URLRequest and release the slot; calling `close()` on an already-OPEN socket releases the slot immediately (handshake had already drained it). What does *not* release a slot is letting the JS object dangle in a closure (e.g. `setTimeout(()=>{... ws ...}, 60000)`) — the URLRequest will eventually be torn down on document unload, but until then the socket can keep its renderer-process resources. **Concrete cleanup recipe** (see code in §4 below): explicit `removeEventListener` on all four handlers, then `close()`, then `null` the reference. AbortController is not yet wired into the legacy `WebSocket` constructor (only `WebSocketStream`).

**Firefox/Safari:** Firefox enforces ~200 globally per profile (longstanding lore, never updated to a single citation); Safari has no documented hard cap and tends to surface as ECONNRESET. Per-host limits are protocol-irrelevant for `wss://` (the well-known "6 per host" only applies to HTTP/1.1 fetches).

### 2. Close code 1006 is structurally indistinguishable, but you can heuristically separate cases

RFC 6455 §7.1.5 explicitly forbids 1006 from appearing on the wire — it is set locally by the user agent when no close frame was received before TCP teardown. The browser further suppresses error detail from `CloseEvent.reason` and the `error` event for security (it would otherwise leak network topology). Consequence: **JavaScript cannot distinguish (a) TCP RST, (b) HTTP 401/403/500 during upgrade, and (c) renderer-side resource exhaustion from the `CloseEvent` alone.** All three present as `code=1006, reason="", wasClean=false`.

What works in practice (consensus across `partysocket`, `reconnecting-websocket`, ably-js, Twilio Voice SDK):

| Signal | Discriminates |
|---|---|
| `wasEverOpen` flag set in `onopen` | (b)+(c) handshake failure vs (a) mid-flight drop |
| Time from `new WebSocket()` to `onclose` | <50ms typically = renderer-side reject; ~RTT to a few sec = upstream reject; minutes-then-drop = network |
| Burst rate of consecutive 1006 with `!wasEverOpen` | Strong renderer/upstream-handshake-reject signal — *fail fast* |
| DevTools Network tab inspection of the upgrade response | The only way to see the actual HTTP status (not exposed to JS) |
| Server-side log correlation by `Sec-WebSocket-Key` or auth token | Definitive but requires a backchannel |

The "fail fast on rapid 1006 bursts" pattern is exactly what Twilio Voice's docs describe (their 1006/1015 fallback heuristic) and what your circuit breaker should encode: if N consecutive closes are 1006 with `!wasEverOpen` and inter-close interval is below some threshold, *open the circuit immediately* without exhausting MAX_ATTEMPTS — this is the protective layer that keeps you off the 255-cap.

### 3. Backoff curves: industry consensus

There is no IETF document specifically targeting WebSocket reconnect backoff. The closest normative pieces:

- **RFC 6585 §4** defines HTTP 429 with `Retry-After`. RFC 7231 §7.1.3 (and now RFC 9110 §10.2.3) define `Retry-After` for 503/3xx. **Honor `Retry-After` if the *handshake* HTTP response carries it** — but you'll only see this server-side; `Retry-After` from a failed WebSocket upgrade is not exposed to JS by the browser. Useful only if your server returns a normal 503 to a regular fetch probe.
- **draft-ietf-tcpm-rto-consider** (and the Marc Brooker / AWS body of work) is the de-facto reference: capped exponential backoff with jitter, with **decorrelated** or **full** jitter beating no-jitter and equal-jitter. 

Comparison of production curves (all confirmed against source):

| Library / SDK | Default curve | Cap | Max attempts |
|---|---|---|---|
| **Phoenix Channels** (`assets/js/phoenix.js`) | `[10, 50, 100, 150, 200, 250, 500, 1000, 2000][tries-1] || 5000` ms | 5s | unbounded; reset on socket `open` |
| **Phoenix rejoin** (per-channel) | `[1000, 2000, 5000][tries-1] || 10000` ms | 10s | unbounded |
| **Socket.IO v4** | `min(reconnectionDelay·2^attempt, reconnectionDelayMax) · (1 ± randomizationFactor)` | 5s | `Infinity` |
| **signalr (ASP.NET Core)** | `[0, 2000, 10000, 30000]` then `null` | 30s | **4** then give up |
| **ably-js** | exponential to `disconnectedRetryTimeout` then steady at `suspendedRetryTimeout=30s` | 30s | unbounded but state-flagged "suspended" |
| **centrifuge-js** | exponential with jitter, `minReconnectDelay=500`, `maxReconnectDelay=20000` | 20s | unbounded |
| **partysocket / reconnecting-websocket** | `minDelay·growFactor^attempt` (default 1.3) capped at `maxDelay` | configurable | configurable, defaults `Infinity` |
| **Twilio Voice JS** | exponential capped at `backoffMaxMs`, max signaling-reconnect window 30s | configurable | bounded by `maxCallSignalingTimeoutMs` |
| **AWS IoT Device SDK** | full jitter (Marc Brooker), default min 1s, max 120s | 120s | configurable |

**Takeaway:** Your current `2, 4, 8, 16, 30, 60×N` is unusual on three axes:
1. It starts late (2s) compared to Phoenix's 10ms — fine for cold-start but slow for transient flips.
2. Lacks jitter entirely — guarantees thundering-herd against your FastAPI server when many tabs reload after a deploy.
3. Has the discontinuities you noticed (16→30, 30→60). Decorrelated jitter eliminates this with a smooth distribution.

The two industry-standard curves to choose between (Marc Brooker / AWS Architecture Blog 2015, validated by Polly, AWS SDK retry, AWS IoT Device Advisor):

```js
// Full jitter — Brooker's "best for most cases"
sleep = random_uniform(0, min(cap, base * 2 ** attempt));

// Decorrelated jitter — slightly higher work, tighter completion-time variance
sleep = min(cap, random_uniform(base, sleep_prev * 3));
```

For client-side WebSocket reconnect against a single server (your case), **full jitter is the safer default** — decorrelated's `prev*3` clamping (Thom Wright 2024 critique) effectively saturates at `cap` quickly and reduces the jitter benefit. Reference vanilla-JS implementation:

```js
// backoff.js — minimalist, dependency-free
const BASE_MS = 500;     // first attempt envelope
const CAP_MS  = 30_000;  // ceiling

function fullJitterDelay(attempt) {
  const exp = Math.min(CAP_MS, BASE_MS * 2 ** attempt);
  return Math.floor(Math.random() * exp);
}

// Decorrelated alternative — keeps prevDelay across calls
function makeDecorrelated(base = 500, cap = 30_000) {
  let prev = base;
  return () => {
    const next = Math.min(cap, base + Math.random() * (prev * 3 - base));
    prev = next;
    return Math.floor(next);
  };
}
```

Note: 20 attempts under full jitter with cap=30s gives an *expected* total wait of ≈ Σᵢ E[Uniform(0, min(30000, 500·2^i))] / 1000 ≈ 6–8 minutes (most attempts are saturated at the 30s cap, but jitter halves the average). That's the right zone.

### 4. Reconciling close-handler and health-monitor: one state machine, one token

The pattern in your current code — `onclose` triggers reconnect AND a `setInterval(90s)` triggers reconnect AND zeros the counter — has three independent failure modes:

1. **Race**: close handler fires reconnect at t=2s; monitor fires reconnect at t=90s; you now have two pending `WebSocket` objects competing for the same channel.
2. **Counter zeroing**: every 90s the breaker resets, so the system can never actually open the circuit. This is the proximate cause of "461 attempts."
3. **Double-fire from `onerror`+`onclose`**: per RFC 6455 the `error` event always precedes a 1006 `close`. Reconnecting from both produces 2× the schedule.

Industry consensus is to make the close handler the *only* reconnect trigger and to use the periodic loop *only as a watchdog* that fires when the close handler demonstrably failed to. A clean implementation uses a generation token to keep duplicates idempotent:

```js
// ws-channel.js — minimalist per-channel state machine
const STATE = { IDLE: 0, CONNECTING: 1, OPEN: 2, BACKOFF: 3, OPEN_CIRCUIT: 4 };

function createChannel({ url, onMessage, onAuthSuccess, name }) {
  const MAX_ATTEMPTS = 20;
  const HANDSHAKE_TIMEOUT = 10_000;
  let ws = null;
  let state = STATE.IDLE;
  let attempts = 0;
  let generation = 0;          // monotonic — stale callbacks check vs current
  let backoffTimer = null;
  let handshakeTimer = null;
  let wasEverOpen = false;
  let recent1006Burst = [];    // for fail-fast heuristic

  const log = (...a) => console.debug(`[${name}]`, ...a);

  function setState(s) { log('state', state, '->', s); state = s; }

  function cleanupSocket(sock) {
    if (!sock) return;
    sock.onopen = sock.onclose = sock.onerror = sock.onmessage = null;
    try { sock.close(1000, 'cleanup'); } catch {}
  }

  function scheduleReconnect(reason) {
    if (state === STATE.OPEN_CIRCUIT) return;     // explicit user-required retry
    if (state === STATE.BACKOFF || state === STATE.CONNECTING) return; // idempotent
    attempts += 1;
    if (attempts > MAX_ATTEMPTS) {
      setState(STATE.OPEN_CIRCUIT);
      window.dispatchEvent(new CustomEvent('ws-circuit-open',
        { detail: { name, attempts, reason } }));
      return;
    }
    const delay = fullJitterDelay(Math.min(attempts - 1, 10));  // cap exponent
    log('backoff', delay, 'ms', 'attempt', attempts, 'reason', reason);
    setState(STATE.BACKOFF);
    backoffTimer = setTimeout(connect, delay);
  }

  function connect() {
    if (state === STATE.OPEN_CIRCUIT) return;
    if (document.visibilityState === 'hidden') {       // see §5
      log('hidden, deferring connect');
      return;                                          // pageshow/visibilitychange will retrigger
    }
    if (ws && (ws.readyState === WebSocket.CONNECTING ||
               ws.readyState === WebSocket.OPEN)) {
      log('connect called while ws live, no-op');
      return;                                          // GUARDS the 255 pool
    }
    cleanupSocket(ws); ws = null;

    setState(STATE.CONNECTING);
    const myGen = ++generation;
    wasEverOpen = false;
    ws = new WebSocket(url);

    handshakeTimer = setTimeout(() => {
      if (myGen !== generation) return;
      if (ws && ws.readyState === WebSocket.CONNECTING) {
        log('handshake timeout');
        try { ws.close(); } catch {}                    // releases 255-slot
      }
    }, HANDSHAKE_TIMEOUT);

    ws.onopen = () => {
      if (myGen !== generation) return;
      clearTimeout(handshakeTimer);
      wasEverOpen = true;
      setState(STATE.OPEN);
      // Note: do NOT reset attempts here — wait for auth_success
    };

    ws.onmessage = (ev) => {
      if (myGen !== generation) return;
      let msg; try { msg = JSON.parse(ev.data); } catch { return; }
      if (msg.type === 'auth_success') {
        attempts = 0;                                    // ONLY place we reset
        recent1006Burst = [];
        onAuthSuccess?.(msg);
      }
      onMessage?.(msg, ev);
    };

    // Per RFC 6455, error always precedes close. Do NOT schedule from onerror.
    ws.onerror = (e) => { if (myGen === generation) log('error (advisory)', e); };

    ws.onclose = (ev) => {
      if (myGen !== generation) return;
      clearTimeout(handshakeTimer);
      log('close', ev.code, ev.reason, 'wasEverOpen=', wasEverOpen);

      // Fail-fast: rapid 1006 with !wasEverOpen ⇒ likely renderer/upstream cap
      if (ev.code === 1006 && !wasEverOpen) {
        const now = Date.now();
        recent1006Burst.push(now);
        recent1006Burst = recent1006Burst.filter(t => now - t < 5_000);
        if (recent1006Burst.length >= 3) {
          log('fail-fast: 3+ rapid 1006s, opening circuit');
          setState(STATE.OPEN_CIRCUIT);
          window.dispatchEvent(new CustomEvent('ws-circuit-open',
            { detail: { name, reason: 'rapid-1006-burst' } }));
          return;
        }
      }
      if (ev.code === 1000 || ev.code === 1001) {       // normal/going-away
        setState(STATE.IDLE);
        return;
      }
      scheduleReconnect(`close ${ev.code}`);
    };
  }

  // Watchdog: never resets the counter; only fires reconnect if we are
  // demonstrably in a wedged state that the close handler failed to react to.
  const watchdog = setInterval(() => {
    if (state === STATE.OPEN_CIRCUIT || state === STATE.BACKOFF ||
        state === STATE.CONNECTING) return;
    if (state === STATE.IDLE) return;                   // explicit shutdown
    if (ws && ws.readyState === WebSocket.CLOSED) {
      log('watchdog: socket CLOSED with no scheduled reconnect, recovering');
      scheduleReconnect('watchdog');
    }
    // Liveness probe — only if state===OPEN
    if (state === STATE.OPEN && ws?.readyState === WebSocket.OPEN) {
      try { ws.send(JSON.stringify({ type: 'sys_ping', ts: Date.now() })); }
      catch (e) { log('ping send failed', e); }
    }
  }, 30_000);

  return {
    connect,
    manualRetry() {                                      // wired to UI banner button
      attempts = 0;
      recent1006Burst = [];
      setState(STATE.IDLE);
      connect();
    },
    close() {
      clearInterval(watchdog);
      clearTimeout(backoffTimer);
      clearTimeout(handshakeTimer);
      generation++;
      cleanupSocket(ws); ws = null;
      setState(STATE.IDLE);
    },
    get state() { return state; },
    get attempts() { return attempts; },
  };
}
```

Key invariants this enforces (and that match Phoenix Channels' `Timer`/`channel.rejoinTimer`, signalr's `RetryContext`, and centrifuge-js's reconnecting state-machine semantics):

- **Single trigger.** `onclose` schedules; watchdog only re-arms `scheduleReconnect` if the close handler somehow didn't (e.g., bfcache resume, tab woken from sleep).
- **Generation token.** Late-arriving callbacks from a previous `WebSocket` instance are dropped, eliminating double-fires.
- **No `onerror` reconnect.** Per RFC 6455 §7.1.4, `error` always precedes `close`; reconnecting from both is double-counting.
- **Counter only resets on `auth_success`**, not on TCP `open`. This is critical: if your auth handshake fails repeatedly post-`open`, you must count those as attempts.
- **`readyState` guard before `new WebSocket()`** — the line `if (ws && ws.readyState === CONNECTING/OPEN) return;` is what prevents you from refilling the 255-pool while a previous handshake is still pending.

**Server-side ping vs client-side `sys_ping`:** RFC 6455 §5.5.2 ping/pong frames are mandated to be supported but the browser `WebSocket` API does not expose them to JavaScript — only the server can initiate a ping that the browser auto-pongs. The corollary is that **client-driven application-level pings (your `sys_ping`) are necessary for the client to detect a half-open TCP**; the browser's pong of a server-initiated ping won't surface to your JS at all. Phoenix uses this same pattern (the special "phoenix" topic heartbeat). For uvicorn/FastAPI you should *also* enable `ws_ping_interval=20, ws_ping_timeout=20` server-side — that handles the *server's* detection of dead clients.

### 5. Page Lifecycle integration

What actually happens to a WebSocket when Chrome backgrounds/freezes a tab:

- **`visibilitychange` (hidden):** WebSocket is *not* closed. `setTimeout` enters Chrome's intensive throttling after ~5min of being hidden + silent (chrome.com Page Lifecycle docs; Janus / Supabase realtime issue threads confirming 5-min mark). Pending reconnect timers will fire at ≥1 Hz instead of their nominal schedule, then *all queue at once when the tab becomes visible* — the "thundering herd from one client" anti-pattern.
- **`freeze` (Chrome only):** All freezable tasks are suspended. WebSocket is held open but `setTimeout`s and most async callbacks do not run. `resume` fires when the tab returns to active.
- **`pagehide` / BFCache:** A page with an open WebSocket is **ineligible for back/forward cache** in Chrome and Firefox. Browser will close the socket. `pageshow` with `event.persisted === true` indicates BFCache restoration — your old WebSocket reference is invalid.
- **`pageshow` (regular load):** Treat as cold start.

Industry consensus pattern (web.dev BFCache article, Chrome Page Lifecycle API docs, socket.io issue #5232):

```js
// page-lifecycle.js — wire the channel created above
function attachLifecycle(channel) {
  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'hidden') {
      // Optional: aggressive — close socket so tab is bfcache-eligible.
      // For your notifications UX, keep open but pause reconnect attempts.
      // The connect() guard already does that.
    } else {
      // Coming back: if socket is dead and we are in BACKOFF, fire immediately.
      if (channel.state !== 0 /* IDLE */ && channel.state !== 4 /* OPEN_CIRCUIT */) {
        channel.manualRetry?.();   // or a softer "kick" that doesn't reset counter
      }
    }
  });

  // BFCache restore — old WS object is invalid, must reconnect from scratch.
  window.addEventListener('pageshow', (ev) => {
    if (ev.persisted) channel.manualRetry();
  });

  // Best practice: close on pagehide so the tab can BFCache.
  window.addEventListener('pagehide', () => channel.close());

  // Chrome-only freeze/resume
  document.addEventListener('freeze',  () => channel.close());
  document.addEventListener('resume',  () => channel.connect());

  // Network-aware
  window.addEventListener('online',  () => channel.manualRetry());
  window.addEventListener('offline', () => channel.close());
}
```

**Decision point — should reconnect attempts pause when hidden?** Yes, with a caveat. The pattern above relies on the `if (document.visibilityState === 'hidden') return;` guard inside `connect()`: backoff timers still fire, but they no-op until visibilitychange brings the tab back. This avoids the storm-on-resume because `attempts` only increments when an actual `WebSocket` is constructed. Phoenix and centrifuge-js do not implement this; ably-js explicitly does (their "suspended" state aligned with app-background events on mobile). For your two-channel notifications UI it's correct: a hidden tab does not need real-time updates.

**Should the counter reset on `pageshow`?** Only on `event.persisted === true` (BFCache restore — fundamentally a new lifetime). On a regular `pageshow` from cold load, the channel is brand-new anyway. The current code ostensibly resets the counter on a 90s timer because of latent fear of these scenarios; replacing it with `pageshow.persisted` and `online` events is the correct surgical fix.

### 6. Testing surface — minimalist setup

**Recommendation: jest-websocket-mock (mock-socket under the hood) for unit tests of the state machine; Playwright `page.routeWebSocket()` for end-to-end behavioral tests.**

`jest-websocket-mock` strengths: zero-config global `WebSocket` polyfill via `mock-socket`, custom matchers `.toReceiveMessage` / `.toHaveReceivedMessages`, runs in jsdom. Weakness: incompatible with `jest.useFakeTimers()` (the mock-socket relies on real `setTimeout`s internally), which is exactly what you'd want for testing exponential backoff timing. Workaround: use real timers with short BASE_MS for tests.

Playwright `page.routeWebSocket()` strengths (added 1.48, October 2024, stable through 1.50+): full request/response interception including selectively *not* connecting to the upstream (perfect for simulating "renderer-side resource exhaustion"). Weakness: only WS, not native browser events like `visibilitychange` (use `page.emulateMedia` and `evaluate()` to dispatch).

Cypress's `cy.intercept` does **not** support WebSocket frames — only the upgrade HTTP request. Unsuitable for this test surface.

### 7. Additional consensus topics

**Circuit breaker shape (closed/open/half-open vs simple max-attempt cap).** Hystrix's three-state model is appropriate for *server* fault tolerance because the server has many concurrent flows that benefit from probing while keeping most calls blocked. For a browser WebSocket with a single user-facing channel, half-open is degenerate: there is no "throttled trickle" mode — you either open the socket or you don't. The right shape is **two-state circuit (closed/open) plus a manual-retry button as the user-driven half-open probe.** This is what ably-js's `suspended` state effectively is, and what your Solution A already proposes. Approve.

**Per-channel vs per-server circuit.** Production multi-channel libraries split at the *transport* level: Phoenix Channels has *one* transport socket and N channel state machines on top; signalr similarly. Centrifuge multiplexes channels over one connection. **Your architecture (two raw browser WebSockets) is the unusual one.** Given that constraint, per-channel circuits are correct: a queue-channel auth failure (e.g. RBAC) shouldn't take down the audio-channel, and vice versa. Industry would say "fix the architecture" (single multiplexed socket); given you don't want to, per-channel is right.

**Threshold values for max attempts.** signalr defaults to 4 (gives up in ~42s). Phoenix never gives up but caps at 5s — net behavior is "retries forever, indistinguishable from `MAX_ATTEMPTS=∞` for any user scenario". Socket.IO defaults to `Infinity`. ably-js gives up never but exposes `suspended` for the user. **The mature pattern is: never give up *automatically* on transport reconnect, but gate the retries with a circuit that requires user re-engagement after a budget is spent.** Your 20-attempt cap fits that — but pair it with a banner + manual-retry button (Solution A already does), because a user who is staring at "Disconnected" for 6 minutes will hit reload anyway, which negates BFCache and creates more load.

**`WebSocket` cleanup to release renderer slots.** Definitive cleanup recipe: `removeEventListener` on each handler (or set the four `on*` properties to `null`); `close(1000, 'cleanup')`; null the reference. Don't rely on GC. The `AbortSignal`/AbortController integration does *not* exist for the legacy `WebSocket` constructor — that's a `WebSocketStream` feature only.

**WebSocketStream.** Chromium-only, shipped behind the API in Chrome 124+ (chromestatus 5189728691290112; `'WebSocketStream' in window` to feature-detect). It accepts `signal: AbortSignal` and exposes backpressure through `ReadableStream`/`WritableStream`. It does *not* change the 255-pending-handshake cap — that's enforced at the URLRequest layer common to both APIs. It's worth using for high-throughput ingestion (your audio channel?) but not for the queue channel.

**Service Worker as connection broker.** Since Chrome 116 you can keep a WS open from a Service Worker (developer.chrome.com/docs/extensions/.../websockets), but only with regular keepalive sends within the 30s SW idle window. For a normal web page (not an extension) this is awkward and brittle: the SW lifecycle is even more aggressive than the page, and posting messages back to the page adds a round-trip. **Not recommended as a primary channel.**

**SharedWorker for cross-tab WS sharing.** Real benefit (single connection across N tabs reduces server load and avoids any per-tab pool issues), real cost: Safari support is intermittent (works in 16.4+, but spotty), no DOM access (debugging painful), browsers may terminate idle SharedWorkers. The mature alternative is "leader election via BroadcastChannel + localStorage" (cyberangles best-practice writeup), which works in all browsers but is bespoke. **For your two-channel notifications use case, SharedWorker is overkill and adds debug surface.** Recommend deferring.

**Server-Sent Events as fallback.** SSE has built-in reconnect (`Last-Event-ID` header replay) and uses regular HTTP, so it gets the higher per-host concurrency budget. But it's unidirectional (server→client only); you'd lose `sys_ping` and any client→server commands. Reasonable as a *degraded mode* if WS is permanently blocked (corporate proxies), not as primary.

### 8. Anti-patterns confirmed by consensus

| Anti-pattern | Confirmed by | Severity |
|---|---|---|
| Resetting counter on a wall-clock timer | The bug being debugged; absent from every library reviewed | **Critical** |
| Reconnecting from `onerror` AND `onclose` | RFC 6455 §7.1.4 (error always precedes close) | High |
| No jitter against shared backend (thundering herd on deploy/restart) | AWS Builders' Library; Brooker 2015; AWS IoT Device Advisor test cases | High |
| `new WebSocket()` while a prior instance is `CONNECTING` | Chromium throttler 255-pending cap | **Critical** for your bug |
| Reconnect attempts firing while tab hidden, then storming on resume | Chrome 88+ intensive throttling; supabase realtime issue #121 | Medium |
| Not closing WS on `pagehide` (ineligible for BFCache) | web.dev/articles/bfcache; socket.io issue #5232 | Medium |
| Ignoring `bufferedAmount` backpressure | RFC 6455 §6.1; MDN; tests.ws documentation | Medium |
| Resetting counter on `open` rather than `auth_success` | Solution A correctly avoids this; ably auth-token issue #232 documents the failure mode | High |
| Synchronous tight loop of `new WebSocket()` | Renderer per-process throttler delay function will simply queue them all | Critical |
| Unbounded automatic retries with no user surface | Net effect equivalent to giving up silently from user's POV; ably/signalr all surface state | Medium |

## Recommendations

### Validate Solution A with three refinements

**Approve as-is:**

1. ✅ Per-channel circuit breaker (queue and audio independent).
2. ✅ `MAX_ATTEMPTS=20` ceiling.
3. ✅ Reset counter on `auth_success` (application-level) not on TCP `open`.
4. ✅ UI banner with manual-retry button when circuit is open.
5. ✅ Single `connectionRetries` counter conceptually replaced with per-channel state.

**Refine before merge:**

1. **Replace the curve `2,4,8,16,30,60×N` with full-jitter exponential, base=500ms cap=30s.** This drops the discontinuities, prevents thundering herd, and gives ~6–10 min total budget at 20 attempts (vs 16 min on the fixed curve). Exact code in §3 above.
2. **Delete the periodic counter-zeroing health monitor.** Replace with the watchdog pattern in §4: it only fires `scheduleReconnect()` when `readyState === CLOSED` AND no reconnect is currently scheduled, and it never touches the attempt counter. Keep the 30s `sys_ping` send while in `OPEN` state for half-open TCP detection.
3. **Add the `readyState`-guard before `new WebSocket()`.** This is the single line that prevents you from refilling the 255-pending pool when uvicorn is slow-rejecting handshakes. Without it, the circuit breaker can still catastrophically fail because `MAX_ATTEMPTS=20` per channel × 2 channels × any tab opening more tabs of the same app = renderer cap exhausted before the breakers have a chance to open.

**Add (out of scope for Solution A but tightly coupled):**

4. **Page Lifecycle integration** per §5: pause connect attempts while hidden, hard-close on `pagehide`, manual-retry on `pageshow.persisted` and on `online`.
5. **Fail-fast heuristic on rapid 1006-with-`!wasEverOpen`** (3 within 5s opens circuit immediately, irrespective of MAX_ATTEMPTS). This is the protective layer specifically against your tunnel-FD-exhaustion failure mode.
6. **Server-side**: set `uvicorn --ws-ping-interval=20 --ws-ping-timeout=20` and ensure your auth handshake completes within ≤2s of `open` or close with an explicit application close code (e.g., 4001 "auth failed"). This lets the client distinguish auth failures from network failures via `CloseEvent.code` instead of relying on the 1006 heuristic.

### Thresholds that should change the recommendation

- If you observe `attempts` reaching 20 routinely in production telemetry (>1% of sessions), drop to 10 and surface the banner faster — at that point the user is better served by a clear "reconnect" affordance than by automated retries.
- If your audio channel ever needs to send >100 KB/s, migrate it to `WebSocketStream` (feature-detected with classic `WebSocket` fallback) so you can apply real backpressure and avoid the `bufferedAmount`-polling anti-pattern.
- If you see the renderer cap hit *despite* the `readyState` guard (e.g., a third-party script in your page is opening WS), introduce a SharedWorker broker — but only then, because the debug cost is significant.

### Out-of-scope but flagged

- The architecture of two parallel raw browser WebSockets per page is the deeper issue. Phoenix, signalr, ably, and centrifuge all multiplex channels over one transport for exactly this reason — fewer connections, smaller cap exposure, simpler reconnect (one state machine), simpler auth (one handshake). If you ever revisit the protocol, multiplex `/ws/queue` and `/ws/audio` over a single `/ws` with channel-namespaced messages. Do not block Solution A on this.

## Caveats

- The Chromium throttler source (`websocket_throttler.h`) is canonical, but the relationship between *pending handshake count* and the `Insufficient resources` symptom is documented largely by example (issue #15895, gorilla/websocket #477) rather than by a single Chrome bug describing the user-visible symptom; the connection between them is inferred from the source code constant `kMaxPendingWebSocketConnections = 255` matching the empirical "after 255 connections" observation across multiple bug reports. The inference is robust, but treat it as engineering deduction rather than as a Chromium-team statement.
- `WebSocketStream` is Chrome-only (since 124, stable). Deno has interest, no Firefox/Safari intent-to-implement at the time of this writing. Treat as progressive enhancement.
- Phoenix Channels' `[10, 50, 100, 150, ...]` curve is from `assets/js/phoenix.js` v1.4 source as observed in the search; the v1.7+ source preserves the same defaults but allows override via `reconnectAfterMs`. The values quoted are defaults.
- Marc Brooker's article and the AWS Builders' Library piece are 2015–2019 vintage; the algorithms themselves are well-replicated, but Brooker's own 2024 follow-ups note that the work-vs-time tradeoff between full and decorrelated is workload-dependent. For a single-server, single-user reconnect (your case) the tradeoff is degenerate and full jitter is preferable for its simpler invariants.
- The `bufferedAmount` heuristic for backpressure is widely used but not bulletproof — Cloudflare Workers and `ws` (Node) have had implementation gaps. In the browser it's reliable.
- The "fail-fast on 3 rapid 1006s" heuristic is a synthesized recommendation drawing from Twilio's 1006/1015 fallback logic and the websocket.org error-handling guide, not a single canonical citation. Tune the 3-in-5s threshold based on your observed failure rate in healthy operation.
- Behavior under bfcache is browser-divergent: Chrome and Firefox close open WebSockets when entering bfcache; Safari is more permissive. The pattern of closing on `pagehide` is correct for all three.
- Chrome's intensive `setTimeout` throttling kicks in after 5 minutes of a tab being hidden+silent; the exact threshold has shifted across Chrome versions (88, 96, 110+) and is documented as "approximate" by Google. Treat 5min as a planning number, not a contract.
