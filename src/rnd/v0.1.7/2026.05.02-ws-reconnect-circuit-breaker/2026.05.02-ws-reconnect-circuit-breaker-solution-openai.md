# WebSocket Reconnect and Circuit Breaker Consensus Report

## Executive conclusion

The recommended fix is **bounded reconnect with jitter, per-connection state, explicit health/heartbeat, and a circuit breaker/manual recovery path**.

The current implementation is close to a classic failure mode: an optimistic reconnect loop that works fine during transient outages but becomes pathological during sustained local transport failure.

The production-grade version to ship is:

1. **Per-channel reconnect state**, not one shared `connectionRetries`.
2. **Single reconnect owner per channel**, not both `onclose` and health monitor scheduling independently.
3. **Exponential backoff with jitter**, capped.
4. **Circuit breaker after bounded attempts**, with a visible “Retry now” action.
5. **Reset only after authenticated success**, not after TCP `open`.
6. **Explicit stale-socket cleanup**: remove handlers, close if needed, set old socket reference to `null`.
7. **Application-level browser heartbeat**, because browser JavaScript cannot send protocol ping frames.
8. **Health monitor should observe and escalate**, not reset counters or create a second reconnect loop.

The attached brief identifies the core problem: the existing reconnect strategy has no max-attempt cap, a shared counter, and a health monitor that resets the counter and independently calls `scheduleReconnect`, which can hide cumulative failure state and create racing reconnect paths. The current source confirms those mechanics: the health monitor checks both sockets every 90 seconds and resets `connectionRetries` before calling `scheduleReconnect`, while `scheduleReconnect` increments a shared counter and schedules another `connectWebSockets()` with no upper bound.

## What the broader consensus says

### 1. Reconnects should be bounded and jittered

The AWS retry/backoff literature is still the best-cited consensus anchor here: exponential backoff is standard, but backoff alone is not enough; **jitter is what prevents synchronized retry spikes and repeated contention**. AWS explicitly says exponential backoff with jitter remains a pillar of how its SDKs implement resilient remote calls.

For this client, the current deterministic sequence:

```text
2s, 4s, 8s, 16s, 30s, 60s, 60s, 60s, ...
```

should become something closer to **decorrelated jitter** or capped full jitter:

```js
delay = random(0, min(cap, base * 2 ** retries));
```

or decorrelated:

```js
delay = min(cap, random(base, previousDelay * 3));
```

For a single-user dev UI, deterministic backoff is not catastrophic by itself. But it is still a bad habit, and it becomes more relevant once multiple tabs, reloads, or clients are involved.

### 2. WebSocket closure is normal, not exceptional

Browser WebSocket client guidance treats disconnect handling as a normal part of WebSocket programming, including `open`, `message`, `error`, and `close` handlers. The API also starts connecting immediately when `new WebSocket(url)` is constructed, which matters because repeated construction is itself a resource allocation path.

The current code creates new native `WebSocket` objects in `connectQueueWebSocket()` and `connectAudioWebSocket()` and unconditionally schedules reconnect on `onclose`. That is a common pattern, but incomplete unless it is bounded, deduped, and cleaned up.

### 3. Heartbeats are necessary, but browser clients need app-level heartbeats

Server libraries can use protocol-level Ping/Pong. For example, Python `websockets` documents a default ping interval and pong timeout, and describes ping/pong as serving keepalive, heartbeat, and latency measurement purposes. HTTP/1.1 infrastructure commonly closes idle connections after tens of seconds to a couple of minutes, and proxies may kill idle WebSockets prematurely.

Browser JavaScript cannot directly send WebSocket protocol ping frames, so the browser side needs an application-level `sys_ping`/`sys_pong` or equivalent. The existing code/brief already appears to have `sys_ping` semantics, which is good. The missing piece is that heartbeat failure should feed a **per-channel connection state machine**, not merely trigger ad hoc reconnect from multiple places.

### 4. `navigator.onLine` is useful only as a hint

Do not rely on `navigator.onLine` as a hard gate. Browser and OS heuristics differ; LAN connectivity may count as “online” even without Internet; VPN/firewall behavior can mislead; and the property is inherently unreliable for determining site availability.

Still, `online`/`offline` events are useful to suppress obviously futile retries while offline and to trigger a manual/low-budget retry when the browser comes back online.

### 5. BFCache/page lifecycle makes reconnect logic more important

There is active standards/browser discussion around active WebSockets and the back/forward cache. Proposed behavior is for user agents to automatically disconnect active WebSockets when a page enters BFCache, relying on `onclose` to trigger existing reconnection logic when restored. Apps that cannot handle this are likely already broken for device suspension and network switching.

This supports the same conclusion: **do not special-case every browser lifecycle event first. Build correct reconnect semantics, then optionally add `pagehide`, `pageshow`, and `visibilitychange` as policy inputs.**

## Specific critique of the current implementation

### Problem 1: shared retry counter across queue/audio

The source has `queueWS` and `audioWS`, but a shared `connectionRetries`. A queue connection can be healthy while audio is failing, or vice versa. Shared state causes false coupling and makes diagnostics misleading.

Prefer:

```js
this.wsState = {
  queue: {
    ws: null,
    retries: 0,
    timer: null,
    circuitOpen: false,
    connecting: false,
    lastAuthSuccessAt: null
  },
  audio: {
    ws: null,
    retries: 0,
    timer: null,
    circuitOpen: false,
    connecting: false,
    lastAuthSuccessAt: null
  }
};
```

### Problem 2: the health monitor resets the retry counter

This pattern is architecturally wrong:

```js
this.connectionRetries = 0;
```

The health monitor should not create a “fresh start” merely because time passed. Fresh start should mean **the socket completed the semantic session**, which in this app is `auth_success`, not TCP open.

Correct rule:

```text
retries = 0 only after auth_success for that channel
```

Not after:

```text
new WebSocket()
onopen
health monitor tick
online event
manual retry scheduled
```

Manual retry can reset state, but only because the user explicitly asked to try again.

### Problem 3: `onclose` and health monitor are both reconnect schedulers

The close handler should be the primary event-driven reconnect trigger. The health monitor should be a watchdog that says:

```text
“Socket appears stale and no reconnect is already scheduled; ask the channel state machine to reconcile.”
```

It should not directly reset state or compete with `onclose`.

### Problem 4: no max attempt budget

The current `scheduleReconnect()` increments and schedules forever.

That is not acceptable for browser-native WebSocket loops. The browser is not just a stateless retry caller; each `new WebSocket()` goes through renderer/network-service allocation paths. Even if Chromium eventually collects resources, the operational symptom observed — `Insufficient resources` until tab death — is consistent with the client digging itself into a renderer-local resource hole.

Use two thresholds:

```js
MAX_RECONNECT_ATTEMPTS = 20;
RAPID_FAILURE_COUNT = 5;
RAPID_FAILURE_WINDOW_MS = 30_000;
```

Trip if either condition fires.

### Problem 5: old sockets are not explicitly released

When a connection fails, clean up old sockets before replacing them:

```js
cleanupSocket(channel) {
  const state = this.wsState[channel];
  const ws = state.ws;
  if (!ws) return;

  ws.onopen = null;
  ws.onmessage = null;
  ws.onerror = null;
  ws.onclose = null;

  try {
    if (ws.readyState === WebSocket.CONNECTING || ws.readyState === WebSocket.OPEN) {
      ws.close(1000, "client cleanup");
    }
  } catch (_) {}

  state.ws = null;
}
```

This does not guarantee immediate Chromium slot reclamation, but it removes JavaScript references and event closures so garbage collection has a path.

## Recommended design

### State machine

Use one state machine per logical channel:

```text
DISCONNECTED
CONNECTING
AUTHENTICATING
CONNECTED
BACKING_OFF
CIRCUIT_OPEN
```

Transitions:

```text
DISCONNECTED -> CONNECTING               connect requested
CONNECTING -> AUTHENTICATING             native onopen
AUTHENTICATING -> CONNECTED              auth_success
CONNECTING/AUTHENTICATING -> BACKING_OFF onerror/onclose/timeout
CONNECTED -> BACKING_OFF                 close, heartbeat timeout
BACKING_OFF -> CONNECTING                timer fires
BACKING_OFF -> CIRCUIT_OPEN              retry budget exhausted
CIRCUIT_OPEN -> CONNECTING               user clicks Retry now
```

### Reconnect function sketch

```js
scheduleReconnect(channel, reason = "unknown") {
  const s = this.wsState[channel];

  if (s.circuitOpen) return;
  if (s.connecting) return;
  if (s.timer) return;

  s.retries += 1;
  s.failureTimestamps.push(Date.now());
  s.failureTimestamps = s.failureTimestamps.filter(
    t => Date.now() - t <= this.RAPID_FAILURE_WINDOW_MS
  );

  const rapidFailure =
    s.failureTimestamps.length >= this.RAPID_FAILURE_COUNT;

  if (s.retries >= this.MAX_RECONNECT_ATTEMPTS || rapidFailure) {
    this.openCircuit(channel, reason, { rapidFailure });
    return;
  }

  const delay = this.computeReconnectDelayMs(s.retries);
  s.status = "BACKING_OFF";

  s.timer = setTimeout(() => {
    s.timer = null;
    this.connectChannel(channel);
  }, delay);

  this.wsDiag(
    `[${channel}] reconnect #${s.retries} in ${delay}ms reason=${reason}`
  );
}
```

### Jitter

```js
computeReconnectDelayMs(retries) {
  const base = this.RECONNECT_BACKOFF_FLOOR_MS; // 2000
  const cap = this.RECONNECT_BACKOFF_CEIL_MS;   // 60000
  const exp = Math.min(cap, base * Math.pow(2, retries - 1));

  // Full jitter: [base, exp], preserving a floor.
  return Math.floor(base + Math.random() * Math.max(0, exp - base));
}
```

For reconnect UX, prefer a floor of roughly one to two seconds. Zero-delay jitter is fine for machine clients; for browser UIs it can create flickery logs and noisy user feedback.

### Auth success reset

The reset point should be in the channel-specific auth-success handler:

```js
onChannelAuthSuccess(channel, envelope) {
  const s = this.wsState[channel];

  s.retries = 0;
  s.failureTimestamps = [];
  s.circuitOpen = false;
  s.connecting = false;
  s.lastAuthSuccessAt = Date.now();
  s.status = "CONNECTED";

  if (s.timer) {
    clearTimeout(s.timer);
    s.timer = null;
  }

  this.updateStatus(`${channel}-ws-status`, "Connected", "good");
}
```

### Health monitor rewrite

The health monitor should become:

```js
checkWebSocketHealth() {
  for (const channel of ["queue", "audio"]) {
    const s = this.wsState[channel];

    if (s.circuitOpen) continue;
    if (s.connecting || s.timer) continue;

    const ws = s.ws;
    const notOpen = !ws || ws.readyState !== WebSocket.OPEN;
    const heartbeatStale = this.isHeartbeatStale(channel);

    if (notOpen || heartbeatStale) {
      this.scheduleReconnect(
        channel,
        notOpen ? "health:not_open" : "health:heartbeat_stale"
      );
    }
  }
}
```

No retry reset. No parallel reconnect path. No attempt to reconnect channels that are already scheduled or circuit-open.

### Manual retry

Manual retry should do the “big hammer” cleanup:

```js
retryWebSocketsNow() {
  for (const channel of ["queue", "audio"]) {
    const s = this.wsState[channel];

    if (s.timer) {
      clearTimeout(s.timer);
      s.timer = null;
    }

    this.cleanupSocket(channel);

    s.retries = 0;
    s.failureTimestamps = [];
    s.circuitOpen = false;
    s.connecting = false;
    s.status = "DISCONNECTED";
  }

  this.connectChannel("queue");
  this.connectChannel("audio");
}
```

Recommended banner text:

```text
Connection lost — server unreachable after repeated attempts.
Check the SSH tunnel / network, then Retry now.
```

For development builds, mention the tunnel explicitly:

```text
Connection lost. If using ssh -L, check whether the tunnel is still alive or has hit “Too many open files”.
```

## Answers to the brief’s open questions

### 1. Is the Chromium ~255 WebSocket cap real?

Treat it as operationally real enough even if the exact number is version-dependent. There may not be a stable authoritative browser promise for the exact per-tab cap, but the browser-visible `Insufficient resources` transition is sufficient evidence that the renderer/network stack hit an allocation limit in the incident.

The robust engineering answer is: **never design a browser reconnect loop that can allocate unbounded WebSocket objects during a sustained outage.**

### 2. Can JavaScript distinguish TCP reset vs server refusal vs renderer exhaustion?

Not robustly. Browser WebSocket error events intentionally expose little detail. `CloseEvent.code` helps after close, but `1006` is the generic abnormal-closure bucket. Symptom-string heuristics are useful diagnostically in Chrome DevTools, but not something to build production logic around.

Use behavioral signals:

```text
consecutive failures
time since last auth success
close code
heartbeat timeout
navigator.onLine hint
page visibility/lifecycle hint
```

Not raw socket errno.

### 3. Better backoff curve?

Use capped exponential backoff with jitter. The exact curve matters less than these constraints:

```text
floor >= 1–2s
cap <= 30–60s for interactive UI
max attempts finite
jitter enabled
manual retry available
```

The existing 60-second cap is reasonable. The missing pieces are jitter and finite budget.

### 4. Should both close handler and health monitor schedule?

No. The clean pattern is:

```text
close/error handler: primary signal into state machine
health monitor: watchdog that calls reconcile(channel), not raw reconnect
state machine: sole owner of scheduling
```

### 5. Special-case tab suspend?

Not for v1. Make the reconnect state machine correct. Then optionally add:

```js
window.addEventListener("pageshow", e => {
  if (e.persisted) this.retryWebSocketsNow();
});

document.addEventListener("visibilitychange", () => {
  if (!document.hidden) this.checkWebSocketHealth();
});
```

The current BFCache direction in standards/browser behavior strengthens the need to rely on `onclose` and reconnect correctly.

### 6. Test strategy?

Start with **unit tests around a mock WebSocket constructor**, not Playwright first. Playwright is valuable for the final browser integration test, but the bug is mostly a state-machine bug.

Minimum tests:

```text
1. close schedules one reconnect
2. repeated close increments per-channel retries
3. queue success resets only queue retries
4. audio failure does not affect queue retries
5. health monitor does not reset retries
6. health monitor does not schedule if timer already exists
7. circuit opens after N failures
8. rapid-failure path opens circuit
9. Retry now clears timers, nulls sockets, resets counters
10. offline event suppresses or delays reconnect; online event triggers reconcile
```

For the browser integration test, use Playwright with an injected fake `WebSocket` class that can synchronously fail, asynchronously fail, hang in `CONNECTING`, or emit `open` followed by auth failure. That will reproduce the pathological “near-synchronous failure” path safely without trying to wedge Chrome for real.

## One subtle implementation note

If `scheduleReconnect()` increments before delay calculation and computes:

```js
delay = min(1000 * 2 ** retries, maxDelay);
```

then the first delay is two seconds, then four, eight, sixteen, thirty, thirty, thirty, and eventually sixty depending on when the max cap changes. So twenty attempts is in the ballpark of many minutes, but the exact duration depends on the `maxDelay` transition and whether health-monitor races are removed.

For this SSH-tunnel-heavy workflow, start with:

```text
MAX_RECONNECT_ATTEMPTS = 12 for development
MAX_RECONNECT_ATTEMPTS = 20 for production-ish long-lived UI
RAPID_FAILURE_COUNT = 5 within 30s
```

If the tunnel is gone for more than roughly several minutes, a visible banner is better than invisible thrash.

## Final recommendation

Ship this as a **connection manager refactor**, not as a three-line cap only. The three-line cap is acceptable as an emergency patch, but the real bug is architectural: retry scheduling is distributed across close handlers and health polling, with shared mutable retry state.

Best v1 patch:

```text
Per-channel state + single scheduler + jitter + circuit breaker + auth-success reset + manual retry.
```

Best v1.1 patch:

```text
Add rapid-failure breaker + explicit page lifecycle hooks + mock-WebSocket unit tests.
```

That puts the implementation in line with current WebSocket operational consensus: treat disconnects as normal, retry politely, never retry forever, and make the UI honest when the local transport layer is broken.
