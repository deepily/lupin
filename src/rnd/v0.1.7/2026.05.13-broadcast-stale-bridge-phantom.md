## TL;DR

`GET /api/commons/active-sessions` returns one MORE session than Rick has actually running. The 6th is a dead-PID bridge (`mr radio` @ PID 518880, terminated earlier today). Two staleness filters that should have pruned it both misfire:

1. **PID-liveness filter** (`session_bridge._can_trust_host_pids`) is intentionally disabled inside Docker because host PIDs are invisible from inside the container — without that disable, ALL bridges would be rejected as dead. Trade-off: zero liveness pruning when the FastAPI server reads bridges.
2. **Time-threshold filter** (`commons.py::_bridge_last_activity_epoch`) looks for fields the bridge writer doesn't populate (`last_activity_epoch` / `last_activity` / `updated_at`); the bridge actually stores `idle_detection.last_interaction_at` as an ISO string nested one level deep. Result: `None` returned for every bridge, threshold check becomes a no-op.

Both gaps existed in Phase 2 but never surfaced because the prior bug (same-user-scoping filter rejected everything) hid them.

## Hypothesis

Phase 2 designed both filters in good faith but didn't reconcile them against the actual bridge schema:

**For Filter A**: The Docker-bypass was a deliberate trade-off. The R&D rationale (`_can_trust_host_pids` docstring) acknowledges that returning False inside Docker is the lesser of two evils — better to leak some stale bridges than to reject every bridge. The implicit assumption was that **another** mechanism (Filter B + the host-side stamping) would catch staleness in Docker contexts. That mechanism never landed correctly.

**For Filter B**: The bridge schema documentation (whenever it was written) likely referenced an aspirational `last_activity_epoch` / `last_activity_iso` field that was renamed or moved into `idle_detection.last_interaction_at` during a refactor without updating the consumer.

**Why this didn't surface earlier**: The companion bug ([2026.05.13-broadcast-ui-no-active-sessions-bug.md](2026.05.13-broadcast-ui-no-active-sessions-bug.md)) rejected ALL sessions via the same-user filter. With zero sessions visible, the staleness leak in Filters A and B had no observable effect. Today's fix to the same-user filter exposed both pre-existing gaps.

## Ranked solutions

### Option 1 — Read `idle_detection.last_interaction_at` (quick + correct)

Extend `_bridge_last_activity_epoch` to parse the nested ISO field and convert to epoch seconds. Symmetrically extend `project_session_response` so the API's `last_seen_iso` field actually populates.

```python
# src/cosa/rest/routers/commons.py

def _bridge_last_activity_epoch( bridge: Dict[ str, Any ] ) -> Optional[ float ]:
    """Try numeric epoch fields first; fall back to ISO string under idle_detection."""
    for field in ( "last_activity_epoch", "last_activity", "updated_at" ):
        val = bridge.get( field )
        if isinstance( val, ( int, float ) ):
            return float( val )
    # NEW: nested ISO field actually written by set_idle_detection_field
    idle = bridge.get( "idle_detection" ) or { }
    iso  = idle.get( "last_interaction_at" )
    if isinstance( iso, str ) and iso:
        try:
            from datetime import datetime
            return datetime.fromisoformat( iso ).timestamp()
        except ValueError:
            return None
    return None
```

Mirror change in `project_session_response` so `last_seen_iso` field returns the value.

| Property | Verdict |
|---|---|
| Effort | ~15 LOC + 3-4 unit tests for the new branch + projection field |
| Unblocks Rick today | ✅ phantom mr radio (last_interaction_at = "2026-05-13T09:56:37-04:00", >2h ago) gets filtered by the 10-min threshold |
| Multi-mechanism | ✅ works inside Docker (Filter B no longer a no-op); pairs cleanly with Filter A's Docker-bypass |
| Future-proof | ✅ as long as the bridge keeps storing `idle_detection.last_interaction_at`, the filter stays correct |
| Risk | ⚠ Long-running idle sessions (e.g., a CC session you opened this morning but haven't typed into) get filtered out if their `last_interaction_at` is past threshold. Default threshold = 600s = 10 min — may be too tight for "I'm working in another window" use cases. **Recommendation: bump default to 24h or make the broadcast-specific threshold a separate INI key.** |

### Option 2 — Add a host-side stale-bridge sweeper

Add a daemon (or scheduled-once-per-hour task) that runs on the host (NOT inside Docker), iterates `~/.claude/sessions/cc-*.json`, and **deletes** files whose host PID is dead. Removes the bridges from disk, so the FastAPI server never sees them.

| Property | Verdict |

| Effort | ~30-50 LOC + a systemd timer / shell hook / built-in cron registration + tests |
| Unblocks Rick today | ⚠ once the first sweep runs |
| Multi-mechanism | ✅ canonical fix — bridges that survive on disk represent live sessions |
| Future-proof | ✅ |
| Risk | Adds a new background process / cron entry; one more thing for you to maintain |

### Option 3 — Both (recommended for robustness)

Land Option 1 as the immediate fix; file Option 2 as a follow-on enhancement. Option 1 handles the in-Docker filtering correctly today; Option 2 cleans up bridge files on disk over time so other consumers (the focus bar, session-strip, etc.) also benefit.

| Unblocks Rick today | ✅ via Option 1 |
| Defense-in-depth | ✅ Filter B + on-disk sweep — even if one path drifts, the other still catches |

## My recommendation

**Option 1 only (for now), with Option 2 filed in TODO.md.**

Rationale:
- Option 1 is small, single-file, testable, and ships today
- The 10-min default threshold needs to be reconsidered (probably bump to 1-4 hours or add a dedicated INI key) so legitimate idle sessions aren't filtered
- Option 2 is a real enhancement but its complexity (background process, file deletion) deserves its own design pass — not a same-day bolt-on
- Option 4 is a band-aid; not worth doing as the "fix" but you can run that command right now if you want the phantom gone before Option 1 lands

If you'd rather go aggressive: Option 1 + Option 4 right now (delete the stale file + land the proper filter fix). The delete is reversible (next session start re-creates a bridge with a different PID).

## Fallback / mitigations

- **Immediate cleanup**: `rm ~/.claude/sessions/cc-518880.json` — phantom disappears on next page refresh
- **Per-session courtesy**: if a CC session ends cleanly via SIGTERM, the session-end hook deletes its bridge. The phantom exists because mr radio died ungracefully (SIGKILL or crash). The session-end hook IS the design's "happy path" cleanup.
- **Operational**: Option 2's sweeper would catch this class of bug regardless of how the session died.
