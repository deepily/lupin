## 2. Three use cases enumerated (per Rick's correction mid-conversation)

| # | Use case | Recipient role | What recipient does on tick |
|---|----------|----------------|------------------------------|
| 1 | **Observer** (María's role in cascade) | Peer session outside the cascade review chain | Probes commons (`commons_who` + `commons_read` on coordination topic); DMs Manager if anything unread |
| 2 | **Manager / Facilitator** (Tiberius cascade role) | Orchestrator at the center of the cascade | Universal-step-zero disk-read on every active topic; checks each worker's last-post timestamp; advances pipeline state |
| 3 | **Watcher of implementer** (Tiberius watching Roscoe-shaped sessions) | Peer session external to the implementer | Probes implementer's commons activity; DMs implementer if dormant; requests phase-checkpoint commit at phase boundaries (cf. the existing `/plan-session-checkpoint` skill — the same mid-session-commit shape the Watcher asks the implementer to perform) |

**The structural insight** (Rick's correction at conversation turn 2 was load-bearing): all three use cases share one poker *shape* — the poker's code is invariant; it wakes `N` recipient sessions on a cadence and exits on a terminating condition (clean signal or hard cap). Variance lives in config values + recipient-side doctrine; the poker never *branches* on recipient role (it may carry `role` as opaque passthrough metadata — §4).

This set is the empirically-observed set, not an exhaustive taxonomy; the generic-poker abstraction below is what lets a new recipient role be added as a Layer-2 doctrine without touching the poker.

**Layer 1 — Generic poker** is use-case-agnostic Lupin infrastructure. ONE class, seven config params (5 required + 2 defaulted — see the class sketch above). Stays simple.

**Layer 2 — Per-recipient doctrines** are workflow-doc protocols that codify what each role does when poked. Two already exist (Observer + Manager); a NEW Watcher-mode protocol needs authoring as part of this design.

**`RecipientSpec`** (per finding F-Rio-B1): `recipients` is a list of `RecipientSpec` entries, not bare strings — a flat `List[str]` cannot carry the per-recipient `role` that §4's `poke_body` requires, nor disambiguate the identifier type. Each `RecipientSpec` names an **addressable identifier + its type** (a persona-name for `commons_send_to` routing, or a raw session-id) and the recipient's **role** (`manager` / `observer` / `watcher`). Rick's origin scenario — one poker poking "you and María" in *different* roles — confirms `role` must be per-recipient, not job-level.

**Layer-1/Layer-2 handoff prerequisite** (per finding F-Rio-B4): a poke carries `role` (a doctrine *selector*), never the doctrine *body*. The recipient session must therefore already be doctrine-loaded — cold-cast with its Layer-2 protocol in context — *before* the first poke lands, or the poke reaches a session that does not know what to do with it. Recipient cold-cast is a launch-time prerequisite of the poker run, not something the poke itself delivers.

**Agentic-pool occupancy (config dependency — analysis)** (per finding F-Rio-B3): a `HeartbeatPokerJob` is an `AgenticJobBase`, so CJ Flow dispatches it to the agentic `ThreadPoolExecutor`, where it holds ONE pool slot for its entire lifetime (up to `max_duration_seconds`, default 12h) — a held slot, not transient, even while sleeping between ticks.

*The tradeoff, stated honestly*: the legacy `cascade_heartbeat_scheduler.py` is a standalone daemon consuming **zero** CJ Flow pool slots. Moving the heartbeat into CJ Flow as an agentic job **newly introduces** pool contention that does not exist today. This is a deliberately-accepted tradeoff — Rick ratified `HeartbeatPokerJob` as an `AgenticJobBase` subclass at the F-Krishna-B1 escalation, on the grounds that the gains (todo-queue ingress, `scheduled_at`, lifecycle, cancellation, persistence) outweigh the slot cost *provided the pool is sized for it*.

*The sizing rule*: with N pokers running concurrently the agentic pool must be **≥ N+1**, so the fast-lane and other agentic jobs (Deep Research, Podcast, Presentation, BFE/TFE) are not starved. §4 contemplates N = 2 concurrent pokers → pool ≥ 3 for that case. **"3" is the N = 2 instance of the `≥ N+1` rule, not a universal floor** — more than two concurrent pokers requires a correspondingly larger pool. The prod default is `cj flow max concurrent agentic jobs = 1` (`[Lupin: Production]` inherits `[Lupin: Baseline]`), which a single long-lived poker fully saturates — so running pokers in prod carries a hard deployment prerequisite: resize the prod pool (tracked as task I10 in §6).

## 4. Decisions locked during conversation

### Q1 — Recipient state model → **Path A (one minimal poker class)**

My original framing was "stateless vs stateful poker." Rick's correction surfaced that the state-tracking I was attributing to the implementer case actually lives in the **Watcher's recipient behavior**, not the poker abstraction. The poker stays simple; per-recipient state (last-post-timestamp, phase counter, dormancy threshold) lives in the recipient's role doctrine, not in the poker's config.

**Prior-art for the Watcher's dormancy detection**: the last-post-timestamp check reuses the existing `commons_who().last_post_ts` field — no new state-tracking primitive is needed; the recipient's role doctrine simply polls it.

### Poke delivery + response detection (per finding F-Rio-C1)

§4 specifies poke *content* (`poke_body`, below) — but the delivery *call* and the response-*detection* mechanism are equally load-bearing: the ratified dead-man's-switch (Q2) triggers on "3 silent pokes … no recipient response," which is un-implementable until "response" is mechanically defined.

- **Delivery**: the poker delivers each tick via `commons_send_to(recipient=<RecipientSpec identifier>, body=<poke_body JSON>)` — the same persona-routed DM call the prototype's `fire_heartbeat` uses. (This is why `RecipientSpec` carries the identifier *type* — `commons_send_to` resolves persona-names.)
- **Detection**: a poke counts as *answered* if the recipient's `commons_who().last_post_ts` advances past that tick's send time; a poke with no such advance by the next tick counts as *silent*. This reuses the existing `commons_who` liveness surface — no new primitive (cf. Q1's dormancy-detection note).

### Q2 — Termination model → **Three layered exits, in priority order**

Inherit the proven pattern from existing `cascade_heartbeat_scheduler.py`:

| Exit | Trigger | Behavior |
|------|---------|----------|
| **Clean** | `kind: <one_of_signal_kinds>` posted to `termination_topic` **after job start** | Stop poking, exit 0, log success |
| **Dead-man's-switch** | 3 silent pokes in a row from a **given recipient** (no response) — the silent-streak counter is **per-recipient**, so one responsive recipient never masks another's silence | Fire `notify()` to user **once per silent streak** (a per-recipient `dms_fired_this_streak` flag prevents re-firing every tick past threshold); **KEEP poking** (don't auto-die — user decides); **reset that recipient's silent-streak counter and fired-flag when it revives**, so a later streak re-escalates cleanly |
| **Hard cap** | `max_duration_seconds` exceeded (default 12h) | Stop poking, exit, fire `notify()` with timeout reason |

**Key design call**: dead-man's-switch ESCALATES, doesn't terminate. Silence might just mean recipients are heads-down in tool work, not phantom.

**Clean-exit guard** (prototype-learned; mechanism per finding F-Rio-C4): only termination signals posted *after* the poker's start timestamp count — without this guard, a stale termination signal from a *prior* run still sitting in `termination_topic` triggers a false clean-exit at tick 1. **Mechanism**: capture `job_start_ts` at launch and detect via `commons_read(termination_topic, since=job_start_ts)` — timestamp-based, natively supported by the commons store, and robust to topic-retention pruning. (The prototype `cascade_heartbeat_scheduler.py` used a fragile `initial_size` byte-offset index; the abstraction adopts the timestamp form instead, which survives retention pruning that would invalidate a byte offset.)

**Per-use-case signal kinds** (config-driven, not class-baked):
- Cascade case: `["cascade_complete"]` (already in `plan-review-cascaded-defaults.md` kind enum)
- Implementer-keep-alive case: `["implementation_done", "implementation_blocked"]` — **NEW kinds** to add to defaults.md enum during implementation pass

### Concurrent-poker routing → **Two separate jobs, independent; recipient routes via `poke_body` metadata**

When Manager is simultaneously running a cascade AND watching an implementer, that's two distinct work streams. Each gets its OWN poker job. The two pokers are fully independent — no cross-coordination — each with its own lifecycle, cadence, termination signal, dead-man's-switch.

**Recipient-side options** (operator decides per scenario):

| Setup | When to use |
|---|---|
| Two separate recipient sessions | When persona pool has headroom; clean separation, no context-switching |
| Same session, two pokers | When persona pool is at ceiling; recipient uses `poke_body` JSON metadata to dispatch each tick to the right role-handler |

**Poke body shape** (JSON, recipient parses on tick):

```json
{ "kind": "heartbeat", "workstream": "<cascade-id-or-impl-id>", "role": "manager|observer|watcher" }
```

**Field provenance** (per finding F-Rio-C2): `kind` is the literal `"heartbeat"`; `role` is stamped per-recipient from that recipient's `RecipientSpec` (§3); `workstream` is sourced from the poker's `workstream_id` config param (§3). The poker stamps all three and never branches on `role` — it is opaque passthrough metadata for the recipient's own dispatch.

**Failure-mode-#6 risk** (signal-density-obscures-needle) re-emerges with concurrent ticks. Three mitigations:
1. **Stagger cadences** — choose values that are NOT integer multiples (e.g., 150s + 240s rarely collide — LCM 1200s; whereas 150s + 300s collide on *every* Poker-B tick, since 300 is an exact multiple of 150)
2. **Activate Observer-mode probe protocol** — already codified in v1.1; the parallel safety net catches what concurrent-tick density buries
3. **Recipient-side prioritization** — when ticks collide on the same session, recipient handles cascade-orchestration tick before watcher tick (orchestration-load is higher-stakes)

### Open Q — Persona-allocation strategy under concurrent work streams → **RATIFIED 2026-05-21: OUT-OF-SCOPE for the poker abstraction**

**Ratified by Rick** (session `bc15c374` interactive `ask_yes_no`, 2026-05-21).

**This is NOT a poker-abstraction question** — the poker supports any number of recipients. It's a scenario-design question: how does the operator decide which persona plays which role when work streams overlap?

**Operator-side options** (NOT baked into the poker class — governed by user + Manager judgment per scenario):

| Setup | When to use |
|---|---|
| Pre-allocate roles at scenario launch (manual) | Pool has headroom; clean role assignments up front |
| Pool-expansion (grow persona pool — already grown 6→8 in v0.1.7) | Recurring ceiling pressure across multiple scenarios |
| Same-session-two-roles pattern | Pool at ceiling; recipient context-switches per tick via `poke_body` JSON dispatch (already supported by §4 concurrent-poker routing decision) |

**Rationale for out-of-scope ratification**:

1. The poker class doesn't need to know about persona pool ceilings or role assignment — those are operator decisions
2. Same-session-two-roles is already supported by the `poke_body` JSON dispatch (§4 concurrent-poker routing)
3. Persona pool sizing is governed by the existing voice-persona allocation R&D doc (`2026.04.28-per-session-voice-personas` + `2026.05.16-voice-persona-stale-bridge-and-sam-overflow`), not this design

**No safety cap added**: rejected the option of baking a `max_concurrent_recipients` safety cap into the poker class — over-subscription is an operator failure mode best caught at scenario-design time, not by the poker's config validator.
