# Notifications UI — Two Tweaks

## Context

Two quick UX corrections to the notifications page (`src/fastapi_app/static/js/notifications.js`):

1. **Focus-bar icon collisions.** In chorus mode, all of Rick's parallel sessions are working in the Lupin repo, so the strip pills all display the letter "L" (project-initial). They become visually indistinguishable. The persona is what disambiguates voices at the ear (Tiberius, Rio, Marcus, etc.); the focus bar should mirror that.

2. **TTS barge-in during recording.** When Rick presses the mic to record a notification reply or new prompt, the TTS queue keeps playing other personas' messages. He can't speak while listening to someone else speaking. The pause/resume infrastructure already exists; it's simply not wired to the recording lifecycle.

Both targets live in `src/fastapi_app/static/js/notifications.js` — plain JS, NOT the `multiplexer/` TS code carrying the 100% c8 coverage mandate.

## Tweak 2: Pause TTS queue around voice recording

### Timing requirements

- **Pause BEFORE the mic engages** — not after `onRecordingStart` fires (which is after `getUserMedia` resolves). Pause must happen at the top of `recordingManager.startRecording`, before `new AudioRecorder(...)` is constructed.
- **Resume with a ~750ms delay AFTER recording stops** — gives a comfortable beat between Rick releasing the mic and the TTS queue re-engaging. Same delay applies on ESC-cancel.

### Existing API to leverage

- `pauseTTS()` at line 13500 (suspends Web Audio + pauses HTML Audio, sets `isTTSPaused = true`)
- `resumeTTS()` at line 13534 (mirrors above in reverse)
- `recordingManager.ui` is the notifications instance, so calls are `self.ui.pauseTTS()` / `self.ui.resumeTTS()`

### State tracked on `recordingManager`

- `_ttsPausedByRecording` (boolean) — true if WE caused the current pause; false if the user already had TTS paused before recording started.
- `_resumeTimeoutHandle` (number|null) — pending `setTimeout` handle for the delayed resume; non-null between recording-stop and resume-fire.

### Three hook points (all in `recordingManager`)

**1. `startRecording` top — `notifications.js:3418`**

Insert AFTER the existing auto-cancel-previous block (line 3422-3425) but BEFORE the token check / `new AudioRecorder(...)` construction. Order matters: auto-cancel must run first so the prior recording's `cancelRecording` schedules a resume that we then cancel here.

```js
startRecording: async function( contextId, button, inputElement, options = {} ) {
    const self = this;

    // Auto-cancel any active recording (existing — line 3422)
    if ( this.activeRecording ) {
        this.ui.log( `Auto-cancelling previous recording: ${this.activeRecording.contextId}` );
        this.cancelRecording();
    }

    // === NEW: pause TTS synchronously, before any mic engagement ===
    // Cancel any pending delayed-resume from a just-finished recording
    // so we don't get a flicker (resume → re-pause when chaining).
    if ( self._resumeTimeoutHandle ) {
        clearTimeout( self._resumeTimeoutHandle );
        self._resumeTimeoutHandle = null;
    }
    // Claim the pause (only if not already paused, manually or by us).
    if ( !self._ttsPausedByRecording ) {
        self._ttsPausedByRecording = !self.ui.isTTSPaused;
        if ( self._ttsPausedByRecording ) self.ui.pauseTTS();
    }
    // === END NEW ===

    // Get auth token (existing — line 3428)
    const token = localStorage.getItem( 'lupin_access_token' ) || this.ui.authToken;
    // ... rest unchanged ...
}
```

**2. `onRecordingStop` callback — `notifications.js:3456`**

Schedule a delayed resume instead of resuming immediately:

```js
onRecordingStop: ( audioBlob ) => {
    self.ui.log( `Recording stopped: ${contextId}, ${audioBlob.size} bytes` );
    self._stopDurationCounter();
    self._detachCancelListener();
    button.classList.remove( 'recording' );
    button.classList.add( 'processing' );
    button.textContent = '⏳';
    button.title = 'Transcribing audio...';
    button.disabled = true;

    // === NEW: schedule delayed TTS resume (750ms) ===
    self._scheduleTTSResume();
},
```

**3. `cancelRecording` — `notifications.js:3525`**

ESC-cancel does NOT fire `onRecordingStop`, so paired delayed-resume here too:

```js
cancelRecording: function() {
    if ( !this.activeRecording ) return;
    // ... existing teardown ...
    this.activeRecording = null;

    // === NEW: schedule delayed TTS resume (750ms) ===
    this._scheduleTTSResume();
},
```

### New private helper on `recordingManager`

Slot in near the other private helpers (`_startDurationCounter`, `_stopDurationCounter`, etc., around line 3558+):

```js
TTS_RESUME_DELAY_MS: 750,

_scheduleTTSResume: function() {
    const self = this;
    // No-op if we never paused TTS this round.
    if ( !self._ttsPausedByRecording ) return;
    // Replace any pending resume (defensive — shouldn't happen, but harmless).
    if ( self._resumeTimeoutHandle ) clearTimeout( self._resumeTimeoutHandle );
    self._resumeTimeoutHandle = setTimeout( () => {
        self.ui.resumeTTS();
        self._ttsPausedByRecording = false;
        self._resumeTimeoutHandle  = null;
    }, self.TTS_RESUME_DELAY_MS );
},
```

### Behavior across recording lifecycle

| Event | TTS state | `_ttsPausedByRecording` | `_resumeTimeoutHandle` |
|---|---|---|---|
| First mic-press | paused (synchronous) | true | null |
| `onRecordingStop` | still paused | true | T1 scheduled (750ms) |
| 750ms later, T1 fires | resumed | false | null |
| ESC cancel | still paused | true | T1 scheduled (750ms) |
| User chains a new recording mid-delay | still paused (T1 cleared, no re-pause) | true | null |
| User had TTS manually paused before mic-press | paused (untouched) | false | null |
| `onRecordingStop` after user-paused case | paused (still — `_scheduleTTSResume` no-ops) | false | null |

### Design decisions

- **Pause is synchronous, before mic** — meets Rick's "pause before recording starts" requirement. `getUserMedia` permission prompts can take 100ms+ in some browsers; pausing first ensures silence during that window too.
- **750ms resume delay** — middle of Rick's "half a second to a second" range. Lives as the `TTS_RESUME_DELAY_MS` constant on `recordingManager` for easy tuning.
- **State-preserving**: We track `_ttsPausedByRecording` so a manually-paused TTS stays paused after recording. We never auto-resume something the user paused themselves.
- **Unconditional (not chorus-gated)**: `pauseTTS()` early-returns when nothing's playing (line 13501), so the cost in solo/phone mode is a no-op. In solo, pausing your own session's TTS during recording is also desirable (no self-barge). Gating by `tts_interaction_mode` would require exposing that flag to the client (server-side only today). If Rick prefers strict chorus-gating, easy follow-up.
- **Chain-recording flicker prevented**: starting a new recording within the 750ms resume window clears the pending timeout and skips re-pausing (TTS was never resumed). No audible blip.

### Barge-in fix (added during testing, 2026-05-13)

The original plan called out queue-advance as a known limitation. Live testing confirmed it: with mic engaged at T-0 of a 15-second countdown and a fresh TTS arriving while recording, the new arrival barged through. Root cause: `pauseTTS()` early-returns when nothing is currently playing (line 13501), leaving `isTTSPaused` false — `activateNextTTS` (line 12950) then sees an open gate and lets new arrivals play.

Two-edit fix:

1. **`startRecording` (~L3447)** — after `pauseTTS()`, force `self.ui.isTTSPaused = true`. Closes the gate even when no item was playing at pause-time.
2. **`_scheduleTTSResume` (~L3613)** — after `resumeTTS()`, if `activeTTSItem` is null but `ttsQueue.length > 0`, manually call `activateNextTTS()` to drain messages that accumulated during recording. Without this kick, the queue stalls.

**Verified live (2026-05-13)**: Rick confirmed "I'm preventing auto TTS for incoming notifications while I'm recording — wonderful thing, you've fixed barge-in for me."
