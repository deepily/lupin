# Driver upgrade plan: 535 → R580 LTS (and a faster fix you should consider first)

**Bottom line up front.** Two things in the original brief are wrong, and they change the recommendation materially. **First, R550 is not an LTS branch.** NVIDIA's official lifecycle table lists only R535 (LTSB, EOL June 2026) and **R580 (LTSB, EOL August 2028)** as long-term branches; R550 was a Production Branch whose terminal release `550.163.01` shipped 18 April 2025 and receives no further updates, and Canonical has been transitioning the `nvidia-driver-550` metapackage on jammy to point at 580 since LP #2125411 (Sept 2025). The right "newer than 535 with a real support runway" target is **R580 LTS**, not R550. **Second, the Error 804 problem is fixable without touching the host driver at all** — strip `cuda-compat-12-4` out of the `lupin:1.0.0` image (or rebuild on `ubuntu:22.04`) and PyTorch's cu124 wheel runs cleanly on the existing 535.104.05 driver via Minor Version Compatibility, because MVC is unrestricted by GPU class while Forward Compatibility (the thing currently blowing up) is restricted to data-center SKUs. You should do that fix first, validate it, and then upgrade the host driver to R580 LTS as a deliberate, separately-rollback-able operation. The rest of this document covers both paths in depth.

The user's specific stack — dual RTX 4090 (Ada AD102, sm_89, no PCIe P2P, no NVSwitch), Ubuntu 22.04 GA kernel from May 2022, headless ML server, nvidia-container-toolkit, no host CUDA toolkit — admits a clean apt-managed upgrade with full rollback. The interesting decisions are *which* branch (R580 LTS, recommended), *which kernel module flavor* (open, recommended for Ada), *which install source* (Ubuntu's `restricted` archive, recommended), and whether to bump the kernel to HWE 6.8 simultaneously (yes, in the same apt transaction). Below I work through each in detail with concrete commands, then the procedure, then rollback, then the four open questions from the handoff.

## Path A: don't upgrade the driver yet — fix the image

The 804 error is mechanically well understood. The `nvidia/cuda:12.4.1-base-ubuntu22.04` base image apt-installs `cuda-compat-12-4`, which drops a userspace `libcuda.so.1` (R550-class) under `/usr/local/cuda-12.4/compat/`. At container start, libnvidia-container's mount logic and the image's own `LD_LIBRARY_PATH`/`ldconfig` cache cause that compat libcuda to shadow the host's R535 libcuda that nvidia-container-toolkit injects at `/usr/lib/x86_64-linux-gnu/libcuda.so.1`. Inside `cuInit()` the compat driver detects forward-compat-upgrade mode, queries the GPU class, and returns `CUDA_ERROR_COMPAT_NOT_SUPPORTED_ON_DEVICE` (804) because **Forward Compatibility is restricted to NVIDIA Data Center GPUs, select NGC-Server-Ready RTX SKUs, and Jetson** (verbatim from the [CUDA Compatibility Guide §Forward Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/forward-compatibility.html)). RTX 4090 is consumer GeForce — none of those buckets apply.

Crucially, **Minor Version Compatibility is a different mechanism with no GPU-class restriction**. Per [§Minor Version Compatibility, Table 1](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html), CUDA 12.x toolkits run on any driver `>= 525`. Driver 535.104.05 ≥ 525, so the cu124 cudart and the bundled `nvidia-*-cu12` userspace libraries (cuBLAS, cuDNN 9.1, NCCL, cuFFT) will load and run on RTX 4090 + driver 535 the moment the compat shim is out of the way. PyTorch's CUDA dlopen chain only needs **the host's `libcuda.so.1` (driver-paired) plus the wheel's bundled cudart**; nothing else. flash-attn 2.8.3 is wheel-compiled against torch 2.6.0+cu124's ABI and uses the same userspace libcuda — it inherits MVC for free.

The minimal fix to `lupin:1.0.0`:

```dockerfile
# Right after FROM nvidia/cuda:12.4.1-base-ubuntu22.04
RUN apt-get update && apt-get purge -y cuda-compat-12-4 && \
    rm -rf /usr/local/cuda-12.4/compat /usr/local/cuda/compat && \
    ldconfig
```

The cleaner fix is to **abandon the `nvidia/cuda` base image entirely**. The cu124 PyTorch wheel ships its own cuBLAS, cuDNN, cuFFT, NCCL, and cudart via the `nvidia-*-cu12` PyPI wheels; the only thing you need from the host is `libcuda.so.1`, which nvidia-container-toolkit injects automatically given `NVIDIA_VISIBLE_DEVICES=all` and `NVIDIA_DRIVER_CAPABILITIES=compute,utility`. Rebuild on `ubuntu:22.04` or `python:3.11-slim`, install Python via uv, `uv sync --frozen`, done. No cuda-toolkit, no cuda-compat, no 804, no host-driver dependency for CUDA 12.x. This is the recommended modern pattern and is what the [nvidia-container-toolkit#1084](https://github.com/NVIDIA/nvidia-container-toolkit/issues/1084) and [NIM CUDA driver troubleshooting](https://docs.nvidia.com/nim/large-language-models/2.0.2/troubleshooting/cuda-driver.html) docs converge on. There is **no documented env var** (`__NV_DISABLE_COMPAT`, `CUDA_FORCE_PTX_JIT`, etc.) that suppresses the compat path; `NVIDIA_DISABLE_REQUIRE` only disables libnvidia-container's pre-flight version check, not the in-process cuInit path; `LD_LIBRARY_PATH` overrides are unreliable when libnvidia-container has already bind-mounted the compat library read-only ([toolkit#125](https://github.com/NVIDIA/nvidia-container-toolkit/issues/125)). Removing the package is the only robust answer.

You should still upgrade the host driver — 535 LTSB hits EOL in June 2026, the Jammy GA kernel from May 2022 is two years of CVEs behind, and CUDA 12.4-native support is genuinely useful for future containers — but **decoupling the image fix from the driver upgrade is the right operational sequencing**. Fix the image, ship `lupin:1.0.0` to production, then take a maintenance window to do the driver work cleanly.

## Path B: the driver upgrade — what to install

### Branch landscape, April 2026

NVIDIA's [supported drivers and CUDA toolkit versions table](https://docs.nvidia.com/datacenter/tesla/drivers/supported-drivers-and-cuda-toolkit-versions.html) currently lists exactly three live branches; everything else (R515, R525, R550, R555, R560, R565, R575) is end-of-life, including the supposed "550-LTS" target.

| Branch | Designation | Latest Linux | Native CUDA | EOL | Recommendation for this user |
|---|---|---|---|---|---|
| R535 | LTSB | 535.274.02 (Sep 2025, security-only) | 12.2 | **June 2026** | Current; will need replacement in ~2 months regardless |
| R570 | Production Branch | 570.211.01 (Jan 2026) | 12.8 | February 2026 (per docs; courtesy patches continue) | Acceptable fallback if R580 packaging is still rough |
| **R580** | **LTSB** | **580.95.05** ("Recommended/Certified") or **580.126.09** | **13.x** | **August 2028** | **Recommended primary target** |
| R590, R595 | New Feature Branches | 590.48.01 / 595.58.03 | 13.x | NFB | Avoid for production ML; community-reported UE5/Wayland regressions |
| R550 | EOL | 550.163.01 (terminal, Apr 2025) | 12.4 | Already past | **Do not target as a long-lived install** |

The minimum driver for native CUDA 12.4 on Linux is **550.54.14** (per [CUDA 12.4 Release Notes Table 3](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-toolkit-release-notes/index.html)); R580 trivially satisfies this and additionally supports CUDA 12.6, 12.8, and 13.x via backward + minor-version compatibility, so the same host driver will run the user's current `lupin:1.0.0` (cu124) and any future cu126/cu128/cu13x containers without further driver work for nearly three years. **Picking 550 today means installing a dead-end branch that you will be migrating off in a year anyway** — not an LTS choice, despite the name. The only reason to deliberately install 550.163.01 is if some external constraint (fleet uniformity, a CUDA toolkit version pinned across hosts) requires it.

Known Ada-relevant regressions surveyed: R570 release notes since 570.124.06 carry a *"Disable GPU-initiated RO traffic on Ada Lovelace and older GPUs"* note about a hardware errata that can cause silent data corruption in `simpleP2P` on certain Sapphire-Rapids+ platforms; **moot on dual RTX 4090 because consumer Ada has no PCIe P2P at all** (NVIDIA disabled it at the silicon/firmware level on RTX 40-series, confirmed across PyTorch and NVIDIA forum threads). 570.148.08 had a DKMS-postinst regression on some Ubuntu setups; 570.124.06 had a `nvidia-smi tlimit` query bug. R580 (580.95.05 → 580.126.09) shows no documented Ada/PyTorch/cuDNN regressions. R590/R595 are NFBs with reported UE5 and Vulkan regressions — explicitly off-limits for production ML.

### Kernel module flavor: open, not proprietary

NVIDIA's [August 2024 policy statement](https://developer.nvidia.com/blog/nvidia-transitions-fully-towards-open-source-gpu-kernel-modules/) is explicit: *"For newer GPUs from the Turing, Ampere, Ada Lovelace, or Hopper architectures, NVIDIA recommends switching to the open-source GPU kernel modules."* By R560 the open module reached feature parity for compute on Ada; from CUDA 12.6+ the `cuda-drivers` metapackage flipped its default dependency to `nvidia-open`. **Userspace libraries (`libcuda.so`, `libcudart`, `libcudnn`, `libnccl`) are byte-identical between the two flavors** — they all ship in `libnvidia-compute-580` independent of the kernel module package. Phoronix benchmarks since R555 show no measurable performance delta. NVENC, NVDEC, CUDA, cuDNN, NCCL, GPUDirect, DRM-KMS, Vulkan, GSP firmware loading — all identical. The only reasons to still pick proprietary would be (a) Maxwell/Pascal/Volta cards in the same host, or (b) certain vGPU/SR-IOV configurations — neither applies here. Pick **`nvidia-driver-580-server-open`** (server variant for headless, `-open` for the kernel module flavor).

### Install source: Ubuntu `restricted`, not the CUDA repo, definitely not `.run`

For an apt-managed Ubuntu host, the cleanest path is the **Ubuntu `restricted` archive** (`nvidia-driver-580-server-open`), for four concrete reasons. **First**, Ubuntu ships pre-built signed kernel modules in `linux-modules-nvidia-580-server-generic-hwe-22.04`, eliminating per-kernel DKMS rebuilds — even with Secure Boot off, this is faster, more reliable, and survives `apt full-upgrade` kernel bumps without intervention. **Second**, the package metadata declares Conflicts/Replaces with previous-branch packages so that `apt install nvidia-driver-580-server-open` correctly displaces the 535 stack inside a single transaction; with the NVIDIA CUDA repo, the same package names exist in both repositories and apt selects by pin priority (the CUDA repo's `cuda-repository-pin-600` outranks Ubuntu's default 500), which silently swaps origins and surprises future upgrades. **Third**, Canonical's QA cycle catches DKMS-postinst regressions like the 570.148.08 bug before SRU promotion. **Fourth**, rollback is mechanically clean: `apt --purge remove '*nvidia*580*' && apt autoremove --purge && apt install ./nvidia-535-backup/debs/*.deb` reproduces the exact prior state, byte-for-byte if you captured the .debs first.

The NVIDIA CUDA apt repo has its place — it carries newer patch levels and the matched `cuda-compat-12-X` packages — but for *driver installation on a long-lived ML host* the Ubuntu archive wins on stability and rollback predictability. The `graphics-drivers` PPA is community-maintained without a Canonical SLA and is DKMS-only, with no signed pre-built modules. The `.run` installer from nvidia.com is **strongly contraindicated** on apt-managed systems: no apt tracking (so `apt-get download` cannot back up your current state), file-level conflicts with future apt installs of `libnvidia-*`, no clean downgrade path, and kernel upgrades silently break the module unless `--dkms` was passed. The Ubuntu Server docs explicitly warn against it.

To identify the user's current 535.104.05 install source — necessary because 535.104.05 is older than what jammy-updates currently ships (535.274.02), so it's either stale apt state, the CUDA repo, the PPA, or a `.run` install:

```bash
# Authoritative: check the version table and origins
apt-cache policy nvidia-driver-535
# Look for the "***" line and the priority+URL on the next indented line.
# Suffix interpretation:
#   X-0ubuntu0.22.04.N    → Ubuntu jammy-updates/restricted
#   X-1   or  X-0ubuntu1  → developer.download.nvidia.com (CUDA repo)
#   X-0ubuntu0~gpu22.04.N → graphics-drivers PPA

dpkg -l | grep -i nvidia
ls /etc/apt/sources.list.d/*.list /etc/apt/sources.list.d/*.sources 2>/dev/null \
    | xargs grep -lEi 'nvidia|graphics-drivers|cuda' 2>/dev/null

# Red flag for .run installer (no dpkg entry, but binary exists):
ls /usr/bin/nvidia-uninstall /usr/bin/nvidia-installer 2>/dev/null
test -f /var/log/nvidia-installer.log && echo ".run installer was used"

# Module signer (tells you who built/signed it):
modinfo nvidia | grep -E '^(version|filename|signer)'
# "Canonical Ltd. Secure Boot Signing" → Ubuntu pre-built signed module
# "Build time autogenerated kernel key" → DKMS locally built
```

If the source resolves to `.run`, **stop and uninstall via the matching `.run` first** (`sudo /usr/bin/nvidia-uninstall`); a clean apt install on top of `.run` residue is unreliable.

### Kernel: HWE 6.8, in the same apt transaction

The user's `5.15.0-33-generic` is the May 2022 GA kernel and is two-plus years of CVEs behind the current Jammy 5.15 (`5.15.0-130.140`). **This is a non-negotiable hygiene fix regardless of the driver decision.** The interesting question is whether to also adopt HWE.

The 22.04 HWE stack (`linux-generic-hwe-22.04`) is on the **6.8 series** as of April 2026 — `linux-image-6.8.0-107-generic 6.8.0-107.107~22.04.1` is current in jammy-updates, with the metapackage at `6.8.0.107.107~22.04.20`. NVIDIA's R570 release notes explicitly qualify *"Ubuntu 22.04 with NVIDIA HWE kernel"* for HGX H100/H200/B200 — bare 22.04 GA is not on the validated matrix for newer driver branches. R580 builds cleanly on both 5.15 and 6.8. The 6.8 kernel brings better cgroup v2, io_uring, NVMe, and IOMMU behavior — all relevant to multi-GPU container hosts. **Recommended: move to HWE 6.8 in the same apt transaction as the driver upgrade.**

Critical sequencing: **do not reboot into 6.8 while still running driver 535** — 535's DKMS does not build cleanly above ~kernel 6.5, you will boot to a black console with no GPU. Combine kernel and driver into one `apt install` so DKMS rebuilds (or signed-module installation) targets 6.8 directly, then reboot once.

### nvidia-container-toolkit: bump to 1.19.0 and adopt CDI

The current stable as of April 2026 is **nvidia-container-toolkit v1.19.0** (March 2026). The toolkit's only stated driver requirement is `>= 418.81.07`, so the user's existing 1.14.x/1.15.x will keep working with 580 — but you should upgrade anyway because (a) toolkit 1.18.0 made **JIT-CDI the default runtime mode** of `nvidia-container-runtime`, replacing the legacy `nvidia-container-runtime-hook`, (b) several CVEs and TOCTOU fixes shipped between 1.14 and 1.17, and (c) 1.19.0 ships the `nvidia-cdi-refresh.{path,service}` systemd units that auto-regenerate `/var/run/cdi/nvidia.yaml` on driver and device changes — meaning future driver bumps don't require you to re-run `nvidia-ctk cdi generate`. CDI is also the only path supported by Podman, containerd-without-Docker, and recent CRI-O, and it fixes a known bug class where `systemctl daemon-reload` detaches GPUs from running containers under the legacy hook.

**Do not set `"default-runtime": "nvidia"`** in `/etc/docker/daemon.json` for this host — every `docker build` becomes GPU-coupled and built images become non-portable. The right config is a registered named runtime (which `nvidia-ctk runtime configure --runtime=docker` produces), invoked per-container via `--gpus all` or `--runtime=nvidia` or the modern `--device=nvidia.com/gpu=all` (CDI) form.

## The procedure

This is the full sequence assuming you've adopted the recommended path (R580 LTS, open module, server flavor, Ubuntu archive, HWE kernel, toolkit 1.19, CDI). Total wall-clock time on a healthy system is roughly 25–40 minutes including two reboots; rollback is roughly 10–15 minutes if needed.

### Phase 0 — pre-flight backup (run this even if you skip the upgrade)

```bash
# Stop the Docker stack and any GPU consumers cleanly first
sudo systemctl stop docker
sudo fuser -v /dev/nvidia*    # confirm no processes hold GPU handles
sudo nvidia-smi -pm 0          # clear persistence mode (it does not survive a driver reload anyway)

mkdir -p ~/nvidia-535-backup/debs && cd ~/nvidia-535-backup

# Inventory
dpkg -l '*nvidia*' 'libnvidia*' > dpkg-l-nvidia.txt
apt-mark showhold > apt-holds.txt
apt-mark showmanual | grep -i nvidia > apt-manual-nvidia.txt
cp -a /etc/apt/sources.list.d sources.list.d.backup
cp -a /etc/apt/preferences.d  preferences.d.backup
apt-cache policy > apt-policy.txt
for p in $(dpkg -l '*nvidia*' | awk '/^ii/{print $2}'); do
    apt-cache policy "$p" >> apt-cache-policy-nvidia.txt
done
uname -r > kernel.txt
modinfo nvidia | tee modinfo-nvidia.txt
cat /proc/driver/nvidia/version > proc-nvidia-version.txt
nvidia-smi > nvidia-smi.txt
nvidia-ctk --version > nvctk-version.txt 2>&1 || true

# Cache the .debs for offline rollback (the critical step)
cd debs
apt-get download $(dpkg -l | awk '/^ii.*nvidia.*535/{print $2}' | sed 's/:amd64//')
apt-get download $(dpkg -l | awk '/^ii.*libnvidia.*535/{print $2}' | sed 's/:amd64//')
# Also grab the matching linux-modules-nvidia for the running kernel, if present:
apt-get download "linux-modules-nvidia-535-$(uname -r | sed 's/-generic//')" 2>/dev/null || true
ls -la
cd ..
```

If `apt-get download` fails for any package (Canonical retired the version), pull the `.deb` directly from `https://launchpad.net/ubuntu/jammy/amd64/<package>/<exact-version>` — Launchpad keeps every published version permanently. If the source was the NVIDIA CUDA repo, the same applies to `https://developer.download.nvidia.com/compute/cuda/repos/ubuntu2204/x86_64/`.

**On filesystem snapshots**: if the root filesystem is on ZFS or LVM, `zfs snapshot rpool/ROOT/ubuntu@pre-nvidia-580` or `lvcreate -s -L 5G -n pre-nvidia-580 /dev/vg/root` is cheap insurance and probably faster to roll back than apt. Timeshift on ext4 with rsync is heavier and slower; not particularly recommended over the .deb cache approach for a driver-only change. The .deb cache is the load-bearing artifact regardless.

### Phase 2 — kernel + driver + toolkit, one transaction (reboot 2)

apt-mark showhold | grep -i nvidia | xargs -r sudo apt-mark unhold

# Single apt transaction: HWE 6.8 + R580 open + new toolkit
sudo apt update

    nvidia-container-toolkit nvidia-container-toolkit-base \
    libnvidia-container-tools libnvidia-container1

sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
sudo systemctl enable --now nvidia-cdi-refresh.path nvidia-cdi-refresh.service

# Verify DKMS / signed-modules state BEFORE rebooting
dkms status   # should show nvidia/580.x.y, 6.8.0-107-generic, x86_64: installed
              # (or empty if signed pre-built modules satisfied the dependency, which is also fine)

dpkg -l 'linux-modules-nvidia-580-server*' 2>/dev/null        # signed pre-built path

The Conflicts/Replaces in `nvidia-driver-580-*` should remove the 535 stack automatically; the explicit autoremove is paranoia. If apt complains about unmet dependencies, the most common cause is a hold you missed or a leftover `cuda-drivers-535` metapackage from the NVIDIA CUDA repo — purge it explicitly. **Do not use `apt purge '*nvidia*'` blindly** — that would also purge `nvidia-container-toolkit` and force a full toolkit reinstall.

```bash
sudo reboot
```

R580 natively supports CUDA 13.x and is backward-compatible with the entire 12.x family per the [CUDA Compatibility Guide §Binary Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/#binary-compatibility). ## Specific gotchas to watch for

The 535→580 transition's biggest failure mode is **mixed-branch package retention**: ending up with `libnvidia-compute-535` co-installed with `libnvidia-compute-580` because the package names are versioned per branch and apt doesn't see them as conflicting. `nvidia-smi` then reports symbol mismatches or driver-library version mismatches. The fix is the explicit `apt --autoremove purge '*nvidia*535*' 'libnvidia-*-535*'` after the install — verify with `dpkg -l '*nvidia*' | grep -v 580 | grep -v container`. A second, less common failure is a **hold left on `nvidia-kernel-common-535` or `libnvidia-common-535`** from a previous attempt to pin 535; `apt-mark showhold` before the install catches this.

**DKMS rebuild failures** during the install are almost always one of: missing kernel headers for the *running* kernel (`apt install linux-headers-$(uname -r)` and re-run `dpkg --configure -a`), insufficient disk space in `/var/lib/dkms` or `/usr/src` (the build needs ~2 GB transient), or a kernel header/source mismatch after a partial upgrade (run `apt full-upgrade` to convergence first). If you adopted the recommended Ubuntu-archive path with `linux-modules-nvidia-580-server-generic-hwe-22.04`, DKMS isn't on the critical path — Canonical's signed pre-built modules satisfy the dependency directly.

**Persistence mode does not survive a driver reload or reboot**; if you want it on, configure `nvidia-persistenced` as a systemd service (the `nvidia-compute-utils-580-server` package installs the service unit; `systemctl enable --now nvidia-persistenced`). For a containerized workload that's running 24/7 anyway, persistence mode mostly matters for cold-start latency on the first container after boot.

**GPU enumeration order** (which physical card is `cuda:0`) is determined by PCIe bus ID by default and **does not change across driver upgrades**. The variable that does change behavior is `CUDA_DEVICE_ORDER` — if anything in the user's stack sets it to `FASTEST_FIRST`, two identical 4090s have indeterminate ordering. Containers should explicitly bind to UUIDs via `NVIDIA_VISIBLE_DEVICES=GPU-<uuid>,GPU-<uuid>` if the workload depends on stable indexing, but for symmetric dual-4090 inference this rarely matters.

**Module-loading order** (`nvidia` → `nvidia_uvm` → `nvidia_modeset` → `nvidia_drm`, plus `nvidia_peermem` if RDMA) is handled automatically by `modprobe` aliases and udev. The user does not need to touch `/etc/modprobe.d/` for this. If `nvidia_uvm` fails to load post-reboot (`modprobe nvidia_uvm` returns -1), the cause is almost always a stale module from the old branch in `/lib/modules/$(uname -r)/`; `sudo depmod -a && sudo modprobe nvidia_uvm` resolves it. **`nvidia-fabricmanager`** is only relevant on NVSwitch systems (HGX, DGX) — RTX 4090 has no NVSwitch, no fabric, do not install it; `cuda-drivers-580` does not pull it in by default. **`nvidia-peermem`** matters only for GPUDirect RDMA over Mellanox NICs — not relevant here. **`nvidia-prime`** is only meaningful for hybrid graphics laptops.

**libnvidia-container-toolkit caveat for the upgrade**: the toolkit reads driver state via `/proc/driver/nvidia/` and dlopens the host's libcuda. After a driver-only swap, **a `systemctl restart docker` is not sufficient** — the running kernel still has the old `nvidia.ko` resident until reboot, and containers started in that window will fail to map devices. Always reboot after the driver swap before trying containers. If you upgrade the toolkit *without* changing the driver, `systemctl restart docker` is sufficient.

**The `cuda-compat-12-X` package on the host is unrelated** to the in-image one and would only be installed if the user previously did `apt install cuda-toolkit-12-4` on the host (they didn't, per the brief). You do not need it. If something pulled it in transitively, `apt purge 'cuda-compat-*'` is safe.

**Holding the new install at 580**: Canonical has been bumping older NVIDIA branches via SRU transitional packages (550→580 in Sept 2025). To prevent your 580 install from being silently bumped to 590 in a future SRU, hold the metapackage and the common packages:

```bash
sudo apt-mark hold nvidia-driver-580-server-open libnvidia-common-580 \
    nvidia-kernel-common-580 nvidia-utils-580-server
```

Release with `apt-mark unhold` when you decide to move to a newer branch.

## Rollback procedure

If 580 misbehaves intractably (Xid storms, dual-GPU instability, nvidia-smi hangs, container failures that bisect to the driver), the rollback is mechanical and takes 10–15 minutes including reboot. **The state preserved in Phase 0 is what makes this clean** — without the .deb cache and the package list, you'd be reinstalling 535 from whatever Canonical currently ships (which is `535.274.02`, not your original `535.104.05`), and the kernel module signatures and exact userspace ABI would shift. Probably fine in practice but not byte-identical.

```bash
# Stop GPU consumers
sudo systemctl stop docker
sudo fuser -v /dev/nvidia*

# Purge 580
sudo apt --autoremove purge '*nvidia*580*' 'libnvidia-*-580*' nvidia-utils-580-server

# Reinstall the cached 535 stack from the local .debs
cd ~/nvidia-535-backup/debs
sudo apt install ./*.deb       # apt resolves dependency order

# Optionally: if you also rolled the kernel, the 5.15 kernel is still present
# in /boot/ unless you purged it. Pick it at the GRUB menu, or:
sudo grub-set-default "Advanced options for Ubuntu>Ubuntu, with Linux 5.15.0-130-generic"
sudo update-grub

# Re-apply holds
xargs -a ~/nvidia-535-backup/apt-holds.txt sudo apt-mark hold

sudo reboot
# Validate
nvidia-smi                          # 535.x.y restored
docker run --rm --gpus all nvidia/cuda:11.8.0-base-ubuntu22.04 nvidia-smi
```

**Container state is unaffected** by a driver downgrade — Docker images, volumes, and stopped containers persist on disk regardless of driver version. *Running* containers are killed by the reboot, but that's a reboot side-effect, not a downgrade side-effect; if you `docker stop` cleanly first, container state survives perfectly. Image registries, layer caches, and bind-mounted host paths are filesystem objects with no driver dependency.

If you adopted HWE 6.8 in Phase 2 and want to roll *that* back too, `apt --autoremove purge linux-generic-hwe-22.04 linux-headers-generic-hwe-22.04 linux-image-6.8.0-*-generic linux-headers-6.8.0-*-generic` returns to the 5.15 GA stack. The 5.15 kernel images you booted on in Phase 1 are still in `/boot` and `dkms status` will rebuild against them. Whether you roll back the kernel depends on whether the failure correlates with kernel or driver — `journalctl -k -b -1` on the new boot helps bisect.

## Answers to the four open questions from the handoff

**(1) Is the 804 diagnosis correct, and is there an env-var/LD_PRELOAD trick to disable forward-compat?** Yes, the diagnosis is exactly right. The mechanism is the `cuda-compat-12-4` package shipped in the `nvidia/cuda:12.4.1-base-ubuntu22.04` image, which drops a userspace R550-class `libcuda.so.1` under `/usr/local/cuda-12.4/compat/` and gets loaded preferentially over the host driver's libcuda; inside `cuInit()` the compat driver detects forward-compat-upgrade mode, queries the GPU class, and rejects RTX 4090 because Forward Compatibility is restricted to data-center SKUs. There is **no documented env var to disable the compat path** — `__NV_DISABLE_COMPAT` does not exist publicly, `CUDA_FORCE_PTX_JIT` is unrelated, `NVIDIA_DISABLE_REQUIRE` only suppresses libnvidia-container's pre-flight check (not the in-process cuInit). LD_PRELOAD-ing the host libcuda is fragile because libnvidia-container has read-only-bind-mounted the compat library. **The robust fix is `apt-get purge cuda-compat-12-4` inside the image**; alternatively, rebuild on `ubuntu:22.04` and skip the `nvidia/cuda` base image entirely. Either lets the cu124 wheel run on the existing 535 driver via Minor Version Compatibility, which is unrestricted by GPU class.

**(2) 550-LTS vs newer for ML workloads.** R550 is *not* an LTS branch — that designation is incorrect. The actual LTSBs are R535 (sunsetting June 2026) and **R580** (EOL August 2028). R570 is the current Production Branch (effectively in maintenance after Feb 2026). For Ada / RTX 4090 ML workloads in April 2026, **R580 LTS is the right answer**: 3-year support runway, native CUDA 13.x with full backward compatibility to cu124/cu126/cu128 wheels, NVIDIA's "Recommended/Certified" Linux stable (580.95.05 Oct 2025; 580.126.09 Jan 2026), no documented Ada/PyTorch/cuDNN regressions. R570 is acceptable as a fallback. R555/R560/R565/R575 are all EOL feature branches — skip. R590/R595 are New Feature Branches with reported UE5/Wayland regressions — explicitly off-limits for production ML. R550 itself, if you must, terminates at 550.163.01 (Apr 2025) and receives no further updates; its only justification is fleet-uniformity with other hosts already on it.

**(3) Can you unblock by pulling cuda-toolkit out of the image and relying on the wheel's bundled cu124 libs?** **Yes, definitively, on the existing 535 driver, on RTX 4090, with no driver upgrade needed for this purpose alone.** This is the cleanest possible answer and it's what I'd ship first. The cu124 PyTorch wheel bundles `nvidia-cuda-runtime-cu12` (libcudart.so.12), `nvidia-cublas-cu12`, `nvidia-cudnn-cu12==9.1.x`, `nvidia-nccl-cu12`, `nvidia-cufft-cu12`, etc.; the only thing it needs from outside is `libcuda.so.1`, which nvidia-container-toolkit injects from the host driver. Per [CUDA Compatibility §Minor Version Compatibility, Table 1](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html), **CUDA 12.x toolkits run on driver `>= 525` with no GPU-class restriction** — MVC is unrestricted, unlike Forward Compatibility. Driver 535.104.05 ≥ 525, so cu124 cudart loads and runs on RTX 4090. The compat shim is what triggers 804 — remove it (`apt purge cuda-compat-12-4` after `FROM`, or rebuild on `ubuntu:22.04`) and the 804 disappears. flash-attn 2.8.3 is wheel-compiled against torch 2.6.0+cu124's ABI and uses the same userspace libcuda chain — it works under the same MVC contract on sm_89.

**(4) ABI-locking best practice for torch pinning.** Pin exactly, including the index, and commit `uv.lock`. **Do not use `torch>=2.6,<3`**: PEP 440 local segments (the `+cu124` suffix) are opaque to most resolvers, so a range specifier will happily match `2.6.0+cpu`, `2.6.0+cu118`, or whatever PyTorch promoted as the PyPI default for that version on a given day — silently breaking ABI compatibility with flash-attn (which is hard-pinned against a specific torch ABI) and with the bundled cuDNN 9.1 that flash-attn 2.8.3 was tested against. Use:

```toml
[project]
dependencies = ["torch==2.6.0", "flash-attn==2.8.3", ...]

[tool.uv.sources]
torch = { index = "pytorch-cu124" }

[[tool.uv.index]]
name = "pytorch-cu124"
url = "https://download.pytorch.org/whl/cu124"
explicit = true   # consult this index ONLY for torch — avoids resolver issues with nvidia-cublas-cu12 etc.

[tool.uv]
no-build-isolation-package = ["flash-attn"]

[[tool.uv.dependency-metadata]]
name = "flash-attn"
version = "2.8.3"
requires-dist = ["torch", "einops"]
```

Commit `uv.lock`; build with `uv sync --frozen --no-dev`. The lockfile records the exact `+cu124` build and the resolved index, giving byte-reproducible builds across rebuilds. The `explicit = true` flag is critical to avoid known uv issues ([astral-sh/uv#9901](https://github.com/astral-sh/uv/issues/9901)) where unconstrained `pytorch-cu124` priority resolves transitive `nvidia-*-cu12` deps from the wrong index. Don't write `torch==2.6.0+cu124` in the dependency list; uv's resolver historically had issues with explicit local segments on the public PyPI registry path ([uv#11406](https://github.com/astral-sh/uv/issues/11406)).

Once you do upgrade the host driver to R580 LTS, you have license to relax this further — the same image will run on driver 535 (via MVC), 570 (native), 580 (backward-compatible), and any future 12.x or 13.x driver you migrate to — but the *ABI* coupling between torch, flash-attn, and bundled cuDNN remains, so exact-pinning of those three packages is still the right call regardless of host driver. If you want an upgrade cadence, let Renovate open PRs that bump `torch`, `flash-attn`, and the cuDNN bundle in lockstep, with CI running the smoke tests above before merge — not a `>=` range that auto-floats on every rebuild.

## Conclusion

The user's situation has a **fast fix and a strategic fix**, and they're independent. The fast fix — purge `cuda-compat-12-4` from `lupin:1.0.0` (or rebuild on `ubuntu:22.04`) — eliminates the 804 error today on the existing 535 driver via Minor Version Compatibility, with no host changes, no reboot, no risk to `lupin:0.9.0`. **Do this first.** The strategic fix — upgrade the host driver to R580 LTS via Ubuntu's restricted archive, with the open kernel module flavor, the server variant, the HWE 6.8 kernel in the same apt transaction, and nvidia-container-toolkit 1.19 with CDI — gives a 3-year support runway, native CUDA 13.x for future containers, and a clean apt-rollback path anchored on the cached `.deb` files from Phase 0. **The "550-LTS" target in the original brief should be reread as "R580 LTS"**: R550 was never an LTSB, is upstream EOL, and Canonical is already transitioning the jammy package off it. The dual-RTX-4090 specifics that look scary in isolation — no PCIe P2P, R570's Ada-RO-traffic erratum, the 535-era forced-548-bump SRU, the open-vs-proprietary debate — all resolve cleanly on the R580-server-open path, because consumer Ada has no PCIe P2P to lose, the erratum is moot without P2P, the SRU surprise is defused by `apt-mark hold`, and the open module is byte-identical in userspace to proprietary while being NVIDIA's officially recommended path for Turing-and-newer since R560. The single most important deliverable from this exercise isn't the upgrade itself — it's the Phase 0 backup. Capture the .debs, the dpkg list, the holds, and the apt sources before touching anything; everything downstream becomes an undo-able operation.
