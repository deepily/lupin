## 3. Failure Clusters (root-cause grouped)

### Cluster A — Notification dispatch returned HTTP 503 across every expediter scenario ★ HARNESS

**Affected pytest failures**: #1 (12/13 cancels), #6 (6/6 expediter cancels in proxy_integration), #8 (3/3 swe-team cancels). **~21 sub-scenario cancellations.**

**Symptom (verbatim, from results.md)**:
```
Notification status: http_error_503
FAIL: User cancelled unexpectedly
```
appearing on every expediter-flow scenario. Calculator + CRUD scenarios in `test_proxy_integration.py` (1–8) PASSED — including `CRUD_DELETE` whose proxy auto-confirms — so the proxy itself was not unconditionally down.

**Mechanism**:
- `RuntimeArgumentExpeditor._ask_for_arg` / `_ask_for_confirmation` call `notify_user_sync(...)` and store the HTTP status:
  - `src/cosa/agents/runtime_argument_expeditor/expeditor.py:684` (`_ask_for_arg`)
  - `src/cosa/agents/runtime_argument_expeditor/expeditor.py:735` (`_ask_for_confirmation`)
  - `src/cosa/agents/runtime_argument_expeditor/expeditor.py:836` (third notify path)
- That status is surfaced into the job-done payload at `src/cosa/rest/routers/mock_job.py:316` as `config.notification_status`.
- The smoke-test post-condition checks read it at `test_expeditor_mock_job_smoke.py:344-346` and label "User cancelled unexpectedly" when status ≠ `responded` and the scenario didn't `expect_cancel`.

**Hypothesis**: The notification HTTP endpoint that `notify_user_sync` POSTs to was returning 503 for every expediter call. The 503 is consistent across three independent test files using three independent voice commands — this is a **service-level outage of the notification dispatch path**, not a per-scenario logic bug. The fact that calculator/CRUD scenarios passed confirms the WS broadcast / job pipeline itself was healthy; only the *interactive* notification round-trip was broken.

**Recommended action (harness — not product code)**:
1. Add a `NOTIFICATION_503` annotation in the smoke harness that distinguishes this signal from a true cancellation, so future runs surface the cluster as one infra failure rather than 21 mystery cancellations.
2. Add a pre-flight in `pre_run_hook` that POSTs a noop notification request and aborts the suite early with a clear "notification dispatch unavailable" message rather than running 21 scenarios that will all 503.
3. Determine *what* served 503 at 22:15 EDT yesterday — check container logs (`docker logs lupin-rest-test --since 12h | grep -E "503|notify_user"`). If transient, log and move on; if a config-block routing issue (`Lupin: Testing` notification target points somewhere unreachable), fix in INI.

**Why not a product bug**: `notify_user_sync` itself is doing the right thing — it propagates the upstream HTTP status faithfully. The expeditor handles the 503 by returning `None` (treated as cancellation), which is correct degradation behavior.

### Cluster B — Two presentation tests scheduled without `--auto-proxy` pytest_args ★ SCHEDULER

**Affected pytest failures**: #4 (`test_presentation_live_endpoint`), #7 (`test_research_to_presentation_live`).

**Symptom**: Both fail in their `pre_run_hook` with explicit `RuntimeError`:
```
test_presentation_live_endpoint requires --auto-proxy when invoked under pytest.
The 4 presentation-gate approvals cannot complete without an auto-answer proxy.
Re-submit via /api/test-suite/submit with pytest_args including
'--auto-proxy --cost-cap-usd <N>' (e.g. '--auto-proxy --cost-cap-usd 5.00').
```

**Mechanism**: The pytest invocation received `argv = ['src/tests/smoke/', '--junit-xml=/tmp/smoke-junit-20260501-013221.xml']` — only the suite path and JUnit-XML output. The `--auto-proxy --cost-cap-usd N` args required by these two tests were not included in the test-suite job's `pytest_args` field.

**Evidence**:
- Hard-coded refusal: `src/tests/smoke/test_presentation_live_smoke.py:351` and `src/tests/smoke/test_research_to_presentation_live_smoke.py:268` raise `RuntimeError` if `--auto-proxy` is absent.
- The submit form / scheduler that produced this run set `pytest_args` to only the path + junit-xml; no per-test extra args were composed.

**Recommended action (scheduler — not product code)**:
1. Per-test `extra_pytest_args` mapping: when a scheduled `all` run includes one of the two `*_live_smoke` tests, the scheduler should auto-append `--auto-proxy --cost-cap-usd 5.00` (presentation_live) and `--cost-cap-usd 10.00` (research_to_presentation) to the args passed to that specific test invocation, OR
2. Bypass approach: split the scheduler into "long-running interactive E2E" and "fast smoke" buckets so the interactive-required tests are scheduled with their own arg block (matches the cost-tiered pyramid in `src/rnd/v0.1.6/2026.03.14-presentation-generator/2026.04.07-e2e-testing-strategy.md`).

**Why not a product bug**: The tests are correctly self-defending. The scheduler is the missing piece.

### Cluster D — `mode='test_suite'` produces malformed router command → HTTP 500 ★ REAL BUG (small fix)

**Affected pytest failure**: #9 (`test_test_suite_live_pipeline::DRY_RUN_BOTH`).

**Symptom**:
```
FAIL: HTTP 500: {"detail":"Failed to push job to queue:
  'NoneType' object has no attribute 'split'"}
```

**Mechanism (verified by reading the code path)**:
- `src/cosa/rest/todo_fifo_queue.py:53–68` defines `MODE_TO_AGENT`, which **includes `"test_suite"`** as a "Test Suite" entry (despite a comment two lines above stating "Agentic process modes (route through `AGENTIC_MODE_MAP`, not `MODE_TO_AGENT`)").
- `src/cosa/rest/todo_fifo_queue.py:87–96` defines `AGENTIC_MODE_MAP` which maps `"test_suite" → "agent router go to test suite"` (with a **space**).
- At line **634** the routing dispatch is `if user_mode and user_mode in MODE_TO_AGENT:` — this branch fires *first*, since `"test_suite" ∈ MODE_TO_AGENT`.
- Inside that branch (line **636**): `command = f"agent router go to {user_mode}"` builds `"agent router go to test_suite"` (with **underscore**, never transformed).
- The `elif command in AGENTIC_AGENTS:` branch (line 719) does not match because the registered key is the *space* form.
- Falls through to `else:` (line 738) which prints "TO DO: Implement else case command…" and returns a partially-built result that downstream callers expect to `.split()`. With `agent` left as `None`, a downstream attribute access on `None.split(...)` raises the observed exception, surfaced as HTTP 500 by `src/cosa/rest/routers/queues.py:247`.

**Fix (one-liner candidates)**:

**Option 1 — narrow**: Re-order the dispatch in `todo_fifo_queue.py` so `AGENTIC_MODE_MAP` is checked **before** `MODE_TO_AGENT`. Agentic modes that appear in both dicts then get the space-form command.

```python
# todo_fifo_queue.py, lines 634-647 — current order
if user_mode and user_mode in MODE_TO_AGENT:
    command = f"agent router go to {user_mode}"   # ← bug: produces "test_suite"
elif user_mode and user_mode in AGENTIC_MODE_MAP:
    command = AGENTIC_MODE_MAP[ user_mode ]

# Proposed re-order:
if user_mode and user_mode in AGENTIC_MODE_MAP:
    command = AGENTIC_MODE_MAP[ user_mode ]
elif user_mode and user_mode in MODE_TO_AGENT:
    command = f"agent router go to {user_mode}"
```

**Option 2 — clean**: Remove the agentic-mode entries (`deep_research`, `podcast`, `research_to_podcast`, `claude_code`, `swe_team`, `presentation`, `research_to_presentation`, `test_suite`) from `MODE_TO_AGENT`. The comment at line 56 already says they shouldn't be there. The UI dropdown likely reads `MODE_TO_AGENT` for display names — verify before deleting; if so, refactor display-name lookup to consult both dicts.

**Recommendation**: **Option 1** — minimal blast radius; one branch swap; no UI impact; gets the test green.

**Carryover note**: This same failure appears in the prior post-mortem (2026-04-29) under the same name. **It was identified but not fixed.** Re-confirmed today.

**Files to edit**: `src/cosa/rest/todo_fifo_queue.py:634-647` (CoSA submodule — editable in this session per memory; commit must be staged in CoSA's own session per nested-repo rules).

**Test that will go green**: `src/tests/smoke/test_test_suite_live_pipeline.py::test_test_suite_live_pipeline`.

**Risk**: Near-zero — re-ordering branches when the second-branch dict is the canonically correct one for those keys. Add a unit test asserting `mode='test_suite'` → command `"agent router go to test suite"` to lock the ordering.

### Cluster F — `idle_waiter` subprocess didn't exit in 15s, killed by SIGKILL ★ POSSIBLE BUG

**Affected pytest failure**: #2 (`test_idle_waiter_smoke::test_waiter_lifecycle_state_transitions`).

**Symptom**:
```
proc.communicate(timeout=15) → subprocess.TimeoutExpired
proc.kill()
pytest.fail("waiter did not exit in 15s — possible hang in REST call or sleep")
```
Process killed (returncode `-9`).

**Mechanism**: The test spawns `python -m lupin_cli.claude_code.hooks.lib.idle_waiter` with:
- `LUPIN_IDLE_WAITER_TEST_SLEEP_SECS=2` (sleep should be 2s, not the prod default)
- `LUPIN_API_URL=<unreachable>` (test-only, expected to fail)
- It then expects: 2s sleep → unreachable REST call (must time out, not hang) → exit.

The subprocess didn't reach exit within 15s of being spawned, even though the sleep is 2s. The remaining ≥13s budget was consumed by the REST call. **Hypothesis**: the unreachable URL produced a longer-than-expected connect/read wait — probably no explicit `timeout=` on the `requests.post(...)` (or equivalent) inside `idle_waiter.py`. On Linux the default TCP SYN retry pattern can take ~15-30s without an explicit timeout.

**Recommended action**: Open `lupin_cli/claude_code/hooks/lib/idle_waiter.py` and audit every REST call for an explicit `timeout=(connect, read)` argument. A reasonable bound is `timeout=(2, 5)` — the waiter is by definition fire-and-forget; nobody is waiting on its REST result. **This is a real bug if confirmed**: the prod waiter could hang indefinitely on a transient network glitch.

**Files to inspect**: `src/lupin_cli/claude_code/hooks/lib/idle_waiter.py` (haven't opened it in this session — recommend a focused read + sweep for `requests.` / `urllib.` / `httpx.` calls without `timeout=`).

**Risk**: Once fixed, the test will reliably exit in <5s instead of needing SIGKILL. No production behavior change for healthy endpoints.

### Cluster G — `mock_job.py` keyword fallback missing "presentation" branch ★ SCENARIO GAP (sub-failure)

**Affected sub-scenario**: `test_proxy_integration.py::EXP_PRES_MISSING` (1 of 15 inside failure #6).

**Symptom**:
```
FAIL: HTTP 400: {"detail":"Could not match voice command to any agentic agent.
  Available: ['agent router go to deep research', 'agent router go to podcast generator',
  'agent router go to research to podcast', 'agent ..."}
```

**Mechanism**: `src/cosa/rest/routers/mock_job.py:259–280` first tries keyword-overlap matching against `AGENTIC_AGENTS.keys()`, then falls back to a hard-coded if/elif:

```python
# mock_job.py:268-275 — current
if not matched_command:
    if "podcast" in voice_command.lower() and "research" in voice_command.lower():
        matched_command = "agent router go to research to podcast"
    elif "podcast" in voice_command.lower():
        matched_command = "agent router go to podcast generator"
    elif "research" in voice_command.lower():
        matched_command = "agent router go to deep research"
```

Voice command `"make me a presentation"` contains neither "podcast" nor "research", so all three elifs miss, and the explicit raise at line 278 fires.

**Note**: The keyword-overlap pass at lines 261–266 *should* succeed for "presentation" because `AGENTIC_AGENTS` includes a `"agent router go to presentation generator"` entry (registered at `src/cosa/rest/routers/presentation_generator.py:201`). The keyword extraction strips the `"agent router go to "` prefix → `["presentation", "generator"]` → checks if both are in `"make me a presentation"` → "generator" is NOT, so the overlap match fails. Same for `"agent router go to research to presentation"` → keywords `["research", "to", "presentation"]` → "research" not in command.

**Recommendation**: Add explicit fallback cases for the two presentation flows at `mock_job.py:268–275`. Order matters — check the more-specific compound first:

```python
if "presentation" in voice_command.lower() and "research" in voice_command.lower():
    matched_command = "agent router go to research to presentation"
elif "presentation" in voice_command.lower():
    matched_command = "agent router go to presentation generator"
# ... existing podcast/research branches
```

**Carryover**: Per the prior post-mortem, this exact gap was flagged. Not fixed.

**Files to edit**: `src/cosa/rest/routers/mock_job.py:268-275` (CoSA submodule).

**Risk**: Tiny — adding two elif branches identical in pattern to the existing three.
