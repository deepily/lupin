## TL;DR

The `lupin:1.0.0` image we just built ships **PyTorch 2.6.0+cu124** (compiled against CUDA 12.4). The host's NVIDIA driver maxes out at **CUDA 12.2** (driver 535.104.05). The mismatch is being papered over by CUDA's "Forward Compatibility" mechanism, which **NVIDIA only supports on Tesla / data-center GPUs (A100/H100/V100/etc.)**. Both GPUs in this host are **GeForce RTX 4090** consumer cards. As a result, `torch.cuda.is_available()` returns `False` with **Error 804: forward compatibility was attempted on non supported HW**.

**Recommended fix: bump host NVIDIA driver to the 550.x branch** (native CUDA 12.4 support). This requires a host reboot, no in-container changes, and keeps the Tier 0+1 hygiene wins (Python 3.13, uv-managed install, modern torch wheel) intact.

```

available: False
count via NVML: 2
```

- NVML still sees the 2 GPUs (so `nvidia-container-toolkit` injection works fine).
- The CUDA runtime initialization fails with **error 804** the moment torch tries to call `cudaGetDeviceCount()`.
- Per NVIDIA's CUDA driver developer notes, **error 804 = `cudaErrorCompatNotSupportedOnDevice`** — the driver attempted to use the **CUDA Forward Compatibility** package (because the running driver is older than the userspace CUDA the application was compiled with), but the GPU model is not on the supported-for-forward-compat list.

## Compatibility theory — what we believe is happening

NVIDIA defines **two** related-but-distinct compatibility regimes within a major CUDA version (CUDA 12.x):

1. **Minor Version Compatibility (MVC)** — applies in the **other** direction: an older CUDA *toolkit* application can run on a *newer* driver within the same major. e.g., a cu121 app runs fine on driver 550.x. **Not our case.**

2. **Forward Compatibility (CUDA Forward Compatibility Package)** — applies when the *application* uses a newer CUDA userspace than the driver natively supports (cu124 app on a 535-branch driver, which is our exact case). This regime is **explicitly limited to Tesla / data-center GPU SKUs** (T4, A100, H100, H200, etc.). On consumer GPUs (GeForce / Quadro / RTX), the runtime aborts with error 804 the moment forward-compat is attempted.

We believe the cu124-bundled libcuda forward-compat shim is shipping inside the torch wheel (as `nvidia/*-cu12` runtime libraries), and it's that shim path that tries to engage on RTX 4090 → error 804.

References we're consulting (please correct/extend):
- [CUDA Compatibility Guide — Forward Compatibility chapter](https://docs.nvidia.com/deploy/cuda-compatibility/index.html#cuda-forward-compatible-upgrade) — states *"the forward compatibility upgrade is supported only on data-center GPUs and NVIDIA AI Enterprise."*
- [CUDA Driver Release Notes — driver-↔-toolkit version table](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html#id5) — driver 535 family supports CUDA 12.2 native; driver 550 family supports CUDA 12.4 native.
- Empirically: identical wheel runs cleanly on data-center GPUs at this exact driver version per multiple GitHub issues on `pytorch/pytorch`.

## Why the cu124 wheel was chosen in the first place

Earlier in this build cycle:
- **First attempt** used the default PyPI torch wheel — that resolved to `torch>=2.7` compiled against CUDA **13.0**. The flash-attn build inside the image hit a hard `RuntimeError: detected CUDA version (12.2) mismatches the version that was used to compile PyTorch (13.0)` because the in-image apt-installed toolkit was `cuda-toolkit-12-2`.
- **Fix attempted**: switched the in-image apt to `cuda-toolkit-12-4`, switched the torch source to `https://download.pytorch.org/whl/cu124`, bumped the base image to `nvidia/cuda:12.4.1-base-ubuntu22.04`. flash-attn built; **build succeeded; runtime regressed.**
- **What the original Tier 0+1 plan assumed**: that "CUDA 12.4 toolkit on a CUDA 12.2 driver works via Minor Version Compatibility." That assumption was wrong — what's actually engaged here is **Forward Compatibility**, not MVC, and Forward Compat is Tesla-only.
- **Why we couldn't go lower** (cu121): PyTorch's `cu121` wheel index is frozen at `torch==2.5.1+cu121` and has no cp313 wheels. We need cp313 because Tier 0 of the upgrade was Python 3.11.5 → 3.13. Going lower than cu121 (cu118) was not investigated yet.

## Recommendation

**Bump the host NVIDIA driver to the 550.x branch** (currently the production-stable 550 series; latest 550 LTS as of 2026 is `550.144.x`, latest non-LTS 550 is `550.163.x`). This driver branch natively supports CUDA 12.4, which is exactly what `lupin:1.0.0` needs. After the bump:

- `lupin:1.0.0` runs as built; no Dockerfile or pyproject.toml changes needed.
- Tier 0+1 wins are preserved end-to-end (Python 3.13.7, uv-managed install, modern torch).
- `lupin:0.9.0` (built against cu12.x older, using Python 3.11.5) continues to run unchanged on the 550 driver because of MVC in the opposite direction.

Steps (please verify against current NVIDIA guidance for 550 LTS install on Ubuntu host):

```bash
# 1) Stop the lupin Docker stack first so containers don't claim devices during driver swap:
docker compose down

# 2) Remove old driver
sudo apt-get purge '^nvidia-.*' '^libnvidia-.*' '^cuda-.*'

# 3) Install 550 driver (Ubuntu 22.04, via NVIDIA's CUDA repo, recommended over Ubuntu's `restricted`):
#    Adjust per current NVIDIA guidance — this is illustrative.
```

## Alternatives if a driver bump is not acceptable

In rough order of risk:

| Path | What changes | Cost | Risk |
|------|--------------|------|------|
| **Driver bump 535 → 550** *(recommended)* | Host driver only; image untouched | One reboot | Low — well-trodden path |
| Re-resolve image against `cu118` torch | uv.lock regeneration; torch downgrades to whatever cu118's latest cp313 build is; re-build flash-attn against cu118 toolkit | ~30 min rebuild + lock | Medium — older CUDA, may stress flash-attn 2.8.3 build |
| Re-resolve against `cu121` + Python 3.12 | Tier 0 partial regression; uv.lock + Dockerfile changes; cp312 wheels for everything | Larger rework | Higher — Python downgrade defeats one of the two Tier 0 motivations |
| Wait for `cu124` wheels on driver 535 via official forward-compat | Not happening — Tesla-only is policy, not a temporary state | n/a | n/a |

Is there an env var or ld-preload trick to *disable* the forward-compat path so torch runtime falls back gracefully to "no GPU" without that warning? (Honest non-blocker — we'd just bump the driver — but useful to know.)
2. The 550 LTS branch (550.144.x) vs 550 non-LTS — does either have known regressions on RTX 4090 / Ada that would matter for ML inference workloads (PyTorch + flash-attn + sentence-transformers)? Any reason to prefer 555.x or 560.x instead?
3. We *could* unblock by also pulling cu124 toolkit/userspace **out of the image** (use `--gpus all` to mount the host's libcuda only and rely on the wheel's bundled cu124 libs). On consumer GPUs, does that runtime composition avoid the forward-compat path, or does PyTorch still try to engage it?
4. We currently pin `torch>=2.6,<3` and let uv resolve to whatever's on the cu124 index. Once the driver is bumped, should we pin a specific torch (e.g., `torch==2.6.0`) or leave the range and let Renovate bump? The expert plan's policy says "pin torch exactly (ABI-locked)."
