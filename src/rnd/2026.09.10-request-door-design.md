## 1. Data model — reuse the branch's columns, add nothing

Migration `8beada291153` (branch) puts three nullable columns on `task_items`: `request_state` (`pending`/`approved`/`denied`), `request_move` (`admit`/`demote`), `request_ts`. One request per row at a time.

⇒ **History lives in the audit trail, not the columns.** Every filing and verdict appends a `TaskEvent`, so a re-file that overwrites the columns loses nothing: the denial it replaced is still an event. No new table, no new state.

## 2. The filing door

`POST /api/tasks/{task_id}/request` · body `{ "move": "admit" | "demote", "reason": "<non-blank>" }`

| Check, in order | Result when it fails |
|---|---|
| Row exists | 404 |
| `move` ∈ `REQUESTABLE_MOVES` (`admit`, `demote`) — won't-fix and un-park are not requestable | 422 naming the two legal moves |
| The move fits where the row is now: `admit` only from `not_approved`; `demote` only from a live, non-terminal status | 409 "this row is already in the holding area / on the board" |
| Caller may file (see §5) | 403 naming who may file |
| No request is already pending on the row | 409 naming the pending move and its `request_ts` |
| `reason` non-blank | 422 |

On success: in one row-locked transaction set `request_state=pending`, `request_move=<move>`, `request_ts=now`, append a `request_filed` event carrying the actor, reason and move, and return the serialized item. The row's `status` is untouched (R2).

A row whose last request is `approved` or `denied` may be filed again; the columns are overwritten and the prior verdict survives as an event.

No batch form (R7): one task id per call.

## 3. What a pending request authorises — nothing (rule 4)

Unchanged from the branch's `task_request_lifecycle.grants_the_move`: `pending` grants nothing, silence changes nothing (R4). The move gate stays `refusal_for_admission`, which after the allowlist narrowing admits Rick's account alone (R1). A pending request never short-circuits that gate.

## 4. Verdicts — and the Q2 fork

`POST /api/tasks/{task_id}/request-verdict` stays as built: Rick's account alone, 409 when nothing is filed, 409 when already answered.

| Verdict | Q2 option 1 — approval performs the move (recommended) | Q2 option 2 — approval records permission only |
|---|---|---|
| `denied` | Write `denied`, append `request_denied`. **Row status untouched** (R5) | Same |
| `approved` | In the **same transaction**: write `approved`, then apply the move through the **same transition path Rick's own board click uses** — `validate_transition`, then the approval gate with Rick's account, then any later gate that path runs. **Option 1 needs a refactor** the branch does not have: `transition_task` is one handler. Extract its body into a function both the transition route and the verdict route call, so a promote by approval is byte-for-byte a promote by click. Two copies of the gate order would drift.

- an approved `demote` goes to `not_approved` with a `next_chase_ts` that Rick supplies in the verdict body, as his demote control requires today.

## 5. Who may file — reuse the manager check that already exists

Rule 3 says a **manager** may request. The tree already answers "is this caller a manager?" in one place, and the close door (row adaf7698) reuses it with its own `move` label:

`task_promotion_gate.manager_refusal( session_id, actor, …, account_persona, move )` returns None when either:
- the login account maps to an approver persona (the browser path), or
- `is_manager_figure( session_id )` reads `role == "manager"` off the session bridge, with the session id taken from the actor's suffix (`rules.session_id_from_created_by`).

It fails closed on an unreadable bridge.

⇒ **Filing calls `manager_refusal( …, move="requesting a promote or demote" )`.** A worker is refused with a sentence telling it to ask its manager. No new identity mechanism.

⚠️ **Carried limits, not new ones.**
- The bridge can be borrowed: a detached process was measured resolving as another seat (row 54a43bcf). Rick accepted "is a manager" as sufficient.
- The code notes that the approver allowlist agrees with the manager check "by coincidence, not by construction". After the narrowing the two stop agreeing by design: the allowlist is Rick, and managers are whoever the bridge says. That is correct here, because filing asks the manager question and moving asks the approver question.

## 6. Clients — board, legacy page, MCP

Surveyed at `e87d9aff`.

**What the board does today.**
- The multiplexer's `HoldingAreaStore` and `TaskListStore` poll `/api/tasks` every 60 s and write through `POST /api/tasks/{id}/transition`.
- Each row has one verb dropdown (`render/taskVerbs.ts`): `approve` goes to `queued`; `demote` goes to `not_approved` and asks for a reason and a "Triage this by" date.
- **Neither client knows whether the viewer is an approver.** Every signed-in viewer sees approve and demote, and the server's gate is the only control.
- The legacy page (`notifications.js`: `renderHoldingArea`, `renderTaskList`, `_transitionTask`) is the same shape.

**Board design (multiplexer):**
1. **Badges.** Fetch `GET /api/tasks/request-badges` on the same 60 s poll. Put the holding-area count beside `multiplexer-holding-area-count` and the task-list count beside the Task List count chip, as two chips that are never summed.
2. **Pending chip per row.** When `request_state == "pending"`, show the move, the filer, the reason and the age. The full row already carries `request_state`, `request_move` and `request_ts`, but the filer and reason live on the `request_filed` event.
3. **Approve / Deny on that chip.** Show them to every viewer, as the board already does for approve and demote; the verdict door refuses anyone but Rick. Do not add approver-awareness plumbing to hide them: that is presentation, and the server is the control.
4. **Approving a demote needs a triage date**, as Rick's own demote control does today. Under Q2 option 1 the verdict body carries `next_chase_ts` when approving a demote, and the chip asks for it.

**Legacy page — BOTH clients (D4, Mr. Radio 2026-09-10 ~19:40):** Rick works from the legacy page too, and the New Ticket card already shipped to both.
- `notifications.js`: fetch the badges beside `fetchHoldingArea` / `fetchTaskList`, draw the chips in `_renderHoldingAreaGroup` / `renderTaskListTable`, and wire Approve/Deny beside `_wireHoldingAreaControls`.
- **One copy of the rules.** Put the chip's state and wording in a shared module under `static/js/shared/`, the way `task-verbs.js` and `task-list-query.js` are already shared. Otherwise the two clients drift.

**MCP verb `task_request( task_id, move, reason )`**, added the way every `task_*` tool is:
1. `task_request_impl` in `task_store_tools.py` calls `task_store_request( "POST", f"/api/tasks/{task_id}/request", … )`.
2. A thin `@mcp.tool` wrapper passes `actor=_task_store_identity()`. That actor carries the session id `manager_refusal` needs, and it is never a tool parameter.
3. The docstring states that a request waits on Rick's board and that no answer means no.

Also add `request_state` and `request_move` to `_serialize_item_terse`, so a manager's `task_query( terse=True )` shows a pending request without a `task_get` per row.

## 7. Stale requests

A request can go stale without a verdict: Rick moves the row directly, a worker closes it, or it is dropped. Left alone, the badge keeps counting a question that has no subject.

Proposal: any transition that makes the pending `request_move` impossible clears the request. The columns go back to NULL and a `request_withdrawn` event records why. This is not a denial (R5 is about Rick's "no") and not an approval, so it writes neither state. **Mr. Radio's call** — see §9.

## 8. The refusal names the door

Today's refusal (`refusal_for_admission`) ends "ask one of them to make this move". After the narrowing, "them" is Rick alone, and the sentence names no request path.

For `admit` and `demote` only, the refusal adds one sentence:

> To ask Rick for this move, file a request: `POST /api/tasks/{id}/request` with `{"move": "<admit|demote>", "reason": "…"}` (MCP: `task_request`). It waits on his board until he answers; no answer means no.

Won't-fix and un-park keep today's text, since neither is requestable.
