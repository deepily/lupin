## Firsthand env-mechanism corroboration for e2e_ui (Cheech, 2026-07-03)

Rachel flagged: e2e_ui uses its OWN `clean_test_db` (`src/tests/e2e_ui/conftest.py:492`), distinct from integration's — verify its reset scope covers the auth tables. Verified firsthand:

- e2e_ui `clean_test_db` is **row-level, not a full drop/recreate** (docstring is stale): `DELETE FROM users WHERE NOT is_protected` + `TRUNCATE auth_audit_log, failed_login_attempts, job_history, proxy_decisions, trust_states`. **`refresh_tokens` is NOT in the explicit reset list.**
- BUT `refresh_tokens.user_id` is `ForeignKey("users.id", ondelete="CASCADE")` (`postgres_models.py:174`). So `DELETE FROM users WHERE NOT is_protected` **cascade-clears refresh tokens for the fresh-registered non-protected users** that the failing fixtures create (`logged_in_page` / `admin_page` register a NEW user per test — conftest.py:709/:742).
- The collision `"Token already exists"` is an `IntegrityError` on INSERT into `refresh_tokens` (`refresh_token_service.py:110-111` → `auth.py:113`).

**Conclusion**: intra-suite refresh-token accumulation for fresh users is NOT expected (the cascade clears them each test), so the 32 auth-setup errors are most consistent with **CROSS-SUITE residue** — which a bounce-fresh single-suite run clears. This independently corroborates Rachel's by-construction proof for the e2e_ui fixture specifically.

**Companion-token edge — SETTLED by schema (Rachel, firsthand, after this check drove a mutual correction)**: `refresh_tokens` has exactly ONE uniqueness = `PRIMARY KEY(jti)` (user_id / token_hash are NON-unique indexes; schema.sql:26 + backup DDL). Since `jti = uuid4()` per issuance, a persisting companion token CANNOT collide with a fresh companion re-login (new jti). So `"Token already exists"` = a **duplicate-jti double-store ONLY** — the SAME jti written twice, which requires a concurrent/retried write during the cross-suite back-to-back handoff, NOT steady-state companion accumulation. Both suites' `clean_test_db` are row-level (Rachel corrected her own report — integration's is ALSO row-level, not DROP/CREATE), and NEITHER truncates `refresh_tokens`, so companion tokens accumulate — but **accumulation ≠ collision** under this schema. **Net (honest scope, per Rachel)**: a bounce-fresh SINGLE-suite run kills the CROSS-SUITE double-store path with certainty — BUT a duplicate-jti double-store can ALSO arise INTRA-suite (pytest-xdist racing two writes, or a login/HTTP retry re-POSTing the same issued token), which a single-suite run would NOT rule out. So the mechanism argument STRENGTHENS the ENV-CLEARED prediction but does not PROVE it: **criterion (iv) — the green re-run — is the arbiter, not the mechanism.** If any of the 32 SURVIVE, check the double-store origin: intra-suite xdist/retry race → still test-infra (non-blocker); anything else → trace the exact double-store with Rachel.

**Refined test-harness fix (both suites, Rachel)**: (1) bounce-between-suites [root]; (2) add `refresh_tokens` to the `clean_test_db` TRUNCATE list [now directly indicated — currently never truncated in either suite]. Non-blocker for THIS merge (test infra), but the durable fix.
