# R2P Lessons Learned: Notification Wiring Bug Cascade

**Date**: 2026-03-08 (Session 329)
**Author**: Claude Opus 4.6 + Ricardo Ruiz
**Status**: Analysis complete, packaging guide update pending

## Context

The R2P (Research-to-Podcast) job required **5 distinct bug fixes across Sessions 328-329**, each revealing a notification wiring pattern that was either undocumented in the packaging guide or documented only after the bug was discovered. The standalone Deep Research and Podcast Generator jobs work because they accumulated these patterns organically over dozens of sessions. R2P, as the first **chained multi-pipeline job**, exposed every gap.

This document captures the lessons learned and proposes updates to the CJ Flow Packaging Guide to prevent future jobs from repeating this cascade.

## The Bug Cascade (Sessions 328-329)

| # | Bug | Root Cause | Was in Guide? |
|---|-----|-----------|---------------|
| 1 | Missing `TARGET_USER` | Not set in `_execute()` or `_execute_dry_run()` | Mentioned but didn't emphasize both paths |
| 2 | `id_hash` vs `base_id` for sender_id | `register_scoped_job()` appends `::user_uuid`, breaking sender_id regex | Pitfall 6.4 added **post-hoc** |
| 3 | Missing `job_id`/`queue_name` on notify() | UI can't route notifications to job cards without these params | **Not documented** |
| 4 | Missing `set_job_id()`/`clear_job_id()` | Internal notifications from delegated agents can't auto-inject job_id | **Not documented** |
| 5 | Missing `reconfigure()` for dual voice_io | Stale module-level state when switching between DR and PG phases | **Not documented** |

**Key insight**: 3 of 5 bugs were **completely undocumented**. The packaging guide was written for single-pipeline jobs (DR, PG) and didn't cover chained jobs.

## Detailed Bug Analysis

### Bug 1: Missing TARGET_USER (Session 328.2)

**Symptom**: "Cannot resolve target_user" error — notifications couldn't route to the correct user.

**Root cause**: `cosa_interface.TARGET_USER = self.user_email` was not set in either `_execute()` or `_execute_dry_run()`.

**Why it got missed**: The packaging guide (Section 2.6) mentions setting `TARGET_USER` but doesn't emphasize that **both real and dry-run execution paths** need it independently. The standalone DR and PG jobs both set it in both paths, but the R2P template didn't copy this.

**Fix**: Added `cosa_interface.TARGET_USER = self.user_email` in both methods.

### Bug 2: id_hash vs base_id for sender_id (Session 328.1)

**Symptom**: `AsyncNotificationRequest` Pydantic validation error — sender_id regex failure because `id_hash` contained `::user_uuid` suffix after `register_scoped_job()`.

**Root cause**: R2P used `self.id_hash` instead of `self.base_id` when constructing sender_id. After `register_scoped_job()` mutates `id_hash` from `rp-5c35fd5c` to `rp-5c35fd5c::0cf47e2d-...`, the `::UUID` fragment breaks the sender_id regex pattern.

**Why it got missed**: The `base_id` property exists on `AgenticJobBase` specifically for this case, but the packaging guide's Pitfall 6.4 was written **after** this bug was discovered — it's a post-hoc documentation of R2P's failure.

**Fix**: Changed `self.id_hash` to `self.base_id` in both `_execute()` and `_execute_dry_run()`.

### Bug 3: Missing job_id/queue_name on notify() (Session 329)

**Symptom**: Notifications were delivered via WebSocket but the browser couldn't route them to the running job card. They appeared as general notifications instead.

**Root cause**: The `job_id` and `queue_name` parameters on `voice_io.notify()` calls tell the JS UI which job card to route the notification to and which queue section to render it in. R2P had none of these on any of its 14 notify() calls.

**Why it got missed**: The packaging guide doesn't mention `queue_name` at all. The example notification pattern (Section 2.6) shows a simplified `notify()` call without `job_id` or `queue_name`. The standalone DR job had these parameters, but they weren't in the template.

**Fix**: Added `job_id=self.id_hash, queue_name="run"` to all 14 notify() calls.

### Bug 4: Missing set_job_id()/clear_job_id() (Session 329)

**Symptom**: Top-level R2P notifications appeared in the job card, but internal progress notifications from `run_research()` (e.g., "Topic 1/5 complete") did not — they lacked `job_id`.

**Root cause**: The `voice_io` module has a module-level `_job_id` variable. When set via `voice_io.set_job_id()`, all downstream `notify()` calls auto-inject it. The standalone DR job calls `set_job_id()` before `run_research()`, enabling auto-injection. R2P did not.

**The auto-injection mechanism** (`src/cosa/agents/utils/voice_io.py` lines 291-293):
```python
# If caller didn't provide job_id, use the module-level _job_id
if job_id is None and _job_id is not None:
    job_id = _job_id
```

**Why it got missed**: This mechanism is **completely undocumented** in the packaging guide. It's a pattern that the standalone DR job learned to use but was never formalized as a requirement for new jobs.

**Fix**: Added `voice_io.set_job_id( self.id_hash )` before pipeline execution and `voice_io.clear_job_id()` in the finally block.

### Bug 5: Missing reconfigure() for dual voice_io (Session 328.1)

**Symptom**: Stale module-level state from a previous voice_io import could affect notifications in the R2P pipeline.

**Root cause**: R2P delegates to two agent modules (Deep Research and Podcast Generator), each with their own voice_io import. Module-level state (sender_id, target_user) can leak between phases if `reconfigure()` isn't called.

**Why R2P is unique**: Standalone jobs only use one voice_io module. R2P is the first job to switch between two, requiring explicit state reset.

**Fix**: Added `voice_io.reconfigure()` at the start of `_execute()`.

## Proposed Packaging Guide Updates

### Update 1: Replace Section 2.6 with "Notification Wiring Checklist"

Every agentic job must set up these 5 things in `_execute()` BEFORE sending any notifications:

1. **Sender identity** (cosa_interface):
   ```python
   cosa_interface.SENDER_ID   = cosa_interface._get_sender_id( suffix=self.base_id )  # NOT self.id_hash
   cosa_interface.TARGET_USER = self.user_email
   ```
   ⚠️ Use `self.base_id` — `self.id_hash` may contain `::user_uuid` after `register_scoped_job()`

2. **Job ID auto-injection** (voice_io):
   ```python
   voice_io.set_job_id( self.id_hash )
   ```
   This enables ALL downstream notify() calls to auto-inject job_id — critical for
   delegated agents whose internal notifications must route to your job card.

3. **Cleanup in finally block**:
   ```python
   try:
       result = await self._run_pipeline()
   finally:
       voice_io.clear_job_id()
   ```

4. **Include queue_name on all notify() calls**:
   ```python
   await voice_io.notify(
       "Starting...",
       priority="medium",
       job_id=self.id_hash,
       queue_name="run"          # ← REQUIRED for UI job card routing
   )
   ```

5. **Set up BOTH paths** — `_execute()` AND `_execute_dry_run()` need identical
   sender identity + job_id setup. Dry-run validates the notification path.

### Update 2: New Section 2.6a "Multi-Pipeline Jobs (Chained Agents)"

If your job delegates to multiple agent modules (e.g., Research → Podcast), each with
their own voice_io import, add these extra steps:

1. **Call reconfigure() before each phase**:
   ```python
   from cosa.agents.deep_research import voice_io as dr_voice_io
   dr_voice_io.reconfigure()  # Clear stale state from prior imports
   ```

2. **set_job_id() covers all phases**: Because voice_io uses a module-level variable,
   setting it once at the top of `_execute()` covers both phases — as long as they
   share the same voice_io module import.

3. **If phases use different voice_io modules**: You must call `set_job_id()` on EACH
   module's voice_io before that phase runs.

### Update 3: Enhance Pitfall 6.4 with Prevention

Add a "Prevention" subsection linking back to the checklist in 2.6.

## Diagnostic Infrastructure Added (Session 329)

As a byproduct of debugging R2P, we added permanent diagnostic logging to `emit_to_user()` in `websocket_manager.py`:

- Logs when `user_id` not found in `user_sessions` (always)
- Logs when `send_json()` fails with the actual exception (replaces bare `except:`)
- Logs when `sent_count=0` (always — delivery failure)
- Logs subscription/connection mismatches (debug mode only)
- Copies session list before iterating to prevent mutation during loop

Also fixed: `WebSocketManager` was missing `self.debug` attribute entirely — now reads `app_debug` from config in `__init__()`.
