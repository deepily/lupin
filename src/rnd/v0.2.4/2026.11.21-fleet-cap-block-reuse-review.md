# Reuse review: the config-block lookup in the fleet cap writer (row 138c1c8f)

Three definitions are new in `src/lupin_mcp/fleet_cap_ini_io.py`: `active_block`, `inherit_chain` and `pick_definition`. The `fetch_similar` call for each answered `CALL_FAILED` with an empty shortlist (0 of its entries answered), so the receipts name no candidate. Each lookup therefore rests on its `record_search` and on the source I read.

## What I read

- `ConfigurationManager.__init__` reads the block from `LUPIN_CONFIG_MGR_CLI_ARGS` inline: it splits the string on spaces, pairs the names, reads `config_block_id` and turns `+` into a space. It also requires `config_path` and `splainer_path` in the same string, and there is no callable that returns only the block.
- `ConfigurationManager._calculate_inheritance` and `_build_inheritance_list` walk the `inherits` pointers of an instantiated manager. They return a list, and they also follow an `inherits` that names a file path. The manager is a singleton with no reload, which is why the fleet cap is read fresh from the file.
- No block of the shipped config file inherits from a file path: its four `inherits` lines all name a section, and the splainer's one hit is description text. `test_every_inherits_line_of_the_shipped_ini_names_a_section_and_none_a_file_path` pins that count and shape.

## The named gaps

- `inherit_chain` follows `inherits` pointers that name a section and does not follow one that names a file path, as the manager does. A file pointer would end the chain, `pick_definition` would then find no definition in it, and the writer would refuse. That is the safe side, and the test above reddens before it can happen.
- The manager cannot be asked for a chain from a path and a block without building itself. Building it needs the splainer file, prints banners and, as a singleton, would hold the value the fresh read exists to avoid.
