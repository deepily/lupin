### Isolation rules

### What the learner requires of it

- **Per-field structure:** prompt, option labels and descriptions, selection mode, default and any recommended flag.
- **Link types:** what each link points to, so "an approval link exists for this field" is answerable.
- **History with as-of status:** up to three prior questions, each answered or pending as of the ask, with the tier, confidence and evidence that `rebuild_context` returns (parent, thread, job, sender, session; the example above uses its field names, not invented ones). `rebuild_context` has no "expired" status, so none is promised. **Cut rule (author's choice):** take its attachments in the order it returns them, strongest tier first and newest first within a tier, and keep the first three that are questions; a pending question counts toward the three, because a pending duplicate is evidence of repetition. Candidates it lists under `missing` (a partial or conflicting signal) are never included. Human-authored informational messages (status `not_a_question`) are kept beside the three, not counted in them. Evidence joined through the `session` tier is marked inferred.
- **The typed answer, attached later:** stance and qualifier, option ids per field, write-in text, or free text, with actor, source and answer time.
- **Exposure:** when Rick revealed the prediction, if he did, and his draft answer at that moment, with "unknown" as a legal value. `revealed_at` is read from `prediction_log.fold_opened_at`, which the seen route already stores first-write-wins (`PredictionLogRepository.record_seen`); no second store. Only `draft_at_reveal` is new, one optional field on that route.

## Layer 1: principle memory and fresh synthesis

Layer 1 turns each informative human answer into timed evidence for short conditional principles, then forecasts from the current card plus the principles that apply.

### Storage

Two tables, append-only on the evidence side:

```text
preference_principles : id, owner_id, kind ( decision | ask_form ), dimension, statement,
                        rationale, scope ( global | project:<name> ), embedding,
                        encoder_version, extractor_version, created_at
preference_evidence   : id, principle_id, notification_id, field_key,
                        relation ( supports | contradicts | refines ), condition,
                        answered_at, extracted_at, extractor_version, retracted_at,
                        source ( extractor | review_card )
unique key on preference_evidence : ( principle_id, notification_id, field_key, extractor_version, source )
```

A row with source `review_card` is Rick's ruling on a contested principle (Pocholo-B-1): the one input the extractor never reads and the status function does. His choice maps to the row: one side wins, both under a condition (both sides gain that condition), or retract. Evidence stays append-only: no existing row is updated. The status function derives the retraction or the added condition from the ruling row, and applies it only to an ask for which the ruling's `answered_at` and `extracted_at` are both at or before the ask (Pocholo-B-6). So a replay of an ask made before the ruling still sees the principle as contested. Without it, a contested principle would stay contested after he ruled, because status comes only from evidence rows.

**Two times, not one (Pocholo-B-2).** Live, a principle's evidence exists only once the extractor has run, so it is usable at an ask only if `answered_at <= asked_at` **and** `extracted_at <= asked_at`. Replay filters on both: it assumes a stated extraction lag (a config value, starting figure TBD, to be set from the live lag once shadow runs) and reports two variants, instant extraction and lagged extraction, so a B1 win that needs instant extraction is visible as one. **One as-of predicate (Rachel-B-5).** Evidence status, `episode_view` and the leakage test use the rule `rebuild_context` already has: an answer counts as known when it was given at or before the ask time, and an answer after the ask time is out. Evidence status calls that rule (`_answer_as_of`, made public or wrapped) instead of writing a fourth comparison, so the boundary cannot differ between them. Status is derived, never stored: hypothesis (one supporting episode), established (supporting episodes from two or more sessions), contested, or retracted. Replay derives it from evidence answered before the target's ask time, which is what makes chronological replay possible.

`encoder_version` names the embedding model and the input text recipe that produced the vector. Retrieval compares a query only against principles with the same encoder version, and a change of encoder re-embeds the table instead of mixing vectors.

### The extractor

- **When:** a queued job after an attributed human answer. It has no latency budget. **Enqueue point (Rachel-B-3):** the post-answer hook in `submit_notification_response` (`notifications.py`, the block headed "Prediction Engine Hook 2", which already runs `record_outcome_from_ledger` off the event loop), after that call; no second hook and no poller. The attribution check runs there, using `answer_source_of` (source `ui`, the owner as `answered_by`) and the review-card marker above; an answer that fails it enqueues nothing.
- **Model (ruled):** Sonnet, called through `model_transport.complete`, with its own INI key and a longer timeout than the forecast call. The model id is written into `extractor_version`.
- **Which answers create hypotheses:** a no, a neither, any qualifier or comment, any option pick, any write-in, any free text. A bare yes only adds support to principles that already applied.
- **Input:** the episode view from the same `episode_view( notification_id, as_of=asked_at )` call the forecast uses (so it carries the layer 0 tiers, the three-question cut and the inferred marks, and no second reader of history exists), the typed answer from `derive_answer`, and the nearest existing principles for the same owner.
- **Output:** hypotheses and their relation to existing principles.

## Layer 2: pairwise reranker

Layer 2 learns how much each kind of principle matters by treating every answered field as a set of comparisons, using the existing `BayesianLogisticRegression` class unchanged.

That class keeps a full posterior covariance with rank-one updates, and `predict()` returns a probability and an uncertainty. A Bradley-Terry comparison is logistic regression on a feature difference, so no new math is needed:

```python
x = features( chosen, episode, principles ) - features( rejected, episode, principles )
model.update( x, 1 )

p, uncertainty = model.predict( features( a, episode, principles ) - features( b, episode, principles ) )
```

### Features and comparisons

- **Features per candidate:** for each dimension, whether the candidate agrees with, opposes or is neutral to the applicable principles (taken from layer 1's forecast call). Then four flags: asker default, recommended, first offered, write-in.
- **Keyed on dimensions, not principle ids,** so merging or splitting principles leaves the weights valid.
- **Comparisons from organic answers:** the chosen option against each unchosen option in that field; the chosen stance against the other two; a write-in against every offered option.
- **Output:** a ranking per field with a margin. Abstain when the top-two margin is within its uncertainty.

### Constraints

- **Own state:** the trust tracker uses the same class. The reranker gets its own instance and persistence, one per owner. The class is reused unchanged; its `to_dict` and `from_dict` serialise it. The only persistence today is `TrustState.blr_state`, keyed by user, domain and category, which this plan must not touch (no trust writes), so the per-owner row is new storage, TBD in step 5.
