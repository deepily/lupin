## Layer 1: principle memory and fresh synthesis

Layer 1 turns each informative human answer into timed evidence for short conditional principles, then forecasts from the current card plus the principles that apply.

### Storage

Two tables, append-only on the evidence side:

```text
preference_principles : id, owner_id, kind ( decision | ask_form ), dimension, statement,
                        rationale, scope ( global | project:<name> ), embedding,
                        encoder_version, extractor_version, created_at
preference_evidence   : id, principle_id, notification_id, field_key,
                        relation ( supports | contradicts | refines ), condition,
                        answered_at, extracted_at, extractor_version, retracted_at
```

Status is derived, never stored: hypothesis (one supporting episode), established (supporting episodes from two or more sessions), contested, or retracted. Replay derives it from evidence answered before the target's ask time, which is what makes chronological replay possible.

`encoder_version` names the embedding model and the input text recipe that produced the vector. Retrieval compares a query only against principles with the same encoder version, and a change of encoder re-embeds the table instead of mixing vectors.

### The extractor

- **When:** a queued job after an attributed human answer. It has no latency budget.
- **Model (ruled):** Sonnet, called through `model_transport.complete`, with its own INI key and a longer timeout than the forecast call. The model id is written into `extractor_version`.
- **Which answers create hypotheses:** a no, a neither, any qualifier or comment, any option pick, any write-in, any free text. A bare yes only adds support to principles that already applied.
- **Input:** the episode view, the typed answer, and the nearest existing principles for the same owner.
- **Output:** hypotheses and their relation to existing principles.

```python
{ "field_key"  : "held_bugs",
  "kind"       : "ask_form",
  "dimension"  : "ask.approval_needs_link",
  "hypotheses" : [
    { "statement" : "an approval request must link the thing being approved",
      "condition" : "field asks for approval", "grounded_in" : "answer" } ],
  "relations"  : { "pref-017" : "supports", "pref-031" : "refines" } }
```

- **Rules:** at most three hypotheses per field. A condition must be grounded in text from the card or the answer, otherwise it is recorded as unknown. Statements stay under 240 characters and carry no project nouns unless the scope is that project.
- **Conflicts:** on a contradiction, a split step looks for a card feature that separates the two sets of supporting episodes. If one exists, both sides gain a condition. If none does, the principle is contested and excluded from retrieval. Rick rules a capped, batched card for these: "a capped, batched multiple-choice card to Rick. It uses the existing ask path: the two conflicting answers, with options for one, the other, both under a condition, or retract. Those cards get their own answer source and no forecast, so the learner never learns from its own review queue. Cap it at about three a day." Nothing is urgent, because a contested principle is already out of retrieval.

* **Unaided answers first:** the extractor reads the draft at reveal where one exists, otherwise the final answer. An answer given after a reveal with no draft is used but marked as possibly influenced.

### Forecasting

B1 builds no forecaster of its own. Rick, 19 Nov: "Phase 6 builds it, and B1 is the same job plus one prompt block." The steps below are the added block, run inside remediation phase 6's job when B1's switch is on. The extractor and offline replay do not depend on phase 6.

1. Retrieve principles by cosine over statement and rationale, filtered by owner, scope and status.
2. In one model call, judge which apply to this card and forecast each field.
3. Return a typed result per field: stance and qualifier, option ids, "write-in expected" with its gist, a text decision with rationale, or an abstention with its reason. Each cites the principle ids it used.

The prompt contains the current card, the selected history from layer 0 and principles. It contains no answer text from other conversations.

## Layer 2: pairwise reranker

Layer 2 learns how much each kind of principle matters by treating every answered field as a set of comparisons, using the existing `BayesianLogisticRegression` class unchanged.

That class keeps a full posterior covariance with rank-one updates, and `predict()` returns a probability and an uncertainty. A Bradley-Terry comparison is logistic regression on a feature difference, so no new math is needed:

```python
x = features( chosen, episode, principles ) - features( rejected, episode, principles )
model.update( x, 1 )

p, uncertainty = model.predict( features( a, episode, principles ) - features( b, episode, principles ) )
```

### Features and comparisons

- **Features per candidate:** for each dimension, whether the candidate agrees with, opposes or is neutral to the applicable principles (taken from layer 1's forecast call). Then four flags: asker default, recommended, first offered, write-in.
- **Keyed on dimensions, not principle ids,** so merging or splitting principles leaves the weights valid.
- **Comparisons from organic answers:** the chosen option against each unchosen option in that field; the chosen stance against the other two; a write-in against every offered option.
- **Output:** a ranking per field with a margin. Abstain when the top-two margin is within its uncertainty.

### Constraints

- **Own state:** the trust tracker uses the same class. The reranker gets its own instance and persistence, one per owner. The class is reused unchanged; its `to_dict` and `from_dict` serialise it. The only persistence today is `TrustState.blr_state`, keyed by user, domain and category, which this plan must not touch (no trust writes), so the per-owner row is new storage, TBD in step 5.
