# Context-aware online preference learner: plan, layers 0 to 3

Nov 17, 2026 · @Richard P Ruiz

## Summary

The learner is a principle memory with fresh synthesis (layer 1), a pairwise reranker over it (layer 2) and best-of-N for free text (layer 3), all reading one shared ask-time record (layer 0). It runs as an undisplayed shadow arm beside the remediated baseline, which is a separate, parallel project.

- **Layer 0 is not built twice.** The remediation project owns it (its items 1, 2 and 6). This plan states what the learner needs from that record and gives a fallback so work can start before it lands.
- **The claim under test is narrow.** Principles must beat the same model given the same card and history without principles. Otherwise any lift is the context, not the memory.
- **The pilots are too small to rank arms.** They hold 20 stance cards, 32 single-select fields, three open-text targets and one multi-select card. They can prove plumbing and fix the design, nothing more.
- **Read against** the Lupin checkout at `abbf1152c`, the remediation plan and the context-window findings, both dated 18 November 2026.

### Decisions needed

1. **Who owns the trained ranker.** Remediation items 8 and 11 each mention a lightweight trained model. I recommend that work is layer 2 here, and the baseline stays untrained (priors plus neighbors).
2. **Whether learner forecasts are displayed.** I recommend not, until the learner wins on replay and live shadow. The baseline hint stays visible as the remediation plan says.
3. **Which models.** I recommend a bounded Claude Code job for the extractor, and for prediction the same frozen model as the card-only control arm.
4. **Whether ask-form principles are in scope.** These capture how Rick wants to be asked, as opposed to what he decides. I recommend yes; the pilots show them directly.

## Arms and isolation

Six arms forecast the same asks into the same ledger; the primary comparison is B1 against C0.

| Arm | Predictor | Owner | Displayed |
| --- | --- | --- | --- |
| A0 | Fixed rules: always yes, first option, recommended option, asker default | Remediation item 4 | No |
| A1 | Remediated case-based engine | Remediation | Yes |
| C0 | Frozen model on the card plus selected history, no memory | Remediation context experiment | No |
| B1 | C0 plus applicable principles | This plan, layer 1 | No |
| B2 | B1 plus the reranker | This plan, layer 2 | No |
| B3 | B2 plus best-of-N for text | This plan, layer 3 | No |

### Isolation rules

- **Evidence is human answers only.** The extractor reads answers attributed to the owner with source `ui`. It never reads a forecast from any arm, a timeout default or a proxy proposal.
- **Separate stores.** Principles and their evidence live in their own tables. A1's case store is untouched.
- **One-way flow.** The reranker reads principles and writes none.
- **No trust writes.** No arm in this plan touches trust state or any gate.
- **Forecast before answer.** Each arm writes its forecast to the ledger before the answer arrives. A forecast that lands after the answer is void, not scored.
- **Hint exposure is recorded.** A1's visible hint can pull Rick's answer toward it. That affects every arm's absolute score equally, so paired differences stay fair; absolute accuracy is reported with that caveat.

## Layer 0: the shared ask-time record

The learner needs one function that returns what was knowable about an ask at a given time, and nothing later.

```python
episode = episode_view( notification_id, as_of=asked_at )

{ "owner_id"   : "...",
  "project"    : "lupin",          "asker" : "claude.code@lupin.deepily.ai#a1b2c3d4",
  "asked_at"   : "2026-11-17T01:47:57Z",
  "title"      : "...",            "abstract" : "...",
  "links"      : [ { "kind" : "supporting_doc", "target" : "..." } ],
  "fields"     : [ { "key" : "held_bugs", "prompt" : "...", "mode" : "single",
                     "options" : [ { "id" : "o1", "label" : "Approve", "description" : "...", "recommended" : True } ],
                     "default" : "o2" } ],
  "history"    : [ { "notification_id" : "...", "status" : "answered", "answer" : "...",
                     "match" : "same_task_id" },
                   { "notification_id" : "...", "status" : "pending", "match" : "same_field" } ],
  "hint_visible" : "unknown" }
```

### What the learner requires of it

- **Per-field structure:** prompt, option labels and descriptions, selection mode, default and any recommended flag.
- **Link types:** what each link points to, so "an approval link exists for this field" is answerable.
- **History with as-of status:** up to three prior questions, each answered, pending or expired as of the ask, with the match evidence. Human-authored informational messages are kept.
- **The typed answer, attached later:** stance and qualifier, option ids per field, write-in text, or free text, with actor, source and answer time.
- **Exposure:** whether a hint was visible, with "unknown" as a legal value.

### Fallback and timing

- **Fallback:** until remediation item 6 lands, `episode_view` is an adapter over the context export and the `notifications` table. The learner calls only this function, so the swap is one change.
- **Timing:** learner forecasts run after the WebSocket push, off the notify path. The baseline's `predict()` stays where it is.

## Layer 1: principle memory and fresh synthesis

Layer 1 turns each informative human answer into timed evidence for short conditional principles, then forecasts from the current card plus the principles that apply.

### Storage

Two tables, append-only on the evidence side:

```text
preference_principles : id, owner_id, kind ( decision | ask_form ), dimension, statement,
                        rationale, scope ( global | project:<name> ), embedding,
                        encoder_version, extractor_version, created_at
preference_evidence   : id, principle_id, notification_id, field_key,
                        relation ( supports | contradicts | refines ), condition,
                        answered_at, extracted_at, extractor_version, retracted_at
```

Status is derived, never stored: hypothesis (one supporting episode), established (supporting episodes from two or more sessions), contested, or retracted. Replay derives it from evidence answered before the target's ask time, which is what makes chronological replay possible.

`encoder_version` names the embedding model and the input text recipe that produced the vector. Retrieval compares a query only against principles with the same encoder version, and a change of encoder re-embeds the table instead of mixing vectors.

### The extractor

- **When:** a queued job after an attributed human answer. It has no latency budget.
- **Which answers create hypotheses:** a no, a neither, any qualifier or comment, any option pick, any write-in, any free text. A bare yes only adds support to principles that already applied.
- **Input:** the episode view, the typed answer, and the nearest existing principles for the same owner.
- **Output:** hypotheses and their relation to existing principles.

```python
{ "field_key"  : "held_bugs",
  "kind"       : "ask_form",
  "dimension"  : "ask.approval_needs_link",
  "hypotheses" : [
    { "statement" : "an approval request must link the thing being approved",
      "condition" : "field asks for approval", "grounded_in" : "answer" } ],
  "relations"  : { "pref-017" : "supports", "pref-031" : "refines" } }
```

- **Rules:** at most three hypotheses per field. A condition must be grounded in text from the card or the answer, otherwise it is recorded as unknown. Statements stay under 240 characters and carry no project nouns unless the scope is that project.
- **Conflicts:** on a contradiction, a split step looks for a card feature that separates the two sets of supporting episodes. If one exists, both sides gain a condition. If none does, the principle is contested, excluded from retrieval and queued for Rick.

### Forecasting

1. Retrieve principles by cosine over statement and rationale, filtered by owner, scope and status.
2. In one model call, judge which apply to this card and forecast each field.
3. Return a typed result per field: stance and qualifier, option ids, "write-in expected" with its gist, a text decision with rationale, or an abstention with its reason. Each cites the principle ids it used.

The prompt contains the current card, the selected history from layer 0 and principles. It contains no answer text from other conversations.

### Reuse

- `dot_topk( metric="cosine" )` and the embedding provider for retrieval.
- The existing LLM client and XML response models for the forecast call.
- The job queue for the extractor.

### Acceptance

- **Pilot cases as fixtures.** `8591a6bf`: the forecast sees Rick's reply to the complaint, not only the complaint. `5a0e252a`: the other session's answer is absent at ask time. `7cb2120f`: the record shows no approval link for that field. `e10ce89c`: pending asks produce no evidence rows.
- **Idempotent replay:** running the extractor twice yields the same principle and evidence counts.
- **No leakage:** no forecast's evidence has an answer time at or after its ask time.
- **Collision test:** identical wording over two different plans yields different forecasts or an abstention.
- **Comparison:** paired wins and losses for B1 against C0 per interaction type, with novel multiple-choice families reported separately.
- **Coverage:** 100% lines, branches and functions.

## Layer 2: pairwise reranker

Layer 2 learns how much each kind of principle matters by treating every answered field as a set of comparisons, using the existing `BayesianLogisticRegression` class unchanged.

That class keeps a full posterior covariance with rank-one updates, and `predict()` returns a probability and an uncertainty. A Bradley-Terry comparison is logistic regression on a feature difference, so no new math is needed:

```python
x = features( chosen, episode, principles ) - features( rejected, episode, principles )
model.update( x, 1 )

p, uncertainty = model.predict( features( a, episode, principles ) - features( b, episode, principles ) )
```

### Features and comparisons

- **Features per candidate:** for each dimension, whether the candidate agrees with, opposes or is neutral to the applicable principles (taken from layer 1's forecast call). Then four flags: asker default, recommended, first offered, write-in.
- **Keyed on dimensions, not principle ids,** so merging or splitting principles leaves the weights valid.
- **Comparisons from organic answers:** the chosen option against each unchosen option in that field; the chosen stance against the other two; a write-in against every offered option.
- **Output:** a ranking per field with a margin. Abstain when the top-two margin is within its uncertainty.

### Constraints

- **Own state:** the trust tracker uses the same class. The reranker gets its own instance and persistence, one per owner.
- **No active querying:** the reranker never causes an extra question to Rick.

### Gate to start

- B1 has beaten C0 on replay.
- The notification inventory shows enough independent comparisons. My starting rule is 20 per feature across many sessions; that is a judgment, to be replaced by a number once the inventory exists.

### Acceptance

- Paired wins and losses for B2 against B1.
- Disabling the reranker returns B1's forecasts exactly.
- Merging two principles in the store changes no weight.
- The reranker writes no evidence rows.
- Coverage at 100% lines, branches and functions.

## Layer 3: best-of-N for free text

For open-text and batch fields, layer 3 generates several forecasts and lets the reranker pick one or abstain.

- **Generation:** three forecasts to start, each from a different subset of the applicable principles.
- **Selection:** layer 2 scores each candidate's decision, not its wording. The top candidate is the forecast unless its margin is within uncertainty.
- **Timing:** runs after the push, like the rest of the learner, and must finish before the answer or it is void.

### Gate to start

- The blinded rubric from remediation item 10 exists.
- There are enough personal open-text targets to compare arms. The pilot had three.

### Acceptance

- B3 against B2 on blinded intent agreement.
- The count of invented conditions is no higher than B2's.
- Coverage at 100% lines, branches and functions.

## Sequence and gates

The first step needs nothing from the remediation project; each later step names what it waits for.

1. **Fixture replay (no dependency).** Build the episode adapter over the 50-target export, the two principle tables and the extractor. Replay chronologically. The output is working plumbing and a list of extracted principles for Rick to read. It makes no accuracy claim.
2. **Inventory (waits on the read-only inventory SQL being run).** Size the corpus per interaction type and set layer 2's gate numbers.
3. **Live shadow (waits on remediation item 2, the ledger).** B1 and C0 write undisplayed forecasts for every ask.
4. **Archive replay (waits on remediation item 4, the harness).** Compare B1, C0, A1 and A0 on the same asks, in time order.
5. **Layer 2,** if its gate is met.
6. **Layer 3,** if its gate is met.

### Stop rule

If B1 does not beat C0 on novel multiple-choice families and on text, principle memory is not earning its cost. Stop before layer 2 and keep C0 as the contextual predictor.
