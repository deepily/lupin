## Ranked implementation backlog

### 1. Preserve the actual target and its owner

**Bug.** The UI offers “neither,” and Lupin already has a parser for it. The predictor counts every nonblank decision that does not start with “yes” as “no,” then applies the same rule when selecting a qualifier. It can learn the wrong stance from an accurate historical record. The comparator credits a correct yes/no even if the attached condition reverses its meaning. In direct checks, “yes, deploy immediately” matched “yes, only after review,” and predicting “neither” failed against “neither [comment: split this into two questions].”

**Change.** Keep the raw answer. Produce a versioned typed label with stance, qualifier, selected option(s) by field, a field-level write-in preserving the original text, or an open-ended reply. Reuse the existing tri-state parser, validate its fallback explicitly, and keep unknown encodings unscored. Use the same representation in reconstruction, storage, voting, display, and scoring. Give personal cases an owner and an origin. Filter on both before retrieving neighbors. Today the vector row has no recipient column, the query filters type and category, and the outcome writer stamps cases as organic. An authenticated actor, intended recipient, asking agent and answer source are four different facts.

**Acceptance.** Round-trip all three stances with and without comments, mixed select modes, explicit empty sets where permitted, and free text. A timeout, malformed answer, proxy proposal or other user’s answer contributes zero personal votes. Qualifier-only differences appear in the scorecard. ## Recovering the notification history

**The highest-value historical asset is the original question, the choices actually offered, and Rick’s submitted answer.** A wrong old forecast or saturated old score does not spoil that pair. An ask with no old forecast can be a good training or replay example. Conversely, 100,000 event rows could describe far fewer distinct decisions. The size of the usable corpus is an inventory result.

1. **Count the source population.** Start with `notifications`, scope by recipient and `response_requested`, and group by type, time, source and state. Left join `prediction_log.notification_id` and the answer-case `prediction_decisions.id = notifications.id::text`. Aggregate attempts before joining. Keep `hintvote-…` IDs separate. Treat `proxy_decisions` and `trust_states` as different populations. The companion inventory runs in a read-only transaction and produces aggregate counts. Its keys were checked against the checkout; the SQL has not been run against the owner’s database. [Read-only inventory SQL](./notification-history-inventory.sql)
2. **Preserve originals and reconstruct a derived dataset.** Keep raw envelopes, timestamps, offered schema, origin and a pointer to the source. Decode native answer objects and JSON strings nested under `value`; handle historical shapes with an explicit schema version. Map a bare choice label only if a single field and option fit. Preserve genuine free-form “Other.” Resolve recipients and actors with historic evidence; record an attribution-confidence tier where the actor field predates logging. Deduplicate retries while keeping genuine repeated decisions. Track parser failures and compare a stratified sample to original cards. Keep backfill version and join method so corrections are reversible.
3. **Rebuild context in descending order of certainty.** Use direct notification/parent, job, thread and full-sender links first, then time-bounded session matches. Recover contemporaneous plan details from preceding notifications, transcripts or a versioned artifact where available. Keep ambiguous joins as missing; an inferred attachment must carry its evidence and confidence. Record the first time each input or answer was known. Replay must not read the eventual reply, later status, final plan, future edits or the target’s own stored case.
4. **Assign uses according to evidence.** A verified human answer with a sufficiently reconstructed question can enter a chronological training **or** test partition. A valid answer with incomplete context can support prompt-only baselines or tiers where that context is optional. Weakly attributable or ambiguous mappings can support a sensitivity analysis after review. An unanswered or defaulted ask can identify frequent question families, improve retrieval vocabulary, or provide preceding context. Synthetic cases support regression testing. Derived scores, proposals, timeout defaults and missing feedback carry no independent human label.
5. **Recover by response family.** Reprocess qualified and neither answers from raw strings; historical binary votes have already lost information. For MC, reconstruct the offered choices and compare them with the answer. The audit’s 2,391 rescored historical predictions and 75 matches measure an old predictor; the underlying human choices deserve a fresh eligibility check. For open text, pair original prompt, contemporaneous context and response, then re-score a reviewed subset. Keep old scores under their original metric version. For batch, reconstruct individual field prompts and answers before scoring.
6. **Prove the import before expanding it.** Produce counts at every step from source rows → distinct eligible asks → usable answers → unambiguous typed labels → reconstructable context → independent families. Report exclusions and missingness by type and era. Run the same backfill twice and compare IDs, counts and content hashes. Freeze a chronological holdout and test that no holdout answer or future neighbor enters an earlier forecast. Expand only the reconstruction work that increases usable coverage or measurable held-out lift.
