## 2. What embedding them would take

- Text to embed: the ask's own message, stripped: `message.strip()`. Measured 19 Nov: the live store path (`_store_decision` in `prediction_engine.py`) embeds `original_message`, which `notifications.py` sets to `message.strip()`; the query path embeds `message` as `retrieval_text` for yes/no and multiple choice. So Clayton's 18 Nov concern that the two paths use different fields resolves: they use the same text, and stripping matches the stored side exactly. Nothing else goes in: no answer, no category, no context (context is step 6).
- Call: `EmbeddingProvider.generate_embeddings_batch( texts, content_type="prose" )`, role left unset. That is the call the live store path makes (`provider.generate_embedding( question, content_type="prose" )`), so old and new vectors share one encoder role. A process that does not own the engines routes it over HTTP to `/api/embeddings/batch`. So the model server does the work and nothing here touches a GPU.
- Check each vector with `validate_fresh_vector` from `cosa.rest.db.embedding_regeneration` (768 wide, finite, norm in the current model's band). A reject is counted and listed, never padded.
- **Scope (ruling above): all 3,610 asks**, not only the 2,306 without a vector. The 1,304 stored vectors are not reused.
- **Record the model on every vector.** Call `provider.describe_engines()` (`embedding_provider.py`), which reads the model server's `/embeddings/info` through the same target the batch call uses. Do not use `read_info()`: it defaults to the FastAPI server. The first read must show `loaded: true` and a non-null `revision`, or the run stops. The info block (`_describe_engine` in `src/lupin_model_server/main.py`) names the `model`, its `revision` (the loaded model's commit hash), `dtype` and `dimensions`. Read it before the first call and after the last. If any field differs between the two reads, the run stops and writes nothing. Each vector carries `model` and `revision`; the side file's header carries the whole block once.
- Cost: 3,610 short texts. Time is not measured; step 1 times the first 20 before the rest.

## 5. Leak rules

1. A vector depends only on the question text and the model, so a vector made today for an old ask carries no later information, **if** only the ask's own text is embedded (section 2).
2. A new case becomes visible to a later ask only when its `responded_at` is at or before that ask. `rows_as_of` already enforces it.
3. The case's final answer and ratification state are used as stored. No revision history exists for these asks, which is the known limit the replay already states.
4. Replay targets use stored vectors only; the engine's embed call stays switched off, so a replay never embeds on the fly.
5. All vectors come from one model by construction: every one is regenerated in one run, and the model's info block is read before and after it (section 2). Step 1 still reports the new norms beside the 1,304 stored ones, as a finding, not a gate.
6. A retry of the same ask is excluded as the replay already does, so a new case cannot be its own neighbour.
