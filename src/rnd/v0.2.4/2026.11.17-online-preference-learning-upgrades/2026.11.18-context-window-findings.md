# How much conversation history helps Lupin?

**Keep both windows in the archive. For shadow prediction, start with the current card’s abstract and options, retrieve up to three prior questions, and give the model only the earlier answers or updates relevant to the current decision.** Five recent notifications alone rarely surfaced a previous answer. Three recent questions often did. A simple replay also showed that copying a recent stance made predictions worse. Relevance is the next experiment; increasing the window is a lower priority.

## Did history change predictions?

I ran a deliberately simple comparison to distinguish having an earlier answer from knowing when to use it. All six views used the same targets. No model was fitted. For stance, the fallback was always yes. If the window included an attributable yes/no/neither answer, the challenger copied the most recent such stance. For single-select, the fallback was the first offered option. The challenger reused a recent MC answer only when the earlier field header matched and the chosen label was offered on the current field. Written replies remained in the scoring denominator. [Reproducible comparison](./compare_context_windows.py)

| Prediction rule | Target only | Last 1, 3, or 5 notifications (each) | Last 3 questions | Combined |
|---|---:|---:|---:|---:|
| Stance, personal pilot subset | 16/20 | 16/20 | 13/20 | 13/20 |
| Single-select, exact field answer | 21/32 | 21/32 | 21/32 | 21/32 |

The question-history rule found a previous stance on 16 of 20 cards. It changed three correct forecasts into errors and fixed none. The MC rule found zero transferable header/label pairs, so its result came entirely from the fallback. These results reject blind reuse as a default for this sample. They leave open the value of interpreting the abstract, matching a decision across differently worded fields, and identifying when Rick is responding to the way the question was asked.

The stance comparison excludes the one Rick-account arithmetic-check card flagged in the earlier pilot. The full 21-card always-yes count remains 17/21. Neither the rule comparison nor these data can estimate text-generation accuracy. There are three personal open-text targets, one multi-select target, and no personal batch targets. The examples below assess what a predictor could have known at the time.

## What can be recovered without reconstructing the archive

- **The current question’s context is already largely available.** The original target rows restore 49 abstracts, 50 timeout settings and 24 nonempty top-level defaults. All 50 have null thread and reply pointers; five have a job ID. The exporter used session scope for 44 targets, job scope for five, and a bare sender for one. Record the scope used when building each example. Match task references when a conversation crosses sessions.
- **The asker’s default and Rick’s preference can differ substantially.** On all 21 stance cards, the default matched only 5/21 actual stances. Thirteen questions defaulted to “no” and received “yes.” Keep the default as an ask-time input and a measured baseline. A timeout applying that default supplies no human label.
- **Answer provenance improved.** All 50 targets have a submitted response attributed by JWT to their recipient and marked with source `ui`; all decoded answers agree with the first export. The 47 Rick-account rows still include the one possible fixture. The other three remain test-account examples. These fields support account attribution; they cannot independently establish who physically clicked or whether a hint was visible.
- **Replay needs a strict ask-time projection.** On all 50 targets, the prediction log’s `predicted_at` follows the notification’s actual `responded_at`, by about 2–413 ms. This confirms that timestamp is unsuitable as the forecasting cutoff. Ten targets also appear as legitimate history for later targets. Join through the target-specific links. Of 332 links, 82 have an earlier answer, 28 are pending under the export’s cutoff rule, and 222 are informational. One earlier answer lacks actor metadata. One pending link already has final stored state `responded` even though its answer and response time are correctly masked. Exclude raw final state and the target’s own answer from features. Recompute state from eligible events, distinguishing expiry where the evidence allows it. Do not expose outcomes by looking up linked IDs in the final target rows.

## Changes to the remediation order

1. **Extend the first replay build to include the original card.** Use message, structured fields and options, abstract, and decision-relevant link types. On some records the author supplied the information omitted by the older export. Compare these fields before paying to reconstruct missing history.
2. **Add question history with explicit status and relevance.** Return up to three questions with as-of answers, pending status, and match evidence such as a shared task ID, same field, or direct follow-up. Separate pending duplicates from answered precedents. Keep informational messages available for current-state facts, human directions and commitments. Down-rank repetitive tool-completion notices.
3. **Test whether that selection earns its complexity in visible shadow mode.** Compare the same frozen predictor on the full current card alone, with question history, and with relevant informational updates added. Log candidate and baseline before Rick answers. Evaluate paired wins and losses, field coverage, neither/write-ins, and condition fidelity on later, independent sessions. This pilot supports the evidence-selection design. It supplies no measured lift for a new contextual predictor.

The present export is sufficient to build and exercise that comparison. The next data investment is broader chronological coverage, particularly organic multi-select, text, repeated task references, and unanswered asks. More adjacent tool notifications for these same 50 would resolve little.
