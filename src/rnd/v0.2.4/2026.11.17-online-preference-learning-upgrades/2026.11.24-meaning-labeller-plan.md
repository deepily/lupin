## 3. The vocabulary: `answer-meaning-v2`

Version is part of the table's unique key (`notification_id`, `schema_version`, `annotator`), so v2 rows sit beside v1 and nothing is rewritten. The repository refuses values outside its constants, so the constants change in the same commit. No migration: v2 uses the existing JSON columns and the schema version is a string.

**Yes, no and neither cards.** The stance is plain code; the label is the comment's relation to it.

| label | meaning |
|---|---|
| `support` | the comment reinforces or conditions the stance without changing the action |
| `dissent` | the comment contradicts or reverses the stance, or objects to part of it |
| `re_frame` | the comment rejects the question's premise or asks something else |
| `no_comment` | stance only; plain code, no model call |

**Multiple-choice cards**, per field:

| label | meaning |
|---|---|
| `agrees` | selects the recommended option, adds nothing material |
| `expands_recommendation` | selects the recommended option and adds a condition or detail |
| `expands_other_option` | selects another listed option and adds a condition (carries `modifies_option_id`) |
| `chose_different_listed_option` | selects a listed option that is not the recommended one, with no comment (was `selects_other`; plain code) |
| `wrote_own_answer` | a typed answer tied to no listed option (was `other_opinion`) |
| `no_recommendation_on_card` | the card offered none, so the first three are undefined (named apart from the v1 alignment value `no_recommendation`) |

**Plain code decides** (yes/no and multiple-choice cards): the stance word, the selected option ids, the recommended-option match, whether a comment exists, an empty selection, the answer's `source` (a `timeout_default` is labelled `cancellation`, not given a stance), and the unknowns `no_explicit_stance`, `neither`, `absent_field`. It reuses `extract_qualifier_comment`, `answer_source_of` and `episode_view.fields_of`.
**The model decides only**: support against dissent against re-frame for a comment that exists, `expands_*` against `wrote_own_answer` for a typed answer, and conditions with their `modifies_option_id`.

### 3b. Open-ended and batch open-ended answers (B1)

Rick's 23 Nov ruling puts both card types in ("recorded, forecast and scored like the other two", pipeline plan line 42), so the labeller covers them. He gave no vocabulary for them, so the names below are **labeller-internal additions, uncertified** (§6).

Native kinds already exist in v1: `open_ended_text` (one text per card) and `batch_field_text` (one text per header, read with `parse_field_selections`, one entry per header).

| relation | meaning | who decides |
|---|---|---|
| `no_answer` | blank text, or `source = timeout_default` (also `cancellation` in unknowns) | plain code |
| `answers` | the text answers what was asked | model |
| `declines_or_defers` | refuses, or puts it off | model |
| `re_frame` | rejects the question's premise or asks something else | model |

The content of the reply rides in `acts` (`approve`, `decline`, `challenge_premise`, `request_information`, `defer`, `propose_alternative`), chosen by the model from the existing `ACT_KINDS`, with `supporting_spans` quoting the text. A batch card gets one entry, one relation and its own acts per header. A stance-like string typed into an open-ended field is not inferred as a stance: it is an `answers`.

### 3c. Where each label lives (B2)

No new column. `add` still requires `native_answer`, `acts`, `conditions`, `alignment` and `unknowns`; a v2 row fills them as follows.

| item | where it goes | what a v2 row puts there |
|---|---|---|
| the stance or choice label (`support`, `agrees`, `answers`, …) | `native_answer[ field_key ][ "relation" ]`, beside the existing `"kind"`; `field_key` is the header, `"answer"` for a single-field card | the §3 or §3b value; the repository refuses one outside the v2 relation constants |
| inferred stance (§5) | `native_answer[ field_key ][ "stance_source" ]` | `"inferred"`, otherwise absent |
| `kind` | `native_answer[ field_key ][ "kind" ]` | one of `NATIVE_KINDS`; a yes/no card is `yes_no_stance` |
| `acts` | the column | `[]` on yes/no and multiple-choice cards; the §3b acts on open-ended and batch cards |
| `conditions` | the column | the model's conditions, each with `modifies_option_id` (a typed condition on a multiple-choice card) |
| `alignment` | the column, **derived by plain code from the relation, never by the model** | `agrees` → `aligned`; `expands_recommendation` → `partial`; `expands_other_option` and `chose_different_listed_option` → `diverges`; `no_recommendation_on_card` → `no_recommendation`; every other relation → `unknown` |
| `unknowns` | the column | `no_explicit_stance`, `neither`, `cancellation`, `absent_field`, `unreadable_payload`, `uncertain_annotator`, as v1 |
| `supporting_spans`, `uncertainty` | the columns | quoted spans; the model's number or `None` |

One test asserts that no relation maps to two alignments and that every relation constant appears in this table's mapping.

## 4. Neither and the qualified yes

- A **neither with a comment** is `re_frame`. The labeller may return `support` or `dissent` only when the comment clearly leans, and the reply must quote the span that leans (`supporting_spans`). A neither with no comment is `no_comment`.
- A **yes with a "but"** keeps its comment verbatim. The labeller writes the label (`support` or `dissent`) and **never touches a trust counter**: the proxy already stores it as `qualified_yes` with no trust movement (Pocholo `e540018ed`, behind the neither switch), and the labeller has no write path to the proxy.
- When the labeller can tell support from dissent, a later, separately gated change may count a supporting qualifier as a yes (pipeline plan, Q5 recommendation). Not in this plan.

## 5. Stance-less strings

Four on dev, so the recovery path is small and reviewable by hand.
1. Rules first: `extract_qualifier_comment` returns `( None, None )`, so no stance and no comment exist for plain code.
2. The string goes to the model with `no_explicit_stance` available. The model may infer the stance. 3. Voting is unchanged: `usable_cases` keeps its rule, and typed-answer votes wait on the labeller's pass line behind `prediction engine typed answer votes enabled`.

## 6. The yes-only pass, and the tracking count

**What "yes-only" means here.** The labeller runs over every stored answer, because every card needs a meaning record before its feedback reaches a later ask. What is certified is narrow: the pass line is checked for the **yes class** and the report carries the stamp

```text
certified_classes: [yes]   uncertified: [no, neither, support-on-no, dissent, re_frame]   basis: fewer than 20 of Rick's own labelled cards in the class, or fewer than 30 slice cards
```

Labels for the other classes are written and kept, and consumers may read them as **uncertified**. No document, card or report may cite dissent or re-frame accuracy from this pass.

**The held-back slice (settled by Cheech, row `05ea77a8`, relayed by Mr. Radio 24 Nov 12:32).** The **gold set is the settled label on every development card** (Cheech, relayed 24 Nov 12:33): the two AI readers' agreed label, or Rick's ruling where they disagree (`adjudicate.resolve`). It is the whole development sample, not Rick's blind share. The slice is **30% of the development gold set, split by card type** (yes/no, multiple choice, open-ended, batch), with **at least 30 cards per type**. A type with **fewer than 60 gold cards goes unscored**, and the report says so. The draw is hashed and seeded at the moment the gold labels freeze, before any tuning, and **Cheech holds the ids**. **Within each card type the slice is stratified by answer class** (Cheech, row `05ea77a8`, 24 Nov 12:35). The 30-card floor is **per card type only**, and **the sample is not enlarged for no and neither**. For each class the report gives its count, recall and precision with a **95% Wilson interval**; a class with **fewer than 30 slice cards is marked unscored, with the interval only**. The labeller's tuning code never reads the ids (step 9a tests that).

**Pass line for yes** (inside the yes/no slice): Cohen's kappa at least 0.7 on the held-back slice, at least 30 yes slice cards (the class floor above, replacing the earlier 20), the same bar the readers are measured against (pipeline plan, O16). A class under 30 slice cards is reported with its count and interval, descriptive, never pass or fail.

**What the yes certificate covers (Q-b).** A yes card can carry `dissent` ("yes, but not the migration"). The yes kappa is computed on yes-stance cards with the labels collapsed to two categories: `plain_or_support` (`no_comment`, `support`) against `not_plain_or_support` (`dissent`, `re_frame`). The report prints the count of the minority category beside the kappa, and the pass needs **at least 10 cards of the minority category** as well as 30 yes slice cards, because most yes answers carry no comment (252 of 1,468 on dev), so a two-category kappa could otherwise pass on a handful. The 10 is my number; Mr. Radio may change it. So the yes certificate says the labeller can tell a plain or supporting yes from one that is not. It says nothing about which of dissent or re-frame the "not" is, and the stamp keeps `dissent` and `re_frame` uncertified. Open-ended and batch relations (§3b) and multiple-choice relations carry no certificate in this plan; the stamp names them too.

**What the 20 counts, and what must be true for a class to lift (B6).** Two different numbers, named apart:
- **The trigger: 20 of Rick's own gold-labelled cards of the class** (row `38b66247`). Reaching it makes the tracker call `labeller_pass_line( class )`. It does not lift anything by itself.
- **The scorability floor: 30 cards of the class in the held-back slice** (Cheech's class rule above; this replaces the earlier 20). The re-check scores the class on the slice of 9a with its recall and precision and 95% Wilson interval. A class under 30 slice cards is reported "triggered, not scorable: the slice holds k of 30", with the interval only, and the stamp stays. The slice is 30% of the settled gold set, so 30 slice cards needs about 100 settled gold cards of the class (30 / 0.3). **The sample is not enlarged for no or neither** (Cheech), so at the §2 mix of Rick's answers (no 16.9%, neither 10.6%) a class reaches 100 settled cards only in a development sample of about 590 yes/no cards for no and about 940 for neither, my arithmetic and an estimate. Below that the class triggers on Rick's 20 but stays unscored, and the interval says how wide the doubt is. That is the ruled outcome, not a defect.

**Who may lift (B5).** Until Rick says otherwise **the lift counts his own labelled cards** (the trigger above), as his Q3 ruling and row `38b66247` say. The settled count is printed beside it and lifts nothing. Whether settled labels may lift a stamp is Rick's question (§9 item 4), and the default stays his own count.

**Lift per class, not joint (Q-a).** Rick's Q3 text says no claim on dissent or re-frame "until 20 gold-labelled no and 20 neither cards exist". Row `38b66247`, written by Mr. Radio from that ruling, says "When a class reaches 20, re-run the labeller's pass-line check for that class and lift the stamp for it". The plan follows the row: the stamp lifts per class. This is a reading of ambiguous words, flagged in §9 for Mr. Radio to confirm with Rick if he wants a joint rule.

**Tracking (row `38b66247`)**: a function `gold_progress( gold_labels )` counts Rick's own gold-labelled **no** cards and **neither** cards, by the card's stance class, and shows the settled count (the readers' agreed label or Rick's ruling, §6 slice) **beside** it. **Only Rick's own count triggers the per-class re-check** (row `38b66247`; Rick ruled the no and neither stamps lift against his judgement, `7b86d55a` Q3, and the settled label includes the readers' agreed label, which would grade the labeller partly against itself). It returns

```text
{ "rick": { "no": n, "neither": n }, "settled": { "no": n, "neither": n }, "target": 20, "reached": [..], "stamp_lifts_for": [..] }
```

`reached` and `stamp_lifts_for` are computed from the `rick` counts only.

It reads the gold-label store of step 8e. Each time a batch lands the manager posts the two counts on row `38b66247`. When Rick's own count of a class reaches 20, `labeller_pass_line( class )` is re-run for it; the stamp loses the class only if the class is scorable on the slice (30 slice cards, §6), otherwise it stays and the report says "triggered, not scorable". Today's value: **0 of 20 for no, 0 of 20 for neither** (the store of 8e does not exist yet).

**What the plain blind share yields.** Rick's blind 20% is a plain seeded random share (`confirm.blind_sample_ids`), exactly as he ruled it; this plan does not change it. This concerns the batches Rick labels himself. On the §2 mix of his answers (214 neither of 2,023 is 10.6%, 341 no is 16.9%), a share of 60 to 80 cards holds about 6 to 8 neither and 10 to 14 no cards, which is **below 20 each**. The settled count will climb faster than Rick's, because the readers label the whole development sample, but it does not lift a stamp. The tracker prints both so nobody reads one as the other, and a test shows a settled count of 40 with a Rick count of 19 lifts nothing. My arithmetic from the §2 counts, an estimate. Whether to add anything to close that gap is Rick's decision, in §9 as "later, needs Rick".

## 7. Who labels, and how the labeller is checked

- **Two AI reader seats**, fresh, blind to each other and to every forecast, label the whole development sample. **Rick labels a blind 20%** (`confirm.BLIND_SHARE`, `blind_sample_ids`) and settles every dispute (`adjudicate.disputes`, `resolve`). Kappa 0.7 is measured Rick against each reader, on the blind sample only (`confirm.KAPPA_BASIS`). The readers' agreement with each other is a reproducibility figure, nothing more.
- **The labeller is a third thing**: automated, and checked against the gold labels. The readers and Rick produce the reference; the labeller is scored against it.
- Blindness for the labeller: it sees the card and the answer, never a forecast, never the answer's later outcome. A test asserts the prompt holds no forecast text.

## 11. The development-sample card builder (Krishna, row 9ee8a6c2, 24 Nov 2026)

Rick approved row 9ee8a6c2 on 24 Nov; it holds step 1 of §8 and this builder. The builder turns stored answers into the packet that §8 steps 8c to 8f read. It is the file `src/scripts/build_answer_card_sample.py`, run from the main checkout against the database in a read-only transaction.

- **Population, per Cheech (row 05ea77a8) and Mr. Radio.** Yes/no and multiple-choice cards come from the checkpoint cohort `src/conf/prediction-checkpoint-cohort.jsonl`, cut by Rachel's `filter_stop_hook_cards.py` (`stop_hook_ids` and `split_cohort`, imported, not re-written; row 244f6766). Open-ended and batch cards come from every answered notification of those two types. In all four types only an answer whose source is `ui` (`answer_source_of`) counts; that leaves out a timeout default, whose source is `timeout_default`, and an answer with no source.
- **Quotas.** 200 yes/no, 180 multiple choice, 100 open-ended, all 96 batch cards: 576 cards. Each type is drawn uniformly with `random.Random( f"{seed}|{type}" )` over its sorted ids. A type with fewer cards than its quota stops the build.
- **Items.** The sample is drawn by card; the item is the field, because `refs` maps an item to `{ notification_id, field_key }`. A yes/no or open-ended card is one item, field key `answer`; a multiple-choice or batch card is one item per answered header. A field with no answer text is left out and counted in the receipt: a blank is plain code (`no_answer`), not a card for Rick.
- **Item payload.** `card_text` is the title (left out when the message opens with it), message, abstract and field prompt; `options` the field's labels; `recommendation` the first recommended label or `None`; `answer` the stored answer text; `stance_class` the yes/no stance, else `none`. No forecast and no label rides along.
- **Packet.** `{ name, blind, disputes, refs }`. Every item goes in `blind`, since no reader has labelled any yet; `disputes` is empty. The file is written once and never overwritten, because the seed and the file together rebuild the batch ids. The builder then calls `voice_batches` once as a check and prints a receipt: population and cards per type, items per type, blanks left out, batches.
