# A promotion ticket carries `answer_by` beside `resolves_by` — design

**Row** `dbe42964` (approved by Rick ~20:00 EDT 2026-09-10) · **Author** Tiffany 💍, implementer on Mr. Radio 🦉's crew · **Branch** `tiffany-petition-answer-by`, based on `chloe-request-door` `38585d23` · **Status** design approved by Mr. Radio at 20:08 EDT, then built. Rehearsal evidence: `2026.09.10-migration-525a4ad4067a-scratch-rehearsal.md`

## The problem

A ticket carries one deadline, `resolves_by`: ask timeout 120 s, plus notification grace 300 s, plus apply margin 60 s, for 480 s in all. That is the **stall** deadline. Rick's **answer window** is the ask timeout alone, 120 s. The ticket carries nothing that tells a reader which number means what, and on 2026-09-10 that misled a relay twice. The source is Finding 6 of `2026.09.10-petition-ratio-exemption-and-deadline.md`.

## Decisions

### 1 · One function reads the ask timeout once and computes both deadlines

`task_promotion_resolver.py` gains:

```python
@dataclass( frozen=True )
class PromotionDeadlines:
    answer_by   : datetime
    resolves_by : datetime

def deadlines_for( requested_at, timeout_fn=promotion_gate.get_ask_timeout_seconds,
                   grace_fn=get_notification_grace_seconds,
                   apply_margin_seconds=APPLY_MARGIN_SECONDS ):
    answer_by   = requested_at + timedelta( seconds=int( timeout_fn() ) )
    resolves_by = answer_by + timedelta( seconds=int( grace_fn() ) + int( apply_margin_seconds ) )
    return PromotionDeadlines( answer_by, resolves_by )
```

- `resolves_by_for` keeps its signature and becomes `deadlines_for( … ).resolves_by`. Its existing tests stay untouched.
- **The timeout is read once.** It is a live setting. If each deadline read it separately, an operator's edit could land between the two reads and stamp a row with an answer window and a stall deadline computed under different timeouts. Computing `resolves_by` from `answer_by` fixes the gap between them at exactly grace + margin.
- **The minting code calls `deadlines_for` once**, in both places tickets are minted (the P0 petition in `create_task`, and the asynchronous 202 in `transition_task`). No site adds the numbers itself.
- **The clock starts at `requested_at`**, the same starting point `resolves_by` uses. The row's own wording is "ask timeout from the petition's own created time", and `requested_at` is the ticket's creation time. The ask actually fires one short transaction later, so the stamp runs early by that much and never late. The docstring says so.

### 2 · Schema: one nullable column and one CHECK

- Column `answer_by timestamptz NULL` on `task_promotion_tickets`, added to `TaskPromotionTicket` as `Optional[datetime]`.
- CHECK `ck_task_promotion_tickets_answer_by_before_resolves_by`: `answer_by IS NULL OR answer_by <= resolves_by`. The model and the migration both carry the literal, and a parity test holds them together verbatim, as the two existing CHECKs on this table are held.
- **No backfill.** Existing rows keep `NULL` and serialize `answer_by: null`. Backfilling would compute old tickets' answer windows from today's timeout setting, and `resolves_by_for`'s docstring forbids exactly that. A NULL says "not recorded", which is true.
- **Why nullable rather than NOT NULL:** NOT NULL needs a backfill, and there is none to give. Both minting sites set the column, and the tests check both.

### 4 · Every response that hands out a deadline hands out both, with the same explanation

| Surface | Today | After |
|---|---|---|
| `POST /api/tasks` 201, `petition` field | `resolves_by` | `answer_by` · `resolves_by` · `deadlines` |
| `POST /api/tasks/{id}/transition` 202 | `resolves_by` | `answer_by` · `resolves_by` · `deadlines` |
| `_serialize_ticket`, used by `GET /api/tasks/promotions/{id}` (`task_promotion_status`) and `GET /api/tasks/promotions` | `resolves_by` | `answer_by` · `resolves_by` · `deadlines` |

`deadlines` is one module constant, `task_promotion_resolver.DEADLINES_NOTE`:

> answer_by is when Rick's answer window closes (the ask timeout). resolves_by is the stall deadline (ask timeout + notification grace + apply margin): a ticket still pending after it is an orphan. An ask unanswered by answer_by is refused, never granted.

The 202 goes one surface past the row's wording. It is the same ticket and invites the same misreading, so I recommend including it.

## Tests — each claim at the real HTTP door, each with its revert arm

The tests use the harnesses of `test_the_petition_at_the_real_create_door.py` (the create door) and `test_the_asynchronous_promotion_resolves_or_shouts.py` (the transition door, the poll and the listing). The ask timeout is set to **77 s**, so a hardcoded 120 fails.

| # | Claim | Arm | Revert that must turn it red |
|---|---|---|---|
| C1 | `answer_by` = `requested_at` + ask timeout | `deadlines_for` with timeout 77 | `answer_by` computed from `resolves_by`, or a literal 120 |
