## 2. The door today

`submit_notification_response` (`POST /api/notify/response`, `src/cosa/rest/routers/notifications.py`) declares one dependency, `Depends( get_websocket_manager )`. It writes the answer to the database through `_submit_response_sync`, and to the in-memory `pending_responses[ notification_id ][ "response_data" ]` that the waiting ask reads. A string answer is stored as `{"value": …, "source": "ui"}`. **Nothing records who posted it.**

**Yes, by code read. Not driven.** Two routes in the same router have no auth dependency:

1. `GET /notifications/senders-visible/{user_email}` lists the sender ids that have written to that user.
2. `GET /notifications/conversation/{sender_id}/{user_email}` returns rows carrying `"id"`, `"state"` and `"response_requested"`.

Eleven more routes in this router also have no auth dependency (for example `/notifications/{user_id}`, `active-conversation`, `bulk/{user_email}` DELETE). **Those are reads and deletes, not this row's door.** They should be filed as their own row rather than folded in here.

## 5. Options

### Option A — authenticate the door, stamp `answered_by` into the stored answer (recommended)

1. The door gains `require_api_key_or_jwt` (which returns 401 on a missing or bad credential), plus a small new dependency that says **which** method succeeded and the account email. For a JWT that is `authenticated_account_email`; for an API key it is none.
2. The server writes `answered_by = { "user_id", "account_email" | null, "method": "jwt" | "api_key" }` into the stored response dict **and** into `pending_responses[…]["response_data"]`, so the waiting ask and the database agree.
3. **Overwrite, don't just approve**: if the caller's body already contains `answered_by`, the server replaces it. This is the same rule as `_resolved_operator_attestation`.
4. The promotion and petition gate (`task_promotion_gate`, via the ask outcome) counts an approval only when `answered_by.method == "jwt"` and `approver_persona_for_account( answered_by.account_email )` resolves to a persona in `ASK_EXEMPT_PERSONAS`. **No literal `"rick"` anywhere** (Mr. Radio's review, 17:21 EDT): the account-to-persona map and the exempt list stay the single source, so changing who the operator is means changing configuration, not this gate. Otherwise it refuses, and the refusal names who answered and why that does not count.
5. The callers change: both proxies pass their listener's JWT into the responder, and the silence-proof script logs in. Browsers and mobile already send a token.

**Pros**
- No database migration. Existing readers (`_extract_response_value`, the `notify_user_sync` poll) read `value` and ignore extra keys.
- Browsers and mobile are unchanged.
- The proxies already hold the credential they need.
- It reuses the account-email seam and the overwrite doctrine the task store has already had reviewed.

**Cons**
- `answered_by` lives inside a JSON blob, so querying who answered means JSON operators rather than a column.
- A proxy answer is recorded under the proxy's login account (for example `mock.tester@…`), which is correct but has to be read as "the proxy", not as a person.

### Option B — dedicated columns on the notification row

Same door dependency. Add `responded_by_user_id`, `responded_by_email` and `responded_via` columns, set in `_submit_response_sync`.

- **Pros**: indexed and queryable; cannot collide with a caller's `response_value` keys.
- **Cons**: needs a schema migration on a shared Postgres, and the in-memory waiter still needs the same fields handed to it separately, so there are two writes to keep in step.

### Option C — JWT only, no API keys

The door accepts only a Bearer JWT, so "who" is always a login account.

- **Pros**: the strongest "who"; the gate check reduces to reading the account.
- **Cons**: it refuses any future API-key caller, and every fleet seat is one. Nothing posts with an API key today, but this closes the option by construction rather than by policy, and that is a ruling for Rick.

## 6. Recommendation

**Option A** — it closes the anonymous door and gives the gate a server-resolved "who" without a migration, and the only callers that need a change already hold the token they need.
