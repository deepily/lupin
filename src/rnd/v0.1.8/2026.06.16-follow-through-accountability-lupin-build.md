## 3. Build items

### 3a. INI key (config rider — never hardcoded)
- `lupin-app.ini` `[Lupin: Baseline]`: **`follow through escalation tick multiplier = 2`** (default 2, tunable).
- Matching `lupin-app-splainer.ini` explanation.
- Consumed via `ConfigurationManager`; the watcher reads the **live manager-tick interval** and multiplies by this factor → `T_escalate`. NO literal `2` in code.

### 3b. Aged-escalation watcher (design §4.3)
- Lives alongside the heartbeat arbiter (`src/cosa/agents/heartbeat_arbiter/`) OR rides the existing poke path — prefer the arbiter loop it already runs.
- Per accountable item in `blocked`/awaiting-manager state: compare `now − awaited_since_ts` vs `T_escalate = live_tick_interval × multiplier`.
- On FIRST crossing → fire **ONE** escalation poke to the manager session + mark the item `escalated` (one-shot; never re-fire). Matters only when the manager-tick has died.

### 3c. §4.5 escalation hygiene — idempotent, self-clearing (THE careful part)
- An awaiting/escalation flag **CLEARS** on EITHER (a) **manager-ack** OR (b) **worker self-park** (valid `.heartbeat-hold-*.json` with documented `work_owed`).
- The arbiter MUST **read the worker's declared hold before** firing any "blocking <worker>" escalation at the manager. A validly-parked worker is NOT a blocking condition.
- Escalation state is **one-shot-then-cleared** — `escalated` marker prevents a repeating alarm.
- *Founding evidence: the arbiter over-fired "blocking María" at me 2–3× this session while María was validly parked — this guard is the fix.*

## 4. Phasing
