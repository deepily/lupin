# Manager-ownership badge missing on live-spawned worker — investigation

**Date:** 2026-06-17 · **Investigator:** Arnold 🪨 (session 6d302c4e, worker under Mr. Radio 🦉)
**Bug (Rick, broadcast):** in the legacy notifications UI focus-bar strip, a newly-spun-up worker's
persona icon does NOT show its manager-ownership corner badge until a full-page force-refresh.
**Status:** ROOT CAUSE NARROWED — the brief's stated assumption is **refuted**; the real cause is a
spawn-time timing/delivery race, which needs a server-side stamp to fix robustly (scope decision for
the manager).

## TL;DR

The brief assumed *"the live-update render paints the icon but omits the badge **code**"* — i.e. a
static client gap. **That is not the case.** Every static link in the chain is correct:

| Link | Verdict | Evidence |
|---|---|---|
| Client live handler renders the badge when the event carries `payload.manager_persona` | ✅ works | `manager_badge_live_update.test.ts` (3/3) — both orderings + null case |
| Server resolves the manager persona from the worker's `spawned_by` | ✅ works | live probe on REAL bridges: arnold→mr radio 🦉, Rio→mr radio, Rachel→Tiberius 👑 |
| `payload` (carrying `manager_persona`) is serialized to the WS client | ✅ delivered | `notification_fifo_queue.py:217` `"payload": self.payload` |
| Full-load path resolves + renders the badge | ✅ works (Rick confirms) | `senders-visible` stamps `manager_persona` (`notifications.py:2578`) → `managerPersonaMap` (`notifications.js:14188-14194`) |

So when the live `voice_persona_assigned` event arrives **with** a resolved `manager_persona`, the badge
appears with no refresh. The miss is therefore a **race**, not a missing render branch.

## The surface (confirmed)

"Each persona's icon … carries a manager-ownership badge" = the **focus-bar session strip**, the only
per-persona-icon-with-corner-badge surface. (The task-list table and fleet-status table group by
owner/manager as **text** and fully re-render every poll — no incremental-icon gap there.)

- Builder: `_applyManagerBadge` → `.cc-strip-manager-badge` (`notifications.js:10750`).
- Icon creation: `_addStripIcon` reads `managerPersonaMap.get(senderId)` (`:10825`).
- Live patch onto an existing icon: `_setManagerBadgeOnStripIcon` (`:10774`).
- Live handler: `handleNotificationUpdate` case `voice_persona_assigned` (`:5681-5727`) — sets the map
  (`:5690`), patches an existing icon (`:5699`), then creates the icon if absent (`:5714`). Both
  orderings covered.
- Server emit: `voice_persona.py:454-464` pushes `voice_persona_assigned` with
  `payload.manager_persona = _resolve_manager_persona(session_id)`.
- Resolver: `voice_persona.py:64-103` — worker bridge `spawned_by` → `get_voice_persona(manager_id)` →
  `{icon,color,name,initial}`.

## Why it still misses live (the race)

`_resolve_manager_persona` returns the badge **now** (settled state) but can return `None` **at the
instant of the worker's `voice_persona_assigned` emit** during the worker's own SessionStart. Candidate
windows (not yet pinned to one with a live spawn capture):

1. **Resolution race at emit.** The emit calls `_resolve_manager_persona(worker)`. If the worker bridge's
   `spawned_by` write (`register_session.py:~984`, Phase 2/3) is not yet visible to the in-container
   server through the bind-mount at the moment Phase 4.5 fires the allocate, the resolver returns `None`
   → `payload.manager_persona = null` → client paints the icon with no badge (test 3 reproduces this
   exact null-payload outcome). By force-refresh, the bridge is settled → `senders-visible` resolves it.

2. **Icon painted by a non-persona event.** If the worker's first event to reach the dashboard is a plain
   notification (→ `createSenderCard` → `_addStripIcon`, `managerPersonaMap` empty → no badge) and the
   `voice_persona_assigned` either carried a null `manager_persona` (race #1) or did not reach this
   dashboard, the icon stays badge-less until full-load.

Both windows yield Rick's exact symptom: **icon present, badge absent, fixed by force-refresh.**

## Recommended fix (robust, race-proof) — make live identical to full-load

Full-load is reliable because **every** sender in `senders-visible` is stamped with `manager_persona`
server-side, independent of any single event's timing. Mirror that on the live path:

- **Server:** stamp `manager_persona` (via `_manager_persona_for_sender_id`) onto the live notification
  envelope for CC senders — not only on `voice_persona_assigned`. (Smallest version: also re-resolve on
  the first plain notification from a spawned worker.)
- **Client:** in `handleNotificationUpdate` / `createSenderCard`, whenever a notification for a CC sender
  carries `manager_persona`, populate `managerPersonaMap` + `_setManagerBadgeOnStripIcon` — so whichever
  live event paints the icon also carries the lineage, exactly like full-load.
- **Belt-and-suspenders (client-only, smaller):** when a CC worker icon is created live with no manager in
  the map, lazily reconcile from the authoritative source (the same data `senders-visible` returns).

**Why this is a manager scope decision:** the brief scoped a client-only fix, but a race-proof fix needs
a server-side stamp on the live envelope. Recommend confirming scope with Mr. Radio before touching the
server push path (blast radius: every `push_notification` caller for CC senders).

## RESOLVED — race-proof server-side fix implemented (Tiffany 💍, 2026-06-17)

**Scope confirmed** by Mr. Radio 🦉 (Rick's TOP priority): ship the smallest correct **server-side**
fix. Implemented the "make-live-identical-to-full-load" option from the recommendation above.

### What changed (production)

1. **Server — `src/cosa/rest/notification_fifo_queue.py`** — new `_stamp_manager_persona( notification_dict, sender_id )`,
   invoked at the `_emit_notification_added` chokepoint (the single live-WS emit path both the
   normal-priority `push()` and the urgent/high `push_notification()` route through). It stamps a
   **top-level `manager_persona`** onto the outbound envelope for every CC worker sender
   (`sender_id` containing `#`), resolved fresh via the existing `_manager_persona_for_sender_id`
   (deferred import — the router imports this module at load, so a module-level import would be
   circular). Best-effort: never raises, skips non-CC senders (no bridge read).

2. **Client — `src/lupin_app/static/js/notifications.js`** — `handleNotificationUpdate` now reconciles
   top-level `manager_persona` for ANY notification **before** the type switch: positive
   `managerPersonaMap.set` + `_setManagerBadgeOnStripIcon`. Purely additive (deletion stays owned by
   the explicit `voice_persona_assigned`/`voice_persona_released` cases).

### Why this fixes the race (self-heal)

The full-load (`senders-visible`) path is reliable because it re-stamps `manager_persona` on EVERY
sender on EVERY poll, independent of any single event's timing. This change gives the **live** path the
same property: even if the worker's `voice_persona_assigned` raced to a null manager at the spawn
instant, the worker's **next** notification (bridge now settled) re-resolves and the client patches the
badge live — **no page refresh**. The previous code carried `manager_persona` only inside the one
`voice_persona_assigned` payload, so a single raced event meant the badge waited for a manual refresh.
