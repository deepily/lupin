## TL;DR verdict

> **A Stop-hook `{"decision":"block","reason":…}` does NOT reliably force a continuation turn on a genuinely-idle / quiescent session under the current Claude Code Stop-hook contract.** The official hooks docs are **ambiguous/under-specified** on whether `block` *auto-submits* a continuation vs merely *injects context and waits* — so the project cannot rely on `block` alone to wake a stopped session. **The tmux keystroke injection is the canonical wake.**
>
> **Recommendation: DOCUMENT — no code change required.** The correct fix already landed: the Stop hook pairs the `decision:block` emit with a same-site `inject_qualifier_via_tmux(...)` keystroke (`stop.py:1492-1509`). This document formalizes that pairing as the canonical wake and records the evidence. The emit format is correct as-is; the keystroke is what produces the turn.

## The question, precisely

When the heartbeat oracle decides a stopped session owes work (`OUTCOME_POKE`), `_run_heartbeat` returns `{"decision":"block","reason":<poke text>}` and the caller emits it on stdout. Per the Stop-hook contract that is supposed to make Claude "continue working." **Does that emit, by itself, cause a genuinely-stopped session (user walked away; the CLI is idle waiting for input) to start a new turn?**

If yes → the tmux keystroke pairing is redundant and should be removed. If no → the keystroke is load-bearing and must be documented as the canonical wake.

## Evidence

### 1. The CC Stop-hook contract is ambiguous (official docs)

The official Claude Code hooks reference documents the Stop-hook block decision as:

```json
{ "decision": "block", "reason": "Tests failed with 3 errors. Fix before stopping." }
```
> "When blocked, Claude sees your reason and **can continue** working on the problem."

The operative phrase is **"can continue"** — it does **not** state *whether* the continuation is **automatic** (the agent loop re-enters immediately, no input) or **deferred** (the `reason` is injected as context and the CLI sits idle until something is actually submitted). The docs also do **not** specify any difference in behavior between an **actively-running** session and a **genuinely-idle** one, nor do they pin the role of `stop_hook_active` beyond loop-prevention. (Confirmed via a documentation sweep: the contract is under-specified on exactly this point — it is a documentation gap, not an answered guarantee.)

**Consequence:** an under-specified contract cannot be the liveness mechanism for a fleet. "Might auto-continue" is not a guarantee you can build the work-owed wake on.

### 2. The codebase already encodes the empirical answer: block ≠ submit

`src/lupin_cli/claude_code/hooks/lib/hook_common.py:717` (the `inject_qualifier_via_tmux` docstring) states the observed behavior verbatim:

> "**After a stop block, CC enters 'waiting for user input' state.** This spawns a background process that sleeps briefly, then uses `tmux send-keys` to inject the text as first-class user input."

That is the empirical finding: the `decision:block` emit leaves the pane **idle/awaiting input** — it does **not** auto-submit a continuation turn on a quiescent session. The keystroke injection (`tmux send-keys -l … && … Enter`, `hook_common.py:782-793`) is what actually re-enters the loop. This mirrors the **battle-tested** pairing already used for the qualifier-continue path (`stop.py:705 & 722`) and peer-DM delivery (`hook_common.py:849`).

### 3. The fix is already in the tree (and is correct)

`src/lupin_cli/claude_code/hooks/stop.py:1492-1509` — the `OUTCOME_POKE` branch of `_run_heartbeat` — already pairs the emit with the keystroke:

```python
poke_reason = result[ "hook_output" ].get( "reason" )
if poke_reason:
    inject_qualifier_via_tmux( session_id, poke_reason, wrap=False )   # the canonical wake
return result[ "hook_output" ]                                         # the decision:block emit (logging + continue RECEIPT)
```

- `wrap=False` → the poke text is injected **verbatim** (a system poke, not a human-voice reply) → **no** speakerphone rider → silent, so it composes with auto-narrate without double-speak.
- This single site is the **shared adapter for both poke branches** (speakerphone `main()` path + Branch-C path), exactly like `_announce_poke`.

### 4. Exactly-one-continuation is preserved (no double-submit risk)

The keystroke pairing cannot cause a runaway re-poke loop:

- **`stop_hook_active` guard** (`stop.py:1552`): a re-fire (the turn the injected keystroke produces) short-circuits at the top of `main()` and never re-enters `_run_heartbeat` — so the block+inject pair fires **at most once** per quiescence.
- **`poke_cap`** bounds `OUTCOME_POKE` across turns (the `c121037b` poke-cap fix, merged `1b474d21`) — a capped session stops poking entirely.

So the emit + keystroke pair is safe: one wake per stop, never a double-submit, never an unbounded nag.

## Why "document, don't change"

The emit format is **already correct** — `{"decision":"block","reason":…}` is the right Stop-hook shape and provides the logging/continue **receipt** that the oracle log and the v2 agentic Poker consume. The only thing the emit *cannot* guarantee is the wake itself (per §1), and that gap is *already* closed by the keystroke injection (§3). There is **nothing to fix in code** — changing the emit format would not buy a stronger guarantee (the docs don't define one), and removing the keystroke would re-open the dark-session failure mode (§2). The correct action is to **formalize the tmux keystroke injection as the canonical wake**, which is what this verdict does.

## Two-line wake hierarchy (for the canonical record)

The fleet has **two** keystroke-injection wake paths; this verdict concerns the first:

1. **Stop-hook self-inject** (`stop.py:1508`) — **1st line.** Pairs every owed-and-stopped self-poke with a same-process keystroke. Fires immediately at turn-end, before the session goes dark. This is the canonical per-session wake.
2. **Arbiter tmux-inject** (`:8001` `fleet_arbiter`) — **2nd line.** A central detector that wakes a stale manager the stop-hook's 1st line did not (e.g. a session that never re-fired, or cross-session staleness). Defense-in-depth, not the primary wake.

Both rely on the **same** mechanical truth this verdict establishes: **a keystroke — not a `decision:block` emit — is what forces a continuation turn on an idle Claude Code session.**

## Verdict (one line)

**`decision:block` does NOT reliably force a continuation on an idle session (contract ambiguous → not relyable-upon); the tmux keystroke injection is the canonical wake; the pairing already landed at `stop.py:1492-1509` and is correct — DOCUMENT, no code change.**
