## 0. TL;DR

Add a **5th liveness signal — `dm_age`** — to the arbiter's freshest-of union, sourced from a
**per-session `dm_ts`** (max `created_at` of `direction='ai_to_ai'` notification rows for that
session). Gate it behind a **runtime flag `arbiter count dm as liveness` (default TRUE)** so
flag-OFF reproduces today's exact 4-signal behavior. The signal is computed/surfaced as a
distinct column for **auditability** regardless of the flag; the flag governs only whether it
**drives the verdict**.

**What it adds beyond the existing bridge-mtime bump** (the Tiberius nuance): an **explicit,
auditable, hook-independent, server-side-sourced** liveness signal that closes the
**MCP-tool / coordination-only** coverage hole (a manager whose only activity is `dm_send` — no
Read/Edit/Bash — and whose bridge-mtime therefore may not bump). See §4.

## 1. The config switch

### Name + shape
- **INI key**: `arbiter count dm as liveness = True`
  - Section: `[Lupin: Baseline]` in `src/conf/lupin-app.ini`; paired explainer in
    `src/conf/lupin-app-splainer.ini` (mandate: every key gets a splainer entry).
  - **DEFAULT TRUE** (Rick's intent — the new behavior is ON by default; the OFF path is the
    rollback / escape hatch).
- **Constructor param** on `ArbiterConsumerJob.__init__`: `count_dm_as_liveness: bool = True`
  (mirrors every other arbiter threshold — config arrives as a constructor param wired by the
  `:8001` factory, NOT read ad-hoc inside the leaf).

### Why ConfigurationManager/INI, NOT heartbeat_settings.py
The toggle-pattern precedent named in the brief — `count_inbound_questions_as_owed` (default
False) read at `stop.py:1376` via `heartbeat_settings.load_heartbeat_settings()` — is the right
**shape** (named bool, documented default, fail-safe) but the **wrong substrate** here:
`heartbeat_settings` reads `~/.claude/settings.json` and is consumed **hook-side** (the Stop
hook). This flag governs the **server-side arbiter** (the `:8001` long-running job), which gets
**all** its config from `ConfigurationManager` (INI) via the factory — not from `settings.json`.
Putting an arbiter flag in `settings.json` would split the arbiter's config across two
substrates. So: **same toggle shape, INI substrate.**

### Runtime-tunability (no bounce) — the seam
The arbiter job is long-running (12h recycle). Reading the INI once at construction would make
the flag bounce-only. To honor "runtime-tunable", inject a **re-read seam**:

```python
count_dm_as_liveness_fn : Optional[ Callable[ [], bool ] ] = None
```

- The `:8001` factory wires it to read the INI **each call** via `ConfigurationManager`
  (`get_config_bool( "arbiter count dm as liveness", default=True )`). `ConfigurationManager`'s
  cache is **mtime-gated**, so a per-poll read is cheap and only re-parses when the INI file
  changes — and **Rick's dev env hot-reloads `lupin-app.ini`** (no `:7999`/`:8001` bounce needed
  for INI-only changes, per `reference_hot_config_reload`). Flipping the key in the INI takes
  effect on the **next poll**.
- Default `None` → `lambda: True` (inert-safe default that reproduces the INI default), so
  in-pool / unit-fake construction needs no wiring. (Mirrors the existing `owed_work_fn` None-seam
  pattern: a None seam is visibly inert, never a hidden behavior change.)
- The flag is read **once per poll** in `_publish_fleet_snapshot` and threaded into
  `build_snapshot(...)` → `compute_liveness(...)`. (Keeps the pure leaves pure; the IO/flag-read
  lives in the orchestrator, like `bridge_discovery_fn` / `owed_work_fn`.)

## 2. DM activity source — `dm_ts`

### Where DMs live
A peer DM is an ordinary **`notifications`** row with `direction='ai_to_ai'` (body inline), written
by `POST /api/dm/send` via `NotificationRepository.create_notification(...)`. Relevant columns:
`direction` (indexed), `sender_*`, recipient session, `thread_id`, `created_at`. The notifications
table **is** the audit substrate (no commons mirror) — authoritative for DM activity.

### The query
A **new read method** on `NotificationRepository` (Tiberius's call on exact name), conceptually:

```
latest_dm_activity_ts_by_session( since: datetime ) -> { session_id: max(created_at) }
```

- Filter `direction == 'ai_to_ai'` AND `created_at >= since` (a `since` ≈ `now - stale_seconds`,
  e.g. last ~1h, bounds the scan — the `ix_notifications_direction` index keeps it cheap).
- Group by session to the **max** `created_at`.
- **SENT vs RECEIVED** — **recommend SENT-only by default** (the sender doing `dm_send` is the
  genuine sign of life; the message is *their* tool activity). RECEIVED-DM liveness is weaker and
  can **over-report**: a parked/dormant recipient does NOT wake on an inbound DM unless it's under
  `/loop` (`reference_dm_send_does_not_wake_parked_workers`), so counting "was DMed at" as the
  recipient's liveness can mark a dark session live. Keep received as a **documented future
  option** (a separate sub-flag if ever wanted), not the v1 default. **→ Open Q for Tiberius (§7).**

### Where it plugs into `build_fleet_view`
Mirror exactly how `commons_ts` is sourced today (`_commons_ts_for_session`):
- The orchestrator (`_poll_once`) runs the dm-activity query **once per poll**, ideally folded into
  the **same one-DB-session-per-poll** that `owed_work_fn` already opens (one `get_db()`, two
  reads). Inject as a seam `dm_activity_fn() -> { session_id: ts }` (default `None` → inert,
  no query, `dm_ts=None`).
- Pass the resulting map into `build_fleet_view(..., dm_activity=...)`. In the per-session VIEW
  build, set a new **`dm_ts`** field (datetime|None), prefix-tolerant on session-id
  (`_who_matches`, like commons). **`dm_ts` confers membership** (a DMing-only session enters the
  roster) — consistent with the union doctrine.
- Keep `dm_ts` **OFF the activity axis** (never `state`, never `last_event_ts`) — it is a LIVENESS
  ts only, exactly like `commons_ts` / `idle_prompt_ts`. (C4: state vs liveness stay orthogonal.)
- **Zero-cost-when-off**: when the flag is OFF, the orchestrator **skips the dm query** entirely
  (`dm_ts=None` everywhere) → identical behavior + identical DB load to today.

## 3. Wiring — the 5th `dm_age` signal

### `compute_liveness` (fleet_render.py) — the freshest-of union
Today (4 signals): `freshest = min(bridge_age, event_age, commons_age, idle_prompt_age)`.
Add `dm_age` as a **5th candidate, gated by the flag**:

```
dm_age = _event_age( view.get( "dm_ts" ), now )      # always computed (auditable column)
candidates = [ bridge_age, event_age, commons_age, idle_prompt_age ]
if count_dm:                                          # flag gate
    candidates.append( dm_age )
freshest = min( present candidates )
```

- The liveness block always returns a distinct **`dm_age_s`** column (present/None) for
  auditability — the render table can show "LIVE by DM @HH:MM" — **but it only enters the
  freshest-of union when the flag is ON.**
- **Flag-OFF → byte-identical to today's 4-signal verdict** (dm_age computed but excluded). This
  is the reversibility guarantee.
- Thread the flag through `build_snapshot(..., count_dm_as_liveness=True)` →
  `compute_liveness(..., count_dm=...)`. Default `True` on both signatures (Rick's intent), so any
  caller that doesn't pass it gets the new behavior; tests pass `False` to assert the off-path.

### STATE vs LIVENESS separation (C4)
`dm_ts` / `dm_age_s` live **only** in the liveness block + as a view liveness ts. `state`,
`holding_on`, `stuck`, and the PROGRESS signature (`last_task_transition_ts`) are **untouched** —
DM activity is a LIFE signal, never a PROGRESS or STATE signal. (This is the deliberate contrast
with `task_transition`, which is progress-only and stays OUT of liveness; `dm` is
liveness-only and stays OUT of progress. The two beacons are mirror-images across the C4 line.)

## 4. What it adds **beyond** the existing bridge-mtime bump (the Tiberius nuance)

**Established fact**: a `dm_send` ALREADY bumps the **sender's** bridge-mtime via the universal
tool-activity stamp (commit `55dd10ac`), and `bridge_age` is already signal #1 in the union. The
in-code comment in `fleet_data_model.py` says it outright: *"Liveness is already broad (PreToolUse
+ PostToolUse bridge-mtime stamps cover a task-writing session)."* So for the **sender**, DM
activity is — in principle — **already** counted. The honest question is what a dedicated DM
signal ADDS.

**The observed discrepancy to explain** (per Tiberius): sessions flagged **MANAGER-STALE despite
active `dm_send`s**. Candidate causes (to confirm with Tiberius — §7):

1. **Deployment gap** *(most likely for the *observed* incident)*. Per
   `reference_arbiter_staleness_threshold_loop_cadence`, the bridge-mtime-as-manager-liveness fix
   (`9694fb11`) **must be deployed** (`systemctl --user restart lupin-arbiter-app.service`) or the
   running `:8001` reads pre-fix code where tool-activity bridge-mtime doesn't count. If THIS was
   the incident's cause, it's an **ops gap, not a design gap** — and any new signal (including
   `dm_age`) equally needs deployment, so DM-as-liveness wouldn't have prevented it. **This must be
   ruled in/out first** so we don't build a feature to paper over a missed restart.

2. **MCP-tool PostToolUse coverage hole** *(the real design gap DM-as-liveness closes)*. If the
   universal bridge-mtime stamp is wired in a PostToolUse matcher that does **not** fire for MCP
   tools (`mcp__cosa-voice__dm_send` is an MCP call, not a native Read/Edit/Bash), then a manager
   whose **only** activity is AI↔AI DMs — pure coordination, zero file tools — **never bumps
   bridge-mtime** and ages into STALE while genuinely alive and talking. This is **exactly Rick's
   target case**: "exhibit signs of LIFE, not progress." A coordinating-only manager is alive but
   makes no progress and touches no files; today's signals can miss it. **DM-as-liveness closes
   this authoritatively** (server-side store, independent of any hook matcher).

3. **Receiver blind spot**. Bridge-mtime only ever covers the **sender**. A session that is the
   subject of active DM traffic is part of a live conversation; a (future, opt-in) RECEIVED-`dm_ts`
   would surface it — with the dormant-recipient caveat from §2.

**Net answer (what it ADDS):** an **explicit, auditable, hook-wiring-independent, store-sourced**
liveness signal. The bridge bump is **implicit, coarse, and dependent on the PostToolUse hook
firing for the tool in question**; `dm_age` is **explicit** (its own column — "this session reads
LIVE because of a DM at HH:MM", vs an opaque bridge mtime), **authoritative** (the notifications
table is the DM audit substrate), and **robust to candidate #2** (covers the coordination-only /
MCP-tool case the bridge stamp may miss). If #1 (deployment) turns out to be the whole story,
DM-as-liveness is still worth it as **belt-and-suspenders redundancy + auditability**, but its
*primary* justification is closing #2.

## 5. 100% L/B/F coverage plan

All logic lives in **pure leaves** (`compute_liveness`, `build_fleet_view`) + the orchestrator
seam — 100% lines/branches/functions is the hard gate (TS-style `c8 --100` n/a; Python
`--cov-fail-under=100`).

| Surface | Branches to cover |
|---|---|
| `compute_liveness` | flag **ON** + `dm_ts` present → dm_age is a candidate; dm_age is the **freshest** → drives verdict; dm_age present but NOT freshest → another signal wins. flag **ON** + `dm_ts` absent → dm_age None, 4-signal behavior. flag **OFF** + `dm_ts` present → dm_age computed, EXCLUDED → byte-identical to 4-signal. flag **OFF** + absent → today. `dm_age_s` column present in all four. |
| `build_fleet_view` | `dm_ts` present → set on view + confers membership (DM-only session enters roster); `dm_ts` absent → None, no spurious member; prefix-tolerant id match; `dm_ts` stays OFF activity axis (state still derives w/o it). |
| flag-read seam | `count_dm_as_liveness_fn` None → default True; returns True; returns False; (factory INI read is the `# pragma: no cover` IO boundary, mirroring `_default_owed_work_fn`). |
| `dm_activity_fn` seam | None → inert (no query, dm_ts None everywhere); fake returns a map → folded in; SENT-only filter asserted. |
| `build_snapshot` passthrough | `count_dm_as_liveness` default True; explicit False threads to compute_liveness. |
| smoke tests | extend `fleet_render.quick_smoke_test` + `fleet_data_model.quick_smoke_test` with a DM-only session (LIVE-by-DM with flag on, offline with flag off). |

The production INI read + the `NotificationRepository` DM query are the **IO boundaries** — marked
`# pragma: no cover` with a same-line reason, exercised at the `:8000` integration tier (like
`_default_owed_work_fn` / `LupinArbiterGateway.from_environment`). All **decision logic** is
unit-tested via injected fakes.

## 6. Behavior / risk

- **"Chatty-but-no-progress" is a FEATURE here, not a bug.** A manager that only DMs (coordinating,
  unblocking peers, no file edits) will read **LIVE** — which is **exactly Rick's intent**:
  *exhibit signs of LIFE, not progress.* This is the **deliberate inverse** of the
  `task_transition` PROGRESS beacon, whose docstring explicitly avoids counting "commons chatter /
  idle DMs" as **progress**. We are NOT re-opening the chatty-but-stuck **progress** blind spot —
  the WHOLE-FLEET-STALL detector reads the **progress** signature (`last_task_transition_ts`),
  which `dm_ts` deliberately does **not** feed (§3, C4). DM activity moves the **liveness** verdict
  only. So a chatty-but-stuck session reads **LIVE but not PROGRESSING** — exactly the right
  two-axis truth.
- **Over-reporting guard**: recommend **SENT-only** (§2) so a dormant recipient isn't marked live
  by inbound traffic it never woke for.
- **Reversibility**: flip the INI key to `False` → next poll reproduces today's 4-signal behavior
  byte-for-byte (dm_age computed for audit, excluded from verdict); no bounce (hot-reload), no
  redeploy, no data migration. Default TRUE means the feature is on out of the box; the flag is the
  kill-switch.
- **Observer invariant intact**: the DM query is swallow-safe (a query failure → `dm_ts=None`,
  fail-safe to the other 4 signals), exactly like every other arbiter seam. Bounded scan
  (`since` window + indexed `direction`).
