## 1. Problem — liveness ≠ availability

The fleet today can tell whether a session is **alive**. It cannot tell whether a session has **free capacity**. Those are different questions:

- *Liveness*: "is this session processing / recently active?" (heartbeat, bridge-mtime, `commons_who` recency).
- *Availability*: "could this session take on another unit of work right now?"

A manager that is **held / blocked-on-peers** — e.g. Mr. Radio while L3/L4 build — actually has **free bandwidth** to accept another lane. Nothing advertises that. So:

- **No cross-manager load-balancing.** When one manager is overloaded and another is idle-but-alive, there is no signal to shift a lane. The Mr-Radio↔Tiberius L1 carve-up this session was done *by hand over DM*; it should be derivable from a public availability signal.
- **The arbiter conflates "held with capacity" with "stalled."** It is already false-escalating held managers (observed live this session). Availability is the missing dimension that lets it tell "deliberately holding, has capacity" from "stuck."
- **Rick can't see fleet capacity** at a glance — who's free, who's saturated.

## 2. Current signals (inventory)

| Signal | What it says | Gap |
|---|---|---|
| `commons_who` → `last_post_ts` | recency of last commons post | liveness only; silent on capacity; a busy session that doesn't post looks "stale" |
| Stop-hook hold file `.heartbeat-hold-<sid>.json` | `work_owed` + `awaiting` + ttl | **per-session / local** — read only by that session's own Stop hook; no peer/arbiter consumes it for availability |
| Task store rows | owed items (queued / in_progress / blocked) | encodes *what is owed*, not *spare capacity*; no "available" concept |
| Arbiter | infers blocked / stalled from store + bridge | no availability axis → false-escalates held-with-capacity |

**Conclusion**: every existing signal is about *liveness or owed-work*. None is a public *capacity/availability* advertisement.

## 3. Proposed — an explicit AVAILABILITY dimension

A small state set, **orthogonal to liveness**, published per session:

| State | Meaning |
|---|---|
| `BUSY` | active owned lanes at/above soft cap — do not assign more |
| `HELD_WITH_CAPACITY` | blocked on peers (hold present, `awaiting:peer`) BUT `open_capacity > 0` — could accept work |
| `IDLE_AVAILABLE` | no owed work, free to take a lane |
| `OFFLINE` | not live (liveness already covers this; included for a single readout) |

Plus a scalar: **`open_capacity = soft_cap − active_owned_lanes`** (soft_cap default 8/manager per the manager-autonomy envelope).

**Key property**: availability is **derived, not hand-set** — computed from `(active in_progress lane count, hold state, soft_cap)` and **emitted on transition** (lane start/done, hold write/clear), never per-turn (avoids the token/load multiplier that killed the old per-Stop push).

## 4. Where to publish — options + recommendation

**Option A — store-backed availability (RECOMMENDED).** A per-session availability row (dedicated `/api/fleet/availability` table or a typed presence item) written on transition; surfaced via `GET /api/fleet/availability` and the existing fleet/notifications UI card.
- *Pro*: the arbiter and UI **already read the store** — one source of truth; durable; queryable by peer managers; composes directly with the L1 done/blocked-on-user detector work.
- *Con*: new schema + endpoint.

**Option B — commons presence topic.** `commons_post` to a `presence`/`availability` topic on transition.
- *Pro*: zero schema; peers already read commons.
- *Con*: ephemeral, polling-based, and a known token sink (`commons_read` cost) — conflicts with the #1 token-efficiency goal.

**Option C — extend the session bridge.** Add availability fields to the bridge, read by the arbiter + a new manager API.
- *Pro*: bridge is already the central liveness substrate.
- *Con*: host-side; less directly queryable by peer manager sessions.

→ **Recommend A.** Store-backed, single source of truth, consumed by the systems that already read the store (arbiter + UI), and it slots into the L1 detector rework instead of fighting it.

## 5. Consumers

- **Peer managers** — load-balancing: a manager with overflow lanes queries availability and hands a lane to an `IDLE_AVAILABLE` / `HELD_WITH_CAPACITY` peer (the manual carve-up, automated).
- **Arbiter** — distinguishes `HELD_WITH_CAPACITY` from stalled → suppresses the false MANAGER-DOWN / WHOLE-FLEET-STALL escalations (this is the *positive* sibling of L1's blocked-on-user exclusion).
- **Rick's UI card** — fleet capacity at a glance: who's free, who's saturated.

## 6. Relationship to existing work

- **Hold file**: `HELD_WITH_CAPACITY` ≡ "fresh hold present (`awaiting:peer`) AND `open_capacity > 0`." Availability can be derived from the hold + store rather than a wholly new artifact.
- **Engagement #7 (follow-through-accountability)**: accountability tracks *who owes what*; availability tracks *who is free* — two halves of fleet work-routing.
- **Arbiter L1 (Tiberius)**: L1 teaches the arbiter *done / blocked-on-user* awareness (don't escalate). Availability adds *has-capacity* awareness. Strong candidate to **fold the consumer side into L1** so the arbiter gains both at once.

## 7. Open questions for Rick
