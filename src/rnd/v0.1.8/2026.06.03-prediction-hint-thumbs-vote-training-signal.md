## 2.1 Existing "vote on appropriateness" UI — found, and it validates Option A

Rick recalled an existing UI to "vote on the appropriateness of a response." The dig found exactly one such mechanism:

- **Admin Decision-Proxy ratification** — `proxy-ratify.html` (Trust Dashboard): Approve / Reject (modal + inline quick-action + bulk) with an optional **feedback** textarea → `POST /api/proxy/ratify/{decision_id}?approved=&feedback=&user_email=` → `ProxyDecisionRepository.ratify()` sets `ratification_state = approved|rejected`, `ratified_by`, `ratified_at`, `ratification_feedback` on the Postgres `proxy_decisions` table, then `trust_repo.update_after_ratification(...)`.
- **How that signal enters the calculation:** ratified cases feed the CBR majority vote — `confidence = max_similarity × verdict_consistency`, where `verdict_consistency = majority_count / len(cases)`. Approved cases reinforce the verdict; the trust counters gate autonomy.

**This is the pattern to mirror — NOT the table to reuse.** Critical distinction the dig surfaced:
- The **prediction engine** (what generates the notification hints) learns from its OWN CBR store, the LanceDB `ProxyDecisionEmbeddings` table (`add_decision()` / `find_similar()`), which ALREADY carries a `ratification_state` field and an `update_ratification_state(id, new_state)` method.
- BUT `find_similar()` currently filters only by `category` / `data_origin` / `response_type` — it does **NOT** yet weight or filter by `ratification_state` (`proxy_decision_embeddings.py:211-225`). And `prediction_engine.py:1235` records outcome cases as `ratification_state="not_required"`.

**So the implementation hook for "incorporate my signal into the calculation":**
1. 👍 → write/flip the hint's case to `ratification_state="approved"` (organic) in the prediction engine's CBR store; 👎 → `"rejected"`.
2. Make the prediction retrieval **ratification-aware** (the piece that does not exist yet): in the per-engine vote tally, **up-weight** `approved` cases AND treat `rejected` cases as a **NEGATIVE vote against** their `decision_value` — i.e. the engine actively **steers away** from a thumbs-downed answer rather than merely ignoring it (Rick's decision 2026-06-03: down-vote = negative example, not exclude). Approved cases reinforce; rejected cases penalize their value in the majority tally — mirroring, and extending, how the admin ratification drives `verdict_consistency`.

This is the minimal, faithful extension: same conceptual mechanism as the existing appropriateness vote, applied in the prediction engine's own store where the hints come from.

Goal (Rick's words): a 👍/👎 control on the LLM-generated prediction hint so that "when I see the LLM-related value that I like I can give it a thumbs up… accumulating my agreement with these calculated predicted answers at runtime… stirring in clear high-value training signal."

**Key reuse insight:** the CBR store's `add_decision()` is already the mechanism by which a confirmed answer influences future predictions. A thumbs-up that writes an approved organic case IS "stirring in training signal" with no new learning machinery.

## 2. The architectural fork (Rick to confirm)

**What does a 👍 DO to the signal?**

- **A. Confirm-as-case (RECOMMENDED).** 👍 → `add_decision(question, predicted_value, ratification_state="approved", data_origin="organic")`; 👎 → store a rejected/down-weighted marker excluded from retrieval.
  - Pros: most direct realization of "accumulate my agreement"; reuses `add_decision`; improves future similar predictions immediately; closes the human-confirmed loop.
  - Cons: mutates the live CBR store at runtime → needs dedup (repeated 👍 on near-identical questions) + a small down-weight/exclude path for 👎 in retrieval.
  - Wrong if: the CBR store should stay admin-curated only.
- **B. Vote-tally only.** Record votes in a new `prediction_votes` table; weight retrieval by vote ratio later.
  - Pros: clean separation, reversible, no immediate CBR mutation. Cons: inert until a separate weighting step is built.
- **C. Approve-as-response.** 👍 auto-submits `predicted_value` as the user's actual answer via the existing response loop.
  - Pros: zero new learning path. Cons: conflates "I like this" with "this is my answer"; pollutes accuracy stats.

## 3. Proposed design (assuming Option A — to be confirmed)

**Backend**
1. `prediction_votes` table OR reuse CBR `add_decision` directly + a thin `PredictionVote` audit row (`{id, notification_id, vote, user_email, voted_at, predicted_value_snapshot, confidence_snapshot}`) for traceability/idempotency.
2. `POST /api/notify/prediction-vote/{notification_id}` (JWT) — body `{vote: "up"|"down", feedback?: str}`. On `up`: dedup-guarded `add_decision(...ratification_state="approved", data_origin="organic")`; on `down`: record rejected marker. Returns `{status, vote, case_id?}`. Mirrors the dismiss endpoint's shape.
3. Repository method `record_prediction_vote(...)` (idempotent per notification+user — re-voting updates, not duplicates).
4. WebSocket emit `prediction_vote_recorded` so other sessions/devices reflect the vote.
5. Ratification-aware vote tally: `approved` cases up-weight their `decision_value`; `rejected` cases cast a **negative vote** against their `decision_value` (steer-away — Rick's decision), so a downvoted answer is actively penalized in the majority tally, not just dropped. Config knob for the negative-vote magnitude.

**Frontend**
6. `buildPredictionVoteControls()` rendering 👍🏼/👎🏼 buttons under the hint (medium-light skin tone, U+1F3FC — Rick's preference, NOT default yellow; see [[feedback-thumbs-emoji-skin-tone]]) (only when `confidence ≥ prediction hint vote min confidence threshold`); wired to `window.notificationsUI.votePrediction(notificationId, "up"|"down")` → `authedFetch` POST → reflect selected state. (Note the inline-onclick global lesson: use `window.notificationsUI`, never a copied dead global — see [[feedback-verify-inline-onclick-global-resolves]].)
7. CSS for the vote control + selected/active state.

**Config** (`lupin-app.ini` + splainer)
8. `prediction hint voting enabled = true`
9. `prediction hint vote min confidence threshold = 0.50`
10. (Option A) `prediction hint downvote retrieval policy = exclude|downweight`

**Tests (full pyramid — per testing mandate)**
- Unit: repository `record_prediction_vote` (up→approved organic case, down→rejected, idempotent re-vote); endpoint success / bad-id 400 / error 500; dedup guard.
- Integration (:8000): DB-backed 👍 writes a retrievable approved case; 👎 excluded from `find_similar`; re-vote updates in place.
- E2E (:8000): hint renders vote buttons above threshold / hidden below; click 👍 persists + reflects selected state; global-resolution guard on the new onclick (reuse the `test_inline_onclick_globals_resolve` pattern).
