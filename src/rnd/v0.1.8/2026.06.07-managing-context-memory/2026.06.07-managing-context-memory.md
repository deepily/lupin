# Programmatic Context / Memory Assessment in a Claude Code Session

There are **two distinct mechanisms** that answer two different questions. The
distinction matters because they are frequently conflated.

---

## 1. Cumulative token accounting (always available)

Every `ResultMessage` carries a `usage` dict; per-step `AssistantMessage.usage`
and `ResultMessage.model_usage` give per-model breakdowns.

- Per-step usage: `AssistantMessage.usage` (+ `AssistantMessage.message_id`)
- Per-model breakdown: `ResultMessage.model_usage`
- Each assistant message wraps a nested message with an `id` and a `usage`
  object containing token counts.

The `usage` dict exposes:

- `input_tokens`
- `output_tokens`
- `cache_creation_input_tokens`
- `cache_read_input_tokens`

This is **flow accounting** — what each turn cost — *not* occupancy.

> Cost caveat: `total_cost_usd` is a **client-side estimate** computed locally
> from a price table bundled at build time, not authoritative billing data. Use
> the Usage and Cost API / Console for billing.

---

## 2. Context-window occupancy breakdown (the real target)

This is the programmatic equivalent of the `/context` slash command. Historically
a gap — the SDK surfaced only cumulative usage with no per-category breakdown.
That gap is now closed: `ClaudeSDKClient` exposes an **async** `get_context_usage()`
method.

Return type: a `ContextUsage` dataclass — "a breakdown of current context window
usage by category, matching the data shown by the `/context` command in the CLI."

### Fields

| Field                 | Meaning                                                        |
| --------------------- | -------------------------------------------------------------- |
| `categories`          | `list[ContextUsageCategory]` — tokens per category             |
| `totalTokens`         | Total tokens currently in the context window                   |
| `maxTokens`           | Effective ceiling (may be reduced by the autocompact buffer)   |
| `rawMaxTokens`        | Raw model context window size                                  |
| `percentage`          | Percentage of window used (0–100)                              |
| `model`               | Model the usage is calculated for                              |
| `isAutoCompactEnabled`| Whether autocompact is enabled for this session                |
| `memoryFiles`         | CLAUDE.md and memory files                                     |

## Minimalist working pattern

```python
from claude_agent_sdk import ClaudeSDKClient

async def context_pressure(client: ClaudeSDKClient) -> float:
    ctx = await client.get_context_usage()
    for cat in ctx.categories:                 # list, not dict — see caveat below
        print(f"{cat.name:<16} {cat.tokens:>8,}")
    print(f"{ctx.totalTokens:,} / {ctx.maxTokens:,} ({ctx.percentage:.1f}%)")
    return ctx.percentage

async with ClaudeSDKClient() as client:
    await client.query("Analyze this codebase")
    async for _ in client.receive_response():
        pass
    if await context_pressure(client) > 75:
        await client.query("/compact")
```

## Caveats

1. **Client-only.** `get_context_usage()` lives on `ClaudeSDKClient`, not on the
   one-shot `query()`. It requires a live, connected session. Fine for a sidecar
   topology; won't work in fire-and-forget `query()` loops.

2. **Field-access discrepancy in circulating examples.** The original
   feature-request threads (`sdk-python #507`, `claude-code #16587`) illustrated
   dict-style access like `context.categories['messages']`. The **shipped** type
   is a `list[ContextUsageCategory]`, so iterate objects rather than index a dict.
   Do not copy the issue snippets verbatim. The exact attribute names *inside*
   `ContextUsageCategory` are unconfirmed here (likely `name`/`tokens`, possibly a
   percentage) — verify with `print(vars(cat))` or the source before wiring it in.

3. **Version-gate it.** This landed relatively recently. Use a defensive
   `hasattr(client, "get_context_usage")` guard, or pin a known-good version, so
   older wheels don't hard-fail.

---

## Application to a coordinator sidecar

For a five-state machine, `get_context_usage()` is the natural trigger source for
the `QUIESCING → RELOADING` transition: poll `percentage` against
`isAutoCompactEnabled` and the `maxTokens` / `rawMaxTokens` delta to decide whether
to pre-empt autocompact yourself versus letting the runtime do it.
