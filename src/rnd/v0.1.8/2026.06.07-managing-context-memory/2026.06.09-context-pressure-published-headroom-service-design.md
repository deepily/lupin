## 2. The new requirement, precisely

1. **Read-only**, no side effects, no auto-action. A pure sensor read.
2. **Published by the arbiter service**, consumable by **anyone with the API key**.
3. A **summary object keyed by persona** (a map `persona → record`, not a list).
4. Each record's headline stat = **headroom to a soft budget line**:
   - window `1,000,000` → budget line at **50%** → `500,000` tokens
   - window `200,000` → budget line at **75%** → `150,000` tokens
   - headroom = `budget_ceiling − current_occupancy` (tokens remaining before the line).

The two fractions are a **policy** (Rick's): hold the big `[1m]` window to a generous-headroom
half, hold the 200K tier to a later three-quarters line. Both are **config-driven** (§6) so
they're tunable without code.

## 3. Headroom math

Per worker (all derived from the Phase-1 leaf + the pinned `window_size`):

```
occupancy_tokens          = last_prompt_size          # input+cache_creation+cache_read (the /context total)
budget_fraction           = policy[ window_size ]      # 0.50 for 1M, 0.75 for 200K (config map)
budget_ceiling_tokens     = round( window_size * budget_fraction )   # 500_000 / 150_000
headroom_tokens           = budget_ceiling_tokens - occupancy_tokens # may be negative (over budget)
consumption_pct_of_window = 100 * occupancy_tokens / window_size
headroom_pct_points       = budget_fraction*100 - consumption_pct_of_window  # window-points to the line
status                    = "over_budget" if headroom_tokens < 0 else "within_budget"
```

- **Occupancy basis (Q1 — RESOLVED: expose both, no single headline).** Publish **two
  co-equal** occupancy figures and a headroom for each — neither is privileged as "the"
  number; the consumer chooses:
  - `occupancy_tokens` = `last_prompt_size` (measured current consumption; the calibrated
    `/context` total) → `headroom_tokens_current`.
  - `next_prompt_estimate` = `last_prompt_size + last_output + pending_input` (forward,
    conservative) → `headroom_tokens_forward`.
- **Sign-honest**: headroom can go negative; we report the real number, never clamp
  (so "over budget" is visible, not hidden).

Worked example — a 1M worker at 205k occupancy:
`ceiling = 500_000`, `headroom = 295_000` tokens, `consumption = 20.5%`, `headroom = 29.5`
window-points to the 50% line, `status = within_budget`.

## 4. The published object (keyed by persona)

`GET /api/arbiter/context-pressure` (or the `context_pressure` section of `/state`):

```jsonc
{
  "generated_at": "2026-06-09T17:30:00+00:00",          // UTC; consumers convert to EDT
  "policy": { "1000000": 0.50, "200000": 0.75, "default": 0.50 },
  "personas": {
    "Tiberius": {
      "session_id"               : "7b76ad86",
      "window_size"              : 1000000,
      "budget_fraction"          : 0.50,
      "budget_ceiling_tokens"    : 500000,
      "occupancy_tokens"         : 205000,         // current (measured)
      "next_prompt_estimate"     : 206400,         // forward (conservative)
      "consumption_pct_of_window": 20.5,
      "headroom_tokens_current"  : 295000,         // ceiling − occupancy
      "headroom_tokens_forward"  : 293600,         // ceiling − next_prompt_estimate
      "headroom_pct_points"      : 29.5,           // window-points to the line (current)
      "status"                   : "within_budget",
      "liveness"                 : "ACTIVE",
      "last_turn_age_s"          : 41
    },
    "maria": { "session_id": "42954f0b", "liveness": "IDLE", "status": "idle",
               "window_size": 1000000, "occupancy_tokens": null, "headroom_tokens": null }
  },
  "summary": { "personas": 4, "within_budget": 4, "over_budget": 0, "idle_or_unknown": 1 }
}
```

- **Keyed by persona** per Rick's ask. **(Q2 — RESOLVED: no collision guard.)** The
  voice-persona naming system never mints colliding names, so persona keys are unique by
  invariant — no suffixing, no collision flag, no defensive code against an impossible case.
- **IDLE / DEAD / UNKNOWN** workers appear with `occupancy_tokens: null` + a `status` of
  `idle`/`unknown` (no false zero — absence of a fresh measurement is explicit).
- Shape is a **superset** of Rachel's §3 list shape — same per-worker facts, re-keyed by
  persona, plus the four budget fields. One writer can emit both views.

## 5. Architecture (reuses the Phase-2 plumbing)

```mermaid
flowchart LR
    subgraph A[":8001 lupin-arbiter-app"]
        W["context-headroom writer<br/>(standing cadence, 60s)"] -->|assess_fleet_context_pressure| L["context_pressure leaf (P1, live)"]
        L -->|list[WorkerContextPressure]| W
        W -->|apply budget policy §3<br/>key by persona §4| SEC["store.set_section<br/>'context_pressure'"]
    end
    SEC -->|GET /state composite| M["7999 /api/arbiter/context-pressure<br/>(thin proxy, API-key gated)"]
    M --> C["any API-key holder<br/>(read-only)"]
```

- **Writer** on `:8001`: same shape as the health/fleet loops; each tick calls the live leaf,
  applies the budget transform (§3), keys by persona (§4), writes the `context_pressure`
  section. **Read-only — no commons emission, no notify** (that recommender half stays in
  Rachel's Phase 2/3 lineage; this service is a pure sensor read).
- **`:7999` surface**: a **dedicated** `GET /api/arbiter/context-pressure` that pulls `:8001/state`
  and returns just the `context_pressure` section. Gated by `require_api_key_or_jwt` →
  "anyone with the API key." (The section also rides the existing `/api/arbiter/fleet-state`
  composite for free; the dedicated endpoint is the clean public surface.) *(Open Q3.)*
- `:8001` is localhost-only + unauthenticated → **not** the public surface; the `:7999`
  proxy is. Consumers always go through `:7999`.
