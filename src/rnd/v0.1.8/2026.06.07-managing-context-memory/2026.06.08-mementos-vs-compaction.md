# Memento-on-Clear vs. Native Compaction: A Context-Boundary Strategy for the Lupin/CoSA Fleet

## TL;DR
- **For Lupin/CoSA, the optimal policy is a hybrid keyed to your existing assessor thresholds: let native compaction (microcompaction + the tiered auto-compact) run for *mid-pressure intra-task continuity*, but reserve harvest+respawn-with-memento for *task boundaries and CRITICAL pressure*.** Compaction wins on token economy and latency for continuation; the memento wins decisively on determinism, auditability, and cross-boundary fidelity — the two axes you cannot get from an opaque in-place summary.
- **Determinism is the deciding factor.** Native compaction is a non-inspectable, mid-task-triggered LLM rewrite with documented failure modes (silent constraint reversion, cascading hallucination, ~7–12K-char summaries that drop the user's verbatim intent). A self-authored memento is a version-controllable artifact you can diff, lint, and gate — the only path that gives you reconstruction you can reason about *before* the boundary, not after.
- **The cache economics roughly converge.** Both `/clear`+reload and a full Tier‑3 compaction abandon the warm KV prefix and force a cold re-read; compaction's "savings" come from a *smaller* re-warmed prefix, not from cache reuse. Since your workers are tmux CLI processes on a 5-minute-TTL prompt cache, idle gaps already cold-blow the cache between turns, which materially weakens the "compaction preserves cache" argument in your specific deployment.

## Key Findings

### 1. Native compaction is a three-tier, cache-economized pipeline — not a single summarizer
Claude Code's context management is three composed tiers, run in order before each API call (budget → microcompact → full compaction):
- **Tier 1 / Microcompaction:** lightweight, no-LLM cleanup that clears old tool results, keeping only the ~5 most recent inline and replacing the rest with `[Old tool result content cleared]`. Large tool outputs are demand-paged to disk (default ~50K-char threshold per tool; `Read` opts out) and replaced with a ~2KB preview plus a file path. This is the "hot tail / cold storage" pattern.
- **Tier 2:** API-level server-side strategies (thinking-block and tool-result clearing) gated on token thresholds, deleting whole blocks deterministically.
- **Tier 3 / Full compaction:** a forked LLM summarization into a strict 9-section XML template (Primary Request & Intent, Key Technical Concepts, Files & Code, Errors & Fixes, Problem Solving, **All User Messages**, Pending Tasks, Current Work, Optional Next Step). The model writes an `<analysis>` chain-of-thought scratchpad that is *stripped*, keeping only the `<summary>`. After summarization, Claude Code rebuilds: boundary marker + summary + the 5 most-recently-read files (capped 50K tokens) + re-injected skills (≤25K) + re-announced tools + re-run hooks + restored CLAUDE.md. A continuation message tells an autonomous agent "don't acknowledge the summary, just continue." Notably, the summarization prompt explicitly instructs the model to preserve security-relevant constraints *verbatim* so they remain in effect after compaction.

The whole architecture is governed by **prompt-cache economics**. On the warm path, microcompaction does *not* rewrite local messages — it queues `cache_edits` blocks that tell the server to surgically delete tool-result blocks by `tool_use_id` without touching the cached prefix. The Tier‑3 summarization call reuses the *same* system prompt, tools, model, and message prefix (the compaction instruction is appended as a user message) so it hits cache; the alternative — a dedicated summarizer system prompt — was measured at a ~98% cache-miss rate.

### 2. Thresholds and reserves (mid-2026)
- **Auto-compact trigger:** community source-code analysis converges on *effective context window − ~13,000 tokens*, where effective window = model window − min(max_output, ~20,000). Claude Code's `/context` grid labels this ~13K reserve the "Autocompact Buffer."
- **Reported usage threshold** sits around **~83.5%** on the 1M window (claudefa.st/Verdent), with a ~33K reserved buffer; other sources cite "near 95%" historically, and the threshold has been pushed *down* over time to protect working memory. Configurable via `CLAUDE_CODE_AUTO_COMPACT_WINDOW` / `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`; there are open feature requests (#34126) for per-model thresholds (e.g., a user wanting Opus@30% but Sonnet subagents@90%).
- **Circuit breaker:** auto-compaction pauses after 3 consecutive failures, prompting manual `/clear`.
- **Compact boundary semantics:** compaction is non-destructive on disk — it *appends* a `compact_boundary` system document (subtype `compact_boundary`) with `compactMetadata` (trigger type + pre-compaction token count) to the JSONL. Post-compaction API requests send only summary + recent messages (~85% payload shrink in one mitmproxy experiment). In SDK/headless mode an `SDKCompactBoundaryMessage` signals the break.
- **1M window:** GA on Opus 4.6/Sonnet 4.6 (no surcharge since March 2026). The lost-in-the-middle effect "doesn't wait for you to run out of room" — practitioners recommend compacting at ~60% on a 1M window, not at the auto-trigger.

### 3. Compaction's quality failure modes are real, silent, and mid-task
- **Silent constraint reversion** is the dominant production failure: an arXiv study ("Facts as First Class Objects") documents that after 3× compaction, non-default constraints (a specific Redis veto, a GDPR region, a tested retry limit, an API-versioning strategy) are lost and the model **silently reverts to reasonable defaults** while remaining confident and coherent. As that paper puts it, this is "not accuracy degradation within the window, but silent reversion to defaults after compaction."
- **Cascading hallucination:** Claude Code issue #36068 ("URGENT: Auto-Compaction Regression") documents auto-compaction dropping the user's verbatim intent/corrections, causing agents to act on assumptions and forcing manual re-alignment cycles.
- **Lossy-vs-verbatim:** Morph's taxonomy distinguishes LLM summarization (high compression, human-readable, hallucinates, paraphrases exact details) from verbatim deletion (zero hallucination, fully inspectable, lower compression). The "dumb zone" / faithfulness-hallucination onset is commonly reported around 125K–150K tokens on frontier models.
- **Autocompact's core defect is timing:** it fires *mid-task* at a threshold, not at a semantic boundary, so the summary "decides for itself" which decisions survive. Manual `/compact` at a phase boundary, with a focus hint, is consistently reported as producing materially better summaries.
- **"Context anxiety":** Anthropic itself documents (in "Scaling Managed Agents") that Claude Sonnet 4.5 "would wrap up tasks prematurely as it sensed its context limit approaching" and that adding context resets eliminated the behavior; Cognition observed the same in Devin and fixed it by capping usage *below* a larger window. This is direct evidence that proximity to the boundary degrades behavior before any data is actually lost — an argument for harvesting early, not late.

### 4. The research frontier favors curated external artifacts over in-place rewriting
- **Anthropic's own guidance** (effective-context-engineering, Sept 2025): context is finite with diminishing marginal returns ("context rot"); the discipline is, verbatim, "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." They explicitly endorse **structured note-taking / agentic memory** (write notes to files outside the window) and **sub-agent context offloading** alongside compaction.
- **Anthropic's long-running-harness work** (Nov 2025) is essentially a memento pattern: an **initializer agent** sets up the environment, and each coding agent reads a `claude-progress.txt` + git log + a JSON feature list to orient on a fresh context window, then leaves structured artifacts. Critically, verbatim: *"However, compaction isn't sufficient. Out of the box, even a frontier coding model like Opus 4.5 running on the Claude Agent SDK in a loop across multiple context windows will … fall short of building a production-quality web app if it's only given a high-level prompt."* They also found the model is **less likely to overwrite JSON than Markdown** (it treats JSON as "code").
- **Memory tool + context editing** (Sonnet 4.5): Anthropic's own news post "Managing context on the Claude Developer Platform" (Sept 2025) states verbatim that "combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement. In a 100-turn web search evaluation, context editing enabled agents to complete workflows that would otherwise fail due to context exhaustion—while reducing token consumption by 84%." *(Self-reported internal evals.)*
- **MemGPT/Letta lineage:** OS-style virtual memory hierarchy (core/in-context vs. archival/external), agent self-edits memory blocks; when context fills, history is **recursively summarized** into a memory block but raw messages remain retrievable. Letta's "filesystem is all you need" benchmark states verbatim: "This simple agent achieves 74.0% on LoCoMo with GPT-4o mini and minimal prompt tuning, significantly above Mem0's reported 68.5% score for their top-performing graph variant" — the thesis being "memory is more about *how agents manage context* than the exact retrieval mechanism." The Letta Leaderboard isolates read/write/update memory ops with a penalty for extraneous operations (top performers: Claude 4 Sonnet, GPT‑4.1, GPT‑4o).
- **Sleep-time compute** (Letta/UC Berkeley, arXiv:2504.13171): precompute "learned context" during idle time. The abstract states verbatim that "sleep-time compute can reduce the amount of test-time compute needed to achieve the same accuracy by ∼5× on Stateful GSM-Symbolic and Stateful AIME and … by scaling sleep-time compute we can further increase accuracy by up to 13% on Stateful GSM-Symbolic and 18% on Stateful AIME"; cost per query drops ~2.5× when amortized across related queries (Multi-Query GSM-Symbolic); the SWE-Features case study drops live answer-time tokens from ~10K to ~3K (Claude 3.7 Sonnet). Directly relevant: your "harvest" phase *is* a sleep-time-compute step.
- **Cognition (Devin) vs. Anthropic:** Cognition's Walden Yan, "Don't Build Multi-Agents" (June 12, 2025), argued for single-threaded agents with a *separate* compression model, warning parallel sub-agents are fragile because "actions carry implicit decisions, and conflicting decisions produce bad results" (the Flappy-Bird example: one sub-agent builds a Super-Mario background while another builds a non-game-asset bird). Core principle: **"Share context, and share full agent traces, not just individual messages."** By March 2026 Cognition shipped "Managed Devins" (coordinator + isolated-VM sub-agents) — converging on the orchestrator-with-isolated-subagents pattern. Devin uses fine-tuned summarization models at agent-agent handoff boundaries.

### 5. Cache economics of `/clear`+memento vs. compaction — the decisive nuance for your deployment
- **Pricing (2026):** cache write = 1.25× base (5m TTL) or 2.0× (1h TTL); cache read = 0.10× base (90% discount). Break-even: ~2 reads (5m) or ~3 reads (1h). Write is ~12.5× the read rate.
- **`/clear`:** fully blows the cache — the new session re-reads CLAUDE.md, re-warms files, pays full write price on the new prefix.
- **Compaction:** the *compaction call itself* is a cache hit (same prefix), but **after** compaction the summary replaces the history as the new prefix, so every subsequent turn warms a brand-new cache. As one careful cost analysis puts it: "The net cost is similar to 'cache blown away,' but the mechanism is prefix replacement, not cache invalidation." So compaction does **not** preserve your warm prefix going forward — it only makes the re-warmed prefix smaller.
- **The 5m-TTL regression:** Claude Code issue #46829 presents JSONL evidence that the default cache TTL silently regressed from 1h to 5m around early March 2026, causing a ~20–32% cache-creation cost increase; any pause >5 min cold-blows the entire cached context. For a tmux fleet with bursty, human-in-the-loop (voice) cadence, **you are very likely already paying cold-cache costs between turns**, which flattens the cache advantage compaction would otherwise have over `/clear`.
- **`--resume` is a cache trap:** issues #27048 and the cache-fix repo document that session resume / plugin-state changes / non-deterministic tool ordering silently bust the cache (up to ~20× cost), with no UI signal.

## Details

### Why a memento beats an internal summary on determinism and controllability
The four-axis lens makes the trade-off legible:

| Axis | Native compaction (`/compact` / auto) | Harvest+respawn with memento |
|---|---|---|
| **Fidelity across boundary** | Good *within* a task; lossy and silently default-reverting across hard boundaries; mid-task trigger picks what survives | High if the memento is well-structured; you choose what survives; risk is staleness / self-serving omission |
| **Token economy** | Best for continuation (smaller re-warmed prefix, server-side `cache_edits` on the warm path) | Pays memento generation cost + full cold re-read of CLAUDE.md + memento |
| **Latency** | Compaction instant since v2.0.64; continuation seamless | Adds harvest-write + respawn + cold prefill latency |
| **Determinism / auditability** | Opaque LLM rewrite; not inspectable before it fires; non-reproducible | **Inspectable, diffable, version-controllable, lintable, gateable** — reconstruct deterministically |

The memento's structural advantage is that it is a **primary artifact you author and can verify before the boundary**, whereas a compaction summary is a secondary, opaque derivative produced *at* the boundary by a non-deterministic pass. The "dictionary of AI coding" framing is apt: secondary sources fail by being lossy and by drifting from the primary source; the cure is sending the agent back to the primary. A memento under version control *is* a curated primary source for the next worker.

The memento's failure modes are different and more controllable than compaction's: (a) **staleness** — the memento describes a world that has since changed (mitigate by regenerating at harvest, not reusing an old one); (b) **self-serving omission** — a worker narrating its own arc may under-report its own dead-ends or unfinished work (mitigate with a strict template that forces "Pending/Unverified/Known-broken" sections and with git-diff cross-checks); (c) **generation cost/latency** — one extra LLM turn. Compaction's failure modes (silent constraint reversion, cascading hallucination, mid-task timing) are by contrast *invisible until they bite*, which is strictly worse for an autonomous fleet where no human is watching each worker.

### How to structure the memento for fidelity-per-token and determinism
Borrow the empirically-validated structure from Claude Code's own 9-section compaction contract and Anthropic's harness work, but make it an *authored, inspectable* file:
1. **Format: JSON or a JSON+Markdown hybrid, not pure prose.** Anthropic empirically found the model is less likely to destructively rewrite JSON than Markdown. Use JSON for the machine-checkable state (files touched, feature/test status, pending tasks, constraints) and a short Markdown narrative only for the "why."
2. **Verbatim-preserve the hard constraints.** The "Facts as First-Class Objects" failure (silent default reversion) and Claude Code's own summarization prompt (which mandates verbatim preservation of security-relevant constraints) both point the same way: a `constraints` array with exact values (versions, regions, thresholds, vetoes) preserved character-for-character. This is the single highest-value, lowest-token section.
3. **Carry the user's actual intent verbatim**, mirroring the "All User Messages" section — this is precisely what auto-compaction is documented to drop (#36068).
4. **Pointers over payloads (just-in-time / code-as-memory).** Store file paths, git SHAs, query strings — not file contents. This mirrors Anthropic's JIT-retrieval pattern and the Managed-Agents `getEvents()` session-as-context-store model, and keeps the memento small enough to live in the high-attention head of the next context.
5. **Append an `Optional Next Step` and an explicit `Unverified/Known-broken` list** to counter both the "declare victory early" failure and self-serving omission.
6. **Place the memento immediately after CLAUDE.md in the reload order** so both sit in the primacy-favored head of the window (lost-in-the-middle: heads and tails are privileged; mid-context is not).

### Interaction with your context-pressure assessor
Your assessor already computes occupancy out-of-band from the last assistant turn's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` over the JSONL. That sum is exactly the SDK's own compaction-threshold quantity (the Claude API docs define the compaction threshold check as `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`), so your numbers are directly comparable to Claude Code's internal accounting — add `output_tokens` of the final turn if you want exact parity. Recommended policy mapping:
- **Below WARN (~70%):** do nothing. Let microcompaction (Tier 1) and disk-paging of tool results run; they are nearly free and cache-friendly.
- **WARN (~70–85%), mid-task, single coherent thread:** allow native `/compact` *with an explicit focus hint* (or let auto-compact fire) for continuation. This is the regime where compaction's token/latency advantage is real and the fidelity risk is lowest. Crucially, fire it *proactively at WARN* rather than waiting for the auto-trigger near the reserve, because (a) you control the focus hint and (b) the summary is built from higher-signal context.
- **CRITICAL (~85%) OR any task boundary, whichever comes first:** **harvest+respawn with memento.** At a task boundary, the memento's determinism dominates and you also get a clean cache reset anyway. At CRITICAL mid-task, you are near the ~13K reserve where auto-compact would fire blindly; pre-empt it with a controlled harvest so *you* decide what survives.
- **Tune the trigger to beat the buffer.** Since auto-compact fires at effective-window − ~13K, set your CRITICAL harvest threshold a few thousand tokens *below* the auto-trigger so your controlled harvest always wins the race against the blind one. On a 200K worker that's ~85%; on a 1M worker, occupancy-% is misleading — the lost-in-the-middle degradation begins long before the ~83.5% trigger, so cap *effective* working set far lower (practitioners use ~60% on 1M) and harvest at task boundaries regardless of raw occupancy.

### Per-model and per-window considerations
- **200K workers:** the ~13K reserve is ~6.5% of the window; fixed overhead (system prompt, tools, MCP, CLAUDE.md) can leave only ~100–120K usable. Compaction fires often; harvest+respawn at task boundaries is attractive because the cold re-read cost is bounded by a small window.
- **1M workers (Opus 4.6/Sonnet 4.6):** ~830K usable after the ~33K buffer; fewer compactions, but lost-in-the-middle degradation accrues silently well before the trigger. Here the memento is *more* valuable, not less: it lets you deliberately retire a worker at ~50–60% occupancy with a clean handoff instead of dragging a degraded 800K context. (Anthropic's own framing reinforces that context management drives quality: per the Opus 4.5 launch materials, context management/memory improved Opus 4.5's score on a deep-research evaluation by almost 15 percentage points.)
- **MRCR v2 at 1M:** Opus 4.6 ~78.3%; Sonnet 4.6 GraphWalks BFS ~68.4% — i.e., even the best 1M models lose ~20–30% of long-range coreference at full fill, quantifying why "just use the big window" is not a fidelity strategy.

## Recommendations

1. **Adopt the hybrid policy above as the default**, encoded directly in the coordinator sidecar's quiesce/reload state machine: microcompact-passive < WARN; proactive focused `/compact` for mid-task continuity in WARN; harvest+respawn-with-memento at CRITICAL or task boundary. This is not a compromise — it assigns each mechanism to the regime where it dominates on the weighted axes.

2. **Make the memento a first-class, versioned artifact.** Emit it as JSON+Markdown to a path the respawned worker reads first (after CLAUDE.md). Generate it via a dedicated "harvest" prompt that reuses Claude Code's 9-section contract but adds verbatim `constraints` and `unverified` arrays. Commit it to git so it is diffable and auditable — this is the entire determinism win.

3. **Decouple harvest from the live worker (sleep-time compute).** Run the memento generation as a separate, possibly cheaper-model pass over the JSONL transcript rather than asking the dying worker to narrate itself under context pressure. This avoids self-serving omission, removes generation latency from the critical path, and matches the Letta sleep-time result (~3× live-token reduction; ~5× test-time-compute reduction to equal accuracy on Stateful GSM-Symbolic/AIME). Cross-check the memento against the git diff before accepting it.

4. **Stop treating warm-cache preservation as a primary objective on this fleet.** Your bursty, voice-driven, tmux cadence with 5m-TTL almost certainly cold-blows the cache between turns already (#46829). Measure your actual `cache_read_input_tokens / cache_creation_input_tokens` ratio per worker from the JSONL you're already parsing; if reads are not dominating, the cache-preservation argument for compaction-over-respawn is moot, and you should optimize for fidelity/determinism (memento) instead. **If** reads dominate, pin a 1h TTL for the stable CLAUDE.md+tools prefix to make respawn cheaper (note Bedrock/Vertex support only 5m, so this favors first-party API or careful provider selection on GCP/Vertex).

5. **Instrument the boundary.** Log the `compact_boundary` metadata (pre-compaction token count, trigger type) and, for memento paths, the memento's token size and the post-respawn cold-prefill cost. This gives you the empirical per-worker data to tune WARN/CRITICAL and to detect the silent-constraint-reversion failure (e.g., a regression test that asserts the post-boundary worker still honors the `constraints` array).

6. **Avoid `--resume` for cross-boundary continuity.** It is a documented cache trap and reprocesses context. Prefer a clean respawn with the memento as the explicit first user turn.

### Benchmarks/thresholds that would change these recommendations
- If your measured cache-read ratio is high (>~70%) **and** workers run long single-threaded tasks, shift the WARN band upward and prefer compaction more aggressively — the token economy then genuinely favors it.
- If you observe constraint-reversion or cascading-hallucination incidents post-compaction (catch them with the `constraints` regression test), move the CRITICAL harvest threshold *down* and prefer memento earlier.
- If Anthropic ships per-model autocompact thresholds (#34126) or a configurable, inspectable compaction prompt, re-evaluate: a steerable compaction prompt narrows the determinism gap somewhat (you can pin verbatim constraints), though it still produces a non-versioned, non-diffable artifact.

## Caveats
- **Much of the compaction internals are community reverse-engineering**, partly from the late-March-2026 accidental source-code exposure (~510K lines). Specific numbers (13K reserve, 83.5% threshold, 50K file cap, 5-recent-files) are credible and mutually corroborated but are not all officially documented and have shifted version-to-version; verify against your installed Claude Code version's `/context` output.
- **Anthropic's 39%/29%/84% figures are self-reported internal evaluations**, not independent benchmarks; treat as directional. The Letta LoCoMo (74.0% vs 68.5%) and sleep-time numbers are primary-source but use different models (GPT‑4o‑mini, Claude 3.7 Sonnet) and tasks than your workload, so transfer is qualitative.
- **The "~15% decrease in compaction events after 1M shipped" claim could not be verified to a named Anthropic source** and has been removed; the nearest verifiable Anthropic figure is the ~15-percentage-point deep-research-eval gain from context management cited at the Opus 4.5 launch. Treat any "fewer compactions on 1M" claim as plausible but unconfirmed.
- **The 5m-TTL regression (#46829) is a community-diagnosed inference**, plausibly an infra regression rather than intended behavior; Anthropic had not (per available sources) confirmed it. Your own JSONL is the authoritative source for *your* cache behavior — measure it.
- **The memento approach is not free of drift/omission risk**; it trades compaction's invisible, uncontrollable failures for visible, controllable ones. That trade is favorable for an autonomous fleet, but only if you actually build the verification (git cross-check + constraints regression test); without it, a self-narrated memento can be as lossy as a summary.
- **Multi-VM/GCP:** prompt cache is per-organization/workspace and KV state is held in-memory at Anthropic's side, so cache locality does not follow your VM topology; a worker respawned on a different GCP VM has the same cold-cache cost as one respawned locally. Plan cache economics around request cadence and TTL, not VM placement.
