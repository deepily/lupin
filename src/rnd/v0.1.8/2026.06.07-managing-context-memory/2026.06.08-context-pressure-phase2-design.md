## 0. TL;DR

Phase 1 gave us `assess_fleet_context_pressure()` — a pure leaf that returns per-worker pressure.
Phase 2 surfaces it through the standalone arbiter (`lupin_arbiter_app`, :8001) and flags CRITICAL
workers to the manager. **It's small**: the arbiter's store is already section-keyed and `/state`
already returns the whole composite, so a new `context_pressure` section flows out through `/state`
and the `:7999` reverse-proxy with near-zero plumbing. Still **sensor-only** — no auto-action (that's
the gated Phase 3).

## 1. What already exists (verified 2026-06-08)

| Component | Fact (grounded in source) |
|---|---|
| `LocalSnapshotStore` | Section-keyed: `set_section(name, value)` / `get() → {"loop_a": {...}, "loop_b_fleet": {...}}`. Thread-safe. **Accepts arbitrary new sections — no schema change to add one.** |
| `GET /state` (`app.py` L4) | Returns the **whole composite** `store.get()`. A new section appears automatically. |
| Loop B (`loop_b.py` L3) | Writes section `loop_b_fleet` via `snapshot_sink = lambda snap: store.set_section("loop_b_fleet", snap)`. Runs on a standing cadence. |
| `:7999` reverse-proxy | `GET /api/arbiter/fleet-state` (`cosa/rest/routers/arbiter.py`) **PULLS** the `:8001/state` composite. Passes sections through. |
| Config | The seven `arbiter context *` keys already landed in Phase 1 (`lupin-app.ini` + splainer). |

**Design win:** because the store is section-keyed and `/state` is a pass-through composite, Phase 2
adds a *writer* and a *section* — it does **not** restructure the store, `/state`, or the proxy.

recommendation for any CRITICAL worker.

## 3. The `context_pressure` store section (shape)

```json
{
  "generated_at": "2026-06-08T17:00:00Z",
  "thresholds": { "warn_pct": 70, "critical_pct": 85 },
  "workers": [
    { "session_id": "…", "persona": "Tiberius", "tmux_session": "…",
      "liveness": "ACTIVE", "pct": 53.3, "state": "OK",
      "next_prompt_estimate": 533000, "last_prompt_size": 531000,
      "pending_input_estimate": 1356, "window_size": 1000000,
      "last_turn_age": 41.2, "recommendation": "" }
  ],
  "summary": { "ACTIVE": 3, "IDLE": 2, "DEAD": 0, "WARN": 0, "CRITICAL": 0 }
}
```

~200 bytes/worker — matches the expert's per-VM-summary sizing (§7 of the brief), so the **same shape
generalizes** to the multi-VM fan-in below.

---

## 4. CRITICAL emission (sensor → recommender, still no auto-action)

When a worker is `CRITICAL` (and `ACTIVE`, not IDLE/DEAD), the writer:
1. posts a recommendation to the reserved commons topic `context-harvest-decision`
   (`arbiter context harvest decision topic`), and
2. `notify()`s the worker's manager (resolved via the existing `manager_resolver` in `heartbeat_arbiter`).

It **recommends** ("harvest+respawn with memento" or "compact now if mid-turn") — it never acts.
De-dupe: emit once per worker per CRITICAL episode (track last-emitted state per session_id), so a
worker parked at CRITICAL doesn't spam every tick.

---

## 5. Multi-VM future (the expert's sidecar — documented seam, NOT built now)

Today the fleet is single-host: `:8001` reads local bridge files directly, so the writer runs in-process
and there's nothing to fan in. For the GCP multi-VM future, the **same writer becomes a per-VM sidecar**:
each VM emits its `context_pressure` section (the §3 shape) over pub/sub or a thin HTTP endpoint, and the
arbiter aggregates the sections instead of reading peers' transcripts over shared FS (which the expert
ruled out: latency ×fleet, eventual-consistency on hot writes, fate-sharing, egress). **No code now** —
this section just records that the §3 shape is the fan-in unit so we don't repaint later.
