## 1. Claim A — validated, with a caveat about format drift

The partition argument is correct. The three input fields are mutually exclusive slices of the same prompt, so their sum is cache-split-invariant by construction. There's no hidden "system prompt" or "tool defs" bucket — Anthropic accounts for the entire input prompt across exactly those three fields, regardless of how many `cache_control` breakpoints you've planted in it. Your worked examples are arithmetically consistent.

One format-drift hazard to harden against: in recent API versions the `usage` object often carries a *nested* breakdown alongside the flat field:

```json
"cache_creation_input_tokens": 1032,
"cache_creation": {
  "ephemeral_5m_input_tokens": 832,
  "ephemeral_1h_input_tokens": 200
}
```

The top-level flat field is the sum of the nested one, so you're fine *today*. But if Anthropic ever deprecates the flat field in favor of the nested form (they've done analogous things), your reproducer silently reads `None` and the addition raises. Either guard the read or sum `cache_creation.values()` as a fallback. Cheap insurance.

There's also `server_tool_use` accounting that can appear in `usage` for sessions that hit `web_search` / `code_execution`. It doesn't belong in occupancy (those tokens aren't in your context window, they're consumed server-side), but you should explicitly verify your parser ignores it rather than incidentally ignoring it.

## 2. Claim A2 (excluding `output_tokens`) — defensible but probably wrong for your use case

You've framed this as a one-turn lag and dismissed it as "negligible for a 30–60s tick." I'd push back. The semantics of what you're measuring matter here:

- **"Size of the last prompt I sent"** → exclude `output_tokens`. This is what your formula gives you.
- **"Size of the prompt I'm *about to* send"** → include `output_tokens`, because the model's last response is now part of the message history and will be in the next input.

For a *pressure* metric whose purpose is to fire WARN/CRITICAL before degradation, (b) is the more honest reading. The gap matters specifically at the red line — a worker sitting at 84% occupied-by-last-prompt who just emitted a 30k-token Opus response with thinking is actually at ~87% going into the next turn, which is the difference between WARN and CRITICAL on your thresholds. The lag is also non-stationary: long structured outputs (planning mode, large diffs) inflate it, exactly when you most want an accurate reading.

Recommendation: include `output_tokens` and update the formula to:

```
occupied = input_tokens
         + cache_creation_input_tokens
         + cache_read_input_tokens
         + output_tokens
```

The cache-invariance argument still holds for the first three; the fourth is added because it becomes part of the next prompt. If you want to preserve the original semantics, expose both as `last_prompt_size` and `next_prompt_size` and let consumers pick.

## 3. The issue you haven't surfaced: pending user/tool messages since the last assistant turn

This is the one I'd flag hardest. Your design reads the *last assistant turn's* usage. In a Claude Code worker doing aggressive tool use, the interval between assistant turns can accumulate substantial input that your formula never sees:

1. Assistant fires 5 parallel `bash_tool` / `view` calls. `usage` recorded.
2. Five `tool_result` messages land back, each potentially carrying multi-kilobyte stdout/stderr or large file views.
3. User adds a clarifying message.
4. Before the next assistant turn fires, your sidecar reads the transcript.

What you observe: the assistant turn from step 1, unchanged.
What's actually in the context that will be sent on the next assistant turn: step 1's prompt + step 1's output + 5 tool results + 1 user message.

For Lupin/CoSA workloads where a coordinator dispatches tool-heavy subagents, this gap can be tens of thousands of tokens. A worker can appear stable at 60% while sitting on a queued 40k of unread `view` output that will push it to 90% the moment the next assistant turn fires.

Mitigation isn't expensive: after finding the last assistant turn, sum a rough token estimate of every message *after* it in the JSONL. For a health check you don't need perfect token counting — `len(content) / 4` as a Latin-character heuristic, or `tiktoken` / `anthropic.tokenizer` if you want fidelity. Surface it as `pending_input_estimate` alongside the authoritative `last_prompt_size`.

This concern interacts with §2: the cleanest pressure metric becomes

```
next_prompt_estimate = last_prompt_size
                     + last_output_tokens
                     + sum_since_last_assistant
```

with the third term being approximate but on the conservative side.

## 4. Claim B / A3 — agree, this is the weakest link

You've self-identified this correctly. Two practical paths:

**Path 1 (authoritative, preferred):** the assistant message object should carry a `model` field — parse it. The `[1m]` window is gated by the `context-1m-2025-08-07` beta header on the *request*, which doesn't appear in the assistant response. But the bridge file knows how the worker was spawned. Pin window-size in the bridge JSON at spawn time (`"window_size": 1000000` next to the persona) and read it from there. This makes denominator selection a property of the *worker*, not an inference from the *transcript*. Both correct and cheap.

**Path 2 (heuristic, fragile):** "if observed occupancy ever exceeds 200k, it must be a 1M worker" — but the converse fails. A 1M worker at 138k looks identical to a 200k worker at 138k from the transcript alone, and the 200k worker is on fire while the 1M worker is fine. Don't ship this.

Go with Path 1. The bridge file already pins persona and tmux_session; adding `window_size` is a one-line `session_spawner.py` change.

## 5. A4 — yes, divide by effective ceiling, not raw

Confirmed. `/context` reports against the effective ceiling, which is `rawMaxTokens − autocompact_reserve − max_response_tokens`. If you divide by raw, your 85% threshold fires noticeably later than it should — autocompact will likely have triggered already, or the next big tool result will starve the response budget. Calibrate against a live `/context` dump from a known-state worker once; the reserve has historically been on the order of ~45k for 200k windows but I wouldn't trust any specific number without measuring it on your fleet.

## 6. Liveness: `mtime` is necessary but not sufficient

Your open question. `mtime`-only is wrong in both directions:

- **Healthy worker, idle** → stale mtime → false-dead.
- **Hung worker with side-effecting hooks still running** (e.g., a `SessionStart` hook that touches files, or a stuck tool that periodically writes status) → fresh-ish mtime → false-alive.

Add a `kill -0 listener_pid` (or whichever PID is the actual `claude` CLI parent) as the AND-gate. Cheap, accurate, and matches the semantics you actually want: *"is there a process that will produce the next assistant turn?"* For phantoms specifically, the `listener_pid` being dead is the definitive signal — bridge mtime can be days fresh from cleanup hooks and the worker is still gone.

Three-state model is cleaner than two-state:

```
process_alive ∧ mtime_fresh        → ACTIVE
process_alive ∧ mtime_stale        → IDLE   (don't compute pressure; flag last_turn_age)
¬process_alive                     → DEAD   (sweep bridge)
```

## 7. §6 — per-instance-local sidecar, not shared storage

This isn't a close call. Shared transcript storage (GCS-FUSE / NFS) introduces:

- Read latency on every poll, multiplied across the fleet.
- Eventual-consistency hazards on GCS — your reader can see a half-written JSONL line during a hot assistant write.
- A fate-sharing dependency: lose the mount, lose pressure visibility for *every* VM rather than one.
- Egress cost on a metric you're polling at 30–60s ticks.

A per-VM sidecar that owns assessment for its local workers and emits a small JSON summary (`{persona, session_id, occupied, pct, state, pending_estimate, last_turn_age}`) over pub/sub or a thin HTTP endpoint is the right shape. It matches CoSA's "small agents" topology, makes each VM a clean fault domain, and the arbiter just aggregates summaries — no transport concerns about transcript volume. Each summary is ~200 bytes; you can poll a thousand workers and the arbiter sees <1MB/tick.

The only argument for shared storage is post-mortem forensics (an arbiter inspecting a peer's transcript after the fact). Solve that separately with on-demand transcript shipping triggered by an arbiter request, not by making the hot path go through shared FS.
