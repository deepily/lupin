## TL;DR

The `:7999` dev server intermittently hangs — `/health` Docker probe times out
(`ExitCode 1`, `TimeoutError`) — and it correlates with pending blocking voice
questions (`ask_yes_no` / `ask_multiple_choice`). **Root cause: the notification
path runs the Prediction Engine synchronously on the FastAPI event loop.** The
fix wraps those hooks in `asyncio.to_thread(...)`, reusing the "FM-7" offload
pattern already present one block above the offending code. Six call sites across
two routers; no engine, schema, or config changes.

## Context — why this change

### Symptom

Docker healthcheck output, 2026-06-05 22:25–22:26:

```
import urllib.request; urllib.request.urlopen('http://localhost:7999/health', timeout=3)
...
TimeoutError: timed out
ExitCode: 1
```

Rick's observation: the server hangs *while a blocking voice question is on
screen*, so he cannot answer it.

### Root cause — event-loop starvation

`/health` is a trivial `async def` that only returns a dict
(`src/cosa/rest/routers/system.py:95`). If it can't answer within 3 seconds, the
asyncio event loop itself is blocked. The notification path runs the Prediction
Engine **synchronously, on that loop**, with no offload:

| Async handler | Bare synchronous call | Location |
|---|---|---|
| `notify_user` | `prediction_engine.predict({...})` | `notifications.py:830` |
| `submit_notification_response` | `record_outcome(...)` | `notifications.py:1111` |
| `vote_on_prediction_hint` | `record_hint_vote(...)` | `notifications.py:1318` |

`predict()` / `record_outcome()` / `record_hint_vote()` are plain `def`s that chain:

- GPU embedding generation — `_generate_embedding`, `prediction_engine.py:1409`
- LanceDB vector search — `store.find_similar`
- `record_outcome` alone: **3–5** embedding calls + a LanceDB write (`_store_decision`)

The embedding HTTP fallback (`_generate_embedding_via_http`,
`prediction_engine.py:1441`) is a blocking `requests.post()` to the server's
**own** `/api/embeddings/generate` — a **reentrant self-call**: the loop is
blocked *making* the request, so it can't *serve* it, stalling until the request
timeout fires. And the embeddings endpoints themselves (`embeddings.py:67,91`)
are `async def` in name only — they call the sync GPU provider inline.

While any of this runs (worst case ~5–10s under GPU contention), `health()`
cannot be scheduled → the probe times out, and the pending question can't receive
its answer. It feels *random* only because it stalls solely when the embedding
path is slow (cold LanceDB, GPU contention, HTTP self-call); a warm path
completes in tens of ms.

### The precedent already in the file

The same file already solved this exact class of problem for the DB write — the
**FM-7 fix** at `notifications.py:589`:

```python
# Lever B (messaging plane): run the blocking DB I/O OFF the event loop
# via asyncio.to_thread so a slow DB under fleet load can't stall the
# notify path (and every other request sharing the loop) — the FM-7 fix.
db_notification_id = await asyncio.to_thread( _persist_notification_sync, ... )
```

The Prediction-Engine hooks simply never inherited that treatment. The codebase
uses `asyncio.to_thread` for off-loop offload in ~15 places (commons bridge I/O,
queue pushes, peer notify, podcast file I/O); this fix is consistent with that
established idiom.

## Approach

Wrap each synchronous Prediction-Engine / embedding call inside an async handler
in `asyncio.to_thread(...)`. `asyncio` is already imported in `notifications.py`.
Both `PredictionEngine` and `EmbeddingProvider` are thread-safe
double-checked-locking singletons with internal metrics locks, so they are safe
to invoke from worker threads. **No behavior change — only where the work runs.**

Side effect: once `predict()` / `record_outcome()` run on a worker thread, the
`requests.post` self-call also runs off-loop, so the loop stays free to serve the
embeddings endpoint — the reentrant deadlock dissolves.

### Tier 1 — the reported bug (required)

| Site | Change |
|---|---|
| `notifications.py:830` | `await asyncio.to_thread( prediction_engine.predict, {...} )` |
| `notifications.py:1111` | `await asyncio.to_thread( prediction_engine.record_outcome, ... )` |
| `notifications.py:1318` | `await asyncio.to_thread( engine.record_hint_vote, ... )` |

Existing `try/except` wrappers stay; exceptions propagate identically through
`await`. Keyword args bound via `functools.partial` or `to_thread`'s `*args/**kwargs`.

### Tier 2 — the embedding endpoints (required; closes the self-call path)

| Site | Change |
|---|---|
| `embeddings.py:77` (`generate_embedding`) | `await asyncio.to_thread( provider.generate_embedding, request.text, content_type=request.content_type )` |
| `embeddings.py:104` (`generate_embeddings_batch`) | `await asyncio.to_thread( provider.generate_embeddings_batch, request.texts, content_type=request.content_type )` |

### Tier 3 — adjacent same-family offender (recommended, low risk)

`generate_session_gist` (`notifications.py:2522`) calls `gister.get_gist(...)`
bare — a LanceDB cache read + (on miss) a blocking LLM HTTP call on the loop.
Wrap in `asyncio.to_thread`. Included to sweep the offender class per the
"sweep for all pattern offenders" rule.

> **Deliberately out of scope (follow-up sweep — explicit, not silent):**
> - the ~20 synchronous PostgreSQL handlers in `notifications.py` (short
>   single-row queries) — not the reported symptom.
> - the same-class admin/test endpoints in `system.py`: `/api/init` (`:224`) and
>   `/api/prediction-engine/reset` (`:249-287`). They call the engine
>   synchronously too, but are admin-triggered, NOT on the notification hot path,
>   so they don't affect the hang. Listed for sweep honesty.

## Required review change — the LanceDB write-lock (concurrency safety)

Krishna's review found the original safety argument **wrong** on two counts, and
the lock surface larger than first stated:

1. `asyncio.to_thread` runs on the **default `ThreadPoolExecutor`**, not the CJ
   Flow agentic pool — so "agentic pool = 1" buys no serialization.
2. LanceDB's `_table.add()` / `merge_insert()` **release the GIL** in native
   Rust — so GIL-serialization is a fiction. Two concurrent `record_outcome`
   workers really can collide, and the write methods swallow exceptions → a
   **silently-dropped CBR record**. The single-threaded loop serialized these
   writes for free; offloading destroys that guarantee.
3. **Third hazard — `record_hint_vote` is check-then-act:** `exists(case_id)` →
   (`update_ratification_state` | `add_decision`). Two concurrent votes can both
   see `exists()==False` and both insert → duplicate/clobbered case. A lock
   *inside* the write methods alone does **not** close this — the race is in the
   gap between `exists()` and the write.

**Fix — one shared re-entrant lock** (`ProxyDecisionEmbeddings._write_lock`,
class-level `threading.RLock`, shared across all stores):
- guards `_table.add()` in `add_decision`
- guards `merge_insert().execute()` in `update_ratification_state`
- `PredictionEngine.record_hint_vote` acquires the **same** lock across its whole
  `exists()→(update|add)` compound; nested `add_decision`/`update` re-acquire it
  cleanly (hence `RLock`, not `Lock`).
- Reads (`find_similar`, `exists`) stay lock-free — LanceDB MVCC snapshots are
  write-safe. Writes are infrequent → zero perf concern.
