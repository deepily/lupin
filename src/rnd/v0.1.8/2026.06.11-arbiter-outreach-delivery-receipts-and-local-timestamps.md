### 1.3 Latent second failure mode (Tiberius's prime suspect — would hit next)

Fixing R1 alone is NOT enough. Rick's WS was provably offline around those
timestamps, and:

- **L1** — `_http_post` returns only `resp.status` and **discards the response
  body**. `/api/notify` reports the real delivery outcome in the body
  (`status: "queued" | "user_not_available" | "delivered_via_listener"`) — all
  **HTTP 200**. A `user_not_available` miss is invisible to the arbiter today.
- **L2** — worse, the dedup guard (`make_live_notify_fn`) records ANY
  non-raising transport call as "sent", so a `user_not_available` outcome
  **suppresses identical retries for 15 minutes** (`sent[message] = now` fires
  because no exception was raised).
- **L3** — the warm-up wrapper suppresses silently (`escalation_suppressed_warmup`
  is logged, but R4 still journals "rick" as reached).

### 1.4 Bonus misattribution (visible in the §1.1 evidence)

Every fleet-arbiter journal line carries `"loop": "health_watcher"` — because
`assemble_app` defaults `log_fn` to `health_watcher._default_log_fn` and passes
it to the fleet-arbiter factory. The loop label lies about which loop emitted
the event. One-name rule violation; fixed in this design (§3.8).

### 1.5 What the root cause means for the design

The misses were not one bug but a **stack of swallowed outcomes** with a journal
that asserts success it never verified. So the design's spine is: **every
outbound hop returns a structured outcome; every outcome is journaled as its own
event; the intent event stops claiming delivery; receipts close the loop from
both ends; undelivered Rick-bound advisories actively re-announce.** No layer is
allowed to swallow a result without journaling it under the outreach's id.

## 2. ITEM A — human-parsable journal timestamps (`ts_local`)

### 2.1 Contract

Every arbiter structured-log line (all loops, all events) carries BOTH:

```json
{"ts": "2026-06-11T21:28:46.444270+00:00", "ts_local": "2026-06-11-at-17-28-46-(EDT)", ...}
```

- `ts` — unchanged: ISO-8601 UTC, machine-sortable. Never removed.
- `ts_local` — NEW: `%Y-%m-%d-at-%H-%M-%S-(%Z)` rendered in the configured
  timezone. Same instant as `ts`, always.

### 2.2 Runtime flag (INI, deploy-tunable)

```ini
arbiter journal local timezone = America/New_York
```

Read once at app wiring (`assemble_app`); threaded to the shared line builder.
Invalid/unknown tz → **fall back to UTC** (`-(UTC)` label) + one loud
`journal_tz_invalid` event at startup. (Observer invariant beats fail-fast here:
a typo'd tz must never take the watcher down — but it must be visible.)

### 2.3 One shared line builder (one-name rule)

Today the line shape is **copy-pasted five times** (`arbiter_live_notify`,
`health_watcher`, `fleet_arbiter_loop`, `context_pressure_writer` each have a

mean five identical edits — so the line shape gets ONE owner:

## 3. ITEM B — end-to-end outreach delivery receipts

### 3.1 The dot-connect spine: `outreach_id` + three events

Every routed/direct outreach mints one `outreach_id` (uuid4 hex). Three event
types share it — **one `journalctl` grep shows the whole story**:

| Event | Cardinality | Meaning |
|---|---|---|
| `arbiter_outreach` | 1 per outreach | **INTENT** — what the arbiter decided to send, to whom, why (kind/case/tier). `recipients` is renamed in meaning: the PLANNED recipient set. Gains `outreach_id`. |
| `arbiter_outreach_result` | 1 per recipient×channel attempt | **ATTEMPT OUTCOME** — what actually happened on that hop: `{outreach_id, recipient, channel, outcome, detail?}`. Re-announce retries emit fresh results (`attempt: N`). |
| `arbiter_outreach_receipt` | 1 per recipient terminal state | **CONFIRMATION** — the loop closed (or terminally didn't): `{outreach_id, recipient, outcome, latency_s?, attempts?}`. |

Channels: `live` (POST :7999/api/notify → Rick), `durable` (commons
`fleet-escalations` post), `dm` (commons `dm-<persona>` post), `dm_push`
(POST :7999/api/commons/register-question → listener tmux injection).

Result outcomes (vocabulary, FINALIZED at build 2026-06-11): per channel —
- `live`: `queued`, `delivered_via_listener`, `user_not_available`,
  `http_error` (carries status when known), `unexpected_response` (2xx with an
  unrecognized body — never silently assumed delivered), `deduped`,
  `legacy_notify` (a legacy `None`-returning seam pushed; delivery unverifiable),
  `disabled`
- `durable`: `posted`, `post_error`
- `dm`: `posted`, `post_error`
- `dm_push`: `dispatched` (201 + `dm_dispatched: true` — the recipient WOKE),
  `registered_no_push` (201 without listener dispatch), `push_unavailable`
  (422/timeout/non-2xx), `disabled`
- `all`: `suppressed_warmup`

Receipt outcomes: `delivered` (Rick: body-status `queued`/`delivered_via_listener`),
`reannounced_delivered` (Rick, after ≥1 retry), `expired` (Rick: TTL exhausted
while offline), `acked` (manager threaded reply seen), `unacked` (manager: ack
window passed, one re-send also unacked — terminal).

The S3 accounting invariant from the F1 design ("journal mirrors reality") is
RESTATED, not violated: reality now lives at the **result** level; the intent
event mirrors the plan. The existing `test_arbiter_outreach_logging.py`
assertions move accordingly.

### 3.2 Break the contract: notify seams return outcomes (no more `str → None`)

We own every consumer ([[feedback_one_descriptive_name_everywhere_break_contract]]),
so the blind `notify_fn( message ) -> None` stack is rewritten end-to-end — no
compat shim:

```
_http_post( url, headers )            -> ( status, body_dict )      # body no longer discarded
transport( message )                  -> result dict                # parses body["status"] into outcome
make_live_notify_fn( … )              -> live_notify( m ) -> result # dedup records ONLY delivered outcomes (kills L2)
make_escalation_notify_fn( … )        -> notify_fn( m ) -> [ durable_result, live_result ]
make_warmup_notify_fn( … )            -> notify_fn( m ) -> [ {channel:"all", outcome:"suppressed_warmup"} ] | inner(m)
ArbiterConsumerJob._notify_fn( m )    -> list[ result ]             # _route consumes it
```

Every layer still **never raises** (observer invariant); failures become outcome
values instead of swallowed exceptions. `_route` journals one
`arbiter_outreach_result` per entry in the returned list (recipient `rick`),
plus one per manager `dm`/`dm_push` attempt — and **stops claiming** anything it
didn't verify (kills R4). HTTP-404-user-not-found becomes
`{channel:"live", outcome:"http_error", detail:"404 User not found: …"}` — tonight's
exact miss, visible per-event (Tiberius's steer).

`_make_health_notify_fn` (Part-6 #1/2/3) consumes the same contract and journals
the same result events — health escalations get receipts for free.

### 3.3 Manager push: ride the register-question hop (kills R6)

New injected seam on the job (escalation-path only, best-effort, default `None` —
mirrors `live_notify_fn`'s R4-compatibility exactly):

```python
dm_push_fn( recipient_persona, body, outreach_id ) -> result dict
```

Built in `app.py` next to the live transport (same X-API-Key, same base_url):
`POST :7999/api/commons/register-question` with `question_id = outreach_id`,
`recipient_persona`, `topic = dm-<persona-slug>`, short TTL. A 201 with
`dm_dispatched: true` means the recipient's listener got `commons_question_received`
→ tmux injection → the manager session WAKES (the same machinery
`commons_send_to` uses — directed-DM doctrine, now honored by the arbiter).

Order per manager recipient: `gateway.send_to` (durable board write, unchanged,
detection-path-safe) THEN `dm_push_fn` (best-effort). Both journal results. A
422/timeout/disabled push degrades to today's board-only behavior — but VISIBLY
(`push_unavailable`).

INI gate: `arbiter outreach dm push enabled = true`.

*Build-time risk to verify (named for the reviewer)*: `_resolve_dm_recipient`
resolution scoping — the arbiter's `ck_live_…` key must resolve manager personas
from the bridge dir the same way a CC session's call does. Verified live before
the held commit; on mismatch the fallback is board-post + receipt polling
(§3.4), which closes the loop regardless, just slower.

### 3.4 Manager-side receipt: threaded-ack polling (the acked-ledger pattern, adapted)

The stop-hook oracle's acked-ledger insight: **the receipt is an explicit,
durable, owner-written mark — never an inference**. The commons already has that
mark: the threaded reply (`metadata.in_reply_to = <qid>`) that
[[feedback_close_inbound_commons_questions_with_threaded_reply]] obligates
managers to send. So the arbiter's DM body sets `metadata.outreach_id` and asks
for a one-line threaded ack; the receipt check is:

- Each poll, for pending manager outreaches: `gateway.read( dm-<persona>, since=sent_ts )`
  — **filesystem read, detection-path-safe (R4-clean)** — looking for entries
  with `metadata.in_reply_to == outreach_id`.
- Found → `arbiter_outreach_receipt {outcome:"acked", latency_s}`.
- Not found past `arbiter outreach ack window seconds` → ONE re-send (dm +
  dm_push, journaled as results with `attempt: 2`), then a fresh window; still
  nothing → terminal `receipt {outcome:"unacked"}`. **No third send, no
  escalation recursion** — an unacked-manager fact flows to Rick inside the NEXT
  Rick-bound advisory body, never as a new outreach loop.

### 3.5 Rick-side receipt + re-announce-on-return (milestone-must-land)

The `/api/notify` body-status IS Rick's receipt:

- `queued` / `delivered_via_listener` → `arbiter_outreach_receipt
  {recipient:"rick", outcome:"delivered"}`. Done.
- `user_not_available` (or any error) → the advisory enters the **pending
  ledger** and re-announces: each poll where `now - last_attempt ≥ reannounce
  interval`, re-fire the live transport (escalation-path retry — R4-clean;
  bounded: only while the ledger is non-empty). Each retry journals a result
  (`attempt: N`). First delivered outcome →
  `receipt {outcome:"reannounced_delivered", attempts:N}` + ledger removal.
  TTL exhausted → terminal `receipt {outcome:"expired"}` (the DB notification
  row from :7999's unconditional persist remains his passive trace — the missed
  notifications UI; this design adds the ACTIVE layer Rick demanded).
- Dedup interplay (kills L2): only delivered outcomes enter the dedup window;
  re-announce intentionally bypasses content-dedup (it re-sends the SAME text —
  that's the point) by keying retries on `outreach_id`, not message content.

**Pending ledger persistence** — `io/arbiter/outreach-pending.json` (NEW module
`cosa/agents/heartbeat_arbiter/outreach_ledger.py`, modeled line-for-line on
`heartbeat_acked_ledger.py`: degrade-safe reads → empty, atomic
tmp-write+rename, merge-don't-clobber). Survives the 12h job recycle AND a
service restart — a stall advisory fired while Rick sleeps re-announces when he
returns in the morning, even across a deploy. Path via `cu.get_project_root()` +
relative INI value (PATH MANAGEMENT). Entry shape:

```json
{ "outreach_id": "…", "message": "…", "kind": "stall", "case": 11,
  "created_ts": "…", "attempts": 3, "last_attempt_ts": "…", "last_outcome": "user_not_available" }
```

### 3.6 Startup misconfiguration guard (kills R1's silence, not just R1)

`_build_live_notify_fn` gains a pure, unit-tested validator
(`validate_live_notify_target`): empty `target_user` OR a surviving `${` →
- loud `live_notify_misconfigured` journal event (with the offending value),
- a durable `fleet-escalations` post naming the misconfiguration (so it ALSO
  surfaces on any future consumer of that board),
- live push disabled (no doomed 404 spam) — but unlike today, **visibly**:
  every subsequent Rick-bound outreach journals
  `result {channel:"live", outcome:"disabled", detail:"misconfigured target_user"}`.

The deploy-side fix for tonight's actual gap is Tiberius's (§7).

### 3.7 What `fleet-escalations` is, post-design

Unchanged as the durable record. This design does NOT add a consumer for it —
the live+push+receipt loop makes the active path trustworthy, and the board
stays the forensic archive. (A board consumer remains available as a future
layer if Rick wants belt-and-suspenders.)

### 3.8 Loop-label fix (§1.4)

`assemble_app` builds per-loop log_fns via `make_log_fn( loop=… )`:
`"fleet_arbiter"`, `"health_watcher"`, `"context_pressure"`,
`"fleet_arbiter_live_notify"` — each loop journals under its own name. No more
fleet-arbiter events wearing the health-watcher's label.
