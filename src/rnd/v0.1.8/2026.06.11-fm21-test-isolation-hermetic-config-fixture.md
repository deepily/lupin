## 1. Problem

Two distinct isolation-leak classes were polluting full-suite unit runs:

### 1.1 F2 — event-loop pollution (the known "3 fails")

`src/tests/unit/test_bridge_liveness_middleware.py` (pytest-asyncio) closes its
event loop and leaves the asyncio policy's `_set_called` flag set. Three
`TestDecisionResponder` tests in `src/tests/unit/test_decision_proxy_config.py`
then call the deprecated `asyncio.get_event_loop().run_until_complete()` →
`RuntimeError: There is no current event loop in thread 'MainThread'` on the
Python 3.13 venv. All three pass solo; they fail only in full-suite collection
order. Every worker gating on the full suite 2026-06-10/11 had to caveat
"6xxx passed / 3 failed (known pollution)".

**Minimal repro** (Rachel's, re-verified by Rio on the pre-fix tree):
`pytest test_bridge_liveness_middleware.py test_decision_proxy_config.py`
→ `3 failed, 70 passed in 0.83s`. NOT config pollution — same isolation-leak
class as FM-21, different mechanism, bundled into one engagement.

### 1.2 FM-21 proper — ConfigurationManager singleton + env leakage

`ConfigurationManager` is a decorator-registry singleton. Any module's
`set_config()` mutations, `_reset_singleton=True` recreations with custom INIs,
or bare `os.environ` writes to `LUPIN_CONFIG_MGR_CLI_ARGS` / `LUPIN_ROOT`
persisted into every later module. The stated contract: **config state cannot
leak between test MODULES.**

## 2. Fixes

### 2.1 Fix 1 (F2, narrow) — commit `cd6d2fb0`

The 3 victim call sites swap `asyncio.get_event_loop().run_until_complete(...)`
→ `asyncio.run(...)` — a self-contained loop per call, immune to ambient loop
state. 3 lines, no product code.

### 2.2 Fix 2 (FM-21) — commit `92cf32c4`

`hermetic_config_module_boundary` — module-scoped autouse fixture in top-level
`src/tests/conftest.py`:

1. **Setup** (per module): `ConfigurationManager.reset_for_testing()` (drops
   the decorator-registry entry, O(1); live references in already-imported
   modules stay valid) + snapshot of the tracked env vars.
2. **Teardown** (per module): reset again + env restore — absent-at-snapshot
   vars are deleted, present ones restored to snapshot value.

Tracked vars: `LUPIN_CONFIG_MGR_CLI_ARGS`, `LUPIN_ROOT`,
`LUPIN_TEST_HERMETIC_SENTINEL` (never set in real runs — it is the verify
pair's leak channel AND keeps the delete-on-restore arm exercised on every
module teardown).

**Why module scope, not function scope**: the contract is module-boundary
isolation; function scope would churn singleton re-instantiation (~30ms × every
CM-touching test) and break intra-module setup patterns that legitimately share
a CM instance across tests. `test_hermetic_config_fixture_a.py::
test_pollution_persists_within_module` pins the module-scope contract — it
fails if anyone downgrades the fixture to function scope.

The first post-fixture run exposed **2 pre-existing order-DEPENDENT tests** —
tests that pass in full-suite order ONLY because an earlier module seeds the CM
singleton, and **fail solo on the pre-fixture tree** (verified — this is the
inverted twin of the order-dependent-failure class FM-21 kills):

1. `test_lancedb_gcs_manager.py::test_local_backend_with_relative_path_applies_project_root`
   — patches `du.get_project_root` → `/project/root`; a virgin CM init then
   resolved its INI path against the fake root → `AssertionError` in
   `sanity_check_file_path`. **Repair**: seed the CM singleton from the
   canonical env before entering the fake-root patch.
2. `test_user_prompt_submit_hook.py` (first test in module) — captures
   `sys.stdout` and parses it as JSON; a virgin CM init printed its banner into
   the captured stream → `JSONDecodeError`. **Repair**: seed the CM singleton
   in `_run_hook_main` before stdout capture.

Both repairs are the same idiom: make the previously-implicit "singleton
already exists" precondition explicit. Both files now pass solo AND in suite.
