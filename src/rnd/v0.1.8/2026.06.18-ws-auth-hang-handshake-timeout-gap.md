# WS Auth-Hang Gap — mux lacks legacy `ws-channel.js`'s handshake-timeout watchdog

**Date**: 2026-06-18
**Author**: Rio ⚡ (read-only audit; no live-code edits)
**Trigger**: surfaced while building the reconnect-parity fix (audit `4450995d`, commit `33ec6db8`). Filed as a separate durable cutover-audit task at Mr. Radio's direction.
**Severity**: **LOW-MEDIUM cutover risk** — NOT live today (mux cutover is Rick-gated). Pre-flip robustness gap, NOT introduced or worsened by the reconnect-parity fix.

---

## TL;DR

Legacy `ws-channel.js` arms a **handshake-timeout watchdog** (`HANDSHAKE_TIMEOUT_MS = 10_000`): a socket stuck in `CONNECTING`/`AUTHENTICATING` for 10s is force-closed, which feeds the normal close→reconnect accounting. The mux transport has **no equivalent**. After the reconnect-parity fix (which correctly makes the CSM stay in `connecting`/`reconnecting` until `auth_success`), a server that **completes the TCP/WS handshake but never returns `auth_success`** leaves the CSM parked in `connecting` **indefinitely** — no `socket_close`, no `backoff`, no `failed`, no reconnect, no user signal. A silently-dead transport.

---

## Evidence

### Legacy `ws-channel.js`
- `HANDSHAKE_TIMEOUT_MS = 10_000` (`:47`).
- On `connect()`, arms `handshakeTimerId = setTimeout(...)` (`:316-324`): if still `CONNECTING` or `AUTHENTICATING` at 10s, `ws.close(1000, "handshake-timeout")` → `onclose` → `handleClose` → `scheduleReconnect` (normal reconnect accounting).
- Cancelled on open / auth_success / close (`cancelHandshake()` at `:250`, `:301`).

### Mux (`QueueTransport` / `BaseTransportImpl` + `ConnectionStateMachine`)
- No handshake/auth timer anywhere. `BaseTransportImpl` arms only the **backoff** timer (`scheduleBackoff`), which fires after a `socket_close`/`backoff` — never while waiting in `connecting` for `auth_success`.
- Post reconnect-parity fix: `socket_open` is sent to the CSM only on `auth_success`. So between TCP open and auth success the CSM is in `connecting` (or `reconnecting`). If `auth_success` never arrives and the socket never closes, the CSM has no event to act on → parked forever.
- WSChannel surfaces `onOpen`/`onMessage`/`onClose` but does not itself bound the post-open auth wait.

---

## Blast radius

- **When it bites**: server accepts the WS upgrade but the auth path hangs — server-side auth bug, a wedged auth dependency, a silently-dropped `auth_request`, or a proxy that holds the socket open without forwarding frames.
- **Impact**: the affected transport (queue or audio) sits dead with no reconnect, no `failed`, and no user-facing signal — strictly worse UX than a clean disconnect (which DOES reconnect). Legacy self-heals via the 10s force-close→reconnect.
- **Likelihood**: low (a healthy server always answers `auth_request` quickly). It's a robustness/defense-in-depth gap, not a common path.
- **Relation to the reconnect-parity fix**: the fix did NOT create this — pre-fix the CSM reached `connected` on TCP open and then sat with `authReady=false` forever (equally dead, just mislabeled "connected"). The fix makes the state honest (`connecting`) but the missing-timeout gap is unchanged. Independent follow-up.

---

## Recommendation — **add an auth-handshake timeout** (for the cutover owner)

Mirror the legacy 10s watchdog in `BaseTransportImpl`:
- On `onSocketOpen` (TCP open), arm a handshake timer (e.g. `HANDSHAKE_TIMEOUT_MS`, configurable/injectable for tests).
- Cancel it on `auth_success` (in `onMessage`) and on `onSocketClose`/`stop`.
- On expiry while not-yet-authed: `wsChannel.stop()` + `csm.send({ type: "socket_close" })` → normal `backoff`/reconnect accounting (so it composes with the reconnect-parity budget — a persistently-hanging server then trips `max_attempts_reached → failed`).
- Inject the timer (like `WebSocketCtor`/`graceMs`) so unit tests drive it deterministically; target c8 --100 on the changed surface.

Scope: single-point in `BaseTransportImpl` (covers queue + audio), same shape as the reconnect-parity fix. Estimated small (~1 timer + arm/cancel sites + ~4 tests).
