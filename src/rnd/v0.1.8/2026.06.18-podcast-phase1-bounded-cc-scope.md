## 1. Current shape (what exists today)

- **Envelope**: `PodcastGeneratorJob( AgenticJobBase )` (JOB_TYPE `podcast`, prefix `pg`), async `_execute()`. On the agentic pool already.
- **LLM phase ("Dynamic Duo" script synthesis)**: `PodcastOrchestratorAgent` drives `PodcastAPIClient` through four text-synthesis calls, all `script_model` (Opus), all firewalled-key, all funneling to one `messages.create` (L419):
  - `call_for_analysis` → `parse_analysis_response`
  - `call_for_script` → `parse_script_response` (the main script)
  - `call_for_revision` (optional human-feedback revision loop)
  - `call_with_json_output` (structured metadata; already strips ```json fences, raises on bad JSON)
- **Audio phase (NOT LLM)**: parsed segments → `PodcastTTSClient` (ElevenLabs-style TTS) → `PodcastAudioStitcher` → single MP3.
- **Output contract**: a markdown script of `**[Host Name - Role]**: text *[prosody]*` segments; `parse_script_response` splits it into `get_segment_count()` segments the audio phase consumes.

## 2. Migration boundary (what changes vs what stays)

| Stays as-is | Migrates to bounded CC (in-process sdk_query, D-DR1-X) |
|---|---|
| `PodcastGeneratorJob`/`AgenticJobBase` envelope, CJ Flow routing, agentic pool | The **four script-phase LLM methods** (`call_for_analysis`/`call_for_script`/`call_for_revision`/`call_with_json_output`) — currently the `AsyncAnthropic`/`messages.create` path at `api_client.py:184,419` |
| **Audio phase**: `PodcastTTSClient`, `PodcastAudioStitcher`, the MP3 output | The firewalled-key dependency for the script phase (drop unused refs; `__init__`/api_client firewalled prose → historical for the migrated phase) |
| The parsers `parse_script_response`/`parse_analysis_response` (made LENIENT — §4) | The `_call_with_retry` SDK-retry wrapper → mapped onto CJ Flow primitives (no duplicate retry) |
| Voice I/O, the human review/revision loop (orchestrator state machine) | — |

**Boundary is tight**: only `PodcastAPIClient`'s LLM calls swap mechanism. The orchestrator, parsers, and audio phase are untouched except the parser-leniency change (§4).

## 3. Invocation = D-DR1 Option X (in-process `claude_agent_sdk.query()`)

Replace `PodcastAPIClient`'s `AsyncAnthropic` calls with in-process `sdk_query` + `ClaudeAgentOptions`, mirroring BFE/TFE:

```python
# illustrative target shape (NOT yet written — scope only)
options = ClaudeAgentOptions(
    model           = self.config.script_model,        # Anthropic Opus, unchanged
    system_prompt   = system_prompt,                   # existing personality/script prompts, unchanged
    tools           = [],                              # podcast script-gen needs NO tools (pure synthesis)
    permission_mode = "plan",                          # read-only; no file writes from the model
    max_turns       = self.config.script_max_turns,    # NEW INI key — §5; podcast is ~1-shot, small cap
)
collected = []
async for message in sdk_query( prompt=user_message, options=options ):
    if isinstance( message, AssistantMessage ):
        for block in message.content:
            if isinstance( block, TextBlock ):
                collected.append( block.text )
script_text = "".join( collected ).strip()             # feeds the existing (now-lenient) parser
```

- **No tools** — podcast script-gen is pure text synthesis (unlike DR which needs WebSearch/WebFetch). Simplest possible bounded-CC shape; `tools=[]`, no `can_use_tool` callback needed.
- **OAuth/Max-plan billing** is automatic via `sdk_query` (no API key passed) — the zero-per-token path.
- The four `call_for_*` methods keep their signatures (system_prompt, user_message, temperature, max_tokens) so the orchestrator is unchanged; only their bodies swap to `sdk_query`. **Note**: `ClaudeAgentOptions` may not surface a per-call `temperature` the way the SDK `messages.create` did — if not, fold the "be creative" steer into the system prompt (documented risk, verify at build).

## 4. Output parser = D6 LENIENT (TTS is tolerant)

Per the ratified **D6=LENIENT for Podcast**: bounded CC returns a single completion string that may carry minor formatting variance (leading prose like "Here's the script:", extra whitespace, stray fences). Make `parse_script_response`/`parse_analysis_response` **best-effort with fallbacks**, not fail-loud:
- Tolerate a leading non-segment preamble (skip lines until the first `**[… - …]**:` segment marker).
- Strip ```/```json fences (the `call_with_json_output` path already does this — extend the same leniency to the script parser).
- On a segment that doesn't match the `**[Host - Role]**: …` shape, **skip-and-log** rather than abort the whole script (a dropped malformed line ≠ a failed podcast).
- Keep a floor invariant: if **zero** segments parse, THEN fail (an empty script is a real failure, not variance).

Rationale: the audio phase is tolerant (a slightly-off segment just produces slightly-off TTS); fail-loud here would turn cosmetic drift into total job failure, exactly the user-hostile outcome D6-lenient avoids for Podcast.

## 5. `max_turns` cap + `scheduled_at` (D2 post-midnight)

- **`max_turns`**: podcast script-gen is effectively single-shot (1 synthesis turn, maybe a revision turn). Add INI key `podcast script max turns` (+ splainer entry per the config mandate), default **5** (generous headroom over the ~1-2 turns actually needed; far below DR's 20). The bounded path requires an explicit cap.
- **`scheduled_at` (D2)**: non-interactive podcast generation (batch, scheduled) defaults `scheduled_at` to the next post-midnight slot (12 AM–9 AM EDT). **User-clicked synchronous** podcast requests (a person clicks "generate" and waits) **omit** `scheduled_at` and fire immediately. Field is first-class on `ClaudeCodeQueueRequest:49` — but note: under D-DR1-X (in-process sdk_query) the schedule rides the **`PodcastGeneratorJob` submission/enqueue**, not the in-process call.

### Design reconciliations (for the reviewer)
1. **Parsers are JSON-based, not markdown-segment-based.** Scope §4 prose implied skipping `**[Host - Role]**:` markers, but the actual `parse_script_response`/`parse_analysis_response` (and the `SCRIPT_GENERATION_SYSTEM_PROMPT` output contract) are **JSON** (`json.loads` of a `{title, segments:[…]}` object). D6-LENIENT was therefore applied as **robust JSON-from-prose recovery** (port of BFE's `_extract_last_json_object`), which is exactly the right leniency for chattier `sdk_query` output. The "zero-segment floor" is enforced downstream (orchestrator Phase 5 guards: all-segments-failed → RuntimeError), so the parser stays graceful (returns default) rather than raising — preserving the existing degrade-don't-crash contract.
2. **No per-call temperature** in `ClaudeAgentOptions` (verified by field inspection) → folded into the system prompt via `_temperature_to_steer` (0.8→creative, 0.5→precise, mid→none).
3. **`permission_mode="plan"`** chosen over `bypassPermissions`: with `tools=[]` nothing is permittable anyway; "plan" is belt-and-suspenders read-only. **Live-verified** it does NOT trigger planning/refusal for pure no-tool synthesis.
