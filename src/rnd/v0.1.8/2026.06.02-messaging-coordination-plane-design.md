## TL;DR

Under fleet load, interactive messages to Rick (notify/TTS) and DMs between sessions (commons) **silently vanish**. Root cause is **one plane, not four bugs**: every per-session cosa-voice MCP subprocess fires a **blocking `requests.post(..., timeout=5)`** at the **single shared `:7999` FastAPI server**; when that server's event loop is busy (fleet traffic + inline blocking I/O inside `async` handlers), the 5-second client budget expires and the message is **dropped with no retry, no ack, no durable queue, and no pull-able fallback**. Transient slowness becomes permanent loss.

The fix is five independent levers — **(A) client-side durable outbox + retry/ack**, **(B) server-side loop de-blocking**, **(C) load isolation for the interactive lane**, **(D) a pull-able inbox** (kills the AFK-invisibility FM-18), **(E) backpressure/concurrency caps**. Each is a separate decision; they compose. Recommended order: **A → D → B → C → E**, because A+D alone eliminate *silent loss* (the worst symptom) at the lowest risk.

## Problem — the four FMs are one plane

| FM | Symptom (observed yesterday) |
|---|---|
| **FM-7** | Interactive `notify`/TTS to Rick timed out under fleet load — his voice channel was the first casualty. |
| **FM-11** | Directed `commons_send_to` pushes dropped (`register_network_error`). |
| **FM-15** | Dropped sub-batch reports mimicked author stalls. |
| **FM-18** | `notify` to an AFK user silently bounced → ~4h of real progress invisible → misread as idleness. |

Common shape: **no delivery guarantee · no load isolation · no pull-able fallback.**

## Root cause (confirmed in code, 2026-06-02)

- **Layer-A (refuted the earlier "MCP saturation" theory):** cosa-voice MCP is **stdio, per-session** (`claude mcp get cosa-voice` → `Type: stdio`). Each CC session has its *own* MCP subprocess — there is **no shared MCP server** to saturate.
- **Layer-B (the real bottleneck):** all those per-session subprocesses converge on **one shared `:7999` FastAPI server**.
  - **Client side:** the fire path does a **synchronous `requests.post` with a ~5s timeout** (`src/lupin_mcp/cosa_voice_mcp.py` — auth-validate at line 316 `timeout=5`; `_notify_impl` POSTs `/api/notify`). On timeout the call **raises/returns failure and the message is gone** — no retry, no durable spool. The blocking-ask path (`src/lupin_cli/notifications/notify_user_sync.py`) holds an SSE stream open for the full `timeout_seconds` (split connect/read timeouts), so each in-flight ask **occupies a connection**.
  - **Server side:** handlers are `async def` (`routers/notifications.py::notify_user`, `routers/commons.py::*`) — but they do **inline blocking I/O on the event loop**: file-based commons blackboard reads/writes, DB persistence (response-required mode), WebSocket fan-out. Under N concurrent fleet callers, blocking I/O on the single loop stalls *every* request, so the cheap fire-and-forget notify misses its 5s budget too.
  - **No pull-able fallback:** delivery is push-only. If the user is AFK or the push misses, nothing records a "you have undelivered messages" state the user can later pull (FM-18).

**Already present to build on:** the `/api/notify` endpoint accepts an **`idempotency_key`** (dedup on retry) and a `NotificationFifoQueue` exists server-side — so retry-safety and a queue are partially scaffolded.

## Goals / Non-goals

**Goals**
1. **No silent loss** — every interactive notify + directed DM is either delivered, durably queued for retry, or visibly marked undelivered.
2. **Interactive lane survives fleet load** — Rick's voice path is isolated from bulk traffic.
3. **Pull-able recovery** — an AFK/returning user (or a stalled-looking author) can *pull* what they missed.
4. **Backward-compatible** — existing callers keep working; new reliability is opt-in-by-default at the MCP wrapper, transparent to tool callers.

**Non-goals (this milestone)**
- Replacing `:7999` with a message broker (Redis/RabbitMQ/NATS) — noted as a future option, not proposed now (adds an ops dependency).
- Changing the commons file-blackboard *semantics* (Phase-1 polling model stays; we make its *writes* non-blocking).
- The TTS brevity cap (already shipped) and harvest/reap (already fixed) — separate post-game items.

## Design — five levers, each a decision

### Decision A — Client-side delivery reliability (durable outbox + retry + ack)
*Problem: a timed-out `requests.post` loses the message entirely.*

| Option | Pros | Cons |
|---|---|---|
| **A1. Durable outbox + bounded retry + idempotency_key (RECOMMENDED)** | On send-failure/timeout, write the payload to a per-session on-disk outbox; a background flusher retries with the existing `idempotency_key` (server already dedups) until ack or TTL. Eliminates silent loss with zero server-protocol change. | A little MCP-side state (one small spool dir per session) + a flusher thread. |
| **A2. Inline synchronous retry (N attempts, backoff)** | Trivial; no spool. | Still blocks the caller; if all N fail (server still slow), message is lost — doesn't fix the root failure, just narrows the window. |
| **A3. Fire-and-truly-forget (UDP-style, no ack)** | Zero overhead. | Accepts loss — exactly today's behavior. Rejected. |

**Recommendation: A1.** It's the single highest-leverage fix — it converts "transient slowness → permanent loss" into "transient slowness → delayed delivery." **Flip to A2** only if a per-session spool proves unacceptable (it shouldn't — it's a few KB).

### Decision B — Server-side event-loop de-blocking
*Problem: inline blocking I/O in `async` handlers stalls the single loop under load.*

| Option | Pros | Cons |
|---|---|---|
| **B1. Move blocking I/O off the loop (`run_in_executor` / async file+DB I/O) (RECOMMENDED)** | Handlers stop starving each other; the cheap notify returns fast even while commons writes/DB run on a threadpool. Targeted, no API change. | Must audit each handler for blocking calls; some refactor. |
| **B2. Separate worker process for heavy commons/DB work** | Full isolation. | New process + IPC to manage; heavier than needed now. |
| **B3. Leave as-is, rely on A+C** | No server change. | The loop still stalls; A masks it via retry but latency stays bad. |

**Recommendation: B1**, scoped to the hottest handlers first (commons file writes, response-persist). **Flip to B2** only if profiling shows a single handler dominates beyond what a threadpool absorbs.

### Decision C — Load isolation for the interactive lane
*Problem: Rick's TTS shares a saturation domain with bulk fleet traffic.*

| Option | Pros | Cons |
|---|---|---|
| **C1. Priority/express lane for interactive notify+ask (RECOMMENDED)** | Tag interactive (user-facing) messages; serve them ahead of bulk fleet/commons traffic (priority queue or a dedicated lightweight ingest route that only enqueues). Rick's voice survives a fleet storm. | Needs a priority signal + a small scheduling change. |
| **C2. Separate port/process for the interactive path** | Hard isolation. | Ops complexity; another surface to run + monitor. |
| **C3. Rely on E (caps) only** | Simplest. | Caps slow the fleet but don't *prioritize* the user — Rick could still queue behind bulk. |

**Recommendation: C1.** Pairs naturally with E. **Flip to C2** only if C1's in-process prioritization proves insufficient under real load.

### Decision D — Pull-able inbox (kills FM-18)
*Problem: push-only delivery means an AFK user silently misses messages.*

| Option | Pros | Cons |
|---|---|---|
| **D1. Undelivered-inbox + on-return surfacing (RECOMMENDED)** | Server marks push-failed/҂AFK messages "undelivered"; a `GET` lets the UI (and an agent) **pull** them; on reconnect the UI surfaces "N missed." Directly fixes the "did nothing for 4h" misread. Reuses the existing notification store. | A new read endpoint + an "undelivered" state flag + a UI surfacing hook. |
| **D2. Email/secondary-channel fallback on AFK** | Reaches a truly-away user. | New channel + creds; over-scoped for now. |
| **D3. Rely on A1's outbox replay** | No server read endpoint. | A1 replays *sender→server*; it doesn't help the *user* pull what the server holds. Complementary, not a substitute. |

**Recommendation: D1.** It's the user-facing half of "no silent loss" and the specific antidote to FM-18. **Flip to add D2** later if Rick wants true away-from-keyboard reach.

### Decision E — Backpressure / concurrency caps
*Problem: an unbounded fleet can overwhelm `:7999` regardless of the above.*

| Option | Pros | Cons |
|---|---|---|
| **E1. Per-source concurrency cap + 429-with-retry-after (RECOMMENDED)** | The server sheds/queues excess fleet load gracefully; A1's outbox honors `retry-after`. Protects the box. | Callers must honor 429 (A1 already retries). |
| **E2. Global rate limit only** | Simple. | A burst from one source can still starve others; less fair. |
| **E3. No caps** | Nothing to build. | The original failure mode persists at scale. |

**Recommendation: E1.** Cheap insurance once A+C exist. Lowest urgency of the five.

## Phased rollout (lowest-risk-first)

| Phase | Lever | Why this order | Risk |
|---|---|---|---|
| **1** | **A1** durable outbox + retry/ack | Eliminates *silent loss* immediately, MCP-side only, no server change | Low |
| **2** | **D1** pull-able undelivered inbox | Fixes FM-18 (the human-cost failure); read-only server addition | Low |
| **3** | **B1** de-block the hot handlers | Restores latency under load; targeted refactor + tests | Medium |
| **4** | **C1** interactive express lane | Guarantees the voice path under a storm | Medium |
| **5** | **E1** backpressure caps | Hardens against future scale | Low |

**Each phase is independently shippable + testable**, gated by the 100% coverage mandate. Phases 1–2 alone retire the *silent-loss* class.

## Testing plan (per phase)
- **Unit:** outbox spool/flush/idempotency (A1); undelivered-state transitions + pull endpoint (D1); executor-offload wrappers (B1); priority ordering (C1); 429/retry-after (E1).
- **Integration (`:8000`, scheduled):** N-concurrent-sender storm → assert zero lost messages + interactive-lane latency bound. This is the regression that reproduces yesterday's outage.
- **Live drill (`:7999`):** spawn a small fleet, induce load, confirm Rick's notify still lands (or is replayed) — the empirical proof.
