## Fix 1 — Confidence percentages exceeding 100% (the "22123%")

### Root cause (pinned)
The prediction-engine confidence inherits a **similarity percentage that is not bounded to [0,100]**.

Pipeline:
- `proxy_decision_embeddings.py:208` searches with `.metric("dot")` (dot-product).
- `proxy_decision_embeddings.py:233` converts: `similarity_pct = (1.0 - distance) * 100`, where the dot metric defines `_distance = 1 - dot_product`. So `similarity_pct = dot_product * 100`.
- The dot product equals cosine **only for unit-normalized vectors**. The stored/query vectors are **not** unit-norm (the docstring's "(normalized)" claim is aspirational), so `dot_product` exceeds 1 → `similarity_pct` exceeds 100 (observed ≈ 22123, i.e. dot ≈ 221).
- Downstream: `prediction_engine.py` does `max_similarity = similarity_pct / 100.0` (lines 290/458/679/864) assuming `similarity_pct ∈ [0,100]`, so `max_similarity` became ≈ 221 instead of ≤ 1; `confidence = max_similarity × consistency` stayed > 1.
- Display: `notifications.js:15930` does `Math.round( hint.confidence * 100 )` — **correct** for a 0–1 input; it faithfully rendered the upstream overflow as 22123%.

The healthy engine paths all assume the [0,100] contract; the violation is at the production boundary, so that is where the fix belongs.

### Fix (minimal blast radius, fix-at-source)
`proxy_decision_embeddings.py:233` — clamp to the percentage contract:
```python
similarity_pct = max( 0.0, min( 100.0, ( 1.0 - distance ) * 100 ) )
```
This bounds **every** downstream consumer (`/100 → confidence ∈ [0,1]`) at one chokepoint shared by the prediction engine and the CBR/decision store — no per-consumer defensive code, no display-side patch needed.

Deeper follow-up (not done; bigger blast radius): unit-normalize embeddings on write+query so dot == cosine natively. That requires re-embedding stored rows (a migration) and is deferred; the clamp is correct-by-contract in the meantime.

### Test
`src/tests/unit/test_proxy_decision_embeddings.py::test_similarity_pct_clamped_to_0_100_for_non_unit_vectors` — stores a deterministic non-unit vector (‖v‖=3 → self-dot ≈ 9 → pre-clamp similarity_pct = 900) and asserts every returned `similarity_pct ∈ [0,100]`. Fails without the clamp. **11/11 pass; 138 prediction/decision regression tests pass.**

## Fix 2 — Send-bar code fences render as code (not literal backticks)

### Finding (from the investigation)
Nothing is scrubbed on send — text is stored raw. Two display surfaces differ:
- **Recent Activity** feed: `marked.parse()` + permissive DOMPurify → ``` fences already render.
- **Notification message bubble**: `renderMarkdownInline()` → `marked.parseInline()` (`notifications.js:13746`), whose whitelist allows inline `code` but **not `<pre>`**. `parseInline()` ignores block-level constructs, so ``` fenced blocks did NOT render in the bubble (single-backtick inline code did).

### Fix (minimal blast radius)
`notifications.js renderMarkdownInline()` — when the text contains a fence, delegate to the existing block renderer:
```javascript
if ( typeof text === 'string' && text.indexOf( '```' ) !== -1 ) {
    return this.renderMarkdown( text );   // permits <pre>/<code>, CSS-styled
}
```
Messages without a fence keep the lighter inline path (no `<p>` wrapping) → **zero regression** for the common case. Added `.message-text pre` / `code` CSS in `notifications.css` so the block is legible and contained.

### Test
`src/tests/e2e_ui/test_system_status.py::TestNotificationMarkdownRendering` — drives the actual shipped `renderMarkdownInline()` in a real browser (marked + DOMPurify loaded):
- fenced input → output contains `<pre>`/`<code>`, no raw backticks;
- inline input → `<code>` only, no `<pre>` (no-regression guard).
Venue: :8000 (the `logged_in_page` fixture registers/cleans a DB user). Read-only assertions, but fixture mutation routes it to the scheduled venue.
