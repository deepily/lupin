## TL;DR

`GET /api/commons/active-sessions` (recipient preview) and `POST /api/commons/broadcast-to-cc-sessions` (actual fan-out) both route through `filter_and_project_sessions()` and exclude any session whose **last user interaction** is older than a threshold (`commons broadcast active session threshold seconds`, INI value `28800` = 8h). That conflates *"recently interacted"* with *"alive."* For a fleet of idle-but-alive workers, those diverge by hours — so three live workers (Tiffany, Rachel, Mr. Radio), dormant ~9.5h since the heartbeat campaign wrapped, age out and become unreachable.

**Fix:** switch the reachability signal from `idle_detection.last_interaction_at` → **bridge-file mtime**, governed by a new dedicated key `commons broadcast liveness threshold seconds = 28800` (8h). The idle-waiter heartbeat keeps an armed session's bridge mtime fresh even with zero interaction; a dead session's mtime freezes and ages out. Since `mtime ≥ last_interaction_at` always, mtime@8h is strictly more inclusive than the retired interaction@8h filter (zero false-negative regression) AND rescues the dormant workers.

> **⚠️ Threshold corrected 7200 → 28800 after a live empirical check — see "Empirical correction" below.** The originally-approved 2h window proved unsafe: only sessions with an *armed idle-waiter* keep mtime fresh; a waiterless-idle session (e.g. María) lets mtime go stale while alive, so 2h would false-negative it. 8h is the safe dominant value. A tight window needs a fixed-cadence listener heartbeat first (deferred follow-up).

## Root cause (file:line)

`src/cosa/rest/routers/commons.py:365-367` — `filter_and_project_sessions()`:

```python
last_epoch = _bridge_last_activity_epoch( bridge )            # reads idle_detection.last_interaction_at
if last_epoch is not None and ( now_epoch - last_epoch ) > active_session_threshold_seconds:
    continue                                                  # excludes dormant-but-alive workers
```

The threshold is read at startup from the old key (`src/fastapi_app/main.py:590`, INI `src/conf/lupin-app.ini:602` = `28800`). The 2026-05-13 fix correctly wired `_bridge_last_activity_epoch` to read the nested `last_interaction_at` (closing a phantom-leak), and the value was bumped 600s → 28800s to stop filtering idle interactive dev sessions. But 8h still excludes a worker dormant longer than 8h — and the heartbeat-campaign fleet routinely is.

## Why mtime is the correct signal (provable dominance)

`last_interaction_at` measures **when the user last interacted**. Bridge **mtime** measures **when the bridge was last written** — and the bridge is written by (a) every interaction (Stop hook → `set_idle_detection_field`) AND (b) every idle-waiter re-arm tick. Therefore:

> **mtime ≥ last_interaction_at, always.**

So replacing the `last_interaction_at` age check with an mtime age check, at the *same or tighter* threshold, can **only include more** live sessions, never fewer. It cannot regress any session the old filter admitted. And because the idle-waiter heartbeat keeps mtime fresh on a known cadence, we can *tighten* the window (8h → 2h) and prune dead phantoms 4× faster than today.

Dead sessions still get pruned: when a session dies, its idle-waiter child detects PPID death (30s-chunked liveness check) and exits — no more re-arms — so the bridge mtime freezes and ages past the threshold.

## Threshold math + Empirical correction (why 8h, not 2h)

**The original (flawed) argument for 2h:** idle-waiter backoff schedule (`src/lupin_cli/claude_code/hooks/lib/idle_settings.py:25`) is `[5, 10, 20, 40, 60]` minutes, capped at 60 (`idle_waiter.py:213`). Each re-arm rewrites the bridge (`idle_waiter.py:114-118,290-301`), bumping mtime → worst-case mtime staleness for a deeply-idle session ≈ 61 min. So a 2h window seemed to give a safe 2× margin AND prune dead phantoms 4× faster than 8h.

**Why it's wrong (live empirical check, 2026-06-05):** that 61-min bound holds ONLY for a session with an **armed idle-waiter**. Live bridge census:

| Session | idle-waiter | mtime age | @2h | @8h |
|---|---|---|---|---|
| Tiffany 💍 (spawned worker) | active (waiter_pid set, backoff 4) | ~37 min | ✅ | ✅ |
| Rachel 🕊️ (spawned worker) | active | ~37 min | ✅ | ✅ |
| Mr. Radio 🦉 (spawned worker) | active | ~41 min | ✅ | ✅ |
| **María 🌸 (peer)** | **none — `waiter_pid=None`, backoff 0** | **~3.5 h** | ❌ **dropped** | ✅ |
| Tiberius 👑 (me, active) | none, but actively writing the bridge | ~20 min | ✅ | ✅ |

A session that is idle WITHOUT an armed waiter (María) has nothing refreshing its bridge mtime, so mtime goes stale while the session may still be alive. A 2h window would false-negative exactly such a session — the precise bug (dropping a reachable session) this change exists to fix.

**The safe value — 8h (28800):** since `mtime ≥ last_interaction_at` always, an mtime@8h filter includes *every* session the retired interaction@8h filter included (a session with interaction younger than 8h necessarily has mtime younger than 8h) → **zero false-negative regression** — AND additionally rescues the dormant workers (interaction 18h old but mtime ~40 min). Phantom tolerance stays at today's 8h; the original complaint was dropped workers (false-negatives), not lingering phantoms.

**To safely tighten later:** add a fixed-cadence bridge heartbeat to the cc-notification-listener so EVERY alive session (not just those with armed waiters) refreshes mtime on a known interval. Then the window can drop to ~2h with the invariant `threshold > heartbeat_interval`. Tracked as the deferred "listener heartbeat" follow-up.

## Design

### New INI key (replaces the old one)
- **`commons broadcast liveness threshold seconds = 28800`** — NEW dedicated key. Retires `commons broadcast active session threshold seconds` (interaction-based; removed).
- Mechanism-agnostic name on purpose: the signal (mtime) is documented in the splainer, not baked into the key.

### Core change — `filter_and_project_sessions()` (`commons.py:317`)
- Add injectable `mtime_fn: Callable[ [ Any ], float ] = lambda p: p.stat().st_mtime` (mirrors the existing `now_epoch_fn` injection pattern in `execute_broadcast`) for filesystem-free unit tests + Clock-injection discipline.
- Replace the `_bridge_last_activity_epoch(bridge)` age check with: `age = now_epoch - mtime_fn( path ); if age > threshold: continue`. The `path` is already the first element of each `raw_sessions` tuple.
- `mtime_fn` has a real default, so `execute_broadcast()`, `get_active_sessions`, and the commons-ask fan-outs (the other `filter_and_project_sessions` callers) need **no signature changes** — they inherit the default. Only `execute_broadcast` gains a pass-through `mtime_fn` param (default real impl) to keep symmetry with `now_epoch_fn` for its own tests.
- `_bridge_last_activity_epoch()` (`commons.py:247`) is no longer called by the filter. **Kept** (not removed) as a still-tested helper — its dedicated tests live in BOTH test trees, and removing it would churn ~30 unrelated tests for no functional gain; coverage stays 100% because its tests still execute it. (Minimum-blast-radius call.)
- `project_session_response().last_seen_iso` is unchanged — keeps reading `last_interaction_at` as *informational* "last actually interacted" display (distinct from the reachability decision).
- `mtime_fn` is also threaded (with a real default) through `execute_broadcast()`, `_resolve_dm_recipient()`, and `execute_register_question()` — every source caller of the filter — so their string-path unit tests inject a fake mtime. Route handlers use the real default.

### Config wiring
- `src/fastapi_app/main.py:590`: read the new key (`default=28800`).
- Internal param/var name `active_session_threshold_seconds` / `_active_session_threshold_seconds` is left as-is (still accurate: "how recently must a session show activity" — now liveness) to keep blast radius minimal across its ~8 threading sites.
