# WS Reconnect Parity Gap — legacy `ws-channel.js` vs mux `ConnectionStateMachine` + `QueueTransport`

**Date**: 2026-06-18
**Author**: Rio ⚡ (read-only audit; no live-code edits)
**Trigger**: surfaced during the JS→TS mux-migration scope assessment of `ws-channel.js` (umbrella `312ba8ab`). Filed as durable task `4450995d` for the mux-cutover owner.
**Severity**: **MEDIUM-HIGH cutover risk** — NOT a live bug today (the multiplexer is built but the cutover is Rick-gated / not flipped). Must be resolved **before/at** the notifications.js→mux cutover, because the mux *replaces* the legacy circuit-breaker.

---

## TL;DR

The legacy `ws-channel.js` circuit-breaker resets its reconnect-attempt budget **only on an application-level `auth_success`** envelope. The mux replacement (`ConnectionStateMachine` driven by `QueueTransport`) resets the budget on **TCP/WS socket open**, *before* auth. Consequence: against a server that completes the WebSocket handshake but then **fails or rejects authentication**, the mux enters an **unbounded reconnect loop** — its terminal `failed` (circuit-open) state is effectively **unreachable** for the auth-failure path. The legacy breaker correctly trips (`OPEN_CIRCUIT`) and routes the failure to a token-refresh / "session displaced" / "permission denied" handler.

Three concrete parity gaps (one primary, two secondary).

---

## Evidence

### Legacy `ws-channel.js` (production-wired via `notifications.js` dynamic import)
- Counter reset **only** on `auth_success` envelope — `ws-channel.js:279-282` (`attempts = 0; recentFailures = []` inside the `auth_success` branch).
- `AUTHENTICATING` state set on socket open; `CONNECTED` only after `auth_success` (`:251`, `:282`).
- **Three** trip paths to terminal `OPEN_CIRCUIT`:
  1. **budget-exhausted** — `attempts >= MAX_ATTEMPTS_PER_CHANNEL (20)` (`:352`).
  2. **rapid-fail** — `>= RAPID_FAIL_COUNT (5)` closes within `RAPID_FAIL_WINDOW_MS (30s)` while the socket *never opened* (`:337`).
  3. **auth-permanent** — close code ∈ `{4001,4002,4003}` → straight to `OPEN_CIRCUIT`, no decrement (`:303-307`, `PERMANENT_CLOSE_CODES`).
- `CIRCUIT_OPEN_EVENT` dispatched on `window` with `detail.reason` + `detail.code` so the consumer routes 4001→token-refresh, 4002→session-displaced, 4003→permission-denied (`:380-402`).

### Mux `ConnectionStateMachine.ts` + `QueueTransport.ts`
- `connected` state entry runs **`resetAttempts`** (`ConnectionStateMachine.ts:135-136`, `entry: "resetAttempts"`).
- `QueueTransport.onSocketOpen()` sends `{ type: "socket_open" }` to the CSM **on TCP open, before auth** (`QueueTransport.ts:214-215`), then issues the `auth_request` (`:219-228`).
- `connecting --socket_open--> connected` and `reconnecting --socket_open--> connected` both hit the resetting entry (`:129`, `:147`).
- Grace-fluke path: a `socket_close` within `DEFAULT_GRACE_MS (100ms)` of open → `reconnecting` with **no `incrementAttempts`** (`:138-141`).
- Terminal `failed` reached **only** via `max_attempts_reached`, fired by the wrapper when `csm.attempts >= maxAttempts (20)` (`QueueTransport.ts:301-304`).

### The failure trace (auth-rejecting server, mux)
```
TCP open → CSM socket_open → connected (entry: resetAttempts → attempts=0)
         → transport sends auth_request
server rejects auth, closes (auth_error / generic close code, NOT 4001-4003)
         → CSM socket_close
            ├─ if close <100ms after open → reconnecting (NO increment)   → attempts stays 0
            └─ else                       → backoff (increment → 1)
         → reconnect → TCP open → connected (resetAttempts → attempts=0 AGAIN)
         → … repeats forever; attempts never approaches 20; `failed` never reached.
```

## Parity gaps

| # | Legacy behavior | Mux behavior | Gap | Severity |
|---|---|---|---|---|
| **1** | Budget resets **only on `auth_success`** | Budget resets on **TCP `socket_open`** (`connected` entry) | **Auth-failure reconnect is UNBOUNDED — circuit never opens.** Grace-fluke path makes fast auth-fails not even increment. | **HIGH** |
| **2** | Permanent auth close codes `4001/4002/4003` → immediate `OPEN_CIRCUIT` + `reason`/`code` routing | No `4001/4002/4003` handling anywhere in `transport/` or `auth/` (grep: 0 hits); treated as a normal close | No fast-fail on permanent auth rejection; no token-refresh / displaced / permission-denied routing | **MEDIUM** (compounded by #1 → loops forever) |
| **3** | `rapid-fail`: 5 never-opened closes / 30s → `OPEN_CIRCUIT` | No rapid-fail accounting (grep: 0 hits) | Fast-flapping never-open socket relies solely on the 20-attempt budget (slower trip); acceptable for pure-connectivity loss | **LOW** |

**Handled-differently / NOT gaps (mux is equal-or-better):**
- **budget-exhausted (20 attempts)** — parity ✓ (`DEFAULT_MAX_ATTEMPTS = 20`, same as legacy). Works correctly for **pure connectivity failure** (TCP never opens → no reset → trips at 20).
- **offline / network_online** — mux models a distinct `offline` state (network-aware); legacy approximates via `online`/`offline` → `manualRetry`/`close`. Mux arguably cleaner.
- **grace-fluke fast reconnect** (`<100ms`) — a mux improvement (no legacy equivalent), but it interacts badly with gap #1 (see trace).
- **`AUTHENTICATING` state** — not modeled as a distinct state, but auth IS performed by the transport. The only material consequence is gap #1 (reset-on-open vs reset-on-auth).

## Blast radius

- **When it bites**: any time the server completes the WS handshake but auth then fails — expired/invalid token whose refresh also fails, displaced session, revoked permission, or a server-side auth bug.
- **Impact**: the client hammers the server with `reconnect → auth_request → reject` forever — no circuit-open, no user-facing "session expired / re-login" affordance, continuous battery/network/server load. The legacy breaker stops after 20 (or 5 rapid) and routes the user to token-refresh.
- **Scope**: applies to **every** transport built on `QueueTransport` (queue + audio). The give-up policy lives in the shared base, so the fix is single-point.
- **Not live today**: the mux is not cut over (Rick-gated). This is a **pre-cutover correctness gate**, not a production incident.

---

## Recommendation — **FIX before cutover** (not noop)

**Primary (gap #1, required):** realign the budget-reset to application-level auth success.
- Option A (smallest): in `QueueTransport`, do **not** send `socket_open` to the CSM on TCP open; send it (or a new `auth_succeeded` event) only when the `auth_success` envelope arrives (`onMessage`, `:249`). Keep `connected`'s `resetAttempts`.
- Option B (most faithful to legacy): add a distinct `authenticating` state to the CSM (`connecting/reconnecting --socket_open--> authenticating`; `authenticating --auth_succeeded--> connected[resetAttempts]`; `authenticating --socket_close--> backoff[increment]`). Mirrors the legacy `AUTHENTICATING` semantics exactly.
- Either way: a server that opens-then-rejects-auth must **accumulate attempts** so `max_attempts_reached → failed` is reachable.

**Secondary (gap #2, recommended):** map permanent auth close codes `4001/4002/4003` (and/or an `auth_error` envelope) to an **immediate** `failed` transition carrying a `reason` + `code`, so the cutover's notifications UI can route token-refresh / session-displaced / permission-denied (legacy `CIRCUIT_OPEN_EVENT.detail`).

**Tertiary (gap #3, optional):** add rapid-fail fast-trip if pure-connectivity flap-protection latency matters; otherwise the 20-budget is an acceptable substitute.

**Verification**: add unit tests to the CSM/transport suite asserting (a) an open-then-auth-fail loop trips `failed` within the budget, and (b) a `4001` close routes to `failed` with the reason/code. (Mirror legacy `07-test-strategy.md` Layer-1 expectations.)
