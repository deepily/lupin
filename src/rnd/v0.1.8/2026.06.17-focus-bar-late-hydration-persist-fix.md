# Focus-bar selection lost on page refresh — late-hydration restore fix

**Date:** 2026-06-17 · **Author:** Tiffany 💍 (worker under Mr. Radio 🦉) · **Branch:** `wt-tiffany-focusbar-persist` (off `abb95fe6`)
**Bug (Rick, TOP priority):** the focus-bar toggle in the LEGACY `notifications.js` loses its selection on
page refresh — the user must reselect focus every reload.

---

## TL;DR

The selection is **already persisted** to `localStorage` (`_saveCcFocusState`) and there **is** a restore
pass (`_restoreCcUiAfterLoad`). The bug is NOT missing persistence — it is an **incomplete restore for a
focused session that hydrates late** (after the restore pass runs).

## Root cause (verified in code)

1. On reload, `_restoreCcUiAfterLoad()` runs after `loadConversationHistory`. If the focused sender's
   **card is not present yet**, it calls `_exitFocusMode( false )` — which reverts the **in-memory**
   `ccFocusState` to `{ enabled:false, focused_sender_id:null }` while **keeping the localStorage intent**
   (`persist=false`). Comment at the call site explicitly preserves intent for "next reload."
2. The late-arrival re-apply in `_addStripIcon` (the `data-focused` mark) and `_applyFocusHiddenToCard`
   only consult the **in-memory** `ccFocusState.enabled` — now `false`. So when the focused session finally
   arrives via async WS, **nothing re-reads the persisted intent**, and focus is never re-applied.
3. Focused sessions are frequently the late-arriving ones (an active worker whose first report comes over
   WS, not in the initial `senders-visible` payload) → the symptom hits nearly every reload.

Net: localStorage holds the right selection, but the UI silently stays in default mode until the user
manually reselects. Exactly Rick's report.

## Fix (smallest correct — completes the restore)

`_maybeReapplyPersistedFocus( senderId )` (new), called from the **top of `_addStripIcon`** (before its
idempotent early-return, so it also covers the icon-present/card-absent ordering). When a session's
icon/card hydrates, it re-reads `localStorage[CC_FOCUS_STATE_KEY]`; if focus is persisted-enabled for THIS
senderId but in-memory focus is currently disabled, it calls `_enterFocusMode( senderId )` (no flash),
which re-walks all cards+icons and re-syncs in-memory + localStorage. Idempotent: no-ops once focus is
active, for a non-focused session, when nothing is persisted, or on corrupt JSON (caught).

Bonus: this also strengthens the existing "preserve intent across transient icon dealloc/re-add" design —
a focused session that briefly drops and returns now re-applies focus automatically.

**Why client-only:** the entire focus feature is client-state in `localStorage`; no server surface is
involved. No server change needed or made.

- **Reproduction + proof:** focused session A hydrates LATE → focus self-restores (toggle pill ON, A icon

- Guards: non-focused late arrival doesn't steal focus; disabled/absent persisted focus is a no-op;
  already-active focus is idempotent; corrupt localStorage is swallowed (no throw); missing senderId no-op.
