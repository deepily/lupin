## 0. TL;DR (the decision Rick actually needs)

`notifications.js` is a **20,288-line single God-class** (`class NotificationsUI` →
`window.notificationsUI`), loaded by exactly ONE page (`notifications.html`).

**The dominant finding: its successor already exists.** The multiplexer
(`static/js/multiplexer/**`, ~75 `.ts`) is a near-complete parallel
reimplementation and is **flip-ready** (per `2026.06.17-multiplexer-migration-flip-walkthrough.md`).
Every major unit of notifications.js already has a TS twin in the mux (table §2).

**⇒ Primary recommendation: do NOT decompose notifications.js into standalone
bundles. COMPLETE-AND-FLIP the mux (retire notifications.js wholesale via the INI
redirect; keep `?classic=1` as the JS-vs-TS research corpus per Rick's D2).**
Standalone decomposition would re-build ~75 mux modules that already exist — the
same throwaway/duplication trap that (correctly) killed the broadcast-panel.js port.

Standalone extraction only pays off for units loaded by **other** (non-notifications)
pages — which is exactly why `lupin-nav.js` (16 pages) and `websocket-diagnostic.js`
(own page) were clean wins. **Nothing inside notifications.js is cross-page** — it is
all `window.notificationsUI`, notifications.html-only → all superseded by the flip.

A contingency slicing order is given in §4 **only** if Rick rejects the flip and
wants incremental de-risking instead.

## 1. Structure at a glance

- **Shape**: one ES class, ctor state lines 26–426 (≈12 subsystems' state intermingled), then ~25 `// ===` method sections.
- **The spine**: a `switch( envelope.type )` WebSocket router at **line 2688** (cases: auth_success/error, connect, tts_job_request, job_state_transition, job_removed, notification_queue_update, notification_responded/expired/play_sound, sys_time_update, sys_ping). **Almost every feature is driven from here** — it is the highest-coupling extraction obstacle.
- **The heart**: a dense ~5,300-line / 138-method block (lines 10076–15377) holding notification render + sender-cards + strip-icons + focus-bar + persona badges + commons-activity + master-detail reading pane. Tightest internal coupling.
- **Satellites** (separate files, coupled via `window` globals): `broadcast-panel.js` (`window.broadcastPanel`, driven by the spine's `commons_broadcast_ack`/voice-persona cases @5734/5771/5799 — scoped + DEFERRED 2026-06-18) and the **audio cluster** (`audio-recorder.js`, `sequential-audio-manager.js` [Rio→TS], `hybrid-tts.js`, `chunk-sequencer.js`, `tts-audio-cache.js` — Rio's lane).

## 3. Coupling reality

- **Single spine, deep reach.** The `switch@2688` drives render, strip-icons, focus, TTS, queue, broadcast-hooks, and triggers the fleet/task pollers. Any unit pulled out of the page must either subscribe to a new event bus or keep a hook back into this switch — i.e. the mux's EventBus architecture, which already exists.
- **The "heart" is not modular.** Focus-bar, strip-icons, sender-cards, persona badges, and TTS-state-mirroring share DOM and call each other freely (140 focus refs alone). These cannot be sliced cleanly without first building the seams the mux already built.
- **Two genuinely-bounded internals**: fleet-status and task-list are the only units fed by their **own** poll intervals (not the spine) and each has a complete mux twin — so they are the *least*-coupled, but still notifications-page-only.

## 4. Recommendation

**Primary (strongly recommended): flip, don't decompose.** Finish + flip the mux
(retire notifications.js wholesale; `?classic=1` stays as research corpus). The
decomposition work is ~90% already done *as the mux*. Re-extracting it into
standalone bundles duplicates that and produces throwaway code at flip time.

**Contingency slicing order** (ONLY if Rick rejects the flip and wants to thin the
monolith incrementally, e.g. to de-risk):
1. **Utility methods first** — the shared substrate; everything depends on it (mux has dom/html/time/markdown to mirror).
2. **Fleet-status, then task-list** — the two bounded, own-poll units with complete mux twins to copy; lowest collision; the only ones that resemble a clean standalone port.
3. **Genie animation / section-visibility toolbar / abstract tooltip** — small, self-contained, low value (do only if idle).
4. **Defer indefinitely**: the spine, the render/strip/focus/sender-card heart, TTS, queue UI, job-submission, action-required — highest coupling + active churn; never worth standalone extraction when the flip retires them wholesale.

**Do not** standalone-port anything notifications-page-internal speculatively — it is
the broadcast-panel.js trap (real code, but superseded + throwaway at flip).

## 5. What this confirms about the standalone-entry pattern

The standalone esbuild-entry pattern (`tsconfig.<name>.json` + `build-<name>.sh`,
proven by `nav` + `websocket-diagnostic`) is the right tool for **cross-page or
own-page independent modules** — NOT for carving up a single-page God-class whose
successor already exists. The two clean ports done + this assessment together draw
the line cleanly for Rick: extract what's shared/independent; flip what's page-bound.
