### 2.2 What the arbiter actually depends on (Explore, 2026-06-10)

- **Shells out to `docker inspect <container> --format '{{json .State.Health}}'`** (`health_watcher.py:104-119`) for each watched container → **needs the docker CLI + daemon access**.
- Watched containers come from INI key `arbiter health watch containers` (default `lupin-rest-dev,lupin-rest-test,lupin-model-server,lupin-postgres`) and `arbiter health flap exclude containers` (default `lupin-rest-dev`) — **both are local container names; they MUST be overridden for the VM** (the cloud stack has different names + no postgres).
- **Import chain is LIGHT** — measured this session: `create_production_app`'s import graph pulls **ZERO** heavy modules (no torch / pandas / numpy / transformers; 468 light modules). The arbiter is FastAPI + uvicorn + `cosa.config` + `cosa.agents.heartbeat_arbiter` + `cosa.utils` only.
- **`LupinArbiterGateway.from_environment`** posts escalations to durable commons topics (file-based store) — degrade-safe.
- **Live-notify hop** (`arbiter live notify url`, default `http://127.0.0.1:7999`) POSTs escalations to `/api/notify`; reads the X-API-Key from `~/.lupin/config`. **Degrades to None safely** if disabled or the key can't be resolved.
- **context_pressure_writer** reads CC transcripts from `~/.claude/projects/**/*.jsonl` — on the VM there are no interactive CC sessions, so this is idle / degrade-safe.
- **Runs host-side locally** — confirmed: no arbiter container exists locally; it is a `systemd --user` unit (`~/.config/systemd/user/lupin-arbiter-app.service`) whose `ExecStart` is `src/scripts/run-lupin-arbiter-app.sh`, binding `0.0.0.0:8001`. The :7999/:8000 reverse-proxies reach it via `host.docker.internal:host-gateway`.

### 2.3 The fork: containerized service vs host systemd — and the recommendation

Two viable shapes for the arbiter on the VM:

**Option A — containerized compose service** (in a *separate* `docker-compose.cloud-arbiter.yml` so its lifecycle is independent of the app stack)
- ➕ No host venv (reuses a baked image).
- ➖ **The lupin image ships NO docker CLI** (verified: `docker exec lupin-rest-dev which docker` → empty; Dockerfile has no `docker-ce-cli`). A containerized arbiter therefore needs a *new* image (slim python + `docker-ce-cli` + the light deps) OR a fragile host-binary bind-mount.
- ➖ Needs `/var/run/docker.sock` bind-mount + `group_add: ["137"]` (host docker GID) for UID-1001 to read the socket.
- ➖ Even in a separate project, a `docker compose down` of the arbiter file kills the watcher; out-of-band is only *partly* recovered.

**Option B — host `systemd --user` on the VM (mirror local) — ✅ RECOMMENDED**
- ➕ **Mirrors the local architecture exactly** — lowest conceptual divergence (the M1 "deploy model" decision explicitly valued lowest divergence).
- ➕ **Truest out-of-band** — survives a full `docker compose down` of the app stack (the watcher's entire reason to exist).
- ➕ Uses the **VM host's docker CLI natively** (the VM's `startup.sh` installs driver+toolkit+**docker**) — no socket-in-container, no GID juggling, no image rebuild.
- ➕ The host venv is **cheap** — the arbiter pulls no heavy deps (measured), so a light `requirements-arbiter.txt` venv suffices (no torch).
- ➖ One new provisioning surface: a host `python3 -m venv .venv` + light pip install. Fully scriptable.

**Recommendation: Option B.** The docker-CLI-not-in-image finding + the light-deps finding + the out-of-band principle all point the same way. The existing systemd unit, run script, and install README already exist (`src/lupin_arbiter_app/systemd/`) — only three VM-specific values change (LUPIN_ROOT path, config block → Testing-GCS, watched-container override).

> **DECISION FOR RICK (queued §7, via Tiberius):** ratify Option B (host systemd) vs Option A (containerized). Default = B; artifacts below are built for B (reversible — no GCP mutation). This is the arbiter analogue of M1's Auth-Proxy "sidecar vs host systemd" open question, where sidecar was chosen for the *proxy*; the arbiter is the opposite case because out-of-band independence is its defining property.

## 5. Resolved open items

- **(f) `LUPIN_ENV` testing-vs-production tension — RESOLVED.** `is_cloud_backed()` (`database.py:32-51`) gates **solely** on `LUPIN_CLOUD_BACKED`; it is never inferred from the env name. - **(g) Single-L4 model double-load — RESOLVED (verified 2026-06-10).** Three facts close it: (1) the cloud-test `lupin-rest` service has **NO GPU reservation** (verified — no `deploy.resources.reservations.devices` block) → it physically cannot grab the L4; (2) STT already defers — Baseline `speech to text provider = model-server` → no in-process Whisper; (3) the only remaining in-process GPU consumer would be the embedding **encoders** (Baseline `embedding provider = local`). **Resolution:** `[Lupin: Testing-GCS]` now also sets `embedding provider = model-server`, so the rest app routes embeddings over HTTP to `lupin-model-server:7998` and loads **NO** models in-process. Net: the GPU-resident `lupin-model-server` is the **SOLE L4 consumer** — zero double-load, zero contention. Both overrides confirmed loading via ConfigurationManager against the Testing-GCS block.
