# New-Deployer Runbook — Lupin GCP cloud-test VM (full bring-up + validation)

**Created:** 2026-06-15 (Tiberius 👑, captured live during the keys→login→Phase-G session with Rick)
**Audience:** a **new deployer** who needs to stand up — or operate — the Lupin app + model-server on the GCP cloud-test VM from a near-empty state, **including every gotcha we actually hit** (each one cost real debugging time; they are the most valuable part of this doc).
**Scope:** picks up *after* infra (M1/M2 terraform: VM, Cloud SQL, secrets, Artifact Registry, IAM) already exists. For the infra provisioning itself, see the M2 milestone doc.
**Companion docs:**
- Command-level SSH/login reference: [VM Connectivity & Claude /login Runbook](2026.06.15-vm-connectivity-and-claude-login-runbook.md)
- Infra + critical-path origin: [M2 Arbiter Ride-Along + VM Cutover](2026.06.10-m2-arbiter-ride-along-and-vm-cutover.md)

> **Mental model first (read this or nothing else makes sense):**
> The containers do **NOT** run the code baked into the image. They run the **host bind-mount**: `/mnt/lupin-data/lupin/src` → container `/var/lupin/src` (the WORKDIR). So "deploy new code" = **update the on-VM git checkout + restart the container** (image rebuilds are deps-layer only). The on-VM repo is owned by **UID 1001** (the container user) — this single fact causes ~half the gotchas below.

## 0b. Browser access — IAP tunnel (no public IP)

The VM has no public IP; the app `:7999` is published to the VM host (`0.0.0.0:7999`). Reach it from a local browser via an **IAP TCP tunnel**.

> **Port convention (project standard):** local test ports = the corresponding **dev port minus 1000**. The dev server is `:7999`, so the cloud-test tunnel maps to local **`:6999`**. This keeps the tunnel from colliding with the local dev `:7999` and gives every test port a predictable `-1000` mapping.

```bash
gcloud compute start-iap-tunnel lupin-host-test 7999 \
  --local-host-port=localhost:6999 --zone=us-central1-a
```
Leave that terminal running (foreground), then browse **http://localhost:6999** (forwards local `6999` → VM `7999`; works for the UI + WebSockets). `Ctrl-C` closes the tunnel.

## 1. Provider keys → VM  ⚠️ GOTCHA #1 (1001-owned dest)

The model-server is **unhealthy until the 10 provider-key files exist** in `src/conf/keys/` (mount model: keys are read from FILES, not Secret Manager).

**The trap:** the dest dir is **UID-1001-owned**, so your SSH user **cannot `scp` directly into it** (`Permission denied` on every file). **Stage in `/tmp`, then `sudo cp` + `chown`.** The 10 files: `anthropic-api-key-firewalled openai groq google gemini mistral eleven11 kagi huggingface notification-api-claude-code-dev`.

```bash
# 0) staging dir
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap --command='mkdir -p /tmp/lupin-keys'
# 1) scp into staging (glob form — dest exists, so keys/* not keys/ to avoid keys/keys nesting)
gcloud compute scp --recurse /mnt/DATA01/include/www.deepily.ai/projects/lupin/src/conf/keys/* \
  lupin-host-test:/tmp/lupin-keys/ --zone=us-central1-a --tunnel-through-iap
# 2) sudo-copy into the 1001 dir + chown + cleanup + verify (expect 10 files owned 1001)
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap \
  --command='sudo cp /tmp/lupin-keys/* /mnt/lupin-data/lupin/src/conf/keys/ && sudo chown 1001:1001 /mnt/lupin-data/lupin/src/conf/keys/* && rm -rf /tmp/lupin-keys && ls -la /mnt/lupin-data/lupin/src/conf/keys'
```

## 2. Make the model-server read the keys  ⚠️ GOTCHA #2 (restart, not up -d)

Keys on the mounted volume are only read **at process start**. A container that's been up does **not** see newly-added files, and `docker compose up -d` will **not** recreate it (its config didn't change — only mounted file contents did). **`docker restart`** the model-server:

```bash
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap \
  --command='docker restart lupin-model-server-cloud-test'
```
Verify (healthcheck ~1 min to load 3 models): `docker ps` → `healthy`; log should show `API key loaded ...`, `device=cuda:0`, `models_loaded=['whisper','code_rank_embed','nomic_embed_text_v1_5'] errors=[]`.

## 3. Code currency (optional for validation)  ⚠️ GOTCHA #3 (local bundle + 1001 .git)

**PREFERRED (automated) — `src/scripts/deploy-cloud-test.sh`** (task `d8c699aa`; design `src/rnd/2026.06.23-gcp-code-sync-to-runtime-design.md`). This scripts the entire flow below, *correctly*: it exports a **committed** ref (`git archive`, never the dirty tree), **auto-detects the axis** (pure `src/` change → bind-mount sync + `docker restart`; `pyproject.toml`/`uv.lock` change → fail-loud, requires `--deps` to take the image-rebuild path — never a silent restart that won't load new deps), stamps provenance to `/mnt/lupin-data/lupin/.deployed-ref`, keeps the prior `src/` as `.bak-<stamp>`, and health-gates with auto-rollback. Pure helpers are unit-tested in `src/tests/unit/deploy/test_deploy_cloud_test_lib.py`.
```bash
./src/scripts/deploy-cloud-test.sh --dry-run            # print the plan, touch nothing
./src/scripts/deploy-cloud-test.sh                      # AXIS-A code sync of HEAD
./src/scripts/deploy-cloud-test.sh --ref <sha> --deps   # AXIS-B (deps changed) image rebuild path
```
"What's running?" is now one `cat /mnt/lupin-data/lupin/.deployed-ref` (SHA + ts + axis), not a code-grep.

**MANUAL fallback** (what the script automates — kept for first-run / debugging):
The running code = on-VM checkout via the bind-mount. To update it:
- Origin is a **local bundle** (`/mnt/lupin-data/lupin-wip.bundle`), not GitHub → you must **regenerate the bundle on the dev box, SCP it, and re-point/replace it**. (A delta bundle from the VM's current HEAD is tiny — ~160 KB.)
- `.git` is **1001-owned** → `git -c safe.directory=...` silences the *ownership warning* but does **NOT** grant write; `git pull` as your SSH user fails (`cannot open .git/FETCH_HEAD: Permission denied`). Run git via **`sudo`** (passwordless sudo is enabled), then **`sudo chown -R 1001:1001 /mnt/lupin-data/lupin`** afterward (a pull writes files as the pulling user; the container needs 1001).
- After updating the checkout, **`docker restart`** the app container (FastAPI runs `reload=False` in cloud) to load new code.

**Validation does NOT require latest code** — none of the held commits affect Phase G. Refresh only when you specifically need the latest branch, and only when the branch is settled + pushed.

## 4. Claude Code `/login` (OAuth, the human step)  ⚠️ GOTCHA #4 (token precedence)

The bounded-CC / Max-subscription path needs an OAuth login. **D1 (precedence):** a **non-empty `CLAUDE_CODE_OAUTH_TOKEN` env var overrides** the stored `~/.claude` login and re-introduces the static-token expiry race. Verify the running container has it empty:
```bash
docker exec lupin-rest-cloud-test sh -c 'echo TOKEN=[${CLAUDE_CODE_OAUTH_TOKEN}]'   # want TOKEN=[]
```
Then log in interactively (real TTY — SSH in plainly, not `--command`):
```bash
docker exec -it lupin-rest-cloud-test claude
  → /login  → open the printed URL in any browser  → paste the code back
```
- Creds land in the container and **survive `docker restart`**; lost only on full `docker rm`/recreate.
- **Durable persistence** across recreates needs the `claude-creds` named volume (compose enabler commit `b524c15d`) — which requires a code refresh (§3) + a `docker compose up -d` recreate (which **wipes** an ephemeral login → re-login once after). Treat as a separate hardening step.

## 5. Seed a DB user  ⚠️ GOTCHA #5 (migration drift) + GOTCHA #6 (auth boundary)

A fresh `lupin_db_test` (alembic-bootstrapped) has **0 users**; pipeline/job tests need an authenticated user. Seed via the app's own hashing:
```python
# inside the container:
from cosa.rest.user_service import create_user
create_user( "interactive.job.tester@lupin.deepily.ai", "<password>", ["user"] )
```

> **⚠️ GOTCHA #5 — KNOWN BUG (model-vs-migration drift):** `create_user` fails with
> `column "is_protected" of relation "users" does not exist`. The `User` model
> (`src/cosa/rest/postgres_models.py:84`) declares `is_protected`, but **no alembic
> migration adds it** — so ANY migration-bootstrapped DB lacks the column. `alembic
> upgrade head` did **not** fix it (no migration existed). **Reproducible fix — NO hand-`ALTER`, ever:**
> migration `src/migrations/versions/d4e5f6a7b8c9_add_is_protected_to_users.py` (written 2026-06-15)
> adds the column — `Boolean, NOT NULL, server_default 'false'`, matching the model and backfilling
> existing rows. It is applied by the **normal alembic flow**; the deploy must run `alembic upgrade head`
> automatically on startup (see Known Issue #2). The DB is **never patched by hand**. *(Drift on the
> `users` table is exactly this one column; the other 8 are present — still, run the parity check, not a guess.)*

> **⚠️ GOTCHA #6 — auth boundary:** running schema/`INSERT`/job-submit writes against the
> **live cloud DB** is a state mutation. An AI agent's harness classifier will (correctly)
> **block** an unrequested `ALTER`/write even if the user said "go" by voice — a voice OK
> does not clear a harness denial. These cloud-DB writes must be run **by the human in-band**
> or behind an explicit settings permission rule.

## 6. Phase G — validation scorecard (agent-executed; the user is never the tester)

Run over the IAP tunnel; report pass/fail. Commands that worked this session:

| Check | How |
|---|---|
| Containers healthy | `docker ps --format "{{.Names}}|{{.Status}}"` → all 3 `healthy` |
| REST `/health` | `docker exec lupin-rest-cloud-test python3 -c "import urllib.request;print(urllib.request.urlopen('http://localhost:7999/health',timeout=8).read())"` |
| Model-server `/health` | same against `localhost:7998` → `status:ready`, 3 models, `load_errors:[]` |
| GPU / cuda:0 | `nvidia-smi --query-gpu=name,memory.used,memory.total --format=csv,noheader` → L4 + VRAM resident |
| Cloud-SQL round-trip | in-container psycopg2 to `/cloudsql/<conn>` socket, `select count(*) from information_schema.tables` → 17 |
| **Claude `/login` OAuth** | `docker exec -it lupin-rest-cloud-test claude -p "Reply with exactly: CLOUD OAUTH OK"` → returns the text ⇒ OAuth proven (same auth bounded-CC uses; **no DB needed**) |
| Arbiter `/state` (:8001) | **separate operator-gated step** — host systemd `lupin-arbiter-app` (see §7); absent by default |
| Full CJ-Flow bounded-CC job | follow-up — needs the §5 user seed (behind GOTCHA #5/#6); submit `task_type=BOUNDED` to `POST /api/claude-code/submit` |

**`claude -p` is the cheapest proof of `/login`** — it exercises the OAuth subscription directly without the DB/JWT/queue path. Use it to validate the login gate; the full CJ-Flow job is a deeper integration test.

## 7. Arbiter ride-along (optional, operator-gated)

`bash src/scripts/provision-arbiter-on-vm.sh` creates the `.venv-arbiter` + user unit but does **not** enable it. The operator then runs `loginctl enable-linger` + `systemctl --user enable --now lupin-arbiter-app.service`. Until then `:8001/state` is absent — expected, not a stack failure.

## Known Issues (carry into a fix queue)

1. **`is_protected` migration drift** (GOTCHA #5) — model column with no migration; breaks user-seeding on every fresh/migration-bootstrapped DB. **Fix written:** migration `d4e5f6a7b8c9_add_is_protected_to_users.py` (2026-06-15). *(Discovered during cloud-test bring-up.)*
2. **No auto-migrate on startup** — `run-fastapi-lupin.sh` (image CMD) starts the app without running `alembic upgrade head`, so DBs silently lag the migration head. **Fix in progress:** wire auto-`alembic upgrade head` into startup (needs `env.py` to resolve the cloud DB URL — currently it only honors `DATABASE_URL`, which the cloud compose does not set; the app's `database.py` builds it from the cloudsql socket + creds). Until then a deploy must run `alembic upgrade head` as an explicit (scripted, not hand-typed) step.
