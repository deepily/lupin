Confirmed: `.gitignore:67` excludes `src/conf/keys/**`; the 10 key files are untracked → a `git pull` on the VM delivers zero keys, so out-of-band delivery is mandatory. Tech-debt: relocate to a gitignored dir and/or Secret Manager — re-evaluate post-stand-up.
- 2026-06-03 — **CC hosting** → **Manual OAuth token seed + documented re-auth** on expiry. Why: mirrors the interim manual-key approach; CC hosted without building refresh automation. Tech-debt: automated refresh.
- 2026-06-03 — **Secure Boot** → **Keep OFF for this milestone** (verify the rest first). ### Architecture: two stacks, one seam

- **`terraforming-vms`** (separate repo) — owns the VM + VPC + NAT + IAP SSH + GPU. Already stood up.
- **Lupin `src/terraform`** — owns the data plane (Cloud SQL, secrets, AR, GCS, IAM). Already applied.
- **Seam** = a thin Lupin deploy runbook/scripts that sequences the two and brings the app up on the VM.

## Key facts established (Explore, 2026-06-03)

- **Cloud SQL = Auth Proxy unix socket, NOT private-IP TCP.** `src/cosa/rest/db/database.py:90-91` builds `postgresql+psycopg2://{user}:{password}@/{database}?host=/cloudsql/{instance}`. → the VM **must run the Cloud SQL Auth Proxy** (listening on `/cloudsql/<CONNECTION_NAME>`). `is_cloud_backed()` (`database.py:32-51`) gates SOLELY on `LUPIN_CLOUD_BACKED` truthy — never inferred from env name.
- **Image is multi-env, config-by-env-var** — no code change to run cloud-backed: set `LUPIN_CLOUD_BACKED=true`, `CLOUD_SQL_CONNECTION_NAME`, DB_* and `config_block_id=Lupin:+Testing-GCS` at runtime.
- **`[Lupin: Testing-GCS]`** (`src/conf/lupin-app.ini:486-506`) already sets `storage backend = gcs` + the `-test` LanceDB/Deep-Research buckets; DB comes from env vars.
- **No cloud docker-compose variant exists** — local `docker-compose.yml` only knows local Postgres; no Auth-Proxy service. **This is the main new deliverable.**
- **IAM repoint path is concrete** — `src/terraform/modules/iam/` binds roles to a module-created `runtime-sa`; add an optional `var.external_vm_sa_email` and `coalesce(var.external_vm_sa_email, google_service_account.runtime_sa.email)`. The follow-up is already flagged in `src/terraform/envs/test/main.tf:35-37`.
- **Reusable as-is:** `src/scripts/cloud-run-build.sh` (build + push to AR), `cloud-run-config.sh` (resolver), `secret-scan-gate.sh`. **Not reusable** (Cloud-Run-specific): `cloud-run-deploy.sh`, `cloud-run-setup-secrets.sh` (Cloud Run secret-mount; the mount model reads keys from files instead).

## Phase E — VM bring-up (the deploy seam)

On `lupin-host-test` via IAP SSH (outward-facing → confirm):
1. `git clone`/`pull` the Lupin repo onto the **200 GB data disk**.
1b. **UID/GID alignment for the bind-mounts (mount-model requirement).** The `rruiz` user is **created inside the image** by the Dockerfile (`docker/lupin/Dockerfile:74-75` `useradd -u ${LUPIN_UID}`), UID/GID **1001/1001** (already build-args `LUPIN_UID`/`LUPIN_GID`, lines 37-38) — it is a **container-internal user; the VM host needs NO `rruiz` OS account.** But because the container process runs as UID 1001 and we bind-mount the host checkout, the checkout + keys + `io/` must be accessible to UID 1001 → `chown -R 1001:1001` the checkout after clone (one provisioning-script line). Alternative: rebuild with `LUPIN_UID`/`LUPIN_GID` matching the VM's deploy user. **Fully automatable — not manual.**
2. **scp the 10 key files** local `src/conf/keys/` → the VM checkout's `src/conf/keys/` (Decision 3b manual interim); ensure owned by 1001:1001.
3. Fetch `DB_PASSWORD` from Secret Manager (`gcloud secrets versions access`) → the deploy env.
4. `docker compose -f docker-compose.cloud-test.yml pull && up -d`.
5. Confirm the Auth Proxy opens the `/cloudsql/<conn>` socket and the app connects.

> **Note (optional future cleanup, not M1):** the container user is named after Rick personally (`rruiz`). Functionally it's just a label on UID 1001 (the numeric UID/GID is what filesystem perms key on, and those are already parameterized). A cleaner portable cloud image could rename it to a generic `lupin`/`app` later — no functional impact.

## Phase F — Claude Code hosting on the VM

**Installation = ALREADY automated; zero human step.** Verified: `docker/lupin/Dockerfile:238` runs `curl -fsSL https://claude.ai/install.sh | bash` (CC CLI) and `pyproject.toml:39` pins `claude-agent-sdk==0.1.56`; the image already provisions `/home/rruiz/.claude/` with `settings.json` + `.mcp.json` (`Dockerfile:281-282`). CC runs **inside the `lupin-rest` container** (the Agent SDK spawns the CLI subprocess for `ClaudeCodeJob`/BFE/TFE/SWE). So once Phase D builds + Phase E runs the image, CC is present — no install step on the VM.

**THE single human intervention point (yours) = one-time OAuth.** OAuth needs a browser; the VM has none. So:
1. **Rick runs `claude setup-token` ONCE on his home dev box** (browser present) → a long-lived Max-subscription OAuth token. (This is the "copy my token from my home box" path — the blessed headless route.)
2. The token is delivered out-of-band like the keys (a file alongside `src/conf/keys/`), and the cloud compose injects it as **`CLAUDE_CODE_OAUTH_TOKEN`** on the `lupin-rest` service (the SDK reads it; no app-side token code — confirmed). Alternative: drop `~/.claude/.credentials.json`. **The VM never needs a browser.**
3. Bounded-CC then runs zero-per-token on the Max plan. CC is GPU-independent.

**Recurring intervention = same one step on expiry:** re-run `claude setup-token` on the home box → re-seed `CLAUDE_CODE_OAUTH_TOKEN`. This is the documented re-auth; **automated refresh is the flagged tech-debt** (Decision 4).

**Timing in the sequence:** Rick can generate the token anytime (independent of the VM); the only ordering constraint is that the token must be seeded before the Phase-G CC-bounded-job verification.
