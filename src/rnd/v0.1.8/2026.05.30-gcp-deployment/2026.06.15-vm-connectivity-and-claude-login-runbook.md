## 1. SSH into the VM

```bash
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap
```

- The `WARNING: ...consider installing NumPy` line is benign (tunnel-throughput hint only).
- Inside the VM, `docker` works **without sudo** (the SSH user is in the `docker` group).

### Two git gotchas on the VM

The repo is owned by **UID 1001** (so the container bind-mount lines up), but your SSH user is your Google identity — so plain `git` commands fail with **`fatal: detected dubious ownership`**. Two ways through:

```bash
# Per-command (no persistent config change):
git -c safe.directory=/mnt/lupin-data/lupin <subcommand>

# OR once, persistently for your SSH user:
git config --global --add safe.directory /mnt/lupin-data/lupin
```

**After any git write (pull/checkout), re-chown back to 1001** so new files keep container-correct ownership:

```bash
sudo chown -R 1001:1001 /mnt/lupin-data/lupin
```

## 2. The single-sitting sequence (keys + pull + recreate + login)

Ordered for one clean pass. **Step A is already done** (held stack pushed to origin this session).

### A. ✅ Push held stack (DONE — dev box)
`origin/wip-v0.1.8…` now at `5ce5dba5` (includes `b524c15d` = the `claude-creds` compose enabler). The VM can now pull it.

### B. SCP the 10 provider-key files → VM  *(run from the dev box — absolute paths)*

The 10 files are: `anthropic-api-key-firewalled`, `openai`, `groq`, `google`, `gemini`, `mistral`, `eleven11`, `kagi`, `huggingface`, `notification-api-claude-code-dev`.

**The VM's `src/conf/keys/` is owned by UID 1001 — your SSH user CANNOT `scp` directly into it** (a direct `scp` fails with `Permission denied` on every file). **Stage in a writable `/tmp` dir, then `sudo cp` + `chown` into place.** Glob form (`keys/*`) lands the files, not a nested `keys/` dir.

```bash
# 0) make a writable staging dir on the VM
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap \
  --command='mkdir -p /tmp/lupin-keys'

# 1) scp the 10 key files into staging (your SSH user owns /tmp/lupin-keys → writable)
gcloud compute scp --recurse \
  /mnt/DATA01/include/www.deepily.ai/projects/lupin/src/conf/keys/* \
  lupin-host-test:/tmp/lupin-keys/ \
  --zone=us-central1-a --tunnel-through-iap

# 2) sudo-copy into the 1001-owned dir, chown to the container UID, clean up, verify
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap \
  --command='sudo cp /tmp/lupin-keys/* /mnt/lupin-data/lupin/src/conf/keys/ && sudo chown 1001:1001 /mnt/lupin-data/lupin/src/conf/keys/* && rm -rf /tmp/lupin-keys && ls -la /mnt/lupin-data/lupin/src/conf/keys'
```
Step 2's final `ls` should show **10 files owned by `1001 1001`**. Flips `lupin-model-server-cloud-test` from **unhealthy → healthy** once the stack recreates (Step E).

### C. SSH in & pull the held stack  *(on the VM)*
```bash
cd /mnt/lupin-data/lupin
git -c safe.directory=/mnt/lupin-data/lupin pull
# expect HEAD to move 8f4a36f2 → 5ce5dba5; docker-compose.cloud-test.yml now contains the claude-creds volume
git -c safe.directory=/mnt/lupin-data/lupin cat-file -t b524c15d && echo "b524c15d PRESENT"
```

### D. Re-chown everything back to UID 1001  *(on the VM)*
```bash
sudo chown -R 1001:1001 /mnt/lupin-data/lupin
```

### E. Recreate the stack to pick up keys + the new volume  *(on the VM)*
```bash
docker compose -f docker-compose.cloud-test.yml --env-file cloud-test.env up -d
```
- `up -d` **recreates** containers whose config changed — required because the `claude-creds` named volume is a **new mount** (a plain `docker restart` would NOT pick it up).
- Verify: `docker ps --format "{{.Names}}|{{.Status}}"` → all three **healthy** (model-server should now be healthy with keys present).

### F. Live Claude Code `/login`  *(on the VM, inside the rest container)*
```bash
docker exec -it lupin-rest-cloud-test claude
# at the claude prompt:
/login
# it prints a URL → open it in ANY browser on your laptop → paste the returned code back
```
The `claude-creds` named volume mounts the container's `/home/rruiz/.claude`, so the login **persists across container recreates** and auto-refreshes. (This is why the pull in Step C matters — without `b524c15d` the login is ephemeral and evaporates on the next recreate.)

### G. ⚠️ D1 — token precedence check  *(on the VM — Rick verifies; file is mode 600)*
`cloud-test.env` must export **NO non-empty** `CLAUDE_CODE_OAUTH_TOKEN`. A non-empty static token **overrides** the stored `~/.claude` `/login` creds (correct precedence) and re-introduces the expiry race. Leave it unset/empty under the `/login` model.
```bash
grep -E '^CLAUDE_CODE_OAUTH_TOKEN' cloud-test.env || echo "OK — not set"
```
