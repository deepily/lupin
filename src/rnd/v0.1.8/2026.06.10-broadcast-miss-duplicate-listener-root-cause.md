# Broadcast-Miss Root Cause — Duplicate Listeners + Silent Skip Gates

**Date**: 2026-06-10 · **Author**: Tiberius 👑 (session 4f7a7ab8) · **Status**: DIAGNOSIS (no fix applied)
**Bug**: a USER BROADCAST silently never reached a CC session while directed DMs to the same session still landed (observed 2026-06-06). Known anomaly: TWO live `cc_notification_listener` processes for ONE session (spawned 09:34 and 16:22, same log) on a ~14h-old `claude` process.

---

## 1. Plain-English Summary (for Rick)

**What the bug is.** Every Claude Code session gets a small background helper — a "listener" — whose
only job is to receive messages (broadcasts, DMs) from the server and type them into the session's
terminal. The bug is twofold:

1. **The system can accidentally start TWO listeners for one session and never notices.** When
   Claude Code restarts a session with `--continue`, it fires the startup hook twice in parallel
   (a documented quirk). Both firings start a listener; there is **no "is one already running?"
   check** (`register_session.py:1026`). The session's record only remembers the LAST listener's
   PID, so at session end only that one gets killed — the other becomes a permanent orphan that
   still listens and still types into the same terminal.

2. **Two listeners typing into one terminal corrupt each other.** Each injection is two steps:
   "type the text" then "press Enter." With two listeners racing, the keystrokes interleave —
   text A, text B, Enter, Enter — and the session can receive a garbled mess or effectively
   nothing. That is the silent loss: no error anywhere, the broadcast just never lands as a
   readable message.

**Why DMs still worked.** DMs travel the same final step (listener → terminal) but a different
upstream path with no liveness filtering, and a single DM racing two listeners *sometimes* lands
intact — it's stochastic. Broadcasts additionally pass through an upstream recipient filter that
can drop a session **silently** (see §3), so they have more ways to vanish.

**Why it matters.** Your broadcasts are the fleet-wide control channel ("everyone stop," "note
where you are"). A silent miss means a worker keeps acting on stale orders, and nobody — not you,
not the manager — gets any error. The 2026-06-06 AFK broadcast miss was exactly this class.

**The fix, in three parts (smallest first):**
1. **Singleton guard at spawn** — before starting a listener, check for a live one already serving
   this session (PID file / lock per session hash); if found, don't spawn a second. ~15 lines in
   `register_session.py`.
2. **Reap-all at session end** — SessionEnd should kill every listener whose `--session-id`
   matches, not just the single PID recorded in the bridge (`session_end.py:169-200`).
3. **Fanout receipts** — the broadcast endpoint should report *filtered-out* sessions (today the
   mtime filter drops sessions silently, `commons.py:370-385`), so a miss is at least visible.

## 2. The Delivery Pipeline (facts, with citations)

**Broadcast path**: `POST /api/commons/broadcast-to-cc-sessions` → `execute_broadcast()`
(`commons.py:453`) → recipient discovery `filter_and_project_sessions()` (`commons.py:317`) with
**8h bridge-mtime liveness filter** (`commons.py:370-385`; INI `commons broadcast liveness
threshold seconds = 28800`, `lupin-app.ini:718`) → per-session fanout + `action:broadcast_received`
notification (`commons.py:392-450`) → listener WebSocket `notification_queue_update`
(`cc_notification_listener.py:223-280`) → `accepted_ids` job-id gate (`:270-273`) →
`handle_broadcast()` (`broadcast_handler.py:193-266`) → tmux injection
(`cc_notification_listener.py:541-604`: `send-keys -l <text>` then `Enter`).

**DM path difference**: DMs (`commons_send_to` / register-question) push directly to the identified
session — **no mtime liveness filter** — then share the same listener→tmux tail.

## 4. The Duplicate-Listener Mechanism (the 06-06 anomaly)

- **Spawn**: SessionStart hook Phase 5.5, `_spawn_listener()` (`register_session.py:151-274`,
  call at `:1026`), detached `Popen`. **No per-session singleton check.**
- **Documented double-fire**: `--continue` fires two concurrent SessionStart hooks
  (`register_session.py:741-751`). The stable-id lockfile is write-once, but BOTH hooks still
  reach `_spawn_listener()` → two listeners, one session.
- **PID shadowing**: each spawn overwrites `session_data["listener_pid"]` (`:264`) — the bridge
  remembers only the last. SessionEnd kills only that PID (`session_end.py:169-200`).
- **No reaper**: nothing scans for orphaned listeners; they live until manually killed.
- **Failure mode with 2 listeners**: both subscribe to the same WebSocket events; both fire
  `handle_broadcast()`; both inject into the same tmux pane; the two-step `send-keys` sequences
  interleave → garbled or lost input. **No dedup exists at any layer.**
