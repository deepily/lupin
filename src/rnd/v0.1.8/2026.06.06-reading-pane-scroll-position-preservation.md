## TL;DR

In **horizontal (master-detail) layout mode**, clicking the abstract icon (📋) opened the
abstract in the reading pane **and** jerked the center content column to the very top. Rick
wanted the center column to **stay exactly where it was** when the pane opens. Fixed by
capturing the topmost visible center card as a scroll **anchor** just before the pane opens and
re-pinning it to the same viewport position immediately after — surviving the simultaneous
80%-width reflow. Consumer-only change in `notifications.js` (`_openContentPane` + two new
helpers).

## Root cause — a scroll-container handoff, not an explicit scroll-to-top

Nobody calls "scroll to top." The jump is a side effect of **which element owns the scroll**:

- **Pane CLOSED** (horizontal mode): `.content-shell` is block layout; `.left-column` has no
  overflow constraint, so the **window/document** scrolls. The user's scroll position lives on
  the window.
- **Pane OPEN**: `_openContentPane` adds `.pane-open` → CSS flips `.left-column` to
  `overflow-y:auto; max-height:calc(100vh-100px)` (`notifications.css:5654`) — making it its
  **own** scroll container, which starts at `scrollTop=0`. The window scroll is now irrelevant.

So a brand-new scroll container appears already at the top; the content the user was reading is
suddenly above the fold. Net effect = "jumped to the top."

**Second factor:** on open, `.container` also reflows to `max-width:80%` (`notifications.css:5662`).
The narrower column re-wraps text → every card's vertical offset shifts. This is why a naive
"save `scrollTop`, re-apply `scrollTop`" would **drift** — the saved number doesn't map onto the
reflowed, handed-off container. An **anchor element** (pin a specific card's top) survives the
reflow; a raw offset does not. (This is why anchor restore was chosen over offset restore —
Rick's pick via `ask_multiple_choice`, 2026-06-06.)

## Scope — only the closed→open transition

The handoff (and thus the jump) happens **only** on the closed→open transition. When the pane is
**already open** and the user clicks another abstract, `.left-column` is already the scroll
container — no handoff, no jump. So capture/restore is gated on
`wasClosed && this._layoutMode === "horizontal"`. Baked into `_openContentPane`, the fix covers
**every** open path through it — the abstract icon **and** doc-link clicks — for free, while
doing zero work in the already-open and vertical-mode cases.

## Implementation (`notifications.js`)

`_openContentPane( type, payload, title )`:
1. `const wasClosed = !!shell && !shell.classList.contains("pane-open")`.
2. If `wasClosed && horizontal`: `scrollAnchor = this._captureCenterScrollAnchor()` **before**
   any DOM mutation.
3. … existing render + `shell.classList.add("pane-open")` + `_updateToolbarPosition()` …
4. If `scrollAnchor`: `this._restoreCenterScrollAnchor(scrollAnchor)` — **synchronously**.

New helpers:
- `_captureCenterScrollAnchor()` → walks `.left-column .container`'s cards
  (`.conversation-pair, .notification-message, .sender-card`) and returns `{ el, top }` for the
  first whose `getBoundingClientRect().top >= 100` (below the ~100px nav strip). Returns `null`
  when the column or any visible card is absent (empty list → caller skips).
- `_restoreCenterScrollAnchor({ el, top })` → `leftColumn.scrollTop += el.getBoundingClientRect().top - top`.

**Why synchronous (no `requestAnimationFrame`):** reading `getBoundingClientRect()` forces a
synchronous layout flush, so the `.pane-open` flex + 80%-width reflow are fully applied when we
measure. Setting `scrollTop` in the **same frame** means the intermediate `scrollTop=0` state is
never painted → **no visible flash**. An rAF-deferred restore would paint one frame at the top
first (a flash), which is exactly the artifact we're removing.

## Obverse — close-time preservation (Rick, 2026-06-06, follow-up)

Rick asked for the symmetric inverse: **closing** the pane should NOT snap the center column
back to the top either — it should return to its calling position. Closing is the exact reverse
handoff: `_closeContentPane` removes `.pane-open`, so `.left-column` loses its overflow and the
**window** owns the scroll again — at its stale `scrollY` (often ~0), which is the snap-to-top.

Same anchor technique, applied to the close transition:
- `_restoreCenterScrollAnchor` was **generalized** to scroll whichever container is live: when
  `.pane-open` is present (open handoff) it scrolls `.left-column.scrollTop`; when absent (close
  handoff) it `window.scrollBy(0, delta)`. The capture helper is direction-agnostic
  (`getBoundingClientRect` is viewport-relative).
- `_closeContentPane`, gated on `wasOpen && horizontal`, captures the topmost visible center card
  BEFORE removing `.pane-open` and re-pins it AFTER (synchronous → no flash).
- The `horizontal` gate means a **switch-to-vertical** close (which sets `_layoutMode="vertical"`
  before calling `_closeContentPane`) does zero scroll work — correct, since vertical is a wholly
  different layout we don't fight.

Behavior note: if the user scrolled the center column *while the pane was open*, close keeps that
current spot (the topmost-visible card at close time) — which equals the calling position when
they didn't scroll. This is the least-surprising symmetric behavior.

Added tests (same file): `_restoreCenterScrollAnchor` window-branch; `_closeContentPane`
reverse-handoff preservation; already-closed no-op; vertical-mode no-op.
