## 1 — Layout-mode toolbar skewed wildly left

**Symptom:** clicking the layout-mode toggle (`⇆`) put the floating `.section-toolbar` far left instead of centered over the container.

**Root cause:** in horizontal mode the toolbar centers via `left: var(--toolbar-center-x)` + `transform: translateX(-50%)`. `_updateToolbarPosition` set that variable to `paneSplitRatio / 2 * 100%` **unconditionally** — the left-column center *as if the Reading Pane were open*. But the pane is **closed by default** after a toggle to horizontal, so `.content-shell` stays block-layout and the container spans the full width (center = 50%). With the 0.667 default ratio the toolbar parked at ~33%.

**Fix (`notifications.js`):**
- `_updateToolbarPosition` is now pane-aware: `50%` when `.content-shell` lacks `.pane-open`, `ratio/2*100` when open.
- Added `_updateToolbarPosition()` calls in `_openContentPane` / `_closeContentPane` so it re-centers as the pane state changes.

**Test:** `src/tests/e2e_ui/test_layout_mode_toolbar_centering.py` — `TestLayoutModeToolbarCentering`: var cleared in vertical; 50% pane-closed; **geometric** toolbar-center within 30px of container-center; `ratio/2` pane-open; re-center on close; var cleared on return to vertical.

## 2 — Reading-pane doc-link "localhost refused to connect"

**Symptom:** following a doc-link rendered in the Reading Pane failed in the iframe with Chrome's "localhost refused to connect."

**Diagnosis:** it was **not** a TCP failure. Both the doc-viewer (render-time) and `_normalizeDocLinkHref` (click-time) strip `localhost` to host-relative, and the user accessed via `localhost:7999` (same origin). Chrome shows "**\<host\> refused to connect**" inside an iframe when framing is **blocked by `X-Frame-Options` / CSP `frame-ancestors`**.

**Root cause:** `add_security_headers` middleware (`src/fastapi_app/main.py`) set `X-Frame-Options: DENY` on **every** response. `DENY` blocks **all** framing — even same-origin — so the master-detail Reading Pane (which embeds `/app/docs?path=…` in an iframe) was refused.

**Fix (`main.py`):** serve the document-viewer page (`/app/docs`) with `X-Frame-Options: SAMEORIGIN` (still blocks cross-origin clickjacking); keep `DENY` on every other route.

```python
if request.url.path == "/app/docs":
    response.headers["X-Frame-Options"] = "SAMEORIGIN"
else:
    response.headers["X-Frame-Options"] = "DENY"
```

**Verified LIVE on :7999** (server auto-reloaded): `/app/docs` → `SAMEORIGIN`; `/app/notifications` + `/health` → `DENY`.
**Test:** `src/tests/smoke/test_doc_viewer_iframe_embedding.py` — 3 tests (viewer SAMEORIGIN, two controls DENY). Passed 3/3 against the running server.

## 3 — iframe rendered as a "postage stamp"

**Symptom:** a doc opened in the Reading Pane rendered in a tiny ~150px box instead of filling the pane.

**Root cause:** the iframe rule already had `width:100%; height:100%`, but `height:100%` needs a parent with a **resolved** height. `.content-pane` had only `max-height: calc(100vh-100px)` plus `align-self: flex-start` (which overrides the row's `stretch`), so its height was **content-driven / indefinite** — the percentage-height chain collapsed and the iframe fell back to its intrinsic ~150px.

**Fix (`notifications.css`):**
- `.content-pane` → **definite** `height: calc(100vh - 100px)` (tracks the viewport via `vh`; resizes on window resize).
- `.content-pane-body` → `min-height: 0` (flexbox: lets `flex:1` resolve a real height so the iframe fills + scrolls).
- `.content-pane-body:has(iframe)` → `padding: 0` so the document fills **edge-to-edge** (abstract text keeps its gutter).
- Width already tracks the splitter via `flex` + iframe `width:100%`.

**Test:** `TestReadingPaneIframeFillsContainer` — iframe >400px tall and matches pane-body W/H within 4px.

## 4 — "Bust out" button (header → new tab)

**Feature:** a third button (`⤢`, "Open in new tab") in `.content-pane-header` → `[← back] [title] [⤢] [× close]`. On click it pops the pane's **current** content into a new browser tab, then closes the pane (which restores the centered layout + re-centers the toolbar via `_closeContentPane`).

**`_bustOutContentPane()` (`notifications.js`):**
- **doc** → `window.open(normalizedUrl, "_blank")` (same-origin tab, shares JWT, full doc-viewer).
- **abstract** → `window.open("", "_blank")` + write `renderMarkdown(payload)` (DOMPurify-sanitized) + base stylesheet; `<title>` escaped at the substitution boundary.
- **New TAB, not a window:** passing **no feature string** is what makes the browser open a tab (next to the current one) rather than a positioned pop-up. **No `noopener`** — we keep the returned window reference both to write the abstract HTML and to decide whether to collapse the pane.
- Popup blocked (`window.open` → null) → pane left open so content isn't lost.

> **Design churn (recorded for honesty):** shipped first as a positioned pop-up window, then upper-right corner, then settled on a **new tab** per Rick's final call. The tab form is the simplest (no window features) and matches the request.

**Test:** `TestReadingPaneBustOut` — doc + abstract: a new Page opens in the Playwright context, the pane hides, and the toolbar re-centers to 50%. Window *screen position* is intentionally NOT asserted (browser/OS-dependent, flaky in the harness).
