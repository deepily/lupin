## 1. Endpoints + response shapes consumed

### `GET /api/notifications/senders-visible/{user_email}` (notifications.py:2339)

Already fetched ONCE at boot by the Lane B WP9 strip hydration (boot.ts:401-407). This
design REUSES that single fetch — no second senders-visible round-trip.

Response: array of sender-activity dicts:

```json
{ "sender_id": "lupin-arbiter-app-8001", "last_activity": "2026-06-11T19:50:12-04:00",
  "count": 1, "new_count": 1, "voice_persona": null, "manager_persona": null }
```

**Window-equivalence proof (why we do NOT pass `hours` to this fetch):** the endpoint's
`hours` param only drops senders whose `last_activity` is older than the cutoff
(notifications.py:2405-2410); `count`/`new_count` are computed by the repo unfiltered
either way. So an unfiltered fetch + a client-side `last_activity >= now − effectiveHours`
filter is EXACTLY equivalent to JS classic's server-filtered call — and it leaves the
WP9 strip hydration (which needs ALL sessions, not just today-active ones) untouched.

### `GET /api/notifications/conversation-by-date/{sender_id}/{user_email}?hours=H&anchor=ISO` (notifications.py:2041)

One call per window-passing sender, mirroring classic `loadSenderConversation`
(`hours` = effective window, `anchor` = that sender's `last_activity` — classic's
activity-anchored window). Response: `{ "YYYY-MM-DD": [row, ...], ... }` with row shape:

```json
{ "id": "<DB UUID>", "sender_id": "...", "message": "...", "title": "...", "type": "...",
  "priority": "...", "state": "...", "is_hidden": false, "abstract": null,
  "created_at": "<ISO app-tz>", "delivered_at": "...", "responded_at": "...",
  "response_requested": false, "response_type": null, "response_value": null,
  "job_id": null, "progress_group_id": null, "timestamp": "<ISO app-tz>",
  "time_display": "HH:MM TZ" }
```

### Effective window (ruling 1 as AMENDED, classic-verbatim)

Classic's virgin default (notifications.js:360): a constant **48h rolling window** —
`DEFAULT_HISTORY_WINDOW_HOURS = 48` exported from NotificationStore.ts, passed by boot as
`effectiveHours`. No selector, no localStorage key, no INI key, no midnight math.

> Pre-review revisions of this doc specified the today-anchored
> `max( 1, ceil( (now − local midnight) / 3600000 ) )` formula
> (`computeTodayAnchoredEffectiveHours`) — removed with the ruling amendment; see the
> Rulings section for the rationale.

## 2. Store-seeding order (boot wiring)

Extend the existing WP9 block in boot.ts — the fetch promise fans into three consumers:

```
senders-visible response ──► stores.sessionStrip.hydrate(records)        (existing WP9, unchanged)
                         ──► stores.senders.hydrate(records)             (NEW — step 1, sync)
                         ──► stores.notifications.hydrateHistory(api, {  (NEW — step 2, async)
                                userEmail,
                                effectiveHours: DEFAULT_HISTORY_WINDOW_HOURS,
                                senders: records (window-filtered inside) })
```

- **Step 1 — `SenderStore.hydrate(records)`** (mirrors `SessionStripStore.hydrate`):
  upsert one `SenderRecord` per record with a non-empty `sender_id`. Merge semantics =
  **never regress live state** (a live event may have arrived before the fetch resolved):
  - `last_active_ts` = max(existing, parsed `last_activity`)
  - `unread_count`   = max(existing, `new_count`) — server's purpose-built unread field
  - `voice_persona`  = existing ?? normalized hydrated persona (null persona → leave unset
    → gray persona-less card, ruling 2)
  - `conversation_mode_active` untouched; `display_name` untouched
  - ONE `store_senders_changed { changeKind: "hydrated" }` emission for the whole snapshot.
    Type change: `SenderChangeKind` gains `"hydrated"` (types.ts:384) — SessionStrip's
    kind already has it (types.ts:426).
- **Step 2 — `NotificationStore.hydrateHistory(api, opts)`** (name follows
  `JobStore.hydrateHistory` precedent, JobStore.ts:155):
  - Guarded by `historyHydrated` flag + `isHistoryHydrated()` (idempotent re-call = no-op).
  - Window-filter the senders client-side (§1 equivalence), then fetch all
    conversation-by-date pages via `Promise.allSettled` — a failed sender fetch is
    SKIPPED (best-effort, mirrors WP9's boundary-catch posture), never rejects the batch.
  - Normalize each row → seed `active[]` + `byId`, with hydration-specific deltas vs the
    live `normalize()`:
    - `id_hash` ← row `id` (DB UUID)
    - **NO unread bump** (the localStorage envelope + per-sender `new_count` own unread;
      classic's history load also never touches its global unread persistence)
    - **NO `expires_at`** even when `response_requested` — these are historical rows;
      setting expiry would feed the `sys_time_update` local-sweep and archive them
      seconds after paint
    - `action_required = false` ALWAYS — historical action-required rows (state
      responded/expired) render as plain conversation messages (classic renders them
      as incoming messages too); they must NOT resurrect in the live AR pane. Live AR
      behavior is untouched (ActionRequiredStore consumes live frames only).
    - rows whose `id` already exists in `byId` are SKIPPED (live-first wins — §4)
  - Seed order: rows sorted ascending by ts before append (cosmetic only — the card
    template re-sorts per date bucket internally, senderCard.ts:148-157).
  - **ONE** `store_notifications_changed { changeKind: "hydrated" }` AFTER all settled
    (`NotificationChangeKind` already includes `"hydrated"`, types.ts:321).

Mount-order invariant (Pass 2 A8) untouched: hydration is a floated data promise like
WP9 and the config fetch — no new renderer, no new mount slot, transports still start last.

## 3. Hydrated-emission contract

Each NEW hydration path fires exactly ONE `"hydrated"` emission per boot, only after the
store's full snapshot is seeded: `SenderStore.hydrate` → one
`store_senders_changed{hydrated}`; `NotificationStore.hydrateHistory` → one
`store_notifications_changed{hydrated}`.

**Precision note (post-review wording fix — the code and tests were already correct, the
doc's earlier "exactly ONE per store per boot" claim was imprecise):**
`NotificationStore`'s CONSTRUCTOR also emits a `"hydrated"` change (the pre-existing
localStorage unread-envelope paint, NotificationStore.ts `hydrate()`), so the store emits
TWO `"hydrated"` events per boot in total. The constructor emission fires during
`createStores()`, BEFORE any renderer mounts/subscribes, so it has zero subscribers and
zero renderer effect — the history emission is the only `"hydrated"` a renderer observes.
The unit suite acknowledges this by counting hydrated emissions AFTER construction.

**Accepted residual — no re-entry guard:** `hydrateHistory` sets its `historyHydrated`
flag at the END (JobStore precedent). A second call issued while the first is still
in-flight would double-fetch; the id-keyed `byId` skip makes the seed idempotent, but the
window exists. Accepted because boot is the SINGLE call site (one floated promise chain);
not worth a lock for a path with exactly one production caller.

The renderer is ALREADY reconcile-from-store — `renderSenderSection()` re-reads
`notifications.list()` + `senders.list()` and `keyedListMerge`s on EVERY
`store_notifications_changed` / `store_senders_changed` (NotificationsListRenderer.ts:153-165)
— so cards paint on the hydrated emission with zero renderer changes. Interim emissions
(step-1 senders-hydrated before step-2 resolves) repaint the empty-state harmlessly.

## 4. Renderer reconcile vs live events — the dedupe contract

**The renderer needs no dedupe** — it has no per-event append path; every store change
triggers a full re-read + keyed merge (`data-id-hash` keys). Dedupe therefore lives
entirely in `NotificationStore.byId`, and the contract is **id-keyed, both arrival orders**:

| Order | Path | Outcome |
|---|---|---|
| hydrate-first, live re-arrival second | existing `onQueueUpdate` idempotent branch (NotificationStore.ts:274) | update-in-place, NO unread bump, `"updated"` emission |
| live-first, hydrate-second | `hydrateHistory` skips ids present in `byId` (JobStore `inSessionIds` precedent, JobStore.ts:163-168) | live item kept, no dupe |

**The identity problem (recon finding — the hard edge Tiberius flagged):** id-keyed dedupe
currently CANNOT work across the two surfaces, because the fire-and-forget ONLINE delivery
path creates its live `NotificationItem` WITHOUT threading the DB id —
`push_notification(...)` at notifications.py:727 omits `id=`, so the live frame's
`id`/`id_hash` is a fresh `uuid4()` (notification_fifo_queue.py:50) while the persisted
row (and thus the hydrated item) carries the DB UUID from `_persist_notification_sync`.
Same logical notification, two identities.

Receipts that this is an OMISSION, not a design choice:
- The response-required path already passes `id = notification_id` with the comment
  *"Use database ID for consistency"*.
- The offline cc-listener fallback frame already stamps `"id_hash": db_notification_id`
  (notifications.py:658-659).

**Proposed fix-at-source (server one-liner):** thread `id = db_notification_id` into the
fire-and-forget online `push_notification` call (None on persist-failure → falls back to
`uuid4`, current behavior). Live frame id == DB row id ⇒ the dedupe table above is
airtight. Safety: `queue_dict`, `mark_played`, io_tbl logging all key off
`NotificationItem.id` — the AR path has run DB-id-keyed for months, proving the key shape
safe; UUID uniqueness is unchanged.

**Race anatomy (why dedupe is needed at all):** boot floats the hydration fetch, then
starts the WS transports; the server-side history query may execute before OR after WS
auth completes. A notification persisted in that overlap window can appear in BOTH the
hydration response and a live frame. JS classic has this same race and blind-appends
(`addNotificationToSenderGroup` has no id check — notifications.js:12365ff); the window is
milliseconds wide, which is why it's never been observed. **Fallback if the server
one-liner is rejected:** ship client-only and inherit classic's ms-wide residual race —
documented, not silent.

## 5. Out of scope (queued enhancements, per rulings + parity-with-mux-live)

- Window selector UI (ruling 1).
- Non-CC distinguishing chip (ruling 2).
- Outgoing `response_value` bubbles: classic renders the user's reply as a separate
  outgoing message during history load; the mux has no outgoing-message concept in its
  LIVE path either — adding it only for hydrated rows would make cold-load richer than
  live. Parity-with-mux-live; flagged for the post-cutover parity backlog.
- Server replay of the in-flight active list on reconnect (P1 Option C deferral,
  NotificationStore.ts:26-30) — unchanged by this work; hydration covers the cold-load
  gap, not mid-session reconnect.
