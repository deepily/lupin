## Audit: liveness ≠ progress (the key distinction)

The arbiter separates two concepts handled by **different** signals:

### LIVENESS — "is the session alive?" — ALREADY BROAD
- `post_tool_use.py:57` calls `touch_bridge_mtime()` on **every** tool call → `dm_send`, `task_create/update/transition`, `notify`, `Edit`/`Write`/`Bash`/`Read` all already bump liveness.
- Plus the union signal (`build_fleet_view`): bridge mtime ∪ commons activity ∪ idle_prompt ∪ stop-event.
- `assess_liveness` (`context_pressure.py:306`): process-alive OR-gate + mtime freshness.
- **GAP**: `pre_tool_use.py` does **NOT** call `touch_bridge_mtime()` — only PostToolUse does. So a long-running in-flight tool doesn't refresh liveness until it completes. → **Fix 1.**

### PROGRESS — "is work advancing?" — THE FALSE-STALL CULPRIT
- `_fleet_progress_signature` (`arbiter_job.py:1545`) hashes **only** each session's `(session_id, state, stuck, holding_on)` — the semantic work-state.
- Its docstring is explicit: *"commons chatter is liveness, not progress; it never reaches the signature"* — deliberate, to catch chatty-but-stuck fleets.
- Consequence: a manager actively coordinating (DMing crew, moving task items, commits held) registers ALIVE but **not progressing** → false WHOLE-FLEET-STALL. This is what hit Mr. Radio repeatedly this session.

## Fixes

### Fix 1 — PreToolUse emits liveness (clear)
Add `touch_bridge_mtime()` to `pre_tool_use.py` (mirror `post_tool_use.py:57`). Cheap mtime touch, no content write. Closes the "pre AND post both emit life" gap. Tests: PreToolUse bumps mtime.

### Fix 2 — task-store TRANSITIONS count as progress (strongest, needs feasibility check)
A task moving `queued→in_progress→done` is unambiguous work-advancement. Fold a task-store transition signal into `_fleet_progress_signature` (or an adjacent progress input) so an actively-managing fleet reads as progressing.
**Feasibility to confirm FIRST**: does the arbiter's `fleet_view` (built from bridges, `:7999`-free per R4) have access to task-store transition data without adding a `:7999`/DB dependency? If not, propose the minimal plumbing (e.g. a per-session "last task-transition ts" in the bridge, written by the task hook). Implementer investigates before building.

### Fix 3 — work-bearing DMs as progress (DESIGN CALL — Rick's input)
Counting **all** DMs as progress would re-open the chatty-but-stuck blind spot the design deliberately closed (idle "still blocked" chatter must NOT count). Distinguishing *work-bearing* DMs (assignments, verdicts, nods) from idle chatter is the open question. **Deferred pending Rick's design call** — do NOT implement until decided.
