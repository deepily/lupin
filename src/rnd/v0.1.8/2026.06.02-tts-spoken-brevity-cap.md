## Problem

The spoken `message` / `question` field of the cosa-voice speaking tools is read aloud via TTS. Long bodies become a "wall of text" in the user's ear. The standing doctrine (detail → `abstract`, headline + one takeaway → spoken) was repeatedly violated under marathon load (FM "TTS-brevity decay"). Rick asked for a **systematic, mechanical** limit, not "try harder."

## Design decisions (ratified live with Rick, 2026-06-02)

| # | Decision | Rationale |
|---|---|---|
| D1 | **Enforce at the MCP layer (caller side), NOT the notifications REST API** | Limit the *agent's spoken verbosity* at the tool boundary; leave the shared delivery API free to carry longer payloads from jobs / system events. |
| D2 | **Override flag, default off:** `override_size_limitation: bool = False` | A long spoken message must be sent KNOWINGLY (opt-in-and-intentional), not by accident. |
| D3 | **Cap the SPOKEN field only** (`message` / `question` / each `questions[i].question`) | `abstract` is never capped — rich detail lives there. |
| D4 | **Over-cap behavior = REJECT, not truncate** | Raises `ValueError` naming the field + measured length + the fix; FastMCP surfaces it to the model → it re-crafts. No silent content loss. |
| D5 | **Cap value in `lupin-app.ini`, read via ConfigurationManager** | Tunable without a code edit. |
| D6 | **Runtime-tunable (mtime-gated re-read)** | Edit the INI → picked up on the next call, no MCP restart. Cheap hot path (re-reads only when the INI mtime changes). |
| D7 | **Default = 500 chars (~80 words)** | Rick's call; balances "routine ~60 words" with a little headroom. (My initial 750 inference from the rider's 120-word ceiling was overridden.) |

## Implementation

- **`src/lupin_mcp/cosa_voice_mcp.py`**
  - `SPOKEN_CHAR_CAP_DEFAULT = 500`; `_SPOKEN_CAP_INI_KEY = "cosa voice spoken char cap"`; module-level `_spoken_cap_cache`.
  - `_get_spoken_char_cap()` — stats the INI mtime; on change, reloads via `ConfigurationManager( _reset_singleton=True ).get( key, return_type="int" )`; caches value + mtime; fails open to the last good value / default.
  - `_enforce_spoken_brevity( spoken, override_size_limitation, field )` — resolves the cap, flattens str / questions-list into spoken units, raises `ValueError` on the first over-cap unit (unless overridden).
  - Wired at the top of all 5 spoken tools (outside their try/except so the raise reaches FastMCP): `notify`, `converse`, `ask_yes_no`, `ask_multiple_choice`, `ask_open_ended_batch`. New `override_size_limitation` param + Args docstring on each.
- **`src/conf/lupin-app.ini`** `[Lupin: Baseline]` — `cosa voice spoken char cap = 500` (+ explanatory comment block).
- **`src/conf/lupin-app-splainer.ini`** — matching splainer entry.

## Verification

- `py_compile` clean; import clean.
- **`src/tests/unit/lupin_mcp/test_spoken_brevity_cap.py` — 11/11 green**: resolver (default=500, int, positive), boundary (== cap passes, +1 rejects), actionable error message, override bypass (str + list), questions-list per-index reporting, malformed-entry skip.
- **Live runtime-tunability proof** (transient script, since removed): resolver `500` → edited INI → `333` → restored → `500`, all within one process (`RUNTIME_TUNABLE_OK`). INI restored, no leftover backup.

## Activation & rollback

- **Activation:** one-time MCP restart (per-session stdio subprocess still runs the pre-change code). After that, all re-tuning is INI-only.
- **Rollback:** revert the 4 source files; or set the cap very high in the INI to effectively disable; or callers pass `override_size_limitation=True`.
