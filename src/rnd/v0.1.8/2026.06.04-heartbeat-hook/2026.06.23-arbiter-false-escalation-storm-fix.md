The deployed fleet arbiter fired relentless FALSE escalations all session — false
MANAGER-DOWN on demonstrably-live managers, and phantom DEADLOCK on a fresh,

## Bug 1 — tap-ACK false MANAGER-DOWN (`e8f40042`)

### Root cause (María, code-confirmed)
`_check_manager_acks` decided a manager's liveness-proxy ACK from only TWO
sources — commons activity (`who()`) + bridge-mtime. That set is **strictly
narrower** than the general fleet-render verdict (`fleet_render.compute_liveness`),
which uses the FULL 5-signal union: bridge + stop-event + commons + idle_prompt +
sent-DM (dm gated by `arbiter count dm as liveness`). So a manager whose only sign
of life was a sent DM (coordination-only — no Read/Edit/Bash to bump the bridge,
nothing posted to commons) or a fresh stop-event read `down` and false-escalated
MANAGER-DOWN to Rick every `manager_ack_window_seconds` (600s) while LIVE.

Secondary: `_manager_bridge_activity` matched persona by exact `==`, so a fresh
bridge file under a different persona spelling (the `canonical_persona_key` / F-B
association miss) left `bridge_activity` None.

### Fix
- New `_manager_liveness_activity(manager, fleet_view, now, count_dm)` routes the
  ACK through `compute_liveness` across the manager's view row(s) and returns the
  freshest liveness datetime (`now - freshest_age_s`) so the existing
  `last_activity >= tapped_at` comparison is unchanged. The ACK is now a strict
  **superset** of the verdict's life signals — it can never drift narrower again.
- Persona→view matching uses `canonical_persona_key` → subsumes the secondary
  bridge-association miss (María: "optional-not-blocking").
- `who()`-sourced commons retained as a belt (the view's `commons_ts` is
  phantom-nulled when the bridge is absent, so a bridge-less-but-commons-posting
  manager would otherwise lose that ACK).
- `count_dm` threaded from `_poll_once` into `_check_manager_acks` so the DM
  toggle stays consistent with the verdict path.
- Retired `_manager_bridge_activity` (sole consumer replaced; no shim).

### Regression tests (`test_arbiter_manager_tap.py`)
- `test_dm_only_manager_not_false_downed` — fresh dm, stale bridge, empty commons
  → does NOT down (the headline e8f40042 case + María's divergence check).
- `test_dm_only_manager_downs_when_dm_toggle_off` — NEGATIVE control: same manager
  downs when `count_dm=False` (proves dm is what saved it + toggle honored e2e).
- `test_fresh_stop_event_acks_commons_and_bridge_silent_manager` — the event_age fold.
- `test_manager_liveness_activity_picks_freshest_and_handles_edges` — direct unit
  (5-signal freshest, canonical matching, count_dm gating, edge cases).

## Bug 2 — deadlock loop-fires on a progressing wait (`436a366b`)

### Root cause (María + Tiberius's repro)
The deadlock escalation built its cycles from the SELF-REPORTED `holding_on:
peer:X` edges (`build_wait_edges`), with **no** store corroboration, **no** dwell,
and **no** de-dup (`_recent_pings` cool-down is wired to `_auto_ping` only). Live
from `:8001/state` the false ring was Krishna `holding_on=peer:mr_radio` +
Mr Radio `holding_on=peer:Krishna` — a FRESH, legitimate sequencing wait (Krishna
genuinely awaited Mr Radio's merge+build), NOT a deadlock. At least one edge was
fresh+legit, so a freshness guard ALONE cannot drop it.

Key store-schema fact (verified): `blocked_by` is **item-kind** (task→task UUIDs),
not persona→persona. So "gate on store blocked_by" requires a task→owner map.

### Fix (ratified by Mr. Radio — v1 scope)
Three gates now stand between a derived cycle and an escalation:
1. **Store-corroboration** (single-source-of-truth mandate): a cycle fires ONLY
   when EVERY ring edge is backed by an authoritative store `blocked_by`
   owner-edge. New pure helpers in `dependency_graph.py`:
   - `build_store_wait_edges(owed_by_persona)` → `{canonical_owner: set(awaited)}`.
     Resolves item-kind refs to owners via a task-id→owner map built from the SAME
     per-poll owed read; persona-kind refs are direct; user-kind/unresolvable/
     self-edges are dropped.
   - `cycle_is_store_backed(cycle, store_edges)` → every consecutive ring edge
     present (personas compared canonically).
2. **Dwell / progressing-wait belt** (`deadlock_dwell_seconds`, default 300s): a
   store-backed ring must PERSIST past the dwell before it escalates. A fresh ring
   is recorded (first-seen) and given the grace window to self-resolve — a
   progressing wait clears within it and never fires. `dwell=0` ⇒ fire on first
   corroborated sight.
3. **De-dup**: each persisting store-backed ring escalates ONCE (not every poll).
   Both trackers (`_deadlock_first_seen`, `_deadlock_escalated`) PRUNE a signature
   the moment its ring is gone (resolved → re-arm).

The per-poll owed read is now done ONCE (`_read_owed`) and SHARED by both
`_classify_owed` (CLASS_* labels) and `build_store_wait_edges` — one query per
poll preserved (the observer invariant).

### Ratified scope limit (v1)
A PURE-coordination ring — two managers mutually awaiting with ZERO store rows —
is **out of scope v1**. Rationale (Mr. Radio): rare, a human breaks it anyway, and
the correct fix is managers expressing real waits as store `blocked_by`. This gate
is a **hygiene forcing-function, a feature not a gap**.

**Deliberate bias asymmetry**: when the owed read is unwired/hiccupped,
`store_edges` is empty → NOTHING fires. Deadlock detection **fail-SUPPRESSES** —
the OPPOSITE bias from the stall / manager-down detectors (which fail-SAFE toward
escalating), BY DESIGN, because over-escalation IS this bug.
