## 1. Problem

A manager-reaped worker lingers on the arbiter fleet roster tagged `stale Nm` for up to
~60 minutes instead of disappearing. Rick's verbatim observation:

```
mr radio  manager  working  LIVE  12.1%
Krishna   worker   unknown  LIVE   6.8%
Rachel    worker   idle     stale 32m   — —     ← reaped last session, still listed
```

Expectation: a reaped session should CEASE TO EXIST in the roster, not linger.

### 1.1 Root cause (reproduced from live filesystem)

Reconstructed Rachel's exact row byte-for-byte:

- **Reap DOES delete the bridge.** `session_spawner.dismiss_sessions` unlinks the bridge
  file (`session_spawner.py:545-555`); confirmed — no `cc-*.json` with `name=Rachel`
  exists on disk.
- **Reap LEAVES the heartbeat-event file.** `~/.claude/heartbeat-events/96930bc4-….jsonl`
  persists (reap never touches it). Its last two records:
  - `{"outcome":"idle", "ts":"2026-06-15T21:20:41Z"}` → drives `state="idle"`
  - `{"kind":"idle_prompt", "ts":"2026-06-15T21:21:41Z"}` → the freshest signal
- **The arbiter accumulator never drops a whole session.** `FleetEventAccumulator`
  (`arbiter_state.py`) keys a dict by `session_id` → a `deque(maxlen)` tail; it caps each
  tail but never evicts a session entry, so the tail lives for the process lifetime.
- **`compute_liveness`** (`fleet_render.py:110`) takes
  `freshest_age = min(bridge, event, commons, idle_prompt)`. After reap:
  `bridge=None` (deleted), `commons=None` (phantom-guard nulls bridge-absent sessions,
  `fleet_data_model.py:291`). So `freshest = idle_prompt_age` ≈ 32m at Rick's view →
  `_verdict` (`fleet_render.py:87`) returns **`"stale 32m"`**.
- **`prune_offline_rows`** only drops `verdict=="offline"`, so she stays PUBLISHED.

### 1.2 Why the existing fast-eviction path can't fire

There are two eviction mechanisms; for a reap, only the slow one applies:

| Path | Mechanism | Fires for a reap? |
|------|-----------|-------------------|
| Fast | `process_dead`/kill-0 (`find_dead_sessions`, `session_bridge.py:684`) forces `offline` in ~1 poll | **NO** |
| Slow | event/idle_prompt ages cross `stale_seconds` (3600s) → `offline` → publish-prune | Yes, ~60 min late |

`find_dead_sessions` requires the **bridge file** to read the worker PID, and treats a
candidate with no matching bridge as **NOT dead** (`absence ≠ death`, bias-to-alive,
`session_bridge.py:699`). The reap deletes the bridge *first* → no PID → the reaped
session is structurally never in `process_dead`. The reap destroys the very evidence the
fast path needs.

### 1.3 The conceptual gap

The roster has exactly **one** reaped-vs-idle discriminator (`process_dead`), and the reap
blinds it. So for ~60 min a **reaped-dead** session (host gone → should evict NOW) is
indistinguishable from an **idle-alive-quiet** session (keep, with the stale tag). Both ride
event-age decay `quiet → stale → offline`. Closing that distinction is the fix.

## 2. Design

**Hand the arbiter an explicit death signal on the rail it already consumes.** The arbiter is
an event-sourced consumer of `~/.claude/heartbeat-events/*.jsonl`; the clean fix is a
**reap tombstone** — one terminal record the reaper appends to the reaped session's event
file. The arbiter reads it on the next poll and force-offlines the row, reusing the existing
`process_dead` → publish-prune machinery.

This mirrors how `idle_prompt` was added as the 4th union signal: a kind-tagged record that
carries **no `outcome`** (so it can never map through `_STATE_BY_OUTCOME`) and is handled
off the activity axis.

### 2.1 Why this over the alternatives

| Option | Verdict |
|--------|---------|
| **Reap tombstone on the event rail** (chosen) | Supplies the death signal kill-0 can't; reuses all existing eviction machinery; FS-durable + degrade-safe; no false-death risk (authoritative marker, never inferred). |
| Subscribe arbiter to the `session_reaped` notification it already emits | Rejected — best-effort rail the arbiter does NOT currently consume; may not arrive; couples the arbiter to a new input. |
| Cross-poll "bridge disappeared" detection in the pure leaf | Rejected — needs per-session memory in a pure leaf; can't distinguish "never bridged" from "bridge just deleted." |

## 3. Implementation (4 edits + tests)

### Edit 1 — `heartbeat_events.py`: new terminal kind + emitter

- Add constant `EVENT_KIND_REAPED = "reaped"` (mirrors `EVENT_KIND_IDLE_PROMPT`,
  `heartbeat_events.py:81`).
- Add `emit_reaped( session_id, persona=None, ts=None, base_dir=None )` — a near-copy of
  `emit_idle_prompt` (`:162`): appends one JSON line `schema_version · session_id · persona ·
  ts · kind="reaped"`, **no `outcome` key**, fail-safe (`return False` on any
  `OSError/TypeError/ValueError`, never raises). Reuses `events_path` (`:97`).

### Edit 2 — `session_spawner.py`: append the tombstone at reap time

In `dismiss_sessions` (`:464`), the bridge identity (incl. `session_id`) is already captured
into `identities` BEFORE the bridge is unlinked (`_capture_reap_identity`, `:383`). In the
existing per-reaped-name loop (`:545-559`, right beside the bridge-unlink + emit), add a
best-effort `emit_reaped( ident["session_id"], persona=… )` — guarded so a write failure
NEVER breaks the reap (same fail-safe posture as the bridge unlink and `_default_emit_reap`).

> Note: `dismiss_sessions` runs host-side (MCP subprocess of `claude`), and the arbiter
> (`:8001`) reads the same host `~/.claude/heartbeat-events` — confirmed shared (bridge
> discovery + `events_tail` both read it). The marker is therefore visible to the arbiter.

### Edit 3 — `fleet_data_model.py`: recognize the kind, set a `reaped` flag (off the activity axis)

In `build_fleet_view` (`:164`), the records are already split by the `kind` discriminator
(`:252-253`). Add a third bucket: a record with `kind == EVENT_KIND_REAPED` sets
`reaped = True` for that session's view. Like `idle_prompt`, it must be filtered OUT of
`activity_recs` so it never becomes `state` and never feeds `last_event_ts`. Emit a new
view key `"reaped": bool` alongside the existing fields (`:305-319`). Membership: a reaped
marker counts as a real signal (the row must still appear so it can be force-offlined and
then pruned — auditable, like the phantom row).

### Edit 4 — `fleet_render.py`: force `offline` on `reaped` (mirror the `process_dead` block)

In `build_snapshot` (`:197`), immediately after the existing `process_dead` override
(`:287-289`), add a sibling: `if view.get("reaped"): liveness["reaped"] = True;
liveness["verdict"] = "offline"`. The existing default `include_offline=False` /
`prune_offline_rows` path then evicts the row in ~1 poll. `process_dead` stays as-is (it
still catches `/exit`'d sessions whose bridge lingers); `reaped` covers the
bridge-already-deleted case it can't.

## 5. Edge cases & risk

- **Blast radius: LOW.** +1 constant, +1 small emitter, ~5-10 additive lines in the reaper,
  one new bucket in one pure leaf, one force-offline branch in another. No existing path
  is altered (`process_dead` untouched; phantom guard untouched; union/canonicalization
  untouched).
- **No false-death risk.** The marker is written ONLY by the authoritative host-side reap —
  never inferred (contrast kill-0's container blindness). A force-offline can only follow a
  real reap.
- **Idempotent.** A double-reap appends a second `reaped` line — harmless (still offline).
- **Marker for a never-tracked session.** `tail_fleet_events` reads new files from offset 0,
  so a session the arbiter never saw still gets force-offlined when its file appears.
- **Reaper has no `session_id`** (capture returned None): skip the emit (best-effort) — falls
  back to today's ~60-min age-out, no worse than status quo.
- **Permanent membership in the FULL snapshot.** The reaped row stays in `fleet_view` /
  the `include_offline=True` detection snapshot (offline), pruned only from the PUBLISHED
  view — identical to every other offline session. No new graveyard.
