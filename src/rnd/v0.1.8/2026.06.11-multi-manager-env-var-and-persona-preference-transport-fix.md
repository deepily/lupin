## Item 2 (ships FIRST, small patch) — `persona_preference` is never transported

### Symptom

`spawn_sessions( persona_preference="Rio" )` repeatedly yields a different persona (Krishna, twice in two days). Fresh reproduction: session `3810dfa6` spawned ~13:22 UTC 2026-06-11 requesting Rio, allocated **Krishna 🦚** (confirmed in `.claude-session.md` manifest section for `3810dfa6`).

### Root cause (verified file:line)

The preference travels exactly nowhere:

```
spawn_sessions( persona_preference="Rio" )           src/lupin_mcp/cosa_voice_mcp.py:2233 → :2278
  └─> session_spawner.spawn_sessions(...)            src/lupin_mcp/session_spawner.py:203
        ├─> child env dict built                     session_spawner.py:298-302
        │     { COSA_VOICE_SPAWNED_BY,                 ← preference NOT added
        │       COSA_VOICE_HEADLESS,
        │       COSA_VOICE_ROLE }
        ├─> preference echoed in RETURN dict only    session_spawner.py:327
        └─> child SessionStart hook fires
              └─> pick_preferred_persona_from_env()  register_session.py:984
                    reads COSA_VOICE_PREFERRED_PERSONA__<PROJECT>   voice_persona_helpers.py:720-762
                    → unset → preferred=None
                          └─> server random-allocates → Krishna
```

- The docstring contract (`session_spawner.py:252-253`, `cosa_voice_mcp.py:2258-2259`) — "predictable-fail honored by the child's SessionStart, not silently re-allocated" — is **aspirational**; no transport code was ever written.
- The spawn *echo* (`persona_preference` in the return dict) reflects the **request**, never the allocation — which is why every spawn "looked" right.

### Server side already has both semantics (no endpoint work needed)

`src/cosa/rest/routers/voice_persona.py:184-191`:

| Query param | Semantics |
|---|---|
| `requested_persona_name` | **STRICT** — atomic allocate-or-fail, 422 (unknown) / 409 (occupied). The "predictable-fail" the docstring promises. |
| `preferred_persona_name` | **SOFT** — on miss, random-allocate + push `voice_persona_conflict` notification. (The per-repo shell-default path.) |

The two are mutually exclusive (`voice_persona.py:242-245`).

### Fix design

1. **Transport** (`session_spawner.py:298-302`): inject the per-child preference into the env dict. `persona_preference: str | list` — a str applies to every child; a list maps by child index (extra children beyond the list get no preference). New env var:
   - `COSA_VOICE_REQUESTED_PERSONA=<name>` — session-scoped (per-process env; no project suffix needed, unlike the shell-rc-scoped `__<PROJECT>` var).
2. **Hook** (`register_session.py` Phase 4.5): read `COSA_VOICE_REQUESTED_PERSONA` FIRST; when set, call the allocation endpoint with `requested_persona_name` (strict). Fall back to the existing `pick_preferred_persona_from_env` soft path when unset. On strict 409/422: bridge stays persona-less (Sam TTS fallback), the failure is LOUD in hook stderr, and the child's first DM to its manager names the failure — manager decides reap/respawn. No silent re-allocation, making the docstring contract TRUE.
3. **Contract truth-up**: docstrings at both spawn layers updated to describe the actual mechanism.

**Decision for Rick (Q3)**: strict (recommended — honors the existing contract, gives managers verifiable rosters) vs soft (zero hook change, but papers over the contract — explicitly contrary to the one-name-rule preference).

### Deployment caveats

- `session_spawner.py` / `cosa_voice_mcp.py` run inside the **host-side MCP server process** — running sessions keep old code; the fix takes effect for sessions whose MCP server starts after the change (**flag: MCP restart needed**).
- `register_session.py` is a **LIVE SessionStart hook** (executes from the working tree on every session start) — edits built in a **git worktree**, landed only after review.
- `voice_persona.py` / `voice_persona_helpers.py` are server-side on `:7999` (auto-reload).

## Item 1 — Multi-manager declaration env var

### Current state: manager-ness is implicit and mostly already N-capable

A session "is a manager" today iff it has called `spawn_sessions` (it then owns a lineage manifest `~/.claude/sessions/spawned-<id>.json`). Discovery findings:

| Layer | File:line | Multi-manager today? |
|---|---|---|
| Lineage manifests | `session_spawner.py:162-165, 283, 317-320` | **YES** — one manifest per manager; N managers coexist naturally |
| Worker→manager resolution | `heartbeat_arbiter/manager_resolver.py:65-106` | YES — exactly-one-per-WORKER (lineage), unaffected by manager count |
| Active-manager fanout | `manager_resolver.py:146-213` | YES — already returns a sorted LIST |
| Arbiter fallback | INI `arbiter manager on duty` (`lupin-app.ini:547`), `fleet_arbiter_loop.py:134,168` | **NO** — single persona string `manager-on-duty` |
| DM routing | commons (persona-addressed) | YES — provided personas are distinct (← Item 2) |
| Fleet-status rendering | arbiter fleet_render | Partially — manager badge derives from manifest ownership only; a manager that hasn't spawned yet is invisible as a manager |

So the load-bearing gap is **declaration**: there is no way to say "these N personas are managers for this repo" ahead of (or independent of) their first spawn. That is exactly what Rick asked for.

### Proposal

**Env var** (Q1 — shape for Rick): `COSA_VOICE_MANAGERS__<PROJECT>` — comma-separated persona names, e.g.

```bash
export COSA_VOICE_MANAGERS__LUPIN="Tiberius, Rio"
```

- Mirrors the established per-project pattern (`COSA_VOICE_PREFERRED_PERSONA__<PROJECT>`, `voice_persona_helpers.py:720`): one universal lookup, project normalized strip+UPPER+hyphen→underscore.
- CSV of strings = Rick's "array/list of strings"; whitespace-tolerant; case-insensitive match against the pool (same `_find_persona_in_pool` matcher).

**New helper**: `pick_declared_managers_from_env( project ) -> list[str]` in `voice_persona_helpers.py` — sibling of `pick_preferred_persona_from_env`, same never-raise contract, returns `[]` when unset.

**Consumers** (Q2 — semantics for Rick):

1. **Arbiter fallback** (`fleet_arbiter_loop.py:134`): the single `manager_on_duty` string becomes the declared list — an unresolvable worker escalates to ALL declared+alive managers instead of one hardcoded persona. INI key `arbiter manager on duty` retained as last-resort when the env var is unset.
2. **Fleet-crisis fanout** (`manager_resolver.py:146`): candidate set becomes declared ∪ lineage-derived (declared managers count even before their first spawn), still phantom-guarded by bridge liveness.
3. **Fleet-status rendering**: manager badge for any live session whose persona ∈ declared list (today: manifest-owners only).
4. **Spawn/lineage/DM**: **no change** — already N-manager-safe; each manager keeps its own manifest, children DM their own manager's `dm-<persona>` topic.

**Out of scope (recommended)**: persona RESERVATION at SessionStart (declared list does not pre-claim personas — Item 2's strict request is the mechanism for a manager to claim its name). Recommended Q2 answer: role declaration only.

### Confirmed Decisions (Rick, 2026-06-11)

- **Q1 — env var shape**: `COSA_VOICE_MANAGERS__<PROJECT>` CSV, multi-word names verbatim (verified: `_find_persona_in_pool` matches case-insensitively on pool key + display name, whitespace-tolerant; commas are the only delimiter — `COSA_VOICE_MANAGERS__LUPIN="Tiberius, Mr. Radio"` works as typed).
- **Q2 — declared-manager semantics**: role declaration only. Declaration does NOT reserve personas.
- **Q3 — spawn preference semantics**: STRICT **ordered-fallback chain** with opt-in wildcard (Rick's refinement of plain strict):
  - A preference is a **persona chain** — ordered list of names, optional `*` tail meaning "then take anything free".
  - `"Rio"` → strictly Rio or loud fail. `["Rio","Krishna"]` → Rio, else Krishna, else loud fail. `["Rio","Krishna","*"]` → Rio, else Krishna, else random from the free pool.
  - No preference at all (ad hoc session) → random allocation, unchanged.
  - `count > 1`: every child gets the same chain; each takes the first FREE name at boot (sibling races resolved by the server's atomic allocate — first sibling wins a name, the next falls through to the next name).
  - Loud fail = bridge stays persona-less (Sam TTS fallback) + `voice_persona_conflict` notification carrying the per-name outcomes; manager decides reap/respawn.

### Chain mechanics (final)

**One concept, one name — "persona chain"** ([[feedback_one_descriptive_name_everywhere_break_contract]]):

| Layer | Carrier |
|---|---|
| MCP tool arg | `persona_preference: str \| list` (public arg name retained; its VALUE is a chain) |
| Spawner → child | env var `COSA_VOICE_PERSONA_CHAIN` (CSV, injected at `session_spawner.py:298-302`) |
| Per-repo shell default | `COSA_VOICE_PREFERRED_PERSONA__<PROJECT>` (name retained — Rick's existing vars; VALUE upgraded to chain syntax) |
| Hook → server | query param `persona_chain` on the allocate endpoint |
| Server helpers | `parse_persona_chain()`, `allocate_persona_chain_for_session()` in `voice_persona_helpers.py` |

**The chain walk lives SERVER-side** (new `persona_chain` query param on `/api/voice-persona/allocate`), not as a hook-side HTTP loop: single round trip, one atomic decision under the server's allocation path, conflict notification pushed server-side on exhaustion, and fully unit-testable to the 100% gate without touching the live hook beyond a pass-through. Unknown chain names are skipped-with-record (a typo or renamed pool must not brick session start; the outcome list in the 409 detail + conflict notification surfaces it loudly).

**Chain generalizes the old soft path**: bare `"María"` = strict chain of one; the legacy `preferred_persona_name` soft semantics = `"María,*"`. The hook's preferred path migrates to chain; `preferred_persona_name` is retired from the endpoint after consumer audit (break-the-contract rename rule — we own all consumers).

**Hook precedence** (`register_session.py` Phase 4.5): spawn-injected `COSA_VOICE_PERSONA_CHAIN` first; else per-repo `COSA_VOICE_PREFERRED_PERSONA__<PROJECT>`; else no param → random (today's behavior).

### Implementation deltas vs the original sketch

- `pick_declared_managers_from_env` landed in `heartbeat_arbiter/manager_resolver.py` (not `voice_persona_helpers.py`) — its consumers are all arbiter-side, and it kept the file ownership disjoint from the Item-2 test work.
- Hook precedence extracted to pure `resolve_session_start_persona_chain( project, environ )` in `voice_persona_helpers.py` — the live hook's delta is a 1-line call (fully unit-tested without touching hook-file coverage debt).
- **Headless guard** (new decision, flagged to Rick): a spawned child (`COSA_VOICE_HEADLESS=1`) WITHOUT an explicit spawn chain gets NO chain (random) — it does NOT inherit the per-repo `"Mr. Radio,Tiberius,*"` default, which would let a preference-less worker squat a manager name. Matches de-facto pre-chain worker behavior.
- **tmux boundary**: `start-cc-with-tmux.sh` forwards `COSA_VOICE_PERSONA_CHAIN` via `-e` (tmux does not inherit arbitrary parent env — without this the spawner's injection dies at the boundary, the original bug one layer down).
- Per-worker declared fallback: `arbiter_job.declared_fallback_manager` = roster head (else INI `arbiter manager on duty`); the Part-6 fanout reaches ALL declared+alive managers via the `resolve_active_managers` union.
