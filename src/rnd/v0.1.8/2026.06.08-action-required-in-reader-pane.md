# Action Required card in the Reader Pane (horizontal mode) — Design

**Date:** 2026-06-08 (evening) · **Author:** Rachel 🕊️ (session 6fc52b2e) · **Requested by:** Rick
**Status:** DESIGN — Rick wants design + thoughts BEFORE any implementation
**Surface:** notifications UI (current JS client `notifications.js`, NOT the multiplexer)

---

## 1. Goal (Rick's framing)

Today the **Action Required** card (a notification with `response_requested === true` — yes/no,
multiple-choice, open-ended) renders **at the top** of the list and the view **scrolls to it**, then
scrolls back on dismiss. That's the **vertical-mode** behavior.

Rick wants to **experiment**: in **horizontal (master-detail) mode**, render the Action Required card in
the **right-hand Reader Pane** at a **50/50 split** — 50% center content, 50% reader (the action-required
card). Vertical mode stays exactly as it is.

## 2. What it would look like

```
VERTICAL (unchanged)                    HORIZONTAL (new — action-required active)
┌───────────────────────────┐          ┌──────────────────────┬──────────────────────┐
│ ⚠ ACTION REQUIRED  (top)  │          │  Center content 50%  │  Reader pane 50%     │
│  "Deploy to prod?"        │          │  · notification list │  ┌────────────────┐  │
│  [Yes] [No]               │          │  · sender cards      │  │ ⚠ ACTION REQ'D │  │
├───────────────────────────┤          │  · scrollable        │  │ "Deploy prod?" │  │
│  notification list …      │          │                      │  │ [Yes]  [No]    │  │
│  (scrolled to the card)   │          │                      │  └────────────────┘  │
└───────────────────────────┘          └──────────────────────┴──────────────────────┘
                                        split forced to 0.5 while the card is up; the
                                        user's preferred ratio is restored on dismiss.
```

## 3. Current architecture (what we build on)

- **Action-required model:** `actionRequiredNotifications` Map (id → notification + UI state) +
  `actionRequiredQueue` (FIFO). Entry point: `addActionRequiredNotification(notification)` (called from
  `handleNotificationUpdate` when `response_requested === true`, ~line 5800). Renders into
  `#action-required-section` (top). Persisted to localStorage (refresh survival, ~14086/14141).
- **Reader pane:** `_paneSplitRatio` (default `0.667`, range `[0.30, 0.85]`); `_applyPaneSplitRatio()`;
  `_openContentPane(type, payload, title)` + `_renderContentPaneEntry(entry)` (currently `type` ∈
  {`abstract`, `doc`}); `_closeContentPane()`; in-memory `_contentPaneHistory` with Back navigation.
- **Coupling:** an active action-required triggers **focus mode** (`focusModeNotificationId`) which pauses
  the TTS queue while the user responds. This is **orthogonal to where the card renders** and must be
  preserved.

## 4. Proposed design

**Routing rule** — at `addActionRequiredNotification` time:
- `this._layoutMode === "horizontal"` → render the card in the **Reader Pane** (a new pane content
  `type: "action-required"`), force the split to **0.5**.
- else (vertical) → **current** top-section behavior, untouched.

**Pane preemption + restore.** The pane may already be showing an abstract/doc. Action-required is the
highest-priority thing on screen (it blocks the user for a response), so it **preempts** the pane. On
dismiss: if a queued action-required remains, show the next; else **restore** the prior abstract/doc and
the user's preferred split ratio (or close to full-width center if the pane was empty before).

**Reuse the card renderer.** The existing action-required card markup + response-button handlers are the
same; the only change is the **mount point** (pane body instead of `#action-required-section`) and the
**split**. The `_renderContentPaneEntry` switch gains an `action-required` branch that renders the card
into the pane body with its handlers live.

**Forced 0.5 split (with restore).** While an action-required occupies the pane, `_applyPaneSplitRatio`
uses `0.5` (not the user's ratio) so the card gets balanced room for its buttons. Capture the user's
ratio on entry, restore it on dismiss.

**Queue = one-at-a-time in the pane.** The pane shows the **front** of `actionRequiredQueue`; dismissing
advances to the next; a small "N more" affordance if the queue is deep (optional).

**Layout-switch + refresh.** Switching to vertical while an action-required is in the pane → close the
pane, re-home the card to the top section (and vice-versa). The localStorage refresh-restore path must
route to the pane when restoring in horizontal mode.

## 5. My thoughts / trade-offs

- **Why it's a nice fit:** the reader pane already exists for "focused reading on the right"; an
  action-required is exactly a "stop and engage with this one thing" — so it's a natural tenant. 50/50
  (vs the 67/33 reading default) is right: a response card needs button room, not a narrow column.
- **Main complexity = preemption/restore**, not the render. Cleanly stashing+restoring the prior pane
  entry (abstract/doc + ratio) is the fiddly part. A simpler v1 could **close** the pane on dismiss
  (no restore) and add restore later — lower risk, still meets the core ask.
- **Interactivity must survive the move.** The response buttons + focus-mode/TTS-pause coupling have to
  work identically in the pane. Reusing the existing card builder (not re-implementing) protects this.
- **Don't double-render.** In horizontal, the card should live ONLY in the pane (not also the top
  section) to avoid two copies + two sets of live buttons.

## 6. Open questions for Rick (before build)

2. **Multiple action-required:** one-at-a-time in the pane (queue, advance on dismiss), or stack them in
   the pane? *(My lean: one-at-a-time — it's a focused response UX.)*
3. **Forced 0.5:** hard-force 50/50 while the card is up (restore your ratio after), or respect a manual

4. **Top section in horizontal:** suppress it entirely (card only in pane), or keep a slim record there?
   *(My lean: suppress — card only in pane, no duplication.)*

## 7. Decisions — LOCKED (Rick, guided walkthrough 2026-06-08)

**Key refinement (Rick):** the build is a **LIFT-AND-MOVE of the existing `action-required-content`
element** into the pane in horizontal mode — NOT a re-render. That element already renders the pending-
action-required-items list + live response handlers; relocating the live DOM node preserves its state and
avoids duplicate button sets. It moves back to its home location when the queue empties (or on switch to
vertical). *(Confirm the exact element id at build — Rick named it `action-required-content`.)*

| # | Question | Ruling | Note |
|---|---|---|---|
| 1 | Dismiss behavior | **Restore prior content** | On empty-queue, restore the prior abstract/doc that was in the pane + the user's split ratio — NOT just close-to-center. Stash-on-preempt / restore-on-release. |
| 2 | Multiple cards | **One at a time** | The moved `action-required-content` already lists pending items; the pane shows it as the single surface. |
| 3 | The split | **Hard-force 50/50** | Force 0.5 while the content is in the pane; capture + restore the user's ratio on release. |
| 4 | Top section | **Only in the pane** | Fully moved, no top trace in horizontal ("move it entirely"). |

### Resulting flow (horizontal mode)
1. Action-required arrives (or already present on entering horizontal) → **stash** any current pane entry
   (abstract/doc) + the user's split ratio → **move** `action-required-content` into the pane body →
   force split **0.5**.
2. User responds / dismisses; while items remain, the moved element keeps showing the list.
3. Queue empties → **move** `action-required-content` back to its home → **restore** the stashed pane
   entry **AND the divider/splitter X position (the split ratio)** — the divider snaps back to the EXACT
   place the user had it, not just the content (Rick emphasized this, 2026-06-08) — or close to
   full-width center if nothing was stashed. The stash on preempt MUST capture both `{prior entry, prior
   `_paneSplitRatio`}` as a unit so the restore is pixel-faithful.
4. **Layout switch** while active: horizontal→vertical moves it back to the top section; vertical→horizontal
   moves it into the pane. Refresh-restore (localStorage) routes to the pane when restoring in horizontal.

**Vertical mode: entirely unchanged.**
