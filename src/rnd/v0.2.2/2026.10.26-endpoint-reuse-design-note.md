# Endpoint reuse: pointing a TypeScript client need at an existing FastAPI route

*26 October 2026. Rick asked how FastAPI endpoints would be documented so that a TypeScript client that needs some kind of data finds the Python route that already serves it. The measurements below are mine; the design is a recommendation, and every decision in it is Rick's.*

## Verdict

The checker can point a client need at an existing route with **no model calls**, because every client call site found already names its route. The work is one new kind of search result (a route) and one mechanical need extractor. Documentation by what a route does is mostly in place already.

**What these numbers do not say.** Matching is by path only, so a client that calls `GET /x` where the route is `POST /x` still counts as a match. Whether the route does what the client *needs* is the judgment the reviewer makes; the path match only says where to look. The 64 sites are today's multiplexer client, not a sample of future needs.

## Design

### 1. Route-aware search (Rick's ask 1)

**Today.** `check_exists` and `fetch_similar` search symbols only. `reuse_redact.py` and `reuse_tools.py` read `routes.md` just to redact paths from a need, so a route is never a candidate (row text; I did not re-read those files for this note). A handler is findable as a Python symbol, but its method and path are not in the result.

**Recommendation.** Add the route to the symbol record instead of building a second index.
- At index build, join `routes.md` to `symbols.jsonl` on handler id. 237 of 239 join today; the two that do not are named in the build log, not guessed.
- A symbol record gains `routes: [ { method, path } ]`. Search, ranking and the vector set do not change.
- A result for a handler then reads *"GET /api/multiplexer/config, `get_multiplexer_config`, <capability page>"*, and the reviewer can rule **call it** instead of **reuse the function**.
- Add one new verdict word, `CALL_ROUTE`, beside the existing ones, so the ruling is recorded and countable.

**Cost.** Small: one join in `build.py`, one field, one verdict value, tests. **Risk.** A symbol record that changes shape changes the index pin; the golden-fixture tests move with it.

### 2. An endpoint need kind (ask 2)

**Recommendation.** Key the need from the call site, with no judge call.
- Extract each client call site as `( file, line, method if visible, normalised path )`. The 64 sites need a TypeScript AST pass, not a regex, to catch the template and the concatenated bases and to read `method`.
- The need is the route the client already names, so **the answer is known when the need is made**. Two uses follow:
  - **a scoring set**: how often does search return the right route for a need written from the handler docstring, with the path withheld. This measures route search with a known answer, as the plan's planted pairs do for functions;
  - **a live check**: a new call site whose path matches no route is a client calling something that does not exist, or a new route that must be written, which is exactly the moment to ask whether a route does the job already.
- The yield is **measured: 60 of 64 exact, 3 by prefix, 0 unmatched**, so a path match is a sound key today. The honest limit is that the current client is already consistent with the server, so zero unmatched says the key works, not that the check would find reuse.

**Cost.** One TypeScript extractor pass (the index already runs one for symbols). **Risk.** Dynamic paths (`base + x`) the AST cannot resolve; the prefix cases above show three of 64, so about 5%.

### 3. Documenting routes by what they do (ask 3)

**Today.** A route appears in 124 of the 185 `/api/` cases on a capability page, and 237 of 239 handlers have a docstring summary in the index. What is missing is a **consistent line per route that says what it returns, in the words a client author would use**.

**Recommendation.** No new document type.
- Each capability page that covers a router gets a `## Routes` table with `method | path | what it returns | who calls it`. The last column is filled mechanically from section 2, so it cannot drift.
- A guard test reads `routes.md` and fails when an `/api/` route has no row on any capability page. 61 of 185 would fail today; that list is the backlog.
- The handler's own docstring first line stays the source for "what it returns", so the page and the index say the same thing.

**Cost.** The guard and the generated column are small. Writing the 61 rows is the real cost, and it is documentation work, not code.

## Order I would build it in

1. The join and the `routes` field (ask 1), because the other two use it.
2. The call-site extractor (ask 2), producing the scoring set and the live check.
3. The guard and the generated "who calls it" column (ask 3).

## Decisions for Rick

| # | Decision | Recommended |
|---|---|---|
| 1 | Add routes to symbol records, or build a separate route index | Symbol records: one index, one pin, and 237 of 239 already join |
| 2 | Is a path match enough to key a need, or must the method match too | Path first; add the method only where the AST reads it, and report both rates |
| 3 | Fail the build on an undocumented `/api/` route, or only report | Report first; fail once the 61 are written |

## Not measured

- The 6 decorators `routes.py` does not extract.
- Whether the 237 joins are all the *right* handler (same file and name; a duplicated name in one file would pass).
- How often a route a client needs exists but the client wrote its own call to something else. That needs a reviewer, and is the question the live check is for.
