# One vector or two: should purpose lines get their own embedding, apart from the code and signature?

2026.10.14 · Claude, for Rick · an extra arm for sections 6 and 9 of [the candidate-stage problem statement](2026.10.14-reuse-lookup-candidate-stage-problem-statement.md)

This note covers one design choice inside option B and how to test it offline. It does not reopen the choice between A, B and C.

## 1. The question

Option B embeds each index entry. The entry can be embedded two ways:

- **One vector** over the concatenated enriched text: signature, split identifiers, module path, first docstring line and purpose line.
- **Two vectors**, each giving its own ranked list into RRF:
  - a **prose vector** over the purpose line and docstring;
  - a **code vector** over the signature, split identifiers and module path, and optionally the source.

The Option 2 write-up of 2026.10.07 already specifies "two embedding vectors and a word index", which means three ranked lists. The community survey of 2026-10-14 recommended one vector over enriched text as a simplification, to save a pin and storage. That was not a finding that two vectors do worse. This note states the difference and how to settle it.

## 2. Why two vectors could recall more

| | prose vector | code vector |
|---|---|---|
| What is embedded | purpose line + docstring | signature, split identifiers, module path |
| Compared with the need | prose with prose: same kind of text, an easy case for a general text embedder | prose with code: needs a code-trained embedder |
| What it catches | same behaviour under different names | names the caller half-remembers |
| How it fails | a wrong or generic purpose line | cryptic names and no docstring |

One vector over both averages two different signals. A long signature can dilute a sharp purpose line, and the reverse. As separate lists, an entry reaches the shortlist if either view ranks it high. Before the judge, that "any list's top hit" property is what we want.

Evidence we hold, all indirect:

- **Anthropic's Contextual Retrieval** (Sept 2024) prepended LLM-written context to each chunk. Top-20 retrieval failure fell from 5.7% to 3.7% with contextual embeddings, to 2.9% with contextual BM25 added, and to 1.9% with a reranker. That supports purpose lines. It does not compare one vector against two.
- **CoIR** (ACL 2025) puts BM25 far below code embedders on prose-to-code retrieval: nDCG@10 of 26.75 against 81.79 on CodeSearchNet. That supports a code-trained embedder for the code view.
- **No source found** measures prose-vector against code-vector against concatenated on a symbol catalogue with one-line docstrings. We would have to measure it ourselves.

## 3. A third variant: hypothetical code from the need

An LLM writes a hypothetical signature or stub from the need, and that text is searched against the code vector. Both sides of the comparison are then code.

The cost is a model call on every query. That puts a model back on the query path, which option C avoids and the frozen form of B avoids. Replay needs the generated text cached by the hash of the need, and the generating model becomes another pin. Test it only if the two-vector arm still misses on vocabulary mismatch.

## 4. Effect on the constraints in section 10

- **Pins.** Using one embedding model for both views keeps the pins at three: judge, embedder, purpose-line writer. A second embedding model makes four.
- **Freezing.** Purpose lines and both vectors are keyed by the entry's pin, written once and stored. Search is exact cosine over about 8,400 rows, so the same need and the same index give the same shortlist.
- **Receipt.** Add the embedding model version, the vector-set hash and which lists fed RRF.
- **Storage.** Two vectors per entry at 1,024 dimensions in float32 come to about 69 MB for 8,428 entries. That is negligible.
- **Privacy.** Writing purpose lines sends source to a vendor once per pin. A local embedding model, such as the open-weight nomic-embed-code, sends nothing further. The need string is still unscreened (section 10).
- **Languages.** Both views cover Python, TypeScript and JavaScript entries alike. Purpose-line quality per language has not been measured.

## 5. How to test it

These are extra arms on T1 and T3, at zero live judge calls. Embedding the index and the 30 needs is a one-off cost.

| arm | lists fed to RRF |
|---|---|
| C0 | BM25 over split identifiers, module path, signature and docstring |
| C1 | C0 with frozen purpose lines added to the BM25 text |
| B1 | C1 + one concatenated vector |
| B2 | C1 + prose vector + code vector |
| B2w | B2 + wiki-page list |

For each arm, record:

- **T1:** recall of the full-sweep shortlist at K in 32, 64, 128, 256 and 512, over the 30 needs.
- **T3:** where the known twin lands for the 376 known-twin members, by language. This is the direct test of vocabulary mismatch.
- **T2**, only for arms that survive: the flip rate and verdict agreement after replaying cached judge answers.

**Rule:** keep two vectors only if B2 beats B1 on T3 twin rank, or on T1 recall at K = 128. Otherwise ship B1. All of T1 to T3 is in-sample (section 9 rules), so the arms are ranked against each other here. The fresh needs are kept for T4.

## 6. Sketch

```python
import numpy as np

def cos_rank(qv, M, ids):                        # M: frozen, row-normalised
    sc = M @ (qv / np.linalg.norm(qv))
    return [ids[i] for i in np.lexsort((np.array(ids), -sc))]

def rrf(lists, k=60, K=128, top_m=8):
    s = {}
    for ranked in lists:
        for r, e in enumerate(ranked, 1):
            s[e] = s.get(e, 0.0) + 1.0 / (k + r)
    order = sorted(s, key=lambda e: (-s[e], e))  # deterministic tie-break
    forced = {e for ranked in lists for e in ranked[:top_m]}
    head = [e for e in order if e in forced]
    return head + [e for e in order if e not in forced][:max(0, K - len(head))]

def arm_b2(need, bm25_rank, embed, P, C, ids, K=128):
    q = embed(need)
    return rrf([bm25_rank(need), cos_rank(q, P, ids), cos_rank(q, C, ids)], K=K)
```

`P` and `C` are the stored prose and code matrices. `embed` is the pinned model with query vectors cached by hash. B1 is the same with one matrix.
