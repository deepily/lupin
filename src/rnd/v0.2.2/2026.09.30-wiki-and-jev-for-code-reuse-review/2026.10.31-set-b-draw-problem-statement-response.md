# Set B draw: expert review of the problem statement

Oct 31, 2026 · @Richard P Ruiz

Review of `2026.10.31-set-b-draw-problem-statement.md` (Cheech, lupin). The statement is well built and asks the right second-order questions, but it walks past three first-order defects, and Q6 is the one that should decide the rest. Defects first, then the seven answers, then nits.

## Three things the statement does not ask

**1. The success criterion is unstated, and under the obvious one the work-alike stratum is vacuous.** A need is written from seed S; the key is {S, anything else doing the job}. If "found" means *any key member*, the checker finds S (the need was paraphrased from it) and the item passes without the work-alike T ever being retrieved. That holds for mined and synthetic alike. To make T carry information you must either hide S (doctoring, the same sin as planting) or score recall per key member. Pick one and write it down before sourcing anything, because it changes what a "work-alike" item even is.

**2. The mining instrument is the checker's own judge.** Mined work-alikes are, by construction, pairs Fable 5.1 already rules same-job. §3's failure-step list includes "the judge did not rate it relevant"; on mined items that step is pre-passed. The stratum can detect retrieval and agent-stage misses but is structurally blind to judge misses on exactly the class the checker exists for. Mine with a different instrument (another model family, behavioural equivalence, or people), or state the blindness in the report.

**3. Set A's "work-alike" and Set B's are different constructs.** Set A's is code→code (two functions, same job, different shape). Set B's hardness lives in need→code: a sentence in caller vocabulary whose answer is shaped unlike the obvious implementation. Pair-mining is a proxy for the second property, and 0/563 says it is a poor one. The property is *measurable per item* from a single real function: run a cheap lexical retriever (BM25 over identifiers and docstrings) on the need; "exists but BM25 misses" is the natural work-alike pool. That sources hard items from real Python without pairs and without planting.

Related: who writes the need sentences, and from what distribution? The checker already makes live agents write one before coding. Those are the true distribution; model-written needs from seeds are Fable paraphrasing code for a Fable-judged search, home-field advantage all the way down. At minimum, calibrate model-written needs against logged ones.

## The seven questions

**Q1, mixed source.** Separate reporting is enough only if nobody ever compares the two halves, and someone will, because the 60/40 split invites it. Perfect confounding (language ≡ source) is a design flaw, not a reporting problem. Resolve it by removing synthetic from Set B (Q6) and sourcing Python work-alikes by measured hardness (defect 3), not by mining 150 from TypeScript. Also, 9,000 calls rests on 5/500: Wilson 95% on that rate is roughly 0.4%–2.3%, so 90 mined keys cost anywhere from \~4,000 to \~21,000 calls. The plan has a point estimate where it needs an interval.

**Q2, trusting survivors.** The selection effect has a known direction: run-checks favour pure, small, side-effect-free functions, so survivors skew simple. Bound it by comparing survivors to the seed population on LOC, cyclomatic complexity, side-effect count, and call-site count, and report the shift. Keep the rejects and the un-runnable ones as labelled sub-populations, not discards. This matters for Set A's 20 synthetic pairs regardless of what you do with Set B.

**Q3, κ = 0.29.** At n = 20 the interval on κ runs from about zero to the mid-0.6s; the point estimate is not a finding. The damning number is intra-rater 12/20: with a plausible base rate, 60% self-agreement is roughly what two coin-flips with the same bias give. When a labeller cannot agree with themselves, the construct is ill-posed, not the labellers. Replace "same job" with a substitutability checklist (same input domain, same outputs over it, same observable side effects, callers of one could call the other with at most argument adaptation) and derive the binary from it. Yes to a per-stratum agreement figure with an interval.

**Q4, confirm mode.** Make it adaptive and pre-registered: blind-20% κ above a threshold you name now (say 0.6) permits confirm mode on the remainder; below it, the stratum goes fully blind. Given Set A's numbers, expect work-alikes to go fully blind. 150 items double-labelled is a day of human time against days of machine time; the asymmetry does not justify anchoring the one number anyone will quote.

**Q5, 150 vs 60.** The miss bound at zero misses is 3/n: 2% at 150, 5% at 60. For a diagnostic that decides nothing, 5% is fine. But a bound on a key with κ ≈ 0.3 is a bound on agreement with noise, so key precision dominates key count. Take 60–80, checklist-labelled, fully blind, and spend the saved effort measuring hardness continuously across the near-copy stratum. The dichotomy is a convenience; hardness is not bimodal.

**Q6, planting.** Do not plant into Set B. The planted function's docstring and identifiers descend from the same one-sentence description the need descends from, so the item is generated inside the retriever's own representation space, and (defect 1) it adds nothing unless you also hide the seed. Planting is right for a *positive control*: plant Set A's 20 synthetic pairs once, confirm the checker finds them, then remove them. That proves the instrument can find something; it is not a stratum.

**Q7, first 1,000 calls.**

1. Zero calls: settle the success criterion, the checklist, and no-planting.
2. \~200 calls: 50 real seeds end-to-end through the stage-attribution pipeline, to prove the diagnostic can name a losing stage at all. If it cannot, Set B is moot.
3. \~300 calls: 100 real seeds through BM25 and the checker, to measure the natural work-alike yield per 100 seeds in each language. That tells you whether 150 is reachable from real code.
4. \~200 calls: the positive control from Q6.
5. Remainder: run Set A's 20 synthetic pairs through the run-check to see how many of the 3 drifted pairs it catches and how many of the 12 unsure-flagged it resolves. That is the cheapest validation of a mechanism already ruled on.

## Nits on the document

- The 0/563 row should say "rate below 0.53%" rather than an undefined cost.
- Name the model that writes the need sentences.
- State what "all 300 found" assumes about the key set, since the bound inherits its error.
