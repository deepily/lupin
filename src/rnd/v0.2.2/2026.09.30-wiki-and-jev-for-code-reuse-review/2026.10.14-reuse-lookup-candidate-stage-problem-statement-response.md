# Embeddings + LLM Judge ("Jev") for "Does This Already Exist?" — State of the Yard, 14 Oct 2026

The community consensus is clear: use a cheap, high-recall hybrid first stage (identifier-aware BM25 plus a code-capable embedding, rank-fused), then a pinned LLM judge on a few dozen to ~128 candidates, with determinism provided by caching and frozen artefacts rather than by the model. For your setup that means a **frozen-artefact variant of Option B**, not A or C. Your threshold flips are a documented property of hosted LLM judges, so fix them in the decision layer, not by re-asking.

## TL;DR
- **Pick B, built from frozen parts.** Use frozen purpose lines, BM25 over split identifiers, one embedding model with vectors stored once, exact (brute-force) cosine over ~8K rows, RRF with id tie-breaks, K=128, and judge packs of ≤10–50. Brute-force sweep (A) spends ~98% of judge calls on obvious negatives. Lexical-only ranking (C) loses badly on vocabulary mismatch: on CoIR, BM25 averages 29.79 nDCG@10 versus 56.26 for Voyage-Code-002.\[1\]
- **Flips come from the judge and its serving stack, not from your cutoffs.** Verdicts near a decision boundary flip across identical temperature-0 runs.\[2\] Server batch variance is a main cause,\[3\] and scores in packed prompts depend on co-members, position and batch size.\[4\]\[5\] Make replay deterministic with request-hash caching, and handle boundary cases with an explicit margin/"uncertain" band calibrated out-of-sample.
- **Treat the wiki as a ranking signal, never a gate. Treat "not retrieved" as a bounded miss rate, not proof of absence.** Back this with a shadow audit. With the rule of three, zero misses in ~300 audited full sweeps gives a 95% upper bound of ≈1%, which takes ~30K queries at a 1% audit rate.

## Key Findings

### 1. State of the art (2025–2026)
- **Retrieve-then-rerank is the default; agentic grep is the counter-current.**
  - Claude Code creator Boris Cherny says early versions used "RAG + a local vector db" but found "agentic search generally works better," citing security, privacy, staleness and reliability.
  - Sourcegraph removed embeddings from Cody Enterprise in v5.3 in favour of its own search plus adapted BM25. Its Cody FAQ says this is "More secure: No code being sent to a third-party embedding API," brings less "need for refreshes," and scales to larger and more repos.
  - Cursor reports the opposite for its agent (Cursor blog, "Improving agent with semantic search," Nov 2025): semantic search added on top of grep gave **"on average 12.5% higher accuracy in answering questions (6.5%–23.5% depending on the model)"**, and "the combination of these two leads to the best outcomes."
  - Your use case is different from agent navigation. It is one-shot, high-frequency and needs an auditable shortlist, which is exactly where the pre-built index approach still wins.
- **Code-specialised retrieve-and-rerank beats agents on cost.** SweRank (Salesforce) retrieves the top-100 functions with an embedder, then reranks them with a listwise LLM.\[6\] It reports state-of-the-art function localization on SWE-Bench-Lite and LocBench, beating agent systems at far lower cost per instance. SweRank+ extends this to multiple languages.\[7\]\[8\]\[9\]
- **Embedding models (vendor-reported; treat with caution):**
  - Voyage claims voyage-code-3 beats OpenAI-v3-large by 13.80% and CodeSage-large by 16.81% across 32 datasets.\[10\]
  - Nomic's open 7B nomic-embed-code reports CodeSearchNet Python 81.7 vs voyage-code-3's 80.8.\[11\]
  - CodeXEmbed (COLM 2025) tops CoIR.\[12\]
  - The CoIR authors warn that Voyage-Code-002's top average comes "with high variance, suggesting weaker generalization."\[1\]
- **Enriching documents with LLM-written context is the most robust win.** Anthropic's Contextual Retrieval prepends LLM-generated context to each chunk before embedding and BM25 indexing. Top-20 retrieval failure fell from 5.7% → 3.7% with contextual embeddings, → 2.9% adding contextual BM25, and → 1.9% with reranking.\[13\]\[14\]\[15\] Your "purpose line" is the same idea at symbol granularity.
- **Generated wikis (DeepWiki and similar) are a navigation layer, not an index of record.** They are generated from the repo, link back to source, and sit on vector retrieval underneath. Codersera's DeepWiki guide warns that "for fast-moving repos, the index may lag behind main by hours or days."

### 2. Evidence on lexical vs. dense, and vocabulary mismatch
- **CoIR (ACL 2025), nDCG@10:**
  - BM25 averages 29.79 versus 56.26 for Voyage-Code-002.\[1\]
  - On text-to-code CosQA, BM25 scores 13.96 vs 29.79, and on CodeSearchNet 26.75 vs 81.79.\[1\]
  - This is the best public proxy for "short prose need → function" retrieval, and it is the case Option C is weakest on.
- **BM25 is not uniformly bad.** Roberts & Roberts (SIGIR-AP 2025) found BM25 gave better human–LLM-judge agreement than CodeT5+ for Python, C, JS and Java, and worse only for Go. Their repos had 57% (Python) and 94% (JS) of functions without docstrings, so short or missing docs do not doom lexical search. Semantic retrievers, however, solved synonym gaps like "heap" ↔ `priority_queue` "without needing to resort to custom configuration lists."\[16\]
- **Tokenization matters more than the scoring function.** A 2026 BM25 study (Radha et al., arXiv:2605.18561) used an oracle-tuned q-log IDF under generic tokenization to lift CodeSearchNet-Go nDCG@10 from 0.2575 to 0.4874 (+89.3%). It also found "identifier-aware tokenization largely removes the incremental gain from q-IDF," so splitting identifiers is mandatory for C.
- **No published number isolates "identifier/signature-only BM25 vs. embeddings" on an in-house symbol catalogue with one-line docstrings. Evidence here is thin; measure it on your own labels.**
- **Semantic clone detection is still hard.** LLMs handle Type-1/2 clones but "face significant challenges" with Type-3/4 (same behaviour, different structure and names).\[17\] A 2026 study finds state-of-the-art Type-4 detectors rely on lexical shortcuts and degrade under semantics-preserving rewrites.\[18\] Expect the judge to under-call "extend" cases.
- **Why this matters:** GitClear's "AI Copilot Code Quality 2025" report (211M changed lines) found code blocks with 5+ duplicated lines rose 8× during 2024, and 2024 was the first year copy/pasted lines exceeded moved (reused) lines.

## Details: Gotchas, Bugs and Workarounds

| Gotcha | Evidence | Workaround |
|---|---|---|
| Temperature 0 ≠ deterministic | Thinking Machines (Horace He, "Defeating Nondeterminism in LLM Inference," Sept 2025): the main source is server batch variance. 1,000 temperature-0 runs of Qwen3-235B on one prompt produced 80 unique completions; with batch-invariant kernels, all 1,000 were identical. | Treat the cache as the source of truth: the request hash → stored verdict. Pin the model and serving version. Run batch-invariant kernels if you self-host.\[19\]\[20\] |
| Judge verdicts flip at boundaries | "Coin Flip Judge" (2026): 44.7% of pointwise score variance is within-judge noise.\[21\] Temperature-0 flip rates were 2.8–7.9% across judges.\[22\] A safety-judge study found 1–2 of 7 borderline items still non-reproducible under top_k=1.\[2\] "Rating Roulette" (EMNLP Findings 2025): self-reliability "fairly static… independent of the number of runs."\[23\] | This is a model property concentrated near the threshold, which matches your 0.03–0.05 jitter. Use an explicit margin band (|score − cutoff| < δ, with δ set from measured repeat jitter) → "uncertain-read-source." Don't median-of-n at temperature 0; correlated noise doesn't average out. |
| Pack co-member dependence | Threshold priming (SIGIR-AP 2024): the "same documents" got different scores depending on earlier batch members.\[5\] Korikov et al. 2025: at 90 passages per prompt, AUC-PR dropped (e.g. 22 vs 34 on DL-19) with a lost-in-the-middle tail.\[4\] BatchGEMBA: "All models experience a quality drop at batch sizes larger than 1."\[24\] | Your 10/50-pass, 200-fail finding matches the literature. Cap packs at ≤10–50. Build packs canonically (sorted by id, not rank) so replay reproduces co-members. Test co-member independence by swapping filler candidates. |
| Listwise position bias | Multiple 2025–26 papers: input order changes scores and rankings, and flattening position exposure doesn't restore consistency.\[25\]\[26\] | Prefer pointwise scores with fixed packing. If listwise, use permutation self-consistency, at a cost.\[27\] |
| Embedding API nondeterminism | OpenAI forum: repeated text-embedding-3-small calls on identical text produced 3 distinct vectors in 10 runs; some "drift" was a base64 client artefact.\[28\]\[29\] | Embed the catalogue once and store the vectors. Cache query vectors by hash. Record the model id and dimension in the index manifest. |
| ANN nondeterminism / recall loss | HNSW rebuilds can yield different graphs and orderings. In one OpenSearch test, a low efSearch lost 27% of true neighbours.\[30\]\[31\] | At ~8K × 1–2K dims, use exact cosine via a numpy matmul. ANN buys nothing here. |
| RRF quirks | At k=60, rank 1 vs 2 differs by only 1.6%, and fusion acts as a consensus vote that can bury a single retriever's top hit.\[32\] Many implementations don't specify tie order. | Use RRF only as a candidate generator, with a wide union (K=128+) so k barely matters. Tie-break on (-score, id). |
| BM25 + cosine score mixing | A GitHub issue (hivemind #337): BM25's unbounded ~1–3 scores "overpowered cosine," pushing semantic hits out of top-K.\[33\] | Fuse by rank (RRF), never raw scores.\[34\] |
| Index staleness / re-embed cost | Cursor caches embeddings by chunk content.\[35\] A third-party blog claims stale embeddings cost up to 20% downstream (secondary source).\[36\] | Key purpose lines and vectors by your pin (comment-stripped code hash). Only changed pins get re-generated. |

## Anti-patterns
- **Gating on wiki/area pages.** You measured a 25% shortlist loss. No source recommends hard gates ahead of a high-recall stage. Add the wiki page as a third ranked list in RRF, or as a judge-prompt feature ("capability: X"). *(Inference, consistent with general hybrid-retrieval practice.)*
- **Small top-k into the reranker.** RankGPT-style rerankers "cannot recover" what stage 1 drops.\[27\] SweRank uses the top 100, and Anthropic's reranker sees the top 150.\[7\]\[15\]
- **Embeddings-only** (misses literal identifiers), or **lexical-only without splitting** (misses `getUserProfile` ↔ "user profile").\[37\]
- **Raw LLM scores as probabilities**, and **thresholds tuned in-sample.** Your drop from 33% to 10% flips at in-sample cutoffs is optimistic by construction.
- **"Not in shortlist" ⇒ "doesn't exist."** Report the audited miss-rate bound alongside every "write new" verdict.

## Recommendations (bearing on A / B / C)
1. **Adopt B with frozen artefacts.**
   - Generate purpose lines offline once per pin with a pinned model, store them, and never regenerate on read.
   - BM25 over: split identifiers + module path + signature + args/return names + docstring + purpose line.
   - Add one embedding over the same enriched text, with stored vectors and exact search.
   - The wiki-page list is the third RRF input.
   - Union to K=128, widening to 512 when the top judge score falls inside the margin band.
   - Judge cost drops from ~164 calls to ~3–13 calls (packs of 50 or 10), roughly 2–8% of A's judge spend before the 1% shadow-sweep overhead. *(Arithmetic on your figures.)*
2. **Keep C as the measured floor, not the product.** Frozen purpose lines + BM25 is the right deterministic middle ground to ship first. Test whether adding the embedding list raises audited recall@128 on paraphrased needs. CoIR and the heap/priority-queue example suggest it will, mainly for vocabulary-mismatch queries.\[16\]
3. **Recall-bound statistics.** Zero misses in n audits gives a 95% upper bound ≈ 3/n, so n ≈ 300 to claim <1%. With m misses, use a Wilson or Clopper–Pearson bound. Stratify audits by language (Python/TS/JS/Dart), since recall differs by language in SweRank+ and Roberts & Roberts.\[16\]\[38\]
4. **Verdict layer:**
   - Calibrate cutoffs on a held-out labelled set of (need, entry, reuse/extend/new) triples.
   - Set δ from measured repeat jitter, ≥0.05 given your data.
   - Report "uncertain" when the top score sits within δ.
   - Accept that this trades flips for abstentions. That is the honest outcome, because the boundary cases genuinely are ambiguous.
5. **Privacy:** purpose-line generation sends source to a vendor once per pin. Screen at generation time, and prefer a local embedding model (nomic-embed-code is open-weights)\[11\] so no vectors leave the building.

```python
import numpy as np
def rrf(lists, k=60, depth=512):
    s = {}
    for ranked in lists:                       # each: list of entry ids, best first
        for r, eid in enumerate(ranked[:depth], 1):
            s[eid] = s.get(eid, 0.0) + 1.0 / (k + r)
    return sorted(s, key=lambda e: (-s[e], e))  # deterministic tie-break on id

def dense_rank(Q, M, ids):                     # exact cosine; M rows pre-normalised, frozen
    sc = M @ (Q / np.linalg.norm(Q))
    return [ids[i] for i in np.lexsort((np.array(ids), -sc))]

def packs(cands, n=10):                        # canonical packing: co-members fixed by id
    c = sorted(cands); return [c[i:i+n] for i in range(0, len(c), n)]

def upper95(misses, n):                        # rule of three / Wilson
    if misses == 0: return 3.0 / n
    z, p = 1.96, misses / n
    return (p + z*z/(2*n) + z*np.sqrt(p*(1-p)/n + z*z/(4*n*n))) / (1 + z*z/n)
```

## Caveats
- Vendor embedding claims (Voyage, Nomic, Cursor) are self-reported and not independently replicated.
- Several 2026 judge-reliability papers (Coin Flip Judge; the temperature-0 safety study) are recent, partly single-author preprints with small samples.
- No relevance-judge-specific temperature-0 test–retest study was found. Applying those flip rates to Jev is an inference.
- The batch-scoring studies disagree on direction: one shows batched scoring winning only when calls are repeated at temperature 1.\[4\]
- GitClear's duplication data is correlational, not attribution to AI.\[39\]
- Claims about Cognition's SWE-grep and stale-embedding penalties come from secondary blogs.\[36\]\[40\]
