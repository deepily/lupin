# Our response to the two expert critiques of the reuse checker

*Lupin team, 23 October 2026. "First opinion" and "second opinion" are the two outside responses of 21 October; "the synthesis" is our summary of them. Every fact in section 2 was checked against the code or the stored data on 23 October, and each one names where it came from.*

## 1. Our position in brief

**We accept the central critique.** The checker should not say "write new" on the evidence it has today. Both experts are right that the judge never sees code, that the cut-offs were fitted to protect the cheap error, and that "not sure" has no follow-through. We do not dispute any of those.

We are **not** starting over. We agree with both experts that the catalogue, the MCP tools, the receipts and the search experiments stay. What changes is what the checker may claim.

Checking the code turned up four things that change the picture:

1. **The judge leak that matters for "write new" is 42%, not 49%.** The 51% figure in our problem statement counted twins that were judged relevant *and* made the top-ten list. "Write new" depends only on whether a twin was judged relevant at all, and 256 of 438 were (58%). It is still a large leak.
2. **The twins are the easy kind of duplicate.** They were found by matching code structure, so they are near-copies. The judge still misses 42% of them on signature and docstring alone. Duplicates that do the same job in different code have not been tested and are probably missed more often.
3. **The live checker rarely says "write new".** Of 200 stored full-sweep answers, 21 said NEW (10.5%) and 85 said "not sure" (42.5%). So the bigger practical hole is the expert finding about "not sure" with no follow-through, not false NEW alone.
4. **Two of the experts' suspected defects are not present.** The embedding prefixes are applied correctly, and the twins were not mined with the same index the checker uses, so the 90% code-like result is not circular.

## 4. What we propose to do, in order

This follows the merged list in the synthesis, reordered by what the code check showed. Costs are the experts' estimates unless marked.

1. **Retire NEW and give "not sure" teeth.** One change covers both: a scoped no-match result, a reported count of everything not looked at, and a scripted search the agent must run and record. Cost: 1 to 2 days (first opinion). Done when every negative answer carries its scope and every implement decision carries a completed search record.
2. **Build the first test set, small.** 80 to 120 realistic needs (second opinion), written without the target's identifiers, including no-match cases and some code that does the same job in different words. Label each stage where a match is lost. Cost: about a week including reviewer time (our estimate).
3. **Measure plain Claude Code on the same needs.** Grep, glob and read only, with the prompt fixed in advance. Compare it with the checker plus the scripted search. **This result decides whether the checker continues.** Rick's planned experiment (section 7, item 4) is the main form of this step: the same cascaded review run with and without the checker, judged by the code it produces.
4. **In parallel, the cheap fixes:** report dropped ids, pass the purpose line to the judge as an experiment, and pilot the jscpd clone warning on diffs.
5. **Only if step 3 shows the checker adds something:** the body-reading verifier, refitted cut-offs, the coverage fixes and richer catalogue entries.

**Stop rule, fixed before the results are in.** We start from the first expert's numbers and ask Rick to confirm or change them:

- **Continue** if the checker plus the scripted search finds at least 90% of real matches and beats plain Claude Code by at least 10 points.
- **Stop** if it beats plain Claude Code by under 5 points, or finds under 75%. Then we keep the clone warning on diffs and a compact map of what exists, and shelve the pre-write judge.
- **In between:** keep the clone warning and the map, and shelve the judge.

**Budget.** About two engineer-weeks for steps 1 to 4 (both experts' ranges overlap there). That is the ceiling for finding out whether the checker is worth keeping.

## 7. Rick's follow-up questions (23 October, evening)

*Measured on 23 October against commit `4b430a87d`, using the index's own file-selection and extraction code (`spec.py` `spec_for` and `all_files`, `py_index.py` `extract_python`, `js_index.py` `extract_js_shapes`) over `git ls-files`. The Firefox plugin sub-repo is left out.*

### 7.1 What Rick asked

1. **Files we do not index at all.** A share of the tree is never searched. How large is it, and what is in it?
2. **Private methods are left out.** That matters for inheritance, where subclasses override or call underscore methods.
3. **Language.** There is no point searching Python when the thing being built is TypeScript or JavaScript, and we have not acted on that.
4. **No baseline.** We do not know how Claude does on its own with grep. Rick will run the same cascaded review with and without the reuse index and compare the code each run produces.
5. **Full coverage in the first pass.** What would it take for the search stage, which embeds code text and prose from docstrings, to stop dropping useful information?
6. **The judge's inputs.** The second expert said the Jev judge does not see what the embedding search sees. We never answered that directly.

### 7.2 Our answers

**1. Unindexed files: most of the gap is tests, and the rest is small.**

| Files | Tracked | Indexed | Share |
|---|---|---|---|
| All Python | 3,568 | 960 | 26.9% |
| All TypeScript | 556 | 182 | 32.7% |
| All JavaScript | 42 | 19 | 45.2% |
| Python, leaving out tests, R&D, migrations and ephemera | 963 | 960 | 99.7% |
| TypeScript, same exclusions | 186 | 182 | 97.8% |
| JavaScript, same exclusions | 31 | 19 | 61.3% |

The headline gap is test code: 2,464 Python files and 370 TypeScript files under `tests/` directories are skipped by design (`SKIP_PARTS` in `spec.py`). The real misses in shipped code are 12 JavaScript files outside `src/lupin_app/static/js` (mostly under `static/html`), 4 TypeScript files and 3 Python files. **What we make of it:** for shipped code the file gap is small, and the bigger loss is inside the files (answer 2). Test helpers are a real reuse target, because agents write new test fixtures as often as new features, so we recommend indexing tests as a **separate scope** that is searched only when the need is test code. Mixing them into the main catalogue would add about 2,800 files of near-duplicate test functions to every sweep.

**2. Private methods: agreed, and the loss is about a third of all definitions.** The index keeps 6,548 of 9,571 Python definitions (68.4%) and 2,043 of 2,955 TypeScript and JavaScript definitions (69.1%). The rest are underscore-named, private or protected members, and helpers nested inside functions. Rick's inheritance point is right: a base class's `_build_prompt` or `_parse_response` is exactly what a new subclass should override rather than rewrite, and the checker cannot point at it today. `fetch_similar` already looks up private definitions, and the duplicate miner (`dups.py`) includes them by default; only the catalogue the judge sweeps leaves them out. **What we will do:** add private and protected methods of indexed classes, with their class named in the entry so the judge can see the inheritance path. Nested helpers stay out, since they cannot be called from outside. This adds at most about 3,900 entries (that count includes the nested helpers we leave out), so at most about 45% more judge calls per full sweep, up to about $0.15 instead of $0.10.

**3. Language: agreed, and the checker does not filter by language at all.** Every entry carries its language (`lang` is `py` or `ts`), but `check_exists` takes no language argument and `sendable()` keeps every language by design. So a TypeScript need is judged against all 6,548 Python entries as well as the 2,043 TypeScript ones: about three quarters of the calls in that sweep cannot produce something the agent could call. They cost money, and each one is a chance of a false "relevant" that pushes the answer to "not sure". **What we will do:** `check_exists` takes the target language, defaults to searching only that language, and says in its result which languages it searched. One exception is worth keeping on request: a TypeScript client feature often needs a server endpoint, and there the right answer is "the Python route already exists". That becomes an explicit cross-language option, not the default. This is a cheap fix and joins step 4 of section 4.

**4. Baseline: agreed, and Rick's experiment is the right one.** It measures what we actually care about, the code a cascaded review produces, rather than a proxy such as checker recall on labelled needs. It becomes the main form of step 3 in section 4, and its result decides whether the checker continues. To make the comparison hold up, we suggest:

- the same plans and the same model in both arms, with the reuse tools removed from the MCP server in the "without" arm rather than only left unmentioned;
- at least three runs per arm, because one run each cannot separate the index from run-to-run variation;
- scoring that does not depend on Jev: new definitions that duplicate existing code (the structural miner `dups.py` and a jscpd clone check on each diff against its base), existing symbols the new code calls, and lines added;
- one person reviewing a sample of the flagged duplicates in each arm, so the score is not only machine-judged.

The labelled test set in step 2 stays, but becomes the tool for finding *where* the checker loses a match, not the go/no-go test.

**5. Full first-pass coverage.** Today the search stage embeds two texts per entry (`vector_build.py`, `entry_texts`): a code text of path, name and signature, and a prose text of name, purpose line and the **first docstring line only**. To stop dropping information:

| Gap | Fix |
|---|---|
| Private and protected methods missing (answer 2) | Add them to the catalogue |
| Wrong-language entries crowd the search (answer 3) | Filter by target language |
| Only the first docstring line is embedded | Embed the whole docstring in the prose text, then check the embedding model's input limit, which we have not yet checked (section 6) |
| 16 shipped JavaScript and TypeScript files outside the index roots | Widen the JavaScript roots to all of `src/lupin_app/static`, leaving out built bundles; check the 3 unindexed Python files one by one |
| Entries dropped as sensitive are lost | Keep them and mask only the sensitive part (already accepted in section 3) |
| Test code missing | Separate test scope (answer 1) |
| Functions with no docstring | 196 of 6,548 public Python definitions (3.0%) have none. Their purpose line, which a model writes from the body, is their only prose, so every entry must have one; we will count the entries that lack one before claiming coverage |

The function body itself is still not embedded, by design. The purpose line is our summary of the body. If the experiment in answer 4 shows that matches are lost at search, embedding the body is the next step to test.

**6. The judge's inputs: the critique is right.** The two stages read different text:

| | Embedding search | Jev judge |
|---|---|---|
| Path, name, signature | Yes | Yes (as the id and signature) |
| First docstring line | Yes | Yes |
| Purpose line, written from the body | **Yes** | **No** |
| Body | No | No |

So the purpose line, the only text in either stage that describes what the code actually does, reaches search but not the judge. The judge prompt even says to "judge only from CANDIDATE's signature and docstring" (`reuse_tools.py`, `PROMPT_TEMPLATE`). That is a likely cause of part of the 42% of twins the judge missed: when a docstring is thin, the judge rules on a name, while the search stage has a one-line account of the body. **What we will do:** give the judge the same text search uses, the purpose line included and the whole docstring once answer 5 lands, and measure the change on the held-out twins and the test set before shipping it. It is the cheapest test of the "judge sees no code" leak, and we run it before the more expensive body-reading verifier. Note that the 58% was measured without the purpose line, so it is the floor for this design, not its ceiling.
