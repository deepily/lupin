# Stopping AI coding agents from rewriting code that already exists: is our reuse checker the right design?

*A problem statement for an outside expert. Lupin project, 21 October 2026. Requested by Rick Ruiz (project lead); drafted by Cheech.*

## 0. What we're asking you

We have built a checker that an AI coding agent is meant to consult before it writes a new function: "does this already exist in the codebase?". We have been measuring it against the wrong error. We guarded against the checker wrongly saying **"reuse this"**. The error that actually costs us is the checker wrongly saying **"nothing exists, write it new"** when a matching function is already there, because that is how duplicate code gets written and nobody notices.

We'd like your independent judgement on three things, and every answer is on the table:

1. **Is this design salvageable** for the goal of minimising false "write new" verdicts? Or should it be thrown out and redesigned, possibly without the judge model we use today (Jev)?
2. **Is there a ceiling?** It may be that similarity search over our catalogue can't catch much more than it catches now. If so, the real question becomes **whether our checker beats what Claude Code already does on its own**, a brute-force grep-and-read of the repository. Please look through the literature for reality checks of that kind.
3. **How much is this worth?** Duplicate code will never reach zero; it never has with human programmers either. We want help judging how much time and money a "best we can do" deserves.

Section 8 lists the specific questions.

## 1. The goal and the scoring rule

**Goal:** reduce how much redundant or duplicative code our AI coding agents write.

**Scoring rule (set by Rick on 21 October 2026, and new to this project):**

| Checker says | When the truth is | Counts as |
|---|---|---|
| "Write new" | A matching function exists | **The costly error: minimise it** |
| "Not sure, read the source" | Anything | **Not an error.** The agent falls back to reading code by hand. It has a cost (section 3.6) but isn't held against the checker |
| "Reuse X" or "Extend X" | X doesn't really do the job | A cheap error: the agent opens X, sees the mismatch and moves on |

Why the asymmetry: a wrong "reuse" is caught the moment someone reads the suggested function. A wrong "write new" is silent. Nobody second-guesses it, and the duplicate stays in the tree.

## 2. The setting

- **The codebase:** one repository (Lupin) of 8,661 public functions, methods and classes: about 6,550 Python, 1,200 TypeScript and 900 JavaScript. Counting private and nested definitions, there are about 11,700. It changes daily.
- **Who writes the code:** a fleet of Claude Code sessions, several at a time, each implementing tasks in its own git worktree. A human (Rick) designs and reviews; he does not write most of the code.
- **The judge:** Jev is a small "System One" classification model from TypeSafe. You give it a typed question with fixed answer choices, and it returns a probability for each choice. It is fast and cheap, and we call it thousands of times per question.

## 3. How the system works today

### 3.1 The entry points

Agents call it through our MCP server:

- **`check_exists(need)`**: the need is one or two sentences describing a function the agent is about to write. It returns a **verdict** (REUSE, EXTEND, NEW or UNCERTAIN_READ_SOURCE), a shortlist, the nearest entries, the causes of any uncertainty, and a receipt id.
- **`fetch_similar(entry)`**: given an existing function, it lists its likely duplicates. A review skill uses this on every function a change adds, then the reviewer reads the candidates' source and rules DUPLICATE, EXTEND or DISTINCT.

Every call writes an immutable, content-addressed receipt, so any answer can be replayed and audited later.

### 3.2 The catalogue

An index is rebuilt from the source tree: one entry per public definition, holding its id, signature, the first line of its docstring, file and module. We do not index function bodies.

For the shortlist stage (3.3), each entry also has:

- a **purpose line**: one sentence of at most 25 words, written once by a Claude Code job and regenerated when the source changes;
- **embedding vectors** of the entry's text (name, signature, purpose line and docstring; never the body), made with nomic-embed-text-v1.5 and nomic-ai/CodeRankEmbed;
- a **word index** (BM25) over the split identifiers and the prose.

The vectors are refreshed daily, re-embedding only the entries that changed.

### 3.3 Two routes to the judge

**Route A, the full sweep.** Jev is asked about **every sendable entry** in the catalogue: about 8,200 calls per question (8,187 on 15 October, against 8,661 catalogue entries). Entries whose id, signature or docstring line holds an email, URL, IP address, path or credential-shaped token are dropped before the sweep, and the dropped ids are not reported. `fetch_similar` always takes this route, on either configuration. This was the original design (30 September), deliberately with no embeddings, so that "write new" would mean "the judge looked at everything". **This is the route agents actually get today**: the MCP server's configuration doesn't switch on the shortlist route.

**Route B, the shortlist stage.** Built and tested in October to cut cost, but **not switched on for agents**:

1. The need is redacted (emails, URLs, paths, credentials removed) and embedded.
2. Several ranked lists are made: vector similarity plus two word-index lists. They are merged by reciprocal-rank fusion, which uses rank position only, and the top 5 of every list are always kept.
3. The top **128** entries go to Jev in packs of 50. Only those 128 are judged; the other ~8,500 are never seen. The receipt records how many entries were not asked.
4. Only while the uncertainty band (3.6) is on: if the result sits near a cut-off, the shortlist is widened to **512** and the extra entries are judged too. With the band off, route B judges a fixed 128.

### 3.4 What the judge sees and answers

For each candidate, Jev sees the need and the candidate's **id, signature and first docstring line**, never its source code. It is asked: *"A developer plans to write new code for NEED. Judge only from CANDIDATE's signature and docstring whether it already provides that capability."* It answers with probabilities for **reuse**, **extend** and **unrelated**.

From these we derive two numbers per candidate:

- **overlap** = P(reuse) + P(extend)
- **confidence** = the largest of the three probabilities

### 3.5 The verdict rules

| Term | Rule |
|---|---|
| Relevant candidate | overlap ≥ **0.3** |
| Doubtful candidate | overlap ≥ 0.3 and confidence < **0.9** |
| Strong candidate | overlap ≥ 0.9 and confidence ≥ 0.9 |

The verdict is decided in order:

1. **UNCERTAIN_READ_SOURCE ("not sure")** if any pipeline problem holds (stale index, failed or malformed call, missing key), or any candidate is doubtful and none is strong.
2. **NEW** if no candidate is relevant.
3. **REUSE** if a deciding candidate's top answer is "reuse".
4. **EXTEND** otherwise.

**So "write new" means: every candidate that was judged scored overlap below 0.3, all calls succeeded, and none was doubtful.** On either route it also means "new among sendable entries": an entry dropped for sensitive-looking text can never be found. On route B, "every candidate that was judged" means the 128 (or 512) on the shortlist, not the catalogue. **Nothing in the verdict rules gates NEW on how likely the shortlist was to have missed the match.** A shadow audit was designed to measure that (re-run 1% of lookups as full sweeps and count misses) and exists as a library, but nothing calls it.

### 3.6 The fallback being proposed

The verdict rules above can also carry an **uncertainty band**: an answer within 0.076 of any cut-off is treated as "not sure". In testing, the band as implemented checked every judged candidate rather than only the deciding one, and turned nearly every answer into "not sure". The checked-in policy has the band **on** (0.076) today. **The fallback on the table is to switch it off.** With it off, nothing widens, so route B would judge a fixed 128. This document is not about that test; we mention it only so you know which policy is current and which is proposed.

### 3.7 What happens on "not sure"

Nothing automatic. The agent is told to read the source of the shortlisted and nearest entries before deciding. There is no built-in grep or brute-force search. A counter-reviewer step in the review skill asks for "one or two fixed-string searches" by hand. In effect, "not sure" hands the question back to Claude Code's own search habits, the same baseline we ask you to compare against.

## 4. How "false reuse" became the error we guarded against

This is the part Rick asked us to be candid about. The short version: **the original design guarded against false "write new"; over two weeks of cost-driven redesign, the guard moved to false "reuse", and I found no document that records a decision to move it.**

| Date | What was decided | Which error it guarded |
|---|---|---|
| 30 Sep | Original design: Jev sweeps every entry, no embeddings ("no vector store to go stale"). "Not sure" is never read as NEW. A miss is defined as a receipt that said NEW on code later found to be a duplicate, and "the share of receipts... that recover their miss is the number to watch". An embedding pre-filter was ruled out as "a recall risk exactly where duplicates hurt". | **False NEW** |
| 7 Oct | An outside response recommended a full sweep, with a cheap recall stage only at 50,000 to 100,000 entries, and "write new" only if "zero unasked entries". The Option 2 write-up (headed with Rick's name) allowed embeddings first, but said the stage "may only return 'write new'" if Jev found nothing **and** no shortlisted entry went unasked **and** the stage's miss rate had a 95% upper bound under **1%**. Targets: recall ≥ **0.98** at 128 and ≥ **0.995** at 512. Ship the full sweep first; promote the shortlist only after a shadow audit. | **False NEW** |
| 14 Oct | The shortlist stage was planned (to make each search cheaper and faster). The plan kept the miss-rate bound only as a **number reported** beside each "write new" (D8), not as a condition. The 0.98 recall target appears in the problem statement's questions but **not in the response or the plan**; it was dropped without a recorded decision. Ruling R10 set **"the false-reuse rate is 5%"** as the input to fitting the cut-offs. I found no written rationale for choosing false reuse. | **False reuse** |
| 15 Oct | The relevance cut-off was fitted to R10 and changed from 0.5 to **0.3** (commit `09a1e0707`). The fit chose 0.3 as the cut that found the most known duplicates among the cuts it tried that kept false reuse within 5% (held-out: **4.7%**, 660 of 14,001). The fit reports that the 5% cap was the binding constraint. On the same held-out data, only **51%** of known duplicate pairs scored as relevant. | **False reuse** |

Two observations, stated separately so you can judge the link yourself:

- Lowering the cut from 0.5 to 0.3 makes NEW *rarer*, so the fit moved in the right direction for us. The 5% false-reuse cap is what stopped it going lower.
- At the cut the cap allowed, about half of known duplicates were not flagged as relevant when Jev was asked about them.

## 5. Where real matches leak out

A match can be lost at three points before the verdict. Each measurement below names its population, and none of them is the false "write new" rate itself (section 6).

| Leak | What was measured | Result | Population |
|---|---|---|---|
| **1. The shortlist misses it** (route B only) | Of the entries a full sweep flagged as relevant, how many the shortlist contained | **69%** at 128 and **73%** at 512, as the mean over 13 needs of each need's own fraction. Counted as pooled items, it is 17 of 22 (77%) and 18 of 22 (82%) | 13 needs with a non-empty reference, from 30 in-sample needs, arm B1, 15 Oct |
| **2. The judge doesn't recognise it** | Of known duplicate pairs, how many Jev scored at overlap ≥ 0.3 | **51%** (225 of 438) | Held-out half of a labelled set of known duplicates ("twins") found in the codebase, 15 Oct |
| **3. The cut-off is set for the other error** | 0.3 was the cut that found the most duplicates among those that held false reuse within 5%; that cap bound the choice | False reuse 4.7% (660 of 14,001 non-duplicate pairs) | Same held-out set |

There is one more measurement, on a different population. When the query is a known twin's own name, signature and docstring line (code-like, not a prose need), the shortlist ranks the twin in its top 10 in about 90% of cases. That is 341 of 376, all Python, in-sample, arm B1 at the selected fusion constants (335 at the defaults).

These are separate facts:
- Code-like twin queries are found in the top 10 about 90% of the time.
- Prose needs reach 69% to 73% shortlist recall.

They come from different populations, so we can't say which stage loses more. We have not measured the shortlist and the judge on the same set of needs.

## 6. What has never been measured

- **The false "write new" rate itself.** No run has counted how often the checker says NEW when a match exists, on any population. This is now the headline number, and we have no value for it.
- **Any comparison against plain search.** We have never measured how well Claude Code, unaided, finds existing code before writing new: grep, read, or its own agentic search. We have no baseline to beat.
- **How much duplicate code the fleet actually writes,** with or without the checker.
- **The cost of "not sure"** in practice: how long the hand-off to reading source takes, and whether agents actually do it.
- **The shadow audit: built, never switched on.** It is Phase 6 of the 14 October plan, built on 15 October (`src/cosa/repo/symindex/candidates/shadow_audit.py`), and has produced zero observations.
  - **How it would work:**
    - On about 1% of shortlist lookups it queues the lookup. The pick is a hash of the need and the vector-set generation, so the same lookup is always in or always out.
    - A scheduled job re-runs each queued need as a full sweep of every entry.
    - If the full sweep says REUSE or EXTEND, and none of the functions that caused that verdict were on the shortlist, it counts a **miss**.
    - From the misses it gives a 95% upper bound on the shortlist's miss rate (zero misses in 300 audits is about 1%). `bound_for_verdict` was meant to attach that bound to every "write new".
  - **Why it never ran:** nothing in the lookup path calls `enqueue_if_sampled`, and no scheduled job drains the queue. The project wiki says so: "Nothing in `lupin_mcp` or the server calls it yet." The shortlist route it audits is itself not switched on for agents (3.3), so there are no live shortlist lookups to sample.
  - **What it could and couldn't tell us:**
    - It measures **leak 1 only**: matches the shortlist dropped.
    - It is blind to **leak 2**. The full sweep uses the same judge, so a duplicate Jev fails to recognise is missed by both sides and never counted.
    - It compares against the full sweep, not against the truth.
    - **Its miss rate is not the false "write new" rate, and the two can't be read off each other.** The audit counts a sampled lookup of *any* verdict whose shortlist dropped the full sweep's match; the lookup's own verdict is ignored, so a drop that still ended in REUSE via another candidate, or in "not sure", counts as a miss. The false "write new" rate counts NEW answers among lookups where a match exists. The two figures use different numerators and different denominators.

## 7. Costs we know

| Route | Measured cost |
|---|---|
| Full sweep (route A) | About $0.10 and 8.1 s median per search on the current question; slowest 13.1 s (14 Oct, our own measure) |
| Shortlist stage (route B) | With the band off: about 29,000 Jev tokens and 3 requests per search, roughly $0.001. With the band on: about 107,000 tokens and 10 requests, because the band widens most lookups from 128 to 512 |
| One full sweep of 10 needs (the reference for the recall comparison) | About 26 million tokens |

Agents run on a fixed-price Claude plan, so a Claude Code grep-and-read baseline costs time and plan quota rather than per-token money.

## 8. Questions for you

**On the design**

1. For the goal of minimising false "write new", is a cheap recall stage → small judge → fixed cut-offs a sound architecture at about 8,600 entries? Or should we start over? What would you build instead?
2. Is a judge that sees only a **signature and one docstring line** capable of recognising duplicates? Should it read the body? Is a small classifier like Jev adequate here, or does this need a frontier LLM reading code, or no model at all?
3. Should "write new" ever be a verdict? Alternatives include: never say NEW, only "not sure plus the nearest N"; or say NEW only with a bounded miss rate (as originally designed); or always trigger a background full sweep.

**On the ceiling**

4. With prose needs searched against code entries, is ~70% shortlist recall a property of our implementation or close to what embedding plus word search can do? What does the code-search and clone-detection literature say?
5. If the ceiling is real, how does our checker compare with **Claude Code doing brute-force grep and read**? Is there published evidence on how well agentic search finds existing code? Leads cited to us earlier, which we haven't verified: Anthropic's Boris Cherny on agentic search generally beating retrieval; Sourcegraph dropping embeddings; Cursor reporting about 12.5% higher accuracy from semantic search added on top of grep.
6. Is there evidence on how much duplicate code AI coding assistants write, and on what has actually reduced it? Pre-write lookup, review-time clone detection (for example token-based clone detectors on each diff), or after-the-fact refactoring?

**On measurement and budget**

7. How should we measure the false "write new" rate, and how many labelled cases does a useful bound need? (Zero misses in 300 audits bounds it near 1%.) Our built-but-idle shadow audit (section 6) would bound shortlist misses only, because it shares the judge with its own reference. What would you use to see the judge's misses: human-labelled duplicates, a stronger model, clone-detection tools?
8. Given that "not sure" costs a manual read every time, how should we weigh a lower false-NEW rate against a higher "not sure" rate?
9. What is a reasonable level of investment for this problem, and what result would justify continuing rather than relying on Claude Code's own search?
