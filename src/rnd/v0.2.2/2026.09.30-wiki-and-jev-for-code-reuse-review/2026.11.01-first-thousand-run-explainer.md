# Last night's 1,000-call trial run: what happened and what you need to decide

*Lupin reuse project. Written 1 November 2026 by Cheech for Rick, for a reader with no prior context.*

## The short version

- **What we tried:** a small, capped trial of the pipeline that will build our next test set, before you sign off on the full plan.
- **What happened:** the trial stopped about two-thirds of the way through its first step. It produced no usable test items.
- **What we learned:** the step that finds matching code is far more expensive than planned, and it finds very little. This one finding matters more than the crash.
- **What it cost:** 686 of the 1,000 allowed model calls. 314 are left, and nothing has been spent since.
- **What you need to decide:** whether to spend the remaining 314 calls now, and if so how. My recommendation is to spend nothing until the method is fixed and you've approved the fix.

## Background: what the project is

AI coding agents often write code that already exists somewhere else in the codebase. We built a **reuse checker** for this. Before an agent writes something new, it describes what it needs in one sentence. The checker then searches the codebase and tells the agent if something already does that job.

To know whether the checker works, we need a **test set**: a list of plain-English needs, each paired with the existing code that meets it (the "answer"). We give the checker each need and see whether it finds the answer. This test set is called **Set B**, and it will hold 400 needs.

Building Set B is called **"the draw"**. For each item it goes like this:

1. Pick a real function from the codebase. This is the **seed**.
2. Look for any other code that does the same job as the seed, by asking a model "does this candidate do the same job?" one candidate at a time. Every yes joins the **answer**.
3. Have a model write a one-sentence need that describes the job without giving away the answer.
4. Have a second, different model check that the need and the answer match. If the two models agree, the item is kept.

The full draw is expected to cost roughly 9,000 model calls. Before committing to that, you approved a **trial of 1,000 calls**, with hard limits: nothing labelled by people, nothing published, nothing pushed.

## What the trial was supposed to do

The trial runs four checks in order, sharing the 1,000-call budget:

| Step | What it checks | Planned calls |
|---|---|---|
| 1. Attribution | On 50 seeds: when the checker misses an answer, can we tell which part of it failed? | about 200 |
| 2. Yield | On 100 seeds: how many good items do we get per call spent? This sets the cost of the real draw. | most of the rest |
| 3. Positive control | We plant disguised copies of known code: does the search find them? | small |
| 4. Remainder | Re-checks items people have already labelled | small |

## What actually happened

**Step 1 never finished.** It got through 36 of its 50 seeds. On seed 37, the model sent back a reply the program couldn't read, and at the time the program treated that as fatal and stopped. Steps 2, 3 and 4 never ran. (We've since fixed this: an unreadable reply now skips just that one seed.)

**The bigger problem is where the calls went.** Of the 686 calls:

| Spent on | Calls | Result |
|---|---|---|
| Asking "does this candidate do the same job?" (step 2 of the draw) | 673 | only **3 yes** answers |
| Writing the one-sentence need | 8 | 6 were rejected for giving away the answer |
| Second-model check | 1 | the second model disagreed, so that item was rejected too |
| Calls lost to errors | 4 | — |

So **36 seeds and 686 calls produced zero usable items.** Step 1 had planned for about 200 calls, and it used more than three times that with 14 seeds still to go.

The reason is the candidate check. For each seed the program asks about up to 10 candidates on one search route, or up to 30 on the other, and it only stops early when it gets a yes. Yes answers were so rare (3 in 673) that almost every seed used its full allowance. The 30-candidate route spent three-quarters of the calls and found an answer for 1 of its 18 seeds.

## Why I stopped rather than carrying on

- **Simply restarting wouldn't help.** At about 19 calls per seed, the 14 remaining seeds in step 1 would use roughly 266 of the 314 calls left. That leaves almost nothing for steps 2 to 4, and step 2 is the one that tells us what the real draw will cost.
- **The real fix changes the method.** For example, we could check only the top 5 candidates per seed instead of 10 or 30. The plan hasn't been signed off yet, and changing how it works is your call, not mine.
- The rule for the trial was to stop at a finding rather than spend through it, and this was a finding.

## Why this matters for the project

The trial is already answering the question it was meant to answer. As currently designed, finding matching code is expensive and rarely succeeds. That's the same warning the earlier pilots gave: about 100 calls per match in TypeScript, and none at all in Python. If nothing changes, the 9,000-call estimate for the full draw is likely too low. Better to learn that now, on 686 calls, than halfway through 9,000.
