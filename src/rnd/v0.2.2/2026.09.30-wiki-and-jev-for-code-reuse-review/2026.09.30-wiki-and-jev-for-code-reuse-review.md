# Code wiki + Jev: reuse review lifecycle

Sep 29, 2026 · @Richard P Ruiz

Every "does this already exist?" question in Lupin AF goes through one MCP entry point. The answer comes back as a replayable receipt, and every miss comes back to the librarian as a repair job.

## At a glance

&#91;embedded content: reuse review lifecycle · three callers, one entry point, one repair loop\]

Implementers, reviewers and skeptics all go through one MCP server. Jev judges the wiki and the symbol index, and every answer is stored as a receipt. Receipts that are later overturned feed the librarian, who repairs the summary Jev missed.

## The layers

The wiki reveals four levels, each more detailed than the last. Jev decides which level-1 pages to open, and at level 2 it judges every entry, so nothing is pruned there.

| Level | Holds | Written by | Opened by |
| --- | --- | --- | --- |
| L0 `INDEX.md` | One line per capability: what it does, its key symbols | Librarian, approved by you | Always; it is small |
| L1 `capabilities/<slug>.md` | Intent, canonical entry point, how to extend it, "don't" rules, invariants, `covers:` pins | Librarian, hash-pinned to code | Jev per request (hidden / summary / full), then the reviewer |
| L2 `symbols.md` | Every public signature and first docstring line, with `module.name@hash` | `symindex.py build` from the AST, never by hand | Jev sweeps every entry (reuse / extend / unrelated) |
| L3 source | The code itself | Implementers | The reviewer, only for Jev's shortlist and anything flagged uncertain |

Jev reads only L0 lines and L2 lines, so those one-liners and your docstrings' first lines decide what can be found. L1 pages exist for the reviewer and for the implementer deciding how to extend. L2 is regenerated from code on demand, so it has no embeddings and no vector store to go stale.

## Build it once

The first build takes about a day, mostly librarian time. The one step that needs you is naming the capabilities.

1. **Generate L2.** Run `symindex.py build` to write `symbols.md` and `routes.md` from the AST: stdlib `ast` for Python, `py-tree-sitter` with `tree-sitter-javascript` for the vanilla JS.
2. **Find the damage.** Run `symindex.py dups`. Its near-duplicate clusters are your worst areas, your starting baseline, and your first evaluation set.
3. **Propose capabilities.** Group `symbols.md` by package prefix and FastAPI route prefix (`grimp` if packages don't match capabilities). Give each group to the librarian: "propose slug, one-line purpose, covered symbols, canonical entry point."
4. **Approve the names.** You approve or rename the slugs. This is the only step that needs a human.
5. **Write the pages.** The librarian drafts each L1 page from the covered symbols' source, pins `symbol@hash`, and adds the L0 line. Start with the areas the duplicate clusters show are worst, not the whole repo.
6. **Fill in docstrings.** Every public symbol gets a first docstring line that says what it does, since Jev cannot match an empty one.
7. **Measure the baseline.** For each duplicate cluster, describe one member as a need and call `check_exists`. The share of clusters where the other members come back in the shortlist is your starting recall.

The structural conventions (`[[links]]`, `INDEX.md`, a change log, link lint) come from Karpathy's llm-wiki pattern, via [karpathy-llm-wiki](https://github.com/Astro-Han/karpathy-llm-wiki) if you want its tooling. What's new here is the drift check, because unlike that pattern's `raw/` folder, your source changes daily.

## The MCP entry point

The CoSA reuse MCP server is the only way in: no hooks, and the same tools for every role. Calls are pull-based, so the reuse-reviewer skill makes them mandatory at each decision point in a review, and any other Claude Code instance can call them whenever it wants.

| Tool | Question it answers | Returns | Called by |
| --- | --- | --- | --- |
| `check_exists(need)` | Should I build this? | Verdict (REUSE / EXTEND / NEW / UNCERTAIN\_READ\_SOURCE) + shortlist + receipt | Implementers before writing; reviewers checking a plan |
| `fetch_similar(entry)` | What does this new code resemble? | Shortlist + receipt | Reviewers, per new definition in the diff |
| `read_capability(names)` | How is this meant to work and be extended? | L1 pages | Anyone, after a shortlist names a capability |
| `replay(receipt_id)` | Is this assertion what the evidence said? | The original result from the frozen index, plus a re-run at HEAD | Skeptical reviewers, counter-reviewers |

When each is called:

- **Implementer, while planning:** `check_exists` for each new function or module the plan proposes. The plan records each answer as `reuses:`, `extends:`, or `rejected: <symbol> because <reason>`, each citing its receipt.
- **Implementer, while building:** `check_exists` again the moment a helper starts to take shape that the plan never listed. Runtime is where unplanned duplicates appear.
- **Reviewer:** `fetch_similar` for every new definition in the diff, plus `read_capability` for the pages on the shortlist. It reads the source only for shortlisted or uncertain candidates, then issues DUPLICATE, EXTEND `<symbol>`, or DISTINCT `<why>`.
- **Counter-reviewer:** `replay` on the receipts the first reviewer cited (next section).

The server rebuilds `symbols.md` on the first call after any source file changes, using file modification times. UNCERTAIN\_READ\_SOURCE (Jev confidence < 0.9) is never read as NEW: it obliges the caller to read the source.

## Evidence of review

Every MCP call returns a receipt whose ID is a hash of its inputs, so a claim like "this can be reused" cites evidence anyone can re-run. Receipts don't make the verdicts correct. They make the disagreement concrete: two agents see the same shortlist and dispute only how the source should be read.

A receipt, as stored in `docs/review/receipts/<id>.json`:

```json
{
  "id": "rr_7c1e9a40",
  "tool": "check_exists",
  "query": "download an RSS feed and turn items into articles",
  "index_sha": "sha256:4b2f…",
  "wiki_rev": "git:9e31d7a",
  "jev_model": "jev-1.13.0",
  "threshold": 0.5,
  "verdict": "REUSE",
  "shortlist": [{"entry": "backend/feeds/rss.py::parse_feed(url)", "p_overlap": 0.95, "confidence": 0.97}],
  "caller": "impl-worker-07",
  "at": "2026-09-29T22:59:00-04:00"
}
```

`id` = hash(tool, query, index\_sha, jev\_model, threshold). Every `symbols.md` a receipt was issued against is kept, content-addressed by `index_sha`. It's a few hundred KB per snapshot, so replaying months later is cheap.

The citation rule, for both review comments and plans: every reuse, extend or new assertion carries `reuse-receipt: <id>`. An assertion without a receipt is treated as unsupported and gets challenged.

How a skeptical agent checks the claim:

1. `replay(id)` against the frozen `index_sha`. A different shortlist means the receipt was tampered with or the model changed. Jev repeated 96 of 96 identical decisions in the CMU study, and cached answers repeat exactly.
2. `replay(id)` against HEAD. A different result is legitimate drift: code landed since the review. The skeptic judges against HEAD.
3. The skeptic reads the source of any candidate the reviewer dismissed and rules on it: DUPLICATE, EXTEND, or DISTINCT. That ruling cites its own receipt.
4. When the skeptic overturns the reviewer on a candidate Jev never shortlisted, that's a **miss**. It goes to the miss ledger (see The librarian).

&#91;embedded content: dispute flow · two replays, one ruling, one feedback path\]

A replay at the frozen index checks the receipt itself. A replay at HEAD checks the code as it is now. Only an overturn on a candidate Jev never shortlisted costs the librarian any work.

## The librarian

The librarian is a Claude Code instance that repairs the wiki from a queue. Two kinds of signal fill that queue. Deterministic lint catches pages that have drifted from the code. The miss ledger catches duplicates a person or LLM spotted that Jev failed to shortlist.

| Signal | Detected by | Meaning | Librarian action |
| --- | --- | --- | --- |
| stale | `wiki_lint.py`: pin hash differs from `symbols.md` | Code under a page changed | Re-read the source, update the page, re-pin |
| dangling | `wiki_lint.py`: pinned symbol gone | Renamed or deleted | Repoint to the successor or remove the pin |
| orphan | `wiki_lint.py`: public symbol with no page | New code nobody filed | Add it to a page, or propose a capability |
| unindexed | lint: page missing from `INDEX.md` | Jev can never select it | Add the L0 line |
| miss: review | Reviewer rules DUPLICATE on code whose receipt said NEW, and the match wasn't on its shortlist | Jev couldn't see the overlap | Rewrite the matched symbol's docstring or L0 line; replay the receipt |
| miss: skeptic | A `replay` ruling overturns a DISTINCT or NEW | Same, found one step later | Same |
| miss: CI | `symindex.py dups` finds a new clone whose receipt said NEW | Duplicate got past everyone | Same, plus a consolidation ticket |

Each miss is written to `docs/wiki/misses.jsonl` as a line containing the receipt ID, the symbol that should have matched, and who caught it. The repair is verified the only way that counts: after rewriting the summary, the librarian replays the original receipt at HEAD. The fix is done when the missed symbol appears on the shortlist.

Every repaired miss becomes a permanent regression case. The ledger turns into your evaluation suite, and the share of receipts replayed at HEAD that recover their miss is the number to watch.

Cadence: lint runs nightly or on demand from a manager instance, and misses are handled as they arrive. With little code churn the queue is usually empty or a few items long. Its size tracks how much code changed, not repo size.

## Open items and guardrails

- [ ] Confirm the Jev endpoint URL and auth header against TypeSafe's API reference. Both are guesses in `reuse_check.py`.
- [ ] Add receipts and `replay` to `cosa_reuse_mcp.py`. The delivered server returns the query but doesn't yet store receipts or index snapshots.
- [ ] Pin `jev-1.13.0`. `jev-latest` moves when a new release ships and would break replay.
- [ ] Have the reviewer skill log every MCP call. Without hooks, coverage depends on the skill actually making the calls, and the log is how you check that.
- [ ] Run the baseline recall test on the duplicate clusters before trusting any verdict.
- [ ] Wire CoSA voice access to the same three or four tools.

Guardrails:

- **Data leaving your machine.** Signatures, docstrings and L0 lines go to TypeSafe's hosted API; function bodies and L1 pages don't. Exclude anything sensitive from `symbols.md`.
- **Where Jev is weak.** It is reliable at judging whether a candidate is relevant. It is weak at judging whether two pieces of code are truly equivalent: 76.2% vs GPT-6's 97.6% on coding in the CMU study, and easily swayed by a well-written wrong answer. Every DUPLICATE or DISTINCT ruling therefore comes from the reviewer reading source, never from Jev alone.
- **Prompt injection through docstrings.** Agent-written docstrings are also Jev's input. The reviewer keeps the final say.
- **Code is the source of truth.** When a page disagrees with the code, trust the code and queue the page as stale.
