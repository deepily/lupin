# Two outside experts on Lupin's reuse checker: what they agree on, where they split, and what to do first

*A synthesis for Rick and for a podcast listener. It answers the problem statement dated 21 October 2026. "First opinion" and "second opinion" are the two expert responses. Anything marked "My judgment" is the author's own and was not said by either expert.*

## 1. The combined verdict

Both experts say the same thing in different words: **the checker should stop saying "write new."** Under Rick's scoring rule, a wrong "write new" is the costly error, and the checker has no honest basis for that verdict today. The first opinion puts it as "Stop emitting NEW now." The second opinion puts it as "Retire unqualified NEW for now."

Both agree the judge, Jev, sees only a signature and one line of docstring, never the code. The first opinion calls this the biggest leak and reads the 51% twin score as meaning a NEW verdict on about half of real duplicates (summary at the top). The second opinion calls it an information limit that a larger model cannot fix (section 4.1), but rejects reading 225 of 438 as a live false-NEW rate (section 3 table).

Both want the same next step, and it is not more tuning: build an independent test set, measure plain Claude Code with grep and reading, then decide how much of the checker deserves to live. Both also recommend a clone check on newly written code.

Neither expert says to throw the system away. The first opinion says "Don't start over; re-order priorities" (answer 1). The second opinion says to keep the catalogue, the MCP interface, the hybrid-search experiments and the receipts, and to change what the checker is allowed to claim (second opinion, the recommendation at the top and section 2).

Where they split is on how much of the judge and the full sweep to keep. The first opinion keeps the full sweep and Jev as a cheap first pass, then adds a stronger model that reads code. The second opinion would test a simpler system in which Jev is not on the mandatory path at all. Sections 3 and 5 below cover the split.

## 2. Where the two experts agree

**2.1 NEW should not be a verdict today.**
- First opinion: replace it with a "no match found" result that carries counts (how many were judged, how many were not, how many were dropped, how old the index is) plus the nearest ten, and make the agent run a scripted grep-and-read step. NEW can return only when a measured bound shows the false-NEW rate is low enough (Part 4, action P0-1).
- Second opinion: return a scoped result such as "no match found in searched scope," with a defined next action. It adds that renaming alone is not enough. The agent must actually complete a bounded source search before it decides to implement (section 2, decision 2).

**2.2 "Not sure" has no teeth, so it must be enforced.** The problem statement says "not sure" does nothing automatic (section 3.7). The second opinion lists this as issue D8: apparent caution may just delay the same duplicate, so the follow-through must be executed or required and recorded. The first opinion's scripted step in P0-1 does the same job. Its reason for scripting is evidence that unaided agents miss things (see 4.1 below).

**2.3 The numbers in the problem statement do not measure the thing that matters.** The first opinion says the false-NEW rate "has never been measured" (M1); the second opinion says there is no operational bound and no measured baseline (section 3 table, D9). Both say the built-but-idle shadow audit shares Jev with its own reference, so it cannot see Jev's own misses (first opinion, M2; second opinion, D7 and section 7.5). Both say it counts a different thing than the false-NEW rate, so one cannot be read off the other.

**2.4 The thresholds were fitted to the wrong error.** The first opinion says the 5% false-reuse cap was binding, so the 0.3 cut sacrificed recall to protect the cheap error, which is the reverse of the new rule (key finding 2, issue F1). The second opinion's issue D1 says the same and wants the objective refitted around query-level missed reuse, abstention cost and real duplicate escapes.

**2.5 Switching the uncertainty band off removes a symptom and leaves a hole.** The first opinion says turning it off removes the only mechanism that converts near-misses into "not sure," so a twin scoring 0.25 with nothing else relevant becomes NEW (V2). It says fix the scope to the top candidates and "never turn it off while NEW exists." The second opinion says switching it off leaves a blind spot for confident negatives, that "reduced abstention" is not "improved safety," and to replace the rule and the negative-verdict contract together (section 4.2). As an illustration, if each candidate had a 0.1% chance of triggering the band, at least one would trigger 12.0% of the time at 128 candidates, 40.1% at 512 and 99.97% at 8,200 (second opinion, section 4.2; assumptions, not Lupin measurements). Both want the band fixed or replaced, not simply removed. (My judgment: if NEW is retired, the band-off ruling matters less; the question returns only if NEW does.)

**2.6 The confidence rule adds little.** The first opinion derives that a candidate with overlap between 0.3 and 0.9 is "doubtful" by construction, so the rule is a second overlap threshold at 0.9 (J4). The second opinion derives that confidence of 0.9 or more forces reuse plus extend to 0.9 or more, so the rules largely reduce to overlap thresholds, but adds that "the precise deciding-candidate and tie-breaking logic still needs source inspection" (section 4.2). Both noted that a 4.7% pair-level false-positive rate would imply about 385 spurious "relevant" candidates per full sweep if it transferred, and both flagged that as unverified (first opinion, J3; second opinion, section 4.3).

**2.7 Silent drops, public-only coverage and stale indexes are real holes.** Entries with sensitive-looking text are silently dropped (first opinion I4; second opinion D3), and both want them kept with only the sensitive part masked. Private and nested definitions are missing (first opinion I3, about 26% of definitions; second opinion D4). A daily index misses same-day code in sibling worktrees (first opinion I5; second opinion D5, D18).

**2.7b Route B should not be promoted as it stands.** The first opinion would drop promotion for cost reasons (Part 4). The second opinion says "Do not promote route B as currently described" (section 2, decision 3).

**2.8 The code-to-code path needs a different design.** Both say `fetch_similar` should compare actual code with token or structure-based clone detection, not the signature-only judge (first opinion P1-4; second opinion D16, section 6.5). Both name jscpd and say to start as a warning, not a gate.

**2.9 The arithmetic of "zero misses in 300."** Both agree: 300 clean cases bound the miss rate near 1%, about 150 near 2% (first opinion, P0-2; second opinion, section 7.4). At 1% sampling, 300 audited lookups would need about 30,000 incoming lookups.

**2.10 The 69 to 73% shortlist recall is not proven to be a ceiling.** The first opinion calls it "mostly an implementation property" (answer 4). The second opinion says "No such ceiling is established" (answer 4). Both note that the small gain from 128 to 512 entries points to representation or query wording, not list size (first opinion R2; second opinion section 5.3).

**2.11 The industry leads are real but narrower than the headlines.** Both confirmed the Cherny, Sourcegraph and Cursor leads, and both say none measures duplicate prevention. The first opinion adds that Cherny's own words were "mostly vibes" with "some internal benchmarks," and that Sourcegraph's stated reasons were operational, not recall (section 2.1). Both treat GitClear's rise in duplicate-block commits (0.45% in 2022 to 6.66% in 2024) as vendor observation, not a Lupin rate, and neither found a controlled study showing that a pre-write lookup reduces duplicates (first opinion, Part 3; second opinion, section 5.5).

## 3. Where they disagree, and which side the evidence favors

### 3.1 Multiplying the two leaks
- First opinion: end-to-end recall is at most 51% for the full sweep and about 35 to 37% for the shortlist, from multiplying 0.69 to 0.73 by 0.51 (summary, first bullet). It assumes the two leaks are independent and says the populations differ.
- Second opinion: "Do not multiply 0.69 by 0.51." The figures cover different populations, reference standards and units (section 3).

My judgment: the evidence favors the second opinion. The problem statement itself says the two numbers come from different populations and that the leaks may be correlated (section 5.1). The first opinion's own caveats call both estimates (at most 51%, and 35 to 37%) "illustrative, not measured," and its F2 says the 51% is a judge measurement on a different input type, so production judge recall on prose needs is unknown. The second opinion likewise says 225 of 438 does not mean half of live queries get a false NEW. Treat both of the first opinion's end-to-end figures as a worry, not a finding.

### 3.2 Keep the full sweep, or move away from Jev?
- First opinion: keep route A as the recall stage. Cost is the wrong thing to optimize at this size: about $0.10 and 8 seconds per call comes to roughly $50 a day at 500 checks a day (its own assumption), and the shortlist saves about $0.099 per call at a cost of 27 to 31 points of recall (key finding 6, section 1H). Jev stays as a "recall filter" with a lower cut, and a stronger model that reads bodies does the final call (P1-1, P1-3).
- Second opinion: do not promote route B as described, but also say route A "cannot certify absence" because it shares the same weak representation and judge. It wants to test a system where Jev is not a mandatory rejection gate: local text and symbol search, optional semantic candidates and source reading, with Jev as a ranking or escalation aid that has to earn its place (section 2 decision 4, section 5.4).

**The evidence does not settle this.** The first opinion's design depends on a body-reading model recovering most non-Type-4 twins, drawn from clone-detection papers it says were mostly Java (caveats). The second opinion's drop-Jev design is, by its own account, a test to run, not a finding. (My judgment: they are compatible as test arms; the second opinion's arm D is roughly the first opinion's design. Running both on the same frozen needs settles it.)

### 3.3 How good is Cursor's semantic search evidence now?
- First opinion: the +12.5% accuracy from semantic search on top of grep is "verified; the number is correct but narrow." It reports a Hacker News claim that Cursor later stopped indexing, sourced to "AI says," and marks it "unverified" (section 2.1, caveats).
- Second opinion: Cursor's July 2026 engineering responses say models got better at grep and the dedicated semantic path "was no longer meaningfully helping." Current Cursor documentation describes local grep search and says codebase embeddings are not stored for search. It calls the 2025 result historical (section 5.1).

My judgment: the second opinion has more support here. It cites a team discussion and a current docs page, where the first opinion has only a source it flags as weak. I have not checked either. Treat the Cursor lead as dated.

### 3.4 Size of the first evaluation
- First opinion: about 400 needs (300 with known matches, 100 without), cost around $40 in route-A sweeps, 3 to 5 days (P0-2). It also runs a baseline on the same needs (P0-3).
- Second opinion: 80 to 120 needs for a first diagnostic pass, which it says is "not a 1% reliability certificate," plus a workflow pilot of 20 to 30 tasks with two or three fresh runs per arm, and a prospective sample of real fleet needs for prevalence (sections 7.2 and 8).

They answer different questions: the first sizes the set for a bound near 1%, the second sizes a first pass to find major failures. The second also warns that a bound only holds for independent cases, and paraphrases from one need are correlated (section 7.4). (My judgment: start small, and grow toward 300 labelled positives only if the checker survives the first look.)

### 3.5 Who is the truth-giver for labels?
- First opinion: a stronger model reading bodies labels, with 100 human-checked cases to calibrate it (P0-2, answer 7).
- Second opinion: "A stronger model proposes labels and candidates but is not the final truth oracle." It wants two blinded human reviewers on important disagreements and cases left explicitly unresolved when they are (section 7.2).

My judgment: the second opinion's stricter option fits the problem. The first opinion's F3 warns that if twins were found with the same embeddings or word index, the results are biased toward the current system. I suspect a model labeller carries a similar risk; neither expert says so. The cost is reviewer time, which the second opinion budgets (section 9).

### 3.6 Stop rule
- First opinion gives numbers: continue if the checker plus scripted grep reaches end-to-end recall of 0.90 or more on matched needs, beats grep-only by at least 10 points, and the "not sure" rate on no-match controls is 50% or less. Stop and rely on Claude Code search plus a review-time clone gate if the gain is under 5 points or recall stays under 0.75. In between, keep only the clone gate and an existence map and shelve the pre-write judge (answer 9).
- Second opinion gives no thresholds. It wants the minimum worthwhile difference worked out from the economics before anyone looks at the final results (sections 10.3 and 10.2).

They fit together: treat the first opinion's thresholds as a starting guess, fixed in advance from real costs as the second opinion says.

### 3.7 Background full sweep on every "no match"
The first opinion says it is cheap at $0.10, so do it with receipts (answer 3). The second opinion says a same-judge sweep "is diagnostic, not a cure" (answer 3). Both hold: it creates data but cannot find what the judge cannot recognize.

### 3.8 The shadow audit
- First opinion: defer the 1%-sampled audit as the primary evaluation, since its test set replaces it. Keep it later as a drift monitor, with a judge that differs from production (Part 4, "Drop / defer").
- Second opinion: wire it before any route-B rollout, and add a separate independent audit of NEW, no-match and abstained outcomes (rank 8, section 7.5).

They agree the audit alone is not enough. They differ on timing: the first puts it after the test set, while the second ranks it #8 (P1) and wants it wired before any route-B rollout.

## 4. What each expert said that the other missed

### 4.1 Only the first opinion
- **Direct evidence on unaided agents.** It cites RepoReuse (arXiv 2609.35357, September 2026): agents read 83.6% of relevant repository code at turn 1 and 35.4% by turn 5, and "even the strongest misses 24.3% of repository targets" that the requirement named (section 2.3). The second opinion does not cite this. It is a preprint and one source.
- **A practitioner count.** In six Codex runs on one task, only two found an existing component (section 2.3).
- **A confidence interval on the small sample.** Seventeen of 22 gives roughly 0.55 to 0.92 (F5).
- **Possible circularity in how twins were mined.** If twins came from the same embeddings or word index, the 90% code-like recall is inflated (F3).
- **A decision rule for "not sure."** Abstain whenever the chance a match exists exceeds the ratio of read cost to duplicate cost, which it estimates at 1 to 5% (answer 8). These are its estimates, and it says to measure the read time.
- **A conformal-risk recipe** for setting the Jev cut, which it expects to land far below 0.3, likely 0.05 to 0.1 (P1-3). That is its guess.
- **Index every live worktree,** and a governance rule: a recorded decision for each threshold or objective change (P2-3, P3-3). It traces the drift to three unrecorded steps (G1).
- **Latency, not dollars, is the cost that matters** at this size, and parallel Jev requests can cut it (section 1H).
- **More duplication studies,** such as Huang and colleagues (MSR '26): agent pull requests 1.87 times as redundant as human ones, in one repository with an unvalidated detector (Part 3).

### 4.2 Only the second opinion
- **Similarity is not safe reuse.** A similar function can be unusable because of contracts, side effects, async behavior or location (section 4.1; D20). The first opinion does not take up compatibility.
- **The judge sees less than retrieval does.** Retrieval uses the purpose line; the judge discards it. Passing it on is a cheap experiment (D6).
- **A taxonomy of where a match is lost,** in seven stages from "outside searchable scope" to "correctly reused" (section 7.3).
- **Different denominators for different claims.** False NEW given a match exists differs from risk among NEW answers. It also adds a workflow escape rate: tasks that merge with avoidable duplication even when the checker abstained, since universal abstention can score zero false NEW and still fail (section 7.1).
- **A cleaner baseline comparison.** Four arms: stock Claude Code, plus a bounded search procedure, plus the catalogue without a mandatory Jev gate, and optionally a calibrated Jev step. Paired tasks from identical snapshots (section 8).
- **A break-even formula.** Net value per task is the drop in harmful escapes times their cost, minus running cost, minus build cost spread over expected tasks. Its illustration, which it labels as assumptions: cutting escapes from 8% to 4% at $75 each, after about $1.03 per task of operating cost ($0.10 API, $0.83 human attention, $0.10 maintenance), would repay a $5,000 build in about 2,543 tasks (section 10.2).
- **Merge-time check against the latest target branch,** and a small registry of in-flight work if collisions are common (section 6.4).
- **Evidence on Jev, both ways.** TypeSafe says Jev 1.13 can be literal and struggle with indirection, and its API confidence differs from Lupin's locally defined maximum probability. A September 2026 benchmark (Deußer et al.) reports strong results and useful calibration for Jev on many classification datasets. TypedBench reports wording sensitivity and task-dependent calibration. None is a code-reuse test (section 5.4).
- **Counter-evidence on search baselines.** Kuba Rogut's 50-task comparison found stock Claude Code had the highest file recall, though a read limit confounds it (section 5.2). Agent Retrieval Bench found logged agents miss every gold file on 27 to 35% of samples (section 5.3).
- **Practical design points.** Accept structured intent and constraints, not one sentence (D10); split evaluation data by clone family and time (D17); report results by language and module (D22). The purpose line is, per the first opinion, fed to embeddings only (I2), so passing it to the judge is the second opinion's new experiment.
- **Not all duplication is bad.** Aim at avoidable harmful duplication (section 5.5).
- **Facts to verify first,** such as which route and band are live and whether agents read suggested sources (section 12).

## 5. One merged, prioritized action list

Costs are the experts' own estimates unless marked. Neither expert audited the Lupin code, and the second opinion says so (section 1).

**First, do these now (both experts agree):**

1. **Stop saying NEW.** Replace it with a scoped "no match found" result that says what was searched, what was not, and what the agent must do next.
   - Cost: 1 to 2 days (first opinion) or "small to medium" (second opinion).
   - Measure: every negative result carries its scope and exclusions, and the agent's final decision records that the search was completed.
2. **Build an independent test set.** Realistic prose needs (the first opinion has a strong LLM write them from the function body with identifiers banned; the second has a reviewer paraphrase independently without copying identifiers), hard positives, plausible no-match cases and mined twins, at a frozen snapshot.
   - Cost: 3 to 5 days and about $40 of sweeps (first opinion, sized at around 400 needs). The second opinion says 80 to 120 for a first pass, plus reviewer time.
   - Measure: where each match is lost, the false-NEW rate with its denominator, and the "not sure" rate on no-match cases.
3. **Measure plain Claude Code on the same needs.** Grep, glob and read only, with the prompt fixed in advance.
   - Cost: about 2 days and plan quota (first opinion). The second opinion's version is the arm comparison in 4.2, with 20 to 30 tasks and two or three runs per arm.
   - Measure: recall against the checker alone, grep alone and both together, plus harmful duplicates that reach merge.

**Next, in parallel:**

4. **Close the coverage holes:** keep sensitive-looking entries with only the sensitive part masked, add private and nested definitions, and tie the index to the current worktree and recent merges.
   - Cost: medium (second opinion, ranks 3 and 4); 2 to 4 days to index all worktrees (first opinion).
   - Measure: fixtures with sensitive text, renames and deletions stay discoverable; every exclusion is accounted for.
5. **Give the verifier the code.** First opinion: a stronger model reads the bodies of the top 20 to 30 candidates (about 10,000 tokens a check, 3 to 5 days). Second opinion: first try passing the purpose line to the judge, and test variants including no Jev (rank 5, section 5.4).
   - Measure: recognition on held-out needs, bounded reading cost, no loss in correctness.
6. **Add a review-time clone check:** a maintained token-based detector on each diff against the whole target tree, as a warning first. The first opinion includes other live worktrees; the second compares against the latest target branch.
   - Cost: 2 to 3 days (first opinion).
   - Measure: known clones found; new false alerts counted.

**After the test set exists:**

7. **Fix the band's scope** to the top few candidates (first opinion: top five, hours of work).
8. **Refit thresholds to the right error.** The first opinion proposes a recall-first cut; the second cautions that a very low cut floods agents with distractions, so measure usable evidence per task.
9. **Wire the shadow audit and add an independent audit of NEW and no-match outcomes,** including easy-looking confident negatives (second opinion, rank 8; the first opinion defers the audit, see 3.8).
10. **Test richer representations** (body, body with context, tests, generated descriptions) and an embedding adapter audit. The second opinion ranks this P1 (rank 7); the first opinion ranks query rewriting, richer entries and an embedding bake-off P2 (P2-1, P2-2, P2-4).

**Only if the measurements ask for it:** a reranker, a registry of in-flight work, a nightly refactor agent, learned retrieval (first opinion P3; second opinion ranks 10 and 11). The first opinion would also drop rank-fusion tuning.

**Budget.** The first opinion suggests about 2 engineer-weeks for its first two priority tiers (answer 9). The second opinion suggests 5 to 10 engineering days for a first tranche, plus budgeted adjudication and agent quota, and calls that a management limit rather than something derived from the literature (section 9). (My judgment: those two amounts overlap, so about two weeks is a reasonable ceiling for finding out whether any of this is worth continuing.)

## 6. The nine questions, side by side

Answers are condensed and kept close to each expert's own wording.

| Question | First opinion | Second opinion |
|---|---|---|
| 1. Is the cheap recall, small judge, fixed cut-offs design sound? | Not sound for minimizing false NEW at this size. Keep the full sweep as the recall stage, add body reading on a small top set, remove NEW. Do not start over. | Reasonable for finding candidates, not validated for certifying absence. Keep discovery infrastructure, change the negative-verdict authority, and test whether the judge adds value. |
| 2. Can a signature-and-docstring judge work? Body? Jev or a frontier model? | No. Jev is acceptable only as a recall filter with a low cut. Final calls need a frontier model reading code. Token clone detection is right at review time. | Metadata supports discovery but cannot resolve behavior missing from it. Verify against source. Compare richer-evidence Jev, a stronger code model and no Jev. No model class is established as needed. |
| 3. Should "write new" ever be a verdict? | Not now. It can return as NEW with a stated bound once the test set shows the 95% upper bound is at or below the chosen level. Run a background sweep anyway. | Remove unqualified NEW now. A scoped no-match is allowed after a defined search. Automated clearance later needs end-to-end validation, and a same-judge sweep is only diagnostic. |
| 4. Is about 70% a ceiling? | Mostly a property of this implementation. Do not expect over 95% from retrieval alone, which is why the sweep stays. | No ceiling is established. The sample and reference cannot support that claim. Audit representation, query, scope and embedding setup before widening lists. |
| 4a. Would more signal help? | Yes. Bodies, richer multi-sentence descriptions and rewritten queries are all expected to help. | Worth testing as separate representations, but check the embedding adapter for prefix and truncation defects first. |
| 5. Versus Claude Code grep and read? | Unknown for Lupin. The strongest agent in RepoReuse misses 24.3% of repository targets even when told they exist. Run the baseline. | Unknown locally. The leads are real but context-specific, and Cursor's current docs show a move away from semantic indexing. Run arms A, B and C. |
| 6. Evidence on AI duplication and what works? | Strongest for compact "what exists" maps and review-time clone detection, then LLM review with bodies. Pre-write lookup has no outcome evidence. | Concerns are established but not Lupin's rate or a causal ranking. Combine pre-write discovery with post-write clone checks and test each. |
| 7. How to measure false NEW? | Paraphrase probe, mined twins and no-match controls, labelled by an independent stronger model with 100 human checks. Zero misses in 300 gives about 1%. | Independently label realistic needs at a frozen snapshot with the right denominator. 299 independent eligible-positive needs with no misses gives just under 1%. |
| 8. False NEW versus "not sure"? | Set a cost for a surviving duplicate against a cost for a read. Abstain whenever the chance of a match is above roughly 1 to 5%. | Report both conditional error rates, abstention, adherence, reading cost and workflow escapes. Pick the best measured expected value. |
| 9. How much to invest and when to stop? | About 2 engineer-weeks, with numeric continue and stop thresholds fixed in advance. | A bounded first tranche plus a baseline comparison. Continue only for net benefit over structured native search and simple review checks, using thresholds set from the economics. |

## 7. Caveats

- Neither expert ran anything on Lupin. The first opinion's effect estimates are its own inference (Part 4 header). The second opinion calls its work a research review, not a source-code audit (section 1).
- The first opinion leans on clone-detection results from Java benchmarks (caveats). Several cited results are vendor reports or recent preprints; both experts say so.
- None of the citations was independently verified by the author of this synthesis.
- Open questions the first opinion put to the Lupin team: how the 14,001 negatives were sampled, and how the twins were mined.
