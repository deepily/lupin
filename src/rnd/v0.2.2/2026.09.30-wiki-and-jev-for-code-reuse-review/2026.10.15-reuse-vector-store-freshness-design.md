# Keeping the reuse vector store up to date

Rick asked (2026-10-15, on his yes to gate 476889ba) for a written plan so that the vectors stay current while the code base changes, with a daily rebuild or revisit built in from the start.

Every figure below is marked **measured** (with its run), **from the plan** (quoted from the candidate-stage plan), or **estimated**.

## 1. What the plan already says

| Item | What it says |
|---|---|
| R15 | One vector set only, the current state of the repo, no old sets, no fallbacks. Rebuilt as code changes, possibly daily. |
| Section 4.2a | A rebuild writes the new set beside the live one, then swaps by two renames. A lookup between the two renames gets `VECTOR_SET_UNAVAILABLE`, never a half-written set. |
| `VECTOR_SET_REPLACED` | A replay compares the receipt's manifest hash with the set on disk and refuses when they differ. |
| K3 | Stored vectors go stale after a model or INI change. The manifest hash is in `index_sha`, so a change is a new index generation. |
| K13 | A receipt replays only until the next rebuild. Stored Jev answers outlive the set. |

## 2. What is missing

- **No scheduler.** Nothing starts a rebuild. `candidate_build` is a manual driver; its own docstring says "It is not scheduled."
- **No incremental path in the vectors.** `build_vectors` embeds every entry's three texts (code, prose, concat) on every build. Purpose lines are already incremental (below); the vectors are not.
- **No staleness report.** `is_fresh` in the index builder says whether the *index* matches the tree. Nothing says how far the *vector set* is behind the index. I did not verify whether the vector manifest names the index generation it was built from; the proposal below adds it either way.

## 3. What is already incremental

- Purpose lines are stored per pin, where a pin is a hash of the entry's pin text (**read from `build.py`**). A stored row is never rewritten and a changed pin is written as a new row, the old row staying (**tested**, `test_a_changed_pin_is_rewritten_as_a_new_row_and_the_old_row_stays` in `test_candidates_purpose_lines.py`). A rerun sends no ids already stored (**tested**, `test_a_second_run_sends_no_ids_to_the_writer_and_replaces_a_leftover_new_folder`).
- A rerun after a failure continues from the stored lines. **Measured 2026-10-15** (logs in the build seat's scratchpad, section 4): run 1 of the batch-25 build stopped at 6,249 of 8,538 lines (TimeoutError on one batch, rc=1); the rerun resumed at 6,249 and the stored file held 6,274 lines 90 s later.
- So a daily purpose-line pass costs only the entries whose pin changed since yesterday.

## 5. Proposal

### 5.1 One scheduled job, daily, from the start

- A `reuse-vector-refresh` job runs once a day. It does three things in order: ensure the index, write purpose lines for pins with no stored line, rebuild the vectors and swap them in.
- **When.** The host is usually off from about 11 pm to 10 am EDT (root `CLAUDE.md`, "Scheduled jobs"), so a nightly time would run at boot, late. The job goes at or after 10 AM, next to the librarian tick (`librarian_tick.py`: cron `17 10 * * *`, first hour 10, installed through the shared crontab lock). The 1 PM upper bound comes from row b8fbd2f3's amendment, not from the tick's code.
- **How.** It is submitted through `/api/v2/submit` with `agent router go to claude code` and a top-level `scheduled_at`, so a run that lands while the host is off drains late and logs `[CJ-CATCHUP-LATE]`. Whether the librarian tick's installer or a second cron entry carries it is a choice for Cheech; I recommend the librarian's window and installer, so one crontab line covers both.
- **No change, no work.** If the index's manifest equals the one the vector set was built from and the INI and model are unchanged, the job ends with "fresh" and does nothing else.

### 5.2 Re-embed only what changed (incremental vectors)

- The set stores, beside the three matrices, a `row_texts.jsonl` of `{ id, text_hash }` for each of the three texts. A sidecar is not sealed for free: `vector_store.seal` hashes only `ids.txt` and the three matrix files, so this needs a `seal` change, a `load_vectors` check and its own corrupt-file test (Pocholo's review of this document).
- A rebuild loads the live sidecar and matrices, embeds only rows whose text hash is new, and copies the rest by row. The new set is still written whole to a temporary folder and swapped in by rename, so R15 holds unchanged.
- **Guard.** Reuse is allowed only when the engine revisions, device class, libraries and document roles in the live manifest equal the ones the new build would record. Any difference forces a full re-embed (this is K3 made mechanical).
- **Estimated** saving: embedding time proportional to changed entries instead of 8,538 rows times three texts. The figure to confirm is the measured embedding time of a full set (section 4).
- If this is judged too much for the first release, the daily full rebuild (5.1 alone) already satisfies Rick's "at the very least a daily rebuild", and 5.2 is a follow-up row.

### 5.3 What a reader sees during a rebuild

- The live set is read-only and keeps answering until the swap. The new set is built in `<vectors>.new`.
- The swap is two renames; in the gap a lookup answers `VECTOR_SET_UNAVAILABLE` (**from the plan**). The gap is two renames on one filesystem; I have not measured it.
- After the swap, a receipt made under the old hash replays with `VECTOR_SET_REPLACED` (**from the plan**, K13). Stored Jev answers stay.
- The query cache clears entries of other hashes at swap time (**from the plan**).

### 5.4 The shared projects-data copy

- Today's rule, Rick's yes of 2026-10-15 as Cheech relayed it by DM at 09:33 EDT (thread b49e7c6a, row 11e4bad4's context): copy finished vectors into `projects-data/lupin/reuse-review/vectors`, new files only, by a person.
- A daily refresh must replace files, which that rule does not cover, and a scheduled job writing to projects-data at all is also not covered. **These are decisions for Rick**, not assumed: either the daily job writes straight to the shared folder through the same rename-swap, or it writes to the seat/main `io/` folder and a person copies it.
- Whichever is chosen, the swap in the shared folder is the same two renames, so a reader there never sees half a set.

### 5.5 Detecting and reporting staleness

- The vector set gains `index_manifest` (the index generation it was built from) and `built_at`. Neither goes into the hashed manifest body: `manifest_hash` hashes the whole body today, so a time stamp in it would change the hash on every rebuild, end every replay window and clear the query cache even when no vector moved. Both go in a side file next to the set, not covered by `manifest_hash`; `index_manifest` is the one that might legitimately belong in the hash and is a decision for the reviewer.
- A `reuse_vector_status` check reports: vector set age, whether the index manifest differs from the set's, how many pins have no purpose line, and the last job's outcome and duration.
- It answers *stale* when the set is older than 36 hours (an **estimated** threshold: one missed day plus slack) or the index manifest differs and the next job is not due.
- The result is written to a small status file in the data folder and shown on the librarian's report; a stale answer files a store row, so a missed day is owed, not silent.

### 5.6 Failure behaviour

- A job that dies leaves the live set untouched and the stored purpose lines in place; the next run continues (**measured**, section 3).
- A bounded job that never answers raises `TimeoutError` after 1800 s (`JOB_TIMEOUT`). Run 1 of the batch-25 build stopped this way once. The daily job should retry the stalled batch once and then end with the failure named, never hang.
- A leftover `<vectors>.new` is replaced at the start of the next run (**tested**, `test_a_second_run_sends_no_ids_to_the_writer_and_replaces_a_leftover_new_folder`).
- One run at a time: a lock file in the data folder, so a manual build and the scheduled one cannot overlap.

## 6. What this does not decide

- The embedding time of a full set (owed from the batch-25 run).
- Whether the daily job writes to the shared folder directly (5.4, Rick).
- Whether incremental vectors (5.2) ship with the first scheduler row or after it.
- The size of the daily change set, which needs two index generations compared.
