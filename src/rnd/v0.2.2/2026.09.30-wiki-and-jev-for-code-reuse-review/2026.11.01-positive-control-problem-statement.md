# Problem statement: the positive control for our code-reuse checker failed, and the test may be biased

## 1. The question for you

We built a positive control to show that our code-reuse checker can find duplicated code. It found **5 of 17** planted pairs. Before we act on that number, we want your opinion on three things:

1. Is the control a fair test of the checker as it stands, or does the way we plant code hold it back?
2. If it is unfair, which fix gives a trustworthy result: change how planted code is indexed, change how the control is scored, or change what is planted?
3. What pass mark should a positive control like this have, and how should it treat pairs it could not set up?

Everything below is measured unless it is marked **not measured**.

## 2. What the checker does

A developer describes, in plain words, a piece of code they are about to write (a **need**). The checker looks for existing code in the repository that already does that job.

It works in two steps:

1. **Search.** The need is matched against an index of about 12,700 functions, methods and classes, in Python and TypeScript. Three ranked lists are built and merged into one shortlist of **128** candidates:
   - a **vector list**: an embedding of each entry's name, signature, docstring and a one-line purpose statement, compared with the embedding of the need;
   - a **code list**: word matching (BM25) against identifiers in the code;
   - a **prose list**: word matching (BM25) against the entry's docstring and purpose statement.
2. **Judge.** A language model (Fable 5.1) reads the shortlisted candidates and says which, if any, do the same job as the need.

## 3. What the positive control does

The control takes 20 pairs of code from an earlier labelled set. In each pair, an **original** function exists in the repository, and a **rewrite** was written by a model (Opus) to do the same job in a different way. All 20 are **work-alikes**: same job, different code, not copies. That is the hardest kind of duplicate to find. Of the 20, 8 are Python and 12 are TypeScript.

For each pair:

1. A model drafts a need from the **original**, describing what it does. A leak check rejects any draft that uses the original's own identifiers, so the need cannot be found by name alone. Each draft gets up to four tries.
2. The **rewrite** is added to the index as if it were real code.
3. The checker runs on the need. The pair counts as found if the checker returns the rewrite.
4. The rewrite is removed, and the index is checked to be unchanged.

The plan runs the control twice and stops the whole trial if any pair is missed.

## 4. Result (run -l, 2026-11-01, 18:50 to 18:54 EST)

| | pass 1 | pass 2 |
|---|---|---|
| Pairs drafted | 17 of 20 | 18 of 20 |
| Found | **5 of 17** | **4 of 18** |
| Python found | 1 of 6 | 1 of 6 |
| TypeScript found | 4 of 11 | 3 of 12 |

- The pairs that could not be drafted (3 in pass 1, 2 in pass 2) failed the leak check four times in a row.
- The two passes skipped different pairs and missed different pairs.
- The index was restored exactly after each pass.
- Because pairs were missed, the trial stopped as designed, before its last stage.

## 5. Where the misses happen

We replayed the run from its saved drafts, with no model calls, and got the same 12 misses as the live run.

**All 12 misses in pass 1 were lost at the search step.** In every case the rewrite never reached the 128-candidate shortlist, so the judge never saw it. The judge did not reject any planted rewrite.

| | rank in merged list | rank in vector list | rank in prose list |
|---|---|---|---|
| 5 found | 17 to 93 | 6 to 210 | never listed |
| 12 missed | 151 to 925, or not listed | 65 to 8,800 | never listed |

The vector list holds 12,713 entries; the prose list holds 12,615.

## 6. Why we think the control is biased

**The rewrites have no docstrings.** We parsed all 20: none carries a docstring or a JSDoc comment. That is how they were written for the earlier labelled set, which only compared code.

**So a planted rewrite can never appear in the prose list.** The prose list only indexes entries that have docstring or purpose text. The planted entries are built with an empty docstring and no purpose statement. In the replay, none of the 17 rewrites appears in the prose list.

**Nearly every real entry does appear in it.** The prose list holds 12,615 of the 12,713 entries, about 99%. So in the merged ranking, almost every real competitor gets votes from three lists, while the planted rewrite gets votes from two.

**The vector list is probably weakened the same way (not measured).** The vector text for an entry includes its docstring and purpose statement. For a planted rewrite both are empty, so its vector is built from little more than its name and signature. We have read the code that does this, but we have not measured the effect.

**Not the cause, as far as we can tell:**
- *Vague needs.* The 17 drafted needs are 26 to 39 words and name three to six concrete behaviours each. The leak check replaced the repository's own words with synonyms (for example "slider" became "range-picker"), but kept what the code does.
- *Word overlap.* Counting the words each need shares with its rewrite's name and signature does not separate the 5 found from the 12 missed.
- *An earlier dry run* found 17 of 20, but its stand-in needs read "Code that does what [the original's name] does". They carried exactly the identifiers the leak check forbids, so they are not comparable.

## 7. What we are not sure of

- How much of the shortfall the missing prose list explains. Real undocumented code is also absent from the prose list, so 5 of 17 may be partly a fair picture of how the checker treats undocumented code.
- Whether 17 work-alike pairs are enough to judge the checker. A positive control usually uses easier, unmistakable cases; ours uses the hardest kind.
- Whether the control should score its search step and its judge step separately.

## 8. Options we are considering

| Option | What changes | For | Against |
|---|---|---|---|
| A. Give each rewrite description text | Write a docstring and purpose line for each rewrite, as real code has, then rerun the control (about 160 model calls) | Planted code competes on the same three lists as real code | We would be writing text that helps the checker find the rewrite; it could make the control too easy |
| B. Score without the prose list | Rerun with the prose list left out of the merge for every entry, real and planted | No new text is written; the comparison is level | It tests a different checker from the one in use |
| C. Plant documented code | Choose pairs whose rewrites carry docstrings, or rewrite from documented originals | Closest to real use | New pairs, new drafting, and the earlier labels no longer apply |
| D. Accept the result | Treat 5 of 17 as the checker's recall on undocumented work-alikes and finish the trial | No more work | Overrides the trial's stop rule on a result we believe is biased |

We lean towards A, with a check on the risk in its "against" column. We would like your view before choosing.
