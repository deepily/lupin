# Building a 400-item test set of "this code already exists" cases: is our way of sourcing the hard cases sound?

*A problem statement for a reviewer. Lupin project, 31 October 2026. Requested by Rick Ruiz; drafted by Cheech.*

## 0. What we are asking you

We are about to build a test set (we call it **Set B**) and want you to attack how we plan to source its hardest items before we spend roughly 9,000 model calls on it. The seven questions are in §6. Everything before them is the context you need to answer them; nothing here is settled beyond criticism.

## 1. The project in two paragraphs

AI coding agents often write a function that already exists elsewhere in the codebase. We built a **reuse checker**: before an agent writes new code, it describes what it is about to build in one sentence, and the checker searches the codebase and tells the agent whether something already does that job. A model (the "judge", Fable 5.1) rules whether a candidate does "the same job".

The question that decides the whole project is whether agents with the checker write measurably fewer duplicates than agents without it. That is answered by an experiment (agents build the same features with and without the checker; p < 0.05 fewer duplicates means continue, otherwise stop). Set B is **not** that experiment.

## 2. Two test sets, and how they relate

| | **Set A**, the proof set | **Set B**, the 400-need set |
|---|---|---|
| What it tests | The **duplicate counter**: the tool the experiment uses to count duplicates in each arm | The **reuse checker**: does it find the existing code for a given need? |
| An item | Two functions, A and B: do they do the same job? | One plain sentence of a need, plus the existing code that meets it (or "nothing exists") |
| Size | 222 pairs | 400 needs |
| Decides | Whether the counter is trusted (a pass bar of 0.80 on recall and precision, 0.90 on self-agreement) | **Nothing.** It is a diagnostic |
| Status | Labelled by two people; a third rater settles 47 disputes | Not built. This document is about building it |

**The link between them is one finding, not shared items.** No pair from Set A becomes a need in Set B. But Set A's labels showed us how people judge "same job" on the hardest kind of item, and that is the evidence behind the sourcing question in §4.

## 3. What Set B is for, and what "the draw" is

Set B does three things the experiment cannot:

1. **Explain a "no benefit" result.** For each need it finds the first step where the match was lost: the search did not return the right code, the judge did not rate it relevant, the agent did not read it, or the agent did not rule it the same job.
2. **Give a miss rate with a bound.** If all 300 needs with a known answer are found, the miss rate is under about 1% at 95% confidence.
3. **Check whether recent checker fixes find more.**

**"The draw"** is the step that builds it. We pick seed functions from the codebase, and a model writes a one-sentence need for each, never naming the answer. The answer key is the seed and anything else that does the same job. A second model checks every key, and people label a selected subset.

| Kind | Count | What makes it hard |
|---|---|---|
| Near-copies | 150 | Easy to source; code looks alike |
| **Work-alikes** (same job, different-looking code) | **150** | The case the checker exists for, and the hardest to source |
| Nothing exists | 100 | The checker must say "nothing" |

About 60% TypeScript and JavaScript, 40% Python.

## 4. The problem: where do 150 work-alikes come from?

A work-alike need is one whose existing answer does the job in code that does not resemble the obvious implementation. Natural ones are rare.

**What we measured (pilots, 26 October 2026, each capped at 500 judge calls):**

| Source | Calls | Work-alikes found | Calls per key |
|---|---|---|---|
| Mined from real Python | 563 | **0** | undefined (at least ~190, since the rule of three bounds the yield below 3 in 563) |
| Mined from real TypeScript | 500 | 5 | ~100, so ~15,000 calls for 150 |

**The current plan (Rick's ruling, 29 October), a mix:**
- **About 90 TypeScript work-alikes mined from real code**, about 9,000 calls at the pilot rate.
- **About 60 Python work-alikes written by a model** (synthetic): a model writes a function from a one-sentence description of an existing one, without seeing it.
- Every synthetic key is checked by a person, and the report gives results for the two sources separately.

**Why the synthetic part worries us (measured 31 October, on Set A's 20 synthetic work-alike pairs):**

| Measure | Value |
|---|---|
| Two independent people agreeing "same job or not" | 70% (Cohen's kappa 0.29; 0.54 over all 222 pairs) |
| Pairs one of the two marked "unsure" | 6 of 20 for each person, against 0 to 8 of 97 in every other group |
| Pairs **both** marked unsure | 1 |
| Pairs both people ruled **not** the same job (the generator drifted) | 3 of 20 |
| One person's agreement with themselves, labelling the same 20 again blind a day later | 12 of 20 |

So synthetic work-alikes are hard for people to judge, and the difficulty is spread out, not concentrated in a few bad items.

**What we have added since (rulings of 31 October):**
- **A run-check** before any synthetic Python key reaches a person: the original and the work-alike are run on the same generated inputs, isolated, and a mismatch rejects the key. Keys that cannot be run go to the person with that reason.
- **Call sites** shown beside each item, so a reviewer sees what callers need.
- **A worked-examples sheet** for Set B's reviewers.

## 5. Constraints

- The draw is machine time on a fixed-cost plan, not per-token spend. Days of calls are acceptable; weeks are not.
- Two people label Set B. Its plan uses **confirm mode**: 20% of the selected items are labelled blind by both, and on the rest the second person sees the first person's label and confirms or disputes it. Kappa is reported on the blind 20% only.
- Set B decides nothing, so its rigour is a judgement call. A weak key set would undercut the miss bound, and the miss bound is the one number from Set B anyone might quote.
- Language and source always go together: every TypeScript work-alike is mined, and every Python one is synthetic.

## 6. Questions for you

1. **Is the mixed source acceptable?** A gap between Python and TypeScript results cannot be told apart from a gap between synthetic and mined keys. Is reporting the two separately, and saying so, enough? Or should we mine all 150 from TypeScript (about 15,000 calls) and give up the 60/40 language mix for work-alikes?
2. **Can synthetic keys be trusted after a run-check and a person's check?** Rejected keys get redrawn, so the survivors may lean toward the easy cases. How would you measure or bound that selection effect?
3. **What does a kappa of 0.29 on work-alikes mean for using "same job" as ground truth there?** Should Set B's work-alike stratum carry its own agreement figure and interval, or a different labelling question, such as a short checklist of inputs, results and side effects?
4. **Is confirm mode rigorous enough here?** Seeing the first label anchors the second person. Given how unstable work-alike judgements are, should the work-alike stratum be labelled fully blind by both, even though the set decides nothing?
5. **Is 150 the right number?** The plan wants work-alikes because they are the case that matters most. Would fewer, better-checked work-alikes (say 60, all fully blind) serve the diagnostic better than 150 with a sourcing compromise?
6. **Where does a synthetic key live?** A need's answer must be code that already exists in the index the checker searches. A model-written Python work-alike exists nowhere until we put it there. So "synthetic keys" really means planting new functions into the searched codebase, as the proof set does, and then asking whether the checker finds the planted copy. Does planting make Set B a test of a doctored codebase rather than the real one? Would you plant at all, or confine synthetic work-alikes to the proof set and mine every Set B work-alike? (Found 31 October by the engineer building the tooling: the current draw has no stage where a synthetic key could go.)
7. **What would you have us measure first?** If you were spending the first 1,000 calls, what would you want them to tell you before we commit the rest?
