# Experiment build task: feature list (draft)

*25 October 2026. Phase 4 step 1 of the reuse remediation plan (§7.2). Written from the behaviour of the pages and API at `d9851f5b3` (`src/lupin_app/static/html/auth/*`, `notifications.html`, `src/docs/fastapi/api.json`). Items marked **Rick decides** are choices the plan leaves open; each has a recommendation and nothing is silently defaulted.*

## 1. What the build task is

Each run builds a TypeScript web client from an empty client folder, against today's server frozen at one commit. This list says what a user sees and does. It does not say how the client is organised.

### Rick decides

| # | Question | Recommendation | Why |
|---|---|---|---|
| R1 | **Which slice of the client?** Today's client has about 20 pages (notifications with fleet board, epic board, TTS, admin, multiplexer, document viewer). A run capped at 10 working days cannot rebuild all of it | **Slice A: sign-in pages plus a notifications inbox** (features F01 to F14 below) | It exercises forms, a live socket, lists, filters, deletes and a response card, so duplicate helpers have room to appear (formatting, API calls, error display, list rendering). Every feature runs with no model call, no voice and no second service, so the tests are deterministic. The May to June client the plan scores as a sanity check was a notifications UI, so the slices are comparable |
| R2 | Optional features, marked **(opt)** below (F13, F14) | Include them | They are the heaviest features; they raise the chance a run needs the cap rather than finishing early. Drop them if the pilot shows the slice is too large (the plan's 10-day guard) |
| R3 | **Exact visible labels.** Labels in F09 to F14 that no page has today (`Connected`, `No notifications yet`, `Senders`, `All senders`, `Delete conversation`, `Answered: yes`, `Answered: no`, `Priority`, `Any priority`) are my inventions, because today's notifications page is a different, much larger layout. The auth labels are copied from today's pages. The tests find elements by visible text and ARIA role, never by test id or CSS class. With an empty client folder, the label wording is therefore part of the contract | Fix the labels in the "Visible text" column below, copied from today's pages where a page exists today | Without fixed wording, a correct client could fail a test over a synonym |

## 2. Conventions

- **Base URL** is the run's own server. All pages live under `/app/...` as today.
- A "signed-in user" means a registered account holding a valid session. Sessions persist across page reloads.
- Priority is one of `low`, `medium`, `high`, `urgent`, as the server's notify endpoint defines.
- Text in `code` is the exact visible text. Matching ignores case and surrounding whitespace.

## 3. Features

Feature ids are stable. The acceptance tests cite them (`@pytest.mark.feature( "F03" )`), and a unit test checks that every id here is cited at least once.

### Sign-in pages

| Id | Feature | What the user sees and does | Visible text | Server calls |
|---|---|---|---|---|
| F01 | **Register** | Page `/app/auth/register` titled `Create Your Account`, fields `Email Address`, `Password`, `Confirm Password`, a list `Password must contain:` with five requirements (`At least 8 characters`, `One uppercase letter`, `One lowercase letter`, `One number`, `One special character (!@#$%^&*)`), button `Create Account`. Each requirement is marked met as the user types (a visual change only; the acceptance tests check that the five lines are listed, not how they are styled). On success the page says `Account created successfully! Redirecting to login...` and goes to the login page after about 2 seconds | as listed | `POST /auth/register` |
| F02 | **Register: refusals** | Empty fields: `Please fill in all fields`. Bad address: `Please enter a valid email address`. Weak password: `Password is too weak. Please meet all requirements.` Mismatch: `Passwords do not match`. An address already registered shows the server's refusal. No request is sent for the first four | as listed | `POST /auth/register` |
| F03 | **Log in** | Page `/app/auth/login` titled `Welcome to Lupin`, fields `Email Address`, `Password`, button `Login`, link `Register`. Success goes to the page named by a `redirect` query value that starts with `/app`, else to `/app` | as listed | `POST /auth/login` |
| F04 | **Log in: refusals** | Empty fields: `Please enter both email and password`. Wrong credentials: `Invalid email or password. Please check your credentials and try again.` A refused login leaves the user on the page, signed out | as listed | `POST /auth/login` |
| F05 | **Protected pages send a visitor to log in** | Opening `/app/notifications` or `/app/auth/profile` with no session lands on the login page with `redirect` set to the page asked for; after a successful login the user arrives there | none | `POST /auth/login`, `POST /auth/refresh` |
| F06 | **Profile** | Page `/app/auth/profile` titled `Your Profile` shows the signed-in user's email, user id, roles, email-verified state and account status, with buttons `Change Password` and `Logout`. A user without the admin role sees no `ADMIN ACCESS` section | `Your Profile`, `Change Password`, `Logout` | `GET /auth/me` |
| F07 | **Change password** | Page `/app/auth/change-password` titled `Change Password`, fields `Current Password`, `New Password`, `Confirm New Password`, buttons `Update Password` and `Cancel` (back to the profile). Refusals: `Please fill in all fields`, `New passwords do not match`, `New password must be different from current password`, `Password does not meet requirements. Please check the list below.`. After success the new password logs in and the old one does not | as listed | `PUT /auth/change-password` |
| F08 | **Log out** | `Logout` on the profile ends the session and goes to the login page. Going back to a protected page asks for a login again | `Logout` | `POST /auth/logout` |

### Notifications inbox (page `/app/notifications`)

| Id | Feature | What the user sees and does | Visible text | Server calls |
|---|---|---|---|---|
| F09 | **Inbox list** | A region named `Notifications` lists the signed-in user's notifications, each row showing sender, message text and priority. Order is newest first by creation time, whatever the priority (the server's default order puts urgent first, so the client must ask for or apply creation order). An empty inbox says `No notifications yet` | `Notifications`, `No notifications yet` | `GET /api/notifications/{user_id}` |
| F10 | **Live arrival** | While the live channel is open the page shows the text `Connected`; the tests wait for it before sending. A notification sent to the user while the page is open appears in the list within 5 seconds with no reload | `Connected` | WebSocket queue channel, `POST /api/notify` (the sender's side) |
| F11 | **Senders list and filter** | A list `Senders` names each distinct sender with the number of notifications. Choosing a sender narrows the inbox to that sender; choosing `All senders` restores it | `Senders`, `All senders` | `GET /api/notifications/senders/{user_email}`, `GET /api/notifications/conversation/{sender_id}/{user_email}` |
| F12 | **Delete one, delete a conversation** | Each row has a button `Delete`; it removes that notification, and a reload does not bring it back. With a sender chosen, a button `Delete conversation` removes every notification from that sender | `Delete`, `Delete conversation` | `DELETE /api/notifications/{notification_id}`, `DELETE /api/notifications/conversation/{sender_id}/{user_email}` |
| F13 (opt) | **Answer a question** | A notification sent with a request for a yes or no answer shows its message with buttons `Yes` and `No`. Pressing one records the answer, marks the card `Answered: yes` or `Answered: no`, and disables both buttons. A reload still shows it answered | `Yes`, `No`, `Answered: yes`, `Answered: no` | `POST /api/notify/response`, `GET /api/notifications/awaiting-response` |
| F14 (opt) | **Priority filter** | A control named `Priority` with options `Any priority`, `Low`, `Medium`, `High`, `Urgent` narrows the list to that priority | `Priority`, `Any priority` | `GET /api/notifications/{user_id}` |

## 4. Out of scope for this build task

Everything else the current client does: the multiplexer and console pages, fleet status, the epic board, task lists, job submission forms, text to speech and microphone input, the admin pages, the document viewer and the audio player. Also not in scope: email verification and password reset pages.

## 5. Open points that need no decision

- `POST /api/push` and its sibling job endpoints answer "GONE" today; the slice does not use them.
- The server's notify endpoint takes its fields as query parameters. The acceptance tests call it from the test process (the sender side), with an API key the harness provides. That key's name is a Phase 5 harness detail.
- The role-based pieces (F06's absent `ADMIN ACCESS` section) assume the test account is an ordinary user.
