# Which entries should Jev be asked about when we check for existing code: all of them, the nearest by embedding, or the best by a fixed ranking of our own symbol index?

2026.10.14 · Rachel, for Rick · follows [the request-shape problem statement](2026.10.07-jev-reuse-sweep-request-shape-problem-statement.md) and feeds [the packed-request plan](2026.10.07-jev-reuse-sweep-packed-request-plan.md)

This document states the problem, the options and the evidence we hold. It does not research the options and it makes no recommendation.

**B reopens a ruling.** The implementation plan's row E13 asked whether to put a local embedding shortlist (about the top 200) in front of the Jev sweep, and was ruled **no on 2026-09-30, per the spec**, which leaves embeddings and a vector store out on purpose. The cons recorded there: a second index that can go stale; a recall risk exactly where duplicates hurt (same behaviour, different vocabulary); and embedding all the entries sends the same text to a second vendor. The row's own alternative was a pre-filter only, with recall checked against the full sweep. Path: `src/rnd/v0.2.2/2026.09.30-wiki-and-jev-for-code-reuse-review/2026.09.30-reuse-review-implementation-plan.md`.

## 1. What we need to decide

The reuse lookup answers one question before anyone writes new code: **"does something like this already exist in our repository?"** Today it asks Jev about every entry in the index, about 8,187 of them in the last run, for every need. Measured on 30 needs with the cut-offs in force, **10 needs in 30 flip between repeats (33%)**, or 6 of 30 (20%) on verdict alone. Candidate cut-offs that are not shipped, chosen on the same 30 needs, flip 3 of 30 (10%) (section 4).

The decision: **how the entries that Jev judges are chosen.** Three options:

| | what picks the entries Jev judges | origin |
|---|---|---|
| **A. Today** | Nothing. Jev scores every entry in the index | built and run live |
| **B. Embeddings pick, Jev judges** | Embeddings and word search over the index, fused into one ranking. Jev then judges the top 128 to 512 | Rick's original position, in his words in the voice request of 2026-10-14 about 12:28 EDT recorded in row 2886510e. Described in full by the Option 2 write-up of 2026.10.07 (not in git, see section 5). Not built. **It reopens ruling E13** (below) |
| **C. Fixed symbol-index ranking first, Jev on the shortlist** | A ranking function of the index's own fields (names, module path, signature, first docstring line). No embedding model. The same need and the same index always give the same order | proposed in the conversation of 2026.10.14. Not built |

## 2. The task

- **Input**: a short plain-language description of the code someone is about to write (the "need").
- **Catalogue**: the symbol index, one entry per public function, class and method. 8,185 entries in the old-question run and 8,187 in the new-question run. Language counts for those runs were not taken. The index built today at 13:36 EDT in the main checkout holds 8,428 entries: 6,298 Python (`.py`) and 2,130 tagged `lang=ts`, which are 1,186 `.ts` entries and 944 `.js` entries (the extractor tags JavaScript files `ts`). It holds no Dart. Each entry is an id, a signature and the first docstring line, with a pin (a hash of the code with comments removed) and its module path. The index is built by `src/cosa/repo/symindex/` and grows with the code.
- **Output**: one of four verdicts for the caller (reuse, extend, write new, "uncertain, read the source"), and for us a shortlist of at most 10 entries with scores.
- **Who calls it**: developers and coding agents, possibly many times a day.

## 3. What option A does today

- **Candidate stage**: none. Every entry is judged.
- **Request shape**: packs of 50 entries per request, so about 164 requests per search. Each entry carries its own question inside its pack, and the need is sent with every request.
- **Question**: the "new question" asks whether the candidate already provides the capability, and a coverage level (how much of the need it covers). The "old question" was a three-way choice (reuse, extend, unrelated) that we sum into an overlap.
- **Verdict rule** (`src/cosa/repo/symindex/verdict.py`, decision table in `README-reuse-decision-table.md`): a few cut-offs on those scores decide which entries make the shortlist and which verdict is returned. The values in force for the new question by default are reuse 0.7, shortlist threshold 0.5, uncertainty floor 0.3, coverage 0.5.
- **Replay**: every answer is cached by the hash of its request, so a verdict replays offline from the cache. The cut-offs are not in the key, which is why the cut-offs can be re-tried offline at no cost.
- **Wiki route**: built, and measured once. A page-first route asks about about 62 capability pages, then only the entries those pages cover. It lost about a quarter of the shortlist hits on the old question (John's close-out table). It is not one of the three options here.

## 4. What we have measured

All figures are John's close-out of the W-A work, dated 2026-10-14, read from `projects-data/lupin/wa-john-2026.10.14/2026.10.14-john-plan2-wa-closeout-table.md` and the replay results in the same folder (not in git; see section 5). The runs were 30 needs, 5 repeats each, pack 50, model `jev-1.13.0`, all on option A.

**Latency and cost per search** (one need against the whole index):

| question | searches | wall median | wall max | tokens median | dollars at $0.042 per million |
|---|---|---|---|---|---|
| old, full sweep | 125 | 7.0 s | 21.9 s | 1.84 M | 0.077 |
| new, full sweep | 125 | 8.1 s | 13.1 s | 2.45 M | 0.103 |
| page route, old question | 95 | 1.3 s | 1.8 s | 0.018 M | 0.001 |

At 1,000 searches a day the new question costs about $103 a day (arithmetic from the median, not a measured day). The slowest search of any run was 21.9 s (old question; the new question's slowest was 13.1 s) against a 60 s budget. Not measured: a busy fleet and other worker counts. The 21.9 s outlier is unexplained.

**Flip rate** (a need is "flipped" when two of its five repeats disagree; 95% Wilson interval):

| question | cut-offs | strict rule: verdict or shortlist differs | verdict only |
|---|---|---|---|
| old | default | 21 of 30 (70%) | 1 of 30 (3%) |
| new | default | 10 of 30 (33%, 0.19 to 0.51) | 6 of 30 (20%, 0.095 to 0.373) |
| new | candidate cut-offs: threshold 0.6, floor 0.4 | **3 of 30 (10%, 0.035 to 0.256)** | 3 of 30 (10%) |

What those figures say:

- The plan's gate is 5%. **No rule or cut-off met it on 30 needs.** The best is 3 of 30.
- The candidate cut-offs were chosen on the same 30 needs they are scored on, so 3 of 30 is in-sample.
- Thirty needs cannot show 5% anyway: even zero flips gives an upper bound of about 11%, and a bound under 5% needs at least 73 flip-free needs.
- The three needs that still flip at the best cut-offs each have a best score that sits on a cut-off and moves by 0.03 to 0.05 between repeats. Moving the cut moves which needs sit on it.
- Re-asking near-cut entries three times and taking the median gave no gain in simulation (2.8 against 2.9 flips of 30).
- Moving the cut-offs bought fewer flips at a price: "uncertain, read the source" rose from 31 to 50 of 150 searches.

**Pair baseline** (2026-10-06, from the request-shape statement): for 376 members with a known duplicate, the known twin ranked first for 337 (89.6%) and was in the top ten with overlap over 0.5 for 183 (48.7%).

**Not measured**: any live number for B or C; how often the true match falls outside a 128 to 512 entry shortlist for any ranking; how many of the flipping entries a first stage would have left out.

What the two untracked documents say that bears on this decision:

**The expert's response** recommended a flat sweep of the whole catalogue in packed form and parked the area-first route. On a first stage it says a gate is worth considering only "somewhere around 50K–100K entries, or when daily spend or rate headroom says so", and that even then it would use "a cheap non-Jev recall stage (BM25 or embeddings over signatures)" before areas. Its own labels mark that as inference, not documentation. It also notes that thresholds have to be re-fit on labelled pairs whatever the shape.

**The Option 2 write-up** (its header reads "Oct 7, 2026 · @Richard P Ruiz") describes B in full. Its own summary says to ship the flat sweep first and to build the embedding stage behind a flag, promoted only once a shadow audit shows a stage-1 miss rate under 1% (95% upper bound). It does not put B first.

- Offline, per entry: enriched text (signature, docstring, module path, split identifiers), a one-sentence "purpose line" written by a cheap model from the first 30 lines of source (regenerated only when the source hash changes), two embedding vectors and a word index.
- At query time: three ranked lists fused by reciprocal rank fusion, K = 128 widening to 512, then Jev judges only those entries, then the top 3 and any uncertain entry are re-asked with more source.
- The guarantee changes from "we asked everything" to a measured recall bound printed on every receipt. A "write new" verdict is allowed only if the stage-1 miss rate at that K has a 95% upper bound under a target (proposed 1%).
- A shadow audit: about 1% of live queries also get the full sweep, and any entry Jev rates above the reuse threshold that stage 1 ranked below K counts as a miss.
- Its estimates (not measured): about $0.001 to $0.003 per search against $0.04 to $0.14 for a flat sweep, and 1 to 2 s.

## 6. The three options side by side

| | A. Today | B. Embeddings pick, Jev judges | C. Fixed symbol-index ranking, Jev on the shortlist |
|---|---|---|---|
| Entries Jev judges per search | all 8,187 | 128 to 512 | not set; K would be set by measurement |
| Needs a model to pick entries | no | yes, an embedding model, plus a model that writes purpose lines | no |
| New things to maintain | none | embedding model pin, index snapshot, purpose lines, shadow audit | the ranking function and its word lists |
| Replay inputs | request body | body, entry hashes, embedding model version, index snapshot hash, K | body, entry hashes, ranking version, index hash, K |
| Can miss an existing match | no | yes, at a measured rate | yes, at a measured rate |
| Closes the gap between prose needs and code names | not needed | through purpose lines and vectors | **open**: a fixed ranking sees the need's words, not its meaning |
| Cost per search | $0.10 measured | $0.001 to $0.003 estimated | set by K; not estimated |
| Same bytes in, same order out | not applicable | yes if the model and snapshot are pinned | yes by construction |
| Non-Python entries | yes | yes, if embedded | yes, the index holds them |
| Built | yes | no | no |

What C could use from the index today: identifiers split on underscores and capitals, module path, kind, signature, argument and return names, the first docstring line, and the pin. A variant of C writes purpose lines once, offline, by any model, freezes them as plain text and ranks them with ordinary word statistics. That takes the model out of the replay path but leaves a maintained artifact.

## 7. What is known and not known about flips

Known (measured, section 4):

- A flip is a need whose best score sits on a cut-off and moves across it between repeats.
- Re-asking does not remove it. Moving the cut-off trades flips for "uncertain" verdicts.

A first stage (B or C) does not move a cut-off. It changes which entries are judged. Whether that changes the flip rate has not been measured. Two things are different under a first stage: which near-cut entries are in view, and whether a true match is dropped. A flip shows itself on repeat; a dropped match does not.

## 8. Questions for the expert

1. **Is a first stage the right lever at 8,187 entries?** On the new question option A costs $0.10 and 8.1 s median per search, and its slowest search was 13.1 s (the old question's slowest was 21.9 s). At what catalogue size or daily volume would you add one, and is ours one of those?
2. **B or C?** For a prose need against code entries with a one-line docstring, how much recall does a fixed ranking over names, paths and docstrings give up against embeddings plus purpose lines? Is there published evidence on code search with short docstrings?
3. **Frozen purpose lines**: if the purpose lines are written once and frozen, does ranking them with plain word statistics keep most of B's recall and drop the embedding model from the replay path?
4. **Recall target**: the Option 2 write-up asks for recall at K = 128 of at least 0.98 and a 95% upper miss bound of 1%. Is that the right bar for an advisory lookup, and how many labelled needs does it take to show it? Zero misses in 300 audited queries gives about 1%.
5. **Where do the other flips come from?** Our three stubborn needs each have a best score sitting on a cut and moving by 0.03 to 0.05. Is a band of "always uncertain" around a cut a sound fix, or does it only move the flip to the edge of the band, as our simulation suggests?
6. **Is Jev's score noise near a cut a property of the model?** The 2026-10-08 pack-size run measured a 0.02 noise floor for 99 entries in 100. John's flip-rate plan records, read from a day summary and not measured on the new question, that the old question's flipping entries sit about 0.02 from a cut and move about 0.09 between repeats. Is there anything to record or ask differently to narrow it?
7. **Wiki pages as one signal**: pages as a gate lost a quarter of the shortlist hits. Would a page id as one more ranking feature, not a gate, help B or C?
8. **What would you record** on every response that we are not recording?

## 9. How we would test the answer

Most of this needs no live call, because every entry's answer for the 30 flip needs is already cached for 5 repeats.

| step | what we do | live calls | what we record |
|---|---|---|---|
| T1 | For each of the 30 needs, rank the index by C (and by B, once embeddings exist), keep the top K for K in 32, 64, 128, 256, 512 | 0 | recall of the full-sweep shortlist at each K, per ranking |
| T2 | Replay the cached answers for only those K entries and recompute verdicts at the default and the candidate cut-offs | 0 | flip rate with its interval, verdict agreement with the full sweep, entries the first stage dropped that the full sweep had on its shortlist |
| T3 | Rank the 376 known-twin members' purpose lines (or paraphrases of them) against the index | 0 | where the twin lands, by language and by ranking |
| T4 | Run the confirmation on the 30 fresh needs, for the option that survives T1 to T3 | yes, about 430 M tokens, about $18 at 5 repeats and the full sweep (John's estimate). John's 75-need run, which would reach a bound near 5%, is about 982 M tokens and $41 | flip rate, tokens, dollars, latency, and the miss count against a full sweep on a sample |

Rules for the test:

- T1 to T3 use the same 30 needs the cut-offs were chosen on, so they are in-sample. They rank the options against each other. They do not give the final flip rate.
- The fresh needs were written under a brief that barred opening any Jev output, cache or result file. They are reserved for T4 and must not be used to pick K or the ranking. They are in `io/tmp/2026.10.14-wa-fresh-needs-30.json` of the author seat and, by copy, in `projects-data/lupin/wa-john-2026.10.14/`, neither in git.
- A first stage may only return "write new" if no shortlisted entry was left unasked and its measured miss rate at that K is under the stated bound. This keeps the existing "no silent gaps" rule.

## 10. Constraints

- **Determinism and replay.** A receipt must replay to the same verdict. The first stage must be replayable too: same need and same index give the same shortlist. For B that means a pinned embedding model and an index snapshot hash on the receipt.
- **Pinned model.** `jev-1.13.0` for judgment. A second model (embedding or purpose lines) is a second pin.
- **No silent gaps.** The number of entries not asked must be on the receipt, and a partial failure must never read as "unrelated".
- **Independent scores.** A candidate's score must not depend on which entries share its request. In the 2026-10-08 run, packs of 10 and 50 passed the steadiness tests that ran and packs of 200 failed two. The run's formal verdict is inconclusive: it found 69 borderline entries against the 90 the plan required. Position dependence was not tested at 10 or 50, and sizes between 50 and 200 were not tested.
- **Cost matters more than time.** 8 s is acceptable. Thousands of paid searches a day by agents may not be.
- **Languages.** Entries in every language the index covers need a path to the shortlist: Python, TypeScript and JavaScript today (6,298 `.py`, 1,186 `.ts` and 944 `.js` entries in the 13:36 index), and the extractors also read Dart. The page route reaches only Python.
- **Growth.** The index grows with the code. A fixed ranking needs no re-training; embeddings need a re-embed when the model changes.
- **Private data.** Index entries and pinned text pass `sendable()` and `c1_hits` in `src/lupin_mcp/reuse_tools.py` (patterns for emails, URLs, paths and credentials) before they are sent. No screen on the need string was found in `_need_impl` or `_run_question`, so the need goes to Jev as typed. Whether that is acceptable is open.
