# Is Jev the right judge for "no claim lost" and R&D triage?

2026.09.30 · María, for Rick · feeds decision D3 in the docs-rewrite plan

## 1. What we need to decide

We are rewriting about 1,900 Python docstrings and triaging about 1,000 design documents in a mid-sized codebase (about 335,000 lines of Python plus a Dart mobile app). Two steps need a model acting as a **judge**, not as a writer. We want to know whether Jev can do either judging task accurately, repeatably, at the volume below, and inside our data rules, or whether a general LLM (Claude) is the better fit.

The expert does not need our codebase to answer. Section 6 lists the questions.

## 2. Task A: claim-preservation judging (the main question)

A writer model (Sonnet by default, possibly Haiku) rewrites each docstring to a style standard. That standard asks for shorter text, one idea per sentence, no history and no emphasis, and it lets history move out to a linked design doc. The danger is that a rewrite **silently drops a fact** a caller relies on.

The check runs in three steps.

1. **Extract.** A model lists the atomic claims in the old docstring as JSON, each with a verbatim quote of its source span. Code verifies that each quote really occurs in the old text, and discards any claim with an invented quote.
2. **Judge.** For each claim, a yes/no: *"Does the new text, or the design doc its `Design:` line points to, state this claim?"* Confident answers pass. Uncertain ones escalate to a stronger model (Claude Opus).
3. **Report.** Every claim judged dropped is listed. The rewrite's author must restore it or label it "history, moved to <doc>".

What Task A needs from the judge:

- **The input is three pieces of natural language plus code.** They are the claim (one sentence), the new docstring (5 to 40 lines, often with Requires / Ensures / Raises sections), and sometimes a linked Markdown design doc (up to a few thousand words).
- **The output is yes, no or uncertain,** with a confidence we can threshold.
- **This is paraphrase-tolerant entailment, not string overlap.** "Returns None when the row is parked" must match "A parked row yields None". It must **not** match "Handles parked rows".
- **Accuracy target:**
  - The key number is the **false-pass rate**: a dropped claim judged as still present.
  - We measure it on at least 180 before/after pairs, of which at least 60 have one claim deliberately removed by someone who did not see the extractor's output.
  - The target is **0 misses in 60**, which puts the 95% upper bound at 4.9%. Our fallback is an upper bound at or below 10%.
- **Repeatability:** the same claim list is judged 3 times, and we want at least 95% agreement, both overall and on the seeded removals alone.
- **Volume:** about 3,800 calls for Phase 5 (one extractor call and one judge call per docstring, with claims batched per call).

## 3. Task B: R&D document triage

For each of about 1,000 Markdown design and research documents (dated plans, reviews and post-mortems), classify it as **current** (still describes how the system works or should work) or **history** (superseded or finished). The model is given the document plus signals we compute: its age, whether any live file cites it, and whether the code it names still exists.

- **Hard rule, enforced outside the model:** a document that a live file still cites is never history.
- **Validation:** the model's labels are checked against an earlier hand census, whose 15 held and 2 restored documents must not come out as history. A blind second reviewer also samples each class.
- **Volume:** about 995 whole-document calls, some documents several thousand words long.

## 4. What we already know about Jev

We know this only from our own design notes. Please correct anything wrong.

- We plan to use Jev (model id `jev-1.13.0`) in a **different** role: code-reuse search. Given a described need, it sweeps one-line summaries of every public function and returns reuse / extend / unrelated with a confidence, and anything under 0.9 means "read the source".
- In that role its inputs are short: a signature plus the first docstring line. Our data rule allows only that much of our code to leave the machine.
- A CMU study we were pointed to reports **96 of 96 identical decisions** on repeat runs.
- The client we planned returns **overlap scores, not a yes/no**, so either task here would need its own adapter.
- Our original spec named Jev as the claim judge, with Opus for uncertain answers. The implementation plan switched the default to Claude through Claude Code on a fixed-cost plan, for two reasons: cost at this volume, and data. Task A sends full docstrings and design prose, far more than the reuse search sends.

## 5. Constraints

- **Data leaving the machine:** Task A sends full docstrings and design-doc text, and Task B sends whole documents. Both need Rick's explicit approval under the same exclusion-list process as the reuse search: no credentials, no personal data, and an agreed list of excluded paths.
- **Cost:** the Claude path is effectively fixed-cost (a subscription with a quota). A per-call price for Jev at about 4,800 calls, with inputs of 1 to 10 KB, decides whether Jev is competitive.
- **Throughput:** the sweep is planned at about 11 packages a day for 7 days. Judge latency above a few seconds per call would stretch it.
- **Determinism:** we cannot set temperature on the Claude path, so we measure agreement instead. If Jev is deterministic, that is a real advantage for replayable receipts.

## 6. Questions for the expert

1. Is Jev built or tuned for **entailment between a claim and a passage** (Task A), or only for similarity and ranking of code summaries? Does it have a yes/no or three-way mode with a calibrated confidence?
2. How does it handle **long inputs** (a 40-line docstring plus a 3,000-word linked doc), and what is the input limit?
3. Is there any published or internal accuracy figure on paraphrase entailment, especially the **false-positive rate** (saying "still stated" when it was dropped)?
4. Is it **deterministic** at a fixed model version? Does the 96/96 result carry over to longer, prose-heavy inputs?
5. Is it suited to **document-level classification** (Task B), or is that outside its design?
6. **Price and throughput** at about 4,800 calls with 1 to 10 KB inputs. Is there a batch mode?
7. **Data handling:** retention, training use, and whether an on-premises or no-retention option exists. That would change what Rick can approve.
8. If Jev is a fit for one task only, which one?

## 7. How we would test the answer

If the expert says yes to Task A, we run Jev and Claude side by side on the same 180-pair labeled set during the pilot (Phase 2). We compare false-pass rate with its upper bound, agreement over 3 runs, latency and cost. Rick picks D3 from those numbers. Nothing is sent to Jev until Rick approves the data exclusion list.
