# How the test VM gets its first reuse vector set (proposal, not run)

Scope item 5 of row d3550878. Nothing here has been run. The VM has no `<DEEPILY_DATA_DIR>/lupin/reuse-review` folder, so the nightly refresh has nothing to refresh until a first set exists.

## Recommended: let the refresh job build it on the VM, once, by hand
1. Land and deploy this branch (`lupin-vm.sh deploy` now also refreshes the VM's planning-is-prompting).
2. `lupin-vm.sh push-test-mock-login vm`, then `lupin-vm.sh install-refresh-cron vm`.
3. Build now instead of waiting for 10:47: `lupin-vm.sh run "cd /mnt/lupin-data/lupin && LUPIN_ROOT=/mnt/lupin-data/lupin DEEPILY_DATA_DIR=/mnt/lupin-data/projects-data PLANNING_IS_PROMPTING_ROOT=/mnt/lupin-data/planning-is-prompting REUSE_VECTOR_REFRESH_ENV=\$HOME/.lupin/reuse-vector-refresh.env bash src/scripts/reuse-vector-refresh.sh --force"`.
4. Watch `refresh/refresh.log` and `refresh-state.json` under the VM's `reuse-review` folder; success is `last_outcome` not `failed` and a vector set beside it.

Pros: the same code path cron will use, so the first run proves the install. Cons: it needs the key `reuse vector refresh enabled` true on the VM, the VM's :7999 up (purpose lines are written by bounded Claude Code jobs), and the first run writes every purpose line, which can take an hour or more.

## Alternative: copy dev's built set
Archive dev's `reuse-review` folder and unpack it on the VM. Pros: instant, no job spend. Cons: the freshness check compares the index manifest and engines, so a set built on dev's tree and engines is rebuilt at once if either differs, and nothing proves the VM can build.

Recommendation: the first. Run it during a VM window when no :8000-style test run is scheduled.
