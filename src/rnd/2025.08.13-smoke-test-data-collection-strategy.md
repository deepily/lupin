**Date**: 2025.08.13  
**Purpose**: Define diagnostic-first approach to smoke testing for comprehensive system analysis  
**Status**: Active  
**Author**: Claude + Ricardo

## Executive Summary

This document establishes a data collection methodology for Lupin smoke testing that prioritizes comprehensive diagnostic information gathering over immediate problem resolution. The strategy ensures we have complete system state visibility before attempting any remediation work.

### Core Principle: **Observe First, Fix Later**

All smoke test execution follows a strict **data collection mode** where:
- Tests run to completion regardless of failures
- All output is captured to timestamped log files
- No remediation attempts are made during test runs
- Analysis and planning occur after complete data collection

---

## Data Collection Philosophy

### Why Data-First Approach?

1. **Complete Picture**: Individual test failures may be symptoms of larger systemic issues
2. **Pattern Recognition**: Multiple failures often reveal common root causes
3. **Priority Assessment**: Not all failures are equally critical
4. **Resource Efficiency**: Fix root causes rather than individual symptoms
5. **Baseline Establishment**: Create reliable reference point for system state

### What We Don't Do During Collection

❌ **No Real-Time Fixes**: Never modify code based on test failures during execution  
❌ **No Test Interruption**: Let all tests complete even if early tests fail  
❌ **No Environment Changes**: Don't restart services or modify configurations  
❌ **No Immediate Investigation**: Don't deep-dive into failures during test runs  
❌ **No Assumptions**: Don't assume failure causes without complete data  

### What We Do During Collection

✅ **Comprehensive Logging**: Capture every detail of test execution  
✅ **Error Documentation**: Record complete stack traces and error contexts  
✅ **Timing Measurement**: Track performance metrics for all tests  
✅ **State Capture**: Document system state at time of failures  
✅ **Pattern Observation**: Note recurring themes without immediate action

## Execution Strategy

### Standard Data Collection Command

```bash
cd /mnt/DATA01/include/www.deepily.ai/projects/genie-in-the-box

# Create logs directory structure
mkdir -p src/tests/logs

# Generate timestamp for unique log file
TIMESTAMP=$(date +"%Y%m%d_%H%M%S")
LOG_FILE="src/tests/logs/smoke_test_execution_${TIMESTAMP}.log"

# Execute complete test suite with full output capture

./src/tests/run-lupin-smoke-tests.sh 2>&1 | tee -a "${LOG_FILE}"

echo "===========================================" | tee -a "${LOG_FILE}"
echo "Data collection completed at $(date)" | tee -a "${LOG_FILE}"
echo "Log file: ${LOG_FILE}"
```

## Log Analysis Framework

### Immediate Post-Collection Analysis

#### 1. Quick Statistics Generation
```bash
# Extract basic test counts from log file
grep -c "✅\|❌" "${LOG_FILE}"
grep -c "✅" "${LOG_FILE}"  # Pass count
grep -c "❌" "${LOG_FILE}"  # Fail count
```

#### 2. Failure Pattern Recognition
```bash
# Extract all error messages
grep -A 5 "❌\|ERROR\|FAILED" "${LOG_FILE}" > failures_summary.txt

# Identify common error types
grep -o "ConnectionError\|TimeoutError\|AuthenticationError\|ValidationError" "${LOG_FILE}" | sort | uniq -c
```

#### 3. Performance Analysis
```bash
# Extract timing information
grep -o "([0-9]\+\.[0-9]\+s)" "${LOG_FILE}" | sort -n
```

### Failure Categorization System

#### Error Type Classification

**Category 1: Infrastructure Failures**
- Server connectivity issues
- WebSocket connection failures
- Network timeouts
- Service unavailability

**Category 2: Authentication Failures**
- Token validation errors
- Session management issues
- User routing problems
- Permission denials

**Category 3: Functional Failures**
- API endpoint validation errors
- Data format inconsistencies
- Business logic failures
- Integration issues

**Category 4: Performance Issues**
- Response time exceeding thresholds
- Memory or resource constraints
- Concurrent operation failures
- Throughput limitations

#### Priority Scoring System

**Priority 1 (Critical - Fix Immediately)**:
- Complete system unavailability
- Authentication system failure
- Data corruption or loss
- Security vulnerabilities

**Priority 2 (High - Fix Within 24 Hours)**:
- Core functionality broken
- Performance severely degraded
- User experience significantly impacted
- Integration points failing

**Priority 3 (Medium - Fix Within Week)**:
- Non-critical features failing
- Edge case handling issues
- Minor performance degradation
- Documentation inconsistencies

**Priority 4 (Low - Fix When Convenient)**:
- Cosmetic issues
- Nice-to-have features failing
- Minor optimization opportunities
- Test infrastructure improvements

## Best Practices

### Data Collection Discipline

1. **Never Skip Collection**: Always run data collection before attempting fixes
2. **Complete Runs Only**: Don't stop tests early even if obvious problems exist
3. **Preserve Raw Data**: Keep original log files, create copies for analysis
4. **Document Context**: Note any environmental factors affecting test runs
5. **Timestamp Everything**: Use consistent timestamp formats for easy correlation

### Analysis Methodology

1. **Start with Patterns**: Look for common themes before individual failures
2. **Prioritize by Impact**: Fix issues affecting the most tests first
3. **Consider Dependencies**: Some failures may be cascading effects
4. **Validate Hypotheses**: Test root cause theories before implementing fixes
5. **Measure Progress**: Re-run collection after fixes to validate improvements

### Communication Guidelines

1. **Data-Driven Discussions**: Use actual test results to support decisions
2. **Share Raw Data**: Provide log files for team review and validation
3. **Document Assumptions**: Make problem analysis reasoning transparent
4. **Track Progress**: Update reports as remediation work progresses
5. **Celebrate Improvements**: Acknowledge progress in pass rates and performance

## Troubleshooting Data Collection

### Common Collection Issues

#### Test Runner Not Found
```bash
# Verify test runner exists and is executable
ls -la src/tests/run-lupin-smoke-tests.sh
chmod +x src/tests/run-lupin-smoke-tests.sh
```

#### Server Not Running
```bash
# Check FastAPI server status
curl -f http://localhost:7999/health || echo "Server not responding"

# Start server if needed (but note this in log)
echo "Starting FastAPI server for testing" | tee -a "${LOG_FILE}"
./src/scripts/run-fastapi-lupin.sh &
sleep 5
```

#### Log Directory Issues
```bash
# Ensure logs directory exists with proper permissions
mkdir -p src/tests/logs
chmod 755 src/tests/logs
```

#### Incomplete Output Capture
```bash
# Use unbuffered output for real-time logging
python3 -u ./src/tests/run-lupin-smoke-tests.sh 2>&1 | tee "${LOG_FILE}"
```

### Validation of Data Collection

#### Verify Complete Capture
```bash
# Check log file completeness
tail -5 "${LOG_FILE}" | grep -q "completed\|finished\|Summary" || echo "WARNING: Log may be incomplete"
```

#### Validate Test Coverage
```bash
# Ensure all expected test categories ran
grep -c "notifications\|audio\|queues\|websockets" "${LOG_FILE}"
```
