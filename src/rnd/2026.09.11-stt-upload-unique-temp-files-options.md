# 2026.09.11 — Unique, transient temp files for the speech upload doors

**Row**: `27bcdd79` (P1, Rick) · **Author**: Mr. Radio 🦉 · **Measured**: 2026-09-11 ~13:20–13:35 EDT, code unchanged between `0cac7d44` and `1e0028dd`
**Status**: options for Rick's ruling — nothing built

## The verdict

Only one of the two doors has the bug. The MP3 door writes every recording to one fixed file on the host
disk and never deletes it; the WAV door already writes a unique `/tmp` file and cleans it up.
**Recommend C + B**: one `tempfile.mkstemp` helper for both doors (user + timestamp + random suffix,
uniqueness guaranteed by the operating system rather than by hash odds), in a small `tmpfs` mount so a
leftover from a crash is gone at the next container restart.

## What is there today

| | MP3 door — `/upload-and-transcribe-mp3` | WAV door — `/upload-and-transcribe-wav` |
|---|---|---|
| handler | `upload_and_transcribe_mp3_file` in `src/cosa/rest/routers/speech.py` | `upload_and_transcribe_wav_file`, same file |
| where it writes | `$LUPIN_ROOT` + INI `path to audio recording file` = **`/io/recording.mp3`** | `save_upload_to_temp` → `/tmp/{uuid4}-{client filename}` |
| unique per request | **no** — one name for every user | yes |
| deleted afterwards | **never** | yes, on success, CUDA OOM and other exceptions |
| on which disk | `io/` is bind-mounted, so the **host disk** | container-local `/tmp` |
| user known | optional (`get_optional_user`, may be `None`) | no user dependency at all |

Four measured facts the options rest on:

1. **The last spoken question stays on disk.** Host `io/recording.mp3` was 150,026 bytes, mtime
   2026-09-11 12:56:44 — the most recent MP3 upload, kept indefinitely.
2. **The MP3 overwrite race is latent, not live.** `main.py` runs one uvicorn worker, and between the
   synchronous write and `provider.transcribe` (a synchronous `requests.post` to the model server) there is
   no `await`, so a second request cannot run in between. It goes live the day that call is awaited or
   offloaded to a thread, or `workers` rises above 1. The same fact has a second cost: the event loop is
   blocked for the length of every MP3 transcription (not measured under load).
3. **"Deleted at reboot" is not true inside the container.** `lupin-rest-dev` has no tmpfs
   (`HostConfig.Tmpfs` empty); it was created 09-04 and restarted at host boot 09-11 10:02 EDT, and its
   `/tmp` still held files dated 2026-05-29, 07-01 and 08-16. Container `/tmp` clears only on recreate.
4. **The model server never sees the path.** In model-server mode the provider reads the file and posts
   the bytes as multipart (`speech_to_text_provider.py`, `files = { "audio": ( basename, bytes, … ) }`).
   So the temp file only has to exist inside the `lupin-rest` container — but its **basename is sent to
   the model server**, which matters for what goes in the name.

The WAV door has one weakness of its own: the client-supplied filename is concatenated into the path.
Not driven; `uuid4` is a prefix, so it cannot collide, but a filename carrying `/` is still written
into the path unchecked.

## The options

### A — MP3 door gets a unique `/tmp` name and a `finally` delete

Copy the WAV door's shape: `/tmp/{uuid4}.mp3`, removed in `try/finally`.

- ✅ smallest change; fixes the shared name and the host-disk leftover
- ❌ two doors, two helpers; nothing names the user or the time, so a leftover cannot be traced
- ❌ a crash between write and `finally` (process killed) still leaks into a `/tmp` that is not cleared at restart (fact 3)

### B — A tmpfs mount for the upload directory

`docker-compose.yml`: `tmpfs: [ "/tmp/lupin-stt:size=256m,mode=1777" ]` on the rest services. Combine with A or C.

- ✅ this is the only option that makes Rick's "gone at reboot" true — memory-backed, empty at every container start
- ✅ a size cap bounds the damage from a leak
- ❌ compose change needs `docker compose up -d --force-recreate`, not a restart
- ❌ costs RAM while a file exists (an MP3 question is ~150 KB; WAV is larger — the largest WAV upload is not measured)
- ❌ on its own it fixes nothing: the MP3 door still writes to `io/`

### C — One `mkstemp` helper for both doors (recommended)

```python
def save_audio_upload( content: bytes, user_id: Optional[ str ], suffix: str ) -> str:
    os.makedirs( STT_UPLOAD_DIR, exist_ok=True )
    user_slug = ( user_id or "anon" )[ :8 ]
    stamp     = datetime.now().strftime( "%Y%m%dT%H%M%S" )
    fd, path  = tempfile.mkstemp( dir=STT_UPLOAD_DIR, prefix=f"{user_slug}-{stamp}-", suffix=suffix )
    with os.fdopen( fd, "wb" ) as f:
        f.write( content )
    return path   # caller removes it in try/finally
```

A name looks like `50c73ba7-20260911T133012-k3x9q2wa.mp3` — Rick's user, timestamp and small hash.

- ✅ **uniqueness is guaranteed, not probable**: `mkstemp` opens with `O_EXCL`, so two requests in the same second cannot land on one name even if the random part collided
- ✅ one helper, one cleanup shape, both doors; the client filename stops reaching the path
- ✅ a leftover names who and when
- ✅ uses the **user id prefix, not the email** — the basename travels to the model server (fact 4) and sits in `ls` output
- ❌ the WAV door has no user today; it would need `get_optional_user` added (small, but it touches the endpoint signature)
- ❌ still leaks on a hard kill unless paired with B

### D — No file at all: hand the bytes to the provider

- ✅ nothing to name, nothing to delete
- ❌ changes the `SpeechToTextProvider.transcribe` contract, which takes a path
- ❌ model-server mode already reads bytes, so it would be easy there; local mode hands `whisper_pipeline` a path, and whether that pipeline accepts raw bytes here is **not measured**
- ❌ largest change for the least additional safety over C + B

## Recommendation

**C + B**, then delete `io/recording.mp3` and retire the INI key `path to audio recording file` (and its
splainer entry) once nothing reads it — a caller census of that key is part of the build, not assumed here.

Separately, and not part of this row: fact 2's blocked event loop is worth its own row if Rick wants
transcription offloaded — and offloading it is exactly what would make the old race live, so it must land
after this fix, never before.
