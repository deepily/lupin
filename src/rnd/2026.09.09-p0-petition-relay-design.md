## 1. The actual gap

The refusal the server already sends says:

> *"A manager may petition for it; no manager, override or emergency path sets it directly (Rick, broadcast `e254ec7d`)."*

**That petition path does not exist.** Every seat that hits this wall is instructed to do something it has no mechanism for. This is not a feature to invent — it is an unbuilt promise in an error message.

⇒ So the question is **not** "how do seats file P0s" — they must not. It is **"how does a petition reach Rick?"** Today a refused P0 silently becomes a P1 indistinguishable from an ordinary manager filing, and Rick gets no signal that he asked for something and the system said no. That is what he felt this morning: he ordered two P0s by voice and got two P1s, with nothing marking that he had asked.

## 3. Why the build is small: the machinery already exists

The **admission** refusal already has exactly the shape the **priority** refusal needs, and nobody wired the two together.

| piece | state |
|---|---|
| `task_promotion_tickets` table | built |
| `task_promotion_resolver.py` — `resolve_ticket`, `_apply_resolution`, stalled-sweep, startup reconcile | built |
| `task approval promotion ask asynchronous = True` | live |
| `task_promotion_status` MCP verb — the come-back-later read | built |
| admission asks Rick, returns `202` + ticket, applies on his answer | **already works this way** |
| the **priority** path wired into any of it | **missing — this is the entire gap** |

⇒ The work is *"route the priority refusal into the machinery the admission refusal already uses"*, not *"build a petition system"*.

## 4. Design

### 4.1 Where it fires

`refusal_for_priority_create` and `refusal_for_priority_change` currently return a refusal string. Neither takes `authority`, which is why María's `authority="user_direct"` probe produced an identical 403 — **the relay concept exists in the verb's vocabulary and never reaches the function that refuses.**

The change: when the requested priority is P0 **and** the caller is a manager **and** the call declares `authority="user_direct"`, the door does not refuse. It **mints a petition ticket** and answers `202` with the ticket id, exactly as an asynchronous admission does today.

A worker still gets the flat refusal. A manager not claiming a relay still gets the flat refusal. **The petition is the only new door and it leads to Rick, not around him.**

### 4.2 🔴 The hole this must not reopen, named by the existing code

`TransitionIntent`'s own docstring is the warning:

> *"WHAT IS DELIBERATELY ABSENT: the caller's account identity, and therefore the ask-exempt decision and the manager decision… Persisting a resolved authorization decision and replaying it later makes it forgeable by anyone who can write this JSON."*

⇒ **The ticket must never carry "Rick approved this."** It carries the *request*. The authorization is decided at resolve time, from Rick's actual answer, by the resolver — never replayed from the payload.

`authority="user_direct"` is caller-declared and therefore **proves nothing**. It is not evidence and must not be treated as any. Its only job is to *route* — to say "this caller is claiming a relay, so ask the operator" instead of "refuse flatly." **The claim is never trusted; it is escalated.** That is the whole safety argument for this design, and if a later change makes `authority` grant anything on its own, `b8205986` is reopened.

### 4.3 One approval, two effects

`TransitionIntent` today carries a status transition and no priority. Per Rick's ruling it gains a priority field, and `_apply_resolution` applies both changes in one transaction:

- priority → `P0`
- status → out of `not_approved`, onto the owner's board

**One ticket, one keypress, one atomic write.** A partial application — raised but not admitted, or admitted but not raised — is the worst outcome available, because it is the invisible-work state twice over.

### 4.4 On refusal

Per Rick's ruling: **the row stays P1 and stays in holding.** No transition is applied. The ticket records the refusal and the reason.

⚠️ Recording the cost he accepted: a declined petition lands in the holding area, which is the pile we spent this morning triaging. That is the correct trade — *a no on the urgency is not a no on the work* — but it means declines accumulate somewhere that already needs sweeping.

## 5. Scope — what this does NOT touch

`caller_is_operator( account_email )` also gates **won't-fix**, **demote** and **un-park**. All three are left exactly as they are. Rick was told this explicitly and did not widen it.

⇒ Anyone extending the relay to those verbs is making a **new** decision and needs Rick's word for it. The argument that "the P0 relay was approved" does not carry, because each of those doors was closed for its own reason — `wont_fix` in particular is what stands between the ratio gate and a mint-by-deletion loop.

## 6. Acceptance

1. A manager declaring `authority="user_direct"` on a P0 create receives a `202` + ticket id, not a 403.
2. A **worker** attempting the same still receives the flat refusal — the petition is a manager's door.
3. A manager **not** declaring a relay still receives the flat refusal.
4. Rick's approval applies priority **and** admission in **one transaction**; neither can land alone.
5. Rick's refusal leaves the row at P1 in `not_approved`, with the reason recorded on the ticket.
6. 🔴 **The ticket payload contains no authorization decision.** A test asserts the persisted JSON carries no approval field, and a mutation arm proves the assertion bites — this is the `b8205986` regression guard and it is the most important test in the set.
7. `task_promotion_status` answers for a priority petition exactly as it does for an admission.
8. 100% lines/branches/functions on every file touched.

## 7. What I have not established

Unread; it is the first thing to check in implementation.
- **Whether `_apply_resolution` can currently write a priority at all**, or only a status. I read `TransitionIntent` and the resolver's surface, not the write itself.
- **Whether an existing test pins `TransitionIntent`'s field set** such that adding one reddens it. Likely and fine — but it should be found, not discovered.
