Implementing Role-Based JWT Authentication in FastAPI

Overview of JWT Authentication and OAuth2 Patterns

FastAPI supports OAuth2 authentication flows out-of-the-box, which we can leverage to implement our own JWT-based auth system. The idea is to issue short-lived JWT access tokens (e.g. 15-30 minute lifespan) for regular API requests, and longer-lived refresh tokens (e.g. 7 days) that can obtain new access tokens without forcing the user to log in again ￼ ￼. This mirrors OAuth2 “refresh token” workflows, providing a better user experience (persistent login) while maintaining security ￼. We will use standard libraries instead of reinventing low-level functionality – for example, using PyJWT (or its alternative python-jose) for token encoding/decoding, and Passlib for secure password hashing ￼. A lightweight SQLite database can be used in development to store user data and refresh tokens, keeping things simple.

Key objectives and best practices: We will implement role-based access control (RBAC) by assigning roles to users and embedding those roles in JWTs or database records. We’ll ensure passwords are hashed (never stored in plain text) and tokens have expiration claims. However, we will not focus on advanced hardening (like MFA, account lockout, or request rate limiting) as these are beyond our current scope. Instead, we’ll cover the fundamentals of JWT auth: secure password storage, token generation with expiration, refresh token handling, and role-based authorization checks.

Project Setup and Dependencies

To get started, install FastAPI and the necessary security libraries:

```
pip install fastapi uvicorn PyJWT passlib[bcrypt] python-multipart
```

	•	FastAPI – the web framework
	•	Uvicorn – ASGI server to run FastAPI
	•	PyJWT – JWT encoding and decoding (JSON Web Tokens)
	•	Passlib[bcrypt] – for password hashing (using bcrypt)
	•	python-multipart – needed if using form data for login (e.g. OAuth2 password flow)

These libraries cover the heavy lifting for us. For instance, PyJWT will handle the JWT creation and verification using a secret key and algorithms like HS256, and Passlib will manage hashing passwords with bcrypt (a secure one-way hash) ￼. This means we don’t have to implement cryptographic functions ourselves – “no need to reinvent the wheel,” as you noted.

We’ll also set up some configuration variables for our app, such as the JWT secret key and token expirations. FastAPI can use Pydantic settings or environment variables for this. For example, we might define:
	•	SECRET_KEY – a random secret string used to sign JWTs (keep this safe and out of source code).
	•	ACCESS_TOKEN_EXPIRE_MINUTES = 30 (for a 30-minute access token lifespan).
	•	REFRESH_TOKEN_EXPIRE_DAYS = 7 (for a 1-week refresh token lifespan).
	•	ALGORITHM = "HS256" (HMAC-SHA256 algorithm for JWT).

These could be stored in a config class or .env file. For instance:

```
SECRET_KEY = "your-secret-key"  # ideally read from env
ACCESS_TOKEN_EXPIRE_MINUTES = 30
REFRESH_TOKEN_EXPIRE_DAYS = 7
ALGORITHM = "HS256"
```

This mirrors common secure defaults ￼. In a real app, you’d generate a strong random secret (FastAPI example uses secrets.token_urlsafe(32) for a 32-byte key ￼) and load it from an environment variable.

Defining the User Model and Password Hashing

User Model: For RBAC, our user data should include a role or list of roles. In a simple design, each user could have a role field (e.g. "user", "admin", etc.), or multiple roles. Using Pydantic models (or an ORM model), we might define a User schema with fields like id, email, hashed_password, is_active, and roles (perhaps as a list of strings) ￼. For example:

```
class UserInDB(BaseModel):
    id: int
    email: EmailStr
    full_name: Optional[str] = None
    hashed_password: str
    roles: List[str] = ["user"]  # default role
    is_active: bool = True
```

Here, every new user by default gets the “user” role, and we can assign “admin” or other roles as needed. Roles will be used later to restrict access to certain endpoints.

Password Hashing: When creating or updating users, always hash passwords before storing in the database. We can utilize Passlib’s context with bcrypt for this. For example:

```
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def get_password_hash(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)
```

This uses bcrypt under the hood. The get_password_hash function returns a salted hash of the plaintext password, safe to store in the DB, and verify_password checks a plaintext password against the stored hash ￼. By using Passlib, we follow best practices for password security (strong hashing algorithm and automatic salting) ￼.

In a development setup, a SQLite database (via SQLAlchemy or even just a simple dictionary for initial testing) can store users. Each user record might include their hashed password and roles. For example, a quick in-memory fake DB could be:

```
fake_users_db = {
    "alice@example.com": {
        "id": 1,
        "email": "alice@example.com",
        "hashed_password": get_password_hash("alicepassword"),
        "roles": ["user"],
        "is_active": True
    },
    "admin@example.com": {
        "id": 2,
        "email": "admin@example.com",
        "hashed_password": get_password_hash("adminpassword"),
        "roles": ["admin", "user"],
        "is_active": True
    }
}
```

In production, you’d use a real database and ORM models, but this illustrates the structure.

Generating Access and Refresh Tokens

With PyJWT, we can create JWTs signed with our SECRET_KEY. We’ll generate two types of tokens during authentication:
	•	Access Token: Short-lived (e.g. 30 min) JWT that contains the user’s identity (and possibly their roles or other claims) and an expiration time. This is included in the Authorization: Bearer <token> header for each protected request.
	•	Refresh Token: Longer-lived (e.g. 7 days) JWT used only to fetch new access tokens. We will not send this with every request; instead, it’s stored securely and used to call a special refresh endpoint when the access token expires. The refresh token can have a claim (like "token_type": "refresh") to distinguish it from access tokens ￼.

Let’s write helper functions to create these tokens:

```
import jwt  # PyJWT
from datetime import datetime, timedelta

def create_access_token(subject: str, roles: list, expires_minutes: int = ACCESS_TOKEN_EXPIRE_MINUTES) -> str:
    expire = datetime.utcnow() + timedelta(minutes=expires_minutes)
    to_encode = {
        "sub": str(subject),         # subject (could be user ID or email)
        "exp": expire,               # expiration time
        "iat": datetime.utcnow(),    # issued at
        "roles": roles               # embed roles in token
    }
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

def create_refresh_token(subject: str, expires_days: int = REFRESH_TOKEN_EXPIRE_DAYS) -> str:
    expire = datetime.utcnow() + timedelta(days=expires_days)
    to_encode = {
        "sub": str(subject),
        "exp": expire,
        "iat": datetime.utcnow(),
        "token_type": "refresh"
    }
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
```

In these functions, the payload (to_encode) includes standard JWT claims: sub (subject) identifies the user, exp is the expiry datetime, and iat is issued-at time. We also include custom claims: a list of user roles in the access token, and a "token_type" in the refresh token ￼. The roles claim will let us enforce RBAC without a database lookup on each request (since the token itself carries the role info) ￼.

Notice that the refresh token function sets a longer expiration (7 days by default) and tags the token with "token_type": "refresh" ￼. This helps to ensure refresh tokens are only used in the refresh flow.

Security tip: Use a strong, random SECRET_KEY and keep it secret. The HS256 signing ensures tokens can’t be altered by clients. Also, by giving access tokens a short life, we limit the window an attacker can abuse a stolen token. The refresh token’s longer life is balanced by the fact that we can store and revoke it on the server side (see next section) and it’s not used as widely as the access token ￼.

Storing and Verifying Refresh Tokens

Even though JWTs are usually stateless, in this design we’ll store refresh tokens in a server-side database table (e.g. a refresh_tokens table or as a field on the user record). This is a safety measure: it lets us revoke refresh tokens (for example, if a user logs out or if a token is suspected compromised) by deleting or invalidating the stored token. A self-contained JWT refresh token on its own can’t be revoked early – you’d otherwise have to wait until it expires ￼. Storing it server-side gives us control: the system can check the DB to see if a presented refresh token is still valid.

What to store: You can store the refresh token string itself, or for extra security, store a hash of it. Storing the raw token in a secure database is generally acceptable if the database is properly protected, but storing a hash (like how passwords are stored) means even if the DB is leaked, attackers can’t use the stolen refresh token directly. If you store a hash, you would hash the incoming refresh token and compare to the stored value.

On user login (or token creation), you would save the refresh token in the database. For example, a simple approach is to add a refresh_token field in the user’s record (or a separate table linking user ID and token). In development with SQLite, you might execute an INSERT/UPDATE for the user’s refresh token. Ensure old refresh tokens are replaced or multiple tokens are handled if you allow multi-device logins.

Refresh Token Endpoint: Implement an endpoint like POST /auth/refresh where the client sends their refresh token (usually in the request body or as an HttpOnly cookie). The server will:
	1.	Validate the refresh token: Decode it using the same secret and algorithm. If decoding fails or it’s expired, reject the request with unauthorized error. Also verify that the token has the proper "token_type": "refresh" claim ￼ to ensure an access token isn’t accidentally used at the refresh endpoint. For example:

```
@app.post("/auth/refresh", response_model=Token)
def refresh_access_token(refresh_token: str = Body(...)):
    try:
        payload = jwt.decode(refresh_token, SECRET_KEY, algorithms=[ALGORITHM])
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired refresh token")
    if payload.get("token_type") != "refresh":
        raise HTTPException(status_code=400, detail="Invalid token type")
    user_id = payload.get("sub")
    # (Optional) Check token against DB record for user_id
    # e.g., stored_token = db.get_refresh_token(user_id); compare with refresh_token or its hash
    ...
```

The above uses PyJWT (jwt.decode) which will automatically validate the signature and expiry (exp) if present. We manually check token_type ￼. You would also verify the token exists in the database for that user (to guard against revoked tokens).

	2.	Issue a new access token: If the refresh token is valid, look up the user (by user_id or email in the sub claim) in the database. Ensure the user is still active (has not been disabled or deleted). Then generate a new access token for that user, including their roles. Since we chose static refresh tokens (not rotating them on each use), you can return the same refresh token or issue a new one. In our design, we’ll keep it static for its 7-day lifespan to keep things simple (the refresh token itself will eventually expire after 7 days) ￼ ￼. If you wanted to rotate refresh tokens (a more advanced practice), you would generate a new refresh token here and update the DB, but we’ll stick to static tokens as specified.
	3.	Respond with new tokens: Return the new access token (and optionally a new refresh token if you decided to rotate). The response could be a JSON containing {"access_token": "...", "refresh_token": "...", "token_type": "bearer"} similar to the login response ￼. If you’re not rotating the refresh token, you might choose not to resend it each time. However, sending it again (or confirming it’s still valid) doesn’t hurt. In production, many implementations will set the refresh token in an HttpOnly cookie on the response rather than in the JSON, to keep it secure from JavaScript ￼. For development, returning it in JSON is acceptable, but consider the cookie approach for a real deployment to mitigate XSS risks (the cookie is HTTP-only, so JS cannot read it).

By storing refresh tokens server-side, we gain the ability to revoke them at will ￼. For example, a “logout” endpoint could simply delete the token from the DB (and instruct the client to delete its copy/cookie). Any further use of that refresh token would fail the DB check even if the JWT itself was technically valid. This server-side check is a simple form of invalidating tokens without maintaining a complex blacklist of JWTs.

Protecting Endpoints with OAuth2 and JWT (Token Verification)

FastAPI makes it easy to secure endpoints using dependency injection. We can use the OAuth2PasswordBearer dependency to parse the Authorization: Bearer ... header from requests ￼. This yields the JWT string, which we then verify. Here’s how we can set it up:


```
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")  # URL of the login endpoint

def get_current_user(token: str = Depends(oauth2_scheme)):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except jwt.PyJWTError:  # catches decode errors or expired token
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Could not validate credentials",
            headers={"WWW-Authenticate": "Bearer"}
        )
    # At this point, the token is valid in structure and signature
    # We can parse out user info:
    user_id = payload.get("sub")
    if user_id is None:
        raise HTTPException(status_code=401, detail="Token missing user")
    # Optionally, check expiration explicitly if PyJWT not already doing so.
    # PyJWT will raise on expired token by default, so usually not needed to manual check exp.
    # Fetch the user from DB (to ensure user still exists and is active):
    user = get_user_from_db(user_id)
    if user is None or not user.is_active:
        raise HTTPException(status_code=401, detail="User not found or inactive")
    # You could also attach roles or entire user object to the request context if needed.
    return user
```

What this does: using the oauth2_scheme dependency, FastAPI will extract the token from the request header and pass it to get_current_user. We decode the JWT with PyJWT (jwt.decode), which will verify the signature and expiration. If any validation fails, we throw an HTTPException with 401 or 403 status. If successful, we retrieve the user identified by sub (subject) claim from our database to get the full user info. This double-checks that the user still exists and is active (covering cases like user deletion or disable since the token was issued). After this, the endpoint can safely know current_user is authenticated.

We will use get_current_user as a dependency in any protected route. For example:

```
@app.get("/users/me")
def read_current_user(current_user: User = Depends(get_current_user)):
    return current_user
```

This way, FastAPI will call get_current_user before executing the endpoint logic, automatically enforcing authentication. If not authenticated, the exception will prevent the route from running and return an error to the client.

Implementing Role-Based Access Control (RBAC)

With RBAC, certain endpoints should only be accessible to users with specific roles (permissions). We have a few options to implement this in FastAPI:
	1.	Embed roles in JWT and check in dependency: Since we included roles in the JWT access token payload, we can leverage that. We could extend our get_current_user or write a new dependency that not only authenticates the user but also checks their role. For instance, we can create a dependency factory that takes required roles and verifies the current user has one of those roles:

```
def get_current_user_with_roles(required_roles: list[str]):
    def dependency(token: str = Depends(oauth2_scheme)):
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        # (Decode as before, handle errors similarly)
        roles = payload.get("roles", [])
        user_id = payload.get("sub")
        if payload.get("exp") and datetime.fromtimestamp(payload["exp"]) < datetime.utcnow():
            raise HTTPException(status_code=401, detail="Token expired")
        if required_roles:
            user_roles = set(roles)
            # Allow access if user has at least one required role:
            if not any(role in user_roles for role in required_roles):
                # (Optionally allow admins to bypass)
                raise HTTPException(status_code=403, detail="Insufficient permissions")
        # If passes, fetch user and return (or just return user_id/roles)
        user = get_user_from_db(user_id)
        if not user:
            raise HTTPException(status_code=401, detail="User not found")
        return user
    return dependency
```
This pattern returns a dependency function that can be parameterized with different role requirements. We check if the user’s roles (from the token) include any of the required_roles. If not, we throw a 403 Forbidden ￼. We might also define that an "admin" role automatically grants access to all protected routes (as a common convention) ￼. In the example above, you could add a condition like or "admin" in user_roles to allow admins through regardless of specified roles ￼.

	2.	Check roles in the endpoint function: Another simpler approach is to get the current user (with roles) and then in the endpoint function code, verify the role. For example:

```
@app.get("/admin/dashboard")
def admin_dashboard(current_user: User = Depends(get_current_user)):
    if "admin" not in current_user.roles:
        raise HTTPException(status_code=403, detail="Admin only")
    return {"message": f"Welcome, {current_user.email}. You are an admin."}
```

This manual check works fine for a few endpoints, but can get repetitive if many endpoints need role checks. Using a reusable dependency as in option 1 keeps things DRY.

Using the dependency approach, an example usage would be:

```
@app.get("/admin/stats", dependencies=[Depends(get_current_user_with_roles(["admin"]))])
def get_admin_stats(current_user: User = Depends(get_current_user)):
    # By the time we reach here, role check passed
    ...
```

In this case, we layer two dependencies: one ensures the user has the “admin” role (or aborts), the other retrieves the current_user object for use in the function. This can also be combined if we write the role-checking dependency to return the user object directly.

Assigning Roles: Ensure there’s a way to assign roles to users in your system. In a simple scenario, you might have an endpoint only an admin can call to promote a user to admin role, or you initialize certain users as admins in the database. For development, you can manually mark a user as admin in the SQLite database or your fake user dictionary (as shown with "admin@example.com" having roles ["admin", "user"] above).

With JWT-based RBAC implemented, any attempt to access protected endpoints without the necessary role will result in a 403 Forbidden error with “Insufficient permissions” (or your custom message) ￼. This ensures only authorized roles can perform sensitive actions.

Mock Email Service for Development

In many real-world applications, the authentication system might send emails – for example, email verification links for new users, password reset tokens, or notifications. In a production environment, you’d integrate an SMTP server or third-party email service to send these emails to users. However, during development you likely don’t want to actually send emails to real addresses. Instead, we can mock the email sending so that emails are “sent” to the console or a log file.

Approach: Abstract your email-sending logic into a function or service. For instance, have a function send_email(to_address, subject, body) that you call whenever you need to send an email. In development mode, this function can simply print the email content to the console (or save it to a local file). For example:


```
def send_email(to: str, subject: str, body: str):
    # Development implementation: print to console
    print(f"=== Simulated Email ===\nTo: {to}\nSubject: {subject}\nBody:\n{body}\n")
```


If you trigger a “password reset” or “verify your email” action, the token/link that would normally be emailed to the user will appear in your console log. This lets you simulate the full user experience (you can copy the link from console and paste it in a browser, for instance) without needing a real mail server.

FastAPI also supports background tasks, which is useful if you want to send emails asynchronously (so the API response isn’t delayed by email sending). You could use BackgroundTasks to schedule the send_email call without blocking the request. In dev, it’s not strictly necessary, but it’s something to consider for production if email sending might slow down the response.

When you’re ready for production, you can switch out the email function’s implementation to actually send emails via SMTP or an API (such as SendGrid, Mailgun, etc.). There are libraries like FastAPI-Mail that make this integration easier, supporting features like HTML templates and attachments. During development, FastAPI-Mail can even be configured to write emails to a file instead of sending, which is similar to printing to console (other frameworks like Django have a “console email backend” for this purpose). The key idea is to not send real emails on your dev machine, but still have a way to review the email content. By dumping emails to console, you can verify that things like account activation links or OTP codes are being generated correctly.

Putting It All Together and Next Steps

We have outlined a secure foundation for authentication and RBAC in a FastAPI app: users register or log in, obtaining a hashed password stored in a database and receiving JWT tokens for access. Protected endpoints use the Bearer access token for authorization, and role requirements are enforced either via dependencies or in-line checks. Refresh tokens lasting 7 days allow silent reauthentication – the client can use them to get new access tokens without bothering the user to log in again ￼. We store those refresh tokens in a backend database, enabling us to revoke them if needed for security ￼. All of this follows OAuth2 patterns (the “password” grant type flow) but implemented within our own application using JWTs, which is exactly the approach you’re looking for.

Some best practices to note:
	•	Token Security: Keep access tokens short-lived and refresh tokens longer-lived but secure. Never expose refresh tokens to JavaScript or in URLs. Use HttpOnly cookies for refresh tokens in production for better security ￼.
	•	Password Security: Always hash passwords (e.g. using bcrypt via Passlib) before storing ￼. Never log or email raw passwords.
	•	RBAC Design: Define clear roles and use least privilege principles (e.g. a normal user should only get “user” role capabilities; only grant “admin” where necessary). The JWT should only carry non-sensitive info like user ID, email, and roles. Avoid putting secrets or overly large data in JWTs.
	•	Error Handling: Be careful not to leak information in error messages. For instance, "Could not validate credentials" is fine for invalid token, but don’t explicitly say “token expired” to an attacker (though you might inform a legitimate user). The examples above use generic 401/403 messages as appropriate ￼ ￼.
	•	No Bruteforce/Ratelimit Yet: We haven’t implemented rate limiting on auth endpoints or account lockout on too many failed logins. Those can be added later (using IP-based rate limit or a lock after X failures to mitigate brute force attacks). For now, ensure at least basic measures like using HTTPS in production so tokens/passwords are not intercepted, and maybe a minimum password strength on signup.

With this setup, you have a robust starting point. As the application grows, you might integrate more features: multi-factor auth (MFA), more complex permission systems (beyond just roles, maybe per-object permissions), and auditing of logins/refreshes. But those can be layered on top of the solid JWT + refresh token core you’ve built here.

Summary: Use FastAPI’s OAuth2 dependency injection to secure routes with JWT Bearer tokens, use PyJWT (or similar) to handle signing and verifying tokens, store refresh tokens on the server (e.g. in SQLite during development) to allow token invalidation, and implement role-based checks either in the token payload or via database lookups to enforce permissions ￼. By relying on well-tested libraries for JWT and hashing, we avoid reinventing wheels and align with industry best practices for authentication. And by mocking email delivery in development, we can fully test user registration and recovery flows without needing immediate SMTP setup.
