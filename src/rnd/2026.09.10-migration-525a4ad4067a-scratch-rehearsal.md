**Row** `dbe42964` · **Ran** twice by Tiffany 💍: 2026-09-11 00:18:45Z–00:18:48Z and 00:19:26Z–00:19:27Z · **Condition** Rick's, as on `c9fafb9d`: a migration merged here is applied at the next `:7999` bounce, so it is rehearsed first, and the scratch database has to be shown removed

## Verdict

On Postgres, the migration adds `task_promotion_tickets.answer_by` (`timestamptz`, nullable) and its CHECK. The installed CHECK refuses an answer window that closes after the stall deadline. `upgrade()` restores a missing CHECK on a table that already has the column. The migration downgrades and re-upgrades cleanly. **Both scratch databases named `lupin_scratch_rehearsal_525a4ad4067a` were dropped:** after each drop the listing matched the one taken before that run, and a count of databases with that name returned 0. `lupin_db_dev` was only read. It is still at `9a1c4f27bd30`, with no `answer_by` column.

## Why there were two runs

Run 1 checked drift by calling the unit test `test_metadata_schema_drift.py` against the scratch database. It failed with 25 diff entries, all of them index differences the dev schema already carries (for example on `prediction_log`, `proxy_decisions`, `trust_states` and `job_history`). The script printed only the last 25 lines of that output, so run 1 could not show whether any entry named this table. Rather than read a truncated list as a clean one, run 2 swapped that step for a direct `compare_metadata` filtered to this table and added the positive control above. Every other step was identical in both runs, and so was every result.

## Not established

- **Lock time on the live table.** Adding a nullable column and a CHECK takes brief exclusive locks on `task_promotion_tickets`, which held 8 rows at 00:10Z. This will happen during server start at the next `:7999` bounce, and its duration was not measured.
- **CHECK parity by comparison.** `compare_metadata` does not compare CHECK constraints. The installed predicate was read back through `pg_get_constraintdef` (row 3 of the results), and the unit test `test_the_check_literal_and_name_match_the_model_VERBATIM` checks the model and the migration literal against each other.
- **Tables beyond those copied.** Only `task_items`, `task_promotion_tickets` and `alembic_version` carried data. Reading its source shows the migration touches nothing else; that was not measured against a full copy.
