# Reuse review: Background Jobs accordion sorting and the Run now refusal text (row b076c637)

Eighteen definitions came in with merges 348740f29 (the sort orders and header row, row 4b807ffd) and 4d3f0fa4a (the Run now refusal text, row 6737dbee). The reuse exit gate named all eighteen as having no outcome line.

Ten of them are in the multiplexer client and eight are in the legacy client (`background-jobs.js`). The two clients carry parallel copies by design: Rick's no-shared-code ruling (row 87812328) keeps them independent, so each legacy definition has its multiplexer twin as its nearest candidate and is ruled against that twin's receipt. The symbol index lists only six of the ten multiplexer definitions, and none of the legacy ones, because `background-jobs.js` is one closure with no top-level functions. The other twelve are nested functions and the arrow comparators inside `SORT_ORDERS`. They are ruled against the receipt of the definition they sit beside, which is how earlier reviews ruled nested helpers.

I searched the web tree for another reader of `last_attempt` and for another sortable header (`aria-sort`, the ▲ and ▼ marks). Only the two jobs clients and `jobs/types.ts` read `last_attempt`, and no other file sorts a header or draws those marks. The closest candidates are `trendArrow` (reads a numeric series, not a direction), `_rowTableHeaderRow` in `notifications.js` (a static `<th>` string with no buttons or sorting), and for the refusal text `detailFrom`, `serverDetail` and `holdingRefusalMessage`, which return the status or the raw text where `refusalDetail` must return nothing so the plain line shows. The pinned test "a body without a usable detail falls back to the plain line" feeds a body of `{not json`, and `detailFrom` would return that text.
