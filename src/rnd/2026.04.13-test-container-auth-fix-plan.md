## Resolution (2026-04-13)

**Root cause**: `$LUPIN_TEST_INTERACTIVE_MOCK_JOBS_EMAIL = interactive.job.tester@lupin.deepily.ai` existed in `lupin_db_dev` but not in `lupin_db_test`. The seed script `src/scripts/seed_test_companions.py` allowlist (`COMPANION_EMAILS`) was missing that user (and its `mock.job.tester@...` sibling).

All other hypotheses in the original plan were ruled out by live probes inside the containers:
- DB binding correct (`engine.url.database == lupin_db_test`, `SELECT current_database()` confirmed)
- No password pepper — `password_service.py` uses plain `passlib.CryptContext(["bcrypt"])`
- No image drift — same `authenticate_user()` code path resolved in both containers
- JWT secret per-container is real but cosmetic for this bug

**Fix executed**:

1. **Phase A — Seed fix** ✅
   - `src/scripts/seed_test_companions.py` lines 48-52: added `INTERACTIVE_TESTER` + `MOCK_TESTER` constants; extended `COMPANION_EMAILS`.
   - Ran `docker exec lupin-rest-dev python3 /var/lupin/src/scripts/seed_test_companions.py` → "Seeded 2 user(s) and 0 API key(s) into lupin_db_test".
   - Verification: `curl -X POST http://localhost:8000/auth/login ...` → HTTP 200 + JWT.

2. **Phase B — Regression guard** ✅
   - New file: `src/tests/integration/test_cross_container_auth.py`
   - Parametrized over :7999 and :8000; skips unreachable; uses `$LUPIN_TEST_INTERACTIVE_MOCK_JOBS_*`.
   - Result: 2 passed, 1 skipped (dev :7999 slow on `/health` during run; real traffic fine).

3. **Phase C — TFE Resume E2E scheduling restored** ✅
   - Submitted via test-server scheduler (:8000).
   - Job ID: `ts-9522f777::50c73ba7-36dd-4eaf-a7e2-63256252c84f`

   - Monopolize: false

## Hypotheses, ranked

1. **`/auth/login` on test container is hitting `lupin_db_dev` with a DB user that has a *different* password hash than the one I inspected** — i.e., the "identical hash" I compared is NOT the hash `login` is checking against. Path: a stale connection string or INI override under `Lupin: Testing` pins `postgres database` to a dev DB or a legacy DB that was never re-hashed.
   - **Check**: `docker exec lupin-rest-test python -c "from cosa.rest.db.database import get_db_connection_params; print(get_db_connection_params())"` to see what DB the running app actually opens.
   - **Also**: wrap `verify_password` in `password_service.py` with a one-shot debug log that prints the DB URL + hash it's checking, bounce the test container, try login again.

2. **Password pepper or app-specific secret differs by env** — an extra secret is concatenated before bcrypt. Possible if `password_service.py` reads a config key whose value under `Lupin: Testing` differs from `Lupin: Development`.
   - **Check**: `grep -rn "pepper\|app_secret\|password_secret" src/cosa/rest/password_service.py src/cosa/rest/user_service.py` (initial grep above returned no pepper references, so this is low-probability but worth ruling out).

3. **Test container has diverged code/venv** — it was built from a different commit/tag and its `verify_password` or `authenticate_user` is broken.
   - **Check**: `docker exec lupin-rest-test python -c "import cosa.rest.password_service as p; import inspect; print(inspect.getsourcefile(p))"` and diff against the dev container's same file.
   - **Check image digest**: `docker inspect lupin-rest-test --format='{{.Image}}'` vs `lupin-rest-dev`.

4. **`Lupin: Testing` INI block disables DB auth / redirects `auth mode`** — e.g. falls back to a different auth provider that only honors API keys.
   - **Check**: diff the effective resolved config keys between blocks via a `/api/system/config` debug endpoint (if present) or via `docker exec ... python -c "from cosa.utils.config_manager import ConfigurationManager; cm = ConfigurationManager(...); print(cm.get('auth mode'))"`.

5. **JWT signing secret drift is a separate, co-existing bug** — two containers need to either (a) share a secret if you want tokens portable across them, or (b) each accept only their own tokens (current behavior). For the auth-fix goal, this is cosmetic — once `/auth/login` on 8000 works, tokens minted by 8000 work against 8000 endpoints. But documenting it so we don't chase ghosts later.

Ranked order above is by expected payoff; start at (1).

## Remediation plan (phased)

### Phase 1 — Diagnose (30 min)

1. Enable debug logging on `authenticate_user` and `verify_password` inside the test container (temporary patch, no commit), restart `lupin-rest-test`.
2. Send one login attempt at :8000; capture the log showing:
   - DSN / DB name actually used
   - The hash being passed to `bcrypt.checkpw`
   - The candidate password bytes length (never log plaintext — just length + SHA256 prefix)
3. Cross-reference with `lupin_db_test.users.password_hash` to identify whether hypothesis (1) is correct.

### Phase 2 — Fix (depends on root cause)

- **If hypothesis 1 confirmed**: the bad DB binding is the bug. Repair INI / env so `Lupin: Testing` → `lupin_db_test`. Add an assertion at app startup that logs the connected DB name loudly.
- **If hypothesis 2 confirmed**: unify pepper across envs OR re-seed test DB with env-appropriate hashes.
- **If hypothesis 3 confirmed**: rebuild test image from current commit; pin to same git SHA as dev image via compose.
- **If hypothesis 4 confirmed**: remove the redirect, or document the expected auth provider for test and adjust scheduler skill + `/schedule-tests` to use it.

### Phase 3 — Harden

1. Add an integration smoke test `src/tests/integration/test_cross_container_auth.py`:
   - `POST /auth/login` on both 7999 and 8000 using `$LUPIN_TEST_INTERACTIVE_MOCK_JOBS_*`
   - Assert 200 + `tokens.access_token` on both
   - Exists solely to catch this regression early
2. Decide JWT secret policy: share across containers (requires secret in a shared secret store) OR keep separate and document that tokens are not portable. Either way, document in `src/docs/auth/architecture-overview.md`.
3. Update `/schedule-tests` skill to default `BASE_URL` to `http://localhost:8000` (per the new dual-container rule) and to call out that 7999 only works for "inside the dev container" scenarios.

### Phase 4 — Restore the TFE Resume E2E scheduling workflow

Once :8000 login works, re-submit per the original runbook:

```bash
python3 - <<'EOF'
import os, requests
BASE = "http://localhost:8000"
r = requests.post(f"{BASE}/auth/login", json={
    "email": os.environ["LUPIN_TEST_INTERACTIVE_MOCK_JOBS_EMAIL"],

}, timeout=10)
r.raise_for_status()
tok = r.json()["tokens"]["access_token"]
requests.post(f"{BASE}/api/test-suite/submit",
  headers={"Authorization": f"Bearer {tok}"},
  json={
    "test_types": "integration",
    "pytest_args": "src/tests/integration/test_tfe_resume_e2e.py -v --tb=short",
    "scheduled_at": "<ISO -04:00>",
    "monopolize": False,
    "dry_run": False,
  }, timeout=10).raise_for_status()
EOF
```
