## 5. Open questions / risks

- **Service user**: unit runs as the enabling user (`admin_rickruiz_altostrat_com`). It must (a) be in `docker`
  (Phase 1.2), and (b) read the UID-1001-owned checkout + write `io/` (mementos, `arbiter.log`). If `io/` isn't
  group/world-writable by that user, the arbiter's writes fail — verify in Phase 1.4; may need a group grant on `io/`.
- **`systemd --user` over IAP `--command`**: non-interactive SSH may lack a user D-Bus session; `systemctl --user`
  needs the user manager (linger provides it). Phase 2 (Rick, interactive or post-linger) is the reliable path.
- **usermod is reversible** (`gpasswd -d`), non-destructive. Re-login required before the group takes effect.

## 6. Bring-up execution + two provisioner bugs found (2026-07-22)

Executed Phase 1 + Phase 2 (Rick "go"). Enable succeeded (linger=yes, unit enabled), then the service
**crash-looped** — two latent defects in the provisioning path, both now fixed in-repo:

**Bug 1 — unquoted `Environment=` truncated the config args.** `provision-arbiter-on-vm.sh`'s awk emitted
`Environment=LUPIN_CONFIG_MGR_CLI_ARGS=config_path=… splainer_path=… config_block_id=…` **unquoted**. systemd
splits an unquoted `Environment=` on whitespace → the var kept only the first token → `ConfigurationManager`
got a partial `cli_args` → `KeyError: 'config_path'` → `Restart=always` crash-loop. **Fix**: the awk now wraps
the value in double quotes (`Environment="…"`). Verified the emitted line is quoted.

**Bug 2 — `requirements-arbiter.txt` missing `pyyaml`.** After Bug 1, next crash was
`ModuleNotFoundError: No module named 'yaml'` from `lupin_mcp/commons_store.py:31`, reached via
`LupinArbiterGateway.from_environment()`. The arbiter's import graph grew a YAML dep after the 2026-06-10
requirements freeze. **Fix**: added `pyyaml==6.0.3` to `requirements-arbiter.txt` (installed live on the VM to
unblock).

**Result after both fixes:** `systemctl --user is-active` = `active`, `:8001` LISTEN on `0.0.0.0`, `NRestarts=0`;
container→`host.docker.internal:8001/health` = **REACHABLE**; **bounce-survival** confirmed (restart
`lupin-rest-cloud-gpu` → `:8001` stayed up). VM-side hotfixes: unit `Environment=` quoted + `pyyaml` pip-installed;
both now also correct in the repo so a fresh `provision-arbiter-on-vm.sh` run reproduces the working state.

**Answer to "where do the 2 manual steps live?"** By design, `provision-arbiter-on-vm.sh` stops before
`loginctl enable-linger` + `systemctl --user enable --now` and **prints them** as HELD operator steps. Reason:
`enable-linger` needs root/sudo and both mutate the operator's **login session** — the script deliberately never
actuates a login session unprompted (least-privilege boundary, per the unit's own hold banner). Not a hack, but
they *could* be folded into the provisioner behind an explicit `--actuate` opt-in flag if we want a one-shot
bring-up — a small, safe enhancement (noted as a follow-up).

## 7. Provisioner bug #3 + the deploy gate that now catches it (2026-08-10)

**Third silent venv-drift failure on this VM.** The `fleet-arbiter-loop` thread died on
its first tick with `ModuleNotFoundError: No module named 'sqlalchemy'` and stayed dead
for **two days**. `systemctl status` reported `active (running)`, `/health` returned
`{"status":"ok"}` on every poll, and the health-watcher + context-pressure loops kept
ticking normally. The only symptom reached the operator three hops downstream, as
"No active sessions." in the Fleet Status panel.

**The import came from a DISABLED feature.** `follow through escalation enabled = false`,
yet `make_follow_through_watcher_factory`'s inner `factory` imported the watcher —
and therefore `cosa.rest.db.database` → `sqlalchemy` → `pgvector` → `psycopg2` —
unconditionally, at job construction, before reading the flag.

### What changed

| Change | File | Effect |
|---|---|---|
| Flag read moved **above** the import | `lupin_arbiter_app/fleet_arbiter_loop.py` | flag off ⇒ no DB import ⇒ the light venv stays light |
| Job construction moved **inside** the supervisor's try | same | a ctor raise is logged and retried each cycle instead of killing the thread once, silently |
| Per-loop thread liveness | `lupin_arbiter_app/app.py` | `/health` gains `loops` + `degraded`; `/state` carries `loops` so the panel can tell **dead** from **quiet** |
| Deploy-time import gate | `src/scripts/check-arbiter-venv.py` (new) | imports the arbiter's real runtime graph in the target venv; non-zero exit fails the provision |
| Provision runs the gate | `src/scripts/provision-arbiter-on-vm.sh` | after `pip install`, unpiped, `$?` tested directly |
| Preflight asserts loop liveness | `src/scripts/preflight-vm.sh` | D3b — a 200 with a dead loop now BLOCKS and names the loop |

### Two environment faults found on the VM while fixing it

1. **`.venv-arbiter` was owned by uid 1001 — a nonexistent user on that box** (`stat`
   shows `UNKNOWN`) while the service runs as uid 1721846087. The service could read
   its venv but never write it; any in-place `pip install` failed `Permission denied`.
   Chowned to the running user. Note `preflight-vm.sh:209` **already checks for this
   exact trap** — the check existed and the finding had not been acted on.
2. **`live_notify_disabled`** at every boot — `Environment 'development' not found in
   ~/.lupin/config`. The VM arbiter cannot send live notifications. Not yet fixed.
