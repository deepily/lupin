## 0. Verdict first

The row's diagnosis is right that this is a **rule-composition defect**, and right that fixing an allocation path does not close it. Two corrections change the remedy space materially:

1. **Premise 1 is false as filed.** A session *can* detect its own null. The trap is entirely in the **remedy**, not in observability.
2. **There is a fifth rule the row does not list, and it is the decisive one**: the boot self-announcement — the one zero-cost signal that would surface the null — is **explicitly suppressed when the persona is null**.

⇒ The escape hatch is not merely *priced out*. **A free one exists mechanically and doctrine never names it, while actively silencing the broadcast that would trigger it.**

### 1.1 Why premise 1 being false is good news

Detection is usually the expensive half of a trap. Here it is already solved and already mandated. What the session cannot do is **act** on what it detects. That means any remedy relying on the affected session reporting its own state is **cheap and reliable** — which is not true when a session is blind to its own condition.

### 1.2 The fifth rule, and why it is decisive

```
:700  "if the voice_persona field is non-null, send a brief TTS greeting…"
:707  "If voice_persona is None …, skip the greeting — there's no name to use."
:723  "3. If voice_persona.name is non-null, call notify(…) with a … greeting"
```

The boot announcement is the **only unprompted, zero-interrupt broadcast** in the startup sequence. It is gated OFF precisely in the failure case.

The stated rationale — *"there's no name to use"* — is **locally correct and globally the defect**. It optimises the greeting's *content* and in doing so silences the *alarm*. A session that boots healthy announces itself; a session that boots broken says nothing. **The system is quietest exactly when something is wrong.**

This is the same shape as the guard in `692d1596` that checks column presence but never column shape: a check that reports success for the one case it cannot handle.

### 1.3 A self-contradiction inside one docstring

`request_persona`'s hard rule and its own argument documentation disagree:

| Location | Text |
|---|---|
| `:2247` (hard rule) | "**Do not** call it to fix your own null persona on your own initiative." |
| `:2266-2268` (`name` arg) | "OMIT ENTIRELY … — **the path for healing a session whose `voice_persona` is null**" |

**The remedy is documented in the same docstring that forbids reaching it.** Both sentences are defensible in isolation; together they tell a null session that the cure exists, is named, is one call away, and is off-limits.

### 1.4 The missing tier — the row's sharpest under-statement

The documented remedy set jumps straight from *nothing* to a **blocking `converse()`**. Two cheaper, already-permitted surfaces are never named:

| Surface | Autonomy tier | Interrupt cost to Rick | Named in null doctrine? |
|---|---|---|---|
| `notify()` | self-disclosure — allowed at own initiative | **none** (fire-and-forget) | ❌ actively suppressed at `:707` |
| `dm_send()` to manager | DM tier | **none** | ❌ never mentioned |
| `converse()` | attention-demanding | **one blocking interrupt** | ✅ the only one prescribed |
| `request_persona()` | — | none | ❌ forbidden by rule 2 |

**Rule 4 prices out *interrupts*. It does not price out *non-blocking signals*.** Every worker correctly declining `converse()` is obeying rule 4 as written — but there was never a reason to decline a `notify()`, and doctrine simply never offered one.

⇒ **Restating the done-condition**: a route out that costs no principal interrupt is not missing from the *platform*. It is missing from the *doctrine*, and suppressed by `:707`.

## 2. Candidate remedies

Ordered by my recommendation. **None of these is implemented; all require Rick's ruling.** B and C change standing rules and are his alone.

### D — Un-suppress the announcement + name the non-blocking tier ⭐ recommended floor

Invert `:707`: when `voice_persona` is None, do **not** skip — emit a `notify()` that says the session is unnamed and names its `session_id`. Add `notify()` + manager `dm_send()` to Failure Mode 2 ahead of `converse()`.

| Pros | Cons |
|---|---|
| **No standing rule changes** — rules 2, 3, 4 all survive untouched | Does not *prevent* the null; it surfaces it |
| Zero principal-interrupt cost; rule 4 never engages | Depends on someone (Rick or manager) noticing the card |
| Doc/instruction change only — smallest blast radius on the board | A null session's `notify` is unattributed, so the card must carry the `session_id` explicitly |
| Fixes the "quietest when broken" inversion directly | |
| Works even if allocation is later fixed — it is the general alarm | |

**Why the floor**: it is the only candidate that closes the *observability inversion* without touching a rule the user owns. It composes with A, B, or C rather than competing.

### A — Allocate at spawn/SessionStart so the state cannot arise

| Pros | Cons |
|---|---|

**Assessment**: necessary, not sufficient. Pair with D.

### B — Carve a rule-2 exception for null-self-heal

Permit `request_persona()` (no-arg) **only** when `voice_persona is None`.

| Pros | Cons |
|---|---|

**Assessment**: the cleanest mechanical fix and the highest-authority cost. My concern is the stale-bridge case in the last row — I could not rule it out from source and did not test it live.

## 3. The two checks Arnold ordered — both answered

### 3.1 Can `voice_persona: None` coexist with a live pool allocation? ⇒ **B's risk is structurally prevented**

Occupancy is not a table — it is a **scan of bridge files** (`find_active_sessions( require_persona=True )`, `session_bridge.py:1695`), and three properties close the hole:

| Property | Source | Consequence for B |
|---|---|---|
| Occupancy counts only **non-null** personas on **live** bridges | `:1703-1707` | a null bridge contributes zero occupancy — nothing to double-count |
| **Dead-PID OR stale-mtime bridges are treated as FREE** and filtered out | `:1735-1736` | a stale bridge still holding a name has *already* released it; self-heal cannot collide with it |
| Both the scan and `request_persona` canonicalise on **stable_session_id preferred** | `:1750`, `:2125` | a session cannot resolve to a *different* bridge than the one counted against it |
| Allocation is serialised by a module-level lock (scan→pick→write) | `voice_persona.py:58` | no TOCTOU between occupancy read and write |

The failure I hypothesised required one live session owning two simultaneously-live bridges — one named, one null — with the scan counting the named one while `request_persona` wrote the null one. **Identical canonicalisation on both paths makes that unreachable.**

⇒ **B does not carry the double-allocation risk I flagged. My caveat is withdrawn.** The remaining objection to B is purely one of authority, not safety.

### 3.2 Does a null session's `notify()` render legibly? ⇒ **Yes — but UNATTRIBUTED**

End-to-end, `None` is tolerated at every hop and never raises:

```
_voice_persona_for_sender_id()  -> returns None on missing/unset persona   (notifications.py:50-77)
push_notification( voice_persona=None )  -> Optional[dict] = None          (notification_fifo_queue.py:312)
NotificationItem.voice_persona = None    -> serialised as null             (:106, :215)
client badge hydration: if ( sender_id && voice_persona )                  (notifications.js:5700)
```

**The card renders; only the persona badge is withheld.** The message and abstract display normally.

⇒ **D works, with one binding constraint**: the badge is exactly the channel that carries identity, and it is the channel that goes missing. **D's alarm text MUST name the `session_id` inline** — an unbadged card saying "I am unnamed" is otherwise unactionable, because nobody can tell *who* sent it. That constraint is now load-bearing on D, not cosmetic.

**Pleasing symmetry, and it is the same defect twice**: the persona badge is suppressed when the persona is null, for the same locally-correct reason as `:707` — there is no name to render. The alarm and its identity vanish together.

### 3.3 Does a null session's `dm_send()` resolve? ⇒ **YES — exercised, not inferred. Candidate C is buildable.**

No live null-persona bridge existed to test against (12 bridges scanned, 0 null), and creating one would mutate shared session state. Tested instead by **runtime monkeypatch of `session_bridge.SESSION_DIR`** onto a scratch directory holding synthetic bridges — no shared-state write, no cosa-voice edit.

```
require_persona=True   -> 1 session   (null EXCLUDED — occupancy semantics)
require_persona=False  -> 2 sessions  (null INCLUDED — reachability semantics)

_resolve_dm_recipient( recipient_session_id=<null-persona session> )
  -> {'http_status': 200, 'session_id': 'aaaaaaaa-…', 'persona_name': None}
```

**A null session is addressable by `session_id` and returns 200 with `persona_name: None`.** The occupancy/reachability asymmetry works exactly as `d57dbfea` designed it.

**Harness controls — the 200 is only meaningful because these failed:**

| Control | Result |
|---|---|
| nonexistent `session_id` | **422** `recipient_inactive` |
| resolve a null session **by persona name** | **422** `recipient_not_found` (correct — it has no name) |
| resolve the named session by persona name | 200, `persona_name: 'tester'` |
| cross-user isolation (`owner_user_id` stamped) | **422** `recipient_inactive` |

⚠️ **One false positive in my own harness, caught before reporting it.** My first isolation control returned **200 for a foreign caller**, which reads as a cross-user reachability defect. It was not. Scoping reads **`owner_user_id`**, not `user_id`, and bridges *lacking* that field **pass through by documented back-compat design** (`commons.py:264-276`). My synthetic bridge stamped only `user_id`, so the filter was vacuous. **My instrument was answering a question I had not asked.** Re-run with `owner_user_id` present, isolation enforces correctly (422).

⇒ **C is buildable**: a manager can reach a null worker by `session_id`. C still depends on D to know the worker is null in the first place.
