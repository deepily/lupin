## 2. Why RestartCount is the right signal (positive control, not a flattering zero)

A sanctioned bounce and an unsanctioned crash-loop look identical to the health/flap predicate. They do NOT look identical in docker's `.State.RestartCount`, which is incremented ONLY by the restart POLICY auto-restarting a crashed container — not by a manual `docker restart` (reuse) and not by `compose up --force-recreate` (which mints a new container and resets the count to 0).

**Positive control (2026-08-01, docker 24.0.4), throwaway containers, no Lupin container touched:**

| Phase | Action | RestartCount |
|---|---|---|
| A | crash-loop: `--restart unless-stopped`, command exits immediately | **climbed 1 → 3 → 5 → 6 → 7 in 8s** |
| B | stable container, manual `docker restart` ×2 | **stayed 0** |

The counter *moved in front of me* on a real policy restart and *did not move* on a manual restart. That is a demonstrated difference, not an absence. So a RestartCount-based detector fires on unsanctioned crash-loops and is structurally immune to sanctioned bounces — and it is NOT gated on flap-exclusion. The sanctioned-bounce marker written by `src/scripts/bounce-dev-server.sh` drops to belt-and-suspenders; RestartCount alone carries the distinction.

## 3. Threshold — honest rationale (Mr Radio addition 1)

The four live containers all read `RestartCount = 0`. **This is NOT evidence of a stable-zero baseline.** They were recreated ~2h ago, and a recreate resets the count — so the zero is consistent with *recency*, not proven stability. Claiming "policy restarts never happen here" from that zero would be the same flattering-zero shape the positive control exists to avoid.

The threshold is therefore chosen for **one-off-crash tolerance**, not from a measured baseline: `threshold = 2` means two policy restarts inside the window is a loop, while a single crash that recovers is not paged. In practice a live loop is unmistakable — the positive control hit 7 restarts in 8s, and the watcher polls every 30s, so one poll interval during a real loop shows a jump of many. The window reuses the existing `arbiter health flap window seconds` (600s).

## 4. Count going DOWN (Mr Radio addition 2)

The tracker keys on container **NAME** (same as the health tracker's `_trackers` dict). A recreate resets RestartCount to 0 and mints a new container id, but the name is stable, so the same tracker sees the count DECREASE. A decrease is treated as a **clean state reset** — rise deque cleared, episode flag cleared, baseline re-set — never a negative rise. A sanctioned recreate can never manufacture a crash-loop page.

## 5. Reload blindness — a loud announcement, not a comment (Mr Radio addition 3)

RestartCount is a reliable crash-loop signal ONLY while uvicorn `--reload` is OFF (the R1 default, `main.py:1406`). With reload ON, the supervising reloader is the container's main process; a crashing worker is respawned WITHOUT the container exiting, the restart policy never fires, and RestartCount never moves. The detector would silently go blind — which is today's exact defect.

So at arbiter startup the health watcher inspects each watched container's `.Config.Env`, computes reload-armed state via the SHARED gate `lupin_app.bootstrap_helpers.reload_enabled` (matching `main.py:1377-1378`: prod/test = `{production, test, testing}`), and if reload is armed it emits a LOUD startup escalation naming the container and saying crash-loop paging is disabled there. If the env inspect fails, the state is logged as unknown (no false all-clear, no false alarm).
