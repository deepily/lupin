## 1. The defect in one line

Nine classes route on the ambient `vector store backend` flag. Four of them *also* accept a caller-supplied location, store it on the attribute, and then ignore it whenever the postgres path is active — so a caller who believed it had redirected the store was reading and writing the shared one, silently.

`vector store backend = postgres` has been live in `[Lupin: Baseline]` with **no per-block override since 2026-07-07**, so this was every venue, host included.

## 5. The remedy

One seam, in the module that already owns the flag:

```python
def resolve_lancedb_path( db_path, caller, config_mgr=None ):
    if not is_postgres_backend( config_mgr ): return db_path   # lancedb: honored
    if db_path is not None: raise ValueError( ... )            # postgres + path: REJECTED
    return None                                                # postgres, nothing promised
```

All four path-taking classes resolve the backend **before** storing a location. The five that accept no location (`EmbeddingCacheTable`, `QuestionEmbeddingsTable`, `InputAndOutputTable`, `QueryLogTable`, plus `routers/system.py` which was already correct) cannot be lied to and are untouched.

Reference form for a call site — `src/cosa/rest/routers/system.py:272-289`, which builds its path inside the `else` arm of `if is_postgres_backend( config_mgr )`. It was the only site that asked first.

### 6b. The correction that was worse than the error — a parser's reach posing as the run's content

The most useful finding in this whole remediation is not about `db_path`. It is that **a correct
number was replaced by a smaller one because the smaller one arrived with a receipt.**

Sequence:

1. The record claimed **"345 of the 348 new `ValueError`s."**
2. María (`697e9fef`) showed 348 does not derive from the table above it. Correct — it doesn't.
3. I re-derived from the logs, got **"320 of 329 parseable blocks"**, withdrew 348, and wrote
   the new figure up *with its own limitation named*: "329 parsed vs 360 actual = 31 blocks the
   regex missed; 320 is a floor, and that gap is unexamined."
4. María examined the gap. **The 31 are not a failure class. They are the 31 longest test names.**

My block-splitting regex required five or more underscores per side:

```
^_{5,} (.+?) _{5,}$   →  329 blocks
^_+    (.+?) _+$      →  360 blocks   ← equals the FAILED count exactly; zero unparsed
```

pytest pads its failure banner to **terminal width**, so a longer test name leaves *fewer*
underscores. Measured padding distribution across all 360 blocks: width 1 → 18 blocks, 2 → 2,
3 → 6, 4 → 5, then 5…28 normally. **The 31 blocks with fewer than five underscores are exactly
the 31 I could not parse** — `TestLanceDBManagerPathResolution`,
`TestPgGetSnapshotsByQuestion`, `TestHierarchicalSearchExtended`, `TestDataOriginEmbeddings`…

**`{5,}` is a name-length filter wearing a structure predicate's clothes.**

Why this is the same defect as §6a, one layer up:

| Section | What stood in for what |
|---|---|
| §6a | a **count** stood in for a **set** |
| §6b | a **parser's reach** stood in for the **run's content** |

Both read as clean. Both were checkable and unchecked.

And the failure is self-reinforcing in the dangerous direction: **329/360 is 91%**, high enough
to look like ordinary log noise. "31 unmatched" reads as tolerable slop rather than as the
systematic exclusion of one identifiable population. Had the regex dropped 60% the alarm would
have been immediate; dropping 9% is what let it through.

**The general form**: *naming a limitation is not the same as the limitation being honest.*
"320 of 329 parseable" reads **more** rigorous than "345 of 348" precisely because it discloses
its own boundary — and that disclosure is what made it persuasive enough to displace a correct
figure. A receipt is a claim. It gets audited like one.

Verified independently on the same artifact before accepting: `348 + 12 = 360`.

**Provenance for every number in §6** — `postchange.txt` (1,637,954 bytes, mtime 2026-07-27
10:36:10) in this session's scratchpad, tail `360 failed, 19481 passed, 24 skipped, 3 xfailed`.
⚠️ The four `/tmp/unit-20260727-*.log` files are **10-byte stubs** containing the literal text
`first run` — worthless, do not cite them.

## 7. Two dispositions, applied by intent

Not one blanket rule — the right fix depends on which path the test is *for*.

**LanceDB-path tests** → pin the flag at its single definition site, **during construction**:

```python
with patch.object( vector_store_backend, "get_vector_store_backend",
                   return_value=vector_store_backend.LANCEDB ):
    mgr = SolutionSnapshotManager( config )
assert mgr._use_postgres is False, "backend pin failed — ..."
```

The **during** matters. `test_lancedb_solution_manager.py` already set `mgr._use_postgres = False` — but *after* `__init__`, which had already resolved the backend and (now) raised. A post-hoc pin is not a pin.

**Postgres-path tests** → stop passing a path at all. `test_gist_cache_table` passed the literal `"/unused"`; that string named the defect out loud.

Every pin carries a **control assert** that fires if the pin ever stops pinning.
