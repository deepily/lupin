## 2. The law the harness encodes

BigQuery ingest **LAGS** (minutes). Therefore a `SELECT ... WHERE sentinel` returning nothing is **NOT**
evidence of "not logged." It may simply be **early**.

> ### **A NULL IS NOT EVIDENCE UNTIL THE INSTRUMENT IS PROVEN.**
> ### And its sharper edge: **a null that CONFIRMS a suspicion sails through the checkpoint a contradicting one never would.**
> ### **An observation is evidence only if it could have come out otherwise.** *(Rio)*

So **no function in this harness will ever return "not logged" from a bare SELECT.** Every negative
verdict is gated on a **CANARY** — a known-good write carrying a unique greppable sentinel — having been
**SEEN in the same window in which the silence is trusted.** If the canary does not land: the verdict is
`INADMISSIBLE`. Not a pass. Not a fail. **No verdict.**

### 2a. The asymmetry that governs everything

> ### **A POSITIVE NEEDS NO CANARY. Presence proves itself. Only ABSENCE needs a calibrated instrument.**

This single asymmetry generates three separate rules in the code, and it is worth naming because it is
what keeps the harness from being either paranoid or credulous:

| Observation | Needs a canary? | Why |
|---|---|---|
| The sentinel **IS** in BigQuery | ❌ No | If we can SEE the row, the readout demonstrably worked *for that row*. |
| The sentinel is **NOT** in BigQuery | ✅ **Yes** | Silence from an unproven instrument is not silence. It is deafness. |

### 2b. Three verdicts, never two

```
PROVEN        the positive was OBSERVED
REFUTED       the null is ADMISSIBLE — the canary was seen, and the subject was not
INADMISSIBLE  the instrument never proved it was awake. NO verdict is rendered.
```

`INADMISSIBLE` is the whole point. A two-valued harness has nowhere to put "we were blind," so it puts it
in whichever bucket the author expected — which is how a suspicion becomes a finding.

### 2c. ORDERING IS EVIDENCE — and the plan REFUSES to be built without it

When the harness probes a *subject* (a call whose logging status is the question) against a *canary* (a
call we believe IS logged), the **subject must be fired FIRST**. Then, if the LATER call lands and the
EARLIER one does not, *"it was just slow"* is a materially weaker explanation than it would have been
had we fired them the other way round.

`ProbePlan.__init__` **raises** if `subject_fired_at > canary_fired_at`. This is cheap rigor, and it is
enforced at construction — before any money is spent — rather than discovered in the analysis.

### 2d. No clock may substitute for evidence

Google declares **no ingest delay** for this pipeline (`metadata.ingestDelay: None`). So any hardcoded
wait is **an assumption wearing a constant's clothing** — and it can be **wrong forever, silently**: the
day Google changes the real delay, every negative test starts passing for the wrong reason with nobody
notified. The harness **polls to a bound**. The **canary**, not the clock, licenses the verdict.

## 3. The §4f tension, dissolved

§4f mandates: **assert on the ROW COUNT, never on a COLUMN** — because
`requestResponseLoggingSchemaVersion` is output-only and **versioned (v1/v2)**, so the row shape is not
knowable pre-flight, and naming a column turns a schema bump into a **false failure**.

But a sentinel has to be **found**, which sounds like it needs a column. **It does not.**

```sql
SELECT COUNT(*) AS n
FROM   `project.vertex_logging.<discovered_table>` AS t
WHERE  STRPOS( TO_JSON_STRING( t ), @sentinel ) > 0
```

`TO_JSON_STRING( t )` serializes the **whole row, whatever its schema.** The query therefore names
**ZERO columns** (it survives a v1 → v2 bump untouched) while remaining **attributable** (it finds *my*
row, not somebody else's ambient traffic). **Sentinel attribution and the no-columns rule were never in
conflict.** The sentinel is a **bound parameter**, never interpolated.

**Residual, stated rather than buried**: if the payload lands BYTES-encoded or compressed,
`TO_JSON_STRING` base64s it and the sentinel will not match. That failure mode yields `INADMISSIBLE`
(canary unseen) — **never a false `REFUTED`.** *The instrument fails SAFE.*

### 3a. The table is DISCOVERED, never assumed

The `outputUri` is **dataset-level** (§4d), so **Vertex names the table, not us.** A bare
`SELECT ... FROM request_response_logging` would miss rows landing in a table we never guessed — and
would report a null we would have believed. `list_tables()` reads `INFORMATION_SCHEMA.TABLES`.

This also buys a **free diagnostic that a bare zero-count would have flattened into silence**:

| Readout state | What it means |
|---|---|
| `TABLE_ABSENT` | Vertex creates the table **on first write** ⇒ it has **NEVER written a row.** |
| `NO_MATCH` | The table exists and is queryable; our sentinel is not in it **yet**. |
| `MATCH` | Our sentinel is in it. |

**"We cannot see" and "there is nothing to see" are different findings.** The harness keeps them apart.

## 4. §C — the region-coupling trap, defended

### 4a. "Location" means **three** different things. Only one of them may be compared to the Vertex SSOT.

| Where it appears | What it means | Can it be `global`? |
|---|---|---|
| `CLOUD_ML_REGION` / the `setPublisherModelConfig` **location** | the Vertex **serving/config** location | ✅ **YES — and it must be** |
| The **BigQuery dataset** location (`vertex_logging`) | where the **log sink** lives | ❌ **NO. BigQuery has no `global`.** |
| The **Monitoring `location`** resource label | where the request **was actually served** | ✅ yes — and it is the AC-D4b oracle |

Rev. 4's rule — *"assert the BQ dataset `location == $LUPIN_VERTEX_REGION`"* — became **unsatisfiable by
construction** the moment the Vertex SSOT moved to `global`, and it **broke silently**, because nothing
in the design knew the two locations live in **different namespaces**. Same word. Different universes.
**A shared name is not sameness.**

`assert_bigquery_location_legal()` refuses `global` **as a BigQuery location**, by name, with that
explanation in the error text.

### 4b. The coupling that actually burns money

> ### `CLOUD_ML_REGION` **==** the `setPublisherModelConfig` **location.**

The config is scoped to a **`(project, location, model)`** triple. Write it at one location and the other
has **nothing**: the session **runs perfectly, bills real money, and silently logs nothing** — a false
"logging is on," with every dashboard green.

**This is a REPRODUCTION, not a warning.** The first two real Vertex calls in this project's history
served at `global` while the design still froze the config at `us-central1`. **They were already
invisible to the config we were about to write.** And the mechanism is general: **an unconfigured client
lands on `global`.** A stray SDK default or an inherited `VERTEX_REGION_CLAUDE_*` override re-arms the
trap at any time.

Hence `assert_traffic_config_coupling()` is a **runtime assertion**, not an assumption. Note that
`REGION="${LUPIN_GCP_REGION:-us-central1}"` is a **defaulted env var, not a constant** — a parent shell
can export a different value. **An SSOT is only as strong as the process that reads it.** An *unset*
`CLOUD_ML_REGION` is refused too: unset is not a region, it is a coin flip.

### 4c. The pairing is CERTIFIED, never reasoned

`CERTIFIED_LOCATION_PAIRINGS` contains exactly **one** entry — `(global → US)` — and it **cites its
evidence** (the LRO id and the read-back). Every other pair is **refused**, not guessed. This is the same
certify-then-enforce doctrine `vertex_env.CERTIFIED_VERTEX_REGIONS` applies to regions: **a pairing
enters the table when it has been OBSERVED to work, never when it merely seems reasonable.** A guess here
produces a config that reads back beautifully and logs nothing.

*(The irony, on the record: rev. 3 condemned `bq mk`'s **US multi-region default** as **the bug**. It was
right all along, for a reason nobody had. We were right to distrust a default we hadn't reasoned about;
we were wrong to think distrust was the same as understanding.)*

## 5. §4c — the clobber trap, disarmed BY CONSTRUCTION

**The trap is LIVE, not theoretical.** There is **no `updateMask`**: every write is a **FULL-OBJECT SET**.
A partial write **silently wipes the rest** — logging-off wipes the search gate; search-on wipes logging.
**Nothing errors.** You lose a feature you believe is on.

**Before 2026-07-13 there was nothing to clobber. THERE IS NOW.**

`build_full_config_write_body( fetched_config, mutation )`:

1. **REFUSES** to build a body when `fetched_config` is `None` or `{}`. **You cannot construct a write
   here without having read first.** The clobber trap is closed *by construction*, not by discipline.
2. **Deep-merges** the mutation onto the fetched object, so **fields this codebase has never heard of** —
   a future `claudeFeatureConfig` key, a server-added default — **survive the round trip**.
3. **Re-checks** that no previously-present leaf was dropped, and raises naming the casualties. *(Belt to
   the read-modify-write suspenders. "Should be unreachable" is how the last five defects introduced
   themselves.)*

## 6. AC-D7 is a **ONE-SIDED TEST**. It can confirm logging; it can never refute it.

A deflationary finding, and the harness **enforces** it: for a subject-less probe, `run_probe()` can
return `PROVEN` or `INADMISSIBLE` and **never `REFUTED`** (`test_a_subjectless_probe_can_never_return_REFUTED`).

**Why**: AC-D7's canary **IS** its subject — the Anthropic call is the very thing under test — so
**nothing else can calibrate its null.** *"No rows"* is **not** *"logging is broken."*

**What would make it two-sided**: a **readout positive control** that does not ride the Vertex write path
at all — we insert one row into a table **we** own (`vertex_logging.harness_readout_canary`) and read it
back **through the same query path**. That proves **auth + dataset + query path** are demonstrably awake,
which **upgrades a null** from *"we cannot see ANYTHING"* to *"our readout works; the Vertex write
pipeline produced nothing in this window."* Those are different claims and **only the second is worth
reporting to anybody.** It does **not** eliminate ingest lag — nothing can — it eliminates **the other
explanations**, which is the whole of what a positive control is for.

`readout_positive_control_sql()` **emits** that SQL. It does **not** run it: the INSERT is a **GCP write**
(into our own dataset, no model spend) and is therefore listed for authorization like everything else.

## 7. AC-D5 precedence (F-D18) — "FAILED" and "INDETERMINATE" are not the same verdict

AC-D5 (did web search fire?) **necessarily rides the BigQuery log** — legitimately, because the logged
request/response is the **only** place a tool-use block is visible. That makes it **dependent** on AC-D7,
and the dependency is dangerous:

> ### **If AC-D7 is not PROVEN, an absent search block does NOT read "search didn't fire." It reads "WE CANNOT SEE."**

`classify_ac_d5( logging_verdict, search_block_found )`:

| Logging verdict | Block found? | AC-D5 |
|---|---|---|
| *any* | ✅ | `FIRED` — **a positive needs no calibration.** If we can SEE the block, the log worked for that row. |
| `PROVEN` | ❌ | `NOT_FIRED` — a **real** negative. |
| `REFUTED` / `INADMISSIBLE` | ❌ | **`INDETERMINATE`** — we are blind. **Never `FAILED`.** |

Reporting a blind instrument as a negative result is how a team "learns" something false and **rolls back
the wrong thing.**

## 8. OSQ C-4 — retry-safety is a claim about the SECOND write, so it tests the SECOND write

§4d adopted a dataset-level URI and called it *"retry-safe by construction."* That was an **inference
from a GAP in the schema**: the schema documents the *project-only* form (*"the Dataset and Table is
created"*) and the *full-table* form (*"the Dataset must exist and table must not exist"*). It says
**nothing** about the *dataset-level* form. **Silence was read as permission** — the disease this design
exists to cure, committed inside one of its own fixes.

`assert_double_write_retry_safe()` judges the **second** write: both LROs **polled to `done` with no
`error`** (§4h — *HTTP 200 means ACCEPTED, not APPLIED*), **and** the config **byte-identical** across the
re-apply.

> ### A second write that 200s while silently mangling the config is not retry-safety. **It is the clobber trap wearing a green tick.**

The judgment is built. **The write is Mr. Radio's to execute.**

## 9. 🔴 The privacy question (`823be9cc`) — and the prior I had to kill in my own harness

**The question**: does the logging config cover the Model Garden MaaS publishers (`deepseek-ai`,
`openai`), or **only** the Anthropic one? **UNKNOWN. UNTESTED.**

**Why it matters**: `openai/gpt-oss-120b-maas` streams a second channel alongside `content` —
**`reasoning_content`**, the model's **private chain-of-thought, verbatim.** If the config **does** cover
it, we are persisting **raw CoT into BigQuery at 100% sampling** — **a privacy edge Rick has NOT
approved.**

### 9a. I wrote a confident structural prior into this harness. Half of it was rotten.

My first draft argued the MaaS publishers are **doubly** out of scope: *(a)* the config's resource path is
`publishers/anthropic/models/{model}`, and *(b)* the observed MaaS traffic **served at `us-central1`**
while our config sits at `global` — a different publisher **AND** a different location. **Two independent
reasons.** It felt settled.

**Then I read bug `13c3c480` (Cheech's lane).** The MaaS `openapi/chat/completions` endpoint **IGNORES
its `locations/{region}` path segment** — byte-identical `200`s for `global`, for `us-central1`, and for
the **fictional region `narnia-1`**.

> ### So *"the MaaS traffic served at `us-central1`"* is **NOT an established fact.** It is an **echo of a path segment nobody honored.**
> ### **The region axis of that instrument cannot come out otherwise. It is not an oracle — and it may not prop up my prediction.**

**Leg (b) is dead.** One leg remains, not two. I had imported a fact from a **blind instrument** into my
own reasoning — **in the glow of a design I was pleased with.** *Rigor fails where relief lives.* The
harness text now says so, in `describe_live_calls()`, where the next reader will actually hit it.

**Consequence: the prior is weaker than I wrote it, which is exactly why the probe must actually be RUN.**

### 9b. How the harness answers it — and how it could come out otherwise

Fire **two** calls, each with its **own** sentinel, **subject FIRST**:

1. **SUBJECT** — `openai/gpt-oss-120b-maas`, sentinel `S₁`. *(fired first — ordering is evidence)*
2. **CANARY** — `claude-opus-4-8` @ `global`, sentinel `S₂`. *(fired second — the known-good write)*

| Outcome | Verdict | Meaning |
|---|---|---|
| `S₁` **lands** | `PROVEN` — **immediately**, no canary needed | 🔴 **MaaS IS covered. Raw chain-of-thought is being persisted at 100% sampling. HALT and escalate. Do NOT dump the row.** |
| `S₁` silent, `S₂` **lands** | `REFUTED` — an **admissible** null | The config does **not** cover that publisher. The readout was **demonstrably awake** in the same window. |
| **Neither** lands | **`INADMISSIBLE`** | We are blind. **This is NOT "MaaS isn't logged."** Extend the bound and re-run. |

**Could it have come out otherwise?** Yes — and that is the point. `S₁` and `S₂` ride the **same dataset,
the same query path, the same auth**. If the config covered `openai`, `S₁` **would** have appeared in the
very table where `S₂` demonstrably did. **A green here could have been red.**

**The one residual, stated and not buried**: ingest lag is assumed **not to be publisher-dependent.**
There is **no same-publisher positive control**, and one **cannot exist** without first enabling logging
for that publisher — **which is the very thing under test.** Firing the subject **first** weakens the lag
explanation; it does not kill it. `ProbeResult.residual_assumptions` carries this text into every
`REFUTED` verdict, so no reader can inherit the conclusion without the caveat.
