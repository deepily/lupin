## TL;DR

The arbiter's handling of **manager-SUBJECT** escalations (an escalation whose subject is
itself a declared manager) has **two independent gaps**, both discovered today, both tracing
to the same lineage: `ff91cff4` and `92c7ab1d` established the correct *principles* but each
was applied to only ONE code path, leaving sibling paths uncovered.

- **Gap 1 — DETECTION (`e5e33795`).** The bridge-fresh veto (`92c7ab1d`, `_session_bridge_fresh`)
  suppresses a false "stuck" flag when a session's own session-bridge is fresh. It guards the
  **`_auto_poke`** path (arbiter_job.py:3801) but NOT the **parallel stuck-manager advisory**
  path (`_tap_managers` → `_attention_workers` → `_format_stuck_manager_advisory`). Result:
  a manager working a long op (event-stale but bridge-FRESH) false-fires a case-20 "STUCK/DEAD"
  to Rick. **Confirmed 2026-07-08 10:08:40 EDT: Tiberius flagged STUCK/DEAD while its bridge
  was continuously 0–15s fresh.**

- **Gap 2 — ROUTING (`f48f089d`).** `ff91cff4` ruled that a manager-subject reap/replace
  escalation is **Rick-only** (case 20, `TIER_RICK_ONLY`) — "managers answer to Rick, not each
  other; Rick actuates reap/replace." It swept case 13→20 but NOT the sibling manager-subject
  advisories **cases 15/16/17**. Case 17 (MANAGER-DONE) still fans **"consider reaping
  <manager>"** to every active PEER manager. **Confirmed 2026-07-08: Tiberius received a
  peer-DM telling it to consider reaping Mr. Radio** — a peer has no standing to reap a peer.

**One coherent fix lane** ("arbiter manager-subject hardening") closes both: extend the
bridge-veto to the advisory detection path, and extend the Rick-only routing principle to the
sibling manager-subject advisory cases.

## Gap 1 — Detection: bridge-veto coverage gap (`e5e33795`)

### Evidence (2026-07-08, journal)

Fleet renders, Tiberius (`cda5f427`) — bridge age / event age:

| Tick (EDT) | State | bridge / event | verdict |
|---|---|---|---|
| 10:03 | working | 2s / 7m | LIVE |
| 10:05 | working | 14s / 9m | LIVE |
| **10:08** | **holding peer:rachel** | **15s / 40s** | **LIVE** ← case_20 "STUCK/DEAD" fired HERE |
| 10:12 | holding peer:rachel | 1m / 2m | LIVE |

The session-bridge heartbeat was **continuously fresh (0–15s)** the whole window — the session
was demonstrably alive; only its *domain-event* age grew (busy manager mid-long-operation).
The auto-poke gate correctly saw it: `arbiter_poke_gate` logged `stuck_pokeable=False
why=['not_stuck']` all morning; **zero** stuck-pokes fired; `_poke_count` stayed 0.

### Root cause

The `_auto_poke` path drops a bridge-fresh session from `pokeable` (arbiter_job.py:3801,
`_session_bridge_fresh`) — working correctly. But the **case-20 "appears STUCK/DEAD" text**
comes from `_format_stuck_manager_advisory` (arbiter_job.py:2432/2444), fired from a **different
path**:

```
_tap_managers (arbiter_job.py:2449)
  → attention = _attention_workers(fleet_view, graph, now, bridge_mtimes)   # pulls in the event-stale manager
  → for view in attention:
        if _subject_is_manager(view):
            _route(CASE_STUCK_MANAGER_RICK_ONLY, _format_stuck_manager_advisory(view, free_n))   # arbiter_job.py:2489-2496
```

This branch does **not** apply `_session_bridge_fresh` to the manager-subject before routing.
The `bf8c5cbb` bridge-fresh handling inside `_attention_workers` augments PEER liveness in the
blocked-roster; it does not veto a stuck-flagged manager-SUBJECT on its own fresh bridge.
(Runtime-confirmed: `_default_manager_bridge_mtimes()` returns a healthy, correctly-keyed map —
the reader is NOT dormant; it is simply not consulted on this path.)

### Proposed fix

Before routing `CASE_STUCK_MANAGER_RICK_ONLY` at arbiter_job.py:~2494, apply the same
subject-liveness veto `_auto_poke` uses at 3801:

```python
if self._subject_is_manager( view ):
    if self._session_bridge_fresh( view.get( "persona" ), now, bridge_mtimes ):
        continue                                   # fresh-bridge subject: NOT wedged — suppress (mirror 3801)
    ...existing _route(CASE_STUCK_MANAGER_RICK_ONLY, ...)...
```

Fail-safe: `bridge_mtimes` None/unwired → today's behavior; suppress ONLY on positive
fresh-bridge evidence. Emit the existing `arbiter_stuck_bridge_veto` journal event on suppress.

## Gap 2 — Routing: manager-subject peer-misroute (`f48f089d`)

### Evidence (2026-07-08)

Peer-DM Tiberius received (message_id `8a952b82`, thread `fd77a031`):
> "MANAGER-DONE (advisory, NOT manager-stale): mr radio is silent 45m and owes NO non-terminal
> work — it appears finished/idle. **Consider reaping it.** One-time notice."

The *observation* (Mr. Radio idle) was accurate; the *routing* is the defect — a peer manager
was told to consider reaping a peer.

### Root cause

`CASE_MANAGER_DONE_ADVISORY` (17) routes `TIER_RICK_AND_MANAGERS` (arbiter_routing.py:137). The
`b9911943` `exclude_persona` filter drops only the SUBJECT from the fan-out (Mr. Radio isn't
told to reap itself) but **still fans to every active PEER manager** (arbiter_job.py:~1853:
"cases 14/16/17 … must NOT fan out to that subject, only to its PEER managers + Rick"). So the
"consider reaping it" directive reaches peers.

`ff91cff4` already ruled this pattern inappropriate for the STUCK/DEAD case and made it
**Rick-only** (case 20), excluding BOTH the subject AND peers — but swept only case 13→20, not
the sibling manager-subject advisories 15/16/17.

### Sibling matrix (CORRECTED numbering — Clayton 😎, verified vs `CASE_TIERS` constants 2026-07-08)

> **Numbering fix:** an earlier draft labeled STALE as "case 15" — WRONG. In code:
> `CASE_MANAGER_STALE_ADVISORY = 14`, `CASE_FLEET_DARK = 15` (already `TIER_RICK_ONLY`, no
> manager peers exist by definition — out of scope), `CASE_MANAGER_AWAITING_USER = 16`,
> `CASE_MANAGER_DONE_ADVISORY = 17`. The manager-subject siblings are **14 / 16 / 17**.

**Disposition discriminator (Clayton's D1 axis):** *does a PEER manager have a legitimate
ACTION available?* If no → the peer fan-out has zero coordination value on a manager-subject →
Rick-only. If yes (adopt an orphaned crew) → keep the peer fan-out.

### Proposed fix

**Option A (recommended):** route `CASE_MANAGER_DONE_ADVISORY` (17) → `TIER_RICK_ONLY`, mirroring
`ff91cff4` case 20. Simplest, consistent with the ruling. Per-case judgment for 15/16 (a stale /
blocked-on-Rick FYI to peers may have coordination value that "consider reaping" does not).
**Option B:** keep a peer FYI but STRIP the reap directive from the peer-fanned copy. Recommend
A for consistency.
