## 3. F-Rio-2 — §5d: "never a manager" is a documented wish guarding the wrong door (Layer 1)

**Mr. Radio asked: is it a real control or a documented wish? It is a wish — and it is pointed at a door that is already bolted, while the open door is unmentioned.**

### What I measured (ran, not recalled)

**(a) The env DOES propagate up to the tmux boundary.** The cosa-voice MCP server is, per its own module docstring, a **"stdio subprocess of `claude`"** (`src/lupin_mcp/session_spawner.py:11`) — so it inherits the Vertex env of a `claude-vertex.sh`-launched session. And its spawn runner inherits it onward:

```python
# src/lupin_mcp/session_spawner.py:64-67
return subprocess.run(
    argv, capture_output=True, text=True, timeout=30,
    env=( { **os.environ, **env } if env else None )   # None → inherit; and os.environ is the BASE even when env is given
)
```

**(b) But the env does NOT cross the tmux boundary.** Empirical probe against the **live** fleet tmux server (the real condition — 3 cascade sessions running):

```bash
RIO_VERTEX_PROBE=leaked tmux new-session -d -s rio-envprobe 'env | grep -c RIO_VERTEX_PROBE > /tmp/out'
# → 0        (the client-side var did NOT reach the spawned pane)
```

This is not a surprise to the codebase — **`start-cc-with-tmux.sh` already documents it**:

> `# Forwarded via -e so it crosses the tmux boundary regardless of the tmux server's frozen env (a bare parent export would NOT reach claude).` — `src/scripts/start-cc-with-tmux.sh:117-118`

The script therefore maintains an **explicit `-e` allowlist** (persona chains, `CLAUDE_CODE_DISABLE_MOUSE`, `MCP_TOOL_TIMEOUT`, …). **`CLAUDE_CODE_USE_VERTEX`, `ANTHROPIC_VERTEX_PROJECT_ID`, `CLOUD_ML_REGION`, and `ANTHROPIC_DEFAULT_*_MODEL` are not in it.**

### Therefore

**A Vertex-launched manager spawning fleet workers produces workers on MAX, not Vertex.** The tmux server's frozen environment strips the Vertex vars. §5d's stated catastrophe — *"every spawned worker silently lands on metered billing"* — **does not happen on the fleet spawn path.**

### And the door that IS open

The leak is real for anything launched as a **direct subprocess of the Vertex `claude` process — no tmux in between**:

- a `claude -p …` invoked from the session's **Bash tool**;
- **in-process Claude Agent SDK** (`sdk_query`) calls;
- consequently, **any bounded-CC work driven from that session**.

This collides head-on with `CLAUDE.md § COST MODEL`, whose entire premise is that **bounded CC is covered by the Max plan at zero marginal token cost**. A Vertex-launched session that runs bounded-CC work would **silently convert already-paid-for Max work into metered GCP spend** — the exact inversion of the cost model the toggle exists to protect. **The doc never mentions this path.**

*(Scope honesty: (a) and (b) I measured. The direct-subprocess leak follows from standard `fork`/`exec` env inheritance with no tmux hop — I did **not** execute a billing-level end-to-end proof of it, and I am flagging it as an inference with a named test, not as a measurement. That test is written below.)*

### Required close — mechanical, not prose

1. The launcher exports a tripwire: **`LUPIN_VERTEX_SESSION=1`** alongside the Vertex vars.
2. **A guard in Python, at the seam** — fail loud, non-zero, named error — refusing to launch bounded-CC / `sdk_query` / `claude -p` work when `LUPIN_VERTEX_SESSION=1` is present, **or** explicitly scrubbing `CLAUDE_CODE_USE_VERTEX` + `ANTHROPIC_VERTEX_*` + `CLOUD_ML_REGION` from the child env (deny-list) so Max-covered work stays Max-covered.
3. **Delete the §5d "never a manager" prose**, or demote it to a note that says what is now known: *the fleet spawn path is protected by tmux's frozen env; the direct-subprocess path is not.* A caution that misidentifies its own threat is worse than none — it buys false confidence.

**Why Python and not bash**: `session_spawner.py`'s own docstring says *"All side effects (subprocess, clock) are **injected** so the logic is **unit testable to 100%**"* (`:19-20`). The guard placed there is **coverable under the existing `pytest --cov` gate** — which also answers §9 Q6 (below). A prose caution in a markdown file has no coverage, no test, and no exit code.

**AI-executable ACs this creates** (all `EXECUTOR: AI`):
- Spawn a fleet worker from a process with `LUPIN_VERTEX_SESSION=1` → assert the worker's resolved env contains **no** `CLAUDE_CODE_USE_VERTEX` (regression-locks the tmux-strip behavior so a future `-e` addition can't silently un-bolt the door).
- Invoke the bounded-CC path with `LUPIN_VERTEX_SESSION=1` → assert **non-zero exit + the named error** (red-first).

## 4. F-Rio-4 — Coverage (Convention 6), and the answer to §9 Q6

Phase 3 says *"pytest against `--print-env`"* with **no coverage assertion**, against a **100% lines/branches/functions hard gate**. Bare "tests pass" is the same hollow shape as an untagged AC.

**§9 Q6 asks whether the logic should live in Python with a thin shell wrapper. The coverage mandate decides it — it is not a taste question.** A bash script cannot be measured for line/branch/function coverage by `pytest --cov`; a `--print-env` subprocess test exercises it as an opaque box and reports **zero** coverage on the gate. Put the guard/compose logic in **Python** (importable, injectable, 100%-coverable — exactly as `session_spawner.py` already does it) with a thin `claude-vertex.sh` wrapper that `exec`s it. Then §9 Q6 stops being an open question and the guards in F-Rio-2 become coverable in the same stroke.

## 5. F-Rio-5 — Split execution from ratification on the money/retention gates

Phase 1 bundles five acts behind one **"Rick's go"**: enable an API · read a policy · **open** a policy · create a dataset · POST a config that **both** enables logging **and** flips the data-retention opt-in.

`advancedAiEnabled` (retention) and `loggingConfig` (observability) ride **the same API call**. That means Rick's single "go" silently ratifies a retention posture change bundled with a benign logging change. **Unbundle them in the request narrative**: state plainly, at the gate, that this one POST does both. Rick ratifies the *retention* decision explicitly; the AI executes the call.

Everything else in Phase 1 — API enablement, policy *read*, dataset creation — is `EXECUTOR: AI` with no gate at all.

## 6. F-Rio-6 — The LRO is never polled (the §7 lesson, repeated)

`setPublisherModelConfig` returns a **`GoogleLongrunningOperation`** — the doc says so in §4 and then never polls it. A 200 on the POST means *the operation was accepted*, not *the config was written*.

The doc's own §7 lesson is: *"a silenced stderr turns an auth failure into a confident wrong answer."* An un-polled LRO is the same shape: the POST succeeds, the operation later fails, `fetchPublisherModelConfig` still 404s, and the plan believes logging is on. Combined with the §4 region-coupling trap, this is **two independent ways to get a false "logging is on"** — and the doc's pilot AC ("Query the table") would catch it only *after* real money has been spent.

**Close** (`EXECUTOR: AI`, and this is the pre-flight the region trap needs): poll the LRO to `done: true` **and** assert `error` is absent **and** `fetchPublisherModelConfig` **at the launcher's region** returns `loggingConfig.enabled == true` — *before* the pilot session is allowed to launch. This subsumes §9 Q2: the read-back is not optional, and it belongs at launcher startup, because an observability feature that silently no-ops is worse than one that is off.

## 8. Audit of the REWRITE target (per Mr. Radio's live update)

I was told §A/§C are being rewritten around a single region SSOT because (a) `cloud-run-config.sh` already exists and (b) `us-east5` 403s on `claude-opus-4-8`. **One correction before the rewrite lands, because the rewrite would otherwise inherit a false premise:**

**`src/scripts/cloud-run-config.sh` is TRACKED, not git-ignored.**
```
git ls-files src/scripts/cloud-run-config.sh  → src/scripts/cloud-run-config.sh
git check-ignore -v …                         → not matched by .gitignore
```
What *is* git-ignored is the **`cloud-run.env`** file the resolver optionally sources (with a tracked `cloud-run.env.example` template). The resolver itself is in the repo and already does exactly what §5c.2 wants to reinvent:

```bash
PROJECT_ID="${LUPIN_GCP_PROJECT_ID:?Set LUPIN_GCP_PROJECT_ID (no sandbox default …)}"   # fail-loud
REGION="${LUPIN_GCP_REGION:-us-central1}"
```

**The ownership consequence — and it is a real trap for the rewrite:** because the project ID resolves from a **git-ignored `cloud-run.env` (or a shell export)**, a pytest that shells the launcher and expects it to succeed **is green on Rick's box and red in a fresh clone, a worktree, or CI** — the resolver `:?`-aborts when `LUPIN_GCP_PROJECT_ID` is unset. That is an environment-dependent test masquerading as a passing one, and Lupin has been bitten by exactly this class before (worktree false-greens).

**Required**: the Phase-3 tests must **inject `LUPIN_GCP_PROJECT_ID` / `LUPIN_GCP_REGION` explicitly** (monkeypatch/env fixture) and must **never** depend on the developer's local `cloud-run.env`. Add a red-first case asserting the launcher **fails loud** when the project ID is unset — that is the resolver's contract, and it deserves a test rather than a developer's ambient shell. Both `EXECUTOR: AI`.

**Region SSOT**: adopting `LUPIN_GCP_REGION` is correct, but note its default is **`us-central1`** while the doc's evidence table was built on `global` + `us-east5`. **Every §2 verification row taken at `us-east5` is now void** (403 on the model) and must be re-run at the SSOT region before the rewrite quotes it. The logging config, the launcher's `CLOUD_ML_REGION`, and the `fetchPublisherModelConfig` read-back must all resolve from that one variable — `EXECUTOR: AI`, and it is the pre-flight in F-Rio-6.
