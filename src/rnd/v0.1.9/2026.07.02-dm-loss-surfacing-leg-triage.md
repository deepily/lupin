## TL;DR

`dm_send` returns `status:sent`, the row is store-durable (`dm_list` returns it), and the
message **reaches the recipient's listener and is correctly buffered**. The break is purely in
the **buffer → surface** leg: a DM buffered while the recipient is mid-turn is surfaced only if a
*later* hook happens to drain it in the same session, and the salience/guarantee of that drain is
inconsistent. Result: DMs are either **orphaned forever** (session ends first) or **drained at low
salience** (buried in a heads-down turn, never acknowledged).

**Not** a WS/dispatch/classification fault. `dm.py` dispatch, WS `job_id` routing, `ai_to_ai`
classification, and `_buffer_message` all work — the lost messages are *in the buffers right now*.

## The delivery pipeline (as built)

```
dm_send (MCP) → POST /api/dm/send → execute_dm_send
  → persist notifications row (direction=ai_to_ai)          [durable — dm_list reads this]
  → notification_queue.push_notification(job_id = recipient_session[:8])
     → WS notification_queue_update
        → recipient CCNotificationListener._handle_event
           → direction==ai_to_ai → _deliver_peer_dm
              ├── _recipient_is_injectable()==True  (IDLE/honored/cap_reached)
              │      → _handle_peer_dm → tmux inject   ← RELIABLE, HIGH salience ✓
              └── _recipient_is_injectable()==False (BUSY mid-turn / poked / None)
                     → _buffer_message → cc-buffer-<hash>.jsonl   ← BEST-EFFORT ✗
```

The buffered branch is surfaced only by a **subsequent hook** draining the JSONL:

| Next event after a DM buffers | Drain site | Framing | Salience | Outcome |
|---|---|---|---|---|
| PreToolUse (model calls another tool) | `pre_tool_use.py` | `build_voice_deny_response` | **HIGH** — deny + interrupt | ✓ surfaced |
| PostToolUse only (model writing final answer, no more tools) | `post_tool_use.py` | `build_additional_context` | **LOW** — context append, no interrupt | ✗ buried, not acknowledged |
| Clean Stop, speakerphone | `stop.py` → `deliver_pending_peer_dms` (tmux) | peer-DM reminder | **HIGH** | ✓ (but see gaps) |
| Stop re-fire (`stop_hook_active is True`) | — early-exit `stop.py:1990`, **no drain** | — | — | ✗ not drained |
| Session ends / reaped, no further hook | — | — | — | ✗ **PERMANENT loss** |

The `_recipient_is_injectable` fork is decided from the **last emitted heartbeat outcome**, which
only updates at a Stop. So a session heads-down mid-turn (last outcome `poked`/None) always takes
the fragile BUFFER branch.

## Root cause

**The buffered-DM surfacing path is a best-effort side-channel with no guaranteed, uniformly-salient
delivery across the turn/session boundary.** One fork (idle→tmux) is reliable and high-salience; the
other (busy→buffer) depends on *what the session happens to do next*, producing two loss modes with a
single root:

- **Loss mode 1 — orphaned buffer** (84 confirmed): recipient buffers a DM, then the session ends /
  is reaped / parks with no subsequent draining hook. `SessionEnd` never flushes the buffer; the
  idle→tmux path for *new* DMs injects them directly and does **not** flush a previously-orphaned
  buffer. DM lost forever.
- **Loss mode 2 — low-salience drain**: the DM drains as `PostToolUse` `additionalContext` deep in a
  heads-down turn. It is technically "in context" but the focused model never surfaces/acknowledges
  it → the sender/manager perceive it as lost (matches the 4 receipts-chase cases).
- **Contributing Stop-backstop gaps**: `stop_hook_active` early-exit (`stop.py:1990`) skips the drain
  on a re-fired Stop; `_has_pending_voice` is a non-atomic peek (TOCTOU with a DM landing just after).

## Fix shape (DESIGN GATE — for Mr. Radio)

The **durable store already works** — `dm_list` returns every "lost" row. The surfacing leg should
stop depending on the lossy buffer as its system of record.

- **A. Store-backed inbox reconcile (recommended)** — at each turn boundary (`UserPromptSubmit` +
  `Stop`), poll `dm_list(since=<per-session high-water mark>)` and surface any unacknowledged DMs,
  persisting the high-water mark. At-least-once delivery, decoupled from the buffer; naturally drains
  orphans. Buffer stays as the fast/immediate path.
- **B. Patch the buffer gaps** — (1) `SessionEnd` hook flushes buffer → re-notify/re-queue; (2) make
  `PostToolUse` `ai_to_ai` high-salience (or defer DMs to the Stop drain only); (3) close the
  `stop_hook_active`/TOCTOU drain gaps. More surface area; still best-effort.
- **C. Hybrid** — buffer for immediacy + turn-boundary store reconcile as the guarantee.

**Lean: A (or C).** The durable notifications store is the right delivery guarantee; the buffer should
be an optimization, not the source of truth. This also retires the 84 orphans by construction.

## Phase-2 design — Option A: store-backed inbox reconcile (Mr. Radio ruling, 2026-07-02 11:26 EDT)

**Ruling**: Option A. The durable notifications store becomes the system of record it already is.
Fix-at-source (the buffer was a lossy side-channel promoted to system-of-record — that is the defect),
simplest reversible mechanism, drains-orphans-by-construction. Constraints bound below.

### Mechanism

A new host-side module `hooks/lib/dm_inbox_reconcile.py`, invoked from **`user_prompt_submit.py`**
(start-of-turn = fresh attention). It reconciles this session's DM inbox against a durable
per-session high-water mark and surfaces any un-surfaced DMs as `additionalContext` — **no
interrupt/deny** (constraint 3).

```
UserPromptSubmit → reconcile( session_hash ):
  1. state = read_hwm( session_hash )              # {cursor_ts, surfaced_ids[]}  durable, /clear-proof
  2. ok, rows = GET /api/dm/list?since=cursor_ts&limit=200   (X-API-Key; _request() triple; fail-open)
  3. mine = [ r for r in rows if r.job_id == session_hash[:8] ]          # inbox is user-scoped → filter
  4. fresh = [ r for r in mine if r.message_id not in surfaced_ids ]     # dedup by message_id (constraint 2)
  5. fresh.sort(created_at asc)                                          # read order
  6. context = "\n".join( build_peer_dm_reminder(r) for r in fresh )    # SAME framing as buffer path
  7. write_hwm: cursor_ts = max(cursor_ts, max(created_at of `mine`));   # advance by MY rows only —
                surfaced_ids = bounded_fifo( surfaced_ids + [r.id for r in fresh], cap=500 )   #  never skip a buried DM
  8. return context   →  appended to UserPromptSubmit additionalContext
```

- **Auth**: `X-API-Key` (`read_api_key()` from `src/conf/keys/notification-api-claude-code-dev`,
  `ck_live_…`). **Empirically verified** it resolves to the human owner's user_id, so
  `/api/dm/list` returns the owner's full inbox (all sessions) — hence the `job_id` filter.
  No per-turn `/auth/login`. Reuses `task_store_client._request()`'s never-raise triple.
- **HWM file**: `.dm-inbox-hwm-{session_id}.json` in the SAME runtime-state base dir as the
  heartbeat hold file (`heartbeat_hold._resolve_base_dir`) → survives `/clear` (constraint 2).
- **Framing**: reuses `build_peer_dm_reminder` verbatim (one framing, both paths — no drift).
- **Salience**: additionalContext at turn-start, NO deny (constraint 3). The PreToolUse
  high-salience deny keeps serving mid-turn immediacy (constraint 1 — untouched).
- **Fail-open**: any transport/auth/parse error → surface nothing, do NOT advance HWM, never raise
  (the turn proceeds; next turn retries). Bounded aggressive timeout (~1s) — UserPromptSubmit is a
  turn-boundary, not the every-tool hot path, but still kept cheap.

### Constraint conformance
1. **Buffer/inject/PreToolUse-deny UNTOUCHED** — reconcile is purely additive (new module + one call

2. **Durable per-session HWM, dedup by message_id** — HWM file in the hold-file family; `surfaced_ids`
   FIFO is the exact dedup.
3. **Surface at UserPromptSubmit as additionalContext, no interrupt/deny** — yes.
4. **84 orphans: NO live replay** — inventory below; dry-run-first janitor sweep proposed as a

5. **RED-first, 100% L/B/F, commit-HELD behind Cheech APPROVE** — the module is pure-logic-cored
   (IO seams injected) for full branch coverage; repro test drives the buffered-then-turn-ends path.

### Known bound (no silent cap)
The user inbox is shared across all fleet sessions and `/api/dm/list` caps at 200 newest-since-cursor.
In a DM storm (>200 fleet DMs in one turn gap) a quiet session's older un-surfaced DM could fall
below the page and be missed until traffic subsides and its cursor catches up. Reconcile **logs when a
page returns full (count==limit)** so truncation is visible. Pagination/offset hardening is a noted
follow-up, not required for the 4 receipted cases (all recent, low-volume windows).

### At-most-one redundant surface (accepted)
A DM surfaced mid-turn via the buffer's PreToolUse-deny is NOT recorded in the HWM (buffer path is
untouched), so the next UserPromptSubmit reconcile may re-surface it exactly once, then record its id
→ never again. Harmless per the ruling ("reconcile makes their losses harmless"); documented, not fixed.

## Watch-item (B) resolution — Rio ⚡ (2026-07-02 ~13:05 EDT): CLEARED, benign

Cheech advisory (B) — "watch event-loop latency after go-live (notify-sensitive loop, bug `81854972`)" —
triaged post-go-live. **Verdict: no latency regression; the reconcile's per-turn `GET /api/dm/list`
architecturally CANNOT reproduce 81854972.** No code change warranted.

**Why it's orthogonal to 81854972.** Bug 81854972 was *unbounded embedding daemon threads on the
notification WRITE path* (`InputAndOutputTable.insert_io_row`) saturating GPU + GIL and starving the
asyncio loop → `/health` timeouts / docker "unhealthy" (fixed by the shared **bounded** embedding pool,
`embedding_pool.py`, 2 workers / 64 pending). The reconcile adds a **READ**, and:
1. **Off-loop.** `list_dms` (`routers/dm.py:509`) is `async def` but wraps all DB work in a nested sync
   `_work()` dispatched via `result = await asyncio.to_thread( _work )` (`:527`) — the query never runs on
   the event loop, so a slow read cannot block it.
2. **No embedding / GPU / thread-spawn.** `NotificationRepository.get_dm_inbox` (`:184`) is a pure indexed
   SELECT — `recipient_id == ? AND direction == 'ai_to_ai' AND is_hidden == False`, optional
   `created_at > since`, `ORDER BY created_at DESC LIMIT`. It touches none of the 81854972 machinery.
3. **Human-turn-paced + bounded.** 1 call per UserPromptSubmit per session, 1.5s fail-open ceiling.

**Empirical (live :7999, production `_fetch_inbox` path, 8-call samples):**
- Steady-state tail (`since`=HWM, ~11 rows): **min 199 / med 200 / max 330 ms**.
- Near-worst-case full page (200 rows, `page_full=True`): **min 205 / med 213 / max 226 ms**.
- Row count is negligible (11 vs 200 rows → same ~200 ms) → the ~200 ms floor is **fixed overhead**
  (HTTP round-trip + `require_api_key_or_jwt` + per-call `_load_settings()` config read + threadpool
  handoff), not query cost. All well within the 1.5s fail-open budget (>1.2s headroom).

**Non-blocking residuals (not pursued — immaterial):**
- The ~200 ms fixed floor could be shaved by memoizing `_load_settings()` (advisory C already flags the
  partly-dead `timeout_seconds` load) — a micro-opt, not a latency risk.
- Default `asyncio.to_thread` threadpool-token contention is only a concern at implausibly large fleet
  size; human-turn pacing + off-loop + fast query keep it far from saturation at current fleet (<20).
- The 200-row page cap (advisory A/C known-bound) is a correctness edge (a session receiving >200 DMs
  *between two of its own turns* could miss older ones — implausible per-session), latency-orthogonal.
