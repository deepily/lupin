## 1. Why this exists

When Rick answers a blocking ask, the answer is stored durably and then handed back by waking an **in-memory** dict. If that dict entry is gone, the answer is stored and never travels.

`src/cosa/rest/routers/notifications.py`:

| Line | What happens |
|---|---|
| `:1284` | `_submit_response_sync(...)` persists the answer to Postgres. **Durable. Survives anything.** |
| `:1316` | `if notification_id in pending_responses:` → wake the SSE waiter |
| `:1321` | else: print `"No SSE stream waiting for {id} (may have already completed)"` **and nothing else** |

The waiter lives in one process's memory. A `:7999` bounce wipes every entry; a client reload or network blip wipes one. The asking session then waits out its 600-second timeout and re-asks — the duplicate-prompt symptom.

**Rick's own words for the scenario**: *"three action-requested notifications arrive in quick succession and then the server gets rebooted and drops all of the currently active user sessions."* All three answers land in the database. None of them reach the sessions that asked.

**This is not bounce-only.** R1 (auto-reload off, shipped 2026-08-01 morning) removed the *churn* that made it constant. It did not touch the hole. Any SSE drop — client reload, network blip, closed tab — orphans a waiter identically.

**Intended outcome**: an answer a human typed always reaches the session that asked, whether that session is connected, disconnected, or has been re-spun since.

**Nobody did anything wrong.** The waiter was the right mechanism for a server that never restarted; it became the wrong one when the fleet grew a comms channel that shares a process with everything else.

## 2. Rick's rulings — design to these

1. On response, **check whether the socket is still held open. If it is, push the answer down it** — a held-open socket is the cheapest path and there is no reason to waste one. **If it isn't**, write the answer back through the **normal notification channel, keyed by the notification's ID.** The durable channel is the fallback, not the replacement. *(His words: "Why waste a socket that's been held open?")*
2. **Never expire the record.** No live session ⇒ mark it owed.
3. A returning session **pulls everything accumulated in its absence** — mirror the human client's recovery behavior to the per-session Claude Code listeners.
4. Retrieval is **persona-keyed**, session hash secondary.
5. Replay window **24 hours**, reusing the existing `notification undelivered max age hours` cap (`src/conf/lupin-app.ini:938`). Keep the row forever; bound the replay.
6. **Cross-session persona reuse — DELIVER IT, FLAGGED.** A new session that inherits the persona receives the dead session's owed answer. The envelope must say so: *"answer to a question asked by an earlier session of this persona."* ⇒ the retrieval query matches on `sender_persona` alone; `session_hash8` is a returned field used to set the flag, **not** a filter that suppresses delivery.
7. **Late answer after a re-ask — DELIVER BOTH, TIMESTAMPED.** No supersede, no dedupe by question text. ⇒ no question-identity mechanism is built; `notification_id` is the only dedupe key, and it only prevents delivering *the same answer* twice. If supersede is ever wanted it requires an explicit caller-supplied key, never fuzzy matching.

Rulings 6 and 7 make the envelope load-bearing: every replayed answer carries its **original question text**, its `responded_at`, and — when the asking session differs from the receiving one — the earlier-session flag. A bare answer with no question attached is worse than nothing; the model would bind it to whatever it is doing now. Replayed answers surface as context, **never** as an interrupt or a synthesized tool result (matching `dm_inbox_reconcile`'s no-interrupt contract at `:17-19`).

**Deferred, not blocking**: whether a shorter *actionable* window should sit inside the 24-hour replay window (a 20-hour-old "yes, proceed" is plausibly stale). Ship without it; revisit if it bites.

3. **The CC listener has no catch-up on connect** — a pure live subscriber. Verified by grep over `cc_notification_listener.py` and `base_listener.py` for `undelivered|backfill|catch.?up|hydrat|missed|since=`: zero functional hits. The human client *does* hydrate, and re-hydrates on the reconnect edge (`multiplexer/boot.ts:481-509`). **That asymmetry is the gap.** Corroborated by `src/rnd/v0.1.9/2026.07.28-ws-reload-circuit-breaker-and-durable-notify-path.md:129`: *"`GET /api/notifications/undelivered` already returns the items and no browser code calls it."*
4. **The pattern already exists in-tree.** `src/lupin_cli/claude_code/hooks/lib/dm_inbox_reconcile.py` is a durable at-least-once reconcile with a `/clear`-proof high-water mark, a capped dedupe ledger, an injected fetch seam, and a never-raise contract. **Build a sibling, not an invention.**
5. **The MCP client never learns the notification id** (`notification_models.py:432-501` — no id field on any terminal event), and there is no `GET /api/notifications/{id}` route (the path space is `{user_id}`-shaped). Re-attach-after-stream-death needs both.

> 🟢 **DESIGN-LEVEL INVARIANT — `responded_at IS NOT NULL` is the sole discriminator between "a human answered" and "a default was manufactured."** Stated once here; referenced by §4.1 (A), §4.4 (D), and §4.5 (E). It was discovered independently **three times** — Section B/D (owed predicate would replay forged defaults and live-pending asks), and Section E (a "landed" test keyed on `state` moving or `response_value` non-null maps an expired-offline row to *responded*). All three are the same defect. **Anything that decides answered-ness on `state`, on `response_value` being non-null, or on a bespoke "landed" boolean is wrong by construction** — an offline/expired row carries `state="expired"`, `responded_at` NULL, and a `response_value` holding the stored default no human typed. Only `responded_at IS NOT NULL` tells them apart. Every consumer names this term; none invents its own answered-ness test.

> ⚠️ **A receipt in this area has a trap.** `src/cosa/rest/db/schema_drift.py:6-8` still says *":7999 uvicorn runs with `--reload`, so the model edit IS the deploy."* **R1 turned reload off on 2026-08-01.** A model edit now sits **inert** until someone bounces — safer, but it changes the shipping rule: the migration must be *applied* before the bounce, not merely committed first, or migration and model land together at the next restart. **Fix that docstring as part of this change.**

## 4. The design

### 4.1 Schema — one nullable timestamp, no new `state` value

> **Revised (cascade Section A, 2026-08-01).** Findings A1–A7 accepted, none rejected. Changes from the first draft: `pushed_at` **dropped** (resolves K-A3 and the escaped-to-C finding together — see below); the index is declared the ORM way in `__table_args__` **and** built `CONCURRENTLY` in a non-transactional migration (Rachel + K-A1); `alembic heads` confirmed by two seats at **`38e025169a73`**; the frozen `state` enum was ruled **right, not avoidance**; verification moved to §5 with `EXECUTOR: AI` tags + coverage shapes (K-A2, K-A4).

Add **one** column to `Notification` (`src/cosa/rest/postgres_models.py`, beside `responded_at` at `:603`):

| Column | Meaning |
|---|---|
| `answer_delivered_at` TIMESTAMPTZ NULL | the handback mark: simultaneously the "owed" flag and the don't-deliver-twice guard |

**`pushed_at` is dropped — a deliberate concession, stated so it is not left implicit (K-A3).** The draft defined it as *"we actually emitted a frame,"* but the emitter (`push_notification`) silently no-ops and returns `None` on the paths that matter (§7 flagged this as unverified; the review confirmed it). A column that cannot honestly witness what it claims is the **same lie** as writing `state="delivered"` before the push — so it earns no place. Dropping it here also erases the finding that had escaped into Section C, which was the only site that wrote the column: **one deletion closes A and C at once.**

**Dropping `pushed_at` removes nothing the fallback relied on** (Manager's question, answered here). §4.3 step 4 decides whether to *also* write the durable carrier from `listener_delivered` — a synchronous return of the WS emit (`{user_delivered, listener_delivered, any_delivered}`, `websocket_manager.py:730-737`) — not from `pushed_at`, which was only ever an audit timestamp on a different wire.

> ⚠️ **`listener_delivered` is a SEND signal, not a receipt** (Rio, verified at source; corrects this section's first-draft answer). `emit_to_session` (`:410-440`) hands the frame to `send_json` inside try/except and returns `None` on success **and** on failure, so `listener_delivered` is True even when the socket dies after `send_json` accepts, or the listener reads the frame and dies before acting. It may therefore gate *whether to write the durable carrier*, but it must **NOT** set `answer_delivered_at` — that mark is **receipt-gated** (a woken SSE waiter, or the §4.4 ack). `listener_delivered` True leaves the row **owed** (`answer_delivered_at` NULL) so catch-up re-delivers, with the client `surfaced_ids` ledger absorbing the duplicate. Ruling 1 survives — still push down a held-open socket; just never mark a send as delivered. **The exact gating is Section C's, held for the Manager's C↔D reconciliation; Section A no longer depends on the distinction.**

**The index — ORM idiom, built without locking the table (Rachel + K-A1).** The table is kept forever (ruling 5), so a plain `CREATE INDEX` — a write-blocking `ShareLock` plus a full scan — is not acceptable, and `CREATE INDEX CONCURRENTLY` **cannot** run inside Alembic's default transactional migration. Two coordinated pieces, both required:

1. **Model** — declare the partial index the project's sole idiom (ORM `Index` with `postgresql_where` in `__table_args__`, at `:663`), so it is the schema of record and `alembic autogenerate` does not later report phantom drift:

   ```python
   Index(
       "idx_notifications_answer_owed",
       "sender_persona", "responded_at",
       postgresql_where=text( "response_requested AND responded_at IS NOT NULL AND answer_delivered_at IS NULL" ),
   )
   ```

   > **`responded_at IS NOT NULL` is load-bearing, not cosmetic (Section B reconciliation, fix 2).** Without it, an offline/expired persist — `state="expired"`, `responded_at` NULL, a machine default no human ever typed — matches the owed set and gets **replayed as if it were an answer**: the forged-answer defect reappearing inside its own fix. This term is the **§3 design-level invariant** (stated once there, referenced here): the owed set is exactly *answered-but-undelivered*, and "answered" means `responded_at IS NOT NULL`. §4.4's query carries the identical term; A's index makes it cheap.

2. **Migration** — build it non-transactionally so `CONCURRENTLY` is legal:

   ```python
   with op.get_context().autocommit_block():
       op.create_index(
           "idx_notifications_answer_owed", "notifications",
           ["sender_persona", "responded_at"],
           postgresql_concurrently=True,
           postgresql_where=sa.text( "response_requested AND responded_at IS NOT NULL AND answer_delivered_at IS NULL" ),
       )
   ```

**Both sides are mandatory (Rachel's precision).** `schema_drift.py` checks columns only and will never flag a missing index — so the model declaration is what keeps the index honest against `autogenerate`; the migration is what actually builds it on `:8000`. Declaring one without the other passes `schema_drift` while `autogenerate` reports phantom drift.

**Do not** fix the `delivered`-at-persist-time lie by writing `queued` instead. `get_undelivered_for_recipient` selects exactly `['created','queued']` (`notification_repository.py:498`), so every in-flight ask would immediately land in the human's AFK inbox and missed-badge — the shape of the 2026-06-03 TTS storm. **Leave `state` frozen; add the one honest column alongside it.** (Ruled right, not avoidance — the alternative touches 13 server + 5 client sites: `notification_repository.py` `:402-405`, `:461`, `:498`, `:531`, `:569`, `:595`, `:969`; `notifications.py` `:467-490`, `:1355-1366`; `postgres_models.py` state-machine docstring; `notifications.js` `:13689`, `:15467`, `:1968`, `:20247`, `:20276`.)

**Not added: `seen_at`.** `mark_notification_played` (`notifications.py:1714`) mutates only the in-memory FIFO queue and never the row. No client signal anywhere means "a human's eyes were on this," so the column would be permanently NULL and would read as *"nobody ever saw anything."* **Flagged, not faked** — it needs a client-side emit before it is worth having.

One Alembic revision: one `ADD COLUMN` (no default ⇒ PG catalog-only, no table rewrite) plus the concurrent index in the autocommit block above. **Head confirmed `38e025169a73` via `alembic heads` (two seats, independent); never infer it from directory ordering.**

**No backfill — a backfill would be actively wrong.** Personas are allocated and released (`voice_persona.py:183`, `:536`); re-resolving old rows would read bridge files since reassigned to different sessions and write **wrong** personas into the audit trail permanently. Worse than NULL. Within 24h of deploy every in-window row has the column. Answers already owed at deploy time are unrecoverable by persona — **note it in the runbook and accept it.**

### 4.3 The handback route — replace the print at `:1321`

The ask row **is** the record. No new table, no second row: it already carries `id`, `sender_id` with its `#hash8`, `response_value`, `responded_at`, and — after §4.2 — `sender_persona`. Ruling 2 is satisfied for free; the row is never deleted, only marked.

Inside `submit_notification_response` (`:1264`):

1. **Widen `_submit_response_sync`** to return `sender_id` and `sender_persona` alongside `recipient_id`/`job_id` — a dict, not the 2-tuple. ⚠️ mocked in `src/cosa/tests/unit/rest/test_notifications_router_coverage.py:695-806`.
2. `asker_hash8 = sender_id.split("#",1)[1].strip()` when `#` is present, else `None` — reuse the guard shape at `:65-69`.
3. **One-line live fix at `:1330`**: `job_id = notification_job_id or asker_hash8`. This alone fixes the connected case, because of fact 1.
4. **Try the live socket first; fall back only if it isn't there** (ruling 1). Two live paths, in order:
   - the SSE waiter, if `notification_id in pending_responses` — unchanged, still the fastest path;
   - otherwise the WS emit from step 3, which returns a `{user_delivered, listener_delivered, any_delivered}` triple (`websocket_manager.py:730-737`).

   **Only if `listener_delivered` is False** does `_handback_answer(...)` write a durable carrier through the normal channel — `title="action:ask_answer"`, `job_id=asker_hash8`, `notification_id` in the payload, `suppress_ding=True` (`"action:"` titles route *before* the type filter at `cc_notification_listener.py:496-500`, a path already proven by `broadcast_received`). **A reachable session gets exactly one copy and costs one WS frame; the durable write is spent only on sessions that aren't there.**

   > **Why the gate reads `listener_delivered` at all — the send-signal asymmetry (settles Rio vs Rachel; both were right about different halves).** `listener_delivered` is True iff the socket was present **and** `send_json` did not throw. So **False is trustworthy** — no socket, or the send threw; the frame **definitely did not get through**. **True is not trustworthy** — it means only that the frame reached the buffer, not that anyone read or acted on it. The signal is reliable in **one direction only.** That asymmetry is the whole tie-break: gating the durable carrier on **False** is sound because the gate fires only on the *informative* direction (Rachel), while setting `answer_delivered_at` on **True** is unsound because that reads the *uninformative* direction as a receipt (Rio). Same signal, opposite directions — so both reviewers are correct and neither concession is needed. Fewer live routes also keeps the §5 dedupe red-proof completable (Krishna).

5. **`answer_delivered_at` has exactly THREE setters, all receipt-gated** (the reconciled C↔D↔E contract — stated here, in §4.4, and in §4.5 in the same words):
   - (a) the **§4.3 live path** sets it **only when the SSE waiter was woken** (`notification_id in pending_responses`);
   - (b) the **§4.4 pull path** sets it **only on the client's positive ack of consumption**;
   - (c) the **§4.5 re-attach** sets it **when the post-stream-death poll lands** (`responded_at IS NOT NULL`) — a successful re-attach IS a genuine receipt: the asking process has the human's answer in hand, so it acks.

   **Never** on `listener_delivered` True, **never** on a successful `send_json`, **never** on an emit attempt, **never** on *serving* a row. One reader: §4.4's owed query. Anything not confirmed-received ⇒ `answer_delivered_at` stays NULL ⇒ the row is owed ⇒ §4.4's catch-up re-delivers. **Fails toward re-delivery, never toward silence.** (This is why the send-then-drop case needs no special handling in step 4: the row simply stays owed and catch-up carries it.)

> ⚠️ **POST-CASCADE CONTRACT AMENDMENT — TWO setters, not three (María, 2026-08-01, ruling (b)).** Setter **(c)** — the §4.5 re-attach acking on poll-land — is **REMOVED**. The re-attach **returns** the landed answer to the caller (that return IS the delivery) and **leaves the row OWED**; its receipt is deferred to the next-turn catch-up, which acks via setter **(b)** when the answer is genuinely consumed as `additionalContext`. Rationale: acking on poll-land would mark the row delivered **before** the value reached the caller — "ack on consume, never on serve" rebuilt one level in — so a process death in that window would **lose** the answer. The contract is now exactly **(a)** the live SSE waiter woken and **(b)** ack-on-consume via `POST /answers-owed/ack` (the pull path AND a re-attached answer's catch-up surface). This **fails toward re-delivery** — a bounded double-SEE, never a re-ASK — never toward silence. Guarded by **E-V5**. *(Supersedes the "three setters" / "E acks on land" wording at §4.3, §4.4 and §4.5; the pre-amendment text is retained as the cascade record.)*

**Dedupe is two-layer**, mirroring `dm_inbox_reconcile`: the server column stops re-pushing; the client's `surfaced_ids` ledger stops re-surfacing. Neither alone is sufficient — the server cannot see a client that received the frame and died before acting on it, and the client cannot see a push that never arrived.

> 🔴 **One dedupe ledger, keyed by `notification_id`, across ALL THREE delivery routes (Rachel finding 2 — Rick's duplicate-prompt symptom lives here).** Because the contract makes double delivery **normal** (a send that isn't a receipt leaves the row owed, so live-push and catch-up can both fire), the client `surfaced_ids` ledger is the only thing that collapses them to one surfacing — and it must cover every route: (1) the SSE waiter, (2) the **live `:481` arm**, (3) catch-up. **The `:481` arm MUST check-and-record `notification_id` into the same `surfaced_ids` ledger `answer_catchup` uses, under the same key.** Routing key and dedupe key are **different axes**: a route may address by `job_id`/`asker_hash8`, but every route carries `notification_id` in its payload and dedupes on **that**. A split key (routing on `job_id` here, `notification_id` there) is exactly what would surface the same answer twice — which is the defect §1 exists to kill.

> 🔴 **The ledger CROSSES A PROCESS BOUNDARY — name it, or the spec is satisfiable by a same-process implementation that fails in production (K-D1).** The live `:481` arm runs in the **listener process**; `surfaced_ids` + the HWM are the **hook-side** ledger (`answer_catchup` / `user_prompt_submit`, on-disk JSON in `heartbeat_hold._resolve_base_dir()`, keyed by session hash8). "Records into the same ledger" therefore means one process writing state the *other* process reads. Two design facts make this correct and race-safe:
> - **Shared location.** Both resolve the **same** per-session dir via `_resolve_base_dir()` under the session hash8 (the listener is `cc-listener-{hash}`, so it holds the hash). Same dir ⇒ same ledger, no new path.
> - **Write discipline — reuse the existing seam, keep one writer of the JSON.** The HWM JSON stays **hook-single-writer** (no two-process read-modify-write race on it). The listener instead **appends** each surfaced `notification_id` to a shared, append-only side-log in that dir (`.ask-surfaced-{hash8}.log`, POSIX `O_APPEND` = atomic small-record writes, lock-free across processes). The hook folds that log into its dedupe via the **already-present** `reconcile_context(extra_surfaced_ids=…)` param (`dm_inbox_reconcile.py:93,104`) and compacts it under its sole ownership. The live-emitted `notification_responded` event must carry `notification_id` in its `data` so the arm has an id to append.
>
> **C-V1 must prove the cross-process hop, not in-process dedup** (see §5): the listener-side append and the hook-side check run against the **same on-disk dir**, and a listener write must be **visible** to a subsequent hook reconcile. ### 4.5 MCP asking side — re-attach instead of a bare default

> **Revised (cascade Section E, 2026-08-01).** Findings E1–E3 accepted. E runs in the **MCP-server process** — a THIRD process beyond the hook and the listener — and it is **NOT** a `surfaced_ids` participant: it dedupes **BY ACK** (setter (c)), not by ledger membership (Krishna's correction to the "one ledger" framing). A successful re-attach is a genuine receipt, so it acks; the acked row leaves the owed set and catch-up never re-fetches it. One race window remains and is declared below rather than papered over.

>
> **Superseded within this §4.5**: step 3's first bullet ("`POST …/ack` … **setter (c)** — this is the receipt") and the race note's "E acks **immediately on land**" no longer hold — the re-attach does NOT ack; it returns and leaves the row owed, and E-V4/E-V5 assert that post-return state.

1. **Server** yields an opening `{"status":"ack","notification_id":...}` frame right after the WS push (`notifications.py:~1122`, before the `await asyncio.wait_for`). Purely additive — `consume_sse_stream` already `continue`s on unrecognized status (`notify_user_sync.py:115-127`), so every existing client is unaffected.
2. **Client** captures it (`consume_sse_stream` returns the id alongside the event); new `GET /api/notifications/response/{notification_id}` — registered before the `{user_id}` routes — returns `{state, response_value, responded_at}`. **Pure read, no ack** (the ack is an explicit second call, step 3).
3. **On stream death** (`notify_user_sync.py:254-260`, where `event is None` currently becomes a bare `status="stream_error"`), poll that endpoint against the **remaining** wall-clock budget at a bounded interval. **"Landed" ≡ `responded_at IS NOT NULL`** — the §3 design-level invariant, applied here (this is the invariant's third discovery site). Decide the outcome on that term, **never** on `state` moving or `response_value` being non-null:
   - `responded_at IS NOT NULL` ⇒ a human answered ⇒ **`POST /api/notifications/answers-owed/ack`** for that `notification_id` (**setter (c)** — this is the receipt), then map to **`RespondedEvent(default_used=False)`** → `status="responded"`. The ack removes the row from owed so catch-up will not re-surface it.
   - a row with a `response_value` but `responded_at` NULL is a manufactured default, **not** an answer ⇒ **no ack**, map to **`ExpiredEvent(default_used=True, timeout=True)`**, **never** `responded`.
   - budget exhausted with no landed answer ⇒ `ExpiredEvent(..., timeout=True)` → `status="expired", is_timeout=True`.

   **Reuse the existing terminal-event vocabulary** (`RespondedEvent`/`ExpiredEvent`, `notification_models.py:437,451`) — the client already `isinstance`-branches on those events; do **not** invent a bespoke "landed" boolean. This finally makes the retry gate at `:460` mean something, since `stream_error` carries `is_timeout=False` and falls straight through today.
4. **Keep the re-attach inside `_send_sync_notification`** — below the `max_attempts=1` line every MCP verb passes. Zero verb-level changes, smallest blast radius.

> ⚠️ **The E×catch-up race is DECLARED, not closed — because nothing can close it, and pretending otherwise is worse (Krishna's correction).** E's dedupe is **ack-based**: land ⇒ ack ⇒ row leaves owed ⇒ catch-up excludes it. But if a catch-up pass fires in the window **between E landing the answer and E's ack committing**, catch-up surfaces the answer as **replayed context** while E returns it as the **tool value** — two *different surfaces* to the model, which `surfaced_ids` **structurally cannot** dedupe against each other (they are not both ledger surfacings). **This transient double is ACCEPTABLE and bounded**: it is confined to the ack round-trip window; it is a context-line + a tool-return, **never a re-ask** (not Rick's duplicate-prompt symptom); the context copy is flagged replayed and non-interrupt (ruling 6 / `dm_inbox_reconcile` no-interrupt contract); and it fails toward the model seeing the answer **twice** rather than losing it. E acks **immediately on land** to keep the window as small as the round-trip. **The §5 race red-proof asserts the post-ack state (row not owed), and the doc states the double is accepted** — it is not silently assumed away.

**Observability — a CONCRETE, assertable, fail-loud signal, not "log it" (K-E2).** The re-attach path exposes a state field/counter with two terminal values a test can assert and production can query: **`reattach_armed`** (stream died, poll loop entered, at least one poll fired against the remaining budget) vs **`reattach_unavailable`** (stream died but the id was never captured, so no re-attach is possible — the silent-no-op failure, surfaced **loud**). "Armed" is the wiring proof; "unavailable" is the alarm. A bare log line is neither assertable nor queryable and is prohibited here.

**Left filed separately**: `ask_yes_no` returning a default that is **indistinguishable from an error** (`cosa_voice_mcp.py:1557-1571`, flagged in its own code comments — it swallows timeout, expiry, offline-without-a-value, transport error and server error alike). Fixing it changes what the verb returns on failure: a breaking contract change on a live surface, and Rick's call, not a smuggled side effect. **This plan shrinks that defect** by removing its most common trigger (stream death producing a false default) without touching the return contract — which may itself change the cost/benefit of the contract break when he rules on it.
