## Phase 2 Approach — DM Quality Judge (THIS is the real A/B)

Runs synchronously inside `execute_dm_send`, after the DM is accepted, before the tool call returns to the sender — latency is accepted, the sender should see its own grade in the same turn, not via a later round trip. Toggle: `dm quality judgment enabled` in `lupin-app.ini`, default `False`. **OFF = control** (Phase 1 baseline only, no judge, no quality field). **ON = treatment** (baseline + judge feedback on every send).

**Dependency — SATISFIED, verified this session, not blocking**: `curl localhost:3001/v1/models` returns `ConfidentialMind/Mistral-Small-3.2-24B-Instruct-2506-GPTQ-AutoRound-TextOnly` live. Mr. Radio's install (`$DEEPILY_PROJECTS_DIR/vllm-mistral-small-24b/`) is up and serving.

**1. Length is Python-only — no LLM call.** LLMs are bad at counting (same reason the TTS budget is word-based, not character-based). Deterministic 5-level bucket on the word count Phase 1's counter already produces:

| Words | Emoji | Weight |
|---|---|---|
| ≤ 60 | ⭐ | +2 |
| 61–90 | 👍 | +1 |
| 91–150 | 🤷 | 0 |
| 151–250 | 👎 | −1 |
| 251+ | 😞 | −2 |

**2. LLM judge pass covers Directness and Tone only** — a fixed-rubric prompt (with concrete anchor examples per level, not just adjectives — a 24B model calibrates far better against anchors) sent to the Mistral endpoint via the **existing** `LlmClientFactory`/`ChatClient` (`cosa/agents/llm_client_factory.py` — already supports a `vllm://host:port@model` descriptor, add the new host:port as a config entry, reuse the client). **House pattern to clone, not invent**: `LlmAnswerVerifier`/`VerificationResponse` at `cosa/agents/notification_proxy/verification.py` + `xml_models.py` — same `str`-typed XML fields ("LLM I/O is always text"; Python does all arithmetic, the LLM never emits a number directly, only a grade LABEL like `needs_improvement`), same `BaseXMLModel.from_xml()` parsing raising `XMLParsingError` on malformed output, same 3-attempt/backoff retry. **New files**: `cosa/agents/dm_quality_judge/xml_models.py` (`DmQualityJudgeResponse`), `cosa/agents/dm_quality_judge/judge.py` (`DmQualityJudge`), prompt template `src/conf/prompts/dm-quality-judge.txt`, registered in `PromptTemplateProcessor.MODEL_MAPPING`.

**Judge-call failure — safe fallback, same shape as always.** If the judge call fails or exhausts its 3 retries, the DM still SENDS normally. Directness and Tone both report 🤷/0 with `detail`="judge unavailable"; `quality` is ALWAYS present with the same shape — nothing downstream ever special-cases a missing key, and the quality-audit counts the fallback the same as a real 🤷 (a stretch of judge downtime shows up as a flat run of neutral grades, not a gap).

**3. Zero-centered 5-point Likert scale** (per dimension + overall):
- 😞 terrible (−2) · 👎 needs improvement (−1) · 🤷 meh / mediocre (0) · 👍 good (+1) · ⭐ exemplary (+2)

**4. Overall combination rule — equal weight to quantitative vs qualitative CATEGORIES, not to 3 flat dimensions** (Rick's correction — a flat 3-way average lets the 2 LLM-judged dimensions outvote Length 2-to-1): `qualitative_weight = avg(directness_weight, tone_weight)`. `overall_weight = round_half_up(0.5 * length_weight + 0.5 * qualitative_weight)`, bucketed back to the nearest of the 5 levels. Round-half-up is a deliberate, explicit tie-break (0.5→1, −0.5→0) — not Python's default `round()`, which rounds-half-to-even and would be inconsistent boundary to boundary. Worked example (Rick's): length=😞(−2), directness=⭐(+2), tone=⭐(+2) → qualitative_avg=2 → overall=round(0.5×−2 + 0.5×2)=round(0)=0 → 🤷.

**5. Return shape** — appended to `dm_send`'s tool result as a new `quality` field: `{"length": {"emoji": "👎", "weight": -1, "detail": "187 words, target ~60"}, "directness": {...}, "tone": {...}, "overall": {"emoji": "🤷", "weight": 0, "note": "Cut to length next time — the verdict sentence was good."}}`. **`overall.note` is Python-templated, not an LLM field** — `overall_weight` is Python-computed after the judge call (item 4), so its note is built the same way: a short template selecting on which component (length vs qualitative) dragged the score, e.g. `f"Length pulled this down ({length.detail}); tone/directness were fine."` No new LLM call for `overall.note` — consistent with "LLM I/O is text, Python does arithmetic" (item 2).

**6. Tracking — TWO audits, on two axes, both fleet-wide aggregate only (no persona split — Rick: he cares about the trend, not any one persona's, and a split adds structure nobody would read):**
- **Length-audit** (already built, Phase 1) — runs unconditionally in BOTH arms, continuously. The "did DMs actually get shorter" signal.

Only accumulates during TREATMENT windows (judge doesn't run when toggle is off) — its own `since`/count naturally scope it, no toggle-awareness needed in the counter itself.

Comparing both: if the feedback loop works, length-audit's avg_words should trend down THROUGH a treatment session (not just be lower than control on average — an in-session trend, DM by DM), and quality-audit's avg overall weight should trend up over the same window.
