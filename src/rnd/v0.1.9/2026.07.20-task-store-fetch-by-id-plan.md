## 3. What it actually costs today

Rio's §0 procedure requires *"these EIGHT items, by ID. Open every body. DO NOT DERIVE THIS LIST FROM A FILTER"* — an instruction that **forbids the only method available** through MCP. His documented workaround is three steps:

1. `task_query( project=…, terse=True, include_terminal=True, limit=100 )` → locate the UUID
2. `task_query( <narrowest filter>, terse=False )` → still errors on size, but the harness dumps JSON to a file
3. `jq -r '.tasks[] | select(.id|startswith("…")) | .body' <dump>`

And both arms of the documented fallback union **error outright**: `389,242` and `201,062` characters, exceeding max tokens.

**Measured cost this session (mine):** I claimed `a5aa1362` was not closed. It was — sitting at `offset=15` of a `limit=15` page. I had no way to ask for the row, so I asked a filter and read its silence as an answer. That is the defect's signature failure.

## 4. Proposed design

Expose the existing route. **No server change.**

### 4.1 New MCP verb `task_get`

```
task_get( task_id ) → the full serialized item, or an error dict carrying the
                      server's 404 detail verbatim ("task {id} not found")
```

- Thin proxy over `GET /api/tasks/{task_id}`; same auth path as every other store verb.
- Accepts a **full UUID**. §5 covers the prefix question.
- 404 returns an **error dict, never an empty success** — an absent row must never render as a silent nothing, since that is the very confusion this row exists to kill.

### 4.2 Docstring must state what it is FOR

The verb's docstring names the failure it prevents: *"a filtered query's empty result is not evidence a row is absent — use this to ask about a row directly."* The MCP docstring is the only documentation most seats will ever read.

## 5. ✅ RULED — option (a), single-row `task_get` only (Mr. Radio, 2026-07-20)

**Decision**: option (a). `task_get(task_id)` single-row only; **no `ids` batch filter, no server change**. Consistent with Rick's standing ruling #8 ("fetch-by-ID = single-row `task_get` only"). The batch case (Rio's §0 eight-rows) is survivable at 8 small calls; a server `ids` filter is real work justified by a use case that has arisen once in a procedure that may be re-written — deferred to its own row if the batch ergonomics prove painful in practice. Original analysis retained below.

### 5.0 (original) OPEN QUESTION — one row per call, or batch?

The REST route is strictly one-row. Rio's real use case is **eight rows by ID**.

| Option | Shape | Trade |
|---|---|---|
| **(a) `task_get(task_id)` only** | 1 call → 1 row; 8 rows = 8 calls | **Zero server work.** Verbose for the batch case but each call is small and cheap |
| **(b) also add `ids=[…]` to `task_query`** | 1 call → N rows | Needs a **server change** — the query endpoint has no `ids` filter. Must also count as a *narrowing* filter for the unscoped-query guard, or it 422s |
| **(c) `task_get(task_ids=[…])` client-side fan-out** | 1 verb → N REST calls under the hood | No server change, batch ergonomics; but N sequential round-trips hidden behind one call, and partial failure needs a defined shape |

**My recommendation: (a) now, (b) only if the batch case proves painful in practice.** (a) is available today with zero server risk and closes the failure that actually bit us — *asking about one specific row*. Eight small calls is a real cost but a survivable one; a server filter is real work justified by a use case that has arisen once, in a procedure that may itself be re-written.

**Against my own recommendation, stated fairly**: Rio's §0 is a *standing procedure*, not a one-off, and (a) leaves it needing eight calls every time it runs. If §0 is going to survive in its current form, (b) is the honest fix.

## 6. Acceptance criteria

1. `task_get` with a valid id returns the **full** item including `body` — not the terse projection.
2. `task_get` with a well-formed but absent UUID returns an **error dict** carrying the server's 404 detail verbatim. **Not** an empty success, **not** `None`.
3. `task_get` with a malformed id surfaces the server's 422 verbatim rather than raising client-side.
4. Auth failure surfaces as an error dict, not an exception.
5. **Negative control**: a test proving the pre-change MCP surface *cannot* fetch by id — so the fix is shown to close a real gap rather than merely pass.
6. 100% lines + branches + functions on every changed file.
7. No change to `GET /api/tasks/{task_id}` — a diff touching `routers/tasks.py` means the scope was misread.
