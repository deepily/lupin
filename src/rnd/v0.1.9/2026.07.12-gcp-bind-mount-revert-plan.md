## 1. Directive (Rick, voice, 2026-07-12)

1. App code must **NOT** be baked into the docker image.
2. Code lives in a **host checkout, bind-mounted** into the container at spin-up, refreshable to the latest committed ref at any time without an image rebuild.

This is a **return to the original M2 "Decision 3" mount model**, which was superseded (leg-scoped, not permanently) on 2026-07-07 during the pgvector cutover.

## 2. Why the 07-07 flip happened — and why its reason no longer holds

The flip was a **consistency guard, not a model preference**: the on-VM checkout was stale at pre-cutover `8f4a36f`, so a live `./src` bind would have SHADOWED the baked `-r3` Postgres cutover code (no `backend=postgres`, no auto-migrate) — the mount-shadow trap Clayton's probe caught (host-code-green ≠ artifact-green).

The trap is a **staleness** problem, not a mount problem. Once the on-VM checkout is synced to a ref ≥ cutover HEAD `c2b02065`, mount and image agree and the guard's reason evaporates. The mount model then restores the property Rick wants: deploy = checkout refresh + `docker restart` (seconds), image rebuilds only for deps (AXIS B).

**Bonus correctness fix:** `src/scripts/deploy-cloud-test.sh` AXIS-A (code sync + restart) silently assumes the `./src` bind exists. Post-07-07 it would sync the checkout and restart a container that **ignores the checkout** — a false-green deploy. The revert restores the script's validity; until the revert lands, AXIS-A must not be used.

**Mechanism — `BAKE_CODE` build arg (FROM-selector), default `off`.** Docker has no conditional `COPY`, so the both-paths flag is implemented as a stage selector rather than an if-statement:

- `runtime-base` — Dockerfile's former lines 65–310 verbatim (deps + runtime env; **no code, ever**).
- `code-off` (**default**) — empty stage over `runtime-base`. `/var/lupin/src` exists only as the empty mountpoint `WORKDIR` creates.
- `code-on` — the legacy baked tree (the former 317–348 COPY block, incl. the cross-stage mux-dist COPY), preserved verbatim for the postponed prod decision (§6). Build with `--build-arg BAKE_CODE=on`.
- `final` — `FROM code-${BAKE_CODE}`; code-independent tail (claude-config, `agy`, WORKDIR, CMD) shared by both.

BuildKit prunes the unselected stage, so a codeless build **also skips the Node/multiplexer-builder stage entirely**. The selector touches no instruction above the old line 312, so all ~31 GB of CUDA/uv-sync/HF-model/playwright layers stay cache-valid (verified: 22/22 `runtime-base` steps CACHED; only the 4 final-stage steps ran).

## 5. "Pull latest from master" — the remote question (RESOLVED 2026-07-12)

The VM's git origin is a **local bundle file** (`/mnt/lupin-data/lupin-wip.bundle`), not GitHub — the IAP-only VM has no GitHub creds. The 06-23 design chose scripted archive+SCP (Option C) over a real GitHub remote (Option A) for exactly this reason. Rick's "pull the latest from master at any point" is satisfiable two ways:

- **C (status quo, works today):** `deploy-cloud-test.sh` from the dev box — one command, pushes any committed ref. No VM credentials.
- **A (true VM-side pull):** add a read-only deploy key / fine-grained PAT on the VM, point origin at GitHub, then "update" = on-VM `sudo git pull` + restart. Adds a credential surface on cloud infra.

**Recommendation: stay on C** — same outcome (any-time refresh, seconds), zero new credential surface. Revisit A only if dev-box-independence becomes a requirement. **RESOLVED: Rick ratified C (manual pull) by voice 2026-07-12.**

## 7. Does no-baked-code break the "static snapshot" test-server model? — NO (analysis)

**Rick's question (2026-07-12):** with no code in the image, can a test server still lock in a series of code changes — run a static snapshot created at its re-spin time — while development continues on the local filesystem?

**Answer: yes — snapshot isolation comes from WHERE the mount points, not from baking.** A bind mount does not have to point at the live working tree. The doctrine's operative phrase is *"snapshot materialized at re-spin time"*:

| Venue | What the container mounts today | Snapshot quality |
|---|---|---|
| **GCP cloud-test VM** (post-revert) | the on-VM checkout at `/mnt/lupin-data/lupin/src` — written ONLY by `deploy-cloud-test.sh` (git archive of a committed ref) | **True static snapshot by construction** — dev-box edits physically cannot reach it between deploys. Baking would add nothing. |
| **Local `:8000` test server** | the LIVE working tree (`./src:/var/lupin/src`, `docker-compose.yml:222`) with `reload=False` | **Partial snapshot**: Python is frozen at import time, but anything read from disk at runtime — static JS/CSS/HTML (the mux bundle), templates, hot-reloaded INI, data files — drifts LIVE with dev edits. This is exactly why the "no mux rebuild during a live :8000 run" discipline exists. |

**The gap is local-only, pre-existing, and orthogonal to the GCP revert** — it neither worsens nor improves by un-baking the GCP image.

**Optional hardening (if true local `:8000` isolation is wanted):** at `:8000` (re)spin, materialize a snapshot dir from a committed ref (`git archive <ref> | tar -x -C <snapshots>/8000-<stamp>/`) and point the compose `src` mount at it (env-var-parameterized mount source). Working tree stays free for development; the test server's tree is immutable by construction; discipline rules about mid-run rebuilds become unnecessary. Cost: one extra materialize step per re-spin (~seconds) + snapshot-dir cleanup. **Not scheduled — flagged for Rick to promote if wanted.**
