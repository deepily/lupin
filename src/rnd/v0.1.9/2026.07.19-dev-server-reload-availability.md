## 1. Verdict

`:7999` runs `uvicorn --reload`. Every reload restarts the application while the
**listening socket stays bound**, held by the reloader parent process. During that window
the kernel **accepts** connections that nothing is there to answer, so a client whose
budget is shorter than the window hangs and raises `TimeoutError` — **not**
`ConnectionRefused`.

Measured across 8.4 days of container logs, current-config clean reload class:
**n=143, minimum 6.59s, median 6.91s, maximum 18.76s. 143 of 143 exceed 5s** (197 of 197
across both configurations).

The container healthcheck reports HEALTHY throughout because `interval 30s × retries 3`
means it can only turn red after ~60–90s of *continuous* failure, against a ~7s median
outage. It did not miss the window. It is **structurally incapable** of reporting a
sub-60s outage.

## 4. The mechanism — proven in an isolated replica

`:7999` was never touched. A replica was built on a scratch port: uvicorn **0.46.0**
(host and container both), `watchfiles` **absent** in both → the **StatReload** supervisor,
`reload=True`, `timeout_graceful_shutdown=5`, one long-lived connection held open.

Substrate confirmed in the replica's own log: `Started reloader process [1050627] using
StatReload`, `StatReload detected changes in 'app.py'. Reloading...`, server child
`1050629` → `1050883`.

**Result — one probe issued just after the trigger returned `OK` with latency `8.249s`.**
Not refused. **Accepted, held, and answered 8.25 seconds later.** The listening socket
survives the restart because the reloader parent owns it and hands it to each child.

The same 245 samples, judged at the budgets real clients actually use:

| Client | Budget | Would that request have failed? |
|---|---|---|
| SessionStart hook | 2s | **YES** |
| Container healthcheck | 3s | **YES** |
| Mr Radio's probe | 5s | **YES** |
| This investigation's probe | 15s | No — recorded as a slow success |

### 4.1 Instrument note — outcome vs latency

Rev 1's first analysis printed only **outcome** transitions and concluded "no outage."
That was wrong. **On a budget wider than the window, a reload is not a failure — it is a
slow success.** The question asked was "did it fail?"; the measurable was "how long did it
take?" The signal was in the latency column throughout. The 15s budget — deliberately
wider than every real client budget — is what made the tail visible instead of truncating
it.

## 5. Frequency, duration, and the real floor

### 5.0 Baseline and slices — say which slice, always

`docker logs` retains **8.4 days** on this container (2026-07-11 → 2026-07-20), not the
10.4h rev 1 sampled. 231 paired windows. They are **not one population**; three classes
are mixed, and every number below names its slice.

The slice boundary is **`2026-07-14T17:48:58Z`, the first `Started reloader process` after
commit `bbadcaa8`** — not the commit itself. `uvicorn/supervisors/basereload.py:100` calls
`get_subprocess(config=self.config, ...)`, so each child inherits the **parent's** Config,
built when the reloader started. A `main.py` constant therefore cannot take effect until the
reloader parent itself restarts, which here was **27.3h after the commit**. Windows in that
orphan band ran the old configuration despite post-dating the commit.

| Slice | n | min | median | p90 | max |
|---|---|---|---|---|---|
| **Clean reload, current config** ← operative | **143** | **6.59s** | **6.91s** | 11.90s | **18.76s** |
| Clean reload, prior config (incl. orphan band) | 54 | 6.65s | 6.88s | 10.88s | 176.54s |
| Clean reload, full 8.4d (both) | 197 | 6.59s | 6.91s | 11.55s | 176.54s |
| **Crash-loop** (separate defect — §5.3) | 34 | 6.82s | — | — | 589.3s |

**197 of 197 clean windows exceed 5s — 143 of 143 in the current-config slice.**
Reload-mechanics duty cycle is ~0.25%; frequency tracks fleet write activity into watched
directories and is heavily clustered (a 03:14–03:16Z cluster ran ≈48% unavailable, which
is what Mr Radio sampled as "1 timeout in 3", with his "5/5 clean" being the quiet after).

### 5.1 🔴 The floor is EMPIRICAL, not by construction — rev 1 was wrong

**Rev 1 claimed every window is ≥5s "by construction" because `main.py:1223` sets
`timeout_graceful_shutdown=5`. That is FALSE.** It was derived from `main.py`'s *comment
about* uvicorn rather than from uvicorn. Read at source, `uvicorn/server.py:287-295`:

```python
await asyncio.wait_for(
    self._wait_tasks_to_complete(),
    timeout=self.config.timeout_graceful_shutdown,
)
```

`asyncio.wait_for` is a **CEILING, not a floor.** It returns as soon as the tasks finish;
with an empty connection set that is ~0.1s. The constant caps the drain, it does not
impose one.

The log confirms it, and these figures were reproduced independently from Clayton's:

| Phase | n | median | min | max |
|---|---|---|---|---|
| `Shutting down` → `Started server`, timeout **not** exceeded | 208 | **6.38s** | 6.07s | — |
| `Shutting down` → `Started server`, timeout **exceeded** | 23 | **11.38s** | 11.18s | 17.03s |
| `Started server` → `startup complete` (lifespan/boot) | 245 | **0.52s** | 0.50s | 0.61s |

The two teardown medians differ by **exactly 5.00s**, which is the constant appearing as a
surcharge — and `timeout graceful shutdown exceeded` fires in **23 of 231 shutdowns
(~10%), not 100%.**

**⇒ The irreducible floor is ~6.4s of teardown, fork, and importing `lupin_app.main`. The
5s constant is a 10%-frequency surcharge on top of it.**

**Why this changes the remedy, not just the wording.** As rev 1 wrote it, §5.1 invited
"lower the constant to 1s" — which would buy 5s in 10% of windows and **nothing in the
other 90%**. It also under-credited §9(b): against a ~6.4s irreducible floor, **reducing
reload frequency is the only lever that touches the bulk of the exposure.**

**What survives is stronger than rev 1's version.** A1's 2s→5s widening cannot win, and
the reason is now purely empirical: **197 of 197 clean windows exceed 5s — 143 of 143 in
the current-config slice.** Rev 1 said "it follows from a config constant plus a measured
minimum." **Strike that — it follows from the measurements alone**, and needs no theory of
uvicorn's internals to stand.

*(Rev 2 phrased this as "0 of 231 windows fell below 6.59s." That is a tautology — 6.59s
**is** the minimum, so the sentence asserts only that the minimum is the minimum. The
budget-relative form above is the one that kills A1.)*

### 5.2 Why the pairing had to be split

`Shutting down` → next `Application startup complete` is a **naive pairing that silently
merges failure classes.** It reported a 589.3s "reload window" that was actually broken
code crash-looping, recovered by human container restarts. A first re-classifier still
missed the 346.6s case because it matched only the literal `Application startup failed`
line, while that window emitted tracebacks instead. The working predicate: *a window is a
crash-loop if it contains a traceback, an exception line, a startup failure, or a reloader
restart.*

Independently verified by the reviewer against the full log with his own predicate:
231 → **197 clean / 34 crash**, no misses and no clean window wrongly excluded. The
excision could not have hidden a counterexample — **no window in either class falls below
5s, and the crash class minimum (6.82s) is above the clean class minimum (6.59s).**

### 5.3 Correction owed to `5aea73f3` / commit `77d64647`

Row `204911ca` already corrects `77d64647`'s scoring of A1 from "buys nothing" to
"load-bearing." This plan adds the second half: **A1 as *sized* still cannot win**, on the
empirical grounds in §5.1. A reader of the row could otherwise conclude the retry now
suffices. It does not.

### 5.4 The pre/post split is a reporting convention — NOT evidence that `5b654a15` worked

> 🔴 **Rev 2 claimed "`5b654a15` worked — the tail is GONE." That claim is WITHDRAWN.**
> It is *consistent* with the data and **not established by it.**

The two slices differ: earlier windows carry a long tail (max 176.54s) from unbounded
`Waiting for connections to close` hangs; later ones top out at 18.76s. Rev 2 read that as
the fix working. Three tests say the data cannot carry that claim:

1. **n=2.** The entire tail is two windows — 176.5s at `2026-07-12T23:48:36Z` and 122.2s at
   `2026-07-13T00:13:37Z`. Nothing else in 8.4 days exceeds 20s.
2. **Mis-located by 14.3h.** The last long window is 00:13:37Z; the commit landed 14:29:23Z
   the same day. The tail stopped well *before* the fix. Only **11** clean windows separate
   them (max 7.00s) — far too few to distinguish "stopped" from "did not recur."
3. **Insensitive to the cut.** Moving the boundary changes nothing:

| Cut | PRE n / max | POST n / max |
|---|---|---|
| −24h | 16 / 11.6s | 181 / **176.54s** |
| −12h | 24 / 176.5s | 173 / 18.76s |
| **0h (the commit)** | 35 / 176.5s | 162 / 18.76s |
| +12h | 50 / 176.5s | 147 / 18.76s |

Any cut between 00:13Z and the commit yields an identical partition, and at −24h the long
windows flip to the POST side entirely. **No cut in this range is identified by the data at
all** — the split is located by where those two events happen to sit. That is the shape of
a boundary drawn around the data.

*(The reviewer independently found the cut was at the wrong instant — the 27.3h orphan band
now handled in §5.0. He withdrew that point as subsumed: if no cut is identified, a more
defensible cut does not rescue the claim. The §5.0 boundary is retained anyway because it
is the correct instant for a reporting convention, which costs nothing.)*

**One datum, recorded as consistent-with and nothing more.** Both long windows show
`Shutting down` → `Waiting for connections to close` → **no `timeout graceful shutdown
exceeded`** → server back ~2-3 minutes later. That is mechanism-consistent with an unbounded
drain. It does **not** license the causal claim, for the three reasons above.

The slices are retained as a **reporting convention with a stated boundary**, because mixing
configurations would be worse. No causal claim attaches to them.

**Why this got written.** Nobody asked for §5.4 — it was added in rev 2 on the
investigator's own initiative, and it **flattered a fix in this codebase**. An unrequested
claim that makes our own work look good is the one that gets the least scrutiny on the way
in, which is exactly why it shipped untested and had to be withdrawn one revision later.

What is unaffected: the residual defect stands on the post-fix slice's own numbers —
**the bounded blip exceeds every client budget**, whatever produced the bound.

## 6. Gaps — carried verbatim, not closed by inference

**Gap 1 — the live `:7999` arm captured zero reloads.**
231/231 host samples clean at 0.003s; 228/228 in-container; 231/231 on `:8000`. **Zero
reloads occurred during that window**, so this confirms the healthy baseline only. It is
**not** direct on-`:7999` confirmation of the mechanism. Do not let this gap close by
inference. *(Reviewer's note, recorded: the real-server log forensics in §5 make the plan
less replica-dependent than this section concedes — the frequency, duration, and phase
data are all from the real server. The socket-binding mechanism specifically remains
replica-derived.)*

**Gap 2 — an instrument lied, and the healthcheck question is still open.**
`docker events --since 12h --filter event=health_status` returned **zero** — which looked
like confirmation. Auditing the instrument showed the oldest event it replays is **~5
minutes** old. **That zero was a false negative from a blind instrument, and it was
confirming exactly what was expected.** Docker retains only 5 health-log entries; journald
has nothing.
What *is* now evidence rather than inference is the **cause** of the 589s outage: two
back-to-back container restarts (reloader pid 7 at 18:07:43 and again at 18:08:05 — a low
pid each time, i.e. a fresh PID namespace), `docker inspect` `StartedAt` = 18:07:59 sitting
between them, and a session topic pushed at 18:08:12 reading *"Fix dead alembic stamp
a3b4c5d6e7f8 blocking dev startup."*
**None of that touches the healthcheck's state.** Whether the container ever went red
remains unverified, and the container restart is *suggestive of a human responding*, not
proof the signal fired.

**Gap 3 — the replica is not the real thing, but the socket claim is now source-confirmed.**
§4 proves uvicorn's behaviour under this configuration: same version, same absent
`watchfiles`, same supervisor. Strong, but a replica argument.
**Narrowed in rev 3**: `uvicorn/supervisors/basereload.py:100` reads
`get_subprocess(config=self.config, target=self.target, sockets=self.sockets)` — the parent
hands **its own listening sockets** to each child. The socket-survives-restart mechanism is
therefore read directly from uvicorn's source, not inferred from the replica. What remains
replica-derived is the *client-observable consequence* (accepted-then-answered-late), and
gap 1 is still the way to close that on the real server.

**Investigator errors, recorded.** (i) Rev 1 asserted a ≥5s floor "by construction" from a
source comment rather than uvicorn's source — the same class of error as reading
"unreachable" off a banner (§5.1). (ii) The first two sandbox runs silently probed a
**leftover server** already holding the port; the bind was never verified. (iii)
Background probes twice died early and a stalled probe was nearly read as server data.
(iv) The naive pairing merged three distinct classes (§5.2), and the first corrected
predicate still missed one. (v) §9(a) was first sized at ">10s" — wrong in the favourable
direction — then justified at 20s by a coverage figure computed on the slice that selected
the maximum, which is near-circular (§9(a)). (vi) **Rev 2 added §5.4's "the fix worked"
claim unrequested, and it flattered work in this codebase. It shipped untested and was
withdrawn one revision later.** An unrequested claim that makes our own work look good gets
the least scrutiny on the way in; that is the mechanism, not the excuse.

## 7. Why the healthcheck is green — the Q2 answer

`docker-compose.yml:192-197`:

```yaml
test: ["CMD-SHELL", "python3 -c \"import urllib.request; urllib.request.urlopen('http://localhost:7999/health', timeout=3)\""]
interval: 30s
timeout: 10s
retries: 3
start_period: 60s
```

**(a) The arithmetic forbids it.** `retries: 3` at `interval: 30s` means the container
flips to unhealthy only after ~60–90s of *continuous* failure. A ~7s outage produces **at
most one** failing sample, and `FailingStreak` resets. This is not a tuning miss — a
healthcheck that could see a 7s window would need `interval ≤ ~3s` and would then flap on
every routine dev reload.

**(b) It probes the wrong side.** It requests `localhost:7999` **inside** the container,
so it never exercises the host publish hop.

**The signal and the failure mode are mismatched in kind.** A binary container state cannot
express "available 99.75% of the time, in ~7-second holes." That is the more important
half of this row, and no tuning of the existing check fixes it.

## 9. Remediation — for review, nothing implemented

**Do not implement any of this until §5.1's rewrite is accepted** — rev 1's false floor
would have mis-aimed (a) and under-credited (b).

### (a) Client-side budget — load-bearing, fleet-wide 🔴
Every `:7999` client assumes a response inside a budget the server cannot honour during a
reload. A1 patched **one** caller; every other client has the same exposure and no retry.

**Size against the observed maximum with explicit headroom — not against a coverage
percentage.**

> 🔴 **Rev 2 recommended 20s on the strength of "100.0% coverage". That justification is
> WITHDRAWN as near-circular**: a coverage figure computed on the same slice that selected
> the maximum will *always* read 100%. It reads as a guarantee and is nothing of the kind.
> And 20s clears the observed max of 18.76s by **1.24s — a 1.07× margin** on a single
> configuration's evidence. That is not a budget, it is a coincidence.

Current-config clean reload class (n=143, §5.0):

| Statistic | Value |
|---|---|
| median | 6.91s |
| p90 / p95 | 11.90s / 12.77s |
| **observed max** | **18.76s** |

| Budget | Margin over observed max | Verdict |
|---|---|---|
| 10s | below max | fails observed windows |
| 20s | 1.07× | coincidence, not headroom |
| 25s | 1.33× | thin |
| **30s** | **1.60×** | **recommended** |

**Recommendation: ~30s for the reload class**, stated as *covers the observed maximum with
60% headroom* — explicitly **not** as a coverage guarantee. We have one configuration's
evidence about where the ceiling even is; the budget should reflect that uncertainty rather
than hug the largest number we happened to observe.

**A client budget is the right instrument for the bounded, modal ~7s window and the wrong
instrument for anything multi-minute.** Multi-minute events — crash-loops (§5.3 / Arnold's
row) and the retired pre-fix drain regime — need **reconnect-with-backoff, not a bigger
timeout.** No timeout can or should paper over an application that never booted.

### (b) Reduce reload frequency — upgraded from hygiene 🔴
Install `watchfiles` and use real `reload_excludes`, or narrow `reload_dirs` further.
`main.py:1176-1191` documents that `reload_excludes` is **inert** today because
`watchfiles` is absent, so passing excludes now would look like a fix and change nothing.

**Rev 2 upgrades this item.** Against a **~6.4s irreducible floor** (§5.1) that no constant
tuning can reach, frequency reduction is **the only lever that touches the bulk of the
exposure**. Rev 1 filed it as hygiene on the strength of a false floor.

### (c) A health signal that can see this — the Q2 answer
Replace or supplement the binary healthcheck with an **availability SLI over request
outcomes** (success rate, latency percentiles). Per §7 this is a kind-mismatch, not a
tuning problem.

### (d) Architectural — a question for Rick, not a recommendation
**Should `:7999` run `--reload` at all**, given it carries the fleet's MCP transport and
the task store? Every reload is a fleet-wide availability event. Stated as a question for
Rick's ruling; this plan makes no recommendation.

### Not in scope — cited, not claimed
The **crash-loop class** (34 windows, 1898s across the log) is a **separate defect filed by
Arnold 🪨**: a StatReload child that dies on import leaves `:7999` dead with no supervisor
recovery. It is also the real answer to Gap 2. Cited here so §5's crash rows are not read
as unowned.
