# Model version pinning across the Claude Code agents — survey and options

**Date**: 2026-08-02
**Author**: Cheech 🌿 (session b07d59ac)
**Status**: Research — no code changed. Awaiting Rick's pick.
**Trigger**: Rick observed a podcast job calling Opus 4.6 and asked (a) how widespread the hardcoding is, and (b) what the options are for changing versions without editing source.

---

## Headline

**The configuration flags you asked for already exist.** Every agent family reads its model IDs
from `src/conf/lupin-app.ini`. You can move the podcast generator, deep research, and the rest off
Opus 4.6 today by editing the INI — no source edit, no code change.

The reason it *looks* hardcoded is that each INI read sits next to a dataclass default holding the
same string, so a grep for `claude-` lights up in every agent. Of 58 model literals under
`src/cosa/agents/`, only about 14 are live defaults; the rest are smoke-test assertions and
docstrings.

Proof the pattern works: `cc session spawn model *` in the same INI is already on
`claude-opus-4-8` while everything else sits at 4.6. Nobody edited source to do that.

## The three genuine hardcodes

Everything else is config-driven. These three are not:

1. **`notification_proxy/config.py:51`** — `LLM_FALLBACK_MODEL = "claude-sonnet-4-5-20250929"`.
   A bare module constant with no INI key and a dated ID. This one needs a small code change to
   become configurable.

2. **`deep_research/cost_tracker.py:48-62`** — `MODEL_NAME_TO_TIER` maps model IDs to price tiers.
   It knows the 4.5 and 4.6 families and nothing newer. An unknown model **silently falls back to
   Sonnet pricing** (line ~356) behind a debug print. So a bump to `claude-opus-5` keeps working
   but reports Opus spend at Sonnet rates — roughly a 40% understatement ($3/$15 booked against
   $5/$25 actual). This is a reporting defect, not a runtime one, and it bites whichever option
   you pick.

3. **`model_registry.py`** — 565 lines defining a `ModelRegistry` with per-model configs. It is
   **dead code**: commented out in `src/cosa/agents/__init__.py:48` and referenced only by its own
   unit test. Do not mistake it for the live mechanism; it isn't one. Either wire it up
   deliberately or delete it, but it should not sit in the tree looking authoritative.

## Option A — bump the INI to pinned current IDs

Change 12 INI values from `claude-opus-4-6` → `claude-opus-5` and `claude-sonnet-4-6` →
`claude-sonnet-5`. Nothing else.

- **Pro**: explicit and reproducible — the INI states exactly which model ran, which matters when
  you are comparing podcast or research output across weeks. No code change. Reversible in one edit.
- **Con**: you repeat it at every model launch. Twelve lines each time.

## Option B — use the SDK's floating aliases

`ClaudeAgentOptions.model` accepts `"opus"`, `"sonnet"`, `"haiku"`, or `"inherit"` as well as a
full model ID (`claude_agent_sdk/types.py:77-78`, SDK 0.1.56). Putting `opus` in the INI means the
agents track whatever Anthropic currently ships as Opus, permanently, with **zero** code change —
this is the closest thing to the "constant representing the latest version" you asked about.

- **Pro**: you never bump again. One-word INI values.
- **Con**: you stop controlling *when* you move. A model launch changes your podcast output with
  no diff and no announcement — bad for reproducibility and bad the week of a demo. It also only
  works on the bounded-CC / Agent-SDK path; the direct Anthropic SDK requires a real model ID, so
  `notification_proxy` and anything else on that path cannot use it.
- **Note**: `cost_tracker` would see `"opus"`, not find it, and book Sonnet pricing — defect #2
  above becomes permanent rather than occasional.

There is no Anthropic-side floating alias (no `claude-opus-latest`); the published IDs are all
fixed. So this SDK alias is the only "always latest" lever that exists.

## Option C — one indirection layer, then bump one line ★ recommended

Add two keys to `[Lupin: Baseline]`:

```ini
default lead model    = claude-opus-5
default worker model  = claude-sonnet-5
```

and have each agent's existing key inherit from them, keeping the per-agent key as an override for
the cases that genuinely differ (the Testing-section TFE override, a cheap model for a
high-frequency path).

- **Pro**: you get Option A's explicitness with a one-line bump at each launch, and you keep the
  ability to pin one agent to something different without disturbing the rest. It also makes the
  intent legible: today, twelve identical values give no hint whether they are *deliberately* the
  same or merely *coincidentally* the same.
- **Con**: a small amount of plumbing in each `from_config` (the config manager has no native key
  inheritance, so each agent reads the default key when its own is unset).

**My recommendation: C, with the values from A.** B is tempting and I would not pick it — floating
your demo path to whatever shipped last night is exactly the failure you would find out about on
stage. Pin deliberately, bump in one place.

## Required regardless of which option you pick

These are not optional cleanup; a bump lands wrong without them.

1. **Teach `cost_tracker` the new IDs** — add `claude-opus-5` / `claude-sonnet-5` (and 4.7/4.8 while
   there). Consider making the unknown-model fallback loud rather than a debug print, so the next
   bump cannot silently mis-book spend.
2. **Update the smoke-test assertions that read the INI.** `podcast_generator/config.py:621` and
   `deep_research/config.py:236` assert on the value loaded *from config*, so they fail the moment
   the INI changes. The assertions on default-constructed configs (`:486`, `:194`) only fail if the
   dataclass defaults move too. Better: assert the value is non-empty and well-formed rather than
   pinning the literal, so the test stops re-breaking at every launch.
3. **Add splainer entries** for any new INI key, per the standing rule that every key in
   `lupin-app.ini` has a matching explainer in `lupin-app-splainer.ini`.
