## F1 — §3.1's refutation is invalid. `reload_dirs` is a watch list, not an import path.

The plan rejects the surgical fix because "the REST app genuinely imports from that exact directory in 8+ places." Those two facts are unrelated. `reload_dirs` controls which directories uvicorn **stats for mtime changes**. It has no bearing on `sys.path` or on imports.

**Ran** (live container, uvicorn 0.46.0):

```
docker exec lupin-rest-dev python -c "import uvicorn, inspect, uvicorn.supervisors.statreload as s; print(uvicorn.__version__); print(inspect.getsource(s))"
```

Output — the entire use of `reload_dirs` in `StatReload`:

```python
def iter_py_files(self) -> Iterator[Path]:
    for reload_dir in self.config.reload_dirs:
        for path in list(reload_dir.rglob("*.py")):
            yield path.resolve()
```

It rglobs for `.py` files and compares `st_mtime`. Nothing else.

**Ran** (does uvicorn's config inject watch dirs onto the import path?):

```
docker exec lupin-rest-dev python -c "import inspect, uvicorn.config as c; print('sys.path' in inspect.getsource(c))"
→ False
```

⇒ Removing `lupin_cli` from `reload_dirs` would **not** have broken `session_bridge`, `heartbeat_hold`, or any of the eight listed call sites. The table in §3.1 is evidence for a different claim than the one it sits under.

**What the real trade-off is** (and what the plan should say instead): dropping the directory means edits to `session_bridge.py` — a file the server *does* import — stop being served until someone bounces. That is a genuine cost, and it is the same cost R1 imposes globally.

- §3.1's *conclusion* ("the surgical fix is not the answer") **still holds** — R1 is what Rick asked for and it subsumes the surgical fix.
- §3.1's *reasoning* must be replaced, or the next reader inherits a false belief about how `reload_dirs` works — in a section headed "established, do not re-derive."

The neighbouring claim — that `reload_excludes` is inert without `watchfiles` — **is correct**; the running `StatReload.__init__` carries that exact warning.

## F2 — §4.1: the all-clear does *not* belong in the script. It belongs in the server's startup.

The plan's load-bearing sentence: *"the script … is the only participant alive on both sides of the restart."* False twice over.

1. **The listener processes are alive on both sides.** `cc_notification_listener.py` runs on the host, not in the container; it reconnects after the restart.
2. **More importantly — the restarted server is alive at the moment the all-clear must be spoken.** The all-clear is not spoken *during* the outage; it is spoken *after it ends*. The process best positioned to assert "I am up" is the one that just came up.

`src/lupin_app/main.py:409` already has a `lifespan` hook, and prints `FastAPI startup complete` at `:968`. An all-clear emitted there is **strictly more reliable than the script's**, because it fires on *every* start:

| Bounce path | Script emits all-clear? | Startup hook emits all-clear? |
|---|---|---|
| `bounce-dev-server.sh` | ✅ | ✅ |
| Hand-typed `docker restart lupin-rest-dev` | ❌ | ✅ |
| `docker compose up -d` after an image rebuild | ❌ | ✅ |
| Crash / OOM auto-restart | ❌ | ✅ |
| Host reboot | ❌ | ✅ |

⇒ **Keep the warning in the script** (nothing inside the container can reliably speak while being torn down). **Move the all-clear into the lifespan startup hook.** The script then *waits for* the all-clear instead of *sending* it — a better readiness check than polling `/health`, because it proves the notification path works rather than that the process is merely listening.

**Residual risk to decide**: a crash-loop emits one all-clear per restart. `CommonsBroadcastRateLimiter` already returns 429, so the blast is bounded, but the plan should state the intent — suppress-if-within-N-seconds-of-last, or let it speak.

## F3 — Hazard #2 confirmed: "confirm 200" is provably insufficient. Use the ack file, not a sleep.

**Ran**: `sed -n '543,575p' src/cosa/rest/websocket_manager.py`

```python
future = asyncio.run_coroutine_threadsafe(
    self.emit_to_user( user_id, event, data ),
    self.main_loop
)
# Don't wait for result to avoid blocking the COSA thread
```

The future is bound and never awaited; the docstring says *"Does not block calling thread."* In `commons.py` `_fan_out`, a recipient is counted `successful += 1` right after `push_notification(...)` returns — i.e. after the emit was **scheduled**. So `200 {recipients: 7}` means *seven emits were queued on the event loop*, not *seven sessions received anything*. `docker restart` sends SIGTERM the instant the next script line runs; frames still on the loop die unsent.

No pause value is defensible, because the thing being waited on is unobserved. A real receipt already exists.

### The ack channel provably fires — measured, not traced

**Ran**: `ls -l io/commons/broadcast-acks.md` → `11013 bytes, Aug 1 11:29`. A live file, not a stub.

**Ran**: `tail -30 io/commons/broadcast-acks.md` — the most recent broadcast (`22f7a215`, this morning) produced real ack rows:

```
2026-08-01T15:29:08.186987+00:00 | Cheech 🌿 #7edf6e5e…  {"kind":"ack","broadcast_id":"22f7a215…","status":"completed"}
2026-08-01T15:29:08.212469+00:00 | maria 🌸 #2b9feb77…   {"kind":"ack","broadcast_id":"22f7a215…","status":"completed"}
```

**Ran**: `grep -c "broadcast_id" io/commons/broadcast-acks.md` → **20**; all 20 carry `"status": "completed"`.

Two properties make this the right instrument, both confirmed by the write path (`cc_notification_listener.py:795` → `broadcast_handler.handle_broadcast` → `_post_ack` → `store.post(topic="broadcast-acks")`, and `CommonsStore` at `src/lupin_mcp/commons_store.py:188`, docstring **"File-based store for commons topic files"**):

- The ack is posted **by the listener at WS-receipt time**, not on the session's next turn — it measures delivery, not the session's cadence.
- The ack is a **direct filesystem write by a host-side process**. It never travels through `:7999`, so reading it does not depend on the server the script is about to kill.

Observed round-trip latency is **sub-second** (acks at `.186` and `.212` of the same second), so the poll deadline can be short.

### ⚠️ One defect the poll design must handle: acks duplicate

In the same tail, session `7edf6e5e` acked broadcast `22f7a215` **twice** — `.186987` and `.221588`, same session, same status. This is known: `_dedupe_broadcast_acks_by_recipient` (`commons.py:640`) exists for it, and its docstring records the 2026-05-15 forensic case (one recipient, three bit-identical rows). **That dedupe lives on the read path of the history endpoint, not in the file.**

⇒ A script counting raw rows in `broadcast-acks.md` will **over-count and restart early**. It must dedupe on `(broadcast_id, sender_session_id)` before comparing against the recipient count — the same key that helper uses.

⇒ Replace *"confirm 200 then pause"* with: **post the warning → take `recipients` + `filtered_out` from the 200 body → poll `io/commons/broadcast-acks.md` for that `broadcast_id`, deduped by session, until the count matches → then restart.** On deadline expiry, restart anyway but name the sessions that never acked. Bounded, observable, no magic number.

## F4 — §4.2: yes, you are fooling yourself. But you are one design move from not having to be.

The plan asserts *"there must be no bounce path that skips the broadcasts"* and then offers documentation plus an optional SIGTERM backstop. Documentation is not a mechanism, as §4.2 itself says two sentences earlier.

There is also an unnamed tension: **§4.2 wants exactly one bounce path; resilience wants at least two.** With reload off, the bounce *endpoint* (Phase 3) lives inside the very server that may be wedged. If the in-container button is the only sanctioned path, a hung server is unbounceable by the sanctioned path — so a hand-typed `docker restart` is not merely a discipline leak, it is the **recovery path**, and it has to keep working.

⇒ Stop trying to eliminate bounce paths. **Move the broadcasts to the server's own process edges**, which every path crosses:

| Edge | Emits | Covers |
|---|---|---|
| `lifespan` startup (`main.py:409`) | all-clear (R5) | every start, including crash and hand-typed restart |
| `SIGTERM` handler | warning (R4), best-effort | `docker restart`, `docker stop`, compose down |
| Bounce script, pre-restart | warning (R4), **ack-confirmed** | the sanctioned path, with a delivery receipt |

The script's warning stays because it is the only one that can be *confirmed delivered* before the kill. The SIGTERM handler backstops the paths that skip the script. Neither is load-bearing alone; together the only uncovered case is `docker kill` / OOM / power loss — where no warning is possible by anyone, and the startup all-clear still closes the loop.

**Honest limit, put it in the plan**: `docker stop` grants ~10s before SIGKILL. A SIGTERM warning must be best-effort and time-boxed, and it will sometimes lose the race. Acceptable *only because* the all-clear is independent of it. **Ran**: `grep -n "SIGTERM\|signal\." src/lupin_app/main.py` → no handler exists today; this is new code, not a tweak.

## F6 — `restart` vs `recreate` (Cheech's point, and it bites the plan twice)

`docker restart` reuses the existing container, so **compose changes, bind-mounts, env-var changes, and image rebuilds are not picked up** — only a recreate applies those. This is already in the fleet record (a single-file bind serving stale bytes by inode). Two consequences for this plan:

1. **The bounce control must name its verb, and probably needs both.** `refresh-test-server.sh` uses `docker restart`, which is right for "serve the new Python" and wrong for "apply the new mount." If the control is offered to workers and managers (R3), it needs to say which one it is, or someone will press "bounce", watch a config change not land, and conclude the config is broken.
2. **A recreate is a longer outage than a restart**, so the warning-broadcast wait and the `/health` deadline (30s in the template) both need to be sized for the slower path, not the faster one.
