## Context

Editing watched `lupin` source restarts `:7999` (uvicorn `--reload`). On 2026-07-27 six restarts inside ~70s left Rick's browser disconnected while he sat at the keyboard, and `/api/notify` returned **503 "User is offline and no default response provided"** for every blocking ask. Our own CC listeners stayed connected throughout — so any fix asserting *"the registry is non-empty"* passes straight through the failure.

The opening question was whether a small persistent cache could restore session information across a reload. **It cannot, and building it makes the failure worse** (Finding 1). The real defect is on the browser, and it is a deliberate design decision made against a different restart profile (Findings 2–3).

## The trade, in one table

| phase | what it costs | what you actually get | what it does NOT fix |
|---|---|---|---|
| **1 — reload-aware breaker** | 1 file, ~20 lines, 5 unit tests + mutation pass. **~half a day.** No schema, no protocol, no server change. | The browser reconnects **by itself within ~60s** of the last restart. No banner click. The symptom disappears. | Anything sent *during* the outage window is still lost. |
| **2 — don't lose the gap** | 2 independent halves, ~1 day each. Both reuse machinery that already exists and is unwired. No schema change. | Fire-and-forget notifications sent while disconnected **appear on return**, instead of a bare "N missed" badge. | Blocking asks — they need a live answer, so a replayed copy is a stale question. |
| **3a — hoist the idempotency check** | ~2 hours + 2 tests. | A retried ask stops minting a second prompt. | Does not dedup **across** a restart — the cache is in-memory with a 60s TTL. |
| **3b — durable pending asks** | **2–4 days**, a protocol change across MCP + server + models + browser. Needs its own design doc and review pass. | An ask fired across a restart is answered once, by the user, rather than dying as a 503. | — end of the path. |

**Recommendation**: Phase 1 alone buys most of the felt relief. Phase 2 is worth it if unattended notifications need to land. **Do not build 3b yet** — its entire value is surviving a restart storm, and Phase 1 makes that storm recoverable.

# Findings

## Finding 1 — why the persistent-cache framing is rejected

`WebSocketManager` state is all in-memory (`src/cosa/rest/websocket_manager.py:54-85`); `disconnect()` (`:210`) clears every entry. Of those dicts:

- `active_connections: Dict[str, WebSocket]` (`:54`) holds **live socket objects**. They die with the uvicorn child. Nothing on disk reconstructs a kernel socket.
- Every sibling (`session_to_user` `:56`, `user_sessions` `:58`, `session_client_types` `:68`, `session_timestamps` `:74`) is metadata and *is* serializable.

But metadata is exactly what the liveness predicate reads: `is_user_connected()` (`:788-812`) returns True when the resolved user UUID has ≥1 session id that is *also a key in* `active_connections`. Restoring the metadata restores the half that makes the predicate answer **True for a socket that no longer exists**.

⇒ `/api/notify` returns **200 `delivered`** and the message goes nowhere. **A loud 503 becomes a silent drop.** Rejected.

*(A durable session registry already exists — the bridge files under `~/.claude/sessions/` (`src/lupin_cli/claude_code/hooks/lib/session_bridge.py`). The notify path reads them for persona decoration only (`notifications.py:50`, `:80`). Teaching that surface to answer delivery-liveness reintroduces the same false positive.)*

## Finding 2 — the mechanism, and why only the browser was lost

| | browser (`ws-channel.js`) | CC listener (`base_listener.py`) |
|---|---|---|
| retry budget | 20 attempts, full-jitter 1s→30s (`:42-44`, `:349-363`) | 10 attempts, 1s→30s (`base_config.py:27-30`) |
| rapid-fail trip | **5 never-opened closes / 30s → `openCircuit()`** (`:332-343`, `:380`) | none |
| on exhaustion | **terminal `OPEN_CIRCUIT`** — `connect()` returns at `:212`; only `manualRetry()` `:416`, wired to the banner button (`notifications.js:2585-2617`), exits | **infinite outer restart loop**, 60s cooldown, `_attempt=0` each cycle (`cc_notification_listener.py:1337-1412`) |

During a reload the uvicorn parent keeps the listening socket bound (documented `cc_notification_listener.py:60-86`), so the browser's TCP connect **succeeds** but no HTTP 101 arrives — `wasEverOpen` stays false, the 10s handshake watchdog (`:316`) force-closes, and `handleClose()` books a rapid-fail. Reload windows measured ~18.76s; six in ~70s sits well inside the 5-in-30s envelope.

**That asymmetry is the whole story**: the listeners have no breaker, so they came back; the browser has a terminal one requiring a human click.

## Finding 3 — the design considered server restarts and ruled them harmless

The circuit-breaker milestone removed an off-hours reconnect gate on exactly this reasoning:

> *"reconnect attempts at 3 AM during a server restart will count against [the budget] … the spam is bounded at MAX_ATTEMPTS (default 20) regardless of clock time."*
> — `src/rnd/v0.1.7/2026.05.02-ws-reconnect-circuit-breaker/03-phase-2-notifications-integration.md:35`, `:97-100`; restated `08-rollout-and-rollback.md:63` as *"logged but harmless."*

The profile evaluated was **one restart, overnight, nobody at the keyboard**. It bounded the 20-attempt arm and never considered the **rapid-fail** arm firing during a dev edit storm with the user present. The same milestone's own research recommends the shape we are missing:

> *"never give up automatically on transport reconnect, but gate the retries with a circuit that requires user re-engagement after a budget is spent … a user staring at 'Disconnected' for 6 minutes will hit reload anyway."*
> — `…-solution-claude.md:443`

## Finding 4 — the idempotency cache has a writer with no reader

Source-verified. `_idempotency_cache` is an in-memory `OrderedDict` with a **60s TTL** (`notifications.py:116-119`).

- The **read** happens once, at `:801`, inside `if not response_requested:` (`:787`) — the fire-and-forget branch.
- The **writes** happen at `:906`, `:929` **and `:978`** — and `:978` is on the *response-required* path.

⇒ **Blocking asks populate a cache nothing consults.** A retried ask mints a second prompt. That is how the same question reached Rick twice, three minutes apart, and got two opposite answers (`860c57ee` vs `bf033a65`, 2026-07-27).

Second-order: the cache is in-memory with a 60s TTL and the reload window is ~18.76s — so a restart inside the TTL destroys the dedup record that would have suppressed the retry. Hoisting the check (3a) fixes the branch bug; it does **not** make dedup survive a restart.

# Phase 1 — reload-aware circuit breaker

`OPEN_CIRCUIT` stops being terminal. The **existing** 30s watchdog (`tickWatchdog` `:467`, timer `:508`) gains one branch: after a cooldown has elapsed in `OPEN_CIRCUIT`, run exactly **one** probe `connect()`.

**File**: `src/lupin_app/static/js/ws-channel.js` — single file, no server change.

1. Add `const HALF_OPEN_COOLDOWN_MS = 60000;` beside the constants at `:42-48`.
2. In `openCircuit()` (`:380`), stamp `circuitOpenedAt = Date.now()` and retain `reason`.
3. In `tickWatchdog()` (`:467`), replace the unconditional `if ( state === STATE.OPEN_CIRCUIT ) return;` at `:470` with: return **unless** the cooldown has elapsed **and** `reason !== "auth-permanent"`; then clear `recentFailures`, set `attempts = MAX_ATTEMPTS_PER_CHANNEL - 1`, re-stamp `circuitOpenedAt`, and `connect()`.
4. Leave `manualRetry()` (`:416`) untouched — the banner stays, and a click remains the fast path.

**Three properties, each pinned by a test:**

- **`auth-permanent` stays terminal.** A 4001/4002/4003 trip (`PERMANENT_CLOSE_CODES` `:59`) must not self-probe — re-probing a revoked token is a hammer loop, and the consumer owns token refresh.
- **The probe does not refund the budget.** `attempts = MAX-1` buys exactly one attempt; a failed probe re-trips immediately at `:352`. Only a real `auth_success` (`:279-282`) zeroes the counter — preserving the frozen Q3 invariant *"counter resets only on `auth_success`, never on TCP open, never on timer."*
- **The hidden-tab guard still wins.** `tickWatchdog` returns on `visibilityState === "hidden"` at `:469`, before any new branch.

**Also in Phase 1 (~2 lines):** `connect()` returns on a hidden tab at `:209` *after* the backoff timer has already fired and cleared itself (`:359-362`) — the wakeup is burned and nothing is rescheduled, parking the channel in `BACKOFF` with no socket and no pending timer until a `visibilitychange`. Re-arm the timer on that return instead of dropping it.

# Phase 2 — don't lose what was sent during the gap

Two independent halves; either can ship alone.

## 2a — browser fetches missed *content*, not just a count

Today the server sends `undelivered_count` on `auth_success` (`websocket.py:117-137`, `:512-520`) and the browser renders it as a badge — `_surfaceMissedNotifications()` (`notifications.js:16053-16072`) writes "N missed while away" and stops. **`GET /api/notifications/undelivered` (`notifications.py:1394-1444`) already returns the items and no browser code calls it**; the only existing client reference is the dismiss POST (`notifications.js:16084`).

- **Step 0**: read the endpoint's serializer and confirm it carries what the card renderer needs. Its location and filter are verified; its response shape is **not** — do not assume parity.
- Change: in `_surfaceMissedNotifications`, when `undelivered_count > 0`, fetch the items, render them into the existing notification list, then call the existing dismiss endpoint.
- Filter is `state IN ('created','queued') AND is_hidden = False` plus an age cap (`notification undelivered max age hours`, default 24), so this is bounded by construction.
- **Cost**: ~1 day, one JS file plus a smoke test. No server change, no schema change.

## 2b — MCP spools a 503 instead of dropping it

`src/lupin_mcp/notify_outbox.py` is a complete disk spool + background flusher keyed by `idempotency_key`. It is wired at `cosa_voice_mcp.py:1010-1105` to fire on **transport failure only** — a 503 `user_not_available` is a successful HTTP exchange, so nothing spools.

- Change: extend `_spool_failed_notify` (`:1066`) to also spool on the offline outcome, for fire-and-forget only.
- The flusher already reuses the original key, and the server already de-dups that path (`notifications.py:801`), so a redelivered item cannot double-post while the cache is warm.
- ⚠️ **Bound the TTL deliberately.** A notification arriving 40 minutes late is worse than one that never arrives, if it reads as current. Pick a TTL in minutes, not the outbox default, and record the choice on the row.
- **Cost**: ~1 day including a spool/flush unit test and one live drill.

# Phase 3 — blocking asks survive a restart

## 3a — hoist the idempotency check

Move the check at `notifications.py:790-804` **above** the `if not response_requested:` branch at `:787`, so the response-required path reads the cache it already writes at `:978`.

- **Effect**: a retried ask returns the first ask's response instead of minting a second prompt — within the 60s TTL, in one server process.
- ⚠️ **State the limit on the row**: this does **not** dedup across a restart.
- **Cost**: ~2 hours + 2 tests (one asserting the response-required path now hits the cache; one mutation restoring the branch placement and proving red).

## 3b — durable pending asks (the expensive one)

`pending_responses` (`notifications.py:107`) is an in-memory dict of `asyncio.Event` futures. A reload destroys both the future and the HTTP connection the MCP call is blocked on. Nothing on disk rescues that, for the same reason as Finding 1 — an in-flight request is not serializable state.

Making an ask survive a restart is a **protocol change**, not a patch:

1. Persist the pending question (it already has a `notifications` row — `postgres_models.py:490` carries `response_requested`, `response_type`, `state`) and treat `idempotency_key` as its durable handle.
2. Change the MCP side from *"one long blocking HTTP request"* to *"submit, then poll/resume by key"*, so a dropped connection re-attaches instead of erroring.
3. On reconnect, the browser must surface a still-unanswered question rather than a historical card.

- **Cost**: 2–4 days across `cosa_voice_mcp.py`, `notifications.py`, the notification models, and the browser. Own design doc, own review pass.
- **Recommendation: do not build yet.** Revisit only if asks keep dying after Phase 1 ships.
