## Part 3 — Design principles (these are the whole point)

Each of these is a lesson already paid for in this repo. They constrain the implementation, not decorate it.

1. **Assert ACCEPTANCE, not PRESENCE.** `os.path.exists()` passes on the exact shape that broke (mode-600 key). Check 5a said "readable"; only 6a — *does this server accept it?* — caught the wrong-value defect. **Every credential probe ends at the endpoint that consumes it.**

2. **An absence means two things — split it.** *Not mounted* logs a WARNING and is LOUD. *Mounted but empty* registers the scope and 404s every file under it, **SILENTLY** — no warning is even possible. Every mount assertion must check presence **and non-emptiness**.

3. **Never gate an alarm on the healthy value.** The Cloud SQL proxy reported `healthy` for the entire outage because its probe never touched the socket it exists to publish. Probe the **artifact**, not the **provider's self-report**: `test -S <socket>`, then a real query.

4. **An assertion is not a guard until you have deleted the thing it guards and watched it go red.** Every check ships with a recorded negative control. A check that agrees with a healthy system is indistinguishable in its output from a check that cannot fail.

5. **The instrument must not lie about the environment.** `gcloud ssh --command` opens a **non-login** shell that does **not** source `~/.bashrc`. A naive `env | grep LUPIN_ROOT` therefore reports MISSING on a perfectly-configured VM. **The preflight must read the env the way the consumer reads it** — source the profile explicitly, and report *which* surface it checked. This trap has already produced three false REDs on this VM (wrong route, wrong auth mechanism, wrong interpreter).

6. **Every FAIL carries an executable remedy.** Not "check the mounts" — the exact command.

7. **Fail-loud toward broken.** Where a probe cannot determine the answer, report `UNKNOWN` and count it as blocking. `unknown` is never folded into `pass` (the `secret_drift` rule).

## Part 5 — What this design deliberately does NOT do

- **It does not replace `docker compose`.** Provisioning stays where it is; preflight only *asserts*.
- **It does not silence the eight correct scope warnings.** Those repos genuinely are not on the VM; the registry is reporting reality (§7c).
- **It does not auto-repair.** Every failure prints a remedy the operator (or a follow-up script) runs. Auto-repair on a misdiagnosis is worse than a red line.
- **It cannot see what it does not assert.** A green preflight means *these 30 things hold* — never *the VM is fine*. The list grows every time the VM teaches us something new; that growth is the deliverable, not a sign of failure.

## Part 6 — RULED by Rick, 2026-07-26 (genuine keypress, `default_used: false`)

| Question | Ruling | Note |
|---|---|---|
| Auto-repair? | **Assert-only for v1** | Every failure prints an executable remedy; the script repairs nothing. A `--fix` flag may follow once assertions have earned it. |
| Where in the deploy flow? | **BOTH pre- and post-deploy** | *Not* my recommendation (I proposed post-only). Rick's reason is the stronger one: running both arms **distinguishes "the deploy broke it" from "it was already broken."** Today's socket outage is exactly that case — a green pre-run and a red post-run would have named the deploy as the cause in one line, instead of a stack trace and five minutes of bisection. |
| `push-unversioned` manifest | **Build it now** | Category B3 has no other home; check B3 needs the manifest to exist as data. |

### Consequence of the both-arms ruling

The pre-arm and post-arm are **not** the same assertion set:

- **PRE** answers *"is this VM in a fit state to deploy onto?"* — layers A, B3 (unversioned payloads), C (mount set), E. It **skips** B1/B2 parity (the deploy is about to change HEAD, so asserting the old one is meaningless) and skips the D-tier app probes that a mid-deploy restart will disturb.
- **POST** runs **everything**, parity included.
- A **BLOCK in PRE** stops the deploy before it touches anything. A **BLOCK in POST** reports loudly but does not roll back — rollback on a half-applied deploy is more dangerous than a named failure.
- The script therefore takes `--phase pre|post|full` (default `full` for a standalone run).

## Part 7 — Implementation shape

Following the precedent set by `src/scripts/lib/deploy-cloud-test-lib.sh` + `src/tests/unit/deploy/test_deploy_cloud_test_lib.py` (task `d8c699aa`), the work splits in two so it is testable:

| File | Role |
|---|---|
| `src/scripts/lib/preflight-vm-lib.sh` | **PURE helpers** — manifest parsing, mount-set diffing, mode/owner comparison, env-var validation, verdict aggregation. No SSH, no docker, no gcloud. Every branch behaviorally tested. |
| `src/scripts/preflight-vm.sh` | **Thin runner** — gathers real state on the VM, feeds it to the lib, prints `[OK]`/`[FAIL]`/`remedy`, exits 0/1/2. |
| `src/conf/vm-unversioned-manifest.tsv` | **Version-controlled data** — the payloads git cannot deliver, with expected owner/mode. |
| `src/tests/unit/deploy/test_preflight_vm_lib.py` | Behavioral branch coverage of the lib, per the bash-coverage note in the precedent suite. |

**Coverage note (100% mandate)**: bash line-coverage tooling (kcov/bashcov) is not part of the Lupin `pytest --cov` / `c8` gate, so the lib cannot be line-instrumented. Per precedent, the suite instead asserts **every branch of every pure function behaviorally**, and the Python in the test file is itself 100%-covered.
