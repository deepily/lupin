## 1. Problem

The cosa-voice **UserPromptSubmit hook** appends a ~400-word speakerphone rider to **every inbound turn** — including peer-DM-triggered turns. It re-states the *entire* static TTS-brevity + interactive-routing contract verbatim each time. That contract does not change turn-to-turn, so ~95% of the rider is pure repetition. In a DM-heavy cascade review the burn compounds across every reviewer DM.

**Principle**: a per-turn rider carries only what is true-now-and-changed; the standing contract lives once in the session-init `instructions` payload.

---

## 2. The rider (FINAL — unconditional, speakerphone-ON, no chorus line)

~50 words (vs ~400). The one catastrophic rule (500-char hard cap) stays spelled out; everything else is a keyword checklist pointing at the session `instructions`.

```
[turn-state] input=<voice(distance)|typed>
TTS contract ACTIVE — full rules in session instructions. This turn:
• KISS · 3LoL · NoMC C2C · NoAA — verdict first, ≤3 sentences AND ≤60 words; OVER = whole call REJECTED (silent fail). Longer ONLY WHEN ASKED
• after replying, call notify(message=<reply>, suppress_ding=True, priority='high')
• recraft for speech — no markdown/paths/JSON/URLs
• rich detail → abstract (not length-capped)
• questions → cosa-voice ask_yes_no / ask_multiple_choice / converse / ask_open_ended_batch — never AskUserQuestion
• ack receipt in 1 line before tool calls
```

Only live token in the rider is the **input modality** (`voice(distance)` vs `typed`). No `speakerphone` flag (assumed ON), no `mode`, no chorus line.

### 2a. AMENDMENT 2026-07-19 — brevity acronyms promoted to bullet 1 (Rick, direct order)

**The gap he named**, reviewing a live ASR injection: *"What's missing? The entire notion of KISS 3LoL, NoAA, etc."* The rider stated the constraint **mechanically** (`spoken ≤3 sentences AND ≤500 chars … cut to a headline`) and never named the mandate the fleet is actually drilled on — so the per-turn surface and the brevity doctrine used different vocabularies for the same rule.

**The change**: the acronyms **replace** that bullet and **lead** the list. Substitution, not addition — the rider does not grow.

**AMENDED SAME DAY — the budget is stated in WORDS, not characters.** Rick: *"LLMs suck at counting characters, but they know what words are."* A character figure is an **unactionable instruction dressed as a precise one** — the rider's only consumer cannot evaluate it, so a precise-looking number bought nothing but false confidence.

The budget is **derived** from the char cap (`spoken_word_budget()`, ratio `_SPOKEN_CHARS_PER_WORD = 8.3`), not hardcoded, so the single-source invariant survives the change of denomination: move `get_spoken_char_cap()` and the stated word count moves with it. At the default 500-char cap this yields exactly Rick's **60 words**, so deriving cost nothing.

The ratio is **deliberately pessimistic** — spoken English averages ~6 chars/word including the space, so a compliant 60-word reply projects to ~360 chars against a 500-char cap (~28% headroom). The asymmetry is the point: overshooting fails **silently** (whole call rejected, reads as the assistant going mute) while undershooting costs a few words. Round the error toward the recoverable side. Guarded by `test_a_compliant_reply_cannot_breach_the_real_cap`, which was verified RED at ratios 6.0 / 5.0 / 4.0 before being trusted.

⚠️ Enforcement remains in **characters**, server-side. Words are the *guidance* denomination only; the two must never be allowed to drift, which is why the rider states one number and derives it from the other.

**Why the reject-cap warning stayed on that same bullet** (deliberate, not leftover): breaching the cap is the one failure here that is **silent** — the whole `notify`/`ask` is rejected and reads to the user as the assistant going mute. Trading a catastrophic warning for a mnemonic would be a bad swap, so the acronyms carry the cap rather than displace it.

**Consistency**: the wording mirrors the peer-DM and STT riders (`ac661631`, `bc2b5fe9`) so all three surfaces read identically.

**Guarded by** `src/tests/unit/test_speakerphone_wrap.py`: acronym presence, **position** (asserted on bullet *index*, not mere presence — a presence-only test passes with the acronyms buried at the bottom, which is exactly what the ask forbids), cap retention on the acronym bullet, and the retired `cut to a headline` prose being **gone** (proving substitution rather than growth). All four verified red against demoted/stripped mutants before being trusted.

**SIBLING SURFACE NOT CHANGED — flagged for Rick**: the standing MCP `instructions` contract (`hook_common.py` §Speakerphone TTS Contract) also never names the acronyms; it teaches the same rule in prose. Out of scope for this order, but it is the same gap one layer up.

## 4. The once-stated contract block (move to session-init `instructions`)

State this **once** in the cosa-voice MCP server's `instructions` payload (the §"Instructions vs Per-Turn Rider" contract already lives there — this extends it). The per-turn rider (§2) then only says "TTS contract active — see instructions."

```
## Speakerphone TTS Contract (applies on every turn — speakerphone is the standing default)

CLOSING TURN: after your user-facing reply, call
notify(message=<full reply, recrafted for speech>, suppress_ding=True, priority='high').

SPOKEN CHANNEL RULES:
- Recraft for speech — do NOT pipe terminal markdown through notify(). Strip headings,
  bullets, code fences, inline backticks, file:line refs, JSON, hashes, URLs (all TTS-hostile).
- Max 3 sentences: s1 = headline/verdict, s2–3 = at most two takeaways. Speak the verdict,
  not the inventory.
- HARD LIMIT ~500 chars on the spoken payload. The server REJECTS anything longer — the
  ENTIRE notify/ask fails (perceived silence + burned retries). If near the cap, cut to a
  headline; do NOT trim word-by-word.
- All rich detail goes in `abstract` (UI card; not length-limited).

INTERACTIVE TOOL ROUTING (prefer cosa-voice blocking tools over AskUserQuestion — the user is
listening, not watching):
- yes/no → ask_yes_no
- 2–4 options → ask_multiple_choice
- one open question → converse
- multiple open questions → ask_open_ended_batch
- For ask_*/converse the SPOKEN question is ONE short line (the question only); pros/cons +
  recommended option go in the option descriptions + `abstract`, never in the spoken text.
```

**Rollout — restart the long-running importers (else the OLD rider persists).** The §2 rider is emitted in two distinct paths with different reload behavior, and only ONE auto-reloads:
- **Per-turn UserPromptSubmit hook** (`hook_common.py:774`) — spawns a **fresh subprocess every turn**, so it reads the new slim `speakerphone_wrap` the instant the file changes. **No restart needed** for this path.
- **Long-running importers** that hold `speakerphone_wrap` in **module memory** — the cosa-voice notification listener (`cc_notification_listener.py:685`, `source="voice"`) and the speakerphone REST router (`src/cosa/rest/routers/speakerphone.py`). These cache the OLD wrap at import and will keep injecting the verbose rider until **their process is restarted**.

Therefore the rollout MUST restart those long-running importers, not just edit the file: the `:7999` bounce (step 2) restarts the REST router (it's part of the cosa-voice app), but the **notification listener is a separate long-running process and must ALSO be bounced**. Symptom if skipped: the typed/hook path shows the slim rider while the voice/listener path still shows the verbose one (the exact split observed in the 2026-06-27 incident — diagnosed by María, confirmed by Rick: verbose = listener injecting mid-tool-call from stale memory; slim = the hook's fresh per-turn read).

**Estimated savings**: ~350 words/turn, compounding across every cascade DM.
