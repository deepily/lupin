## 0.5 Two deployment targets (Cloud Run GPU ↔ VM FastAPI) — READ THIS

Lupin's GCP footprint is **two separate services, billed differently** (verified live 2026-07-15):

| Target | What runs | GPU? | Billing |
|---|---|---|---|
| **Cloud Run** `lupin-model-server` (`…-uc.a.run.app`) | the model-inference server | **Yes** — `nvidia.com/gpu: 1`, cpu 8 / 32 Gi | **Scale-to-zero** (`minScale: 0` / `maxScale: 1`): idle = 0 instances = **$0 GPU**. A request cold-starts the GPU instance, it serves, then scales back to zero after the idle window. |
| **VM** `lupin-host-test` | the FastAPI Lupin app (`lupin-rest-cloud-gpu` container, `:7999`) | **No** (e2-standard-8) | Always-on: the VM meter runs the whole time the instance is `RUNNING`, regardless of traffic. |

The VM's rest app offloads **all** model inference to the Cloud Run GPU service via `LUPIN_MODEL_SERVER_URL`. The `cloud-gpu` in the container name means "the variant that talks to the cloud GPU model server" — **NOT** that the VM has a GPU.

**Billing implication:** the expensive GPU is cold-until-called (good — `$0` when idle; each call incurs a cold-start + serve). The VM's e2-standard-8 bills continuously while `RUNNING` — **suspend the VM** to stop that meter. `minScale: 0` is what makes the GPU cold-when-idle; whether it's at zero *this instant* depends on whether anything called it inside the idle-timeout window.

## 1. SSH into the VM

```bash
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap
```
- No external IP → `--tunnel-through-iap` is mandatory (already works — needs `roles/iap.tunnelResourceAccessor` + the IAP-range firewall rule, both in place).
- First run in a while? `gcloud auth login` if the token has expired.

## 2. Port-forward the servers to the laptop

Bind **laptop 6999 → VM 7999**, **laptop 7000 → VM 8000**, **laptop 7001 → VM 8001**:

```bash
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap -- -N \
  -L 6999:localhost:7999 \
  -L 7000:localhost:8000 \
  -L 7001:localhost:8001
```
- Everything after `--` is passed to `ssh`. `-N` = hold the tunnels, run no remote command. `localhost` is resolved **on the VM**, so it reaches the container's published ports.
- Then browse **`http://localhost:6999`** for the live VM Lupin.
- **7000 and 7001 will connect but nothing answers yet** — no 8000 server and no arbiter are running (see §4b, §5). They're harmless placeholders until you bring those up.
- Leave this shell open for the session; `Ctrl-C` drops the tunnels.

## 3. Bind a VM-resident source checkout to the containers (source no longer in the image)

**This is already wired.** `docker-compose.cloud-gpu.yml` host-bind-mounts the VM checkout into the container:

```
/mnt/lupin-data/lupin/src            → /var/lupin/src   (rw)
/mnt/lupin-data/lupin/io             → /var/lupin/io    (rw)
/mnt/lupin-data/lupin/src/conf/keys  → /var/lupin/src/conf/keys (ro)
```

So the "local copy" is the **VM checkout at `/mnt/lupin-data/lupin`** — Docker cannot mount your *laptop's* tree into a container running on the VM; the copy must live on the VM's data disk.

**To point the servers at your source:**
```bash
# on the VM
vm$ git config --global --add safe.directory /mnt/lupin-data/lupin   # clears the "dubious ownership" guard
vm$ sudo git -C /mnt/lupin-data/lupin fetch origin
vm$ sudo git -C /mnt/lupin-data/lupin checkout <branch>              # e.g. wip-v0.1.9-...
```
Then apply it:
- **Source-only edits** under the already-mounted `src/` are live in the container filesystem immediately. If the app isn't running with `--reload`, restart just the app process/container:
  ```bash
  vm$ sudo docker compose -f /mnt/lupin-data/lupin/docker-compose.cloud-gpu.yml restart lupin-rest-cloud-gpu
  ```
- **Mount or compose changes** (adding a new volume, changing ports/env) require a **full recreate** — `docker restart` will NOT pick up new mounts:
  ```bash
  vm$ cd /mnt/lupin-data/lupin
  vm$ sudo docker compose -f docker-compose.cloud-gpu.yml up -d --force-recreate
  ```
  (This is the documented preflight gotcha — only `rm -f` + `up -d` applies new bind-mounts.)

3. Bring it up:

## 5. Stand up the `:8001` arbiter

There's a ready, idempotent provisioning script — **`src/scripts/provision-arbiter-on-vm.sh`** (Option B: host `systemd --user`, design of record `src/rnd/v0.1.8/2026.05.30-gcp-deployment/2026.06.10-m2-arbiter-ride-along-and-vm-cutover.md §2.4`).

**Prereqs:** repo on VM with `LUPIN_ROOT` set; the running user in the `docker` group (`id -nG | grep -qx docker`); the watched container stack up.

```bash
vm$ export LUPIN_ROOT=/mnt/lupin-data/lupin
vm$ bash "$LUPIN_ROOT/src/scripts/provision-arbiter-on-vm.sh"
```
The script **validates prereqs → builds `.venv-arbiter` → installs the `systemd --user` unit** (config block `Lupin:+Testing-GCS`). It **deliberately does NOT actuate** (operator gate); it prints the two final manual commands:
```bash
vm$ loginctl enable-linger "$USER"                              # survive logout
vm$ systemctl --user enable --now lupin-arbiter-app.service     # start + enable
vm$ systemctl --user status lupin-arbiter-app.service           # verify :8001 live
```
