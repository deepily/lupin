### 3.2 The ack channel provably fires — with one defect you must handle

`io/commons/broadcast-acks.md` is live (11 KB). Broadcast `22f7a215` carries real ack rows from two sessions at `15:29:08.186` and `.212` — **sub-second round trip**, so a poll deadline can be short.

🔴 **Acks DUPLICATE.** One session acked the same broadcast **twice** (`.186987` and `.221588` — same session, same status). `_dedupe_broadcast_acks_by_recipient` (`commons.py:640`) exists for exactly this, and its docstring records a 2026-05-15 case of three bit-identical rows — **but that dedupe lives on the history endpoint's READ path, not in the file.**

⇒ **A script counting raw rows over-counts and restarts EARLY.** Dedupe on `(broadcast_id, sender_session_id)` before comparing against the recipient count.

### 3.3 Restart vs recreate — the verb is load-bearing

`docker restart` reuses the container: right for *"serve the new Python,"* **wrong for "apply a new mount or compose change."** A recreate is also a **longer outage**, so the health deadline (30 s in the `refresh-test-server.sh` template) and the broadcast wait both need sizing for the slower path.

⇒ **The control must name its verb**, or someone presses bounce, watches a config change fail to land, and blames the config.

*(Measured today: a bind-mounted single file re-resolves its inode on container **start**, so a plain restart did clear a stale-credential 401. That is a bind-mount inode, not a compose change — don't overgeneralize from it.)*

## 4. Design — Tiffany's, superseding my Rev 1

### 4.1 🔑 The tension I never named: one path vs two

Rev 1 wanted **exactly one** bounce path, so the broadcasts could never be skipped. That is wrong, structurally:

> **With reload off, the Phase-3 button lives *inside* the server that might be wedged.** So a hand-typed `docker restart` is not a discipline leak — **it is the recovery path, and it has to keep working.**

⇒ **Stop eliminating paths.** Move the broadcasts onto the server's own **process edges**, which *every* path crosses.

### 4.2 Where each signal lives

| Signal | Home | Why there | Honest limit |
|---|---|---|---|
| **All-clear (R5)** | lifespan **post-yield**… no — **startup**, after a bounded settle window (§4.2.1) | Runs on **every** start — script, hand-typed restart, crash-restart, `compose up` | the settle window is a **guessed** number; see §4.2.1 |
| **Warning (R4), backstop** | **lifespan POST-YIELD** (~`main.py:972`), **pinned BEFORE WS task cancellation** at `main.py:994+` | Runs on every **graceful** SIGTERM, and the edge already exists | `docker stop` gives **~10 s** before SIGKILL — **best-effort, will sometimes lose the race** |
| **Warning (R4), sanctioned** | the **bounce script** | The only place that can **ack-confirm before the kill** | covers only the sanctioned path |

> ### ⛔ DO NOT install a bare `signal.signal( SIGTERM, … )`
> It **replaces uvicorn's own handler**, breaking graceful shutdown, the `timeout_graceful_shutdown=5` bound, and the **Bug 5b654a15** fix at `main.py:1286` — the fix that exists *because a shutdown hang once took the whole fleet down.* **We are not reintroducing a fleet outage in order to announce outages.** Use the lifespan post-yield edge, and **pin it before** WS cancellation (`main.py:994+`) or it is a silent no-op that still looks implemented. *(Found by Rio on the spec-refutation pass, before any code landed.)*

**Uncovered by construction**: `docker kill`, OOM, and any crash **before** the lifespan yield. A process that never reaches `yield` cannot self-announce, so **no in-process fix exists** — see §7.

#### 4.2.1 The all-clear's settle window — a compromise, not a measurement

**The problem**: `perform_fanout` targets a **live snapshot** of sessions at fire time. Emitted at startup, the browser and `cc-listener` sockets have not yet reconnected after the restart blip, so **recipients may be ≈ 0.** The all-clear fires and reaches nobody — the same shape as *"200 means queued, not sent."*

> ⛔ **REJECTED: replay-on-connect.** It is *exactly* the durable-notify path Rick placed a standing hold on — `2026.07.28-ws-reload-circuit-breaker-and-durable-notify-path.md:6`, verbatim: *"DESIGN ONLY — NOT APPROVED FOR EXECUTION. Rick, 2026-07-28: 'This plan is not to be executed, DO NOT implement.'"* Its half 2 is literally *"notifications sent while disconnected appear on return."* **Do not build it.** *(It was recommended, then ruled, then caught by Krishna — see §9.)*

**Sanctioned: Option A — a bounded settle window.** After startup, poll `find_active_voice_persona_sessions()` until **at least one recipient** or a short deadline (**~10–15 s**), then fire the boot-stamped all-clear **once**. **Never blocks boot.**

**Krishna's residuals, in his words — do not smooth these:**
> (1) a straggler reconnecting after the deadline misses the live push — though `perform_fanout` still writes the durable `broadcasts` commons entry, so it's in the record, just not pushed; (2) the settle window is an arbitrary number, and true exactly-once-on-reconnect is precisely the parked durable path. So we are knowingly buying a good-enough with a named cost, not solving it.

**Tiffany's note, kept deliberately:**
> We spent this morning establishing that guessed durations are how the warning failed, and the sanctioned fix for the all-clear is a guessed duration. The difference is that this one degrades to *"in the record but not pushed"* rather than to silence — but it should be written down as the compromise it is, **so nobody later reads 15 seconds as a measured value.**

⚠️ **The 15 s is a guess. It has never been measured. Anyone tuning it must say so.**

#### 4.2.2 Crash-loop posture — CLOSED, not open

**Ruled (María, acting lead, 2026-08-01): the all-clear SPEAKS on every boot, including inside a crash loop.** A suppressed all-clear is indistinguishable from a server that never came back — the exact silent failure this design exists to prevent.

**That ruling plus AC7 (per-boot-distinguishing body) ARE the decision.** Five all-clears in two minutes must *read as a flap*, not as five identical messages people learn to ignore. **This is settled — do not re-open it as an unresolved question.**

### 4.3 The warning needs a receipt, not a sleep

Rev 1 said "confirm 200, then pause." **Refuted**: `emit_to_user_sync` fires `asyncio.run_coroutine_threadsafe(...)` and never touches the returned future (comment at `websocket_manager.py:553`: *"Don't wait for result to avoid blocking the COSA thread"*), and `_fan_out` counts a recipient `successful` the moment it **schedules**. **200 means queued, not delivered.**

⇒ **Poll `broadcast-acks` until the deduped ack count matches `recipients` from the 200 body, with a deadline.** Sub-second round trips observed, so the deadline can be short. On expiry: proceed with the bounce but **say so** — a warning that reached 3 of 5 is not a warning that reached nobody, and the operator should know which.

### 4.4 R2/R3 — one endpoint, two front-ends

A single authenticated endpoint invokes the same script; both clients get a button. **Do not implement the bounce twice.**

Resolve **before** building Phase 3:
- **Who may press it?** R3 says workers and managers, not just Rick — broader than admin-only.
- **In-flight UI state.** The client is about to lose its own WebSocket; it must show that and reconnect on the all-clear, not appear frozen.
- **Double-click / concurrent presses.** Two racing bounces are worse than one. Needs a lock.
- **Pressing it while a blocking ask is pending** kills that ask. Warn, block, or accept?
- **Which verb** — restart or recreate (§3.3)? The control must say.

### 6.1 Staging a crash-restart (for AC2 leg c)

Without a named method, leg (c) becomes the one everyone marks "verified" off the back of legs (a) and (b). **A proposed method — predicted from the config, NOT yet demonstrated:**

🔴 **DO NOT hardcode the PID.** Resolve the app process dynamically:

```bash
# Resolve the python app PID inside the target container, then kill it.
PID=$( docker exec <container> pgrep -f 'lupin_app.main' )
docker exec <container> kill -9 "$PID"
```

**Why the mechanism works**: the wrapper script ends with `python3 -m lupin_app.main` as its **last command — no loop, no trap, no supervisor** — so killing the app exits PID 1, the container exits, and the `unless-stopped` restart policy brings it back. A genuine crash-restart: **not** `docker restart`, **not** a graceful SIGTERM. It exercises exactly the `docker kill`/OOM case §4.2 lists as uncovered *for the warning* — which is the point, because the **all-clear** must close the loop anyway.

> ⚠️ **A hardcoded `7` was in this document and it was WRONG.** PID 7 is correct for `lupin-rest-dev` (verified there). In `lupin-rest-test`, PID 1 is the bash wrapper and the app is its **child at PID 8** — so `kill -9 7` **hits nothing**. Rachel checked the target container instead of trusting the number.
>
> **The failure mode this would have produced is the dangerous kind**: the container sits there healthy, the test appears to run, and a crash-restart that **never happened** gets recorded as verified. **A number measured on one container, carried to another.**
>
> *(This was flagged in-doc as "predicted, not demonstrated." That flag is what made it cheap to catch — keep the practice.)*

**Every guard gets mutation-proofed**: revert the guard, watch the test go red, siblings stay green. A test that cannot fail is indistinguishable from an absent one.
