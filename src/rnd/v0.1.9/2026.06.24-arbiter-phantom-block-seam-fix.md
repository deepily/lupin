## TL;DR

The heartbeat arbiter loop-fires a **phantom** advisory — `"maria is blocking worker mr radio"` (cc) plus the periodic `"1 blocked: mr radio"` observation — with **zero store backing**. ## Root cause — the seam mismatch

The peer edge and the staleness filter read **two different records**:

| Concern | Source record | Code site |
|---|---|---|
| Edge minted (`holding_on: peer:X`) | `last_activity.awaiting` (heartbeat/activity stream) | `fleet_data_model.py:412` — `"holding_on": ( last_activity.get( "awaiting" ) or "none" ) if last_activity else "none"` |
| Edge filtered (drop dead-hold edges) | the **hold file** via `_hold_reader_fn(sid)` | `arbiter_job.py:2210` `_stale_hold_holders` → `dependency_graph.hold_is_stale` |

`_stale_hold_holders` only **subtracts** an edge when the holder's hold is **provably DEAD** (`hold_is_stale`), and its contract explicitly states *"a session with NO readable hold is NOT added (absence ≠ deadness)."*

**The gap:** a holder whose **current hold says `awaiting=none`** (fresh, honored) but whose **`last_activity.awaiting` still says `peer:maria`** (a stale activity record) mints a phantom edge that the filter does **NOT** drop — because the hold is *fresh* (not stale), and the hold's authoritative `awaiting=none` is **never reconciled against** the bridge/last_activity `holding_on`. A fresh hold that *contradicts* the stale edge should kill the edge; today it doesn't.

**Secondary gap (confirm + cover):** a *dead* session whose bridge still carries `holding_on: peer:X` but has **no hold file** → `absence ≠ deadness` → edge survives. The `alive_personas` pruning at `arbiter_job.py:~1026` may or may not already cover this for the outbound-ping path; the crew must determine whether it covers the **advisory** path too.

## Proposed fix (design it; this is the direction, not the literal patch)

**Reconcile the live hold's `awaiting` against the derived `holding_on` edge.** A holder with a **fresh/honored** hold whose `awaiting` is `none` (or does not name the same peer as `holding_on`) must contribute **ZERO** peer edges — the hold's declared `awaiting` is authoritative over a stale `last_activity.awaiting`. Extend `_stale_hold_holders` (or add a sibling reconciliation upstream of `build_graph`, applied to BOTH the advisory graph and the cc path) so the subtraction set includes:

- holders whose hold is **dead** (today's behavior — keep), AND
- holders whose hold is **fresh but `awaiting` contradicts the `holding_on` peer** (new — kills this phantom).

Keep it **additive and fail-SAFE**: unwired seam / unreadable hold / store hiccup → no change from today (never suppress a *real* escalation). Apply the staleness/reconciliation filter **upstream of every edge consumer** (advisory "X blocking Y", outbound ping/cc, and — carefully — without breaking the store-corroborated deadlock escalation that intentionally reads the UNFILTERED cycle graph at `arbiter_job.py:1018`).
