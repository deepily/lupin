## 1. The defect

`park_reason` is a **frozen quote** of a row's decisive sentence, captured at park time:

> `7b449098` → *"NOT TO BE WORKED per Rick's direct instruction"*

Amend the row afterward and the quote stays syntactically valid while it stops being true. **Nothing goes red.** A reviewer reading a parked row is told a story that was accurate once, with no signal that it has expired.

This is the species María relayed from Tiffany: **a test went stale without going red** — the contract changed underneath, the assertion stayed true under both designs, the docstring described behavior the code no longer had.

**You cannot stop prose going stale. You can only make the divergence visible.**

## 2. Alternatives rejected

| # | Option | Why rejected |
|---|---|---|
| 2 | Re-attest the quote at unpark | Routes through a human noticing. Also fires too late — the stale quote misleads for the whole park window, and unpark is exactly when nobody re-reads it. |
| 3 | Accept as prose, document it | Honest but inert. Converts a detectable defect into a documented one. |
| 4 | **Derive capture time from `task_events`** (no new column) | The park event is already append-only with `ts` + `transition` + `reason` (`postgres_models.py:1457-1487`), so "when was this parked" IS already recorded — this is the `unpark_when` instinct correctly applied, and any reviewer will land here. **Rejected because the predicate lives in the HOT READ PATH and needs a SQL twin**: deriving it means a correlated subquery per row (latest park event per item), which is materially harder to mutation-test for parity than a column comparison. The column is justified — but only against this alternative, not by default. (María, review 2026-07-19.) |
| **1** | **Store capture timestamp, flag STALE on read** | **The only mechanical option** that keeps the read path a plain column comparison. No human in the loop. |

María's ruling, verbatim: *"It is the ONLY one of the three that makes staleness DETECTABLE; 2 and 3 both route through a human noticing."*

⚠️ **Consequence of rejecting option 4**: `park_reason_captured_at` and the `task_events` park row become **two records of one fact** — the exact defect class this plan exists to fix. Mitigation is mandatory, not optional: **write both in the same transaction**, and carry a test asserting they agree (AC10).

## 3. The change

### 3.1 Schema
One new column on `task_items`:

```
park_reason_captured_at   TIMESTAMPTZ NULL
```

- Set at park time to the **POST-write `updated_ts`** — the value the park write itself stamps on the row. Not `now()`, and **not the pre-write value** — see §3.4.
- Invariant at park: `park_reason_captured_at == updated_ts`, exactly.
- Parallel DB CHECK, matching the existing `parked_requires_reason` pattern:
  `status != 'parked' OR park_reason_captured_at IS NOT NULL`

  ⚠️ **THIS CHECK CONSTRAINS THE WRITE PATH, NOT JUST THE DATA — READ §3.4 BEFORE IMPLEMENTING THE PARK.** It is evaluated **per statement**, and PostgreSQL **cannot defer a CHECK** (`DEFERRABLE` accepts UNIQUE/PK/FK/EXCLUDE only). Therefore **any multi-statement park that sets `status='parked'` before `park_reason_captured_at` dies on this constraint mid-transaction, in every ordering.** A schema decision silently foreclosed a write design; the two sections must be read together, and this document shipped for several hours with them contradicting each other. **In-memory SQLite cannot prove a Postgres constraint boundary** — which is why 156 unit tests passed over a park that could not execute.

### 3.2 The predicate
Lands in `src/cosa/rest/task_store_owed.py`, beside `park_is_active` / `is_owed`:

```
park_reason_is_stale( status, park_reason_captured_at, updated_ts ) -> bool
    # True iff status == PARK_STATUS
    #      AND park_reason_captured_at is not None
    #      AND updated_ts > park_reason_captured_at
```

**Twin required**, per the same rule as the existing pair: a SQLAlchemy expression alongside the Python one, **genuinely independent** (neither calls the other, no shared helper), so the parity gate can mutation-test them.

📌 **STATE OF THE TWIN AS SHIPPED — IT HAS NO WIRE CONSUMER, AND THAT IS A CHOICE, NOT AN OVERSIGHT.** `park_reason_is_stale_clause` appears exactly twice repo-wide — its own `def` and its `__all__` entry — plus tests. **Both `_serialize_item` and `_serialize_item_terse` call the PYTHON predicate**, whose null arms `return False` explicitly. Staleness is advisory and therefore never enters an owed-ness filter, which is the whole reason the clause has nothing to read it. ⇒ The SQL twin exists as a **parity / mutation-testing artifact**, and becomes load-bearing only the day a query filters on staleness. **Say this out loud rather than assuming it**: a reader who finds a twin with no callers will otherwise conclude it is dead code and delete it, taking the parity gate's second half with it.

📌 **WHERE THE NULL GUARDS ACTUALLY EARN THEIR KEEP — NOT PRODUCTION.** Established by two seats independently, from opposite directions, and confirmed by measurement:
- **Unreachable in production.** `updated_ts` is `nullable=False` + server_default; the CHECK forbids NULL `park_reason_captured_at` on exactly the parked rows; and SQL three-valued logic closes the rest — **`FALSE AND NULL` is FALSE**, so a non-parked row cannot project NULL *even with the guards deleted*; only `TRUE AND NULL` (a parked row with a NULL operand) yields one. The two conditions cannot co-occur on a real row.
- **Measured, not merely derived**: the real clause and the null-blind mutant were both run as projections over all **1049 live dev rows** — real clause 0 NULL / 0 true / 1049 false, **mutant 0 NULL as well.** On production data *the mutant is indistinguishable from the real thing.*
- **They earn their keep on unconstrained TEST substrates**: the hand-rolled portable DDL in `test_migration_reheal_project_aliases.py` carries the columns and **no CHECK at all**, so parked + NULL captured_at IS constructible there and the null-blind clause returns NULL. `create_all`-built substrates DO emit the CHECK.
⇒ **Document the guards as TOTAL-ness fail-safes over the input domain, never as production defenses** — the predicate is called on dicts and ORM rows that never passed a CHECK. No wire-level coercion; the boundary already returns a strict `bool` on all six null-matrix shapes, verified by `type()`.

⚠️ **THE STANDING COST OF THE TWIN PATTERN — INDEPENDENCE DUPLICATES THE COVERAGE DUTY.** `owed_status_row` does its own coercion and deliberately does NOT call `park_is_active`; that independence is load-bearing, since it is precisely what lets a mutation sweep move one side while the other holds. **But it means every arm exists twice, and only one copy tends to get tested.** *Receipt, 2026-07-19: `cosa.rest.task_store_owed` sat at 94% with the residual entirely in `owed_status_row`'s coercion arms — `park_is_active`'s string/tz arms had tests, its twin's had none, and the gap was invisible because the module read as well-covered.* ⇒ **Whenever an arm is added to one twin, the same arm is owed on the other, in the same change.** This will re-open otherwise, and it will re-open silently.

*(Note on the closing number: `cosa.rest.task_store_owed` reached 100% lines AND branches, 0 missing — but that is 100% of what the project measures, 8 of 9 functions, with `quick_smoke_test` excluded from the denominator by `pyproject`'s `exclude_also` under standing project-wide policy. Stated because "100%" and "100% of what is measured" are different claims, and the seat that produced the number is the one who insisted on the distinction.)*

### 3.3 Surfacing
- `task_query` returns `park_reason_stale: bool` on every parked row.
- Terse projection includes it — a staleness flag nobody sees is option 3 wearing option 1's clothes.
- **Advisory only.** A stale `park_reason` does NOT change owed-ness, does NOT unpark, does NOT block. It marks the quote untrustworthy, nothing more.

### 3.4 The ordering trap — read this before implementing

Writing `park_reason_captured_at = now()` is **wrong** and will look right. So is capturing the **pre-write** `updated_ts` — and that is what THIS SECTION ORIGINALLY PRESCRIBED. It was caught in review; the correction is below.

**The mechanism**: `updated_ts` carries `onupdate=func.now()` (`postgres_models.py:1391-1396`, ORM-client-side, no DB trigger). **The park write bumps it.** Therefore:

| Capture value | Result at park | Verdict |
|---|---|---|
| `now()` | races the `updated_ts` stamp; born stale or born fresh depending on microsecond order | ❌ non-deterministic |
| **pre-write** `updated_ts` | `captured_at < updated_ts` the instant park commits → predicate fires → **every row born STALE** | ❌ the trap itself |
| **post-write** `updated_ts` | `captured_at == updated_ts` at park (not stale); any later amendment bumps `updated_ts` strictly greater (stale) | ✅ correct |

⇒ ~~Capture the **POST-write `updated_ts`** — the value the park write itself sets, read back in the same transaction.~~

🔴 **STRUCK — THAT SEQUENCE CANNOT COMMIT. §3.1's CHECK FORBIDS IT.** Found by seat 2 (session 7889d857) implementing it exactly as written: the first flush writes `status='parked'` with `park_reason_captured_at` still NULL, and **a CHECK is evaluated PER STATEMENT, not at commit**, so the park dies on its own constraint before the second statement is reached:

```
psycopg2.errors.CheckViolation: new row for relation "task_items"
violates check constraint "ck_task_items_parked_requires_captured_at"
```

**PostgreSQL cannot defer a CHECK** — `DEFERRABLE` accepts UNIQUE / PK / FK / EXCLUDE only — so **no ordering of the two-step works.** The read-back formulation is dead in every variant, not merely mis-ordered. *It passed 156 unit tests and 500'd on the first real park.*

✅ **THE SHIPPED MECHANISM — one clock read, one value, one statement:**

    ts = SELECT now()                        -- DB clock, same transaction, read ONCE
    UPDATE … SET status = 'parked',
                 park_reason            = <quote>,
                 park_reason_captured_at = ts,
                 updated_ts              = ts   -- written EXPLICITLY
    task_events.ts = ts                        -- same value stamps the park event (AC10)

Three properties, each load-bearing:

| Property | Why it is required |
|---|---|
| **One value assigned in one statement** | Equality is true **by construction**, not by two values happening to agree. Pins AC3 at the mechanism — strictly stronger than the read-back it replaces. |
| **`updated_ts` written EXPLICITLY** | An explicit write **suppresses `onupdate` for that statement**. Omit it and `updated_ts` advances past the capture — every row born stale, §3.4's original trap arriving through its own fix. |
| **DB clock, never `datetime.now()`** | Every other `updated_ts` in the system is DB-clock. A cross-clock comparison **fails toward false FRESH** — silently toward the very defect being detected. Rule 10 applied to a clock choice. |

⚠️ **The invariant is unchanged and still EQUALITY** (AC3). What changed is that equality is now guaranteed by the write's shape rather than asserted about two separately-produced values.

> **Note for the record, third revision of this section.** §3.4 has now been wrong three times: it prescribed the born-stale arm in draft (caught in review by María), it framed the capture as a read-back (caught by seat 2 executing it), and its prescribed sequence was forbidden by §3.1 of the same document (same seat, same minute). **Every correction came from someone implementing it; none came from anyone reading it** — including two review passes and a manager who had the trap memorised. §6's finding, a third time, in the section written to prevent it.

⚠️ **The invariant is EQUALITY, not "not stale".** *Immediately after park, `park_reason_captured_at == updated_ts`.* Asserting merely `park_reason_is_stale == False` is **one assertion short of pinning the ordering** — it also passes for a `now()`-written-after implementation that leaves an undetectable amendment window. AC3 asserts equality for exactly this reason.

> **Note for the record**: this section prescribed the born-stale arm of its own trap. The plan that named the failure mode committed it in the sentence meant to prevent it. Caught by María, not by its author — §6's finding, one more time.

## 6. Standing rules this crew inherits (earned 2026-07-19, all the hard way)

1. **Migration ids**: never continue the visual hex pattern of neighbouring files — it walks into the absorbed range. Check `_ABSORBED_REVISIONS` first. (`a3b4c5d6e7f8` collided with a live migration.)
2. **Renaming a migration is only safe BEFORE it has run anywhere.** A revision id is a value written into every database that ran it. After a rename, check `alembic_version` in every live DB in the same breath. (This took `:7999` down for ~10 min.)
3. **Container liveness ≠ application liveness.** `docker ps` read "Up 5 hours (healthy)" through ten minutes of a dead app. Read the logs.
4. **State instruments are blind to transient writes.** `find -newermt` and md5 manifests both compare two instants — a create+delete leaves no trace in either. Use pytest's `--collect-only` ID list as the witness for "could a phantom have run."
5. **`-newermt` with a RELATIVE string is blind** (silently matches nothing). Absolute timestamps only. `find` itself is fine.
6. **`timeout` kills the wrapper, not the pytest child.** Orphans keep running and keep their fd.
7. **Never reuse a log path across runs.** Two processes, one file, and `tail` silently picks a winner. Timestamp it.
8. **Reconcile reported duration against wall clock.** One subtraction; it catches the above instantly.
9. **Every attestation carries its own positive control**, and the control must not perturb what it measures (a canary cannot attest to a freeze).
10. **State which way your instrument lies**, and whether that direction can hurt the claim. Noise pushing *away* from your conclusion is safe; a clean instrument failing *toward* it is not.
11. **"Passes in isolation" / "didn't reproduce" / "probably stale" are diagnoses of MECHANISM, not exonerations.** A red is a defect until run to ground.
12. **Suite receipts state the env they ran in.**
13. **A freeze covers WRITES and RUNNING SUITES.** Report in-flight suites to the manager.
14. **A control licenses only what its scope covers.** State what the control covers, then check that against what is being asserted. *Receipt: an md5 tree-manifest control PASSED and was correct — it validated the tree, while the number it appeared to license came from a different process writing the same log.*
15. **A correction is a claim and carries a receipt like any other.** `docker inspect StartedAt` answers WHEN, never WHO. *Receipt: the 14:07:59 restart was attributed from StartedAt alone by two seats in succession, each while correcting the other's version of the same error. It remains unattributed.*
16. **A memento is read cold, by a seat with no way to check it — receipt its claims accordingly.** Conversation claims get challenged; memento claims get inherited. *Receipt: one unreceipted memento sentence was inherited on rehydrate, relayed to a second seat as a correction, and re-derived by a third before any receipt existed.* (María, self-struck 2026-07-19.)
17. **A negative result is evidence only when the instrument has been shown capable of a positive one.** *Receipts: `find -newermt` with a relative string matches nothing and returns clean-empty; a search over a leading-dash directory name parses it as an option and returns clean-empty; a grep at a nonexistent path returns a warning plus a zero count.*

18. **ON A `--reload` SERVER SHARING ONE DB, THE MODEL EDIT *IS* THE DEPLOY — AND IT LANDS BEFORE ITS MIGRATION.** Adding a `mapped_column` to `postgres_models.py` hot-loads into the live `:7999` within seconds; the ORM then SELECTs a column the database does not have, and **every** `task_query` returns 500 fleet-wide — the store being the owed-work oracle that the Stop-hook and the arbiter both read. There is no local-only stage in which to hold a model edit. *Receipt: 2026-07-19 ~18:53, `psycopg2.errors.UndefinedColumn: column task_items.park_reason_captured_at does not exist`, from an in-progress seat-1 slice with 11 CC listeners live against the store.* ⇒ **Model and migration land together, migration first.** A brief that says "proceed on the unblocked half" while the migration waits on a manager ruling has not identified an unblocked half — that instruction was the manager's error, not the seat's. Corollary: the restore is to LAND the migration, never to hand-ALTER the column in (unreproducible, drifts the two DBs, and it makes the backfill verification measure a hand-made column) and never to revert the model file (a checkout wipes peers' uncommitted work in a shared tree).

18b. **COROLLARY — ON DEV, *WRITING* A MIGRATION FILE IS *APPLYING* IT, SO "TEST FIRST, THEN DEV" IS NOT ENFORCEABLE THERE.** `main.py:445` runs `alembic upgrade head` inside the lifespan, and `StatReload` fires on **every watched-file save** — so the next save of any watched file after a migration lands stamps `lupin_db_dev` automatically, whoever wrote it and whatever they intended. *Receipt, 2026-07-19: migration file mtime `22:54:36Z`; seat 1 reported both DBs at head via a deliberate test→verify→dev run at `22:56:29Z`; the next lifespan auto-migrate fired at `22:56:47Z` and was a no-op. The ordering condition was satisfied by an **18-second margin, in a race the seat did not know it was in** — thirty more seconds spent verifying the test DB and the reload would have backfilled 25 live parked rows before verification.* ⇒ **A staging condition the platform can satisfy on its own is not a control; it is a coin-flip that reports success.** Verify on the test DB *before* the migration file exists in a watched path, or accept that dev is migrated the moment you save.

19. **A BACKEND CAN DISARM YOUR TRAP AND LEAVE THE GREEN LOOKING EARNED.** On Postgres, all three candidate write orderings for `park_reason_captured_at` yield EXACT equality at park — `now()` is `transaction_timestamp()`, stable across the transaction, so a second flush's `onupdate` re-fire returns the same value. **§3.4's born-stale arm cannot fire within one transaction on PG.** ⇒ "0 equality violations on PG" proves the ordering was SURVIVABLE, not that it was IMPLEMENTED; the trap this document is built around is disarmed by luck on our own production backend. Pin the mechanism explicitly (one captured value written to both columns in one statement, stamped into the `task_events` park row) so AC3 and AC10 hold on any backend, and state in the docstring WHY the equality holds so no later reader concludes more from it than it proves. *Found by seat 2 (7889d857) probing in isolation on a throwaway DB — after auditing away three successive instrument defects in the probe itself, the first run of which printed "AC4 BROKEN" three times in clean, plausible output.*

19b. **EVERY DELIBERATE DUPLICATE CARRIES A STANDING OBLIGATION TO UPDATE ALL COPIES IN THE SAME CHANGE — AND EVERY ONE OF OURS HAS NOW FAILED IT.** This system duplicates on purpose in at least three places, each for a good reason, and the duplication is invisible at the moment you edit one copy:

| Duplicate pair | Why it exists | How it failed |
|---|---|---|
| Python predicate ↔ SQL twin | independence lets the parity gate mutation-test them | *(guarded — this is the one that works)* |
| `park_is_active` ↔ `owed_status_row`'s own coercion | independence is load-bearing for the mutant sweep | only one copy's arms had tests; module sat at 94% with the gap invisible |
| ORM model ↔ hand-maintained portable SQLite DDL twin | portability for migration re-heal tests | `park_reason_captured_at` landed in the ORM, not the twin — **and the guard that caught it says in its own docstring that it exists because `urgency` drifted identically in June.** Same defect, same file, one column later |

⇒ **Adding a column, an arm, or a key means finding every deliberate copy in the same change.** The guards firing is the system working; *a guard being needed twice for the same file* is the finding.

19c. **A FILTER-SHAPED TEST CANNOT SEE A NULL GUARD — TEST THE SHAPE THE CODE IS ACTUALLY USED IN.** In a WHERE clause, `updated_ts > park_reason_captured_at` against a NULL evaluates to NULL and PostgreSQL discards the row *anyway* — so an explicit `isnot(None)` guard is **invisible to any membership/filter test**, and a mutant that deletes it SURVIVES. Re-run the same clause as a **PROJECTION** — the shape §3.3 uses to surface `park_reason_stale: bool` — and the mutant returns **`None`** where the Python twin returns **`False`**. ⇒ **The parity matrix must cover BOTH shapes**, and a `bool` field that is sometimes `None` is exactly what §3.3 promises it is not: coerce at the projection boundary, at the source, never at the consumer. *Found by seat 1 reading a surviving mutant as "my gate has the wrong shape" rather than "the mutant is inert."*

19d. **A UNIT SUBSTRATE CARRIES COLUMNS WITHOUT CONSTRAINTS — SO A GREEN THERE SAYS NOTHING ABOUT WHICH ROW SHAPES ARE REACHABLE.** Every unit substrate in this build is metadata-built or hand-rolled: it has the twins' three columns and **none of the table's CHECKs**. ⇒ **Any test whose docstring explains WHY a row shape is legal must be re-read against the constraints that actually exist.** *Receipts, both from the same file in one evening: (a) `test_a_parked_row_with_no_capture_reads_not_stale` justified itself by citing §7's no-backfill clause — a clause that had been STRUCK — to describe a row shape the CHECK forbids and the migration backfills away, and it passed throughout because SQLite had no CHECK to violate; (b) the §3.4 two-step park passed 156 unit tests and 500'd on the first real park, because* ***the unit tier did not fail to test the sequence — it tested it against a substrate with no CHECK to violate. Green meant "no CHECK here" and was read as "the sequence works."*** *(Arnold's formulation.)* Such tests are still worth keeping — as explicit FAIL-SAFES proving the predicate is **TOTAL**, since in-memory readers call it without the CHECK travelling with them — but they must say so, and must not be read as evidence a shape occurs.

19e. **A MUTANT SWEEP IS ONLY AS COMPLETE AS ITS MUTANT LIST, AND A MISSING MUTANT IS INVISIBLE BY CONSTRUCTION.** The seat that reported **8/8 killed** did not have a *weak* drop-null-guards mutant — **it had none at all.** Its sweep carried null-arm-INVERTED, which is visible precisely because inverting ADDS rows, while the *deletion* of the same guard changes no row set under a filter. ⇒ **A clean sweep over an untested guard is indistinguishable from a clean sweep over a tested one**, and running it harder can never reveal the gap. This is `f68bc520` relocated into the test layer: correct components, faithfully exercised, with the seam between them unowned. ⇒ **Derive the mutant list from the code's guards, one mutant per guard, and check the list against the source — do not accumulate mutants by inspiration.** *The corrected sweep asserts BOTH halves — the mutant SURVIVES the filter (identical row set, which is WHY a filter-only sweep false-greens) and DIES in projection — because either half alone misleads.*

19f-bis. **`git add` IS A GLOBAL MUTATION — THE INDEX IS SHARED, SO YOUR STAGED FILES LAND IN A PEER'S COMMIT UNDER A PEER'S MESSAGE.** Strictly worse than the `--amend` hazard below, because **it needs no concurrent commit to bite — only a concurrent STAGE**, and the victim is whoever commits *second*, who did nothing wrong. *Receipt, 2026-07-19 20:59: the manager staged 8 files (the `f68bc520` wire path + seat 2's staleness write/surfacing) and was composing the message; a seat's `git commit` — by explicit path, correctly — swept all 8 into `b49ddc9f`, a commit whose message describes only its own single file. **`git log -1` would NOT have caught it: HEAD had not moved.*** ⇒ **The check is `git diff --cached --stat` immediately before every commit**: if the staged set is larger than your own edits, it is carrying a peer's work. ⇒ And the repair is **not** a reset or an amend — the content is correct and committed; **record the truth rather than rewrite shared history.**

> **`b49ddc9f` — WHAT IT ACTUALLY CONTAINS**, since its message under-describes it: the `f68bc520` six-layer `park_reason` wire path (authored by the pre-respin seat Clayton, reaped 22:52 before it was committed); seat 2's single-statement DB-clock capture of `park_reason_captured_at` + `updated_ts` with the same instant stamped into the `task_events` row; `park_reason_stale` in the full and terse projections; four drift-fix unit files; **and** the mutant-adequacy generator its message names. Verified 184 passed on that surface; live proof `ts-6f7168ee`, 5/5 on real Postgres.

19f-ter. **A STALE INDEX AFTER YOUR OWN `reset --soft` IS A STAGED REVERT WAITING FOR WHOEVER COMMITS NEXT — AND IT WILL NOT BE THE PERSON WHO CREATED IT.** `reset --soft` moves HEAD and **leaves the index behind**. If the index then disagrees with HEAD in the deleting direction, the next commit by ANY session silently removes that code under whatever message its author thought they were writing. *Receipt, 2026-07-19 ~21:02: a repair sequence left index-vs-HEAD reading **26 insertions / 259 DELETIONS**, including stripping `park_reason` from `task_transition_impl` — the P0 wire path — with **nothing pending and no commit intended.** Caught by the seat running `git diff --cached` on the result of their own reset and reading the hunk DIRECTION; the manager saw the same numbers in their own output, called them "confusing," and moved on. The manager's re-commit was path-scoped (`git commit -- <paths>`), which bypasses the index for named paths — **safe by accident, not by understanding.***

⇒ **THREE CHECKS, THREE HAZARDS, ONE SHARED TREE:**

| Check | Catches | Blind to |
|---|---|---|
| `git log -1` before amending | a **moved HEAD** (rule 19f) | a peer's staged files; a stale index |
| `git diff --cached --stat` before committing | a **peer's staged work** (rule 19f-bis) | a landmine with nothing pending |
| **`git diff --cached` AFTER every HEAD-moving operation** | a **stale index / staged revert** | — |

19f-quinquies. **AFTER A PEER'S RESET, EACH SEAT MUST RE-VERIFY ITS OWN COMMITS' REACHABILITY — NO SINGLE SEAT CAN DO IT FOR EVERYONE.** A reset backwards and then forwards can strand anything committed **inside** the window, and the seat performing it does not know whose commits those are. ⇒ **The structural reason this cannot be delegated**: the seat that observes the reset can see the *window*; only each other seat can see which of its *own* commits fall inside it. **Neither view contains the other** — this is a blind spot on a shared branch, not a diligence gap. *Receipt, 2026-07-19: three commits by a seat uninvolved in the reset sat inside the `cfcbf0cf → b49ddc9f` window; they survived, but that outcome was not knowable without that seat checking for itself.* ⇒ Announce a reset to every active seat, and **each seat re-verifies its own** with `git branch --contains <own-sha>` plus a content spot-check.

19f-sexies. **A NET-NEGATIVE LINE COUNT IN A STAGING DIFF IS A RED FLAG, ALWAYS — ASK WHY BEFORE DOING ANYTHING ELSE, AND READ DIRECTION RATHER THAN FILENAMES.** This sits *above* the three checks: they tell you **where** to look, this tells you **what you are looking at.** *Receipt: `26 insertions, 259 deletions` was on two seats' screens; one read the file list and moved on, the other read the direction and found a staged revert of a P0 wire path.* Generalises past git to any diff, patch, or migration preview: **a change that removes more than it adds is a claim that needs a reason.**

19f-quater. **ON A SHARED BRANCH, A REACHABILITY CHECK IS ONLY TRUE AT THE INSTANT IT IS TAKEN.** `--is-ancestor`, `branch --contains` and `status` are all point-in-time: a peer's `reset` can dangle a commit you verified a minute ago, or **un-dangle one you declared lost.** *Receipt: two seats measured the same commit four minutes apart and reached opposite, individually-correct conclusions — `b49ddc9f` was reachable, then dangling (branch reset back to `cfcbf0cf`), then reachable again. Neither instrument was wrong; the thing being measured moved.* ⇒ Re-verify immediately before acting on any reachability finding, and **prefer `git reflog` over `git log` when reconstructing what happened — the reflog is the only record that survives a ref moving backwards.**

19f. **`--amend` AMENDS WHATEVER `HEAD` IS *NOW*, NOT THE COMMIT YOU THINK YOU MADE.** On a shared branch with concurrent committers, HEAD moves between your commit and your amend, and the amend **silently absorbs your work into a peer's commit and keeps THEIR message.** *Receipt, 2026-07-19: a seat amended four times in one evening; the fourth landed on a peer's commit, publishing that peer's 3 files and the amender's 2 as one commit under the peer's subject.* ⇒ **Check `git log -1` immediately before every amend, or do not amend at all on a shared branch.** Repair is `git reset --soft <peer-sha>` — it moves HEAD only, leaves index and working tree untouched, and restores the peer's commit at its exact sha; verify both originals are intact **first**. Never `checkout`, `reset --hard`, `stash`, or `clean` on a tree carrying peers' uncommitted work.

19g. **A PARAM NAME LEARNED FROM A TOOL DOCSTRING IS NOT A WIRE CONTRACT — AND UNKNOWN QUERY PARAMS FAIL SILENT AND DEFAULT, NEVER LOUD.** The MCP tool and the HTTP router are **two vocabularies for one store**: `include_parked` (MCP) vs **`hide_parked` (HTTP, default True)**. FastAPI **silently ignores** an unknown query param — so the wrong spelling is not a 422; it is the default staying in force, an empty result, and an assertion firing as *"the parked row is absent from its own terse query."* **A green-looking API that quietly did the opposite of what was asked.** ⇒ Verify param names against the **router signature**, never the tool docstring; verify the envelope too (`{ tasks, count }`, not `items`). *Two-records-of-one-fact in the vocabulary layer — the class AC10 guards at the data layer — live in this build.*

19h. **A DEFENSIVE HEDGE MARKS THE SPOT WHERE SOMEONE DECLINED TO FIND OUT.** Both fixture defects above sat under an `isinstance` fallback written to tolerate two response shapes. **The hedge was not protecting against a real ambiguity — it was hiding that the shape had never been verified at all.** ⇒ The house prohibition on defensive `getattr`/`isinstance` chains is not only style: **a hedge is a detector.** When auditing, grep the fallbacks first — each is a place a claim went unchecked. *Found by a seat pulling on its own hedge because the style forbade it, and finding two live defects underneath.*

19i. **DERIVE THE MUTANT LIST FROM THE AST, AND MAKE THE SWEEP CLASSIFY EACH GUARD RATHER THAN MERELY PASS.** Two halves, both mechanical:
- **Generation** — for an N-term conjunction: **DROP each term AND NEGATE each term**, plus operator variants on each comparison. For `park_reason_is_stale_clause` (4 terms, 1 comparison) that is **11 mutants — derived, not judged.** *A list built this way cannot be short by forgetting.* DROP and NEGATE are **not interchangeable**: on the same null guard, NEGATE lands LIVE (inverting ADDS rows, so a filter sees it) while DROP lands FAIL-SAFE (deletion is invisible to a filter). A sweep carrying only NEGATE is structurally blind, **not careless** — which is exactly how an 8/8 came back green over a guard that had never been exercised.
- **Classification** — run every mutant through **every shape** (filter AND projection) and cross-reference **reachability**, then read the survival pattern:

| Survival pattern | Verdict |
|---|---|
| dies in every shape | **LIVE GUARD** |
| dies only in some shapes, on REACHABLE rows | **SHAPE-SENSITIVE** — a gate testing the other shape false-greens |
| dies only on UNREACHABLE rows | **FAIL-SAFE** — correct to keep, wrong to call a production defense |
| survives everywhere on reachable data | **DEAD CODE or blind gate** |

*Result on this build: **LIVE 9 · SHAPE-SENSITIVE 0 · FAIL-SAFE 2 · SURVIVES-EVERYWHERE 0** over 48 rows (31 reachable, 17 forbidden by CHECK/NOT NULL), with the two FAIL-SAFEs auto-identified as the null guards and no human deciding it.* ⇒ **Reachability belongs in the verdict as a COLUMN, not as a follow-up question someone must think to ask** — had it been, tonight's null-guard finding would have been labelled FAIL-SAFE at the moment of discovery instead of being escalated as a live wire defect and walked back an hour later. **That is the fix for that class: a required step, not a resolution to be more careful.**

19j. **CARE DOES NOT SURVIVE TRANSCRIPTION; A CHECK DOES — AND A COMPLETENESS CHECK THAT HAS NEVER FAILED IS INDISTINGUISHABLE FROM ONE THAT CANNOT.** *Receipt: the seat who wrote `test_the_mutant_list_is_STRUCTURALLY_complete` — requiring every conjunct mutated in BOTH directions by name — then failed it within a minute, **while copying the list from the generator's own correct printed table.** The missing mutant (NEGATE updated-notnull) exists only because the guard bit its author.* The list was not derived wrong; **a right list was copied and a row was dropped.** ⇒ Anywhere a derived list is hand-copied into code, guard it mechanically. And a guard's first genuine failure is the receipt that it *can* fail — until then it is an untested instrument reporting green (rule 17, pointed at our own checks).

19k. **AN OPEN-ENDED PROVENANCE CLAIM CANNOT BE RUN DOWN; A BOUNDED ONE FALLS OUT IN ONE LOOK.** *Receipt: "those hunks predate my crew" was true and useless. Bounding the same claim with `git log -1` per file — last commit `a877e7b3` at 14:22, working-tree mtimes by 18:47 — reduced it to a four-and-a-half-hour window with a short list of live sessions, and the owner then fell out of the diff CONTENT in a single read.* Corollary, learned twice tonight from opposite directions: **mtime is authoritative for LAST WRITE, never for hunk provenance** — a 19:20 mtime says nothing about a hunk sitting since 15:00 — exactly as `docker inspect StartedAt` answers WHEN and never WHO.

19l. **DOUBT IS A COST — SPEND IT WHERE YOU CAN NAME THE MECHANISM. THE ADJACENCY ERROR RUNS BACKWARDS TOO.** Every other rule here warns against trusting an adjacent reading. **This one is its counterweight**: a *generic* disclaimer can be allowed to override a *specific* positive finding, which is the same error inverted and costs real time on questions already answered.

**The separator** (Arnold's, and it governs the rest of §6): ***Can I name the mechanism by which this signal could be wrong?*** If yes → verify. **If the only basis for doubt is boilerplate that would attach to ANY result on that channel, the doubt is about the CHANNEL, not the FINDING — resolve it yourself.**

*Receipt, 2026-07-19 ~21:15: a ratification arrived through a backgrounded `ask_multiple_choice` whose completion event carried standard boilerplate asserting that no human input had been received and that the result must not be treated as approval. **The payload was a real selection and the disproof was already in hand** — no `default` was passed, so a timeout returns an error dict, therefore a returned answer could only be human. **Two seats held that reasoning and neither closed on it**; the question was re-asked and the user answered it a second time, sharply. The wrapper's boilerplate was authoritative for "this channel CAN carry unverified results" — adjacent to, and not the same as, "THIS result is unverified."*

⇒ Pairs with rule 15 (*a correction is a claim and carries a receipt like any other*): **verifying costs something, and a verification demanded on a signal you cannot fault is a claim without a receipt.**

20. **AN INSTRUMENT WHOSE RESOLUTION IS COARSER THAN THE GAP IT MEASURES IS A FALSE-GREEN GENERATOR.** SQLite's `CURRENT_TIMESTAMP` is SECOND-resolution: a park-then-amend inside the same wall-clock second reads NOT STALE **whatever the code does**. An AC4 unit test on SQLite with no >1s settle cannot fail — aimed directly at the most load-bearing assertion in the build. ⇒ AC4 asserts against **constructed** timestamps; real-write park-then-amend belongs on Postgres beside AC10. *Caught before the test existed, by the seat that does not own it.*

21. **A negative result is evidence only when the instrument has been shown capable of a positive one.** *Receipts: `find -newermt` with a relative string matches nothing and returns clean-empty; a search over a leading-dash directory name parses it as an option and returns clean-empty; a grep at a nonexistent path returns a warning plus a zero count. Applied well, 2026-07-19: before trusting a clean equality count, all three verification queries were driven RED first — against a fabricated 1-second skew, against a NULLed capture time (`IS DISTINCT FROM`, so the three-valued arm cannot pass by matching nothing), and the CHECK itself against a parked row with NULL captured_at — each inside `BEGIN…ROLLBACK`.*

22. **CHOOSE THE CONTROL AGAINST THE FAILURE MODE IT MUST EXCLUDE, NOT THE ONE THAT REPORTS GREEN.** An equality count over `captured_at == updated_ts` is satisfiable by **both columns moving together** — it cannot distinguish "the backfill left `updated_ts` alone" from "the backfill bumped both." An md5 fingerprint of `id||updated_ts` taken before and after cannot be fooled that way. *Receipt: `a92d7c4ef9a957fdfabdfd351eb1db07` over 25 dev rows, identical across the migration; plus 0 non-parked rows carrying a non-NULL `captured_at`, bounding the write's scope to the 1022 rows it must not have touched.*
