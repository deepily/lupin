# Configuration Splintering Across Dev and Test — Analysis & Recommendation

**Date**: 2026-07-26
**Author**: Mr. Radio 🦉 (session `9a63d597`)
**Requested by**: Rick — *"analyze… whether we have created part of the configuration problem by splintering configuration across multiple points on the dev and test servers… whether it would simplify things to centralize or consolidate configuration touch points."*
**Precondition to**: [VM bring-up automation + preflight design](2026.07.26-vm-bring-up-automation-preflight-design.md) (P0 row `47c4801b`) — Rick's instruction: run this FIRST, because it may change what the preflight tests for.
**Status**: 🟡 ANALYSIS — recommendations not yet implemented.

---

## TL;DR — the verdict

**Yes, we created part of it. But "too many files" is the wrong diagnosis, and "one big config file" would be the wrong cure.**

The measurable defect is narrower and more actionable:

> **The same fact is asserted in N places, and nothing compares them.**

Seven of the last week's defects are instances of exactly that shape. Not one was caused by a *value being wrong in isolation* — every one was caused by **two authorities for one fact drifting apart with no comparator in between**.

That reframing matters, because several of these surfaces **must** stay separate (a secret cannot live in git; a VM-local path cannot be shared with dev). Consolidating them is impossible. **Comparing them is not.**

**And we have already solved this correctly, twice** — the CC-hooks template (one in-repo authority, machine-specific instantiation) and the doc-scope parity test (irreducible duplication + a comparator). The recommendation is to *generalize the two patterns we already proved*, not to invent a scheme.

## Part 1 — The evidence: how many authorities per fact?

I counted the surfaces that independently assert each fact, and whether anything compares them.

### FACT 1 — "which host directories the app container mounts"

| Authority | File |
|---|---|
| dev `:7999` | `docker-compose.yml` → `lupin-rest-dev` |
| dev `:8000` | `docker-compose.yml` → `lupin-rest-test` |
| VM pgvector leg | `docker-compose.cloud-test.yml` → `lupin-rest` |
| VM GPU leg | `docker-compose.cloud-gpu.yml` → `lupin-rest` |

**Four hand-maintained mount lists for one service shape. No two agree.** Measured today:

| mount target | dev-dev | dev-test | cloud-test | cloud-gpu |
|---|:--:|:--:|:--:|:--:|
| `/var/lupin/src` | ✅ | ✅ | ❌ *(deliberate)* | ✅ |
| `/var/lupin/.git` + `.claude/worktrees` | ✅ | ✅ | ❌ | ❌ |
| `/home/rruiz/.claude/sessions` | ✅ | ✅ | ❌ | ✅ |
| `/var/external-projects/*` (doc viewer) | ✅ | ✅ | ❌ | ✅ *(only since 07-25)* |
| `/cloudsql` | ❌ | ❌ | ✅ | ✅ |

**Comparator**: only `test_external_scope_mount_parity.py`, shipped 2026-07-25 — and it compares **compose ↔ INI**, never **compose ↔ compose**.

**Receipt**: the doc viewer served nothing on the VM for weeks because two binds that `docker-compose.yml` had carried since 2026-05-12 were never copied into `cloud-gpu.yml`. *Nothing compared the two files* — that is the root cause in the runbook's own words.

⚠️ **Not every divergence is a defect.** `cloud-test.yml` omits `./src` **deliberately and with a documented ruling** (the baked `-r3` image must not be shadowed by the on-VM checkout). So the goal is **not uniformity** — it is that every divergence be *declared and dated* rather than discovered. Its missing external-project binds are currently **unclassified**: I do not know whether that leg is meant to serve the doc viewer, and nothing in the repo answers it. That unanswered question *is* the cost.

### FACT 2 — "the notification API key"

**Five surfaces, two independent validators:**

| # | Surface | Role |
|---|---|---|
| 1 | `src/conf/keys/notification-api-claude-code-dev` | the file the client sends from |
| 2 | `LUPIN_API_KEY` env var | the value the hooks/MCP send |
| 3 | `~/.lupin/config` → `api_key_file` per `[environment]` | which file the notify client reads |
| 4 | DB `api_keys` table (bcrypt hash) | **validator A** — `:7999` / per-DATABASE |
| 5 | GCP Secret Manager `lupin-notification-api-key` | **validator B** — Cloud Run model server |

**"The key" is not one fact.** It is one *name* over N per-deployment facts, with two validators that were never compared to each other or to the client file.

**Receipts — the same defect twice, at each validator**:
- **STT 401** (07-25): Secret Manager held one version from 2025-11-12 while the app key had been re-minted. Validator B drifted. → `secret_drift.py` now compares 1↔5.
- **DM `missing_auth_header`** (07-25): the file held the *dev box's* key, unregistered in the VM's own database. Validator A drifted. → **nothing compares 1↔4**; check 6a papers over it by *probing acceptance*, which is the right answer for a bcrypt hash (it cannot be compared, only exercised).

### FACT 3 — "which config block the app runs under"

| Authority | Sets |
|---|---|
| `LUPIN_ENV` (compose `environment:`) | the **database** — *"never inferred"*, per `cloud-test.yml`'s own comment |
| `LUPIN_CONFIG_MGR_CLI_ARGS config_block_id` | the **INI block** (`Lupin: Testing-GCS`, etc.) |
| `~/.lupin/config` `[environments] default` | the **notify client's** api_url/key/recipient — *and nothing else* |

**Three knobs, three different meanings, similar names, coupled only by convention.** On `cloud-gpu.yml`, `LUPIN_ENV: testing` sits beside `config_block_id=Lupin:+Testing-GCS` — they *can* disagree and nothing notices.

**Receipt**: runbook §7a opens by *clarifying to Rick* that `[environments] default` selects the notify client's endpoint and **NOT** the server runtime profile. **That clarification, needed at all, is the splintering cost measured in a human's confusion.**

### FACT 4 — "where the project root is"

`LUPIN_ROOT` has **36 read sites**. It is written by: each machine's `~/.bashrc`, `push-env`, every compose `environment:` block, and defaulted inside `cu.get_project_root()` to `/var/lupin`. Values legitimately differ per machine (`/mnt/DATA01/...` vs `/mnt/lupin-data/...`), so this **cannot** be centralized — only asserted.

### FACT 5 — "the Claude Code python interpreter"

Authorities: `LUPIN_CC_VENV`, the implicit `$LUPIN_ROOT/.venv` default, the hooks' own resolution, the installer's resolution.

**Receipt**: on the VM `$LUPIN_ROOT/.venv` is a **symlink into `.venv-arbiter`** (uid 1001, py3.10) — the whole host CC integration pointed at another service's venv. The dev box masks it completely, so the defect **cannot be found by observation on dev**.

### FACT 6 — "which doc scopes exist"

Authorities: `lupin-app.ini § external repos`, each repo's `.docview.yml`, and the compose binds. **This one has a comparator** (07-25) — and it is the model to copy: bidirectional, with a `KNOWN_ABSENT` map that fails in *both* directions so an exemption cannot outlive the gap it excused.

### FACT 7 — "the 8 Claude Code hooks"

Authorities: `src/conf/claude-code-hooks.json` (canonical, in-repo, env-var-relative) → merged into each machine's `~/.claude/settings.json` by the installer.

**This one is already right.** One in-repo authority; machine-specific instantiation by a script; the template ports verbatim because it is env-var-relative. **It is the pattern the rest should follow.**

## Part 2 — So did splintering cause the problem?

**Scoring the 30 defects from the bring-up inventory against this lens:**

| Cause | Count | Splintering-caused? |
|---|---:|---|
| Two authorities for one fact, no comparator | **7** | **Yes — directly** |
| Machine-specific reality dev cannot show you (uid, gid, compose version, non-login shell) | 11 | No — irreducible; only assertable |
| Genuine code bugs | 5 | No |
| Installer/tooling gaps | 5 | Partly — an installer exists *because* config is per-machine |
| Files git cannot deliver | 4 | No — a property of secrets/size, not of our layout |

**Verdict: splintering is responsible for roughly a quarter of it — the 7 config-drift defects — and it is the quarter that is fully in our control.** The other three-quarters are the intrinsic cost of running two different machines, and no consolidation scheme touches them.

**The sharpest single data point**: the doc-viewer outage. Two files, one fact, weeks of silence, and the only reason anyone found it was Rick clicking a link that 404'd. A comparator would have caught it on the day the second file was written.

## Part 3 — Recommendation

### The principle

> **Centralize what is genuinely one fact. Where duplication is irreducible, ship a comparator. Never leave two authorities uncompared.**

Applied honestly, this means **most of the surfaces stay where they are** — and I am recommending *against* the consolidation that the question invites, for reasons stated below.

### R1 — Compose parity test *(highest value, lowest risk — do first)*

A static test that diffs the `lupin-rest` service across **all four** definitions and fails on any mount target or environment key present in one and absent in another, **unless** there is a dated `KNOWN_DIVERGENT` entry with a reason. Copy the bidirectional shape of `test_external_scope_mount_parity.py` so a stale exemption fails too.

- **Cost**: ~1 test file. No deploy risk, no runtime change.
- **Buys**: FACT 1 entirely. Forces an answer on cloud-test's unclassified doc-viewer binds.
- **Why not compose overlays (`-f base.yml -f cloud-gpu.yml`) instead?** It is the "proper" fix and I am **deferring** it: it rewrites the deployment mechanism of a system we are actively debugging, and a mistake lands on a running server. The parity test gets ~90% of the benefit with ~5% of the blast radius. Revisit once the VM is boring.

### R2 — One credential-status verb

`lupin-vm.sh creds-status` printing all authorities for a credential **side by side** — file sha256, Secret Manager version sha256, and a live acceptance probe against the DB validator (200 vs a deliberately-wrong-key 401 control).

- **Buys**: FACT 2. Both 07-25 outages become one command's output.
- **Note**: validator A (bcrypt) can *only* be exercised, never compared. That is why the probe is the design and not a shortcut.

### R3 — An in-repo env-var contract *(the hooks pattern, generalized)*

`src/conf/env-contract.tsv`: var name · who writes it · who reads it · per-machine expected shape · required/optional. Then **`push-env` generates from it** and **preflight asserts from it** — one authority, two consumers, exactly like `claude-code-hooks.json`.

- **Buys**: FACTs 3, 4, 5. Kills the "36 read sites, 4 writers, no list" problem.
- **This is the one place I do recommend real centralization**, because the *contract* genuinely is one fact even though every *value* is machine-specific.

### R4 — Assert that `LUPIN_ENV` and `config_block_id` agree

A one-line preflight check plus a startup assertion. They are two knobs for coupled facts; today nothing notices a disagreement.

### R5 — Leave genuinely-local config local

`cloud-gpu.env`, `src/conf/keys/**`, `~/.lupin/config` credentials — **do not centralize these.** They are correctly per-machine and per-deployment. They are now registered in `src/conf/vm-unversioned-manifest.tsv` (built today), which gives them the one thing they lacked: **a version-controlled list of what must exist**, without moving the payloads.

### What I recommend AGAINST

- ❌ **One master config file.** Half these surfaces are secrets or VM-local; a master file either can't hold them or leaks them.
- ❌ **Making the four compose files identical.** At least one divergence is a ruled decision. Uniformity would silently revert it.
- ❌ **Rewriting to compose overlays right now.** Right idea, wrong week — see R1.

## Part 4 — How this changes the preflight design

This is why Rick had me run it first. **Five changes**, all in the direction of asserting *agreement between authorities* rather than *the value of one*:

| Preflight item | Was | Becomes |
|---|---|---|
| A1 (env vars) | hardcoded list of 5 names | **driven by `env-contract.tsv`** (R3) — the list stops living in the script |
| C1 (mount set) | running ⊇ compose-declared | **plus** compose ↔ compose parity (R1) — catches the defect one deployment *earlier*, at commit time rather than at deploy time |
| D4 + D5 (credentials) | two separate probes | **one credential-authority triangle** (R2): file ↔ Secret Manager ↔ DB-acceptance, reported together |
| — | *(absent)* | **NEW**: assert `LUPIN_ENV` and `config_block_id` agree (R4) |
| B3 (unversioned payloads) | unchanged | manifest already built today; R5 confirms this is the right shape |

**Net effect on the assertion count**: 30 → 31, but **three of them stop being hardcoded** and become data-driven. The preflight gets *smaller and harder to rot*, which is the actual win.

**Sequencing recommendation**: R1 and R3 are preconditions for the improved A1 and C1, so build them **as part of** the preflight work rather than after it. R2 and R4 are additive and can follow.

## Part 5 — Honest limits of this analysis

- **I counted authorities, not incidents.** A surface with 5 authorities and no history of drift is a latent risk, not a proven one. FACT 2 is proven (twice); FACT 3's cost is measured only in one documented human confusion.
- **`cloud-test.yml`'s missing doc-viewer binds are UNCLASSIFIED**, not diagnosed. I did not verify whether that leg serves the doc viewer at all. I am deliberately not calling it a latent outage — that would be asserting a conclusion I have not tested.
- **No consolidation is free.** R1/R3 add two files that themselves become authorities. They are worth it only because each *replaces* a comparison nobody was doing — if they ever stop being run, they are net negative.
