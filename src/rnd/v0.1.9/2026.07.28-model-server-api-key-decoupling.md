# Model-server API key decoupling — one file, two authorities

**Filed** 2026-07-28 · **Author** Mr. Radio 🦉 (`951a4459`) · **Rows** `574fd1dc` (P1, the live outage) · `6cc52525` (P2, the unpinned mount)
**Status** Phase 1 in progress · Phase 2 deferred

---

## 1. The problem

`/embeddings/generate` on Cloud Run has returned **100% 401** since **2026-07-26 03:04:57** — ~38h and ongoing at time of filing. Rick's trace:

```
RuntimeError: EmbeddingProvider HTTP fallback returned 401 from
  https://lupin-model-server-um6r4fv7nq-uc.a.run.app/embeddings/generate:
  {"detail":"Invalid X-API-Key"}
```

**This is not key drift, and no file sync fixes it.** One file — `src/conf/keys/notification-api-claude-code-dev` — serves two consumers whose truth lives in different authorities.

| | **Consumer A** — Lupin's own API | **Consumer B** — model-server client |
|---|---|---|
| Reads it | `src/cosa/utils/config_loader.py:52` (`LUPIN_API_KEY_FILE`) | `src/cosa/memory/embedding_provider.py:228` (`du.get_api_key`) |
| Validated by | `src/cosa/rest/middleware/api_key_auth.py:68` | `src/lupin_model_server/main.py:236` |
| **Against** | the **`api_keys` TABLE** — `bcrypt.checkpw` per row | **one in-memory hash** of the Secret-Manager-mounted file |
| **Authority** | a database — **one per deployment** | a single secret version — **global** |
| ⇒ correct value | **differs on every host** | **identical everywhere** |

A file holds one string. **A demands per-host; B demands global.**

### Why it hid for months
On the dev box the two authorities **coincide by accident** — dev's key was seeded into Secret Manager as v2, so one string satisfies both. **Dev is the only host where the flaw is invisible.**

### Measured, read-only, 2026-07-28
One predicate on every side (`sha256(stripped)`, first 12):

```
dev-box key file          26e3c096d4df   == secret v2
VM key file               ccfc494d8084   <-- matches NEITHER version
secret v1                 09baaa60e463
secret v2 (= latest)      26e3c096d4df
```

Exactly **two** secret versions exist, both ENABLED — the search space is complete.

⇒ **`ccfc494d8084` is what "correct for A" looks like on a host where B was never provisioned.** `create_service_account.py:227` minted it into the VM's own database (right for A); it was never uploaded to Secret Manager (wrong for B). **The 07-26 rotation did not break the VM — it removed the coincidence that made a broken design look healthy.**

### ⚠️ A falsified decision table
`574fd1dc` was parked for a day awaiting one fingerprint read, with a binary table:
> `09baaa60e463…` ⇒ push-unversioned · `26e3c096d4df…` ⇒ Cloud Run redeploy

**Neither branch fires.** Parking for the read was right; the table's own premise — that the VM holds one of the two versions — was never itself checked. Rio's monotonicity argument (*"`latest` only moves forward"*) was valid reasoning that assumed both sides drew from the same secret. **A binary table with an unexamined "neither" branch is an instrument that cannot return the answer that is true.**

### ⚠️ A predicate trap, recorded so it is not re-walked
First hash of the dev file gave `26f45dbc7276`; Rio's record said `26e3c096d4df`. **Same key, different predicate** — the file carries a trailing newline, Rio stripped it. Comparing across methods would have manufactured a discrepancy that does not exist. **Both consumers strip** (`util.py:754`, `main.py:157`), so **stripped is the predicate**.

## 2. The name is part of the cause — Rick's ruling

> *"Those two keys should have two different names. The original was called `notification-api-claude-code-dev`, literally because that was how it was originally designed to be used — calling the notifications API, by Claude Code, by a developer. That scope has broadened over time to the point where it could now be called `notification-api`. The key we use to call the model server on Cloud Run should be called by its purpose in life: `model-server-api`."*

`docker-compose.yml:90-91` states the coupling in its own words:

> *"Model-server **reuses the existing** `notification-api-claude-code-dev` ck_live_* key via the volume-mounted src/conf/keys/ dir."*

**That reads as sensible thrift**, and only because the name does not say who the key is for. The name described consumer A's purpose accurately; borrowing it for B was a decision nothing in the name argued against. ⇒ **A name that describes one consumer's purpose, used by two, made the wrong architecture look like the frugal one.**

### The evidence, not just the taste
Every other credential in `src/conf/keys/` is named by **purpose alone**:
```
anthropic-api-key-firewalled  gemini  google  groq  huggingface
kagi  mistral  openai  eleven11    notification-api-claude-code-dev  <-- the outlier
```
Eight siblings carry one claim; the outlier carries three (API · caller · environment). The new names **return the directory to the convention it already follows.**

And `-dev` is not merely redundant — **it is false today**: the VM, not a dev host, holds a file named `…-dev`. `create_service_account.py:245` builds it from a real `{env}` parameter, but only one variant was ever minted, so an environment suffix froze into a literal and travelled to the wrong environment.

## 3. Design

| Surface | Was | Becomes | Phase |
|---|---|---|---|
| B key file | *(shared with A)* | `src/conf/keys/model-server-api` | 1 |
| B Secret Manager id | *(shared: `lupin-notification-api-key`)* | `lupin-model-server-api` | 1 |
| B Terraform `api_key_name` | `notification-api-claude-code-dev` | `model-server-api` | 1 |
| B Terraform `api_key_secret_id` | `lupin-notification-api-key` | `lupin-model-server-api` | 1 |
| A key file | `notification-api-claude-code-dev` | `notification-api` | **2** |
| A generated name | `create_service_account.py:245` | `"notification-api"` | **2** |

⚠️ Secret ids keep the `lupin-` prefix (project namespace, all 14 in `secret-manager/variables.tf`); **file** names do not, matching their siblings.

### Why the phases are separate
**B is a brand-new file** — nothing reads it until the client is pointed at it. Zero migration risk.

**A's rename is a live-credential migration**: the name is **generated**, not merely referenced, and the file exists on every host plus Secret Manager. Renaming in-tree without renaming on every host in lockstep breaks **every authed call on all hosts** — a strictly larger blast radius than the outage being fixed. `outbound_api_key.py:30` holds it as a module constant gating MCP auth for the whole fleet.

### ⛔ The pin belongs in Terraform, never `gcloud`
`cloud-run-model-server-deploy.sh:10-24`, finding #4: **Terraform is the SINGLE deploy authority.** An earlier `gcloud run deploy` created two divergent authorities → state drift and a secret mount path that diverged from what the app reads → 503 on every authed request. `6cc52525`'s pin lands in `api_key_secret_version`.

### ⚠️ Rotation order — the outage in miniature
`_install_api_key()` (`main.py:275`) hashes **at boot**:
```
1. add the new secret version
2. terraform apply with the new api_key_secret_version   <- instances re-hash
3. THEN distribute the file to callers
```
Reverse it and every caller 401s until instances recycle — exactly 07-26. **With `latest` unpinned there is no controlled moment for step 2.** ⇒ **The pin is what makes step 2 an event you schedule** — a stronger argument for `6cc52525` than "prevents silent drift".

### 🔷 Open decision — Rick's
The server holds **one** hash, so every rotation is a hard cutover with a disagreement window.
- **(a) ship as designed** — cutover, ordered as above *(assumed by this plan)*
- **(b) accept two hashes during a rotation window** — no window; more state, second live key to revoke

Written so (b) is an additive change to `_install_api_key`.

### 🔴 A collision I caused, and the fix
`terraform plan` wanted to **create** `lupin-model-server-api` — because I had already created it with the seeder script. Apply would have 409'd. **The module owns the secret CONTAINER; the script seeds VERSIONS. I did those in the wrong order.** Resolved with `terraform import` (non-destructive, preserved the seeded version); re-plan then showed 1 add / 1 change / 0 destroy.

⇒ Same two-authorities shape as finding #4, one layer down. **The seeder should either create-if-absent under Terraform's ownership or refuse when the secret is Terraform-declared** — filed as a follow-on, not fixed here.

### 🔴 A live regression I introduced on dev, and why it is the row's own lesson
Dev `:7999` bind-mounts `./src` with `--reload`, so **my client change went live the moment I saved it**, while the dev model-server container still hashed the old key name. Measured: client would send `dbda9daf8dbf`, server held the notifications key ⇒ dev embeddings/STT were 401ing.

**I moved the CLIENT before the SERVER — the exact ordering this document warns against, committed by its own author, on the machine where the warning was written.** Repaired by recreating the container (`--no-deps --force-recreate`; `restart` would NOT have picked up the env).

### ⛔ Why the VM is not finishable by a container recreate
`docker-compose.cloud-gpu.yml:100` bind-mounts `./src:/var/lupin/src` — **the VM runs its own checkout's code.** Measured on the VM:
```
HEAD                                            82958c2d8
grep -c LUPIN_MODEL_SERVER_API_KEY_NAME
   src/cosa/memory/embedding_provider.py        0
```
⇒ Its client still hardcodes the old key name. A recreate would restart a container whose code has not changed. **The VM needs the code deployed first** — scope this plan did not anticipate, because the plan assumed compose/env alone would carry the change.

**VM sequence, when authorized:**
1. commit
2. `lupin-vm.sh push-bundle` (moves code to the VM checkout)
3. `docker compose -f docker-compose.cloud-gpu.yml --env-file cloud-gpu.env up -d --no-deps --force-recreate lupin-rest`

⚠️ `--no-deps` is load-bearing: without it compose recreates `cloudsql-socket-init`, whose command is `rm -f /cloudsql/*/.s.PGSQL.5432` — deleting the live socket under the running proxy (bug `300bc7ca`).
⚠️ Rick's Claude Code runs on the VM **host**, so it survives; what drops for ~30–60s is the Lupin app the MCP tools route through.
⚠️ The VM is currently **still 401ing** and will remain so until this lands. Nothing about today's deploy made it worse — the old key never matched any secret version.
