Every measurement below came from SELECTs against the live database. **Nothing has been

---

## 1. Scope: the whole table, and why a norm can't decide that

**Every row gets regenerated.** An earlier draft of this document proposed regenerating only
the 79,318 rows whose vectors read norm 1.0, on the theory that the other 209,468 were
"already correct." Rick overruled it, and the reasoning is worth keeping:

> Those values are the results of embeddings created by two different embedding spaces, two
> different training sets, two different services.

The measurement error underneath my proposal: **a norm tells you whether a vector was
normalized, not which model produced it.** The norm band separates the OpenAI era from the
local era only because those two happen to differ in normalization. It is blind to any
boundary *inside* the local era — a model version, a training set, a service endpoint, or a
prose/code engine choice could all have changed without moving the norm at all. Calling
those 209,468 rows correct asserted a provenance nothing in the survey established.

The invariant that matters is that the whole table live in **one space, produced by one
model, in one pass**. Similarity is only meaningful between vectors from the same space; a
table assembled from two or more yields comparisons that are arithmetic without being
meaning. Partial regeneration leaves exactly that, and leaves it undetectable — which is
how the original defect survived two and a half months.

So the selection predicate is **"has source text"**, not "looks stale".

## 2. Why regenerate rather than normalize

Dividing the old vectors by their norm would leave them exactly where they are: in OpenAI's
vector space. Measured cosine between the two producers on identical text is ~0.008 — they
are unrelated coordinate systems that happen to share a dimension count. Normalizing makes
the *lengths* agree and the *meanings* no more comparable than before.

This is also why nothing ever failed loudly: both models emit 768 dimensions, so the table
is shape-compatible and scale-incompatible at the same time. A dimension mismatch would
have thrown on day one.

## 3. What was built

| file | what it is |
|---|---|
| `src/cosa/rest/db/embedding_regeneration.py` | the pipeline — pure core plus an isolated live-IO boundary |
| `src/tests/unit/test_embedding_regeneration.py` | 83 unit tests, no DB, no HTTP |
| `src/scripts/embedding_regen_probe.py` | builds a throwaway clone so the pipeline can be rehearsed |

Structure follows the in-repo `vector_store_backfill.py` exemplar: every decision lives in
a pure function reachable from a unit test, and the parts that need a real session, a real
GPU-backed server, or a command line are quarantined behind `# pragma: no cover`.

### The safety model

Four subcommands. Each must be asked for by name; none is a side effect of another.

| command | writes | gate |
|---|---|---|
| `plan` | nothing | — (this is the default) |
| `fill` | **shadow columns only** | busy check, off-peak clock, per-vector validation |
| `verify` | nothing | — |
| `swap` | the live vector column | refuses unless `verify` passes clean |

`--table-prefix=regen_probe.` redirects every statement at a clone, so the whole pipeline
runs end to end without the live tables being addressed at all.

Three gates worth calling out:

- **An unknown busy state blocks.** If the `/api/busy` probe cannot be reached,
  `should_proceed` refuses rather than assuming idle. The point of the check is that we do
  not guess about a server somebody else is using.
- **`--force` overrides the clock, never the queue.** A unit test pins that.
- **Every fresh vector is validated before it goes near the DB** — dimension, finiteness,
  and norm band. A vector that comes back normalized means the embedder changed again
  mid-run; the run stops instead of writing a second generation of wrong data. That is the
  failure this whole exercise exists because nobody caught the first time.

## 4. How this gets tested without touching the live table

Four layers, in increasing cost and decreasing isolation.

**Layer 1 — pure unit tests. Done, green.**
83 tests, 100% lines and branches on the module. No DB, no network. Covers norm
classification (including the 3.0 fixture), vector validation, batching, the busy/clock
gate, the swap verdict, checkpoint round-trip and corruption, and resume arithmetic.

**Layer 2 — read-only rehearsal against the live table. Done, green.**
`plan` issues nothing but SELECTs and reports 288,932 / 288,932 / 500 in scope, with zero
rows missing a vector and zero rows carrying a vector but no text. This proves the selection
SQL, the spec registry, and the connection path against real data with no write capability
in the code path at all.

**Layer 3 — full pipeline against a clone. Built, not run.**
`embedding_regen_probe.py create --rows=500 --apply` creates schema `regen_probe`, clones
each table's structure with `CREATE TABLE ... (LIKE ...)`, copies 250 rows from EACH
embedding era, and adds the shadow columns. Sampling both eras matters: a probe drawn only
from the OpenAI-era rows would rehearse against the shorter texts and under-measure batch
timing. The live tables appear in exactly one place — inside the
`SELECT` of an `INSERT ... SELECT`. Then `fill` → `verify` → `swap` all run with
`--table-prefix=regen_probe.`, exercising the real embedder, the real batching, the real
checkpoint, and the real swap against real data. `drop --apply` removes the schema.

This is the layer that answers "does it actually work" — the rows carry the same text
lengths, the same vector fingerprints, and the same nulls as production, because they *are*
production rows, copied.

**Layer 4 — a bounded live pass.** `fill --limit=500` against the live table writes only
shadow columns; the live vectors are untouched and `verify` can be read before anything is
swapped. This is the first step that writes to the live database, and it is the first thing
that needs your word.

## 5. The whole process, beginning to end

What I would propose running, in order. Everything from step 3 down is unstarted.

1. **Rehearse on the clone** — `probe create` → `fill` → `verify` → `swap` → `probe drop`,
   all under `--table-prefix=regen_probe.`. Nothing live is written.
2. **Add the shadow columns to the live tables** — three `ALTER TABLE ADD COLUMN`
   statements. Additive; existing columns and queries are unaffected. Roughly **3.3 GB**
   across the two `input_and_output` shadow columns at 288,932 rows (768 floats × 4 bytes
   × 2 × 288,932), so disk headroom is worth checking before step 2 rather than during it.
3. **Fill in the off-peak window** — 578,364 embedding calls, batched at 256, resumable via
   checkpoint. Writes shadow columns only.
4. **Verify** — read-only. Every in-scope row filled, every new vector in the current
   model's norm band, every one 768-dimensional. Nothing proceeds if this is not clean.
5. **Swap** — the one destructive statement, per table.
6. **Drop the shadow columns** once you are satisfied.

### Open questions for you

- **Where does the fill get its embeddings?** A script outside the FastAPI process routes
  over HTTP to `/api/embeddings/batch` on `:7999` — the server you are driving for the
  demo. **578,364 calls** is substantial load. Options: run it off-peak anyway, point it at
  `:8000`, or run it in-process. **This is the decision I would most like your ruling on**,
  and the whole-table scope makes it more pressing than it was at a quarter the size.
- **How long does it take?** Unmeasured, and I do not want to guess from a cold start. The
  clone rehearsal gives a real per-batch rate on real text lengths, which turns this into a
  number instead of an estimate. That is an argument for running layer 3 before scheduling.
- **Rollback.** Once swapped, the old vectors are gone unless the shadow columns are kept
  or a table backup is taken first. My inclination is a `pg_dump` of the two tables before
  step 5, but that is a real chunk of disk and your call.
