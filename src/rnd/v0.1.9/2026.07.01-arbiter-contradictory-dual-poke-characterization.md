## TL;DR

Within one ~2-min window the `:8001` arbiter DM'd Tiberius **two contradictory advisories**:

1. `02:08:13Z` **MANAGER-DONE** — "owes NO non-terminal work — appears finished/idle. Consider reaping."
2. `02:10:20Z` **STUCK auto-poke** — "repeated cap-reached WITH WORK OWED and no progress. Are you blocked or wedged?"

They disagree on the very predicate (owes-work: **NO** vs **YES**). The contradiction is **architecturally real**: the two advisories are emitted by two independent detectors that read **two different owed-work oracles** with different freshness and different attribution keys.

## The two oracles (this is the root of the contradiction)

| Detector | Emit site | Owed-work source | Attribution key |
|---|---|---|---|
| **MANAGER-DONE** (case 17) | `_check_manager_acks`, `arbiter_job.py:2802-2811` | `owed_class` ← `_classify_owed` → **task STORE** read (`_default_owed_work_fn:260`), plus a hold `work_owed=false`→DONE override (25ba173e, `:2592`) | `owner_persona` (canonicalized via `canonical_persona_key`) |

- **CLASS_DONE** ⇔ `_classify_owed` sees **zero** non-terminal store rows for the persona (`arbiter_job.py:2551-2552`).

Because these are **different sources**, a single session can be classified DONE by the store oracle and STUCK by the activity-tail oracle in the same poll. Both detectors run per-poll from `build_snapshot` (`:1183`).

## H1 — why MANAGER-DONE fired despite live `in_progress` rows (NEEDS RED repro)

For MANAGER-DONE to fire, `_classify_owed` had to classify "Tiberius" as **CLASS_DONE = zero non-terminal store rows** (`:2551`). Two candidate mechanisms:

- **(a) persona-key / re-spin attribution mismatch (leading suspect).** The store rows were `created_by "Tiberius 91de0c54"` (the PRE-`/clear` session); the poked session is the re-spun `eb4b105f`. The store read keys on `owner_persona` (`:260`), canonicalized — which *should* match "tiberius". But the tapped-manager identity in `_last_tap_at` / `owed_class` is derived from the **fleet_view / bridge persona label** of the re-spun session. If that label resolves to a persona string that canonicalizes differently from the rows' `owner_persona`, the store read returns an empty list → CLASS_DONE. This is a **re-spin continuity gap** distinct from prior fixes.
- **(b) hold `work_owed=false` override.** Ruled UNLIKELY: the 02:04Z hold declared `work_owed=True`, so the 25ba173e override (`:2592`) would not force DONE.

**RED-first repro:** seed 2 `in_progress` rows `owner_persona=tiberius` (`created_by` a *prior* session id) + a tapped re-spun session whose fleet_view persona is "Tiberius"; assert `_classify_owed` → CLASS_ACTIVE (NOT DONE) ⇒ no case-17 MANAGER-DONE.

## H2 — STUCK poke not suppressed for an awaiting-PEER manager (**CONFIRMED gap**)

The c9575068 suppression `_session_awaiting_user` (`arbiter_job.py:3108-3148`, applied at `:3187-3188`) drops a session from `pokeable` **only** when its fresh honored hold declares **`awaiting: user:...`** (`:3146`) OR holds an **open user-gate** (`:3148`).

The 262c59f6 hold declared **`awaiting:peer:Rachel,peer:Cheech`** with **NO** open user-gate (`pending_user_gates=[]`). Therefore:

```
_session_awaiting_user( eb4b105f ) == False   # awaiting starts "peer:", not "user:"; no open gates
  → NOT dropped from pokeable
  → the harsh "you appear STUCK — wedged?" poke fires
```

**A manager correctly parked awaiting LIVE WORKERS — proper MANAGE-not-BUILD posture, with no store transition to show BY DESIGN — is not recognized as a defended quiescence.** The stuck detector reads "no progress" (no self-transition) + `work_owed` in the activity tail as "wedged", which is exactly wrong for a delegating manager.

This is the missing suppressor. c9575068 covered awaiting-**user**; it did NOT cover awaiting-**peer**.

1. **Unify the owed-work source across both detectors.** The stuck-poke path should consult the **store `owed_class`** (the authority) before firing — if the persona is CLASS_ACTIVE-delegated, it is not wedged. 3. **Close H1 attribution.** Ensure the tapped-manager owed-work read uses the SAME canonical persona key as the store rows' `owner_persona`, independent of session re-spin (`created_by`). Add a re-spin-continuity unit.
