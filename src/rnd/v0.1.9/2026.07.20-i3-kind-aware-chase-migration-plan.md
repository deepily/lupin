## 1. The defect, in one sentence

I3 forbids a chase-less blocked row **globally** (`status != 'blocked' OR next_chase_ts IS NOT NULL`), so the honest state *"blocked on Rick, no schedulable chase time"* is **inexpressible** — and the work dies quietly in `queued` prose where the arbiter counts it as active owed work instead.

---

## 2. The ruling (Rick, 2026-07-20)

**Kind-differentiated chase requirement**, enforced by a **kind-aware DB CHECK** (Alembic migration):

- **KEEP** the `next_chase_ts` requirement where `blocked_by` contains a **PERSONA** ref — a peer IS chaseable, so a chase time is honest and required.
- **DROP** it where the blocker is **USER** or **ITEM** only — you cannot schedule Rick; an item resolves on its own edge.
- **ADD** `blocked_by` + `next_chase_ts` params to the `task_create` MCP verb so a row can be **minted** blocked (today it cannot — verified §4.3).

Rationale: preserve I3 intact where it is enforceable rather than weakening it globally. One predicate on blocker kind — **no new status, no relaxed global rule.**

**Rejected** (do not implement): drop-the-CHECK / rules-only; sentinel far-future chase (launders a blocker into a deadline); null-chase-for-ANY-blocker (offered earlier, not chosen).

## 3. 🔴 María's catch, and a correction to it — the migration does NOT need a constraint-backfill

María flagged (correctly, as a general principle): *"a CHECK added to a table with violating rows fails the migration — confirm the backfill step is in the plan."*

**Verified against the schema — and it does not bite here, because this CHECK gets WEAKER, not stricter:**

| | Old CHECK | New CHECK |
|---|---|---|
| Predicate | `status != 'blocked' OR next_chase_ts IS NOT NULL` | `status != 'blocked' OR next_chase_ts IS NOT NULL OR NOT (blocked_by @> '[{"kind":"persona"}]')` |
| Blocked rows permitted | only those WITH a chase | those with a chase **OR** with no persona blocker |

The new permitted set is a **superset** of the old. Every existing blocked row already carries `next_chase_ts` (the old CHECK is why), so every existing row satisfies the new CHECK. **Zero violators ⇒ the DROP+ADD migration is safe on existing data with no backfill and no `NOT VALID` carve-out.**

**Where the real "backfill" lives — and why it is OUT of this plan's scope:** the honest repair is re-typing the five mis-filed prose-blocker rows (`eab1d7da` body: `1595d3bc`, `cb02fe97`, `76f26f9b`, `d2fefe9b`, `e2f11f6f`) from `queued`-with-prose into proper `blocked`. Four are blocked-on-user with no firm chase — **now expressible** once this lands. But three of the five are `skills-distillation` / `plan` project rows owned by other seats; re-typing them is the owner's data-repair, not a lupin schema migration. **Named here, filed to their owners, not done by this plan** (§8).

⇒ María's principle is right and I'm keeping the check-for-violators step in the AC (§6 AC5) as a **proof** of zero violators, not as a backfill.

## 4. Proposed design — four coordinated changes, one predicate

### 4.1 The CHECK predicate (immutable, JSONB-containment)

```
status != 'blocked'
  OR next_chase_ts IS NOT NULL
  OR NOT ( blocked_by @> '[{"kind": "persona"}]'::jsonb )
```

`@>` (jsonb containment) is IMMUTABLE, so it is legal in a CHECK constraint. Truth table:

| status | blocked_by | next_chase_ts | passes? |
|---|---|---|---|
| queued/any-non-blocked | — | — | ✅ (first clause) |
| blocked | `[{user:rick}]` | null | ✅ (no persona ⇒ third clause) |
| blocked | `[{item:X}]` | null | ✅ (no persona ⇒ third clause) |
| blocked | `[{persona:tiffany}]` | null | ❌ (persona + null chase) |
| blocked | `[{persona:tiffany}]` | set | ✅ (chase present) |
| blocked | `[{user:rick},{persona:sam}]` | null | ❌ (contains persona) |

### 4.2 Alembic migration (`src/migrations/versions/`)

`alembic revision -m "i3_kind_aware_blocked_chase"` (auto-chains `down_revision` to current head). Body:
- `op.drop_constraint( "ck_task_items_blocked_requires_chase_ts", "task_items", type_="check" )`
- `op.create_check_constraint( "ck_task_items_blocked_requires_chase_ts", "task_items", "status != 'blocked' OR next_chase_ts IS NOT NULL OR NOT (blocked_by @> '[{\"kind\": \"persona\"}]'::jsonb)" )`
- `downgrade()` reverses to the old predicate (a real down-migration, not a stub).

### 4.3 Model parity (`postgres_models.py:1426`)

Update the `CheckConstraint(...)` literal to the new predicate **verbatim**, so model and migration do not diverge (the file's own comment at :1446-1448 names this exact hazard for the park CHECKs). A parity test asserts the two strings match.

### 4.4 Rules layer (`task_store_rules.py` `validate_transition`, ~:643)

Today: `->blocked` unconditionally requires `next_chase_ts`. Change to require it **only when `blocked_by` contains a `{kind:"persona"}` ref**. The 422 message must **name the kind that triggered it** — e.g. *"a persona blocker requires a chase time"* — NOT the old generic *"blocked requires next_chase_ts"*, or a user filing a user-blocked row that trips an unrelated check reads a wrong error (María, review gate). User/item-only blocks with null chase now pass. Keeps the app layer and the DB layer saying the same thing (defense in depth, not divergence).

### 4.5 `task_create` one-call mint-blocked — ⛔ DEFERRED to its own row (2026-07-20)
