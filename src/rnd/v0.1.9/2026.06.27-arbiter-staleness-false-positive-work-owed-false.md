# BUG: Arbiter manager-staleness poke fires on `work_owed=false` (done) sessions

**Date**: 2026-06-27
**Reporter**: Mr. Radio 🦉 (session f25224cf) — observed live this session
**Severity**: P2 (no data loss; **actively wastes the user's scarce weekly tokens** by re-waking finished sessions every ~45m)
**Class**: arbiter false-positive (the family Rick wants stamped out)
**Look at**: 2026-06-28

---

## TL;DR

A manager session that has correctly declared itself **done** (`work_owed: false` in its heartbeat hold) keeps getting **manager-staleness pokes every ~45 minutes**. Each poke re-invokes the session (burning tokens) and "advises Rick" of a non-existent wedge. Root cause: the arbiter's staleness logic classifies a `work_owed=false` hold as **STALE/dead** and pokes it — it does **not** distinguish "hold dead because the session is DONE (suppress poke)" from "hold dead because it expired while work was still owed (poke)."

## Environment

- Arbiter service: `lupin-arbiter-app.service` (:8001). Detectors: staleness **2700s**, tap-ACK 600s, whole-fleet-stall 1800s.
- Hold writer: `src/lupin_cli/claude_code/hooks/lib/heartbeat_hold.py` (`declared_work_owed`, `is_fresh`).
- Staleness/dead-hold logic: `src/cosa/agents/heartbeat_arbiter/dependency_graph.py`.
- Poke emitter: `src/cosa/agents/heartbeat_arbiter/arbiter_job.py` (+ `arbiter_routing.py`).

## Symptom (live evidence, this session)

1. Cascade work fully complete; I set the hold `work_owed: false` at **18:46** (held_at fresh).
2. Arbiter manager-staleness poke fired at **19:33** ("no signal 45m… Rick has been advised").
3. Refreshing the hold (fresh `held_at`, `work_owed:false`) did **not** suppress it — an earlier poke had already fired the same way after a prior `work_owed:false` write (~18:00 window). So `work_owed:false` does not exempt a session from staleness pokes; only `held_at` age (>2700s) is effectively gating, and a done session that stops refreshing crosses it every cycle.

## Root-cause lead (precise)

`src/cosa/agents/heartbeat_arbiter/dependency_graph.py`:
- L30 (doc): "session's HOLD goes DEAD (expired / **work_owed=false** / past next_chase)".
- L139 / **L159**: `if declared_work_owed( hold ) is False:` → the hold is treated as a DEAD/stale hold.
- **L575 (unit assertion, codifies the current behavior)**: `assert hold_is_stale( { **live_hold, "work_owed": False }, now_dt ) is True   # NOT-WORK-OWED`.

So `work_owed=false` ⇒ `hold_is_stale == True`. If the **manager-staleness POKE** path keys off the same `hold_is_stale`/dead-hold signal, a DONE session is indistinguishable from a wedged/expired one → it gets poked. The "dead hold" concept (legit for *dependency-graph edge removal* — a done session shouldn't hold a dependency) is being **conflated** with "stale manager needs a poke."

## Hypothesis

Two distinct concepts share one predicate (`hold_is_stale`):
- **(A) Dependency-graph liveness**: "is this hold still holding an edge?" — here `work_owed=false` ⇒ dead is CORRECT.
- **(B) Staleness-poke trigger**: "should I nudge this manager?" — here `work_owed=false` must mean **DONE → DO NOT poke**, the opposite of the current behavior.

The staleness-poke path (B) is reusing predicate (A) and inheriting the wrong polarity for the done case.

## Suggested fix (for the fixer to confirm)

In the staleness-poke decision (arbiter_job.py / arbiter_routing.py, wherever the 2700s manager-staleness branch lives): **explicitly exempt `declared_work_owed(hold) is False`** from the poke — a done session is reported/optionally-reaped, never staleness-poked. Keep `hold_is_stale`'s work_owed=false⇒dead semantics for the dependency graph, but split the poke trigger so it fires only on `work_owed=true AND held_at expired AND past next_chase`. Add a unit assertion mirroring L571-575 that a `work_owed=false` hold yields **no staleness poke** (distinct from `hold_is_stale`).

Cross-check: task `e02e22b9` ("L1 — Arbiter detector gaps: blocked-on-user exclusion + **done-aware suppression** + tap-ACK/loop-cadence") was marked DONE — verify whether its done-aware suppression (a) regressed, (b) only covered `status=done` store items but not `work_owed=false` holds, or (c) never reached the staleness-poke path. This live evidence says the suppression is NOT effective for `work_owed=false` holds.
