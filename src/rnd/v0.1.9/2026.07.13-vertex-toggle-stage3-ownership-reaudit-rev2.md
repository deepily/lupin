## F-Rio-R1 — **F-D10 is narrated, not closed** (Layer 1 · CRITICAL · the ownership defect of rev. 2)

**Every reversible failure got a mechanical guard. The one irreversible failure got a MUST.** That is the exact inversion of where guards belong — and it is the document's own §7 lesson 8 (*"writing a risk down is not the same as pricing it"*) committed against its own most expensive finding. **It priced billing latency (T+24h) and did not price billing *ordering*.**

**And it is worse than a missing guard — the prerequisite has an unmet prerequisite:**
- **No billing API is enabled** on the project (`gcloud services list --enabled | grep -i billing` → nothing). A Cloud Billing → BigQuery export cannot be configured without it.
- `cloudbilling.googleapis.com` appears **nowhere in §2's ground-truth table** (which lists `aiplatform`, `bigquery`, `logging`, `orgpolicy`).
- **Phase 1's enable-list enables `orgpolicy.googleapis.com` only.**

So the plan's one irreversible step depends on an API that is off, unlisted, and un-enabled by any phase.

### Required close (mechanical — the standard rev. 2 itself set)

## F-Rio-R3 — the BQ-oracle bug, **reincarnated in the negative test** (Layer 1)

**The Manager asked: is the final oracle AI-observable end to end, or did we relabel the problem a third time?**

**Answer: the oracle is SOUND and I verified it is reachable** (`monitoring.googleapis.com` enabled). Cloud Monitoring `PublisherModel` is emitted by the serving path, shares zero failure modes with §4, and has a provable-zero baseline. **That is a real fix, not a relabel. Credit where it is due.**

**But its *freshness* is never bounded — and that reopens the exact hole that disqualified the BQ oracle.**

`grep` over the doc: **billing** latency is priced (`T+24h`, twice). **Cloud Monitoring ingestion latency is mentioned zero times.** Yet:

- **AC-D4** and **AC-D9a** are **BLOCKING, in-session** assertions on a **DELTA metric** that does not appear instantly.
- **AC-D8** is a **NEGATIVE** assertion — *"assert `model_invocation_count` did **NOT** increment."*

**A negative assertion on a lagging metric false-passes during the lag window.** Run plain `claude`, query immediately, see no increment, conclude "no leakage" — **while the leak is real and simply hasn't been ingested yet.** That fails toward *"nothing happened"* when the truth may be *"you are being billed"* — **the precise failure direction, and the precise reasoning, that disqualified the BigQuery oracle two pages earlier** (§6a struck block: *"Two opposite outcomes — one free, one burning metered Opus — produce an IDENTICAL observation"*).

The positive oracle was fixed. **The negative test inherited the original bug.** And §7 lesson 1 already names it: *absence-of-output read as absence-of-the-thing.*

**Close** (`EXECUTOR: AI`):
- **Bound the freshness**: poll with an explicit timeout/backoff; state the metric's ingestion delay as a measured number, not an assumption.
- **Never trust a negative from an unproven pipeline**: a negative result is only admissible **after** the positive series (AC-D4) has demonstrated the pipeline is live *in that same window*. **An empty series from an untested pipeline is not evidence of absence — it is absence of evidence.**
- **Lead the negative test with the deterministic check** — `CLAUDE_CODE_USE_VERTEX` unset under `env -i` has **no latency and cannot false-pass**. AC-D8 already contains it; make it primary and the metric check corroborating.
