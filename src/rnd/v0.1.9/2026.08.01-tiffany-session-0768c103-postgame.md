## The central defect, and why it survived a review

The settle gate existed to wait for sockets to reconnect. It counted **bridge files** on an 8-hour mtime window. Bridge files survive a bounce, so the count read *7 present* the instant the process came up, the threshold of 1 was met at `0.0s`, and the fanout ran before a single socket returned.

```
all-clear 8c7b824d : 0 acks      warning e878b872 : 7 acks
all-clear 72e06c7d : 0 acks      warning 542a950e : 7 acks
```

Same file, same seven sessions, same few minutes. **The warnings are the control**: the ack channel was provably live, so zero is genuine non-delivery.

### The line everyone read as success

```
reached 7 recipient(s); settle gate threshold met after 0.0s
```

Three people read that as proof the feature worked — the implementer who wrote it, the reviewer who certified the gate, and the manager who reported it upward twice. It was the bug's **signature**: a real settle cannot complete in zero seconds, because reconnecting takes time.

The tester had the identical number and asked a different question: *what is this counting?*

> **Lesson.** A green figure answers "did it pass." It does not answer "what did it measure." Only the second question finds an always-true proxy. Ask what the number is counting, not whether it is green.

### Why the review missed it

The reviewer certified the gate's **mechanism** — `wait_for_recipients`, mutation-checked, 100% branch — and never audited the **signal** fed into it. A correct algorithm over a meaningless input is a correct algorithm.

> **Lesson.** Reviewing a computation is not reviewing its inputs. When certifying a gate, name the signal and ask what it reads under the condition the gate exists to handle.

## Second defect, invisible until the first was fixed

With the signal corrected, `minimum recipients = 1` still fired at the **first** socket back — under-delivering to a fleet returning staggered. The implementer found this himself, in the direction the manager had explicitly told him *not* to look ("bound your ambition").

Fix: fire on **stabilization** — the live count unchanged across N consecutive reads (default 2), deadline as outer bound. One steady read is not a plateau: reconnects spaced wider than the poll interval look flat between every arrival, which is the same bug in a slower costume.

> **Lesson.** A fix that removes a masking defect can expose a second one. Budget for the possibility that the first fix is only the thing that lets you *see* the real bug.

## The backstop that did not exist

The manager bounded the fix: *"don't build a delivery guarantee — the durable commons entry is the straggler backstop."* The reviewer pushed back, flagging it as a concern to verify rather than an assertion.

Verified: `perform_fanout` writes broadcasts entries **per-recipient against the fire-time snapshot**, and nothing replays them. Both undelivered all-clears left **7 durable entries each — written, targeted, and read by nobody.**

The backstop was the same emitted-≠-heard failure one layer down. The instruction was retracted before the implementer built against it.

**Where the wrong idea came from**: `splainer:916` stated that a straggler past the deadline "IS in the durable `broadcasts` commons entry." False. The documentation taught the manager the wrong model, and the manager taught it to the crew.

> **Lesson.** A doc that describes a safety net nobody has is worse than no doc: it converts an unknown into a confident wrong belief. Corrected in the same change that fixed the code.

## The bigger defect nobody was looking for

The warning instructs every session to hold notifications *until the all-clear*. When the all-clear is lost, **the hold never lifts** — indefinitely, not for minutes.

This caught the manager of the change. She held her own messages after the bounce, received no all-clear, and resumed only by probing the health endpoint on a hunch. **The bug silenced the person running the project, and an instinct rescued her, not the system.**

Fix: a **string**, not a mechanism —

> *hold until the all-clear, **or until you can confirm the server is healthy yourself***

The reviewer's guard on it is the load-bearing part: the clause must stay an **affirmative check**, never a timer. *"or after N minutes"* would defeat the hold entirely — a timeout is not a health signal, and someone resumes into a server that is still restarting.

His reframing was better than the original rationale: the all-clear was only ever a **proxy** for "the server is up." A session that checks health directly holds the *stronger* signal. The clause replaces a losable proxy with a direct check.

> **Lesson.** A hold whose only exit is a message that can be lost is a trap. When you build a wait, name at least one exit that does not depend on delivery.

## Process defects, owned

### 1. `git add` and `git commit -- <pathspec>` do not compose

A peer's key (`arbiter health restart loop threshold transitions`) sat in the same shared config file as ours. The manager detected it, built a hunk-filtered patch, applied it with `git apply --cached`, and **verified the staged content excluded the peer's line** — then committed with `git commit -m … -- <pathspec>`.

**`git commit -- <pathspec>` commits the WORKING-TREE state of those paths and ignores the index.** The safeguard was silently discarded by the very mechanism being used for peer safety. The peer's key landed in a managed-bounce commit — the identical defect filed against someone else that morning.

- **Pathspec-commit** keeps a peer's whole *file* out of your commit. Correct tool, common case.
- **Part of a file** a peer is also editing needs `git apply --cached` then a **bare** `git commit`, accepting that a bare commit takes everything staged.

Not repaired by rewriting history: three sessions were committing to the branch, and a rewrite is a larger hazard than a provenance error. Recorded instead.

> **Lesson.** Building the right instrument is not the same as using it. The safeguard was never tested against the command that defeated it.

### 2. A count is only true at the minute it is taken

The tester published "19 failures outside `training/`" from an 8-minute run. By the time it was read, 10 were already fixed in the working tree — three sessions were writing to the tree concurrently. The live figure was 9.

The manager corrected her, then made the same class of error in reverse minutes later: reasoning about a test file's contents from a read that had gone stale mid-analysis.

> **Lesson.** On a tree several sessions are writing to, re-measure immediately before publishing a number. `pytest` collects from disk, and the disk moves.

### 3. A count nobody counted

"39 unit tests green" travelled through the implementer, the reviewer, and nearly into a commit message. The integration regression file contains **one** test. Both corrected on being asked to count; the reviewer noted he had read the file and still quoted the wrong number.

> **Lesson.** A number repeated by three people is not corroborated — it is propagated.

## What worked

- **Adversarial review that pushed back on the manager.** The reviewer refuted the manager's bounding, caught the drift in her own proposed clause, and scoped his PASS to what he had actually certified (gate logic + tree health, explicitly *not* delivery). A reviewer who defers is worth nothing.
- **A tester who retired her own passing criterion.** Acceptance-bar item 3 read *satisfied* because the durable entry existed. When it emerged nothing replays that entry, she voided her own green and replaced it — not deleted it — with the true criterion: *a session reconnecting after the fire is not told, and the named log records it.*
- **Prediction receipts.** The implementer ran a mutant with the predicate weakened, predicted the failure text before observing it, and got it exactly. A red you can predict pins behaviour; a red you merely observe happens to fail today.
- **Refuting your own negative.** Asked to root two `pass→skip` flips, the tester built the one causal link available (settle-thread timing vs suite start) and refuted it with 80 seconds of clear air, rather than asserting no connection.
- **Commit messages that state what is NOT proven.** Both commits said outright that delivery was unclaimed. That honesty is why the failure was caught rather than buried.
