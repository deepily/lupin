## 2. The census — what actually touches record paths

**Corpus**: 877 transcript files, 603,730 JSONL lines (every session on this box, all projects).
**Predicate** (named so the numbers are readable): a Bash `tool_use` whose command text contains
`mementos/`, split into shell segments; a segment counts only when a destructive verb **owns**
a record path in its *own* arguments — not merely when a record path appears somewhere in the
same compound command.

> That refinement matters. A naive "command mentions a memento path AND contains `rm`" count
> returns **96 `rm`s**. Nearly all are scratchpad cleanups in commands that also happen to
> mention a record. The honest number is **29**.

| verb | all | excl. my own reproduction |
|---|---:|---:|
| `>` redirect onto a record path | 34 | **31** |
| `rm` | 29 | **28** |
| `find` — **read-only**, no `-delete` / `-exec rm` | 10 | 10 |
| `mv` | 9 | **9** |
| `git clean` — **dry-run `-n`** | 1 | **1** |
| `sed -i` | 1 | **1** |
| **destructive-capable total** | 84 | **80**, across **29** distinct sessions |

Out of **796** Bash commands that mention a record path at all.

### 2.1 The finding that should drive the design

**`git clean -xdf` against records: ZERO real instances in 877 transcripts.** The single
`git clean` hit is `git clean -xdn` — a dry run, someone *checking*.

Meanwhile **the most common destructive-capable act is `>` redirect creation (31)** — which is
not deletion at all. It is the **orphan creation** case the `Write`/`Edit` guard already refuses
and Bash walks straight past.

⇒ The row's rejection rationale is built around `git clean -xdf` being the case an `rm`-matcher
misses. **That reasoning is still correct** (the token genuinely is absent), **but the measured
live surface is creation-by-redirect, not deletion.** A remedy aimed at deletion would be aimed
at the rarer half.

### 2.2 ⚠️ What this census CANNOT see — the search space, stated

- **Only agent-issued Bash through the harness.** A human typing `git clean -xdf` in a terminal
  leaves no transcript. The documented nine-record catastrophe (memento-management.md §3.5) may
  well have come from exactly there — **this corpus cannot confirm or refute it.**
- Only this box, only retained transcripts.
- Commands that reference a record by a variable (`rm "$F"`) with no literal `mementos/` in the
  segment are **invisible** to the predicate. Undercount, direction known, size unknown.

**So: the zero is a zero about agents, not about the world.** It is still the relevant zero for
a hook on agent tool calls — a PreToolUse hook cannot see a human shell either.

## 3b. What was recommended before the ruling — kept for the record

Ranked by what the measurement supports:

1. **Strengthen the mirror** (already the load-bearing layer *by design*, memento-management.md:257).
   It is the only layer that survives **both** an agent's Bash *and* a human's terminal — the
   surface this census proves it cannot see. Dominates any hook on coverage grounds.
2. **If a hook is wanted anyway, aim it at CREATION, not deletion** — `>`/`cat >` onto a record
   path is the most frequent real act (31) and is precisely the orphan the existing guard exists
   to prevent. Deletion (28 `rm`) is mostly deliberate cleanup by seats who know what they are doing.
3. **`LOG_ONLY` first, following in-repo precedent.** `worktree_creation_guard.py` ships
   `MODE="LOG_ONLY"`, uninstalled, behind a Rick gate (:19, :84) — *its own authors did not trust
   their shell parse to enforce.* Nothing here justifies more trust than they had.
4. **Or accept the gap explicitly and stop re-proposing it** — a legitimate outcome, and cheaper
   than a guard nobody can trust. This is the third time the fix has been proposed and cut.

**Whatever ships must enumerate what it does not cover** (Rio's A5). The existing `CREATE_DENIAL`
already models that discipline — it is the reason this row had evidence to stand on.
