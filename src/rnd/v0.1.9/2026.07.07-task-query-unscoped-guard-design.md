## The guard semantics (agreed parts)

Independent of placement, the guard is:

1. **Exclude terminal (`done`/`dropped`) by default** (María #2 — the 89→2 payload collapse). New param `include_terminal: bool = False`. An explicit `status=done`/`status=dropped` filter overrides (you asked for terminal, you get it).
2. **`unscoped_audit: bool = False`** — the explicit escape for legitimate full sweeps.
3. **Hard-fail** iff `unscoped AND (non-terminal count > THRESHOLD) AND not unscoped_audit`. Threshold **50** non-terminal rows (María default). The count is the cheap `count_tasks` COUNT(*) — no row materialization.
4. **Warn, not fail**, on a *non-terse large* pull (log a structured warning; don't block) — a nudge toward `terse=True`.
5. Error message is **educational**: names the two fixes ("add an `owner_persona`/`status`/`item_class`/`project` filter, or pass `unscoped_audit=true` for a deliberate audit") — same teach-while-enforcing pattern as the `?scope=` 400.

### "Unscoped" definition — a refinement to flag for María

María's amendment lists the scoping filters as `owner_persona / status / item_class / project`. **But the arbiter's operator-gate sweep (#6) filters by `gate_class="operator"`** — which is NOT in those four, so under a literal reading it is "unscoped" and could trip the guard (operator gates are few today, but relying on "few rows" is fragile). **Recommendation: define scoped = ANY of `{owner_persona, status, item_class, project, gate_class, accountable_manager, correlation_key}` present** (exclude only `urgency`, which is too broad to narrow meaningfully). This keeps every genuinely-narrowing filter safe (arbiter operator sweep, manager board-audit by `accountable_manager`, idempotency probes by `correlation_key`) while still catching the true abuse: the **bare `task_query()`** with zero filters. Flagging because María reviews the guard boolean.

## THE FORK (Tiberius sign-off gate): where does the guard live?

### Option A — REST endpoint only (`query_tasks` router) — **arbiter safe BY CONSTRUCTION**

Enforce in the REST handler (or a shared `task_store_rules.enforce_query_guard` it calls). Add `include_terminal` + `unscoped_audit` to the REST endpoint + MCP verb + `task_query_impl`. Repository stays unguarded.

- **Callers to update**: #2 + #3 (the two UI board cards) pass `unscoped_audit=true` (+ `include_terminal=true` to preserve their current all-status display). #1 (MCP verb) plumbs the two params. **Arbiter + watchers: ZERO change** — they bypass the guard.
- **Rick's concern**: met **maximally** — the arbiter literally cannot hit the guard, so it cannot break. No flag to forget, no atomic-deploy hazard, **no `:8001` restart needed** for this change.
- **Tension with Rick's verbatim words**: Rick said "make the arbiter pass the flag." Under Option A the arbiter passes no flag (it doesn't need one). This ACHIEVES Rick's GOAL (arbiter never breaks) more robustly than a flag would, but does NOT literally implement his instruction — Tiberius should decide whether to route this back to Rick.
- **Weakness**: the guard is bypassable by any *repository-direct* caller (present or future). "Nobody can pull thousands" is true for the fleet-facing MCP/UI surface but not for server-internal code. (Internal code is code-reviewed; the guard targets the fleet surface Rick described.)

### Option B — Repository layer (`TaskRepository.query_tasks`) — **universal, literal to Rick**

Enforce in `query_tasks` itself (raise a domain `UnscopedQueryError`; the REST handler maps it to HTTP 400, the MCP verb to an error-dict). Add the two params at the repository + thread them REST → impl → verb.

- **Callers to update**: #5 (arbiter bare sweep) passes `unscoped_audit=True` (+ `include_terminal=True` if it needs terminal owners — verify); #6 stays safe under the broadened scope def; #2/#3 UI cards pass the escape; #1 plumbs params; #7 already scoped.
- **Rick's concern**: met via **atomic co-deploy** — guard + arbiter-flag land in ONE commit; the arbiter loads both together on its next `:8001` restart (no stale-code window), and its other two sweeps are already scoped, so nothing trips. The RED regression test proves the flagged sweep returns COMPLETE results.
- **Strength**: universal + un-bypassable — "nobody" is truly nobody, and it **literally implements** Rick's "arbiter passes the flag." 
- **Cost**: touches the LIVE arbiter hot path (exactly what Rick flagged) — mitigated but non-zero; needs a `:8001` restart on the sanctioned batch (like today's Lever-A/P deploy).

### My recommendation

**Option B (repository-layer), done with the atomic-co-deploy discipline.** Rationale: (1) it is the only placement where Rick's "nobody can pull thousands" is *literally* true — a REST-only guard is silently bypassed by any repo-direct caller; (2) it directly honors Rick's verbatim "arbiter passes `unscoped_audit=True`"; (3) the arbiter-break risk is fully closed by the same discipline that made today's Lever-A/P deploy safe (atomic change + already-scoped sibling sweeps + a RED regression test proving completeness). **If Tiberius prefers the lower-touch path, Option A is a legitimate, arbiter-safest alternative — I'll take his ruling.**

> Either way the deployment honors María #3: **callers-updated-first or single atomic commit; the guard never fails a legitimate sweep in production.**

## Test plan (RED-first, venue :7999, 100% L/B/F on changed code)

- **Guard fires**: bare unscoped pull with >50 non-terminal rows + no audit → `UnscopedQueryError` / HTTP 400 (RED on main).
- **Escape**: same pull + `unscoped_audit=True` → full set returned.
- **Scoped-but-large is safe**: `owner_persona=me` with 60 non-terminal rows → NO fail (the exact false-positive to avoid).

- **Warn-not-fail**: non-terse large pull → structured warning logged, rows returned.
