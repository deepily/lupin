## 1. The wrong-axle finding (the whole point)

The prior research enumerated the `Openapi*` family, live in `hello-world-foo-423219`:

```
GlobalOpenapiInputTokensPerMinutePerBaseModel    40,000/min
GlobalOpenapiOutputTokensPerMinutePerBaseModel   12,000/min
GlobalOpenapiTotalTokensPerMinutePerBaseModel    52,000/min
```

Those govern the **OpenAI-compatible `endpoints/openapi/chat/completions`** path — i.e. the **MaaS** models. But the toggle this cascade exists for bills **`claude-opus-4-8`**, an **Anthropic publisher model served via `rawPredict` at `location=global`**. It does **not** ride the openapi path.

> **A clamp on `Openapi*` would cap the models we are NOT worried about while leaving the model we ARE worried about wide open — and it would LOOK like a brake.** Same false-comfort class as the metadata-200 and the region-blind openapi endpoint.

**What actually governs Claude** (Google, *Quotas for Anthropic Claude models*):

- Models launched **after 2026-05-26** use **shared model-lineage quotas**: one limit shared across all versions in a lineage, per location. Calling Opus 4.8 through the global endpoint counts against the **`anthropic-claude-opus`** bucket *regardless of the specific Opus version*.
- Expressed in **QPM** (queries/min) and **TPM** (tokens/min). **TPM includes BOTH input and output tokens** — one combined bucket.
- **Global and each multi-region endpoint are INDEPENDENT buckets.** Usage on global does not consume multi-region quota and vice-versa.
- To filter quotas, use the **`base_model`** dimension with the lineage value (e.g. `anthropic-claude-opus`).
- Quota increases are requested via the Cloud console.

**Consequence for the clamp**: it must target the **Claude lineage quota at the `global` endpoint**. That is exactly where our traffic lands (`global` is the *only* place Opus 4.8 is servable — us-central1 `rawPredict` 400s). Region and brake finally agree.

Sources:
- [Quotas for Anthropic Claude models](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/quotas)
- [Global endpoint for Claude models GA on Vertex AI](https://cloud.google.com/blog/products/ai-machine-learning/global-endpoint-for-claude-models-generally-available-on-vertex-ai)

## 3. The arithmetic

Implemented in `src/cosa/utils/vertex_spend_ceiling.py` (pure functions, no GCP calls, 100% line+branch).

**The design decision that matters.** The TPM bucket meters input and output **together**, but they bill at **different rates** ($5 vs $25). So the dollar value of a metered token depends on a **mix we do not know and cannot control**. Picking a mix ratio to make the number prettier is the same sin as inventing a price.

⇒ **The clamp is computed at the OUTPUT rate.** That is the *only* mix-independent guarantee: it bounds spend from above under **every** mix, including the adversarial 100%-output one. On a realistic input-heavy agentic mix, true spend lands well *below* the cap. The clamp under-permits rather than over-permits — it errs in the only direction that cannot hurt you.

```
$50/day ÷ $25/MTok = 2,000,000 tokens/day
2,000,000 ÷ 1,440 min = 1,388.89 → floor → 1,388 TPM
```

| Target | Binding daily $ | Combined TPM clamp (worst-case) |
|---|---|---|
| $50/day (as stated) | $50.00 | **1,388** |
| $1,000/month ÷ 31d | $32.26 | **895** |

**Floor, never ceil.** 1,389 TPM prices back to $50.004/day — a permanent, silent breach. The code floors, and a test pins it.

### The headroom — the defaults are not a ceiling, they are the absence of one

At the MaaS default of 52,000 TPM: `52,000 × 1,440 = 74,880,000 tokens/day`. Priced at Opus output rates that is **$1,872/day — ~37× Rick's $50 target**. (This pins the *arithmetic*, not a claim about Claude's actual default — **that number is still unread**.)

## 4. 🔴 Rick's two targets are inconsistent — he must rule

> **$50/day × 31 days = $1,550. That blows the $1,000/month ceiling.**

They cannot both be hard caps. Either:

- **(A) The monthly cap binds** → clamp at **895 TPM** ($32.26/day). Safe by construction; a month can never exceed $1,000. Costs him burst headroom on any single day.
- **(B) $50/day is the rate cap, $1,000/month is an ALERT** *(my recommendation)* → clamp at **1,388 TPM**; budget alerts at 50/80/90% of $1,000 catch the case where too many near-$50 days stack up.

**(B) is the honest two-layer design and the one this cascade's own law points to**: *rate* enforces the instantaneous ceiling (instant, 429, at the API layer); *dollars* alert on the cumulative one (laggy, informational). It also matches reality — a worst-case clamp on an input-heavy mix will spend far below $50 on a typical day, so the monthly cap is unlikely to bind in practice. But we must not **bank** on that; the alert layer is what catches it if we're wrong.

🔴 **THE DECREASE TRAP — read this before firing.** A clamp is a **quota DECREASE**, and Cloud Quotas applies **safety checks** that will *reject* it. From the discovery doc, `ignoreSafetyChecks` accepts exactly:

- `QUOTA_DECREASE_BELOW_USAGE` — fires if the new limit is below observed recent usage
- `QUOTA_DECREASE_PERCENTAGE_TOO_HIGH` — fires if the decrease is a large % drop

Going from a (likely 5-figure) default to **1,388** is *both* a large percentage drop *and* possibly below recent usage. **Expect the first attempt to be refused.** That refusal is **not** a bug — it is the API telling you the brake is real. Overriding requires appending, deliberately:

```
&ignoreSafetyChecks=QUOTA_DECREASE_PERCENTAGE_TOO_HIGH
```

**Do not reflexively add both flags.** `QUOTA_DECREASE_BELOW_USAGE` firing means *we are currently using more than the cap we are about to set* — that is load-bearing information about live traffic, and it deserves a look before it is silenced.

## 7. The red-first test — and what would make my clamp wrong

`src/tests/unit/test_vertex_spend_ceiling.py` — **33 tests, 100% line + branch.**

The load-bearing assertion is a **round-trip safety invariant**: clamp a budget → price the clamp back at the worst-case rate → **it must never exceed the budget**. Three mutations were introduced, each **verified live in the interpreter**, each observed to go red, then reverted:

| # | Mutation | Effect if shipped | Result |
|---|---|---|---|
| M1 | Clamp at **input** price ($5) not output ($25) | TPM 1388 → **6944**; permits **5× the budget** | **9 failed** ✅ |
| M2 | **ceil** instead of floor | TPM → 1389; permits $50.004/day, a permanent silent breach | **9 failed** ✅ |
| M3 | Fabricate an aggregator price for an **unpriced** model | Confident-looking clamp that guards nothing | **3 failed** ✅ |

Revert → **33 passed**, tree byte-identical to pristine.

### 🔴 A FOURTH FINDING — the mutation harness itself produced a FALSE RED

The first mutation run reported the suite still red *after* the revert, while the file on disk was provably clean. Cause: **the M3 mutation was exactly size-neutral** — `None` → `0.56` and `None` → `1.68` are both 4 characters. CPython validates a `.pyc` on **(source mtime, source size)**. The restore landed within the same second and preserved the byte count, so **both** validation fields matched and Python served **stale bytecode from the mutated build**. *The file was clean; the code being executed was not.*

Here it produced a false **red** (benign). **The identical mechanism produces a false GREEN** — mutate the code, have the stale `.pyc` keep serving the *good* build, and conclude "my test can't catch this defect" or "the code is fine." Either conclusion is wrong, and neither is visible.

**Rule adopted, and it generalises past this cascade**: run mutation testing with `python -B` / `PYTHONDONTWRITEBYTECODE=1`, and **probe the mutated value live in the interpreter before trusting the test result**. A green — or a red — is only evidence if you can prove which build produced it. *The bytecode cache is an instrument too.*

### The canary the clamp still needs (DESIGN ONLY — do not fire)

Everything above proves the **arithmetic**. It does **not** prove the **clamp reaches Opus**. That claim has exactly one honest oracle:

> **Deliberately exceed the clamped rate and REQUIRE a 429.**

The trap, stated so nobody falls in it: **"no 429 observed" means BOTH "the cap works" AND "we never approached it."** Under-approach and success are indistinguishable. A quota you set and never exercised is a **promise**, not a brake.

**The canary costs a few cents and IS a prediction call ⇒ it is Mr. Radio's, on Rick's explicit word.** Shape: burst > 1,388 tokens/min of *output* against `claude-opus-4-8` at `global`, assert **HTTP 429**. A run that produces **no 429 is INADMISSIBLE, not passing** — it means the instrument never spoke.
