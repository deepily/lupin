## 1. What landed

Out-of-process `:7999` clients had transport budgets shorter than the server's own
reload window, so each one failed on every reload it happened to land in. Raised to
**~30s = 1.60× the observed maximum reload window of 18.76s** — a multiplier with
explicit headroom.

🔴 **Never stated as a coverage percentage.** Rev 2's "20s = 100.0% coverage" was
withdrawn as near-circular: a coverage figure computed on the same slice that
supplied the maximum will always read 100%. It is not reintroduced anywhere in this
diff — not in a comment, a docstring, an INI splainer, or the commit body.

**THE TRADE, stated plainly**: a genuinely hung server now takes ~30s to report
instead of ~2-10s. Rick accepted this knowingly. It is not free, and no comment in
this diff sells it as free.

### 1.1 Why the old budgets failed — the mechanism

`:7999` runs `uvicorn --reload`. The reloader **parent** holds the listening socket
across a restart and hands it to each child (`uvicorn/supervisors/basereload.py:100`).
So during a reload the kernel **ACCEPTS** a connection that nothing is there to
answer. The client does not get a fast `ConnectionRefused` — it hangs and eventually
raises `TimeoutError`.

Measured over 8.4 days of container logs (current-config clean-reload class, n=143):
min **6.59s**, median **6.91s**, p90 11.90s, max **18.76s**. All 143 exceed 5s.

## 3. Findings that changed the inventory

### 3.1 🔴 `swe_team/orchestrator.py` was excluded twice, wrongly

Cheech excluded it as in-process. Arnold re-verified and **confirmed the exclusion** —
`decision_proxy/__main__.py` imports `swe_team.proxy.*`, not the orchestrator, so the
standalone proxy mode does not reach it. True, and irrelevant.

**`swe_team` ships its own `__main__.py`**, which does:

```python
from .orchestrator import SweTeamOrchestrator
...
result = asyncio.run( orchestrator.run() )
```

documented in its own docstring as `python -m cosa.agents.swe_team "…"`. That is a
**separate OS process**. Three sites exposed.

The exclusion was verified by asking **which other package imports this module** — the
one question that structurally cannot see the module's *own* entry point. Arnold had
written the correct rule ("any module with a `__main__.py` is dual-mode by
construction") in the very document that then mis-applied it.

**It was found only because the brief said to audit results that CONFIRM what you
expected.** "The exclusion holds" was exactly that.

### 3.2 Entry-point enumeration finds packages; the transitive walk finds shared libraries

Auditing all seven in-tree `__main__.py` packages caught `swe_team`,
`notification_proxy`, `decision_proxy` — but **`proxy_agents/rest_submitter.py:71`
(10s)** belongs to none of them. It lives in `utils/`, underneath both proxies, and
rides both CLI entry points.

A per-package grep cannot see it. **Enumerating entry points is step one; walking
transitively from them is what reaches the shared layer.** That is the reusable half
of the method.

### 3.3 🔴 During a reload, `connect()` SUCCEEDS — only the READ budget is exposed

The reloader parent holds the listening socket, so the kernel completes the TCP
handshake. The hang is entirely in waiting for a response. Consequences:

- A **single-value** timeout (`requests.post(timeout=5)`, `urlopen(timeout=N)`)
  applies to both legs ⇒ the read budget is that number ⇒ **exposed**.
- A **split tuple** `(connect, read)` is **not** exposed on its connect leg, however
  small. `notify_user_sync.py:235`'s 3s connect never trips.

This sharpens the predicate from *"has a short timeout"* to **"has a READ budget
shorter than the reload window."** Re-screening the set through that lens is what
dropped `notify_user_sync.py` out.

## 5. `register_session.py:606` — the wording was the defect, not just the number

The banner printed a flat **`"Server: unreachable"`** for every probe failure. That
string is what misdirected this investigation across two sessions: readers saw it,
concluded the server was **down**, and hunted a dead server that was in fact
mid-restart.

**Fixed as wording, not as budget** (ruling: Arnold, over the flat 30s):

| Condition | Client-observable | Banner now says |
|---|---|---|
| Server stopped | `URLError(ConnectionRefusedError)`, ~0.0003s | `not running — connection refused` |
| Server restarting | `TimeoutError` at the budget | `no response in 3s — may be restarting` |
| Server answered non-2xx | `HTTPError` | `reachable` |
| Anything else | — | `unreachable — <ExceptionType>` (names it, never flattens) |

The budget went **1s → 3s only**. Sizing this probe at 30s would stall **every**
session boot by 30s whenever the server is genuinely down — a bad trade for one status
line. The split costs no boot latency because the two conditions already render
differently at the client, which is exactly what the plan's controls **C1** (blackhole
socket, TIMEOUT at 15.02s) and **C2** (closed port, REFUSED in 0.0003s) established.

## 6.4 🔴 THE DUAL-SEMANTICS DEFECT — why the obvious value is wrong here

**Read this before "unifying" the field-carried budget with the cohort constant.**
The number is 6, the cohort is 30, and that difference is not an oversight.

### The finding: one field, two incompatible meanings

`AsyncNotificationRequest.timeout` is read as **two different quantities** in the
same call path:

| Site | Meaning it assigns | Evidence |
|---|---|---|
| `notify_user_async.py:47` `calculate_retry_intervals( timeout_seconds )` | **TOTAL retry budget** — the schedule is trimmed to fit *inside* it: `if cumulative + interval < timeout_seconds - 0.5` | docstring: *"Returns list of intervals that fit within timeout"*, *"Total interval time < timeout_seconds - 0.5"* |
| `notify_user_async.py:201` `requests.post( …, timeout=request.timeout )` | **PER-ATTEMPT transport budget** — spent again on every attempt | bare `timeout=` governs both connect and read legs |

So one number simultaneously sets *how long the whole thing may take* and *how
long each of N attempts may take* — and N is itself derived from that number.
Raising it multiplies against itself.

**6 is not a tuned value. It is where these two meanings currently land without
exploding.** The defect is the dual semantics; 6 is the accommodation.

### Measured cost (`calculate_retry_intervals`, real intervals)

| budget | attempt start times | rides out an 18.76s window? | worst-case wall clock |
|---|---|---|---|
| 3s | 0, 4, 8 | **NO** — all attempts close inside it (this was F1) | 11s |
| 5s | 0, 6, 12, 19 | yes, by 0.24s | 24s |
| **6s** ← chosen | **0, 7, 14, 22** | **yes — attempt 3 (14→20) is still open at 18.76s, and attempt 4 starts after it** | **28s** |
| 10s | 0, 11, 22, 34, 46, 59 | yes | 69s |
| 30s ← cohort value | 0, 31, 63, … | yes | **267s** |

Verified independently by the reviewer against `notify_user_async.py:163-176`
(`all_delays = [ 0 ] + retry_intervals`) plus `except Timeout: continue` at
`:270`, confirming a timeout genuinely retries rather than aborting.

### ⚠️ >10s crosses a BRANCH, not a tuning line

`calculate_retry_intervals` (`:72-83`) switches strategy at `timeout_seconds <= 10`:
a fixed aggressive `[1,1,2,2,3]` below, exponential-with-5s-cap above. **A budget
change across that boundary changes the retry SHAPE, not just its size.** Anyone
re-tuning this must re-read the branch, not interpolate the table above.

### The rule this generalises to

> **A RETRYING caller needs its LADDER to span the reload window.
> A NON-RETRYING caller needs a SINGLE budget that does.**

That is the whole reason `_SERVER_TRANSPORT_TIMEOUT_SECONDS = 30` is correct at
the 21 direct call sites and wrong at these two. The direct sites get one shot,
so their single budget must outlast the window. These two get four shots, so the
*schedule* must outlast it — and buying that with a bigger per-attempt number
costs 267s of wall clock on a path wrapped in `except: pass` **precisely so a
notification failure never blocks Claude Code**. A 4.5-minute stall is a worse
defect than the dropped notification F1 reported.
