## TL;DR

The heartbeat arbiter's Part-6 #4 blocker detector correctly throttles the **blocker
ping** (per-edge escalating backoff 60/300/900/3600s) but re-sends the **owning-manager
cc** — "X is blocking worker Y … chase if they stay silent" — on **every** ping fire,
with no independent idempotency. Result: the manager was flooded with identical cc DMs
(3 in ~6 min for one block, each minting a fresh thread → recipient-side dedup
impossible). Fix: gate the cc on a `(blocker, blocked_item, recipient)` cooldown,
reusing the in-file `58660c64` advisory-cooldown machinery. The **blocker ping is
untouched** (a silent blocker SHOULD keep being nudged).

---

## Root cause

`_auto_ping` (`arbiter_job.py`) iterates blocked-worker→blocker edges. Per edge, when the
backoff gate `should_ping(...)` passes it calls:

```python
manager, cc_msg = self._blocker_manager_cc( awaited, holder, persona_to_sid )
self._route( 4, PING_MESSAGE_TEMPLATE..., blocker=awaited, owning_manager=manager, cc_message=cc_msg )
```

`_route(4, …)` emits **two** DMs — the blocker ping (correctly backoff-throttled via the
per-edge ledger) and the manager cc. The cc has **no** dedup of its own, so it rides the
ping's backoff schedule. The observed cadence `0 / +61s / +302s` is exactly
`schedule[0]=60` then `schedule[1]=300` (+ poll jitter) — confirming the cc piggybacks
the ping, not a loop tick.

### Why the item id must be in the key (Mr. Radio's evidence)

Two **sequential** block instances were recorded, both `sam blocks Rio → cc mr radio`,
differing only in the blocked **task item**:

| Instance | Item | Fires |
|---|---|---|
| 1 | `99399723` | 21:44:04, 21:45:05 (+61s), 21:50:07 (+302s) — should collapse to **1** |
| 2 | `ca8d6a19` (Rio Phase 2) | 22:14:14, 22:15:14 (+60s echo) — should collapse to **1** |

Same `(blocker=sam, blocked_worker=Rio, recipient=mr radio)` across both → a persona-only
key would **over-suppress** instance 2 (a genuinely-new block). Therefore the blocked
**item id** belongs in the idempotency key: `(blocker, blocked_item, recipient)`. The
diagnostic signature (a ~60s echo after first announce, then irregular event-driven
re-fires) also sets the window floor: **the cooldown must be ≥ the chase interval**, not
just >60s.

## Fix

**Key = `canonical(blocker) | canonical(blocked_worker) | item_sig`** where `item_sig` is
the sorted `+`-joined blocked task-ids for that edge. The recipient (owning manager) is
deterministic from the blocker's lineage, so `(blocker, blocked_item)` carries it
implicitly.

1. **`dependency_graph.build_store_blocked_item_index(owed)`** — the item-preserving
   companion to `build_store_wait_edges` (which collapses items to bare persona pairs).
   Returns `{ (canonical_holder, canonical_awaited): frozenset(item_ids) }` from the SAME
   per-poll owed read. Empty when the store read was UNKNOWN.
2. **`arbiter_job._blocker_cc_key(holder, awaited, edge_items)`** — renders the key;
   canonicalized personas; empty `item_sig` (store-unknown fail-safe) degrades to a
   persona-only pair, with clear-on-resume distinguishing sequential blocks instead.
3. **`_auto_ping` cc gate** — when a cc is owed, `_advisory_cooldown_blocks("blocker-cc",
   key, now)` suppresses it (sets `cc_msg=None`, blocker ping still fires); else
   `_stamp_advisory_cooldown(...)`. Reuses the `58660c64` state + the observable
   `arbiter_advisory_suppressed_cooldown` journal event.
4. **Clear-on-resume** — drops the blocker-cc cooldown for edges no longer active, so a
   genuinely-new block on the same edge re-cc's immediately (mirrors the ping-ledger
   clear-on-resume).

**Cooldown window**: reuses `manager_advisory_cooldown_seconds` (default =
`manager_stale_poke_threshold_seconds` = 2700s ≈ 45 min). Comfortably ≥ the observed
~20-min chase interval. `0` restores the legacy per-ping cc (deliberate opt-out — same
disable semantics as the case-16/17 advisory cooldown).

### Why reuse `manager_advisory_cooldown_seconds` (no new INI knob)

Smallest blast radius: no new config surface, no ctor-signature change, reuses
fully-tested cooldown helpers + their observability. The semantic ("one advisory per
blocked-episode window to the same manager") is identical to the case-16/17 families.
Tradeoff surfaced for review: setting that knob to `0` disables the case-16/17 cooldown
**and** this blocker-cc dedup — acceptable since `0` is an explicit opt-in to legacy
noisy behavior. If a reviewer wants independent tunability, splitting into a dedicated
`blocker_cc_cooldown_seconds` knob is a trivial follow-up.

## Secondary wart — arbiter has no DM return channel for chase-acks

The bug notes the arbiter is DM-unreachable (`recipient_unresolved` for persona +
`lupin-arbiter-app-8001`); the chase-ack round-trip has no return channel, so the ack was
posted to commons `system-events` instead.

**Recommendation (for ratification, NOT built here): document commons `system-events` as
the canonical arbiter-ack path.** The arbiter is a headless systemd loop, not a CC session
with an inbox — building a DM-addressable inbox into it is disproportionate for a P3 and
introduces a new inbound surface on a service whose contract is *observe-and-emit, never
actuate* (the redline). Commons is already the working return channel. This is a design
call left to Mr. Radio; no code lands for it in this fix.
