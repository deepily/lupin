# Arbiter STUCK auto-poke bridge-mtime veto (bug 92c7ab1d)

**Date**: 2026.07.02 · **Owner**: Rio ⚡ · **Manager**: Tiberius 👑 · **Priority**: P2
**Store item**: `92c7ab1d` · **Related**: `8894e597` (poke reply-template unaddressable), `26dd3afb` / `097778b8` (the MANAGER-STALE bridge-veto family this mirrors)

## Symptom (the incident)

2026-07-02: three identical `(⏰ auto-poke): … you appear STUCK — repeated cap-reached
with work owed and no progress` pokes fired at **16:05:27 / 16:06:29 / 16:07:32 EDT**
(~60s cadence, = the poll cadence) against Tiberius session `95c8eba0` while that
session was **demonstrably active between the pokes**:

- DMs sent (`afd0f099` at 16:07, verdicts banked),
- hold rewritten via `write_hold` at 20:05:50Z (fresh mtime),
- continuous bridge activity,
- 3 wip merges landed within the hour.

The advertised ≤3/episode cap did not damp it and going-quiet did not help.

## Root cause — `stuck` conflates "at poke-cap + owes work" with "wedged"

`stuck` is derived by `fleet_data_model._count_stuck_episodes(...)`: it counts
`cap_reached` records with `work_owed=True` across the **accumulated tail (maxlen 50)**,
with **NO recency bound**, and flips the flag on at `STUCK_REPEAT_THRESHOLD` (2).

Crucially, `cap_reached` is emitted by the **session's own Stop hook on every turn it
ends while `owed AND poke_count >= cap`** (`heartbeat_decision.py:153` →
`heartbeat_events.emit_outcome`). It is **not** a "no progress" signal — it only means
"this session still owes work and has exhausted its self-poke nudge budget." A busy
manager who legitimately **owns a full board** (many open store items) emits
`cap_reached` on *every* turn end, productive or not. Two such turns ⇒ `stuck=True`,
and the flag then sticks until the old records age out of the 50-deep tail.

The four owed-work suppressors in `_auto_poke` cannot catch this:

| Suppressor | Why it misses the busy-manager case |
|---|---|
| `_session_awaiting_user` | Requires an `awaiting: user:` hold / open user-gate — a busy manager is not parked on Rick. |
| `_session_awaiting_peer` | Requires `work_owed=true` **and** `awaiting: peer:` — a busy manager mid-merge declares neither. |
| `owed_class` DONE / BLOCKED_ON_USER | The manager genuinely owes **ACTIVE** work → `CLASS_ACTIVE` → fail-SAFE, never suppressed. |
| The `alive` gate | The session *is* alive — that is the precondition for poking, not a defense. |

So a genuinely-active session that owns owed work and has exhausted its self-poke
budget is flagged `stuck` from stale cap-history and poked on a poll cadence. This is
the same class as `c9575068` and the `262c59f6`/`26dd3afb` family — the detector reads
a **stale oracle** and does not consult a **ground-truth sign of life**.

## Fix — mirror the 26dd3afb MANAGER-STALE bridge-mtime veto into `_auto_poke`

`_check_manager_staleness` already solved the isomorphic problem: a fresh **session-
bridge mtime** is ground-truth liveness (every hook fire touches the bridge) that the
derived oracle can miss. `_auto_poke` is the ONE poke detector that was never threaded
`bridge_mtimes` (`_tap_managers` and `_check_manager_staleness` both receive it).

**Why bridge-mtime cleanly distinguishes active-from-wedged here:** at poke-cap the
self-poke nudge STOPS (`cap_reached → should_increment=False`; the session is allowed
to go idle). So a *genuinely* wedged/parked-at-cap session takes no further turns →
its bridge goes stale → it is NOT vetoed → it is still poked (the true-positive is
preserved). A *busy*-at-cap session keeps taking real turns → its bridge stays fresh →
it is vetoed. Exactly the discrimination the incident needs.

**Change** (`arbiter_job.py`, arbiter-PROCESS code → needs `:8001` redeploy on land):

1. Thread `bridge_mtimes=manager_bridge_mtimes` into the `_auto_poke(...)` call in
   `_poll_once` (the map already read once per poll via `_read_manager_bridge_mtimes`).
2. `_auto_poke` gains a `bridge_mtimes=None` kwarg.
3. New helper `_session_bridge_fresh(persona, now, bridge_mtimes)` — returns True iff
   the persona's canonical-keyed bridge mtime is within
   `manager_stale_poke_threshold_seconds` (reused for consistency with the sibling
   veto), with the `097778b8` `0 <= age` lower bound so a future/corrupt mtime does
   NOT falsely veto. Logs one `arbiter_stuck_bridge_veto` event when it vetoes.
4. The `pokeable` comprehension drops any session for which
   `_session_bridge_fresh(...)` is True — a fourth suppressor beside the three above.

**Seam discipline (identical to 26dd3afb / the awaiting-* suppressors):**
`bridge_mtimes` None (seam unwired / read raised) ⇒ INERT ⇒ today's behavior; a
persona with no bridge entry ⇒ no veto; negative age ⇒ no veto (fail toward poking).
The veto can ONLY suppress on **positive** liveness evidence — it never hides a real
stall.

## Safety direction (the load-bearing invariant)

A genuinely wedged/dark session produces NO fresh bridge → is NOT vetoed → STILL poked.
The veto strictly narrows the poke set on positive evidence of turn-taking; it can
never manufacture silence for a real stall. The RED-first tests pin this direction
explicitly (stale bridge → still pokes; absent persona → still pokes; None map →
inert; future mtime → still pokes).

## Fresh cross-evidence (2026-07-02, post-redeploy) + the deeper root cause

While this fix was in review, the **deployed** `:8001` arbiter (which does NOT yet carry
this fix) loop-poked **Mr Radio** twice in 62s (22:00:18Z / 22:01:20Z) and Tiberius
three times earlier (16:05–16:07) — same "repeated cap-reached w/ work owed" signature.
Mr Radio's forensic on his own preserved events file (`8a92b253`, 135 records) sharpened
the mechanism behind the stale cap-history:

- The arbiter tails `~/.claude/heartbeat-events/*.jsonl` **from tracked offsets**. A
  `:8001` redeploy/restart **resets those offsets**, so the process **re-consumes
  HISTORICAL `cap_reached` records as if fresh**. His last real `cap_reached` was
  21:27:07Z (33 min stale, from his predecessor's arc) and was followed by **five**
  `honored`/`poke_count=0` outcomes — yet the restart replayed it and loop-fired.
- Both false-fire bursts land **~40 min after a redeploy** (Tiberius' 16:05 ≈ 43 min
  after the 15:22 redeploy; Mr Radio's 22:00 shortly after the 21:47 redeploy) — the
  offset-reset-replay signature.

**Scope note (for Cheech):** these instances **post-date `1a4d8565`/`46eb7b98`** (the
union `freshest_age_s` `0<=fa` floor), which proves that floor is a **different
detector** and does not touch this class. This fix (`_auto_poke` bridge-veto) and the
staleness floor are disjoint.

## Decision — offset-reset hardening is a FOLLOW-ON, not in this diff (flagged for Cheech)

Mr Radio proposed three hardenings: **(a)** ts-freshness gating on consumed
`cap_reached` records (ignore ones older than a threshold or superseded by a newer
`honored`/`poke_count=0` in the same stream), **(b)** durable offsets across restarts,
**(c)** a fire-throttle. **My call: all three are a SEPARATE follow-on item, NOT folded
into this reviewed-ready diff.** Rationale:

1. **This diff already closes the TITLED bug** — "loops on an ACTIVE session." The
   bridge-veto suppresses every false-poke at a session taking real turns, which is
   exactly the reported harm (Tiberius + Mr Radio were both demonstrably active).
2. **(a)/(b) live in different files/layers** — `fleet_data_model._count_stuck_episodes`
   (the `stuck` computation) and the events-tail **offset store** — not `_auto_poke`.
   Folding them in would force Cheech to re-review unrelated surfaces and bloat a clean
   diff.
3. **They address a DISTINCT, deeper root cause** the bridge-veto does not fully cover:
   a genuinely-IDLE session (stale bridge) carrying old *consumed* `cap_reached` would
   STILL be falsely poked after a restart-replay — the veto only defends the *active*
   case. So (a)/(b) are genuine additive robustness deserving their own RED-first cycle.
4. **Layering is honest:** this diff = the *symptom* fix for active sessions (P2, the
   titled bug); the follow-on = the *root-cause* fix for restart-replay at any session
   (durable offsets + consumed-record ts-gating + throttle).

Filed as a follow-on store item (see the DM/store record). Cheech gates this decision
explicitly alongside the code.

## Companion fix — 8894e597: strip the arbiter's false reply affordance (Option B)

Reviewed + built in the SAME cycle (Tiberius ruling 2026-07-02, Option B GO). Same
theme as 92c7ab1d: make the arbiter poke HONEST to the sessions it addresses.

**Problem:** every arbiter poke/advisory ends with a literal
`↳ Reply via dm_send( recipient="…", reply_to="…", thread_id="…" )` affordance —
built by the SHARED `hook_common.build_peer_dm_reminder`. But the arbiter is a `:8001`
background process with **no bridge registration and no inbox**: advisories sign as
"a peer session" → `recipient_not_found`; session-id `lupin-arbiter-app-8001` →
`recipient_inactive`; even a real thread-id → `recipient_not_found`. Three failed
replies by Tiberius on 2026-07-02. Every poked session **burns a turn** attempting the
impossible reply, then falls back to hold-mtime as the de-facto ACK.

**Decisive evidence (why Option B, not A/C):** bug `9694fb11` already RATIFIED that the
arbiter has no deliverable ACK path — `_check_manager_acks` docstring: *"there is NO
deliverable tap-ACK path — a manager literally cannot DM the arbiter back. So the only
honest ACK is the liveness proxy (bridge-mtime + stop-event + commons + idle_prompt +
sent-DM)."* Registering an inbox (a) or a commons-tail (c) would only let the arbiter
RE-DERIVE liveness it already computes — redundant with `9694fb11`. Option B makes the
message match the ratified truth at the lowest cost, and **composes with 92c7ab1d**:
the arbiter now literally reads bridge-freshness as the sign-of-life, so "signal by

**Change:**
1. `hook_common.build_peer_dm_reminder( …, one_way=False )` — new param. `one_way=True`

   `one_way` → unchanged, regression-guarded by their existing tests.
2. `arbiter_live_notify._default_peer_dm_reminder` passes `one_way=True` (the ONLY
   arbiter-authored framing seam, feeding both `make_tmux_push_fn` and
   `make_dm_push_fn`). De-pragma'd + directly tested so the WIRING (arbiter → one-way),
