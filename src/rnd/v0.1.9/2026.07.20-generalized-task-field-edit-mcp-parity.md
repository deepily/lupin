## 0. THE ONE-PARAGRAPH VERSION

A manager or human needs a last-mile "change field X to value Y" on a task-store row — most concretely, **demote a mis-inflated `priority`**. That capability **already exists over REST** as `PATCH /api/tasks/{id}` (7 whitelisted fields, `extra="forbid"`, enum-validated, invariant-safe by design). **It has no MCP verb**, so an MCP-only session (every fleet worker) cannot reach it — the mechanical root of the C7 P1-inflation finding. This plan adds **one thin MCP verb, `task_edit`, that wraps the existing PATCH endpoint** — no new server logic, no new invariants, no schema change. The endpoint's existing two-bucket split (7 free-edit fields vs. the 5 invariant-bearing fields it refuses) is inherited verbatim.

---

## 1. THE PREMISE CORRECTION (why this is smaller than "generalize task_amend")

The originating idea was "generalize the `task_amend` MCP verb to cover everything — specify field + value." Ground-truth investigation (agent report, 2026-07-20) surfaced two facts that reshape it:

| Assumption | Ground truth | Consequence |
|---|---|---|
| `task_amend` sets fields | `task_amend` is **APPEND-ONLY to `body`** + one audit event (`tasks.py:639`, `TaskAmendIn` `tasks.py:217`). It overwrites nothing. | Overloading it would *destroy* a distinct, valued semantic (immutable audit-append). ❌ Don't. |
| We need to build a generic field editor | `PATCH /api/tasks/{id}` **already is one** (`tasks.py:701`, `TaskPatchIn` `tasks.py:235`) — 7 fields, `extra="forbid"`, `validate_patch` enum checks. | The build is **MCP parity only**, not a new editor. |

⇒ **The gap is one missing MCP wrapper, not a new endpoint.** Reuse the shipped, reviewed, invariant-safe PATCH; do not re-implement field validation in the MCP layer.

---

## 2. THE VALIDATION QUESTION, ANSWERED CONCRETELY

> *"Are we performing any validation of the submitted value, since Pydantic will catch illegal values and throw?"*

**Pydantic catches illegal VALUES; it does not catch illegal STATES.** Two layers, both already present on PATCH:

1. **Value validation** (Pydantic + `validate_patch`, `task_store_rules.py:931`): wrong type → 422; bad enum (`priority` not in P0–P3, `gate_class` not in none/manager/operator, `urgency` not in urgent/normal/low) → 422; empty `title` → rejected. **This fully covers the 7 free-edit fields.** No extra MCP-layer validation needed.
2. **State/invariant protection** (DB CHECKs + `LEGAL_TRANSITIONS` + `extra="forbid"`): the 5 fields `status, blocked_by, next_chase_ts, park_reason, park_reason_captured_at` carry cross-field invariants (I3 kind-aware chase `postgres_models.py:1436`; parked-requires-reason/chase/captured_at `1445/1449/1459`; the transition-legality matrix `task_store_rules.py:79`). Setting any in isolation would pass Pydantic and then **500 on a DB CHECK** — or silently corrupt the staleness invariant. PATCH refuses all 5 at the wire via `extra="forbid"`.

⇒ **Answer: yes, validation is complete for the editable set — and it already exists.** The invariant-bearing fields are deliberately NOT editable this way; they stay on `task_transition`, which moves the coupled fields together.

### The buckets (post-review, 2026-07-20 — Krishna 🦚 + María 🌸 converged)

PATCH's `PATCH_EDITABLE_FIELDS` (`task_store_rules.py:886`) whitelists 7 fields. **`task_edit` exposes only 5 of them** — the two owner fields are deliberately excluded (see below).

**FREE-EDIT (this verb):** `title` · `body` · `priority` · `gate_class` · `urgency`

**REFUSED → `task_reassign`** (owner-change path, mandatory `reason` + `authority="manager_relay"`): `owner_persona` · `accountable_manager`
> **Amendment (María, required):** editing owner via a bare `task_edit` would be a *reason-free backdoor to reassignment* — `task_reassign` mandates a non-empty `reason` and stamps `manager_relay`; `task_edit` defaults optional/`standing`. Same endpoint, same `patched` event, so there is NO audit divergence to "document" (my original §8 framing was wrong). Keep ONE owner-change path. The C7 priority-demote use case needs no owner field.

**REFUSED → `task_transition`** (invariant-bearing, would break a DB CHECK if set alone): `status` · `blocked_by` · `next_chase_ts` · `park_reason` · `park_reason_captured_at` · `receipt_refs` · `correlation_key`
> **Wording fix (María):** the *source* (`TaskPatchIn` docstring `tasks.py:240` + `validate_patch:937`) names only **5** explicitly — `status, blocked_by, next_chase_ts, receipt_refs, correlation_key`. `park_reason`/`park_reason_captured_at` are refused too, but by `extra="forbid"` catching everything non-whitelisted, NOT by name. Don't imply the model enumerates all 7.

**🔴 REFUSED → stripped/rejected (Krishna, BLOCKING — dict-smuggle):** `actor` · `authority` · `reason` are valid `TaskPatchIn` fields (NOT `extra=forbid`-blocked); `patch_task` stamps the audit event from `payload.actor` in the body. `task_edit(id, updates={"actor":"victim",...})` would spoof the audit identity past the bridge. **The impl MUST whitelist `updates` keys to the 5 free-edit fields and stamp `actor` LAST.**

## 3. ✅ RULED (Rick, 2026-07-20) — Option A: `task_edit(task_id, updates={field: value, ...})`

Rick ratified the dict shape. Build proceeds on Option A; §4 onward assumes it. Original fork preserved below for the reviewer's context.

### 3.x Original fork — verb naming/shape

The design forks on how the new MCP verb presents. All three wrap the same PATCH; the difference is ergonomics + how the two-bucket split is communicated to the caller.

| Option | Shape | Pro | Con |
|---|---|---|---|
| **A (recommended)** — new verb `task_edit(task_id, updates={field: value, ...})` | dict of fields, one call edits several | matches PATCH 1:1 (multi-field in one txn); one audit event; future-proof | new verb name to learn |
| **B** — new verb `task_edit(task_id, field, value)` | strictly one field per call | matches your "specify what field, what value" phrasing exactly | multi-field edit = N calls, N events; can't express "retype title+priority atomically" |
| **C** — overload `task_amend` to also set fields | no new verb | fewest verbs | **conflates immutable audit-append with mutable overwrite** — two opposite semantics on one name. ❌ |

**Recommendation: A.** It mirrors the endpoint exactly (PATCH already accepts a partial-field body), keeps edits atomic + single-audit-event, and leaves `task_amend`'s append-only contract intact. B is a strict subset of A (call A with a one-key dict). C is discouraged on semantic-collision grounds.

## 4. DESIGN (assuming Option A)

Thin transport wrapper — **zero new server logic**:

- **MCP tool**: `task_edit` in `src/lupin_mcp/cosa_voice_mcp.py` (beside `task_amend` @3680 / `task_transition` @3595). `actor` bridge-stamped via `_task_store_identity()` — **not** a caller param (identity guarantee, `cosa_voice_mcp.py:3436`). Params: `task_id`, `updates` (dict), `reason` (optional), `authority` (default "standing").
- **🔴 KEY-WHITELIST (blocking, Krishna)**: `task_edit_impl` MUST filter `updates` down to the **5 free-edit keys** before building the PATCH body — `actor`, `authority`, `reason`, the two owner fields, and any invariant field are stripped/rejected (reject-loud preferred over silent-strip). The bridge `actor` is stamped **LAST**, after the `updates` spread, so no caller key can shadow it. **This is the only new logic in the verb.** (María confirms the same actor-stamp-last ordering.)
  - ⚠️ **The whitelist is a REAL client-side guard, not cosmetic**: `task_edit`'s 5-key set DIVERGES from the server's 7-key `PATCH_EDITABLE_FIELDS`. Owner fields + `actor`/`authority`/`reason` would all be ACCEPTED by a raw PATCH — the MCP layer is the only thing refusing them. Tests must assert the refusal at the MCP boundary (drive `task_edit_impl`), never lean on a server 422 for these.
- **Transport impl**: `task_edit_impl` in `src/lupin_mcp/task_store_tools.py` (beside `task_amend_impl` @300, mirroring `task_reassign_impl` @243 — the living thin-PATCH-wrapper twin) → `PATCH /api/tasks/{task_id}` with the filtered `updates` dict as the body.
- **Server**: **NO CHANGE** to `tasks.py:701` `patch_task`, `TaskPatchIn`, or `validate_patch`. The refusal of invariant fields is already `extra="forbid"` → 422. The verb inherits it.
- **Docstring**: names the 5 editable fields, states that owner fields route to `task_reassign` and invariant fields to `task_transition`, and notes `updated_ts` bumps ORM-side (PATCH goes through the ORM so this is fine).

### What this verb explicitly does NOT do
- Does not touch `status` or any oracle field (→ `task_transition`).
- Does not mint rows (→ `task_create`).
- **Does not change owner** — `owner_persona`/`accountable_manager` route to `task_reassign` (one owner-change path, mandatory reason). *(Amended 2026-07-20; original "edits owner as a plain field" was the reason-free-backdoor hazard María + Krishna flagged.)*
- No new authority gate. Authority stamps the audit event only. The sole hard role-gate (manager-only blocked-*mint*, `tasks.py:439`) is create-scoped and untouched.

## 5. ACCEPTANCE CRITERIA

- **AC1** — `task_edit(task_id, updates={"priority":"P3"})` demotes priority via MCP; audit event `patched` recorded with actor bridge-stamped. (Closes the C7 P1-inflation mechanical gap.)
- **AC2** — each of the **5 free-edit fields** (`title, body, priority, gate_class, urgency`) is settable; multi-field dict edits in one call → one event, one txn.
- **AC3** — every invariant-bearing field (`status, blocked_by, next_chase_ts, park_reason, park_reason_captured_at, receipt_refs, correlation_key`) is **refused with 422** naming `task_transition`. (Assertion against `extra="forbid"`.)
- **AC4** — illegal enum value (`priority="P9"`, `gate_class="bogus"`, empty `title`) → 422 from `validate_patch`, no row mutation.
- **AC5** — terminal item (done/dropped) → rejected (inherits `tasks.py:759`).
- **AC6** — empty `updates` → 422 (inherits `validate_patch:958`).
- **AC7 (dict-smuggle) — ⚠️ DESCOPED (Rick, 2026-07-20, deadline).** Rick waived the audit-identity spoof concern: *"I don't care about that, we gotta ship."* The impl keeps the **basic actor bridge-stamp (stamped last)** it already had — free, no expansion. The `authority`/`reason` smuggle arms are NOT built. Integration keeps a **tolerant** AC7b smoke (passes if refused OR `event.actor==bridge`). Follow-up hardening, if ever wanted, is a separate row.
- **AC8 (owner-refusal, María + Krishna)** — `updates={"owner_persona":...}` or `{"accountable_manager":...}` → **rejected at the MCP LAYER** with a message pointing to `task_reassign`. ⚠️ **Assert at the MCP boundary, NOT a server 422**: `task_edit`'s set (5) DIVERGES from the server's `PATCH_EDITABLE_FIELDS` (7) — the raw PATCH would still ACCEPT owner fields, so this refusal is a new client-side guard (same key-whitelist mechanism as AC7), not an inherited 422. (Keeps the single mandatory-reason owner-change path.)
- **AC9** — **zero diff** to `routers/tasks.py`, `task_store_rules.py`, `postgres_models.py`, and no migration. (Proves "MCP parity only".)
- **AC10 (100% mandate)** — new `task_edit` + `task_edit_impl` at 100% lines/branches/functions; any file-level shortfall is pre-existing surface, named in-commit + reversible.
