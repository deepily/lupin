# Purpose-Built vLLM Install for Mistral Small 3.2 (2506)

## Context

Rick wants a dedicated installation directory and virtualenv for Mistral Small 24B, separate from the general-purpose `vllm-pip` sandbox: a `vllm-mistral-small-24b` directory under `$DEEPILY_PROJECTS_DIR` with its own `.venv`, into which the needed dependencies get installed. This is the original ask from earlier in the session — it was approved once already, Step 0 (serialization) ran, but execution then got sidetracked into the disk-cleanup detour and the checkpoint-compatibility research. Nothing has been created on disk yet. This plan restores focus to just that: create the directory, the venv, and install the pinned dependencies. The checkpoint download is a separate, still-open decision and does not block this.

**Verified this session (unchanged facts):**
- **GPUs**: 2× RTX 4090 (24GB each), driver 535.104.05, sm_89 (Ada).
- **CUDA is not a blocker**: driver reports native CUDA 12.2, and torch 2.6.0+cu124 (the wheel vLLM 0.8.5 pulls in) was empirically verified to run real GPU matmuls on this driver via CUDA 12.x minor-version compatibility.
- **vLLM 0.8.5** (in the existing `vllm-pip` venv) has `awq_marlin`, `gptq_marlin`, and `fp8` quantization support, and `Mistral3ForConditionalGeneration` is a registered architecture — the family loads on this vLLM version.
- **Real gap found**: `mistral_common` is pinned at 1.5.4 in the existing venv; Mistral Small **3.2** needs `>=1.6.2`. The new venv installs the upgraded version from the start.
- **HF caching**: `HF_HOME=/mnt/DATA01/include/www.deepily.ai/projects/models` is already set globally in `~/.bashrc` — no per-project cache config needed. Headroom is no longer a concern: the disk cleanup completed earlier this session freed `/mnt/DATA01` from 95GB to **1.2TB free (35% used)**.
- **Version pin revised — 0.8.5 was never a real ceiling.** It was mirrored from the sibling `vllm-pip` venv purely for convenience, not because it's the newest our CUDA setup supports. Our driver (535.104.05) caps out at CUDA major-version 12 (native 12.2, minor-version-compatible with any 12.x wheel, already proven with 12.4) — it cannot run CUDA 13.x builds (needs a 580-series driver we don't have). vLLM's current release, **0.26.0** (2026-07-25, confirmed via PyPI), still defaults a plain `pip install vllm` to CUDA 12.9 — still major-version 12, still inside our proven envelope. `cu130` (CUDA 13) wheels exist but are opt-in only, not the default. **This plan now installs latest (0.26.0) instead of pinning 0.8.5** — 0.8.5 is 15 months and ~18 minor versions behind, and concretely, that gap is why native AutoRound quantization support isn't there (it landed in the release right after 0.8.5). Same empirical GPU-verification pass from earlier this session gets re-run against the new version before anything is trusted.
- **Checkpoint decision — likely resolved by the version bump**: Rick's pick, `Intel/Mistral-Small-3.2-24B-Instruct-2506-int4-AutoRound`, uses `quant_method: "auto-round"`, unsupported on 0.8.5 but natively supported by any vLLM release after 2025-05-19 — which 0.26.0 comfortably is. Final confirmation happens in Verification step 4 below (actually loading it), not assumed here.

The interpreter and `.venv` layout are proven; the specific vLLM/torch version is new and gets its own verification pass below.

## Resolution (2026-07-31, post-plan-approval execution)

Reality diverged from every version-pin assumption above — recorded here rather than
edited away, since the divergence itself is the useful record:

- **`vllm==0.26.0` (latest) failed step 4's premise entirely.** Its compiled extension
  links against `libcudart.so.13` — CUDA 13 — regardless of which torch build sits next
  to it (`uv --torch-backend=auto` correctly picked `torch+cu129`, but vLLM's own
  prebuilt kernels don't adapt). Driver 535 cannot run CUDA 13 at all (major-version
  jump, needs a 580-series driver). vLLM's docs claiming "defaults to CUDA 12.9" did not
  hold for what PyPI actually serves for this release.
- **Bisected down to `vllm==0.16.0`** (Feb 2026) — resolves `torch==2.9.1+cu129`, real
  GPU matmul passes. But its quantization loader has a genuine bug: `"auto-round"` maps
  to a working `INCConfig` class internally, but an earlier list-membership gate
  (`QUANTIZATION_METHODS`) rejects the string before the mapping is ever reached —
  `get_quantization_config("auto-round")` raises `ValueError` unconditionally on this
  version. The Intel `int4-AutoRound` checkpoint Rick originally picked would not have
  loaded here either.
- **Final environment**: `vllm==0.16.0` + `torch==2.9.1+cu129` + `mistral_common==1.11.7`
  — see `requirements.txt` in the project dir for the full resolved set.
- **Final checkpoint**: switched to
  `ConfidentialMind/Mistral-Small-3.2-24B-Instruct-2506-GPTQ-AutoRound-TextOnly` (Rick's
  call, 2026-07-31) — same underlying Intel AutoRound algorithm, packaged with
  `quant_method: "gptq"` instead, sidestepping the broken gate entirely via the
  well-supported `gptq_marlin` path.
- **Real weight footprint is ~19.6GB in VRAM** (15GB on disk), not the ~13.5GB the
  original deep-research doc estimated for a generic W4A16 24B — this specific
  community quant runs larger. That, plus CUDA-graph-capture scratch overhead, forced
  `--max-model-len 8192` (not 32768), `--gpu-memory-utilization 0.95`, and
  `--enforce-eager` to fit on a single 24GB card. Full detail in the project's own
  `README.md`.
- **HF_HOME did not inherit through `nohup ./script.sh &`** as the plan assumed —
  the first real download landed in the default `~/.cache/huggingface` instead of
  the intended path. Moved by hand (no re-download needed); the launch script now
  exports `HF_HOME` explicitly rather than relying on shell inheritance.
- **Verified end-to-end 2026-07-31**: real `/v1/chat/completions` request returned
  correct output ("The capital of France is Paris.") in 0.32s, ~25 tok/s, on GPU1
  (GPU0 is occupied by the always-on `svllmr` production router).
