## 0. Verdict first

The ruling's remedy is right. **Its premise is wrong in a way that changes the ordering constraint.**

The ruling says the hardcoded `container_name` is the only thing preventing stack 2's socket-init from deleting stack 1's live socket, so the rename and the topology split must land in one commit. That is true **only across distinct compose projects**. The repo does not invoke them that way, and does not pin a project name anywhere. Under the shape the deploy scripts actually use, there is **no guard at all**, and the socket deletion is not something a rename would arm — it is already armed, waiting on the first `up` of a second stack.

⇒ The dangerous act is **bringing the second stack up**, not renaming a container. The one-commit rule still holds; the reason it holds is different, and so is what must be true before anyone runs `compose up` on the VM.

## 2. The measurement — two arms, isolated throwaway project, torn down

docker 24.0.4 / compose v2. Two files, both declaring `container_name: clay-probe-sockinit`, a `shared` volume, and `holder --depends_on(service_completed_successfully)--> sockinit` where `sockinit` runs `rm -f /shared/*.sock` and appends to an audit log. Stack A up, a socket touched into the volume, then stack B up. Prediction written before each run.

### ARM 1 — same project (both files in one directory, no `-p`, no `name:`) — the repo's real shape

```

               Container clay-probe-holder-a   Recreated
               Container clay-probe-sockinit   Starting / Started / Waiting / Exited

              audit = RAN-THE-RM-a, RAN-THE-RM-b     <- the rm ran twice

              volume still probe-sameproj_shared     <- one volume, shared
              clay-probe-holder-a -> "No such object: clay-probe-holder-a"
```

**No conflict. Compose recreated.** And beyond what I predicted: **stack A's app container was destroyed.** Compose saw service `holder` redefined with a different `container_name`, recreated the service, and the old container ceased to exist.

## 3. What this changes about the ordering constraint

The ruling: *"a commit whose diff is only `container_name` removals must not exist."* **Keep it.** It is still the reviewable-in-ten-seconds change that looks tidy and ships a P1 — and under ARM 2's regime it is precisely as described.

What must be added to it:

1. **The rename is not what arms the deletion under the repo's own invocation.** Removing the names changes nothing about ARM 1, because ARM 1 never reached a name conflict. A reviewer who reads the ruling as *"names present ⇒ safe"* will conclude the current files may be co-run. **They may not.**
2. **`lupin-rest` is a second, unguarded path.** Both files define a service by that name with divergent container names (`lupin-rest-cloud-gpu` / `lupin-rest-cloud-test`). That is the shape that destroyed `clay-probe-holder-a`. No hardcoded name protects it, in either regime.
3. ⇒ **The gating act is the first `compose up` of stack 2 on the VM, and it must not happen until the project names are pinned in the files.**

---

## 4. The change, as one commit

Preconditions 1–3 of §6 must hold first. The commit itself:

1. **Pin a top-level `name:` in each cloud compose file** — `lupin-cloud-gpu` and `lupin-cloud-test`. This is the load-bearing half and the one the current plan does not have. It is invocation-independent: it survives an operator who forgets `-p`, which every call site in this repo does. Per Mr Radio's own rule, *an invocation-dependent guarantee is not a guarantee* — and `-p` on the call sites is exactly that.
2. **In the same commit, drop or per-stack parameterize `container_name`** on `cloudsql-socket-init` and `cloud-sql-proxy` in both files. Pinning distinct project names already namespaces the volumes (`lupin-cloud-gpu_cloudsql-socket` vs `lupin-cloud-test_cloudsql-socket`, measured), so each stack's init clears only its own.
3. **Remap `cloud-test`'s rest publish** `7999:7999` → `8000:7999`. **`:7999` ONLY** — the `7998` clash is struck: `cloud-gpu` runs the model server on Cloud Run and publishes nothing on 7998 (confirmed at source, `cloud-gpu.yml:94` vs `cloud-test.yml:84,148`).
4. **Update the guard** `src/tests/unit/deploy/test_compose_dual_stack_project_isolation.py` — `test_todays_guard_is_the_name_collision_arm` asserts the accidental arm is what protects us today, and must be re-narrated when the real arm takes over. It is written to go red on exactly that transition rather than pass silently through it.

**Not in this commit** (they belong to the bring-up, not the file change): the VM-side verification of §6.3, and preflight learning the second stack.

## 5. The guard that is already landed

`src/tests/unit/deploy/test_compose_dual_stack_project_isolation.py` — 11 tests, green today.

It asserts `project_isolated OR name_collision_guard`, so a rename-only diff turns it red while the correct one-commit shape stays green. Its scope is stated in its own docstring rather than implied: **it covers the socket-deletion path only.** The `lupin-rest` recreate path from ARM 1 is unguardable by any container-name arm, and a green run is not a claim that the two stacks may be co-run.
