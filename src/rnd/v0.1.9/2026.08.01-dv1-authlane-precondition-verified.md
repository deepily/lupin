## 1. The precondition (Rick's one hard gate, §7)

> The catch-up fetch must read the **X-API-Key** lane, **not** the listener's ambient service-account `self._user_id` — the plan's one silent-failure surface. Prove the seeded owed row comes **back**; an empty result is **not** the pass signal.

## 2. Verdict — satisfied, and stronger than the requested test

The trap is **closed by construction**, not merely avoided at runtime:

- `answer_catchup._fetch_owed(persona, session_hash8, since, limit)` has **no `user_id` parameter**. It authenticates with `task_store_client.read_api_key()` (X-API-Key) and calls `GET /api/notifications/answers-owed?persona=…`. No user_id crosses the boundary.
- The endpoint `get_answers_owed` takes `authenticated_user_id` from `require_api_key_or_jwt` but **never uses it**. The repo query `get_answers_owed_for_persona` filters on `sender_persona` **alone** (ruling 6).
- `self._user_id` lives on the listener instance (`base_listener.py:268`, the shared service account) and is **never passed** to the fetch (`cc_notification_listener._on_connected`).

So `self._user_id` cannot scope the fetch **by any path**. "Runs the right lane" would be a runtime accident; "has no parameter for the wrong lane" is a structural guarantee.

## 4. The mirror-image finding (filed, not fixed) — bug `fd245188`

The same property that closes Rick's trap opens a different one: because the query is **persona-keyed only** and never consults the caller, the endpoint **authenticates but does not authorize** — any caller with any valid credential can pull **any** persona's owed answers (original question + the human's typed answer) by naming the persona. "Structurally cannot be scoped to `self._user_id`" and "structurally cannot be restricted to an owner" are the same sentence read two ways.

Blast radius is small in a single-operator fleet; it grows with any multi-tenant / multi-human deployment. This is a **design question above the tester lane** (authorize by owned-personas vs accept persona-keyed-only per ruling 6) — filed as bug `fd245188` (P2), not fixed here.
