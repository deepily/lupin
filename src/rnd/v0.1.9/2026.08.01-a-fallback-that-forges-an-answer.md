# A fallback that emits the same shape as a real answer is a forgery

**Date**: 2026-08-01 · **Status**: DRAFT — Cheech 🌿 to correct his half before this is final
**Authors**: Mr. Radio 🦉 (`9056b85b`) drafting · Cheech 🌿 (`7edf6e5e`) on `voice_io` ·
Tiffany 💍 on ack-dedupe · Maria 🌸 spotted that the three were one thing

Three defects were found in one day, in three unrelated subsystems, by three people who
were not looking for the same thing. They are the same bug.

> **The line is Cheech's, and it is better than the one I had:**
> *a fallback that emits the same shape as a real answer is not a fallback, it is a forgery.*
> Mine forged a grade. His forged a click.

---

## 1. The shape

A component cannot produce its real answer. Rather than say so, it returns a value that is
**indistinguishable at the boundary** from a real answer. The caller has no field to check,
no exception to catch, no sentinel to test. The failure leaves the building wearing the
costume of a judgement.

Two halves, and the second is the one that keeps getting missed:

1. **The value is wrong.** Recoverable, and usually the part that gets fixed.
2. **The wrongness is unreadable.** No downstream consumer can tell the difference, so the
   wrong value is consumed with the same confidence as a right one — and, being
   well-formed, it survives every schema check, every type check, and every test that
   asserts on shape.

A fallback is legitimate when a caller can *tell*. These three could not.

---

## 2. The three instances

### 2.1 A parse failure published as an opinion — `normalize_grade_label` (Mr. Radio)

The DM Quality Judge maps a grade label to a weight on a five-point scale. The live model
emits its labels **spaced**: `needs _ improvement`. The normalizer ran two sequential
replaces:

```python
key = str( label ).strip().lower().replace( " ", "_" ).replace( "-", "_" )
```

`needs _ improvement` → `needs___improvement` → not in `GRADE_TABLE` → falls through to the
`meh` fallback.

⇒ The **most frequently emitted multi-word label in the scale** was discarded on every
occurrence, and a real `−1` was published as a considered neutral `0`. Tone read `meh` for
every message tested.

The fallback was doing exactly what it was written to do. `_FALLBACK_LABEL = "meh"` exists
so an unrecognizable label never raises, and that is a reasonable thing to want. It simply
cannot tell *"I do not recognize this"* from *"I failed to parse something I should have
recognized"* — and it reports both as a considered `meh`.

**Fix**: collapse any run of whitespace / hyphen / underscore to one separator. 10 tests
across all five levels × four sloppy spellings, asserting the **weight** rather than the
key, because the defect was a wrong *number* reaching a reader. Plus a negative control
that a genuinely unknown label still lands on `meh`, so "fix the normalizer" cannot be
satisfied by accepting everything. Mutation control: restore the old normalizer → 7 red,
negative control correctly stays green. Commit `6ba616cb`.

### 2.2 Silence published as consent — `voice_io` (Cheech)

> ⚠️ **Cheech's account, relayed. He is correcting this section — do not treat it as final.**

The gate returned the first option on failure. Two things make it worse than that sentence
suggests:

- **It was six sites, not one**: non-interactive mode, blank CLI entry, out-of-range
  number, unparseable multi-select, and the dispatch-failure catch. **Five of the six had
  nothing to do with a failed call** — they fired when a human was right there and simply
  did not answer.
- **All three return paths emitted an identical payload.** A caller could not distinguish
  *"user pressed Approve"* from *"user typed nothing"* from *"the call 503'd."*

**Fix (landed)**: all six sites take an explicit per-gate default or raise, and the return
carries `default_used` / `answered` / `default_source`. 27 tests green.

**A detail worth more than the fix**: a green test suite over the *same function* vouched
for none of it. It covered the non-interactive branch — where returning option one is
**deliberate**. The tested twin and the broken twin lived eight lines apart.

## 3. Where they diverge, and why the distinction earns its keep

Cheech's framing, and it is the sharpest thing in this document:

| | mangles an input it should have understood | never had an input at all |
|---|---|---|
| **`normalize_grade_label`** | the label existed; the parser broke it | |
| **`voice_io`** | | nobody answered; it manufactured one from list position |

**A parse failure published as an opinion** versus **silence published as consent.** Same
failure to distinguish *"I know"* from *"I don't know"* — different reasons for not
knowing, and therefore different fixes. Collapsing them into one bug would have produced a
remedy that fits neither: the first needs a better parser, the second needs a caller-supplied
default and an honest receipt.

---

## 4. Why tests did not catch any of them

Each suite was green, and each was green *honestly* — every assertion was correct about the
question it asked.

- **`normalize_grade_label`**: the unit tier fed hand-written clean XML, so it tested the
  **parser**, not whether the model's actual output survived it. A constant `meh` is
  well-formed XML with a valid label. Nothing could go red.
- **`voice_io`**: the green test covered the branch where the behaviour is **correct by
  design**, eight lines from the one where it was not.
- **Coverage measured the wrong axis.** The judge package carried 100% lines and branches
  across three review rounds. Full coverage of the code that *handles* a value says nothing
  about whether the value means anything.

⇒ **A test that supplies its own input tests the code's response to that input.** All three
of these defects live in the gap between the input a test invents and the input the world
actually sends.

---

## 5. The generalisation, stated so it can be acted on

**A fallback must be distinguishable from a real answer at the boundary.** If a caller
cannot tell, it is not a fallback — it is a forged answer, and it will be consumed as a
considered one.

Concretely, a fallback owes its caller:

1. **A discriminator in the return** — `default_used`, `answered`, `source`, or an
   out-of-band sentinel a type checker will notice. Not a magic in-band value.
2. **A reason** — "unrecognized" and "failed to parse something recoverable" are different
   events and must not share a code path.
3. **A caller-supplied default rather than a library-chosen one**, wherever the right
   default is a policy question. `meh` and "option one" are both the library guessing at
   something only the caller knows.
4. **A test whose input is what the world actually sends**, not what the test author finds
   convenient to type.

**The smell to grep for**: a `.get(x, DEFAULT)`, a bare `except: return SOMETHING`, or an
`if not recognized: return NEUTRAL` where `DEFAULT` / `SOMETHING` / `NEUTRAL` is a member of
the same value set as a successful return.

## 6. A related but distinct family — filed separately, not folded in

Maria flagged a second shape the same day, and it is **not** this one:
**a control whose inputs cannot produce the failure it guards against.**

- My discrimination probe compared only a good body against a bad one, and reported
  `SEPARATED` while the middle of the scale was inverted. A two-point sample cannot express
  ordering.
- Tiffany's ack-dedupe control used a same-status pair, so it passed without ever
  exercising the status filter.
- And once more, in my own instrument: the probe demanded a strict *tone* ordering across
  three bodies that vary in **directness** and barely vary in tone — marking a correct
  answer wrong.

That is a **sampling** defect, not a **fallback** defect. Kept apart deliberately: they
would otherwise dilute into "be careful", which is not a rule anyone can apply.
