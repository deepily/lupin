# The Mistral 24B cutover: why it never worked, and why it is parked

**Date**: 2026-08-02 · **Author**: Mr. Radio 🦉 (session `1bf47c18`) · **Ruling**: Rick — park it, restore Phi-4
**Outcome**: `:3001` back on Phi-4, 27 config references repointed, gister verified 3/3. Cutover parked, not abandoned.

---

## 0. Short version

The 07-31 cutover changed the **model** and nothing else. Two things had to change and neither did,
so every one of the 29 references to the new spec had been failing since — silently, because the
one visible consumer degrades to a 5-word fallback that still looks like a real answer.

1. **Transport.** `prompt_format` stayed `instruction_completion`, which bypasses the chat template.
   Mistral-Small-3.2 requires it. Output was literal garbage.
2. **Prompt shape.** Even with the transport fixed, this repo's 30 Alpaca-style XML templates make
   Mistral emit unparseable XML. A chat-native prompt fixes it — which makes this a 30-template
   rewrite, not a config change.

**Parked on Rick's ruling**: not before Thursday. Phi-4 carries the fleet again.

---

## 1. How long, and why nobody saw it

Cutover landed 2026-07-31 (`5499fdbf`, 29 references renamed `kaitchup/phi_4_14b` →
`confidentialmind/mistral_small_24b`). `:3001` kept serving Phi-4 the whole time, so every call
404'd on a model name the server did not have.

**102 degraded gists on 2026-08-02 alone.** It stayed invisible because the listener's fallback is
honest in the log and silent in the product:

```
[CC-Listener] Gister failed: … "The model `ConfidentialMind/Mistral-Small-3.2-24B…` does not exist" (404)
[CC-Listener] DEGRADED: gist unavailable — emitting 5-word prefix fallback "Good morning Cheech Let's start".
              This is NOT a model-generated gist.
```

A five-word prefix still reads like a gist in the UI. **The log said exactly the right thing and
nobody was reading the log.**

**It was never only gists.** The spec key feeds gist generation, all 11 agent-router keys, the
formatters, math agent, debugger, qualifier classification, fuzzy file matching, TFE resume
matching, the runtime argument expeditor, and the notification proxy matcher.

### The shape of the miss

The 07-31 session verified Mistral with a real inference call against its own dedicated venv and
port — a genuine test that proved the checkpoint loads and generates. What it did not test is
**the path the application actually uses**: `:3001`, through `llm_client_factory`, through an
Alpaca prompt, into a strict XML parser. Same family as "a saved file is not a served file" — the
thing was verified somewhere it was not going to run.

## 2. Defect 1 — transport (fixed, then parked with the spec)

`prompt_format: "instruction_completion"` sends a raw `/v1/completions` request with no chat
template at all (`llm_client_factory.py:149` — `completion_mode = prompt_format in
[instruction_completion, special_token]`).

Same prompt, same live model, two transports, 3 trials each:

| transport | result | sample |
|---|---|---|
| `instruction_completion` (`/v1/completions`) | **3/3 INVALID** | `the list.1. The new 10000000000000000000…` |
| `json_message` (`/v1/chat/completions`) | **3/3 VALID** | `<response><gist>Yesterday's accomplishments and triage help</gist></response>` |

This also explains the config's own standing note that *"the 24B did not score clean on the fixed
path where Phi-4 did"* — the DM judge hit the same cause through a different consumer.

**The corrected `prompt_format: "json_message"` is retained on the parked spec**, so whoever
resumes the cutover starts from the fixed value rather than rediscovering this.

---

## 3. Defect 2 — prompt shape (the one that parks it)

With the transport corrected, the real gist prompt still fails. The model gets the *content* right
every time and the *format* wrong every time:

```
<?xml version="1.0" encoding="utf-8 ?>          <- closing quote missing
< response >                                    <- space after <
	 < gist > The weather in Washington, D.C. tomorrow afternoon. </ gist >
</ response >
```

The example it is shown is **well-formed** — it is mangling a clean template, not copying a dirty one:

```
<?xml version="1.0" encoding="utf-8"?>
<response>
	<gist>Calculate the square root of 144</gist>
</response></stop>
```

### The measurements

| prompt shape | body parseable |
|---|---|
| Alpaca blob as one user message (what ships today) | **0/3** |
| Alpaca split → instructions=system, input=user | **0/3** |
| chat-native prompt | **3/3** ✅ |

**Not sampling.** Byte-identical output at `temp .25 / top_p .25 / top_k 10`, at `temp 0`, and at
`temp 0 / top_p 1`. Three decode settings, same bytes — so this is the model+prompt combination,
not decode randomness. Ruling that out mattered: "turn the temperature down" is the cheap answer
that would have looked plausible and fixed nothing.

**Splitting the roles does not help either**, which is the result that sizes the job. If moving the
instructions into a system turn had worked, this would have been a client-side change. It did not,
so the Alpaca scaffolding itself has to go.

### ⚠️ A counterintuitive one, recorded because it will mislead someone

Removing the `<?xml?>` declaration from the **example** made things **worse**, not better:

| chat-native prompt | body parseable |
|---|---|
| example includes `<?xml … ?>` | **3/3** |
| example omits it | **0/3** |

Without the declaration the model reverts to `< response >`. The declaration appears to act as a
formatting anchor. Anyone "cleaning up" the example by dropping the declaration — a reasonable-looking
tidy, since the parser strips it anyway — will silently break the thing they were tidying.

### Size of the real fix

- **38** prompt templates use the `### Instruction:` scaffolding
- **30** of those inject `{{PYDANTIC_XML_EXAMPLE}}`
- **7** live specs were still on `instruction_completion`

Each conversion needs its own re-validation against the live model. The discrimination probe's own
docstring already states the rule: the unit tier measures the **parser**, not whether the prompt
still makes the model comply. A model swap is a bigger change than a prompt edit.

| | |

| `:3001` | Mistral killed, Phi-4 restarted (Rick, by hand) |

| Verification | Gister **3/3 real gists** on Phi-4 (0.58s) — the same three utterances that returned `''` on Mistral |

**Rick's reasoning, and it is the right call**: fixing 30 templates is not a today-sized job, the
risk is out of proportion to the benefit, and there is other work before Thursday. Restoring the
known-good configuration costs minutes and returns the whole surface.

### The DM judge, and what it costs to leave off

Measured on Phi-4 immediately **before** the swap, so a re-enable has something to beat:

```
✓ MONOTONIC on both dimensions, identical across 2 runs
  DIRECT_PLAIN  direct=2   tone=2      BURIED_PLAIN   direct=-1  tone=2
  DIRECT_JARGON direct=2   tone=-2     BURIED_JARGON  direct=-1  tone=-1
```
Directness 2 vs −1 holding prose constant; tone 2 vs −2 holding structure constant. Re-enabling is a
one-line flip **plus** a re-run of `src/tests/smoke/dm_judge_discrimination_probe.py` — the table
above is the bar.

## 5. If someone resumes this

In order, and do not skip the first:

1. **Convert one template chat-native and measure it** before touching the other 29. The result is
   already known for the gist prompt (3/3); confirm the method generalises before committing to the
   sweep.
2. **Keep the `<?xml?>` declaration in every example.** §3 says why.
3. **Set `prompt_format: "json_message"`** — already correct on the parked spec.
4. **Build the per-template gate first.** The failure mode this postmortem exists to prevent is not
   "the model is bad", it is "nobody noticed for two days." A harness that reports XML-parse rate per
   template per model turns the cutover into a gated flip. Without it, the next attempt fails the
   same way and is found the same way — by accident, in a log, while looking for something else.

**The one-line lesson**: the cutover verified that the model *works*, and never verified that the
*application* works with it. Those are different tests and only the second one matters.
