# Parked-worker DM-wake gap (bug d1bb1456) — TRIAGE receipt + recommendation memo

**Author**: Cheech 🌿 (reviewer/triage, session 25c7441c) · **Accountable**: Mr. Radio 🦉

**Rule honored**: NO build until Mr. Radio ratifies a fix direction (this doc is the gate deliverable).

## TL;DR
Inbound peer DMs to a **parked-at-prompt** worker are silently **buffered instead of tmux-waking the
pane** whenever the worker's heartbeat-events file has **no surviving qualifying `outcome` record** —
i.e. `last_emitted_outcome()` returns `None` (only `idle_prompt` beacons, or a truly-fresh session) or
returns `"poked"`. A buffered DM drains only at the next PreToolUse/PostToolUse/Stop tool-boundary **or**
a UserPromptSubmit — none of which a parked pane produces without an external keystroke. So the DM waits
indefinitely until a manual tmux tap or a slow arbiter staleness poke. **This is a residual of baf5ea6d**
(which fixed only the *masking* case, not the *no-outcome-at-all* case).

## The two delivery legs (both fail for a parked no-outcome worker)
1. **Real-time listener** — `cc_notification_listener._handle_event` routes `direction==ai_to_ai` to
   `_deliver_peer_dm` (:282). That calls `_recipient_is_injectable()` (:314): **True → tmux-wake**
   (`_handle_peer_dm`→`_inject_via_tmux`), **False → `_buffer_message`**. The predicate (:404) returns
   `last_emitted_outcome(full_id) in {EVENT_IDLE, OUTCOME_HONORED, OUTCOME_CAP_REACHED}`. `None`/`"poked"`
   → **False → buffer**.
2. **Store-backed reconcile** — `user_prompt_submit.py:123` calls `surface_dm_inbox()` (bug 59f355e0 /
   commit 4cfc9ddc). This is the durable backstop — but it runs **only inside the UserPromptSubmit hook**,
   which a parked pane fires only when a keystroke is injected. No keystroke → no reconcile.

Net: for a parked, no-qualifying-outcome worker, leg 1 buffers and leg 2 never runs → DM stranded.

## Mechanism confirmation
`_recipient_is_injectable()` is an **allowlist of three positive outcomes**. It correctly excludes `poked`
(busy mid-turn) and — per its own docstring — treats `None` as "BUSY/active … buffer cleanly rather than
interrupting", which is right for a **truly fresh booting** session but **wrong for a parked pane that
emitted `idle_prompt` beacons without ever emitting an `idle` OUTCOME**. baf5ea6d taught
`last_emitted_outcome` to skip trailing `idle_prompt` records that *mask* an existing outcome; it did not
address the case where **no qualifying outcome exists at all** → `None` → the same false-BUSY buffer path
baf5ea6d set out to kill. Case C (`poked` then re-parked with no fresh idle emit) is a second parked
sub-state that also strands.

## Recommendation memo — two fix candidates (+ the :7999-outage constraint)

**Constraint (Mr. Radio, 2026-07-02):** any listener-side mechanism must fail gracefully when :7999 is
down (e.g. the container swap at quiesce). Note both candidates are inherently server-coupled for
*delivery*: during a hard :7999 outage NO DM is delivered by any path (WS push and the DB-backed store are
both behind :7999), so nothing can wake for a DM that hasn't arrived. "Fail gracefully" here means the
wake mechanism must not hang/crash the listener when the server is down, and must re-deliver + wake on
reconnect. The listener already has reconnect resilience (`run()` restart loop).

### Candidate A — fix the listener classification (RECOMMENDED as primary)
Broaden `_recipient_is_injectable()` so a **genuinely parked-at-prompt** pane is injectable regardless of
which specific outcome (or none) was last emitted — the acute defect is the narrow 3-outcome allowlist
mis-labelling parked panes as busy. Options: (a) treat a trailing `idle_prompt` beacon as a parked signal
(inject); (b) add a direct tmux pane-idle probe (is the pane sitting at a prompt?) as the injectability
source of truth instead of inferring from heartbeat outcomes.
- **Pros:** smallest blast radius; fixes the confirmed mechanism at its source; local tmux tap (no new
  cross-process/DB coupling); listener already resilient to server-down → satisfies the constraint; fast
  (real-time, the moment the DM arrives).
- **Cons:** still WS-delivery-coupled (can't wake during a hard outage — but nothing can); a pane-idle
  probe adds a tmux call to the delivery path (must be bounded + fail-open, like the existing 2s-timeout
  send-keys).
- **Risk to guard:** do NOT over-broaden into `poked`-while-actually-busy (would inject mid-turn and
  corrupt a running turn). A pane-idle probe (option b) is the safest discriminator because it observes
  the pane's real state rather than inferring from a possibly-stale outcome log.

### Candidate B — extend the poker gateway to tap on undelivered inbound DMs
The arbiter/poker gateway already tmux-taps parked sessions on its poll loop (that's what eventually
rescued Rio after ~80 min). Extend its injectable-recipient logic to also fire on a detected undelivered
peer DM.
- **Pros:** independent of whether the listener saw the WS push (a true backstop); reuses an existing,
  battle-tested tmux-injection path; the arbiter is a separate process (`:8001`) so it survives a `:7999`
  *app* restart.
- **Cons:** SLOW — the arbiter polls on staleness/tap-ACK intervals (~600–2700s), which is exactly why
  Rio waited 80 min; making it DM-aware means adding DM-store polling to the arbiter loop; heavier,
  cross-process, and DB-coupled (the DM store is behind :7999's Postgres → blind during a :7999 outage
  too).

### Cheech's recommendation
**Primary: Candidate A, option (b) — a bounded, fail-open tmux pane-idle probe as the injectability
source of truth**, replacing/augmenting the narrow outcome allowlist. It fixes the confirmed root cause on
the fast real-time path with minimal coupling and satisfies the server-down constraint (local, resilient).
**Keep Candidate B as the existing slow safety-net** (it already partially exists as the staleness poke) —
no new build needed there unless we want to shrink its latency. During a hard :7999 swap, neither path can
deliver a not-yet-arrived DM, so the accompanying **manual tap remains the correct operational workaround
for that bounded, supervised window** — the fix targets steady-state, not the outage window.

## DEPLOY-NOTE (operational)
`cc_notification_listener` is a **long-running host process** (spawned once at SessionStart). A code fix
to `_recipient_is_injectable` takes effect only on **listener restart** — same stale-process class as bug
63c5d913 (confirmed on Tiberius's spawn 2026-07-02). Landing the fix requires restarting the listeners
(or re-spinning the sessions), not merely committing the code. During a hard :7999 outage neither wake
path can deliver a not-yet-arrived DM, so the accompanying manual tap remains the workaround for that
bounded, supervised window.

### Listener restart procedure (fleet rollout — Mr. Radio owns coordination)
The listener is spawned once per session by `register_session.py` (SessionStart) under
`listener_spawn_lock( short_id )`. The REAL argv (confirmed against register_session.py, per Mr. Radio's
crew rollout) is:
`python -m lupin_cli.claude_code.hooks.lib.cc_notification_listener --session-id <hash> [--accepted-ids <hashes>] --log-file ~/.claude/sessions/cc-listener-<hash>.log --centralized-log ~/.claude/sessions/cc-listeners.log`
(`--debug`/`--verbose` are added only when the `LUPIN_CC_HOOK_LISTENER_DEBUG`/`_VERBOSE` env vars are set;
env carries `PYTHONPATH=<root>/src` + `PYTHONUNBUFFERED=1`; Popen is detached via `start_new_session=True`.
There is NO `--buffer-path` in the live form — the buffer path is auto-computed from the session hash.)
A live listener does NOT auto-reload code (only reconnect-exhaustion restarts the WS, same process/code).
So to land `b4e87e8b`:

1. **Enumerate** live listeners: `pgrep -af "cc_notification_listener.*--session-id"` (fleet) or, per
   session, `listener_processes.find_live_listener_pids( <hash> )` (pgrep ground-truth, bridge-independent).
2. **Preferred — re-spin the session** (`dismiss_sessions` + respawn): SessionStart re-runs
   `register_session` → a fresh listener boots on the committed code. Cleanest; also refreshes the bridge.
3. **In-place — live session you don't want to re-spin**: SIGTERM the PID(s) from step 1 (SessionEnd's
   `_find_all_listener_pids` is the same kill set — bridge `listener_pid` + cmdline matches, so no orphan),
   then relaunch the spawn command above under `listener_spawn_lock( <hash> )`.
4. **Verify LIVE**: re-run step 1 — a NEW PID whose process start-time is AFTER the b4e87e8b commit is the
   proof the fix is running (analogous to the `:8001` redeploy `/health` check). The old PID must be gone.

## Post-review advisories (Tiffany cross-review, verdict 9136e754 — non-blocking, fail-safe direction)
1. **Narrow-pane divider assumption.** `IDLE_PROMPT_DIVIDER = "─" × 40` assumes the pane is ≥ 40 columns
   wide. A genuinely-idle but NARROW/resized pane could fail the positive-idle check → buffer → strand
   (rare; the fail-direction is the safe one — buffer, never mis-inject). If it ever bites, lower the
   threshold or key idle on a width-independent chrome marker.
2. **Probe-error-on-parked-pane residual.** A transient `tmux capture-pane` failure while a pane is truly
   parked classifies not-idle → buffer → the DM waits for the next UserPromptSubmit (store reconcile).
   Accepted under the never-corrupt-over-never-strand principle; the buffered DM is recoverable, a
   corrupted running turn is not.

Both are deliberate consequences of the fail-closed-toward-buffer design, not defects.
