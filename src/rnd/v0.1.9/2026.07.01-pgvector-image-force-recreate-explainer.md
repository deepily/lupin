# pgvector Image Force-Recreate — What's Involved (Explainer for Rick)

**Date:** 2026-07-01 · **Author:** Mr. Radio 🦉 · **Gate:** shared-infra greenlight for v0.2.0 Lane A (`b89407b5`)
**Parent design:** [2026.06.30-lancedb-to-postgres-pgvector-migration-design.md](2026.06.30-lancedb-to-postgres-pgvector-migration-design.md) §11

## TL;DR

Swap the local Postgres container's base image from `postgres:16.3-alpine` to `pgvector/pgvector:pg16` and recreate the container **on the same data volume**. Your data is untouched (it lives on a host bind-mount), downtime is roughly a minute, and the change is trivially reversible. This is the one shared-infra prerequisite standing between the reviewed-green P1 code (`e2afdfac`) and the live-PG proof tier.

## Why it's needed at all

The v0.2.0 migration stores 768-dim embeddings in Postgres via the `vector` extension (pgvector). Stock `postgres:16.3-alpine` does **not** ship that extension — `CREATE EXTENSION vector` fails because the compiled library isn't in the image. `pgvector/pgvector:pg16` is the official pgvector project build of Postgres 16 with the extension baked in. There is no way to add the extension to the running container without an image that carries it.

## What actually happens, step by step

1. **Edit one line** in `docker-compose.yml` (line 6): `image: postgres:16.3-alpine` → `image: pgvector/pgvector:pg16`. (Tiffany's held commit `e2afdfac` already contains this diff — it lands with the code, per the co-land rule.)
2. **Pull the image** — a one-time download (Debian-based, a few hundred MB).
3. **`docker compose up -d --force-recreate postgres`** — Docker stops and removes the old `lupin-postgres` container, then creates and starts a new one from the new image, attached to the same network aliases and the same data directory.
4. **Verify** — `SELECT * FROM pg_available_extensions WHERE name='vector'` returns a row; all existing tables and data present.

## Why "force-recreate" and not "restart"

`docker restart` reuses the existing container, which is permanently bound to the OLD image — the image line in compose is only read at container **creation**. This is the exact drift class the `preflight-test-container.sh` check exists to catch (same reason bind-mount changes need rm+up, not restart).

## Is my data safe? (yes)

The database files live on the **host**, outside the container, at
`lupin-data/postgresql-dev-data` (bind-mounted to `/var/lib/postgresql/data`).
Recreating the container replaces the disposable runtime box, not the data directory. Both images are Postgres **major 16**, so the on-disk format is identical — the new image opens the existing cluster as-is. No dump/restore, no migration of data.

## Blast radius

- **Who notices:** anything talking to `lupin-postgres` — the dev server (`:7999`) and test server (`:8000`) — loses DB connectivity for the stop→start window (seconds to ~a minute after the pull). Connections re-establish on their own.
- **When to do it:** with `:8000` idle (nothing scheduled/running) and no queue jobs mid-write. I verify both before executing.
- **What it does NOT touch:** cloud-test / prod use Cloud-SQL, which supports pgvector natively (`CREATE EXTENSION` only) — **no image change there, ever**. This swap is local dev/test compose only.

## Rollback

Revert the one compose line → `docker compose up -d --force-recreate postgres` again → back on stock `16.3-alpine`. Before the alembic migration has been applied there are zero vector objects in the DB, so rollback is a pure image swap. (After migration, rolling back the image would orphan the vector columns — which is exactly why the **co-land rule** exists: models + alembic migration + `pgvector==0.4.2` dep + image land TOGETHER, never separately.)

## Discovered in execution (2026-07-01, post-greenlight) — the collation rider

The swap was executed same-day on Rick's greenlight and surfaced one thing the "data is safe" section above did not predict: **the data was safe, but the text indexes were not.** Alpine images use musl libc; the Debian pgvector image uses glibc — and the two **sort text differently**. Every btree index over a text column, built under musl, is silently out-of-order under glibc. First symptom: task-store writes started failing with `IndexCorrupted` on `ix_task_items_accountable_manager` (reads kept working, which made it look like an app bug). Postgres gave no warning because musl records no collation version to compare against.

**Remedy (applied + verified green):**
1. `REINDEX DATABASE lupin_db_dev` / `lupin_db_test` / `postgres` — rebuilds every index under glibc ordering (~seconds at current data size; queues were verified idle).
2. Recorded `datcollversion='2.36'` in `pg_database` so future glibc upgrades DO warn.
3. Re-ran the failed store write — clean.

**Standing rule this mints:** any libc-crossing image swap on an existing Postgres data dir (alpine↔Debian in either direction) gets an immediate post-recreate `REINDEX DATABASE` on every database in the cluster. The design doc §11 now carries this rider.
