## 0. The one-paragraph problem statement (grounded)

`FcmWakeService` boots **DISABLED** on the cloud-test VM because `firebase_admin` is not importable inside the running container. This is by design (OSQ-7 lazy-import tolerance — `src/cosa/rest/fcm_wake_service.py:192-197`), but it means live wake-pushes never fire. The dependency `firebase-admin>=6.5,<7` is **already pinned** (`pyproject.toml:67`) and **already resolved to 6.9.0 in the lockfile** (`uv.lock:1015-1029`) — both landed in commit `53fef419` (2026-06-19), which is **after** the `lupin:1.1.0` image was built (AR image created 2026-06-11). The running `1.1.0` image therefore predates the lock entry and carries no firebase-admin.

Confirmed verbatim in the M2 doc (`2026.06.10-m2-arbiter-ride-along-and-vm-cutover.md:340`):
> "firebase-admin is absent from the 1.1.0 image but its import is lazy by design (OSQ-7) → FCM register/unregister + fcm_tokens persistence LIVE, wake-sends DISABLED until an image rebuild + service-account JSON."

**Two independent gaps must both close for wake-sends to flow:**
1. **firebase-admin in the image** — a deps-layer rebuild (this runbook §1-§2). The mount model means app *code* rides the on-VM `./src` bind-mount, but `firebase_admin` is a **dependency** baked into the venv, so ONLY a rebuilt image delivers it.
2. **the service-account JSON + env var wiring** — a runtime key file (mounted `:ro`) plus one `environment:` line (this runbook §3). No build input — it's purely a runtime mount, confirmed by `fcm_wake_service.py:183-200` reading the credential from a FILE PATH named by an env var.

## 1. Rebuild steps — bake firebase-admin into a candidate image tag

### Why a rebuild is sufficient (no Dockerfile edit needed)

`docker/lupin/Dockerfile:227-232` installs deps via `uv sync --locked` against the copied `pyproject.toml` + `uv.lock`:
```dockerfile
COPY --chown=rruiz:rruiz pyproject.toml uv.lock ./
RUN --mount=type=cache,... uv sync --locked ...
```
Because firebase-admin 6.9.0 is **already in `uv.lock`**, a fresh `uv sync --locked` resolves and installs it with **zero Dockerfile change**. The fix is "rebuild against the current lockfile," not "add a dependency."

### Tag discipline — DO NOT overwrite `1.1.0`

`1.1.0` is the working, locally-adopted, soaked tag. Per the no-auto-promote rule, **park the rebuild at a candidate tag `1.2.0`** and never tag it `latest`. The AR repo is **immutable-tags** (M2 doc:171) — overwriting is impossible anyway; deletion is the only rollback.

### Reuse `cloud-run-build.sh` as-is (one env override + one interactive answer)

`src/scripts/cloud-run-build.sh` is reusable verbatim:
- `[0/3]` runs `secret-scan-gate.sh .` (hard gate, build aborts on any secret in context) — `cloud-run-build.sh:54-55`.
- `[1/3]` `docker build -f docker/lupin/Dockerfile -t $REGISTRY/$PROJECT_ID/$AR_REPO/$IMAGE_NAME:$VERSION .` — `:63-66`.
- `[2/3]` optional local test prompt (answer **n**) — `:73`.
- `[3/3]` `docker push ...:$VERSION` — `:98`.
- "tag as latest?" prompt at the end (answer **n** — no auto-promote) — `:105-108`.

**Critical gotcha (from M2 doc:167):** the default `AR_REPO` is `lupin` but the real repo is `lupin-images`. You MUST override `LUPIN_GCP_AR_REPO=lupin-images`, else the push targets a non-existent repo.

```bash
# [AI-automatable] — runs on the dev box; build+push are local-docker + outward-to-AR.
#   (The OUTWARD PUSH to AR is the gated part — see §4. The build itself is local & ungated.)
cd /mnt/DATA01/include/www.deepily.ai/projects/lupin
export LUPIN_GCP_PROJECT_ID=hello-world-foo-423219     # from cloud-run-config.sh resolver (fails loud if unset)
export LUPIN_GCP_AR_REPO=lupin-images                  # MUST override; default 'lupin' is wrong (M2:167)
gcloud auth configure-docker us-central1-docker.pkg.dev # one-time docker→AR auth
./src/scripts/cloud-run-build.sh 1.2.0                 # secret-scan → build → push 1.2.0; answer 'n' to local-test, 'n' to tag-as-latest
```

Resulting image: `us-central1-docker.pkg.dev/hello-world-foo-423219/lupin-images/lupin:1.2.0`

**Verify the push:**
```bash
gcloud artifacts docker images list \
  us-central1-docker.pkg.dev/hello-world-foo-423219/lupin-images/lupin --include-tags | grep 1.2.0
```
**Rollback (immutable repo → delete, never overwrite):**
```bash
gcloud artifacts docker images delete \
  us-central1-docker.pkg.dev/hello-world-foo-423219/lupin-images/lupin:1.2.0
```

> **Build-time note:** the prior `1.1.0` AR build was 18.4 GB and layer-cached off the same Dockerfile; the firebase-admin delta is one extra wheel in the already-cached `uv sync` layer, so the rebuild is **cache-warm** — expect a short build dominated by the push of changed layers, not a from-scratch ~20-min build (unless the cache is cold).

## 2. Redeploy-to-VM steps — pull the new image + recreate the container

### Why `pull` + `up --force-recreate`, NOT `docker restart`

The cloud-test compose pins `image: ${LUPIN_IMAGE:-lupin:1.1.0}` (`docker-compose.cloud-test.yml:73`). The VM must (a) **pull** the new tag and (b) **recreate** the container off it. `docker restart` re-runs the SAME container off the SAME image — it will NOT pick up a new image (mirrors the local "recreate, not restart, for image change" rule, M2 doc:274,278). The mount-model gotcha — "only `docker rm -f` + up picks up new mounts/images, not `docker restart`" — applies here for the image axis too.

**On the VM** (the running user has passwordless sudo + docker group; repo at `/mnt/lupin-data/lupin`):
```bash
# [needs-Rick-GCP-go] — pull from AR + container recreate on the live VM are GCP infra actions.
gcloud compute ssh lupin-host-test --zone=us-central1-a --tunnel-through-iap   # interactive, or --command='...'

# ON THE VM:
export LUPIN_ROOT=/mnt/lupin-data/lupin
cd "$LUPIN_ROOT"

# 1) Point the compose at the candidate tag (cloud-test.env is mode-600, git-ignored).
#    Append/replace the LUPIN_IMAGE line:
#      LUPIN_IMAGE=us-central1-docker.pkg.dev/hello-world-foo-423219/lupin-images/lupin:1.2.0
#    (compose default is bare lupin:1.1.0 — the env file overrides it; M2:16)

# 2) Pull the new image (VM authenticates to AR via vm_sa metadata creds; M2:316)
docker compose -f docker-compose.cloud-test.yml --env-file cloud-test.env pull lupin-rest

# 3) Recreate ONLY the rest container off the new image (--force-recreate guarantees a fresh
#    container even if compose thinks config is unchanged; proxy + model-server untouched)
docker compose -f docker-compose.cloud-test.yml --env-file cloud-test.env up -d --force-recreate lupin-rest
```

> **`--force-recreate` rationale:** when only the env-file `LUPIN_IMAGE` value changes, `up -d` recreates because the resolved image ref differs. `--force-recreate` is belt-and-suspenders to defeat any "config unchanged" short-circuit, and is the correct verb when the §3 `environment:` add also lands in the same recreate (compose recreates on environment-block change). **`docker restart` would silently no-op both the new image AND the new env var.**

**Verify the container is on the new image:**
```bash
docker inspect lupin-rest-cloud-test --format '{{.Config.Image}}'    # → ...lupin:1.2.0
docker exec lupin-rest-cloud-test python3 -c "import firebase_admin; print(firebase_admin.__version__)"   # → 6.9.0
```
**Rollback:** set `LUPIN_IMAGE=...lupin:1.1.0` in `cloud-test.env` + `up -d --force-recreate lupin-rest`.

## 3. FCM wiring delta — one env var + one key file

Two runtime artifacts, neither a build input:

### 3a. The env var (one `environment:` line in the cloud-test compose)

`FcmWakeService` reads the credentials-file path from the env var named by INI key
`fcm service account credentials env var = FCM_SERVICE_ACCOUNT_JSON` (`src/conf/lupin-app.ini:1016`),
defaulting to `FCM_SERVICE_ACCOUNT_JSON` (`fcm_wake_service.py:131`). The compose file does **not** currently set it. Add ONE line to the `lupin-rest` service `environment:` block in `docker-compose.cloud-test.yml` (alongside the existing `LUPIN_API_KEY_FILE` etc. at lines 103-110):

```yaml
    environment:
      ...
      FCM_SERVICE_ACCOUNT_JSON: /var/lupin/src/conf/keys/firebase-admin-key.json
```

### 3b. The in-container path is the EXISTING `:ro` keys mount

The keys directory is already mounted read-only:
`./src/conf/keys:/var/lupin/src/conf/keys:ro` (`docker-compose.cloud-test.yml:87`), with `LUPIN_ROOT=/var/lupin`. So a file dropped at the on-VM host path
`/mnt/lupin-data/lupin/src/conf/keys/firebase-admin-key.json`
appears in-container at
`/var/lupin/src/conf/keys/firebase-admin-key.json` — exactly the env-var value above. **No new mount is needed; the key rides the existing keys mount.**

### 3c. Dropping the key file (same UID-1001 gotcha as the 10 provider keys)

The dest dir is **UID-1001-owned**, so SCP-direct fails (`Permission denied`). Stage in `/tmp`, then `sudo cp` + `chown 1001:1001` — identical to the provider-keys procedure (new-deployer runbook §1, lines 48-63):
```bash
# [needs-Rick-GCP-go] — writing to the VM filesystem.
# From the dev box (key file source TBD — generated in the Firebase console by Rick):
gcloud compute scp /path/to/firebase-admin-key.json \
  lupin-host-test:/tmp/ --zone=us-central1-a --tunnel-through-iap
# ON THE VM:
sudo cp /tmp/firebase-admin-key.json /mnt/lupin-data/lupin/src/conf/keys/ \
  && sudo chown 1001:1001 /mnt/lupin-data/lupin/src/conf/keys/firebase-admin-key.json \
  && rm /tmp/firebase-admin-key.json
```

> **Secret-scan-gate interaction (IMPORTANT):** `src/conf/keys/` is `.dockerignore`'d and excluded from the build context (`Dockerfile:307-309`), so the key file CANNOT leak into the image. But `cloud-run-build.sh` runs `secret-scan-gate.sh .` over the build context — confirm the firebase key lands ONLY under `src/conf/keys/` (gate-excluded), never elsewhere in the tree, or the §1 rebuild aborts. The key is a **VM-side runtime drop**, fully decoupled from the image build.

### 3d. Ordering

The env var add (§3a) lands in `cloud-test.env`/compose and takes effect on the **same §2 `--force-recreate`** that pulls the new image — do §3a + §3c BEFORE the §2 recreate so one recreate delivers image + env + key together. (The key file, being a mount, is re-read at process start — the recreate picks it up.)

## 6. How this generalizes to `d8c699aa` (GCP code-sync-to-runtime)

`d8c699aa` asks: how does code/deps reach the running cloud container? The cloud-test deploy has **two distinct axes**, and this runbook is the canonical worked example of one of them:

| Axis | Mechanism | Update verb | This runbook |
|---|---|---|---|
| **App code** (`src/...`) | host **bind-mount** `./src → /var/lupin/src` (compose:85; mount model, runbook:11) | update on-VM git checkout + `docker restart` (FastAPI `reload=False` in cloud) | NOT used here — firebase-admin is a dep, not app code |
| **Dependencies / runtime** (venv, system libs, CLIs) | **baked into the image** via `uv sync --locked` (Dockerfile:227-232) | **rebuild image → push to AR → pull on VM → `up --force-recreate`** | **THIS runbook (§1-§2) — the deps-axis worked example** |

**The d8c699aa tradeoff, made concrete by this case:**
- **Bind-mount (Option A)** — app code changes are cheap (git pull + restart), but it **cannot deliver a new Python dependency**: `firebase_admin` lives in the image's venv, not under `./src`. This is exactly why FCM stayed disabled despite the S6 *code* being live on the VM via the mount (M2:340).
- **Baked image (Option B)** — the only path for deps/runtime changes; heavier (rebuild + 18 GB push + pull + recreate) but the sole mechanism that moves the venv. This runbook is the reference procedure.

**Generalization for `d8c699aa`:** classify every "sync to runtime" need as **code-axis** (→ bind-mount refresh, lightweight) or **deps/runtime-axis** (→ image rebuild+redeploy, this runbook's §1-§2 template). A change that touches `pyproject.toml`/`uv.lock`/system apt/baked CLIs is **always Option B** and inherits this exact rebuild→push→pull→`--force-recreate` sequence and the same Rick-GCP gates (§4). The forcing insight: **a bind-mount can never carry a dependency** — that single fact is what makes firebase-admin the clean exemplar for the deps-axis half of the code-sync question.
