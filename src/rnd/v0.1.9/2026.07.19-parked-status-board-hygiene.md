Three consequences, in ascending severity:

1. **The burn-down number is fiction.** A board reporting "79 queued" is reporting a

2. **Some rows can never close by being done.** `19b3f653` carries a *standing*

   `86c1bb85` is a *record of a measurement*; auditing it would destroy the deliverable.

3. **The owed-work oracles count them.** Un-actionable rows generate **false pokes** —
   the root cause of the symptom silenced by flag in commit `09c3fcc0` (arbiter
   audience-scoped poke gates). That commit treated the symptom. This treats the cause.

### 1.1 The store cannot express the true state

Under today's schema a deliberately-held row has two honest-looking homes, and **both lie**:

| Candidate | The lie it tells |
|---|---|
| `queued` | "This is workable right now." It is not — a human ruled otherwise. |
| `blocked` | "Something is blocking it." Nothing is. Rick/Sam **approved** it and chose *later*. |
| `dropped` | "This is abandoned." It is not — it is expected back. |

The record for this very change (`954428b3`) is itself in that class — approved by Rick,
explicitly sequenced behind another item — and was filed `queued` with the hold in its
body. **The proposal's own tracking row is an instance of the defect it fixes.**

## 2. The Approved Change

Add **`parked`** to the status enum. `queued` then means, honestly, *"actually workable now."*

| Element | Rule |
|---|---|
| `park_reason` | **REQUIRED** on park. Free text. MUST quote the row's own decisive sentence. |
| `next_chase_ts` | **REQUIRED** on park. **Reuses the existing field** — no new date column. |
| Expiry | **Computed at READ time.** A parked row whose `next_chase_ts` has PASSED is *not parked* — it rejoins the owed count automatically. |
| Visibility | `task_query` hides park-active rows by default; `status="parked"` or `unscoped_audit=True` surfaces them. |
| Readers | Stop-hook oracle, `:8001` arbiter, and `task_query` apply the **same** park-suppression clause. |
| Indefinite hold | **NOT** parked. That is `dropped` with a reason — because dropping is *visible*. |

### 2.1 The strongest argument for reusing `next_chase_ts`

`blocked` **already** requires it. `validate_transition` enforces
`to_status == "blocked" => next_chase_ts is present` (`task_store_rules.py:623`, "I3 — no
'pending X' graves"), and a DB `CheckConstraint` backs it at
`postgres_models.py:1405`. `query_chase_due` already implements "chase has come due" in
SQL (`task_repository.py:341`).

Reuse is therefore not a convenience — it is **the established precedent for exactly this
shape of rule**, already enforced at two layers with a working SQL reader. Park gets the
parallel rule and a parallel CHECK.

> **Correction propagated (Mr. Radio 🦉, self-corrected on Rachel 🕊️'s challenge):** the
> brief that seeded this crew said "`next_chase_ts` verified present on 85/85 rows."
> That is **false as written**. The **column** is universal; the **value** is null on
> every queued row and non-null only on the ~12 blocked ones — i.e. it is currently set
> only where a CHECK already demands it. The precedent argument above survives the
> correction; the "85/85" phrasing does not. Do not repeat it.

### 2.2 Parking buys bounded, self-expiring silence — never an exit

This is the load-bearing property. A park is not a way off the board; it is a way to be
quiet **until a date you named**. There is:

- **no daemon**, **no sweeper**, **no cron**, **no human action** required to un-park;
- **no way to park forever** — `next_chase_ts` is required, and any timestamp eventually passes.

Enforced by *arithmetic on read*, which cannot be forgotten, cannot silently fail, and
cannot drift. A sweeper that stops running leaves rows parked forever; a computed
predicate that stops running returns no rows at all — a **loud** failure, not a silent one.

## 3. Design Rationale — and Two Overturned Rulings

Both rulings recorded here were **overturned by evidence on the same day they were made**.
That pattern is itself the lesson of this section, recorded deliberately rather than tidied away.

### 3.1 María 🌸 — Q1: why a *status*, and not a new `blocked_by` kind

**Her question:** the readiness predicate already reads `blocked_by`. Why not express the
hold there — add a `kind` meaning "a human ruled this not-now" — instead of widening the
status enum?

**Her answer, which decides it:** the `blocked_by` kinds in live use are
`item` / `persona` / `user` (`task_store_rules.py:46`). **There is no kind meaning "a human
ruled this not-now."** The hold is **unrepresentable in the field the readiness predicate
actually reads.**

The two available moves are not symmetric:

- **A status value is the honest widening.** It adds a state the vocabulary genuinely
  lacked, and every reader that enumerates statuses is *forced* to confront it.
- **A "ruling" kind would lie.** `blocked_by` is a list of *things being waited on*. A
  deliberate hold waits on nothing — Rick already said yes. Worse, it would make
  `blocked_by=[]` mean two different things depending on a value elsewhere in the row,
  destroying the one field whose emptiness the oracle trusts.

**Credit — Sam's framing:** this is the distinction between an **in-vocabulary** and an
**out-of-vocabulary** state. An in-vocabulary state can be expressed with the words the
schema already has; an out-of-vocabulary one cannot, and stuffing it into an existing field
produces a field that no longer means what its name says. `parked` is out-of-vocabulary.
It gets a word.

### 3.2 Rick — the amendment: a review ruling ADDED a field the store already had

The reviewed proposal required **two** new fields on park: `park_reason` **and**
`unpark_when` (a date or named event). Rick overruled the second:

> parking *"doesn't need an unpack-when field, it needs a chase, which already exists."*

He is right, and §2.1 is the evidence. `unpark_when` would not have been a new capability —
it would have been a **second, divergent date field** competing with a mature one, a fresh
source of the exact three-readers-disagree bug this change exists to kill.

**Standing rule going forward:** anyone proposing a new date field on the task store must
**first explain why `next_chase_ts` is insufficient.**

#### 3.2.1 The correction is itself the lesson

A **review** — the step whose job is to catch exactly this — **added a field the store
already had.** Reviewer and author both knew the store well. Neither checked whether the
capability existed before specifying it.

Naming the failure precisely: a design review optimizes for *"is the proposed thing
correct?"* and answers it locally. It does not naturally ask *"is the proposed thing
already present under another name?"* — that question has no local answer; it requires
sweeping the schema. Both rulings overturned today (this one, and the 42%→19% marker
miscount in §5) failed the same way: **a conclusion defended on its own terms, never
checked against the artifact it described.**

This is why §5 mandates writing the marker predicate down as an artifact. A predicate you
can hand to the next seat can be **refuted row-by-row**. A predicate you keep in your head
gets re-derived, and re-derivation is where the count moves.

### 3.3 `park_reason`: a real column, not the transition `reason`

**Considered and rejected:** reuse the existing transition `reason` field, which
`validate_transition` already accepts and which lands on the append-only `TaskEvent` trail.

**Why it is insufficient** (applying §3.2's own standing rule to myself): `reason` is
stored on the **event**, not the **item**. A parked row is hidden by default; the entire
point of surfacing one is to read *why*. With `reason` on the event trail, rendering N
parked rows costs **N event-trail fetches** — and the terse projection, the token-efficient
path every board glance uses, cannot carry it at all.

`park_reason` is text, not a date, so it does not collide with Rick's amendment; that ruling
was specifically about a redundant **date** field where a chase already existed. There is no
existing read-time text field. **Approved by Mr. Radio 🦉** (informing Rick, not asking).

## 4. The Owed Definition — one home, ONE-CALL admission

### 4.1 Home: a NEW module, not `task_store_rules.py`

**Ruled by Mr. Radio 🦉 on Krishna 🦚's catch.** My first draft put the predicate in
`task_store_rules.py`. That module's docstring declares itself **pure**, verbatim: *"Every
function is pure (no DB, no HTTP)"*. A SQLAlchemy twin breaks that contract, and **a module
whose docstring lies is how the next reader gets misled.**

⇒ **`src/cosa/rest/task_store_owed.py`** — new module. Holds `PARK_STATUS`,
`park_is_active()`, `is_owed()`, and the SQLAlchemy twin, adjacent, one home. It **imports**
`VALID_STATUSES` / `TERMINAL_STATUSES` from `task_store_rules`. `rules.py` keeps its purity
contract intact and untouched.

Named `_owed`, not `_parked`: it owns the **owed** definition, of which parked-ness is one term.

```python

def park_is_active( status, next_chase_ts, now=None ) -> bool:
    """True iff the row is parked AND its chase has not yet come due."""

def is_owed( status, next_chase_ts, now=None ) -> bool:
    """The honest GENERAL owed predicate. See §4.2 — this is NOT what R2 adopts in this pass."""
    # == status not in TERMINAL_STATUSES and not park_is_active( status, next_chase_ts, now )
```

- `now=None` → `datetime.now( timezone.utc )`.
- `next_chase_ts` accepts an ISO-8601 `str` **or** a `datetime`; tz-naive is read as UTC.

### 4.2 🔴 SCOPE — the owed set is pinned; only parked rows move

> **⚠️ RETRACTED RULING RECORDED BELOW.** This section first specified *additive*
> suppression. It was refuted and replaced by the one-call admission. The retraction is kept
> in full, not deleted, because **how** it was wrong is the most instructive thing in this
> document. The binding shape is the second sub-heading.

**Ruled by Mr. Radio 🦉, raised by Rachel 🕊️ against my draft. This is the ruling that
changed the plan.**

My `is_owed()` — "not terminal and not park-active" — is the **whole** owed definition.
Adopting it wholesale would change what the Stop hook counts: it enumerates
`("queued","in_progress")` today, and would begin counting `blocked` / `claimed` / `review`
rows as owed. **That is a behavior change on demo eve, for a defect Rick did not order fixed.**

#### The first fix was wrong, and the way it was wrong is worth recording

The initial ruling was **additive**: *"`owed_only=True` applies park-suppression ON TOP of
whatever status filter the caller already passes."* **It cannot express what it orders.**
Krishna 🦚 refuted it with a three-line trace:

```
status=queued                          -> the Stop hook counts it          ✓
park it (status=parked, chase FUTURE)  -> matches neither queued nor
                                          in_progress -> not counted       ✓ (desired)
the chase PASSES (status=parked, PAST) -> STILL matches neither
                                       -> STILL NOT COUNTED                ✗ THE BUG
```

Park-suppression is **subtractive**: it can only *remove* rows from a set. An expired parked
row was never **in** the Stop hook's set, because parking **moved its status out of
`queued`**. Subtracting nothing from a set that already excludes the row leaves it excluded
forever — and the rejoin is the single most important behavior in this design.

**§4.4 below diagnoses exactly this trap, and the additive rule was the thing it prescribed.**
The author of the diagnosis and the author of the prescription were the same seat, in the
same document. Naming the failure precisely: the diagnosis was written about *the reader*,
the prescription about *the query* — and nobody traced one row through both.

A second, independent defect kills additive outright: `query_owed`
(`task_store_client.py`) **LOOPS the status tuple and SUMS** the per-status counts.
Per-status admission would count every expired-parked row **TWICE** — parking a row would
make the board look **BUSIER** than never parking it, inverting the feature.

#### The binding shape: `owed_only` defines the set in ONE call

```
owed_only=True, status=None  ->  queued ∪ in_progress ∪ (parked AND NOT park-active)
```

**This is not the widening §4.2 rejects.** That widening was `owed_only` meaning "all
non-terminal", which drags in `blocked`/`claimed`/`review`. This is pinned to exactly today's
two statuses **plus a restored set that is provably a subset of those same two** — because
park is legal **only** from `("queued","in_progress")` (§6). Nothing new is admitted; **AC11
is satisfied, not breached.**

One call, not a per-status loop, is also the only shape in which `"parked"` appears in **no
caller's status tuple** — so the flag and the status set cannot drift apart later.

**Rejected alternative:** a `parked_from_status` column to record where a row came from.
Rick overruled that exact shape today — *a new field where a rule suffices*. The write-time
legality rule gives the same guarantee with nothing to keep in sync.

`is_owed()` still exists as the honest general predicate — it is the right long-term shape —
but **no reader adopts it wholesale in this pass.**

### 4.3 Constant centralization — YES, semantics unification — NO

The constants defining "owed" are hardcoded in **four** places: `stop.py:1358`,
`task_store_drain.py:68`, `arbiter_job.py:259`, `task_store_rules.py:37`. Folding them onto
one definition is a **de-duplication with no behavior change**. Do it.

What must **not** happen: unifying the differing owed **semantics** behind that de-dup.
Same constants; **each reader's current status set preserved.**

**Pre-existing divergence, found by Rachel 🕊️, NOT fixed here:** a `blocked` row is owed to
the arbiter and the store, but **not** owed to the Stop hook. That is a real three-way
disagreement and it predates this change. **Rachel files it as its own P1 row.** Fixing it
inside this pass would smuggle an unordered behavior change past the demo.

### 4.4 Reader wiring (seat 2 — Krishna 🦚)

| Reader | Today | After |
|---|---|---|
| `task_query` | filters by status in SQL | ANDs `owed_clause` (park-suppression); `status="parked"` / `unscoped_audit=True` surfaces |
| Stop-hook owed oracle | `STORE_OWED_STATUSES = ("queued","in_progress")`, server-side `count_only` **per status** (`task_store_client.py`) | **ONE** call on `owed_status_clause` — the per-status loop is what would double-count |
| `:8001` arbiter | `_default_owed_work_fn`, `status not in ("done","dropped")` (`arbiter_job.py:234`) | same set, **minus park-active** (`owed_clause`) |

**`STORE_OWED_STATUSES` is DELETED, not re-pointed** — at both `stop.py` and
`task_store_drain.py`. A constant that no longer exists cannot drift. (Sequencing note: the
constant died before its consumers, which red-lit unit *collection* until the tests caught
up — see §7.1.)

**The non-obvious one is the Stop hook.** It holds no local predicate — it asks the server
for counts, one per status. A parked row has `status="parked"`, so a `status=queued` count
excludes it *for free* while park-active. But an **expired** parked row **still has
`status="parked"` in the database** — expiry is computed, never written back. A
status-enumerating count therefore **misses the rejoin**, which is the single most important
behavior in this design. Seat 2's work here is a seam change, not a filter tweak.

### 4.5 The SQL twin — ruled, build it

"NO second implementation" collides with SQL: `task_query` and `count_only` filter in
Postgres **before** `LIMIT`/`OFFSET`, so a Python-only predicate would filter *after* `LIMIT`
(wrong results) or pull the whole board (defeating the unscoped guard at
`UNSCOPED_QUERY_THRESHOLD = 50`).

**Ruled**: two **co-derived** expressions — Python canonical plus SQLAlchemy twin — in one
module, adjacent, bound by a **MANDATORY parity test that fails the build on divergence**.
The Python-only-with-board-ceiling alternative is **rejected**.

> — **26 park-eligible, plus 5 blocked-in-prose rows that must NOT park.** This section
> contributes the *predicate* and its negative control; it deliberately asserts **no
> number**. Cite her artifact.

### 5.1 The predicate

A row is a **park candidate** iff its **body** contains a sentence that is *all three* of:

1. **IMPERATIVE, addressed to a worker** — "DO NOT BUILD", "NOT TO BE WORKED",
   "STAYS QUEUED", "do NOT graduate", "do NOT audit", "DO NOT WIRE", "HELD BY".
2. **ROW-LEVEL in scope** — governs *this row's* disposition, not one step inside it.
3. **ATTRIBUTED to a person or a ruling** — "Rick", "Sam ruled", "per … direct instruction",
   "on … explicit ruling", "DELIBERATE".

### 5.2 The discriminator, and why the 42% count was wrong

Condition **3 (attribution)** separates a genuine hold from emphasis. The earlier 42% count
matched the "⛔" glyph, and **19 of 31 hits were ⛔ used as emphasis inside an otherwise-
actionable row** — a warning about *how* to do the work, not an instruction *not to*.
Emphasis is unattributed by nature; a ruling names its author, because a ruling is somebody's
decision and the row records whose.

### 5.3 The negative control

Applied to the candidate set I pulled (bodies via `GET /api/tasks/{id}`, 2026-07-19), one row
did **not** match: `e2f11f6f`. That is a **positive** result. It is `owner_persona="rick"` —
an operator decision sitting in Rick's own queue. It is not held *by* a ruling; it *awaits*
one. Different class, different remedy: the operator-gate lane, not parked. **A predicate
that flagged it would be over-broad**, and its non-match is the closest thing to a negative
control this artifact has.

### 5.4 Handoff to seat 3 (Rachel 🕊️)

Seat 3 **drafts** the triage; **Mr. Radio and Rick approve before any row is touched.** Every
park decision must **quote the row's own decisive sentence** into `park_reason` — not
paraphrase it. The quotes in §1 are the format.

Rows I flag as requiring a judgment call rather than a mechanical park:

## 6. Schema Changes

**Enum** (`task_store_rules.py:36`) — **seven** values today, not the five commonly cited;
`parked` makes **eight**:

```
queued | claimed | in_progress | blocked | review | parked | done | dropped
```

`parked` is **non-terminal**, so `LEGAL_TRANSITIONS` (derived, never hand-listed) grants it
edges to and from every other non-terminal state automatically.

**Column** — `task_items.park_reason`, `TEXT`, nullable (rows never parked have none).

**Validation** — `validate_transition`, mirroring the existing `->blocked` rules exactly:

```
to_status == "parked"  =>  next_chase_ts is present       (reuses I3)
                       AND park_reason is a non-blank str (new)
```

**DB constraints** — parallel to `ck_task_items_blocked_requires_chase_ts`. Rachel 🕊️
requires these explicitly: **without them her rejection tests have no teeth below Pydantic.**

```sql
status != 'parked' OR next_chase_ts IS NOT NULL   -- ck_task_items_parked_requires_chase_ts
status != 'parked' OR park_reason  IS NOT NULL    -- ck_task_items_parked_requires_reason
```

Two separate CHECKs, not one conjunction — so a violation names *which* field is missing.

**Migration** — new Alembic revision, `down_revision = 'f2a3b4c5d6e7'` (current head). Adds
the column + both CHECKs. No data re-stamp: no row is `parked` before this lands.

## 7. Acceptance Criteria

Coverage is the Lupin hard gate: **100% lines / branches / functions**. Every guard must be
verified **RED against a mutant** before it is trusted — a green that cannot go red is not a
green, and this fleet shipped exactly that defect twice this week.

| # | Criterion |
|---|---|
| AC1 | `parked` is a valid non-terminal status; legal transitions derive automatically |
| AC2 | Park **without** `park_reason` is REJECTED (422) |
| AC3 | Park **without** `next_chase_ts` is REJECTED (422) — the reused I3 rule |
| AC4 | A park-active row is **INVISIBLE** to a default `task_query` |
| AC5 | The same row is **VISIBLE** to `status="parked"` and to `unscoped_audit=True` |
| AC6 | A parked row whose `next_chase_ts` has **PASSED REJOINS** the owed count — no daemon, no write-back. 🔴 **UNIT-GREEN ONLY — see §7.4. Requires a live `:8000` run; NO ROW GETS PARKED UNTIL THIS IS LIVE-GREEN** (Mr. Radio 🦉 owns scheduling it) |
| AC7 | All **three** readers agree on the same row, at the same instant, for both active and expired cases |
| AC8 | Both DB CHECK constraints reject a hand-written `parked` row lacking either field |
| AC9 | A `parked` row with `next_chase_ts=None` is treated as **owed** (fail-loud-toward-owed) |

| AC11 | **No-drift**: each reader's owed set is exactly today's set MINUS park-active rows — `blocked`/`claimed`/`review` membership is UNCHANGED for every reader (§4.2) |

AC11 is the regression guard on the scope ruling. It is the one an over-eager refactor breaks.

### 7.1 The verification floor is NOT `py_compile` — standing rule for this crew

**Ordered by Mr. Radio 🦉, 2026-07-19, after this build produced the failure twice.**

`task_repository.py` imported `OWED_BASE_STATUSES` from `task_store_owed` before that symbol
existed. **`py_compile` passed on every individual file** — and `py_compile` is the CLAUDE.md
post-edit floor. The break surfaced only when the `:7999` auto-reload imported the pair
together, and it **took the dev server down fleet-wide** for roughly ten minutes, which is
also why peer DMs were timing out.

The same class recurred immediately: `STORE_OWED_STATUSES` was correctly deleted, but ahead
of its consumers, red-lighting unit **collection** in two test modules.

Both are **cross-seat symbol breaks**. Neither is visible to a per-file compile check,
because each file is individually valid — the defect lives in the *seam between* them, and a
compile check never crosses the seam.

⇒ **STANDING RULE: after any edit that adds, removes, or renames an exported symbol, run**

```bash
PYTHONPATH=src python -m pytest src/tests/unit/ --collect-only -q
```

**before reporting.** Collection imports every module across every seam without executing a
single test — seconds to run, and it is the cheapest instrument that would have caught both
the outage and the red tree.

**Corollary on reporting:** a green scoped to your own files is not a green. "381 passed" and
"collection interrupted" cannot both be the headline; the number that goes to the user is the
one from a run that **completes**. Flagging a breakage and then reporting a number that
excludes it is reporting *around* it.

| Test | My defect |
|---|---|
| `test_alembic_baseline_chain::test_absorbed_revisions_are_gone` | My migration id `a3b4c5d6e7f8` was **already the id of a real, different migration** — `expand_job_id_column_to_64_chars`, since absorbed into the baseline (its `.pyc` is still in `versions/__pycache__`). I picked it by pattern-continuing the hex sequence of the neighbouring filenames, which walks **straight into the absorbed range**. Two migrations under one revision id would make the chain ambiguous to anyone reading or bisecting history. Renamed `c1a7f0e2b9d4`. |
| `test_migration_reheal_project_aliases` (×3) | I added `park_reason` to the ORM but not to the **portable-DDL fixture** that mirrors it. The guard exists precisely to catch ORM/DDL drift, and caught mine. |

Both guards worked exactly as designed. The failure mode was not the code — it was that the
six *obviously* foreign failures made the whole set look foreign. **A plausible owner for
most of a failure set is the most efficient way to stop reading it.**

This is the third instance in one build of the §3.2.1 shape: *a conclusion defended on its
own terms, never checked against the artifact it describes.* First the review that added a
field the store already had; then the diagnosis whose own prescription couldn't reach it;
then this. The rule that falls out: **run the failing test yourself before naming its
owner** — attribution is a claim, and a claim about someone else's work is the one that
costs most when wrong.

### 7.3 Stale runs are real — and "it was stale" needs a control

Krishna 🦚 established, correctly, that with three seats writing concurrently **a suite
result is only evidence about the tree as it existed when the run STARTED.** A four-minute
run on a tree three people are editing is a photograph of something that no longer exists.
He was bitten twice: a run reporting failures in tests whose *names* no longer existed
(rewritten mid-run), and another reporting failures that a settled re-run cleared.

**The rule needs a control, or it becomes the most efficient way to launder a real defect.**
"It was probably stale" explains a red away with a mechanism that requires no fix — and it
is *unfalsifiable* unless the re-run is on **unchanged files**.

That failure happened here immediately. The four §7.2 failures were read as stale-run
artifacts of a migration landing mid-run. They were not. They went green because they were
**fixed**. Proof, on the settled tree, removing only the one-line fixture change and
restoring it:

```
WITHOUT the fixture fix (settled tree):  3 failed, 2 passed
WITH    the fixture fix (settled tree):  5 passed
```

⇒ **A stale-run claim is proven only by a re-run in which you changed nothing.** Green after
someone edited two files is evidence of a fix, not of staleness. This is the same discipline
as the negative control in §7.4 — the claim and its control must arrive together, or the
claim is decoration.

> **⚠️ NOT "find is broken."** The defect is `-newermt` with a **RELATIVE** string, which
> silently resolves to a reference instant matching nothing — a no-match byte-identical to a
> clean tree. The **absolute / epoch** form is sound and proves itself *by returning rows*
> (it returned 2 here, and 27 in the manager's own check). Recording "find is unreliable"
> would make the next seat discard a working tool for a reason that isn't true. The md5
> manifest is preferred only because its control is **intrinsic** — the diff *is* the
> control — not because `find` is defective. *(Ruling amended by Mr. Radio 🦉 on this
> correction.)*
>
> **And no instrument is exempt, including the replacement.** Three seats shipped three
> instruments with the same disease in one afternoon: a `find` matching nothing, a manifest
> covering five files while licensing a whole-tree claim, and — below — a manifest that is
> 94% `.venv`. The fix is never "use the better tool"; it is **prove the tool can fail before
> you trust its silence.**

**The positive half of the rule, and the discriminator — Krishna 🦚.** The above says what
does *not* prove staleness. His legitimate case supplies what *does*: those failures **named
tests that do not exist on the settled tree**, and *a test that cannot exist cannot be a live
defect* — checkable independently of anyone's edits. He had that evidence in one case, none
in the other, and asserted the same conclusion in both. In his words: *"the story fit, so I
stopped looking."*

| Claim | Admissible only with |
|---|---|
| "That red was stale" | the changed-file list between the two runs, shown **not** to include the files under test — **or** the failing tests provably absent from the settled tree |
| "That green is real" | the same check, applied to your **own** result |

**STANDING RULE (Mr. Radio 🦉, crew-wide):** nobody may attribute a red to staleness without
naming the files that changed between the two runs and showing they do not include the ones
under test. **Absent that, a red is a defect until run to ground.**

#### The rule is hardest to apply to your own green

Applied here, immediately and against this author: a full run came back **9811 passed, 0
failed** and was about to be reported. The changed-file check on its own window found

```
run window 13:49:14 -> 13:52:57
modified AFTER run start:
  src/tests/unit/test_task_store_parked_parity.py          (seat 3, mid-run)
  src/tests/unit/test_migration_reheal_project_aliases.py  (this author's own mutation-restore)
```

— including a file perturbed by the very experiment being used to prove a point about
perturbation. That number was **not** evidence about the settled tree and was not reported.

**A green gets less scrutiny than a red for no reason other than that it is convenient.**
A clean result supplies no prompt to go looking, which is precisely when the check has to be
a habit rather than a response.

#### The attestation that shipped

Final run, manifest-bracketed, **positive control first** (plant a canary `.py` → assert the
diff is non-empty → remove it; abort before `pytest` if the manifest cannot see it):

```
CONTROL PASSED: manifest detects a planted file (diff was non-empty)   [32,043 files]
RUN 13:57:43 -> 14:09:17
RESULT  9821 passed, 3 xfailed, 0 failed   (pytest exit 0)
ATTESTATION  NOT SETTLED — changed during the run:
   src/tests/unit/test_arbiter_l1_store_aware.py
```

**Reported as NOT-settled, not as green.** One peer-owned test file moved mid-run; it was
re-verified independently on settled disk (**74 passed**). The number stands, with the
qualifier attached — which is the entire point of §7.3.

**Caveat on this instrument, disclosed rather than buried:** 30,106 of the 32,043 manifest
files are `.venv` (`src/cosa/.venv` alone is 29,303) — 94% noise. It biases toward a **false
NOT-SETTLED**, never a false SETTLED, so a SETTLED verdict from it is *stronger* than needed
and a NOT-SETTLED needs triage for venv churn. Nobody should inherit the number without it.

### 7.4 A 200 is not a verdict: the negative control that made the live probe mean something

Krishna verified `owed_only` end-to-end against `:7999` read-only. The essential part was not
the count — it was the **control**. FastAPI silently **ignores unknown query parameters**, so
a plausible-looking count proves nothing on its own:

| Query | Rows |
|---|---|
| no flag (all non-terminal) | 22 |
| `owed_only=true` | **10** |
| **BOGUS unknown param** | **22** ← the control: unknown params ARE ignored |
| `status=blocked` | 12 |
| `status=queued` / `in_progress` | 10 / 0 |

An ignored parameter returns 22; `owed_only` returns 10; `owed_only == queued + in_progress`
and excludes all 12 blocked rows. **The control is what converts a number into evidence.**

He also caught his own first attempt being inconclusive: it was scoped to a persona with one
queued row and no blocked rows, so "honored" and "ignored" produced *identical* output.
**A fixture with no discriminating row cannot discriminate** — the same failure class as a
green that cannot go red.

#### ⚠️ The most important behavior in this build is NOT yet proven live

**`park → expire → rejoin` has no live proof.** No row can be parked until this lands, and
parking one mutates persistent state — which makes it `:8000` work, not a `:7999` read-only
probe. AC6 is currently green in unit tests **only**.

**Nobody may call this milestone done on the read-only probe.** Stated here so it cannot get
lost in a DM thread between seats.

### 7.5 CONTAINER LIVENESS IS NOT APPLICATION LIVENESS

**The most reusable lesson in this document, and it generalizes well past this build.**

For ten minutes the dev server was dead. Throughout, `docker ps` reported:

```
lupin-rest-dev    Up 5 hours (healthy)
```

The container was up. The application inside it had **exited** — `ERROR: Application startup
failed. Exiting.` — and gone silent. Anyone debugging a fleet-wide outage reaches for
`docker ps` first and **is told everything is fine.** Mr. Radio 🦉 hit the same wall from the
other end: his `docker ps` read `Up 5 hours (unhealthy)`, which still required reading the
logs to learn the app had exited rather than merely degraded.

Worse, the only symptom reaching this seat was **peer DMs timing out** — which reads as a
flaky network, not a dead server. That reading is the one that would have cost the most time,
and it is the natural one, because the outage's victim (MCP messaging) is a different
subsystem from its cause (a migration id).

⇒ **Check the application, not the container:**

| Signal | Why |
|---|---|
| Last log timestamp | A silent container is not a working one — ours went quiet for 10 min |
| In-container health probe | Distinguishes "port unreachable" from "app not running" |
| `Application startup complete` **since the last restart** | The only positive proof the app is actually serving |

The outage was found in ten minutes only because the failing DMs were treated as **evidence
of this author's own recent breakage** rather than as infrastructure flakiness. *Suspect your
own most recent change first* — it is both the most likely cause and the one you can check
fastest.

### 7.6 A migration id is a value written into every database that ran it

Renaming `a3b4c5d6e7f8` → `c1a7f0e2b9d4` (§7.2) fixed the id collision correctly and **caused
the outage in §7.5.**

The dev container auto-migrates on startup, so the migration had *already run* under its
original id and stamped `alembic_version`. The rename left the database pointing at a
revision that no longer existed anywhere on disk:

```
alembic.util.exc.CommandError: Can't locate revision identified by 'a3b4c5d6e7f8'
ERROR:    Application startup failed. Exiting.
```

⇒ **Renaming a migration is only safe BEFORE it has run anywhere.** The rename was correct
but **incomplete**, and the incompleteness hid because the reasoning was about the *file*
while the id was living in a *database*. A revision id is not a filename — it is **a value
written into every database that ran it**, and the two have to move together.

**Crew rule (Mr. Radio 🦉):** after renaming a migration revision, check `alembic_version` in
**every** live database in the same breath.

#### Diagnose before bouncing — the remedies are not interchangeable

A dangling stamp can call for a re-stamp, a revert, or a restart, and picking wrong makes it
worse. What was verified *before* touching anything:

| Check | Result |
|---|---|
| Every live database's `alembic_version` | `lupin_db_dev` / `lupin_db_test` both at `f2a3b4c5d6e7` — a **valid** ancestor |
| Was the DDL already applied? | `park_reason` + both CHECKs present ⇒ yes |
| Does the container see the renamed file, and not the dead id? | yes / yes |
| Does the chain resolve **inside the container**? | head `c1a7f0e2b9d4`, length 15, dead id **absent** |

Only then a restart — which no-opped the already-applied DDL (the migration is idempotent by
inspection) and stamped `c1a7f0e2b9d4`. The app was dead, so no queue needed draining and
nothing could collide.
