## 2. THE FORK IS SETTLED — it IS a code defect

**Arm H settles it.** `owner_persona="mr radio"` is a narrowing filter — *literally the one the mandate

## 3. FINDING 2 — the cap is on ROW COUNT, not on BYTES

`limit` defaults to 100 (`tasks.py:798`, `ge=0, le=500`). Every 100-row arm above is that default firing.
**A row cap is not a size cap.** Rows carry multi-KB bodies with stacked amendments — this plan's own row
runs past 8k — so "100 rows" is anywhere from 21k chars (terse) to 424k (full). The one knob that exists
governs the wrong quantity.

## 4. 🔴 FINDING 3 — THE TRUNCATION IS SILENT AND THE ENVELOPE MISREPORTS

Not in the filed row, and the worst of the three.

```
tasks.py:975    return { "tasks": tasks, "count": len( tasks ) }
```

`count` is **the length of the page**, published under a name every caller reads as *the size of the
result*. Measured, same filter, `terse=true`:

```
count field   : 100
rows returned : 100
offset=100    : 100 more rows      <- the 100 was a SILENT cap
```

No `total`. No `has_more`. No `truncated`. **A caller who reads `count: 100` and stops has been told a
false fact about the world.** That is verbatim the invariant María wrote into this row — *"a degraded
response that does not announce its degradation is worse than an error"* — and the same shape as
`c191be39`, where a count lost its status and reported confidently anyway.

**The existing warning is aimed at an audience that cannot act on it.** `tasks.py:968-973` already detects
the heavy pull and `print()`s a nudge toward `terse=true` — **to the server's stdout**. The caller about to
be truncated never sees it. A warning delivered to someone who cannot act on it is not a warning.

## 5. FINDING 4 — `terse=True` is a 20-38× mitigation, and it is opt-in

D → E is 424,209 → 21,379 (**19.8×**). F → G is 137,526 → 3,638 (**37.8×**). `body` is the size driver,
as María predicted. But terse is **opt-in**, so the default path is the expensive one and the caller who
most needs it is the one who did not know to ask.

## 6. Scope — three fixes, dependency order

- **T1 — STOP MISREPORTING IN THE ENVELOPE.** Return `{ tasks, count, total, has_more, truncated }`.
  `count` = rows in *this page* (unchanged meaning); `total` = rows matching the filter; `has_more` =
  `offset + count < total`. Derive `total` from the repo's existing `count_tasks_by_status`, **not** from
  `len(tasks)` — two independent computations keep `total` vs `sum(breakdown)` a real cross-check instead
  of an unfalsifiable green.
  ⚠️ **`/api/tasks` is NOT internal-only.** The multiplexer parses the full-row shape
  (`render/taskListModel.ts`, `render/TaskListRenderer.ts`, `notifications.js:386`, a 60s poll at
  `multiplexer/boot.ts:586`). **ADD keys. Never rename or remove `count`.** The comment at
  `tasks.py:899-908` is the standing warning about this exact seam — read it before touching the return.
- **T2 — SURFACE THE WARNING TO THE CALLER.** The `print()` at `tasks.py:968` becomes a field in the
  response body, *in addition to* the log line. Same trigger, audience corrected.
- **T3 — A BYTE BUDGET, NOT A ROW BUDGET.** Serialize until a configurable char budget is reached, then
  stop and set `truncated: true` with the honest `total`. Row count stays as a second, independent bound.
  **Never a silent stop.**

**Out of scope**: making `terse` the default. That is a behavior change with a live TypeScript consumer and
needs Rick's ruling, not mine. Noted on the row, not built here.

## 7. Acceptance criteria

1. Arm H (`owner_persona="mr radio"` + `include_terminal`, full) returns `has_more: true` and `total` >
   `count`. **This is the regression test for the whole row** — it is the exact query that misreported today.
2. A result that fits one page returns `has_more: false` and `total == count`.
3. `count` keeps its EXACT present meaning. A test asserts the multiplexer's parsed shape still works —
   added keys only.
4. The heavy-pull notice reaches the **caller**, in the response body; the server log line survives.
5. A byte-budget truncation sets `truncated: true` and reports the honest `total`. **No arm of any test may
   pass with a silent truncation** — that assertion is the point of the row.
6. **Negative control**: a small narrow query is byte-for-byte unchanged except for the added keys.
7. 100% lines + branches + functions on every function touched.
8. MCP-side: `task_query`'s docstring stops describing an envelope that no longer matches the wire, and the
   new fields reach the agent rather than being swallowed at the MCP seam.

## 8. Risk

**Medium — higher than it looks, and entirely because of the multiplexer.** The endpoint has a live
TypeScript consumer polling every 60s. The failure mode is not the server; it is a UI that silently stops
rendering rows because a parser met a shape it did not expect. AC-3 is a hard merge gate. Adding keys is
safe; renaming is not; the file says so in its own words.

## 9. Blocked / unresolved

Nothing blocking. One question deferred to Rick, not gating: **should `terse` become the default?** It is a
20-38× saving on every board read in the fleet, and it is a behavior change with a live consumer.

### 🔴 The finding this build produced: T3 first broke the multiplexer, and the shape gate did not catch it

The card's poll (`limit=500&unscoped_audit=true&include_terminal=true`) measured **30 of 1101 rows**
under the default budget. Every key survived, so §8's shape gate stayed **green** — and a green gate
reads as *checked*. `TaskListStore.ts` states its own invariant three lines above the endpoint constant,
*"the human's view is never silently truncated"*, and the budget made that line false. The card does not
read `truncated`, so from the human's side the stop **was** silent: the exact failure T3 exists to
prevent, relocated one consumer over.

⇒ **A compatibility gate that checks the wire and not the meaning passes the change that breaks the
meaning.** §8 named the parser as the risk; the parser was never what broke. When a change alters *how
much* a consumer receives, the gate has to be the consumer's own stated invariant — and a comment
stating that invariant is the cheapest place to find it.

**Fix — an escape, not a wider budget.** `char_budget`: absent → the 100k default (protects the caller
who did not know to ask); `0` → unbounded; any other value overrides in either direction. The
multiplexer names the escape exactly where it already names its unscoped-size escape. Widening the
budget for everyone would have bought the dashboard's correctness with the agent's context — the trade
T3 exists to refuse.

Post-rebuild, measured: `count=500 total=1101 truncated=false` (the row bound binding again, as before).

### Two deviations from the brief, both deliberate, both ruled correct

1. **`total` comes from `count_tasks`, not `count_tasks_by_status`.** The latter returns a dict, so
   "derive from it" can only mean summing it — collapsing the two sides of the cross-check the brief
   itself calls for. Ruled by Mr. Radio: *"my own rationale refuted my own instruction."*
2. **The first row is admitted unconditionally**, even when it alone exceeds the budget. A budget that
   can return zero rows for a non-empty result set is a pagination dead end — the caller advances
   `offset` forever and never progresses. One oversized row plus `truncated: true` is honest *and*
   advanceable. Tested.
