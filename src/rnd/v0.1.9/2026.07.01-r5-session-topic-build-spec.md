## The gap (confirmed)

Legacy shows a per-session **name/topic** in the CC-session card header, populated live from `session_topic` notifications (`notifications.js:5854-5862`: `notifType === 'session_topic' && session_name` → `saveSessionName(sessionId, session_name, {fromServer:true})` + `refreshSessionNameDisplay`) and editable via a click-to-rename span. The mux renders the `.sender-session-name` span but **never populates it** — `senderCard.ts:136-137,158` ("SenderRecord carries no session-name field … empty until a rename feature lands"). `SenderRecord` has no `session_name`; the mux routes **no** `session_topic` anywhere.

## Data path (established)

- `session_topic` is a **notification_type** (`notifications.py:610`), NOT a distinct WS frame. It arrives at the mux via `notification_queue_update` → `NotificationStore.onQueueUpdate` (`NotificationStore.ts:517`) as `env.notification` with `notification_type === "session_topic"`, carrying `session_name` + `sender_id`.
- Legacy intercepts it in the notification handler and **skips the history card** (`return` at `:5862`) — it is control metadata, not a message.
- SenderStore already reacts to per-sender control notifications via `SENDER_SUBSCRIBED_EVENTS` (`SenderStore.ts:71`: `voice_persona_assigned` / `conversation_mode_changed` / …) with field-update handlers + `senders_changed` emission — the exact template for a session-name setter.

## Proposed design — R5a (server-driven display; the MVP-parity core)

1. **Type** (`shared/types.ts`): `SenderRecord.session_name?: string`.
2. **Interception** (`NotificationStore.onQueueUpdate`): when `norm.notification_type === "session_topic"`, emit a new bus event `session_topic` `{ sender_id, session_name }` and **return** (do NOT add a card) — mirrors legacy "skip history card". Keeps NotificationStore decoupled from SenderStore (bus, not import). Add `"session_topic"` to `LupinEventType` + a `SessionTopicPayload` type.
3. **Store** (`SenderStore`): add `"session_topic"` to `SENDER_SUBSCRIBED_EVENTS` + `onSessionTopic({sender_id, session_name})` → set the record's `session_name`, emit `senders_changed{changeKind:"updated"}`. (Records for not-yet-seen senders: buffer or ignore — see Q2.)
4. **Render** (`senderCard.ts`): `.sender-session-name`.textContent = `sender.session_name ?? ""` (replaces the always-empty span).
5. **Self-verifying loop** (per your mandate): extend `notifications-parity-scenario.json` (add a `session_topic` notification OR a `session_name` on the Tiberius sender) → add a `has_session_name` node to the oracle **skeleton** walker (`CONTRACT_SKELETON_JS`, union selector `.sender-session-name` — legacy uses the same class, so no divergence) → **recapture the sender-card golden** on :7999 (`test_golden_capture.py`, `LUPIN_PARITY_CAPTURE=1`) → Tier 0-3 + golden-conformance green. This makes R5 oracle-visible (unlike R4, which the golden was blind to).

**Note on scope of the oracle node**: `has_session_name` goes in the **skeleton** (presence) walker, not Tier-2/3 geometry — the name is a presence/content gap; adding it to computed-style/geometry would drag in `.sender-session-name` box styling that isn't the gap. (Same reasoning that kept R4 out of Tier-2/3.)

## R5b (manual rename + persistence) — RECOMMEND DEFER

Legacy also supports click-to-rename (`.sender-session-name[title="Click to rename"]`) with `localStorage` persistence (`saveSessionName{fromServer:false}`). This is a separate affordance from the display gap Rick flagged. Recommend deferring R5b to a follow-up (or dropping if the mux favors server-authoritative names) — R5a alone closes the visible parity gap.

## Open questions for review

1. **Interception seam** — NotificationStore emits a `session_topic` bus event → SenderStore consumes (my rec: loose coupling, mirrors existing `voice_persona_assigned` pattern). Or do you prefer a dedicated ingest handler in boot? **Rec: bus event.**
2. **Not-yet-seen sender** — a `session_topic` may arrive before the sender's first card. Buffer the name (Map keyed by sender_id, applied on sender add) or ignore until the sender exists? **Rec: buffer** (legacy persists regardless; parity favors not dropping it).
3. **Reload persistence** — ✅ RESOLVED: the senders-visible hydration (`notifications.py:2495`) stamps `voice_persona` + `manager_persona` per sender but **NOT `session_name`** — so a reload loses the name until the next `session_topic` re-emit. **Rec: mirror legacy exactly — a client-side `localStorage` mirror via `StorageService` keyed by sessionId, applied on sender add. Pure client, NO server change.** (Alternative — add `session_name` to the senders-visible response — is a broader server change; not recommended unless you want server-authoritative names.) This keeps R5a entirely client-side.
