## TL;DR

Running `git worktree prune` **inside** a Lupin server container (`lupin-rest-test` or `lupin-rest-dev`) deletes the **entire host** `.git/worktrees/` registry in one shot, silently detaching every active lane's worktree. The trigger is `preflight-test-container.sh` (and its pytest twin `test_container_preflight.py`), which `docker exec … git worktree prune` as a teardown step. The mechanism is a mount asymmetry: the container bind-mounts `./.git` but **not** `lupin-worktrees/`, so every registered worktree's `gitdir` resolves to a non-existent in-container path and `prune` deems them all stale.

Physical working trees under `lupin-worktrees/` **survive** (only the `.git/worktrees/<name>` admin dirs are deleted) — so no data is lost, but every lane detaches and must be re-attached (`git worktree repair`, or backup→rebuild).

## Mechanism (proven)

### The mount asymmetry

`docker-compose.yml` mounts, for **both** `lupin-rest-dev` (~L138–146) and `lupin-rest-test` (~L221–229):

```
- ./src:/var/lupin/src
- ./io:/var/lupin/io
- ./.git:/var/lupin/.git                         # ← host .git (incl. .git/worktrees/) shared IN
- ./.claude/worktrees:/var/lupin/.claude/worktrees
```

There is **no** mount for `lupin-worktrees/`. So inside the container, `lupin-worktrees/` does not exist.

### Live in-container probe (2026-07-02, `lupin-rest-test`, read-only)

```
$ docker exec lupin-rest-test sh -c 'ls /var/lupin/.git/worktrees/; head -1 /var/lupin/.git/worktrees/*/gitdir; ls -d /var/lupin/lupin-worktrees'
clayton-krishna-review
lane-2-goldens
lane-arnold-amend
...
==> /var/lupin/.git/worktrees/clayton-krishna-review/gitdir <==
/mnt/DATA01/include/www.deepily.ai/projects/lupin/lupin-worktrees/clayton-krishna-review/.git
ls: cannot access '/var/lupin/lupin-worktrees': No such file or directory
```

Each `.git/worktrees/<name>/gitdir` stores a **host absolute path** (`/mnt/DATA01/.../lupin-worktrees/<name>/.git`). Inside the container the filesystem root is `/var/lupin`, so **none** of those `/mnt/DATA01/...` paths exist.

### Why prune wipes everything

`git worktree prune` iterates every entry in `.git/worktrees/`, reads its `gitdir`, and removes the admin entry if that path is missing. In-container, **every** gitdir path is missing → prune removes **every** admin entry. Because `.git` is a shared bind-mount, the deletion propagates to the host `.git/worktrees/`, detaching all host lanes simultaneously. `prune` is all-or-nothing (no `--only <name>`), so it cannot be narrowed.

(Note: the container's own smoke worktree, added at `/var/lupin/.claude/worktrees/<smoke>` from inside the container, stores an in-container gitdir that *does* resolve — so it survives the staleness check. Only the host-registered lanes, whose gitdirs are `/mnt/DATA01/...`, are pruned.)

## Trigger sites

| File | Lines | What |
|---|---|---|
| `src/scripts/preflight-test-container.sh` | 97, 133 | `docker exec … "… ; git worktree prune …"` teardown after a smoke `worktree add`/`remove` |
| `src/tests/smoke/test_container_preflight.py` | 125, 171 | pytest twin — same `docker exec` teardown in two `finally` blocks |

In every case a paired `git worktree remove --force <smoke>` runs immediately before the prune. **`remove` already deletes the smoke worktree's admin entry**, so the trailing `prune` is redundant — and catastrophic in this mount topology.

### Secondary risk (not the observed trigger)

`src/cosa/agents/shared/worktree_reaper.py:222` runs `git worktree prune` on `project_root` in the `git worktree remove` **failure** branch. Run host-side (the normal case) this is **safe** — the host sees all worktree dirs, so prune only removes genuinely-missing entries. But if the reaper ever runs **inside** a container (`project_root == /var/lupin`, e.g. a TFE/BFE reap executing in the server process), the same wipe recurs. Guarded defensively as part of this fix.

## Fix (ACKED by Tiberius, GO on both)

1. **Minimal — remove the trailing prune.** Delete `; git worktree prune …` from `preflight-test-container.sh:97,133` and the two `finally` blocks in `test_container_preflight.py:125,171`. The paired `git worktree remove --force <smoke>` already cleans the smoke worktree; a leftover stale admin entry (if `remove` ever fails) is a benign leak, never a wipe.
2. **Defense-in-depth — reaper in-container guard.** In `worktree_reaper.drain_then_remove`, skip the `git worktree prune` when running in-container (`project_root == "/var/lupin"` or a `LUPIN_IN_CONTAINER` env sentinel), recording a skip note instead. This closes the secondary risk and the whole *class* (any future in-container prune path).
3. **Regression guard test.** A unit test asserting **no `git worktree prune`** appears in either preflight source (`.sh` + `.py`) — so the command can never be re-introduced at a container-exec site.

**Scope**: both containers, not just `lupin-rest-test` — `lupin-rest-dev` has the identical `.git`-mounted / `lupin-worktrees`-unmounted asymmetry (confirmed against `docker-compose.yml`), so Mr. Radio's dev swap-chain is equally exposed.

**Discipline**: RED-first + 100% lines/branches/functions on touched code. Commit-held per lane; push is Rick's. No fix merged until Cheech reviews.
