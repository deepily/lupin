All 31 of `preflight-vm.sh`'s assertions are written against ONE app on `:7999` — `svc
status`, the app-URL probes, the container-surface layer (A1/C). Stand a second stack up and
**preflight goes GREEN while structurally blind to half the machine.**

⇒ **Coexistence must not land before preflight can see both stacks.** A second server with no
instrument is worse than no second server, because the instrument reports success.

## 5. ⚠️ The unresolved question this design cannot close

**Do the two stacks share one Cloud SQL proxy, or run one each?**

Both compose files declare their own `cloud-sql-proxy` *and* their own `cloudsql-socket-init`,
with **identical `container_name`s** (`lupin-cloudsql-proxy`, `lupin-cloudsql-socket-init`).
Running both stacks as-written on one host means two compose projects each trying to own a
container of the same name.

And it collides head-on with `70794d58`. `cloudsql-socket-init` runs:

```
rm -f /cloudsql/*/.s.PGSQL.5432
```

⇒ **If the second stack's socket-init runs while the first stack's proxy is live, it deletes
the running proxy's socket** — the exact P1 closed today, re-armed by a topology change rather
than by a missing flag. **`--no-deps` does not save you here**, because bringing up a genuinely
new stack legitimately runs its own init. The mechanism was measured today (isolated compose
project): the socket is deleted, the proxy never re-creates it, and the proxy keeps reporting
`running health=healthy` the whole time.

Options, none yet chosen:

- **(a) One shared proxy** — owned by whichever stack starts first; the second declares no proxy
  and mounts the same socket volume. Cleanest, but makes the stacks non-independent: a
  `cloud-gpu` bounce silently takes `:8000`'s database with it.
- **(b) Two proxies, two socket volumes, distinct container names.** Fully independent; costs a
  second proxy process and requires both compose files to stop hardcoding `container_name`.
- **(c) Two proxies sharing one socket volume.** ❌ **Never** — that is the `70794d58` deletion
  as a design.

**Recommendation: (b).** The stacks are meant to be independently bounceable — that is the
entire point of a test server beside a dev server — and (a) reintroduces exactly the
cross-stack coupling the coexistence ruling was asked for in order to avoid.

### ✅ RULED 2026-07-27 (Mr Radio 🦉, VM seat): **(b)** — two proxies, non-hardcoded names. (c) rejected.

Mechanics then **measured** in an isolated two-project probe rather than assumed:

```
container_name  ->  GLOBAL to the docker daemon
volumes         ->  PROJECT-namespaced:  topo-stack1_shared  vs  topo-stack2_shared
```

⇒ **Separate volumes are already free** under distinct compose project names — no config needed.
De-hardcoding `container_name` is the load-bearing change, as ruled.

**One correction to the predicted failure mode.** The expectation was that stack 2 *"recreates
stack 1's live proxy outright."* It does not. Docker refuses:

```
Error response from daemon: Conflict. The container name "/lupin-cloudsql-proxy-…"
is already in use by container e697a0c9…
```

Stack 1's container is untouched — same container ID before and after, still running. The
current failure is **loud and non-destructive**, not a silent hijack.

### 🔴 AND THE INVERSION — the hardcoded name is the only thing preventing the deletion TODAY

Probed with the real dependency shape, stack 1 up and its socket-init already **exited**:

```
stack1 : live.sock present, audit.log = "RAN-THE-RM" (1 line), init state = exited
stack2 : Container lupin-cloudsql-socket-init-…  Creating
         Error: Conflict. The container name … is already in use by d15a46e2…
stack1 : live.sock STILL PRESENT, audit lines still 1   <- the rm NEVER RAN
```

**An exited one-shot still holds its name.** Stack 2 aborts on the socket-init name *before the
init is created*, so the `rm` never runs and the socket survives.

⇒ **The name collision that makes coexistence impossible is also what currently prevents the
socket deletion.** De-hardcode the names to enable coexistence — the ruled, load-bearing change
— and you remove that guard in the same stroke.

⇒ **This is `70794d58`'s ordering constraint a SECOND TIME, on the same bug.** In AXIS-B, fixing
the service name alone would have armed the deletion. Here, de-hardcoding the container names
alone arms it again. **A commit that only renames the containers is the dangerous one** — and it
is precisely the commit a reader takes away from "de-hardcoding the names is the load-bearing
change."

### 🔴 CORRECTED 2026-07-27 — my probe's REGIME was wrong (Clayton 😎, commit `db8a4b2d`)

Everything above about volumes being "already free" assumed **distinct compose project
names**, which is what my probe supplied (`-p topo-stack1`, `-p topo-stack2`). **This repo
supplies none:**

- no top-level `name:` in either cloud compose file
- no `-p` / `--project-name` at any call site (`lupin-vm.sh`, `deploy-cloud-test.sh`,
  `preflight-vm.sh`, `lib/*.sh`)
- `COMPOSE_PROJECT_NAME` nowhere in the tree
- both files sit at one root ⇒ **`/var/lupin` resolves to project `lupin` for BOTH stacks**

Clayton ran the arm I did not, same-project, predictions written first:

```
distinct project → Conflict, container name already in use; socket survives   (my result)
same project     → NO conflict. Compose RECREATES:
                   live.sock DELETED, audit 2 lines (the rm ran twice),
                   one shared volume, and stack A's app container DESTROYED
                   (`No such object`) — the service redefined with a different
                   container_name.
```

⇒ **The discriminator is the PROJECT name, not the container name.** Under our own
invocation the guard described above **does not exist**, and the socket deletion is
**already armed** — the gating act is the first `compose up` of stack 2 on the VM, not a
rename.

⇒ **The load-bearing half is pinning a per-file `name:`.** My "an invocation-dependent
guarantee is not a guarantee" line was the right instinct aimed at the wrong risk: I treated
distinct project names as the default and the pin as belt-and-braces. It is the reverse.

⇒ **`lupin-rest` is a second unguarded path** I did not consider — same service name in both
files, divergent container names, which is exactly the shape that destroyed his stack-A
container.

The one-commit rule below **stands**; it is simply not sufficient alone.

**Implementation constraint — one change, both halves:**
1. Drop (or per-stack parameterize) the hardcoded `container_name` on `cloud-sql-proxy` **and**
   `cloudsql-socket-init`, in **both** compose files.
2. In the **same** change, confirm each stack's `cloudsql-socket` volume is its own. Distinct
   compose project names already give this — but **verify it on the VM**. The probe proves
   docker's namespacing rule, not the VM's actual project names.

⚠️ If both stacks were ever brought up under the **same** project name, the volumes would not be
distinct and option (c) — the deletion-as-design — is what you would have built.
