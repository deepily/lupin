The Stop hook tells every session it owns *N* **in-progress** items when what it actually counted was *N* **open** items, because the store-count seam collapses a multi-status owed set into a single integer and re-inflates it as all-`in_progress`.

## 3. ⛔ The constraint that kills the obvious fix

**The obvious fix — have `query_owed` loop per status client-side and return a breakdown — is FORBIDDEN.** That shape was *deliberately deleted* on 2026-07-19 by the PARKED-STATUS build. `task_store_client.py:273` documents why, verbatim:

> 1. It **CANNOT see a park-expiry rejoin.** Park-expiry is computed at READ time and never written back, so an EXPIRED parked row still carries `status="parked"` — it matches neither `"queued"` nor `"in_progress"` and would stay silent forever. Parking would buy PERMANENT silence from the one reader that fires the pokes.
> 2. Server-side admission + a per-status loop **DOUBLE-COUNTS**: an expired parked row would be admitted on the queued call AND again on the in_progress call. Parking a row and letting it expire would make the board look BUSIER than never parking it — the feature inverts.

The owed set is now **server-owned** behind one `owed_only=true` flag:

```
owed = queued ∪ in_progress ∪ ( parked AND NOT park-active )
```

> **Restoring a client-side loop would resurrect two bugs fixed nine days ago.**
> Any reviewer who proposes it should be pointed at this section.

### 3a. This prohibition is ENFORCED, not merely stated (María, review 2026-07-20)

A **shape-level** regression guard against the forbidden fix already exists, from the 07-19 build — `test_task_store_client.py:278`:

```python
assert len( conn_seq[ "requests" ] ) == 1, "more than one request — the per-status loop is back"
```

with the surrounding docstring: *"a re-introduced per-status loop can return a correct total on a board with no parked rows and still be broken the moment one expires. Shape divergence is silent; this makes it loud."*

⇒ **An implementer who reaches for the loop does not merely contradict §3 — they go RED.** Verified firsthand this session, not taken on report.

> ⚠️ **And §3 alone was NOT sufficient.** Until 2026-07-20, `task_store_client.py:196` described the deleted loop **in the present tense, 77 lines above** the `:273` docstring §3 cites as its authority — so a top-down reader met the retired shape first and never reached the correction. ## 4. Proposed design — server-side breakdown, one request

Keep everything the PARKED-STATUS build won (server owns the status set, one request, `count_only` true `COUNT(*)`, fail-closed). Add a **breakdown** beside the count.

### 4.1 Server — ALWAYS return the breakdown, scoped to the `count_only` branch

**Rick ruled (2026-07-20): always return it, no opt-in flag — and grounded the ruling in a caller census rather than an assumption.** A flag a caller can forget is the same failure shape that produced this bug.

`GET /api/tasks?owed_only=true&count_only=true` returns, alongside the existing integer `count`:

```json
{ "count": 16,
  "breakdown": { "in_progress": 2, "queued": 13, "parked": 1 } }
```

> ✏️ **CORRECTED 2026-07-20 (Cheech 🌿, at implementation).** This example
> originally invented a `parked_expired` key, implying a derivation step that does
> not happen. The GROUP BY returns the RAW status column, and **every admitted
> `parked` row has provably expired** — park-active rows are excluded by
> `owed_status_clause` before the grouping ever runs. So the shipped key is
> `parked`, and it IS the expired-parked set with no extra filtering. Mr. Radio
> ruled the doc should match the implementation rather than the reverse.

- Same single query, same server-owned membership, same `COUNT(*)` semantics — a `GROUP BY` on the admitted set, not N queries.
- `count` MUST equal the sum of `breakdown`. That invariant is a test, not a comment.

#### 4.1a Caller census — executed 2026-07-20, not assumed

| Surface | Production consumers |
|---|---|
| `query_owed()` | **Exactly 2** — `stop.py:1398` (`_owed_count_from_store`), `stop.py:1459` (backlog / `accountable_manager` path). All other hits are tests, docstrings, migration comments. |
| `count_only=true` response shape | **Exactly 1** — `task_store_client.py` → `query_owed` → the two sites above |
| `/api/tasks` **full-row** shape | **Frontend consumers EXIST** — `render/taskListModel.ts`, `render/TaskListRenderer.ts`, `notifications.js:386`, and a 60s poll at `multiplexer/boot.ts:586` |

> ⛔ **THE BOUNDARY THIS CENSUS FOUND.** We are the only consumer of the **count** response, so always-return is safe there. But `/api/tasks` as an **endpoint** is NOT internal-only — the multiplexer parses its full-row shape.
> ⇒ **Add `breakdown` ONLY inside the `if count_only:` branch (`routers/tasks.py:818`). The full-row response is UNCHANGED.**
> A reviewer must confirm no `breakdown` key reaches the `count_only=False` path.

### 4.2 Client

**Rick ruled (2026-07-20): map expired-parked onto the existing `pending` / unstarted bucket.**

## 6. Acceptance criteria

1. `count == sum( breakdown.values() )` — enforced by test, both directions.
2. A persona owning only `queued` rows produces `todo_unstarted` and **NOT** `todo_in_progress`.
3. A persona owning a mix produces **both** signals with correct counts.
4. **Park-expiry regression guard**: an expired-parked row is counted exactly **once** and appears in the breakdown — the explicit control against reintroducing the deleted loop's double-count.

6. The pure oracle `heartbeat_work_owed.py` is **unmodified**. Its existing tests stay green untouched.

### 11.2 Rulings applied

- **5(a) — `count` stays independent** (Mr. Radio): an invariant true *by construction* is not a gate. `count` (a `COUNT(*)`) and `breakdown` (a `GROUP BY`) are two independent computations, so `count == sum(breakdown)` is a **falsifiable** cross-check. Two cheap aggregates, one connection, one HTTP request.
- **§4.3(a) — expired-parked → `pending`** (Rick). Accepted cost restated in code: a reader cannot distinguish never-started from rejoined without opening the row.
- **§4.1 key name — `parked`, not `parked_expired`** (see §4.1 correction above).

### 11.3 Two design points decided at implementation, both fail-toward-visible

1. **A malformed/absent `breakdown` does NOT fail the read.** It degrades to `{}` and synthesis falls back to the pre-fix shape (count items, all in_progress). Failing the read would let a *cosmetic* regression **suppress the poke** — strictly worse than a right total with a coarse status. The count keeps the §C fail-safe; the breakdown is a reporting refinement layered on an already-trusted count.
2. **An UNKNOWN store status is counted, not dropped** — it falls back to `in_progress`. Over-reporting one row's urgency is recoverable; dropping it is a session that goes quiet while owing work, which is the failure this build exists to remove.
