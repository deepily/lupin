# DM-inbox HWM files accumulate without bound in the repo root

**Filed**: 2026-07-26 · **Author**: María 🌸 (Workflow Steward, session `56a24527`)
**For**: Mr Radio 🦉 — implementation
**Trigger**: Rick, directly — *"I keep seeing a ton of these files in the root of the Lupin directory `.dm-inbox-hwm-33010f33.json`. What are they doing there and why do I have so many of them?"*
**Severity**: cosmetic today, unbounded tomorrow. **Nothing is at risk** — this is clutter, not damage.

---

## 1. What the files are, and why they exist

`.dm-inbox-hwm-<session_id8>.json` is one session's **DM inbox high-water mark** — a `cursor_ts` plus the `surfaced_ids` already shown to that session.

They are not junk. They are the fix for bug `59f355e0` (Mr Radio's own Option-A ruling, 2026-07-02): a peer DM arriving while the recipient was mid-turn went to a lossy JSONL voice buffer and was **lost** if the session ended before a later hook drained it — **84 orphaned DMs across 46 stale buffer files** at triage time. This file is the durable "already surfaced" ledger that makes delivery at-least-once.

They live in the **repo root on purpose**: the module's own comment says *"durable, /clear-proof — hold-file runtime-state family."* Surviving `/clear` is the point. **Do not "fix" this by hiding them somewhere the reconcile can't find them.**

Source: `src/lupin_cli/claude_code/hooks/lib/dm_inbox_reconcile.py`
Design record: `src/rnd/v0.1.9/2026.07.02-dm-loss-surfacing-leg-triage.md`

## 2. The defect: the design capped the wrong axis

| axis | bounded? | mechanism |
|---|---|---|
| `surfaced_ids` **within** one file | ✅ **yes** | `SURFACED_IDS_CAP = 500`, FIFO tail via `_dedup_tail` |
| **number of files** | ❌ **no** | one per session, **nothing ever deletes one** |

`grep` over the module for `unlink` / `remove` / `prune` / `clean` / `glob` / `expire` / `delete` returns **zero cleanup logic**. There is no janitor, no TTL, no sweep.

⇒ Whoever wrote this thought carefully about unbounded growth — and bounded the inside of the file while the file count grew without limit. **The care was real and it was aimed one level too low.**

## 4. The finding that makes this worth a row rather than an `rm`

**We already built a janitor for exactly this class of per-session runtime dropping — and it cannot see these files.**

`heartbeat_hold.py:79` → `HOLD_GLOB = ".heartbeat-hold-*.json"`, matched via `fnmatch` at `:648`, `:690`, `:719`.

The hold janitor sweeps the same directories, classifies by age, guards cargo, honors live-session sets, and — as of `d779c7ab` today — **actually reclaims**. The HWM family sits beside the hold files, in the same root, with the same `<session_id8>` suffix convention and the same `/clear`-proof rationale, and is invisible to all of it **because of one glob string**.

⇒ The reusable machinery exists. This is a coverage gap, not a new subsystem.

## 5. Recommended approach

> ## 🔴 §5 CORRECTED 2026-07-26 — "extend the glob" WAS WRONG, AND IT WAS WRONG IN THE WAY §7 WARNS ABOUT
>
> The original §5 said: extend `HOLD_GLOB` so the existing janitor sweeps this family too. **Mr Radio 🦉 refuted it by measurement**, predicting the classifier's verdict before running it:
> ```
> predicted: verdict=KEEP  reason=KEEP_NO_PROVABLE_AGE  session_id=None
> actual   : verdict=keep  reason=no_provable_age       sid=None  ttl_ok=False
> ```
> **Two structural reasons, both fatal, both at `heartbeat_hold.py:847-849`:**
> 1. `if held_dt is None or not ttl_usable: → KEEP_NO_PROVABLE_AGE`. An HWM body is `{cursor_ts, seeded, surfaced_ids}` — **no `held_at`, no `ttl_seconds`** (20/20 sampled identical; I re-verified 5/5 independently). The classifier can never prove an HWM's age, so it keeps it forever.
> 2. The live gate reads `sid = hold.get("session_id")` — **HWM bodies carry no `session_id` at all.** The sid8 is in the FILENAME. So the load-bearing guard this document correctly identified **cannot fire either**; it reads `None`.
>
> ⇒ Extending the glob yields a janitor that sweeps 435 extra files per cycle, classifies every one KEEP, **deletes zero, and reports green.** A clean no-op that looks like success.
>
> ⇒ **This document warned against exactly that in §7 ("beware the control that never fires") and then specified it in §5, two sections apart.** The warning and the defect were written the same afternoon by the same author. Same shape as `11461241` earlier today, where the milestone's structural guard stopped guarding *by staying green*.
>
> **The corrected shape — still not a new subsystem**: reuse the **traversal** (`_iter_hold_paths`) and the **reclaim loop**, but give the second family its **own classifier** — **mtime-anchored** (the only clock an HWM has) and **live-gated on the filename sid8**, not on a body field. `classify_hold_file` is hold-shaped by construction and should stay that way.
>
> ⚠️ **Filename-derived sid8s are `[:8]` truncations** (`dm_inbox_reconcile.py:_hwm_path`), so the live gate must compare **8-char prefixes on both sides** — and it will meet **non-hex** suffixes (see §5.1). It must not raise on them.
>
> Read the rest of this section for the *rationale* (which stands); read this box for the *mechanism* (which replaces it).

**Extend the existing janitor to a second file family. Do not write a new sweeper.**

### Why these are *safer* to delete than hold files
| property | `.heartbeat-hold-*` | `.dm-inbox-hwm-*` |
|---|---|---|
| carries hand-written cargo | **yes** — `note_to_my_successor`, etc. Irreplaceable. | **no** — machine-generated cursor + uuid list |
| regenerable | no | **yes** — absent file ⇒ `{"cursor_ts": None, "surfaced_ids": [], "seeded": False}` |
| worst case if wrongly deleted | permanent loss of a continuity record | a session may **re-surface** DMs it already showed |

⇒ The blast radius of a false delete here is **a duplicate DM**, not data loss. That justifies a simpler rule than the hold-file guard stack.

### The one real hazard, and it is not age
**A live session's HWM must never be reclaimed** — deleting it resets the cursor and the session re-surfaces its whole recent DM history as `additionalContext`. Noisy and confusing, though not destructive.

⇒ **Gate on the live-session set, not on mtime alone.** `_default_live_session_ids()` already exists and already returns the live set; reuse it. An HWM whose `session_id8` is in the live set is KEPT regardless of age — a long-running session can legitimately have a stale-looking file.

### Suggested rule
> Reclaim `.dm-inbox-hwm-<sid8>.json` iff **(a)** `sid8` is absent from the authoritative live-session set, **AND (b)** mtime is older than a grace window (14 days is a defensible default — it retains 339 of 434 today and clears 95).

⚠️ **(a) is load-bearing; (b) is politeness.** If the live set is unavailable (`None`), **keep everything** — same bias-to-keep the janitor already implements. Do not let an empty live set read as "nothing is alive."

## 5.1 A file in this family is NOT a session — `stable-s` (found 2026-07-26)

Mr Radio re-derived the counts and found **`.dm-inbox-hwm-stable-s.json`** — written 16:00 today, body the empty seed (`{"cursor_ts": null, "surfaced_ids": [], "seeded": true}`), suffix plainly not a session hash. He correctly refused to touch it while unexplained.

**STATUS: the writer is UNIDENTIFIED. Two hypotheses proposed, both refuted.** Recorded here because the *failed* attempts constrain the answer more than the guesses did.

`_hwm_path()` does `suffix = ( session_id or "" )[ :8 ]`, so any source string beginning `stable-s` collapses to this one filename.

| # | hypothesis | how it died |
|---|---|---|
| 1 | `test_visual_regression.py:38` masks the session-id element with `'stable-session'`; `[:8]` = `stable-s` | **Refuted by Mr Radio 🦉.** The causal path requires a *browser-side DOM text mask* to reach a *host-side Python file write*, and nothing reads that element's `textContent` back into a session id. Arithmetic correct; mechanism never established. Also: no e2e log in the window, and `stable-s` was written **alone** at 16:00:06 — a live e2e run should have left company. |
| 2 | `test_speakerphone_wrap_threading.py` drives `user_prompt_submit.main()` with `session_id="stable-sid-12345"` (also `[:8]` = `stable-s`), and `user_prompt_submit.py:41` imports `surface_dm_inbox` **unmocked** | **Refuted by execution.** Predicted the file's mtime would advance; ran the file; **5 passed, mtime unchanged at 16:00:06.** `surface_dm_inbox` returns `""` and does **not** advance the HWM on a not-ok fetch, so a test with no reachable store writes nothing. |

⇒ **What hypothesis 2's failure actually tells us**, and it is the useful residue: the file was written by something whose **DM fetch SUCCEEDED** — an authenticated call against a reachable store. That is a live hook run, not an offline unit test. **Four candidate literals exist** (`'stable-session'`, `"stable-sid-11111"`, `"stable-sid-12345"`, `"stable-sid-67890"`), so the string is not even uniquely sourced.

⇒ **Consequence that stands regardless of the writer — this is the part that touches the janitor:** the filename live-gate will meet **non-hex, non-session suffixes**. It must compare 8-char prefixes as **strings** (set membership, no hex parse, no charset assumption) and must not raise. `stable-s` is a known-ugly input and belongs in the guard tests as an explicit fixture.

⚠️ **Do NOT file a test-isolation row on this.** Both premises that would support one are dead. **Do not special-case `stable-s`** either — the source is unidentified and possibly not a test at all.

## 7. Verification the implementer owes

Whatever the rule, **prove the guard by breaking it** — the standard this family has been held to all day:

1. **Positive control** — an orphaned, ancient HWM **is** deleted. Without this arm a sweep that deletes nothing reads as a passing test.
2. **Live-session guard** — an HWM whose `sid8` **is** in the live set survives, *at the same age* as one that gets deleted. One variable different, opposite outcome.
3. **Null live-set** — `live_session_ids=None` ⇒ **nothing** is deleted.
4. **Mutation each guard away and watch the corresponding test go red.** A green suite proves nothing until the assertion has been shown to fail.
5. **Regeneration** — after deleting an HWM, `read_state()` returns the empty seed and the next reconcile proceeds without raising.

6. **Assert the sweep deletes a NON-ZERO count** (Mr Radio's addition). "Zero deleted" is precisely the failure mode the §5 correction is about, and it is indistinguishable from a healthy sweep with nothing to do.
7. **A non-hex filename suffix** (`stable-s`, §5.1) is classified without raising.

⚠️ **Beware the control that never fires.** Today's `eeba4858` cost an afternoon because four "successes" were green for a reason unrelated to what they appeared to test — the branch was never evaluated. Pick fixtures where the guarded and unguarded paths genuinely **diverge**.

⇒ **This warning has now caught two things and been violated once — by this document.** §5's original remedy would have produced a sweep that keeps everything and reports success. Mr Radio caught it by **predicting the classifier's verdict and then running it**; reading the plan would not have. *Predict, then execute* is what has worked all day.

## 9. One-paragraph summary for a busy reader

`.dm-inbox-hwm-*.json` are per-session DM bookmarks that prevent peer DMs from being silently dropped. They are correct, deliberate, and gitignored. **Nothing deletes them** — 434 files, 1.8 MB, ~18/day, oldest 2026-07-02 — because the design bounded the ledger *inside* each file (`SURFACED_IDS_CAP = 500`) and never bounded the *number* of files. The janitor that would clean them already exists and already sweeps the same directories — but **it cannot classify them**: an HWM body has no `held_at`, no `ttl_seconds`, and no `session_id`, so `classify_hold_file` returns KEEP-no-provable-age on every one and its live gate reads `None`. **Extending the glob would delete nothing and report green** (§5 correction).

⇒ **Reuse the traversal and the reclaim loop; write a second classifier** — mtime-anchored, live-gated on the **filename** sid8 (an 8-char truncation that may be non-hex, §5.1), keeping everything when the live set is `None`. **Prove every guard by mutating it away, and assert a non-zero delete count.**
