# DM-inbox HWM files accumulate without bound in the repo root

**Filed**: 2026-07-26 · **Author**: María 🌸 (Workflow Steward, session `56a24527`)
**For**: Mr Radio 🦉 — implementation
**Trigger**: Rick, directly — *"I keep seeing a ton of these files in the root of the Lupin directory `.dm-inbox-hwm-33010f33.json`. What are they doing there and why do I have so many of them?"*
**Severity**: cosmetic today, unbounded tomorrow. **Nothing is at risk** — this is clutter, not damage.

---

## 1. What the files are, and why they exist

`.dm-inbox-hwm-<session_id8>.json` is one session's **DM inbox high-water mark** — a `cursor_ts` plus the `surfaced_ids` already shown to that session.

They are not junk. They are the fix for bug `59f355e0` (Mr Radio's own Option-A ruling, 2026-07-02): a peer DM arriving while the recipient was mid-turn went to a lossy JSONL voice buffer and was **lost** if the session ended before a later hook drained it — **84 orphaned DMs across 46 stale buffer files** at triage time. This file is the durable "already surfaced" ledger that makes delivery at-least-once.

They live in the **repo root on purpose**: the module's own comment says *"durable, /clear-proof — hold-file runtime-state family."* Surviving `/clear` is the point. **Do not "fix" this by hiding them somewhere the reconcile can't find them.**

Source: `src/lupin_cli/claude_code/hooks/lib/dm_inbox_reconcile.py`
Design record: `src/rnd/v0.1.9/2026.07.02-dm-loss-surfacing-leg-triage.md`

## 2. The defect: the design capped the wrong axis

| axis | bounded? | mechanism |
|---|---|---|
| `surfaced_ids` **within** one file | ✅ **yes** | `SURFACED_IDS_CAP = 500`, FIFO tail via `_dedup_tail` |
| **number of files** | ❌ **no** | one per session, **nothing ever deletes one** |

`grep` over the module for `unlink` / `remove` / `prune` / `clean` / `glob` / `expire` / `delete` returns **zero cleanup logic**. There is no janitor, no TTL, no sweep.

⇒ Whoever wrote this thought carefully about unbounded growth — and bounded the inside of the file while the file count grew without limit. **The care was real and it was aimed one level too low.**

## 4. The finding that makes this worth a row rather than an `rm`

**We already built a janitor for exactly this class of per-session runtime dropping — and it cannot see these files.**

`heartbeat_hold.py:79` → `HOLD_GLOB = ".heartbeat-hold-*.json"`, matched via `fnmatch` at `:648`, `:690`, `:719`.

The hold janitor sweeps the same directories, classifies by age, guards cargo, honors live-session sets, and — as of `d779c7ab` today — **actually reclaims**. The HWM family sits beside the hold files, in the same root, with the same `<session_id8>` suffix convention and the same `/clear`-proof rationale, and is invisible to all of it **because of one glob string**.

⇒ The reusable machinery exists. This is a coverage gap, not a new subsystem.

---

## 5. Recommended approach

**Extend the existing janitor to a second file family. Do not write a new sweeper.**

### Why these are *safer* to delete than hold files
| property | `.heartbeat-hold-*` | `.dm-inbox-hwm-*` |
|---|---|---|
| carries hand-written cargo | **yes** — `note_to_my_successor`, etc. Irreplaceable. | **no** — machine-generated cursor + uuid list |
| regenerable | no | **yes** — absent file ⇒ `{"cursor_ts": None, "surfaced_ids": [], "seeded": False}` |
| worst case if wrongly deleted | permanent loss of a continuity record | a session may **re-surface** DMs it already showed |

⇒ The blast radius of a false delete here is **a duplicate DM**, not data loss. That justifies a simpler rule than the hold-file guard stack.

### The one real hazard, and it is not age
**A live session's HWM must never be reclaimed** — deleting it resets the cursor and the session re-surfaces its whole recent DM history as `additionalContext`. Noisy and confusing, though not destructive.

⇒ **Gate on the live-session set, not on mtime alone.** `_default_live_session_ids()` already exists and already returns the live set; reuse it. An HWM whose `session_id8` is in the live set is KEPT regardless of age — a long-running session can legitimately have a stale-looking file.

### Suggested rule
> Reclaim `.dm-inbox-hwm-<sid8>.json` iff **(a)** `sid8` is absent from the authoritative live-session set, **AND (b)** mtime is older than a grace window (14 days is a defensible default — it retains 339 of 434 today and clears 95).

⚠️ **(a) is load-bearing; (b) is politeness.** If the live set is unavailable (`None`), **keep everything** — same bias-to-keep the janitor already implements. Do not let an empty live set read as "nothing is alive."

## 6. What I am explicitly NOT deciding

- **Whether the grace window is 7, 14, or 30 days.** Implementer's call with Rick; I have no evidence favoring one.
- **Whether this rides the same `enable_hold_deletion` switch or gets its own.** Argument for its own: these are strictly safer, so coupling them to the cargo-bearing family's kill-switch may be over-conservative. Argument for shared: one switch is one thing to reason about. **Not mine to rule.**
- **Whether to backfill-delete the existing 434.** A one-time sweep under the same rule is reasonable; it is also fine to let the janitor drain them over its normal cadence.

---

## 7. Verification the implementer owes

Whatever the rule, **prove the guard by breaking it** — the standard this family has been held to all day:

1. **Positive control** — an orphaned, ancient HWM **is** deleted. Without this arm a sweep that deletes nothing reads as a passing test.
2. **Live-session guard** — an HWM whose `sid8` **is** in the live set survives, *at the same age* as one that gets deleted. One variable different, opposite outcome.
3. **Null live-set** — `live_session_ids=None` ⇒ **nothing** is deleted.
4. **Mutation each guard away and watch the corresponding test go red.** A green suite proves nothing until the assertion has been shown to fail.
5. **Regeneration** — after deleting an HWM, `read_state()` returns the empty seed and the next reconcile proceeds without raising.

⚠️ **Beware the control that never fires.** Today's `eeba4858` cost an afternoon because four "successes" were green for a reason unrelated to what they appeared to test — the branch was never evaluated. Pick fixtures where the guarded and unguarded paths genuinely **diverge**.

## 9. One-paragraph summary for a busy reader

`.dm-inbox-hwm-*.json` are per-session DM bookmarks that prevent peer DMs from being silently dropped. They are correct, deliberate, and gitignored. **Nothing deletes them** — 434 files, 1.8 MB, ~18/day, oldest 2026-07-02 — because the design bounded the ledger *inside* each file (`SURFACED_IDS_CAP = 500`) and never bounded the *number* of files. The janitor that would clean them already exists and already sweeps the same directories; it simply globs `.heartbeat-hold-*.json` and cannot see them. **Extend the glob, gate on the live-session set rather than age alone, and prove each guard by mutating it.**
