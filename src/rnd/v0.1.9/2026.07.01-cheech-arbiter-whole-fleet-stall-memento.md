## 2. THE LOAD-BEARING INVARIANT (do not regress)

**Facet 2 credits ONLY bridge(build) / dm / hold-refresh — it DELIBERATELY EXCLUDES
`commons_age_s`, `idle_prompt_age_s`, and `event_age_s`.**

This is the sharp catch Tiberius called out. Commons chatter is **liveness, not
progress** — the arbiter's own per-poll `who()` posts surface as commons activity,
so crediting commons would re-open the **chatty-but-stuck blind spot**: a LIVE fleet
posting "still blocked" while nothing builds MUST still stall. `dm_age_s` is read
from the always-present auditable column, so DM is credited regardless of the
`arbiter count dm as liveness` toggle (a sent DM is coordination work here).

**`compute_liveness`'s per-signal ages are datetime-derived: the view timestamp
fields (`dm_ts`, `commons_ts`, `last_event_ts`, `idle_prompt_ts`) are AWARE DATETIME
OBJECTS in production (parsed by `build_fleet_view` via `_parse_iso`), NOT ISO
strings.** `_event_age` does `(now - ts)` and returns None if `ts` is a string. My
RED tests initially passed ISO strings and silently got `dm_age_s=None` (no
suppression) — fixed by passing datetimes. Anyone writing fleet-view fixtures must
pass datetime objects for these fields.

And the reported scenario — {awaiting-user manager + 3 DMing builders, zero
task-transitions} → **NO stall** (correct).

### Known scoping note
`_fleet_progress_signature` raises `TypeError` (unsortable None vs str) if a dict
view LACKS `session_id` while another has one. Not hit in production (build_fleet_view
always sets session_id); I avoided depending on it — my Facet-1 filter guards
`isinstance(v, dict)` only and lets `_session_awaiting_user` handle a None sid
(it's None-safe via try/except). If a future test needs a sidless dict through
`_check_fleet_stall`, that pre-existing fragility must be fixed first.
