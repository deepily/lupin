## 0. COLD-START PLAYBOOK — zero to browser (read this first)

This is the whole path, in order, with no live debugging needed. Every command is a `lupin-vm.sh` subcommand
except the two GCP one-time steps. Commands assume `export LUPIN_GCP_PROJECT_ID=hello-world-foo-423219`.

### One-time, per laptop
```bash
scp <repo>/src/scripts/lupin-vm.sh ~/bin/lupin-vm.sh && chmod +x ~/bin/lupin-vm.sh   # non-dev laptops: no repo needed
gcloud auth login                                                                    # authenticate as yourself
export LUPIN_GCP_PROJECT_ID=hello-world-foo-423219                                    # add to ~/.zshrc / ~/.bashrc
lupin-vm.sh firewall open        # ONE-TIME per project: opens IAP 35.235.240.0/20 -> tcp:7999 on dev-vpc
```

### Every session
```bash
lupin-vm.sh vm-status            # STOPPED?  (VM is suspend-by-default)
lupin-vm.sh vm-start             # if not RUNNING
lupin-vm.sh svc up               # start app containers; wait ~30-60s for health
lupin-vm.sh svc status           # confirm lupin-rest-cloud-gpu = Up (healthy), 0.0.0.0:7999->7999
lupin-vm.sh tunnel 6999          # leave running
# browse  http://127.0.0.1:6999   (127.0.0.1, NOT localhost — see gotcha #5)
lupin-vm.sh vm-stop              # when done, to save cost
```

### First time against a fresh remote DB (your account isn't seeded there)
The VM's Cloud SQL instance (`lupin-pg16-test`) is a **separate database** from your local dev DB — your
login won't exist there yet. Create it once:
```bash
lupin-vm.sh run "sudo docker exec lupin-rest-cloud-gpu python3 -c \"from cosa.rest.user_service import create_user; print(create_user('you@email.com','YourPassword123!',['admin']))\""
```
Prints `(True, '<msg>', '<uuid>')` on success. Password must pass `validate_password_strength`.

| 3 | `no such service: lupin-rest-cloud-gpu` on `svc logs` | `docker compose` wants the **service** name (`lupin-rest`), not the `container_name` | Script uses `REST_SERVICE=lupin-rest`. Fixed in `350c49dc`. |
| 4 | `tunnel` → `ERROR 4003: failed to connect to backend (port 7999)` **while `svc status` shows healthy** | No VPC firewall rule allowing IAP `35.235.240.0/20` → tcp:7999 (SSH works because tcp:22 has one) | `lupin-vm.sh firewall open` (auto-derives network `dev-vpc`, creates `lupin-iap-7999`). | 5 | Tunnel binds (`Listening on port N`) but every browser hit → `OSError: [Errno 9] Bad file descriptor` on `('::1', …)` | macOS resolves `localhost` to IPv6 `::1` first; the IAP tunnel mishandles the `::1` local socket | Script binds `--local-host-port=127.0.0.1:PORT`. ## 3. The script — `src/scripts/lupin-vm.sh`

Single wrapper, subcommand-dispatched. All identity is env-overridable but fails loud on a missing project id
(mirrors `deploy-cloud-test.sh:115` — a silent project default can bill/act on the wrong project).

> **Prefer the `lupin-vm.sh` subcommand — do not hand-run these `gcloud` lines.** They are shown fully concrete
> below (nothing elided) so a copy still works, but a raw `gcloud compute ssh` needs the instance name
> `lupin-host-test` as its first positional arg or you get `argument [USER@]INSTANCE: Must be specified`. In the
> `svc …` rows, `<compose>` = `sudo docker compose -f docker-compose.cloud-gpu.yml --env-file cloud-gpu.env`.

| Subcommand | Action | Underlying call (fully concrete) |
|---|---|---|
| `vm-status` | Is the instance running/stopped? | `gcloud compute instances describe lupin-host-test --zone=us-central1-a --project=hello-world-foo-423219 --format='value(status)'` |
| `vm-start` | Start a stopped/suspended instance (needed before SSH) | `gcloud compute instances start lupin-host-test --zone=us-central1-a --project=hello-world-foo-423219` |
| `vm-stop` | Stop the instance (cost control) | `gcloud compute instances stop lupin-host-test --zone=us-central1-a --project=hello-world-foo-423219` |
| `shell` | Interactive SSH session | `gcloud compute ssh lupin-host-test --zone=us-central1-a --project=hello-world-foo-423219 --tunnel-through-iap` |
| `run "<cmd>"` | Run one remote command | `gcloud compute ssh lupin-host-test --zone=us-central1-a --project=hello-world-foo-423219 --tunnel-through-iap --command "<cmd>"` |
| `svc status` | `docker compose ps` in the app root | remote `<compose> ps` |
| `svc up` | Bring the app containers up | remote `<compose> up -d` |
| `svc down` | Stop the app containers | remote `<compose> down` |
| `svc restart` | Recreate the REST container | remote `<compose> up -d --force-recreate lupin-rest-cloud-gpu` |
| `svc logs` | Tail REST container logs | remote `<compose> logs -f --tail=200 lupin-rest-cloud-gpu` |
| `tunnel [PORT]` | Bind `localhost:PORT` → VM `:7999` (default `PORT=7999`) | `gcloud compute start-iap-tunnel lupin-host-test 7999 --local-host-port=localhost:PORT` |

### Tunnel usage
```
src/scripts/lupin-vm.sh tunnel          # localhost:7999  -> VM :7999
src/scripts/lupin-vm.sh tunnel 8799     # localhost:8799  -> VM :7999  (if 7999 is busy locally)
```
Leave it running in a terminal; open `http://localhost:7999` in the browser. Ctrl-C ends the tunnel.

### Typical session
```
src/scripts/lupin-vm.sh vm-status          # STOPPED?
src/scripts/lupin-vm.sh vm-start           # bring it up
src/scripts/lupin-vm.sh svc up             # start the app containers
src/scripts/lupin-vm.sh tunnel &           # forward :7999 locally
# ... work in the browser at http://localhost:7999 ...
src/scripts/lupin-vm.sh vm-stop            # done — stop to save cost
```

## 5a. Tunnel firewall (one-time) — required for `tunnel` to reach :7999

**Symptom**: `svc status` shows the app `Up (healthy) 0.0.0.0:7999->7999`, yet `tunnel` fails with
`ERROR 4003: failed to connect to backend (Failed to connect to port 7999)`.

**Cause**: IAP TCP forwarding to port 7999 needs a VPC firewall rule allowing the IAP source range
`35.235.240.0/20` → `tcp:7999`. SSH (`shell`/`run`/`--tunnel-through-iap`) works because `tcp:22` already
has such a rule; `7999` does not.

**Fix — one command, baked into the script** (network is auto-derived from the VM; no manual paste):
```bash
src/scripts/lupin-vm.sh firewall open        # creates rule 'lupin-iap-7999' on the VM's network (dev-vpc)
```
That expands to `gcloud compute firewall-rules create lupin-iap-7999 --network=<VM network> --direction=INGRESS
--action=ALLOW --rules=tcp:7999 --source-ranges=35.235.240.0/20`. The rule is **untagged** (applies to all
instances in the network) — safe, because the source range is only Google's IAP forwarders. To inspect
existing rules first: `src/scripts/lupin-vm.sh firewall status` (lists all rules; scan the `sourceRanges`
column — a server-side `--filter` on the `35.235.240.0/20` CIDR is an invalid list-filter expression, so we
list-and-eyeball instead).

No app/VM bounce needed — retry `lupin-vm.sh tunnel 6999` immediately after.

> **Note on `svc logs`/`svc restart`**: these use the compose **service** name `lupin-rest` (the
> `container_name` is `lupin-rest-cloud-gpu`). `docker compose logs <name>` wants the service, not the
> container — passing the container name returns `no such service`. Fixed in commit `350c49dc`.
