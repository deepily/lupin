# The tier-log off-by-one, and what `-s` did to it

**Date**: 2026-09-06 · **Author**: Tiffany 💍 (`b1d5ae8f`) · **Manager**: Mr. Radio 🦉
**Row**: `df7c183f` · **Status**: closed as **UNDETERMINED-WITH-A-REASON**
**Found while**: reconciling a tier log several rows had been quoting as a baseline denominator

---

## Verdict

A tier log at `5a9b9096` reported **one more outcome than its sha collects** — 22,321 against
22,320 — and its progress stream was a different shape from every reproduction: **121,975 lines
and zero `[ NN%]` markers**, against ~935 lines and ~315 markers everywhere else.

**Both halves now have a measured sufficient cause, and neither is established for that specific
log.** An untracked test file explains the `+1`; `-s` / `--capture=no` explains the shape. The one
fact that would promote either from *sufficient* to *established* — what the baseline was actually
invoked with, and what was sitting untracked in its tree — **is provably unrecoverable**, and the
reason it is unrecoverable is the finding worth keeping.

---

## 1. The measurement

Full unit tier, `src/tests/unit/`, plain `-q -s`, `LUPIN_ROOT` and `PYTHONPATH` both pinned,
redirected to a file (non-tty). Waited on **process exit** — pid 1866112 leaving `/proc` — never on
a log line, since a log line can be impersonated by any test that prints one.

| | lines | markers | outcomes |
|---|---|---|---|
| baseline @ `5a9b9096` | 121,975 | 0 | 22,321 (5F/22254P/52S/10X) |
| **`-s` arm @ `c0c95966`** | **119,856** | **0** | 22,885 (4F/22820P/51S/11D/10X), 781.58s, EXIT=1 |
| `-q` control @ `c0c95966` | 934 | 318 | 22,885 — **identical buckets** |

**The control is the outcome buckets.** The two arms at the same sha agree on all five, so they
differ in *output shape only*, not in what ran. Without that, a line-count difference could have
been a different test population rather than a different instrument.

⇒ The `-s` arm reproduces the baseline's shape **to within 1.7% on lines and exactly on markers**.

**Scope, travelling with the number**: different sha from the baseline, ~560 more outcomes, one
tree, one box, one moment (2026-09-06 15:36–15:49 EDT). Box verified QUIET before launch by the
*ownership* scan — zero pytest, zero UNKNOWN — not by a count. `cloud-run.env` `readable=yes
size_bytes=306 lines=6` through the link, so the flash-lite family contributes nothing. The four
failures are the known set at this sha; `test_dom_assert_lint` is fixed at `7f04c945`, which is
*after* `c0c95966`.

## 2. The mechanism is a documented property of this repo

`CLAUDE.md:184` — *"**Logging**: Currently uses print() statements rather than a logging
framework."* A codebase that logs by printing, run with capture off, empties its whole log stream
into the file. **`-s` does not add logging; it stops suppressing it.**

### 2a. I named the wrong cause first, and corrected it before it was acted on

Pointed at the documented import-time watcher
(`git show 4540c666:src/rnd/v0.2.0/2026.08.24-import-time-watcher-thread-poisons-stdout-tests.md`),
I reported it as the driver of the line inflation — **having read the log's HEAD and described the
LOG**. Measured across the whole log at 6,685 lines:

| bucket | lines | share |
|---|---|---|
| MCP structlog | 254 | 3.8% |
| `[busy-probe]` | 9 | — |
| `Session ID changed` — *the doc's own signature line* | **0** | — |
| other structlog | 101 | — |
| **everything else** | **6,322** | **94.6%** |

Sampled rather than assumed: config-manager banners, seeded users, heartbeat-arbiter JSON, XML
prompt fragments.

⇒ **The watcher explains a poisoned JSON parse. `print()`-as-logging explains 121,975 lines.** Two
real findings; only one is about this row. A true mechanism aimed at the wrong quantity is still a
wrong answer.

## 3. Volume is not linear in wall time — and this nearly produced the wrong verdict

| checkpoint | lines |
|---|---|
| 95 s | 4,504 |
| 209 s | 6,685 |
| 297 s | 113,758 |
| final | 119,856 |

A linear extrapolation off the **first** checkpoint predicts ~42,000 and would have made me report
`-s` as **insufficient** — the wrong verdict, in the confident direction. Mr. Radio's own ~50k
projection was wrong by more than 2× for the same reason, and he struck it. **The volume tracks
which tests run.**

⇒ **Do not extrapolate a log's size from a prefix of it**, and do not quote a figure from a run that
has not exited.

### 3a. This resolved an either/or I had written against myself and then walked past

An earlier amendment on the row said: *"Either these three subdirectories are unusually quiet, or
`-s` is not the whole story."* **They were unusually quiet** — the subset gave 4× and extrapolated
to ~4,000; the full tier gives ~120,000. I set the bound and did not connect its resolution; Mr.
Radio did.

⚠️ **One word narrower than the ruling this executes**: the full tier eliminates the **need** for a
further mechanism to explain the line count. It does **not** establish that no further mechanism was
present.

## 5. The one thing left is provably unrecoverable — and that is the durable finding

Whether the baseline **was** invoked with `-s`. Four sources swept read-only, each with its own
positive control:

| source | result | control |
|---|---|---|
| committed runners | 18 of 91 tracked `.sh` touch `tests/unit`; **none** passes `-s` or `--capture=no`. The only tree-wide `--capture=no` hit is a *docstring* in `test_hard_exit_names_itself.py` | 91 tracked `.sh` |
| stored invocation | `git grep sys.argv` and `git grep invocation_params` across the tree **both return empty**. Nothing in `src/` records pytest's own argv, anywhere | — |
| log header | the `[tree-state]` stamp records the **tree** and is silent about the **command** | — |
| the artifacts | baseline log and `det.sh` gone from disk | 929 files scanned |

⇒ **I do not claim the baseline was run with `-s`.** *"This shape is reachable under `-s`"* and
*"the baseline was invoked with `-s`"* are different claims, and only the second closes this on
identity. **A matching magnitude is the weakest form of identification.**

## 6. Two recommendations, one file, one cause — neither built

Both land on the `[tree-state]` stamp (`src/cosa/utils/tree_state.py :: _tree_state_line`, written
at `src/conftest.py:419`). Both are `.py` changes and therefore **Krishna's lane under `73ebccb1`**,
not the author's to write.

1. **`untracked=N`** — `tracked-dirty` is built from `git status --porcelain` with the `??` rows
   already removed, so `tracked-dirty=0` is silent about untracked files *by construction*. A run's
   collected count can move without a single field in the header changing.
2. **The invocation** — the stamp already carries `sha`, `root`, `branch`, `behind`, `ahead`,
   `fetched`, `tracked-dirty`, `dirty-paths`, `run-span`: every coordinate for **which tree** was
   measured and none for **how**.

**Why the second is the right place rather than a preference**, and this is the part that closes the
loop: `src/conftest.py`'s terminal-summary hook already records network mode, coverage file, tree
state and import origin — and its own comment says why the *network* field was added. *A unit tier
reported 5 errors that a baseline on the same code did not, and the whole of the difference was that
one run exported `LUPIN_UNIT_NETWORK` and the other did not. Nothing in either result named the
variable that decided it, so the gap read as a code change.*

⇒ **That is this row, one field over.** The stamp learned to name the ENVIRONMENT that shaped a run
and still does not name the COMMAND.

⚠️ **For whoever builds it**: a captured command line can carry secrets — env-bearing invocations,
`-k` expressions naming credentials. Decide what is recorded before recording it.

⚠️ **What this does not claim**: that either field would have closed *this* row retroactively. It
makes the **next** such row closable and does nothing for a run already logged.

---

## 7. Why this closes rather than parks

Parking implies someone can come back and finish it. **Nobody can** — the invocation was never
written down and the artifacts are gone. Saying that plainly, with the four sweeps that establish
it, is a more useful artifact than an open row nobody can action.

**What is genuinely still unknown, stated so it cannot be quoted away**: whether an untracked file
was in fact present at 18:55 EDT, and what the baseline's actual flags were. Both are unrecoverable
for the same reason — and the one field that would have shown the first is the field that filters
it out.
