## Context

Session 167 uncovered a **delete-all-records bug** during Part 3 Test 4 of the CRUD testing protocol. When a user adds "buy milk" twice (via repeated curl POSTs) then says "delete milk from my grocery list," the system deletes **all** matching rows instead of 1. Root cause: no deduplication guard on inserts + no multi-delete guard on deletes. A detailed plan was created at `~/.claude/plans/cached-growing-mist.md`.

**This session**: Implement the 5-change bug fix, add 6 unit tests, then create a `test_crud_live_pipeline.py` following the calculator pattern (replaces Part 3 curl tests).

## Part A: Bug Fix (Steps 1-5)

### Step 1: Add dedup keys to `schemas.py`

**File**: `src/cosa/crud_for_dataframes/schemas.py`

Add `DEDUP_KEYS` dict and `INFRASTRUCTURE_COLS` set after `COMMON_COLUMNS` (line ~19), plus `get_dedup_keys()` helper after existing helpers.

```python
DEDUP_KEYS = {
    "todo"     : [ "todo_item" ],
    "calendar" : [ "event", "start_date" ],
    "generic"  : [ "name" ],
}

INFRASTRUCTURE_COLS = { "id", "list_name", "created_at" }

def get_dedup_keys( schema_type ):
    return DEDUP_KEYS.get( schema_type, [] )
```

## Part B: Unit Tests (Step 6)

### Step 6: Add 6 new unit tests

**File**: `src/tests/unit/test_crud_for_dataframes_storage.py` (after line ~887)

New test class `TestDeduplicationGuards`:

1. `test_add_duplicate_rejected` — add "buy milk" twice → second returns "duplicate"
2. `test_add_same_item_different_list_allowed` — add to two lists → both succeed
3. `test_match_fields_rejects_list_name` — delete with `{"list_name": "groceries"}` → error
4. `test_match_fields_rejects_id` — delete with `{"id": "abc"}` → error
5. `test_multi_delete_guard_refuses_broad_match` — 2 items same priority, delete by priority → error
6. `test_single_delete_by_match_fields_succeeds` — 2 different items, delete by exact match → 1 deleted

**Structure**:

- `_get_websocket_session_id()` — `GET /api/debug/websocket-state`

- `_check_answer()` — keyword validation in response
- `_print_results_table()` — tabular summary
- `quick_smoke_test()` — orchestrator with `-q` argparse for selective scenarios

### Confirmation Handling

Scenario 4 (DELETE_TODO) triggers a yes/no notification card. Two outcomes:
- **User clicks Yes in browser** → "deleted" / "Done" in response → PASS
- **Timeout (30s, no one clicks)** → "cancelled" in response → PASS (safe default verified)

Both outcomes are valid PASS conditions — `expected_keywords` includes both `"deleted"` and `"cancelled"`. The script reports which outcome occurred.

### Sequential Ordering

Tests 0-5 MUST run in order (add → add → query → duplicate → delete → calendar). Tests 6-7 (LORA) are independent but benefit from data added by 0-1.
