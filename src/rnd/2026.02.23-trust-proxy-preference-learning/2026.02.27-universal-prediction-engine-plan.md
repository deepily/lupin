# Universal Decision Proxy: Multi-Response-Type Prediction Engine

**Status**: PREDICTION ENGINE CODE COMPLETE — PENDING UI HINT RENDERING + LIVE E2E VALIDATION
**Date**: 2026-02-27
**Context**: Extending the trust proxy system to handle all notification response types with prediction hints, accuracy tracking, and progressive learning

---

## Context: Why This Change

The user sees dozens of `response_requested` notifications daily from Claude Code / cosa-voice MCP interactions. Each is a training example going uncollected. The existing decision proxy only handles binary yes/no for hypothetical SWE team overnight jobs. The real, immediate need is a prediction engine that:

1. Shows prediction hints for ALL notification response types
2. Tracks every human response alongside what the proxy predicted
3. Measures accuracy over time, building toward autonomous responses
4. Starts collecting data from day 1 (shadow mode)

The SWE team decision proxy becomes a future consumer of this same engine.

---

## Architecture Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Notification proxy fate | Keep as-is, rename later | Dumb/fast auto-responder for smoke tests stays separate from intelligent proxy |
| Priority focus | Daily notification workflow first | 30+ organic training examples/day vs hypothetical SWE team jobs |
| "Whether vs How" | Partition maintained | Trust engine = whether to respond (type-agnostic); Strategy = how to respond (type-specific) |
| Prediction location | Server-side, in-process | Computed before WebSocket push; library call in FastAPI, not separate agent |
| Embedding producer | Singleton at FastAPI boot | Shared via `app.state`, GPU in-process; CPU fallback for external scripts |
| Category model | Hybrid: 6 fixed + uncategorized | Permission, Confirmation, Approach, Input, Workflow, Meta + catch-all |
| Storage | NEW `prediction_log` table | Clean schema; existing `proxy_decisions` unchanged |
| Implementation model | **Vertical slices by response type** | Full stack per type (predict + UI hint + track), simplest first |

## Response Type Taxonomy (Complete)

| Type | Variant | Response Format (JSONB) | Prediction Method |
|------|---------|------------------------|-------------------|
| `yes_no` | Simple | `{"value": "yes", "source": "ui"}` | CBR majority vote |
| `yes_no` | Qualified | `{"value": "yes [comment: ...]", "source": "ui"}` | Binary vote + comment retrieval |
| `multiple_choice` | Exclusive (single) | `{"answers": {"Header": "OptionA"}}` | Option embedding scoring |
| `multiple_choice` | Inclusive (multi) | `{"answers": {"Header": ["A", "B"]}}` | Per-option independent scoring |
| `multiple_choice` | With "Other" | `{"answers": {"Header": "Custom text"}}` | Option scoring + Other detection |
| `open_ended` | Simple | `{"value": "text", "source": "ui"}` | CBR retrieval → LLM generation |
| `open_ended_batch` | Compound | `{"answers": {"H1": "t1", "H2": "t2"}}` | N independent open_ended |

### Slice 4: open_ended — IMPLEMENTED

**Two-tier prediction** (retrieval + LLM synthesis):
- `_predict_open_ended()` — 3 cold-start guards (no embedding engine, no cases, insufficient cases), then Tier 1: exact normalized question match → `STRATEGY_CBR_RETRIEVAL`; Tier 2: top K similar cases → Phi-4 LLM synthesis → `STRATEGY_LLM_SYNTHESIS`
- `_build_synthesis_prompt()` — Loads template from `prediction-engine-open-ended-synthesis.txt`, injects `{{PYDANTIC_XML_EXAMPLE}}` via `OpenEndedSynthesisResponse.get_example_for_template()`
- `_get_llm_client()` — Lazy-loads via `LlmClientFactory` with caching (single instance reused)
- `compare_open_ended()` — Upgraded from exact match to embedding cosine similarity (threshold 0.85) with exact-match fallback
- `_cosine_similarity()` — Static helper: L2-normalized numpy dot product
- `_enrich_with_embedding_similarity()` — Injects transient `_embedding_similarity` key into `actual_dict`, stripped before DB write by `record_outcome()`
- Fallback hierarchy: exact match → similar cases → LLM synthesis → cold start

**Plan doc**: `src/rnd/2026.02.23-trust-proxy-preference-learning/2026.03.02-slices-4-5-open-ended-prediction.md`

### Slice 5: open_ended_batch — IMPLEMENTED

**Same two-tier approach** as Slice 4, adapted for compound multi-header answers:
- `_predict_open_ended_batch()` — JSON-formatted `{"answers": {...}}` retrieval + synthesis, same cold-start guards as Slice 4
- `compare_open_ended_batch()` — Per-header embedding similarity with average threshold (0.85)
- Per-header enrichment via `_enrich_with_embedding_similarity()`
- `_parse_batch_decision_value()` — JSON parser for compound batch decision values

**Plan doc**: `src/rnd/2026.02.23-trust-proxy-preference-learning/2026.03.02-slices-4-5-open-ended-prediction.md`

## Prediction Hint UI Rendering (Slice 6)

**Status**: NOT STARTED — Prerequisite for live E2E validation

### The Gap

The prediction engine computes predictions server-side and attaches them as `prediction_hint`
on `NotificationItem` (serialized via `to_dict()`). The WebSocket delivers this to the browser.
But `notifications.js` → `createActionRequiredCard()` never reads `notification.prediction_hint`.

### Current Card Layout

```
┌─ Header (cancel, title, timer) ─┐
│ Message                          │
│ Abstract (if present)            │
│ Progress bar                     │
│ Response UI (buttons/inputs)     │
└──────────────────────────────────┘
```

### Proposed Card Layout (with prediction hint)

```
┌─ Header (cancel, title, timer) ─┐
│ Message                          │
│ Abstract (if present)            │
│ ┌── Prediction Hint ──────────┐  │
│ │ Predicted: Yes (85%)        │  │
│ │ Strategy: cbr_majority_vote │  │
│ │ Based on 12 similar cases   │  │
│ └─────────────────────────────┘  │
│ Progress bar                     │
│ Response UI (buttons/inputs)     │
└──────────────────────────────────┘
```

### Rendering by Response Type

- **yes_no**: Explicit text label — "Predicted: Yes (85%)" as a separate line above buttons. No button highlighting.
- **yes_no qualified**: "Predicted: Yes — 'only the unit tests' (85%)" as text label
- **multiple_choice (single)**: Text label "Predicted: OptionA (85%)" above options. No pre-selection.
- **multiple_choice (multi)**: Text label "Predicted: [A, B] (85%)" above options. No pre-selection.
- **open_ended**: Predicted text shown in a collapsible hint box above the input
- **open_ended_batch**: Per-header predicted text in collapsible hints above each input
- **cold_start (no prediction)**: No hint section rendered (graceful absence)

### Implementation Details

**Files to modify**:
- `src/fastapi_app/static/js/notifications.js` — `createActionRequiredCard()` reads
  `notification.prediction_hint` and injects hint section between abstract and progress bar
- `src/fastapi_app/static/css/notifications.css` — `.prediction-hint` styling
  (muted background, small font, collapsible)

**prediction_hint structure** (from PredictionResult.to_dict()):
```json
{
    "predicted_value": "yes",
    "confidence": 0.85,
    "strategy": "cbr_majority_vote",
    "similar_case_count": 12,
    "category": "permission"
}
```

**UX considerations**:
- Hint should be visually distinct but not dominant (muted colors, smaller font)
- Should not bias the user's response — informational, not directive
- Collapsible by default after first few days (configurable)
- For yes_no: subtle text label on predicted answer (not auto-select)
- For open_ended: show as placeholder or collapsed "suggestion" box

## Key Components Detail

### prediction_log Table Schema

```sql
CREATE TABLE IF NOT EXISTS prediction_log (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    notification_id       UUID NOT NULL REFERENCES notifications(id) ON DELETE CASCADE,
    response_type         VARCHAR(50) NOT NULL,
    category              VARCHAR(100) NOT NULL,
    predicted_value       JSONB,
    prediction_confidence FLOAT NOT NULL DEFAULT 0.0,
    prediction_strategy   VARCHAR(50) NOT NULL,
    similar_case_count    INTEGER NOT NULL DEFAULT 0,
    actual_value          JSONB,
    accuracy_match        BOOLEAN,
    accuracy_detail       JSONB,
    predicted_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    responded_at          TIMESTAMPTZ,
    sender_id             VARCHAR(255)
);
```

### PredictionEngine Singleton

Thread-safe singleton with `predict()` dispatch by response type, `record_outcome()` for logging, `get_accuracy_summary()` for dashboard stats.

### NotificationCategoryClassifier

6 fixed keyword categories (Permission, Confirmation, Approach, Input, Workflow, Meta) + uncategorized catch-all.

## Progressive Learning Timeline

```
Days 1-3:   Cold start. All predictions null. Pure data collection.
Days 3-7:   yes_no hints appear for repetitive permission/workflow questions.
Days 7-14:  multiple_choice hints appear where past options overlap.
Days 14-30: open_ended shows "last time you said X" for very similar questions.
Day 30+:    Enough data to consider selective auto-response.
```
