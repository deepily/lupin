# Gist Embeddings in Lupin: Keep vs. Jettison

**Date**: 2026-02-09
**Session**: 155
**Status**: Research Document (No Code Changes)
**Decision**: Pending user review

---

## Context

This document analyzes whether the gist embedding system is pulling its weight in the Lupin/CoSA retrieval pipeline. After tracing every usage of gist generation and gist embeddings across the repo, the answer is clear: **the gist _text_ has value; the gist _embeddings_ are almost entirely dead code.**

---

## How the System Works (Three-Layer Architecture)

Each incoming question produces three representations:

| Layer | Example | Source |
|-------|---------|--------|
| **Verbatim** | "Um, so like, what's the weather in SF?" | Raw user input |
| **Normalized** | "weather san francisco" | `Normalizer` (spaCy - removes filler, expands contractions, lemmatizes) |
| **Gist** | "weather inquiry san francisco" | `Gister` (LLM call to Phi-4 14B) or `Normalizer` fallback |

Each layer then gets an OpenAI embedding (1536-dim `text-embedding-3-small`). Per snapshot, **7 embeddings** are stored: question, question_normalized, **question_gist**, solution, code, thoughts, **solution_gist**.

## The Retrieval Pipeline (4-Level Hierarchical Search)

`lancedb_solution_manager.py:1241-1373`

| Level | What it does | Uses gist text? | Uses gist embedding? |
|-------|-------------|:---:|:---:|
| 1. Exact verbatim | `CanonicalSynonymsTable.find_exact_verbatim()` | No | No |
| 2. Exact normalized | `CanonicalSynonymsTable.find_exact_normalized()` | No | No |
| 3. Exact gist | `CanonicalSynonymsTable.find_exact_gist()` | **Yes** | No |
| 4. Vector similarity | `LanceDB .search(question_embedding)` | No | **No** |

**The smoking gun is line 1317:**
```python
search_results = self._table.search(
    query_embedding,
    vector_column_name="question_embedding"  # <-- NOT question_gist_embedding
)
```

Level 4 searches on `question_embedding`, never on `question_gist_embedding`. The `threshold_gist` parameter (line 1177) is accepted but never applied anywhere in the LanceDB manager.

## Cost of Keeping Gist Embeddings

### Per New Snapshot (at creation time)
- 2 extra OpenAI API calls: `question_gist_embedding` + `solution_gist_embedding`
- ~$0.00004 per snapshot (negligible monetary cost)
- ~200-400ms latency per snapshot creation
- 12,288 bytes storage overhead (2 x 1536 x float32)

### Per Incoming Query (at search time)
- 1 extra OpenAI API call for gist embedding (~100ms) - used for **logging only**
- If gisting enabled: 1 Phi-4 14B LLM call (~500ms per cache miss) - **currently disabled**

### Cognitive/Maintenance Cost
- 7 embedding fields to understand instead of 5
- `threshold_gist` parameter that does nothing
- `get_snapshots_by_solution_gist_similarity()` that's never called
- Confusion about what's active vs. dead

---

## Pros and Cons of Jettisoning

### Pros (Remove gist embeddings)
1. **Eliminates dead code** - ~200 lines of never-executed search/comparison logic
2. **Reduces per-query cost** - 1 fewer OpenAI API call per query
3. **Reduces per-snapshot cost** - 2 fewer OpenAI API calls per snapshot creation
4. **Simplifies the schema** - 5 embedding columns instead of 7
5. **Reduces LanceDB storage** - ~12KB per snapshot
6. **Removes misleading parameters** - `threshold_gist` suggests it's used
7. **Clearer architecture** - easier to reason about what's actually searched

### Cons (Keep gist embeddings)
1. **Future optionality** - could enable gist-based vector search later
2. **Analytics value** - gist embeddings in query logs could support future analysis
3. **Migration effort** - removing columns from existing LanceDB tables requires care
4. **Low monetary cost** - the OpenAI API cost is genuinely tiny

---

## Recommendation

**Phase 1 (Low-risk, immediate):** Remove the dead code paths - the unused search methods, the `threshold_gist` parameter plumbing, and the per-query gist embedding generation (or make it conditional on a config flag for logging). Keep the gist _text_ generation and Level 3 matching intact.

**Phase 2 (If desired):** Stop generating `question_gist_embedding` and `solution_gist_embedding` during snapshot creation. Keep the columns in the schema (nullable/empty) to avoid migration headaches.

**Phase 3 (Optional, future):** If you ever want gist-based vector search, re-enable it intentionally with proper Level 4 integration (search on `question_gist_embedding` column with its own threshold). The current code cross-compares gist embedding against question embedding in the deprecated manager (line 374) which is semantically wrong anyway.
