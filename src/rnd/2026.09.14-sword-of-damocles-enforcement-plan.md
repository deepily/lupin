## 3. Design

### 3.1 The switch

Reuse the approval-settings pattern exactly; no new endpoint.

| Item | Value |
|---|---|
| Setting key | `sword_of_damocles_active` (added to `WRITABLE_KEYS`, `_BOOLEAN_KEYS`, `_VALIDATORS`, `current_settings`) |
| INI key | `task approval sword of damocles active = True` in `[Lupin: Baseline]`, beside its sibling approval keys; Production and Development both inherit Baseline |
| Code fallback (key missing) | `False`, matching `FALLBACK_ENFORCEMENT_ACTIVE`. An unparseable override falls through to the INI, as the other booleans do |
| Reader | `get_sword_of_damocles_active()` |
| How Rick flips it | `PATCH /api/tasks/approval-settings {"sword_of_damocles_active": false}`. Lands on the next request, no bounce. `GET` shows value and source |

### 3.2 The request door

`RequestFileIn` gains `deletion_task_id: Optional[uuid.UUID] = None`. The MCP `task_request` verb gains the same optional parameter.

New pure function `task_request_lifecycle.refusal_for_pledge( move, switch_on, pledge, target_id, requester_persona, pledged_elsewhere )`, called after `manager_refusal` (so a non-manager learns nothing about other rows), before `refusal_for_refiling`:

| # | Case | Answer |
|---|---|---|
| 1 | `move=admit`, switch on, no `deletion_task_id` | **422** — names the rule and the setting, and says how to file |
| 2 | `move=demote` with a `deletion_task_id` | **422** — a demote asks for nothing, so there is nothing to pay (see Q3) |
| 3 | pledge id = the target row | **422** — a row cannot pay for itself |
| 4 | pledge row does not exist | **422** naming the id (404 is reserved for the target row) |
| 5 | pledge `owner_persona` ≠ requester's persona | **403** — "it better be yours" |
| 5a | the session bridge resolves **no persona** for the actor's session id | **403** naming it — never falls back to the typed actor string (María, 22:41; that string is row `b8205986`'s hole) |
| 6 | pledge is `done` or `dropped` | **409** — a finished row is a close, not a deletion (v0.2 ruling 1) |
| 7 | pledge already named on another row's **pending** admit request | **409** naming that row — one pledge per admit |
| 8 | switch **off**, admit with a pledge | accepted and honoured, same checks 3–7. Off means "not required", not "ignored" — a field ignored in silence is the failure this module's settings docstrings warn about |

**Requester persona**: resolved by the session bridge from the session id in `actor`, the same source the manager check reads — **never the typed persona name** (María asked, 22:40). ⚠️ Not yet read: which bridge helper returns the persona; step 4 finds it, and if none does, Mr. Radio hears that before anything weaker is used.

**Locking**: lock both rows with `get_by_id_for_update` in UUID order, so two crossing requests cannot deadlock.

### 3.3 Storage

New nullable column `request_deletion_id UUID` on `task_items`, plus a check constraint `request_deletion_id IS NULL OR request_move = 'admit'`, and a migration pinned the way `test_task_request_columns_migration.py` pins the existing three. `apply_request_filing` takes `deletion_id` and names it in the `request_filed` event reason. Serialized item carries it, so Rick's card and `task_get` show it.

Rejected: keeping the pledge only in the event text. The verdict would have to parse an audit string to find the row it drops.

## 4. Open questions for Rick, each with a recommendation

### Q1. Keep the peer-manager agreement? — **Recommend: drop it**

| | |
|---|---|
| For dropping | "It better be yours" removes the reason it existed: v0.2 let a manager offer a peer's row, so the peer had to agree. Owner-only pledges leave nothing for the peer to protect. It also cannot be checked by a door — a DM thread id is free text — and the friction log shows it was the slowest human step apart from Rick himself |
| Against | Loses a second pair of eyes on whether the pledge is an honest one rather than a freebie |
| Mitigation | Rick still sees the pledged row's title on the card and can deny |

### Q2. What happens to the pledged row on approve and on deny? — **Recommend: approve drops it in the same transaction; deny leaves it alone**

| Verdict | Recommended behaviour |
|---|---|
| **approved** | The admit and the drop happen together, under both row locks, through `_apply_transition_under_lock` for each. The drop's reason names the admitted row and Rick's verdict; its actor is Rick's recorded identity. If either transition is refused, both roll back and the request stays pending |
| **approved, but the pledge is no longer live** (closed or dropped since filing) | Refuse **409**, naming the pledge. The request stays pending. The requester re-files with a new pledge — which means `refusal_for_refiling` must allow a re-file over a pending admit whose pledge is no longer live, by the same requester. Otherwise the request is stuck |
| **denied** | Nothing moves, pledge included. Rick 2026-09-10: "No means take no action whatsoever." The pledge is freed for another request |
| **switch turned off between filing and verdict** | The pledge is still paid. The switch governs what a request must carry, not what a request already offered |

Alternative (not recommended): approve admits and leaves the drop as a second click. That is what the trial did, and it let the promote land without the drop (row `ab8c5728`, amendment 22:51 EDT 2026-09-10: the promote of `1657a852` had landed, the drop of `b52b430b` was "not yet confirmed").

Supersedes v0.2 ruling 2 ("promote stands if the deletion is refused"): with one verdict there is no separate refusal of the deletion. Rick denies the whole request and the manager re-files.

### Q3. Is demote exempt? — **Recommend: yes**

A demote moves a row **off** the board into the holding area; it adds nothing Rick has to fund. Charging for it would discourage exactly the tidying the rule wants. A pledge on a demote is refused 422 rather than ignored (case 2).
