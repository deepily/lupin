### 2025.10.11 (Session 1) - JWT Token Expiration Bug Fix & Auto-Refresh Implementation

**🐛 CRITICAL FIX**: TTS playback 401 errors after >1 hour idle completely resolved

#### Bug Discovery & Root Cause Analysis
- **Symptom**: TTS audio playback fails with 401 errors after browser idle >1 hour
- **Investigation**: Traced through WebSocket → notification → TTS audio playback flow
- **Root Cause**: JWT tokens expire (30 min) but no refresh mechanism before TTS `/api/speech/audio/` requests
- **Impact**: High-priority notifications fail to play after idle periods

#### Complete Fix Implementation
1. **Auto-Refresh on 401** (`queue-fresh.js`):
   ```javascript
   async playAudio( audioUrl ) {
       const fullUrl = `${window.location.origin}${audioUrl}`;
       const headers = { "Authorization": `Bearer ${this.authToken}` };

       let response = await fetch( fullUrl, { headers } );

       // Auto-refresh on 401 and retry once
       if ( response.status === 401 ) {
           await this.ensureValidToken();
           headers["Authorization"] = `Bearer ${this.authToken}`;
           response = await fetch( fullUrl, { headers } );
       }
   }
   ```

2. **Comprehensive Testing**:
   - **Manual validation**: Simulated 401 by modifying token, confirmed auto-refresh works
   - **WebSocket flow**: Verified notification → audio playback → token refresh → retry
   - **Edge cases**: Tested refresh failure handling (fallback to login)

#### Technical Details
- **Token lifecycle**: 30-min access token, 7-day refresh token
- **Retry logic**: Single retry after refresh (prevents infinite loops)
- **Error handling**: Graceful degradation if refresh fails
- **User experience**: Seamless - no visible interruption

- **Approach**: Created Q&A document capturing conceptual understanding vs. implementation

#### Document Contents (`2025.10.10-sse-conceptual-qa.md`)
1. **Async vs Sync SSE Patterns**:
   - Async generator approach: `async def event_stream()` with `yield` - idiomatic FastAPI
   - Sync with queue: `queue.Queue()` + background thread - when dealing with sync code
   - Hybrid: `asyncio.Queue()` + `asyncio.run_in_executor()` - bridges both worlds

2. **Production Strategies**:
   - Redis pub/sub for multi-worker deployments
   - Message queue integration (RabbitMQ, Kafka)
   - Database polling with change detection (simple but less efficient)

3. **Key Insights**:
   - SSE naturally async - matches FastAPI's async model perfectly
   - Generator pattern (`yield`) is the idiomatic approach
   - Background tasks should use `asyncio.create_task()` not threads
   - WebSocket may be better for bidirectional needs

4. **Recommendations**:
   - Use async generators for new SSE implementations
   - Avoid threading unless interfacing with legacy sync code
   - Consider WebSocket for complex real-time interactions
   - Redis pub/sub for production multi-worker setups

**Decision**: Document serves as reference guide for future SSE work. No immediate implementation - we have working WebSocket infrastructure that meets current needs.

### 2025.10.09 (Session 1) - SSE Progress Updates Research & Initial Implementation

**🔬 EXPLORATION**: Server-Sent Events (SSE) as lightweight alternative to WebSocket for one-way progress updates

#### Motivation & Context
- **Current limitation**: WebSocket overkill for simple progress updates (e.g., long-running batch operations)
- **User request**: Research SSE for admin operations like "re-index all snapshots" with real-time progress
- **Goal**: Add SSE alongside existing WebSocket infrastructure (not replacement)

#### Research & Learning
- **What is SSE**: Unidirectional server→client push over HTTP, built into browsers via `EventSource` API
- **Comparison to WebSocket**:
  - SSE: Simpler, HTTP-based, automatic reconnection, one-way only
  - WebSocket: Bidirectional, lower latency, more complex setup
  - **Decision**: Use SSE for progress updates, keep WebSocket for interactive features

#### Initial Implementation
1. **Backend** (`cosa/rest/routers/sse_demo.py`):
   - Created `/api/sse/progress` endpoint using `StreamingResponse`
   - Async generator pattern with `text/event-stream` content type
   - Test endpoint with simulated 10-second progress (0-100%)
   - Proper SSE formatting: `data: {json}\n\n`

2. **Frontend** (`static/sse-demo.html`):
   - `EventSource` API connection to `/api/sse/progress`
   - Real-time progress bar updates
   - Event listener pattern: `source.onmessage = (event) => {...}`
   - Clean error handling and connection management

3. **Testing**:
   - Manual browser test successful
   - Progress updates smooth and real-time
   - Automatic reconnection verified (server restart test)

#### Technical Details
- **SSE Format**: `data: {"progress": 50, "message": "Processing..."}\n\n`
- **Content-Type**: `text/event-stream`
- **Connection**: Persistent HTTP connection with chunked transfer
- **Browser Support**: Native `EventSource` API (all modern browsers)
